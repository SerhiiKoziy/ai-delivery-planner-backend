Частина I · Чому агент вигадує

1 Звідки беруться галюцинації в коді

Модель завжди видає найправдоподібніше продовження. Якщо правильної відповіді немає в контексті, правдоподібне продовження — це вигадка, яка виглядає як справжній код.

Коли агент пише from app.services.routes import optimize_route, а такого модуля немає, це не «баг моделі». Це передбачуваний наслідок: у навчальних даних тисячі FastAPI-проєктів з services/routes.py, а наш реальний код лежить у app/services/route_optimizer/service.py і агент його ще не відкривав. Галюцинації майже завжди мають одну з п'яти причин:

Контекстне вікно — це бюджет

Усе, що агент «знає» про вашу задачу в конкретний момент, лежить в одному контекстному вікні. Туди потрапляє не лише ваш промпт: системні інструкції інструмента, описи всіх підключених інструментів і MCP-серверів, файли пам'яті, уся історія розмови, кожен прочитаний файл і кожен вивід команди. Чим більше там сміття, тим гірше модель «бачить» важливе — навіть якщо до ліміту ще далеко. Це явище називають context rot: якість відповідей падає задовго до того, як вікно заповниться.

Аналогія для фронтендера
Контекстне вікно — як бюджет бандла на першому завантаженні. Ліміт формально великий, але кожна зайва бібліотека «в головному чанку» погіршує метрики, навіть якщо сайт ще вантажиться. Рішення ті самі: тримати в «головному чанку» (файл пам'яті) мінімум, решту підвантажувати ліниво (документацію за посиланням, вкладені файли модулів), а важкі задачі виносити в окремий «воркер» (субагент), який повертає лише результат.

2 П'ять шарів контексту

Не все треба «запихати» в промпт. Добрий контекст розкладений по шарах: що завжди в пам'яті, що підтягується за потреби, а що агент дізнається сам через інструменти.

1. Постійна пам'ять завжди

CLAUDE.md (Claude Code), AGENTS.md (Codex, Cursor та інші), .cursor/rules/*.mdc. Вантажиться в кожну сесію, тому має бути коротким: команди, архітектурні межі, пастки.

2. Документи на вимогу за потреби

docs/, ADR, згадки @app/services/route_optimizer/solver.py, вкладені CLAUDE.md у підпапках модулів. Агент читає їх, коли працює саме з цією частиною коду.

3. Grounding через інструменти завжди

Агент сам читає код, шукає grep-ом, запускає pytest, ruff, tsc. Це найнадійніше джерело правди: код не бреше про те, яка сигнатура в функції.

4. Актуальна зовнішня документація за потреби

Context7 MCP, llms.txt бібліотек, вихідний код встановленого пакета в .venv / node_modules, точні версії залежностей.

5. Специфікація задачі кожна задача

Мета, файли, обмеження, критерії приймання, команда перевірки, що не робити. Це єдиний шар, який ви пишете щоразу заново.

Типова помилка — намагатися вирішити все першим шаром: «запишу в CLAUDE.md усю архітектуру, всі ендпоінти й всі правила». Файл роздувається до сотень рядків, з'їдає бюджет у кожній сесії, а половина інформації застаріває через місяць. Правило: що агент може дізнатися сам через інструменти (шар 3) — не пишіть у пам'ять. Структуру папок він побачить ls, сигнатуру функції — прочитавши файл. У пам'ять ідуть лише речі, які не видно з коду: як запускати, чого не робити, які неочевидні домовленості.

🧭
Перевірка «а чи це видно з коду?» Перед тим як додати рядок у файл пам'яті, спитайте: чи міг би новий розробник дізнатися це за 2 хвилини, відкривши репозиторій? Якщо так — рядок зайвий. «Шари: api → services → repositories» видно з дерева папок, але «у api/ не можна імпортувати репозиторії напряму, лише через сервіси» — вже домовленість, і її варто записати.

Що класти в пам'ять, а що ні

✅ Класти

  • Команди: як запустити тести, лінтер, міграції, dev-сервер
  • Архітектурні межі й заборони («не імпортувати репозиторії в api/»)
  • Неочевидні пастки (bcrypt<4.0 закріплений не випадково)
  • Конвенції, які лінтер не ловить (назви, формат помилок API)
  • «Уроки»: помилки, які агент уже робив і не має повторювати
  • Посилання на документи шару 2 замість їхнього вмісту

❌ Не класти

  • Дерево папок і список усіх файлів
  • Опис кожного ендпоінта (є /openapi.json)
  • Загальні поради («пиши чистий код», «використовуй типи»)
  • Те, що ловить ruff / eslint / tsc
  • Секрети, токени, URL продакшн-бази
  • Історію проєкту й плани на квартал

CLAUDE.md (добре)
# AI Delivery Planner — backend

## Commands
- Tests: `.venv/bin/pytest app/tests -q`
- One test: `.venv/bin/pytest app/tests/test_ai_quota.py -k name`
- Lint: `.venv/bin/ruff check . && .venv/bin/ruff format --check .`
- New migration: `alembic revision --autogenerate -m "..."`

## Architecture rules
- Layers: app/api → app/services → app/repositories.
  api/ never imports repositories or models directly.
- Every query is tenant-scoped: use TenantScopedRepository
  (app/repositories/base.py), never raw select() in services.
- OpenAI calls only via app/services/ai/client.py
  (create_structured_completion, strict JSON schema).

## Gotchas
- Deps in pyproject are unpinned: check installed versions
  with `.venv/bin/pip list` before using a library API.
- bcrypt<4.0 is pinned on purpose (passlib compatibility).
- OR-Tools solve is CPU-bound and sync: do not call it
  directly inside an async endpoint.

## Lessons learned
- Do not edit applied Alembic migrations; add a new one.

Ліва версія займає багато токенів і майже нічого не дає: дерево агент побачить сам, ендпоінти є в OpenAPI, а поради «пиши чистий код» не змінюють поведінку моделі. Права версія — ~30 рядків, і кожен з них запобігає конкретній помилці: неправильній команді тестів, витоку даних між організаціями, виклику OpenAI в обхід обгортки, використанню API не тієї версії.

🔁
Секція «Lessons learned» — найцінніша. Щоразу, коли агент робить помилку, яку ви виправили вручну (редагує застосовану міграцію, кличе солвер з async-коду, забуває organization_id), додайте один рядок. Через місяць файл містить саме ті пастки, на які агент реально наступає у вашому проєкті. Можна просто сказати агенту: «додай у CLAUDE.md правило, щоб ти більше так не робив».

Вкладені файли по модулях

Знання, потрібні лише в одній частині коду, виносьте у вкладений файл поруч із нею. Claude Code підтягує CLAUDE.md з підпапки, коли агент починає працювати з файлами в ній, тож деталі OR-Tools не витрачають бюджет під час роботи над авторизацією.

app/services/route_optimizer/CLAUDE.md
# Route optimizer (OR-Tools)

- Pipeline: builder.py (RoutingProblem) → solver.py (RouteSolver)
  → mapper.py (OR-Tools Assignment → our Route/RouteStop).
- Time is in minutes from the start of the horizon (HORIZON_MINUTES in
  models.py). Convert with _time_to_minutes in service.py; never pass
  datetime objects into the solver.
- All constraints live in constraints.py (apply_*). Add a new constraint
  there, not inside RouteSolver.build_model.
- solve() is synchronous and can take seconds: callers in async code
  must offload it (see service.py _build_and_solve).
- Tests: app/tests/test_route_*.py build small RoutingProblem fixtures;
  do not hit the real distance API in tests.

Для фронтенду в Cursor той самий принцип — правило з globs, яке вмикається лише для файлів фіч:

ai-delivery-planner-frontend/.cursor/rules/features.mdc
---
description: Conventions for feature folders (api hooks, types, components)
globs: src/features/**/*.ts,src/features/**/*.tsx
alwaysApply: false
---
- Each feature has api/ (react-query hooks), types.ts, components/.
- HTTP only through apiClient from src/api/client.ts (adds the token,
  logs out on 401). Never create a new axios instance.
- Server state lives in react-query (v5: useQuery({ queryKey, queryFn })),
  client state in zustand stores in src/store. Do not copy server data
  into zustand.
- Query keys: [feature, ...params], e.g. ['routes', routeId].
Аналогія для фронтендера
Кореневий файл пам'яті — це index.css з глобальними токенами: маленький і завантажується завжди. Вкладені файли модулів — CSS Modules поруч із компонентом: їхні правила діють лише там, де вони потрібні, і не «протікають» на решту застосунку.

4 Шаблон задачі: шість полів

Більшість «галюцинацій» насправді — правдоподібна відповідь на недовизначене питання. Чіткий шаблон прибирає простір для вигадок.

шаблон задачі для агента
## Мета
Що має змінитися для користувача або системи (1–2 речення).

## Контекст
Файли, з яких почати: шлях:рядок, схожий існуючий код як зразок,
посилання на issue / документ.

## Обмеження
Що не можна змінювати, які бібліотеки й версії, архітектурні правила.

## Критерії приймання
Перелік перевірюваних умов: «ендпоінт повертає 404, якщо…», «тест X є».

## Перевірка
Точні команди, які агент має запустити сам, і очікуваний результат.

## Поза межами
Що НЕ робити в цій задачі (рефакторинг сусідніх модулів, нові залежності).

Не обов'язково щоразу писати всі заголовки. Але кожне поле закриває свою дірку: контекст не дає вигадати структуру, обмеження — притягнути нову бібліотеку, критерії — «зробити щось схоже», перевірка — заявити про успіх без запуску, а поза межами — переписати півпроєкту «заодно».

5 Grounding: прив'язка до реального коду

Grounding — це змусити агента спиратися на факти з репозиторію й інструментів, а не на «як зазвичай буває».

Сім прийомів, які реально працюють

  1. «Прочитай X і Y, перш ніж редагувати». Явно назвіть файли-джерела правди: модель, схему, існуючий зразок. Агент, який прочитав app/db/models/route.py, не вигадає поле route_status.
  2. План перед кодом. Див. попередній розділ: дешева перевірка розуміння.
  3. Вимагайте посилань файл:рядок. «Для кожного твердження про поточну поведінку вкажи файл і рядок». Вигадане твердження без посилання одразу видно, а з посиланням — легко перевірити кліком.
  4. Дозвольте сказати «не знаю». Додайте: «Якщо чогось не можеш знайти в коді — скажи прямо або спитай, не вгадуй». Без цього модель схильна заповнювати прогалини.
  5. Типізовані контракти. Генеруйте TS-типи з OpenAPI бекенду (нижче), Pydantic-схеми тримайте як єдине джерело правди. Тип, який не збігається з реальністю, ламає tsc, а не продакшн.
  6. Тести спочатку. «Спершу напиши тест, який відтворює баг, запусти, переконайся, що він червоний, потім виправ». Тест — об'єктивний арбітр, з яким не посперечаєшся.
  7. Маленькі диффи й самоперевірка. Одна зміна — одна перевірка. Агент сам запускає команду з поля «Перевірка» і показує вивід, а не переказує його.
фрагмент промпту: grounding-інструкції
Перед зміною прочитай app/services/route_optimizer/service.py
і app/tests/test_ai_replan.py.
Кожне твердження про те, як код працює зараз, підкріплюй посиланням файл:рядок.
Якщо функції чи поля не існує — так і скажи, не створюй його мовчки.
Після змін запусти .venv/bin/pytest app/tests -q і встав останні 20 рядків виводу.

OpenAPI → TS-типи: фронтенд більше не вигадує поля

Зараз у фронтенді типи написані руками: src/features/routes/types.ts містить interface Route { id: string; driver_id: string | null; … }. Агент, який додає нове поле, може «знати», що воно називається driverId, і TypeScript не заперечить — бо тип теж написаний вручну. FastAPI вже генерує повну схему на /openapi.json, тож типи можна отримувати з неї автоматично.

ai-delivery-planner-frontend — генерація типів
# бекенд запущений локально на 8000
npm i -D openapi-typescript
npx openapi-typescript "http://localhost:8000/openapi.json" -o src/api/schema.d.ts

# package.json → "scripts"
#   "gen:api": "openapi-typescript http://localhost:8000/openapi.json -o src/api/schema.d.ts"
src/features/routes/types.ts — типи з схеми
import type { components } from '../../api/schema';

// RouteRead / RouteStopRead — Pydantic-класи з app/schemas/route.py
export type Route = components['schemas']['RouteRead'];
export type RouteStop = components['schemas']['RouteStopRead'];

Назви схем — це імена Pydantic-класів (RouteRead, RouteStopRead у app/schemas/route.py); решта — в app/schemas. Після переходу будь-яке вигадане поле дає помилку tsc одразу, а не undefined в UI. А в задачі агенту достатньо написати: «типи бери тільки з src/api/schema.d.ts; якщо поля там немає — спершу додай його в Pydantic-схему на бекенді».

Аналогія для фронтендера
Grounding для агента — те саме, що TypeScript для вас. Без типів ви пишете user.adress і дізнаєтесь про помилку в проді; з типами редактор підкреслює її одразу. Агент без доступу до коду й тестів пише «без типів»: правдоподібно, але неперевірено.

6 Правильні версії бібліотек

Знання моделі зафіксовані на момент навчання, а бібліотеки змінюють API щокварталу. Якщо не сказати агенту версію, він напише код для «середньої» версії зі своїх даних.

Ризик у цьому репо: незакріплені залежності

У pyproject.toml бекенду залежності вказані без версій: "fastapi", "sqlalchemy[asyncio]", "openai", "ortools"… Закріплені лише bcrypt<4.0 і ruff==0.15.22. Тобто «яка версія SQLAlchemy у проєкті» залежить від того, коли саме ви робили pip install. Агент цього не знає й не може дізнатися з pyproject.toml.

Класичні пастки через версії: openai.ChatCompletion.create (API 0.x) замість AsyncOpenAI().chat.completions.create; session.query(Route) зі стилю SQLAlchemy 1.x замість select(Route); class Config: з Pydantic v1 замість model_config; useQuery(['routes'], fn) замість об'єктної форми react-query v5. Усе це — «правильний» код, просто для іншої версії.

Як дати агенту версії

  1. Закріпіть версії в репо. Lock-файл (uv lock / pip-compile для Python, package-lock.json уже є у фронтенді) — тоді агент читає точні версії з файлу, а не вгадує. Це корисно й без AI: відтворювані збірки.
  2. Скажіть явно в задачі або в CLAUDE.md: «SQLAlchemy 2.x async API (select, AsyncSession), Pydantic v2, react-query v5». Короткий рядок рятує від цілого класу помилок.
  3. Дайте команду, щоб агент перевірив сам: .venv/bin/pip list, .venv/bin/pip show openai, npm ls @tanstack/react-query.
  4. Актуальна документація через MCP. Context7 віддає документацію конкретної версії бібліотеки прямо в контекст («use context7» у промпті). Деталі підключення — у туторіалі про MCP.
  5. llms.txt. Багато бібліотек публікують /llms.txt — стислу документацію для LLM. Дайте агенту URL замість того, щоб він покладався на пам'ять.
  6. Вихідний код встановленого пакета — остаточна правда. «Відкрий .venv/lib/python3.12/site-packages/openai/resources/chat/completions і перевір сигнатуру». Те саме для node_modules/@tanstack/react-query/build і .d.ts-файлів.

9 Чекліст і задачі

Збережіть як памʼятку: якщо агент почав вигадувати, пройдіться по списку зверху вниз.

  • Файл пам'яті ≤ ~100 рядків, лише команди, межі, пастки й «уроки»
  • Знання модулів — у вкладених файлах або правилах з globs
  • У задачі є мета, файли-зразки, обмеження, критерії, команда перевірки, «поза межами»
  • Агент спершу показав план і посилання файл:рядок
  • Версії бібліотек відомі агенту (lock-файл, рядок у пам'яті, pip list)
  • Типи фронтенду згенеровані з OpenAPI, а не написані руками
  • Перевірки (ruff, tsc, тести) запускаються автоматично, вивід показано
  • Нова задача — /clear; довга задача — PLAN.md
  • Розвідка — через субагента, а не в основній сесії
  • Галюцинацію виправляю фактом (вивід помилки, файл, документ), а не суперечкою

import openai

response = openai.ChatCompletion.create(
    model="gpt-4o",
    messages=messages,
)

Тести з моками проходять. Що не так і яка причина галюцинації?

Що не так: це API бібліотеки openai 0.x. У проєкті встановлено 3.x, де openai.ChatCompletion не існує; правильний шлях — AsyncOpenAI через get_openai_client() і create_structured_completion з app/services/ai/client.py. Ще й синхронний виклик всередині async-коду.

Причина: застарілі знання + немає версії в контексті + тест мокає сам модуль openai, тож реальний API не перевіряється (фейковий «зелений» тест).

Лікування: рядок у CLAUDE.md «openai 3.x: тільки через app/services/ai/client.py»; у задачі — «подивись, як викликає модель planner.py»; у тестах мокати нашу обгортку, а не бібліотеку; швидка перевірка .venv/bin/python -c "import app.services.ai.explainer" плюс pyright/mypy виловили б неіснуючий атрибут.
