Частина I · Швидкість рук

1 Шорткати, що окупаються

Коли агент генерує код за секунди, ваш час іде на навігацію, рев'ю диффів і перевірку. Тут не «всі шорткати світу», а ті 10–15, які дають найбільше за день.

Принцип вибору простий: шорткат вартий заучування, якщо дію ви робите десятки разів на день і зараз тягнетеся за мишкою. Для роботи з AI це насамперед: перервати агента, відкотити його крок, перемкнути режим (план ↔ виконання), швидко згадати файл у промпті, прийняти чи відхилити дифф, стрибнути до місця помилки й запустити тест під курсором.

⚠️
Усі комбінації нижче — для macOS і стандартних keymap. Вони відрізняються між версіями, keymap (наприклад, «VS Code keymap» у JetBrains) і терміналами. Якщо комбінація не спрацювала, знайдіть дію за назвою через палітру команд. Стан на момент написання (листопад 2026).

Власні прив'язки живуть у ~/.claude/keybindings.json — команда /keybindings створює або відкриває цей файл, зміни підхоплюються без перезапуску. Формат — масив блоків «контекст → клавіша → дія». Корисний трюк: дія command:<name> запускає slash-команду, тобто можна повісити /compact на одну комбінацію.

{

  "bindings": [
    {
      "context": "Chat",
      "bindings": {
        "meta+g": "command:compact",
        "ctrl+e": "chat:externalEditor"
      }
    },
    {
      "context": "Confirmation",
      "bindings": {
        "y": "confirm:yes",
        "n": "confirm:no"
      }
    }
  ]
}

Ctrl+C, Ctrl+D та ще кілька комбінацій зарезервовані й не перепризначаються. Якщо прив'язка «мовчить», запустіть claude --debug: попередження про помилки в keybindings пишуться в debug-лог.

Аналогія для фронтендера
Шорткати — як мемоізація в React: кожна окрема економія мізерна (пів секунди), але дія повторюється сотні разів за день, і без неї «ре-рендериться» ваша увага — рука йде до мишки, погляд з коду на меню, контекст у голові втрачається.

Shell і git: аліаси під цей репозиторій

Агент часто сам запускає команди, але ви їх запускаєте ще частіше. Короткі функції в ~/.zshrc прибирають «а як там правильно викликати alembic» і дають агенту ті ж самі назви, якщо ви пропишете їх у CLAUDE.md (про це — у туторіалі 4).

~/.zshrc — фрагмент
# перейти в бекенд і активувати venv
be() {
  cd ~/Documents/personal-repo/ai-delivery-planner-backend && source .venv/bin/activate
}
fe() { cd ~/Documents/personal-repo/ai-delivery-planner-frontend; }

# API без --reload зручніше для дебагу; з reload для щоденної роботи
api()  { uvicorn app.main:app --reload --port "${1:-8000}"; }
wrk()  { celery -A app.workers.celery_app:celery_app worker -P solo --loglevel=INFO; }

# тести: усі / останні впалі / за ключовим словом
t()    { pytest -q "$@"; }
tl()   { pytest --lf -x -q; }
tk()   { pytest -q -k "$1"; }

# alembic
am()   { alembic revision --autogenerate -m "$*"; }
alias aup='alembic upgrade head'
alias adown='alembic downgrade -1'
git-аліаси (виконати один раз)
git config --global alias.st "status -sb"
git config --global alias.lg "log --oneline --graph --decorate -20"
git config --global alias.undo "reset --soft HEAD~1"   # скасувати коміт, зміни лишаються staged
git config --global alias.amend "commit --amend --no-edit"
git config --global alias.wip "commit -am wip --no-verify"

# які гілки вже злиті в main (лише показ, нічого не видаляє)
git branch --merged main

Опційно, але дуже приємно: fzf (нечіткий пошук: історія команд по Ctrl+R, файли по Ctrl+T) і zoxide (z backend замість довгого cd). Обидва ставляться через brew install fzf zoxide, а в ~/.zshrc додаються рядки source <(fzf --zsh) (для fzf 0.48+) та eval "$(zoxide init zsh)".

Частина II · Дебаг

2 Дебагер під цей стек

Агент пропонує гіпотези, але брейкпоінт показує правду. Налаштовуємо дебаг для FastAPI, pytest, Celery, процесу в Docker і для Vite-фронтенду — один раз і в репозиторії.

Чому дебагер важливіший саме в епоху AI: агент «вгадує» з тексту коду, а баги часто живуть у даних під час виконання — що реально прийшло в запиті, що повернув SQLAlchemy, у якому стані сесія. Одна зупинка на брейкпоінті замінює п'ять ітерацій «додай print, перезапусти, вставив вивід агенту».

FastAPI через debugpy (VS Code / Cursor)

Потрібне розширення Python Debugger (Microsoft), воно додає тип конфігурації debugpy. Запускаємо uvicorn як модуль — ровно так, як у app/main.py: uvicorn app.main:app.

ai-delivery-planner-backend/.vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "API: uvicorn (debug)",
      "type": "debugpy",
      "request": "launch",
      "module": "uvicorn",
      // без --reload: брейкпоінти спрацьовують стабільно
      "args": ["app.main:app", "--port", "8000"],
      "envFile": "${workspaceFolder}/.env",
      "justMyCode": false,
      "console": "integratedTerminal"
    },
    {
      "name": "pytest: current file",
      "type": "debugpy",
      "request": "launch",
      "module": "pytest",
      "args": ["${file}", "-x", "-q"],
      "envFile": "${workspaceFolder}/.env",
      "justMyCode": false
    },
    {
      "name": "Celery worker (solo)",
      "type": "debugpy",
      "request": "launch",
      "module": "celery",
      "args": ["-A", "app.workers.celery_app:celery_app", "worker", "-P", "solo", "--loglevel=INFO"],
      "envFile": "${workspaceFolder}/.env",
      "justMyCode": false
    },
    {
      "name": "Attach: API in Docker (5678)",
      "type": "debugpy",
      "request": "attach",
      "connect": { "host": "localhost", "port": 5678 },
      "pathMappings": [
        { "localRoot": "${workspaceFolder}", "remoteRoot": "/code" }
      ],
      "justMyCode": false
    }
  ]
}
  • envFile підтягує DATABASE_URL, REDIS_URL, JWT_SECRET, OPENAI_API_KEY з .env (ключі з .env.example), без них get_settings() впаде на старті.
  • justMyCode: false дозволяє зайти всередину FastAPI, Starlette чи SQLAlchemy. Для щоденного дебагу можна лишити true, щоб step into не провалювався в бібліотеки.
  • Чому без --reload. З reload uvicorn запускає процес-наглядач, який стежить за файлами, і окремий дочірній процес із вашим застосунком, а при кожній зміні файлу вбиває дочірній і стартує новий. Дебагер мусить перепідключатися до кожного нового процесу. Залежно від версії й налаштувань це працює нестабільно: брейкпоінти «зникають» після збереження файлу. Для дебагу — окрема конфігурація без reload, для щоденної роботи — api з reload у терміналі.

pytest і Celery

У проєкті asyncio_mode = "auto", тож async-тести дебажаться так само, як синхронні: брейкпоінт усередині async def test_... зупиняє виконання в event loop, і змінні фрейму доступні. Найзручніший шлях — вкладка Testing у VS Code/ Cursor: після налаштування pytest біля кожного тесту з'являється «Debug Test». Конфіг «pytest: current file» вище корисний, коли потрібні свої аргументи (-x, -k, --lf).

Celery за замовчуванням запускає воркер-процеси через prefork-пул, і брейкпоінт у задачі з app/workers/tasks.py зловити важко: задача виконується в дочірньому процесі. -P solo виконує задачі в тому ж процесі, послідовно, тож дебагер бачить усе. У проді так не запускають, а для дебагу — саме воно.

💡
Ще швидше для задач Celery: викликати функцію задачі напряму в тесті (my_task.run(...) або просто як звичайну функцію), без брокера. Логіку дебажите в pytest, а Celery-конфіг перевіряєте окремо.

Attach до процесу в Docker

Коли баг відтворюється лише в контейнері (інші версії бібліотек, інші змінні оточення), підключаємося до процесу всередині. Dockerfile бекенду копіює код у /code (WORKDIR /code), тому remoteRoot у конфігу вище — саме /code.

термінал — локальний дебаг-запуск образу
# debugpy ставимо лише для дебаг-запуску, у прод-образ він не потрапляє
docker build -t planner-api .
docker run --rm -it --env-file .env -p 8000:8000 -p 5678:5678 planner-api \
  sh -c "pip install debugpy && python -m debugpy --listen 0.0.0.0:5678 --wait-for-client \
         -m uvicorn app.main:app --host 0.0.0.0 --port 8000"
  • --listen 0.0.0.0:5678 — слухати не лише localhost контейнера, інакше хост не достукається.
  • --wait-for-client — застосунок не стартує, доки ви не натиснете «Attach: API in Docker». Так брейкпоінти в коді старту теж спрацюють.
  • Порт 5678 — тільки локально. Відкритий debugpy-порт означає виконання довільного коду, тому ніколи не публікуйте його в fly.toml чи на сервері.
  • Якщо брейкпоінти «сірі» (unverified), майже завжди винні pathMappings: шлях у контейнері не збігається з локальним.

async def assign_routes(deliveries, vehicles):
    plan = await solver.solve(deliveries, vehicles)
    if not plan.routes:

# pytest --trace -k test_quota   -> зупинка на початку кожного вибраного тесту
  • Conditional breakpoint (VS Code: правий клік на полях → Add Conditional Breakpoint): умова delivery.id == 4821 чи «Hit Count» = 100. Ідеально для циклу з тисячею доставок, де падає одна.

  • Ruff ловить забуті print (правило T201) — див. розділ 4. Забутий breakpoint() ловить правило T100 (той самий плагін flake8-debugger у ruff).

Python: ruff, vulture, deptry

У бекенді вже стоїть ruff==0.15.22, але pyproject.toml задає лише line-length і target-version, тож працює набір правил за замовчуванням (E4, E7, E9, F). Розширимо його правилами, які ловлять саме «сміття»:

pyproject.toml — розширений ruff
[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
extend-select = [
  "I",      # isort: порядок імпортів
  "B",      # flake8-bugbear: типові баги
  "UP",     # pyupgrade: сучасний синтаксис 3.12
  "SIM",    # спрощення умов
  "ARG",    # невикористані аргументи
  "ERA",    # закоментований код
  "T10",    # забутий breakpoint()
  "T20",    # забутий print()
  "RUF",    # власні правила ruff
]

[tool.ruff.lint.per-file-ignores]
# фікстури в тестах часто потрібні лише заради side-effect (моки)
"app/tests/**" = ["ARG001", "T20"]

Реальний прогін по app/ лише з правилами «сміття» (без змін у коді) дав таке:

$ .venv/bin/ruff check app --select F401,F841,ERA001,ARG001,T201 --statistics
25	ARG001	unused-function-argument
 1	ERA001	commented-out-code
Found 26 errors.

Невикористаних імпортів і змінних немає — базові правила вже тримають порядок. Цікавіше розібрати ARG001: частина спрацювань — хибні.

$ ruff check app --select ARG001 --output-format concise (фрагмент)
app/core/error_handlers.py:52:9: ARG001 Unused function argument: `request`
app/core/error_handlers.py:80:57: ARG001 Unused function argument: `exc`
app/services/route_optimizer/constraints.py:13:35: ARG001 Unused function argument: `routing`
app/tests/test_ai_replan.py:89:34: ARG001 Unused function argument: `mock_geocode`
  • error_handlers.py — exception handlers FastAPI мусять приймати (request, exc), навіть якщо щось не використовують. Видаляти аргумент не можна; правильна відповідь — перейменувати в _request (FastAPI викликає обробник позиційно) або додати # noqa: ARG001.
  • constraints.py — варто подивитися: можливо, сигнатура лишилась від старого API OR-Tools, і аргумент справді зайвий.
  • Тести — фікстура mock_geocode у параметрах вмикає мок, навіть якщо тіло тесту до неї не звертається. Звідси per-file-ignores для тестів.
  • ERA001 у app/tests/test_route_replan.py:256 — закоментований код. Або видалити, або перетворити на нормальний коментар із поясненням «чому».
🤖
Чому це важливо для AI. Попросіть агента «прибери всі попередження ruff» — і він радо видалить request з exception handler. Тоді впаде рантайм, а не лінтер. Чистку робимо так: ruff показує, людина вирішує, що з цього шум, і фіксує рішення в конфігу (per-file-ignores), щоб наступного разу ні людина, ні агент не наступили на те саме.

vulture шукає мертвий код — функції, класи, атрибути, на які ніхто не посилається. Для FastAPI він шумить: ендпоінти викликає фреймворк через декоратор, а не ваш код. Тому починайте з високого порогу впевненості:

термінал
pip install vulture deptry   # у .venv, як dev-залежності

vulture app --min-confidence 80
# формат виводу:
# app/services/foo.py:12: unused import 'os' (90% confidence)
# app/services/bar.py:40: unused function 'legacy_score' (60% confidence)

# знайдене, але потрібне (pydantic-валідатори, Celery-задачі тощо) — у whitelist:
vulture app --make-whitelist > vulture_whitelist.py
vulture app vulture_whitelist.py --min-confidence 60

deptry звіряє залежності з pyproject.toml із реальними імпортами: DEP001 — імпортується, але не оголошено; DEP002 — оголошено, але не імпортується; DEP003 — використовується транзитивна залежність; DEP004 — dev-залежність використовується в прод-коді. Що він скаже про цей бекенд, можна передбачити простим grep по імпортах:

TypeScript: knip, tsconfig, eslint

У фронтенді tsconfig.json уже має "noUnusedLocals": true і "noUnusedParameters": true, тож невикористані локальні змінні ловить сам tsc. Але TypeScript не бачить експортів, які ніхто не імпортує, і файлів, до яких немає жодного шляху з main.tsx. Це зона knip.

термінал — ai-delivery-planner-frontend
npm i -D knip
npx knip
# Секції звіту:
# Unused files (3)            src/components/OldMap.tsx ...
# Unused dependencies (1)     zustand            package.json

Приклади рядків вище ілюструють формат звіту, а не реальний стан вашого фронтенду: knip у ньому ще не встановлено. Knip сам розпізнає Vite, Vitest і ESLint як плагіни; якщо точки входу визначаться неправильно, додайте knip.json з "entry": ["src/main.tsx"] і "project": ["src/**/*.{ts,tsx}"].

В ESLint 9 (flat config) варто додати правило @typescript-eslint/no-unused-vars з argsIgnorePattern: "^_" — тоді _event стає явним сигналом «не використовую навмисно» і для людей, і для агентів, і узгоджується з noUnusedParameters.

Репозиторій: що знайшлося в цих двох проєктах

🐞
Знахідка №1 (фронтенд): згенерований vite.config.js лежить у git поруч із vite.config.ts і перекриває його. npm run build = tsc -b && vite build, а tsconfig.node.json має "composite": true без noEmit. Тому tsc -b генерує vite.config.js, vite.config.d.ts і *.tsbuildinfo, і всі четверо закомічені. Підступ: Vite шукає конфіг у порядку vite.config.js → .mjs → .ts (перевірено в node_modules/vite/dist/node/constants.js, Vite 5.4). Тобто npm run dev бере старий скомпільований .js, і правка в vite.config.ts не діє до наступного білду. Для агента це класична пастка: він правильно змінить .ts, а нічого не зміниться.
фронтенд — виправлення (виконувати свідомо, з окремим комітом)
# 1. перестати комітити артефакти
cat >> .gitignore <<'EOF'
*.tsbuildinfo
vite.config.js
vite.config.d.ts
EOF
git rm --cached vite.config.js vite.config.d.ts tsconfig.tsbuildinfo tsconfig.node.tsbuildinfo

# 2. щоб tsc -b не генерував їх поруч із кодом — як у свіжому шаблоні create-vite:
#    у tsconfig.node.json прибрати "composite", додати "noEmit": true і
#    "tsBuildInfoFile": "./node_modules/.tmp/tsconfig.node.tsbuildinfo"
#    після цього обов'язково: npm run build && npm run dev
🧨

5 Автоматизація рутини

Мета — щоб кожна повторювана дія мала одну коротку назву, однакову для вас, CI й агента. Тоді агента не треба вчити, «як тут запускаються тести».

Makefile для бекенду і npm scripts для фронтенду

Makefile є на кожному Mac без встановлення. Альтернатива — just (brew install just), з приємнішим синтаксисом, але це ще одна залежність. Важливо: рецепти в Makefile відступаються табами, не пробілами.

ai-delivery-planner-backend/Makefile
.PHONY: dev worker test test-last lint fmt migrate revision check clean

BIN := .venv/bin

dev:            ## API з автоперезавантаженням
	$(BIN)/uvicorn app.main:app --reload --port 8000

worker:         ## Celery-воркер в одному процесі (зручно дебажити)
	$(BIN)/celery -A app.workers.celery_app:celery_app worker -P solo --loglevel=INFO

test:
	$(BIN)/pytest -q

test-last:      ## лише тести, що впали минулого разу
	$(BIN)/pytest --lf -x -q

lint:
	$(BIN)/ruff check .
	$(BIN)/ruff format --check .

fmt:
	$(BIN)/ruff format .
	$(BIN)/ruff check --fix .

migrate:
	$(BIN)/alembic upgrade head

revision:       ## make revision m="add territories table"
	$(BIN)/alembic revision --autogenerate -m "$(m)"

check: lint test ## те саме, що CI

clean:
	find app -type d -name __pycache__ -prune -exec rm -rf {} +
	rm -rf build *.egg-info .pytest_cache .ruff_cache

Додайте в CLAUDE.md один рядок: «перевірка перед завершенням — make check». Агент почне закінчувати задачі прогоном, а не словами «має працювати».

ai-delivery-planner-frontend/package.json — scripts
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "format": "prettier --write .",
    "typecheck": "tsc -p tsconfig.json",
    "test": "vitest run",
    "test:watch": "vitest",
    "knip": "knip",
    "check": "npm run typecheck && npm run lint && npm run test",
    "prepare": "husky"
  }
}

typecheck працює без генерації файлів, бо в tsconfig.json уже стоїть "noEmit": true. Зараз CI фронтенду запускає lint і build, але не test — про це в туторіалі 6.

pre-commit (бекенд), husky + lint-staged (фронтенд)

ai-delivery-planner-backend/.pre-commit-config.yaml
repos:
  - repo: "https://github.com/astral-sh/ruff-pre-commit"
    rev: v0.15.22            # та сама версія, що стоїть у .venv; тримайте їх у синхроні
    hooks:
      - id: ruff-check
        args: [--fix]
      - id: ruff-format
  - repo: "https://github.com/pre-commit/pre-commit-hooks"
    rev: v6.0.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-merge-conflict
      - id: check-added-large-files
      - id: detect-private-key
термінал
pip install pre-commit
pre-commit install            # ставить git-хук .git/hooks/pre-commit
pre-commit run --all-files    # перший прогін по всьому репо
pre-commit autoupdate         # оновити rev до свіжих тегів

Назви хуків і теги змінюються: ruff-check — новіша назва хука (раніше просто ruff). Якщо pre-commit run скаже, що id не знайдено, звірте з README ruff-pre-commit; pre-commit autoupdate підставить актуальні теги.

фронтенд — husky v9 + lint-staged
npm i -D husky lint-staged
npx husky init                 # створює .husky/pre-commit і script "prepare": "husky"
echo "npx lint-staged" > .husky/pre-commit
package.json — конфіг lint-staged
{
  "lint-staged": {
    "*.{ts,tsx}": ["eslint --fix --max-warnings=0", "prettier --write"],
    "*.{css,json,md}": "prettier --write"
  }
}
⏱️
Хук має бути швидким (<5 с), інакше його обходять через --no-verify. Тому в pre-commit лише форматування й лінт змінених файлів. tsc по окремих файлах не запускається (він ігнорує tsconfig, коли отримує список файлів) — повний npm run typecheck і тести ставте в pre-push або залиште CI.
Аналогія для фронтендера
pre-commit хуки — це як beforeEach у тестах для вашого git: однакова підготовка перед кожною дією. А Makefile/npm scripts — це «публічний API» репозиторію: внутрішні команди можуть змінитися, а make check лишається тим самим контрактом для людей, CI й агентів.

Claude Code hooks, skills і claude -p

Детально hooks, skills і субагенти розібрані в туторіалі 2. Тут два хуки, які окупаються з першого дня:

ai-delivery-planner-backend/.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path // empty' | grep -E '\\.py$' | xargs -I{} sh -c '\"$CLAUDE_PROJECT_DIR\"/.venv/bin/ruff format {} && \"$CLAUDE_PROJECT_DIR\"/.venv/bin/ruff check --fix {}' || true"
          }
        ]
      }
    ],
    "Notification": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude чекає на відповідь\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}
  • PostToolUse після кожного Edit/Write отримує в stdin JSON з tool_input.file_path; ми форматуємо лише .py-файли. $CLAUDE_PROJECT_DIR — корінь проєкту. Наслідок: агенту не треба витрачати токени й кроки на «а тепер відформатуй».
  • Notification — системне сповіщення macOS, коли Claude чекає дозволу чи простоює. Можна перемикатися на інше вікно, не перевіряючи термінал щохвилини.
  • Потрібен jq (brew install jq). Перевіряйте хук вручну: echo '{"tool_input":{"file_path":"app/main.py"}}' | <команда>.

Рутинні промпти — у skills. Якщо ви втретє пишете «склади опис PR за диффом у форматі: Що / Навіщо / Як перевірити», це має бути skill (.claude/skills/pr-description/SKILL.md) або Cursor-команда. Кандидати: опис PR, changelog за тегами, commit message у вашому стилі, «додай міграцію Alembic і тест на неї», «оновити типи фронтенду за OpenAPI бекенду».

Headless-режим claude -p вбудовує агента в скрипти. Прапорці нижче — з офіційної документації (headless / CLI reference):

scripts/ai.sh — приклади
# commit message за staged-змінами (дифф подаємо через stdin — Bash-дозволи не потрібні)
git diff --staged | claude -p "Write a concise conventional commit message for this diff. Output only the message."

# changelog між тегами
git log --oneline v0.1.0..HEAD | claude -p "Group these commits into a user-facing changelog in Ukrainian."

# рев'ю диффу як JSON для подальшої обробки
git diff main | claude -p "Review for bugs and security issues. List file:line and issue." \
  --output-format json | jq -r '.result'

# детермінований запуск у CI: без локальних hooks/MCP/CLAUDE.md, лише дозволені інструменти
claude --bare -p "Run the test suite and summarize failures" --allowedTools "Read,Bash(pytest *)"

--bare пропускає авто-завантаження hooks, skills, MCP і CLAUDE.md і потребує ANTHROPIC_API_KEY у середовищі. Він рекомендований для скриптів і CI, бо результат не залежить від того, що лежить у вашому ~/.claude.

Що НЕ варто автоматизувати

  • Деструктивне без сухого прогону: git clean -fdX, docker system prune -a, alembic downgrade на спільній БД, видалення гілок. Автоматизуйте показ (-n, df, --merged), а не видалення.
  • Деплой з локальної машини агентом. flyctl deploy уже робить CI на push у main; давати агенту FLY_API_TOKEN немає сенсу.
  • Автокоміти й автопуш від агента без вашого перегляду диффу.
  • Рідкісне й нестабільне. Якщо дія буває раз на квартал і щоразу трохи інакша, скрипт застаріє раніше, ніж окупиться. Краще чекліст у README.
  • Повільні хуки. Хук на 40 секунд обходять через --no-verify, і тоді ви не маєте навіть швидких перевірок.

Завдання 1легкоПравка у vite.config.ts «не діє»

Ви (або агент) змінили порт у vite.config.ts з 5173 на 3000, запустили npm run dev — сервер усе одно на 5173. Чому, і як виправити назавжди?

Vite шукає конфіг у порядку vite.config.js → .mjs → .ts. У репозиторії лежить закомічений vite.config.js, згенерований tsc -b під час минулого білду, і Vite бере саме його.

Швидко: npm run build перегенерує .js. Назавжди: додати vite.config.js, vite.config.d.ts, *.tsbuildinfo у .gitignore, зробити git rm --cached і налаштувати tsconfig.node.json так, щоб tsc -b нічого не емітив поруч із кодом (noEmit + tsBuildInfoFile у node_modules/.tmp).

Завдання 2середньоБрейкпоінт «зникає» після збереження файлу

Ви запускаєте API у VS Code конфігурацією з "args": ["app.main:app", "--reload"]. Перший запит зупиняється на брейкпоінті, а після правки файлу — вже ні. Поясніть механіку й дайте два варіанти рішення.

З --reload uvicorn запускає процес-наглядач і окремий дочірній процес із застосунком. Після правки файлу дочірній процес вбивається й стартує новий, а дебагер мусить перепідключитися до нового процесу — це працює нестабільно, і брейкпоінти перестають спрацьовувати.

Рішення: (1) окрема дебаг-конфігурація без --reload (як у launch.json вище) і перезапуск Cmd+Shift+F5 після правок; (2) для щоденної роботи — reload у терміналі, а дебагер підключати тільки під конкретну задачу.

Завдання 3середньоАгент «пофіксив» ARG001

Ви попросили агента «прибери всі попередження ruff ARG001». Він видалив параметр request з обробника в app/core/error_handlers.py. Лінтер зелений, тести модулів зелені. Що зламається і як запобігти на майбутнє?

FastAPI/Starlette викликають exception handler як handler(request, exc). Обробник з одним параметром впаде з TypeError у момент першої помилки, тобто саме тоді, коли потрібна гарна відповідь клієнту. Юніт-тести, які не провокують цей виняток через HTTP, цього не побачать.

Запобігти: перейменувати в _request або noqa, зафіксувати в CLAUDE.md правило «не змінювати сигнатури колбеків фреймворку», і мати тест, що через TestClient/httpx.AsyncClient провокує цю помилку й перевіряє формат відповіді.

Завдання 4легкоgit clean: -n, -X, -x

Чим відрізняються git clean -ndX, git clean -fdX і git clean -fdx? Що з цього можна запускати в бекенді без ризику?

-n — сухий прогін (лише показ). -f — справді видалити. -d — включно з каталогами. -X — лише ігноровані файли; -x — ігноровані і невідстежувані (тобто й ваші нові, ще не додані файли).

Без ризику — тільки -ndX. -fdX без шляхів видалить .env, .venv/ і .idea/; -fdx ще й незакомічену роботу. Безпечно — -fdX з явними шляхами (-- app build *.egg-info) після перегляду -n.

Завдання 5складноДебаг Celery-задачі в контейнері

Задача з app/workers/tasks.py падає лише в Docker. Опишіть мінімальні кроки, щоб зупинитися на брейкпоінті всередині задачі, не змінюючи прод-образ.

1. Запустити контейнер з тим самим образом, але іншою командою: pip install debugpy && python -m debugpy --listen 0.0.0.0:5678 --wait-for-client -m celery -A app.workers.celery_app:celery_app worker -P solo --loglevel=INFO, з -p 5678:5678 і --env-file .env.

2. -P solo обов'язковий: з prefork задача виконується в дочірньому процесі, до якого debugpy не підключений.

3. Attach-конфігурація з pathMappings ${workspaceFolder} → /code (з WORKDIR у Dockerfile).

4. Відправити задачу (з API чи celery call) і дочекатися зупинки. Порт 5678 — лише локально, ніколи в fly.toml.
