1 Що таке «нормальний пайплайн»

Не «попросив — отримав код», а повторюваний цикл із перевірками, у якому агент робить механічну роботу, а людина приймає рішення в контрольних точках.

Найчастіший сценарій розчарування в AI-агентах виглядає так: пишемо одне довге повідомлення «зроби фічу X», агент 10 хвилин щось редагує, результат компілюється, але торкається не тих файлів, ламає конвенції проєкту, а тести або не запускались, або були «поправлені» під новий код. Проблема не в моделі, а в процесі: ми дали задачу без розвідки, без плану, без критерію «готово» і без перевірки. Той самий агент у правильному циклі дає передбачуваний результат.

ЕтапЩо робить агентЩо робите виАртефакт
ExploreЧитає app/api/depots/router.py, репозиторій, схеми, тести; нічого не редагуєСтавите питання, уточнюєте межіКороткий звіт: які файли причетні
PlanПише план: файли, кроки, міграції, тестиПогоджуєте або правите планПлан (у plan mode або в PLAN.md)

Commit / PRПише повідомлення коміту і опис PRПушите, CI перевіряє ще разPR
⛔
Чому one-shot промпт не працює. Агент починає редагувати, ще не знаючи, що в проєкті є DepotRepository, мультитенантність через organization_id і квоти в app/core/plans.py. Він вигадує паралельну реалізацію поруч з наявною. Чим довша задача без контрольних точок, тим більше рішень він ухвалює за вас, і тим дорожче їх потім відкочувати.
Аналогія для фронтендера
Це як різниця між «накидати сторінку одним комітом у main» і нормальним флоу: задача в Jira → дизайн-рев'ю макета → гілка → компонент + сторібук → тести → PR → CI → мерж. Пайплайн для агента — той самий процес, тільки «молодший розробник» працює в 20 разів швидше, тому контрольні точки ще важливіші.

Решта сторінки — про те, як закласти цей цикл в інструмент, щоб не повторювати його в кожному промпті: правила проєкту живуть у CLAUDE.md/AGENTS.md, перевірки — у дозволах і хуках, повторювані процедури — у скілах, а незалежне рев'ю — у сабагентах.

2 Claude Code: встановлення, перший запуск, CLAUDE.md

Claude Code — CLI-агент у терміналі (є також розширення для VS Code/JetBrains, десктоп і веб). Він працює прямо у вашому репозиторії: читає файли, запускає команди, редагує код.

Встановлення

terminal — варіанти встановлення (на момент написання)
# рекомендований нативний інсталятор (macOS / Linux)
curl -fsSL "https://claude.ai/install.sh" | bash

# або Homebrew: cask claude-code — стабільний канал (≈ тиждень позаду),
# claude-code@latest — найсвіжіший; brew-версія не оновлюється сама (brew upgrade)
brew install --cask claude-code

# або npm (потрібен Node 22+)
npm install -g @anthropic-ai/claude-code

claude --version
claude doctor          # діагностика встановлення

Офіційна інструкція може змінюватись — звіряйтесь із docs.claude.com перед установкою на новій машині.

Перший запуск у репозиторії

terminal
cd ~/Documents/personal-repo/ai-delivery-planner-backend
claude                 # інтерактивна сесія у корені репо
# всередині сесії:
/init                  # агент сам читає проєкт і генерує чернетку CLAUDE.md

/init дає хорошу чернетку, але не фінальний файл: вона зазвичай задовга, переказує структуру тек (яку агент і так побачить) і пропускає головне — неочевидні правила вашої команди. Сприймайте її як заготовку, яку треба скоротити вдвічі й доповнити тим, що агент не може вивести з коду.

CLAUDE.md для цього бекенду

Хороший CLAUDE.md — це не документація проєкту, а інструкція для нового колеги в перший день: як запустити, як перевірити, куди класти код і чого не робити. Кожен рядок має або економити агенту розвідку, або запобігати конкретній помилці. Ось реалістичний варіант для цього репозиторію:

CLAUDE.md (корінь ai-delivery-planner-backend)
# AI Delivery Planner — backend

FastAPI + async SQLAlchemy + Alembic + Postgres, Redis/Celery, OR-Tools, OpenAI.
Python 3.12, virtualenv in .venv (always use it, never system python).

## Commands
- Run API:      .venv/bin/uvicorn app.main:app --reload
- Tests:        .venv/bin/pytest -q            (single: .venv/bin/pytest app/tests/test_x.py -k name)
- Lint/format:  .venv/bin/ruff check . --fix && .venv/bin/ruff format .
- Migrations:   .venv/bin/alembic revision --autogenerate -m "..." ; .venv/bin/alembic upgrade head
- Check heads:  .venv/bin/alembic heads        (must be exactly one)

## Architecture (strict layering)
app/api/<domain>/router.py -> app/services/<domain>/ -> app/repositories/<x>_repository.py -> app/db/models/
- Routers: HTTP only (validation, status codes, Depends). No SQL, no business rules.
- Services: business rules, quotas (app/core/plans.py), OpenAI calls (app/services/ai/).
- Repositories: all SQLAlchemy queries; always scoped by organization_id (multi-tenancy).
- Schemas: Pydantic v2 in app/schemas/<domain>.py — Create / Update / Read models.
- DI lives in app/core/dependencies.py (get_*_repository, get_current_organization).

## Conventions
- async everywhere; never call blocking I/O in a request handler (OR-Tools solver -> Celery/thread).
- New endpoint = router + schema + repository method + test in app/tests/. Follow app/api/depots/ as reference.
- Errors: raise HTTPException in routers only; services raise domain exceptions (app/core/error_handlers.py).
- Line length 100 (ruff). Type hints on all public functions.

## Migrations
- Never edit a migration that is already in app/db/migrations/versions/ on main — create a new one.
- After autogenerate, READ the migration: autogenerate misses renames and server defaults.

## Tests
- Tests use aiosqlite (see app/tests/conftest.py); don't rely on Postgres-only SQL in tested paths
  without a test-specific workaround.
- Never weaken an existing assertion to make a test pass; fix the code or ask.

## Never
- Read or print .env, tokens, FLY_API_TOKEN, OPENAI_API_KEY.
- git push, alembic downgrade on shared DBs, flyctl deploy — ask the human.
- Add dependencies without saying why (pyproject.toml is the only source).
✅
Що робить цей файл хорошим: точні команди з шляхом .venv/bin/ (агент не «згадує» глобальний pytest); жорстке правило шарів з еталоном (app/api/depots/); заборони, які коштують дорого при порушенні (міграції, секрети, деплой); пояснення чому там, де правило неочевидне (aiosqlite у тестах). Довжина — до ~60–100 рядків: файл підвантажується в кожну сесію, тож кожен зайвий рядок — це токени і шум у кожному запиті.
⚠️
Чого не писати в CLAUDE.md: загальних порад («пиши чистий код»), переказу README, повного дерева тек, змісту, який швидко застаріває (версії залежностей, кількість ендпоінтів). Застарілий CLAUDE.md гірший за відсутній: агент довіряє йому більше, ніж коду. Детальніше — у туторіалі 4 про контекст.

3 Дозволи і режими роботи

Дозволи вирішують, що агент може робити без вашого підтвердження. Добре налаштовані дозволи — це і безпека, і швидкість: рутинні команди не смикають вас, небезпечні — завжди питають.

.claude/settings.json — спільні правила для команди
{
  "permissions": {
    "allow": [
      "Bash(.venv/bin/pytest:*)",
      "Bash(.venv/bin/ruff check:*)",
      "Bash(.venv/bin/ruff format:*)",
      "Bash(.venv/bin/alembic heads)",
      "Bash(.venv/bin/alembic history:*)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(git log:*)",
      "Bash(git branch:*)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Bash(git commit:*)",
      "Bash(.venv/bin/alembic upgrade:*)",
      "Bash(.venv/bin/pip install:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(~/.fly/**)",
      "Bash(flyctl:*)",
      "Bash(.venv/bin/alembic downgrade:*)",
      "Bash(rm -rf:*)"
    ]
  }
}
  • allow — виконується без питань. Сюди йдуть команди, які лише читають або перевіряють: тести, лінтер, git diff. Чим більше перевірок у allow, тим охочіше агент їх запускає.
  • ask — завжди питає, навіть якщо ви раніше погодились «для цієї сесії».
  • deny — заборонено повністю, має пріоритет над allow. Саме тут .env і деплой.
  • Синтаксис Bash(prefix:*) означає «команда починається з prefix». Актуальна документація пише те саме як Bash(prefix *) (пробіл перед *), і саме цю форму зберігає діалог «don't ask again»; обидві форми рівнозначні, але :* працює лише в кінці шаблону. Для файлових інструментів — gitignore-подібні шаблони: Read(./.env), Edit(app/db/migrations/**).
⚠️
Deny на Read не робить секрети невидимими повністю. Агент усе ще може запустити cat .env через Bash, якщо Bash дозволений широко, або прочитати значення з логів. Тому правило «не читати .env» дублюйте в трьох місцях: deny-дозвіл, рядок у CLAUDE.md і PreToolUse-хук (розділ 4). Справжній захист — щоб у робочій копії взагалі не було продакшн-секретів.

Режими (permission modes)

РежимПоведінкаКоли
defaultПитає перед кожним редагуванням і командою поза allowНезнайомий код, ризикові задачі
acceptEditsРедагування файлів без питань, команди — за правиламиПісля погодженого плану
planТільки читає і планує, нічого не змінюєExplore + Plan
autoБез рутинних питань: перед командами й мережевими запитами їх перевіряє фоновий класифікаторКоли режим доступний у вашому плані/налаштуваннях; деталі — у документації permission modes
dontAskНе питає, а відхиляє все, що не дозволено правилами allowСкрипти з чітко заданим allow-списком
bypassPermissionsБез жодних питаньЛише в ізольованому контейнері/CI, ніколи на робочій машині з секретами

Перемикання режимів у сесії — Shift+Tab (циклічно: звичайний → авто-редагування → plan mode, далі — якщо ввімкнені — bypassPermissions і auto). Типовий ритм: починаєте задачу в plan mode, погоджуєте план, перемикаєтесь в acceptEdits на реалізацію, повертаєтесь до звичайного для команд на кшталт міграцій. Режим за замовчуванням можна задати в settings через "permissions": {"defaultMode": "plan"} (значення: default, acceptEdits, plan, auto, dontAsk, bypassPermissions; у проєктному .claude/settings.json не діють auto і bypassPermissions).

Аналогія для фронтендера
Дозволи — це Content-Security-Policy для агента: whitelist того, що можна завантажувати й виконувати, і явні заборони для небезпечного. Як і з CSP, «дозволити все, бо заважає» — найпоширеніша і найдорожча помилка.

4 Hooks: автоматика навколо агента

Хуки — це shell-команди, які Claude Code запускає сам на певних подіях. На відміну від інструкцій у CLAUDE.md (які модель може «забути»), хук виконується завжди.

ПодіяКоли спрацьовуєТипове застосування
PreToolUseПеред викликом інструменту (Edit, Write, Bash…)Заблокувати небезпечну дію
PostToolUseПісля успішного викликуВідформатувати змінений файл, запустити швидкий лінт
UserPromptSubmitКоли ви надсилаєте промптДодати контекст (гілка, задача), відфільтрувати секрети

Це найуживаніші події, а не повний список: на момент написання їх понад 30 (PermissionRequest, PostToolUseFailure, SubagentStart, PostCompact, FileChanged…). Актуальний перелік — у документації hooks.

Хук отримує JSON події на stdin. Для інструментів редагування там є tool_name і tool_input (зокрема tool_input.file_path). Код виходу визначає наслідок: 0 — все гаразд; 2 — блокуюча помилка: для PreToolUse виклик скасовується, а текст зі stderr повертається агенту як пояснення; інші ненульові коди — неблокуюча помилка, яку бачите ви.

{

        "matcher": "Edit|Write|MultiEdit",

    "Notification": [

.claude/hooks/format.sh — форматування після кожного редагування
#!/usr/bin/env bash
# PostToolUse: formats the file the agent just edited. Never blocks (always exit 0).
set -u
file=$(jq -r '.tool_input.file_path // empty')
[ -z "$file" ] && exit 0

case "$file" in
  *.py)
    "$CLAUDE_PROJECT_DIR"/.venv/bin/ruff format "$file" >/dev/null 2>&1
    "$CLAUDE_PROJECT_DIR"/.venv/bin/ruff check --fix "$file" >/dev/null 2>&1
    ;;
  *.ts|*.tsx|*.css|*.json)
    # frontend repo: use its local prettier, not a global one
    npx --no-install prettier --write "$file" >/dev/null 2>&1
    ;;
esac
exit 0
.claude/hooks/guard.sh — захист міграцій і секретів
#!/usr/bin/env bash
# PreToolUse: exit 2 blocks the edit and sends stderr back to the agent as the reason.
set -u
file=$(jq -r '.tool_input.file_path // empty')
[ -z "$file" ] && exit 0
rel=${file#"$CLAUDE_PROJECT_DIR"/}

case "$rel" in
  .env|.env.*)
    echo "Editing $rel is forbidden: secrets are managed outside the repo." >&2
    exit 2 ;;
  app/db/migrations/versions/*.py)
    # a migration already committed on main is immutable; new files are fine
    if git -C "$CLAUDE_PROJECT_DIR" cat-file -e "origin/main:$rel" 2>/dev/null; then
      echo "$rel is already on main. Create a new migration with alembic revision instead." >&2
      exit 2
    fi ;;
esac
exit 0

Не забудьте chmod +x .claude/hooks/*.sh і встановлений jq (brew install jq).

⚠️
Три пастки хуків.
1) Повільні хуки гальмують кожне редагування: не запускайте весь pytest у PostToolUse — тільки форматування/лінт одного файлу. Повні тести — етап Verify.
2) Нескінченний Stop-хук. Якщо Stop-хук змушує агента продовжити (наприклад, «тести червоні — працюй далі»), перевіряйте поле stop_hook_active у вхідному JSON, інакше агент може зациклитись.
3) Безпека. Хуки виконуються з вашими правами. Хук у чужому репозиторії — це чужий код на вашій машині; переглядайте .claude/settings.json після git pull так само, як package.json scripts.
Аналогія для фронтендера
PostToolUse-форматер — це «format on save» у редакторі, а PreToolUse-guard — husky pre-commit, який не пускає коміт у захищені файли. Різниця лише в тому, що «зберігає» і «комітить» агент.

Більше прикладів автоматизації рутини — у туторіалі 5.

5 Skills, слеш-команди і subagents

CLAUDE.md — це те, що агент знає завжди. Skill — процедура, яку він підвантажує, коли задача підходить. Subagent — окремий «колега» зі своїм контекстом і інструментами.

Skill: «додати ендпоінт» за правилами цього репо

Skill — це тека з SKILL.md (і за потреби допоміжними файлами). У фронтматері — name і description: саме за описом агент вирішує, коли підвантажити скіл. Тіло читається тільки тоді, тож скіл може бути детальним, не засмічуючи кожну сесію. Скіл також можна викликати явно: /new-endpoint.

.claude/skills/new-endpoint/SKILL.md
---
name: new-endpoint
description: Add a new REST endpoint to the FastAPI backend following the router → service →
  repository → schema → test layering. Use when asked to add or extend an API endpoint.
---

# Adding an endpoint

Reference implementation: app/api/depots/router.py + app/repositories/depot_repository.py
+ app/schemas/depot.py. Read them first.

## Steps
1. Schema: add Create/Update/Read models in app/schemas/<domain>.py (Pydantic v2,
   `model_config = ConfigDict(from_attributes=True)` on Read models).
2. Repository: add the query method in app/repositories/<domain>_repository.py.
   Every query MUST filter by the repository's organization_id (multi-tenancy).
3. Service (only if there is a business rule, quota or external call):
   app/services/<domain>/. Quotas come from app/core/plans.py.
4. Router: app/api/<domain>/router.py — thin; dependencies from app/core/dependencies.py.
   If the router is new, register it where the other routers are included (search for
   `include_router`).
5. Model change? Create a migration with alembic autogenerate, then read and fix it.
6. Tests in app/tests/test_<domain>*.py: happy path, 404 for another org's object,
   validation error (422), auth required (401). Use the fixtures from conftest.py.

## Done when
- .venv/bin/pytest -q passes
- .venv/bin/ruff check . passes
- .venv/bin/alembic heads shows one head
- Summary lists every file changed and any new migration.

Subagent: незалежний рев'юер

Сабагент працює у власному контекстному вікні: основна сесія передає йому задачу і отримує тільки підсумок. Це корисно, коли робота «брудна» (читає багато файлів, ганяє тести) або коли потрібен свіжий погляд без упередження «я ж це сам написав».

.claude/agents/reviewer.md
---
name: reviewer
description: Reviews the current git diff for bugs, security and layering violations before commit.
  Use proactively after a feature is implemented and tests pass.
tools: Read, Grep, Glob, Bash
model: inherit
---

You are a strict senior reviewer for a FastAPI + async SQLAlchemy codebase.

1. Run `git diff main...HEAD` and `git diff` to see all changes.
2. Check, in this order:
   - Multi-tenancy: every new query filters by organization_id.
   - Async: no blocking calls (requests, time.sleep, heavy CPU) inside async handlers.
   - Races: check-then-act on counters/quotas (see docs/python-tutorials/29-race-conditions.html).
   - Layering: no SQL in routers, no HTTPException in repositories.
   - Tests: new behaviour has tests; no assertion was weakened.
3. Report findings as: severity (blocker/major/minor), file:line, why, suggested fix.
Do not edit files. If nothing is wrong, say so in one line.

7 Cursor: rules, AGENTS.md і режими

Cursor — форк VS Code з вбудованим агентом. Ідеї ті самі (правила проєкту, контекст, перевірки), інші файли і UX.

Правила — Markdown-файли з фронтматером. Три ключі визначають, коли правило потрапляє в контекст: description (агент сам вирішує, чи релевантне), globs (автоматично, коли в контексті файли за маскою), alwaysApply (завжди).

.cursor/rules/backend.mdc (у бекенд-репо)
---

globs: app/**/*.py
alwaysApply: false
---

- Layering: app/api (HTTP only) -> app/services (rules) -> app/repositories (SQL) -> app/db/models.

- Reference endpoint: @app/api/depots/router.py
- Run .venv/bin/pytest -q and .venv/bin/ruff check . before saying a task is done.

.cursor/rules/frontend.mdc (у ai-delivery-planner-frontend)
---
description: React + TS conventions for the planner frontend
globs: src/**/*.{ts,tsx}
alwaysApply: false
---

- Server state: @tanstack/react-query only (hooks in src/hooks or the feature folder); no fetching in useEffect.
- Client state: zustand stores in src/store; keep them small and typed.
- HTTP: the shared axios instance in src/api; never call fetch/axios directly in components.
- Tests: vitest + @testing-library/react next to the component; run `npm test` and `npm run lint`.
- Build must pass `npm run build` (tsc -b && vite build) — type errors are failures.

  4. Рев'ю правил як коду: зміни в AGENTS.md і .claude/ проходять через PR, як і будь-яка конфігурація.

11 Задачі

Спробуйте відповісти самостійно, потім розгорніть відповідь.

Задача 1легкаКуди покласти правило?

Правило: «у app/services/route_optimizer/ солвер OR-Tools не можна викликати з async-хендлера напряму — тільки через Celery або asyncio.to_thread». Куди його записати і чому?

У вкладений app/services/route_optimizer/CLAUDE.md (і відповідно в .cursor/rules/ з glob app/services/route_optimizer/**). Правило стосується лише цієї підсистеми, тож у кореневому файлі воно було б шумом для всіх інших задач. Коротке загальне правило «no blocking I/O in handlers» можна лишити в корені.

Задача 2середняХук, який нічого не блокує

Ви написали PreToolUse-хук, що забороняє редагувати .env, але агент усе одно редагує файл. У хуку echo "forbidden"; exit 1. Що не так?

Дві помилки. 1) Блокує тільки код виходу 2; exit 1 — неблокуюча помилка, виклик інструменту відбувається. 2) Пояснення має йти в stderr (echo "..." >&2), бо саме stderr повертається агенту як причина відмови. Також перевірте matcher: він має включати Edit|Write|MultiEdit.

Задача 3середняSkill чи subagent?

Вам потрібні дві речі: (а) єдина процедура створення Alembic-міграції з перевіркою згенерованого файлу; (б) прогін усіх тестів із коротким звітом лише про падіння, щоб не забивати головну сесію простирадлами трейсбеків. Що з цього skill, а що subagent?

(а) — skill: це інструкція «як робити», яку головний агент виконує у своєму контексті (йому потрібні результати міграції для подальших кроків). (б) — subagent (test-runner): шумна робота у власному контексті, назад повертається тільки стислий підсумок. Критерій: чи потрібен головній сесії весь проміжний вивід.

Задача 4складнаФронтенд вигадав поля

Агент у фронтенд-репо додав useDepotCapacity, але використав поле capacity_percent, якого бекенд не повертає. TypeScript не скаржиться. Чому, і як закрити цей клас помилок у пайплайні?

TypeScript мовчить, бо тип відповіді описав сам агент — він «узгоджений» з вигаданим полем. Типи захищають лише тоді, коли вони згенеровані з джерела правди. Рішення:

1) Генерувати TS-типи з OpenAPI бекенду (FastAPI віддає /openapi.json; інструменти на кшталт openapi-typescript) і заборонити в правилах фронтенду писати типи API вручну. 2) Вставляти контракт явно в промпт (як у кроці 5). 3) Тест хука з мок-відповіддю, взятою з реального прикладу бекенду. Детальніше про заземлення контексту — у туторіалі 4.

Задача 5складнаДозволи для нічного агента

Ви хочете запускати claude -p щоночі, щоб він шукав ендпоінти без тестів і відкривав чернетку PR з тестами. Які дозволи дати і де це запускати?

Запускати не на своїй машині, а в CI-раннері або контейнері без продакшн-секретів (лише токен з правом створити гілку/чернетку PR). Дозволи: Read/Edit у межах app/tests/**, Bash(.venv/bin/pytest:*), git для гілки й коміту; deny на редагування app/** поза тестами, на .env, деплой і міграції. Результат — завжди draft PR, який переглядає людина. Як вбудувати це в GitHub Actions — у туторіалі 6.
