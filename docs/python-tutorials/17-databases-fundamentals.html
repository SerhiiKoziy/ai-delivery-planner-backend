00 Навіщо взагалі різні бази даних

Якби одна база даних добре робила все — інших би не існувало. Але кожна модель даних — це компроміс.

Аналогія з фронтендом
Ви вже інтуїтивно робите такий вибір у браузері: маленькі прості пари ключ-значення — localStorage; структуровані об'єкти з індексами і транзакціями — IndexedDB; тимчасовий кеш відповідей API — Cache Storage / пам'ять React Query. Ви ж не тримаєте все в одному сховищі — обираєте під форму даних і патерн доступу. З базами даних на бекенді — той самий принцип, тільки ставки вищі.

Немає "найкращої бази даних" у вакуумі — є база даних, яка добре пасує до форми ваших даних (плоскі таблиці? вкладені документи? граф зв'язків? часові ряди?), патерну доступу (багато читань чи багато записів? складні JOIN-и чи прості пошуки по ключу?) і вимог до консистентності та масштабу. Решта туторіалу — про те, як ставити ці питання правильно, до того як обирати технологію.

01 Коротка історія

П'ятдесят років еволюції за одну хвилину — щоб NoSQL не здавався "новим винаходом", а SQL — "застарілим".

1966-69Ієрархічні / мережеві БД (IBM IMS, CODASYL)
→
1970Реляційна модель (E.F. Codd)
→
1979Oracle — перша комерційна RDBMS
→
1995-96MySQL, PostgreSQL 1.0
→
2006-09BigTable, Dynamo, MongoDB, Redis, Cassandra
→
2012+NewSQL (Spanner, CockroachDB)
→
ЗаразМультимодельна конвергенція

1960-ті: перші СУБД (IBM IMS, 1966) були ієрархічними або мережевими — дані читались за жорстко закодованими вказівниками "від батька до дитини", як прохід по файловій системі. Змінити структуру — переписати весь код доступу.

1970 рік: дослідник IBM Едгар Кодд публікує статтю "A Relational Model of Data for Large Shared Data Banks" — ідея, що дані можна представити просто як таблиці (відношення), а запити писати декларативно ("що" потрібно, а не "як" туди дістатись), незалежно від фізичного способу зберігання. З цього виросла мова SQL (IBM System R, 1974) і перша комерційна RDBMS — Oracle (1979).

1990-ті — початок 2000-х: RDBMS домінують беззаперечно: Oracle, DB2, Sybase, відкритий PostgreSQL (проєкт Berkeley з 1986-го) і MySQL (1995). Майже всі вебзастосунки того часу — це один сервер, одна реляційна база.

2006-2009: вебкомпанії з мільярдами користувачів (Google, Amazon, Facebook) впираються в стелю масштабування однієї реляційної бази. Google публікує статтю про BigTable (2006), Amazon — про Dynamo (2007): обидві жертвують частиною реляційних гарантій заради горизонтального масштабування на тисячі серверів. Термін "NoSQL" (спершу вжитий ще 1998-го для нішевого проєкту, але популяризований саме тепер) підхоплює ціла хвиля нових баз: MongoDB і Cassandra (2009 / Facebook 2008), Redis (2009).

2012 і далі: Google публікує Spanner — розподілену базу, що поєднує горизонтальне масштабування NoSQL-баз з ACID-транзакціями і навіть SQL, започаткувавши категорію NewSQL (CockroachDB, YugabyteDB — відкриті ідейні наступники).

Сьогодні межа стирається: PostgreSQL має вбудований тип JSONB для документів (з 2012-го) і горизонтальні розширення; MongoDB з версії 4.0 (2018) підтримує мультидокументні ACID-транзакції. "SQL проти NoSQL" — усе менше про вибір технології, усе більше — питання, яку модель даних і компроміс обирає конкретний застосунок.

02 Реляційні (SQL) бази

Дані — у таблицях з жорсткою схемою; зв'язки між таблицями явні, через зовнішні ключі; мова запитів — декларативний SQL.

  • Схема наперед (schema-on-write): кожен рядок таблиці повинен відповідати оголошеним колонкам і типам ще до запису. Помилка типу — відмова запису, а не сюрприз під час читання.
  • Нормалізація: дані розкладаються по таблицях так, щоб кожен факт зберігався рівно один раз (уникнення дублювання й аномалій оновлення); зв'язки відновлюються через JOIN.
  • Транзакції з ACID-гарантіями (детальніше в розділі 6) — кілька змін застосовуються атомарно, "усе або нічого".
  • Індекси (найчастіше B-tree) — прискорюють пошук і сортування ціною трохи повільнішого запису й додаткового місця на диску.
✅
Сильна сторона: складні запити з багатьма зв'язками ("усі доставки цієї організації за останній тиждень, разом з водієм і машиною") — природна territoriя SQL. База сама оптимізує план виконання JOIN-ів.
⚠️
Компроміс: горизонтальне масштабування (розподіл однієї логічної бази на багато фізичних серверів) — історично складніше, ніж у баз, спроєктованих під це з нуля (детальніше — розділ 5, CAP-теорема, і практика — туторіал 18).

03 Звідки виник рух NoSQL — і що це насправді

Поширена помилка — думати, що "NoSQL" означає одну технологію чи один компроміс. Насправді це парасолька для дуже різних моделей даних, об'єднаних лише тим, що вони не реляційні.

NoSQL з'явився не тому, що SQL "поганий", а тому, що конкретні задачі вебмасштабу (мільярди користувачів, географічно розподілені дата-центри) вимагали інших компромісів: простіша модель даних без складних JOIN-ів дозволяє легше розподілити дані по багатьох серверах (шардинг) без дорогих розподілених транзакцій.

💡
Правильніше читати "NoSQL" як "not only SQL", а не "SQL більше не потрібен" — переважна більшість реальних систем сьогодні використовують і реляційну базу для основних даних, і одну-дві NoSQL бази для спеціалізованих задач (кеш, пошук, черга) одночасно.

04 Сімейства NoSQL

"NoSQL" — не одна модель даних, а щонайменше п'ять різних, кожна зі своїми флагманськими продуктами.

СімействоМодель данихПрикладиТиповий кейс

Документна Самодостатні JSON/BSON-документи; гнучка (schema-on-read) структура MongoDB, CouchDB Каталоги товарів, контент з різною формою полів, швидке прототипування

Графова Вузли + ребра як дані першого класу; обхід зв'язків — нативна операція Neo4j, Amazon Neptune Соцмережі, рекомендації, виявлення шахрайства (граф транзакцій)

05 CAP-теорема — чому не можна мати все

Сформульована Еріком Брюером 2000-го, доведена формально Гілбертом і Лінчем 2002-го — фундаментальне обмеження будь-якої розподіленої бази даних.

Теорема каже: розподілена система не може одночасно гарантувати всі три властивості — Consistency (усі вузли бачать одні й ті самі дані одночасно), Availability (кожен запит отримує відповідь, навіть якщо не найсвіжішу) і Partition tolerance (система продовжує працювати попри розрив мережі між вузлами). Оскільки розриви мережі трапляються неминуче (кабель, свіч, дата-центр), P доводиться обирати завжди — а отже реальний вибір архітектора звужується до CP проти AP на момент саме розриву.

ВибірЩо означає на практиціПриклади
CP (консистентність) Під час розриву частина вузлів відмовляється відповідати, щоб не віддати застарілі дані PostgreSQL (single-primary), MongoDB (за замовчуванням), HBase
AP (доступність) Кожен вузол завжди відповідає, навіть якщо дані можуть тимчасово розходитись між вузлами Cassandra, DynamoDB, Riak (у типовій конфігурації)
⚠️
CAP описує поведінку лише в момент розриву мережі — у звичайний робочий час майже всі сучасні бази намагаються дати і консистентність, і доступність одночасно. Не варто застосовувати CAP як універсальний аргумент "ця база гірша" поза контекстом мережевого розриву.

06 ACID vs BASE

Дві протилежні філософії гарантій — реляційна класика проти типової NoSQL-моделі.

ACID (типово RDBMS)
  • Atomicity — транзакція виконується повністю або зовсім ні
  • Consistency — база завжди переходить з одного валідного стану в інший
  • Isolation — паралельні транзакції не бачать проміжний стан одна одної
  • Durability — підтверджений запис переживе збій живлення/процесу
BASE (типово розподілені NoSQL)
  • Basically Available — система відповідає майже завжди
  • Soft state — стан може змінюватись навіть без нового запису (реплікація доганяє)
  • Eventually consistent — усі вузли врешті зійдуться до однакових даних, не миттєво

Це не "правильний і неправильний" підхід — це різні відповіді на те саме питання CAP-теореми: RDBMS зазвичай обирають бік консистентності (жертвуючи доступністю під час збою), а AP-орієнтовані NoSQL — бік доступності (жертвуючи миттєвою консистентністю).

08 Що обрав цей проєкт — і чому

Конкретне рішення з ai-delivery-planner-backend, а не абстрактна теорія.

Цей бекенд використовує PostgreSQL (через асинхронний драйвер asyncpg і SQLAlchemy 2.0) як єдину основну базу даних. Причина — форма даних тут дійсно реляційна: організація має користувачів, депо, водіїв, машини й доставки; маршрут складається зі зупинок, кожна прив'язана до конкретної доставки й водія. Це природний граф зовнішніх ключів з реальними бізнес-обмеженнями цілісності (не можна видалити водія, поки на нього призначені активні маршрути) — саме те, під що RDBMS проєктована з 1970-х.

Другий фактор — ізоляція орендарів (multi-tenancy): кожен запит фільтрується по organization_id (TenantScopedRepository, туторіал 1). Реляційна модель з явними WHERE organization_id = ... робить цю гарантію структурною й легко перевірюваною — на відміну від, скажімо, документної бази, де довелось би довіряти застосунку не забути фільтр у кожному документі окремо.

⚠️
Redis у проєкті поки не активний. Конфігурація для Celery (app/workers/celery_app.py, REDIS_URL в config.py) вже присутня для майбутніх фонових задач (наприклад, довгий OR-Tools solve — див. обговорення офлоаду в туторіалі 3), але сам Redis ще не задіяний у продовому трафіку: rate limiting зараз — in-memory лічильник (app/core/rate_limiting.py), що і є причиною, чому Fly.io-деплой обмежений одним інстансом.

09 Типові помилки вибору бази даних

Найчастіші сценарії, коли вибір бази стає технічним боргом.

❌
"Візьмемо MongoDB, бо це web scale" — без реального навантаження, що вимагає горизонтального масштабування. Результат — втрачені JOIN-и й транзакції, які доводиться емулювати в коді застосунку, заради масштабу, який ніколи не знадобиться.
❌
Реляційні дані в документній базі "плоско" — дублювання одних і тих самих вкладених об'єктів у сотнях документів замість нормалізації, тому що "так простіше зараз". Оновлення одного факту перетворюється на масову міграцію документів.
❌
Фінансові/платіжні дані в AP-базі з eventual consistency без усвідомлення компромісу — тимчасово розбіжний баланс може здатись прийнятним "в середньому", але для грошей неприйнятний навіть на секунди.
⚠️
Передчасна поліглотність — додавання Redis/Elasticsearch/окремої graph-бази ще до того, як основна реляційна база реально впирається в межу, лише множить операційну складність (ще один сервіс для деплою, моніторингу, бекапів) без користі.

10 Підсумок і що далі

Головне з цього туторіалу:

  • SQL і NoSQL — не "нове проти старого", а різні компроміси, вироблені для різних задач масштабу й форми даних.
  • "NoSQL" — парасолька щонайменше для п'яти різних моделей даних (key-value, документна, широко-колонкова, графова, часові ряди) плюс пошукові рушії.
  • CAP-теорема реально проявляється лише в момент розриву мережі — і там доводиться обирати між консистентністю (CP) і доступністю (AP).
  • Вибір бази даних веде форма даних і патерн доступу конкретної задачі, а не хайп.
Далі: Туторіал 18 — конкретні СУБД і питання для співбесіди — PostgreSQL, MongoDB, Redis, реплікація/шардинг і ORM-пастки на реальних прикладах.
Туторіал згенеровано як огляд теорії баз даних для підготовки до співбесід і для того, щоб свідомо обґрунтувати вибір PostgreSQL у репозиторії ai-delivery-planner-backend.
