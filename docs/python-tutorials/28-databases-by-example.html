00Головна ідея: база обирається під запити, а не під дані

Ті самі дані (доставки, маршрути, водії) можна покласти в будь-яку базу. Різниця не в тому, «чи влізуть», а в тому, скільки роботи база робить на кожен ваш типовий запит: скільки рядків/документів прочитати, скільки разів сходити на диск, скільки вузлів кластера опитати, чи можна зробити зміну атомарно.

Кожна модель зберігання — це заздалегідь оплачена відповідь на певний тип запитів:

  • Реляційна платить нормалізацією, щоб будь-який запит (навіть непередбачений) був можливим і дані не суперечили собі.
  • Документна платить дублюванням, щоб один конкретний запит («дай маршрут цілком») був одним читанням.
  • Key-value платить відмовою від запитів «по вмісту», щоб доступ за ключем займав мікросекунди.
  • Wide-column платить «одна таблиця на запит», щоб писати мільйони рядків на секунду на багатьох серверах.
  • Колонкова OLAP платить дорогими оновленнями, щоб агрегувати мільярди рядків.
  • Пошукова платить відставанням і не-ACID, щоб шукати по тексту з помилками.
  • Графова платить слабкими агрегаціями «по всьому», щоб обходити зв'язки на будь-яку глибину.
🎨
Аналогія для фронтендера. Це як вибір форми стану у фронтенді. Нормалізований Redux-store (entities.byId + масиви id) — це реляційна модель: оновив водія в одному місці, і всі екрани бачать нове. Вкладений JSON з API «як є» в React Query кеші — це документна модель: показати екран миттєво, але оновлення водія доведеться робити в кожному кешованому маршруті (або інвалідувати все). Map у пам'яті — key-value. Ти ж обираєш форму стану під те, як компоненти його читають. З базами те саме.

01Домен (реальна схема проєкту) і 8 запитів-тестів

Схема спрощена з app/db/models/: organizations, drivers, vehicles, depots, deliveries, routes, route_stops.

Вісім запитів, якими «тестуємо» кожну базу

  1. Q1Екран маршруту: маршрут + 30 зупинок по порядку + адреси доставок + водій + машина. Читання цілого агрегату, дуже часте.
  2. Q2Звіт: скільки км проїхав кожен водій організації за жовтень. Агрегація з JOIN, рідше, але по великому обсягу.
  3. Q3Оновлення факту: водій змінив телефон. Один факт, що згадується в сотнях маршрутів.
  4. Q4Атомарна операція: створити маршрут, створити 30 зупинок, перевести 30 доставок у assigned, збільшити лічильник квоти — «усе або нічого».
  5. Q5Гарячий лічильник: rate limit «не більше 60 запитів на хвилину на організацію» на кожен HTTP-запит.
  6. Q6Потік телеметрії: кожна машина шле GPS кожні 5 с (1 000 машин → 200 записів/с, ~17 млн/добу); показати трек машини за день.
  7. Q7Пошук: менеджер вводить «хрещатик 22» або «Khreshchatyk», або з помилкою «хрещятик», і має знайти доставку.
  8. Q8Мережа: посилки переходять між депо-хабами; знайти найкоротший ланцюжок передач з депо A у депо Z (і всі депо, досяжні за ≤3 переходи).
ℹ️
Позначення далі: ✅ — природна сильна сторона, ⚠️ — можна, але з компромісом/додатковою роботою, ❌ — неприродно або небезпечно. Складність пишемо в нотації O(·) («O від…»: як росте робота зі зростанням даних), де n — кількість рядків.

02PostgreSQL (реляційна): універсал і джерело правди

Те, що використовує цей проєкт. Модель — саме схема вище.

schema.sql (скорочено)
CREATE TABLE drivers (
  id uuid PRIMARY KEY, organization_id uuid NOT NULL REFERENCES organizations(id),
  name text NOT NULL, phone text NOT NULL
);
CREATE TABLE routes (
  id uuid PRIMARY KEY, organization_id uuid NOT NULL REFERENCES organizations(id),
  driver_id uuid REFERENCES drivers(id), vehicle_id uuid REFERENCES vehicles(id),
  depot_id uuid NOT NULL REFERENCES depots(id),
  status text NOT NULL DEFAULT 'planned', total_distance_km numeric(10,2) NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE route_stops (
  id uuid PRIMARY KEY, route_id uuid NOT NULL REFERENCES routes(id) ON DELETE CASCADE,
  delivery_id uuid NOT NULL REFERENCES deliveries(id),
  sequence int NOT NULL, estimated_arrival time NOT NULL,
  UNIQUE (route_id, sequence)                         -- інваріант: немає двох зупинок №5
);
CREATE INDEX ON route_stops (route_id, sequence);    -- Q1
CREATE INDEX ON routes (organization_id, created_at); -- Q2 і списки маршрутів

Як виконуються запити

Q1 — екран маршруту: 1 запит, 4 JOIN-и
SELECT r.id, r.status, d.name AS driver, d.phone, v.plate_number,
       s.sequence, s.estimated_arrival, dl.customer_name, dl.address
FROM routes r
LEFT JOIN drivers  d  ON d.id = r.driver_id
LEFT JOIN vehicles v  ON v.id = r.vehicle_id
JOIN route_stops   s  ON s.route_id = r.id
JOIN deliveries    dl ON dl.id = s.delivery_id
WHERE r.id = $1 AND r.organization_id = $2
ORDER BY s.sequence;
-- План: index lookup routes (1) → index range route_stops (30) → 30 index lookups deliveries.
-- ~60 сторінок індексів/даних, часто з кешу (shared_buffers) → одиниці мілісекунд.
Q2 — звіт по водіях
SELECT d.name, SUM(r.total_distance_km) AS km, COUNT(*) AS routes
FROM routes r JOIN drivers d ON d.id = r.driver_id
WHERE r.organization_id = $1 AND r.created_at >= '2026-10-01' AND r.created_at < '2026-11-01'
GROUP BY d.name ORDER BY km DESC;
-- Індекс (organization_id, created_at) звужує до маршрутів місяця однієї організації. Для тисяч
-- маршрутів — миттєво. Для сотень мільйонів рядків по всіх тенантах — уже біль (див. ClickHouse).
Q3 і Q4
-- Q3: один рядок, і всі маршрути "бачать" новий телефон через JOIN
UPDATE drivers SET phone = '+380501112233' WHERE id = $1 AND organization_id = $2;

-- Q4: справжня ACID-транзакція через кілька таблиць
BEGIN;
  INSERT INTO routes (...) VALUES (...) RETURNING id;
  INSERT INTO route_stops (route_id, delivery_id, sequence, estimated_arrival) VALUES (...), (...), ...;
  UPDATE deliveries SET status = 'assigned' WHERE id = ANY($ids) AND status = 'pending';
  UPDATE organizations SET routes_generated_count = routes_generated_count + 1
   WHERE id = $org AND routes_generated_count < $limit;   -- атомарна перевірка квоти
COMMIT;   -- або все, або нічого; FK і UNIQUE не дадуть зберегти биті дані
✅ Де виграє
  • Q3, Q4 — нормалізація + ACID + обмеження (FK, UNIQUE, CHECK): дані не можуть суперечити собі.
  • Q1, Q2 — будь-який запит, навіть непередбачений, пишеться декларативно; оптимізатор сам будує план.
  • Нові вимоги (новий звіт, новий фільтр) зазвичай = новий запит + індекс, без переробки моделі.
❌ / ⚠️ Де болить
  • Q5 — гарячий лічильник на кожен запит означає UPDATE одного рядка тисячі разів на секунду: блокування рядка, WAL, мертві версії (MVCC bloat — туторіал 19).
  • Q6 — 17 млн рядків/добу: B-tree індекси й VACUUM не встигають без партиціювання (або розширення TimescaleDB).
  • Q2 на мільярдах — рядкове зберігання читає всі колонки рядка, хоча потрібні дві.
  • Q7 — LIKE '%хрещ%' не використовує B-tree (повний скан). Рішення є (pg_trgm, full-text), див. розділ 10.
  • Горизонтальне масштабування записів (шардинг) — не з коробки.

✅ Де виграє
  • Q1: агрегат одним читанням, без JOIN-ів.
  • Різна форма даних: якщо в різних організацій різні поля доставки (кастомні атрибути, для одних «температурний режим», для інших «поверх і ліфт»), документи приймуть їх без міграцій.
  • Атомарність в межах документа (маршрут + зупинки) безкоштовна.
  • Горизонтальний шардинг вбудований (shard key, наприклад organization_id).
❌ / ⚠️ Де болить
  • Q3: денормалізовані копії → оновлення в N місцях, ризик розбіжностей. Головна пастка.
  • Q4 через кілька колекцій: транзакції є, але дорожчі; якщо їх потрібно багато, модель обрана не під домен.
  • Нові ракурси запитів: «усі зупинки з доставкою del_101 у всіх маршрутах» — пошук всередині масивів, потрібен multikey-індекс stops.delivery_id; «зупинки, згруповані за клієнтом» — $unwind по всіх документах.
  • Масиви, що ростуть необмежено (наприклад, історія GPS у документі машини), впираються в 16 MB і переписують документ.
  • Немає FK: «зупинка посилається на видалену доставку» база не зупинить.
⚖️
Компроміс одним реченням. Embedding (вкладати) — коли дані читаються разом, належать одному «власнику» і не ростуть без меж (зупинки маршруту ✅). Referencing (посилатись за id) — коли дані живуть своїм життям і на них посилаються з багатьох місць (водій ✅ → тримати driver_id, а не копію, або копіювати лише незмінні поля на кшталт імені на момент маршруту).

04Redis (key-value в пам'яті): швидкість за ключем

Тут немає «таблиць». Структура даних — це схема ключів і вибір типу значення під операцію.

Q5 — rate limiter (fixed window)
# атомарно: збільшити і (лише для нового ключа) поставити TTL
pipe = redis.pipeline(transaction=True)
key = f"rl:{org_id}:{now:%Y-%m-%dT%H:%M}"
pipe.incr(key)
pipe.expire(key, 60, nx=True)
count, _ = await pipe.execute()
if count > 60:
    raise HTTPException(429, headers={"Retry-After": "60"})
# ~0.1–0.5 мс, у пам'яті, однопотоково → немає гонок між INCR різних інстансів API
✅ Де виграє
  • Q5: атомарний INCR + TTL — ідеальний розподілений лічильник для кількох інстансів API.
  • Кеш Q1: готовий JSON екрана за ключем; знімає навантаження з Postgres.
  • Поточні позиції машин (GEO), лідерборди (ZSET), черги (Celery broker), pub/sub, сесії.
❌ Де болить
  • Q2, Q7, Q8: немає запитів «за вмісту»; кожен новий ракурс = нова структура ключів, яку треба підтримувати вручну.
  • Q3, Q4 як джерело правди: дані в RAM, персистентність — компроміс (RDB/AOF), немає зв'язків і обмежень; MULTI не відкочує зміни при логічній помилці.
  • Q6 історія: 17 млн точок/добу в RAM — дорого; Streams підходять як буфер, а не як архів.
🎨
Аналогія для фронтендера. Redis — це Map/sessionStorage на сервері, спільний для всіх інстансів. Ключ cache:route:r_7f3a — як queryKey: ['route', id] у React Query. Кеш миттєвий, але джерело правди — сервер (тут Postgres), і головна складність — інвалідація.

05Cassandra (wide-column): мільйони записів на секунду, але «одна таблиця на запит»

Модель проєктується від запиту назад (query-first): спершу пишеш запит, потім таблицю під нього.

CQL — таблиця під Q6
CREATE TABLE gps_by_vehicle_day (
  vehicle_id  uuid,
  day         date,
  ts          timestamp,
  lat double, lng double, speed_kmh float,
  PRIMARY KEY ((vehicle_id, day), ts)       -- (partition key), clustering column
) WITH CLUSTERING ORDER BY (ts ASC)
  AND default_time_to_live = 7776000;       -- 90 днів, видаляється само

-- Q6: трек машини за день = ОДНА партиція, послідовне читання вже відсортованих рядків
SELECT ts, lat, lng FROM gps_by_vehicle_day WHERE vehicle_id = ? AND day = '2026-10-30';
Що станеться з іншими запитами
-- "Всі точки, де швидкість > 120" — не по ключу партиції:
SELECT * FROM gps_by_vehicle_day WHERE speed_kmh > 120;            -- ❌ помилка
SELECT * FROM gps_by_vehicle_day WHERE speed_kmh > 120 ALLOW FILTERING;  -- ⚠️ скан усього кластера
-- Правильно в Cassandra: ще одна таблиця, яку застосунок пише паралельно (денормалізація на запис)
CREATE TABLE speeding_by_org_day (org_id uuid, day date, ts timestamp, vehicle_id uuid, speed_kmh float,
  PRIMARY KEY ((org_id, day), ts, vehicle_id));
-- Q1/Q2 з JOIN-ами — неможливо; Q4 через кілька партицій — немає ACID-транзакцій
-- (є lightweight transactions на одну партицію, повільні, через Paxos).
✅ Де виграє
  • Q6: величезний стабільний потік записів, лінійне масштабування додаванням вузлів, кілька дата-центрів, немає єдиної точки відмови (AP-система).
  • TTL на рівні таблиці/рядка; передбачувана латентність запису.
❌ Де болить
  • Q1–Q4: немає JOIN-ів, транзакцій між партиціями, гнучких фільтрів, FK.
  • Кожен новий запит — нова таблиця й подвійний запис; помилка в моделі ключів = міграція даних.
  • Для 200 записів/с (наш Q6) Cassandra — гармата по горобцях: Postgres з партиціями або TimescaleDB впораються. Cassandra виправдана на десятках і сотнях тисяч записів/с і в мульти-регіоні.

06ClickHouse (колонкова OLAP): агрегації по мільярдах рядків

Відповідає на Q2 і аналітику Q6, коли даних стає дуже багато. Не замінює Postgres, а стоїть поруч.

ClickHouse — таблиця фактів маршрутів і GPS
CREATE TABLE route_facts (
  organization_id UUID, route_id UUID, driver_id UUID,
  created_at DateTime, status LowCardinality(String), total_distance_km Decimal(10,2)
) ENGINE = ReplacingMergeTree
PARTITION BY toYYYYMM(created_at)
ORDER BY (organization_id, created_at, route_id);   -- розріджений індекс під фільтр Q2

-- Q2 по всіх тенантах за рік (сотні мільйонів рядків) — секунди або менше
SELECT organization_id, driver_id, sum(total_distance_km) AS km
FROM route_facts WHERE created_at >= '2026-01-01'
GROUP BY organization_id, driver_id ORDER BY km DESC LIMIT 100;
✅ Де виграє
  • Q2 у великому масштабі, дашборди, аналітика по GPS (середня швидкість по районах, простої).
  • Стискання дає дешеве зберігання історії; materialized views для готових агрегатів.
❌ Де болить
  • Q3 (оновити телефон) і Q4 (транзакція) — оновлення й видалення важкі, ACID-транзакцій немає.
  • Q1: «дай один маршрут з усіма полями» — збирати з багатьох колонок; працює, але це не його профіль.
  • Дрібні вставки по одному рядку — анти-патерн (вставляти батчами).

07Elasticsearch / OpenSearch (пошукова): текст, помилки, релевантність

Головна структура — інвертований індекс: не «документ → слова», а «слово → документи».

Q7 — пошук з помилками
GET deliveries/_search
{
  "query": { "bool": {
    "filter": [ { "term": { "organization_id": "org_1" } } ],        // ізоляція тенанта — обов'язково
    "must":   [ { "multi_match": { "query": "хрещятик 22",
                  "fields": ["address^2", "customer_name"], "fuzziness": "AUTO" } } ]
  } }
}
✅ Де виграє
  • Q7: повнотекстовий пошук, помилки, синоніми, транслітерація, підсвітка, ранжування.
  • Пошук і агрегації по логах (ELK/OpenSearch), фасети («скільки доставок за статусами» у результатах пошуку).
❌ Де болить
  • Як джерело правди: немає ACID і FK; документ стає видимим для пошуку не одразу (refresh, за замовчуванням ~1 с: near-real-time).
  • Q3/Q4: оновлення = переіндексація документа; транзакцій немає.
  • Потрібна синхронізація з основною базою (outbox / CDC) і обробка розбіжностей.
  • Для пошуку по одній таблиці на тисячі рядків — зайвий кластер (див. pg_trgm у розділі 10).

08Neo4j (графова): зв'язки як дані першого класу

Q8: мережа депо-хабів, посилки передаються між ними. Питання про шляхи довільної довжини.

Q8 у Cypher (Neo4j) vs SQL
// Neo4j: шлях з найменшою кількістю переходів, усі депо, досяжні за ≤ 3 кроки
MATCH p = shortestPath((a:Depot {code:'A'})-[:SHIPS_TO*..10]->(z:Depot {code:'Z'})) RETURN p;
MATCH (a:Depot {code:'A'})-[:SHIPS_TO*1..3]->(d:Depot) RETURN DISTINCT d.code;

-- PostgreSQL: те саме через рекурсивний CTE (працює, але кожен рівень — JOIN по таблиці ребер)
WITH RECURSIVE reach(depot_id, depth, path) AS (
  SELECT to_depot, 1, ARRAY[from_depot, to_depot] FROM depot_links WHERE from_depot = 'A'
  UNION ALL
  SELECT l.to_depot, r.depth + 1, r.path || l.to_depot
  FROM depot_links l JOIN reach r ON l.from_depot = r.depot_id
  WHERE r.depth < 3 AND NOT l.to_depot = ANY(r.path)        -- захист від циклів
)
SELECT DISTINCT depot_id FROM reach;
✅ Де виграє
  • Q8 на великих і щільних графах: шляхи змінної довжини, «друзі друзів», виявлення шахрайства (кільця транзакцій), рекомендації.
  • Запити про структуру зв'язків читаються природно.
❌ Де болить
  • Q2, Q6: агрегації «по всьому» і потоки записів — не його профіль.
  • Для 50 депо і 200 зв'язків рекурсивний CTE у Postgres повністю достатній, а окрема база — зайва складність.
  • Зважений найкоротший шлях (за годинами) — алгоритми з бібліотеки GDS (Graph Data Science) або в застосунку (Dijkstra); для маршрутизації машин цей проєкт взагалі використовує OR-Tools (туторіал 21).

11Polyglot persistence: як бази живуть разом в одній системі

У реальних системах зазвичай одна база — джерело правди (system of record), а решта — похідні представлення (derived data), які можна перебудувати з неї. Ключове питання — як доставляти зміни.

⚠️
Ціна кожної бази. Eventual consistency між представленнями (пошук бачить доставку через секунду-дві), моніторинг lag-у синхронізації, повне переіндексування при зміні схеми, окремі бекапи й права доступу, ще одна технологія для on-call. Тому для цього проєкту зараз правильно: Postgres + Redis, і нічого більше, поки навантаження не покаже інше (туторіал 3 · драбина масштабування).

13Задачі (спершу подумай, потім відкривай)

Задача 1. Кастомні поля доставки

Клієнти-організації хочуть додавати власні поля до доставки: одній потрібен «температурний режим», іншій «поверх» і «є ліфт», третій «номер ТТН». Полів може бути до 20, різних у кожної організації, і за ними треба фільтрувати. Переходити на MongoDB?

Розв'язок
  1. Що змінилось: лише форма частини даних. Транзакції, зв'язки з маршрутами, квоти залишились, а це сильна сторона Postgres.
  2. Рішення: колонка custom_fields jsonb NOT NULL DEFAULT '{}' у deliveries + GIN-індекс: CREATE INDEX ON deliveries USING gin (custom_fields jsonb_path_ops);
  3. Фільтр: WHERE organization_id = $1 AND custom_fields @> '{"has_elevator": true}' використовує GIN.
  4. Валідація: схема полів кожної організації — окрема таблиця custom_field_definitions; Pydantic перевіряє значення при записі. Це повертає частину дисципліни schema-on-write.
  5. Висновок: переходити на Mongo заради 5% даних — міняти сильні сторони на слабкі. JSONB дає гнучкість там, де вона потрібна.
Задача 2. Чому екран маршруту повільний?

Q1 у Postgres займає 400 мс. У логах видно 31 SQL-запит на один HTTP-запит. Що відбувається і як виправити? Чи допоможе MongoDB?

Розв'язок
  1. 31 запит = 1 на маршрут + 30 на доставки кожної зупинки. Це N+1 в ORM (ліниве завантаження stop.delivery у циклі).
  2. Виправлення: select(Route).options(selectinload(Route.stops).joinedload(RouteStop.delivery)), тобто 2 запити замість 31.
  3. Перевірити індекс route_stops(route_id, sequence) через EXPLAIN ANALYZE.
  4. Якщо екран дуже гарячий — кеш у Redis з ключем cache:route:{id} та інвалідацією при зміні маршруту.
  5. MongoDB «вирішив» би проблему ціною Q3/Q4. Але причина була в ORM, а не в моделі даних. Спершу знайди справжнє вузьке місце (18 · питання 22).
Задача 3. GPS-трекінг

Додаємо live-трекінг: 1 000 машин × точка кожні 5 с. Потрібно: (а) показати диспетчеру поточну позицію всіх машин організації на карті; (б) трек машини за будь-який день за останні 90 днів; (в) щомісячний звіт «простої понад 15 хв по водіях». Які сховища і чому?

Розв'язок
  1. Обсяг: 1000 / 5 = 200 записів/с ≈ 17,3 млн/добу ≈ 1,5 млрд за 90 днів.
  2. (а) поточна позиція: Redis GEO (GEOADD geo:org_1:vehicles lng lat veh_3) + pub/sub або WebSocket для оновлень. Потрібне лише останнє значення, тож RAM і O(1) якраз до місця.
  3. (б) трек за день: 200 записів/с — це небагато. Postgres з декларативним партиціюванням за днем (або TimescaleDB hypertable), індекс (vehicle_id, ts), видалення старих партицій DROP замість DELETE (миттєво, без bloat). Cassandra з ключем ((vehicle_id, day), ts) була б доречна при 100× більшому потоці або мульти-регіоні.
  4. (в) звіт по простоях: агрегація по 500+ млн точок на місяць — це ClickHouse (або continuous aggregates у Timescale), щоб не навантажувати OLTP-базу.
  5. Головне: не тримати історію GPS у масиві документа машини (Mongo) чи в Redis. Це необмежене зростання.
Задача 4. Rate limiter на 3 інстанси

Бекенд масштабуємо з 1 до 3 інстансів на Fly.io. Зараз rate limit рахується в пам'яті процесу (app/core/rate_limiting.py). Що зламається і де тримати лічильник: Postgres чи Redis?

Розв'язок
  1. Кожен інстанс рахує свої запити, тож реальний ліміт стає 3× більшим, а балансувальник розподіляє запити нерівномірно (18 · питання 12).
  2. Postgres: UPDATE counters SET n = n + 1 на кожен HTTP-запит — це гарячий рядок: черга на блокування рядка, WAL-запис, мертві версії після кожного оновлення (MVCC), постійний VACUUM. Працює на малих RPS, але змішує кеш-навантаження з основною базою.
  3. Redis: INCR + EXPIRE NX у пайплайні — атомарно, у пам'яті, субмілісекундно, ключі самі зникають за TTL. Втрата лічильників при рестарті некритична (це не гроші).
  4. Висновок: Redis. Але квоти тарифу (routes_generated_count), які пов'язані з оплатою, лишаються в Postgres у транзакції Q4, бо там важлива надійність, а не швидкість.
Задача 5. «Давайте все в DynamoDB / Cassandra, бо масштабується»

Колега пропонує перенести всі дані проєкту в DynamoDB, «щоб ніколи не думати про масштабування». Сформулюй контраргументи і чесно назви, коли він мав би рацію.

Розв'язок
  1. Масштаб зараз: тисячі доставок на організацію на день — один Postgres з репліками обслуговує це з великим запасом.
  2. Ціна моделі: key-value / wide-column вимагають знати всі запити наперед. Q2 (новий звіт), фільтри в адмінці, ad-hoc аналітика вимагатимуть нових таблиць/індексів (GSI) і дублювання даних.
  3. Q3/Q4: транзакції в DynamoDB є, але обмежені (кількість елементів у транзакції, вартість). Інваріанти на кшталт «зупинка не посилається на видалену доставку» доведеться гарантувати кодом.
  4. Операційно: міграція, переписування репозиторіїв, нові патерни для команди.
  5. Коли колега правий: якщо патерн доступу вузький і стабільний (наприклад, лише Q6-подібні записи і читання за ключем), трафік величезний і нерівномірний, потрібна мульти-регіональна доступність, і команда готова до query-first моделювання. Тоді частину даних (телеметрію), а не все, варто винести туди.
Короткий підсумок: обирай базу під найважливіші запити й інваріанти, а не під «тип даних». Postgres як джерело правди закриває більшість випадків (і з розширеннями ще більше). Спеціалізовані бази додаються як похідні представлення, коли конкретний запит став головним навантаженням, і синхронізуються через outbox/CDC. Теорія для повторення: 17 · основи, CAP, ACID/BASE; питання для співбесіди: 18 · Q&A.
Схема домену взята з app/db/models/ репозиторію ai-delivery-planner-backend; Q5 і задача 4 спираються на реальний app/core/rate_limiting.py. Цифри латентності й обсягів — порядки величин для орієнтиру, а не бенчмарк.
