01 Що таке GIL і звідки взялась назва

Розберемо абревіатуру по літерах — і трохи історії.

GIL = Global Interpreter Lock, тобто "глобальне блокування інтерпретатора". Розберемо кожне слово окремо:

  • Global — один-єдиний lock (м'ютекс) на увесь процес, а не окремий lock на кожен об'єкт чи структуру даних (як зробили б у Java чи C++).
  • Interpreter — це lock саме навколо виконання байт-коду CPython-інтерпретатора, а не навколо, скажімо, мережі чи диска.
  • Lock — звичайний м'ютекс: у кожен момент часу лише один потік (thread) може тримати цей lock і, відповідно, виконувати Python-байткод.
🎉
Цікавий факт GIL вимовляють як звичайне слово — "джил" (римується з англ. gill — "зябра риби"). Це не офіційна назва, а прижилась як прізвисько абревіатури. Механізм існує в CPython буквально з 1992 року (ще до релізу Python 1.0) — тобто GIL старший за саму публічну історію мови як open-source проєкту.
💼
На співбесіді запитають так "Що таке GIL?" — найчастіше очікують не дослівний переклад абревіатури, а розуміння наслідку: "механізм CPython, який дозволяє лише одному потоку виконувати Python-байткод одночасно, навіть на багатоядерному процесорі — тому threading не дає справжнього паралелізму для CPU-важкого Python-коду". Якщо скажете тільки розшифровку абревіатури — це мінімум-мінімум, покажіть саме наслідок.

02 Як GIL працює технічно

Не просто "один потік за раз" — важливі деталі, коли саме lock звільняється.

  • Потік тримає GIL, поки виконує Python-байткод, і періодично звільняє його (за замовчуванням — кожні ~5 мілісекунд, керується sys.setswitchinterval()), щоб дати шанс іншим потокам.
  • Потік також звільняє GIL, коли робить блокуючий системний виклик (читання файлу, мережевий запит, time.sleep()) — саме тому I/O-очікування в одному потоці не блокує роботу Python-коду в іншому потоці.
  • C-розширення (numpy, деякі частини pandas, hashlib) можуть явно звільнити GIL зі свого C-коду під час важких обчислень — тому numpy-операції над великими масивами можуть виконуватись у кількох потоках паралельно, попри GIL.
🎉
Цікавий факт з історії До Python 3.2 механізм перемикання GIL мав відомий баг, який спільнота називала "convoy effect": якщо один потік робив важкі CPU-обчислення, а інший чекав на I/O, CPU-потік міг систематично "перехоплювати" GIL назад одразу після короткого звільнення, фактично блокуючи I/O-потік на секунди навіть на багатоядерній машині. Це детально показав Девід Бізлі (David Beazley) у знаменитій доповіді "Understanding the Python GIL" (2010) — вона й досі одна з найцитованіших доповідей про CPython. Python 3.2 переписав механізм перемикання (new GIL), щоб це виправити.
💼
Каверзне питання "Чому numpy швидкий, якщо є GIL?" — правильна відповідь: numpy написаний на C, і важкі числові цикли виконуються поза інтерпретатором Python — на цей час numpy явно відпускає GIL, тому інший Python-потік (чи навіть інший numpy-виклик у іншому потоці) може одночасно використовувати інше ядро CPU.

03 Навіщо GIL взагалі існує

Це не "недогляд" авторів мови — а свідомий компроміс, який має конкретну технічну причину.

CPython керує пам'яттю через підрахунок посилань (reference counting): у кожного об'єкта є лічильник того, скільки місць на нього посилаються; коли лічильник падає до нуля — об'єкт видаляється. Цей лічильник змінюється буквально на кожній Python-операції. Без GIL два потоки могли б одночасно змінювати той самий лічильник — класичний race condition, який призвів би до передчасного видалення об'єкта (і краху) або витоку пам'яті.

Альтернатива — дрібногранульоване блокування (окремий lock на кожен об'єкт, як у Java) — технічно можлива, але:

  • сповільнює однопотоковий код (а це переважна більшість Python-скриптів) через накладні витрати на постійне блокування/розблокування;
  • значно ускладнює написання C-розширень (а екосистема Python історично тримається саме на простих у написанні C-розширеннях — numpy, lxml тощо).

Тобто GIL — це свідомий вибір "простота і швидкість однопотокового коду" ціною "немає справжнього багатопотокового паралелізму для чистого Python-коду".

💼
На співбесіді запитають так "Чому Python не прибере GIL?" — покаже, що ви розумієте це як trade-off, а не баг: прибрати GIL "в лоб" ламає reference counting і сповільнює однопотоковий код (детальніше — наступний розділ, "Gilectomy").

04 Спроби прибрати GIL: від "Gilectomy" до PEP 703

GIL намагались прибрати неодноразово за 30+ років історії CPython — ось найвідоміші спроби.

🎉
Звідки назва "Gilectomy" У 2016 році core-розробник CPython Ларрі Гастінгс (Larry Hastings) запустив проєкт з жартівливою назвою "Gilectomy" — за аналогією з медичними термінами на -ectomy ("хірургічне видалення", як у "апендектомія" = видалення апендикса). Тобто буквально — "хірургічне видалення GIL". Проєкт успішно прибрав GIL, але однопотокова швидкість впала настільки суттєво (через потребу в дрібногранульованих локах замість одного глобального), що злиття зі стандартним CPython так і не відбулось — проєкт закрили близько 2018 року.

Головний висновок Gilectomy для індустрії: прибрати GIL легко, зробити це без втрати швидкості однопотокового коду — дуже важко. Саме цю проблему й вирішував наступний, значно успішніший підхід:

ІніціативаСутьСтатус
PEP 684 (per-interpreter GIL) Кілька суб-інтерпретаторів в одному процесі, кожен зі своїм GIL Прийнято, база в Python 3.12+
PEP 703 (Making the GIL Optional) Опційна "free-threaded" збірка CPython без GIL узагалі, зі спеціальними механізмами пам'яті замість простого reference counting Експериментально від Python 3.13 (збірка python3.13t, прапорець --disable-gil), продовжує стабілізуватись у наступних релізах
⚠️
Важливо на співбесіді не сплутати: free-threaded збірка — це поки що окрема, експериментальна збірка інтерпретатора, а не поведінка "звичайного" Python за замовчуванням. Стандартний python3, який запускається з python.org чи через pyenv/brew — досі має GIL.
💼
Питання-пастка "У Python 3.13 прибрали GIL, так?" — трохи неточне формулювання, на яке варто відповісти уточненням: "GIL стало можливо вимкнути в окремій експериментальній збірці (PEP 703), але типова, найпоширеніша збірка CPython усе ще має GIL за замовчуванням". Показує, що ви стежите за деталями, а не за заголовками новин.

05 Конкурентність vs Паралелізм

Терміни, які плутають навіть досвідчені розробники — а на співбесіді це питання №1 після самого GIL.

Паралелізм (parallelism) — кілька задач виконуються буквально одночасно, фізично на різних ядрах/процесорах у той самий момент часу.

Конкурентність (concurrency) — структура коду, яка дозволяє працювати з кількома задачами одночасно (в тому сенсі, що жодна не блокує інші), але не обов'язково виконує їх у той самий фізичний момент — вони можуть перемежовуватись (interleaving) на одному ядрі.

🎉
Класична цитата Роб Пайк (Rob Pike, співавтор мови Go) у знаменитій доповіді "Concurrency is not Parallelism" (2012) сформулював це так: "Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once" — "конкурентність — про те, як працювати з багатьма речами одночасно, паралелізм — про те, як робити багато речей одночасно". Ця фраза — практично стандартна відповідь на співбесідах.

Приклад конкурентності без паралелізму: один кухар (одне ядро CPU) готує три страви, перемикаючись між ними — поки одна тушкується (чекає, "I/O"), він ріже овочі для іншої. Роботу зроблено ефективно, але кухар фізично один і ріже овочі в один момент часу для однієї страви. Це — точний опис asyncio в Python: один потік, багато задач, перемикання під час очікування, а не справжня одночасність.

Приклад паралелізму: три різні кухарі (три ядра CPU), кожен готує свою страву одночасно, фізично в один момент часу. Це — точний опис multiprocessing в Python: кілька процесів, кожен зі своїм інтерпретатором і власним GIL, реально виконуються одночасно на різних ядрах.

💼
На співбесіді запитають так "Дай визначення конкурентності і паралелізму одним реченням кожне — і приклад, де є одне без іншого." Хороша відповідь: "asyncio в Python — конкурентність без паралелізму (один потік); multiprocessing — і конкурентність, і паралелізм (кілька процесів, справжня одночасність)". Ще краще — додати, що паралелізм — окремий випадок конкурентності, а не протилежність їй.

threading, multiprocessing, asyncio — три різні відповіді на "як робити кілька справ одночасно", кожна зі своєю ціною.

Часте питання "Чому multiprocessing повільніше стартує?" — кожен новий процес запускає окремий інтерпретатор Python з нуля і (на деяких платформах, залежно від start method: fork/spawn/forkserver) копіює або переініціалізує стан; дані між процесами передаються через серіалізацію (pickle) — набагато дорожче, ніж просте розділення пам'яті між потоками в межах одного процесу.

07 Коли що використовувати — з реальними прикладами

Практичне правило, яке варто озвучити на співбесіді дослівно.

Правило: визначте, чи задача чекає (I/O-bound) чи рахує (CPU-bound).

  • I/O-bound (мережеві запити, читання файлів, запити до БД, очікування відповіді зовнішнього API) → asyncio — найдешевше й найбільш масштабовано; threading теж працює (GIL звільняється під час I/O), але дорожче на великій кількості задач.
  • CPU-bound (обробка зображень, шифрування, розрахунки, парсинг великих файлів, комбінаторна оптимізація) → multiprocessing (справжній паралелізм) або офлоад у зовнішній сервіс/чергу задач (Celery-воркер на окремому процесі/машині).
  • Мішаний випадок (async-застосунок, всередині якого треба виконати щось CPU-важке) → asyncio.to_thread(...) (простіше, підходить для короткої CPU-роботи) або loop.run_in_executor(ProcessPoolExecutor(), fn) (справжній паралелізм для CPU-роботи, обходить GIL повністю).
⚠️
Реальний приклад із цього самого проєкту: у бекенді AI Delivery Planner є ендпоінт POST /routes/optimize, що запускає солвер Google OR-Tools (комбінаторна оптимізація маршрутів) — чисто CPU-bound задача, яка може тривати до 5 секунд. Метод optimize() — це async def, але сам виклик solver.solve() зроблено синхронно, без asyncio.to_thread. Це блокує єдиний потік event loop на весь час розрахунку — жоден інший запит на цьому процесі не обробляється. Детальний розбір цього самого місця — у туторіалі 2, розділ 6. Це майже ідеальний реальний приклад для співбесіди — див. розділ 12 нижче.
💼
Класична задача на живому кодингу "Напишіть функцію, яка паралельно рахує суму квадратів чисел від 1 до 40 000 000 на 4 ядрах" — типова пастка: кандидат хапається за threading.Thread, бо "паралельно" звучить як "потоки". Правильна відповідь — multiprocessing.Pool чи concurrent.futures.ProcessPoolExecutor, бо це чисто CPU-bound задача, і threading через GIL не дасть жодного прискорення (може навіть сповільнити через накладні витрати на перемикання потоків).

08 Пастка: GIL є, а race condition усе одно можливий

Одне з найпопулярніших "trick questions" на співбесідах — і воно ловить навіть тих, хто добре знає, що таке GIL.

race_condition_demo.py
import threading

counter = 0

def increment():
    global counter
    for _ in range(1_000_000):
        counter += 1   # виглядає як одна операція, а насправді — три байткоди:
                       # LOAD counter -> ADD 1 -> STORE counter

threads = [threading.Thread(target=increment) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()

print(counter)  # очікували 4_000_000, а вийде якесь менше число — нестабільно!

counter += 1 виглядає як одна атомарна дія, але інтерпретатор виконує її як три окремі байткод-інструкції: прочитати значення, додати 1, записати назад. GIL гарантує, що окрема Python-інструкція виконається без переривання, але не гарантує атомарність цілого виразу counter += 1 — перемикання на інший потік може відбутись між цими трьома кроками. Два потоки можуть обидва прочитати те саме старе значення, і один інкремент "загубиться".

race_condition_fix.py
import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(1_000_000):
        with lock:            # явний lock робить "прочитати-додати-записати" атомарним
            counter += 1
💼
Найкаверзніше питання на цю тему "Якщо є GIL, чи потрібні мені Lock-и в багатопотоковому коді?" — так, потрібні, для будь-якої операції над спільним станом, що складається з кількох кроків (read-modify-write, зміна кількох пов'язаних змінних, ітерація по спільній структурі під час її модифікації іншим потоком). GIL захищає лише внутрішній стан самого інтерпретатора (наприклад, не дасть пам'яті "фізично" пошкодитись), а не логічну атомарність вашого коду.

09 asyncio трохи глибше

Кілька деталей, які часто спливають на технічних співбесідах середнього+ рівня.

time.sleep vs asyncio.sleep — класична пастка
import asyncio, time

async def bad():
    time.sleep(2)          # ❌ БЛОКУЄ увесь event loop на 2 секунди —
                           #    жодна інша корутина в процесі не виконається

async def good():
    await asyncio.sleep(2) # ✅ віддає керування event loop-у, інші задачі
                           #    продовжують виконуватись під час очікування
  • Корутина (coroutine) — функція, оголошена через async def; виклик такої функції не виконує її одразу, а повертає об'єкт-корутину, який треба await-нути або передати в asyncio.create_task(...).
  • Task — обгортка над корутиною, яку event loop почав виконувати прямо зараз, у фоні (на відміну від "голого" await, який чекає результат синхронно в поточному місці коду).
  • Історична деталь: синтаксис async/await з'явився в Python 3.5 (PEP 492). До того асинхронний код писали через генератори й декоратор @asyncio.coroutine з yield from — той самий механізм "призупинити й повернутись пізніше", лежав в основі генераторів ще з Python 2.5.
💼
Питання-пастка "Чи async/await автоматично прискорює код?" — ні. Сам по собі async нічого не прискорює — він дає концепцію для дешевого перемикання між задачами під час I/O-очікування. Якщо код нічого не чекає (чистий CPU), обгортання його в async def без реального паралелізму (потоки/процеси) не дасть жодного приросту швидкості — і навіть додасть невеликі накладні витрати на сам event loop.

10 Каверзні питання співбесіди — з відповідями

Натисніть на питання, щоб побачити відповідь. Спробуйте спершу відповісти самі.

БазаЧи Python "справді" багатопотоковий?
Так, потоки (threading.Thread) реально існують і є справжніми OS-потоками. Але через GIL лише один з них виконує Python-байткод у конкретний момент — тому для CPU-роботи вони не дають паралелізму. Для I/O-роботи (де потоки більшість часу чекають, а не рахують) вони працюють ефективно, бо GIL звільняється на час очікування.
БазаЧому numpy/pandas швидкі попри GIL?
Важкі числові операції виконуються в C-коді, який явно звільняє GIL на час обчислень. Тобто "повільна" частина роботи взагалі відбувається поза Python-інтерпретатором — GIL її не стосується.
ПасткаЯкщо є GIL, чи потрібен мені Lock для спільних змінних?
Так, потрібен. GIL гарантує атомарність окремих байткод-інструкцій, але не композитних операцій на кшталт x += 1 чи модифікації структури даних у кілька кроків. Детальніше — розділ 8 вище.
ПасткаЩо станеться, якщо покласти time.sleep(5) всередині async def-функції?
Заблокує весь event loop на 5 секунд — жодна інша корутина/задача в цьому процесі не виконається, навіть якщо вони чекають на щось швидке (наприклад, відповідь з БД, яка вже прийшла). Треба await asyncio.sleep(5), або, якщо це справді блокуюча операція, — await asyncio.to_thread(time.sleep, 5).
БазаЩо станеться, якщо всередині async def виконати важкий CPU-цикл (10 млн ітерацій без I/O)?
Так само заблокує event loop — навіть без жодного блокуючого виклику, сам факт "не віддавати керування" достатній. async не рятує від CPU-bound роботи сам по собі — тільки явний офлоад (to_thread/ProcessPoolExecutor) рятує.
ПасткаGIL — це властивість мови Python чи конкретної реалізації?
Конкретної реалізації — CPython. Специфікація мови Python нічого не каже про GIL. Інші реалізації влаштовані інакше: Jython (на JVM) і IronPython (на .NET) історично не мали GIL і використовували нативні механізми паралелізму своєї платформи; PyPy (JIT-реалізація) теж історично має власний GIL-подібний механізм. Це чудова деталь, яка показує розуміння "мова vs реалізація".
ПасткаЧи є в Node.js "свій GIL"?
Ні, і питання трохи некоректне за формулюванням, що варто пояснити на співбесіді: Node.js виконує JS-код в одному-єдиному потоці за дизайном — там просто немає інших потоків, які могли б конкурувати за виконання, тому й немає потреби в м'ютексі, що обмежує кілька потоків. Python, навпаки, дозволяє створювати реальні OS-потоки, але GIL серіалізує їхнє виконання Python-коду. Схожий результат для чистого CPU-коду (немає паралелізму в одному процесі), різна причина.
ПасткаЧи можна мати кілька GIL в одному Python-процесі?
Так, з PEP 684 (база в Python 3.12+) — суб-інтерпретатори (sub-interpreters) можуть кожен мати власний, ізольований GIL в межах одного процесу. Це відкриває шлях до справжнього паралелізму без окремих OS-процесів, але API для зручного використання з чистого Python усе ще розвивається.
ПросунутеЩо таке "free-threaded" Python і чи це вже стандарт?
PEP 703 — опційна збірка CPython (з Python 3.13, прапорець --disable-gil / збірка python3.13t), де GIL можна вимкнути зовсім, ціною складніших механізмів пам'яті замість простого reference counting. Це не поведінка звичайної збірки за замовчуванням — усе ще експериментальна, окрема опція, яка продовжує стабілізуватись.
БазаДай визначення конкурентності і паралелізму одним реченням кожне.
Конкурентність — структура коду, що працює з багатьма задачами, не блокуючись жодною з них (необов'язково одночасно). Паралелізм — буквально одночасне виконання кількох задач на різних ядрах/процесорах. Приклад першого без другого: asyncio в одному потоці.
Живий кодингНапишіть функцію, яка паралельно порахує суму квадратів на 4 ядрах.
concurrent.futures.ProcessPoolExecutor або multiprocessing.Pool — не threading, оскільки це чисто CPU-bound задача, і GIL не дасть потокам прискорення. Розбити діапазон на 4 частини, порахувати кожну в окремому процесі, підсумувати результати в головному процесі.
БазаЧим asyncio.gather для паралельних HTTP-запитів краще за threading?
Обидва підходи дають конкурентність для I/O-очікування (GIL звільняється під час мережевого виклику в обох випадках). Але asyncio дешевший: не створює реальні OS-потоки (немає накладних витрат на контекст-світчинг ОС, стек пам'яті на потік), тому легко масштабується до тисяч одночасних запитів, тоді як сотні-тисячі OS-потоків уже помітно навантажують систему.
ІсторіяЩо таке "convoy effect" у старому GIL?
Баг у механізмі перемикання GIL до Python 3.2: CPU-важкий потік міг систематично "перехоплювати" GIL назад одразу після короткого звільнення, фактично не даючи I/O-потоку виконатись навіть на багатоядерній машині. Виправлено в Python 3.2 новим механізмом перемикання (детальніше показав Девід Бізлі у доповіді 2010 року — див. розділ 2).

12 Як запам'ятати терміни назавжди

П'ять базових слів, які найчастіше плутають — процес, потік, асинхронність, конкурентність, паралельність — плюс мнемонічні асоціації, щоб не зависати над відповіддю на співбесіді.

Матрьошка: процес → потік → задача

Головне, що варто "прошити" в пам'ять: це не три рівноправні терміни, а вкладені один в одного рівні — кожен наступний живе всередині попереднього.

Процес (Process)

Своя, повністю ізольована пам'ять і власний GIL. Найдорожчий за створення (новий інтерпретатор Python з нуля).

Потік (Thread)

Живе всередині процесу, ділить пам'ять з іншими потоками того ж процесу. Дешевший за процес, але обмежений спільним GIL цього процесу.

Задача / корутина (Task, у asyncio)

Найдешевша одиниця з усіх. Живе всередині ОДНОГО потоку й перемикається з іншими задачами того ж потоку на кожному await — без участі ОС узагалі.

💼
Як це використати на співбесіді Якщо просять "розклади по рівнях" — намалюйте саме цю матрьошку. Вона миттєво показує, що ви розумієте: два потоки одного процесу можуть напряму зіштовхнутись через спільну пам'ять (race condition), а два процеси — ні (їм потрібен явний IPC, щоб взагалі обмінятись даними).

5 базових термінів — одне речення + асоціація

1
Процес
Окрема, ізольована копія програми зі своєю пам'яттю.
Асоціація: окремий будинок з власною адресою — нічого не ділить із сусідом без "листування" (IPC).
2
Потік
Одна "лінія виконання" всередині процесу, ділить пам'ять з іншими потоками.
Асоціація: кімната в тому самому будинку — спільна кухня (пам'ять), тому можна випадково зіткнутись.
3
Асинхронність
Спосіб писати код, що не блокується в очікуванні — відкладає задачу й займається іншою.
Асоціація: офіціант, що не стоїть біля одного столика — приймає замовлення в іншого, поки перше готується.
4
Конкурентність
Парасолька-термін: структура, що працює з багатьма задачами одночасно (необов'язково фізично).
Асоціація: жонглер із кількома м'ячами — встигає з усіма, але в конкретну мілісекунду тримає в руці лише один.
5
Паралельність
Фізично одночасне виконання кількох задач на різних ядрах/процесорах.
Асоціація: кілька жонглерів одночасно — тепер справді кілька рук у русі в один і той самий момент.
Правило одного речення, яке варто вивчити дослівно: "Паралельність — окремий випадок конкурентності, коли одночасність не просто структурна, а фізична; асинхронність — лише один з інструментів (поряд із потоками й процесами) досягти конкурентності, і сама по собі, в Python, паралелізму не дає."

+5 термінів, які найчастіше плутають у темі async Python

6
Event Loop (цикл подій)
Диспетчер, що по колу перевіряє, яка задача готова продовжити виконання, і передає їй керування.
Асоціація: диригент оркестру — сам не грає жодної ноти, лише каже, хто вступає наступним.
7
Корутина (coroutine)
Функція (async def), що вміє призупинитись на await і повернутись до виконання пізніше, з того самого місця.
Асоціація: закладка в книжці — читання можна перервати й продовжити рівно з того самого рядка.
8
Task vs Future
Future — "обіцянка" результату, який з'явиться пізніше. Task — Future + вже запущена в фоні корутина, що цю обіцянку виконує.
Асоціація: Future — порожня коробка з номером квитанції; Task — та сама коробка, але замовлення вже готують на кухні.
9
Блокуючий vs неблокуючий виклик
Блокуючий — потік/процес фізично чекає, нічого іншого не робить. Неблокуючий — задача "залишає заявку" й повертає керування одразу, результат прийде пізніше.
Асоціація: черга в банку без талончика (блокуючий) проти "залиш заявку онлайн, ми подзвонимо" (неблокуючий).
10
Executor (Thread/ProcessPoolExecutor)
Пул потоків або процесів "збоку" від event loop, куди async-код віддає синхронну/важку роботу, щоб не блокувати себе.
Асоціація: аутсорс-бригада — event loop не робить брудну роботу сам, а віддає її підряднику й забирає готовий результат.

13 Готова історія для співбесіди — з вашого власного проєкту

Питання "розкажіть про реальний випадок, де ви розбирались з асинхронністю/паралелізмом" — дуже часте. Ось готова відповідь у форматі STAR, побудована на реальному коді цього репозиторію.

Situation: Бекенд на FastAPI має ендпоінт POST /routes/optimize, що запускає Google OR-Tools для побудови оптимальних маршрутів доставки — чисто CPU-bound задача, яка може рахувати до 5 секунд.

Task: Розібратись, чому весь застосунок побудований на async def і чи це дійсно дає неблокуючу поведінку для цього ендпоінту.

Action: З'ясував, що метод optimize() — async def і коректно робить await до бази даних (репозиторії), але сам виклик solver.solve() — синхронний, без asyncio.to_thread. Оскільки OR-Tools — чиста CPU-робота без I/O-очікувань, під час її виконання event loop не має жодної можливості перемкнутись на інший запит — весь процес фактично "заморожується" на час рахунку.

Result / рекомендація: Найпростіший фікс — обгорнути виклик у await asyncio.to_thread(solver.solve), щоб звільнити event loop. Надійніший варіант для CPU-важкої роботи — офлоадити в окремий процес (ProcessPoolExecutor) або в Celery-воркер (черга на Redis уже підключена в проєкті), бо потоки в Python усе одно обмежені GIL для самих обчислень — вигравати починаємо лише коли event loop звільняється раніше, ніж передати роботу далі, а справжнє паралельне виконання дає лише окремий процес.

💼
Чому ця історія працює на співбесіді Вона демонструє відразу три речі, які інтерв'юери шукають: (1) розуміння різниці I/O-bound vs CPU-bound на практиці, а не в теорії, (2) вміння читати чужий код і знаходити реальну, а не вигадану проблему, (3) знання конкретних інструментів виправлення (to_thread, ProcessPoolExecutor, Celery) з розумінням, коли який доречний.
Туторіал побудований на основі публічно відомої історії й документації CPython (GIL, PEP 703, PEP 684, доповідь Девіда Бізлі 2010 року, проєкт Gilectomy) та реального коду репозиторію ai-delivery-planner-backend.
