Частина I · Що це і які є варіанти

01 Kubernetes і чи потрібен він цьому проєкту

Спершу чесна відповідь на "навіщо", а вже потім "як".

Kubernetes (k8s) — оркестратор контейнерів. Ви не кажете йому "запусти контейнер на сервері X". Ви описуєте бажаний стан: "хочу 3 копії образу api:1.4.2, кожна з 0.5 CPU і 512 MiB, доступні за адресою api.example.com". Kubernetes сам знаходить, на яких машинах їх запустити, перезапускає ті, що впали, переносить з машини, яка зникла, і плавно замінює версію при деплої. Цю ідею називають декларативністю, а постійне "порівняй бажане з реальним і виправ різницю" — reconciliation loop.

💡
Чесно про цей репозиторій: бекенд сьогодні живе на Fly.io (fly.toml): одна машина shared-cpu-1x з 512 MB, міграції через release_command = "alembic upgrade head", health check на GET /health. Kubernetes у проєкті не використовується, і маніфести нижче не застосовувались до живого кластера. Це план "як би ми переїхали", прив'язаний до реального коду: FastAPI в app/main.py, Celery в app/workers/, налаштування через pydantic-settings в app/core/config.py, in-memory rate limiter в app/core/rate_limiting.py. YAML у прикладах перевірено парсером на синтаксис.

Що Kubernetes дає і чого коштує

ДаєКоштує
Самовідновлення: впав под — піднявся новий; зникла нода — поди переїхалиВелика кількість понять: десятки типів об'єктів, мережа, RBAC

⚠️
Коли k8s — перебір: один API-сервіс, один воркер, кілька тисяч користувачів. Fly.io, Render, Google Cloud Run, AWS App Runner/ECS Fargate дають 80% користі (контейнери, автоскейл, health checks, rolling deploy) за 10% складності. Сходинки масштабування описані в туторіалі 3. Kubernetes виправданий, коли сервісів багато (5–10+), є платформна команда, потрібні специфічні речі (GPU, власні оператори, on-prem, мультихмара) або так прийнято в компанії.
💼
На співбесіді запитають так "Чому ви не на Kubernetes?" — сильна відповідь не "він складний", а конкретна: "один сервіс і один воркер, PaaS дає rolling deploy і health checks; переїдемо, коли з'являться N сервісів або вимоги X. Код уже готовий: 12-factor конфіг через env, stateless API (крім rate limiter, і ми знаємо, як його винести в Redis)".

02 Архітектура кластера

Що відбувається між kubectl apply і процесом uvicorn на якійсь машині.

Що відбувається після kubectl apply -f deployment.yaml

  1. apiserver перевіряє маніфест (автентифікація, RBAC, admission webhooks) і зберігає об'єкт Deployment в etcd.
  2. Deployment-контролер бачить новий Deployment і створює ReplicaSet з потрібною кількістю реплік.
  3. ReplicaSet-контролер створює об'єкти Pod. Вони поки без ноди (Pending).
  4. Scheduler обирає ноду для кожного пода. Враховує resources.requests, affinity, taints/tolerations, topology spread.
  5. kubelet на обраній ноді тягне образ, запускає контейнери через containerd, починає перевіряти probes.
  6. Коли readiness probe проходить, IP пода потрапляє в EndpointSlice сервісу, і трафік починає приходити.
🎉
Цікавий факт Kubernetes — грецьке "керманич", тому на логотипі штурвал. "k8s" — нумеронім: між k і s вісім літер. Проєкт виріс з внутрішньої системи Google Borg, відкритий у 2014 році і переданий фонду CNCF.

05 Крок 0: образ, готовий до кластера

Kubernetes запускає контейнери, тож почати треба з Dockerfile. Поточний робочий, але є що покращити.

Dockerfile (зараз у репозиторії)
FROM python:3.12-slim
WORKDIR /code
ENV PYTHONPATH=/code
COPY pyproject.toml ./
RUN pip install --no-cache-dir .
COPY app/ ./app/
COPY alembic.ini ./
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--proxy-headers", "--forwarded-allow-ips=*"]
Dockerfile (k8s-ready варіант)
# --- build stage: збираємо залежності окремо, щоб runtime-образ був меншим
FROM python:3.12-slim AS build
WORKDIR /code
COPY pyproject.toml ./
RUN pip install --no-cache-dir --prefix=/install .

# --- runtime stage
FROM python:3.12-slim
ENV PYTHONPATH=/code \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1
WORKDIR /code
COPY --from=build /install /usr/local
COPY app/ ./app/
COPY alembic.ini ./          # міграції лежать в app/db/migrations — вже скопійовані з app/

# не root: securityContext у k8s це вимагатиме
RUN useradd --uid 10001 --no-create-home appuser
USER 10001

EXPOSE 8000
# exec-форма: uvicorn = PID 1 і сам отримує SIGTERM від kubelet
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--proxy-headers", "--forwarded-allow-ips=*", "--timeout-graceful-shutdown", "20"]
  • Один процес на контейнер. На VM запускають gunicorn -w 4. У k8s зазвичай 1 процес uvicorn на под і більше подів: kubelet бачить кожен процес окремо (probes, рестарти, метрики), а HPA масштабує точніше. Кілька воркерів на под має сенс, коли под отримує 2+ CPU.
  • PYTHONUNBUFFERED=1: логи в stdout одразу, інакше kubectl logs показує їх із запізненням або губить при краші.
  • Тег образу — незмінний (git SHA або semver), а не latest. Інакше незрозуміло, що саме запущено, і rollback неможливий.
  • Міграції (script_location = app/db/migrations в alembic.ini) потрапляють в образ разом з app/, тож Job може запускати їх з того самого образу (див. розділ 8). Детальніше про пакування — туторіал 12.

06 Deployment і Service для FastAPI

Центральний маніфест: скільки подів, які ресурси, як перевіряти здоров'я і як коректно вмирати.

k8s/base/api-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: planner
  labels: { app: api }
spec:
  replicas: 2
  revisionHistoryLimit: 5
  selector:
    matchLabels: { app: api }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # під час деплою максимум +1 под понад replicas
      maxUnavailable: 0    # жодного зменшення потужності під час деплою
  template:
    metadata:
      labels: { app: api }
    spec:
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        seccompProfile: { type: RuntimeDefault }
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels: { app: api }
      containers:
        - name: api
          image: ghcr.io/acme/planner-api:3f9c2e1   # незмінний тег = git SHA
          ports:
            - name: http
              containerPort: 8000
          envFrom:
            - configMapRef: { name: planner-config }
            - secretRef: { name: planner-secrets }
          resources:
            requests: { cpu: 250m, memory: 384Mi }
            limits: { memory: 512Mi }            # CPU limit свідомо не ставимо (див. розділ 10)
          startupProbe:                          # поки не пройде, інші probes не запускаються
            httpGet: { path: /health, port: http }
            periodSeconds: 2
            failureThreshold: 30                 # до 60 с на старт
          readinessProbe:                        # "чи слати мені трафік"
            httpGet: { path: /health/ready, port: http }
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:                         # "чи мене треба вбити й перезапустити"
            httpGet: { path: /health, port: http }
            periodSeconds: 10
            failureThreshold: 3
          lifecycle:
            preStop:
              sleep: { seconds: 5 }              # дати Ingress/kube-proxy час прибрати под з ротації
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
k8s/base/api-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: planner
spec:
  type: ClusterIP
  selector: { app: api }
  ports:
    - name: http
      port: 80
      targetPort: http

Три probes — три різні питання

ProbeПитанняЩо робить при проваліЩо перевіряти
startup"Я вже стартував?"Чекає до failureThreshold × period, потім рестартТой самий дешевий /health. Захищає повільний старт від liveness-вбивства
readiness"Можна слати мені запити?"Прибирає под з Service, не рестартуєГотовність залежностей: пул БД відкрито, конфіг завантажено
liveness"Я завис і мене треба вбити?"Рестарт контейнераЛише сам процес: event loop відповідає. Ніколи не БД!

Зараз у app/main.py є лише GET /health, який повертає {"status": "ok"}. Цього вистачає для liveness. Для readiness варто додати окремий ендпоінт:

app/main.py (додати)
from fastapi import Response
from sqlalchemy import text

from app.db.session import engine   # engine створюється в app/db/session.py

@app.get("/health/ready")
async def ready(response: Response) -> dict:
    try:
        async with engine.connect() as conn:
            await conn.execute(text("SELECT 1"))
    except Exception:
        response.status_code = 503       # под зникне з ротації, але НЕ перезапуститься
        return {"status": "db-unavailable"}
    return {"status": "ready"}

Graceful shutdown: що відбувається при видаленні пода

  1. Под отримує статус Terminating. Паралельно починається прибирання його з EndpointSlice і виконується preStop.
  2. Після preStop kubelet шле процесу SIGTERM. uvicorn перестає приймати нові з'єднання і дообробляє поточні (до --timeout-graceful-shutdown).
  3. Якщо процес не завершився за terminationGracePeriodSeconds (рахується від початку, включно з preStop), приходить SIGKILL.

Саме через "паралельно" на кроці 1 і потрібен preStop: sleep. Без нього uvicorn може закритися раніше, ніж ingress-контролер дізнається про видалення, і кілька запитів отримають 502. Вбудована дія sleep у preStop з'явилась у новіших версіях k8s. На старих кластерах пишуть exec: { command: ["sleep", "5"] }, але тоді в образі має бути бінарник sleep.

07 Конфігурація і секрети

Settings(BaseSettings) у app/core/config.py читає змінні оточення, тож з k8s він дружить без змін у коді.

k8s/base/config.yaml

08 Міграції Alembic: замінник release_command

На Fly.io міграції запускає release_command рівно один раз перед деплоєм. У k8s такої вбудованої речі немає, і тут найбільше пасток.

Спершу додаєте колонку (nullable), деплоїте код, що пише в обидві, переносите дані, і лише в наступному релізі видаляєте стару. Перейменування колонки "в один реліз" гарантує 500-ті помилки на старих подах під час деплою. Детальніше про БД — туторіал 17.

09 Celery workers і фонові задачі

У проєкті є optimize_routes_task (OR-Tools, CPU-важкий) і analyze_delivery_list_task (виклики LLM, I/O). Це окремий Deployment зі своїми правилами.

k8s/base/worker-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker
  namespace: planner
spec:
  replicas: 1
  selector:
    matchLabels: { app: worker }
  template:
    metadata:
      labels: { app: worker }
    spec:
      terminationGracePeriodSeconds: 300      # OR-Tools може рахувати хвилинами — даємо дорахувати
      containers:
        - name: worker
          image: ghcr.io/acme/planner-api:3f9c2e1
          command: ["celery", "-A", "app.workers.celery_app", "worker",
                    "--loglevel=INFO", "--concurrency=2", "--max-tasks-per-child=50"]
          envFrom:
            - configMapRef: { name: planner-config }
            - secretRef: { name: planner-secrets }
          resources:
            requests: { cpu: "1", memory: 768Mi }
            limits: { memory: 1536Mi }
          livenessProbe:
            exec:
              command: ["sh", "-c", "celery -A app.workers.celery_app inspect ping -d celery@$HOSTNAME --timeout 10"]
            periodSeconds: 60
            timeoutSeconds: 20
            failureThreshold: 3
  • SIGTERM для Celery = warm shutdown: воркер припиняє брати нові задачі і дочікується поточних. Якщо grace period менший за найдовшу задачу, вона буде вбита SIGKILL посередині.
  • task_acks_late=True + task_reject_on_worker_lost=True: задача підтверджується лише після завершення, тож при вбитті пода повернеться в чергу. Ціна: задача може виконатися двічі, тому вона має бути ідемпотентною (наприклад, перевіряти статус route_request перед перерахунком).
  • --max-tasks-per-child періодично перезапускає дочірній процес. Це страховка від повільного росту пам'яті в C-розширеннях (OR-Tools) до того, як прийде OOMKilled.
  • Liveness через inspect ping важкий (йде через брокер) і може давати хибні спрацювання при проблемах з Redis. Альтернатива: воркер пише heartbeat-файл у сигналі worker_heartbeat або heartbeat_sent, а probe перевіряє його вік. Багато команд взагалі обходяться без liveness для воркерів.
  • Celery beat (поки відсутній, у celery_app.py лише TODO): рівно одна репліка, strategy: Recreate, інакше задачі за розкладом виконуватимуться двічі. Альтернатива для простих задач — k8s CronJob з concurrencyPolicy: Forbid.

Масштабування воркерів за довжиною черги: KEDA

CPU — погана метрика для воркерів. Черга з 500 задач при 10% CPU (бо задачі чекають на OpenAI) — це сигнал додати воркерів. KEDA (Kubernetes Event-Driven Autoscaling) читає довжину Redis-списку, куди Celery кладе задачі, і масштабує Deployment, включно з нулем реплік.

k8s/base/worker-scaledobject.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: worker
  namespace: planner
spec:
  scaleTargetRef:
    name: worker
  minReplicaCount: 1        # 0 — якщо холодний старт воркера прийнятний
  maxReplicaCount: 8
  cooldownPeriod: 300
  triggers:
    - type: redis
      metadata:
        address: redis.internal:6379
        listName: celery    # черга за замовчуванням у Celery з Redis-брокером
        listLength: "10"    # ціль: ~10 задач у черзі на одну репліку
💡
Розділяйте черги за природою задач: optimize (CPU, мало паралельності, великі ліміти пам'яті) і ai (I/O, висока concurrency, малий CPU). Кожна черга отримує свій Deployment і свій ScaledObject. Так довгий солвер не блокує швидкі AI-задачі. Про черги загалом — туторіал 20, про солвер — туторіал 21.

10 Ресурси і автомасштабування

requests/limits — найважливіші і найчастіше неправильно налаштовані рядки маніфесту.

requests vs limits

  • requests — гарантія і основа для scheduler-а: под ставиться лише на ноду, де вільно стільки ресурсів. HPA рахує відсоток CPU саме від requests.
  • limits.memory — жорстка стеля. Перевищив — ядро вбиває процес: OOMKilled, exit code 137.
  • limits.cpu — стеля через CFS-квоти: процес не вбивається, а пригальмовується (throttling). Для latency-чутливих Python API це дає незрозумілі стрибки p99, навіть коли "середній CPU 30%". Поширена практика: CPU requests ставити, CPU limit не ставити (або ставити щедро), memory limit ставити завжди.
QoS-класУмоваНаслідок

Стратегії релізу

  • RollingUpdate (за замовчуванням): поступова заміна. maxSurge/maxUnavailable керують швидкістю і запасом. Rollback: kubectl rollout undo deploy/api.
  • Recreate: спершу вбити всі старі, потім підняти нові (downtime). Для singleton-ів на кшталт Celery beat.
  • Blue/green і canary — не вбудовані. Argo Rollouts або Flagger перемикають трафік (5% → 25% → 100%) і автоматично відкочують реліз за метриками (рівень 5xx, latency).

13 Мережа, TLS і безпека

Мінімальний набір, без якого кластер не варто відкривати в інтернет.

k8s/base/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
  namespace: planner
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod    # TLS-сертифікат автоматично
spec:
  ingressClassName: traefik          # або nginx, alb, gce...
  tls:
    - hosts: [api.example.com]
      secretName: api-tls
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api
                port: { name: http }
  • Ingress controller сам у кластері відсутній, його ставлять окремо: Traefik, NGINX-based контролери, HAProxy, Envoy-based (Contour, Emissary), хмарні (AWS Load Balancer Controller, GKE Ingress). Популярний community-проєкт ingress-nginx оголосив про завершення підтримки, тож для нових кластерів варто дивитися на Gateway API (Gateway + HTTPRoute), який підтримують Envoy Gateway, Istio, Cilium, Traefik і хмарні провайдери.
  • cert-manager отримує і продовжує сертифікати Let's Encrypt.
  • NetworkPolicy: за замовчуванням будь-який под може ходити до будь-якого. Політика "deny all ingress у namespace + дозволити до api лише від ingress-контролера" обмежує наслідки зламу. Працює лише з CNI, що їх підтримує (Calico, Cilium; хмарні CNI — з увімкненою опцією).
  • RBAC і ServiceAccount: подам API не потрібен доступ до Kubernetes API, тому automountServiceAccountToken: false. Людям — мінімальні ролі, prod — без cluster-admin на кожного.
  • Pod Security Standards: мітка namespace pod-security.kubernetes.io/enforce: restricted не пропустить поди з root, privileged, hostPath. Наш Deployment з розділу 6 їй відповідає.
  • Доступ до хмари без ключів: IRSA/EKS Pod Identity, GKE Workload Identity. Под отримує тимчасові креденшали ролі замість AWS_ACCESS_KEY_ID у Secret.
  • Ланцюжок постачання образів: сканування (Trivy, Grype), підписи (cosign), admission-політики (Kyverno, OPA Gatekeeper): "лише образи з нашого registry, лише з тегом-SHA, лише non-root".

Важливо для цього проєкту: реальний IP клієнта

Rate limiter у app/core/rate_limiting.py рахує запити за IP, а uvicorn запущений з --proxy-headers --forwarded-allow-ips=*, тобто довіряє заголовку X-Forwarded-For від будь-кого. У k8s між клієнтом і подом стоять LB і ingress. Якщо їх налаштовано неправильно, буде одне з двох:

  • усі клієнти виглядають як IP ingress-контролера, і ліміт "20 логінів на хвилину" стає спільним на весь світ;
  • або клієнт сам підставляє X-Forwarded-For і обходить ліміт, бо * довіряє будь-якому джерелу.

Правильно: ingress перезаписує (а не дописує наосліп) X-Forwarded-For, LB-сервіс ingress-контролера з externalTrafficPolicy: Local або PROXY protocol, а uvicorn довіряє лише CIDR подів ingress-контролера: --forwarded-allow-ips=10.0.0.0/8 замість *.

14 Детальні кейси: симптом → причина → виправлення

Десять ситуацій, які гарантовано трапляться при переїзді саме цього бекенду. Кожен кейс прив'язаний до коду репозиторію або до типової поведінки k8s.

Кейс 1. Rate limiter "зламався" після масштабування до 3 реплік

Симптом: на Fly.io реєстрація обмежена 5 спробами на годину з IP. У k8s з 3 подами атакувальник робить ~15 спроб. Іноді користувач отримує 429, а через секунду той самий запит проходить.

Причина: rate_limit_by_ip зберігає лічильники в словнику процесу. Коментар у самому файлі це прямо каже: окремі процеси не діляться цим dict. Саме тому в нотатках проєкту записано "Fly.io має лишатися на 1 машині". Service розподіляє запити між подами, і кожен под рахує свій ліміт.

Виправлення: перенести лічильники в Redis (він уже є для Celery): атомарний INCR + EXPIRE на ключ rl:{scope}:{ip}:{window} або готова бібліотека (limits з Redis-сховищем, slowapi). Ліміти на рівні ingress (rate limit у Traefik/NGINX/Envoy) — додатковий шар, але per-IP логіку бізнес-рівня (register, login) краще тримати в застосунку. Тимчасова "латка" — sessionAffinity: ClientIP на Service. Вона не вирішує проблему (поди перезапускаються, HPA додає нові) і ламає рівномірний розподіл.

app/core/rate_limiting.py (ідея Redis-версії)
import time
from redis.asyncio import Redis

redis = Redis.from_url(settings.REDIS_URL)

async def hit(scope: str, ip: str, max_requests: int, window: int) -> bool:
    bucket = int(time.time() // window)
    key = f"rl:{scope}:{ip}:{bucket}"
    async with redis.pipeline(transaction=True) as pipe:
        pipe.incr(key)
        pipe.expire(key, window)
        count, _ = await pipe.execute()
    return count <= max_requests      # спільний лічильник для всіх подів

Кейс 2. Под API у циклі OOMKilled під час генерації маршрутів

Симптом: kubectl get pods показує RESTARTS 7, а kubectl describe pod — Last State: Terminated, Reason: OOMKilled, Exit Code: 137. Збігається в часі з великими запитами на оптимізацію.

Причина: солвер OR-Tools запущено прямо в запиті (а не в Celery), і на 300+ доставках він з'їдає понад 512Mi ліміту. Python не отримує MemoryError: ядро вбиває процес ззовні, і всі паралельні запити цього пода теж падають.

Виправлення: важкі обчислення — тільки у воркері (optimize_routes_task) з окремою чергою і більшим лімітом пам'яті. В API — швидка відповідь 202 Accepted + id задачі. Плюс верхня межа розміру задачі (кількість зупинок) і time_limit солвера. Ліміт пам'яті підбирайте за реальними піками (Prometheus container_memory_working_set_bytes), а не навмання.

Кейс 3. Під час кожного деплою кілька секунд 502/503

Симптом: моніторинг показує сплеск 502 саме у вікні rolling update, хоча maxUnavailable: 0.

Причини (зазвичай кілька одразу): (а) немає readiness probe, тож новий под отримує трафік до завершення старту; (б) немає preStop: старий под закривається раніше, ніж ingress прибере його з upstream-ів; (в) процес не обробляє SIGTERM (shell-форма CMD: PID 1 — sh, сигнал до uvicorn не доходить, через 30 с SIGKILL рве з'єднання).

Виправлення: readiness probe, preStop: sleep 5, exec-форма CMD, terminationGracePeriodSeconds більший за preStop + найдовший запит, --timeout-graceful-shutdown у uvicorn. Перевірка: прогнати hey/k6 під час kubectl rollout restart і переконатися, що помилок 0.

Кейс 4. Повільна БД перезапустила всі поди одночасно

Симптом: Postgres на 2 хвилини сповільнився (vacuum, бекап). За цей час усі поди API пішли в рестарт, сервіс лежав повністю ще кілька хвилин після відновлення БД.

Причина: liveness probe робила SELECT 1. Проблема залежності перетворилася на рестарти, а рестарти — на "грім" з нових з'єднань до БД, що щойно отямилась (thundering herd).

Виправлення: liveness перевіряє лише сам процес (/health без залежностей). Перевірка БД — тільки в readiness, і то обережно: якщо БД недоступна для всіх, readiness прибере всі поди, і клієнти отримають 503 від ingress замість зрозумілої помилки від застосунку. Часто розумніше лишити под ready і віддавати 503 з застосунку з retry-after.

Кейс 5. CrashLoopBackOff одразу після першого деплою

Симптом: поди в CrashLoopBackOff, паузи між рестартами ростуть (10 с, 20 с, 40 с… до 5 хв).

Діагностика:

terminal
kubectl -n planner get pods

Типові причини для цього проєкту: pydantic ValidationError при старті (наприклад, CORS_ORIGINS у ConfigMap — не валідний JSON); відсутній Secret (CreateContainerConfigError, це ще до запуску процесу); DATABASE_URL вказує на localhost — дефолт з config.py, бо змінна не прийшла; readOnlyRootFilesystem: true, а щось пише в /tmp. Для останнього змонтуйте emptyDir у /tmp.

Кейс 6. Три поди одночасно запускають alembic

Симптом: у логах деплою DuplicateTable або UniqueViolation на alembic_version, частина подів падає, частина ні.

Причина: міграція в initContainer (або в entrypoint-скрипті alembic upgrade head && uvicorn ...). Кожен под мігрує сам, паралельно.

Виправлення: один Job перед rollout-ом (розділ 8). Якщо initContainer неминучий — pg_advisory_lock у env.py Alembic перед run_migrations(), щоб інші чекали. Плюс expand/contract, бо стара версія коду ще працює.

Кейс 7. Маршрути "загубились" під час scale-down воркерів

Симптом: користувач запустив генерацію маршрутів, статус назавжди "в процесі". Збігається з моментом, коли KEDA зменшила кількість воркерів.

Причина: з налаштуваннями Celery за замовчуванням (acks_late=False) задача підтверджується брокеру при отриманні. Под отримав SIGTERM, не встиг дорахувати за grace period, отримав SIGKILL — і задача зникла.

Виправлення: task_acks_late=True, task_reject_on_worker_lost=True, terminationGracePeriodSeconds більший за time_limit задачі, ідемпотентна задача, плюс "сторож" (CronJob), що переводить задачі, які зависли в статусі "в процесі" довше за N хвилин, у failed або перезапускає їх. Зверніть увагу на visibility_timeout Redis-брокера (за замовчуванням 1 година): довга задача з acks_late, що перевищить його, буде видана іншому воркеру вдруге.

Кейс 8. p99 latency стрибає, хоча CPU "лише 40%"

Симптом: середня затримка нормальна, p99 — сотні мілісекунд, kubectl top показує помірний CPU.

Причина: limits.cpu: 500m. CFS дає контейнеру 50 мс CPU-часу на кожні 100 мс. Сплеск (серіалізація великої відповіді, pydantic-валідація списку з 1000 доставок) вичерпує квоту на початку періоду, і процес простоює до кінця вікна. Метрика container_cpu_cfs_throttled_periods_total росте.

Виправлення: прибрати CPU limit або підняти його; правильно задати requests; CPU-важке — у воркери. І пам'ятайте, що os.cpu_count() у контейнері повертає кількість ядер ноди, а не ліміт пода. Бібліотеки, що за нею вибирають кількість потоків (numpy/BLAS, частина OR-Tools-налаштувань, gunicorn -w $(nproc)), запускають забагато потоків. Задавайте явно: OMP_NUM_THREADS, кількість воркерів через env.

Кейс 9. Поди вічно Pending

Симптом: STATUS Pending, у describe — 0/3 nodes are available: 3 Insufficient memory або node(s) had untolerated taint.

Причини і виправлення: requests більші, ніж вміщує будь-яка нода (воркер просить 4Gi на нодах з 4Gi, з яких системі вже зайнято частину) → менші requests або більший тип нод; немає автоскейлера нод → увімкнути Cluster Autoscaler/Karpenter; taint на нодах (наприклад, GPU-пул) → tolerations або інший пул; PVC в іншій зоні доступності, ніж вільні ноди → volumeBindingMode: WaitForFirstConsumer у StorageClass.

Кейс 10. Service є, а запити отримують "connection refused"

Симптом: ingress віддає 503, а kubectl get endpointslices -l kubernetes.io/service-name=api показує порожній список адрес.

Причини: selector Service (app: api) не збігається з labels подів (app: planner-api); усі поди not-ready (readiness падає → дивіться кейс 4); targetPort вказує на ім'я порту, якого в контейнері немає; uvicorn слухає 127.0.0.1 замість 0.0.0.0 (в нашому CMD правильно).

terminal
kubectl -n planner get pods --show-labels
kubectl -n planner describe svc api                 # Selector, TargetPort, Endpoints
kubectl -n planner port-forward deploy/api 8000:8000 &  curl localhost:8000/health   # в обхід Service
kubectl -n planner run tmp --rm -it --image=curlimages/curl -- curl -sv http://api/health  # зсередини кластера

15 План переїзду з Fly.io по кроках

Порядок, у якому зміни мінімізують ризик. Кожен крок окремо корисний, навіть якщо до k8s так і не дійдете.

  1. Підготувати код (ще на Fly.io): rate limiter у Redis (кейс 1), /health/ready, заборона небезпечних дефолтів у production, acks_late + ідемпотентні задачі, структуровані JSON-логи в stdout (туторіал 11). Після цього можна сміливо ставити 2+ машини навіть на Fly.io.
  2. Образ: multi-stage, non-root, тег = git SHA, сканування в CI.
  3. Локально: kind-кластер, Kustomize base, прогнати API + worker + migrate Job проти docker Postgres/Redis.
  4. Інфраструктура: managed кластер (Terraform/OpenTofu), managed Postgres і Redis, ingress-контролер або Gateway, cert-manager, External Secrets, metrics-server, KEDA.
  5. Staging overlay + GitOps (Argo CD), навантажувальний тест, перевірка rolling update без помилок (кейс 3) і kill-тест воркера (кейс 7).
  6. Observability: Prometheus/Grafana або managed-аналог, алерти на OOMKilled, CrashLoopBackOff, throttling, довжину черги; Sentry (туторіал 26).
  7. Переключення: знизити TTL DNS заздалегідь, розгорнути prod, перевести DNS, тримати Fly.io теплим кілька днів для відкату.

Частина III · Питання зі співбесід
A

Kubernetes для бекенд-розробника

Питання, які ставлять Python-бекендерам, а не DevOps-інженерам: як ваш сервіс поводиться в кластері.

01БазаЧим Pod відрізняється від Deployment і навіщо між ними ReplicaSet?

Pod — один екземпляр (1+ контейнерів зі спільними мережею і томами), смертний і незамінний: якщо його видалити, він не повернеться сам. ReplicaSet підтримує N однакових подів. Deployment керує ReplicaSet-ами: при зміні шаблону створює новий ReplicaSet і поступово переносить репліки, старі ReplicaSet-и лишаються для rollback (revisionHistoryLimit). Руками поди і ReplicaSet-и майже ніколи не створюють.

02ПасткаЩо перевіряти в liveness probe, а що в readiness?

Liveness — лише "процес живий і не завис" (дешевий ендпоінт без залежностей). Readiness — "можна слати трафік" (прогрів, пул з'єднань). Перевірка БД у liveness перетворює збій БД на масові рестарти і thundering herd. Startup probe захищає повільний старт від передчасного liveness-вбивства.

Що перевіряють: розуміння, що liveness = рестарт, readiness = виключення з ротації, і каскадних відмов.
03БазаЧим requests відрізняються від limits?

requests — що гарантується і що враховує scheduler (і HPA для відсотка CPU). limits — стеля: перевищення пам'яті = OOMKilled (exit 137), перевищення CPU = throttling без вбивства. Від їх співвідношення залежить QoS-клас (Guaranteed / Burstable / BestEffort) і порядок виселення при нестачі пам'яті на ноді.

04ПасткаЧому застосунок з in-memory кешем або rate limiter працює неправильно після масштабування?

Кожен под — окремий процес з окремою пам'яттю, а Service розподіляє запити між подами. Лічильники, сесії, кеші стають "по одному на под": ліміти множаться на кількість реплік, кеш неконсистентний. Стан треба виносити в Redis/БД. Sticky sessions лише маскують проблему. У цьому проєкті саме так влаштований rate_limit_by_ip.

05БазаЯк відбувається graceful shutdown пода?

Под отримує Terminating; паралельно його видаляють з ендпоінтів і запускають preStop. Потім SIGTERM процесу, і після terminationGracePeriodSeconds (рахується від початку) — SIGKILL. Застосунок має перестати брати нові з'єднання і дообробити поточні; preStop sleep закриває "гонку" з оновленням ендпоінтів. CMD в exec-формі, щоб сигнал дійшов до процесу.

06ПасткаЯк запускати міграції БД при деплої в k8s?

Одним Job-ом (крок CI, Helm pre-upgrade hook, Argo PreSync) до оновлення Deployment, а не в кожному поді. Міграції — зворотно сумісні (expand/contract), бо при rolling update стара версія коду працює з новою схемою. Якщо міграції запускаються в кількох місцях — advisory lock.

07БазаЯкі типи Service існують?

ClusterIP (внутрішня віртуальна IP + DNS, за замовчуванням), NodePort (порт на кожній ноді), LoadBalancer (хмарний балансер), ExternalName (CNAME на зовнішній хост), Headless (clusterIP: None — DNS повертає IP подів напряму, для StatefulSet). HTTP-маршрутизацію за доменами робить Ingress або Gateway API.

08ПасткаЧи шифрує Kubernetes Secret?

Ні: значення лише в base64. Захист — RBAC, шифрування etcd at rest (часто через KMS), зберігання джерела секретів поза git (External Secrets Operator, Sealed Secrets, SOPS), а також не логувати env. Хто може створювати поди в namespace, той фактично може прочитати його секрети.

09ПоглибленоЯк масштабувати Celery-воркерів правильно?

За довжиною черги, а не за CPU: KEDA з Redis-тригером. Окремі черги й Deployment-и для CPU- і I/O-задач, acks_late + ідемпотентність, grace period більший за найдовшу задачу, max-tasks-per-child від витоків пам'яті, beat — рівно одна репліка або CronJob.

10ПоглибленоЧому в Python-сервісах часто не ставлять CPU limit?

CPU limit реалізований CFS-квотою на період 100 мс: короткий сплеск вичерпує квоту, і процес чекає до кінця періоду. Це дає хвости latency при помірному середньому CPU. Requests дають справедливий розподіл при конкуренції і без limit. Memory limit, навпаки, ставлять завжди, бо пам'ять не "стискається".

11СистемноKubernetes чи PaaS (Fly.io, Cloud Run, ECS) для нового продукту?

Для 1–3 сервісів і малої команди — PaaS або serverless-контейнери: менше операційних витрат, ті самі контейнери, автоскейл і rolling deploy. Kubernetes — коли сервісів багато, потрібна платформна однорідність, специфічні навантаження (GPU, оператори, on-prem) або вже є платформна команда. Головне — 12-factor код (конфіг з env, stateless процеси, логи в stdout), тоді переїзд між платформами дешевий.

12СистемноЩо таке GitOps і чим він кращий за "kubectl apply з CI"?

Бажаний стан кластера лежить у git, а агент у кластері (Argo CD, Flux) постійно його синхронізує. CI не потребує креденшалів до кластера, кожна зміна має аудит через PR, ручні зміни в кластері (drift) виявляються і відкочуються, rollback = git revert. Ціна — ще один компонент і окреме рішення для секретів.

13ПасткаПод у CrashLoopBackOff. Ваші перші три команди?

kubectl describe pod (Events: образ, probes, OOMKilled, помилки конфігу), kubectl logs --previous (логи впалого запуску, а не поточного), kubectl get events --sort-by=.lastTimestamp. Далі — перевірити exit code: 137 = SIGKILL/OOM, 1 = виняток застосунку (часто валідація конфігу), 143 = SIGTERM.
