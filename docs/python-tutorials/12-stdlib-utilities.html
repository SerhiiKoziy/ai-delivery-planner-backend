Частина I · collections

1 Counter — підрахунок частот без ручних циклів

python
from collections import Counter

statuses = ["geocoded", "geocoded", "geocode_failed", "geocoded"]
Counter(statuses)
# Counter({'geocoded': 3, 'geocode_failed': 1})

Counter(statuses).most_common(1)
# [('geocoded', 3)]  -- найчастіше значення

Counter — підклас dict, спеціалізований для підрахунку. Без нього довелось би вручну писати defaultdict(int) + цикл += 1. У цьому проєкті — природний кандидат для підсумку результатів імпорту доставок: Counter(row.status for row in import_result.rows) дав би "скільки успішних, скільки провалених" одним рядком.

2 defaultdict — уникнення KeyError без .get()

app/core/rate_limiting.py — реальний код з проєкту
from collections import defaultdict, deque

_WINDOWS: dict[str, deque] = defaultdict(deque)
# звернення до НЕІСНУЮЧОГО ключа автоматично створює порожній deque() -- без if/KeyError

def _check_and_record(key, ...):
    window = _WINDOWS[key]   # перший запит з нової IP -- deque() створюється сам

defaultdict(factory) викликає factory() автоматично при зверненні до відсутнього ключа, замість кидати KeyError. У реальному коді проєкту це прибирає потребу писати if key not in _WINDOWS: _WINDOWS[key] = deque() перед кожним використанням.

Аналогія з фронтендом
Схоже на obj[key] ??= [] в сучасному JS (nullish coalescing assignment) — та сама ідея "якщо ключа нема, підстав дефолтне значення", тільки defaultdict робить це автоматично на кожному зверненні, а не разовим присвоєнням.

3 namedtuple — легкий record-тип

python
from collections import namedtuple

Point = namedtuple("Point", ["x", "y"])
p = Point(1, 2)
p.x, p.y        # (1, 2) -- доступ за іменем, не лише за індексом
p == Point(1, 2) # True -- порівняння за значенням, як у tuple

namedtuple — незмінний (immutable, туторіал 5), легковісний record-тип: займає стільки ж пам'яті, скільки звичайний tuple, але дозволяє звертатись до полів за іменем. У сучасному коді для нових проєктів частіше обирають @dataclass(frozen=True) (туторіал 7) — зручніший синтаксис визначення, підтримка type hints — але namedtuple досі трапляється в старішому коді й у бібліотеках, де важлива сумісність із звичайним tuple (розпакування, індексація).

4 ChainMap — шаруваті конфігурації без злиття словників

python
from collections import ChainMap

defaults = {"timeout": 10, "retries": 3}
env_overrides = {"timeout": 30}   # напр., зі змінних середовища

config = ChainMap(env_overrides, defaults)
config["timeout"]   # 30 -- бере з ПЕРШОЇ карти, де ключ знайдено
config["retries"]   # 3  -- відсутній в env_overrides, бере з defaults

ChainMap не копіює й не зливає словники — тримає посилання на всі й шукає ключ по черзі в кожному, зупиняючись на першому знайденому. Зміна в env_overrides одразу видно через config, без повторного об'єднання. Типовий випадок використання — саме шарувата конфігурація: аргументи командного рядка → змінні середовища → значення за замовчуванням.

5 deque — O(1) додавання й видалення з обох кінців

Уже згадувалось у туторіалі 6 (Big O) — тут повний приклад того, чому саме deque, а не list, обраний для rate limiter-а проєкту.

app/core/rate_limiting.py — реальний код з проєкту
def _check_and_record(key, max_requests, window_seconds):
    now = time.monotonic()
    window = _WINDOWS[key]
    while window and now - window[0] > window_seconds:
        window.popleft()          # видалення з ПОЧАТКУ -- O(1) для deque, O(n) для list
    if len(window) >= max_requests:
        raise HTTPException(...)
    window.append(now)             # додавання в КІНЕЦЬ -- O(1) для обох

Ковзне вікно rate limiter-а постійно видаляє "застарілі" мітки часу з початку черги й додає нові в кінець. Зі звичайним list, list.pop(0) — O(n) (весь список зсувається); з deque — O(1) в обох напрямках, бо реалізований як двозв'язний список блоків, а не суцільний масив.

Частина II · functools і не тільки

6 functools.partial — часткове застосування функції

app/core/rate_limiting.py — реальний патерн з проєкту (концептуально те саме)
from functools import partial

def rate_limit_by_ip(scope, max_requests, window_seconds):
    def _dependency(request):
        _check_and_record(f"{scope}:{request.client.host}", max_requests, window_seconds)
    return _dependency

# еквівалентно було б написати через partial:
register_rate_limiter = partial(_check_and_record, scope="register", max_requests=5, window_seconds=3600)

functools.partial(fn, *args, **kwargs) "заморожує" частину аргументів функції наперед, повертаючи нову функцію, яка приймає лише решту. Проєкт досягає того самого ефекту (розділ 10, туторіал 7 про декоратори) через фабрику функцій-замикань rate_limit_by_ip(...) — обидва підходи ідіоматичні, partial коротший для простих випадків без потреби в додатковій логіці всередині.

7 functools.singledispatch — поліморфізм без ланцюжка isinstance

python
from functools import singledispatch

@singledispatch
def to_response(value):
    raise TypeError(f"unsupported type: {type(value)}")

@to_response.register
def _(value: DeliveryRef) -> dict:
    return {"id": str(value.id), "customer": value.customer_name}

@to_response.register
def _(value: VehicleRef) -> dict:
    return {"id": str(value.id), "plate": value.plate_number}

to_response(some_delivery_ref)   # автоматично викликає ПРАВИЛЬНУ версію за типом аргументу

Без singledispatch довелось би писати if isinstance(value, DeliveryRef): ... elif isinstance(value, VehicleRef): ... — ланцюжок, що росте й стає крихким з кожним новим типом. singledispatch реєструє окрему реалізацію на кожен тип, і Python сам обирає потрібну під час виклику — той самий принцип, що й перевантаження функцій (function overloading) у типізованих мовах, тільки за одним аргументом і в рантаймі.

8 functools.reduce — і чому Python-спільнота його уникає

python
from functools import reduce

total = reduce(lambda acc, d: acc + d.total_distance_km, routes, 0)

# Pythonic-альтернатива, яку обере більшість ревʼюерів:
total = sum(d.total_distance_km for d in routes)

reduce — загальний "згорни список в одне значення" інструмент (той самий, що Array.prototype.reduce у JS), але Гвідо ван Россум свого часу навіть прибрав reduce з вбудованих функцій у Python 3 (лишивши в functools), бо для більшості випадків sum(), max(), чи звичайний цикл/comprehension (туторіал 7) читаються прозоріше. reduce лишається доречним для дійсно нетривіальної згортки, яку не покриває жоден вбудований варіант.

Аналогія з фронтендом
JS-розробники часто зловживають .reduce() там, де підійшов би простіший .map()/.filter() чи цикл — та сама культурна звичка "показати, що знаю reduce" існує і в Python-спільноті, і так само вважається менш ідіоматичною, коли є простіший варіант.

9 heapq і bisect — дві структури для впорядкованих даних

heapq
Мін-купа (min-heap) поверх звичайного списку. heapq.heappush/heappop — вставка й видалення найменшого елемента за O(log n).
Типовий випадок: черга з пріоритетом — "наступна задача на виконання" завжди найменша (найтерміновіша) без повторного сортування всього списку.
bisect
bisect.insort/bisect_left — бінарний пошук позиції у ВЖЕ відсортованому списку за O(log n), замість лінійного O(n) сканування.
Типовий випадок: вставити нову зупинку маршруту в список, уже відсортований за часом прибуття, не сортуючи список заново щоразу.

Обидва рятують від "давайте я просто відсортую весь список заново на кожній вставці" — O(n log n) щоразу замість O(log n) чи O(n) один раз.

10 Каверзні питання співбесіди

БазаЧим defaultdict відрізняється від звичайного dict.get(key, default)?
.get(key, default) повертає дефолт, але не зберігає його в словнику. defaultdict при зверненні до відсутнього ключа автоматично створює й записує нове значення в словник — наступне звернення до того самого ключа поверне вже збережене значення, а не щоразу новий дефолт.
ПасткаЧому deque, а не list, для черги, з якої часто видаляють елементи з початку?
list.pop(0) — O(n): усі елементи зсуваються на одну позицію. deque.popleft() — O(1), бо структура реалізована як зв'язка блоків, оптимізована для операцій з обох кінців, а не лише з кінця, як звичайний список.
БазаНавіщо потрібен functools.singledispatch, якщо можна просто написати ланцюжок isinstance?
Читабельність і розширюваність: кожен тип реєструє свою реалізацію окремою, незалежною функцією (можна навіть в іншому модулі), замість одного великого if/elif-блоку, що росте й стає крихким з кожним новим типом.
ПасткаЧому Python-спільнота часто уникає reduce, хоча він потужний?
Для більшості поширених згорток (сума, максимум, конкатенація) уже є прозоріші вбудовані варіанти (sum(), max(), comprehension) — reduce з lambda часто читається гірше за еквівалентний цикл чи comprehension, тому Гвідо ван Россум прибрав його з builtins у Python 3.
БазаКоли варто обрати heapq замість повторного list.sort()?
Коли елементи додаються/видаляються часто, а потрібен лише найменший (чи найбільший) елемент у будь-який момент — heapq підтримує цю операцію за O(log n) на вставку/видалення, тоді як повторне повне сортування списку — O(n log n) щоразу.
