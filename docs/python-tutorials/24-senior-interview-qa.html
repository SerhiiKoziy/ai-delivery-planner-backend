1

Мова та внутрішня кухня

Як насправді влаштований пошук атрибутів, множинне успадкування і декоратори — те, що відрізняє "вміє писати Python" від "розуміє Python".

01ПросунутеУ якому порядку Python шукає obj.attr?

Спочатку перевіряються дата-дескриптори (мають і __get__, і __set__), знайдені в MRO класу — вони мають пріоритет навіть над instance.__dict__. Потім — instance.__dict__. Потім — звичайні атрибути класу та нон-дата дескриптори (мають лише __get__ — наприклад, звичайні методи). Якщо нічого не знайдено — викликається __getattr__, якщо він визначений.

🎯 Що перевіряють: чи розумієте ви, чому property (дата-дескриптор) не можна "перебити" простим присвоєнням в self.__dict__, а звичайний метод (нон-дата дескриптор) — можна.
02ПросунутеЩо таке дескриптори і як на них побудований property?

Дескриптор — об'єкт-клас, що реалізує __get__/__set__/__delete__ і "перехоплює" доступ до атрибута іншого класу. property — це готовий дата-дескриптор, що під капотом зберігає ваші getter/setter-функції і викликає їх у __get__/__set__.

мінімальний дескриптор вручну
class Positive:
    def __set_name__(self, owner, name):
        self.name = "_" + name
    def __get__(self, obj, owner):
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value < 0: raise ValueError("must be positive")
        setattr(obj, self.name, value)

class Product:
    price = Positive()   # те саме, що @property, але перевикористовується між класами
03ПросунутеЩо таке MRO і C3-лінеаризація? Чому super() — не завжди "батьківський клас"?

MRO (Method Resolution Order) — послідовність, у якій Python шукає метод при множинному успадкуванні; обчислюється алгоритмом C3-лінеаризації, який гарантує консистентний порядок навіть у "діамантовому" успадкуванні (D(B, C), де B і C обидва наслідують A). super() повертає наступний клас саме за MRO, а не обов'язково "прямого батька" — у кооперативному множинному успадкуванні super().__init__() може викликати метод класу-"сусіда" по дереву, а не предка.

ClassName.__mro__ — подивитись реальний порядок.

04БазаРізниця @staticmethod, @classmethod і звичайного методу?

Звичайний метод отримує self (конкретний екземпляр). @classmethod отримує cls (сам клас) — типово для альтернативних конструкторів (Settings.from_env()). @staticmethod не отримує нічого автоматично — це звичайна функція, просто логічно "прописана" в класі як неймспейс.

05БазаЯк написати декоратор, що приймає власні аргументи?

Потрібен третій рівень вкладеності функцій: зовнішня функція приймає аргументи декоратора, повертає сам декоратор, який приймає функцію й повертає обгортку.

decorator factory
import functools

def retry(times: int):
    def decorator(func):
        @functools.wraps(func)          # зберігає __name__/__doc__ оригіналу
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    if attempt == times - 1: raise
        return wrapper
    return decorator

@retry(times=3)
def flaky_call(): ...

functools.wraps тут критично важливий — без нього flaky_call.__name__ став би "wrapper", ламаючи інтроспекцію й дебаг.

06ПросунутеЩо таке metaclass і де ви вже ним користуєтесь, навіть не помічаючи?

Metaclass — клас, екземплярами якого є самі класи (за замовчуванням — type). Кастомний metaclass дозволяє втручатись у створення класу: валідувати атрибути, авто-реєструвати підкласи, збирати оголошені поля в схему.

🎯 Пов'язано з проєктом: і SQLAlchemy (DeclarativeBase), і Pydantic (BaseModel) — обидва вже використовуються в цьому бекенді — покладаються саме на metaclass-механізм, щоб на етапі визначення вашого класу (class User(Base): ...) зібрати оголошені Mapped[...]-поля в реальну схему таблиці/валідації. Ви пишете звичайний клас — вся магія відбувається в metaclass, непомітно.

Пам'ять і продуктивність

Як CPython реально керує пам'яттю, коли reference counting не рятує, і чим профілювати прод.

07ПросунутеЯк влаштоване керування пам'яттю в CPython: чому мало самого reference counting?

Базовий механізм — підрахунок посилань (кожен об'єкт видаляється миттєво, щойно лічильник падає до нуля). Проблема: циклічні посилання (об'єкт А посилається на Б, Б — на А) ніколи не досягнуть нуля самі по собі, навіть якщо ззовні на них ніхто не посилається — витік пам'яті. Тому CPython додатково має поколінний (generational) garbage collector (gc-модуль), який періодично шукає й прибирає саме такі цикли, окремо від reference counting.

08ПросунутеЩо таке __slots__ і коли він реально вартий того?

Обмежує набір атрибутів екземпляра фіксованим списком і прибирає per-instance __dict__ — суттєва економія пам'яті (і трохи швидший доступ до атрибутів), помітна, коли створюються мільйони дрібних об'єктів (наприклад, вузли графа, рядки датасету). Компроміс: не можна динамічно додавати нові атрибути, ускладнюється множинне успадкування з різними __slots__, і потрібно окремо додати "__weakref__" у слоти, якщо об'єкт має підтримувати weak references.

09ПросунутеНавіщо потрібен weakref?

Дозволяє посилатись на об'єкт, не збільшуючи його лічильник посилань — сам об'єкт може бути видалений збирачем сміття, навіть якщо weak-посилання на нього досі існує (тоді воно просто поверне None). Класичні застосування: кеші, що не повинні самі утримувати об'єкт живим (WeakValueDictionary), і розрив природних циклів на кшталт "батько ↔ дитина" (дитина тримає weakref назад на батька замість звичайного посилання).

10БазаЯкими інструментами профілюють Python у продакшені?

cProfile — детермінований CPU-профайлер (скільки разів і скільки часу виконувалась кожна функція); line_profiler — профіль по конкретних рядках; tracemalloc/memory_profiler — де саме росте споживання пам'яті; py-spy — семплюючий профайлер, що вміє підключитись до вже запущеного прод-процесу без зміни коду й без значного оверхеду — саме тому його часто називають першим правильним інструментом, коли "щось повільне на проді, а передеплоїти з профайлером не можна".

11БазаЯка складність основних операцій list і dict?

list.append() — O(1) амортизовано; list.insert(0, x) і list.pop(0) — O(n) (зсув усіх елементів) — для черги FIFO варто collections.deque (O(1) з обох кінців). x in list — O(n). dict/set — get/set/in в середньому O(1) завдяки хеш-таблиці (звідси й вимога хешовності ключів — див. туторіал 4), у гіршому разі (масові хеш-колізії) — O(n), на практиці майже ніколи не трапляється.

ООП і патерни по-пайтонівськи

Класичні GoF-патерни в Python часто виглядають інакше, ніж у Java/C# — сеньйор повинен знати, коли "підручниковий" патерн тут зайвий.

12БазаЧому Python-спільнота проповідує композицію над успадкуванням?

Глибокі ієрархії успадкування + множинне успадкування + MRO швидко стають важкими для розуміння (crypto "чий саме метод виконався" — питання 03 вище). Композиція (об'єкт отримує залежності через конструктор, а не успадковує їхню поведінку) простіша для тестування (легко підмінити залежність-мок) і гнучкіша.

🎯 Пов'язано з проєктом: кожен сервіс у цьому бекенді (DeliveryService, RouteOptimizerService) отримує репозиторії й клієнтів через конструктор (композиція + DI), а не успадковує їх — саме тому кожен шматок легко підмінити в тестах окремо.
13БазаЯк влаштований протокол контекстного менеджера (with)?

__enter__ викликається на вході в блок with (результат — те, що потрапляє в as x); __exit__(exc_type, exc_val, exc_tb) викликається завжди на виході, навіть при винятку всередині блоку — і якщо поверне True, виняток вважається "погашеним" і далі не поширюється. contextlib.contextmanager дозволяє написати те саме генератором з одним yield: код до yield = __enter__, код після (в finally) = __exit__.

🎯 Пов'язано з проєктом: async with AsyncSessionLocal() as session в app/db/session.py — саме цей протокол гарантує, що сесія БД закриється, навіть якщо запит впаде з винятком посередині.
14ПасткаEAFP vs LBYL — і чому EAFP не рятує від race condition

EAFP ("легше просити пробачення, ніж дозволу") — Pythonic-стиль: спробувати дію в try, зловити виняток, якщо не вдалось (try: return d[k] except KeyError: ...). LBYL ("подивись, перш ніж стрибнути") — явна перевірка перед дією (if k in d: ...), звичніша для C-подібних/JS-мов.

Пастка: EAFP в одному потоці Python-коду вирішує проблему "красивого коду", але не вирішує race condition між кількома процесами/запитами до спільного ресурсу — між "спробою" і фактичною дією все одно є вікно, якщо ресурс зовнішній (файл, рядок у БД). Реальний захист там — атомарна операція на рівні самого ресурсу.

🎯 Пов'язано з проєктом: саме тому try_consume_quota в organization_repository.py — не EAFP-код ("спробуй інкремент, зловй помилку перевищення"), а один атомарний SQL UPDATE ... WHERE — єдиний спосіб дійсно унеможливити перегін двох паралельних запитів (детальніше — туторіал 2).
15ПросунутеНавіщо потрібна варіантність (variance) у TypeVar?

TypeVar("T", covariant=True) дозволяє статичному чекеру вважати Container[Cat] сумісним із Container[Animal], якщо Container лише повертає T (read-only). Контраваріантність — навпаки, для типів, які лише приймають T як аргумент. Без правильної варіантності статичний чекер або занадто суворий (відкидає безпечний код), або пропускає реальні помилки типів у generic-класах.

16ПасткаЯк правильно зробити Singleton у Python?

Найчастіше — ніяк спеціально не треба: модуль сам по собі вже сінглтон (Python імпортує й виконує його рівно один раз, кешуючи в sys.modules), тому просто оголосити об'єкт на рівні модуля вже дає той самий ефект, що "класичний" Singleton-патерн у Java. Другий ідіоматичний спосіб — @lru_cache на функції без аргументів: перший виклик створює об'єкт, усі наступні повертають той самий закешований екземпляр.

🎯 Пов'язано з проєктом: буквально так побудований get_settings() в app/core/config.py — @lru_cache def get_settings() -> Settings: return Settings() — це і є Singleton, без жодного __new__-оверрайду чи класичного патерну з підручника.

Просунута асинхронність

За межами "що таке event loop" (це вже в туторіалі 6) — структуроване скасування, обмеження конкурентності, паттерни.

17Пасткаasyncio.gather vs asyncio.TaskGroup — у чому небезпека gather?

asyncio.gather(*tasks) без return_exceptions=True: щойно перша задача кидає виняток, він одразу летить назовні — але задачі, що вже запущені й ще не завершились, продовжують виконуватись у фоні, ніхто їх не скасовує автоматично. Це реальна пастка (можливий витік ресурсів/незавершені запити). asyncio.TaskGroup (з 3.11) вирішує це структурно: якщо одна задача в групі падає, всі інші задачі групи автоматично скасовуються, а винятки збираються в ExceptionGroup.

18ПасткаЧому не можна просто "проковтнути" asyncio.CancelledError?

Скасування задачі (task.cancel()) кидає CancelledError у найближчій точці await всередині неї. З Python 3.8 цей виняток успадковує BaseException, а не Exception — саме тому except Exception: його не зловить випадково. Але голий except: зловить — і якщо після цього не зробити raise повторно, скасування "тихо зникає": задача, яку хтось явно попросив зупинитись, продовжує жити. Правило: ловити CancelledError можна лише для очищення ресурсів, і завжди re-raise-ити його після.

19БазаНавіщо asyncio.Semaphore, якщо asyncio і так конкурентний?

asyncio сам по собі не обмежує, скільки задач можуть одночасно чекати на I/O — технічно можна запустити тисячу одночасних HTTP-запитів. Але зовнішній сервіс (платний API) має власні ліміти й може почати відповідати 429/повільно, якщо "заллити" його запитами одночасно. asyncio.Semaphore(n) обмежує, скільки await-операцій усередині нього виконуються одночасно — природний throttle для конкурентних викликів до зовнішнього API.

🎯 Пов'язано з проєктом: клієнти до OpenAI й Google Geocoding в цьому бекенді викликаються по одному на HTTP-запит, тож семафор поки не потрібен — але якби (як обговорено в туторіалі 2, п. 7) геокодування рядків імпорту запустили паралельно через gather, саме Semaphore став би правильним інструментом не перевищити ліміти Google Maps API.
20ПросунутеКоли обрати asyncio.Queue, а не gather?

gather вимагає знати весь список задач заздалегідь — підходить для "виконати N відомих операцій паралельно і дочекатись усіх". asyncio.Queue — паттерн виробник/споживач: підходить, коли робота з'являється потоково (наприклад, довга черга завдань, вебсокет-повідомлення) і потрібен фіксований пул "воркерів", що розбирають чергу, плюс backpressure "з коробки" (обмежений maxsize черги блокує виробника, якщо споживачі не встигають).

5

Бази даних та ORM

Питання, де "теоретично знаю SQL" і "реально розумію, що робить ORM під капотом" — це дві різні співбесіди.

21БазаЩо таке N+1 query problem і як SQLAlchemy її вирішує?

Отримали список із N батьківських рядків одним запитом, а потім у циклі окремо запитали пов'язані дані для кожного — разом N+1 запитів замість 1-2. Фікс у SQLAlchemy — eager loading: selectinload(Model.relationship) робить один додатковий пакетний запит WHERE id IN (...) для всіх пов'язаних рядків одразу; joinedload(...) замість цього робить один JOIN одразу.

22Системний дизайнЯк пул з'єднань до БД обмежує горизонтальне масштабування?

Кожен інстанс застосунку тримає власний пул з'єднань до Postgres. При N інстансах сумарна кількість відкритих з'єднань ≈ N × (розмір пулу на інстанс), і це не повинно перевищувати max_connections бази — інакше нові з'єднання почнуть відхилятись. Рішення — pgbouncer/вбудований пулер хмарного Postgres у transaction-режимі, куди всі інстанси підключаються через набагато менший спільний пул реальних з'єднань.

🎯 Пов'язано з проєктом: саме тому db/session.py має connect_args={"statement_cache_size": 0} — код уже готовий коректно працювати за таким пулером (детальніше — туторіал 3, крок E).
23ПросунутеЩо таке рівні ізоляції транзакцій — і чи завжди вони потрібні для захисту від race condition?

READ COMMITTED (типовий дефолт Postgres) не бачить незакомічені зміни інших транзакцій, але дозволяє non-repeatable read (той самий рядок може віддати інше значення при повторному читанні в межах однієї транзакції). SERIALIZABLE — найсуворіший рівень, поводиться так, ніби транзакції виконались послідовно, ціною можливих retry при конфліктах.

Нюанс: не завжди потрібно підвищувати ізоляцію, щоб убезпечитись від race condition — часто достатньо зробити перевірку-і-запис однією атомарною командою (UPDATE ... WHERE умова) навіть на звичайному READ COMMITTED, бо атомарність тут гарантує сама СУБД на рівні одного рядка, а не рівень ізоляції транзакції.

24БазаКоли індекс шкодить, а не допомагає?

Індекс пришвидшує читання (WHERE/JOIN/ORDER BY по індексованій колонці), але кожен INSERT/UPDATE мусить додатково оновити й сам індекс — на write-важких таблицях забагато індексів помітно сповільнює запис. Порядок колонок у складеному (композитному) індексі теж критичний: індекс (organization_id, created_at) ефективно обслуговує фільтр лише по organization_id або по обох полях разом, але не фільтр лише по created_at окремо.

Тестування

Senior-рівень тут — не "знаю pytest", а розуміння, де мокати правильно, а де тест перестає щось перевіряти.

25ПасткаЧим небезпечний надмірний мокінг (over-mocking)?

Якщо замокати занадто глибоко (наприклад, саму ORM-сесію чи внутрішній метод сервісу, який тестується), тест перестає перевіряти реальну поведінку системи й починає перевіряти лише те, що ваш мок повертає те, що ви самі йому сказали повернути — хибне відчуття покриття. Правило: мокайте на межі системи (зовнішній HTTP-виклик, сторонній SDK), а не внутрішню логіку, яку якраз і тестуєте.

🎯 Пов'язано з проєктом: DI через Depends (туторіал 1) робить правильний мокінг тривіальним — app.dependency_overrides[get_openai_client] = lambda: fake_client підміняє рівно межу системи (зовнішній SDK), лишаючи всю внутрішню логіку сервісу реальною й перевіреною.
26БазаДе межа між unit, integration і e2e тестами на практиці?

Unit — одна функція/клас в ізоляції, усі залежності замоковані. Integration — кілька реальних компонентів разом (наприклад, реальна тестова БД замість моку сесії). E2E — весь стек разом, включно з HTTP-шаром, найближче до реального користувацького сценарію. У типовому FastAPI-проєкті "API-тести" (запит через тестовий HTTP-клієнт до реальної тестової БД) фактично лежать посередині — це integration, а не чистий unit.

27ПросунутеЩо таке property-based testing (Hypothesis) і коли він доречніший за приклади?

Замість заздалегідь підібраних прикладів вхід/вихід, ви описуєте інваріант ("для будь-якого валідного входу X — властивість Y завжди тримається"), а бібліотека (наприклад, Hypothesis) сама генерує сотні рандомізованих, включно з крайніми, вхідних значень і шукає контрприклад. Доречно для чистих функцій із чіткими математичними властивостями (парсери, серіалізація/десеріалізація, нормалізація даних) — саме там, де приклад-орієнтовані тести найлегше пропускають крайній випадок, про який автор просто не подумав.

Системний дизайн (лайт)

Не повноцінний system design interview, а невеликі, дуже практичні питання, які часто вплітають у "звичайну" Python-співбесіду. Повноцінний розбір теорії й 10 класичних кейсів формату "спроєктуйте X" — окремо, у туторіалі 25.

28Системний дизайнЩо таке ідемпотентність API і навіщо вона потрібна для платних операцій?

Ідемпотентний запит можна безпечно повторити (наприклад, після мережевого таймауту, коли клієнт не знає, чи дійшла перша спроба) — результат буде той самий, без побічних подвійних ефектів. Типова реалізація: клієнт передає унікальний Idempotency-Key, сервер зберігає його разом із результатом першого виконання й на повторний запит з тим самим ключем повертає закешовану відповідь, не виконуючи операцію вдруге.

🎯 Пов'язано з проєктом: POST /routes/optimize у цьому бекенді споживає платну, лічену квоту (маршрути/геокодування/AI-виклики) — без ідемпотентного ключа механічний retry на флакі-мережі з боку фронтенду міг би двічі списати квоту за одну й ту саму дію користувача.
29Системний дизайнFixed window vs sliding window vs token bucket для rate limiting — коли який?

Fixed window (лічильник, що скидається кожні N секунд) — найпростіший, але має "проблему межі вікна": до 2× дозволеного ліміту можна пропустити впритул до й одразу після межі вікна. Sliding window (лог таймстемпів чи зважений підрахунок) згладжує цю проблему ціною більшої пам'яті/обчислень. Token bucket — дозволяє короткі "сплески" до розміру відра, підтримуючи стабільний середній темп — найгнучкіший, типовий вибір для production API gateway.

🎯 Пов'язано з проєктом: app/core/rate_limiting.py у цьому бекенді — саме fixed window (детальніше — туторіал 2). Свідомий, простий вибір для поточного масштабу; token bucket був би природним апгрейдом, якби вимоги до точності ліміту зросли.
30Системний дизайнGraceful degradation — що робити, коли платний зовнішній сервіс падає?

Загальний принцип: віддати перевагу частково корисному результату над жорсткою відмовою всього запиту, якщо це можливо без шкоди коректності. Але це рішення приймається окремо для кожної фічі — деякі відмови справді мають "гучно" провалити весь запит, а не тихо деградувати.

🎯 Пов'язано з проєктом: два різні свідомі рішення в одному бекенді. GoogleGeocodingClient.geocode() повертає None при будь-якій помилці — доставка все одно створюється, просто зі статусом "geocode_failed", замість падіння всього запиту. А ось збій OpenAI (OpenAIError) навпаки — гучно повертає чіткий 503 клієнту (туторіал 2), бо для AI-фічі "мовчки повернути порожній результат" ввело б користувача в оману.

Черги повідомлень: RabbitMQ, Kafka, Celery

Ця тема жодного разу не зустрічається в туторіалах 1-23 (проєкт використовує лише Redis як брокер Celery) — а на співбесідах її питають майже завжди. Дев'ять питань нижче закривають типовий набір.

31БазаЗа рахунок чого RabbitMQ гарантує доставку повідомлень?

Комбінацією чотирьох механізмів, а не якимось одним "перемикачем":

  • Стійкість — черга оголошується durable (переживає рестарт брокера), повідомлення позначається delivery_mode=2 / persistent (пишеться на диск).
  • Підтвердження — publisher confirm каже видавцю, що брокер прийняв і зберіг повідомлення; consumer ack (basic_ack) каже брокеру, що споживач обробив його — без ack повідомлення повертається в чергу.
  • Реплікація — quorum queues (сучасний варіант) або застарілі mirrored queues копіюють повідомлення на кілька нод, щоб падіння однієї не губило дані.
  • Dead Letter Exchange — повідомлення, які не вдалось обробити, йдуть в окрему чергу для аналізу чи повторної обробки, а не губляться мовчки.
32Системний дизайнЯкі рівні гарантій доставки бувають у RabbitMQ і Kafka?

Обидва брокери дають той самий вибір із трьох рівнів, тільки різними механізмами:

  • At-most-once — найшвидше, повідомлення може загубитись: без publisher confirm / без чекання ack від брокера.
  • At-least-once — надійно, але можливі дублікати: persistent + durable + ack у RabbitMQ; ack від брокера продюсеру + ретраї у Kafka. Вимагає ідемпотентної обробки на споживачі.
  • Exactly-once — RabbitMQ сам по собі цього не гарантує, це будується поверх at-least-once через ідемпотентність застосунку; Kafka має нативну підтримку через enable.idempotence=true + транзакційний продюсер (transactional.id) + read_committed на споживачі.
🎯 Що перевіряють: чи розумієте ви, що "exactly-once" — це завжди компроміс складності, а не безкоштовна опція, і що в реальних системах найчастіше свідомо обирають at-least-once + ідемпотентність.
33ПросунутеЯк під капотом влаштована Kafka?

Kafka — розподілений append-only лог, а не черга в класичному сенсі. Кожна партиція — це файл, куди нові повідомлення лише дописуються в кінець (найшвидша можлива операція на диску), а прочитані повідомлення не видаляються одразу — вони живуть за retention-політикою (час/розмір), і різні консьюмери можуть незалежно "перемотувати" свій offset назад. Продуктивність тримається на zero-copy I/O (дані йдуть із page cache напряму в сокет, без зайвих копіювань у пам'яті процесу) та на паралелізмі партицій. Кластер із кількох брокерів реплікує кожну партицію (один лідер, кілька фолловерів), а метаданими й виборами лідера керує Zookeeper (застаріле) або вбудований KRaft (сучасні версії).

34БазаЩо таке топік і партиція в Kafka?

Топік — логічна назва каналу повідомлень (наприклад, order_status_changed); сам по собі він нічого не зберігає. Партиція — фізичний сегмент топіку: незалежний, впорядкований лог зі своїм лічильником offset. Kafka гарантує порядок повідомлень лише в межах однієї партиції, а не між партиціями того самого топіку — тому повідомлення з одним ключем (наприклад, user_id) свідомо направляють в одну й ту саму партицію, якщо порядок для цього ключа важливий.

35БазаЩо таке Dead Letter Exchange у RabbitMQ?

Спеціальний "запасний" exchange, куди RabbitMQ автоматично перенаправляє повідомлення, які не вдалось обробити: відхилені (nack/reject з requeue=False), протерміновані за TTL, або такі, що не влізли в чергу через ліміт розміру. Налаштовується аргументом x-dead-letter-exchange на звичайній черзі. Дає місце для аналізу помилок чи ручного/автоматичного повторного програвання замість того, щоб "погане" повідомлення губилось або нескінченно блокувало чергу.

36Системний дизайнЯк захиститись від невизнаних/недооброблених повідомлень брокера?

Три доповнюючі одна одну техніки:

  • Ручний ack/nack — вимкнути auto_ack; підтверджувати обробку явно після успіху, nack/reject при помилці (з requeue=True/False залежно від того, чи має сенс повторна спроба).
  • TTL + Dead Letter Exchange — повідомлення, необроблене за час X або після N невдалих спроб, автоматично йде в окрему чергу замість того, щоб нескінченно висіти "в польоті".
  • Ідемпотентність обробника — повторна доставка при збоях (краш споживача до ack) є нормою, а не винятком; зберігайте оброблені message_id (Redis/Postgres) і пропускайте дублікати.
37ПросунутеЧи є пріоритизація повідомлень у RabbitMQ, і чи переходить пріоритет між чергами?

Так, RabbitMQ підтримує priority queues: черга оголошується з x-max-priority (типово 5-10 рівнів), а кожне повідомлення публікується з полем priority — вищий пріоритет обробляється раніше, навіть якщо опубліковано пізніше; повідомлення з однаковим пріоритетом ідуть у порядку FIFO.

Але пріоритет ніколи не "переходить" між різними чергами — це не глобальний механізм кластера. Черга сама по собі є атомарною одиницею маршрутизації; якщо пріоритетна черга спорожніла, це ніяк не впливає на порядок в інших чергах. Якщо потрібна єдина пріоритизація — використовують одну чергу з x-max-priority, а не окремі черги "high"/"low".

38ПросунутеЯк Celery працює з пріоритетними задачами?

Через аргумент priority у apply_async(..., priority=9) — Celery кладе його в AMQP-властивість повідомлення, а RabbitMQ сортує чергу за ним (та сама черга мусить бути створена з x-max-priority). Обмеження варто знати заздалегідь: діапазон пріоритету — 0-9 (чи менше, скільки задано в x-max-priority); пріоритет діє лише в межах однієї черги, немає пріоритету між чергами high/low; Redis-брокер пріоритети не підтримує взагалі (лише RabbitMQ, частково SQS через хаки); а великий prefetch_count може звести пріоритет нанівець, якщо воркер вже "нахапав" низькопріоритетних задач наперед.

39Системний дизайнДва повідомлення в черзі змінюють те саме поле користувача — як обрати, яке застосувати?

Обробляти в порядку надходження в чергу небезпечно — мережеві затримки й ретраї можуть переставити повідомлення місцями. Два стандартні рішення:

  • event_time — кожне повідомлення несе час, коли зміну сформовано (не коли вона прийшла); споживач застосовує зміну, лише якщо event_time новіший за збережений у БД час останнього оновлення цього поля, інакше тихо ігнорує.
  • Версійність — повідомлення несе version/seq_id; застосовується, лише якщо version > поточна_версія_в_БД.

Без жодного з двох підходів виникає гонка між застарілою та актуальною подіями — особливо помітно при ретраях і паралельних воркерах.

40БазаЯк переконатись, що Celery-таска дійсно виконається?

Повної "гарантії" з коробки немає, але надійність збирають зі знайомих цеглинок: увімкнути result_backend, щоб мати змогу опитати статус і результат задачі; acks_late=True, щоб таска підтверджувалась брокеру лише після успішного виконання (а не одразу при отриманні воркером) — тоді краш воркера поверне задачу в чергу; моніторинг (Flower, Sentry, Prometheus) для видимості зависань і помилок; і власний try/except з ретраєм (self.retry(...)) навколо нестабільних кроків.

Docker, Kubernetes, Git

Проєкт реально використовує Docker (туторіал 12) і згадує Kubernetes як варіант масштабування (туторіал 3), але базові означення цих технологій — і git-флоу — досі ніде не пояснені окремо.

41БазаЧим Docker відрізняється від віртуальної машини?

Docker-контейнер ділить ядро ОС хоста й ізолює процеси на рівні операційної системи (namespaces, cgroups) — тому запускається за секунди, важить мегабайти, а продуктивність близька до нативної. Віртуальна машина через гіпервізор емулює повноцінне "залізо" й запускає власну ОС — тому старт займає хвилини, розмір вимірюється гігабайтами, а частина ресурсів іде на сам шар віртуалізації. Наслідок для практики: на одному сервері можна тримати сотні контейнерів, але лише одиниці-десятки повноцінних ВМ.

42БазаЯкі основні сутності є в Docker?

Image — незмінний, шаруватий шаблон (ОС + залежності + код), з якого запускають контейнери; кожен крок Dockerfile — окремий кешований шар. Container — запущений (або зупинений) екземпляр image, ізольований від хоста й інших контейнерів. Dockerfile — рецепт побудови image. Volume — сховище даних поза životним циклом контейнера (щоб дані бази чи логи не зникали разом з контейнером). Network — віртуальна мережа для взаємодії контейнерів (bridge — типова, на одному хості; host — мережевий стек хоста напряму; none — повна ізоляція; overlay — між хостами в Swarm).

43БазаЯка типова структура Dockerfile?

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0"]

FROM — базовий образ; ENV — змінні середовища контейнера; RUN — команди на етапі збірки (системні пакети, залежності); WORKDIR — робоча директорія для наступних кроків; COPY — копіювання файлів з хоста (файл залежностей копіюють окремо й раніше коду, щоб кеш Docker не злітав при кожній зміні коду); EXPOSE — декларативна документація порту (не відкриває його сам по собі); CMD — команда запуску контейнера.

45БазаЩо таке под і нода в Kubernetes?

Нода (node) — фізична чи віртуальна машина в кластері, на якій справді виконуються задачі: на ній працюють kubelet, kube-proxy і container runtime. Под (pod) — найменша одиниця розгортання в Kubernetes: один або кілька контейнерів, що завжди запускаються разом, ділять IP-адресу/порти й можуть ділити volume (типово — один контейнер на под, кілька — для sidecar-патернів на кшталт логера чи проксі). Кластер розподіляє поди по нодах з урахуванням ресурсів; якщо нода падає, Kubernetes пересоздає її поди на іншій доступній ноді.

46БазаЯк "перенести" чужий коміт у свою гілку?
cherry-pick
git checkout my-feature
git cherry-pick <commit_hash>

cherry-pick застосовує зміни одного конкретного коміту з іншої гілки поверх поточної, створюючи новий коміт із тим самим змістом — без злиття всієї гілки-джерела.

47ПросунутеЯк під капотом працює git merge?

Залежить від налаштування Merge Request: звичайний merge переносить усі коміти гілки-джерела в цільову гілку зі збереженням історії (merge-коміт із двома батьками). Якщо ввімкнено Squash commits, усі коміти гілки-джерела об'єднуються в один перед злиттям — зручно, коли в робочій гілці накопичилось багато дрібних "wip"-комітів, які не мають сенсу тягнути в основну історію окремо.

48ПасткаЯк терміново залити зміни в main?

Правильна відповідь на співбесіді — "все одно через Merge Request", навіть у терміновому випадку: CI (лінтери, тести) — це саме той запобіжник, який найдорожче обходити під тиском часу. Якщо процес абсолютно не дозволяє чекати на звичайний review-цикл — cherry-pick потрібного коміту в підготовлену гілку для хотфіксу з прискореним, але не пропущеним, review. --no-verify чи прямий push у main — це усвідомлений ризик, а не "хороша практика", і жодна співбесіда не зарахує це як правильну відповідь.

49БазаЩо таке Mock-об'єкт у тестуванні?

Підставний об'єкт, що імітує поведінку реального (БД, зовнішній API, файлова система) для ізоляції тестованого коду від залежностей. Дає три речі одразу: ізоляцію — тест не залежить від реальної мережі/БД; контроль — можна задати, що саме поверне метод (mock.return_value = ...); перевірку викликів — скільки разів і з якими аргументами метод був викликаний (mock.assert_called_with(...)). У Python — unittest.mock.Mock/MagicMock/patch.

🎯 Пов'язано з проєктом: туторіал 23 вже показує реальні fixtures і тести цього репозиторію — поверх over-mocking там же розібрана суміжна пастка (catF, розділ 25).
50ПросунутеЯк розв'язуються колізії хешів у dict?

CPython-словник — хеш-таблиця з відкритою адресацією: hash(key) визначає початковий індекс комірки в масиві; якщо вона зайнята (колізія — два різні ключі дали той самий індекс), інтерпретатор пробує наступну комірку за псевдовипадковою послідовністю кроків (не просто "+1", щоб уникнути кластеризації), поки не знайде вільну або комірку з тим самим ключем. При збігу хешів ключі додатково звіряються через __eq__ — саме тому й хеш, і рівність мають узгоджуватись (a == b ⇒ hash(a) == hash(b)).

51ПросунутеЩо таке досконала (perfect) хеш-функція?

Хеш-функція, побудована під заздалегідь відомий, фіксований набір ключів так, щоб узагалі не давати колізій для цього набору — на відміну від хеш-функції загального призначення в dict. Використовується там, де набір ключів не змінюється в рантаймі: ключові слова мови в компіляторах, таблиці маршрутизації, фіксовані конфігурації. Ціна — функція працює лише для того набору, під який побудована; додати новий ключ означає перебудувати її заново.

52БазаЯка складність пошуку в різних структурах даних Python?
list (непосортований)O(n) — лінійний перебір
list (відсортований, бінарний пошук)O(log n) — тільки для читання, вставка все одно O(n)
dict / setO(1) у середньому (хеш-таблиця); O(n) у виродженому найгіршому випадку при масових колізіях
53БазаЩо таке семафори?

Примітив синхронізації з лічильником дозволів: обмежує, скільки потоків/процесів одночасно можуть користуватись ресурсом — на відміну від Lock, який пускає рівно одного. Ініціалізується числом N ("N квитків"); .acquire() забирає квиток і зменшує лічильник, .release() повертає його; коли квитків 0 — наступний потік чекає. Проєктний приклад асинхронного варіанту (asyncio.Semaphore) розібраний у розділі 19 цього туторіалу.

54Системний дизайнЯк кілька процесів можуть безпечно працювати з одним файлом чи ресурсом?

Без координації виникають гонка даних, втрата чи неконсистентне читання "напівоновленого" стану. Робочі підходи: файлові блокування на рівні ОС (fcntl на Unix, бібліотеки на кшталт portalocker/filelock); міжпроцесна синхронізація — multiprocessing.Lock/Semaphore/Queue; атомарні операції ОС/файлової системи там, де можливо обійтись без явного лока; copy-on-write — робота з копією ресурсу й безпечна заміна оригіналу наприкінці. Для складної конкурентної роботи найнадійніше — не винаходити координацію самостійно, а покластися на СУБД, яка вже має вбудовані транзакції й блокування.

55Системний дизайнДві транзакції одночасно змінюють таблицю — виник deadlock. Що робити?

Deadlock виникає, коли транзакція A тримає рядок X і чекає Y, а транзакція B тримає Y і чекає X — обидві висять назавжди. БД (Postgres, MySQL) сама виявляє це й примусово перериває одну з транзакцій помилкою deadlock detected, тож застосунок повинен це ловити й ретраїти. Профілактика: завжди блокувати ресурси в однаковому порядку (наприклад, за зростанням id) в усіх транзакціях; тримати транзакції короткими; уникати SELECT ... FOR UPDATE, якщо без нього можна обійтись; не використовувати вищий рівень ізоляції (SERIALIZABLE), ніж дійсно потрібно.

56ПросунутеЯк event loop вирішує, якій корутині передати керування?

Через селектори ОС (selectors.DefaultSelector, під капотом epoll/kqueue/select). Коли корутина робить await на I/O, вона реєструє відповідний файловий дескриптор у селекторі й повертає керування в loop. Loop викликає selector.select(timeout) — блокуючий виклик, що каже "розбуди мене, коли будь-який із зареєстрованих дескрипторів готовий". Коли ОС сигналізує готовність (сокет можна читати/писати), event loop ставить відповідний Future/Task у чергу готових і на наступній ітерації відновлює саме цю корутину з місця зупинки. Тобто loop ніколи не обирає "довільно" — лише реагує на готовність, повідомлену селектором, або на явно заплановані виклики (call_soon).

57ПросунутеЩо таке "прогрів" пулу з'єднань (pool warm-up) у SQLAlchemy?

SQLAlchemy за замовчуванням створює з'єднання з БД лениво — за потребою. Прогрів — свідоме створення N з'єднань заздалегідь, ще до першого реального запиту (наприклад, при старті застосунку), щоб перший користувацький запит не платив ціну встановлення TLS-з'єднання й хендшейку з базою, і щоб проблеми з підключенням виявились одразу при старті, а не в момент першого запиту від реального користувача.

58Системний дизайнЧерез що асинхронний сервіс може деградувати при вибірці великих обсягів даних?
  • Пам'ять — fetchall()/execute(...).all() завантажує весь результат у RAM; для сотень тисяч рядків це ріст пам'яті аж до OOM.
  • Блокування в БД — важкі JOIN/GROUP BY/ORDER BY під навантаженням тримають з'єднання довго, використовують тимчасові таблиці, зачіпають продуктивність усієї бази.
  • Перевантаження event loop — асинхронність рятує лише I/O-bound патерн; важка CPU-обробка результату (серіалізація, трансформації) у Python-коді все одно блокує loop.
  • Серіалізація — Pydantic-валідація й перетворення в JSON для тисяч об'єктів одразу дорого навантажує CPU й пам'ять.

Лік — стрімінг замість повного fetchall() (курсор з ітерацією) та chunked-вигрузка (LIMIT/OFFSET чи keyset pagination) замість одного гігантського запиту.

59Системний дизайнЯкі проблеми має асинхронний код загалом?

Складність трасування (фрагментований стек викликів, "проковтнуті" винятки з незачеканих корутин); блокуючий виклик усередині async def (time.sleep, синхронний requests.get) заморожує весь event loop, а не лише свою задачу; не всі бібліотеки мають async-аналог (потрібні aiohttp, asyncpg замість звичних синхронних клієнтів, або обгортка через run_in_executor); async не обходить GIL і не пришвидшує CPU-bound код; тестування вимагає окремої інфраструктури (pytest-asyncio); і найчастіша реальна помилка — передчасний перехід на async там, де I/O-навантаження цього не виправдовує, що просто збільшує складність без вигоди.

60ПросунутеЯкі проблеми виникають з логуванням в асинхронному коді?

Стандартний logging синхронний навіть коли викликається з async def — часте логування (запис у файл/мережу) може блокувати event loop так само, як будь-який інший блокуючий виклик. Повідомлення з різних одночасних задач можуть переплітатись у виводі, якщо не додавати контекст (наприклад, correlation ID — детальніше в туторіалі 11) для розрізнення, яке повідомлення від якого запиту. Рішення: асинхронні логери (aiologger) або QueueHandler з окремим потоком/процесом для фактичного запису, плюс лінива підстановка аргументів (logging.info("User %s", user_id)) замість форматування рядка щоразу.

61БазаЯк зрозуміти, що застосунок зламався?

Одного способу недостатньо — типова комбінація: healthchecks (/live — чи живий процес, /ready — чи готовий приймати трафік, /health — узагальнена перевірка), на які періодично стукає оркестратор чи балансувальник; алерти по метриках (частка 5xx, відсутність трафіку, p95-затримка, ріст черги, CPU/пам'ять) через Prometheus+Alertmanager, Grafana, Sentry; логи помилок зі stacktrace (ELK, Loki, Sentry); дашборди для спостереження в реальному часі; і synthetic monitoring — бот, що періодично ходить по ключових ендпоінтах і перевіряє відповідь.

62Системний дизайнЗа якою стратегією білди зазвичай котяться на продакшн?

Універсального правильного варіанту немає — залежить від розміру команди й архітектури. Типовий безпечний потік: розробка у feature-гілках → MR у гілку test (пайплайн лінтерів/тестів як обов'язкові ворота перед merge, періодичний ручний регрес) → MR із test у main (ще один прогін CI) → окремо мігрції БД і сам деплой застосунку як два різні кроки, щоб їх можна було контролювати незалежно. Розділення "спершу міграція, потім код" важливе саме через сумісність версій під час викатки (див. питання 68 нижче).

63БазаЩо таке pre-commit?

Інструмент, що запускає перевірки й автоформатування (наприклад, black, flake8, видалення зайвих пробілів) автоматично перед кожним git commit. Якщо перевірка провалюється — коміт блокується, поки проблему не виправлено; це ловить дрібні проблеми стилю й очевидні помилки ще до того, як вони потрапляють у CI чи ревʼю.

64ПасткаЧим LEFT/RIGHT/INNER/FULL OUTER JOIN відрізняються один від одного?
INNER JOINлише рядки, для яких є збіг в обох таблицях
LEFT JOINусі рядки лівої таблиці + збіги з правої; де збігу нема — NULL
RIGHT JOINдзеркально: усі рядки правої таблиці + збіги з лівої
FULL OUTER JOINусі рядки з обох таблиць, NULL там, де пари немає в жодну сторону
65ПросунутеЩо таке часткові (partial) індекси в БД?

Індекс, побудований лише для підмножини рядків, що задовольняють умову WHERE — а не для всієї таблиці. Корисно, коли типові запити завжди фільтрують по одному й тому ж значенню (наприклад, WHERE status = 'active'): індекс менший, швидший у побудові й підтримці, займає менше диска. Ціна — він допомагає лише запитам, чия умова дійсно "накривається" умовою індекса; не всі СУБД його підтримують (у MySQL нативної підтримки немає, на відміну від PostgreSQL).

66ПасткаЧому видалення поля в міграції небезпечне при CI/CD, і як це робити правильно?

Якщо в одному MR одночасно видалити колонку з БД і прибрати її використання в коді, під час викатки виникає вікно, де міграція вже застосувалась (колонки нема), а старий код (ще не задеплоєний) усе ще очікує це поле — падає з помилками. Рішення — два окремі MR: спершу прибрати з коду будь-яке використання поля (деплоїти, поки колонка ще існує в БД, просто не читається/не пишеться), і лише другим MR — окрема міграція, яка фізично видаляє колонку.

67БазаЧим функціональне програмування відрізняється від ООП?

ООП об'єднує дані й поведінку в об'єктах (інкапсуляція, успадкування, поліморфізм), стан об'єкта може змінюватись — добре пасує до систем зі складною ієрархією сутностей (бізнес-логіка, веб-застосунки). Функціональне програмування будується на чистих функціях (однаковий вхід → однаковий вихід, без побічних ефектів) і незмінних (immutable) даних — програма складається з композиції функцій, а не взаємодії об'єктів; ефективне для обчислень, обробки потоків даних і паралелізму, де важлива передбачуваність.

68БазаЩо таке композиція (на противагу успадкуванню)?

Принцип "має" (has-a) замість "є" (is-a): об'єкт містить інший об'єкт і користується його функціональністю через посилання, а не успадковує від нього.

композиція: Car "має" Engine, а не "є" Engine
class Engine:
    def start(self):
        return "vroom"

class Car:
    def __init__(self):
        self.engine = Engine()   # композиція: Car ВИКОРИСТОВУЄ Engine

    def start(self):
        return self.engine.start()

Гнучкіше за успадкування: Engine можна підмінити іншою реалізацією без зміни ієрархії класів — тому спільнота Python часто радить "композицію над успадкуванням" (детальніше про мікси й межі цього принципу — туторіал 14, розділ 10, і розділ C, питання 12 цього туторіалу).

69БазаЯк працюють map і filter?

map(function, iterable) застосовує функцію до кожного елемента й лениво повертає ітератор результатів. filter(function, iterable) лишає лише ті елементи, для яких функція повернула truthy-значення.

map / filter
squares = map(lambda x: x ** 2, [1, 2, 3])       # <map object> -- лінивий ітератор
list(squares)                                     # [1, 4, 9]

evens = filter(lambda x: x % 2 == 0, range(6))
list(evens)                                       # [0, 2, 4]

Обидва повертають ітератор, а не список — значення обчислюються лише при ітерації; list comprehension (туторіал 5, розділ 13) частіше вважають більш "пайтонічною" заміною для простих випадків.

70ПросунутеЩо таке замикання (closure) в Python?

Вкладена функція, яка "запам'ятовує" й зберігає доступ до змінних оточуючої функції навіть після того, як та вже завершила виконання.

замикання
def make_multiplier(factor):
    def multiply(x):
        return x * factor    # factor "захоплено" із зовнішньої функції
    return multiply

times3 = make_multiplier(3)   # make_multiplier вже завершилась
times3(10)                    # 30 -- factor=3 усе одно живий
times3.__closure__             # підтвердження: комірка з захопленою змінною

Застосування: фабрики функцій із зафіксованими параметрами, приховування "приватного" стану без класу, і саме на цьому механізмі побудовані декоратори (туторіал 5, розділи 7-9). Якщо потрібно змінювати (не лише читати) зовнішню змінну зсередини вкладеної функції — потрібне ключове слово nonlocal, інакше Python вважає її новою локальною змінною. Зворотна сторона: замикання, що тримають посилання на великі об'єкти, можуть непомітно продовжувати їм життя — це вже розібрано як джерело витоків пам'яті в туторіалі 9, розділ 11.

71ПасткаДекоратор для асинхронної функції — сам працює синхронно чи асинхронно?

Залежить виключно від того, як написаний сам декоратор — асинхронність обгорнутої функції цього не визначає автоматично.

неправильно: синхронний wrapper над async-функцією
def bad_decorator(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)   # поверне coroutine-об'єкт, а НЕ результат
    return wrapper
правильно: async wrapper
def good_decorator(func):
    async def wrapper(*args, **kwargs):
        return await func(*args, **kwargs)   # дочекались реального результату
    return wrapper

Якщо декоратор не async і просто викликає func(...) без await, виклик поверне непрочитаний coroutine-об'єкт замість результату — типова тиха помилка. Правильний декоратор над async def сам мусить бути написаний як async def wrapper з await усередині.

72БазаДекоратор для заміру часу виконання функції
timing-декоратор (sync і async варіант)
import time
import functools

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

def timed_async(func):
    @functools.wraps(func)
    async def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = await func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

functools.wraps обов'язковий, щоб декорована функція не втратила своє ім'я й docstring (детальніше — туторіал 5, розділ 9). Для async def-функцій потрібен саме async-варіант декоратора з await усередині — див. попереднє питання.

73БазаЯкий магічний метод використовувати для зміни типів даних?
__int__(self)виклик int(obj)
__float__(self)виклик float(obj)
__str__(self)виклик str(obj) / print(obj)
__repr__(self)виклик repr(obj) — представлення для розробника
__bool__(self)виклик bool(obj) і перевірка в if obj:

Загальний механізм дандер-методів як "data model" Python уже розібраний у туторіалі 5, розділ 3 — тут лише повний перелік саме для приведення типів.

74Системний дизайнЩо швидше відпрацьовує в авторизації — JWT чи сесії, і чому?

JWT зазвичай швидший: уся інформація про користувача вже лежить усередині токена, тож сервер лише розшифровує й перевіряє підпис — операція повністю в оперативній пам'яті, без звернень до зовнішнього сховища. Сесії вимагають додаткового кроку на кожен запит: клієнт передає ідентифікатор сесії (типово через cookie), а сервер мусить піти в Redis/БД/файлову систему, щоб дістати за цим ідентифікатором дані користувача — саме цей зовнішній запит і робить сесії повільнішими, особливо під навантаженням чи коли сховище на іншому сервері. Компроміс, який варто згадати: швидкість JWT дається ціною складнішого миттєвого відкликання токена (детальніше про access/refresh — туторіал 2, розділ 2).

Це — надбудова над попередніми туторіалами, не заміна: якщо якесь питання виявилось незрозумілим, найкоротший шлях — повернутись до туторіалу 1 (архітектура/DI), 2 (async/безпека), 3 (масштабування), 4 (GIL/конкурентність) чи 5 (типи) — усі приклади там побудовані на тому самому коді.
