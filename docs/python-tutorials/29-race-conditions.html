00Що таке race condition

Race condition (стан гонки) — ситуація, коли результат програми залежить від того, в якому порядку переплелися кроки кількох конкурентних виконавців (потоків, корутин, процесів, серверів, вкладок браузера). При одному порядку все гаразд, при іншому дані псуються.

Гонка можлива лише тоді, коли збігаються чотири умови, і кожна техніка захисту прибирає хоча б одну з них:

  1. Спільний стан: рядок у БД, ключ у Redis, змінна в пам'яті, файл, кеш.
  2. Конкурентний доступ: два виконавці працюють з ним в перекритий проміжок часу.
  3. Хоча б один запис: лише читання ніколи не дає гонки.
  4. Неатомарна послідовність кроків: «прочитати → вирішити → записати» розірвано в часі, і між кроками може вклинитись хтось інший.

Класичний приклад: втрачене оновлення (lost update)

На рахунку 500 грн. Одночасно приходять два списання: 100 грн (запит A) і 50 грн (запит B). Код застосунку робить «прочитати → порахувати в Python → записати»:

❌ read-modify-write у застосунку
account = await repo.get(account_id)          # SELECT balance … → 500
account.balance = account.balance - amount    # рахуємо в пам'яті сервера
await session.commit()                        # UPDATE accounts SET balance = 400 …
🎨
Аналогія для фронтендера. Це те саме, що setCount(count + 1) двічі поспіль у React-обробнику: обидва виклики бачать один і той самий count із замикання, і замість +2 виходить +1. Виправлення у React — функціональне оновлення setCount(c => c + 1): «застосуй зміну до поточного значення, а не до того, що я колись прочитав». Атомарний UPDATE … SET balance = balance - 100 у БД — рівно та сама ідея (розділ B1).

02Карта технік: що прибирає яку з чотирьох умов

Дуже грубе правило пріоритету для бекенду: атомарна операція в БД → обмеження (UNIQUE/CHECK) → оптимістичне блокування → песимістичне блокування → Serializable → розподілений лок. Ліворуч дешевше й надійніше, праворуч гнучкіше, але дорожче й складніше зробити правильно.

AПам'ять одного процесу: потоки й корутини

A1. += — не атомарна операція, навіть з GIL

GIL гарантує, що одночасно виконується лише один байткод, але counter += 1 — це кілька байткодів (прочитати, додати, записати), і потік може бути перемкнений між ними (туторіал 6, розділ 08).

threading — гонка і виправлення
import threading
counter = 0
lock = threading.Lock()

def unsafe():
    global counter
    for _ in range(100_000):
        counter += 1                 # LOAD → ADD → STORE: між ними може перемкнутись інший потік

def safe():
    global counter
    for _ in range(100_000):
        with lock:                   # критична секція: лише один потік всередині
            counter += 1

threads = [threading.Thread(target=unsafe) for _ in range(8)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)   # unsafe: може бути < 800 000 (залежить від версії Python і навантаження); safe: завжди 800 000

Так зроблено і в цьому проєкті: app/core/rate_limiting.py тримає вікна запитів у dict і змінює їх під threading.Lock, бо синхронні залежності FastAPI виконуються в пулі потоків.

A2. asyncio: гонка живе між await

Корутини перемикаються лише на await. Код без await між перевіркою і дією атомарний відносно інших корутин того ж event loop. Але щойно між ними є await, туди може вклинитись інший запит.

asyncio — lazy-ініціалізація з гонкою
# ❌ два одночасні запити обидва побачать None і створять ДВА клієнти/пули
_client = None
async def get_client():
    global _client
    if _client is None:
        _client = await create_expensive_client()     # ← await: тут вклинюється другий запит
    return _client

# ✅ варіант 1: asyncio.Lock + повторна перевірка (double-checked)
_lock = asyncio.Lock()
async def get_client():
    global _client
    if _client is None:
        async with _lock:
            if _client is None:                       # перевірити ще раз уже під локом
                _client = await create_expensive_client()
    return _client

# ✅ варіант 2 (кращий): створювати на старті в lifespan — гонки просто немає
@asynccontextmanager
async def lifespan(app):
    app.state.client = await create_expensive_client()
    yield
    await app.state.client.close()

A3. Request coalescing (singleflight): один запит замість ста

кілька корутин чекають ОДИН результат
_inflight: dict[str, asyncio.Future] = {}

async def get_route_cached(route_id: str):
    if (cached := cache.get(route_id)) is not None:
        return cached
    if route_id in _inflight:                        # хтось уже рахує — чекаємо його результат
        return await _inflight[route_id]
    fut = asyncio.get_running_loop().create_future()
    _inflight[route_id] = fut
    try:
        value = await load_route_from_db(route_id)
        cache.set(route_id, value)
        fut.set_result(value)
        return value
    except Exception as e:
        fut.set_exception(e)
        raise
    finally:
        _inflight.pop(route_id, None)

A4. Прибрати спільний стан замість захисту

  • Immutability: незмінні об'єкти (@dataclass(frozen=True), кортежі) можна ділити без локів.
  • Confinement: стан належить одному виконавцю (наприклад, сесія БД — одна на запит, а не глобальна).
  • Черга + один споживач (actor model): усі зміни стану йдуть через asyncio.Queue одному обробнику, тож він бачить їх послідовно.
⚠️
Межа розділу A: усе тут працює лише всередині одного процесу. Uvicorn з 4 воркерами або 3 машини на Fly.io — це 4 чи 3 різні копії _lock і _WINDOWS. Для спільного стану між процесами потрібна спільна точка: БД або Redis (розділи B і D).

B1Атомарні оновлення (atomic updates) на рівні БД

Атомарне оновлення — це зміна поля на основі його поточного значення прямо в базі одним оператором, без перезапису всього рядка з боку застосунку. Замість «прочитати баланс у пам'ять → відняти → записати число назад» база виконує все як один неподільний крок:

✅ атомарне списання
UPDATE accounts SET balance = balance - 100 WHERE id = 5;

Чому це працює

Коли Postgres виконує UPDATE, він бере row-level lock (блокування рядка) на рядок, який змінює, до кінця транзакції. Другий UPDATE того самого рядка чекає, а після коміту першого перечитує вже нову версію рядка і застосовує свій вираз до неї (у режимі Read Committed). Тому balance - 50 рахується від 400, а не від 500.

Умовне атомарне оновлення: перевірка правила в тому самому операторі

Якщо баланс не може піти в мінус, простого balance - 100 замало: перевірку «чи достатньо коштів» треба зробити в тому самому операторі, інакше повертається check-then-act гонка.

SQL + SQLAlchemy
UPDATE accounts SET balance = balance - 100
WHERE id = 5 AND balance >= 100
RETURNING balance;                 -- 0 рядків → коштів не вистачило (або рахунку немає)

# SQLAlchemy 2.x
stmt = (
    update(Account)
    .where(Account.id == account_id, Account.balance >= amount)
    .values(balance=Account.balance - amount)
    .returning(Account.balance)
)
new_balance = (await session.execute(stmt)).scalar_one_or_none()
if new_balance is None:
    raise HTTPException(409, "Insufficient funds")
await session.commit()
✅
Так зроблено в цьому проєкті: OrganizationRepository.try_consume_quota (app/repositories/organization_repository.py) збільшує лічильник AI-викликів одним UPDATE … WHERE ai_calls_count + 1 <= :limit (і ще умова на сумарний ліміт) та перевіряє rowcount. Тобто «перевірити квоту» і «списати одиницю» неподільні.

Переваги

  • Захист від гонок без ручних локів у коді застосунку.
  • Продуктивність: один round-trip замість SELECT + UPDATE; рядок заблокований мінімальний час.
  • Менше конфліктів: оновлюються лише потрібні колонки. Якщо один сервіс міняє balance, а інший last_login_at, вони не затирають зміни один одного. З ORM-підходом «завантажив об'єкт, зберіг цілком» таке теж можливо, якщо ORM пише всі поля.

Коли цього недостатньо

  • Рішення залежить від кількох рядків або таблиць (наприклад, переказ між двома рахунками з інваріантом «сума не змінюється»). Тоді потрібна транзакція з обома UPDATE в однаковому порядку id (B3) або Serializable (B5).
  • Між читанням і записом потрібна складна логіка в коді або зовнішній виклик (PSP, OpenAI): тоді оптимістичне блокування (B4) або «зарезервувати → виконати → підтвердити».
  • Дуже гарячий рядок (тисячі UPDATE/с одного лічильника): усі стають у чергу на одне блокування. Тоді шардовані лічильники (N рядків, сума при читанні) або Redis INCR (D1).
🎨
Аналогія для фронтендера. SET balance = balance - 100 — це setBalance(b => b - 100), а WHERE balance >= 100 — як setBalance(b => b >= 100 ? b - 100 : b). Різниця лише в тому, що «чергу оновлень» тримає база, а не React.

B2Унікальні обмеження + INSERT … ON CONFLICT

Найчастіша check-then-act гонка — «перевірити, що такого ще немає, потім вставити». Перевірка в коді ніколи не захищає: між SELECT і INSERT інша транзакція встигає вставити те саме (і рівень Read Committed не допоможе, бо рядка, який можна заблокувати, ще не існує).

❌ → ✅ реєстрація з унікальним email
# ❌ два одночасні /register з однаковим email обидва пройдуть перевірку
if await users.get_by_email(email) is None:
    await users.create(email=email, ...)

-- ✅ інваріант живе в базі
CREATE UNIQUE INDEX users_email_uq ON users (lower(email));

# ✅ і застосунок обробляє конфлікт як очікуваний результат
try:
    await users.create(email=email, ...)
    await session.commit()
except IntegrityError:
    await session.rollback()
    raise HTTPException(409, "Email already registered")

Upsert і «get or create» без гонки

PostgreSQL
-- створити або нічого не робити, і дізнатись, чи вставили
INSERT INTO processed_events (event_id) VALUES ($1)
ON CONFLICT (event_id) DO NOTHING
RETURNING event_id;                     -- порожньо → подію вже обробляли (ідемпотентність, розділ C/D)

-- створити або атомарно оновити лічильник
INSERT INTO daily_usage (organization_id, day, calls) VALUES ($1, current_date, 1)
ON CONFLICT (organization_id, day) DO UPDATE SET calls = daily_usage.calls + 1
RETURNING calls;

Часткові (partial) унікальні індекси: правило лише для частини рядків

«у машини не більше одного активного маршруту»
CREATE UNIQUE INDEX one_active_route_per_vehicle
  ON routes (vehicle_id)
  WHERE status IN ('planned', 'in_progress');
-- два паралельні "призначити машину" → другий отримає unique violation, а не тихий дубль

Чому це найнадійніше: обмеження перевіряє база всередині власних механізмів (індекс + блокування ключа), незалежно від того, скільки інстансів застосунку, які мови й скрипти пишуть у таблицю. Це остання лінія оборони, яка спрацює, навіть якщо в коді забули про гонку.

B3Песимістичне блокування: SELECT … FOR UPDATE

Коли треба прочитати, прийняти рішення складною логікою і записати, а одним UPDATE це не виразити, можна явно заблокувати рядки на час транзакції. Інші транзакції, що хочуть змінити (або теж FOR UPDATE) ці рядки, чекають на коміт.

переказ між рахунками
async with session.begin():
    # блокуємо обидва рядки в ОДНАКОВОМУ порядку (за id) → немає deadlock
    ids = sorted([from_id, to_id])
    rows = (await session.execute(
        select(Account).where(Account.id.in_(ids)).order_by(Account.id).with_for_update()
    )).scalars().all()
    src = next(a for a in rows if a.id == from_id)
    dst = next(a for a in rows if a.id == to_id)
    if src.balance < amount:
        raise HTTPException(409, "Insufficient funds")
    src.balance -= amount          # тут read-modify-write безпечний: рядки заблоковані
    dst.balance += amount
# коміт знімає блокування

Deadlock і як його уникнути

  • Однаковий порядок захоплення (сортувати id) — головний спосіб.
  • Короткі транзакції: жодних HTTP-викликів, await на зовнішні сервіси чи «подумати» всередині транзакції з локами.
  • lock_timeout і повтор транзакції при deadlock detected (40P01).
⚠️
Ціна: блокування знижує паралельність (запити до одного рядка йдуть по черзі), тримає з'єднання з пулу, ризик deadlock-ів. Якщо конфлікти рідкісні, оптимістичний підхід (B4) зазвичай кращий.

B4Оптимістичне блокування: колонка version

Ідея: не блокувати під час читання, а під час запису перевірити, що рядок не змінився з моменту читання. Якщо змінився, хтось нас випередив: повторюємо операцію або повертаємо 409 користувачу.

SQL + SQLAlchemy version_id_col
UPDATE routes SET status = 'in_progress', version = version + 1
WHERE id = $1 AND version = $2;          -- 0 рядків → конфлікт

# SQLAlchemy робить це автоматично
class Route(Base):
    __tablename__ = "routes"
    version: Mapped[int] = mapped_column(nullable=False, default=1)
    __mapper_args__ = {"version_id_col": version}
# при flush: UPDATE … WHERE id = ? AND version = ?; якщо 0 рядків → StaleDataError

async def update_with_retry(route_id, change, attempts=3):
    for _ in range(attempts):
        try:
            async with session.begin():
                route = await session.get(Route, route_id)
                change(route)
            return route
        except StaleDataError:
            session.expunge_all()                # перечитати свіжу версію і спробувати ще
    raise HTTPException(409, "Route was modified concurrently, please reload")

B5Рівні ізоляції транзакцій і write skew

Рівень ізоляції визначає, які «переплетення» транзакцій база допускає. За замовчуванням Postgres працює в Read Committed: кожен оператор бачить дані, закомічені до його старту.

Write skew на прикладі проєкту

Правило: «у водія не може бути двох маршрутів, що перетинаються в часі». Дві транзакції одночасно перевіряють, що водій вільний, і кожна вставляє свій новий маршрут. Жоден рядок не змінювався двічі, тому ні атомарний UPDATE, ні version не допоможуть.

три способи закрити write skew
-- 1) Serializable + повтор при 40001 serialization_failure
BEGIN ISOLATION LEVEL SERIALIZABLE;
  SELECT count(*) FROM routes WHERE driver_id = $1 AND tstzrange(starts_at, ends_at) && tstzrange($2, $3);
  INSERT INTO routes (...);
COMMIT;      -- одна з двох транзакцій отримає 40001 → застосунок повторює її → тепер бачить перетин

-- 2) Матеріалізувати конфлікт: заблокувати "ключовий" рядок, спільний для обох транзакцій
SELECT 1 FROM drivers WHERE id = $1 FOR UPDATE;     -- усі планування для водія тепер ідуть по черзі

-- 3) Найнадійніше: виразити правило обмеженням (розділ B7, EXCLUDE)
повтор транзакції при serialization failure
from sqlalchemy.exc import DBAPIError

async def run_serializable(fn, attempts=5):
    for attempt in range(attempts):
        try:
            async with engine.connect() as conn:
                conn = await conn.execution_options(isolation_level="SERIALIZABLE")
                async with conn.begin():
                    return await fn(conn)
        except DBAPIError as e:
            if getattr(e.orig, "sqlstate", None) in ("40001", "40P01") and attempt < attempts - 1:
                await asyncio.sleep(random.uniform(0, 0.05 * 2 ** attempt))   # backoff + jitter
                continue
            raise

B6Advisory locks: лок на «ідею», а не на рядок

Postgres дозволяє брати іменовані блокування на довільне число (ключ), не прив'язане до таблиці. Зручно, коли треба серіалізувати операцію: «одночасно лише одна оптимізація маршрутів на організацію», «лише один інстанс запускає міграцію / cron-задачу».

одна генерація маршрутів на організацію одночасно
-- транзакційний варіант: знімається автоматично на COMMIT/ROLLBACK
SELECT pg_try_advisory_xact_lock(hashtext('optimize:' || $1::text));   -- false → уже йде інша генерація

# Python
got = (await session.execute(
    text("SELECT pg_try_advisory_xact_lock(hashtext(:k))"), {"k": f"optimize:{org_id}"}
)).scalar()
if not got:
    raise HTTPException(409, "Route generation already running for this organization")
  • Перевага: спільний лок для всіх інстансів застосунку без Redis, бо всі ходять в одну БД.
  • Обережно з сесійними (pg_advisory_lock без _xact) і PgBouncer у transaction mode: лок може «прилипнути» до чужого з'єднання. Транзакційний варіант безпечніший.
  • Не тримати лок під час довгих зовнішніх викликів, якщо можна інакше: це тримає з'єднання з пулу.

B7CHECK і EXCLUDE: правила, які база не дасть порушити

інваріанти як обмеження
-- баланс ніколи не від'ємний: навіть якщо хтось забув WHERE balance >= …
ALTER TABLE accounts ADD CONSTRAINT balance_non_negative CHECK (balance >= 0);

-- квота не перевищує ліміт (якщо ліміт зберігається в рядку)
ALTER TABLE organizations ADD CONSTRAINT routes_within_limit
  CHECK (route_limit IS NULL OR routes_generated_count <= route_limit);

-- водій не може мати маршрути, що перетинаються в часі (закриває write skew з B5)
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE routes ADD CONSTRAINT no_overlapping_routes_per_driver
  EXCLUDE USING gist (driver_id WITH =, tstzrange(starts_at, ends_at) WITH &&)
  WHERE (status <> 'cancelled');

EXCLUDE — це «унікальність для діапазонів»: дві строки конфліктують, якщо driver_id рівні і часові діапазони перетинаються (&& читається «перетинається з»). Друга паралельна вставка отримає помилку незалежно від рівня ізоляції. Класичний інструмент для бронювань, розкладів і змін.

CAPI: повторні запити й ідемпотентність

Гонка «той самий запит двічі»: користувач двічі клікнув «Згенерувати», мобільна мережа обірвалась і клієнт повторив запит, балансувальник зробив retry. Без захисту двічі списуються гроші або квота і створюються два маршрути.

C1. Idempotency key

таблиця і логіка
CREATE TABLE idempotency_keys (
  organization_id uuid NOT NULL,
  key text NOT NULL,
  request_hash text NOT NULL,
  status text NOT NULL,                 -- in_progress | completed
  response jsonb,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (organization_id, key)    -- ← саме UNIQUE робить це безпечним при паралельних дублях
);

async def idempotent(org_id, key, body, handler):
    h = sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()
    inserted = (await db.execute(text("""
        INSERT INTO idempotency_keys (organization_id, key, request_hash, status)
        VALUES (:o, :k, :h, 'in_progress') ON CONFLICT DO NOTHING RETURNING key"""),
        {"o": org_id, "k": key, "h": h})).first()
    await db.commit()
    if not inserted:                                    # ключ уже бачили
        row = await get_key(org_id, key)
        if row.request_hash != h:
            raise HTTPException(422, "Idempotency-Key reused with a different body")
        if row.status == "in_progress":
            raise HTTPException(409, "Request with this key is still being processed")
        return row.response                             # повертаємо збережений результат, нічого не виконуючи
    response = await handler()
    await save_completed(org_id, key, response)
    return response
  • Ключ генерує клієнт (UUID на одну логічну дію) і повторює його при ретраях; інакше сервер не відрізнить ретрай від нової дії.
  • Зберігати ключ і бізнес-зміну в одній транзакції, якщо це можливо; інакше між «виконали» і «зберегли відповідь» залишається вікно.
  • TTL на ключі (наприклад, 24 год), окремий простір ключів на тенанта.

C2. Природна ідемпотентність і state machine

переходи стану як умовний UPDATE
-- ❌ "додати 1" не ідемпотентне;  ✅ "встановити стан" — ідемпотентне
UPDATE route_stops SET status = 'delivered', delivered_at = now()
WHERE id = $1 AND status IN ('pending', 'arrived')      -- дозволений перехід
RETURNING id;
-- повтор: 0 рядків (вже delivered) → відповідаємо 200 з поточним станом, а не помилкою
-- конкурентне "cancel" після "delivered": 0 рядків → 409 "already delivered"

Так само обробляються події не по порядку: webhook refunded прийшов раніше за paid. Перехід refunded → paid заборонений умовою WHERE, тож запізніла подія нічого не зламає.

DКілька інстансів, черги й розподілені системи

D1. Спільний лічильник і атомарні операції в Redis

threading.Lock у rate_limiting.py захищає лише свій процес. На трьох машинах кожна має свій _WINDOWS, і реальний ліміт множиться на три. Спільна атомарна точка — Redis, який виконує команди однопотоково.

Redis: INCR, Lua, SET NX
# атомарний лічильник вікна
pipe = redis.pipeline(transaction=True)
pipe.incr(key); pipe.expire(key, 60, nx=True)
count, _ = await pipe.execute()

# складніша умова атомарно — Lua-скрипт виконується без переплетень з іншими командами
CONSUME = redis.register_script("""
local used = tonumber(redis.call('GET', KEYS[1]) or '0')
if used + tonumber(ARGV[1]) > tonumber(ARGV[2]) then return -1 end
return redis.call('INCRBY', KEYS[1], ARGV[1])
""")
left = await CONSUME(keys=[f"quota:{org_id}"], args=[1, limit])   # −1 → ліміт вичерпано

# "зробити один раз": SET NX (лише якщо ключа немає) + TTL
first = await redis.set(f"email-sent:{event_id}", 1, nx=True, ex=86400)
if first:
    await send_email(...)
⚠️
Пастка: GET у Python, перевірка, потім SET — та сама check-then-act гонка, тільки в Redis. Атомарні лише окремі команди, MULTI/EXEC-блоки та Lua-скрипти. WATCH + MULTI — оптимістичне блокування в Redis.

D2. Розподілені локи і fencing tokens

Розподілений лок (Redis SET lock NX PX 30000, etcd, ZooKeeper, Postgres advisory) дає «лише один інстанс виконує це зараз». Головна проблема — лок має TTL: якщо власник завис (GC-пауза, мережа, повільний зовнішній виклик) довше за TTL, лок отримує інший, і тепер працюють двоє.

  • Лок для ефективності (не робити ту саму роботу двічі) прийнятний і простий. Лок для коректності (гроші, інваріанти) потребує fencing token або захисту на рівні сховища (умовний UPDATE з версією).
  • Дебати Kleppmann vs antirez про Redlock — у System Design 13 · розділ 08.
  • Часто кращий шлях — не потребувати лок: атомарна операція в БД або single writer.

D3. Single writer: «зміни однієї сутності — лише через одного виконавця»

Якщо всі зміни замовлення order_42 потрапляють в одну партицію Kafka (ключ = order_id) або в одну чергу, їх обробляє один консюмер послідовно, і гонки між ними неможливі в принципі. Масштабування — більше партицій, тобто більше незалежних сутностей паралельно. Це той самий actor model з розділу A4, але між серверами.

D4. Черги задач: at-least-once означає «готуйся до дублів»

  • Брокери (Celery/Redis, RabbitMQ, Kafka, NATS) гарантують at-least-once: воркер упав після виконання, але до ack, і задача прийде ще раз. З acks_late=True у Celery це штатна поведінка.
  • Ідемпотентний консюмер: INSERT INTO processed_events … ON CONFLICT DO NOTHING в одній транзакції з ефектом задачі (B2).
  • Кілька воркерів з однієї таблиці-черги: FOR UPDATE SKIP LOCKED (кожен воркер бере свої рядки, без подвійної обробки).
Postgres як черга без подвійного захоплення
WITH next AS (
  SELECT id FROM jobs WHERE status = 'queued'
  ORDER BY created_at LIMIT 10
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs SET status = 'running', started_at = now(), worker = $1
FROM next WHERE jobs.id = next.id
RETURNING jobs.*;
Celery: ідемпотентна задача
@celery_app.task(bind=True, acks_late=True, autoretry_for=(TemporaryError,),
                 retry_backoff=True, retry_jitter=True, max_retries=5)

D5. Dual write і transactional outbox

«Записати в БД і відправити подію в брокер» — два незалежні кроки: процес може впасти між ними, а дві паралельні зміни можуть відправити події в іншому порядку, ніж закомітились. Рішення — записати подію в таблицю outbox у тій самій транзакції, що й бізнес-дані; окремий relay публікує їх по порядку (System Design 7 · розділ 07).

EКеш: гонки між кешем і базою

E1. Застаріле значення після інвалідації

  • Інвалідувати після коміту (не до), а для чутливих даних ще раз із затримкою («delayed double delete»).
  • Версія в ключі або значенні: route:{id}:v{version}; читач записує в кеш лише якщо версія не старша за поточну (Lua з порівнянням).
  • Leases (як у Memcache у Facebook): кеш видає токен на заповнення після miss; інвалідація анулює токен, і запізнілий SET відхиляється.
  • Короткий TTL обмежує час, скільки житиме помилка; для критичних даних (баланс, квоти) не кешувати взагалі.

E2. Cache stampede

Популярний ключ протух, і 1000 запитів одночасно йдуть у БД рахувати те саме. Захист: singleflight (A3) або Redis-лок на перерахунок (SET rebuild:key NX EX 10, решта віддають старе значення або чекають), ранній перерахунок до закінчення TTL, jitter у TTL, щоб ключі не протухали одночасно (System Design 3 · розділи 06–07).

FФронтенд: гонки в браузері

F1. Відповіді не в тому порядку

пошук доставок: «ки» відповів після «київ»

GЯк знаходити й тестувати гонки

Звичайний тест виконує запити послідовно, тож гонку не побачить ніколи. Потрібно навмисно запустити кроки одночасно і перевірити інваріант.

pytest: 20 паралельних списань проти справжнього Postgres
import asyncio, pytest

@pytest.mark.integration
async def test_concurrent_withdrawals_do_not_lose_updates(make_client, account_with_balance):
    account_id = await account_with_balance(1000)

    async def withdraw():
        async with make_client() as c:              # окремий клієнт/сесія = окреме з'єднання з БД
            return await c.post(f"/accounts/{account_id}/withdraw", json={"amount": 100})

    responses = await asyncio.gather(*(withdraw() for _ in range(20)))
    ok = [r for r in responses if r.status_code == 200]
    assert len(ok) == 10                             # рівно 10 по 100 з 1000
    assert await get_balance(account_id) == 0        # і нічого не втрачено / не пішло в мінус
  • Тестуйте на справжній БД (testcontainers / docker compose): SQLite в пам'яті має іншу модель блокувань і сховає гонку.
  • Розширити вікно гонки в тесті: штучний await asyncio.sleep(0.05) між читанням і записом (через фікстуру чи monkeypatch), threading.Barrier, щоб потоки стартували одночасно.
  • Навантаження: k6/Locust з багатьма одночасними запитами на той самий ресурс (один рахунок, одна організація).
  • Інваріанти в моніторингу: періодичні звірки (сума ledger = баланс, квота ≤ ліміту), алерти на дублікати.
  • Postgres: pg_stat_activity + pg_locks для очікувань, log_lock_waits = on, лог deadlock-ів.
  • Python: asyncio debug mode, ThreadSanitizer для C-розширень; у Go/Rust — race detector, у Python такого немає, тож тести й рев'ю важливіші.

HКейс з цього репозиторію: квота на генерацію маршрутів

У проєкті є обидва підходи поруч, тож добре видно різницю.

✅ AI-квота: атомарно
  • require_ai_quota викликає try_consume_quota: один UPDATE … WHERE ai_calls_count + 1 <= limit і перевірку rowcount.
  • Перевірка й списання неподільні, тож 50 паралельних запитів не перевищать ліміт.
⚠️ Квота маршрутів: check-then-act
  • require_route_quota (app/core/dependencies.py) читає routes_generated_count і порівнює з лімітом.
  • Потім кілька секунд працює солвер OR-Tools.
  • Потім increment_route_count збільшує лічильник атомарно, але без умови на ліміт.

Як можна виправити (варіанти з trade-offs)

  1. Резерв наперед атомарно: списати квоту умовним UPDATE до солвера (як AI-квота), а якщо солвер упав або повернув менше маршрутів, повернути різницю (SET count = count - :unused). Найпростіше й узгоджено з try_consume_quota. Мінус: треба вирішити, скільки резервувати, коли кількість маршрутів відома лише після розв'язку (наприклад, рахувати за кількістю вибраних машин як верхню межу).
  2. Умовне списання після солвера: UPDATE … SET count = count + :n WHERE count + :n <= limit; якщо 0 рядків — не зберігати маршрути (транзакція з відкатом). Чесно, але солвер відпрацював дарма.
  3. Advisory lock на організацію (B6) на час генерації: серіалізує генерації однієї організації, і перевірка стає коректною. Мінус: тримає з'єднання з БД під час роботи солвера.
  4. CHECK-обмеження як страховка (B7), якщо ліміт зберігати в рядку організації.
ℹ️
Наслідок у цьому проєкті м'який: TRIAL-організація може отримати на кілька маршрутів більше за ліміт. Але той самий шаблон коду на грошах дав би реальні збитки, і тому його варто впізнавати.

JЗадачі (спершу подумай, потім відкривай)

Задача 1. Знайди гонку
склад: резерв товару під замовлення
async def reserve(product_id: str, qty: int):
    product = await repo.get(product_id)
    if product.stock < qty:
        raise HTTPException(409, "Out of stock")
    product.stock -= qty
    await session.commit()
Розв'язок
  1. Тип: read-modify-write + check-then-act. Два запити на останні 3 одиниці обидва прочитають stock = 3, обидва пройдуть перевірку і запишуть 0 (або один перезапише іншого). Продано 6 із 3.
  2. Виправлення одним оператором: UPDATE products SET stock = stock - :qty WHERE id = :id AND stock >= :qty RETURNING stock; немає рядка → 409.
  3. Страховка: CHECK (stock >= 0).
Задача 2. «get or create» водія за телефоном

Імпорт з Excel паралельно обробляє рядки і для кожного робить «знайти водія за телефоном, якщо немає — створити». Після імпорту в організації з'являються дублікати водіїв. Чому і як виправити?

Розв'язок
  1. Check-then-act: два рядки з однаковим телефоном одночасно не знаходять водія і обидва створюють.
  2. Інваріант у базу: CREATE UNIQUE INDEX ON drivers (organization_id, phone) (з нормалізацією телефону, наприклад E.164).
  3. Вставка: INSERT … ON CONFLICT (organization_id, phone) DO UPDATE SET name = EXCLUDED.name RETURNING id — завжди повертає id наявного або нового.
  4. Ще краще для імпорту: спершу дедуплікувати рядки в Python за нормалізованим телефоном, потім один батч-upsert.
Задача 3. Lock не допоміг

Розробник додав asyncio.Lock() навколо списання квоти, тести зелені, але на проді квоти все одно перевищуються. Бекенд запущено як uvicorn --workers 4 на двох машинах. Що не так?

Розв'язок
  1. asyncio.Lock існує в пам'яті одного процесу. Тут 4 × 2 = 8 процесів, тобто 8 незалежних локів.
  2. Тести запускали один процес, тому гонку не бачили.
  3. Виправлення: перенести атомарність туди, де лежить спільний стан, — умовний UPDATE в Postgres (як try_consume_quota) або Redis Lua-скрипт. Лок у пам'яті прибрати, бо він дає хибне відчуття безпеки.
Задача 4. Переказ з deadlock-ами

Переказ між двома рахунками зроблено через SELECT … FOR UPDATE спершу рахунку-відправника, потім отримувача. Під навантаженням з'являються помилки deadlock detected. Чому і що робити?

Розв'язок
  1. Переказ 1→2 блокує 1, потім чекає 2; паралельний переказ 2→1 блокує 2, потім чекає 1. Виходить цикл очікування.
  2. Блокувати в однаковому порядку: WHERE id IN (:a, :b) ORDER BY id FOR UPDATE.
  3. Транзакція коротка: жодних зовнішніх викликів усередині.
  4. Повторювати транзакцію при 40P01 з backoff (рідкісні deadlock-и все одно можливі при інших шляхах доступу).
  5. Альтернатива: два умовні UPDATE в одній транзакції, теж у порядку id.
Задача 5. Лист «маршрут готовий» приходить двічі

Після генерації маршруту Celery-задача шле водію SMS. Іноді водії отримують дві SMS. Celery налаштовано з acks_late=True. Чому і як виправити?

Розв'язок
  1. З acks_late задача підтверджується після виконання. Якщо воркер упав або перезапустився (деплой!) після відправки SMS, але до ack, задачу отримає інший воркер. Це at-least-once.
  2. Ідемпотентність за ключем події: notification_id (наприклад, route_ready:{route_id}). INSERT INTO sent_notifications … ON CONFLICT DO NOTHING перед відправкою; якщо не вставилось, задача пропускає SMS.
  3. Залишкове вікно «вставили запис, але SMS не пішла» закривається статусом (pending → sent) і повтором для pending. Або провайдер SMS з власним idempotency key.
Задача 6. Два диспетчери редагують маршрут

Два диспетчери відкрили той самий маршрут в адмінці. Перший переставив зупинки і зберіг, другий змінив водія і зберіг на хвилину пізніше. Перестановка зупинок зникла. Як спроєктувати API?

Розв'язок
  1. Це lost update на рівні людей: другий зберіг «увесь маршрут» на основі старої копії. Блокувати рядок на хвилини (FOR UPDATE) неможливо.
  2. Оптимістичне блокування: GET повертає ETag: "v7", PATCH з If-Match: "v7"; на сервері UPDATE … WHERE id = :id AND version = 7; 0 рядків → 412.
  3. UI на 412: показати «маршрут змінив інший користувач», підтягнути нову версію, запропонувати застосувати свої зміни повторно.
  4. Додатково зменшити конфлікти: PATCH лише змінених полів замість PUT цілого об'єкта, тоді зміна водія і перестановка зупинок взагалі не конфліктують.
Короткий підсумок: гонка потребує спільного стану, конкурентності, запису і неатомарних кроків. Кожна техніка прибирає одну з цих умов. Для бекенду найчастіше достатньо трьох речей: атомарного умовного UPDATE, обмежень бази (UNIQUE, CHECK, EXCLUDE) та ідемпотентності для всього, що може прийти двічі. Локи (у пам'яті, FOR UPDATE, розподілені) беріть свідомо й пам'ятайте їхні межі.
