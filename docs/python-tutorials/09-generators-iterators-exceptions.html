Частина I · Ітератори й генератори

1 Iterable vs Iterator — два різні протоколи

Найчастіша плутанина термінів у цій темі: "ітерований об'єкт" і "ітератор" — не синоніми.

  • Iterable ("можна перебрати") — будь-який об'єкт із методом __iter__, що повертає ітератор. Список, рядок, словник, множина — усі iterable, але жоден із них сам по собі не є ітератором.
  • Iterator ("сам процес перебору") — об'єкт із __iter__ (що повертає self) і __next__ (повертає наступне значення або кидає StopIteration, коли значень більше немає).
python — власний ітератор вручну, без yield
class CountUpTo:
    """Iterable І Iterator одночасно — не найкраща практика, але показує механізм."""
    def __init__(self, limit):
        self.limit = limit
        self.current = 0

    def __iter__(self):
        return self          # ітератор повертає сам себе

    def __next__(self):
        if self.current >= self.limit:
            raise StopIteration       # сигнал "перебір завершено" для for-циклу
        self.current += 1
        return self.current

for n in CountUpTo(3):
    print(n)   # 1, 2, 3

for x in obj: насправді розгортається так: Python викликає iter(obj) (тобто obj.__iter__()) один раз, а потім у циклі викликає next(...) на результаті, доки не зловить StopIteration — саме тоді цикл завершується, без жодного видимого try/except у вашому коді.

💼
Часте питання на співбесіді "Чим iterable відрізняється від iterator?" — правильна відповідь: iterable вміє породжувати ітератор (__iter__), ітератор вміє видавати значення по одному (__next__). Список — iterable, але не ітератор (iter([1,2,3]) ≠ сам список — це новий об'єкт-ітератор; саме тому два окремі for-цикли по одному списку не "заважають" одне одному).

2 Генератор — цукор над написанням власного ітератора

Той самий клас CountUpTo з розділу 1 — типова причина, чому в мову додали yield.

той самий CountUpTo, але генератором — на 5 рядків коротше
def count_up_to(limit):
    current = 0
    while current < limit:
        current += 1
        yield current       # "видай значення, запам'ятай, де зупинився"

for n in count_up_to(3):
    print(n)   # 1, 2, 3 -- та сама поведінка, без жодного класу

Функція з yield усередині — не звичайна функція: виклик count_up_to(3) не виконує тіло функції одразу, а повертає об'єкт-генератор, який сам автоматично реалізує __iter__/__next__. Кожен next(gen) виконує код до наступного yield, "заморожує" весь локальний стан функції (значення змінних, позицію виконання) і повертає кероване значення — а на наступному виклику продовжує рівно з того самого місця.

Аналогія з фронтендом
JS має буквально той самий механізм із тим самим ключовим словом: function* countUpTo(limit) { let i = 0; while (i < limit) yield ++i; } — ідентична ідея, ідентичний синтаксис (з * замість неявного визначення через наявність yield), і те саме "заморожування" стану функції між викликами .next().

3 Стан генератора і чому лінивість економить пам'ять

Генератор проходить чіткі стани — і саме "заморозка" між ними дає головну перевагу над списком.

python
import inspect

gen = count_up_to(3)
inspect.getgeneratorstate(gen)   # 'GEN_CREATED'   -- ще жодного разу не запускався
next(gen)
inspect.getgeneratorstate(gen)   # 'GEN_SUSPENDED' -- призупинений рівно на yield
list(gen)                        # дороблює решту
inspect.getgeneratorstate(gen)   # 'GEN_CLOSED'    -- вичерпаний, більше next() дасть StopIteration

Головна практична перевага: генератор тримає в пам'яті лише поточний стан, а не всі значення одразу. (x*x for x in range(10_000_000)) — миттєвий, майже безкоштовний по пам'яті вираз; [x*x for x in range(10_000_000)] — одразу виділяє пам'ять під 10 мільйонів чисел.

✅
Коли лінивість критична: обробка файлів, більших за оперативну пам'ять (читання рядок за рядком); нескінченні послідовності (потік подій, сенсорні дані); пайплайни трансформацій, де важливий лише кінцевий результат, а не проміжні повні списки (sum(x*x for x in huge_iterable if x % 2 == 0) ніколи не будує проміжний список).

4 .send(), .throw(), .close() — генератор як двостороння корутина

Найменш відома частина протоколу — генератор уміє не лише віддавати значення, а й приймати їх ззовні.

python — двосторонній генератор
def echo_upper():
    while True:
        received = yield          # yield як ВИРАЗ -- очікує значення ззовні
        print(f"got: {received.upper()}")

gen = echo_upper()
next(gen)                 # обов'язковий "прайминг" -- довести генератор до першого yield
gen.send("hello")         # друкує "got: HELLO"
gen.throw(ValueError("boom"))  # кидає ValueError ВСЕРЕДИНІ генератора, у точці yield
gen.close()                # кидає GeneratorExit всередину -- акуратне завершення

.send(value) продовжує генератор і "підставляє" value як результат виразу yield усередині нього. .throw(exc) кидає виняток рівно в точці, де генератор призупинений — можна зловити його там try/except усередині генератора. .close() кидає спеціальний GeneratorExit, після якого генератор повинен завершитись (ще один yield після цього — RuntimeError).

5 yield from — делегування вкладеним генераторам

python
def inner():
    yield 1
    yield 2
    return "inner is done"      # значення return потрапляє в StopIteration.value

def outer():
    result = yield from inner()  # прозоро передає ВСІ yield з inner() назовні
    print(result)                 # "inner is done" -- дістає значення return з inner()
    yield 3

list(outer())   # [1, 2, 3], і між рядків надрукується "inner is done"

yield from — не просто скорочення для for x in inner(): yield x (хоч і виглядає схоже для найпростішого випадку). Різниця: yield from також прозоро прокидає .send()/.throw() у вкладений генератор і дістає значення його return — цикл for цього не вміє. Саме ця "прозорість" зробила yield from ключовим будівельним блоком для генератор-based корутин (розділ 7).

7 Звідки насправді виріс async/await

Найкраща "cool fact"-відповідь на співбесіді про історію Python — і пряме продовження туторіалу 4.

до PEP 492 (Python < 3.5) — асинхронний код писали ГЕНЕРАТОРАМИ
import asyncio

@asyncio.coroutine
def old_style_coroutine():
    result = yield from some_async_operation()   # yield from замість await
    return result

# сучасний еквівалент, з 3.5+:
async def modern_coroutine():
    result = await some_async_operation()
    return result

PEP 342 (Python 2.5, 2006) додав генераторам .send()/.throw() — саме ці можливості з розділу 4 дозволили писати "генератор-корутини": функцію, що призупиняється на yield, чекає на подію ззовні (наприклад, завершення мережевого запиту), і продовжується, коли подія настала. Рання версія asyncio (Python 3.4) була побудована саме на цьому — на генераторах із декоратором @asyncio.coroutine і yield from. PEP 492 (Python 3.5, 2015) увів async/await як окремий, явний синтаксис поверх тієї самої базової машинерії — по суті, ще один шар синтаксичного цукру (туторіал 7!), який робить корутини окремим типом об'єктів, а не "генераторами, які прикидаються корутинами".

🎉
Чому це чудова відповідь на співбесіді Це показує розуміння того, що async/await — не окрема магічна фіча, а еволюція вже наявного механізму генераторів. Той самий "event loop" з туторіалу 4 у ранньому asyncio буквально ганяв генератори через .send(None) у циклі, ловлячи моменти, де вони "чекають" на I/O.

Асинхронні генератори (Python 3.6+, PEP 525)

app/db/session.py — реальний код з проєкту
async def get_session() -> AsyncGenerator[AsyncSession, None]:
    """Yield an AsyncSession, closing it when the request completes."""
    async with AsyncSessionLocal() as session:
        yield session

async def + yield усередині = асинхронний генератор — споживається через async for. FastAPI використовує саме цей патерн для DI-залежностей із "код до yield = setup, код після = teardown" (той самий принцип, що й у звичайному контекст-менеджері з туторіалу 7, тільки в async-формі).

8 Генератори у вашому проєкті

app/core/dependencies.py — делегування через async for
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    """Yield a request-scoped async SQLAlchemy session."""
    async for session in get_session():    # прозоро прокидає yield із get_session() назовні
        yield session

Це — та сама ідея делегування з розділу 5 (yield from), тільки в асинхронній формі (async for ... yield, бо yield from не працює з асинхронними генераторами напряму). get_db обгортає get_session без дублювання логіки відкриття/закриття сесії — просто прокидає значення далі по ланцюжку DI.

Частина II · Винятки глибше

9 Ієрархія вбудованих винятків

Голий except: і except Exception: — це не одне й те саме, і різниця часто ламає кандидатів на співбесіді.

  • BaseException
    • SystemExit — викликається sys.exit()
    • KeyboardInterrupt — Ctrl+C
    • GeneratorExit — .close() генератора, розділ 4
    • asyncio.CancelledError — з Python 3.8 (туторіал 4!)
    • Exception — база для "звичайних" помилок
      • ValueError, TypeError, KeyError, IndexError...
      • OSError (і мережеві/файлові підкласи)
      • QuotaExceededError — власний, з app/core/plans.py

Голий except: ловить усе, включно з SystemExit і KeyboardInterrupt — тому може "проковтнути" навіть спробу зупинити програму комбінацією Ctrl+C. except Exception: — набагато безпечніший дефолт: не чіпає ці "керуючі" сигнали, бо вони навмисно винесені прямо під BaseException, а не під Exception.

💼
Пряме продовження туторіалу 4 Саме тому asyncio.CancelledError з Python 3.8 навмисно перенесли з Exception під BaseException — щоб типовий except Exception: у чужому коді не міг випадково "проковтнути" скасування задачі, як обговорювалось у туторіалі 4.

10 Власні ієрархії винятків

app/core/security.py та app/core/plans.py — реальний код з проєкту
class InvalidTokenError(Exception):
    """Raised when a JWT is missing, malformed, expired, or has a bad signature."""

class QuotaExceededError(Exception):
    """Raised when an organization has exhausted a plan-based usage quota."""

Власний клас винятку — це просто class MyError(Exception): pass (часто навіть без тіла, як тут — сама назва класу і є "повідомленням" для коду, що його ловить). Перевага над "просто підняти ValueError з текстом" — виклик коду може відрізнити цей конкретний тип проблеми через except QuotaExceededError:, не парсячи рядок повідомлення.

✅
У цьому проєкті QuotaExceededError навіть має централізований обробник (app/core/error_handlers.py, @app.exception_handler(QuotaExceededError)) — один тип винятку, підняний глибоко всередині сервісного шару, автоматично перетворюється на коректний HTTP 403 для будь-якого місця коду, яке забуло зловити його вручну.

11 raise ... from ... — ланцюжки винятків

Рядок, що зустрічається в коді цього проєкту буквально десятки разів — а на співбесіді про нього рідко питають правильно.

app/core/dependencies.py — реальний код з проєкту
try:
    claims = decode_token(token)
except InvalidTokenError as exc:
    raise credentials_error from exc   # явний ланцюжок: НОВИЙ виняток, стара причина збережена
raise X from Y (явний ланцюжок)
X.__cause__ = Y # traceback: "The above exception was the # direct cause of the following exception"
raise X (без from, усередині except)
X.__context__ = поточний виняток (автоматично) # traceback: "During handling of the above # exception, another exception occurred"

Без жодного from, якщо ви піднімаєте новий виняток усередині блоку except, Python сам прикріпить оригінальний виняток як __context__ — неявний ланцюжок, який теж показується в traceback, просто з іншим формулюванням. raise NewError(...) from None — спеціальний випадок: повністю приховує ланцюжок, корисно, коли внутрішня причина не повинна "просочуватись" назовні (наприклад, у публічну відповідь API).

💼
На співбесіді запитають так "Яка різниця між raise X from Y і просто raise X усередині except?" — правильна відповідь: перше — явний, навмисний ланцюжок (__cause__), друге — неявний, автоматичний (__context__). Обидва зберігають повний traceback оригінальної помилки для дебагу — різниця лише в тому, наскільки "навмисно" ця причина позначена.

12 try/except/else/finally повністю

else у винятках — найменш використовуваний, і саме тому найчастіше плутають на співбесіді.

python — усі чотири блоки разом
try:
    value = risky_call()
except ValueError:
    print("сталась ValueError")
else:
    print("risky_call() НЕ впала -- value доступний тут")   # лише якщо try пройшов БЕЗ винятку
finally:
    print("виконується ЗАВЖДИ -- впала функція чи ні")

else виконується, лише якщо try завершився без винятку — логічно еквівалентно перенесенню коду в кінець блоку try, але явно відділяє "код, що може впасти" від "код, що виконується тільки після успіху", не ризикуючи випадково зловити виняток із цього коду тим самим except.

python — класична пастка з return у finally
def f():
    try:
        return "from try"
        raise ValueError("never reached")
    finally:
        return "from finally"    # !! ПЕРЕКРИВАЄ і return, і виняток із try

f()   # "from finally" -- return із try НІКОЛИ не повернувся
❌
Пастка: return (або raise, або break/continue) усередині finally завжди "перемагає" — тихо відкидає будь-яке значення return чи будь-який виняток із блоків try/except вище. Ruff і більшість лінтерів спеціально попереджають про це (return у finally) — уникайте навмисно.

13 Exception Groups та except* (Python 3.11+)

Пряме продовження питання про asyncio.TaskGroup з туторіалу 6.

python 3.11+
try:
    raise ExceptionGroup("multiple failures", [
        ValueError("bad value"),
        TypeError("bad type"),
    ])
except* ValueError as eg:
    print(f"зловив ValueError-и: {eg.exceptions}")
except* TypeError as eg:
    print(f"зловив TypeError-и: {eg.exceptions}")

До Python 3.11 виняток завжди був один. Але asyncio.TaskGroup (туторіал 6, п. 17) може мати кілька задач, що впали одночасно — потрібен спосіб піднести кілька винятків разом, не втрачаючи жодного. ExceptionGroup — контейнер для кількох винятків; except* (з зірочкою!) — новий синтаксис, що "фільтрує" групу за типом, може спрацювати кілька разів для різних типів у тій самій групі, і навіть залишає нерозібрані винятки для повторного підняття, якщо жоден except* їх не покрив.

14 Правильне логування винятків

app/core/error_handlers.py — два різні підходи, обидва навмисні
logger.error("OpenAI API error on %s %s: %s", request.method, request.url.path, exc)
# -- без повного traceback: причина ВІДОМА (зовнішній сервіс), деталі не потрібні

logger.exception("Unhandled error on %s %s", request.method, request.url.path)
# -- З ПОВНИМ traceback: причина НЕВІДОМА, це і є розслідування бага

logger.exception(msg) можна викликати лише всередині except-блоку — він автоматично додає повний traceback поточного винятку (еквівалент logger.error(msg, exc_info=True)). logger.error(msg) без exc_info — звичайний рядок логу, без стектрейсу.

✅
Проєкт свідомо використовує обидва по-різному: помилка OpenAI — очікуваний зовнішній збій (rate limit, аутсейдж), повний traceback тут не додає інформації понад сам факт "OpenAI недоступний". Непередбачений виняток у catch-all-обробнику — це якраз розслідування невідомого бага, де кожен рядок traceback важливий.

15 Каверзні питання співбесіди

Натисніть на питання, щоб побачити відповідь.

БазаЧим iterable відрізняється від iterator?
Iterable має __iter__, що породжує ітератор. Iterator має і __iter__ (повертає себе), і __next__ (видає наступне значення або кидає StopIteration). Список — iterable, але не iterator.
БазаЧим генератор кращий за список для великих послідовностей?
Лінивість: генератор тримає в пам'яті лише поточний стан, а не всі значення одразу. Список матеріалізує все одразу в пам'яті; генератор видає значення по одному, на вимогу.
ПасткаЩо поверне повторний виклик next() на вичерпаному генераторі?
StopIteration — і не одноразово: генератор, що дійшов кінця, лишається "вичерпаним" назавжди (стан GEN_CLOSED), повторний виклик next() завжди кидатиме StopIteration знову, а не перезапускає перебір з початку.
ПросунутеЗвідки історично виріс синтаксис async/await?
З генераторів: PEP 342 (2006) додав .send()/.throw(), що дозволило писати "генератор-корутини" (@asyncio.coroutine + yield from) у ранньому asyncio. PEP 492 (2015, Python 3.5) додав async/await як окремий, явний синтаксис поверх тієї самої базової машинерії.
ПасткаЧи ловить except Exception: KeyboardInterrupt або asyncio.CancelledError?
Ні. Обидва — прямі підкласи BaseException, не Exception, саме щоб типовий "зловити все" код їх не проковтнув випадково. Лише голий except: (без типу) зловить їх теж.
БазаКоли виконується блок else у try/except/else?
Лише якщо блок try завершився БЕЗ винятку. Логічно схоже на перенесення коду в кінець try, але явно відокремлює "код, що може впасти" від "код, що виконується тільки після успіху".
ПасткаЩо станеться з винятком/return з try, якщо в finally теж є return?
return у finally завжди "перемагає" — тихо відкидає і значення return, і будь-який непіднятий виняток із блоків вище. Класична причина важких для дебагу багів; більшість лінтерів (включно з ruff) на це попереджають.
БазаРізниця raise X from Y і просто raise X усередині except?
from Y — явний ланцюжок (__cause__), просто raise X усередині except — неявний, автоматичний (__context__). Обидва зберігають повний traceback причини для дебагу; raise X from None повністю приховує ланцюжок.
ПросунутеНавіщо потрібні ExceptionGroup і except*?
До Python 3.11 виняток завжди був один. asyncio.TaskGroup може мати кілька задач, що впали одночасно — ExceptionGroup дозволяє піднести їх усі разом, не втрачаючи жодної; except* фільтрує групу за типом і може спрацювати кілька разів для різних типів у тій самій групі.
ПасткаКоли можна викликати logger.exception(...)?
Лише всередині блоку except — інакше немає "поточного" винятку, traceback якого можна прикріпити. Виклик поза except запишеться без корисного стектрейсу.
Живе кодуванняНапишіть генератор, що видає нескінченну послідовність Фібоначчі.
def fib():
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b — показує розуміння, що while True усередині генератора цілком безпечний, бо код виконується лише "по вимозі" на кожен next(), а не одразу весь нескінченний цикл.
