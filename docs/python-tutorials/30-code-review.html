00Як робити code review на співбесіді

Інтерв'юер оцінює не кількість знайдених дрібниць, а вміння бачити головне: що зламає прод, що відкриє дірку в безпеці, що загубить дані, і вміння пояснити це спокійно, як колезі.

  1. Прочитай код цілком один раз, не коментуючи. Зрозумій, що він має робити.
  2. Уточни контекст: скільки запитів, чи кілька інстансів, хто викликає, чи це гроші/PII. Від цього залежить, що критично.
  3. Іди за пріоритетами, а не зверху вниз (таблиця нижче). Почни з найважчого.
  4. Кожен коментар: що не так → чим це загрожує (конкретний сценарій) → як виправити.
  5. Наприкінці підсумуй: «блокери такі-то, решта — покращення» і запропонуй, що робити першим.

🎨
Аналогія для фронтендера. Це як рев'ю React-компонента: спершу «тут XSS через dangerouslySetInnerHTML» і «тут гонка відповідей fetch», а вже потім «винеси в кастомний хук» і «перейменуй змінну». Ніхто не почне з відступів, якщо компонент показує дані чужого користувача.
💬
Як формулювати. Не «це жахливо», а «blocker: тут requests.get всередині async def: поки чекаємо геокодер, цей воркер не обслуговує жодного іншого запиту. При 50 RPS латентність усіх ендпоінтів виросте до секунд. Пропоную httpx.AsyncClient зі спільним пулом».

01Пошук доставок Junior · очевидне

Ендпоінт пошуку доставок організації за частиною адреси. Знайди щонайменше 8 проблем.

❌ app/api/deliveries/search.py — до рев'ю
import requests
from fastapi import APIRouter
from sqlalchemy import text

router = APIRouter()

@router.get("/deliveries/search")
async def search(q: str, org_id: str, db=Depends(get_db), user=Depends(get_current_user)):
    print(f"user {user.email} searching {q}")
    try:
        rows = await db.execute(text(
            f"SELECT * FROM deliveries WHERE organization_id = '{org_id}' "
            f"AND address LIKE '%{q}%'"
        ))
        result = []
        for r in rows:
            weather = requests.get(f"https://api.weather.example/now?lat={r.latitude}&lon={r.longitude}").json()
            result.append({**dict(r._mapping), "weather": weather["temp"]})
        return result
    except:
        return []
🔎 Показати проблеми (10)
  1. Critical SQL-ін'єкція. q і org_id вклеєні f-рядком у SQL. Запит q=%' OR '1'='1 поверне доставки всіх організацій, а '; DROP TABLE … залежить лише від прав користувача БД.
  2. Critical IDOR / доступ до чужих даних. org_id приходить з query-параметра, а не з токена. Будь-хто підставляє чужий id і читає чужі доставки (туторіал 22).
  3. High Блокуючий requests у async def. Кожен виклик блокує event loop, тож усі інші запити воркера стоять.
  4. High Немає таймауту. requests за замовчуванням чекає вічно; повисне API погоди — повисне ендпоінт.
  5. High Голий except: return []. Ковтає все, навіть KeyboardInterrupt/CancelledError і помилки SQL. Клієнт бачить «нічого не знайдено» замість 500, а в логах порожньо.
  6. High N зовнішніх викликів у циклі (N+1 до API): 200 доставок = 200 послідовних HTTP-запитів.
  7. Medium print замість логера + PII (email) у логах + рядок пошуку, який може містити персональні дані.
  8. Medium SELECT * і без ліміту: витягує всі колонки (включно з нотатками), може повернути 100 000 рядків.
  9. Medium Відповідь API не перевіряється: .json()["temp"] впаде на 500/HTML-відповіді або іншій схемі.
  10. Low Немає схеми відповіді (response_model), немає типів, Depends не імпортовано, LIKE регістрозалежний.
✅ після рев'ю
import logging
from typing import Annotated
from fastapi import APIRouter, Depends, Query
from sqlalchemy import select

log = logging.getLogger(__name__)
router = APIRouter()

@router.get("/deliveries/search", response_model=list[DeliverySearchItem])
async def search_deliveries(
    q: Annotated[str, Query(min_length=2, max_length=100)],
    user: Annotated[User, Depends(get_current_user)],
    repo: Annotated[DeliveryRepository, Depends(get_delivery_repository)],
    limit: Annotated[int, Query(ge=1, le=100)] = 50,
) -> list[DeliverySearchItem]:
    log.info("delivery search", extra={"org_id": str(user.organization_id), "q_len": len(q)})
    return await repo.search_by_address(user.organization_id, q, limit=limit)

# repositories/delivery_repository.py
async def search_by_address(self, org_id: UUID, q: str, *, limit: int) -> list[Delivery]:
    pattern = "%" + q.replace("\\", "\\\\").replace("%", r"\%").replace("_", r"\_") + "%"
    stmt = (
        select(Delivery)
        .where(Delivery.organization_id == org_id, Delivery.address.ilike(pattern, escape="\\"))
        .order_by(Delivery.created_at.desc())
        .limit(limit)
    )
    return list((await self.session.execute(stmt)).scalars())

Чому так

  • Параметризований запит (SQLAlchemy Core/ORM передає значення окремо від SQL) → ін'єкція неможлива. Екранування % і _ — щоб користувач не перетворив пошук на «знайди все».
  • Тенант береться з токена (user.organization_id), а не з запиту, і фільтр живе в репозиторії, тож його неможливо забути.
  • Погода прибрана з ендпоінта пошуку. Чужий повільний API не повинен бути на критичному шляху пошуку. Якщо вона потрібна — окремий ендпоінт або фоновий збір з кешем (приклади 2–3).
  • Без try/except: неочікувана помилка має дійти до глобального обробника (500 + лог з traceback), а не перетворитися на порожній список.
  • Валідація вводу (min_length, max_length, limit ≤ 100) і response_model, який віддає лише дозволені поля.
  • Лог без PII: довжина запиту замість самого тексту, ідентифікатор замість email.

02Геокодинг з кешем Junior+ · кеш, логи, зовнішній API

Сервіс перетворює адресу на координати через Google Geocoding API і «кешує» результат. Знайди 10 проблем.

❌ app/services/geocoding.py — до рев'ю
import time, httpx, logging

API_KEY = "AIzaSyD-3x4mpl3-k3y"
CACHE = {}

async def geocode(address):
    if address in CACHE:
        return CACHE[address]
    url = f"https://maps.googleapis.com/maps/api/geocode/json?address={address}&key={API_KEY}"
    logging.info("calling " + url)
    for i in range(5):
        try:
            async with httpx.AsyncClient() as client:
                r = await client.get(url)
            data = r.json()
            loc = data["results"][0]["geometry"]["location"]
            CACHE[address] = (loc["lat"], loc["lng"])
            return CACHE[address]
        except Exception as e:
            logging.error("geocode failed: " + str(e))
            time.sleep(1)
    CACHE[address] = None
    return None
🔎 Показати проблеми (11)
  1. Critical Секрет у коді. API-ключ потрапить у git, логи CI, кожен форк. Його треба ротувати й брати з env/секрет-менеджера.
  2. Critical Ключ у логах: logging.info("calling " + url) пише URL разом з key=…. Плюс адреса клієнта (PII) у логах.
  3. High time.sleep(1) в async-коді блокує event loop на секунду при кожній невдачі, тобто 5 секунд «заморозки» всього воркера.
  4. High Ретраї без розбору: повторюємо і 400 (невалідна адреса), і ZERO_RESULTS, і REQUEST_DENIED (поганий ключ). Немає exponential backoff і jitter. 5 спроб × кожна адреса = швидко вичерпана квота платного API.
  5. High Статус не перевіряється: Google повертає HTTP 200 навіть для помилок, а справжній статус лежить у data["status"]. results[0] на ZERO_RESULTS дає IndexError, що маскується під «мережеву» помилку.
  6. High Адреса не URL-закодована: & чи # в адресі ламають запит, і через це можна підставити інші параметри (parameter injection).
  7. Medium Кеш без меж і без TTL: глобальний dict росте вічно (витік пам'яті), живе лише в одному процесі, не спільний для інстансів.
  8. Medium Кешуємо невдачу назавжди: CACHE[address] = None після тимчасового збою мережі. Адреса «ламається» до рестарту.
  9. Medium Ключ кешу — сирий рядок: «Хрещатик 22» і «хрещатик 22 » — різні записи. Нормалізації немає.
  10. Medium Новий AsyncClient на кожну спробу: нове TCP+TLS з'єднання щоразу, жодного пулу з'єднань.
  11. Low Логування: кореневий logging замість getLogger(__name__), конкатенація рядків, str(e) без traceback, немає типів повернення.
✅ після рев'ю
import asyncio, logging, random
from dataclasses import dataclass
import httpx
from cachetools import TTLCache

log = logging.getLogger(__name__)

@dataclass(frozen=True)
class Coordinates:
    lat: float
    lng: float

class GeocodingError(Exception): ...
class AddressNotFound(GeocodingError): ...

RETRYABLE_STATUS = {"OVER_QUERY_LIMIT", "UNKNOWN_ERROR"}

class GoogleGeocodingClient:
    def __init__(self, http: httpx.AsyncClient, api_key: str) -> None:
        self._http = http                                   # спільний клієнт з пулом, створений у lifespan
        self._key = api_key                                 # з settings (env), не з коду
        self._cache: TTLCache[str, Coordinates] = TTLCache(maxsize=10_000, ttl=24 * 3600)

    @staticmethod
    def _norm(address: str) -> str:
        return " ".join(address.lower().split())

    async def geocode(self, address: str) -> Coordinates:
        key = self._norm(address)
        if (hit := self._cache.get(key)) is not None:
            return hit
        coords = await self._fetch_with_retry(key)
        self._cache[key] = coords                           # кешуємо лише успіх
        return coords

    async def _fetch_with_retry(self, address: str, attempts: int = 3) -> Coordinates:
        for attempt in range(attempts):
            try:
                r = await self._http.get(
                    "https://maps.googleapis.com/maps/api/geocode/json",
                    params={"address": address, "key": self._key},     # httpx сам закодує параметри
                    timeout=httpx.Timeout(5.0, connect=2.0),
                )
                r.raise_for_status()
                data = r.json()
            except (httpx.TimeoutException, httpx.TransportError, httpx.HTTPStatusError) as e:
                status = "TRANSPORT"
                log.warning("geocoding transport error", extra={"attempt": attempt, "error": type(e).__name__})
            else:
                status = data.get("status")
                if status == "OK":
                    loc = data["results"][0]["geometry"]["location"]
                    return Coordinates(lat=loc["lat"], lng=loc["lng"])
                if status == "ZERO_RESULTS":
                    raise AddressNotFound()                     # не ретраїмо: відповідь не зміниться
                if status not in RETRYABLE_STATUS:
                    raise GeocodingError(f"geocoding rejected: {status}")   # REQUEST_DENIED тощо
            if attempt < attempts - 1:
                await asyncio.sleep(random.uniform(0, 0.5 * 2 ** attempt))  # backoff + jitter, НЕ блокує loop
        raise GeocodingError(f"geocoding failed after {attempts} attempts (last: {status})")

Чому так

  • Секрети лише з конфігурації (pydantic-settings, env, Vault). У логи не потрапляють ні ключ, ні адреса: логуємо тип помилки і номер спроби.
  • Ретраїмо лише тимчасове (таймаут, мережа, 5xx, OVER_QUERY_LIMIT). Помилки, що не зникнуть, піднімаємо одразу окремими типами винятків, щоб викликач міг відрізнити «адреси не існує» від «сервіс недоступний».
  • await asyncio.sleep замість time.sleep: пауза віддає керування event loop, і інші запити обробляються.
  • Кеш з межею і TTL, нормалізований ключ, кешується лише успіх. Для кількох інстансів — Redis з тим самим ключем (туторіал 20).
  • Один httpx.AsyncClient на застосунок (у lifespan): пул з'єднань, keep-alive, явні таймаути.
  • Повертаємо значення-об'єкт Coordinates (frozen dataclass), а не голий tuple або None.
ℹ️
Залишкова проблема, яку варто назвати на співбесіді сеньйорського рівня: дві корутини одночасно геокодують одну нову адресу, і обидві підуть в API (немає захисту від одночасних промахів кешу, тобто stampede). Рішення — у прикладі 5.

03Пакетний геокодинг: asyncio і конкурентність Middle · корутини

Після імпорту Excel треба геокодувати 2 000 доставок і зберегти координати. Розробник «прискорив» код через asyncio. Знайди 9 проблем.

❌ app/services/import_geocode.py — до рев'ю
import asyncio

processed = 0

async def geocode_one(session, geocoder, delivery):
    global processed
    coords = await geocoder.geocode(delivery.address)
    delivery.latitude, delivery.longitude = coords.lat, coords.lng
    session.add(delivery)
    await session.commit()
    processed = processed + 1
    if processed % 100 == 0:
        print("progress", processed)

async def geocode_all(session, geocoder, deliveries):
    tasks = [geocode_one(session, geocoder, d) for d in deliveries]
    await asyncio.gather(*tasks)
    return processed

def geocode_import_sync(deliveries):
    # викликається з FastAPI-ендпоінта після завантаження файлу
    return asyncio.run(geocode_all(get_session(), get_geocoder(), deliveries))
🔎 Показати проблеми (9)
  1. Critical Одна AsyncSession на 2 000 конкурентних корутин. AsyncSession (як і Session) не безпечна для одночасного використання з кількох задач: паралельні commit на одному з'єднанні дають помилки на кшталт «another operation is in progress», зіпсований стан identity map або частково збережені дані.
  2. Critical Необмежена конкурентність: gather запускає 2 000 запитів до Google одночасно. Отримаємо OVER_QUERY_LIMIT, бан за rate limit, вичерпаний пул з'єднань HTTP і БД.
  3. High Одна помилка ламає все незрозуміло як. gather без return_exceptions піднімає першу помилку, але інші задачі продовжують виконуватись у фоні. Частина доставок збережена, частина ні, і невідомо які.
  4. High asyncio.run всередині вже запущеного event loop. Якщо geocode_import_sync викликати з async def-ендпоінта: RuntimeError: asyncio.run() cannot be called from a running event loop. Якщо з def-ендпоінта (threadpool), запуститься новий loop у потоці, і об'єкти, прив'язані до головного loop (сесія, httpx-клієнт), зламаються. До того ж HTTP-запит чекатиме, поки 2 000 адрес не закінчаться.
  5. High Глобальний лічильник processed: модульна змінна спільна між усіма імпортами всіх користувачів (два імпорти одночасно змішують прогрес), не скидається між викликами, а return processed повертає не те, що здається.
  6. Medium Commit на кожну доставку: 2 000 транзакцій і 2 000 round-trip замість кількох батчів.
  7. Medium Немає ізоляції тенанта і ідемпотентності: повторний виклик (ретрай) знову платно геокодує вже оброблені доставки.
  8. Medium Немає таймауту на весь процес і обробки скасування: користувач закрив вкладку, а 2 000 викликів тривають.
  9. Low print для прогресу замість логера/статусу задачі, яку може прочитати фронтенд.

Тонкий момент про гонку. processed = processed + 1 між двома await не має await, тому в asyncio сама по собі ця операція атомарна відносно інших корутин (на відміну від потоків). Проблема тут не в цьому рядку, а в тому, що стан глобальний і спільний для різних запусків. Варто проговорити цю різницю вголос, бо інтерв'юер часто перевіряє саме її (туторіал 29, розділ A2).

✅ після рев'ю: ендпоінт ставить задачу, воркер обробляє батчами з обмеженою конкурентністю
import asyncio, logging
from dataclasses import dataclass, field

log = logging.getLogger(__name__)

@dataclass
class GeocodeReport:
    ok: int = 0
    not_found: list[UUID] = field(default_factory=list)
    failed: list[UUID] = field(default_factory=list)

async def geocode_pending(
    session_factory: async_sessionmaker[AsyncSession],
    geocoder: GoogleGeocodingClient,
    org_id: UUID,
    *,
    concurrency: int = 10,
    batch_size: int = 200,
) -> GeocodeReport:
    report = GeocodeReport()
    sem = asyncio.Semaphore(concurrency)                       # не більше 10 запитів до Google одночасно

    async def resolve(d: DeliveryToGeocode) -> tuple[UUID, Coordinates | None | Exception]:
        async with sem:
            try:
                return d.id, await geocoder.geocode(d.address)    # лише HTTP, БД тут не чіпаємо
            except AddressNotFound:
                return d.id, None
            except GeocodingError as e:
                return d.id, e

    while True:
        async with session_factory() as s:                     # читаємо батч окремою короткою сесією
            batch = await DeliveryRepository(s).pending_geocode(org_id, limit=batch_size)
        if not batch:
            return report

        async with asyncio.timeout(120):                       # межа на батч (Python 3.11+)
            async with asyncio.TaskGroup() as tg:              # structured concurrency
                tasks = [tg.create_task(resolve(d)) for d in batch]
        results = [t.result() for t in tasks]

        async with session_factory() as s, s.begin():          # ОДНА сесія, ОДИН потік, ОДНА транзакція на батч
            repo = DeliveryRepository(s)
            for delivery_id, res in results:
                if isinstance(res, Coordinates):
                    await repo.set_coordinates(org_id, delivery_id, res.lat, res.lng)   # status → geocoded
                    report.ok += 1
                elif res is None:
                    await repo.mark_geocode_failed(org_id, delivery_id, reason="not_found")
                    report.not_found.append(delivery_id)
                else:
                    await repo.mark_geocode_failed(org_id, delivery_id, reason="error")
                    report.failed.append(delivery_id)
        log.info("geocode batch done", extra={"org_id": str(org_id), "ok": report.ok,
                                              "not_found": len(report.not_found), "failed": len(report.failed)})

# Ендпоінт не чекає 2 000 адрес: ставить задачу у фон і повертає 202 + id задачі для статусу.
# (Celery/arq-воркер, або для простих випадків — окрема asyncio-задача зі збереженим посиланням, див. приклад 5.)

Чому так

  • Конкурентність — лише для I/O, що цього потребує (HTTP до Google), і обмежена семафором. Робота з БД послідовна в одній сесії на батч: сесія ніколи не використовується з двох корутин одночасно.
  • TaskGroup замість gather: якщо щось піде не так (наприклад, таймаут), решта задач скасовується, і ми не маємо «напівживих» фонових запитів. Очікувані помилки (AddressNotFound, GeocodingError) обробляються всередині resolve, тому не валять усю групу.
  • Батчі й одна транзакція на батч: у 200 разів менше commit-ів; при падінні втрачається максимум один батч, і він переобробиться.
  • Ідемпотентність: беремо лише доставки зі статусом pending_geocode, тож повторний запуск продовжує з місця зупинки і не платить двічі.
  • Стан — локальний (GeocodeReport), а не глобальний. Різні запуски не змішуються.
  • Довга робота поза HTTP-запитом: ендпоінт повертає 202, а прогрес видно через статус задачі. Ніякого asyncio.run з коду, що вже працює в event loop.

def verify_signature(raw: bytes, header: str | None, secret: bytes) -> None:
    expected = hmac.new(secret, raw, hashlib.sha256).hexdigest()
    if not header or not hmac.compare_digest(expected, header):      # стійко до timing-атак
        raise HTTPException(400, "invalid signature")

🔎 Показати проблеми (9)
  1. Critical threading.Lock навколо await в async-коді. Перша корутина бере лок і на await call_openai віддає керування. Друга корутина в тому ж потоці викликає _lock.acquire(), яке блокує весь потік, тобто весь event loop. Перша корутина вже ніколи не продовжиться, і це deadlock усього воркера.   4. High Один глобальний лок на всі маршрути: навіть з asyncio.Lock усі пояснення стали б у чергу по одному (20 с кожне). Потрібен лок на ключ або об'єднання однакових запитів.
  5. High Немає повторної перевірки кешу під локом (double-checked): друга корутина, що чекала лок, все одно викличе OpenAI, хоча перша вже заповнила кеш.
  6. High Голий except: ковтає CancelledError. Коли клієнт відключився або спрацював зовнішній таймаут, задачу скасовують, а код ловить скасування, кешує «Explanation unavailable» на 5 хвилин і продовжує роботу. Скасування зламане, а користувачі отримують кешовану заглушку.
  7. High Fire-and-forget без посилання. Event loop тримає лише слабкі посилання на задачі. Задача з create_task, на яку ніхто не посилається, може бути зібрана збирачем сміття до завершення.   9. Medium Кешується невдача («unavailable») так само, як успіх, тож тимчасовий збій OpenAI «застигає» на 5 хвилин для всіх.

import asyncio, logging, time
from dataclasses import dataclass

log = logging.getLogger(__name__)

@dataclass(frozen=True)                       # незмінне значення в кеші: ніхто не змінить спільний об'єкт
class Explanation:
    text: str
    created_at: float

class ExplanationService:
    def __init__(self, ai: AIClient, routes: RouteRepository, ttl: float = 300, maxsize: int = 2048) -> None:
        self._ai, self._routes, self._ttl, self._maxsize = ai, routes, ttl, maxsize
        self._cache: dict[tuple[UUID, UUID], Explanation] = {}
        self._inflight: dict[tuple[UUID, UUID], asyncio.Task[Explanation]] = {}

    def _fresh(self, key) -> Explanation | None:
        e = self._cache.get(key)
        return e if e and time.monotonic() - e.created_at < self._ttl else None

    async def explain(self, org_id: UUID, route_id: UUID) -> Explanation:
        key = (org_id, route_id)                                    # тенант у ключі
        if (hit := self._fresh(key)) is not None:
            return hit
        task = self._inflight.get(key)
        if task is None:                                            # singleflight: один виклик OpenAI на ключ
            task = asyncio.create_task(self._compute(org_id, route_id))
            self._inflight[key] = task
            task.add_done_callback(lambda _t: self._inflight.pop(key, None))
        return await asyncio.shield(task)    # скасування одного очікувача не скасовує спільну роботу

    async def _compute(self, org_id: UUID, route_id: UUID) -> Explanation:
        summary = await self._routes.summary(org_id, route_id)      # перевірка доступу: чужий маршрут → NotFound
        async with asyncio.timeout(20):
            text = await self._ai.explain(summary)                  # помилка/таймаут піднімаються, НЕ кешуються
        exp = Explanation(text=text, created_at=time.monotonic())
        if len(self._cache) >= self._maxsize:
            self._cache.pop(next(iter(self._cache)))                # найстаріший (dict зберігає порядок вставки)
        self._cache[(org_id, route_id)] = exp
        return exp

# Фонові задачі: зберігаємо посилання, логуємо помилки, чекаємо при зупинці
class BackgroundTasks:
    def __init__(self) -> None:
        self._tasks: set[asyncio.Task] = set()

    def spawn(self, coro, *, name: str) -> None:
        t = asyncio.create_task(coro, name=name)
        self._tasks.add(t)                                          # сильне посилання → GC не збере
        t.add_done_callback(self._done)

    def _done(self, t: asyncio.Task) -> None:
        self._tasks.discard(t)
        if not t.cancelled() and (exc := t.exception()) is not None:
            log.error("background task failed", exc_info=exc, extra={"task": t.get_name()})

    async def drain(self, timeout: float = 10) -> None:            # викликати в lifespan при shutdown
        if self._tasks:
            await asyncio.wait(self._tasks, timeout=timeout)

# Ендпоінт: відповідь збирається окремо, кеш не мутується
@router.get("/routes/{route_id}/explanation", response_model=ExplanationOut)
async def get_explanation(route_id: UUID, user: CurrentUser, svc: ExplainerDep, bg: BackgroundDep):
    exp = await svc.explain(user.organization_id, route_id)
    bg.spawn(track_usage(user.organization_id), name="track_usage")
    return ExplanationOut(text=exp.text)                            # email користувача в кеш не потрапляє

Чому так

  • Singleflight замість глобального лока: одночасні запити на той самий маршрут чекають одну спільну задачу, а різні маршрути йдуть паралельно. Повторна перевірка не потрібна: перший приходить до _inflight раніше, ніж будь-хто дійде до await, бо між перевіркою і записом у словник немає await.
  • asyncio.shield: якщо один клієнт відключився і його корутину скасували, спільна задача продовжується для інших очікувачів.
  • Жодного threading.Lock навколо await і жодного lru_cache на корутинах. Для async-кешу: кешуємо результат (значення), а не корутину.
  • Незмінні значення в кеші і окремий DTO відповіді: дані запиту (email) ніколи не змішуються зі спільним станом.
  • Скасування поважається: немає голого except; таймаут і помилки OpenAI піднімаються і не кешуються. Заглушку «недоступно» можна показати на рівні ендпоінта, не кешуючи її.
  • Фонові задачі під контролем: сильні посилання, лог помилок, очікування при shutdown. Для важливого (облік використання, за яким білінг) краще черга або outbox, ніж задача в пам'яті процесу.
  • Межі процесу: кеш і singleflight тут — на інстанс. На кількох машинах спільний кеш і лок — Redis (SET NX + TTL), див. туторіал 29, D1–D2.

06П'ять найпоширеніших антипатернів у Python-коді

1. Ковтання винятків («Pokémon exception handling»: gotta catch 'em all)

❌
try:
    route = await optimizer.solve(problem)
except:
    pass                     # або: except Exception: return None
✅
try:
    route = await optimizer.solve(problem)
except NoFeasibleSolution as e:                   # ловимо лише те, що вміємо обробити
    raise HTTPException(422, "No feasible route for these constraints") from e
# усе інше — до глобального обробника: 500 + log.exception з traceback

Чому погано: баг перетворюється на «тихі» неправильні дані; голий except ловить навіть CancelledError, KeyboardInterrupt, SystemExit. Правило: ловити конкретні винятки якомога ближче до місця, де знаєш, що робити; інакше пропускати вище; log.exception або exc_info=True, щоб зберегти traceback; raise … from e, щоб не губити причину.

2. Блокуючий код в async (sync-in-async)

❌
async def handler():
    data = requests.get(url).json()          # блокуючий HTTP
    time.sleep(1)                            # блокуючий сон
    rows = psycopg2_cursor.execute(sql)      # синхронний драйвер БД
    result = heavy_numpy_or_ortools(data)    # CPU на секунди
✅
async def handler(http: httpx.AsyncClient):
    data = (await http.get(url, timeout=5)).json()
    await asyncio.sleep(1)
    rows = await session.execute(stmt)                           # asyncpg / async SQLAlchemy
    result = await asyncio.to_thread(heavy_numpy_or_ortools, data)  # або ProcessPool / Celery для CPU
# альтернатива: зробити ендпоінт звичайним def — FastAPI виконає його в threadpool

Чому погано: event loop однопотоковий: поки один блокуючий виклик триває, жоден інший запит цього воркера не обробляється. Симптоми — «латентність усіх ендпоінтів стрибає до секунд при невеликому RPS», health-check падає (туторіал 6, туторіал 10).

3. Mutable default arguments і глобальний змінюваний стан

❌
def add_stop(stop, stops=[]):        # список створюється ОДИН раз
    stops.append(stop)
    return stops

current_org = None                   # "контекст" через глобальну змінну
async def handler(user):
    global current_org
    current_org = user.organization_id
    await do_work()                  # інший запит змінить current_org під час await
✅
def add_stop(stop, stops: list | None = None) -> list:
    stops = [] if stops is None else stops
    stops.append(stop)
    return stops

from contextvars import ContextVar
current_org: ContextVar[UUID | None] = ContextVar("current_org", default=None)
async def handler(user):
    current_org.set(user.organization_id)    # своє значення в кожній задачі/запиті
    await do_work()
# а найкраще — передавати залежності явно (параметри, Depends), без прихованого стану

Чому погано: значення за замовчуванням обчислюється при визначенні функції, тож усі виклики ділять один список. Глобальна змінна в async-сервері спільна для всіх одночасних запитів, і між await її перезапише інший запит. Звідси витоки даних між користувачами. ContextVar дає кожній задачі asyncio власну копію.

4. N+1 запитів (до БД або до API)

❌
routes = (await session.execute(select(Route))).scalars().all()
for r in routes:
    for stop in r.stops:                      # lazy load → окремий SELECT на кожен маршрут
        print(stop.delivery.address)          # і ще SELECT на кожну зупинку
# (в async SQLAlchemy це взагалі впаде: MissingGreenlet — ліниве завантаження в async заборонене)
✅
stmt = (
    select(Route)
    .where(Route.organization_id == org_id)
    .options(selectinload(Route.stops).joinedload(RouteStop.delivery))
)
routes = (await session.execute(stmt)).scalars().all()    # 2–3 запити замість 1 + N + N·M

Чому погано: 50 маршрутів × 30 зупинок = 1 551 запит на одну сторінку. Локально з 3 рядками непомітно, у проді — секунди. Той самий патерн з HTTP: виклик API в циклі замість батч-ендпоінта або обмеженої конкурентності (приклад 1, приклад 3). Детальніше: туторіал 18, питання 22.

5. «Товстий» ендпоінт (God function) і змішування шарів

❌ 200 рядків в одному роутері
@router.post("/routes/optimize")
async def optimize(body: dict, db=Depends(get_db)):
    # парсинг body руками, валідація if-ами, SQL-запити, виклик OR-Tools,
    # розрахунок квоти, формування email, логування, побудова JSON — усе тут
    ...
✅ тонкий роутер → сервіс → репозиторій
@router.post("/routes/optimize", response_model=OptimizeResult)
async def optimize(body: OptimizeRequest,                     # Pydantic валідує вхід
                   org: Annotated[Organization, Depends(require_route_quota)],
                   service: Annotated[RouteOptimizerService, Depends(get_route_optimizer_service)]):
    return await service.optimize(org, body)                  # бізнес-логіка не знає про HTTP

Чому погано: неможливо протестувати логіку без HTTP і БД, неможливо перевикористати (CLI, Celery-задача), будь-яка зміна зачіпає все. Так влаштований і цей проєкт: api/ → services/ → repositories/ з DI через Depends (туторіал 1, туторіал 13, туторіал 14).

ℹ️
Ще кілька, які часто трапляються: «магічні» рядки й числа замість Enum/констант; dict замість типізованих моделей (primitive obsession); передчасна оптимізація і кеш «про всяк випадок»; копіпаст замість функції; isinstance-драбини замість поліморфізму; from module import *; відкриті файли/з'єднання без with.

0712 швидких async-пасток (бліц на співбесіді)

Кожна — 1–3 рядки. Спершу скажи, що не так, потім відкривай.

1. result = fetch_user(1) (де fetch_user — async def)

Забутий await. result — об'єкт корутини, функція не виконалась (warning «coroutine was never awaited»). Ловиться тайпчекером: mypy (код помилки unused-coroutine), pyright (reportUnusedCoroutine).

2. for u in urls: data.append(await client.get(u))

Послідовно, а не конкурентно. Кожен запит чекає попередній. Якщо порядок і залежність не потрібні: TaskGroup/gather з Semaphore (приклад 3).

3. await asyncio.gather(*[client.get(u) for u in ten_thousand_urls])

Необмежена конкурентність: 10 000 одночасних з'єднань, rate limit, вичерпання файлових дескрипторів і пулу. Потрібен Semaphore або пакети.

4. asyncio.create_task(send_email(...)) і більше нічого

Задача без посилання може бути зібрана GC, винятки втрачаються, при shutdown обривається. Тримати в set + done-callback (приклад 5) або черга. Ruff ловить це правилом RUF006 (asyncio-dangling-task).

5. except Exception: ... навколо await — чи ловить скасування?

З Python 3.8 asyncio.CancelledError наслідує BaseException, тож except Exception його не ловить, і це правильно. А голий except: або except BaseException: — ловить і ламає скасування. Якщо треба прибрати за собою, то finally або except CancelledError: cleanup(); raise.

6. @lru_cache над async def

Кешує об'єкт корутини; другий виклик → RuntimeError: cannot reuse already awaited coroutine. Кешувати результат (див. приклад 5) або async-lru.

7. with threading.Lock(): await something()

Лок потоків, утримуваний через await, призводить до deadlock event loop, щойно інша корутина спробує його взяти. Потрібен asyncio.Lock.

8. Одна AsyncSession в gather з кількох корутин

AsyncSession не безпечна для конкурентного використання з кількох задач. Кожна задача — своя сесія з async_sessionmaker, або конкурентно лише I/O, а запис послідовно (приклад 3).

9. asyncio.run(main()) всередині FastAPI-обробника

В async def → RuntimeError (loop уже працює). У def → новий loop у потоці, несумісний з об'єктами головного loop. Просто await у async-коді, або asyncio.run_coroutine_threadsafe з потоку в наявний loop.

10. if key not in cache: cache[key] = await load(key) — гонка?

Так: між перевіркою і записом є await, тож кілька корутин одночасно не знайдуть ключ і всі підуть у load (stampede). Для дорогих викликів — singleflight через спільну Task (приклад 5). Сам запис у dict без await атомарний відносно інших корутин.

11. await asyncio.wait_for(task, 5) — що станеться з task після таймауту?

wait_for скасує задачу при таймауті. Якщо задача спільна для кількох очікувачів, обгорни її в asyncio.shield(task). Для блоку коду з 3.11 зручніше async with asyncio.timeout(5):.

12. async def get(): return requests.get(url) працює в тестах, чому це проблема?

У тесті один запит, тож блокування не видно. Під навантаженням блокує event loop. «Async def» не робить код асинхронним: асинхронними мають бути самі виклики I/O (await на async-бібліотеці).
