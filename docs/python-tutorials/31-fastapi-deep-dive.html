00З чого зроблений FastAPI

Перше питання співбесіди часто звучить як «що таке FastAPI». Добра відповідь — у три шари, а не «швидкий фреймворк».

⚛️
Аналогія з фронтенду
Starlette — як React (рендер і події), FastAPI — як Next.js поверх нього (конвенції, роутинг, DX), Pydantic — як zod, тільки схема одночасно стає і валідацією, і TypeScript-типом, і OpenAPI-документацією.

Головна ідея FastAPI: сигнатура функції — це контракт. Анотації типів параметрів кажуть фреймворку, звідки брати дані (path, query, body, header, залежність), як їх валідувати і що показати в Swagger. Тому майже все в цьому туторіалі зводиться до питання «що FastAPI робить з сигнатурою під час старту і під час запиту».

  • Під час старту (include_router, декоратор @router.get): FastAPI один раз аналізує сигнатуру, будує дерево залежностей (Dependant) і Pydantic-моделі для валідації. Це дорого, але робиться один раз.
  • Під час запиту: проходить по готовому дереву, розв'язує залежності, валідує, викликає хендлер, серіалізує відповідь.

01Життєвий цикл запиту

Що відбувається від TCP-пакета до JSON у відповіді. На цій схемі тримаються майже всі наступні розділи.

Як це виглядає на реальному ендпоінті цього проєкту:

app/api/deliveries/router.py (main)
router = APIRouter(tags=["deliveries"], dependencies=[Depends(get_current_user)])


@router.get("/{delivery_id}", response_model=DeliveryRead)
async def get_delivery(
    delivery_id: uuid.UUID,                                    # 5. path-параметр, валідується як UUID
    service: DeliveryService = Depends(get_delivery_service),  # 4. дерево залежностей
) -> DeliveryRead:
    delivery = await service.get(delivery_id)                  # 6. хендлер
    if delivery is None:
        raise HTTPException(status_code=404, detail="Delivery not found")
    return DeliveryRead.model_validate(delivery)               # 7. серіалізація

Дерево залежностей тут таке: get_delivery_service → get_delivery_repository → get_db, а також get_current_user на рівні роутера, який теж використовує get_db. Сесія get_db при цьому створюється один раз: FastAPI кешує результат залежності в межах запиту.

🎯
Як відповісти на співбесіді
«Uvicorn приймає з'єднання і віддає ASGI-скоуп у застосунок. Запит проходить стек middleware, роутер знаходить маршрут, FastAPI розв'язує дерево залежностей (з кешуванням на запит), валідує параметри Pydantic'ом, викликає хендлер: async — в event loop, sync — у threadpool. Результат фільтрується через response_model, серіалізується, і відповідь іде назад через middleware. Після цього виконуються background tasks і закриваються ресурси yield-залежностей.»

02async def vs def: event loop і threadpool

Найпопулярніше питання по FastAPI. Помилка тут — найчастіша причина «сервіс тормозить під навантаженням».

Що всерединіЯк оголоситиЧому
Тільки async-бібліотеки (asyncpg, httpx.AsyncClient, redis.asyncio)async defНайдешевше: немає перемикання потоків
Синхронна бібліотека (requests, psycopg2, boto3, pandas)defFastAPI сам винесе в threadpool
Здебільшого async, але один блокуючий викликasync def + await asyncio.to_thread(fn)Блокуюча частина — в потоці, решта — в loop
Важкий CPU (OR-Tools, numpy на хвилини)Celery / ProcessPoolПотік не обходить GIL і з'їдає слот threadpool

У проєкті солвер маршрутів OR-Tools — синхронний і CPU-важкий, тому його викликають через asyncio.to_thread (детально — туторіал 21, розділ 08):

app/services/route_optimizer/service.py (спрощено)
    # OR-Tools blocks for seconds: the solve runs in a worker thread, so the
    # event loop keeps serving other requests while the solver searches.
    result = await asyncio.to_thread(_build_and_solve, solver)

А ось класична помилка, яку дають на code review:

❌ блокує event loop
@router.get("/geocode")
async def geocode(address: str):
    resp = requests.get(GEOCODE_URL, params={"address": address})  # синхронний HTTP у async def
    return resp.json()
✅ два правильні варіанти
@router.get("/geocode")
def geocode(address: str):                       # варіант 1: просто def → threadpool
    return requests.get(GEOCODE_URL, params={"address": address}, timeout=5).json()


@router.get("/geocode")
async def geocode(address: str, http: HttpClient):  # варіант 2: async-клієнт (один на застосунок)
    resp = await http.get(GEOCODE_URL, params={"address": address})
    return resp.json()
⚠️
Тонкі моменти
1. Ліміт threadpool за замовчуванням — 40 потоків (anyio CapacityLimiter). Його ділять sync-ендпоінти, sync-залежності, UploadFile-операції і sync background tasks. 2. asyncio.to_thread використовує інший пул — default executor asyncio (min(32, cpu + 4) потоків). 3. Знайти блокування допомагає PYTHONASYNCIODEBUG=1 або loop.slow_callback_duration: asyncio тоді логує колбеки, що тримали loop довше 100 мс.

03Dependency Injection углиб

Depends — серце FastAPI. Тут перевіряють, чи розумієш ти дерево, кеш, yield і overrides.

3.1 Дерево і кеш на запит

Залежність — будь-який callable. Її параметри FastAPI розв'язує так само, як параметри ендпоінта: вони можуть бути query, header або іншими залежностями. Виходить дерево, і кожен вузол обчислюється один раз на запит (use_cache=True за замовчуванням). Тому get_current_user і репозиторії в проєкті отримують одну й ту саму сесію.

app/core/dependencies.py (main)
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async for session in get_session():
        yield session


def get_user_repository(db: AsyncSession = Depends(get_db)) -> UserRepository:
    return UserRepository(db)


async def get_current_user(
    token: str = Depends(oauth2_scheme),
    user_repo: UserRepository = Depends(get_user_repository),
) -> User:
    ...


async def require_admin(user: User = Depends(get_current_user)) -> User:
    if user.role != UserRole.ADMIN:
        raise HTTPException(status_code=403, detail="Admin role required")
    return user
💡
Коли потрібен Depends(..., use_cache=False)
Рідко: коли залежність має повертати свіже значення щоразу, коли її згадано в дереві (наприклад, генератор унікального ID). Для сесії БД кеш — саме те, що треба: інакше в одному запиті було б кілька транзакцій.

3.2 Залежності з yield: ресурс і його закриття

Код до yield — це «setup», після нього — «teardown». Це аналог контекстного менеджера, і FastAPI гарантує teardown навіть після помилки в хендлері. Якщо обернути yield у try/except, виняток із хендлера прилетить у залежність (так роблять rollback).

✅ сесія з транзакцією на запит (покращений варіант)
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()       # хендлер відпрацював без помилок
        except Exception:
            await session.rollback()     # будь-яка помилка → відкат
            raise                        # обов'язково прокинути далі

У цьому проєкті commit робить репозиторій (BaseRepository.create викликає session.commit()), а get_db тільки закриває сесію. Простіше, але кілька записів в одному запиті не атомарні: якщо другий упаде, перший уже закомічено. «Unit of Work на запит» з прикладу вище — типова відповідь на питання «як зробити атомарний ендпоінт».

⚠️
Пастка: yield-залежність і BackgroundTasks
Момент виконання teardown змінювався між версіями: до 0.106 він ішов після відправки відповіді (і background tasks могли користуватися сесією), у 0.106 його перенесли до відправки, а в нових версіях з'явився явний вибір (Depends(..., scope=...)). Практичне правило, яке працює в усіх версіях: не передавай request-scoped сесію у фонову задачу, а відкривай у задачі нову (async with AsyncSessionLocal() as s:).

3.3 Annotated: менше повторів

Сучасний стиль, який рекомендує документація FastAPI: оголосити залежність один раз як тип.

app/core/deps_types.py (пропозиція)
from typing import Annotated

DbSession = Annotated[AsyncSession, Depends(get_db)]
CurrentUser = Annotated[User, Depends(get_current_user)]
AdminUser = Annotated[User, Depends(require_admin)]


@router.get("/me")
async def me(user: CurrentUser) -> CurrentUserRead:   # без "= Depends(...)" у кожному ендпоінті
    return CurrentUserRead.model_validate(user)

3.4 Залежності на рівні роутера і застосунку

Коли результат залежності не потрібен, а потрібен тільки побічний ефект (перевірка доступу, rate limit), її вішають на роутер. Так у проєкті закрито всі квантові ендпоінти:

app/main.py (main)
app.include_router(
    build_ledger_router(get_quantum_ledger, get_ibm_runtime_service_factory),
    prefix=f"{API_V1_PREFIX}/quantum/ledger",
    dependencies=[Depends(require_admin)],   # кожен маршрут роутера — тільки для адміна
)

3.6 dependency_overrides — головна причина, чому DI окупається

У тестах будь-яку залежність можна підмінити, не чіпаючи код ендпоінтів. Саме так conftest.py проєкту підставляє SQLite і тестового користувача (див. розділ 11).

4.2 response_model — фільтр безпеки, а не тільки документація

Хендлер може повернути ORM-об'єкт User з hashed_password. Якщо response_model=CurrentUserRead, у JSON потраплять лише поля схеми. Без нього легко злити хеш пароля або внутрішні поля.

app/schemas/auth.py (main, спрощено)
class CurrentUserRead(BaseModel):
    model_config = ConfigDict(from_attributes=True, populate_by_name=True)

    id: uuid.UUID
    email: EmailStr
    organization_id: uuid.UUID = Field(serialization_alias="organizationId")
    role: UserRole
    is_verified: bool = Field(serialization_alias="isVerified")
  • Анотація повернення -> DeliveryRead у нових FastAPI працює як response_model.
  • response_model_exclude_unset=True корисний для PATCH-відповідей.
  • Повернення Response напряму (JSONResponse, ORJSONResponse) пропускає валідацію і фільтрацію. Це швидше, але й небезпечніше.

4.3 Вартість серіалізації

На великих списках (тисячі доставок) серіалізація стає помітною. Що допомагає:

  1. Пагінація: не віддавати 10 000 рядків одним запитом (туторіал 32, розділ 07).
  2. Повертати модель один раз: в проєкті [DeliveryRead.model_validate(d) for d in deliveries], а потім FastAPI ще раз валідує список через response_model. Подвійна робота — відомий компроміс; у гарячих ендпоінтах повертають ORM-об'єкти і дають FastAPI зробити валідацію один раз.
  3. TypeAdapter(list[DeliveryRead]) + dump_json для ручної швидкої серіалізації.

05Помилки й exception handlers

Один формат помилок для всього API — ознака зрілого бекенду.

За замовчуванням FastAPI повертає: HTTPException → {"detail": "..."}; помилка валідації → 422 зі списком помилок; неперехоплений виняток → 500 з plain-text тілом. У проєкті все це вирівняно в app/core/error_handlers.py:

app/core/error_handlers.py (main, фрагмент)
def register_exception_handlers(app: FastAPI) -> None:
    @app.exception_handler(RequestValidationError)
    async def handle_validation_error(request: Request, exc: RequestValidationError) -> JSONResponse:
        return JSONResponse(
            status_code=status.HTTP_422_UNPROCESSABLE_CONTENT,
            content={"detail": _validation_error_message(exc)},  # список → один рядок для UI
        )

    @app.exception_handler(QuotaExceededError)
    async def handle_quota_exceeded(request: Request, exc: QuotaExceededError) -> JSONResponse:
        ...
  • Доменні винятки (QuotaExceededError) кидає сервісний шар, який нічого не знає про HTTP, а мапінг у статус-код живе в одному місці.
  • Handler для Exception ловить усе інше: логує зі стеком (logger.exception), а клієнту віддає загальне «Internal error» без внутрішніх деталей.
  • Хендлер для Starlette HTTPException (а не тільки FastAPI-шного) перехоплює також 404/405 від роутера.

06Lifespan: старт і зупинка застосунку

Де створювати пули, клієнти і моделі так, щоб вони жили весь час роботи процесу і коректно закривались.

app/main.py (пропозиція)
from contextlib import asynccontextmanager


@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup: один HTTP-клієнт із пулом з'єднань на весь процес
    app.state.http = httpx.AsyncClient(timeout=httpx.Timeout(10.0))
    yield
    # shutdown: закрити сокети і пул БД, щоб деплой не обривав з'єднання
    await app.state.http.aclose()
    await engine.dispose()


app = FastAPI(title=settings.APP_NAME, lifespan=lifespan)


def get_http(request: Request) -> httpx.AsyncClient:
    return request.app.state.http
  • @app.on_event("startup") застарів; новий спосіб — lifespan.
  • Створювати httpx.AsyncClient() у кожному запиті — антипатерн: щоразу новий TCP+TLS handshake і жодного переюзу з'єднань.
  • У проєкті engine створюється на рівні модуля (app/db/session.py). Це працює, але без engine.dispose() на shutdown з'єднання обриваються «на льоту» під час деплою.
  • Lifespan виконується у кожному воркері окремо. 4 воркери — це 4 пули БД.

class RequestIdMiddleware:
    def __init__(self, app: ASGIApp) -> None:
        self.app = app

    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        if scope["type"] != "http":
            return await self.app(scope, receive, send)
        request_id = uuid.uuid4().hex
        token = request_id_var.set(request_id)       # contextvar → потрапляє в усі логи запиту
        started = time.perf_counter()

        async def send_wrapper(message: Message) -> None:
            if message["type"] == "http.response.start":
                headers = MutableHeaders(scope=message)
                headers["X-Request-ID"] = request_id
                headers["Server-Timing"] = f"app;dur={(time.perf_counter() - started) * 1000:.1f}"
            await send(message)

        try:
            await self.app(scope, receive, send_wrapper)
        finally:
            request_id_var.reset(token)

09Streaming, SSE, WebSocket

Коли відповідь не вміщується в один JSON або має приходити поступово.

StreamingResponse: експорт CSV без завантаження всього в пам'ять
@router.get("/deliveries/export.csv")
async def export_csv(session: DbSession, user: CurrentUser) -> StreamingResponse:
    async def rows():
        yield "id,customer,address\n"
        stmt = select(Delivery).where(Delivery.organization_id == user.organization_id)
        result = await session.stream_scalars(stmt.execution_options(yield_per=500))
        async for d in result:                 # серверний курсор: по 500 рядків
            yield f"{d.id},{d.customer_name},{d.address}\n"

    return StreamingResponse(rows(), media_type="text/csv")
  • SSE (text/event-stream) — односпрямований потік від сервера: прогрес оптимізації маршрутів, токени LLM. Простіше за WebSocket, працює поверх звичайного HTTP і сам перепідключається в браузері (EventSource).
  • WebSocket (@router.websocket) — двосторонній канал: чат, live-трекінг водія. Залежності працюють, але HTTPException — ні; закривають через websocket.close(code=1008).
  • На кількох інстансах для розсилки подій потрібен спільний брокер (Redis Pub/Sub, туторіал 20).

12Продуктивність і деплой

Скільки воркерів, як рахувати з'єднання до БД і що профілювати першим.

12.1 Воркери

  • Один процес Uvicorn = один event loop = одне ядро для Python-коду (GIL). Щоб використати N ядер, запускають N процесів: uvicorn --workers N або gunicorn з uvicorn-воркерами.
  • Стартова формула для I/O-bound API: воркерів ≈ кількість ядер (не 2×CPU+1, як для sync WSGI, бо async-воркер і так тримає тисячі з'єднань).
  • У Kubernetes частіше 1 воркер на под і масштабування подами: простіше лімітувати пам'ять і бачити метрики (туторіал 27).
  • У проєкті: Fly shared-cpu-1x, 512 MB, один процес uvicorn app.main:app. Для такого розміру це правильно; масштабування — машинами Fly.

12.2 Арифметика з'єднань

🧮
Класична аварія
3 машини × 4 воркери × (pool_size 5 + max_overflow 10) = до 180 з'єднань, а в Postgres max_connections=100. Під піком нові запити отримують «too many connections». Рішення: зменшити пул, поставити PgBouncer, порахувати бюджет (туторіал 32, розділ 08).

12.3 Чек-лист швидкості

  1. Спочатку виміряй: p95/p99 latency по ендпоінтах, кількість SQL-запитів на запит (APM, Sentry, туторіал 26). Профайлер на живому процесі — py-spy.
  2. Найчастіший винуватець — база: N+1, відсутній індекс, OFFSET-пагінація, довгі транзакції.
  3. Далі — блокування event loop (розділ 2) і зовнішні API без таймаутів.
  4. Потім — серіалізація великих відповідей (розділ 4) і кешування (Redis, HTTP ETag/Cache-Control).
  5. uvicorn[standard] вже підтягує uvloop і httptools (так і є в проєкті).

13Структура великого проєкту

Як FastAPI-код не перетворюється на один main.py на 3000 рядків.

  • Шари: api/ (тонкі роутери) → services/ (бізнес-логіка) → repositories/ (SQL) → db/models. Схеми — окремо в schemas/ (туторіал 1).
  • Роутер на домен з APIRouter(tags=[...]), підключений з префіксом /api/v1/... — версіонування на рівні шляху.
  • Конфіг через pydantic-settings + @lru_cache get_settings(): один об'єкт на процес і легка підміна в тестах.
  • App factory create_app() (як у проєкті) — можна зібрати застосунок з іншими налаштуваннями для тестів.
  • Не тягнути FastAPI в сервіси: сервіс кидає доменний виняток, а не HTTPException — тоді його можна викликати з Celery-задачі чи CLI-скрипта (як app/scripts/set_user_role.py).

1420 питань співбесіди

Спочатку відповідай уголос, потім відкривай.

01Чим FastAPI відрізняється від Flask і Django REST Framework?

FastAPI — ASGI (async з коробки), валідація і документація генеруються з type hints через Pydantic, DI вбудований. Flask — WSGI, мінімалістичний, валідація і DI — сторонніми бібліотеками. DRF — частина Django: ORM, адмінка, серіалізатори, багато «батарейок», async обмежений. Вибір: FastAPI — API-сервіси і I/O-heavy; Django — продукт з адмінкою і великою кількістю CRUD.

02Що буде, якщо в async def ендпоінті викликати time.sleep(5)?

Event loop процесу зупиниться на 5 секунд: усі інші запити цього воркера чекають, навіть health-check. Рішення: await asyncio.sleep, async-бібліотека, def-ендпоінт або asyncio.to_thread.

03Чому def-ендпоінт не блокує сервер, а async def із блокуючим кодом — блокує?

FastAPI виконує def-ендпоінти в threadpool (anyio, 40 потоків), тож loop вільний. async def виконується прямо в loop: усе, що всередині не await, займає його повністю.

04Скільки разів виконається залежність, яку використовують три інші залежності в одному запиті?

Один раз: результат кешується на запит (use_cache=True). Між запитами кешу немає. Вимкнути можна через Depends(dep, use_cache=False).

05Як зробити, щоб усі записи в межах одного запиту були атомарні?

Сесія-на-запит у yield-залежності: commit після yield, rollback у except. Репозиторії не комітять самі, лише flush. Зовнішні виклики (HTTP, email) — після commit або через outbox, щоб не тримати транзакцію відкритою.

06Навіщо response_model, якщо є анотація повернення?

Анотація повернення в нових версіях і є response_model. Явний параметр потрібен, коли хендлер повертає інший тип (ORM-об'єкт, dict), а у відповіді має бути схема, або для опцій response_model_exclude_unset тощо. Головне — фільтрація полів (не злити hashed_password).

07Чим 422 відрізняється від 400, і як змінити формат помилок валідації?

422 — запит синтаксично коректний, але не проходить валідацію схеми; 400 — загальна «погана заявка» (часто бізнес-правило). Формат змінюють власним handler'ом на RequestValidationError, як у app/core/error_handlers.py.

08Де ініціалізувати пул БД або HTTP-клієнт?

У lifespan (або на рівні модуля, але тоді з закриттям на shutdown). Не в запиті. Пам'ятати, що lifespan виконується в кожному воркер-процесі окремо.

09BackgroundTasks vs Celery?

BackgroundTasks — у тому ж процесі після відповіді, без ретраїв і без гарантій при рестарті. Celery — окремі воркери, брокер, ретраї, розклад, моніторинг. Email-підтвердження — BackgroundTasks; оптимізація 500 точок — Celery.

10Чому BaseHTTPMiddleware вважають повільним і проблемним?

Він обгортає виклик у додаткові таски і стріми, що дає оверхед і історично проблеми зі streaming та contextvars. Для гарячого шляху пишуть чисте ASGI-middleware (__call__(scope, receive, send)).

11У якому порядку виконуються middleware?

Останній доданий через add_middleware — зовнішній: він першим бачить запит і останнім — відповідь.

12Як протестувати ендпоінт без справжньої БД та авторизації?

app.dependency_overrides[get_db] = ..., [get_current_user] = ...; потім TestClient або httpx.AsyncClient(transport=ASGITransport(app=app)). Не забути прибрати overrides після тесту.

13Скільки воркерів Uvicorn ставити і чому не 2×CPU+1?

Формула 2×CPU+1 — для sync-воркерів, які блокуються на I/O. Async-воркер обслуговує багато запитів одночасно, тож старт — ≈ кількість ядер, далі за метриками (CPU, latency, пам'ять). І порахувати з'єднання до БД: воркери × пул.

14Як віддати файл на 2 ГБ або CSV на мільйон рядків?

FileResponse для файлу з диска; StreamingResponse з async-генератором і серверним курсором (stream_scalars + yield_per) для даних з БД. Краще — згенерувати у фоні, покласти в S3 і віддати presigned URL.

15Чим Depends відрізняється від Security?

Security — це Depends з параметром scopes: OAuth2-скоупи потрапляють у SecurityScopes і в OpenAPI. Для простих ролей, як у проєкті, досить Depends.

16Як обмежити розмір завантажуваного файлу?

На рівні проксі (client_max_body_size у nginx, ліміти платформи) і в коді: читати UploadFile частинами й обривати після ліміту, перевіряти Content-Length. await file.read() без ліміту, як в імпорті доставок, тримає весь файл у пам'яті.

17Чому на кількох воркерах in-memory rate limiter не працює?

Кожен процес має свій лічильник: з 4 воркерами ліміт фактично ×4, а з кількома машинами — ще більше. Потрібне спільне сховище: атомарний INCR + TTL у Redis (туторіал 20).

18Як зробити ідемпотентний POST (повторна відправка форми / ретрай клієнта)?

Клієнт шле заголовок Idempotency-Key; сервер зберігає ключ з результатом (унікальний індекс у БД або Redis SET NX) і на повтор повертає той самий результат (туторіал 29, розділ C).

19Як версіонувати API?

Найпоширеніше — префікс шляху (/api/v1, як у проєкті) з окремими роутерами на версію; рідше — заголовок або media type. Головне — не ламати контракт у межах версії, deprecate через deprecated=True в OpenAPI.

20Що б ти покращив у FastAPI-частині цього проєкту?

(1) lifespan з engine.dispose() і спільним httpx.AsyncClient; (2) Unit of Work на запит замість commit у репозиторії; (3) пагінація на GET /deliveries; (4) Annotated-аліаси залежностей; (5) rate limiter у Redis для кількох машин; (6) request-id middleware і JSON-логи; (7) інтеграційні тести на Postgres поруч із SQLite.

API: 2 × 3 = 6 процесів × (5 + 10) = до 90. Celery (prefork): 2 × 4 = 8 процесів, у кожному свій engine: до 8 × 15 = 120. Разом до 210 при доступних 97 — під піком не вистачить. Рішення: pool_size=5, max_overflow=0 для API, NullPool або пул 1–2 у Celery, а при рості — PgBouncer у transaction mode (тоді statement_cache_size=0, як уже зроблено в app/db/session.py).
