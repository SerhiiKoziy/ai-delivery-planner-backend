00 Що таке VRP і чому це складно

Формулювання задачі — і чому "просто перебрати всі варіанти" не працює вже на середньому масштабі.

Vehicle Routing Problem (VRP) — задача: маючи депо, набір точок доставки й набір транспортних засобів з обмеженнями (вантажопідйомність, робочий час водія), побудувати маршрут для кожного авто так, щоб обслужити всі (чи максимум) точки з мінімальною сумарною вартістю (відстань, час), не порушивши жодного обмеження. У цьому проєкті це буквально те, що робить RouteOptimizerService.optimize() (app/services/route_optimizer/service.py) на кожен запит створення маршруту.

VRP — узагальнення ще старішої класичної задачі, Travelling Salesman Problem (TSP): "одна людина, одне депо, відвідати всі точки з мінімальним пройденим шляхом". VRP додає до TSP кілька транспортних засобів одразу й обмеження на кожен (місткість, час) — і від цього задача не просто складніша, а NP-складна (NP-hard): не існує відомого алгоритму, що знаходить точний оптимум за час, що поліноміально росте з кількістю точок. Кількість можливих способів розподілити N точок доставки між K машинами й впорядкувати кожен маршрут росте комбінаторно — вже для кількох десятків точок повний перебір фізично неможливий навіть на найпотужнішому залізі.

💡
Практичний наслідок NP-складності напряму видно в solver.py цього проєкту (розділ 7): розв'язок шукається не "до знаходження ідеалу", а з жорстким лімітом часу (time_limit.FromSeconds(5)) — і це не недолік реалізації, а єдиний реалістичний спосіб узагалі мати відповідь для NP-складної задачі за прийнятний для HTTP-запиту час.

01 Від TSP до VRP: граф, вузли, дуги

Той самий словник термінів, яким OR-Tools описує задачу всередині.

Задачу подають як граф: вузли (nodes) — депо й точки доставки; дуги (arcs) — можливі переїзди між будь-якою парою вузлів, кожна з вагою (вартістю) — зазвичай відстань чи час у дорозі. Маршрут одного транспортного засобу — це шлях по цьому графу, що починається й закінчується в депо (вузол 0), проходячи підмножину точок доставки рівно по одному разу.

OR-Tools матеріалізує цю модель через два ключові об'єкти — RoutingIndexManager (переклад "індексів солвера" в "номери вузлів" і назад — технічна деталь, потрібна, бо солвер внутрішньо оперує не самими номерами вузлів, а власним індексуванням, зручним для декількох транспортних засобів одразу) і RoutingModel (сама модель задачі: вартість дуг, обмеження, виміри) — обидва видно вже в розділі 4 на реальному коді solver.py.

02 RoutingProblem: як домен перетворюється на вхід солвера

OR-Tools нічого не знає про Delivery/Vehicle/Driver — builder.py перекладає доменні сутності на мову солвера.

app/services/route_optimizer/builder.py
stops.append(
    Stop(
        id=str(delivery.id),
        latitude=delivery.latitude,
        longitude=delivery.longitude,
        demand_weight_grams=round(delivery.weight_kg * 1000),
        demand_volume_ml=round(delivery.volume_m3 * 1_000_000),
        service_minutes=delivery.unloading_minutes,
        time_window=time_window,
        late_penalty=LATE_PENALTY_BY_PRIORITY[priority_key],
        drop_penalty=DROP_PENALTY_BY_PRIORITY[priority_key],
    )
)

Кілька деталей тут невипадкові:

  • Все — цілі числа. Вага в грамах, об'єм у мілілітрах (а не кілограми/кубометри з плаваючою комою) — OR-Tools внутрішньо працює з цілочисельною арифметикою для вимірів (розділ 5); переведення на менші одиниці — спосіб зберегти потрібну точність без чисел із плаваючою комою там, де солвер їх не приймає.
  • Штрафи прив'язані до бізнес-пріоритету ще на етапі побудови (LATE_PENALTY_BY_PRIORITY, DROP_PENALTY_BY_PRIORITY — models.py), а не десь глибоко в солвері — бізнес-правило "VIP-клієнта відкидати найостаннішим" виражене одразу як число, зрозуміле оптимізатору.
✅
Значення штрафів у models.py навмисно розділені на два порядки величини: DROP_PENALTY_BY_PRIORITY (мільйони) завжди набагато більший за будь-який LATE_PENALTY_BY_PRIORITY (сотні-тисячі) — навіть LATE_PENALTY для VIP (10 000) на порядки менший за DROP_PENALTY для найнижчого пріоритету (1 000 000). Це гарантує бізнес- правило текстом коментаря в самому файлі: "ніколи не викидай зупинку лише щоб уникнути невеликого штрафу за запізнення" — розставлені як завгодно пріоритети однаково поважають це правило, бо порядки величин не перетинаються.

03 Матриця відстаней: чесне MVP-спрощення

Солверу потрібна вартість переїзду між кожною парою вузлів — звідки вона береться сьогодні.

app/services/route_optimizer/distance.py
"""MVP simplification: real turn-by-road distance and live traffic would come
from the Google Distance Matrix API. This module estimates both from
great-circle distance and an assumed average urban delivery speed..."""

EARTH_RADIUS_KM = 6371.0
AVERAGE_SPEED_KMH = 30.0

def haversine_km(lat1, lng1, lat2, lng2) -> float:
    # формула great-circle відстані по сфері (напряму, без урахування доріг)
    ...

Матриця — квадратна NxN (N = депо + всі точки), симетрична (відстань A→B дорівнює B→A — справедливо для формули з прямої лінії, але вже не завжди справедливо для реальних доріг з одностороннім рухом) і цілочисельна — вимога самого OR-Tools для callback-ів транзитної вартості. Сьогодні відстань — це haversine (відстань по великому колу, "по прямій" між двома точками на сфері Землі), а не реальна відстань по дорогах, і час у дорозі — грубе припущення (30 км/год середньої міської швидкості), а не дані з реального трафіку.

⚠️
Це свідоме, задокументоване прямо в коді MVP-спрощення — не недогляд. Модуль спроєктований так, щоб замінити цю реалізацію на виклик платного Google Distance Matrix API можна було, торкнувшись лише build_distance_duration_matrix: викликачі (builder.py, solver.py) не знають і не повинні знати, звідки саме взялась матриця, — інверсія залежностей у дії (туторіал 16).

04 Модель OR-Tools: manager, routing, callbacks

Три об'єкти, довкола яких побудований увесь solver.py.

app/services/route_optimizer/solver.py — build_model()
self.manager = pywrapcp.RoutingIndexManager(num_nodes, num_vehicles, 0)
self.routing = pywrapcp.RoutingModel(self.manager)

def distance_callback(from_index, to_index):
    from_node = self.manager.IndexToNode(from_index)
    to_node = self.manager.IndexToNode(to_index)
    if not problem.return_to_depot and to_node == 0:
        return 0
    return self.distance_matrix[from_node][to_node]

distance_callback_index = self.routing.RegisterTransitCallback(distance_callback)
self.routing.SetArcCostEvaluatorOfAllVehicles(distance_callback_index)
  • RoutingIndexManager(num_nodes, num_vehicles, depot=0) — перекладач між "внутрішнім індексом" солвера (кожне авто внутрішньо має власну нумерацію вузлів для свого маршруту) і реальним номером вузла (0 — депо, 1..N — точки). IndexToNode/NodeToIndex — методи саме цього перекладу, вони зустрічаються в кожному callback-у.
  • RoutingModel — сама модель: сюди реєструють функції вартості (callbacks) і обмеження (виміри, розділ 5).
  • Transit callback — функція "вартість переїзду з вузла A у вузол B", яку солвер викликає мільйони разів під час пошуку. RegisterTransitCallback реєструє її під індексом, який потім передається в SetArcCostEvaluatorOfAllVehicles — "мінімізуй суму цих значень по всьому маршруту".

Реальна деталь бізнес-логіки прямо всередині distance_callback: якщо return_to_depot=False (водій не повертається в депо після останньої доставки — реальна опція цього продукту), "переїзд" у вузол депо коштує нуль — бо такого переїзду фізично не буде, і його не можна ні мінімізувати, ні враховувати в сумарну відстань маршруту.

05 Виміри (Dimensions): Time і Capacity

Вимір OR-Tools — накопичувана величина вздовж маршруту (час у дорозі, вага вантажу), а не одноразова вартість дуги.

На відміну від вартості дуги (одне число на переїзд, що просто підсумовується для мети "мінімізувати"), вимір накопичує значення вздовж усього маршруту й дозволяє ставити обмеження на цю накопичену суму в кожній точці шляху — а не лише на фінальний підсумок.

solver.py — вимір "Time"
self.routing.AddDimension(
    time_callback_index,
    HORIZON_MINUTES,  # slack_max — дозволити "чекати" на вікно доставки хоч цілу добу
    HORIZON_MINUTES,  # максимальне накопичене значення
    False,            # НЕ форсувати старт у 0 — авто стартують у свій робочий час
    "Time",
)

Capacity — другий вимір, і показово, що в цьому проєкті їх одразу два незалежні: вага й об'єм (constraints.py, apply_capacity_constraints). Вантаж може вичерпати місткість авто по вазі, не вичерпавши по об'єму, чи навпаки (легкі, але громіздкі коробки) — тому це дві окремі функції-калькулятори попиту, зареєстровані як два незалежні виміри, кожен зі своєю межею на транспортний засіб (AddDimensionWithVehicleCapacity).

Working hours (apply_working_hours_constraints) використовує той самий вимір "Time", тільки прив'язує його межі до старту й кінця маршруту конкретного авто (routing.Start(vehicle_id)/routing.End(vehicle_id)): старт не раніше початку зміни водія, кінець не пізніше її завершення, і додатково — "жорстке" обмеження солвера (routing.solver().Add(...)) на те, що різниця між ними не перевищує max_working_minutes.

06 М'які вікна доставки, штрафи, "дропи"

Найцікавіша бізнес-вимога цього солвера: "якщо приїхав раніше — чекає, якщо запізнився — штраф, а не провал".

constraints.py — apply_time_window_constraints
time_dimension.CumulVar(index).SetRange(stop.time_window.start_minutes, HORIZON_MINUTES)
time_dimension.SetCumulVarSoftUpperBound(index, stop.time_window.end_minutes, stop.late_penalty)

SetRange(start, HORIZON_MINUTES) — жорстка нижня межа: приїхати раніше початку вікна фізично неможливо для солвера (авто просто чекатиме, "з'їдаючи" слек виміру Time). А верхня межа — навпаки, м'яка (SetCumulVarSoftUpperBound): запізнення не робить розв'язок недопустимим, воно лише додає late_penalty (масштабований пріоритетом — розділ 2) до загальної вартості. Це прямо відповідає бізнес-специфікації, зафіксованій коментарем у самому коді: "якщо приїхав раніше — чекає, якщо запізнився — отримує штраф".

Дроп замість провалу (AddDisjunction). Ще один рівень тієї самої ідеї "краще неідеальний розв'язок, ніж жоден": якщо фізично неможливо об'їхати всі точки (забагато замовлень на наявні авто чи час), солвер може повністю пропустити точку ціною drop_penalty — теж масштабованого пріоритетом (розділ 2) — замість того щоб optimize() взагалі кинув виняток "рішення не знайдено". mapper.py окремо збирає такі пропущені точки в unassigned_stop_ids, які сервіс повертає викликачу як явний список, а не мовчки губить.

📎
Best-effort обмеження перерви водія. apply_break_constraints — найтендітніша частина API OR-Tools у цьому коді, обгорнута в try/except в solver.py: якщо жорстке планування перерви через FixedDurationIntervalVar не вдається, помилка логується, а решта солвера продовжує працювати без цього обмеження — усвідомлена деградація, а не крах усього ендпоінту через одну примхливу частину API.

07 Евристика, а не точний оптимум

Прямий наслідок NP-складності (розділ 0): OR-Tools у цьому проєкті свідомо шукає "достатньо добре", а не "найкраще з можливих".

solver.py — solve()
search_parameters.first_solution_strategy = (
    routing_enums_pb2.FirstSolutionStrategy.PATH_CHEAPEST_ARC
)
search_parameters.local_search_metaheuristic = (
    routing_enums_pb2.LocalSearchMetaheuristic.GUIDED_LOCAL_SEARCH
)
search_parameters.time_limit.FromSeconds(5)

Два окремі етапи пошуку, кожен зі своєю роллю:

  • PATH_CHEAPEST_ARC (стратегія першого розв'язку) — жадібна (greedy) евристика: будувати маршрут, на кожному кроці додаючи найдешевшу доступну дугу. Швидко дає хоч якийсь допустимий розв'язок — часто далекий від оптимального, зате майже миттєво.
  • GUIDED_LOCAL_SEARCH (метаевристика покращення) — бере цей перший розв'язок і далі ітеративно покращує його локальними змінами (переставити дві точки, перенести точку в інший маршрут), "штрафуючи" вже досліджені дороги дуги, щоб не застрягати в одному й тому самому локальному мінімумі повторно.
  • time_limit.FromSeconds(5) — жорсткий бюджет часу: що б не знайшла метаевристика за ці 5 секунд, це і повертається як фінальний assignment. Довше — потенційно краще (для NP-складної задачі гарантії "коли зупинитись і мати вже найкраще" не існує), але 5 секунд — свідомий компроміс між якістю маршруту й часом відповіді HTTP-запиту.
⚠️
Ключовий висновок для співбесіди: результат optimize() — це допустимий і добрий розв'язок, а не доведено найкращий можливий. Два послідовні виклики з тими самими вхідними даними теоретично можуть повернути дещо різні (хоч і однаково допустимі) маршрути, якщо локальний пошук встигає дослідити різну кількість варіантів у межах тих самих 5 секунд — детермінізм тут не гарантований так, як для звичайного SQL-запиту.

08 Солвер і event loop: чому asyncio.to_thread

Пряме продовження вже розібраного в іншому турі — тут лише зв'язок із конкретним кодом цього модуля.

service.py
def _build_and_solve(solver: RouteSolver):
    solver.build_model()
    return solver.solve()

result = await asyncio.to_thread(_build_and_solve, solver)

build_model() і solve() — синхронний, CPU-зв'язаний код (сам OR-Tools написаний на C++ і викликається через Python-обгортку, що утримує контроль виконання на весь час пошуку) — без жодного await усередині. Якби його викликали напряму з async def optimize(...), до 5 секунд роботи солвера заблокували б увесь event loop процесу — жоден інший одночасний HTTP- запит не обробився б за цей час, навіть найпростіший. asyncio.to_thread виносить увесь виклик в окремий потік, звільняючи event loop для решти застосунку — це той самий фікс, що детально розібраний у турі 2, розділ 6 і в самому першому запиті цієї серії туторіалів.

09 Аналоги OR-Tools

OR-Tools — не єдиний спосіб розв'язувати VRP, і питання "чому саме він" цілком типове.

ІнструментКлючова відмінність
Google OR-Tools (використано тут) Безкоштовний, open-source, C++ із біндингами для Python/Java/C#. Constraint Programming рушій загального призначення — VRP тут лише одна з підтримуваних категорій задач (є ще bin packing, scheduling).
Gurobi / CPLEX Комерційні MILP-солвери (Mixed-Integer Linear Programming) промислового рівня — зазвичай точніші й швидші на дуже великих задачах, але платні (ліцензії коштують тисячі доларів на рік) — типовий вибір великих логістичних компаній, а не для MVP.
VROOM Open-source, написаний спеціально й лише для VRP (на відміну від OR-Tools загального призначення) — легший інтеграційний поріг для чистого VRP без потреби в інших видах CP-задач.
jsprit Java-бібліотека, теж спеціалізована на VRP, з метаевристиками на кшталт large neighborhood search — природний вибір, якщо стек команди — JVM, а не Python/C++.
Власна евристика "з нуля" (naive nearest-neighbor, генетичний алгоритм) Найдешевше почати, найдорожче підтримувати: правильно врахувати одразу вікна часу, кілька вимірів місткості й м'які штрафи — саме та складність, яку OR-Tools уже вирішив і перевірив за вас.

Практичне правило вибору: OR-Tools — розумний баланс "безкоштовно, достатньо потужно, з готовою підтримкою складних обмежень (вікна часу, кілька вимірів місткості, м'які штрафи)" — саме тому він і обраний тут замість написання власного евристичного алгоритму або платного MILP-солвера.

10 Питання для співбесіди

Прив'язані до реального коду цього модуля — не загальні визначення з підручника.

01Чому VRP вважається NP-складною задачею, і що це означає практично для дизайну солвера?

Кількість способів розподілити N точок між K машинами й упорядкувати кожен маршрут росте комбінаторно з N — не існує відомого алгоритму, що гарантовано знаходить точний оптимум за поліноміальний час. Практично це означає: для реалістичної кількості точок доведеться або обмежити час пошуку й погодитись на "достатньо добрий" розв'язок (підхід цього проєкту — time_limit.FromSeconds(5)), або мати справу з нереалістично довгим часом очікування точного оптимуму.

02У чому різниця між вартістю дуги (arc cost) і виміром (dimension) в OR-Tools?

Вартість дуги — одне число на кожен переїзд, що просто підсумовується в загальну мету "мінімізувати". Вимір — накопичувана вздовж усього маршруту величина (час, вага), на яку можна ставити обмеження в кожній точці шляху, а не лише на фінальну суму — саме через вимір "Time" у цьому проєкті реалізовані і вікна доставки, і робочий час водія одночасно.

03Чим м'яке обмеження відрізняється від жорсткого — і де в цьому коді використано обидва для того самого вікна доставки?

Жорстке обмеження робить розв'язок, що його порушує, недопустимим узагалі. М'яке — дозволяє порушення ціною штрафу до загальної вартості. У apply_time_window_constraints нижня межа вікна доставки жорстка (SetRange — приїхати раніше фізично неможливо для солвера), а верхня — м'яка (SetCumulVarSoftUpperBound — запізнення коштує late_penalty, але не ламає розв'язок).

04Що робить AddDisjunction, і навіщо він потрібен, якщо в системі вже є м'які вікна часу?

Дозволяє солверу повністю пропустити (не відвідати) конкретну точку ціною drop_penalty, замість того щоб узагалі не знайти жодного допустимого розв'язку. М'які вікна часу рятують від конфлікту "затримка проти дедлайну", але не рятують, коли фізично бракує сумарної місткості чи часу на всіх водіїв обслужити всіх — у такому разі саме дроп точки, а не провал усього запиту, дозволяє повернути хоч якийсь корисний результат.

05Чому DROP_PENALTY_BY_PRIORITY і LATE_PENALTY_BY_PRIORITY навмисно розділені на різні порядки величини?

Щоб бізнес-правило "ніколи не викидай точку лише заради невеликого штрафу за запізнення" виконувалось автоматично, для будь-якого пріоритету: навіть найбільший можливий late_penalty (VIP, 10 000) на порядки менший за найменший можливий drop_penalty (low, 1 000 000) — тому оптимізатор завжди обере "запізнитись", а не "пропустити", коли обидва варіанти технічно можливі.

06Чому солвер запускається через asyncio.to_thread, а не напряму з async-функції?

OR-Tools — синхронний, CPU-зв'язаний код (C++ під Python-обгорткою) без жодного await усередині; виклик напряму заблокував би event loop на весь час пошуку (до 5 секунд), зупинивши обробку будь-яких інших одночасних запитів процесу. asyncio.to_thread виносить виклик в окремий потік, звільняючи event loop.

07Чи гарантує цей солвер один і той самий маршрут для одних і тих самих вхідних даних при повторному запуску?

Не обов'язково точно однаковий — детермінізм тут не гарантований так, як для SQL-запиту. Локальний пошук (GUIDED_LOCAL_SEARCH) — ітеративний процес, обмежений часом (5 секунд); те, скільки варіантів він встигне дослідити й у якому порядку, теоретично може відрізнятись між запусками, тож результат — допустимий і добрий, але не обов'язково побітово ідентичний.

08Матриця відстаней сьогодні рахується через haversine, а не реальні дороги. У чому конкретно це може призвести до неоптимального (чи навіть нереалістичного) маршруту?

Haversine — відстань "по прямій" по сфері, що ігнорує річки, будівлі, одностороній рух, реальну дорожню мережу й трафік. Дві точки, дуже близькі по прямій, можуть насправді вимагати великого об їзду по дорогах (наприклад, через річку без мосту поруч) — солвер вважатиме їх дешевими для послідовного відвідування, хоча реальний водій витратить значно більше часу й палива, ніж передбачено моделлю.

09Чому вага і об'єм реалізовані як два окремі виміри місткості, а не один комбінований показник?

Бо вантаж може вичерпати місткість авто по одному показнику, не вичерпавши по іншому — важкі, компактні коробки вичерпують вагу раніше об'єму; легкі, громіздкі — навпаки. Об'єднання в один показник ("умовна одиниця") втратило б цю незалежність і могло б або занизити реальне обмеження (перевантажити авто по вазі), або завищити (недовантажити по об'єму), тоді як два незалежні виміри перевіряють обидва фізичні обмеження одночасно й точно.

11 Підсумок

Головне з цього туторіалу:

  • VRP — NP-складне узагальнення TSP на кілька транспортних засобів з обмеженнями; точний оптимум за прийнятний час у загальному випадку недосяжний.
  • builder.py перекладає домен (Delivery/Vehicle/Driver) у нейтральний RoutingProblem із цілочисельними одиницями й бізнес-штрафами, вираженими як числа.
  • manager/routing/callbacks — базова тріада OR-Tools; виміри (Time, Capacity) — накопичувані обмеження вздовж усього маршруту, на відміну від одноразової вартості дуги.
  • М'які вікна часу й AddDisjunction-дропи втілюють правило "краще неідеальний розв'язок, ніж жоден" — прямо як бізнес-специфікація вимагає.
  • Розв'язок шукається евристично (PATH_CHEAPEST_ARC → GUIDED_LOCAL_SEARCH) з жорстким лімітом часу — свідомий компроміс якості проти швидкості відповіді, не помилка й не недбалість.
  • Синхронний, CPU-зв'язаний виклик солвера завжди офлоаджиться через asyncio.to_thread, щоб не заморожувати event loop на час пошуку.
