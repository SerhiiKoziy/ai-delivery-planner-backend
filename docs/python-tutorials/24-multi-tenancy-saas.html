00 Три моделі multi-tenancy

Перше архітектурне рішення будь-якого SaaS: як фізично розділити дані різних клієнтів (тенантів) в одній системі.

МодельЯк влаштованаКомпроміс
Shared DB, shared schema, discriminator column (обрано тут) Одна база, одні таблиці для всіх тенантів; кожен рядок має колонку organization_id, яка каже, кому він належить. Найдешевше в експлуатації (одна база, один набір міграцій, прості агреговані звіти across-tenant для власного адміна) — але вся ізоляція тримається на дисципліні коду: забутий WHERE organization_id = ... в одному запиті — і стався витік даних.
Shared DB, schema-per-tenant Одна база сервера, але кожен тенант має власну PostgreSQL-схему (tenant_42.deliveries замість спільної deliveries з колонкою). Ізоляція надійніша (сплутати схеми складніше, ніж забути один WHERE), можна навіть бекапити/відновлювати одного тенанта окремо — але сотні/тисячі схем ускладнюють міграції (прогнати одну міграцію треба на кожну схему окремо) і сам connection-pooling.
Database-per-tenant Кожен тенант — фізично окрема база даних (можливо, навіть на окремому сервері). Найсильніша ізоляція з усіх — і найдорожча: власний connection pool, власні бекапи й моніторинг на кожного тенанта; агрегована аналітика across tenants стає окремою (часто ETL) задачею, а не одним SQL-запитом.

Проєкт свідомо обрав перший варіант — той, що дешевший в експлуатації, але вимагає найбільшої дисципліни коду. Саме тому TenantScopedRepository (туторіал 1) — не просто зручність, а компенсація цього архітектурного компромісу: якщо ізоляція не гарантована самою структурою бази (як у двох інших моделях), її треба гарантувати структурою коду так, щоб про неї було фізично неможливо забути в конкретному місці виклику.

01 TenantScopedRepository зсередини

Тур 1 показав get(). Тут — решта методів, і чому кожен із них теж має значення.

app/repositories/base.py
class TenantScopedRepository(BaseRepository[ModelType]):
    def __init__(self, session, model, organization_id) -> None:
        super().__init__(session, model)
        self.organization_id = organization_id      # прив'язано ОДИН раз, при створенні

    async def get_many(self, ids) -> list[ModelType]:
        # "Ids belonging to another organization are silently absent from the
        # result — indistinguishable from ids that don't exist at all."
        stmt = select(self.model).where(
            self.model.id.in_(ids), self.model.organization_id == self.organization_id
        )
        ...

    async def create(self, **kwargs) -> ModelType:
        kwargs.pop("organization_id", None)     # не дати переданому kwarg переписати org
        return await super().create(organization_id=self.organization_id, **kwargs)

    async def update(self, id, **kwargs) -> ModelType | None:
        kwargs.pop("organization_id", None)     # не дати "перепривласнити" рядок іншому org
        return await super().update(id, **kwargs)

Три окремі гарантії, кожна закриває свій сценарій атаки чи бага:

  • get_many явно документує (коментарем у коді) свою поведінку: чужі id не викидають помилку — вони просто відсутні в результаті, невідмінно від id, яких не існує взагалі. Викликач не має способу дізнатись різницю "не існує" vs "чуже" — і це навмисно (розділ 2).
  • create ігнорує будь-яке значення organization_id, передане ззовні через **kwargs, і завжди підставляє self.organization_id — навіть якщо хтось (по помилці чи зловмисно) передасть інший org id у payload, новий рядок все одно прив'яжеться до організації, з якою репозиторій був створений.
  • update так само не дає жодному виклику "переприписати" вже наявний рядок в іншу організацію, прибираючи organization_id з kwargs ще до виклику базового методу.
Аналогія з фронтендом
Схоже на axios-інстанс, у якого baseURL і токен авторизації зафіксовані один раз при створенні — і жоден виклик .get() чи .post() потім не може випадково "переслати" запит на інший домен чи з іншим токеном, бо ці два поля просто недоступні для перезапису з місця виклику.

02 IDOR і другий рівень захисту — обмеження зовнішнього ключа

Тур 2 вже пояснив 404-замість-403 для читання. Тут — що відбувається на запис, коли чужий id підставляють не в URL, а в тіло запиту.

TenantScopedRepository захищає читання й прямі мутації "свого" ресурсу за його власним id. Але є інший вектор: що, якщо організація А спробує прив'язати свій ресурс до чужого id — наприклад, створити авто (Vehicle) з driver_id, що насправді належить організації Б?

app/tests/test_multi_tenancy.py
def test_vehicle_cannot_link_to_foreign_driver(client, other_org_driver) -> None:
    response = client.post(
        "/api/v1/vehicles/",
        json={"plate_number": "DD4444DD", ..., "driver_id": str(other_org_driver.id)},
    )
    assert response.status_code == 422

Це не збіг — це другий, незалежний рівень захисту поверх TenantScopedRepository. Валідація на рівні сервісу (не показана тут — див. туторіал 21 для механіки самої валідації) перевіряє існування driver_id саме в межах org-scoped репозиторія водіїв: чужий driver_id для цього репозиторію не існує взагалі (та сама поведінка get_many з розділу 1) — тому запит на створення авто з ним провалюється як "невалідні дані" (422), а не як спроба щось прочитати. Той самий патерн повторюється й для PUT-оновлення наявного авто (test_vehicle_update_cannot_link_to_foreign_driver).

✅
Це ілюструє важливий загальний принцип: ізоляція тенантів — не одна перевірка в одному місці, а властивість, яку треба тримати на кожній межі, де зовнішній ідентифікатор потрапляє в систему — і при читанні за id, і при посиланні на інший ресурс через зовнішній ключ у payload. Одного централізованого фільтра (наприклад, лише в middleware) було б недостатньо для другого сценарію.

03 Реальні тести ізоляції

test_multi_tenancy.py — не одиничний smoke-тест, а систематичний прохід по кожному класу можливого витоку.

Файл побудований навколо фікстур other_org_* — дані, навмисно засіяні в репозиторії, прив'язані до іншої організації, ніж та, від імені якої діє тестовий HTTP-клієнт. Категорії перевірок:

  • Список і читання за id. Список ніколи не містить чужого id; пряме звернення GET /deliveries/{чужий_id} повертає 404 — не порожній об'єкт, не 403, саме "не знайдено".
  • Оновлення й видалення. PUT/DELETE на чужий ресурс — теж 404, і, найважливіше, тест окремо перевіряє, що чужий рядок дійсно лишився незміненим у базі після спроби (test_update_and_delete_are_org_scoped) — тобто не просто "клієнт отримав помилку", а "сервер фізично нічого не торкнувся".
  • Крос-org id всередині складнішого запиту. Найцікавіший випадок — test_optimize_silently_drops_cross_org_delivery: якщо в POST /routes/optimize підставити чужий delivery_id у список доставок, солвер (туторіал 23) просто не побачить цю доставку — вона не потрапляє ні в маршрути, ні в unassigned_deliveries, ні навіть у skipped_not_geocoded. Поводиться так, ніби id ніколи не існував — це прямий наслідок того, що DeliveryRepository.get_many (org-scoped) мовчки виключає чужі id ще на етапі завантаження вхідних даних для солвера, задовго до того як OR-Tools взагалі побачить задачу.
  • Агрегати dashboard. test_dashboard_overview_is_per_organization перевіряє, що зведена статистика (кількість активних водіїв, пройдена відстань) теж рахується виключно по своїй організації — легко забутий випадок, бо агрегатні запити (COUNT, SUM) на перший погляд не "про конкретний ресурс", і про WHERE organization_id в них забути найлегше.
  • Наскрізний тест із реальними JWT. test_real_registration_isolates_orgs не використовує тестові фікстури взагалі — реєструє двох реальних користувачів через справжній POST /auth/register, підтверджує обидва email, і перевіряє ізоляцію через справжні токени двох різних сесій. Це страховка на випадок, якщо якийсь із проміжних шарів (JWT → get_current_user → organization_id) працює інакше в реальному потоці, ніж у тестових фікстурах, що напряму створюють об'єкти в базі.

04 Ретроактивна міграція на живі дані

Multi-tenancy в цьому проєкті додали не з нуля — колонку organization_id ввели в базу, що вже мала дані без явного власника. Реальний файл міграції, а не навчальний приклад.

…_add_organization_id_multi_tenancy.py
# 1. Додати колонку NULLABLE спочатку — наявні рядки ще не мають значення.
op.add_column("users", sa.Column("organization_id", sa.Uuid(), nullable=True))

# 2. Backfill: кожному наявному users — власна нова Organization.
# П'ять таблиць ресурсів (deliveries, depots, drivers, vehicles, routes)
# не мають колонки "власник" узагалі — усі їхні наявні рядки переносяться
# в одну спільну organization "Legacy Data" з фіксованим id.
for user_id, email in existing_users:
    org_id = uuid.uuid4()
    # INSERT organization, потім UPDATE users SET organization_id = ...

# 3. Тепер, коли КОЖЕН рядок має значення — увімкнути NOT NULL + FK.
op.alter_column("users", "organization_id", nullable=False)
op.create_foreign_key("fk_users_organization_id", "users", "organizations", ...)

Тристадійний паттерн тут — не випадковість, а єдиний безпечний спосіб додати обов'язкову (NOT NULL) колонку з посиланням на непорожню таблицю:

  1. Спочатку nullable. ALTER TABLE ... ADD COLUMN ... NOT NULL без дефолту на таблиці з наявними рядками одразу провалиться — Postgres не знає, чим заповнити вже наявні рядки.
  2. Backfill окремим кроком. Для users — по одній новій Organization на кожного наявного користувача (зберігаючи правило "один користувач = одна організація", яке з цього моменту діє і для нових реєстрацій). Для ресурсних таблиць, де немає жодної колонки "хто створив" — чесний компроміс: усі старі рядки об'єднуються в одну спільну LEGACY_ORG_ID-організацію, бо атрибутувати їх конкретному користувачу вже неможливо.
  3. Лише тепер — NOT NULL і зовнішній ключ. Коли кожен рядок вже гарантовано має значення, обмеження можна ввімкнути безпечно.
⚠️
Чому downgrade() не видаляє backfilled-організації: коментар у самому файлі пояснює свідомий вибір — видалити колонку легко, але видалити саме ті Organization-рядки, які створив цей backfill (а не ті, що реальні користувачі встигли створити з моменту апгрейду), вже неможливо надійно розрізнити. Автори міграції обрали залишити "осиротілі" рядки як безпечніший результат, ніж ризик видалити щось реальне.

05 Квоти на рівні organization

Коротко — щоб не дублювати вже розібране в турі 2: organization_id це не лише межа видимості даних, а й межа білінгу.

Та сама колонка-дискримінатор, що ізолює дані тенантів одна від одної, природно стає й одиницею обліку споживання — ліміт маршрутів на trial-плані, ліміт викликів геокодування й AI на організацію. Атомарна перевірка-і-запис квоти одним SQL UPDATE ... WHERE (проти TOCTOU race condition) уже детально розібрана в турі 2, розділ 6 — тут важливо лише підкреслити зв'язок: без надійної ізоляції по organization_id (розділи 1-3) сам облік квоти по organization був би безглуздим — організація А могла б випадково чи навмисно "спожити" ліміт, приписаний організації Б.

06 Питання для співбесіди

Прив'язані до реального коду й тестів цього проєкту.

01Які є три основні архітектурні моделі multi-tenancy, і чому ця система обрала найдешевшу з них?

Shared DB + shared schema з колонкою-дискримінатором, shared DB + schema-per-tenant, і database-per-tenant — зростання ізоляції й вартості експлуатації в цьому порядку. Проєкт обрав перший варіант заради простоти операцій (одна база, одні міграції), компенсуючи слабшу структурну ізоляцію дисципліною коду — TenantScopedRepository, що робить забуту фільтрацію фізично неможливою.

02Чому get_many у TenantScopedRepository не кидає помилку для чужого id, а просто виключає його з результату?

Щоб зробити "не існує" й "належить іншій організації" невідмінними одне від одного для викликача — той самий принцип, що й 404 замість 403 при прямому читанні: жодна відповідь системи не повинна підтверджувати зловмиснику сам факт існування чужого ресурса.

03Що станеться, якщо організація спробує створити Vehicle з driver_id, що належить іншій організації — і чому це не той самий механізм захисту, що для прямого читання за id?

Запит провалюється з 422 (невалідні дані), бо org-scoped репозиторій водіїв для цієї організації просто не бачить чужий driver_id — та сама поведінка get_many, але застосована на етапі валідації зовнішнього ключа в payload, а не на етапі прямого доступу за URL-параметром. Це другий, незалежний рівень захисту: ізоляцію треба тримати на кожній межі, де зовнішній ідентифікатор потрапляє в систему, а не лише в одному централізованому місці.

04У тестовому наборі є і фікстурні тести, і один тест із реальними JWT-сесіями двох зареєстрованих користувачів. Навіщо потрібен саме останній, якщо фікстурні тести вже перевіряють ізоляцію?

Фікстурні тести засівають дані напряму через репозиторії, минаючи HTTP і весь ланцюжок автентифікації — вони перевіряють ізоляцію на рівні репозиторія/ендпоінта, але не гарантують, що весь шлях JWT → get_current_user → organization_id насправді працює однаково в реальному потоці запиту. Наскрізний тест із двома реальними зареєстрованими користувачами закриває саме цей розрив — перевіряє інтеграцію всіх шарів разом, а не кожен окремо.

05Чому колонку organization_id при retroактивній міграції спочатку додають як nullable, а обмеження NOT NULL і зовнішній ключ вмикають лише третім кроком?

Бо додати обов'язкову колонку без дефолту на таблиці, що вже має рядки, неможливо — база не знає, чим заповнити наявні рядки. Правильна послідовність: додати nullable-колонку → backfill-ити значення для кожного наявного рядка окремим кроком → лише тоді, коли кожен рядок гарантовано має значення, увімкнути NOT NULL і зовнішній ключ.

06П'ять ресурсних таблиць (deliveries, depots, drivers, vehicles, routes) не мали колонки "власник" до цієї міграції. Як вирішили, кому передати їхні наявні рядки — і чому саме так?

Усі наявні рядки цих таблиць перенесли в одну спільну організацію з фіксованим id ("Legacy Data"), а не намагались вгадати чи реконструювати справжнього власника — атрибутувати їх конкретному користувачу було вже неможливо, і чесний, безпечний компроміс — явно позначити ці дані як "успадковані", а не вигадувати неправдиву прив'язку.

07 Підсумок

Головне з цього туторіалу:

  • Три моделі multi-tenancy — shared schema+discriminator (тут), schema-per-tenant, database-per-tenant — компроміс між вартістю експлуатації й силою структурної ізоляції.
  • TenantScopedRepository компенсує слабшу структурну ізоляцію дисципліною коду: organization_id прив'язаний один раз при створенні репозиторія й недоступний для перезапису через жоден виклик.
  • Ізоляція тенантів — властивість кожної межі, де приходить зовнішній ідентифікатор: і прямого читання за id (404), і посилання через зовнішній ключ у payload (422), і агрегатних запитів (dashboard).
  • Реальний тестовий набір систематично покриває всі ці межі, включно з наскрізним тестом на справжніх JWT-сесіях двох користувачів.
  • Multi-tenancy можна ввести ретроактивно на живі дані за безпечний трикроковий паттерн: nullable-колонка → backfill → NOT NULL + FK.
