00 Загальна ідея

Перш ніж дивитись на файли — головна відмінність мислення бекенд- і фронтенд-розробника.

Аналогія з фронтендом
У фронтенді ви звикли ділити код на компоненти (UI), стор/хуки (стан і логіка), API-клієнт (запити). Бекенд ділиться дуже схоже, тільки замість UI — HTTP-шар, замість стора — сервіси (бізнес-логіка), а замість API-клієнта — репозиторії, які "розмовляють" із базою даних замість зовнішнього API.

Цей проєкт побудований як класична шарувата (layered) архітектура: кожен шар знає тільки про шар одразу під собою і нічого не знає про шари вище. Роутер не знає, як влаштована база даних. Репозиторій не знає, що таке HTTP. Це дозволяє змінювати один шар (наприклад, перейти з Postgres на іншу БД), не чіпаючи інші.

01 Дерево каталогів

Ось реальна структура app/ в цьому репозиторії. Читайте зверху вниз — саме в такому порядку варто знайомитись із кодом вперше.

З чого почати читати код уперше: app/main.py → один роутер у app/api/ (наприклад routes/router.py) → сервіс, який він викликає → репозиторій → модель. Це і є маршрут одного запиту.

Патерн "application factory" — застосунок збирається функцією, а не створюється як глобальний об'єкт напряму.

Аналогія з фронтендом
Це майже те саме, що функція createApp() у Vue або фабрика configureStore() у Redux — збирає всі шматки (мідлвари, роутери, обробники помилок) в один об'єкт замість того, щоб розкидати конфігурацію по імпортах з побічними ефектами.

Чому це зручно: у тестах можна викликати create_app() ще раз з іншими налаштуваннями (наприклад, іншою тестовою БД), не чіпаючи глобальний стан. Один app.py-файл — і одразу видно весь склад застосунку: які мідлвари, які роутери, які префікси URL.

03 Шар api/ — тільки HTTP

Роутери відповідають за одну річ: перетворити HTTP-запит на виклик сервісу і сервісну відповідь — на HTTP-відповідь. Ніякої бізнес-логіки тут бути не повинно.

app/api/routes/router.py
router = APIRouter(tags=["routes"], dependencies=[Depends(get_current_user)])

@router.post("/optimize", response_model=OptimizeResult)
async def optimize_routes(
    payload: OptimizeRequest,
    organization: Organization = Depends(require_route_quota),
    service: RouteOptimizerService = Depends(get_route_optimizer_service),
    org_repo: OrganizationRepository = Depends(get_organization_repository),
) -> OptimizeResult:
    """Run the OR-Tools solver to build optimized multi-driver routes."""
    try:
        result = await service.optimize(payload)
    except ValueError as exc:
        raise HTTPException(status_code=422, detail=str(exc)) from exc

    if result.routes:
        await org_repo.increment_route_count(organization.id, by=len(result.routes))

    return result

Зверніть увагу: вся логіка солвера (OR-Tools, побудова маршрутів) — усередині service.optimize(...). Роутер лише: перевіряє квоту (через DI-залежність require_route_quota), викликає сервіс, конвертує ValueError у HTTP 422, і оновлює лічильник. Це навмисно тонкий шар.

Аналогія з фронтендом
Роутер ≈ обробник маршруту в Next.js API route або контролер у NestJS: він "проводка", а не мозок. Мозок — у сервісі, як бізнес-логіка в хуку/thunk-і, а не в JSX-компоненті.

04 Шар schemas/ — контракти даних

Pydantic-моделі описують форму вхідних і вихідних даних — і одночасно валідують їх у рантаймі.

Аналогія з фронтендом
Уявіть TypeScript interface + Zod-схему в одному файлі, яка ще й реально виконується на кожному запиті: якщо клієнт надішле email без "@" або пароль коротший за 8 символів — запит впаде з 422 ще до того, як код роутера взагалі почне виконуватись. У TS такого немає "з коробки" — типи стираються в рантаймі, тут же вони живі.

Схеми — це "прикордонний контроль" між зовнішнім світом (JSON з фронтенду) і внутрішнім кодом (Python-об'єкти, ORM-моделі). Помилка валідації автоматично перетворюється на читабельну відповідь — дивіться app/core/error_handlers.py, розділ про безпеку в туторіалі 2.

05 Шар services/ — бізнес-логіка

Тут живе те, "що насправді робить" фіча: оркестрація кількох репозиторіїв, зовнішніх API, розрахунки.

app/services/deliveries/service.py
class DeliveryService:
    """Application-level orchestration for the deliveries vertical slice."""

    def __init__(self, repository, geocoder, org_repo, organization):
        self.repository = repository
        self.geocoder = geocoder       # зовнішній HTTP-клієнт (Google Geocoding)
        self.org_repo = org_repo       # для перевірки квоти
        self.organization = organization

    async def _create_from_fields(self, fields: dict) -> Delivery:
        await self._consume_geocode_quota()          # 1. перевір ліміт
        coordinates = await self.geocoder.geocode(fields["address"])  # 2. зовнішній API
        fields["latitude"], fields["longitude"] = coordinates or (None, None)
        return await self.repository.create(**fields) # 3. запиши в БД

Один метод _create_from_fields координує три різні системи: тарифну логіку (квота), зовнішній платний API (геокодування) і базу даних. Саме тому це не в роутері й не в репозиторії — це "клей", специфічний для домену.

Аналогія з фронтендом
Сервіс ≈ Redux thunk або TanStack Query mutationFn, яка робить кілька кроків і кілька запитів заради однієї користувацької дії — тільки тут це виконується на сервері, а не в браузері.

06 Шар repositories/ — доступ до БД

Repository pattern: усі SQL-запити для однієї моделі — в одному класі, замість того щоб розкидати session.execute(...) по всьому коду.

app/repositories/base.py
class BaseRepository(Generic[ModelType]):
    """Generic repository over a single SQLAlchemy model."""

    async def get(self, id) -> ModelType | None:
        return await self.session.get(self.model, id)

    async def create(self, **kwargs) -> ModelType:
        instance = self.model(**kwargs)
        self.session.add(instance)
        await self.session.commit()
        await self.session.refresh(instance)
        return instance


class TenantScopedRepository(BaseRepository[ModelType]):
    """A BaseRepository whose model has an `organization_id` column.

    The organization is bound once at construction ... so every
    read/write this repository makes is automatically confined to that
    organization — there's no method call site where a caller could
    forget to scope a query."""

    async def get(self, id) -> ModelType | None:
        stmt = select(self.model).where(
            self.model.id == id, self.model.organization_id == self.organization_id
        )
        result = await self.session.execute(stmt)
        return result.scalar_one_or_none()

TenantScopedRepository — ключовий клас проєкту: організація (тенант) прив'язується один раз при створенні репозиторію (в DI, з JWT-токена користувача), і після цього кожен запит до БД автоматично фільтрується по organization_id. Розробник фізично не може написати запит, що поверне чужі дані — бо він просто не має доступу до "нескопованого" методу. Це не лише зручність, а й захист (детальніше — туторіал 2).

Аналогія з фронтендом
Схоже на те, як `axios`-інстанс можна створити з "baseURL" і заголовком авторизації один раз, і далі всі запити через нього автоматично його використовують — тільки тут "прив'язка" це фільтр по орендарю (org), а не заголовок.

09 Dependency Injection у FastAPI

Depends(...) — це серце того, як усі шари зшиваються докупи без глобальних синглтонів.

app/core/dependencies.py
def get_delivery_repository(
    db: AsyncSession = Depends(get_db),
    current_user: User = Depends(get_current_user),
) -> DeliveryRepository:
    return DeliveryRepository(db, current_user.organization_id)


def get_delivery_service(
    repo: DeliveryRepository = Depends(get_delivery_repository),
    org_repo: OrganizationRepository = Depends(get_organization_repository),
    organization: Organization = Depends(get_current_organization),
) -> DeliveryService:
    return DeliveryService(repo, GoogleGeocodingClient(), org_repo, organization)

Це ланцюжок залежностей: щоб зібрати DeliveryService, FastAPI спочатку сам розв'яже get_delivery_repository, який своєю чергою вимагає get_db (сесія БД) і get_current_user (розкодований JWT). Кожна функція — маленька і testable окремо; підмінити будь-яку ланку в тестах — тривіально (app.dependency_overrides[...]).

Аналогія з фронтендом
Найближчий аналог — DI-контейнер Angular або React Context + custom hooks, де компонент оголошує "мені потрібен цей сервіс", а хто саме його створює й з чим — компонент не знає і не повинен знати. FastAPI робить це на рівні функцій, а не класів з декораторами @Injectable().

10 Наскрізний приклад: один запит від і до

Простежимо POST /api/v1/routes/optimize через усі шари — це найкращий спосіб "відчути" архітектуру.

  1. HTTP — клієнт шле JSON з delivery_ids, vehicle_ids, depot_id.
  2. DI перед виконанням роутера — FastAPI розкодовує JWT (get_current_user), тягне організацію, перевіряє квоту (require_route_quota), збирає RouteOptimizerService з шести репозиторіїв.
  3. Роутер (api/routes/router.py) валідує тіло запиту через схему OptimizeRequest, викликає service.optimize(payload).
  4. Сервіс (services/route_optimizer/service.py) тягне доставки, машини, водіїв і депо через репозиторії; будує RoutingProblem; віддає його в RouteSolver (OR-Tools); мапить рішення назад у доставки/зупинки; зберігає нові Route/RouteStop через репозиторії.
  5. Репозиторій виконує реальний SQL: INSERT INTO routes ..., INSERT INTO route_stops ..., скоуплено по organization_id.
  6. Назад нагору: сервіс повертає Pydantic-схему OptimizeResult, роутер оновлює лічильник використаних маршрутів і віддає її як JSON — FastAPI сам серіалізує схему у відповідь.
💡
Жоден шар не "перестрибує" через сусідній: роутер ніколи не робить session.execute(...) напряму, сервіс ніколи не читає request.headers. Якщо колись побачите таке в PR — це сигнал, що архітектурна межа порушена.

11 Добре / погано на реальному коді

Конкретні рішення з цього проєкту — і чому вони саме такі.

✅
Добре — org-scoping вбудований у репозиторій, а не "згадується" у кожному запиті. TenantScopedRepository.get() завжди додає WHERE organization_id = .... Розробнику фізично ніде забути цей фільтр — немає методу, який його не має.
❌
Як було б погано (гіпотетично, не з цього проєкту): якби кожен роутер сам писав select(Delivery).where(Delivery.id == id) і окремо десь перевіряв if delivery.organization_id != current_user.organization_id: raise 403 — рано чи пізно хтось забув би цю перевірку в одному з 30 ендпоінтів, і це стало б витоком чужих даних (IDOR).
✅
Добре — роутери тонкі. api/routes/router.py не містить жодного рядка про OR-Tools чи алгоритми — тільки виклик сервісу й перетворення помилок у HTTP-статуси. Це означає, що логіку оптимізації можна юніт-тестувати без піднятого HTTP-сервера (дивіться test_route_optimizer_unit.py).
⚠️
Компроміс, який варто розуміти: DI-функції в dependencies.py напряму створюють конкретні класи сервісів (GoogleGeocodingClient(), DeliveryService(...)) — це простіше, ніж повноцінний DI-контейнер з інтерфейсами/абстракціями (як буває в Java/NestJS), але означає, що підміна реалізації (наприклад, інший провайдер геокодування) вимагає правити dependencies.py, а не конфіг. Для проєкту такого розміру це свідомий і розумний trade-off простоти проти гнучкості.

12 Інші підходи в індустрії

Шарувата архітектура — не єдиний спосіб. Ось як цей вибір виглядає поруч з іншими популярними підходами.

ПідхідІдеяКоли доцільний
Layered (цей проєкт) api → services → repositories → db, кожен шар знає лише сусідній нижче Середні API-проєкти, команда 1-10 людей, чіткі бізнес-правила
MVC (напр. Django) Model-View-Controller, часто "товсті моделі" з логікою прямо в ORM-класах Швидка розробка CRUD-важких застосунків, готовий адмін-панель "з коробки"
Clean / Hexagonal (Ports & Adapters) Бізнес-логіка в центрі, зовсім не знає про БД/HTTP/фреймворк — вони "адаптери" ззовні Складна доменна логіка, потрібно легко міняти інфраструктуру, довгоживучі проєкти
Vertical Slice / Feature-based Код групується по фічі (усі шари для "deliveries" в одній папці), а не по технічному шару Великі команди, багато незалежних фіч, менше конфліктів при мерджі
Мікросервіси Кожен домен — окремий деплойований застосунок зі своєю БД Дуже велика команда/навантаження, потрібне незалежне масштабування й деплой частин

Цікаво: services/route_optimizer/ у цьому проєкті — вже трохи "vertical slice" усередині шару services (builder, constraints, distance, mapper, models, solver — все про одну фічу в одній папці). Тобто підходи не взаємовиключні — можна комбінувати шарувату архітектуру "зверху" з feature-групуванням "усередині" одного шару.

🎯
Для проєкту такого розміру (один бекенд-сервіс, невелика команда, одна БД) шарувата архітектура — розумний і поширений вибір: досить структури, щоб код не перетворився на "спагеті", без накладних витрат мікросервісів чи повного Clean Architecture з інтерфейсами на кожен клас.

13 Підсумок і що далі

Головне з цього туторіалу:

  • Дані йдуть вниз (api → services → repositories → db) і назад вгору через Pydantic-схеми.
  • Кожен шар має одну відповідальність: роутер — HTTP, сервіс — логіка, репозиторій — SQL.
  • TenantScopedRepository робить ізоляцію орендарів структурною, а не "за домовленістю".
  • DI (Depends) збирає весь цей ланцюжок автоматично й робить кожну частину тестованою окремо.
Далі: Туторіал 2 — асинхронність і захист від атак — як цей самий код виконується без блокування, і що реально захищає API від зловживань.
Туторіал згенеровано на основі реального коду репозиторію ai-delivery-planner-backend — усі приклади й номери рядків відповідають фактичному стану проєкту на момент генерації.
