00Куди йде час запиту

Перш ніж оптимізувати, треба знати, яка частина шляху повільна. Найчастіше це зовсім не сам SQL.

🎯
Відповідь на «ендпоінт повільний, що робиш?»
1) Дивлюся APM / логи: скільки SQL-запитів на HTTP-запит і скільки часу в БД, а скільки в Python. 2) Якщо запитів багато — N+1, лікую eager loading або батчами. 3) Якщо один запит повільний — беру його з pg_stat_statements і запускаю EXPLAIN (ANALYZE, BUFFERS). 4) Дивлюся на Seq Scan по великій таблиці, розбіжність estimated/actual rows, сорт на диск. 5) Лікую індексом, переписом запиту або оновленням статистики. 6) Перевіряю, що не стало гірше на записі.

01EXPLAIN ANALYZE: читаємо план

Головний інструмент. На співбесіді часто дають план і просять сказати, що не так.

  • EXPLAIN — тільки план з оцінками, запит не виконується.
  • EXPLAIN ANALYZE — виконує запит і показує фактичні час і рядки. Для UPDATE/DELETE загортай у BEGIN; … ROLLBACK;.
  • BUFFERS — скільки сторінок по 8 КБ прочитано з кешу (shared hit) і з диска (read). Часто показовіше за час.

Реальний запит проєкту: TenantScopedRepository.list() — «усі доставки організації, новіші першими». Ось як він виглядає на 200 000 рядків без індексу на organization_id (а в проєкті його зараз немає):

WHERE organization_id = '5f0c…'
ORDER BY created_at DESC
LIMIT 50;

Як читати

  1. Знизу вгору, зсередини назовні: дочірні вузли виконуються першими. Тут: Seq Scan → Sort → Limit.
  2. cost=startup..total — умовні одиниці планувальника, не мілісекунди. Порівнюй їх тільки між планами одного запиту.
  3. rows=5000 (оцінка) проти actual … rows=5000 — тут оцінка точна. Розбіжність у 10–100× — головна причина поганих планів (розділ 2).
  4. Rows Removed by Filter: 195000 — прочитали 200 000 рядків, щоб віддати 5 000. Це і є сигнал «потрібен індекс».
  5. loops=N — вузол виконався N разів (усередині Nested Loop). Фактичний час = time × loops.

02Статистика планувальника

Planner вибирає план за оцінками кількості рядків. Хибна статистика → хибний план, навіть якщо індекси правильні.

  • ANALYZE table (і autovacuum) збирає вибірку: частку NULL, кількість різних значень (n_distinct), найчастіші значення і гістограму. Дивитися — у pg_stats.
  • Після масового імпорту (у проєкті — імпорт Excel на тисячі доставок) статистика застаріла, доки не відпрацює autovacuum. Явний ANALYZE deliveries після великого імпорту — нормальна практика.
  • Корельовані колонки: planner вважає умови незалежними. city = 'Kyiv' AND region = 'Kyiv oblast' він оцінить як добуток вибірковостей і сильно занизить кількість рядків. Лікується через CREATE STATISTICS … (dependencies) ON city, region FROM ….
  • Перекошені дані (одна організація має 90% доставок): для неї Seq Scan правильний, для решти — Index Scan. Postgres це враховує через most common values, якщо статистики достатньо (ALTER TABLE … ALTER COLUMN … SET STATISTICS 1000).
⚠️
Типовий симптом
У плані Nested Loop (rows=1) (actual rows=48000 loops=1): planner думав, що рядок буде один, обрав вкладений цикл, а рядків 48 000, і кожен з них — окремий пошук. Спочатку ANALYZE, потім розширена статистика, і тільки потім переписування запиту.

03Типи індексів у Postgres

«Який індекс для якого запиту» — улюблене питання. B-tree покриває 90% випадків, але решта 10% якраз і перевіряють.

💡
Як Postgres рахує, чи використати індекс
Індекс-скан — це випадкові читання heap-сторінок, а Seq Scan — послідовні. Якщо умові відповідає велика частка таблиці, Seq Scan дешевший, і planner правий, що ігнорує індекс. Тому «додав індекс, а він не використовується» — не завжди баг.

04Як проєктувати індекс

Не «індекс на кожну колонку», а індекс під конкретний запит.

4.1 Складений індекс: порядок колонок

Правило: спочатку колонки з рівністю, потім діапазон або сортування. Індекс (organization_id, status, created_at) обслуговує:

  • WHERE organization_id = ? ✅ (лівий префікс)
  • WHERE organization_id = ? AND status = ? ORDER BY created_at ✅
  • WHERE status = ? ❌ без першої колонки (Postgres 18 вміє skip scan, але покладатися на це не варто)
  • WHERE organization_id = ? AND created_at > ? — частково: діапазон по created_at не використовує індекс ефективно, бо між ними є status

4.2 Частковий індекс

тільки «живі» рядки
-- геокодер щохвилини шукає доставки без координат; таких ~1% таблиці
CREATE INDEX CONCURRENTLY ix_deliveries_pending_geocode
    ON deliveries (organization_id)
    WHERE status = 'pending_geocode';

Індекс у 100 разів менший і не оновлюється для решти 99% рядків. Запит мусить містити ту саму умову status = 'pending_geocode', інакше planner індекс не використає.

4.3 Індекс по виразу

регістронезалежний логін
CREATE UNIQUE INDEX ux_users_email_lower ON users (lower(email));
-- працює тільки для WHERE lower(email) = lower(:email)

4.4 Покривний індекс (INCLUDE) і Index Only Scan

список стопів маршруту без читання таблиці
CREATE INDEX CONCURRENTLY ix_route_stops_route_seq
    ON route_stops (route_id, sequence) INCLUDE (status, delivery_id);

Якщо запит бере тільки колонки з індексу, Postgres може не ходити в heap. Але він перевіряє visibility map: якщо сторінку змінювали після останнього VACUUM, читання heap однаково буде (Heap Fetches у плані). Тому Index Only Scan гарний на таблицях, які не дуже часто оновлюються, або при агресивному autovacuum.

4.5 Ціна індексу

  • Кожен INSERT пише в усі індекси таблиці; UPDATE — в усі, якщо не HOT-update.
  • HOT-update (heap-only tuple): якщо змінені колонки не індексовані і на сторінці є місце, індекси не чіпаються. Індекс на updated_at або status, які часто оновлюються, вбиває HOT. Допомагає fillfactor 80–90 для «гарячих» таблиць.
  • Індекси займають пам'ять у shared_buffers і витісняють корисні дані.
  • Невикористані індекси шукай через pg_stat_user_indexes.idx_scan = 0 (розділ 11).
🔑
Пастка: зовнішні ключі
Postgres автоматично індексує тільки PRIMARY KEY і UNIQUE. Колонку з FOREIGN KEY він не індексує. Наслідки: (1) повільні JOIN і фільтри по ній; (2) DELETE FROM deliveries WHERE id = … робить Seq Scan по route_stops, щоб перевірити, чи на рядок ніхто не посилається. У цьому проєкті так з route_stops.route_id, route_stops.delivery_id і organization_id у більшості таблиць (розділ 13).

06ORM: N+1 і bulk-операції

Більшість проблем продуктивності в Python-бекендах — не повільний SQL, а забагато SQL.

6.1 N+1

❌ N+1: 1 запит на маршрути + N на стопи
routes = await route_repo.list()                       # 1 запит
for route in routes:
    route.stops = await stop_repo.list_by_route(route.id)   # +1 запит на КОЖЕН маршрут

В async SQLAlchemy ліниве завантаження зв'язку (route.stops без eager loading) навіть не спрацює тихо, а впаде з MissingGreenlet. Це корисний запобіжник: N+1 видно одразу.

✅ варіанти
# 1) selectinload: 2 запити, другий — WHERE route_id IN (...)
stmt = select(Route).where(Route.organization_id == org_id).options(selectinload(Route.stops))

# 2) joinedload: 1 запит з JOIN — добре для many-to-one (stop → delivery),
#    погано для one-to-many (дублює рядки батька)
stmt = select(RouteStop).options(joinedload(RouteStop.delivery))

# 3) вручну батчем, як у get_route_with_stops цього проєкту:
stops = await stop_repo.list_by_route(route_id)
deliveries = await delivery_repo.get_many([s.delivery_id for s in stops])   # один IN-запит

# запобіжник: заборонити ліниве завантаження на рівні моделі
stops: Mapped[list[RouteStop]] = relationship(lazy="raise")

У проєкті relationship() поки не використовуються, і зв'язані дані збираються вручну батчем через get_many (IN-запит) — це правильний патерн, 3 запити на маршрут незалежно від кількості стопів.

07Пагінація: OFFSET vs keyset

OFFSET 100000 змушує базу прочитати й викинути 100 000 рядків. Keyset починає одразу з потрібного місця.

✅ keyset (cursor) пагінація для GET /deliveries
async def list_page(self, limit: int = 50, cursor: tuple[datetime, uuid.UUID] | None = None):
    stmt = (
        select(Delivery)
        .where(Delivery.organization_id == self.organization_id)
        .order_by(Delivery.created_at.desc(), Delivery.id.desc())   # id — тай-брейкер
        .limit(limit + 1)                                           # +1, щоб знати, чи є наступна
    )
    if cursor:
        stmt = stmt.where(tuple_(Delivery.created_at, Delivery.id) < cursor)
    rows = list((await self.session.scalars(stmt)).all())
    has_more = len(rows) > limit
    return rows[:limit], has_more

# індекс під цей запит:
# CREATE INDEX CONCURRENTLY ix_deliveries_org_created_id
#     ON deliveries (organization_id, created_at DESC, id DESC);
  • Курсор кодують у непрозорий рядок (base64 від created_at|id), фронтенд тільки передає його назад — як getNextPageParam в useInfiniteQuery.
  • Мінус keyset: не можна стрибнути на «сторінку 37». Для адмінок з номерами сторінок OFFSET прийнятний на невеликих обсягах.
  • Зараз GET /deliveries у проєкті віддає усі рядки організації без ліміту — це перше, що зламається на великому клієнті.

09Транзакції, блокування, таймаути

Довга транзакція шкодить усім: тримає з'єднання, локи і не дає VACUUM прибрати мертві рядки.

  • Не роби мережевих викликів усередині транзакції (OpenAI, геокодер, SMTP). 10-секундний виклик = 10 секунд тримання з'єднання і рядкових локів.
  • idle in transaction у pg_stat_activity — застосунок відкрив транзакцію і «забув» про неї. Захист: idle_in_transaction_session_timeout.
  • statement_timeout на рівні ролі застосунку (наприклад, 5 с для API, більше для звітів) — запобіжник від запиту, що з'їдає базу.
  • Довгі транзакції блокують VACUUM: мертві версії рядків, які ще може бачити найстаріший знімок, не можна прибрати → bloat і повільніші скани (туторіал 19).
  • Рядкові локи (FOR UPDATE) брати якомога пізніше і на мінімум рядків, в однаковому порядку — інакше дедлоки (туторіал 29, B3).
хто кого блокує

1420 питань співбесіди

Спочатку відповідай уголос, потім відкривай.

01Чим EXPLAIN відрізняється від EXPLAIN ANALYZE?

EXPLAIN показує план і оцінки, не виконуючи запит. ANALYZE виконує його і додає фактичні час, рядки і loops. Для змінювальних запитів — у транзакції з ROLLBACK. BUFFERS додає статистику сторінок.

02Індекс є, але planner робить Seq Scan. Чому?

(1) Умова повертає велику частку таблиці — Seq Scan справді дешевший; (2) функція або приведення типу над колонкою; (3) застаріла статистика; (4) запит не використовує лівий префікс складеного індексу; (5) маленька таблиця; (6) LIKE '%x'. Перевіряю EXPLAIN ANALYZE і pg_stats.

03Як вибрати порядок колонок у складеному індексі?

Колонки з рівністю першими, потім колонка діапазону або сортування. Враховувати, які запити мають використовувати індекс як лівий префікс. Вибірковість — вторинний критерій.

04Що таке Index Only Scan і чому він іноді все одно читає таблицю?

Усі потрібні колонки є в індексі. Але видимість рядка зберігається в heap, тож Postgres перевіряє visibility map: для сторінок, не позначених all-visible, читає heap (Heap Fetches). VACUUM оновлює visibility map.

05Коли GIN, коли GiST, коли BRIN?

GIN — «багато ключів у значенні»: JSONB, масиви, повнотекстовий пошук, триграми. GiST — геометрія, діапазони, найближчий сусід, exclusion constraints. BRIN — величезні append-only таблиці, де значення корелює з фізичним порядком (час запису).

06Чому OFFSET-пагінація повільна на дальніх сторінках?

Базі треба знайти і пропустити всі рядки до OFFSET. Час росте лінійно з номером сторінки; до того ж при вставках рядки дублюються або губляться. Keyset: WHERE (created_at, id) < (:ts, :id) ORDER BY … LIMIT n з відповідним індексом.

07Що таке N+1 і як його знайти й виправити в SQLAlchemy?

Один запит на список + по запиту на кожен елемент. Знаходять за логами SQL / APM (однаковий запит повторюється N разів). Лікують selectinload (one-to-many), joinedload (many-to-one), ручним IN-батчем; lazy="raise" як запобіжник.

08Чому Postgres-з'єднання дорогі і навіщо PgBouncer?

Кожне з'єднання — окремий процес з власною пам'яттю; встановлення дороге, а сотні активних з'єднань погіршують пропускну здатність. PgBouncer мультиплексує багато клієнтських з'єднань на кілька серверних (transaction mode).

09Які обмеження PgBouncer у transaction mode?

Стан сесії не переживає транзакцію: SET, тимчасові таблиці, сесійні advisory locks, LISTEN/NOTIFY. Prepared statements — проблема для старих версій (asyncpg: statement_cache_size=0); PgBouncer 1.21+ підтримує їх на рівні протоколу.

10Як додати індекс на таблицю з 100 млн рядків у продакшені?

CREATE INDEX CONCURRENTLY поза транзакцією (в Alembic — autocommit_block), з lock_timeout; моніторити pg_stat_progress_create_index; після збою — видалити INVALID індекс і повторити.

11Чим шкідливі довгі транзакції?

Тримають з'єднання з пулу і локи, блокують інші запити і DDL, не дають VACUUM прибрати мертві версії (bloat, повільніші скани, ризик wraparound). Захист — короткі транзакції, без мережевих викликів, idle_in_transaction_session_timeout, statement_timeout.

12Чому COUNT(*) у Postgres повільний на великій таблиці?

Через MVCC немає одного «поточного» лічильника: кожен рядок треба перевірити на видимість для знімка. Index Only Scan допомагає, якщо visibility map свіжа. Альтернативи — оцінка reltuples, денормалізований лічильник, кеш.

13Що робить VACUUM і чим він відрізняється від VACUUM FULL?

VACUUM позначає місце мертвих версій для перевикористання, оновлює visibility map і freeze-статуси, не блокуючи читання й запис. VACUUM FULL переписує таблицю повністю з ACCESS EXCLUSIVE локом — у продакшені замість нього pg_repack. Детально — туторіал 19.

14Як знайти найповільніші запити в продакшені?

pg_stat_statements за total_exec_time; log_min_duration_statement і auto_explain; APM на стороні застосунку; pg_stat_activity для того, що виконується зараз.

15Коли партиціонувати таблицю?

Коли таблиця дуже велика і більшість запитів фільтрує по ключу партиції (час, тенант), а старі дані треба регулярно видаляти чи архівувати. Не як заміну індексам: запити без ключа партиції стануть повільнішими.

16Чим відрізняються work_mem і shared_buffers?

shared_buffers — спільний кеш сторінок для всіх процесів (типово ~25% RAM). work_mem — пам'ять на одну операцію сорту чи хешу в одному запиті; запит може взяти її кілька разів, тож великий work_mem × багато з'єднань = OOM. Ознака нестачі — external merge Disk у плані.

17Як зробити bulk-вставку 1 млн рядків з Python?

COPY (asyncpg copy_records_to_table, psycopg copy) — найшвидше. Далі insert() з executemany і батчами в одній транзакції. Для дуже великих — тимчасово прибрати некритичні індекси й створити після, потім ANALYZE.

18Як вибрати розмір пулу з'єднань?

Від бюджету БД: Σ процесів × (pool_size + max_overflow) < max_connections − резерв. Для одного процесу достатньо невеликого пулу (5–10): більший пул маскує повільні запити й довгі транзакції. Якщо процесів багато — PgBouncer.

19Чому важливо індексувати foreign key?

Postgres не робить цього сам. Без індексу JOIN і фільтр по FK — Seq Scan, а видалення/оновлення батьківського рядка змушує сканувати дочірню таблицю для перевірки обмеження (і тримати локи довше).

20Як би ти прискорив дашборд цього проєкту на 1000 організацій?

Індекси (organization_id, created_at) і (organization_id, status); один запит з FILTER замість кількох COUNT; sargable-діапазон замість date(); кеш у Redis на 30–60 с на організацію; для історії використання — щоденна зведена таблиця, яку наповнює Celery beat.
