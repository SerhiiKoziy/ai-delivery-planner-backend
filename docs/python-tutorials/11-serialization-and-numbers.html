Частина I · Серіалізація

1 Що JSON НЕ вміє серіалізувати "з коробки"

JSON — формат з дуже обмеженим набором типів: рядок, число, булеве значення, null, масив, об'єкт. Python-типів у ньому набагато більше.

python
import json
from datetime import datetime
from uuid import uuid4

json.dumps({"created_at": datetime.now()})
# TypeError: Object of type datetime is not JSON serializable

json.dumps({"id": uuid4()})
# TypeError: Object of type UUID is not JSON serializable
Python-типПроблема з JSON
datetime / dateНемає стандартного типу дати — потрібно самому вирішити формат (зазвичай ISO 8601 рядком)
UUIDНемає типу — серіалізується як рядок
DecimalНемає точного десяткового типу — типово серіалізується як рядок, щоб не втратити точність
setНемає типу множини — потрібно перетворити на list (і втратити гарантію унікальності при десеріалізації)
bytesНемає бінарного типу — потрібне кодування (наприклад, base64)

Найпростіший (хоч і не завжди найзручніший) спосіб — власна функція default= для json.dumps, яка каже, як перетворити "невідомий" тип на щось, що JSON уже розуміє:

python
def default(obj):
    if isinstance(obj, (datetime, date)):
        return obj.isoformat()
    if isinstance(obj, UUID):
        return str(obj)
    raise TypeError(f"Object of type {type(obj).__name__} is not JSON serializable")

json.dumps({"created_at": datetime.now()}, default=default)  # тепер працює

2 Як цю проблему вирішує Pydantic (і чому ви цього майже не помічаєте)

У цьому проєкті, як і в будь-якому FastAPI-застосунку, ви навряд чи колись писали власний default= — і ось чому.

app/schemas/route.py (концептуально) — Pydantic-схема
class RouteRead(BaseModel):
    id: uuid.UUID
    created_at: datetime
    total_distance_km: float
    # ...

# FastAPI автоматично серіалізує RouteRead у JSON-відповідь —
# UUID стає рядком, datetime -- ISO 8601 рядком, без жодного ручного коду

Pydantic уже знає, як серіалізувати всі поширені "не-JSON" Python-типи (datetime, UUID, Decimal, Enum тощо) — саме тому шар schemas/ у цьому проєкті (туторіал 1) не просто валідує вхідні дані, а й "безкоштовно" вирішує проблему серіалізації на виході, яку інакше довелось би вирішувати вручну для кожного ендпоінта.

3 pickle — зовсім інший підхід до серіалізації

JSON описує лише дані. pickle — стандартний модуль Python для серіалізації — описує майже будь-який Python-об'єкт, включно з його класом.

python
import pickle

data = {"routes": [1, 2, 3], "created": datetime.now(), "id": uuid4()}
blob = pickle.dumps(data)      # -> bytes, зрозумілі лише Python
restored = pickle.loads(blob)  # -> точна копія, без ручного default=

pickle "з коробки" серіалізує практично будь-що (включно з datetime, довільними класами, навіть функціями) — ціною того, що результат уже не текст, а специфічний для Python бінарний формат, нечитабельний і несумісний з іншими мовами.

4 Чому pickle небезпечний

Найважливіший факт цього туторіалу з погляду безпеки — і одне з улюблених "trick questions" на співбесідах.

Десеріалізація (pickle.loads) — це не просто "прочитати дані". Формат pickle — це фактично послідовність інструкцій для маленької віртуальної машини: "створи об'єкт такого класу", "виклич цей метод", "встанови цей атрибут". Якщо клас має метод __reduce__, pickle використовує його, щоб дізнатись, як саме відтворити об'єкт — а __reduce__ може повернути виклик будь-якої функції.

python — навіщо офіційна документація попереджає "не unpickle-іть недовірені дані"
import pickle, os

class Demo:
    def __reduce__(self):
        # pickle.loads() виконає os.system("echo pwned") САМ, без жодного
        # виклику якоїсь "небезпечної" функції з вашого боку -- просто через
        # сам факт десеріалізації цього байт-рядка
        return (os.system, ("echo pwned",))

blob = pickle.dumps(Demo())
pickle.loads(blob)   # виконує echo pwned -- ДОВІЛЬНИЙ КОД під час "просто читання даних"
❌
Ключовий висновок: pickle.loads(bytes_from_untrusted_source) еквівалентно виконанню довільного коду з тим самим рівнем прав, що й ваш процес. Це не теоретичний ризик — офіційна документація Python прямо каже: "Ніколи не unpickle-іть дані з ненадійного чи неавтентифікованого джерела".
Аналогія з фронтендом
Той самий клас проблеми, що й eval() довільного JS-рядка від користувача, або небезпечне (не-"safe") десеріалізування YAML — "формат серіалізації", що вміє відтворювати не лише дані, а й поведінку, завжди потенційно небезпечний на недовіреному вході.

5 Коли pickle все ж доречний

✅ Прийнятно
Кеш у Redis/на диску, який пише і читає ЛИШЕ ваш власний процес Обмін даними між довіреними внутрішніми сервісами по приватній мережі multiprocessing.Queue — передача даних між ВЛАСНИМИ процесами
❌ Ніколи
Дані, отримані через публічний HTTP API Payload з черги повідомлень, куди можуть писати треті сторони Що завгодно, збережене чи передане поза межами вашого довіреного периметра

Практичне правило: якщо дані коли-небудь перетинають межу довіри (мережа, зовнішній клієнт, файл, до якого має доступ хтось інший) — pickle не годиться; JSON (чи інший формат "лише даних") — так.

6 Celery і серіалізація задач

Пряме продовження туторіалу 3 — Celery вже підключений у проєкті (app/workers/celery_app.py) для майбутніх фонових задач.

Аргументи Celery-задачі (optimize_routes_task(route_request_id: str)) теж треба серіалізувати — вони йдуть через Redis (брокер) від процесу, що ставить задачу в чергу, до окремого процесу-воркера, що її виконує. Історично Celery за замовчуванням використовував pickle — але через ризики з розділу 4, з Celery 4+ дефолтний серіалізатор — JSON. Це означає: аргументи задач мають бути простими, JSON-сумісними типами (рядки, числа, списки, словники) — саме тому сигнатура optimize_routes_task(route_request_id: str) у проєкті приймає простий рядок-ідентифікатор, а не складний об'єкт.

✅
Якби воркер і застосунок, що ставить задачу в чергу, не довіряли одне одному повністю (наприклад, черга спільна з іншими командами/сервісами), явний вибір JSON замість pickle для Celery — не просто дефолт, а свідоме рішення про безпеку периметра.
Частина II · Точність чисел

7 Чому 0.1 + 0.2 != 0.3

Не баг Python — фундаментальна властивість того, як comp'ютери представляють дробові числа.

python
0.1 + 0.2
# 0.30000000000000004

0.1 + 0.2 == 0.3
# False

float у Python (як і в JS, Java, C — практично скрізь) — це двійкове число з плаваючою комою подвійної точності (IEEE 754). Комп'ютер зберігає дробові числа у двійковій системі числення, а не десятковій — і так само, як 1/3 не можна точно записати скінченним десятковим дробом (0.333...), число 0.1 не можна точно записати скінченним двійковим дробом. Воно округлюється до найближчого представного значення — і сума двох таких округлень дає крихітну похибку.

Аналогія з фронтендом
0.1 + 0.2 === 0.30000000000000004 — та сама поведінка в JavaScript, слово в слово. Це не особливість Python — це властивість формату IEEE 754, який використовує майже кожна мова програмування для чисел з плаваючою комою.

8 Decimal — точна десяткова арифметика

python
from decimal import Decimal

Decimal("0.1") + Decimal("0.2")
# Decimal('0.3')  -- точно, без похибки

Decimal("0.1") + Decimal("0.2") == Decimal("0.3")
# True
⚠️
Класична пастка: Decimal(0.1) (з float, без лапок) все одно успадковує похибку — бо саме число 0.1 уже неточне ще до того, як потрапило в Decimal. Завжди створюйте Decimal з рядка: Decimal("0.1"), а не з float-літерала.

Decimal зберігає число як точну послідовність десяткових цифр (не двійкових) — саме тому десяткові дроби на кшталт 0.1 представляються без жодної похибки. Ціна — суттєво повільніша арифметика за float, тому Decimal використовують вибірково, там, де точність критична, а не всюди.

9 float vs Decimal vs цілі копійки

ПідхідКоли доречнийРизик
floatНаукові розрахунки, координати, відстані (як total_distance_km у цьому проєкті) — де крихітна похибка не змінює бізнес-результатНіколи не порівнювати на точну рівність (==) — лише з допуском
DecimalГроші, тарифи, бухгалтерія — де кожна копійка має значення юридичноПовільніший; легко забути створювати з рядка, а не float
Цілі копійки (int)Дуже поширений патерн у платіжних системах: зберігати суму в найменшій одиниці (центи/копійки) як звичайне ціле числоТреба пам'ятати домовленість "це число — у копійках" на кожному кроці коду
💼
На співбесіді запитають так "Як би ви зберігали суму грошей у базі даних?" — хороша відповідь: Decimal (чи еквівалентний точний тип у БД, наприклад Postgres NUMERIC) або цілі копійки — і ніколи float/FLOAT, саме через накопичувальну похибку округлення з розділу 7, яка на великих обсягах транзакцій може призвести до реальних розбіжностей у балансі.

У цьому проєкті total_distance_km і total_duration_minutes — навмисно float, не Decimal: це виміряні/розраховані величини (результат OR-Tools-солвера), де похибка в шостому знаку після коми не має жодного практичного значення — на відміну від грошей.

10 Каверзні питання співбесіди

БазаЯкі Python-типи не серіалізуються в JSON "з коробки"?
datetime/date, UUID, Decimal, set, bytes — усі вимагають або власної функції default= для json.dumps, або бібліотеки/фреймворка (як Pydantic), що вже знає, як їх перетворити.
ПасткаЧому pickle.loads() вважається небезпечним, а json.loads() — ні?
Формат pickle може містити інструкції на виклик довільних функцій (через __reduce__) — десеріалізація фактично виконує код. JSON описує лише прості структури даних (рядки, числа, списки, об'єкти) — розбір JSON ніколи не призводить до виконання довільного коду.
БазаЧому 0.1 + 0.2 != 0.3 в Python?
float — двійкове число з плаваючою комою (IEEE 754); 0.1 не має точного скінченного представлення у двійковій системі, тому округлюється, і сума двох округлень дає крихітну похибку. Це властивість формату, не баг конкретно Python.
ПасткаУ чому пастка з Decimal(0.1) замість Decimal("0.1")?
Decimal(0.1) (без лапок) створює Decimal із уже неточного float-значення — похибка успадковується. Decimal("0.1") (з рядка) створює точне десяткове представлення з нуля.
БазаЧому Celery за замовчуванням серіалізує задачі в JSON, а не pickle?
Історично Celery використовував pickle, але через ризик виконання довільного коду при десеріалізації задачі з черги (розділ 4) сучасний дефолт — JSON, безпечніший для черги, де могли б з'явитись дані з менш довірених джерел.
БазаЯк правильно зберігати грошові суми в базі даних?
Decimal/NUMERIC для точної десяткової арифметики, або цілі копійки (int) — ніколи float, через накопичувальну похибку округлення.
