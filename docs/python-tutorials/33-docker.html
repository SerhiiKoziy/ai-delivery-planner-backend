00Навіщо Docker

Docker пакує застосунок разом з усім, що йому потрібно для запуску, в один незмінний артефакт. Цей артефакт однаково запускається на ноутбуці, в CI і в продакшні.

Без Docker бекенд цього проєкту потребує на сервері правильний Python 3.12, системні бібліотеки для ortools, pandas та asyncpg, потрібні версії пакетів і правильну команду запуску. Будь-яка розбіжність дає «у мене працює». Docker прибирає цю розбіжність: ти один раз описуєш середовище в Dockerfile, збираєш з нього образ (image) і запускаєш контейнери з цього образу будь-де, де є контейнерний рантайм.

⚛️
Аналогія з фронтенду
Dockerfile — як конфіг збірки (vite.config.ts + package.json), образ — як готовий dist/ разом із запіненими node_modules, тільки ще й з «операційкою». Registry — це npm-реєстр для образів. Тег (:latest, :v1.4) схожий на dist-tag у npm: його можна перевісити на іншу версію. Дайджест sha256:… — як integrity-хеш у package-lock.json: він гарантує точний вміст. Контейнер схожий на відкриту вкладку з задеплоєним білдом: вкладок може бути багато, а білд один.

Що Docker дає, а що ні

Дає
  • Відтворюване середовище: однакові ОС-бібліотеки, Python і пакети всюди
  • Один артефакт для CI, staging і prod: тестуєш те, що деплоїш
  • Ізоляцію процесів, мережі й файлової системи плюс ліміти CPU/RAM
  • Швидкий старт (секунди, не хвилини, як у VM) і щільне розміщення
  • Стандартний формат (OCI), який розуміють Fly, Cloud Run, ECS, Kubernetes
  • Простий rollback: задеплоїти попередній образ
Не дає
  • Відтворюваності залежностей без lock-файлу: pip install під час збірки бере «останні» версії
  • Безпеки «з коробки»: за замовчуванням процес працює від root
  • Збереження даних: файли в контейнері зникають разом з ним, якщо не винести їх у volume
  • Оркестрації: автоскейлінг, rolling-деплой і self-healing — це завдання Fly, k8s, ECS
  • Повної ізоляції, як у VM: ядро ОС спільне

01Контейнер vs віртуалка: що всередині

Класичне перше питання. Відповідь — три механізми ядра Linux, а не «легка віртуалка».

МеханізмЩо робитьЯк це видно
NamespacesІзолюють, що процес бачить: pid, net, mnt, uts, ipc, user, cgroupУ контейнері ps показує uvicorn як PID 1; є власний eth0 і власний localhost
cgroupsОбмежують, скільки процес може взяти: CPU, RAM, I/O, кількість PID--memory=512m: при перевищенні процес вбиває OOM killer (exit 137)
Union FS (overlayfs)Накладає read-only шари образу і тонкий записуваний шар контейнераЗапис у /code зникає після docker rm; 10 контейнерів ділять ті самі шари на диску

Стандарти: Docker ≠ контейнери

  • OCI (Open Container Initiative) визначає формат образу і рантайму. Образ, зібраний docker build, запускають containerd, Podman, CRI-O, Kubernetes, Fly, Cloud Run.
  • Docker Engine — це dockerd (API і збірка через BuildKit), який делегує запуск containerd, а той — runc (створює namespaces/cgroups).
  • Kubernetes з версії 1.24 прибрав dockershim і працює з containerd напряму. Для образів це нічого не змінило: вони OCI-сумісні.
  • На macOS немає Linux-ядра, тож Docker Desktop (OrbStack, Colima) запускає маленьку Linux-VM. Звідси повільніші bind-mount-и і нюанс з архітектурою: M-чип збирає linux/arm64, а більшість серверів — linux/amd64 (див. розділ 15).
  • Fly.io взагалі не запускає Docker на своїх серверах: він розпаковує OCI-образ у rootfs і стартує Firecracker microVM. Ти отримуєш ізоляцію рівня VM при зручності образів.
🎯
Коротка відповідь
«Контейнер — це процес Linux з власними namespaces (що він бачить), cgroups (скільки ресурсів бере) і overlay-файловою системою з шарів образу. Ядро спільне з хостом, тому контейнер стартує за секунди й займає мегабайти, але ізоляція слабша, ніж у VM. Коли потрібна сильна ізоляція (multi-tenant код клієнтів), використовують microVM: Firecracker, gVisor, Kata.»

02Образ, шари і кеш збірки

Найпрактичніша тема. Від порядку інструкцій залежить, чи збірка займе 10 секунд, чи 4 хвилини.

  • Кожна RUN, COPY і ADD створює новий шар — diff файлової системи з sha256-адресою. ENV, WORKDIR, EXPOSE і CMD змінюють лише метадані образу, шарів на диску вони не додають.
  • Під час збірки BuildKit іде інструкціями зверху вниз і для кожної шукає шар у кеші. Ключ кешу: попередній шар + текст інструкції, а для COPY/ADD ще й контрольні суми файлів.
  • Щойно один крок промахнувся повз кеш, усі наступні кроки перезбираються.
  • RUN кешується за текстом команди, а не за результатом. RUN apt-get update, закешований місяць тому, так і лишиться місячної давності. Тому update і install пишуть в одному RUN.
⚛️
Аналогія з фронтенду
Це той самий трюк, що й у CI фронтенду: кеш node_modules з ключем за хешем package-lock.json. Або vendor-чанк у Webpack/Vite з [contenthash]: правка в компоненті інвалідує тільки app-чанк, а 2 МБ React і бібліотек браузер бере з кешу. COPY pyproject.toml перед COPY app/ — це і є «vendor-чанк окремо від коду».

Наслідки, про які питають

  • Видалення в наступному шарі не зменшує образ. COPY big.zip + RUN rm big.zip = файл назавжди лишається в нижньому шарі. Для секретів це ще й витік: шар можна витягнути з образу.
  • Об'єднуй RUN-и, які створюють і прибирають сміття: apt-get install … && rm -rf /var/lib/apt/lists/* в одній інструкції.
  • Шари спільні між образами. Десять сервісів на python:3.12-slim зберігають базу на диску один раз, і pull тягне лише відсутні шари.
  • BuildKit cache mount (RUN --mount=type=cache,target=/root/.cache/pip …) зберігає кеш pip між збірками, але не кладе його в образ. Навіть коли pyproject.toml змінився, вже завантажені wheel-и не качаються вдруге.
  • Подивитися шари: docker history <image>, детально — утиліта dive.

03Наш Dockerfile рядок за рядком

13 рядків, і за кожним стоїть рішення. На співбесіді «поясни свій Dockerfile» — дуже часте завдання.

Dockerfile — реальний код з проєкту
FROM python:3.12-slim

WORKDIR /code
ENV PYTHONPATH=/code

COPY pyproject.toml ./
RUN pip install --no-cache-dir .

COPY app/ ./app/
COPY alembic.ini ./

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--proxy-headers", "--forwarded-allow-ips=*"]
РядокЩо робитьЧому так
FROM python:3.12-slimБазовий образ: Debian + CPython 3.12 без компіляторів і документаціїglibc, тож для ortools, pandas, numpy, asyncpg, bcrypt є готові manylinux-wheels і нічого не компілюється. На Alpine (musl) частину з них довелося б збирати з сирців. Версія 3.12 збігається з requires-python і CI.
WORKDIR /codeСтворює теку і робить її поточною для наступних інструкцій і для рантаймуНе треба писати cd у кожному RUN. Відносні шляхи в COPY і alembic.ini рахуються від /code.
ENV PYTHONPATH=/codeДодає /code у шляхи імпортуСам пакет app через pip не встановлюється (див. наступний рядок), тож import app.main працює саме завдяки PYTHONPATH.
COPY pyproject.toml ./Копіює лише маніфест залежностейОкремий шар для кешу (розділ 2): поки pyproject.toml не змінився, важкий pip install береться з кешу.
RUN pip install --no-cache-dir .Ставить проєкт з pyproject.toml разом з усіма dependenciesТрюк: коду ще немає, тому setuptools не знаходить пакетів і ставить «порожній» дистрибутив, але всі залежності встановлюються. --no-cache-dir не лишає ~100 МБ кешу pip в образі. Мінус: немає lock-файлу, тож версії резолвляться в момент збірки (туторіал 12, розділ 8).
COPY app/ ./app/Копіює кодЯвний список замість COPY . .: в образ не потрапляють .env, .venv і docs/. Тести з app/tests потрапляють, бо лежать усередині app/: це кілька КБ, не критично, але варто знати.
COPY alembic.ini ./Конфіг міграційПотрібен для release_command = "alembic upgrade head" у fly.toml. Самі міграції (app/db/migrations) приїхали з app/.
EXPOSE 8000Лише документація: метадані «сервіс слухає 8000»Порт не публікує. Публікує docker run -p, а на Fly — internal_port = 8000 у fly.toml.
CMD [...] (exec-форма)Команда за замовчуванням при старті контейнераJSON-масив: uvicorn стає PID 1 напряму, без /bin/sh, і сам отримує SIGTERM/SIGINT для graceful shutdown. Shell-форма (CMD uvicorn …) зробила б PID 1 оболонку, яка сигнали не пересилає.
--host 0.0.0.0Слухати всі інтерфейси контейнераЗі 127.0.0.1 (дефолт uvicorn) сервер приймає з'єднання лише з loopback усередині контейнера, а трафік з -p чи від Fly Proxy приходить на eth0. Це найчастіший баг «контейнер працює, а порт не відповідає».
--proxy-headers --forwarded-allow-ips=*Довіряти X-Forwarded-For/-Proto від проксіПеред застосунком стоїть Fly Proxy (TLS-термінація). Без цих прапорців request.client.host — це IP проксі, і rate limit по IP рахує всіх як одного клієнта. * безпечно лише тому, що машина недоступна в обхід проксі.
⚠️
Чого тут немає (і що стане питанням «що б ти покращив?»): .dockerignore, lock-файлу, non-root користувача, PYTHONUNBUFFERED, піна бази за дайджестом, HEALTHCHECK для локального запуску. Покращена версія — у розділі 6, повний аудит — у розділі 16.

Глибше: 10 · чому саме uvicorn і ASGI, 12 · пакування і lock-файли, 0 · розділ 21, вибір базового образу.

04Довідник інструкцій і налаштувань

Усі інструкції Dockerfile з тим, що про кожну корисно сказати на співбесіді.

ІнструкціяДля чогоНюанс, про який питають
FROM image AS nameБаза; AS іменує стадію для multi-stageПінь версію, а для продакшну ще й дайджест: python:3.12-slim@sha256:…
ARGЗмінна часу збірки (--build-arg)Не потрапляє в рантайм-середовище, але видно в docker history. Секрети сюди класти не можна. ARG до FROM видно лише в FROM.
ENVЗмінна оточення і для збірки, і для рантаймуВшивається в образ. Для конфігурації за замовчуванням підходить, для секретів — ні.
RUNВиконує команду і зберігає результат шаромКешується за текстом. Підтримує --mount=type=cache|secret|ssh|bind (BuildKit).
COPYКопіює файли з контексту або з іншої стадії (--from=builder)--chown=app:app, --chmod. Кешується за контрольними сумами файлів.
ADDЯк COPY, плюс розпаковує tar і завантажує URLЧерез «магію» за замовчуванням беруть COPY. ADD — лише для локального tar-архіву.
WORKDIRПоточна текаСтворює теку, якщо її немає. Краще за RUN cd, бо cd не переживає кінця RUN.
USERВід якого користувача виконувати наступні RUN і рантаймКраще числовий UID (10001): Kubernetes з runAsNonRoot перевіряє саме число.
EXPOSEДокументує портНічого не відкриває. docker run -P публікує всі EXPOSE на випадкові порти.
CMDКоманда / аргументи за замовчуваннямПерезаписується аргументами docker run image …. Exec-форма (JSON) замість shell-форми.
ENTRYPOINT«Виконуваний файл» контейнераCMD стає його аргументами. Патерн: ENTRYPOINT ["/entrypoint.sh"], який робить підготовку і закінчується exec "$@", щоб процес став PID 1.
HEALTHCHECKКоманда перевірки здоров'яВикористовують Docker, compose і Swarm. Kubernetes і Fly її ігнорують: у них свої probes і checks.
VOLUMEОголошує точку монтуванняСтворює анонімний volume при кожному запуску. У застосункових образах зазвичай не потрібен.
STOPSIGNALСигнал для docker stop (за замовчуванням SIGTERM)Корисний, якщо застосунок чекає на інший сигнал (наприклад, nginx — SIGQUIT).
LABELМетаданіorg.opencontainers.image.source зв'язує образ у GHCR з репозиторієм.
SHELLОболонка для shell-форми RUNSHELL ["/bin/bash", "-o", "pipefail", "-c"], щоб падіння в пайпі не ховалося.

CMD vs ENTRYPOINT: таблиця, яку просять намалювати

Dockerfiledocker run imgdocker run img alembic upgrade head
CMD ["uvicorn", …] (як у нас)uvicorn …alembic upgrade head — CMD замінено
ENTRYPOINT ["uvicorn"] + CMD ["app.main:app"]uvicorn app.main:appuvicorn alembic upgrade head — зламалося
ENTRYPOINT ["/entrypoint.sh"] + CMD [...]entrypoint.sh uvicorn …entrypoint.sh alembic … — скрипт робить exec "$@"

Саме тому в нас лише CMD: той самий образ запускається і як API, і як одноразова міграція (release_command), і в майбутньому як Celery-воркер — просто з іншою командою.

06Продакшн-Dockerfile: multi-stage, non-root, lock-файл

Як виглядав би наш Dockerfile після рев'ю. Кожна зміна пояснена нижче.

Dockerfile — покращена версія
# syntax=docker/dockerfile:1
ARG PYTHON_IMAGE=python:3.12-slim

# ---------- builder ----------
FROM ${PYTHON_IMAGE} AS builder
ENV PIP_DISABLE_PIP_VERSION_CHECK=1
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# lock-файл: точні версії й хеші (pip-compile / uv export)
COPY requirements.lock ./
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --require-hashes -r requirements.lock

# ---------- runtime ----------
FROM ${PYTHON_IMAGE} AS runtime
ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONPATH=/code \
    PATH="/opt/venv/bin:$PATH"

RUN useradd --uid 10001 --create-home --shell /usr/sbin/nologin app
WORKDIR /code

COPY --from=builder /opt/venv /opt/venv
COPY --chown=app:app app/ ./app/
COPY --chown=app:app alembic.ini ./

USER 10001
EXPOSE 8000

HEALTHCHECK --interval=15s --timeout=3s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2)"

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--proxy-headers", "--forwarded-allow-ips=*"]

Multi-stage з venvФінальний образ без pip-кешу і (за потреби) без компіляторів. Чесно: у нас усі залежності ставляться з готових wheel-ів, тож виграш у розмірі невеликий. Головне — чистота і готовність до пакета, який доведеться компілювати.

Сигнали і graceful shutdown

docker stop надсилає PID 1 сигнал SIGTERM, чекає 10 секунд (--time) і тоді надсилає SIGKILL. Uvicorn на SIGTERM перестає приймати нові з'єднання, дочікується поточних запитів і запускає lifespan-shutdown (закриває пул БД). Є три способи це зламати:

  1. Shell-форма CMD: PID 1 — /bin/sh, він не пересилає SIGTERM, і через 10 с процес отримує SIGKILL (exit 137).
  2. entrypoint.sh без exec: та сама проблема, скрипт лишається PID 1.
  3. Довгі запити (генерація маршруту OR-Tools) довші за grace period. На Fly це kill_timeout (за замовчуванням 5 с, сигнал kill_signal — SIGINT), у k8s — terminationGracePeriodSeconds. Довгу роботу краще винести у воркер.

PID 1 у Linux особливий: ядро не застосовує до нього дефолтні обробники сигналів. Якщо процес сам не поставив обробник SIGTERM, сигнал просто ігнорується. Uvicorn обробник ставить, а саморобний скрипт — часто ні.

10Роль Docker у нашому проєкті

Dockerfile — це контракт між кодом і Fly.io. Ось повний шлях від git push до трафіку.

  1. CI (.github/workflows/ci.yml): job test ставить залежності прямо на раннер (без Docker), ганяє ruff і pytest.
  2. Job deploy (лише push у main) викликає flyctl deploy --remote-only. --remote-only означає: збирати не на раннері, а на білдері Fly. Він ближче до реєстру і завжди amd64.
  3. Білдер читає Dockerfile (секція [build] порожня, тож використовується Dockerfile з кореня) і пушить образ у registry.fly.io.
  4. release_command запускає тимчасову машину з новим образом і виконує alembic upgrade head. Якщо міграція впала, деплой зупиняється.
  5. Машини оновлюються по одній (rolling). Кожна нова має пройти http_service.checks на /health з grace_period = 10s.
  6. Fly Proxy термінує TLS і пересилає HTTP на internal_port = 8000. Звідси --proxy-headers у CMD.

Особливості, про які варто сказати вголос

  • Stateless. На будь-якій платформі контейнер можуть убити й підняти деінде. Файли, сесії, кеш — у Postgres, Redis, S3, не на диску контейнера. Наш Excel-імпорт мусить обробляти файл у пам'яті або класти його в об'єктне сховище.
  • Порт. Cloud Run, Heroku і Render передають порт через $PORT. Наш --port 8000 захардкоджений: для Fly це ок, для Cloud Run треба або --port 8000 у конфігу сервісу, або shell-обгортку з ${PORT:-8000}.
  • Архітектура CPU. Graviton (AWS) і Ampere — це arm64: дешевше, але образ має бути multi-arch.
  • Міграції. На кожній платформі є свій механізм «одноразового запуску образу перед релізом»: Fly release_command, Heroku release phase, Cloud Run Job, ECS run-task, k8s Job / Helm hook.
  • Пул з'єднань. При горизонтальному масштабуванні машини × pool_size може перевищити max_connections Postgres. Звідси PgBouncer (туторіал 32, розділ 8).
  • Холодний старт. Розмір образу і час імпорту (import pandas, ortools — сотні мс) важать для scale-to-zero. У нас min_machines_running = 1, тож проблеми немає.
🎯
«Чому Fly.io, а не Kubernetes?»
«Один API-сервіс, маленька команда, без виділеного DevOps. Fly дає все, що нам потрібно від оркестратора: rolling-деплой, health checks, міграції через release_command, секрети, TLS. І все з того самого Dockerfile. Kubernetes додав би кластер, ingress, cert-manager і Helm, які треба підтримувати. Оскільки артефакт — стандартний OCI-образ, переїзд на Cloud Run, ECS чи k8s не вимагає змін у коді, лише нового рантайм-конфігу.»

12Стратегії релізу, міграції і rollback

Як нова версія образу замінює стару без простою і без поломки даних.

Міграції + rolling = обидві версії коду мають працювати з новою схемою

release_command накочує міграцію до того, як оновиться перша машина. Тобто старий код якийсь час працює з новою схемою. Перейменування колонки одним кроком зламає старі машини. Тому міграції пишуть за патерном expand → migrate → contract: додати нову колонку, писати в обидві, перенести дані, перемкнути читання, і лише в наступному релізі видалити стару. Деталі — туторіал 32, розділ 10.

Теги образів і rollback

  • :latest у продакшні — антипатерн. Тег змінний: дві машини можуть стягнути різні образи, і незрозуміло, що саме задеплоєно. Тегуй git SHA (api:3f2c1ab), а деплой роби за дайджестом.
  • Rollback = задеплоїти попередній образ, не перезбирати старий коміт: перезбірка без lock-файлу дасть інші залежності. На Fly: fly releases --image показує образи, fly deploy --image registry.fly.io/…:deployment-… повертає потрібний.
  • Міграції назад зазвичай не відкочують. Якщо схема сумісна з обома версіями (expand/contract), відкат коду безпечний і без alembic downgrade.

13Образи в CI/CD

Зараз Docker-збірка відбувається лише під час деплою з main. Зламаний Dockerfile виявиться, коли PR вже змерджено.

.github/workflows/ci.yml — job для PR: зібрати й просканувати образ
  image:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3

      - name: Build (без push)
        uses: docker/build-push-action@v6
        with:
          context: .
          load: true
          tags: delivery-api:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Smoke test
        run: |
          docker run -d --name api -p 8000:8000 -e JWT_SECRET=test delivery-api:${{ github.sha }}
          for i in $(seq 1 20); do curl -fsS localhost:8000/health && exit 0; sleep 1; done
          docker logs api; exit 1

      - name: Scan
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: delivery-api:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: "1"
  • cache-from/to: type=gha зберігає шари BuildKit у кеші GitHub Actions. Без цього кожна збірка на свіжому раннері починається з нуля.
  • Smoke test ловить те, що не ловить pytest: забутий COPY, неправильний CMD, падіння імпорту на старті.
  • Сканування (Trivy, Grype, Docker Scout) шукає CVE в ОС-пакетах і Python-залежностях образу.
  • Простіша альтернатива для нашого стеку: flyctl deploy --build-only у PR збирає образ на білдері Fly без релізу.
  • Реєстри: GHCR (зручно з GitHub), ECR/GAR/ACR (поруч зі своїм хмарним рантаймом), Docker Hub (ліміти на анонімні pull — у CI логінься або дзеркаль базові образи).
  • Supply chain: SBOM (docker buildx build --sbom=true або syft), provenance-атестації, підпис образу (cosign) і перевірка підпису на кластері.
  • Multi-arch: docker buildx build --platform linux/amd64,linux/arm64 --push збирає один тег-маніфест для обох архітектур.

1725 питань співбесіди

Спочатку відповідай уголос, потім відкривай.

01БазаЧим образ відрізняється від контейнера?

Образ — незмінний набір шарів файлової системи плюс метадані (CMD, ENV, порти), адресований тегом і дайджестом. Контейнер — запущений з образу процес з власними namespaces, cgroups і тонким записуваним шаром. З одного образу можна запустити багато контейнерів.

02БазаЧим контейнер відрізняється від віртуальної машини?

Контейнер ділить ядро з хостом і ізолюється namespaces і cgroups; VM має власне ядро поверх гіпервізора. Контейнери стартують за секунди і займають мегабайти, але ізоляція слабша. Firecracker і Kata поєднують обидва підходи: OCI-образ, але в microVM. Так працює Fly.io.

03БазаЯк працює кеш шарів і чому залежності копіюють до коду?

Кожна інструкція має ключ кешу: попередній шар + текст інструкції (+ контрольні суми файлів для COPY). Перший промах інвалідує всі наступні шари. Код змінюється часто, залежності — рідко, тому COPY pyproject.toml і pip install ідуть перед COPY app/. Тоді правка коду не перевстановлює 300 МБ пакетів.

04ПасткаEXPOSE відкриває порт?

Ні, це лише документація в метаданих образу. Публікує порт docker run -p, ports: у compose, internal_port у Fly або Service у k8s.

05БазаCMD vs ENTRYPOINT?

ENTRYPOINT — виконуваний файл, CMD — його аргументи за замовчуванням. Аргументи docker run img X замінюють CMD, але не ENTRYPOINT. Ми тримаємо лише CMD, щоб той самий образ запускати як alembic upgrade head. Якщо є entrypoint-скрипт, він має закінчуватися exec "$@".

06ПасткаЧому exec-форма CMD, а не shell-форма?

У shell-формі PID 1 — /bin/sh -c, який не пересилає SIGTERM дочірньому процесу. docker stop чекає таймаут і вбиває SIGKILL: запити обриваються, пул БД не закривається, exit 137. В exec-формі uvicorn — PID 1 і сам обробляє сигнал.

07ПасткаКонтейнер запущений, -p 8000:8000 є, а запит не проходить. Чому?

Найчастіше застосунок слухає 127.0.0.1 усередині контейнера, а проброшений трафік приходить на eth0. Треба --host 0.0.0.0. Далі перевіряю, що процес живий (docker logs), що порт правильний (docker port), і чи немає конфлікту на хості.

08БазаARG vs ENV?

ARG існує лише під час збірки і задається --build-arg. ENV вшивається в образ і доступна в рантаймі. Обидва видно в історії чи конфігу образу, тож секрети не передають ні тим, ні іншим. Для секретів збірки — RUN --mount=type=secret, для рантайму — secret store платформи.

09ПасткаСкопіював .env, а в наступному RUN видалив. Секрет в безпеці?

Ні. Шари адитивні: файл лежить у шарі від COPY, а наступний шар лише позначає його видаленим. docker save і розпакування tar дістають його. Виправлення: ротувати секрет, перезібрати без нього, додати .dockerignore.

10БазаЩо таке multi-stage build і що він дає Python-проєкту?

Кілька FROM у Dockerfile: у builder-стадії ставиш компілятори і збираєш venv або wheel-и, у фінальну копіюєш лише результат (COPY --from=builder). Менший образ, менше CVE, немає інструментів збірки в проді. Для нашого проєкту виграш помірний, бо всі пакети приходять готовими wheel-ами. Головна користь — чистота і готовність до пакетів, які компілюються.

11БазаЧому slim, а не alpine?

Alpine на musl libc. Більшість бінарних wheel-ів (manylinux) зібрані під glibc, тож для ortools, pandas, numpy на Alpine або немає wheel-ів, або є musllinux не для всіх версій. Тоді pip компілює з сирців: довго, треба toolchain, і образ стає більшим за slim. Плюс відмінності в DNS-резолвері і локалях.

12БазаVolume vs bind mount vs tmpfs?

Named volume керується Docker і переживає контейнер — для даних БД. Bind mount — тека хоста в контейнері, для hot-reload коду в dev. tmpfs — у пам'яті, для тимчасових файлів при --read-only. У продакшн-PaaS локальних дисків зазвичай немає або вони ефемерні: стан тримають у керованих сервісах.

13БазаЯк контейнери в compose знаходять один одного?

Compose створює user-defined bridge-мережу з вбудованим DNS: ім'я сервісу резолвиться в IP контейнера. Тому DATABASE_URL вказує на db:5432. localhost у контейнері — це він сам. До хоста з контейнера на Mac/Windows можна звернутися через host.docker.internal.

14Пасткаdepends_on гарантує, що Postgres готовий?

Без умови — ні, лише що контейнер стартував. Треба healthcheck у db (pg_isready) і condition: service_healthy. У продакшні на порядок старту не покладаються взагалі: застосунок ретраїть підключення, а платформа перезапускає його.

15БазаExit code 137 — що це і як розібратися?

128 + 9 = SIGKILL. Або OOM killer (перевищено ліміт cgroup — State.OOMKilled: true), або процес не завершився за stop timeout після SIGTERM. Для нашої 512 МБ машини підозрювані — pandas на великому Excel і OR-Tools на великій задачі. Дивлюся метрики пам'яті, profile-ю, збільшую VM або виношу задачу у воркер.

16ПросунутеЗбираю на MacBook M-серії, на сервері exec format error. Чому?

Образ зібраний під linux/arm64, а сервер amd64. Рішення: docker buildx build --platform linux/amd64 (через емуляцію QEMU, повільно), multi-arch маніфест для обох платформ або збирати на білдері з потрібною архітектурою. Ми робимо останнє через fly deploy --remote-only.

17БазаЯк ти передаєш конфіг і секрети в контейнер у проді?

Через змінні оточення в рантаймі, а образ однаковий для всіх середовищ (12-factor). Несекретне — в [env] у fly.toml під версіонуванням, секрети — fly secrets. У k8s — ConfigMap і Secret (краще з External Secrets / Vault), в AWS — Secrets Manager у task definition. pydantic-settings валідує їх на старті.

18ДеплойЯк у вас запускаються міграції і чому не в CMD?

release_command = "alembic upgrade head": Fly один раз запускає тимчасову машину з новим образом перед оновленням. Якби міграція була в CMD, її запускала б кожна машина при кожному рестарті — гонки між репліками, довший старт, і поламана міграція валила б усі машини. Якщо міграція впала, release зупиняється, і старі машини продовжують працювати.

19ДеплойЯк зробити деплой без простою?

Кілька реплік за балансувальником, rolling або blue-green з health checks, graceful shutdown (SIGTERM → дочекатися запитів), drain з'єднань на LB, і зворотно сумісні міграції (expand/contract), бо дві версії коду працюють одночасно. З однією машиною (наш min_machines_running = 1) rolling на мить лишає застосунок без реплік — для справжнього zero-downtime потрібно хоча б дві.

20ДеплойПорівняй Fly.io, Cloud Run, ECS Fargate і Kubernetes.

Fly — PaaS з microVM: мінімум конфігу, release_command, глобальні регіони. Cloud Run — serverless: scale-to-zero, оплата за запити, cold start, $PORT. ECS Fargate — керована оркестрація AWS без серверів, сильна інтеграція з VPC та IAM, але багато інфраструктурного коду. Kubernetes — максимум контролю й екосистеми, найвища складність. Вибір залежить від розміру команди, профілю трафіку і того, в якій хмарі вже живе компанія.

21БазаЧому :latest — погана ідея в продакшні?

Тег змінний: репліки можуть стягнути різні версії, не видно, що задеплоєно, rollback неоднозначний, а кеш IfNotPresent у k8s не підтягне оновлення. Тегуй git SHA і деплой за дайджестом.

22ПросунутеЯк зменшити розмір образу?

Slim або distroless база; multi-stage; --no-cache-dir або cache mount; чистити apt-списки в тому ж RUN; .dockerignore; не ставити dev-залежності (pytest, ruff) у прод; перевірити dive, що займає місце. У нашому випадку основну вагу дають pandas, ortools і numpy. Чесна оптимізація — питання, чи потрібен pandas лише заради читання Excel (openpyxl може впоратися сам).

23ПросунутеЩо таке PID 1 problem і навіщо --init / tini?

Ядро не застосовує дефолтні обробники сигналів до PID 1, і PID 1 відповідає за «прибирання» осиротілих процесів-зомбі. Застосунок, не розрахований на роль init, може ігнорувати SIGTERM і накопичувати зомбі. tini (docker run --init) стає PID 1, пересилає сигнали і збирає зомбі. Uvicorn без воркер-процесів впорається сам, але з --workers N чи підпроцесами tini корисний.

24ПросунутеОдин процес на контейнер — чому? Як запустити API і Celery?

Один процес — один набір логів, один health check, незалежне масштабування і перезапуск. Supervisord усередині ховає падіння дочірнього процесу від оркестратора. Тому API і воркер — окремі контейнери з того самого образу і різними командами: сервіси в compose, [processes] у Fly, два Deployment-и в k8s.

25ДеплойРозкажи, як влаштований деплой у твоєму проєкті і що б ти змінив.

Push у main → GitHub Actions: ruff і pytest → flyctl deploy --remote-only → білдер Fly збирає образ з Dockerfile (slim, залежності окремим шаром, exec-CMD uvicorn з proxy headers) → release_command накочує Alembic → rolling-оновлення machines з health check /health → Fly Proxy з TLS. Змінив би: lock-файл, збірку і скан образу в PR, non-root, .dockerignore, PYTHONUNBUFFERED, compose для локалки, другу машину для справжнього zero-downtime, і з появою Celery — окрему process group.

Що перевіряють: чи розумієш ти весь шлях від коміту до трафіку і чи бачиш слабкі місця свого сетапу.

Задача 1. Знайди всі проблеми
Dockerfile від колеги
FROM python:latest
ARG OPENAI_API_KEY
COPY . /code
WORKDIR /code
RUN apt-get update
RUN apt-get install -y gcc

Розв'язок
  1. python:latest: незапінена версія, а повний образ важить ~1 ГБ. Беремо python:3.12-slim (+ дайджест).
  2. ARG OPENAI_API_KEY: секрет видно в docker history. Він потрібен лише в рантаймі, тож передавати його треба через env.
  3. COPY . /code до встановлення залежностей: будь-яка правка коду перевстановлює все. До того ж копіює .env, .git, .venv.
  4. apt-get update окремим RUN: шар закешується і застаріє; списки apt не прибрано. gcc для наших wheel-ів не потрібен узагалі.
  5. Shell-форма CMD: SIGTERM не дійде до uvicorn.
  6. Немає --host 0.0.0.0: порт ззовні не відповідатиме.
  7. Немає --proxy-headers, root-користувач, немає .dockerignore.

Виправлена версія — Dockerfile з розділу 6.

Задача 2. Чому API не бачить базу?

Колега запускає docker compose up, у .env лежить DATABASE_URL=postgresql+asyncpg://postgres:postgres@localhost:5432/ai_delivery_planner, сервіс db працює. API падає з ConnectionRefusedError. Назви дві причини.

Розв'язок
  1. localhost усередині контейнера api — це сам api. Треба @db:5432: це ім'я сервісу, яке резолвить DNS compose. Тому в запропонованому compose.yaml DATABASE_URL перевизначено в environment, яке має пріоритет над env_file.
  2. Навіть з правильним хостом API може стартувати раніше, ніж Postgres прийматиме з'єднання. Потрібен healthcheck з pg_isready і depends_on: condition: service_healthy, а в ідеалі ще й ретраї в коді.
Задача 3. Деплой зламав старі машини

Реліз містить міграцію ALTER TABLE deliveries RENAME COLUMN address TO address_line і код, що читає address_line. Деплой rolling, міграція в release_command. Що бачать користувачі і як мало бути?

Розв'язок

Міграція виконується до оновлення машин. Поки rolling не завершився, старі машини звертаються до address, якої вже немає, і отримують 500. Якщо новий код не пройде health check, деплой зупиниться, і усі машини лишаться старими зі зламаною схемою.

Правильно — expand/contract у трьох релізах: (1) додати address_line, писати в обидві колонки, backfill; (2) читати з address_line; (3) видалити address. Кожен проміжний стан сумісний з попереднім і наступним кодом.

Задача 4. Exit 137 після імпорту Excel

Після завантаження Excel на 80 000 рядків машина на Fly перезапускається, у fly logs видно Out of memory: Killed process … (uvicorn). Що відбувається і які є варіанти?

Розв'язок
  • Процес перевищив 512 МБ VM, і ядро вбило його SIGKILL (137). pandas тримає весь DataFrame, а openpyxl ще й розгорнуте дерево XML — пам'ять у кілька разів більша за файл.
  • Швидко: fly scale memory 1024.
  • Правильно: читати потоково (openpyxl.load_workbook(read_only=True) + iter_rows), обробляти батчами, ліміт розміру файлу на вході. Важку обробку — у воркер з окремим лімітом пам'яті, щоб OOM не валив API.
  • Не забути: API вбитий посеред запиту, тож усі паралельні запити на цій машині теж обірвались. Ще одна причина тримати ≥ 2 машини.
Задача 5. Розклади збірку по кешу

В Dockerfile з розділу 6 послідовно відбуваються три коміти: (a) змінено app/api/routes/router.py; (b) додано пакет у requirements.lock; (c) оновлено ARG PYTHON_IMAGE на новий дайджест. Які кроки перезберуться в кожному випадку?

Розв'язок
  1. (a) Обидві стадії до COPY app/ беруться з кешу; перезбираються COPY app/, COPY alembic.ini і метадані. Секунди.
  2. (b) У builder: промах на COPY requirements.lock → pip install заново (але cache mount дасть уже завантажені wheel-и) → у runtime промах на COPY --from=builder і все вище. Runtime-кроки FROM, ENV і useradd лишаються в кеші.
  3. (c) Змінилась база обох стадій, тож перезбирається все. Так і має бути: оновлення бази — це патчі безпеки.
