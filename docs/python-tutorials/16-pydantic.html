00 Що таке Pydantic і навіщо він існує

Коротке визначення — і одразу зв'язок із тим, що вже сказано в іншому місці цього сайту.

Pydantic — бібліотека, яка дозволяє описувати форму даних звичайними Python-класами з анотаціями типів, а тоді реально перевіряє й приводить (coerce) вхідні дані до цих типів у рантаймі. Туторіал 4, розділ 6 вже показав головний факт, з якого все випливає: самі по собі type hints Python повністю ігнорує під час виконання — Pydantic і є тим двигуном, що перетворює анотації на реально працюючий контракт. Тут це порівняння не повторюємо, а йдемо далі — у сам API бібліотеки.

Чотири практичні задачі, під які Pydantic реально використовують:

  1. Валідація недовіреного зовнішнього вводу — тіла HTTP-запитів. Саме тому FastAPI побудований навколо Pydantic: кожна схема в app/schemas/ цього проєкту — це межа довіри між "що надіслав клієнт" і "що бачить код застосунку".
  2. Типізована конфігурація застосунку зі змінних середовища — BaseSettings (розділ 7).
  3. Серіалізація "не-JSON" Python-типів (UUID, datetime, Decimal) у JSON без жодного ручного коду.
  4. Парсинг довільних зовнішніх даних — відповіді стороннього API, конфіг-файл, повідомлення з черги — у надійні типізовані об'єкти замість "сирих" словників.

01 Базове визначення моделі

Модель — це клас, успадкований від BaseModel, де кожен атрибут з анотацією типу стає полем.

app/schemas/route.py
from pydantic import BaseModel

class OptimizeRequest(BaseModel):
    delivery_ids: list[uuid.UUID]
    vehicle_ids: list[uuid.UUID]
    depot_id: uuid.UUID
    return_to_depot: bool = True

delivery_ids, vehicle_ids і depot_id мають анотацію типу без значення за замовчуванням — тобто вони обов'язкові: якщо клієнт не надішле поле, Pydantic одразу відхилить весь об'єкт. return_to_depot має дефолт True — тобто необов'язкове, і якщо клієнт його не передасть, буде використано дефолтне значення.

Pydantic не лише перевіряє тип — він ще й приводить (coerce) вхідні дані до оголошеного типу там, де це має сенс. Рядок із самих цифр, переданий для поля типу int, буде приведений до числа:

coercion — не лише перевірка, а й приведення типу
class Foo(BaseModel):
    count: int

Foo(count="42").count
# 42 (int) — рядок з цифр приведено до int, а не відхилено як "невірний тип"
🎯
Строгий режим: якщо ця "магія" приведення типів небажана — наприклад, коли рядок і число мають лишатись явно різними речами — Pydantic дозволяє вимкнути її для окремого поля (Field(strict=True)) чи цілої моделі (model_config = ConfigDict(strict=True)), вимагаючи точного збігу типу без конвертації.

Якщо дані все ж не проходять валідацію (і ніяке приведення типу не рятує), Pydantic кидає ValidationError — одразу, ще на етапі створення об'єкта:

невалідні дані → ValidationError
from pydantic import ValidationError

try:
    OptimizeRequest(delivery_ids=["not-a-uuid"], vehicle_ids=[], depot_id="also-not-a-uuid")
except ValidationError as e:
    print(e.errors())

Що саме повертає e.errors() і як це пов'язано з 422-відповіддю FastAPI цього проєкту — детально в розділі 8.

02 Field(): обмеження та метадані

Коли самої анотації типу недостатньо — потрібні межі значень, дефолти складніші за літерал, чи документація для API.

кілька обмежень на невеликій моделі
from pydantic import BaseModel, Field

class DeliveryNote(BaseModel):
    text: str = Field(min_length=1, max_length=500, description="Нотатка водія до доставки")
    priority: int = Field(default=0, ge=0, le=5)
    tags: list[str] = Field(default_factory=list)
    external_id: str | None = Field(default=None, alias="externalId")

Обмеження довжини й меж: min_length/max_length для рядків і списків, gt/ge/lt/le (більше / більше-або-дорівнює / менше / менше-або-дорівнює) для чисел — priority вище обмежений діапазоном 0-5 саме через ge=0, le=5.

default проти default_factory. На відміну від дефолтних аргументів звичайних функцій, де def f(x=[]) — класична пастка (той самий список ділиться між усіма викликами), Pydantic-поля з мутабельним літералом на кшталт = [] насправді безпечні: бібліотека сама глибоко копіює дефолтне значення для кожного екземпляра моделі окремо. default_factory потрібен не заради безпеки, а для дефолтів, які треба обчислити в момент створення екземпляра (наприклад, default_factory=list для порожнього списку "з нуля" щоразу, чи default_factory=uuid.uuid4 для нового унікального ідентифікатора при кожному створенні) — а не одного разу на етапі визначення класу.

description — не просто коментар: FastAPI бере це значення й автоматично показує його прямо в згенерованій Swagger/OpenAPI-документації ендпоінта, без жодного додаткового коду з вашого боку.

alias дозволяє полю з іменем external_id у Python приймати (і, за потреби, віддавати) дані під іншим ключем JSON — тут "externalId", типовий випадок, коли клієнт (наприклад, фронтенд на camelCase) і бекенд (на snake_case) називають те саме поле по-різному. Чи можна прийняти обидва варіанти імені одночасно — залежить від опції populate_by_name в model_config (розділ 6).

03 Вкладені моделі

Поле моделі може саме бути іншою моделлю — Pydantic валідує вкладену структуру рекурсивно, за один виклик.

app/schemas/route.py — реальна вкладеність
class RouteRead(BaseModel):
    id: uuid.UUID
    depot_id: uuid.UUID
    status: str
    stops: list[RouteStopRead] = []

    model_config = ConfigDict(from_attributes=True)


class OptimizeResult(BaseModel):
    routes: list[RouteRead]
    unassigned_deliveries: list[DeliveryRef]
    skipped_not_geocoded: list[DeliveryRef]
    vehicles_without_driver: list[VehicleRef]

OptimizeResult містить список RouteRead, кожен з яких сам містить список RouteStopRead. Один виклик OptimizeResult(**raw_dict) обходить усе дерево цілком: кожен маршрут, кожну зупинку кожного маршруту — все перевіряється й приводиться до типів за один прохід, без жодного ручного циклу з вашого боку.

Найкорисніший наслідок вкладеності — точна адреса помилки. Якщо в п'ятій зупинці третього маршруту зіпсоване поле estimated_arrival, помилка вкаже саме на цей шлях у структурі (щось на кшталт routes.2.stops.4.estimated_arrival) — а не просто "десь у даних щось не так".

04 Кастомні валідатори: @field_validator і @model_validator

Коли обмежень з Field() недостатньо — потрібна довільна логіка перевірки чи трансформації.

⚠️
Цей проєкт поки не використовує кастомні валідатори — жоден реальний файл у app/schemas/ не містить field_validator чи model_validator. Приклади нижче — гіпотетичні, побудовані як природне розширення вже наявних реальних моделей, щоб показати, як це виглядало б, якби знадобилось.

@field_validator("ім'я_поля") перевіряє чи трансформує одне конкретне поле — декоратор застосовується до класметоду, який отримує вже приведене до типу значення цього поля й повертає (можливо, змінене) значення або кидає помилку:

гіпотетичне розширення VehicleRef
from pydantic import field_validator

class VehicleRef(BaseModel):
    id: uuid.UUID
    plate_number: str | None = None

    @field_validator("plate_number")
    @classmethod
    def normalize_plate(cls, v: str | None) -> str | None:
        return v.strip().upper() if v else v

@model_validator(mode="after") — інший інструмент для іншої задачі: він бачить уже повністю зібраний екземпляр моделі (self), а не одне поле окремо, тому це правильне місце для перевірок, які залежать від кількох полів одночасно:

гіпотетичне розширення OptimizeRequest
from pydantic import model_validator

class OptimizeRequest(BaseModel):
    delivery_ids: list[uuid.UUID]
    vehicle_ids: list[uuid.UUID]
    depot_id: uuid.UUID
    return_to_depot: bool = True

    @model_validator(mode="after")
    def check_not_both_empty(self):
        if not self.delivery_ids and not self.vehicle_ids:
            raise ValueError("Потрібен хоча б один delivery_id або vehicle_id")
        return self

Різниця в двох словах: field_validator дивиться на одне поле ізольовано; model_validator(mode="after") дивиться на модель цілком, коли потрібна узгодженість між кількома полями — саме таким є приклад вище: неможливо перевірити "хоча б один із двох списків непорожній", маючи доступ лише до одного з них.

05 Серіалізація: model_dump(), model_dump_json(), model_validate()

Туторіал 15, розділ 2 уже показав, що Pydantic автоматично серіалізує "не-JSON" типи (UUID, datetime, Decimal) — тут інша половина: сама механіка перетворення туди й назад.

модель ↔ dict ↔ JSON
route = RouteRead(id=some_id, depot_id=some_depot_id, status="pending",
                  return_to_depot=True, total_distance_km=12.4,
                  total_duration_minutes=35, created_at=now, updated_at=now)

route.model_dump()          # -> звичайний Python dict
route.model_dump_json()     # -> рядок JSON напряму, без проміжного dict

RouteRead.model_validate(route.model_dump())
# -> dict назад у типізований об'єкт RouteRead — той самий екземпляр за змістом

model_dump() перетворює модель на звичайний Python dict (зручно, коли дані передаються далі всередині застосунку, не назовні). Наступний рядок кроку — той-таки dict напряму, серіалізований у рядок JSON. model_validate(data) — зворотна дія: класметод, що парсить і валідує вже наявний словник (чи будь-що dict-подібне) у екземпляр моделі — альтернатива виклику конструктора з іменованими аргументами, особливо корисна, коли вхідні дані вже прийшли як dict звідкись іззовні (відповідь стороннього API, рядок із черги).

Практична деталь для часткових оновлень: model_dump(exclude_unset=True) серіалізує лише ті поля, які клієнт реально передав, а не ті, що тихо отримали дефолтне значення — саме те, що потрібно для PATCH-подібного ендпоінта з кількома необов'язковими полями, де важливо не затерти нулем чи дефолтом те, що клієнт узагалі не чіпав. У поточних схемах цього проєкту немає моделі з кількома незалежними необов'язковими полями, де це було б потрібно, — але саме такий сценарій і є типовим випадком застосування.

📎
v1 проти v2: якщо десь в інтернеті чи в старому коді трапляються .dict(), .json(), .parse_obj() — це назви Pydantic v1. У v2 їх перейменували на .model_dump(), .model_dump_json(), .model_validate() відповідно (старі назви лишились як застарілі alias'и для сумісності, але нові — стандарт).

06 model_config / ConfigDict

Об'єкт налаштувань поведінки моделі — на рівні класу, не окремого поля.

model_config — спеціальний атрибут класу, що замінив вкладений class Config: із Pydantic v1. Реальний приклад із цього проєкту:

app/schemas/route.py
class RouteRead(BaseModel):
    ...
    model_config = ConfigDict(from_attributes=True)

from_attributes=True (у Pydantic v1 ця сама опція звалась orm_mode) дозволяє будувати модель напряму з об'єкта з відповідними атрибутами — наприклад, із рядка SQLAlchemy ORM — а не лише зі словника. Саме тому RouteRead/RouteStopRead у цьому проєкті можна повернути прямо з обробника роутера, отримавши на вході ORM-рядок із бази: Pydantic сам прочитає потрібні атрибути з об'єкта, без ручної конвертації в dict.

populate_by_name працює в парі з alias із розділу 2 — вмикає можливість передати значення поля або під його оригінальним іменем у Python, або під alias'ом, замість жорсткої вимоги лише одного варіанту.

Ще один реальний приклад із цього проєкту — extra, налаштований у Settings (app/core/config.py):

app/core/config.py
model_config = SettingsConfigDict(env_file=".env", extra="ignore")

Це явно каже: якщо в .env опиниться змінна, якої немає серед оголошених полів Settings, вона просто ігнорується, а не спричиняє помилку валідації. Протилежний варіант — extra="forbid" — навпаки, кидає помилку на будь-яке неочікуване поле, корисно для суворої валідації зовнішнього API-вводу, де зайві поля можуть означати помилку клієнта. Ще одна поширена опція — str_strip_whitespace=True, яка автоматично обрізає пробіли з країв усіх рядкових полів моделі.

07 BaseSettings: типізована конфігурація застосунку

Архітектурна роль цього файлу вже введена в туторіалі 1, розділ 8 — тут детальніше про сам механізм.

app/core/config.py
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    APP_NAME: str = "AI Delivery Planner"
    DATABASE_URL: str = "postgresql+asyncpg://postgres:postgres@localhost:5432/ai_delivery_planner"
    ACCESS_TOKEN_EXPIRE_MINUTES: int = 30
    # ... і решта типізованих полів


@lru_cache
def get_settings() -> Settings:
    return Settings()

BaseSettings — спеціалізований підклас, що вміє читати значення полів не лише з переданих аргументів, а й зі змінних середовища (і з файлу, вказаного через env_file) за їхніми іменами — якщо змінної немає в оточенні, береться дефолт, оголошений у класі. Кожне поле лишається так само типізованим і валідованим, як у звичайному BaseModel: рядок середовища на кшталт ACCESS_TOKEN_EXPIRE_MINUTES=abc провалить валідацію ще на старті застосунку, а не десь посеред обробки випадкового запиту.

@lru_cache тут не другорядна деталь: він гарантує, що зчитування й валідація змінних середовища відбувається рівно один раз, при першому виклику get_settings() — результат кешується, і кожен наступний виклик (а через DI-залежності FastAPI таких викликів за час життя застосунку буде багато) повертає той самий уже готовий об'єкт, а не перечитує оточення заново.

📦
pydantic_settings — окремий пакет, відділений від основного pydantic саме з появою Pydantic v2. Якщо у проєкті встановлено лише pip install pydantic, BaseSettings звідти імпортувати не вийде — потрібна саме pydantic-settings.

08 Помилки валідації: що насправді бачить клієнт API

Пряме продовження прикладу з розділу 1 — тепер із поглядом на структуру помилки й на те, що з нею робить FastAPI.

структура ValidationError
try:
    OptimizeRequest(delivery_ids=[], vehicle_ids=[], depot_id="not-a-uuid")
except ValidationError as e:
    print(e.errors())

# [{'type': 'uuid_parsing', 'loc': ('depot_id',),
#   'msg': 'Input should be a valid UUID, ...', 'input': 'not-a-uuid', ...}]

e.errors() повертає список словників — по одному на кожне невалідне поле (а не лише перше знайдене) — з ключами type (машинно-читаний код помилки), loc (шлях до поля, включно з вкладеністю — див. розділ 3), msg (людське пояснення) і input (те значення, яке саме провалило перевірку).

Це не просто внутрішня деталь Pydantic — це буквально те, що бачить клієнт API цього проєкту. FastAPI ловить ValidationError, кинуту Pydantic при парсингу тіла запиту проти схеми ендпоінта, і автоматично повертає HTTP 422 з тілом, побудованим із цих самих словників, під ключем "detail" — без жодного кастомного обробника помилок з боку коду застосунку:

приблизне тіло 422-відповіді
{
  "detail": [
    {"type": "uuid_parsing", "loc": ["body", "depot_id"], "msg": "...", "input": "not-a-uuid"}
  ]
}

Префікс "body" у loc тут додає вже сам FastAPI (він показує, з якої частини запиту прийшло значення — тіло, query-параметр чи шлях), поверх того, що Pydantic сам генерує для структури всередині цього тіла.

09 Аналоги: коли Pydantic, а коли інше

Pydantic — не єдиний спосіб описати форму даних у Python, і не єдина мова, де ця ідея взагалі існує.

БібліотекаЕкосистемаКлючова відмінність
dataclasses Python, стандартна бібліотека Лише структура — жодної рантайм-валідації "з коробки"
attrs Python Схоже на dataclasses, гнучкіше налаштування, але валідація так само не вбудована за замовчуванням
marshmallow Python Старша бібліотека; схема описується окремо від класу даних, а не разом з ним
cerberus Python Валідація через словники-схеми, без класів узагалі
Zod TypeScript / JS Найближчий міжмовний аналог — schema-first рантайм-валідація для мови, чиї статичні типи так само стираються під час виконання; докладніше — JS Doc, туторіал 13

Практичне правило: тягнутись саме до Pydantic варто там, де форма й достовірність даних не повністю під вашим контролем — зовнішній ввід, конфігурація середовища, відповідь стороннього сервісу. Коли дані вже гарантовано "свої" й довірені — внутрішній контейнер для передачі значень між функціями одного модуля — простий dataclass чи attrs-клас зазвичай виграє за швидкістю й прозорістю, без накладних витрат рантайм-валідації, яка там нічого корисного не додає.

10 Підсумок

Головне з цього туторіалу:

  • Pydantic перетворює анотації типів, які Python сам ігнорує, на реально працюючий рантайм-контракт — з валідацією і приведенням типів.
  • Field() додає обмеження й метадані понад голий тип; @field_validator/@model_validator — довільну логіку, коли обмежень недостатньо.
  • model_dump()/model_dump_json()/model_validate() — три напрями конвертації між моделлю, dict і JSON.
  • model_config/ConfigDict налаштовує поведінку моделі цілком — від from_attributes (побудова з ORM-об'єкта) до extra (що робити із зайвими полями).
  • BaseSettings застосовує ту саму ідею до конфігурації застосунку зі змінних середовища — з кешуванням через @lru_cache.
  • У цьому проєкті Pydantic — це app/schemas/ (кожен вхід/вихід API) і app/core/config.py (уся конфігурація), а помилки валідації напряму стають 422-відповіддю клієнту без жодного додаткового коду.
