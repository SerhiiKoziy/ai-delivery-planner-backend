Частина I · Чотири стовпи ООП

1 Інкапсуляція — без "справжнього" private

Перше, що спантеличує розробників з мов із жорсткими модифікаторами доступу (Java private, TS #field).

python
class Account:
    def __init__(self, balance):
        self._balance = balance     # "protected" — ЛИШЕ домовленість, ніщо не блокує доступ
        self.__secret = "x"          # "приватне" — насправді ІМ'Я ПЕРЕЙМЕНОВАНЕ компілятором

a = Account(100)
a._balance          # 100 -- працює, Python нічого не забороняє
a.__secret           # AttributeError!
a._Account__secret    # "x" -- але ось так — працює!

Один підкреслений (_balance) — лише домовленість "не чіпай ззовні", яку Python ніяк не забезпечує технічно. Два підкреслені (__secret) — спрацьовує name mangling: компілятор перейменовує атрибут на _ClassName__secret, головна мета — уникнути випадкового конфлікту імен у підкласах, не справжня безпека доступу — атрибут завжди можна дістати за повним перейменованим ім'ям.

💼
Каверзне питання "Чи є в Python справжня інкапсуляція?" — правильна відповідь: технічно немає жодного механізму, що робить атрибут недосяжним ззовні (на відміну від Java private). Python покладається на дисципліну спільноти ("ми всі дорослі люди" — цитата з офіційної документації) і домовленості (одне підкреслення = "не чіпай"), а не на примусовий захист компілятором.

2 Абстракція — два різні відповіді Python

abc.ABC — номінативна
class Shape(ABC): @abstractmethod def area(self): ... Shape() # TypeError одразу
typing.Protocol — структурна
class HasArea(Protocol): def area(self) -> float: ... # жодного успадкування не потрібно

abc.ABC — класична, "номінативна" абстракція: підклас явно успадковує абстрактний базовий клас і зобов'язаний реалізувати всі @abstractmethod, інакше інстанціювання одразу впаде з TypeError — перевірка в рантаймі. typing.Protocol (туторіал 6) — структурна абстракція: клас підходить під протокол просто маючи потрібні методи, без жодного явного успадкування — перевірка типово статична (mypy/pyright), не в рантаймі.

3 Успадкування — коротко

Повністю розібрано в туторіалі 7 (super()) та туторіалі 6 (MRO, C3-лінеаризація). Тут — лише нагадування ролі в чотирьох стовпах: дозволяє підкласу перевикористати й розширити поведінку батьківського класу, не переписуючи її.

4 Поліморфізм — по-пайтонівськи через duck typing

У статично типізованих мовах поліморфізм зазвичай вимагає спільного базового класу чи інтерфейсу. У Python (туторіал 5, розділ 4) досить, щоб об'єкт мав потрібний метод — for item in container: працює однаково для list, tuple, генератора чи власного класу з __iter__, незалежно від того, чи є між ними хоч якийсь спільний предок.

Частина II · SOLID

S5 Single Responsibility Principle

"У класу має бути лише одна причина для зміни" (Роберт Мартін).

✅
Уже застосовано в архітектурі проєкту (туторіал 1): роутер відповідає лише за HTTP, сервіс — лише за бізнес-логіку, репозиторій — лише за SQL. Зміна формату відповіді API не вимагає чіпати жодного рядка в репозиторії; зміна схеми БД не вимагає чіпати роутер. Кожен шар має рівно одну причину змінитись.
❌ Порушення
class DeliveryService: def create(self, data): # валідація + геокодування # + SQL-запит + відправка email # + форматування HTTP-відповіді
✅ Дотримано (як у проєкті)
class DeliveryService: def __init__(self, repo, geocoder, ...): ... async def create(self, payload): # оркеструє, не РОБИТЬ усе сам

O6 Open/Closed Principle

"Відкритий для розширення, закритий для модифікації" (Бертран Мейєр).

app/core/plans.py — реальний код з проєкту
PLAN_ROUTE_LIMITS: dict[SubscriptionPlan, int | None] = {
    SubscriptionPlan.TRIAL: 50,
    SubscriptionPlan.FREE: 5,
    SubscriptionPlan.SMALL: None,
    # додати новий тарифний план -- ДОДАТИ рядок у словник,
    # жодна функція, що ЧИТАЄ цей словник, не змінюється
}

Новий тарифний план додається без зміни жодної функції, що перевіряє квоту (require_route_quota) — вона й далі просто читає словник за ключем. Це і є "закритий для модифікації" (наявний код перевірки не чіпається) + "відкритий для розширення" (новий план — це нові дані, не новий код). Порушенням був би if plan == "trial": ... elif plan == "free": ... ланцюжок, що доводилось би правити на кожен новий план.

L7 Liskov Substitution Principle

"Об'єкти підкласу мають бути взаємозамінні з об'єктами базового класу, не ламаючи коректність програми" (Барбара Лісков).

класичний приклад порушення (не з цього проєкту, канонічний)
class Rectangle:
    def set_width(self, w): self.width = w
    def set_height(self, h): self.height = h

class Square(Rectangle):           # математично "квадрат Є прямокутник" -- та ООП тут зраджує
    def set_width(self, w):
        self.width = self.height = w   # порушує ОЧІКУВАННЯ коду, що працює з Rectangle
    def set_height(self, h):
        self.width = self.height = h

def resize(rect: Rectangle):
    rect.set_width(5)
    rect.set_height(10)
    assert rect.width * rect.height == 50   # ПАДАЄ для Square -- підклас непередбачувано зламав контракт
✅
Дотримано в проєкті: TenantScopedRepository (туторіал 1) успадковує BaseRepository й додає поведінку (org-scoping), не порушуючи жодного очікування базового контракту — усюди, де очікується BaseRepository з методами get/create/ list, TenantScopedRepository працює коректно, з тими самими сигнатурами й тим самим сенсом методів.

I8 Interface Segregation Principle

"Жоден клієнт не повинен залежати від методів, якими він не користується."

app/core/dependencies.py — реальний код з проєкту
# НЕ один "мега-провайдер усього" -- окремі, вузькі DI-функції на кожну потребу:
def get_delivery_repository(db=Depends(get_db), current_user=Depends(get_current_user)): ...
def get_vehicle_repository(db=Depends(get_db), current_user=Depends(get_current_user)): ...
def get_route_repository(db=Depends(get_db), current_user=Depends(get_current_user)): ...

Ендпоінт, якому потрібен лише VehicleRepository, оголошує залежність саме на нього — не отримує "про всяк випадок" доступ до DeliveryRepository чи RouteRepository. Кожна DI-функція — вузький, сфокусований "інтерфейс", а не один величезний об'єкт-контейнер із доступом до всього одразу.

❌
Порушення виглядало б так: один get_all_repositories(), що повертає об'єкт з усіма репозиторіями проєкту одразу — кожен ендпоінт технічно отримував би доступ до всього, навіть якщо реально використовує один метод одного репозиторію, ускладнюючи і тестування (треба мокати "все"), і розуміння реальних залежностей коду.

D9 Dependency Inversion Principle

"Модулі високого рівня не повинні залежати від модулів низького рівня — обидва повинні залежати від абстракцій." Найважливіший принцип для розуміння всієї архітектури проєкту.

app/core/dependencies.py — реальний код з проєкту
def get_delivery_service(
    repo: DeliveryRepository = Depends(get_delivery_repository),
    org_repo: OrganizationRepository = Depends(get_organization_repository),
    organization: Organization = Depends(get_current_organization),
) -> DeliveryService:
    return DeliveryService(repo, GoogleGeocodingClient(), org_repo, organization)
    #                      ^^^^^^^^^^^^^^^^^^^^^^^^^ -- ВСТАВЛЯЄТЬСЯ ззовні, не створюється ВСЕРЕДИНІ DeliveryService

DeliveryService (модуль високого рівня — бізнес-логіка) не знає, як саме влаштований геокодер (модуль низького рівня — конкретний HTTP-клієнт до Google Maps) — отримує його готовим ззовні, через конструктор. Це і є "інверсія залежності": природний напрямок залежності був би "сервіс залежить від конкретного класу geocoding-клієнта", DI розвертає це на "обидва залежать від форми методу geocode(address)" (Adapter з туторіалу 14 + Protocol з туторіалу 6).

Аналогія з фронтендом
Саме той самий принцип, на якому стоїть Angular DI чи React Context: компонент оголошує "мені потрібен сервіс із такою формою", а хто саме його створює й з чим — компонент не знає і не повинен знати (детально — туторіал 1, розділ 9).
Частина III · Практика й пастки

10 Міксини (Mixins) — успадкування заради здатності, не ієрархії

python
class TimestampMixin:
    """Додає created_at/updated_at -- НЕ призначений існувати сам по собі."""
    created_at: datetime
    updated_at: datetime
    def touch(self):
        self.updated_at = datetime.now(UTC)

class SoftDeleteMixin:
    """Додає позначку видалення БЕЗ реального DELETE-запиту."""
    deleted_at: datetime | None = None
    def soft_delete(self):
        self.deleted_at = datetime.now(UTC)

class Delivery(Base, TimestampMixin, SoftDeleteMixin):
    # успадковує ДВІ незалежні "здатності" одночасно, а не єдину лінію предків
    ...

Міксин — клас, що не призначений існувати самостійно (лише в комбінації через множинне успадкування) і додає одну конкретну, вузьку "здатність" (timestamp-поля, серіалізацію, м'яке видалення). Це проміжна точка між "чистою композицією" й "класичною ієрархією успадкування" (туторіал 6, розділ 12) — множинне успадкування, але кожен предок абсолютно незалежний від інших, без спільної "лінії" походження.

11 God Object — коли SRP порушено масштабно

⚠️
God Object (антипатерн) — один клас, що знає й робить занадто багато: валідація, БД-доступ, HTTP, бізнес-правила, форматування — усе в одному місці. Пряме, масштабоване порушення SRP (розділ 5). Симптоми: клас на тисячі рядків, зміна в одній "темі" (наприклад, форматі email) регулярно ламає щось геть не пов'язане (наприклад, розрахунок маршруту), бо все живе в тому самому файлі й неявно пов'язане спільним станом.

Шарувата архітектура цього проєкту (туторіал 1) — структурний захист саме від God Object: фізично складно "накопичити все в одному місці", коли API, логіка й доступ до даних живуть у трьох різних пакетах з чіткими межами.

12 Коли SOLID шкодить — передчасна абстракція

⚠️
Той самий висновок, що й у туторіалі 14 (розділ 6, "коли патерн — зайва складність"): DIP заради самого DIP — інтерфейс/абстракція для класу, у якого й близько не передбачається друга реалізація — додає непряму складність без жодної реальної вигоди. Якщо GoogleGeocodingClient ніколи не планується міняти на інший сервіс, обгортання його в зайвий абстрактний інтерфейс "про всяк випадок" — це вартість сьогодні заради гіпотетичної гнучкості, яка може ніколи не знадобитись.

SOLID — набір евристик, що підказують, де варто закласти гнучкість, а не обов'язкові правила, які треба застосувати скрізь одразу. Найкращий сигнал "тут потрібна абстракція" — коли друга реалізація вже реально з'явилась чи ось-ось з'явиться, а не абстрактне "а раптом колись".

13 Каверзні питання співбесіди

ПасткаЧи існує в Python справжня інкапсуляція (private-атрибути)?
Ні — _attr це лише домовленість, __attr технічно доступний через name mangling (obj._ClassName__attr). Python покладається на дисципліну спільноти, а не на примусовий захист компілятором.
БазаЧим abc.ABC відрізняється від typing.Protocol для абстракції?
ABC — номінативна: явне успадкування, перевірка при інстанціюванні в рантаймі. Protocol — структурна: підходить будь-який клас з потрібними методами, без явного успадкування, перевірка типово статична.
ПасткаКласичний приклад Rectangle/Square — у чому саме порушення LSP?
Square, успадковуючи Rectangle, змінює поведінку set_width/set_height так, що код, написаний під контракт Rectangle (незалежна зміна ширини й висоти), ламається для Square — підклас не є прозоро взаємозамінним із базовим класом.
БазаНаведіть приклад порушення Open/Closed Principle.
Довгий ланцюжок if plan == "trial": ... elif plan == "free": ..., який доводиться редагувати щоразу, коли з'являється новий тарифний план — код, який має "закриватись" від змін, натомість змінюється щоразу разом із даними.
ПасткаЧому Dependency Inversion — не те саме, що Dependency Injection?
Dependency Inversion — принцип ("залежати від абстракцій, не від конкретики"). Dependency Injection — техніка, ЯК цього досягти на практиці (передавати залежності ззовні через конструктор/параметр, а не створювати їх усередині). DI — один із найпоширеніших способів реалізувати DIP, але не єдиний, і це не синоніми.
БазаЩо таке міксин і чим він відрізняється від звичайного базового класу?
Міксин не призначений існувати самостійно — додає одну вузьку, незалежну "здатність" через множинне успадкування. Звичайний базовий клас зазвичай описує "є" (is-a) відношення й може існувати сам по собі як повноцінний тип.
ПасткаКоли застосування SOLID стає шкідливим?
Коли абстракція вводиться "про всяк випадок", без реальної другої реалізації на горизонті — додає непряму складність (зайвий рівень індирекції, складніше читати код) без жодної фактичної вигоди в конкретний момент.
