00 Що таке PostgreSQL, і як цей проєкт з ним працює

PostgreSQL — відкрита, ACID-сумісна реляційна СУБД (чому саме реляційна модель обрана для цього проєкту — розібрано в туторіалі 17, тут це не повторюємо). Цей розділ — про те, як конкретно цей бекенд до неї підключається.

app/db/session.py
engine = create_async_engine(
    settings.DATABASE_URL,
    echo=settings.DEBUG,
    future=True,
    connect_args={"statement_cache_size": 0},
)

AsyncSessionLocal = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,
)

Драйвер — asyncpg (видно з префіксу postgresql+asyncpg:// у DATABASE_URL): нативна реалізація протоколу Postgres на чистому Python + Cython, помітно швидша за psycopg2 у типових бенчмарках, і що важливіше для цього проєкту — асинхронна за дизайном, тобто природно поєднується з async/await замість того, щоб виконувати блокуючий I/O в окремому потоці.

connect_args={"statement_cache_size": 0} — це не дрібниця "про всяк випадок", а конкретний фікс під конкретну проблему: asyncpg за замовчуванням кешує підготовлені запити (prepared statements) на рівні одного фізичного з'єднання. Якщо між застосунком і Postgres стоїть пулер з'єднань у transaction-режимі (наприклад, PgBouncer — типова конфігурація керованого Postgres, зокрема на хмарних платформах), одне й те саме логічне "з'єднання" застосунку може між транзакціями фізично потрапляти на різні серверні з'єднання пулера — а підготовлений запит, закешований для одного фізичного з'єднання, на іншому просто не існує. Вимкнення кешу підготовлених запитів — стандартний, задокументований спосіб зробити asyncpg сумісним із таким пулером ціною невеликого падіння продуктивності на повторюваних запитах.

Розмір пулу з'єднань SQLAlchemy тут явно не налаштований — рушій працює на дефолтах (pool_size=5, max_overflow=10). Тримайте цю цифру в голові — вона повернеться в розділі 8, коли йтиметься про пам'ять під навантаженням.

01 MVCC і "знімки" (snapshots)

Фундамент усього, що далі: як Postgres дозволяє читачам і писачам працювати з тими самими рядками одночасно, не блокуючи одне одного.

MVCC (Multi-Version Concurrency Control) — підхід, за якого база не тримає для кожного рядка рівно одну версію, яку треба блокувати на час читання чи запису, а дозволяє співіснувати кільком версіям одного логічного рядка одночасно. Кожна транзакція працює зі своїм узгодженим "знімком" даних, а не з "живою", постійно змінюваною таблицею.

Знімок (snapshot) — це, по суті, список: які версії рядків вважалися закомміченими станом на певний момент. Усі читання в межах транзакції звіряються саме з цим списком, а не з тим, що відбувається в базі "прямо зараз".

Наскільки довго живе один знімок, залежить від рівня ізоляції транзакції:

Рівень ізоляціїКоли береться знімокНаслідок
Read Committed (дефолт Postgres) Новий знімок на кожен окремий запит у транзакції Два послідовні SELECT в одній транзакції можуть побачити різні дані, якщо між ними щось закомітилось
Repeatable Read / Serializable Один знімок на всю транзакцію Кожне читання в межах транзакції бачить один і той самий, "заморожений" стан бази
🎯
Цей проєкт: рівень ізоляції ніде явно не задається, тож діє дефолт Postgres — Read Committed. Практично це означає: якщо один HTTP-запит робить кілька SELECT-ів поспіль через один AsyncSession, і між ними хтось інший встиг закомітити зміну — другий SELECT це вже побачить. Для більшості CRUD-ендпоінтів це прийнятно й навіть очікувано; для логіки, якій критично бачити один узгоджений стан протягом усієї транзакції, довелося б свідомо підвищувати рівень ізоляції.

02 Що насправді відбувається при UPDATE: приховані системні колонки

Ключовий факт, з якого випливає все інше в цьому туторіалі: Postgres ніколи не змінює рядок "на місці".

Коли ви робите UPDATE, Postgres не перезаписує існуючі байти рядка — він створює цілком нову фізичну версію рядка (новий heap tuple) і позначає стару версію як застарілу. Обидві версії фізично існують у файлі таблиці, доки щось (розділ 4) не прибере стару.

Кожен рядок у Postgres має декілька прихованих системних колонок, які ви ніколи не побачите в SELECT *, але можете запитати явно:

КолонкаЩо зберігає
xminID транзакції, яка створила цю версію рядка
xmaxID транзакції, яка витіснила/видалила цю версію — 0, якщо версія й досі актуальна
ctidФізичне розташування версії (сторінка + зміщення) — змінюється при кожному UPDATE, бо нова версія — це фізично інший тапл
cmin / cmaxНомер команди всередині поточної транзакції, яка створила/видалила версію — актуально, коли одна транзакція виконує кілька операторів
⚠️
Пастка з ctid: оскільки ctid змінюється на кожен UPDATE, тримати його як "стабільний ідентифікатор рядка" між запитами (наприклад, закешувати й повторно використати пізніше) — помилка: рядок могли оновити, і той самий ctid уже вказує або на іншу версію, або взагалі в порожнечу.

Продемонструємо на реальній таблиці цього проєкту — route_stops, чий status (pending → en_route → completed) оновлюється через route_stop_repository.update(stop_id, status=...) (app/api/routes/router.py):

до UPDATE
SELECT xmin, xmax, ctid, status
FROM route_stops
WHERE id = '3f2e...';
--  xmin | xmax | ctid   | status
--  100  | 0    | (0,7)  | pending
UPDATE, потім знову той самий SELECT
UPDATE route_stops SET status = 'en_route' WHERE id = '3f2e...';

--  xmin | xmax | ctid   | status
--  105  | 0    | (0,19) | en_route
-- ctid змінився — це фізично НОВИЙ тапл, а не той самий рядок "на місці"

03 Читання під час запису: MVCC у дії

Пряма відповідь на питання "що відбувається, коли хтось читає рядок, поки інший його пише".

Завдяки механізму знімків із розділу 1, читач, чий знімок було взято до моменту комміту паралельного писача, просто продовжує бачити стару версію рядка — ту, чий xmax (транзакція писача) із точки зору знімка читача ще не вважається закомміченою. Читач ніколи не чекає писача. Писач ніколи не чекає читача.

Єдиний випадок, коли справді виникає блокування, — коли дві транзакції одночасно намагаються UPDATE/DELETE той самий рядок: тоді рядковий лок змушує другого писача чекати, поки перший закомітить або відкотиться.

Аналогія з фронтендом
Це трохи схоже на те, як компонент, що вже отримав дані через props на момент рендеру, продовжує показувати їх, поки батьківський стан десь вище оновлюється — він не "блокується", чекаючи оновлення, а просто отримає нову версію даних наступним рендером. MVCC робить те саме на рівні бази: читач працює зі своїм "знімком пропсів", а не з живим станом, що змінюється просто зараз.

Конкретно для цього проєкту: дашборд-запит, що рахує зупинки з RouteStop.status != "completed" (app/services/dashboard/service.py), який виконується рівно в той момент, коли водій через API оновлює статус зовсім іншої зупинки, ніяк не блокується цим паралельним записом. MVCC робить конкурентні читання й записи на активній таблиці дешевими за замовчуванням, без додаткових зусиль з боку коду застосунку.

04 VACUUM і autovacuum: прибирання мертвих версій

Розділ 2 показав: UPDATE/DELETE лишають старі версії рядків фізично на місці. Хтось має їх прибирати.

Старі версії, яких уже не бачить жоден активний знімок, називають мертвими таплами (dead tuples). Вони займають місце на диску й можуть уповільнювати послідовні скани та роботу індексів, доки лишаються не прибраними.

VACUUM сканує таблицю, знаходить мертві таплі, недоступні жодному активному знімку, і позначає це місце як придатне для повторного використання під майбутні INSERT/UPDATE. Важливий нюанс: звичайний VACUUM не зменшує розмір файлу на диску — він лише робить простір усередині файлу перевикористовуваним. Окрема, значно дорожча команда — VACUUM FULL — справді стискає файл, але вимагає ексклюзивного блокування таблиці на весь час роботи.

autovacuum — фоновий демон, що запускає VACUUM автоматично, щойно оцінена частка мертвих таплів у таблиці перевищує поріг (концептуально: частка від розміру таблиці плюс невелика фіксована константа — конкретні дефолтні числа запам'ятовувати не обов'язково, важливо розуміти сам принцип "поріг залежить від розміру таблиці, і все відбувається само"). На справному Postgres-інстансі ручний VACUUM зазвичай узагалі не потрібен.

🎯
Пов'язано з проєктом: route_stops.status, що перемикається pending → en_route → completed потенційно багато разів на кожен маршрут, помножене на багато маршрутів щодня, — саме той тип часто оновлюваної колонки, що стабільно генерує мертві таплі. А дашбордовий фільтр status != 'completed' — саме той тип запиту, продуктивність якого першим постраждає, якщо autovacuum колись почне відставати (роздування таблиці й будь-якого індексу, що покриває status). На малих/керованих інстансах Postgres під стійким write-навантаженням відставання autovacuum — реальна, доволі поширена production проблема (відстежується через pg_stat_user_tables.n_dead_tup), хоча на поточному масштабі цього проєкту про це ще не доводилось думати.

05 Пікові навантаження на Python-стороні: де росте пам'ять і чому вона не одразу падає

Механізм алокатора вже розібраний у туторіалі 15, розділ 7 — тут лише DB-специфічний шар поверх нього.

Коротко нагадаємо факт із туторіалу 15 (не переказуючи механізм заново): RSS процесу типово не падає одразу після піку — арени pymalloc повертаються ОС лише повністю порожніми, і той розділ уже прив'язує це саме до 512 МБ Fly.io-машини цього проєкту та ендпоінта POST /routes/optimize.

Новий, специфічний для роботи з БД шар — identity map сесії SQLAlchemy. Кожен ORM-об'єкт, завантажений у межах одного AsyncSession, лишається живим і відстежуваним на весь час життя цієї сесії — саме так SQLAlchemy гарантує, що повторний запит того самого рядка в тій самій сесії поверне той самий Python-об'єкт, і знає, що саме треба флашити при коміті. Наслідок: один запит, що завантажує багато рядків (наприклад, дашбордовий запит, який тягне всі маршрути й зупинки організації), тримає їх усі в пам'яті аж до закриття сесії наприкінці запиту — роблячи свій внесок у той самий патерн "пік, потім плато", чий механізм на рівні алокатора вже описаний у туторіалі 15.

Окрема дрібна, але реальна деталь цього проєкту: expire_on_commit=False у session.py. Зазвичай після коміту SQLAlchemy "просрочує" всі завантажені об'єкти, щоб їхні атрибути перечитувались із бази при наступному зверненні. З вимкненою опцією об'єкти після коміту зберігають уже завантажені значення атрибутів у пам'яті без автоматичного перезапиту — виграш у кількості запитів ціною невеликого ризику застарілих значень і трохи довшого утримання даних у пам'яті.

06 Ручний виклик gc.collect(): коли це має сенс

Механіка трьох поколінь GC вже описана в туторіалі 15, розділ 3 — тут лише практичне питання "коли викликати самому".

Ручний виклик gc.collect() має сенс одразу після відомого сплеску роботи, що щедро породжує циклічні посилання — для цього проєкту це сам OR-Tools solve (services/route_optimizer/) або імпорт великого CSV/Excel через pandas (services/importers/). Проактивний виклик прибирає циклічне сміття раніше, ніж до нього дійшов би черговий, менш частий прохід покоління 2 сам по собі — це важливо, якщо ви хочете зняти тиск на пам'ять до наступного запиту, а не колись пізніше.

⚠️
Важливе застереження, що прямо стосується розділу 5 й туторіалу 15, розділ 7: gc.collect() прибирає лише Python-об'єкти (циклічне сміття) — він не зменшує RSS процесу назад, бо арени pymalloc все одно повертаються ОС лише порожніми повністю. Це інструмент "прибрати циклічне сміття раніше", а не "зменшити видиме споживання пам'яті процесом" — плутати ці дві речі — поширена помилка.

07 Перезапуск воркера після N запитів: боротьба з витоком пам'яті

Найпрактичніший розділ туторіалу — і конкретний розрив між "як це зазвичай роблять" і "як це влаштовано в цьому проєкті просто зараз".

Стандартний прийом у продакшн Python-сервісах — gunicorn --max-requests N --max-requests-jitter J. Кожен воркер-процес gunicorn добровільно й грайсфул завершується, обробивши приблизно N запитів; jitter (±J) рандомізує це число, щоб при кількох воркерах вони не перезапускались усі одночасно, уникаючи короткочасного провалу пропускної здатності. Майстер-процес gunicorn одразу піднімає свіжий воркер натомість.

Чому це працює як засіб проти витоку пам'яті, навіть якщо реальну причину витоку так і не знайшли: цей прийом обходить усю проблему фрагментації арен pymalloc із розділу 5 не намагаючись звільнити пам'ять усередині довгоживучого процесу, а просто періодично викидаючи весь процес цілком і починаючи з чистого аркуша. Грубий інструмент — але справді стандартний і надійний у продакшені.

🎯
Чесно про цей проєкт: зараз він запускається через голий uvicorn, без будь-якого gunicorn у залежностях: CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", ...] (Dockerfile) — без прапорця --workers, тобто один процес на одну Fly-машину. max-requests/max-requests-jitter тут просто немає, бо немає й самого багатоворкерного менеджера процесів, який би цю опцію надавав.

Реалістично є два шляхи, кожен зі своїм компромісом — без однозначної "правильної" відповіді:

  • (a) Перейти на gunicorn: gunicorn -k uvicorn.workers.UvicornWorker --max-requests 1000 --max-requests-jitter 100 app.main:app — дає стандартний механізм напряму, працює навіть з одним налаштованим воркером (перезапуск одного воркера індивідуально все одно має сенс). Це вводить pre-fork модель воркерів, уже розібрану в туторіалі 8, розділ 8.
  • (b) Легша DIY-альтернатива: оскільки проєкт і так — один голий uvicorn-процес без pre-fork моделі, у яку вбудовуватись, можна написати ASGI-мідлвар, що рахує запити й, досягнувши порогу, дораховує запити, що вже в польоті, а тоді ініціює грайсфул-завершення (sys.exit(0) чи штатний shutdown uvicorn), покладаючись на restart_policy/нагляд процесів Fly.io, щоб одразу підняти свіжий контейнер. Без нової залежності — але це переізобретення (меншого шматка) того, що gunicorn уже робить із коробки.

08 Інші способи боротьби з витоком пам'яті

Короткий, не дублюючий вже сказане огляд — з посиланнями туди, де кожен механізм уже розібраний.

Тюнінг пулу з'єднань. Явний pool_recycle — періодичне закриття й переоткриття з'єднань пулу, що прожили задовго, захищає від накопичення серверного чи драйверного стану на одному довгоживучому з'єднанні. Явне налаштування pool_size/max_overflow замість дефолтів SQLAlchemy (розділ 0) теж варте уваги на такій тісній 512 МБ межі, як у цього проєкту — сплеск одночасних запитів, кожен з яких відкриває нове з'єднання пулу, має реальну ціну в пам'яті на з'єднання.

Слабкі кеші. Коли потрібен кеш, що сам не тримає записи живими вічно — дивіться weakref, туторіал 15, розділ 5.

Незчищені кеші й підписки на рівні модуля. Це вже розібрано як реальне джерело "витоків" у Python у туторіалі 15, розділ 10.

Профайлінг пам'яті в продакшені. Перш ніж вирішувати, чи перезапуск воркера — справжній фікс, чи лише пластир, варто спершу реально знайти джерело витоку — tracemalloc/objgraph уже розібрані в туторіалі 15, розділ 14.

Рестарт на рівні контейнера. Чесний останній рубіж: жорсткий ліміт пам'яті, що призводить до OOM-кілу й автоматичного перезапуску контейнера — реальна, хай і груба, страховка, на яку покладаються багато продакшн-систем. Це та "підлога", на яку варто падати, якщо нічого вище не спрацювало — а не перша лінія оборони.

09 Підсумок

Дві половини цього туторіалу — і що з ними робити в цьому проєкті вже сьогодні.

  • Postgres-половина: MVCC дає конкурентні читання/записи "безкоштовно" через знімки й приховані колонки (xmin/xmax/ctid), але плата за це — мертві таплі, які прибирає (авто)VACUUM. route_stops.status — реальний кандидат стежити за часткою мертвих таплів зі зростанням навантаження.
  • Python-половина: пік пам'яті на 512 МБ Fly.io-машині — очікувана поведінка алокатора (туторіал 15), не обов'язково "витік". Explicit pool_recycle — річ, яку варто розглянути на цій тісній межі пам'яті вже зараз.
  • Перезапуск воркера як прийом проти витоків у цьому проєкті поки не налаштований зовсім — з голим uvicorn без gunicorn це варто додати до того, як це стане реальним інцидентом, а не після.
