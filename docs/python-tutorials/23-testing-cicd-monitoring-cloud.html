Частина I · Тести бекенду

1 Піраміда тестів і де ми на ній

Класична "піраміда тестування" — багато дешевих і швидких тестів унизу, мало дорогих і повільних нагорі.

РівеньУ цьому проєктіШвидкість
Unittest_route_optimizer_unit.py — чиста логіка солвера, без HTTP/БДМілісекунди
IntegrationБільшість app/tests/*.py — через TestClient + in-memory SQLite (розділ 2)Секунди на весь набір
E2Eai-delivery-planner-e2e-tests — реальний браузер проти задеплоєного фронтенду+бекендуХвилини

Аналогія з фронтендом
Та сама піраміда, що й у типовому JS/TS-стеку: unit/integration — Jest/Vitest (тут — pytest), e2e — Playwright/Cypress (тут — буквально теж Playwright, лише проти цього конкретного застосунку, а не бекенд-коду напряму).

2 conftest.py — реальні фікстури проєкту

Найцікавіша частина тестової інфраструктури бекенду — як тести отримують "чисту" базу даних і підмінені зовнішні залежності.

app/tests/conftest.py — реальний код з проєкту
engine = create_async_engine(
    "sqlite+aiosqlite:///:memory:",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,
)

@pytest.fixture(autouse=True, scope="session")
def _disable_real_email_sending():
    """Tests must never hit real Gmail SMTP, regardless of what's in the
    local .env — force the no-provider (log-only) path for the whole run."""
    get_settings().GMAIL_ADDRESS = ""
    get_settings().GMAIL_APP_PASSWORD = ""

@pytest_asyncio.fixture
async def db_session():
    """Create all tables, yield a session, then drop all tables."""
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    # ...
  • In-memory SQLite (sqlite+aiosqlite:///:memory:) замість реального Postgres — кожен тестовий прогін отримує повністю чисту, ізольовану базу, що живе лише в пам'яті процесу тестів; жодних побічних ефектів між тестами, жодної потреби піднімати реальний Postgres локально чи в CI.
  • StaticPool — гарантує, що всі підключення в межах одного тесту йдуть через те саме єдине з'єднання (звичайний пул для SQLite in-memory інакше міг би відкрити "порожню" нову базу на кожне підключення).
  • autouse=True, scope="session" фікстура — вимикає реальну відправку email на весь тестовий прогін одразу, незалежно від того, що лежить у локальному .env розробника. Захист від "тест випадково надіслав реальний лист".
✅
DI платить за себе тут напряму: та сама архітектура Depends(...) з туторіалу 1 дозволяє conftest.py підмінити get_db, get_current_user, get_openai_client через app.dependency_overrides[...] — тести жодного разу не торкаються реального Postgres чи реального OpenAI API, попри те, що продакшн-код написаний так, ніби вони завжди справжні.

3 Приклад реального тесту

app/tests/test_drivers_api.py — реальний код з проєкту
def test_create_driver_returns_expected_fields_and_defaults(client: TestClient) -> None:
    response = client.post("/api/v1/drivers/", json=_make_payload())
    assert response.status_code == 200

    body = response.json()
    assert body["name"] == "Alice Driver"
    assert body["status"] == "active"
    assert body["working_hours_start"] == "08:00:00"
    assert body["max_working_minutes"] == 600
    assert "id" in body

client — фікстура з conftest.py, що дає TestClient, підключений до in-memory БД і з обійденою автентифікацією. Тест перевіряє не лише "запит пройшов", а й конкретні значення за замовчуванням (робочі години, максимальна тривалість зміни) — саме такі "значення за замовчуванням" найлегше випадково зламати рефакторингом, і найкорисніше мати тест, що це вловить.

Частина II · E2E-репозиторій

5 Навіщо окремий репозиторій для e2e

ai-delivery-planner-e2e-tests окремий репозиторій — не частина бекенду, а самостійний проєкт.

  • E2E-тести перевіряють весь стек разом — фронтенд (Vercel) + бекенд (Fly.io) — тому логічно не належать конкретно жодному з двох репозиторіїв.
  • Окремий життєвий цикл: e2e-набір можна ганяти проти будь-якого середовища (прод, staging), незалежно від того, який саме коміт зараз у бекенді чи фронтенді.
  • Інший технологічний стек (TypeScript+Playwright, не Python) — окремий package.json, окремий CI, без змішування залежностей із бекендом.

6 Технології: Playwright + TypeScript

package.json — реальний код з e2e-репозиторію
{
  "name": "ai-delivery-planner-e2e-tests",
  "scripts": {
    "test": "playwright test",
    "test:ui": "playwright test --ui",
    "report": "playwright show-report"
  },
  "devDependencies": {
    "@playwright/test": "^1.48.0",
    "dotenv": "^16.4.5",
    "typescript": "^5.5.0"
  }
}

Playwright — фреймворк для браузерної автоматизації від Microsoft: керує справжнім Chromium/Firefox/WebKit, клікає, заповнює форми, чекає на елементи так само, як робив би реальний користувач. TypeScript, а не JS — типізовані Page/Flow-класи (розділ 8) ловлять помилки в самих тестах ще до запуску, той самий принцип "статична перевірка типів" з туторіалу 4, тепер із боку тестів, а не бекенду.

Аналогія з фронтендом
Playwright ≈ Cypress, тільки керує кількома реальними браузерними рушіями (не лише Chromium-подібним), і за дизайном орієнтований на паралельний запуск і CI з коробки.

7 Структура репозиторію

реальна структура з e2e-репозиторію
tests/

  fixtures/
    base.fixture.ts       # підключає Flow-класи до test (розділ 9)
  flows/                  # Page Object -- по одному класу на розділ застосунку
    auth.flow.ts
    drivers.flow.ts
    depots.flow.ts
    vehicles.flow.ts
    deliveries.flow.ts
  specs/                  # самі тести -- ЩО перевіряємо

    vehicles.spec.ts

Чіткий поділ "ЯК взаємодіяти зі сторінкою" (flows/) від "ЩО ми перевіряємо" (specs/) — той самий принцип шаруватої архітектури з туторіалу 1, тільки застосований до тестового коду: специфікація тесту читається як список бізнес-кроків, а не як перелік CSS-селекторів.

8 Flow (Page Object) патерн

tests/flows/drivers.flow.ts — реальний код з e2e-репозиторію
export interface DriverInput {
  name: string;
  phone: string;
}

export class DriversFlow {
  constructor(private page: Page) {}

  async goto() {
    await this.page.goto('/drivers');
  }

  async create(driver: DriverInput) {
    await this.page.getByRole('button', { name: '+ New Driver' }).click();
    await this.page.locator('#drv-name').fill(driver.name);
    await this.page.locator('#drv-phone').fill(driver.phone);
    await this.page.getByRole('button', { name: 'Create' }).click();
  }
}
tests/specs/drivers.spec.ts — реальний код з e2e-репозиторію
test('creates a new driver', async ({ page, driversFlow }) => {
  const name = `E2E Driver ${Date.now()}`;

  await driversFlow.goto();
  await driversFlow.create({ name, phone: '0501234567' });

  await expect(page.getByText(name)).toBeVisible();
});

Flow (він же Page Object в індустрії) — клас, що ховає деталі конкретної сторінки (які саме селектори, які кроки) за читабельними методами (create(driver)). Якщо фронтенд змінить розмітку форми водія — правиться один файл (drivers.flow.ts), а не кожен тест, що коли-небудь створює водія.

9 Fixtures у Playwright ≈ Depends у FastAPI

tests/fixtures/base.fixture.ts — реальний код з e2e-репозиторію
export const test = base.extend({
  authFlow: async ({ page }, use) => use(new AuthFlow(page)),
  driversFlow: async ({ page }, use) => use(new DriversFlow(page)),
  depotsFlow: async ({ page }, use) => use(new DepotsFlow(page)),
  vehiclesFlow: async ({ page }, use) => use(new VehiclesFlow(page)),
  deliveriesFlow: async ({ page }, use) => use(new DeliveriesFlow(page)),
});

test.extend<Flows>({...}) — Playwright-версія Dependency Injection (туторіал 1 і 16): кожен тест оголошує у своїх параметрах, які саме ...Flow-об'єкти йому потрібні (async ({ page, driversFlow }) =>), а фреймворк сам збирає й передає готові екземпляри — тест не створює new DriversFlow(page) вручну щоразу, так само як FastAPI-ендпоінт не створює DeliveryRepository(...) вручну.

💼
Хороша відповідь на співбесіді "Чи стикались ви з DI поза бекендом?" — Playwright fixtures — прямий, конкретний приклад того самого патерна (Dependency Injection) у тестовому фреймворку, а не у веб-застосунку.

10 storageState — логін один раз, а не в кожному тесті

tests/auth.setup.ts + playwright.config.ts — реальний код з e2e-репозиторію
setup('authenticate', async ({ page }) => {
  const auth = new AuthFlow(page);
  await auth.login(process.env.TEST_EMAIL!, process.env.TEST_PASSWORD!);
  await page.waitForURL('/');
  await page.context().storageState({ path: STORAGE_STATE });   // зберігає cookies/сесію у файл
});

// playwright.config.ts:
projects: [
  { name: 'setup', testMatch: /auth\.setup\.ts/ },
  { name: 'chromium', use: { storageState: STORAGE_STATE }, dependencies: ['setup'] },
]

Окремий "setup"-проєкт логіниться один раз через реальний UI і зберігає сесію (cookies, localStorage) у файл; усі інші тести стартують уже залогіненими, підвантажуючи цей файл — не витрачають 5-10 секунд на повторний логін у кожному тесті. Виняток — login.spec.ts, який навмисно скидає стан (test.use({ storageState: { cookies: [], origins: [] } })), бо сам логін і є тим, що він перевіряє.

11 Що покрито, що ні — і чому

✅ Покрито
Логін (вдалий і невдалий) Навігація по всіх основних розділах Створення водія/депо/машини/доставки Логаут
⏳ Навмисно поки ні
Повна генерація оптимізованого маршруту (ланцюжок: геокодування депо + доставок, частина з яких асинхронна на бекенді — чекає стабільного розуміння таймінгів)

Із README репозиторію: "Scope is intentionally minimal: log in, walk through the main functionality, verify it works" — свідомо мінімальний "smoke"-набір, а не намагання покрити кожен можливий сценарій. Швидкий, стабільний набір, який реально запускають на кожен PR, цінніший за повільний і крихкий, який ніхто не хоче чекати.

Частина III · CI/CD

12 CI бекенду

.github/workflows/ci.yml — реальний код з бекенд-репозиторію
jobs:
  test:
    steps:
      - run: pip install ".[dev]"
      - name: Run ruff
        run: ruff check .
      - name: Run pytest
        run: pytest

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    steps:
      - uses: superfly/flyctl-actions/setup-flyctl@master
      - run: flyctl deploy --remote-only
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}

Лінійний, простий пайплайн: лінт → тести → (лише на main) деплой. deploy-джоба має needs: test — деплой фізично не може запуститись, якщо тести не пройшли. if: github.ref == 'refs/heads/main' гарантує, що PR-и (гілки, що не є main) ніколи не деплояться, лише перевіряються.

13 CI e2e-репозиторію

.github/workflows/playwright.yml — реальний код з e2e-репозиторію
jobs:
  e2e:
    timeout-minutes: 30
    steps:
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
        env:
          BASE_URL: ${{ secrets.BASE_URL }}
          TEST_EMAIL: ${{ secrets.TEST_EMAIL }}
          TEST_PASSWORD: ${{ secrets.TEST_PASSWORD }}

      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 14
  • timeout-minutes: 30 — захист від "зависання" (браузерні тести можуть застрягти, чекаючи елемент, що ніколи не з'явиться).
  • Secrets (BASE_URL, тестовий акаунт) — тести йдуть проти реально задеплоєного застосунку (прод чи staging URL), а не локального інстансу — саме тому потрібні реальні облікові дані в GitHub Secrets, не в коді.
  • upload-artifact ... if: !cancelled() — HTML-звіт Playwright (зі скріншотами й відео провалених тестів, screenshot: 'only-on-failure', video: 'retain-on-failure' з конфігу) зберігається як артефакт навіть при падінні — можна відкрити й побачити, що саме пішло не так, не перезапускаючи локально наосліп.

14 Чому два окремі пайплайни, а не один

✅
Бекенд-CI відповідає за коректність коду бекенду (лінт, unit/ integration-тести) — швидко, і без залежності від того, чи задеплоєний зараз фронтенд. E2E-CI відповідає за коректність усього застосунку разом, коли він уже живий у проді — принципово інша перевірка, на інших часових рамках (e2e логічно доречно ганяти й за розкладом, не лише на кожен пуш, щоб ловити регресії від змін у фронтенд-репозиторії, які бекенд-CI фізично не бачить).
Частина IV · Моніторинг і хмара

15 Що вже є

fly.toml — реальний код з проєкту
[[http_service.checks]]
  method = "GET"
  path = "/health"
  interval = "15s"
  timeout = "5s"
  grace_period = "10s"

Fly.io сам опитує GET /health кожні 15 секунд; якщо машина перестає відповідати — платформа перезапускає її автоматично. Це базовий рівень "чи процес взагалі живий" — найпростіша, але реальна форма моніторингу, що вже працює без жодного додаткового налаштування.

16 Чого чесно немає

⚠️
Поза health-чеком Fly.io й логами в stdout (туторіал 11 — які, нагадаємо, теж не повністю налаштовані сьогодні) проєкт наразі не має: APM (application performance monitoring — Sentry/Datadog/New Relic для трасування повільних запитів), централізованого збору помилок (Sentry-подібний сервіс, що ловить і групує винятки автоматично), алертів (Slack/email при падінні health-чеку чи сплеску 5xx-відповідей), чи дашборда з реальними метриками (латентність, RPS, використання БД-пулу).

Для поточного масштабу (один інстанс, невелике навантаження — туторіал 3) це прийнятний, свідомий рівень інвестицій в observability. Природний наступний крок при рості — Sentry для помилок (найдешевший, найшвидший до впровадження) ще до повноцінного APM/дашбордів.

17 Хмара — коротко

Повний розбір деплою (Fly.io, single-machine trade-offs, драбина масштабування) — уже є в туторіалі 3. Тут — лише нагадування, як тестування й CI з цього туторіалу підключаються до тієї картини: deploy-джоба CI (розділ 12) і є тим самим кроком, що застосовує зміни до Fly.io-машини, описаної в тому туторіалі — тести й лінт як обов'язкові ворота перед кожним таким деплоєм.

18 Каверзні питання співбесіди

БазаНавіщо in-memory SQLite для тестів, якщо прод використовує Postgres?
Швидкість (не треба піднімати реальну БД у CI) та ізоляція (кожен тестовий прогін — чиста база). Компроміс: SQLite й Postgres мають дрібні відмінності поведінки (типи даних, деякі SQL-функції) — для більшості CRUD-тестів це не критично, але це не 100% гарантія поведінки на реальному Postgres.
БазаЧим Page Object (Flow) кращий за виклик селекторів напряму в кожному тесті?
Ізолює деталі розмітки сторінки в одному місці — зміна форми на фронтенді вимагає правки одного Flow-класу, а не кожного тесту, що з цією формою взаємодіє.
ПасткаЧому login.spec.ts окремо скидає storageState, а решта тестів — ні?
Решта тестів навмисно стартують уже залогіненими (через збережену сесію з auth.setup.ts), щоб не витрачати час на повторний логін у кожному тесті. Але сам логін — це те, що login.spec.ts перевіряє, тож він мусить стартувати з порожнього, незалогіненого стану.
БазаЧому деплой-джоба в CI має needs: test?
Гарантує, що деплой фізично не може запуститись, якщо лінт чи тести впали — структурний захист від випадкового розгортання зламаного коду, а не домовленість "не мерджити, поки CI червоний".
ПасткаЧому e2e-тести живуть в окремому репозиторії, а не в бекенді чи фронтенді?
E2E перевіряє весь стек разом (фронтенд + бекенд), тому логічно не належить жодному з них окремо; має власний технологічний стек (TS/Playwright, не Python), власний життєвий цикл і CI, незалежний від того, який коміт зараз у кожному з інших двох репозиторіїв.
БазаЧи вважається health-check на Fly.io повноцінним моніторингом?
Ні — це лише базова перевірка "процес живий/мертвий" з автоматичним рестартом. Повноцінний моніторинг включає трасування продуктивності, збір і групування помилок, алерти й метрики — усього цього в проєкті поки немає, свідомо, для поточного масштабу.
