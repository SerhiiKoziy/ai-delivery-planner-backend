1 Reference counting — основа основ

Кожен об'єкт у CPython носить із собою лічильник: скільки місць на нього зараз посилаються.

python
import sys

x = [1, 2, 3]
sys.getrefcount(x)   # 2, не 1!

y = x
sys.getrefcount(x)   # 3
del y
sys.getrefcount(x)   # 2

Щойно лічильник об'єкта падає до нуля, CPython звільняє пам'ять негайно — на відміну від мов зі "справжнім" garbage collector-ом (Java, JS), де звільнення відкладене до наступного циклу збирання сміття. Це й пояснює "зайву" одиницю у прикладі вище: sys.getrefcount(x) сама по собі створює тимчасове посилання на x — сам виклик функції передає x аргументом, і це вже друге посилання (перше — сама змінна x).

💼
Класичне питання-пастка "Чому sys.getrefcount(x) одразу після створення x повертає 2, а не 1?" — тимчасове посилання від самого виклику функції (аргумент передається за посиланням) — не забудькуватість CPython, а прямий наслідок того, як працює виклик функції в Python.

2 Цикли — де reference counting безсилий

Найважливіший факт цього туторіалу: reference counting сам по собі ніколи не звільнить об'єкти, що посилаються один на одного по колу.

python — класичний цикл
class Node:
    def __init__(self):
        self.other = None

a = Node()
b = Node()
a.other = b   # a посилається на b
b.other = a   # b посилається на a -- ЦИКЛ

del a
del b
# -- обидва об'єкти ВСЕ ЩЕ живі: a.other тримає b, b.other тримає a,
# refcount кожного = 1 (не 0!), хоча жодна змінна на них уже не вказує

3 Generational GC — три покоління

Окремий, додатковий механізм (модуль gc), який періодично шукає саме такі "острівці" — об'єкти, недосяжні від жодного кореня програми, але з ненульовим refcount через цикл.

python
import gc

gc.get_threshold()   # (700, 10, 10) -- типові дефолтні пороги
gc.collect()          # примусово запустити повне сканування всіх поколінь

Ідея — покоління (generational hypothesis): більшість об'єктів "помирають" (стають непотрібними) дуже швидко після створення; ті, що пережили одне сканування, з набагато більшою ймовірністю проживуть довго. CPython ділить відстежувані об'єкти на 3 покоління: нові об'єкти потрапляють у покоління 0; якщо об'єкт переживає збирання — підвищується до покоління 1, потім 2. Покоління 0 скануються найчастіше (дешево, бо там мало об'єктів і вони швидко відмирають), покоління 2 — рідко (дорожче сканувати, але там мало сенсу — об'єкти вже довели, що живуть довго).

💡
Відстежуються (tracked) лише "контейнерні" типи, здатні утворити цикл — списки, словники, класи, екземпляри користувацьких класів. Прості незмінні об'єкти (int, str) не можуть посилатись самі на себе, тому gc їх взагалі не сканує — reference counting сам по собі повністю достатній для них.

4 __del__ і цикли — коротка історія PEP 442

🎉
Цікавий факт з історії До Python 3.4 цикл, що містив хоч один об'єкт із методом __del__, взагалі не міг бути автоматично зібраний generational GC — CPython не мав безпечного способу визначити порядок виклику __del__ для об'єктів циклу (виклик __del__ одного міг би "воскресити" інший через глобальне посилання). Такі об'єкти складались у список gc.garbage — назавжди "підвішені", доки програма не завершиться. PEP 442 (Python 3.4, 2014, "Safe object finalization") розв'язав цю проблему новим, безпечним протоколом фіналізації — відтоді цикли з __del__ збираються нормально.

Практичний висновок сьогодні: на сучасних версіях Python (3.4+) наявність __del__ у циклі вже не блокує збирання — але сам факт, що це колись було справжньою production-проблемою, пояснює, чому досвідчені розробники досі обережні з __del__ у класах, здатних утворити цикл.

5 weakref — розірвати цикл свідомо

python
import weakref

class Node:
    def __init__(self):
        self._other = None
    @property
    def other(self):
        return self._other() if self._other else None   # weakref -- виклик як функція
    @other.setter
    def other(self, node):
        self._other = weakref.ref(node) if node else None

a, b = Node(), Node()
a.other = b   # ЗВИЧАЙНЕ посилання a -> b
b.other = a   # СЛАБКЕ посилання b -> a -- не збільшує refcount a

Замість покладатись на те, що generational GC знайде цикл (розділ 2-3), можна уникнути циклу взагалі — одна зі сторін тримає слабке посилання (weakref.ref), яке не рахується в refcount. Об'єкт звільняється звичайним reference counting, щойно останнє сильне посилання зникає — навіть якщо слабке посилання ще технічно "існує" (воно просто почне повертати None).

Типове застосування — батько-дитина (дитина тримає weakref назад на батька) і кеші, які не повинні самі утримувати об'єкт живим (WeakValueDictionary).

6 __slots__ — економія кількісно

Уже згадувалось у туторіалі 6 — тут конкретна причина, чому це економить пам'ять.

Звичайний екземпляр класу зберігає атрибути у власному __dict__ — а словник, навіть порожній, має суттєвий базовий оверхед (виділена хеш-таблиця з запасом під майбутній ріст). __slots__ каже CPython узагалі не створювати __dict__ для екземплярів цього класу — значення зберігаються напряму у фіксованих слотах, схожих на поля C-структури. На практиці економія для простих класів з кількома атрибутами часто становить порядку 40-50% пам'яті на екземпляр — суттєво, коли створюються мільйони таких об'єктів (наприклад, вузли графа маршруту).

⚠️
Пастка з множинним успадкуванням: якщо два базові класи обидва оголошують непорожній __slots__, спроба успадкувати від обох одразу кидає TypeError: multiple bases have instance lay-out conflict — CPython не може узгодити два різні фіксовані layout-и пам'яті в одному екземплярі.

7 Чому RSS процесу не падає одразу після del

Один із найчастіших "production-збиваючих з пантелику" фактів — і безпосередньо стосується деплою цього проєкту.

CPython не звертається до ОС за пам'яттю на кожен маленький об'єкт — це було б занадто повільно. Замість цього для дрібних об'єктів (<512 байт) працює власний аллокатор pymalloc: він запитує в ОС великі шматки ("арени", типово по 1 МБ), ділить їх на пули фіксованого розміру блоків, і видає/забирає блоки з цих пулів. Коли ви видаляєте об'єкт, його блок повертається в пул CPython — але сама арена віддається назад операційній системі лише тоді, коли вся вона стає порожньою. Якщо в арені лишився хоч один живий, довгоживучий об'єкт серед тисяч уже звільнених — уся арена лишається зарезервованою за процесом.

⚠️
Пов'язано з проєктом: цей бекенд задеплоєний на Fly.io з memory = "512mb" (туторіал 3). Кожен важкий POST /routes/optimize (OR-Tools) чи імпорт великого CSV/Excel через pandas створює й одразу звільняє величезну кількість тимчасових об'єктів — але RSS процесу після такого запиту типово не повертається до попереднього рівня, саме через фрагментацію арен вище. На обмеженій 512 МБ машині це варто розуміти перед тим, як тлумачити графік споживання пам'яті як "витік" — він може бути просто нормальною поведінкою аллокатора.

8 gc.freeze() і pre-fork воркери

Просунута, але дуже практична деталь — пряме продовження туторіалу 8 (Gunicorn pre-fork модель воркерів).

Коли Gunicorn-майстер-процес форкає кілька воркер-процесів (--workers N, туторіал 8), діти спершу ділять усю пам'ять батька через механізм ОС copy-on-write — фізично нова пам'ять не копіюється, доки якийсь процес не спробує записати в спільну сторінку. Проблема: звичайний прохід generational GC регулярно "торкається" (оновлює внутрішні лічильники) навіть довгоживучих об'єктів — а це запис, який запускає copy-on-write і фактично дублює пам'ять для кожного воркера окремо, зводячи нанівець економію від спільних сторінок.

типовий production-патерн (не в цьому проєкті, для довідки)
# у Gunicorn post_fork/pre_fork хуках, ПІСЛЯ завантаження застосунку,
# але ДО форку воркерів:
import gc
gc.freeze()   # все, що вже відстежується GC, переходить у "постійне" покоління —
              # наступні проходи GC більше НЕ торкаються цих об'єктів

gc.freeze() (Python 3.7+) переносить усі наразі відстежувані об'єкти в окреме "заморожене" покоління, яке звичайні проходи gc.collect() більше не сканують — воркери після форку не "бруднять" спільні сторінки лише через прохід GC, реально економлячи пам'ять на багатоворкерному деплої.

9 del не гарантує негайного звільнення пам'яті

python
big_list = [0] * 10_000_000
alias = big_list       # друге посилання на той самий список

del big_list
# пам'ять НЕ звільнилась -- alias усе ще тримає той самий об'єкт живим!

del x прибирає лише прив'язку імені x у поточному просторі імен — об'єкт звільняється, лише якщо це було останнє посилання на нього (refcount падає до 0). Якщо десь ще існує посилання на той самий об'єкт (як alias вище), del нічого фізично не звільняє.

10 Незчищені кеші й підписки — реальні "витоки" в Python

Python не має класичних C-style витоків пам'яті (забутий free()) — але має свій, дуже поширений клас: структура, що навмисно тримає посилання, і ніхто ніколи їх не прибирає.

app/core/rate_limiting.py — реальна знахідка в цьому проєкті
_WINDOWS: dict[str, deque] = defaultdict(deque)

def _check_and_record(key, max_requests, window_seconds):
    now = time.monotonic()
    with _LOCK:
        window = _WINDOWS[key]                      # створює запис у dict НАЗАВЖДИ на новий key
        while window and now - window[0] > window_seconds:
            window.popleft()                          # видаляє СТАРІ мітки часу зсередини deque...
        # ...але сам порожній deque(), і сам ключ у _WINDOWS, НІКОЛИ не видаляється
⚠️
Реальна, повільна знахідка: кожен унікальний "scope:IP" (наприклад, "register:1.2.3.4"), який хоч раз звернувся до /auth/register чи /auth/login, лишає запис у _WINDOWS на весь час життя процесу — навіть коли цей IP більше ніколи не повертається, а його deque давно спорожнів. За довгий час роботи одного процесу (туторіал 3: тут саме так задеплоєно) з великою кількістю унікальних клієнтських IP цей словник повільно, необмежено росте. Не критичний, гострий витік — лише в межах кількості унікальних IP-адрес за весь час роботи процесу — але саме такий клас проблем важко помітити без спеціального пошуку.

Інші поширені варіанти того самого класу проблеми:

  • @lru_cache без maxsize (@lru_cache(maxsize=None)) на функції з великою кількістю різних аргументів — кеш росте необмежено, доки програма не впаде через нестачу пам'яті. get_settings() у цьому проєкті безпечний саме тому, що не приймає жодних аргументів — кеш обмежений одним-єдиним записом за дизайном.
  • Observer/pub-sub без відписки (туторіал 14) — якщо суб'єкт тримає список підписників і ніхто ніколи не викликає unsubscribe, кожен новий підписник назавжди лишається живим через це посилання, навіть якщо решта коду про нього забула.

11 Замикання, що тримають зайве живим

python
def make_handler(huge_dataset):
    def handler(request):
        return len(huge_dataset)   # використовує лише len(), але замикання тримає ВЕСЬ об'єкт
    return handler

# huge_dataset живе стільки, скільки живе сам handler -- навіть якщо
# реально потрібне лише число len(huge_dataset), обчислене один раз

Замикання (closure) утримує посилання на змінні з зовнішньої області видимості, не копію значення — якщо handler лишається живим довго (зареєстрований як callback, збережений у список маршрутів), увесь захоплений об'єкт теж лишається живим, навіть якщо функції насправді потрібна лише крихітна частина інформації з нього.

✅
Фікс тут простий: обчислити потрібне значення один раз до створення замикання (size = len(huge_dataset)) і захопити лише його — тоді huge_dataset може звільнитись одразу після виходу з make_handler.

12 __del__ ненадійний для очищення ресурсів

Пряме продовження туторіалу 7/9 (контекст-менеджери) — тепер із поясненням "чому саме with, а не покластись на GC".

__del__ викликається, коли refcount об'єкта падає до нуля — але коли саме це станеться, ніколи не гарантовано наперед: залежить від того, коли останнє посилання зникне (може бути одразу, а може — через generational GC, з непередбачуваною затримкою в циклі). При завершенні інтерпретатора порядок фіналізації об'єктів взагалі не визначений — покладатись на __del__ для критичного очищення (закрити файл, звільнити мережеве з'єднання, закомітити транзакцію) — ризиковано.

app/db/session.py — реальний код з проєкту, правильний підхід
async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:   # ГАРАНТОВАНЕ закриття через __exit__,
        yield session                              # а не "коли-небудь" через __del__

Саме тому with/async with (детально — туторіал 7, розділ 18; туторіал 9) — правильний інструмент для детермінованого очищення ресурсів, а __del__ лишається лише "останньою лінією оборони" для випадків, коли явне закриття було пропущено.

13 sys.getsizeof() бреше (точніше — не бреше, а лише про дещо інше)

python
import sys

big_strings = ["x" * 1_000_000 for _ in range(100)]
sys.getsizeof(big_strings)
# ~900 байт -- лише "обгортка" самого списку (масив покажчиків)!
# РЕАЛЬНІ 100 мільйонів символів у самих рядках НЕ враховані

sys.getsizeof(obj) повертає лише власний, поверхневий розмір об'єкта — для контейнера це розмір масиву покажчиків на елементи, а не розмір самих елементів. Щоб дізнатись реальний, "глибокий" розмір структури даних із усіма вкладеними об'єктами, потрібно або рекурсивно підсумовувати самому, або сторонній інструмент (pympler.asizeof).

15 Каверзні питання співбесіди

БазаЧому sys.getrefcount(x) одразу після створення x повертає 2, а не 1?
Сам виклик функції передає x як аргумент — це і є друге, тимчасове посилання, що існує на час виконання getrefcount.
ПасткаЧому reference counting сам по собі не звільняє циклічні посилання?
Об'єкти циклу посилаються один на одного — refcount кожного лишається >0 навіть коли жодна зовнішня змінна на них не вказує. Потрібен окремий механізм (generational GC), що шукає такі "недосяжні від кореня" острівці явно.
ПросунутеЧому до Python 3.4 наявність __del__ у циклі блокувала його збирання?
CPython не мав безпечного способу визначити порядок виклику __del__ для об'єктів циклу — виклик одного міг би "воскресити" інший через глобальне посилання. PEP 442 (Python 3.4) увів безпечний протокол фіналізації, що вирішив цю проблему.
ПасткаВи видалили всі свої посилання на великий об'єкт, але RSS процесу не зменшився. Це витік?
Не обов'язково — CPython (через pymalloc) повертає пам'ять ОС лише коли вся арена (типово ~1 МБ) стає повністю порожньою. Фрагментація (один живий об'єкт серед тисяч звільнених в тій самій арені) — нормальна, очікувана поведінка аллокатора, не обов'язково витік.
БазаЧому не варто покладатись на __del__ для закриття файлів/з'єднань?
Момент виклику __del__ непередбачуваний (залежить від того, коли впаде refcount, чи від затримки в generational GC при циклі), а при завершенні інтерпретатора порядок фіналізації взагалі не визначений. with/ async with дають детерміноване, гарантоване закриття.
ПасткаЩо поверне sys.getsizeof() для списку з мільйоном великих рядків?
Лише розмір самого списку (масиву покажчиків) — не розмір рядків, на які він посилається. Реальний "глибокий" розмір структури набагато більший і вимагає рекурсивного підрахунку або спеціального інструменту (pympler.asizeof).
ПросунутеНавіщо викликати gc.freeze() перед форком воркерів у Gunicorn?
Щоб звичайні проходи GC після форку не "торкались" (і тим самим не запускали copy-on-write дублювання) об'єктів, які вже існували в батьківському процесі до форку й мали б лишатись спільними між усіма воркерами через сторінки пам'яті ОС.
