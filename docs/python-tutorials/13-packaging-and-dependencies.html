1 Віртуальне середовище — навіщо воно взагалі

Перша річ, яка спантеличує людину з фронтенду: у Python немає автоматичної ізоляції залежностей "за замовчуванням", як node_modules в кожній папці проєкту.

Без віртуального середовища (venv) усі пакети, встановлені через pip install, йдуть в один спільний системний Python — два проєкти з різними версіями однієї й тієї самої бібліотеки (наприклад, fastapi==0.100 і fastapi==0.115) не можуть співіснувати. python -m venv .venv створює ізольовану копію інтерпретатора й окрему теку для пакетів саме для цього проєкту.

Аналогія з фронтендом
venv ≈ node_modules, тільки не створюється автоматично при npm install — Python вимагає явно "увійти" в середовище (source .venv/bin/activate) перед тим, як команди python/pip почнуть використовувати саме цю ізольовану копію, а не системний Python.

2 pip — базовий інструмент і його межі

pip install fastapi — найпростіший спосіб встановити пакет; читає requirements.txt для списку залежностей. Обмеження, які й привели до появи Poetry/uv:

  • pip сам по собі не генерує lock-файл — requirements.txt зазвичай пишеться вручну й легко розходиться з тим, що реально встановлено.
  • Немає вбудованого поділу на "залежності для розробки" vs "для проду" без окремих файлів (requirements-dev.txt) чи розділів.
  • Розв'язання конфліктів версій між транзитивними залежностями — базове, історично слабше за сучасні резолвери.

3 Lock-файли: чому просто "версії в requirements.txt" не досить

requirements.txt — недостатньо точно
fastapi>=0.100
# сьогодні поставить 0.104.1, через місяць -- вже 0.115.0 (обидва задовольняють >=0.100)
# транзитивні залежності fastapi теж не зафіксовані взагалі

Lock-файл (poetry.lock, uv.lock, чи pip-compile-згенерований requirements.txt з точними версіями) фіксує рівно ту саму версію кожного пакета, включно з транзитивними залежностями, для кожного встановлення — гарантує, що pip install сьогодні і через рік поставить ідентичний набір версій.

Аналогія з фронтендом
Точний аналог різниці package.json (діапазони версій, ^4.2.0) і package-lock.json/yarn.lock (точні, зафіксовані версії всього дерева залежностей) — та сама проблема, те саме рішення, інша мова.

5 pyproject.toml нашого проєкту, розібраний по частинах

pyproject.toml (PEP 518/621) — сучасний єдиний файл конфігурації, що замінив історичну трійцю setup.py + setup.cfg + requirements.txt.

pyproject.toml — реальний файл з проєкту
[project]
name = "ai-delivery-planner-backend"
version = "0.1.0"
description = "AI Delivery Planner — backend (FastAPI, OR-Tools, OpenAI)"
requires-python = ">=3.12"
dependencies = [
    "fastapi",
    "sqlalchemy[asyncio]",
    "asyncpg",
    "... решта продакшн-залежностей ..."
]

[project.optional-dependencies]
dev = [
    "pytest",
    "pytest-asyncio",
    "ruff==0.15.22",
    "aiosqlite",
]

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[tool.ruff]
line-length = 100
target-version = "py312"
  • [project] — метадані пакета (PEP 621, стандарт для всіх інструментів): назва, версія, обов'язкові залежності для запуску.
  • [project.optional-dependencies] — іменовані групи "додаткових" залежностей; dev тут — лише для розробки/тестів (pip install ".[dev]" встановить і їх).
  • [build-system] — яким інструментом (setuptools, альтернативи — hatchling, poetry-core) зібрати сам пакет.
  • [tool.ruff] — конфігурація стороннього інструмента (лінтера); будь-який інструмент може мати власну секцію [tool.X] у тому самому файлі — саме тому pyproject.toml став єдиною точкою правди для всієї конфігурації проєкту, не лише залежностей.
Аналогія з фронтендом
pyproject.toml ≈ package.json: метадані пакета + залежності + конфігурація інструментів (там — eslintConfig, prettier ключі всередині того самого файлу; тут — секції [tool.ruff], [tool.pytest.ini_options]).

6 Семантичне версіонування й оператори версій

Формат SemVerЗначення
MAJOR.MINOR.PATCHMAJOR — ламаючі зміни API; MINOR — нова функціональність, зворотно сумісна; PATCH — виправлення багів
Оператор у PythonЗначення
fastapiБудь-яка версія (як у цьому проєкті — навмисно "розв'язати" останню сумісну на момент встановлення)
fastapi==0.115.0Рівно ця версія, і жодна інша
fastapi>=0.100,<0.120Діапазон
fastapi~=0.115.0"Сумісний реліз" — дозволяє 0.115.x, забороняє 0.116.0

Оператор ~= у Python — приблизний аналог ^ у npm/semver (дозволяє patch/minor-оновлення, забороняє наступний major), хоча точні межі трохи відрізняються залежно від того, скільки цифр версії вказано.

7 wheel vs sdist — що реально встановлюється

  • sdist (source distribution, .tar.gz) — вихідний код пакета "як є"; при встановленні може знадобитись локальна компіляція (для пакетів із C-розширеннями, наприклад asyncpg чи pandas).
  • wheel (.whl) — вже зібраний пакет, готовий до прямого розпакування без компіляції — саме тому встановлення з wheel набагато швидше і не вимагає компілятора на машині користувача.

pip install fastapi за замовчуванням шукає й ставить wheel, якщо він є для вашої платформи (Linux/macOS/Windows, версія Python) — sdist використовується як запасний варіант, коли підходящого wheel не знайдено.

8 Наш Dockerfile — реальний trade-off без lock-файлу

Dockerfile — реальний код з проєкту
COPY pyproject.toml ./
RUN pip install --no-cache-dir .

COPY app/ ./app/

pip install . встановлює залежності напряму зі списку в [project.dependencies] — без lock-файлу. Це означає: якщо fastapi (вказаний без фіксованої версії) випустить нову мінорну версію між двома білдами Docker-образу, наступний білд поставить іншу версію, ніж попередній — навіть без жодної зміни коду проєкту.

⚠️
Свідомий (чи принаймні прийнятний) trade-off для поточного масштабу: простіший Dockerfile й pyproject.toml без додаткового інструменту (Poetry/uv) чи окремого lock-файлу для підтримки — ціною відсутньої гарантії, що продакшн-білд сьогодні поставить рівно ті самі версії пакетів, що й учора. Для більшого проєкту чи команди природним наступним кроком був би lock-файл (uv.lock чи pip-compile-згенерований requirements.txt), закомічений у репозиторій і використаний у Docker-білді замість "голого" pip install ..
💼
Хороша відповідь на співбесіді "Як забезпечити відтворюваність (reproducibility) production-білдів?" — прямо протилежність тому, що робить Dockerfile цього проєкту зараз: закомічений lock-файл із точними версіями, встановлений замість "діапазону версій" з pyproject.toml напряму.

9 Каверзні питання співбесіди

БазаНавіщо потрібне віртуальне середовище?
Ізолює залежності одного проєкту від системного Python і від інших проєктів — дозволяє двом проєктам мати різні, потенційно несумісні версії однієї й тієї самої бібліотеки одночасно на одній машині.
ПасткаЯкщо requirements.txt задає точні версії (fastapi==0.115.0), хіба це вже не lock-файл?
Ні — фіксує лише прямі залежності, а не весь транзитивний ланцюжок (залежності ваших залежностей). Справжній lock-файл фіксує кожен пакет у дереві встановлення з точною версією й хешем, гарантуючи побітово однакове встановлення.
БазаРізниця wheel і sdist?
Wheel — вже зібраний, готовий до встановлення пакет (швидко, без компіляції). Sdist — вихідний код, може вимагати локальної компіляції під час встановлення (повільніше, потребує компілятора для пакетів із C-розширеннями).
ПасткаЩо станеться, якщо задеплоїти цей проєкт двічі поспіль без змін коду, а fastapi тим часом випустить нову версію?
Другий білд поставить нову версію fastapi, бо pyproject.toml не фіксує точну версію, а lock-файл у проєкті відсутній — поведінка застосунку може змінитись без жодного коміту в самому репозиторії.
БазаЩо описує кожна з трьох цифр у семантичному версіонуванні (SemVer)?
MAJOR — ламаючі, несумісні зміни API; MINOR — нова функціональність, що не ламає існуючий код; PATCH — виправлення багів без зміни публічного API.
