1 Чому не просто print()

Різниця здається косметичною, поки застосунок не потрапляє на прод.

print()logging

⚠️
Найпоширеніша практична причина: print() у production-застосунку неможливо вибірково вимкнути. З logging достатньо підняти рівень логера з DEBUG до WARNING в один рядок конфігурації — і всі "діагностичні" повідомлення зникають, не чіпаючи жодного рядка коду.

2 Ієрархія логерів і propagation

Найважливіша, і найчастіше незрозуміла частина модуля — логери утворюють дерево, а не список.

python
logging.getLogger("app.services.route_optimizer.solver")
# ім'я з крапками автоматично будує ІЄРАРХІЮ, як шлях у файловій системі:
#   root
#    └── app
#         └── app.services
#              └── app.services.route_optimizer
#                   └── app.services.route_optimizer.solver

Логер, названий за домовленістю __name__ (тобто повним шляхом модуля, наприклад app.services.route_optimizer.solver), автоматично стає "дитиною" логера app.services.route_optimizer, той — дитиною app.services, і так до кореневого root-логера. За замовчуванням запис логу, зроблений на найглибшому логері, піднімається (propagate) вгору по всьому дереву — кожен предок теж отримує шанс обробити цей запис своїми handler-ами, якщо вони є.

Практичний наслідок: зазвичай достатньо налаштувати handler-и лише один раз на root-логері (чи на логері верхнього рівня "app") — усі "дочірні" логери в кожному модулі автоматично скористаються тим самим налаштуванням через propagation, без повторної конфігурації в кожному файлі.

Аналогія з фронтендом
Схоже на CSS-каскад: властивість, не задана явно на елементі, "успадковується" від батька. Тут — не властивість стилю, а сам факт "чи є кому обробити цей запис логу" — успадковується вгору по дереву логерів, а не вниз, як у CSS, але ідея ланцюжка відповідальності та сама.

3 Рівні логування — коли який

РівеньКоли використовувати
DEBUGДетальна діагностика для розробника — значення змінних, кроки алгоритму. Вимкнено за замовчуванням у проді.
INFOНормальний хід подій, вартий запису: "користувач зареєструвався", "маршрут оптимізовано".
WARNINGЩось незвичне, але застосунок продовжує працювати коректно — типовий рівень за замовчуванням.
ERRORОперація не вдалась, потрібна увага — але процес живий.
CRITICALЗастосунок (чи ключова його частина) не може продовжувати роботу.
💡
Логер з рівнем WARNING (типовий дефолт, якщо нічого не налаштовано) просто ігнорує виклики .debug(...) і .info(...) — і робить це дешево: рядок повідомлення взагалі не форматується, якщо рівень вимкнено (на відміну від print(f"..."), де f-string обчислюється завжди, навіть якщо результат нікуди не піде).

4 Handler, Formatter, Filter — хто за що відповідає

  • Logger — точка входу у ваш код (logger.info(...)); вирішує, чи взагалі обробляти запис (за рівнем), і передає його своїм handler-ам і, через propagation, — предкам.
  • Handler — вирішує, куди йде запис: StreamHandler (консоль), FileHandler (файл), RotatingFileHandler (файл з ротацією за розміром), чи handler для зовнішнього сервісу логів.
  • Formatter — вирішує, як виглядає рядок: які поля (час, рівень, ім'я логера, повідомлення) і в якому порядку.
  • Filter — додаткова, тонша умова: пропустити запис далі чи ні, за будь-якою логікою понад простий рівень важливості.

Один Logger може мати кілька Handler-ів одразу (наприклад: консоль для розробки + файл для аудиту), і кожен Handler може мати власний Formatter і власний, незалежний від логера, рівень.

5 basicConfig vs dictConfig

app/core/logger.py — реальний код з проєкту
def configure_logging(level: int = logging.INFO) -> None:
    """Configure root logging handlers/formatters. Safe to call multiple times."""
    global _CONFIGURED
    if _CONFIGURED:
        return
    logging.basicConfig(
        level=level,
        stream=sys.stdout,
        format="%(asctime)s | %(levelname)s | %(name)s | %(message)s",
    )
    _CONFIGURED = True

logging.basicConfig(...) — найшвидший спосіб налаштувати кореневий логер одним викликом: рівень, формат, куди писати. Проєкт додатково захищає його прапорцем _CONFIGURED, щоб повторний виклик нічого не зламав — сам basicConfig і без цього по замовчуванню ігнорує повторні виклики, якщо root-логер уже має handler-и, але явний прапорець тут прибирає будь-яку двозначність.

Для складніших сценаріїв (кілька handler-ів з різними форматами, окремі логери з різними рівнями) використовують logging.config.dictConfig({...}) — декларативний словник (чи YAML/JSON-файл), що описує все дерево конфігурації одразу, а не послідовністю Python-викликів.

6 Чесний розбір: як логування влаштоване саме в цьому проєкті

Не теорія — реальний стан речей у репозиторії, включно з нюансом, який варто знати.

Хто як отримує логер у проєкті
# app/core/error_handlers.py
logger = logging.getLogger("app.errors")

# app/services/notifications/email.py
logger = logging.getLogger("app.notifications.email")

# app/services/route_optimizer/solver.py
logger = logging.getLogger(__name__)

Усі три модулі отримують логер напряму через logging.getLogger(...) — стандартний stdlib-виклик, без жодних кастомних налаштувань поверх нього.

⚠️
Цікавий, реальний нюанс: у проєкті окремо існує app/core/logger.py з функціями configure_logging() і get_logger(name) (показано в розділі 5) — але жоден інший файл у проєкті не імпортує get_logger з цього модуля. error_handlers.py, email.py і solver.py викликають "голий" logging.getLogger(...) напряму, минаючи configure_logging() зовсім. Це означає: без явного виклику configure_logging() десь на старті застосунку (а такого виклику в main.py цього проєкту зараз немає), кастомний формат "%(asctime)s | %(levelname)s | ..." ніколи фактично не застосовується — логи йдуть з поведінкою Python "за замовчуванням".
✅
Чому це не критично на практиці зараз: Python має вбудований "handler останньої надії" (handler of last resort), що виводить WARNING+ повідомлення в stderr навіть зовсім без конфігурації — тому logger.exception(...) і logger.error(...) у error_handlers.py (обидва ≥ WARNING) усе одно щось надрукують. Але без явного configure_logging() це виведення не має ані формату з configure_logging(), ані гарантії, що менш важливі рівні (INFO) взагалі колись покажуться.
💼
Хороша відповідь на співбесіді "Розкажіть про випадок, де ви знайшли неочевидну проблему в чужому коді" — це саме такий приклад: код, що виглядає повністю налаштованим (є функція, є формат, є прапорець від повторної конфігурації), але ніде фактично не підключений. Знайти це — питання одного grep по імпортах, а не складного дебагу.

7 logger.exception vs exc_info=True

Коротке нагадування з туторіалу 9, тут — з акцентом на саме логування, а не на винятки.

app/core/error_handlers.py — реальний код з проєкту
logger.error("OpenAI API error on %s %s: %s", request.method, request.url.path, exc)
# -- звичайний рядок, БЕЗ traceback

logger.exception("Unhandled error on %s %s", request.method, request.url.path)
# -- еквівалент logger.error(msg, exc_info=True): traceback додається АВТОМАТИЧНО
⚠️
Ще одна деталь, вартa уваги: logger.error("...: %s", exc) передає exc як звичайний аргумент форматування рядка (викликає str(exc)) — це не те саме, що exc_info=True. Перше дає лише текст повідомлення про помилку; друге додає повний traceback. Обидва підходи в цьому проєкті навмисно різні (розділ 14, туторіал 9): очікувана зовнішня помилка (OpenAI) — без traceback, непередбачена — з повним traceback.

8 Structured logging (JSON-логи)

Формат з core/logger.py — рядок тексту, зручний для читання людиною в консолі. У проді з централізованим збором логів частіше потрібен інший формат.

Рядковий формат (поточний) 
2026-07-19 14:02:11 | ERROR | app.errors | OpenAI API error on POST /ai/chat: rate limit

Легко читати очима в терміналі; важко фільтрувати/шукати програмно у великому обсязі логів з багатьох інстансів.

Структурований (JSON) формат 
{"ts": "2026-07-19T14:02:11Z", "level": "ERROR", "logger": "app.errors", "msg": "OpenAI API error", "method": "POST", "path": "/ai/chat"}

Кожне поле — окремий ключ: система збору логів (ELK, Datadog, CloudWatch) може фільтрувати й агрегувати по path, level тощо без парсингу тексту.

Найпростіший шлях отримати структуровані логи в stdlib — власний Formatter, що серіалізує record.__dict__ (потрібні поля) у JSON замість форматованого рядка; популярні готові бібліотеки — python-json-logger, structlog.

9 Correlation ID — трасування одного запиту через логи

Проблема: у застосунку з багатьма одночасними запитами (а це — увесь сенс async, туторіал 2) логи від різних користувачів переплітаються в одному потоці виводу.

типовий підхід — middleware генерує ID на початку запиту
import uuid, contextvars

request_id_var = contextvars.ContextVar("request_id", default="-")

class RequestIdMiddleware:
    async def __call__(self, scope, receive, send):
        request_id_var.set(str(uuid.uuid4()))
        # ...передати керування далі по ASGI-ланцюжку (туторіал 8)

contextvars.ContextVar — спеціально створений для async-коду аналог "потік-локального" сховища (threading.local): значення, встановлене на початку обробки запиту, лишається доступним у будь-якому await-виклику всередині того самого запиту, навіть якщо кілька запитів обробляються "паралельно" в одному event loop (туторіал 4) — кожен бачить лише своє власне значення. Кастомний Formatter потім автоматично додає це значення до кожного рядка логу — і всі логи одного запиту можна знайти одним фільтром по ID, навіть якщо вони технічно перемежовані в загальному виводі з логами інших запитів.

💡
Цей проєкт наразі не генерує correlation ID — кожен запит логується без спільного ідентифікатора між рядками. Для одного інстансу з невеликим навантаженням це не критично; стає важливим, щойно з'являється кілька інстансів (туторіал 3) і треба зрозуміти, які саме рядки логів належать одному й тому самому користувацькому запиту.

10 Каверзні питання співбесіди

БазаЧому не варто використовувати print() для продакшн-логів?
Немає рівнів важливості, немає гнучкого напрямку виводу, неможливо вибірково вимкнути без зміни коду, і рядок форматується завжди — навіть якщо результат нікуди не піде.
ПасткаЛогер "app.services.solver" не має власних handler-ів. Куди піде його запис логу?
Піднімається (propagate) до найближчого предка з handler-ами — типово аж до root-логера. Якщо ніде в дереві немає жодного handler-а, спрацьовує вбудований "handler останньої надії" (виводить WARNING+ у stderr).
БазаРізниця logger.error(msg) і logger.exception(msg)?
logger.exception — те саме, що logger.error(msg, exc_info=True), і має сенс лише всередині except-блоку: додає повний traceback поточного винятку. Звичайний logger.error(msg) — просто рядок, без traceback.
ПасткаВи викликали logger.getLogger(__name__).info("..."), але нічого не вивелось. Чому?
Найімовірніша причина — рівень логера (чи кореневого логера) вищий за INFO (типовий дефолт без конфігурації — WARNING), тому запис просто відкидається ще до будь-якого handler-а. Друга можлива причина — logger.propagate = False на якомусь проміжному логері обриває шлях до handler-а, що міг би вивести запис.
БазаНавіщо конвенція називати логер через __name__?
Ім'я модуля з крапками автоматично будує ієрархію логерів, що відповідає структурі пакетів застосунку — дозволяє потім керувати рівнем логування для цілого піддерева (наприклад, увімкнути DEBUG лише для app.services.route_optimizer, не чіпаючи решту застосунку) без ручного перелічування кожного модуля окремо.
ПасткаНавіщо потрібен contextvars.ContextVar, а не звичайна глобальна змінна, для correlation ID?
Звичайна глобальна змінна — одна на весь процес: у конкурентному async-застосунку (туторіал 4) кілька запитів, що виконуються "одночасно" в одному event loop, переписували б значення одне одному. ContextVar дає кожному логічному потоку виконання (кожній async-задачі) власну, ізольовану копію значення.
БазаЧим structured (JSON) logging кращий за звичайний текстовий формат у продакшені?
Система збору логів (ELK, Datadog тощо) може фільтрувати й агрегувати по окремих полях (рівень, шлях запиту, id користувача) напряму, без потреби парсити довільний текстовий рядок регулярними виразами.
