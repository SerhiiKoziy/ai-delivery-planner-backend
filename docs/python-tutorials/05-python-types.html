01 Динамічна типізація: де насправді Python на цій шкалі

Перше, що варто "прошити": у Python змінні не мають типу — тип має значення, на яке змінна посилається.

python — тип належить значенню, не змінній
x = 5           # x зараз посилається на int
x = "hello"     # та сама змінна x тепер посилається на str — Python це дозволяє
x = [1, 2, 3]   # і тепер на list — жодної помилки на жодному з кроків
Аналогія з фронтендом
Це поводиться точно як звичайний JS: let x = 5; x = "hello"; x = [1,2,3]; — теж без жодної помилки. Різниця з'являється, коли додати TypeScript: TS зафіксував би тип x як number після першого присвоєння й закричав би на других двох рядках ще на етапі компіляції. У Python "аналог TypeScript" (type hints + mypy/pyright) теж може так поводитись — але лише якщо ви його свідомо підключите й запустите окремим кроком. Сам інтерпретатор Python типи ігнорує завжди — про це розділ 5.
МоваТипізація
JavaScriptДинамічна, слабка (багато неявних приведень типів)
TypeScriptСтатична (перевіряється компілятором tsc до запуску, "стирається" в рантаймі)
Python (без hints)Динамічна, відносно сувора (мало неявних приведень — розділ 11)
Python (з hints + mypy/pyright)Динамічна в рантаймі + опційна статична перевірка окремим інструментом
💼
На співбесіді запитають так "Python — типізована мова?" — пастка у формулюванні. Правильна відповідь: "так, і сильно типізована (мало неявних приведень типів між різними типами), але динамічно — типи перевіряються під час виконання, а не заздалегідь". "Сильно/слабо" (strong/weak) і "статично/динамічно" (static/dynamic) — дві незалежні осі, їх часто плутають навіть досвідчені кандидати.

02 Все — об'єкт (навіть самі типи)

У Python буквально все — число, функція, клас, модуль — є об'єктом з типом. Це варто відчути на прикладах, а не просто прочитати.

python
type(5)          # <class 'int'>
type(int)        # <class 'type'>      -- int сам є ОБ'ЄКТОМ класу type
type(type)       # <class 'type'>      -- type є екземпляром самого себе!

def foo(): pass
type(foo)        # <class 'function'>  -- функції теж об'єкти
foo.__name__     # 'foo' — у функції є атрибути, як у будь-якого об'єкта

isinstance(5, object)   # True — навіть примітив 5 є object
🎉
Мозколомний факт type — це клас, що описує "як влаштований клас" (метаклас). І він настільки фундаментальний, що є екземпляром самого себе: type(type) is type → True. Класи в Python — не особлива синтаксична конструкція, а звичайні об'єкти, створені викликом type(...) "під капотом". Саме тому в Python можна створювати класи динамічно, у рантаймі, простим викликом type("MyClass", (BaseClass,), {"attr": 1}).
Аналогія з фронтендом
У JS теж "все об'єкт" у широкому сенсі (функції — first-class citizens, мають властивості), але примітиви (5, "str", true) технічно не об'єкти — JS лише тимчасово "обгортає" їх у Number/String коли викликають метод (autoboxing). У Python різниці немає взагалі: (5).bit_length() — цілком звичайний виклик методу на цілому числі, без жодної магії обгортання.

03 Вбудовані типи: mutable vs immutable

Найважливіший практичний поділ усіх типів у Python — не за "формою даних" (число/текст/колекція), а за тим, чи можна їх змінювати на місці після створення.

int, float, complex
immutable Числа
Python: int — довільна точність, без переповнення. float — завжди double (64-біт).
str
immutable Рядок
s[0] = "x" — TypeError. Будь-яка "зміна" рядка створює новий об'єкт.
bool
immutable Логічний тип
Насправді підклас int! True == 1, isinstance(True, int) → True.
tuple
immutable Незмінний кортеж
Хешовний, якщо всі елементи хешовні — тому може бути ключем dict/елементом set.
frozenset
immutable Незмінна множина
"Заморожена" версія set — саме тому, на відміну від set, може бути хешовною.
None
immutable Єдиний "нема значення"
Один синглтон на весь процес: x is None завжди коректно й швидко.
list
mutable Список
Змінюється на місці: append, [0]=x. Нехешовний — не можна в set/dict-ключ.
dict
mutable Словник
З Python 3.7 гарантовано зберігає порядок вставки (раніше — деталь реалізації CPython 3.6).
set
mutable Множина
Унікальні елементи, без порядку. Сам нехешовний — не можна вкласти set у set.
⚠️
Чому це найважливіший поділ, а не "число vs текст": mutable/immutable напряму визначає поведінку при передачі в функцію, копіюванні, використанні як ключ словника і навіть при використанні як аргумент за замовчуванням (розділ 9 — там живе одна з найвідоміших пасток Python).

04 Duck typing і структурна типізація

"Якщо крякає як качка — це качка" — Python історично не питає клас об'єкта, а лише те, чи має він потрібну поведінку.

python — duck typing
def print_all_items(container):
    for item in container:     # не важливо, list це, tuple, set чи власний клас —
        print(item)             # важливо лише, що container вміє ітеруватись

print_all_items([1, 2, 3])
print_all_items((1, 2, 3))
print_all_items({1, 2, 3})
typing.Protocol — духтайпинг з type hints
from typing import Protocol

class SupportsGeocode(Protocol):
    async def geocode(self, address: str) -> tuple[float, float] | None: ...

# GoogleGeocodingClient з нашого проєкту (app/services/geocoding/client.py)
# НІДЕ явно не пише "implements SupportsGeocode" — але підходить під це
# Protocol просто тому, що має метод geocode з такою сигнатурою.
Аналогія з фронтендом
Це — та сама ідея, що й TypeScript interfaces: TS теж структурно типізований — об'єкт підходить під interface Point { x: number; y: number }, якщо має поля x і y, без явного implements Point. typing.Protocol — це буквально перенесення цієї TS-ідеї в Python: жодного успадкування, лише "форма" (набір методів/атрибутів) повинна збігатись.
💼
На співбесіді запитають так "Що таке duck typing?" — відповідь-мінімум: "поведінка об'єкта визначається не його класом, а тим, які методи/атрибути в нього фактично є". Плюс-бал — згадати typing.Protocol як спосіб типобезпечно описати цю ідею для статичних чекерів, не змушуючи класи явно наслідувати інтерфейс (на відміну від abc.ABC, де успадкування явне й обов'язкове).

05 Type hints — це підказки, а не контракт

Найбільша пастка для людини з TypeScript-бекграундом: анотації типів у Python виглядають так само, але нічого не забороняють у рантаймі самі по собі.

python — тип-хінти НЕ блокують виконання
def add(a: int, b: int) -> int:
    return a + b

add("hello", "world")   # поверне "helloworld" — інтерпретатор просто ІГНОРУЄ анотації!
                         # TypeScript на еквівалентному коді відмовився б компілюватись.
Python + hints
def add(a: int, b: int) -> int: ... add("x", "y") # working fine at runtime

Перевірка — окремим інструментом (mypy/pyright), запущеним вручну чи в CI. Інтерпретатор сам ніколи не звіряє типи.

TypeScript
function add(a: number, b: number) ... add("x", "y") // build FAILS, tsc error

Перевірка вбудована в білд-крок — код, що не проходить перевірку типів, фізично не скомпілюється в JS.

💼
Дуже часте питання на співбесіді "Чи Python-код впаде на старті, якщо типи в анотаціях не збігаються?" — ні, ніколи (сам інтерпретатор). Type hints у Python — це метадані для людей і сторонніх інструментів (IDE-автодоповнення, mypy, pyright, Pydantic — розділ 6), а не частина виконання мови. Єдиний спосіб отримати помилку — свідомо запустити перевірку типів окремою командою, або використати бібліотеку, що сама валідує значення в рантаймі.

Сучасний синтаксис (Python 3.10+): str | None замість Optional[str], list[int] замість List[int] (з 3.9) — вбудовані generic-колекції більше не потребують імпорту з typing.

06 Коли типи РЕАЛЬНО перевіряються в рантаймі

Якщо type hints самі по собі нічого не перевіряють — то як тоді, наприклад, наш проєкт відхиляє некоректний JSON з 422-помилкою?

Pydantic — типи + рантайм-валідація в одному
# схема з app/schemas/ (спрощено) — Pydantic ЧИТАЄ анотації типів
# і сам, у рантаймі, перевіряє й конвертує вхідні дані під них
class UserCreate(BaseModel):
    email: EmailStr
    password: str = Field(min_length=8)

UserCreate(email="not-an-email", password="123")
# -> ValidationError, ще ДО того, як код роутера взагалі почне виконуватись

Pydantic бере ті самі анотації типів, які сам Python ігнорує, і додає над ними власний рантайм-двигун перевірки — це і є секрет, чому в цьому проєкті (та в будь-якому FastAPI-застосунку) невалідний запит реально повертає 422, хоча "звичайні" type hints самі по собі нічого б не заблокували.

ІнструментКоли перевіряєЩо робить з невалідними даними
def f(x: int) (голі hints)Ніколи (сам інтерпретатор)Нічого — просто виконує код далі
mypy / pyrightСтатично, до запуску (окрема команда/CI)Повідомляє помилку в консолі/IDE, код і так МОЖЕ запуститись
Pydantic (BaseModel)У рантаймі, при створенні об'єктаКидає ValidationError одразу
dataclasses (стандартна бібліотека)Ніколи (як і голі hints — це просто зручний спосіб описати поля)Нічого, без стороннього __post_init__
TypedDictНіколи в рантаймі — лише підказка для статичних чекерівНічого — це звичайний dict під капотом
✅
Практичне правило для співбесіди й для роботи: "хочу описати форму даних для читабельності й IDE" → досить dataclass/TypedDict. "Хочу, щоб зовнішні (ненадійні) дані реально перевірялись і падали з чіткою помилкою" → потрібен Pydantic (чи ручна валідація) — саме тому весь шар schemas/ у цьому проєкті побудований на ньому, а не на голих dataclasses.

07 is vs == — ідентичність проти рівності

Виглядає просто, але саме тут ховається одна з найпопулярніших "пасток" на технічних співбесідах з Python.

  • == — питає "чи значення однакові?" (викликає __eq__).
  • is — питає "чи це той самий об'єкт у пам'яті?" (порівнює id(...), буквально адресу).
python — класична пастка з кешуванням цілих чисел
a = 256
b = 256
a is b        # True  — CPython кешує "малі" цілі числа від -5 до 256 як сінглтони

c = 257
d = 257
c is d        # False — за межами кешу це вже ДВА різні об'єкти в пам'яті
c == d        # True  — значення однакові, і саме тому == тут правильний вибір
❌
Ніколи не використовуйте is для порівняння чисел чи рядків за значенням — поведінка вище (кешування -5..256) є деталлю реалізації CPython, а не гарантією мовної специфікації. Інша реалізація (PyPy) чи навіть інша версія CPython може кешувати інакше. Єдиний "безпечний" і сталий випадок використання is — порівняння з None, True, False (це справжні синглтони за специфікацією мови).
💼
Класичне питання на співбесіді "Чому 256 is 256 дає True, а 257 is 257 — False?" — відповідь: кешування малих цілих чисел CPython (`-5..256`) як оптимізація пам'яті/швидкості. Бонус-бал: та сама історія існує для коротких рядків ("string interning") — "hello" is "hello" часто теж True, з тієї ж причини (implementation detail, не покладайтесь на це).
Аналогія з фронтендом
is ≈ === для об'єктів у JS (порівняння посилань: {} === {} теж false, бо це різні об'єкти) — але для примітивів JS === порівнює значення (5 === 5 → true завжди), тоді як Python is завжди про ідентичність об'єкта, навіть для чисел — просто для малих чисел ідентичність "випадково" збігається через кешування.

08 Truthy/Falsy: де Python і JS фатально розходяться

Найнебезпечніша тема для переходу з JS: інтуїція "порожнє = falsy" загалом підтверджується — окрім одного дуже частого випадку.

JavaScript
Boolean([]) // true !! Boolean({}) // true !! [] == false // true (коерція) [] == ![] // true (легендарна пастка)
Python
bool([]) # False bool({}) # False [] == False # False (нема коерції між типами) bool("0") # True (непорожній рядок!)
⚠️
Головна пастка при переході з JS: порожній масив truthy в JS (if ([]) { ... } — виконається!), але порожній список — falsy в Python (if []: ... — НЕ виконається). Це протилежна поведінка на, здавалось б, ідентичному синтаксисі — типова причина тихих багів при портуванні логіки з фронтенд-мислення.

Falsy в Python (повний список): False, None, 0, 0.0, 0j, "", (), [], {}, set() і будь-який об'єкт, чий __bool__ (чи __len__, якщо __bool__ не визначено) повертає False/0. Геть усе інше — truthy, включно з "0", "False" (непорожні рядки!) і [0] (непорожній список, навіть якщо єдиний елемент — falsy-значення).

💼
Питання-пастка "Що поверне bool("False")?" — інтуїтивно хочеться сказати False (бо рядок "виглядає" як falsy-слово), але правильна відповідь — True: це непорожній рядок, а рядкове значення "змісту" геть не має значення для truthy/falsy — лише порожність.

09 Пастка: мутабельний аргумент за замовчуванням

Мабуть, найвідоміша пастка в усій мові Python — регулярно ловить навіть досвідчених розробників, і майже завжди спливає на співбесідах.

python — класична пастка
def append_to(element, target=[]):    # [] обчислюється ОДИН РАЗ, при визначенні функції!
    target.append(element)
    return target

append_to(1)   # [1]
append_to(2)   # [1, 2]   -- !! очікували [2], а список "запам'ятав" минулий виклик
append_to(3)   # [1, 2, 3] -- той самий об'єкт-список переживає між викликами

Причина: значення аргументу за замовчуванням обчислюється один раз — у момент def (визначення функції), а не при кожному виклику. Якщо це mutable-об'єкт (list, dict, set), той самий об'єкт повторно використовується і накопичує зміни між викликами, що не мають між собою нічого спільного.

правильний варіант
def append_to(element, target=None):
    if target is None:      # свіжий список створюється ЗАНОВО на кожен виклик
        target = []
    target.append(element)
    return target
Аналогія з фронтендом
У JS цієї пастки немає: function appendTo(el, target = []) {...} — значення за замовчуванням у JS обчислюється заново при кожному виклику. Якщо ви прийшли з JS, інтуїція тут прямо працює проти вас — і саме тому цю пастку варто запам'ятати свідомо, а не покладатись на "здоровий глузд".
💼
Дуже часте питання на співбесіді "Що виведе цей код?" (з прикладом вище) — очікують саме розуміння чому: "аргументи за замовчуванням обчислюються один раз, у момент визначення функції, і зберігаються як атрибут об'єкта функції (append_to.__defaults__)" — а не просто "так, це баг Python".

10 Shallow vs deep copy

Логічне продовження теми mutable/immutable: "копіювання" списку копіює сам список, але не завжди — те, що всередині нього.

python — shallow copy не рятує від вкладеної мутабельності
import copy

original = [[1, 2], [3, 4]]
shallow = original.copy()      # те саме, що list(original) або original[:]

shallow[0].append(99)
print(original)   # [[1, 2, 99], [3, 4]]  -- original ТЕЖ змінився!
                   # shallow-копія скопіювала ЗОВНІШНІЙ список, але внутрішні
                   # списки — це ті самі об'єкти, на які й далі посилаються ОБИДВІ копії

deep = copy.deepcopy(original)
deep[0].append(-1)
print(original)   # [[1, 2, 99], [3, 4]]  -- тепер справді незалежна копія
💼
На співбесіді запитають так "У чому різниця shallow і deep copy?" — коротка правильна відповідь: "shallow копіює лише перший рівень контейнера — вкладені mutable-об'єкти лишаються спільними; deep рекурсивно копіює все дерево об'єктів". Гарний бонус — навести саме цей приклад зі списком списків, бо це найпоширеніший реальний баг (той самий принцип стосується словників з вкладеними списками/словниками як значеннями).

11 Приведення типів: Python суворий, JS — ні

Хороша новина для тих, хто настраждався від JS-коерції: у Python цього драматично менше.

JavaScript
"5" + 3 // "53" (число стає рядком) "5" - 3 // 2 (рядок стає числом!) 1 + true // 2 (bool стає числом) [] + [] // "" (масиви стають рядками)
Python
"5" + 3 # TypeError: can only concatenate str "5" - 3 # TypeError: unsupported operand type(s) 1 + True # 2 (bool — підклас int, теж коерція, але передбачувана) [] + [] # [] (нема несподіваного рядка)

Python — сильно типізована мова: майже ніколи не буде мовчки конвертувати один тип в інший заради того, щоб операція "якось спрацювала". Виняток, який варто пам'ятати: bool — підклас int (True == 1, False == 0), тому арифметика з булевими значеннями працює як з числами.

python — trick: bool арифметика
True + True         # 2
isinstance(True, int)   # True  -- bool є підкласом int!
sum([True, True, False, True])   # 3 -- рахує True як 1
💼
Каверзне питання "Що виведе True + True?" — правильна відповідь 2, з поясненням: bool у Python — не окремий примітивний тип, а підклас int (усього з двома значеннями), тому в арифметичному контексті True і False поводяться як 1 і 0.

Ланцюгові порівняння — ще одна відмінність, яка іноді дає різний результат

Python
1 < 3 > 2 # True # еквівалент: (1 < 3) and (3 > 2)
JavaScript
1 < 3 > 2 // false // еквівалент: (1 < 3) > 2 -> true > 2 -> 1 > 2

Python має справжнє ланцюгове порівняння як мовну конструкцію (a < b < c означає "і те, і те" одночасно), тоді як JS обчислює зліва направо як звичайні бінарні оператори з неявним приведенням булевого результату до числа на другому кроці — тут результати можуть реально розійтись, а не просто "виглядати по-різному".

12 Hashable: чому list не можна в set чи як ключ dict

Пряме продовження теми mutable/immutable — і ще одне часте джерело TypeError у реальному коді.

python
d = {[1, 2]: "value"}
# TypeError: unhashable type: 'list'

d = {(1, 2): "value"}     # OK — tuple незмінний і хешовний
s = {[1, 2], [3, 4]}      # TypeError: unhashable type: 'list'
s = {(1, 2), (3, 4)}      # OK

Ключі словника й елементи множини повинні бути хешовними — мати стабільний __hash__(), що не змінюється впродовж життя об'єкта. Мутабельні типи (list, dict, set) навмисно не реалізують __hash__ — якби змінюваний список можна було покласти в set, зміна його вмісту після вставки зламала б внутрішню хеш-таблицю (елемент лежав би "не в тій комірці", яку дає його новий хеш).

💼
На співбесіді запитають так "Чому список не можна використати як ключ словника?" — правильна відповідь через причину, а не просто факт: "бо списки мутабельні, а хеш ключа має лишатись сталим протягом усього життя запису в словнику; якби хеш міг змінитись після вставки, елемент став би "загубленим" у неправильному хеш-бакеті". tuple дозволений саме тому, що незмінний — але тільки якщо всі його елементи теж хешовні ((1, [2,3]) — досі TypeError, бо всередині є list).

13 Каверзні питання співбесіди — з відповідями

Натисніть на питання, щоб побачити відповідь. Спробуйте спершу відповісти самі.

БазаPython — статично чи динамічно типізована мова? А сильно чи слабко?
Динамічно (типи перевіряються під час виконання) і сильно (майже немає неявних приведень типів між непов'язаними типами — на відміну від JS). Це дві незалежні осі, не плутайте їх.
ПасткаЩо виведе повторний виклик функції з мутабельним аргументом за замовчуванням?
Список/словник за замовчуванням створюється ОДИН РАЗ при визначенні функції й переживає між викликами — стан "просочується" з попереднього виклику в наступний. Фікс: target: list | None = None, і створювати новий список всередині функції, якщо target is None. Деталі — розділ 9.
ПасткаЧому 256 is 256 дає True, а 257 is 257 — False?
CPython кешує "малі" цілі числа в діапазоні -5..256 як сінглтони при старті інтерпретатора — тому будь-яка змінна з таким значенням фактично посилається на той самий об'єкт у пам'яті. За межами діапазону створюються нові об'єкти на кожне присвоєння. Це деталь реалізації CPython, а не гарантія мови — ніколи не покладайтесь на is для порівняння чисел за значенням.
БазаУ чому різниця is і ==?
== порівнює значення (викликає __eq__), is порівнює ідентичність об'єкта (той самий об'єкт у пам'яті, буквально id(a) == id(b)). Правильне використання is — лише для None/True/False та явних перевірок "це той самий об'єкт", ніколи для порівняння значень чисел/рядків.
ПасткаЧи порожній список truthy чи falsy? А порожній масив у JS?
У Python порожній список — falsy (bool([]) == False). У JS порожній масив — truthy (Boolean([]) === true). Найпряміша поведінкова розбіжність між мовами для розробника, що переходить з фронтенду.
БазаЩо таке duck typing і як він пов'язаний з typing.Protocol?
Duck typing — коли поведінка об'єкта визначається наявністю потрібних методів/атрибутів, а не явним успадкуванням від конкретного класу. typing.Protocol дозволяє описати такий "неявний інтерфейс" для статичних чекерів (mypy/pyright), не вимагаючи явного class Foo(Protocol) успадкування у класу, що йому відповідає — аналог структурних interface у TypeScript.
ПасткаЧи впаде програма на старті, якщо тип аргументу не збігається з анотацією?
Ні — "голі" type hints нічого не перевіряють у рантаймі, це підказки для людей та інструментів (mypy/pyright/IDE). Щоб отримати реальну помилку при невідповідності типу, потрібен інструмент, що явно валідує (Pydantic BaseModel) або ручна перевірка (isinstance).
ПасткаЧому список не можна покласти в set чи використати як ключ dict?
Список мутабельний і тому не має стабільного, незмінного хешу — якби це дозволили, зміна вмісту списка після вставки зламала б внутрішню структуру хеш-таблиці. tuple дозволений, бо незмінний — але лише якщо всі його елементи теж хешовні.
БазаУ чому різниця shallow і deep copy?
Shallow (.copy(), [:], list(x)) копіює лише перший рівень контейнера — вкладені mutable-об'єкти лишаються спільними між оригіналом і копією. Deep (copy.deepcopy()) рекурсивно копіює все дерево об'єктів, роблячи копію повністю незалежною.
ПасткаЩо виведе True + True + False?
2. bool — підклас int (True == 1, False == 0), тому в арифметичному контексті булеві значення поводяться як числа.
Просунутеisinstance(True, int) — що поверне і чому?
True — bool є підкласом int в ієрархії типів Python, а isinstance враховує успадкування (на відміну від type(x) is int, яке для True дало б False, бо точний тип — саме bool, не int).
БазаЧому isinstance() зазвичай кращий вибір, ніж type(x) == SomeClass?
isinstance враховує успадкування (спрацює й для підкласів, і навіть для кількох типів одразу — isinstance(x, (int, float))) та підтримує ABC/Protocol-реєстрацію. type(x) == SomeClass вимагає точного збігу класу — типовий "не-Pythonic" код, який ламається на першому ж підкласі.
Живе кодуванняЩо виведе 1 < 3 > 2 в Python? А еквівалентний вираз у JS?
Python: True — справжнє ланцюгове порівняння, рівнозначне (1 < 3) and (3 > 2). JS обчислює послідовно як два окремі бінарні оператори: (1 < 3) > 2 → true > 2 → 1 > 2 → false. Результати можуть реально розійтись між мовами на однаковому синтаксисі.
