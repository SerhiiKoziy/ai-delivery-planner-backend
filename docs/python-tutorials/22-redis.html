00 Що таке Redis і для чого він

Одне визначення — і одразу межа з тим, що вже розказано в інших турах, щоб не повторюватись.

Redis (REmote DIctionary Server) — сховище даних типу "ключ-значення", яке тримає весь основний набір даних в оперативній пам'яті, а не на диску. Звідси й головна властивість: операції над простими типами виконуються за мікросекунди, на порядки швидше за похід у реляційну базу на диску. Туторіал 17 вже класифікував Redis як key-value базу в загальному ландшафті NoSQL, а туторіал 18, категорія C вже розібрав однопотокову модель продуктивності, персистентність (RDB/AOF) і базовий набір структур даних — тут це не повторюється, натомість дано практичну карту: коли Redis узагалі беруть, і які теми довкола нього не потрапили в жоден із попередніх турів.

Чотири типові ролі, під які Redis реально ставлять у бекенд-системах:

  1. Кеш — результат дорогого обчислення чи запиту в основну базу лежить у Redis з TTL, замість того щоб рахуватись заново на кожен запит.
  2. Сховище сесій — коли застосунок працює на кількох процесах/інстансах, сесія не може жити в пам'яті одного процесу (наступний запит може прилетіти на інший) — Redis стає спільним місцем, яке бачать усі інстанси.
  3. Брокер повідомлень / черга задач — саме ця роль сконфігурована в цьому проєкті для Celery (розділ 5).
  4. Лічильники й обмеження швидкості (rate limiting) — атомарний INCR на спільному ключі, видимий одразу всім процесам (розділ 6, і саме це — план на майбутнє для app/core/rate_limiting.py цього проєкту).
💡
Спільна нитка всіх чотирьох ролей: Redis потрібен там, де кілька окремих процесів чи інстансів застосунку мусять бачити один спільний стан швидше, ніж дозволяє диск. Це саме та властивість, якої зараз бракує in-memory лічильнику rate limiting цього проєкту — детальніше в розділі 2.

01 Аналоги: Memcached, Valkey, KeyDB, Dragonfly

Redis — не єдиний гравець у цій ніші, і питання "чому саме Redis" — цілком типове на співбесіді.

СистемаКлючова відмінність від Redis
Memcached Старший і простіший: лише рядки (byte-стрічки), без структур даних (списків, множин, sorted sets), без персистентності на диск, без pub/sub. Натомість — нативна багатопотоковість "з коробки" (Redis до версії 6 був повністю однопотоковим у виконанні команд). Береться, коли реально потрібен лише найпростіший key→value кеш і нічого більше.
Valkey Форк Redis під егідою Linux Foundation (за участі AWS, Google Cloud, Oracle та інших), що з'явився після зміни ліцензії Redis з відкритої BSD на більш обмежувальну. Протокол і команди — сумісні з Redis, тому міграція здебільшого зводиться до зміни рядка підключення. На практиці — головна причина, чому команда сьогодні може свідомо обрати "Redis-сумісну" систему, а не сам Redis.
KeyDB Ще один сумісний з Redis форк, головна фішка — багатопотокова обробка команд "з коробки" для кращого використання багатоядерних машин, там де Redis традиційно використовує одне ядро.
Dragonfly Написана з нуля (не форк), сумісна з протоколом Redis, розрахована на сучасне багатоядерне залізо — інша внутрішня архітектура заради вищої пропускної здатності на одному інстансі, без потреби в шардингу/кластері раніше, ніж це реально треба.
Просто in-process кеш (наприклад, dict у пам'яті процесу) Найпростіший "аналог" — узагалі без окремого сервісу. Саме такий підхід сьогодні використовує app/core/rate_limiting.py цього проєкту. Найдешевший варіант, доки застосунок працює як один процес; ламається одразу, як тільки процесів чи інстансів стає більше одного, — детальніше в розділі 2.
⚠️
Ліцензійний контекст, який варто знати: у 2024 Redis Ltd. змінила ліцензію основного проєкту з BSD на комбінацію SSPL/RSALv2 — більш обмежувальну для хмарних провайдерів, які продають Redis як послугу, не роблячи внесків у сам проєкт. Valkey — прямий наслідок цього рішення: спільнота й великі хмарні гравці форкнули останню BSD-версію й продовжили розвиток окремо. На співбесіді це часто спливає як питання "чому не просто Redis" — відповідь рідко технічна, частіше ліцензійна/організаційна.

02 На якому етапі цей проєкт його використовує

Чесний, прив'язаний до реального коду розділ — без прикрашання того, що Redis тут поки не робить.

У app/core/config.py оголошено поле конфігурації:

app/core/config.py
# Redis / Celery
REDIS_URL: str = "redis://localhost:6379/0"

Це значення споживає app/workers/celery_app.py, де Redis виступає і брокером, і бекендом Celery одночасно (що означають ці дві ролі — розділ 5):

app/workers/celery_app.py
celery_app = Celery(
    "ai_delivery_planner",
    broker=settings.REDIS_URL,
    backend=settings.REDIS_URL,
)

А в app/workers/tasks.py зареєстровано рівно дві Celery-задачі — і обидві є заглушками:

app/workers/tasks.py
@celery_app.task(name="optimize_routes_task")
def optimize_routes_task(route_request_id: str) -> None:
    """Run route optimization asynchronously and persist the result."""
    raise NotImplementedError


@celery_app.task(name="analyze_delivery_list_task")
def analyze_delivery_list_task(import_batch_id: str) -> None:
    """Run LLM-based delivery list analysis asynchronously."""
    raise NotImplementedError
⚠️
Практичний висновок: ці задачі жодного разу не викликаються ніде в коді застосунку (обробка маршруту й аналіз списку доставок сьогодні виконуються синхронно, у самому запиті — офлоад у чергу лишається запланованим кроком, про який згадано в туторіалі 3). А відсутні виклики означають, що жодна команда ще не пішла в Redis по мережі — з'єднання конфігуроване, але непрограмоване в дію. Класична ситуація "інфраструктура підготовлена наперед", яка сама собою — чесна тема для співбесіди (розділ 9, питання 7).

Другий, окремий факт: обмеження швидкості запитів для незалогованих ендпоінтів (реєстрація, логін) сьогодні реалізоване не через Redis, а через простий лічильник у пам'яті процесу:

app/core/rate_limiting.py
"""In-memory, not Redis-backed: nothing in this deployment assumes more than
a single API process (no redis/queue service is wired up for the app itself
— only Celery's broker). If this ever runs as multiple worker processes or
instances, swap the in-memory `_WINDOWS` dict for a Redis-backed counter."""

_WINDOWS: dict[str, deque] = defaultdict(deque)

Це — не випадковий недогляд, а свідомий, задокументований у самому коді компроміс: коли застосунок працює як рівно один процес, звичайний dict у пам'яті бачать усі запити однаково добре, і Redis тут був би зайвою мережевою залежністю без користі. Саме тому в fly.toml стоїть жорстке обмеження:

fly.toml
[http_service]
  min_machines_running = 1

Ці два факти — одне рішення, розказане з двох боків. min_machines_running = 1 існує тому що лічильник rate limiting не переживе появу другого процесу (кожен інстанс мав би власний окремий _WINDOWS, і ліміт фактично подвоївся б чи більше). Redis тут — не абстрактна "хороша практика", а конкретний, наперед відомий крок: як тільки з'явиться реальна потреба масштабуватись за межі одного інстансу, перше, що доведеться зробити, — перенести саме цей лічильник у вже сконфігурований Redis.

03 TTL, expiration і eviction policies

Тема, якої не було в туторіалі 18 — механіка "часу життя" ключа і що робить Redis, коли пам'яті бракує.

Будь-якому ключу можна призначити час життя: EXPIRE key 60 (або одразу при записі — SET key value EX 60). Після спливання TTL ключ вважається неіснуючим для будь-якого читання — але фізично він не зникає з пам'яті миттєво в момент спливання. Redis прибирає протерміновані ключі двома паралельними механізмами:

  • Лінива (lazy) експірація — коли клієнт звертається саме до цього ключа, Redis спершу перевіряє TTL і, якщо він сплив, видаляє ключ і повертає "не знайдено", замість застарілого значення.
  • Активна (active) експірація — фоновий цикл, що періодично (за замовчуванням десять разів на секунду) бере випадкову вибірку ключів із TTL і видаляє прострочені, навіть якщо їх ніхто не запитує. Це потрібно, бо суто лінивого підходу недостатньо: ключ, до якого ніхто не звертається, лежав би в пам'яті вічно.

Друге, окреме питання — що робити, коли пам'яті, виділеної під maxmemory, більше немає, а хтось намагається записати новий ключ. Політика витіснення (eviction policy) визначає поведінку:

ПолітикаПоведінка
noevictionНічого не витісняти — новий запис відхиляється з помилкою. Правильний вибір, коли Redis тримає дані, втрату яких неможливо компенсувати (наприклад, чергу задач).
allkeys-lruВитісняти найдавніше не використовуваний ключ серед усіх ключів. Типовий вибір для чистого кешу без TTL на кожному ключі.
volatile-lruТе саме, але тільки серед ключів, у яких узагалі встановлено TTL — ключі без терміну дії ніколи не чіпаються.
allkeys-lfuВитісняти найрідше використовуваний ключ (frequency, а не recency) — краще за LRU, коли є "гарячі" ключі, до яких рідко, але регулярно звертаються великими сплесками.
volatile-ttlСеред ключів із TTL — витісняти той, у якого найменше часу лишилось до природного спливання.
allkeys-randomВипадковий ключ — рідко використовується свідомо, здебільшого як найпростіший baseline.
📎
Якби цей проєкт сьогодні тримав у Redis лише кеш (наприклад, результати геокодування), природним вибором була б allkeys-lru чи allkeys-lfu — втрата кешованого значення просто означає один зайвий похід у джерело даних. Але для лічильника rate limiting (розділ 2) чи черги Celery-задач втрата ключа означає втрату реального стану — там правильний вибір ближчий до noeviction з окремим, достатньо великим лімітом пам'яті.

04 Pub/Sub проти Streams

Дві різні моделі "надіслати повідомлення багатьом" усередині одного Redis.

Pub/Sub (PUBLISH channel message / SUBSCRIBE channel) — модель "вистрілив і забув": повідомлення миттєво розсилається всім, хто в цю мить підписаний на канал, і ніде не зберігається. Якщо в момент публікації підписників немає — повідомлення втрачається назавжди, без жодного сліду. Підходить для сценаріїв на кшталт "розіслати сповіщення про live-оновлення всім активним WebSocket-з'єднанням прямо зараз", де відсутність історії — прийнятна ціна за простоту.

Redis Streams (XADD/XREAD/XREADGROUP) — структура даних, що поводиться як журнал доповнення (append-only log): кожен запис зберігається з унікальним ID і лишається доступним для читання навіть після публікації. Streams підтримують consumer groups — кілька споживачів можуть ділити між собою обробку одного потоку так, щоб кожен запис обробив рівно один із них, з підтвердженням (XACK) і можливістю повторно прочитати необроблені записи після збою споживача. Це вже набагато ближче до повноцінної черги повідомлень, ніж до простого сповіщення.

Практичне правило
Якщо втрата повідомлення при відсутності живого підписника прийнятна — Pub/Sub. Якщо кожне повідомлення обов'язково має бути оброблене рівно один раз, навіть якщо споживач у момент публікації офлайн чи впав, — Streams (або окрема черга на кшталт того, як Celery в цьому проєкті вже використовує Redis, розділ 5).

05 Redis як брокер Celery: broker vs backend

Прив'язано напряму до app/workers/celery_app.py цього проєкту.

Celery розділяє дві принципово різні ролі, і в конфігурації цього проєкту обидві закриті однією й тією самою Redis-URL:

app/workers/celery_app.py
celery_app = Celery(
    "ai_delivery_planner",
    broker=settings.REDIS_URL,
    backend=settings.REDIS_URL,
)
  • Broker — місце, куди FastAPI-обробник кладе повідомлення "виконай задачу X із аргументами Y", і звідки Celery-воркер це повідомлення забирає. Це, по суті, черга задач.
  • Backend — місце, куди воркер після виконання задачі записує результат (або факт помилки), щоб той, хто задачу запустив, міг пізніше запитати статус чи отримати повернуте значення через AsyncResult.
⚠️
Компроміс, який варто вміти назвати: використання однієї Redis-URL і для broker, і для backend — цілком нормальне рішення для невеликого чи раннього проєкту (саме так налаштовано тут), але на більшому навантаженні трафік черги задач і трафік результатів починають конкурувати за одні й ті самі ресурси одного інстансу. Типове масштабне рішення — розвести їх на окремі бази/інстанси Redis (наприклад, redis://.../0 для broker, redis://.../1 для backend), або взагалі винести backend в іншу систему (базу даних, RPC-результат).

Celery в глибину: at-least-once, ретраї, ідемпотентність

Ключова гарантія, яку варто знати про Celery ще до першого реального запуску таски: за замовчуванням він гарантує at-least-once виконання, а не "рівно один раз". Якщо воркер впаде після того як забрав задачу з черги, але до того як підтвердив (ack) її виконання брокеру — та сама задача повернеться в чергу й буде виконана повторно іншим (чи тим самим, після рестарту) воркером. З task_acks_late=True це вікно ризику навіть ширше й свідоме: підтвердження відправляється після успішного виконання, а не одразу після забору задачі — це безпечніше для довгих задач (переживає падіння воркера посеред роботи), але явно означає: таска може виконатись двічі з тими самими аргументами, і код таски зобов'язаний це пережити коректно.

✅
Обидві таски цього проєкту вже ідемпотентні за задумом. optimize_routes_task(route_request_id) і analyze_delivery_list_task(import_batch_id) приймають лише ID вже наявного запису, а не "команду щось додати" — повторний виклик з тим самим ID означає перерахувати той самий маршрут чи той самий аналіз наново й перезаписати результат за тим самим ключем, а не створити другий дублікат. Це саме той принцип "ідентифікатор, а не дія", який уже розібраний для HTTP-запитів у турі 2, розділ 8 — тут той самий підхід, тільки застосований до задач черги, а не до HTTP POST.

Механіка ретраю зсередини самої таски — те, чого поки немає в жодному з двох стабів, але знадобиться одразу, як вони перестануть бути заглушками:

типовий retry з backoff (не з реального коду — стаби не мають retry)
@celery_app.task(
    name="optimize_routes_task",
    bind=True,                 # bind=True дає доступ до self.retry(...)
    autoretry_for=(ConnectionError,),
    retry_backoff=True,        # 1с → 2с → 4с → ... замість фіксованої паузи
    max_retries=3,
)
def optimize_routes_task(self, route_request_id: str) -> None:
    ...

autoretry_for перелічує винятки, при яких Celery сам, автоматично, повторить таску (типово — тимчасові мережеві збої: втрачене з'єднання з базою чи зовнішнім геокод-API); винятки поза цим списком (наприклад, помилка валідації вхідних даних) одразу позначають таску як провалену без жодної спроби повтору, бо повторний запуск із тими самими "поганими" даними так само провалиться знову.

Canvas: chain, group, chord

Це API Celery для складання кількох задач в один робочий процес — жодна з них сьогодні не використовується в цьому проєкті (обидві таски викликаються поодинці, якщо взагалі викликаються), але типова наступна сходинка, як тільки з'явиться більше однієї пов'язаної фонової задачі:

  • chain(a, b, c) — послідовний конвеєр: результат a стає аргументом b, результат b — аргументом c. Кожен крок чекає завершення попереднього.
  • group(a, b, c) — паралельний віяловий запуск: усі три таски стартують одночасно, незалежно одна від одної, і не чекають одна на одну.
  • chord(group(...), callback) — group із додатковим зворотним викликом, що спрацьовує рівно один раз, коли всі задачі групи завершились — типовий патерн "розпаралель роботу, а тоді зведи результати докупи".
💡
Гіпотетичний приклад для цього проєкту: якби геокодування адрес при імпорті доставок (сьогодні — послідовний цикл, тур 2, розділ 7) колись переїхало у фонові таски, природна композиція виглядала б як chord(group(geocode_row.s(r) for r in rows), finalize_import_batch.s()) — геокодувати всі рядки паралельно, а після того як останній з них завершиться, рівно один раз запустити фінальну таску, що зведе статуси в один звіт по всьому батчу.

06 Атомарність: INCR, EXPIRE і гонитва станів

Туторіал 18 (питання 12) уже пояснив, навіщо потрібен спільний атомарний лічильник для rate limiting. Тут — про те, як його коректно побудувати, і де ховається типова пастка.

Наївний спосіб реалізувати "лічильник запитів за вікно часу з автоматичним скиданням" виглядає як дві команди підряд:

наївна, ламка версія
count = redis.incr(key)      # 1) збільшити лічильник
if count == 1:
    redis.expire(key, 60)    # 2) якщо це перший запит у вікні — поставити TTL

Проблема — між кроком 1 і кроком 2 процес може впасти (або мережевий виклик expire може не дійти) саме тоді, коли count == 1. Результат: ключ назавжди лишається без TTL і ніколи природно не скидається — лічильник "протікає" й рано чи пізно назавжди блокує клієнта, для якого мало бути тимчасове обмеження.

Три способи закрити цю прогалину коректно:

  • SET key value EX seconds NX — атомарно "встановити значення й TTL одночасно, лише якщо ключа ще не існує" — годиться, коли лічильник по суті булевий (є запис у вікні чи ні).
  • MULTI/EXEC (транзакція Redis) — обидві команди (INCR і EXPIRE) відправляються в одному пакеті й гарантовано виконуються без переривання іншими клієнтами між ними.
  • Lua-скрипт через EVAL — найгнучкіший варіант: уся логіка "інкремент + умовний expire" виконується на самому сервері Redis як єдина атомарна операція, без жодного проміжного мережевого кроку між частинами.
✅
Саме ця деталь — типовий "просунутий" наступний крок після базового питання туторіалу 18 про rate limiting: кандидат, який знає що Redis тут потрібен, і кандидат, який ще й знає про цю конкретну гонитву станів та її виправлення — це помітно різний рівень глибини на співбесіді.

07 Sentinel проти Cluster

Дві різні відповіді на питання "а що, як Redis впаде чи не влізе в один інстанс".

Redis Sentinel вирішує проблему доступності: група Sentinel-процесів постійно моніторить одну пару "primary + репліки", і якщо primary стає недоступним — автоматично призначає нову primary серед реплік і повідомляє клієнтів про нову адресу. Дані ті самі, просто з відмовостійкістю; обсяг даних, який влазить в один Redis-інстанс, не змінюється.

Redis Cluster вирішує іншу проблему — горизонтальне масштабування обсягу: весь простір ключів ділиться на 16384 хеш-слоти, розподілені між кількома вузлами. Кожен ключ детерміновано потрапляє в конкретний слот (за хешем ключа), і клієнт із самого початку знає, до якого вузла звертатись. Це дозволяє тримати набір даних, що не влазить в оперативну пам'ять жодної окремої машини.

Коли що
Потрібна лише стійкість до падіння одного вузла, а дані й так влазять в один інстанс — Sentinel. Дані фізично не влазять в один інстанс (обсяг, а не відмовостійкість) — Cluster. Для масштабу цього проєкту сьогодні не потрібне жодне з двох: один невеликий Redis-інстанс з головою покриває чергу Celery-задач і майбутній лічильник rate limiting.

08 Патерни кешування: aside / through / behind

Загальна ідея, яка не прив'язана лише до Redis — але саме на Redis її найчастіше й реалізують на бекенді.

ПатернХто пише в кеш і коли
Cache-aside (lazy loading) Застосунок сам перевіряє кеш; при промаху — читає з основної бази й сам же кладе результат у кеш. Найпоширеніший патерн: простий, кеш і база незалежні, але між записом у базу й оновленням кешу можливе тимчасове неузгодження.
Write-through Кожен запис одразу йде і в кеш, і в основну базу синхронно, як одна операція. Кеш завжди узгоджений з базою, ціна — трохи вищий час запису.
Write-behind (write-back) Запис одразу підтверджується клієнту після потрапляння в кеш, а в основну базу відкладено скидається пізніше, асинхронно, пачками. Найшвидший запис, але з ризиком втрати останніх змін, якщо кеш впаде до фактичного скидання в базу.

Це — той самий концептуальний вибір, який JS Doc, туторіал 14 уже розбирав із боку браузера й CDN (TTL проти явної інвалідації кешу): різниця лише в тому, що там кеш живе в браузері чи на CDN-вузлі, а тут — у Redis на бекенді. Сам компроміс "швидкість проти свіжості даних" — однаковий по всьому стеку.

09 Питання для співбесіди

Нові питання, яких немає в категорії C туторіалу 18 (там уже є: чому Redis швидкий попри однопотоковість, RDB/AOF, структури даних, навіщо спільний лічильник для rate limiting).

01У Celery є поняття broker і backend — у чому різниця, і чим ризикований той факт, що в цьому проєкті вони налаштовані на одну й ту саму Redis-URL?

Broker — черга, куди кладуться повідомлення "виконай задачу", і звідки їх забирають воркери. Backend — місце, куди воркер пише результат виконання, щоб той, хто задачу запустив, міг пізніше його прочитати. В celery_app.py цього проєкту обидві ролі використовують один REDIS_URL — прийнятно для невеликого масштабу, але на більшому навантаженні трафік черги й трафік результатів починають конкурувати за ресурси одного інстансу; типове рішення на зростанні — розвести їх на окремі бази чи інстанси Redis.

02Лічильник побудований як INCR, а потім, окремою командою, EXPIRE. Що станеться, якщо процес впаде рівно між цими двома викликами — і як це виправити?

Ключ отримає збільшене значення, але ніколи не отримає TTL — а отже, ніколи природно не скинеться, і лічильник "протікає" назавжди. Виправлення: атомарний SET key value EX seconds NX (коли лічильник булевий), транзакція MULTI/EXEC, або Lua-скрипт через EVAL, що виконує інкремент і умовний expire як одну неподільну операцію на сервері.

03Чим Pub/Sub у Redis принципово відрізняється від Redis Streams?

Pub/Sub — "вистрілив і забув": повідомлення нікуди не зберігається, і якщо в момент публікації немає живих підписників — воно втрачається безслідно. Streams — журнал доповнення з унікальними ID записів, що лишаються доступними для читання й підтримують consumer groups: кілька споживачів ділять обробку потоку, з підтвердженням і можливістю повторно прочитати необроблене після збою.

04Які є політики eviction у Redis, і яку з них варто обрати для чистого кешу, а яку — для черги задач, яку не можна втрачати?

noeviction, allkeys-lru, volatile-lru, allkeys-lfu, volatile-ttl, allkeys-random. Для чистого кешу — allkeys-lru чи allkeys-lfu (втрата ключа коштує лише зайвого походу в джерело даних). Для черги задач чи іншого стану, втрату якого неможливо компенсувати, — noeviction із достатнім лімітом пам'яті, щоб узагалі не доходило до вибору, що видаляти.

05Чому Redis використовує і ліниву, і активну експірацію ключів одночасно, а не лише один із цих механізмів?

Чиста лінива експірація (перевірка TTL лише при зверненні до ключа) лишала б у пам'яті назавжди ключі, до яких ніхто вже не звертається. Чиста активна експірація (лише фоновий цикл) не гарантувала б миттєвого прибирання протермінованого ключа саме в момент звернення. Разом вони покривають обидва випадки: гарячі ключі прибираються одразу при читанні, холодні — фоновим циклом вибіркового сканування.

06Чим Redis Sentinel відрізняється від Redis Cluster — яку проблему вирішує кожен?

Sentinel вирішує доступність: моніторить пару primary+репліки й автоматично перемикає primary при падінні, без зміни обсягу даних, що зберігаються. Cluster вирішує масштаб обсягу: шардує простір ключів на 16384 хеш-слоти між кількома вузлами, дозволяючи тримати набір даних, що не влазить у пам'ять однієї машини.

07Який реальний статус Redis у цьому проєкті сьогодні — і що саме має статись, щоб він почав реально використовуватись у продовому трафіку?

Redis повністю сконфігурований (REDIS_URL, Celery broker+backend), але жодна Celery-задача (optimize_routes_task, analyze_delivery_list_task) сьогодні не реалізована — обидві кидають NotImplementedError і ніде не викликаються, оскільки обробка маршруту й аналіз списку виконуються синхронно в самому запиті. Тригер для реального увімкнення — момент, коли синхронна обробка стане надто повільною для одного HTTP-запиту (наприклад, довгий OR-Tools solve) і задачі реально підуть у чергу Celery.

08Чому rate limiting цього проєкту сьогодні in-memory, а не Redis-backed — і що конкретно зламається, якщо додати другий інстанс без цієї зміни?

Бо весь деплой сьогодні свідомо обмежений одним процесом (min_machines_running = 1 у fly.toml) — за таких умов простий dict у пам'яті бачать усі запити однаково добре, і Redis був би зайвою мережевою залежністю без користі. Якщо додати другий інстанс без зміни лічильника, кожен процес матиме власний окремий словник лічильників — реальний ліміт запитів на клієнта фактично подвоїться (чи помножиться на кількість інстансів), бо жоден процес не бачить лічильник іншого.

09Що таке Valkey, і чому команда сьогодні може свідомо обрати його замість Redis?

Valkey — форк Redis під Linux Foundation, створений після зміни ліцензії Redis Ltd. з відкритої BSD на більш обмежувальну (SSPL/RSALv2) у 2024 році. Протокол і команди сумісні з Redis, тому вибір здебільшого не технічний, а організаційний/ліцензійний — команди й хмарні провайдери, яким важлива саме відкрита ліцензія, переходять на останню відкриту гілку, яку продовжує розвивати спільнота.

10Коли варто обрати Memcached замість Redis?

Коли реально потрібен лише найпростіший кеш "ключ → рядок байтів", без структур даних, без персистентності на диск, без pub/sub — і важлива нативна багатопотокова обробка команд "з коробки". Якщо потрібно щось із розширеного функціоналу Redis (списки, множини, TTL-політики, Streams, транзакції) — Memcached цього просто не має.

11Чим транзакція Redis (MULTI/EXEC) відрізняється від "справжньої" ACID-транзакції в реляційній базі?

Redis гарантує, що всі команди між MULTI і EXEC виконаються без переривання іншим клієнтом (ізольований пакет), але не гарантує відкату при помилці під час виконання самої команди (наприклад, операція над ключем неправильного типу) — попередні команди пакету все одно застосуються. Реляційна ж транзакція здатна повністю відкотити всі зміни при будь-якій помилці всередині неї. Redis перевіряє лише помилки постановки в чергу (наприклад, синтаксис команди) ще до виконання пакету.

12Що таке cache-aside, write-through і write-behind — і який компроміс лежить в основі вибору між ними?

Cache-aside — застосунок сам читає з кешу, при промаху йде в базу й сам оновлює кеш; write-through — кожен запис синхронно йде і в кеш, і в базу; write-behind — запис одразу підтверджується з кешу, а в базу скидається пізніше асинхронно. Компроміс той самий, що й у будь-якому кешуванні: cache-aside й write-through безпечніші, але повільніші на запис; write-behind найшвидший, але ризикує втратити останні зміни, якщо кеш впаде до скидання в базу.

13Якщо в майбутньому в цьому проєкті реально ввімкнути персистентність Redis (RDB чи AOF) на Fly.io, про що додатково доведеться подбати?

Про постійний том (persistent volume), змонтований у контейнер саме під директорію, де Redis зберігає файл дампу — інакше при кожному передеплої (новий контейнер) файл persistence зникне разом зі старим контейнером, і Redis почне з порожньої бази. Це та сама категорія проблеми, яку для PostgreSQL цього проєкту вирішує керована база даних, а не контейнер додатку.

14У чому суть TTL-інвалідації кешу проти явної інвалідації — і де в цьому ж стеку вже розбирався той самий компроміс з іншого боку?

TTL-інвалідація — кеш сам протухає через фіксований час, просто й передбачувано, але якщо джерело даних змінилось раніше — клієнт короткий час бачить застарілі дані. Явна інвалідація — код сам видаляє чи оновлює конкретний ключ одразу в момент зміни джерела: завжди свіжо, але вимагає не забути інвалідувати кеш у кожному місці, де дані змінюються. Точно той самий компроміс уже розібраний з боку браузера й CDN у JS Doc, туторіалі 14 — різниця лише в тому, який шар стека тримає кеш.

10 Підсумок

Головне з цього туторіалу:

  • Redis — key-value сховище в оперативній пам'яті; головні ролі — кеш, сесії, брокер черги задач, атомарні лічильники.
  • Аналоги: Memcached (простіший, без структур і персистентності), Valkey (BSD-форк після зміни ліцензії Redis), KeyDB/Dragonfly (багатопотокові альтернативи), або взагалі простий in-process dict, як сьогодні в цьому проєкті.
  • У цьому проєкті Redis повністю сконфігурований для Celery (broker і backend — одна URL), але обидві задачі — заглушки, тож у продовому трафіку Redis сьогодні мовчить; min_machines_running = 1 у fly.toml — пряме наслідок того, що rate limiting ще не переїхав з in-memory лічильника в Redis.
  • TTL живе через ліниву + активну експірацію; eviction policies вирішують, що робити, коли пам'яті бракує; Pub/Sub — без збереження, Streams — з журналом і consumer groups.
  • Атомарність INCR+EXPIRE — класична пастка гонитви станів; правильне рішення — SET NX EX, транзакція, або Lua-скрипт.
  • Sentinel вирішує доступність, Cluster — горизонтальний обсяг; жодне з двох сьогодні цьому проєкту не потрібне.
