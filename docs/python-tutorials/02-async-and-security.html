Частина I · Асинхронність

1 Event loop: та сама модель, що й у браузері

Найкраща новина для фронтендера: Python-async тут концептуально ідентичний JS.

Аналогія з фронтендом
async def / await у Python — це той самий event loop, до якого ви звикли в JS: один потік, кооперативна багатозадачність, await "віддає" керування цикл-у, поки чекає на I/O (мережа, диск, БД), і продовжує виконання, коли результат готовий. Різниця лише в тому, що в Node event loop один на весь процес "з коробки", а в Python його треба явно запустити (uvicorn робить це за вас).

Ключове правило, однакове для обох мов: async сам по собі не дає паралелізм для CPU-важкої роботи. Він дає паралелізм лише для I/O-очікування (мережа, БД, диск). Якщо всередині async def виконати важкі обчислення синхронно — вони заблокують той самий єдиний потік, і всі інші запити, що чекають на event loop, зависнуть. Це не теорія — нижче показано реальне місце в цьому проєкті, де саме так і сталося (розділ 6).

2 Async у FastAPI-запиті

Кожен ендпоінт у проєкті оголошений як async def — і це не просто стиль.

app/main.py
@app.get("/health")
async def health() -> dict:
    return {"status": "ok"}

FastAPI (через Starlette) виконує async def-ендпоінти прямо в event loop, без переключення потоків. Це дешево і швидко для I/O-навантажених операцій — а весь цей бекенд саме такий: майже кожен запит зрештою чекає на щось зовнішнє (Postgres, OpenAI, Google Maps).

💡
Якби ендпоінт був оголошений як звичайний def (не async), FastAPI сам запустив би його в окремому потоці з пулу — це теж працює, але для суто I/O-навантаженого коду async def ефективніший: не треба створювати потік на кожен запит.

3 Async база даних

SQLAlchemy 2.0 в async-режимі поверх asyncpg — жоден запит до БД не блокує event loop.

app/db/session.py
engine = create_async_engine(
    settings.DATABASE_URL,   # postgresql+asyncpg://...
    echo=settings.DEBUG,
    future=True,
    connect_args={"statement_cache_size": 0},
)

AsyncSessionLocal = async_sessionmaker(
    bind=engine, class_=AsyncSession, expire_on_commit=False,
)

async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        yield session
  • expire_on_commit=False — після commit() об'єкти (наприклад, щойно створена Delivery) лишаються "живими" й читабельними без додаткового SQL-запиту. Без цього прочитати delivery.address після коміту викликало б новий implicit SELECT.
  • statement_cache_size=0 — вимикає підготовлені стейтменти на стороні asyncpg. Потрібно, коли БД стоїть за pgbouncer/пулером з'єднань у transaction-pooling режимі (типово для хмарного Postgres) — інакше кеш стейтментів плутається між різними фізичними з'єднаннями.
  • get_session() — async generator, який FastAPI використовує як DI-залежність (get_db у dependencies.py): сесія відкривається на початку запиту й гарантовано закривається наприкінці, навіть якщо всередині виникла помилка — завдяки async with.

4 Async HTTP-клієнти для зовнішніх API

Google Geocoding і OpenAI викликаються через асинхронні клієнти — інакше запит до зовнішнього сервісу (сотні мілісекунд) заморозив би весь процес.

app/services/geocoding/client.py
async def geocode_full(self, address: str) -> GeocodeResult | None:
    if not self.api_key:
        return None
    params = {"address": address, "key": self.api_key}
    try:
        async with httpx.AsyncClient(timeout=10) as client:
            response = await client.get(GEOCODE_URL, params=params)
    except httpx.HTTPError:
        return None
    # ... парсинг відповіді, з поверненням None на будь-яку "очікувану" невдачу

Той самий підхід для OpenAI — клієнт AsyncOpenAI (SDK-обгортка на httpx) у services/ai/client.py. Обидва мають timeout — важливо: без таймауту "завислий" зовнішній сервіс міг би тримати запит (і, непрямо, ресурси процесу) необмежено довго.

Аналогія з фронтендом
httpx.AsyncClient ≈ fetch у браузері з AbortController-таймаутом. AsyncOpenAI ≈ офіційний JS SDK OpenAI, який теж повертає Promise. Різниця лише синтаксична (await замість .then()), поведінка — та сама.

5 Добре Блокуючий код винесено в окремий потік

Відправка email через smtplib — синхронна бібліотека (немає async-версії). Ось як з нею правильно працювати всередині async-застосунку.

app/services/notifications/email.py
def _send_via_gmail(*, to, subject, html, sender, app_password) -> None:
    """Blocking SMTP send — always called via `asyncio.to_thread`."""
    message = MIMEMultipart("alternative")
    ... 
    with smtplib.SMTP_SSL(SMTP_HOST, SMTP_PORT, timeout=10) as smtp:
        smtp.login(sender, app_password)
        smtp.sendmail(sender, [to], message.as_string())


async def send_verification_email(email: str, token: str) -> None:
    ...
    try:
        await asyncio.to_thread(
            _send_via_gmail,
            to=email, subject="Verify your email address",
            html=_verification_email_html(verification_url),
            sender=settings.GMAIL_ADDRESS, app_password=settings.GMAIL_APP_PASSWORD,
        )
    except smtplib.SMTPException:
        logger.exception("Failed to send verification email to %s", email)

asyncio.to_thread(...) запускає синхронну функцію в окремому потоці з пулу й асинхронно чекає на результат — event loop лишається вільним обробляти інші запити, поки лист відправляється в фоновому потоці. Це правильний патерн для "старих", блокуючих бібліотек, яким немає async-заміни.

Аналогія з фронтендом
Схоже на Web Worker для важкої синхронної роботи — не блокує головний потік (UI), виконуючи роботу окремо і повертаючи результат через "проміс".

6 Погано Реальне вузьке місце: OR-Tools блокує event loop

А ось приклад, де той самий принцип із розділу 5 не застосований — і це справжня, наявна в коді проблема, а не вигаданий приклад.

app/services/route_optimizer/service.py
async def optimize(self, payload: OptimizeRequest) -> OptimizeResult:
    # ... await-виклики до репозиторіїв (це ОК, вони I/O) ...

    solver = RouteSolver(problem)
    solver.build_model()
    result = solver.solve()      <-- СИНХРОННИЙ виклик, без await і без to_thread!
app/services/route_optimizer/solver.py
def solve(self) -> SolveResult:
    search_parameters = pywrapcp.DefaultRoutingSearchParameters()
    ...
    search_parameters.time_limit.FromSeconds(5)   # OR-Tools може рахувати до 5 секунд
    assignment = self.routing.SolveWithParameters(search_parameters)
    ...

solver.solve() — це чиста CPU-робота (комбінаторна оптимізація маршрутів через Google OR-Tools), яка може тривати до 5 секунд за налаштованим лімітом. Метод optimize() оголошений як async def, і всередині є коректні await до бази даних — але сам виклик солвера звичайний, синхронний. Python не "переключить" виконання на інший запит усередині синхронного виклику: увесь event loop процесу стоїть, поки триває пошук рішення.

❌
Наслідок: поки один користувач чекає на POST /routes/optimize, жоден інший запит на цьому ж процесі — навіть простий GET /health — не обробляється, бо єдиний потік event loop зайнятий обчисленнями OR-Tools. При одному uvicorn-воркері (а саме так задеплоєно зараз — див. туторіал 3) це означає: важкий запит оптимізації тимчасово "заморожує" весь сервіс для всіх користувачів.
✅
Як це можна виправити (той самий патерн, що вже застосований у розділі 5): result = await asyncio.to_thread(solver.solve) — переносить CPU-роботу в окремий потік, event loop лишається вільним для решти запитів. Ще надійніший варіант для CPU-bound роботи — ProcessPoolExecutor (окремий процес, а не потік — обходить Python GIL повністю) або офлоад у Celery-воркер (черга Redis уже підключена в проєкті, див. розділ 3 туторіалу про масштабування — задачі там поки заготовки з NotImplementedError).

7 Послідовні await у циклі — не завжди помилка

Ще одне місце, де на перший погляд "варто було б" використати asyncio.gather — але тут це свідомий вибір, а не недогляд.

app/services/deliveries/service.py
for row_number, raw_row in enumerate(raw_rows, start=1):
    if quota_exhausted:
        # ... позначити рядок як пропущений, next
        continue
    try:
        normalized = normalize_row(raw_row)
        created = await self._create_from_fields(normalized.model_dump())  # геокодує ОДИН рядок за раз
    except QuotaExceededError as exc:
        quota_exhausted = True
        # ...

При імпорті CSV/Excel кожен рядок геокодується послідовно, один await за раз — не паралельно через asyncio.gather. Це виглядає як "повільно", але є причина:

  • Квота перевіряється атомарно перед кожним рядком. Якщо запустити 100 геокод-запитів паралельно, неможливо коректно зупинитись рівно на межі ліміту "за замовленням" — частина запитів уже піде до платного Google API до того, як стане відомо, що ліміт вичерпано.
  • Порядок помилок має значення для UX. Результат імпорту повертає статус по кожному рядку окремо (DeliveryImportRowResult) — послідовна обробка гарантує, що рядки з 1 по N оброблені саме в тому порядку, в якому вони прийшли у файлі.
⚠️
Trade-off: для файлу з 500 рядків це може означати 500 послідовних мережевих round-trip-ів до Google Maps API — повільніше, ніж могло б бути. Якби квота не була prepaid-обмеженням, а лише "м'яким" лічильником, паралелізація через asyncio.gather була б доречною. Тут — це усвідомлена ціна за коректність квоти, а не забутий "gather".
Частина II · Безпека

1 Аутентифікація: паролі й JWT

Паролі ніколи не зберігаються у відкритому вигляді; сесія тримається на JWT, а не на server-side session/cookie.

app/core/security.py
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(plain_password: str) -> str:
    return pwd_context.hash(plain_password)

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password, hashed_password)

def _create_token(subject: str, token_type: str, expires_delta: timedelta) -> str:
    now = datetime.now(UTC)
    claims = {"sub": subject, "type": token_type, "iat": now, "exp": now + expires_delta}
    return jwt.encode(claims, settings.JWT_SECRET, algorithm=settings.JWT_ALGORITHM)
  • bcrypt — повільний навмисно (адаптивна вартість), щоб brute-force підбір хешу був економічно недоцільним навіть при витоку бази.
  • exp (expiry) — кожен токен має час життя; протухлий токен jwt.decode(...) відхилить сам, без додаткової логіки.
  • Підпис (JWT_SECRET) гарантує, що клієнт не може сам собі згенерувати валідний токен чи змінити sub (id користувача) в існуючому.

2 access vs refresh — навіщо поле type

Маленька деталь із великим значенням для безпеки.

app/core/dependencies.py
async def get_current_user(token: str = Depends(oauth2_scheme), ...) -> User:
    claims = decode_token(token)
    ...
    if claims.get("type") != "access":     <-- refresh-токен тут відхиляється
        raise credentials_error

Access і refresh токени підписані тим самим секретом і мають однакову структуру — без поля type сервер не зміг би відрізнити один від іншого. Refresh-токен живе довше (7 днів проти 30 хвилин) і призначений лише для обміну на нову пару токенів через /auth/refresh. Без цієї перевірки клієнт міг би підсунути довгоживучий refresh-токен як access — і отримати доступ до захищених ендпоінтів на набагато довший термін, ніж задумано.

✅
Той самий трюк повторюється для токена підтвердження email ("type": "email_verification", живе 24 години) — його теж неможливо використати як access-токен, навіть якщо він десь "просочиться" (наприклад, у логах листування).

3 Email-верифікація закриває дірку, яку rate limiting не закриває

Ліміт на реєстрацію по IP (розділ 4) обмежує швидкість створення акаунтів, але не заважає створити акаунт із чужою чи фейковою поштою.

app/api/auth/router.py
if not user.is_verified:
    raise HTTPException(
        status_code=status.HTTP_403_FORBIDDEN,
        detail="Please verify your email before logging in",
    )

Акаунт створюється одразу (is_verified=False), але увійти в нього не можна, поки власник не перейде за посиланням із листа. Це означає: масове створення акаунтів через ботів все ще можливе (обмежено rate limit-ом), але ці акаунти — непридатні, доки хтось реально не відкриє поштову скриньку. Разом ці два механізми закривають і швидкість, і "реальність" реєстрацій.

4 Rate limiting по IP

Простий, свідомо не Redis-based лічильник — з чіткою межею того, для чого він придатний.

app/core/rate_limiting.py
"""Simple per-IP fixed-window rate limiting for unauthenticated endpoints
(registration, login) where the caller has no organization yet...

In-memory, not Redis-backed: nothing in this deployment assumes more than a
single API process ... If this ever runs as multiple worker processes or
instances, swap the in-memory `_WINDOWS` dict for a Redis-backed counter"""

register_rate_limiter = rate_limit_by_ip("register", max_requests=5, window_seconds=3600)
login_rate_limiter = rate_limit_by_ip("login", max_requests=20, window_seconds=60)

5 реєстрацій/годину з однієї IP — головний важіль проти масового скриптового сайн-апу. 20 логінів/хвилину — достатньо вільно для реальних спроб/помилок людини, але сповільнює credential-stuffing/brute-force атаки на один акаунт з однієї IP.

⚠️
Лічильник живе в пам'яті процесу (Python dict + Lock). Це працює бездоганно, поки застосунок — один процес. Розгорніть два інстанси за балансувальником — і кожен вестиме свій окремий рахунок, а реальний ліміт на одного атакуючого фактично подвоїться. Це прямий наслідок для масштабування — детальніше в туторіалі 3.

5 Ізоляція тенантів — головний захист від IDOR

Найважливіший, хоч і не завжди "видимий" механізм безпеки в проєкті — вже показаний у туторіалі 1, тут — чому це саме security-механізм.

IDOR (Insecure Direct Object Reference) — коли користувач А, підставивши в URL id чужого ресурсу (GET /deliveries/{id}), отримує дані користувача Б. Це один із найпоширеніших класів вразливостей у multi-tenant SaaS. У цьому проєкті його структурно неможливо допустити випадково — тому що TenantScopedRepository.get() завжди фільтрує по organization_id, взятому з JWT поточного користувача, а не з тіла запиту чи параметра URL.

✅
Спроба звернутись до чужого route_id поверне звичайний 404 "не знайдено" — не 403 "заборонено". Це теж навмисно: 403 підтвердив би зловмиснику, що ресурс існує, просто недоступний; 404 не дає такої інформації взагалі.

6 Захист від зловживання платними зовнішніми API

OpenAI та Google Geocoding коштують грошей за кожен виклик — квоти захищають гаманець, а не лише "чесність" використання.

app/repositories/organization_repository.py
async def try_consume_quota(self, organization_id, *, counter_column, limit, amount=1, combined_limit=None) -> bool:
    """... A single conditional `UPDATE ... WHERE ...`, not a separate
    check-then-write, so concurrent requests against the same
    organization can't race past either cap."""
    column = getattr(Organization, counter_column)
    stmt = update(Organization).where(Organization.id == organization_id)
    if limit is not None:
        stmt = stmt.where(column + amount <= limit)     # перевірка й запис — ОДНА SQL-команда
    stmt = stmt.values(**{counter_column: column + amount})
    result = await self.session.execute(stmt)
    await self.session.commit()
    return result.rowcount > 0

Це класичний приклад захисту від race condition типу TOCTOU (time-of-check-to-time-of-use). Наївна реалізація виглядала б так:

❌
Погано (гіпотетичний код, не з проєкту): if org.ai_calls_count < limit: org.ai_calls_count += 1; await session.commit() — два одночасні запити можуть обидва прочитати "ще є ліміт" ще до того, як хтось встигне записати інкремент, і обидва пройдуть — org перевищить ліміт. При платних AI-викликах це пряма фінансова діра.

У реальному коді перевірка й запис — один SQL-запит (UPDATE ... WHERE column + 1 <= limit). База даних гарантує атомарність: або рядок оновиться (і квота витрачена), або WHERE не спрацює й rowcount буде 0 — без вікна, в якому дві паралельні транзакції можуть "проскочити" одночасно.

7 Приховування внутрішніх деталей помилок

Жодна відповідь API не повинна "проговоритись" про внутрішній устрій системи.

app/core/error_handlers.py
@app.exception_handler(OpenAIError)
async def handle_openai_error(request: Request, exc: OpenAIError) -> JSONResponse:
    # Outages/rate limits/auth issues from the OpenAI SDK must never
    # leak its own error text (which can include request ids and other
    # internal details) straight to the client.
    logger.error("OpenAI API error on %s %s: %s", request.method, request.url.path, exc)
    return JSONResponse(status_code=503, content={"detail": "The AI service is temporarily unavailable..."})

@app.exception_handler(Exception)
async def handle_unexpected_error(request: Request, exc: Exception) -> JSONResponse:
    logger.exception("Unhandled error on %s %s", request.method, request.url.path)
    return JSONResponse(status_code=500, content={"detail": "Something went wrong on our end..."})

Без цих обробників необроблений виняток повернув би клієнту сирий traceback (потенційно — назви внутрішніх функцій, шляхи файлів, фрагменти SQL, ключі API у тексті помилки SDK). Тут повне повідомлення завжди йде тільки в лог сервера (logger.exception(...)), а клієнту — уніфіковане, безпечне повідомлення.

8 CORS — явний список джерел

fly.toml (production env)
CORS_ORIGINS = '["https://ai-planning-assistant.vercel.app"]'

У продакшені дозволений лише конкретний домен фронтенду — не ["*"]. У парі з allow_credentials=True (в main.py) це особливо важливо: браузери й так забороняють комбінацію "credentials + wildcard origin", але явний список — правильна практика незалежно від цього.

9 Чесно: чого в проєкті ще немає

Частина "hardening"-роботи вже зроблена (rate limiting, email-верифікація, квоти — додані одним заходом після аудиту), але варто знати межі поточного захисту.

  • Немає revoke/rotation refresh-токенів. Якщо refresh-токен вкрадено, він лишається дійсним аж до природного закінчення терміну (7 днів) — немає server-side "чорного списку" відкликаних токенів.
  • Rate limiter не переживе горизонтальне масштабування без переходу на Redis (розділ 4 вище і туторіал 3).
  • Немає WAF/DDoS-захисту на рівні застосунку — покладається на периметр Fly.io/proxy.
  • CSRF свідомо не актуальний — API використовує bearer-токен у заголовку Authorization, а не cookie-based сесію, тому класична CSRF-атака (яка експлуатує автоматичну відправку cookie браузером) сюди не застосовується.

Це нормально для проєкту такого етапу — головне, що межі захисту явні й задокументовані, а не приховані.
