01 Наскільки великий цей проєкт зараз

Реальна конфігурація production-деплою на Fly.io.

fly.toml
[deploy]
  release_command = "alembic upgrade head"   # міграції БД перед кожним деплоєм

[http_service]
  internal_port = 8000
  auto_stop_machines = false
  auto_start_machines = true
  min_machines_running = 1        <-- рівно одна машина, завжди
  processes = ["app"]

[[vm]]
  size = "shared-cpu-1x"          # наймінімальніший платний тариф Fly
  memory = "512mb"
Машин
1

shared 1x

512 MB

Це — конфігурація "для одного продукту на ранній стадії", а не "для масштабу". Один Docker-контейнер (Dockerfile) запускає один процес uvicorn app.main:app без --workers N — тобто буквально один Python-процес з одним event loop обробляє всі HTTP-запити.

02 Чому саме одна машина — і чому це не випадковість

Два незалежні місця в коді прямо тримають систему прив'язаною до single-instance деплою.

⚠️
Причина 1 — rate limiter у пам'яті процесу (докладно в туторіалі 2). app/core/rate_limiting.py зберігає лічильники запитів у звичайному Python dict. Два інстанси = два незалежні лічильники = реальний ліміт подвоюється, і зловмисник може обійти захист, просто "влучаючи" в різні машини за балансувальником.
⚠️
Причина 2 — блокуючий OR-Tools солвер (докладно в туторіалі 2). solver.solve() виконується синхронно всередині async def optimize() і може займати до 5 секунд, увесь цей час монополізуючи єдиний потік event loop. При кількох uvicorn-воркерах у межах однієї машини це частково пом'якшується (кожен воркер — окремий процес з власним event loop), але сам факт блокування нікуди не зникає — просто "стеля" одночасних важких запитів зростає разом із кількістю воркерів, а не зникає.

Тобто: min_machines_running = 1 — не забудькуватість, а пряме відображення двох конкретних архітектурних рішень у коді. Це важливий урок: інфраструктурні обмеження часто "закодовані" не в конфігах деплою, а в самому застосунку.

03 Celery + Redis вже підключені — але поки не використовуються

У проєкті вже є "риштування" під фонові задачі — саме те, що знадобиться на кроці масштабування "d" нижче.

app/workers/tasks.py
@celery_app.task(name="optimize_routes_task")
def optimize_routes_task(route_request_id: str) -> None:
    """Run route optimization asynchronously and persist the result."""
    raise NotImplementedError

@celery_app.task(name="analyze_delivery_list_task")
def analyze_delivery_list_task(import_batch_id: str) -> None:
    raise NotImplementedError

REDIS_URL уже є в Settings, celery_app.py налаштований (Redis як broker і result backend), але самі задачі — заглушки. Сьогодні все, включно з 5-секундним солвером, виконується синхронно всередині HTTP-запиту. Це нормально для поточного навантаження, але саме тут — готовий, недобудований шлях до кроку "f" у драбині нижче.

04 Драбина масштабування — крок за кроком

Від найдешевшого й найшвидшого кроку до архітектурних змін. Кожен наступний крок стає потрібним лише тоді, коли попередній вичерпав себе.

Крок A

Вертикальне масштабування (більша машина)

Замінити shared-cpu-1x / 512mb на, наприклад, performance-cpu-2x / 2gb у fly.toml. Один рядок конфігурації, нуль змін коду. Дає більше "запасу", але не вирішує ні проблему in-memory rate limiter, ні блокуючий солвер — це все ще один процес, просто на потужнішому залізі. Стеля піднімається, але лишається стелею.

Крок B

Прибрати стан із процесу (rate limiter → Redis)

Необхідна передумова для будь-якого горизонтального масштабування. Замінити _WINDOWS: dict на Redis-лічильник (наприклад, через INCR + EXPIRE, чи бібліотеку на кшталт slowapi/limits з Redis-бекендом) — тоді всі інстанси бачать один спільний рахунок. Redis уже є в інфраструктурі (для Celery) — просто ще не використовується для цього.

Крок C

Прибрати CPU-важку роботу з event loop

Обгорнути solver.solve() в asyncio.to_thread(...) (найпростіше) або офлоадити оптимізацію в Celery-воркер (надійніше — окремий процес, не ділить GIL з веб-сервером; клієнт отримує 202 Accepted і опитує статус чи отримує результат через WebSocket/polling). Без цього кроку додавання машин лише зменшує ймовірність зіткнення двох важких запитів одночасно — не усуває саму проблему для кожної окремої машини.

Крок D

Горизонтальне масштабування (кілька машин/воркерів)

Після B і C — можна безпечно збільшити min_machines_running у fly.toml і/або додати --workers N до uvicorn. Fly.io сам балансує трафік між машинами. Застосунок стає stateless: будь-який інстанс може обробити будь-який запит, бо весь стан (сесії, квоти, rate limit) живе в Postgres/Redis, а не в пам'яті процесу.

Крок E

Пул з'єднань до бази даних

Кожен інстанс тримає власний пул asyncpg-з'єднань. N інстансів × розмір пулу не повинно перевищувати max_connections Postgres. Тут стає в пригоді pgbouncer/вбудований пулер хмарного Postgres (звідси й statement_cache_size=0 у db/session.py — код уже готовий працювати за пулером у transaction-режимі).

Крок F

Реальні фонові задачі через Celery

Активувати optimize_routes_task/analyze_delivery_list_task (прибрати NotImplementedError), запустити окремий Celery-воркер-процес (окремий Fly-машина або docker-compose сервіс). Довгі AI/оптимізаційні запити перестають блокувати HTTP-запит взагалі — API одразу повертає id задачі, фронтенд опитує статус.

Крок G

Кешування й read-репліки

Дашборд (services/dashboard/service.py) — типовий read-heavy ендпоінт. Кеш у Redis (з коротким TTL) чи read-репліка Postgres знімають навантаження з основної БД, не чіпаючи логіку запису.

🎯
Порядок важливий: B і C — обов'язкові передумови перед D. Додавання машин (D) без прибирання in-memory стану (B) і блокуючого коду (C) не дає того масштабування, яке очікується — і навіть послаблює захист від зловживань (подвоєний rate-limit ліміт з туторіалу 2).

05 Аналогія з тим, як масштабується фронтенд

Аналогія з фронтендом
Фронтенд масштабується здебільшого "безкоштовно" — статичні файли на CDN розходяться по edge-серверах по всьому світу, і кожен користувач звертається до найближчого. Бекенд так просто не копіюється: він тримає стан (з'єднання з БД, чергу задач, лічильники) — тому "скопіювати" бекенд-процес на кілька машин безпечно можна лише після того, як увесь цей стан винесено в спільне зовнішнє сховище (БД, Redis). Це і є ключова відмінність: фронтенд масштабується копіюванням статики, бекенд — копіюванням stateless-обчислень навколо спільного стану.

06 Інші архітектурні підходи для масштабування

Куди можна рухатись далі "драбини", якщо навантаження продовжить рости на порядки.

ПідхідІдеяКомпроміс
Одна VM (поточний стан) Один процес, вся логіка разом Найпростіше в експлуатації; жорстка стеля навантаження й ризик единої точки відмови
Кілька VM за балансувальником Горизонтальні репліки одного й того ж застосунку (кроки B–E) Потрібен stateless-дизайн; складніше налагоджувати ("на якій машині це сталось?")
Керовані контейнери (ECS / Kubernetes) Автоскейлінг за метриками, self-healing, rolling deploy Значно більша операційна складність; виправдано при десятках сервісів/високому й змінному навантаженні
Serverless-функції Кожен запит — окремий короткоживучий виклик, платиш лише за використання Погано підходить для OR-Tools-солвера: cold start + типові ліміти по часу виконання (десятки секунд) конфліктують із CPU-важким 5-секундним пошуком рішення; добре підходить для легких, епізодичних ендпоінтів
Event-driven мікросервіси Окремі сервіси (auth, routing, AI, notifications) спілкуються через чергу подій, а не прямі виклики Виправдано лише при дуже великій команді/навантаженні; для одного продукту такого розміру — передчасна складність
✅
Правильний наступний крок для цього проєкту — не стрибати одразу до Kubernetes чи мікросервісів, а пройти драбину A→G вище. Вона дає на порядки більший запас навантаження за набагато меншу операційну ціну.

07 Коли справді масштабувати (а коли — ще рано)

Масштабування "про запас" коштує складності вже сьогодні. Орієнтуйтесь на сигнали, а не на страх.

  • P95/P99 латентність ендпоінтів росте попри те, що запитів не побільшало — сигнал, що поточний процес уже "давиться".
  • Кілька важких /routes/optimize-запитів поспіль помітно сповільнюють прості ендпоінти (наприклад, /health) — пряме підтвердження проблеми з розділу 2 туторіалу про async.
  • Memory/CPU інстансу стабільно впирається у стелю (512 MB тут — досить тісно вже для одного OR-Tools-розрахунку + pandas-парсингу Excel одночасно).
  • Rate limit false positives — легітимні користувачі за спільним корпоративним IP/NAT впираються у ліміти, розраховані на "одну людину".

Без цих сигналів — інвестиція часу краще йде в фічі, а не в передчасну інфраструктуру.

08 Підсумок усіх трьох туторіалів

1. Архітектура — шарувата структура (api → services → repositories → db) з DI через Depends і структурною ізоляцією тенантів через TenantScopedRepository.

2. Async і безпека — event loop той самий, що в JS; блокуючий код правильно винесений у потік для email, але не для OR-Tools-солвера (реальне вузьке місце); безпека спирається на JWT з типізованими токенами, атомарні SQL-квоти й централізовану обробку помилок.

3. Масштабування — сьогодні проєкт навмисно single-instance через два конкретні місця в коді (rate limiter, солвер); шлях вперед — драбина з явним порядком кроків, а не "просто додати більше машин".

Усі три теми одна в одну впираються: архітектурні межі (тур. 1) визначають, де шукати проблеми з блокуванням і безпекою (тур. 2), а ці проблеми, своєю чергою, напряму визначають стелю масштабування (тур. 3).

Туторіал згенеровано на основі реального коду репозиторію ai-delivery-planner-backend — усі приклади й конфігурація відповідають фактичному стану проєкту на момент генерації.
