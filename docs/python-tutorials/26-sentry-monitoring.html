01 Sentry vs logging: інша задача, не заміна

Стандартне логування (туторіал 11) уже є в цьому проєкті. Sentry не замінює його — він вирішує іншу задачу, яку текстові логи вирішують погано.

logging пише розрізнені текстові рядки в stdout чи файл: кожен виклик logger.error(...) — окремий рядок, без жодного зв'язку з іншими рядками, крім сусідства за часом. Щоб зрозуміти, що насправді сталось, треба вручну grep-ати за timestamp і власноруч відновлювати картину: яка це помилка, чи траплялась вона раніше, скільки разів, у кого саме з користувачів. Sentry вирішує саме це:

Що самеlogging (тур. 11)Sentry
Групування Немає — кожен рядок незалежний Автоматичне: однакові помилки (за стек-трейсом) збираються в один Issue
Контекст падіння Те, що явно передали в logger.exception(...) Повний стек-трейс + значення локальних змінних у кожному фреймі на момент краху
"Що сталось до цього" Треба вручну шукати сусідні рядки логу за часом Breadcrumbs — автоматична стрічка подій перед падінням (HTTP-запити, SQL-запити, попередні log-рядки)
Продуктивність запитів Не показує APM: транзакції, spans, флейм-графи повільних ділянок
Вартість впровадження Вже вбудований у stdlib, безкоштовний Окремий SDK + сервіс (SaaS або self-hosted), ціноутворення за обсягом подій
💡
Найкоротше формулювання: logging — для того, що ви свідомо вирішили записати (audit trail, "цей крок пройшов"); Sentry — для того, чого ви не очікували (винятки, регреси, повільні запити), плюс автоматичне групування й трасування продуктивності поверх цього. Хороша система моніторингу використовує обидва одночасно, а не одне замість іншого.

02 Вісім можливостей Sentry

Sentry давно переріс "просто трекер помилок" — нижче основні можливості платформи, коротко й без маркетингової води.

Error tracking / групування помилок (issue grouping)

Ядро продукту. Кожен захоплений виняток autoматично групується зі схожими за стек-трейсом у один Issue — замість тисячі окремих подій ви бачите "цей самий баг стався 340 разів за останню годину". Issue має стан (unresolved / resolved / ignored), може бути призначений на конкретну людину, і показує повний стек-трейс з локальними змінними в кожному фреймі — не лише "де впало", а й "з якими саме значеннями".

Performance Monitoring / APM

Кожен HTTP-запит (чи Celery-таска) стає transaction, усередині якої SDK автоматично створює spans — окремі вкладені відрізки часу для SQL-запитів, зовнішніх HTTP-викликів, шаблонізації тощо. Результат — флейм-графік: видно не просто "цей ендпоінт повільний", а що саме в ньому займає час. Зокрема, інтеграція з ORM (SqlalchemyIntegration) показує N+1-запити прямо на цьому графіку: серію з багатьох майже однакових SQL-spans поспіль усередині однієї транзакції — саме та проблема, яку туторіал 18 розбирає в теорії, а Sentry APM виявляє автоматично, без ручного читання логів запитів.

Release Health і виявлення регресій

Кожна подія прив'язується до конкретного релізу (версії/коміту), який був задеплоєний у момент падіння. Це дозволяє відповісти на питання "ця помилка нова, чи вона була завжди?" і "чи саме вчорашній деплой підняв частоту цього Issue?" — набагато точніше, ніж співставляти timestamp логів із часом деплою вручну.

Alerting

Тип алертуСпрацьовує, коли
Issue alertЗ'явився новий Issue, або частота існуючого різко зросла
Metric alertМетрика перетнула поріг — наприклад, p95 latency чи error rate за останні N хвилин

Обидва типи інтегруються зі Slack, PagerDuty, email чи вебхуком — команда дізнається про проблему одразу, а не постфактум, коли клієнт напише скаргу.

Cron Monitoring

Для періодичних задач (Celery beat, cron) SDK надсилає "пінг" на початок і кінець кожного запуску; якщо задача не запустилась вчасно чи не завершилась — Sentry алертить. У цьому конкретному проєкті ця можливість поки не застосовна: app/workers/celery_app.py має явний коментар TODO: no periodic (celery beat) tasks exist yet — жодних періодичних задач тут ще немає, усе виконується або синхронно в запиті, або on-demand через optimize_routes_task/ analyze_delivery_list_task. Cron Monitoring стане корисним у момент, коли з'явиться перша beat_schedule-задача, а не раніше.

Profiling

Континуальний семплюючий CPU-профайлер, що працює прямо в проді з мінімальними накладними витратами. Природний наступний крок після того, як APM (вище) уже вказав на конкретний повільний ендпоінт чи задачу — профайлер показує, яка саме функція чи рядок коду з'їдає CPU всередині цього відрізку.

Context, tags, user

До кожної події можна прикріпити довільний контекст: user_id, organization_id, версію API тощо. Для мультитенантного SaaS (туторіал 22) це особливо цінно: замість "десь комусь щось зламалось" — фільтр "показати всі помилки саме цієї організації за останній тиждень", що напряму допомагає підтримці й дебагу конкретної скарги клієнта.

03 Як би це виглядало в цьому проєкті

Нижче — типова інтеграція sentry-sdk для FastAPI + Celery + SQLAlchemy, побудована на реальних іменах і файлах цього репозиторію. Сам SDK у проєкті не встановлений — це ілюстрація, як саме додати його, а не опис уже наявного коду.

pyproject.toml — одна нова залежність
dependencies = [
    "fastapi",
    ...
    "celery",
    "redis",
    "sentry-sdk[fastapi,celery,sqlalchemy]",
]

app/core/config.py уже має патерн "порожній рядок = провайдер не налаштований" для GOOGLE_MAPS_API_KEY і GMAIL_ADDRESS/ GMAIL_APP_PASSWORD — SENTRY_DSN природно лягає в той самий патерн, і ENVIRONMENT вже готовий для параметра environment=:

app/core/config.py
    # Third-party APIs
    OPENAI_API_KEY: str = ""
    OPENAI_MODEL: str = "gpt-4.1-mini"
    GOOGLE_MAPS_API_KEY: str = ""

    # Monitoring — empty means "Sentry not configured", same pattern as
    # the email/Google Maps providers above.
    SENTRY_DSN: str = ""

Ініціалізація — до створення застосунку, на початку app/main.py, перед викликом create_app():

app/main.py
import sentry_sdk
from sentry_sdk.integrations.fastapi import FastApiIntegration
from sentry_sdk.integrations.celery import CeleryIntegration
from sentry_sdk.integrations.sqlalchemy import SqlalchemyIntegration

settings = get_settings()

if settings.SENTRY_DSN:
    sentry_sdk.init(
        dsn=settings.SENTRY_DSN,
        environment=settings.ENVIRONMENT,
        integrations=[FastApiIntegration(), CeleryIntegration(), SqlalchemyIntegration()],
        traces_sample_rate=0.2,       # 20% транзакцій — компроміс видимості й вартості, розділ 07
        send_default_pii=False,       # не надсилати IP/cookies за замовчуванням
        before_send=_scrub_sentry_event,
    )

Точні назви класів інтеграцій (FastApiIntegration, CeleryIntegration, SqlalchemyIntegration) і параметр traces_sample_rate — стандартне, стабільне API sentry-sdk, але воно не перевірене запуском саме в цьому репозиторії (пакет не встановлений) — перед реальним впровадженням варто звірити з актуальною версією SDK в офіційній документації.

🔒
before_send — обов'язковий, не опційний, хук. Без нього є реальний ризик відправити в Sentry секрети чи PII: значення локальних змінних у стек-трейсі можуть містити JWT_SECRET, пароль із форми логіну, OPENAI_API_KEY з об'єкта налаштувань, чи персональні дані користувача з тіла запиту. before_send(event, hint) викликається перед кожним відправленням і повинен вирізати такі поля з event (чи повернути None, щоб не відправляти подію взагалі) — та сама дисципліна "не логувати секрети", яка вже застосована в цьому проєкті до rate-limiting і auth-коду.

Взаємодія з наявними обробниками помилок. app/core/error_handlers.py уже централізує перетворення винятків у чисту JSON-відповідь клієнту (register_exception_handlers) — Sentry цьому не заважає й нічого в HTTP-відповіді не змінює: він працює паралельно, лише для захоплення події на власному сервері. Для непередбачених помилок, що долітають до handle_unexpected_error (catch-all на Exception, який уже робить logger.exception(...)), типова поведінка Sentry FastAPI-integration — автоматично захопити той самий виняток без додаткового коду. А для очікуваного, уже обробленого винятку на кшталт QuotaExceededError (в нього вже є власний handler, що повертає чистий 403 — Sentry автоматичне захоплення тут не спрацює, бо виняток нікуди "непередбачено" не долітає) можна свідомо додати ручний виклик, якщо важлива видимість частоти таких подій:

app/core/error_handlers.py
    @app.exception_handler(QuotaExceededError)
    async def handle_quota_exceeded(request: Request, exc: QuotaExceededError) -> JSONResponse:
        sentry_sdk.capture_exception(exc)   # видимість тренду квот, без зміни HTTP-відповіді нижче
        return JSONResponse(status_code=status.HTTP_403_FORBIDDEN, content={"detail": str(exc)})
Топ-кейси саме для цього бекенду

04 Топ-кейс 1: тихі падіння Celery-тасок

Найважливіший кейс для цього конкретного проєкту — і причина, чому Sentry тут цінніший за звичайне логування навіть на невеликому масштабі.

app/workers/tasks.py
@celery_app.task(name="optimize_routes_task")
def optimize_routes_task(route_request_id: str) -> None:
    """Run route optimization asynchronously and persist the result."""
    raise NotImplementedError


@celery_app.task(name="analyze_delivery_list_task")
def analyze_delivery_list_task(import_batch_id: str) -> None:
    """Run LLM-based delivery list analysis asynchronously."""
    raise NotImplementedError

Сьогодні обидві задачі — заглушки. Але коли їх реалізують, будь-яка необроблена помилка всередині @celery_app.task опиниться в принципово іншій ситуації, ніж помилка в HTTP-запиті: немає жодного HTTP-клієнта, який побачить 500 — фоновий воркер просто залогує traceback у свій stdout (якщо хтось туди дивиться саме зараз) і мовчки перейде до наступної задачі з черги. Користувач, що ініціював запит, ніколи не дізнається, що його маршрут не був оптимізований — доки не поскаржиться сам.

🕳️
Це саме та "тиха відмова", проти якої безсилий stdlib logging. Рядок у логах існує, але його ніхто не читає в реальному часі — потрібен хтось, хто активно моніторить stdout воркера 24/7, щоб узагалі помітити проблему. CeleryIntegration вирішує це без жодного додаткового коду в самих тасках: кожен необроблений виняток усередині @celery_app.task автоматично захоплюється, групується в Issue з повним контекстом (аргументи таски, route_request_id/import_batch_id, скільки разів вона ретраїлась) — і, за налаштованим alert-правилом (розділ 02), одразу летить у Slack.

Пов'язано з ідемпотентністю фонових задач, уже розібраною для черг повідомлень загалом у туторіалі 24, категорія H: видимість падінь із Sentry — необхідна, але не достатня умова надійності; сама задача все одно повинна безпечно перезапускатись повторно.

05 Топ-кейс 2: регрес продуктивності солвера

Приклад Performance Monitoring, а не Error tracking — тут узагалі немає винятку, який стався, лише повільна ділянка, яку варто помітити до скарг користувачів.

app/services/route_optimizer/solver.py задає солверу жорсткий ліміт time_limit.FromSeconds(5), а app/services/route_optimizer/service.py викликає solver.solve() синхронно всередині async def optimize() — уже розібрано як bulkhead-проблему в туторіалі 25, розділ 09. З точки зору APM це означає: якщо середній час розв'язання почне повзти вгору (більше зупинок на маршрут, складніші обмеження часових вікон), кожен запит на оптимізацію все частіше впиратиметься в цю 5-секундну стелю — і user experience деградуватиме задовго до того, як хтось напише "чому все зависає".

app/services/route_optimizer/solver.py — custom span
import sentry_sdk

def solve(self) -> SolveResult:
    with sentry_sdk.start_span(op="solver.solve", description="OR-Tools VRP solve") as span:
        result = self._run_solver()
        span.set_data("stops_count", len(self._stops))
        span.set_data("hit_time_limit", result.hit_time_limit)
        return result

Такий custom span з'являється у флейм-графіку транзакції поруч зі звичайними автоматично зібраними SQL-spans (розділ 06 нижче) — і дозволяє поставити metric alert саме на p95 тривалості цього конкретного span'а: "алертити, коли p95 часу солвера наближається до 5 секунд" — це leading indicator проблеми масштабування (той самий розрахунок капасіті, що й у туторіалі 25, розділ 11), а не її наслідок.

06 Топ-кейс 3: N+1-запити через APM

Коротший кейс — той самий N+1, що вже розібраний в теорії, але тепер з точки зору "як його узагалі помітити на проді", а не лише "як його полагодити".

Туторіал 18 вже пояснює, чому N+1 виникає непомітно через ORM, і як його лагодити (selectinload / joinedload). Проблема цієї теорії окремо від практики: у звичайному коді N+1 не кидає жодного винятку — застосунок просто працює повільніше, і без цілеспрямованого профілювання цей факт легко пропустити, доки таблиця не виросте настільки, що стане відчутно.

SqlalchemyIntegration вирішує це автоматично: кожен SQL-запит стає окремим span усередині транзакції ендпоінта, і серія з десятків майже ідентичних SQL-spans поспіль візуально впадає в очі на флейм-графіку транзакції — не треба вручну рахувати запити в логах чи здогадуватись, що саме повільне. Sentry навіть має вбудований детектор саме цього патерну ("N+1 API Call"/"N+1 DB Query" performance issue), який автоматично створює окремий Issue, коли такий патерн трапляється в проді регулярно.

07 Компроміси й обмеження

Sentry не безкоштовний і не нейтральний за замовчуванням — варто свідомо керувати трьома речами.

КомпромісЩо робити
Вартість — ціноутворення за обсягом подій (error events + performance transactions) traces_sample_rate контролює частку транзакцій, що взагалі трасуються (не всі 100% запитів потребують повного APM); sample_rate — аналогічно для помилок при дуже високому трафіку однотипних збоїв
Шум — очікувані/некритичні винятки засмічують Issue-стрічку ignore_errors для явно очікуваних типів винятків (напр. RequestValidationError — уже й так чисто оброблений у error_handlers.py) — інакше кожна помилка валідації форми на фронтенді створює шум, що маскує реальні проблеми
Витік PII/секретів before_send хук (розділ 03) + send_default_pii=False — без цього значення локальних змінних у стек-трейсі можуть потрапити на сторонній сервер
Накладні витрати на продуктивність Незначні при розумному traces_sample_rate, але не нульові — профайлер (розділ 02) додає трохи більше, ніж просте захоплення помилок
SaaS vs self-hosted SaaS (sentry.io) — найшвидший старт, дані йдуть на сторонній сервер; self-hosted — повний контроль над даними, але власна інфраструктура для підтримки

08 Коли досить logging, а коли потрібен Sentry

Практичний чек-лист вибору, що підсумовує розділ 01.

  • Потрібен audit trail свідомих подій ("користувач X увійшов", "квота списана") → logging (туторіал 11) цілком достатній.
  • Потрібно знати, що саме й як часто ламається непередбачено, без ручного читання логів → Sentry error tracking.
  • Кілька людей у команді мають бачити один і той самий баг як один Issue, а не окремо шукати його кожен у своїх логах → Sentry (групування, розділ 02).
  • Потрібно знайти, яка саме ділянка коду повільна, а не просто "ендпоінт X іноді гальмує" → Sentry APM (розділи 05-06).
  • Команда з одного розробника, ранній етап проєкту, невеликий трафік, ще немає production-користувачів, чиї скарги критичні → logging + health check (туторіал 3) — цілком свідомий, прийнятний рівень інвестицій в observability, той самий висновок, що вже зроблено в туторіалі 23.
✅
Це не "або-або". Sentry не замінює logging — типова зріла конфігурація тримає обидва: logging для явного audit trail і структурованих подій (розділи 8-9 туторіалу 11), Sentry — для всього непередбаченого поверх нього.

Sentry / error monitoring

П'ять питань, які регулярно спливають, щойно в резюме чи описі проєкту згадується моніторинг помилок.

01БазаЯк Sentry групує схожі помилки (fingerprinting)?

За замовчуванням Sentry будує "відбиток" (fingerprint) події на основі стек-трейсу — типу винятку, послідовності функцій/модулів у ньому, і структури, а не конкретних значень (наприклад, конкретний user_id у повідомленні помилки не впливає на групування). Дві події з ідентичним "структурним" стек-трейсом падають в один Issue, навіть якщо трапились у різний час і з різними вхідними даними. Fingerprint можна перевизначити вручну (set_fingerprint(...)), якщо дефолтна логіка помилково розділяє те, що насправді одна й та сама проблема, або навпаки — об'єднує різні.

02БазаЧим breadcrumbs відрізняються від звичайних логів?

Breadcrumb — це запис у стрічці подій, що передували конкретній помилці, і показується прикріплено до цього конкретного Issue, а не в окремому суцільному потоці, як звичайний лог-файл. SDK автоматично додає breadcrumbs для HTTP-запитів, SQL-запитів, навігації, і навіть звичайних logging-викликів (якщо LoggingIntegration увімкнена) — тобто вони будуються з тих самих логів, які й так генеруються, просто автоматично прив'язуються до конкретного краху й показуються як його передісторія, а не вимагають ручного grep за timestamp.

03ПросунутеЯк контролювати вартість/шум при високому трафіку?

Три незалежні важелі, які варто комбінувати: traces_sample_rate — трасувати не всі 100% транзакцій, а задану частку (розділ 07); sample_rate — аналогічно для events, коли один і той самий тип помилки трапляється тисячі разів на хвилину; ignore_errors — повністю виключити явно очікувані, некритичні типи винятків зі збору; before_send — точковий фільтр "не відправляти цю конкретну подію", коли перших трьох механізмів недостатньо (наприклад, ігнорувати помилки від відомих сканерів-ботів за User-Agent).

04БазаЧим error tracking відрізняється від APM/tracing?

Error tracking реагує на подію "щось впало" — виняток, необроблений або явно захоплений. APM/tracing вимірює час — скільки тривала транзакція і кожен її span, незалежно від того, чи стався виняток узагалі. Це доповнюючі, а не конкуруючі системи: повільний, але успішний запит не згенерує жодної помилки, проте APM усе одно покаже його як проблему; аварійний краш узагалі не має тривалості, яку варто аналізувати — важливий сам факт і контекст падіння.

05ПасткаЯк не злити секрети чи PII у Sentry?

Найпоширеніша помилка — увімкнути Sentry "за замовчуванням" і не подумати про before_send: стек-трейс за дизайном показує значення локальних змінних у кожному фреймі, а це можуть бути паролі з тіла запиту, JWT-токени, ключі зовнішніх API з об'єкта налаштувань. Обов'язкові кроки: send_default_pii=False (не відправляти IP-адреси й cookies автоматично); власний before_send хук, що явно вирізає відомі чутливі поля з event перед відправленням; і уникати логування "просто всього об'єкта запиту/налаштувань" у повідомленнях винятків — та сама дисципліна, що вже застосована до логів і повідомлень про помилки в цьому проєкті (туторіал 2).
