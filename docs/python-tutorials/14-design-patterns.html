1 Чому патерни в Python часто виглядають інакше, ніж у підручнику

Класичні патерни GoF ("Банда чотирьох", 1994) описані для мов без функцій як значень першого класу (туторіал 7) — Java/C++ того часу. Python має цю можливість із самого початку.

У Java патерн Strategy майже завжди вимагає інтерфейсу й кількох класів, що його реалізують. У Python те саме найчастіше — звичайна функція, передана як аргумент. Це не "спрощена версія" патерна — це та сама ідея (підмінна поведінка), виражена мовою, де для цього не потрібна ціла ієрархія класів.

Аналогія з фронтендом
Те саме, що й React: замість класичного патерна Strategy через ієрархію класів, React-розробник просто передає функцію-пропс (onSort={sortByPrice}) — функції як значення роблять формальний патерн непотрібним у більшості випадків.

2 Adapter структурний

Патерн, що вже присутній у цьому проєкті — просто раніше не був названий.

app/services/geocoding/client.py — реальний код з проєкту
class GoogleGeocodingClient:
    """Thin wrapper around the Google Maps Geocoding API."""

    async def geocode(self, address: str) -> tuple[float, float] | None:
        # усередині -- HTTP-запит до Google Maps API зі своїм власним
        # форматом запиту/відповіді, які наш код НІКОЛИ не бачить напряму
        ...

Adapter — перетворює інтерфейс одного компонента на інтерфейс, який очікує інший, не змінюючи жодного з них. GoogleGeocodingClient ховає за простим методом geocode(address) -> (lat, lng) | None усю специфіку реального Google Maps API — власний формат запиту, JSON-відповідь із вкладеними полями, коди помилок. Решта проєкту (DeliveryService, туторіал 1) працює з чистим, доменно-орієнтованим інтерфейсом, повністю не знаючи, що "під капотом" — саме конкретний зовнішній HTTP API.

✅
Практична вигода: завтра можна замінити Google Maps на інший геосервіс (Mapbox, OpenStreetMap Nominatim), написавши новий клас із тим самим методом geocode(address) — жодного рядка в DeliveryService міняти не доведеться. Той самий принцип, що й typing.Protocol з туторіалу 4/6: адаптер визначається формою методів, не успадкуванням.

3 Factory породжувальний

У класичному ООП — окремий клас "фабрика". У Python FastAPI-проєкту — звичайна функція.

app/core/dependencies.py — реальний код з проєкту
def get_delivery_service(
    repo: DeliveryRepository = Depends(get_delivery_repository),
    org_repo: OrganizationRepository = Depends(get_organization_repository),
    organization: Organization = Depends(get_current_organization),
) -> DeliveryService:
    """Provide a request-scoped DeliveryService, quota-guarded per organization."""
    return DeliveryService(repo, GoogleGeocodingClient(), org_repo, organization)

Factory — інкапсулює логіку створення об'єкта, приховуючи деталі того, з яких саме компонентів він збирається. get_delivery_service — буквально це: викликач (роутер) отримує готовий, повністю зібраний DeliveryService, не знаючи (і не маючи знати), скільки саме залежностей знадобилось зібрати чи в якому порядку. Це та сама ідея, що описана в туторіалі 1 як "DI-ланцюжок" — просто розглянута тепер як конкретний, іменований патерн.

4 Strategy поведінковий

Найяскравіший приклад того, як Python "спрощує" класичний патерн до функції.

python — гіпотетичний приклад: підмінна логіка ціноутворення маршруту
# Класичний Java-стиль: інтерфейс + кілька класів
class PricingStrategy(Protocol):
    def calculate(self, distance_km: float) -> float: ...

class FlatRatePricing:
    def calculate(self, distance_km: float) -> float:
        return 50.0

class PerKmPricing:
    def calculate(self, distance_km: float) -> float:
        return distance_km * 2.5

# Pythonic-скорочення: просто функція
def flat_rate_pricing(distance_km: float) -> float:
    return 50.0

def per_km_pricing(distance_km: float) -> float:
    return distance_km * 2.5

def price_route(distance_km: float, strategy) -> float:
    return strategy(distance_km)     # strategy -- звичайна функція, не об'єкт-стратегія

Strategy — дозволяє підмінити алгоритм без зміни коду, що його викликає. У Python, де функції — значення першого класу (туторіал 7), найпростіша реалізація — передати іншу функцію, а не інший об'єкт класу-стратегії. Клас-обгортка (як PricingStrategy) стає потрібним лише тоді, коли "стратегії" повинні тримати власний внутрішній стан між викликами — а не просто перетворювати вхід на вихід.

5 Observer поведінковий

Найслабше представлений у цьому проєкті — тому корисно розглянути і класичну форму, і найближчий реальний аналог.

Observer — об'єкт ("суб'єкт") сповіщає список підписників про зміну стану, не знаючи заздалегідь, хто саме підписаний і що вони з цим сповіщенням зроблять. Класична форма — список callback-функцій, викликаних по черзі при події.

python — мінімальний Observer вручну
class DeliveryStatusSubject:
    def __init__(self):
        self._observers = []

    def subscribe(self, callback):
        self._observers.append(callback)

    def notify(self, delivery_id, new_status):
        for callback in self._observers:
            callback(delivery_id, new_status)   # кожен підписник реагує незалежно
💡
Найближчий реальний аналог у цьому проєкті: черга задач Celery (app/workers/, туторіал 3) — слабка форма pub/sub: застосунок "публікує" задачу в чергу (Redis), не знаючи заздалегідь, який саме воркер-процес її забере й виконає. Не класичний Observer (немає списку callback-ів в одному процесі), але та сама фундаментальна ідея — відправник і отримувач розв'язані (decoupled), спілкуються через проміжний канал, а не напряму.
Аналогія з фронтендом
element.addEventListener("click", callback) — Observer у чистому вигляді, який ви вже щодня використовуєте в JS: DOM-елемент (суб'єкт) сповіщає список зареєстрованих callback-ів (спостерігачів) про подію, не знаючи наперед, скільки їх і що вони роблять.

6 Коли патерн — рішення, а коли — зайва складність

⚠️
Найчастіша помилка middle-розробника на співбесіді й у коді: застосовувати патерн заради того, щоб "показати, що знаєш патерни". Жоден із патернів вище не варто вводити наперед, "про запас" — усі приклади в цьому туторіалі вже існували в проєкті як природне рішення конкретної задачі (замінний геосервіс, збірка залежностей), а не як навмисно застосований "патерн з підручника".

Правило: якщо патерн вирішує задачу, яка вже реально стоїть перед вами (а не гіпотетичну майбутню) — використовуйте. Якщо ні — звичайна функція чи клас без формальної назви часто читається простіше.

7 Каверзні питання співбесіди

БазаЧим Adapter відрізняється від звичайної обгортки (wrapper)?
Формально — Adapter це і є цілеспрямована обгортка: перетворює інтерфейс одного компонента на інтерфейс, очікуваний іншим кодом, не змінюючи жодного з них. "Просто wrapper" — ширший, менш формальний термін; Adapter — конкретний випадок, коли мета саме в сумісності інтерфейсів.
ПасткаЧому в Python Strategy часто не потребує жодного класу?
Функції в Python — значення першого класу (туторіал 7): їх можна передати аргументом напряму, без обгортання в об'єкт із єдиним методом. Клас-стратегія стає потрібним, лише коли "стратегія" повинна тримати власний стан між викликами, а не просто перетворювати вхід на вихід.
БазаУ чому вигода Factory-функції над прямим викликом конструктора класу?
Викликач не повинен знати, скільки саме залежностей потрібно зібрати чи в якому порядку — вся ця логіка інкапсульована в одному місці (фабричній функції), яку легко змінити, не чіпаючи жодного місця виклику.
БазаНаведіть приклад Observer, з яким ви точно вже працювали, не називаючи його "патерном".
addEventListener у браузерному JS, чи будь-яка pub/sub-система (черга повідомлень, сигнали Django, event emitter) — суб'єкт сповіщає підписників про подію, не знаючи наперед, хто саме підписаний.
ПасткаКоли варто НЕ застосовувати формальний патерн проєктування?
Коли задача, яку він вирішує, ще не виникла реально — "про запас" застосований патерн зазвичай додає непотрібну непрямість і ускладнює код без жодної поточної вигоди. Патерн має вирішувати конкретну наявну проблему, а не демонструвати знання підручника.
