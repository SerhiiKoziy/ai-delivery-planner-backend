Частина I · Класи

1 Клас — це виклик type()

Найважливіша ідея цього туторіалу з самого початку: class — не окрема сутність мови, а лише зручний синтаксис над одним викликом функції.

ці два фрагменти роблять АБСОЛЮТНО те саме
# звичний синтаксис
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

# те саме, написане БЕЗ ключового слова class
def __init__(self, x, y):
    self.x = x
    self.y = y

Point = type("Point", (), {"__init__": __init__})

class Point: ... — це синтаксичний цукор, який Python сам перетворює на виклик type(ім'я, батьки, простір_імен). type тут — не "тип значення", а metaclass, фабрика класів (детальніше в туторіалі 6, питання 6). Саме тому в Python можна створювати класи повністю динамічно в рантаймі — це не хак, а той самий механізм, яким користується звичайний class-синтаксис.

Аналогія з фронтендом
class у сучасному JS — теж синтаксичний цукор, тільки над іншим механізмом: прототипним ланцюжком (Object.create, obj.__proto__). Ідея та сама (сховати низькорівневий механізм за звичним ООП-синтаксисом), реалізація — принципово інша: JS-класи будують ланцюжок прототипів, Python-класи — це буквально об'єкти класу type.

2 __init__ і self — конструктор без прихованого "new"

У JS new непомітно робить кілька речей одразу. У Python усі ці кроки видимі окремо.

Python
obj = Point(1, 2) # 1) Python створює порожній екземпляр # 2) викликає Point.__init__(obj, 1, 2) # self — це і є той екземпляр, ЯВНО переданий першим аргументом
JavaScript
const obj = new Point(1, 2); // new робить те саме, але приховано: // створює об'єкт, прив'язує this, викликає constructor

self — не ключове слово (можна назвати як завгодно, це просто перший параметр методу за домовленістю) і не magic: коли ви пишете obj.method(1), Python сам підставляє obj першим аргументом — Point.method(obj, 1). Це прямий наслідок того, що методи — звичайні функції, прикріплені до класу (нон-дата дескриптори, туторіал 6, п. 1).

💼
Часте питання на співбесіді "Чому self треба писати явно в кожному методі?" — тому що в Python немає прихованого this-байндингу: метод — звичайна функція, а self — звичайний перший параметр, який автоматично отримує значення лише завдяки протоколу дескрипторів при виклику через екземпляр. Це свідомий вибір "explicit is better than implicit" (з Дзен Python), а не недогляд.

3 Магічні методи (dunder) — "data model" Python

Методи виду __щось__ ("dunder" — double underscore) — не приватні хаки, а офіційний протокол, яким Python дає вашим об'єктам вбудовану поведінку: друк, порівняння, довжину, ітерацію, виклик.

python — data model на прикладі
class Money:
    def __init__(self, amount): self.amount = amount
    def __repr__(self): return f"Money({self.amount})"      # для розробника (debug)
    def __str__(self): return f"${self.amount}"              # для користувача (print)
    def __eq__(self, other): return self.amount == other.amount
    def __add__(self, other): return Money(self.amount + other.amount)  # перевантаження +
    def __len__(self): return self.amount

m1, m2 = Money(10), Money(5)
print(m1)          # $10          -- викликає __str__
m1 == Money(10)     # True          -- викликає __eq__
m1 + m2             # Money(15)     -- викликає __add__
[m1, m2]            # [Money(10), Money(5)]  -- список використовує __repr__
Dunder-методВмикає
__repr__ / __str__repr(x) / print(x)
__eq__, __lt__ тощо==, < та інші оператори порівняння
__len__len(x), а також truthy/falsy, якщо немає __bool__
__iter__ / __next__for item in x, list(x)
__getitem__x[0], x["key"]
__call__x() — робить екземпляр викликаним, як функцію
__enter__ / __exit__with x as y: ... — розділ 18
Аналогія з фронтендом
Це — Python-аналог того, що в JS робиться через Symbol-и: __iter__ ≈ [Symbol.iterator] (той самий протокол ітерації, що дозволяє for...of й спред-оператор), __str__/__repr__ — слабкий аналог toString()/valueOf(). Головна різниця: у JS немає загального перевантаження операторів (+, == для довільних об'єктів не можна кастомізувати), тоді як в Python __add__, __eq__ тощо — звичайна, дуже поширена практика.

4 property — цукор для геттерів/сеттерів

Один із найточніших збігів синтаксису між Python і JS/TS з усього цього туторіалу.

Python
class Circle: def __init__(self, r): self._r = r @property def area(self): return 3.14159 * self._r ** 2 c.area # виклик БЕЗ дужок — виглядає як поле
TypeScript / JS
class Circle { constructor(private r: number) {} get area() { return 3.14159 * this.r ** 2; } } c.area // теж без дужок

@property перетворює метод на дата-дескриптор (туторіал 6, п. 2) — доступ виглядає як звичайне поле (c.area, без дужок), але насправді щоразу виконує код методу. Пара @area.setter дозволяє додати логіку й на запис, з валідацією всередині — так само, як set area(v) у TS/JS.

✅
Типовий сценарій використання: почати із звичайного публічного поля, і лише коли знадобиться валідація/обчислення при читанні — перетворити його на @property без зміни зовнішнього API класу (виклики c.area лишаються тими самими рядками коду).

5 Успадкування та super()

Дозволяє класу розширити поведінку батьківського, не переписуючи її з нуля.

python
class Vehicle:
    def __init__(self, brand):
        self.brand = brand
    def describe(self):
        return f"{self.brand} vehicle"

class Car(Vehicle):
    def __init__(self, brand, doors):
        super().__init__(brand)     # делегує ініціалізацію батьківському __init__
        self.doors = doors
    def describe(self):
        return f"{super().describe()} with {self.doors} doors"  # розширює, не замінює

super() повертає проксі-об'єкт, що шукає метод у наступному класі за MRO (туторіал 6, п. 3) — у простому одиничному успадкуванні це "просто батько", але при множинному успадкуванні це може бути й "клас-сусід" у ланцюжку кооперативних викликів.

Аналогія з фронтендом
super().__init__(...) ≈ super(...) у конструкторі TS/JS-класу — та сама ідея "делегувати ініціалізацію батьківському класу перед тим, як додати своє". Різниця — Python дозволяє множинне успадкування (class C(A, B)), а JS/TS — ні (лише один extends, множинну поведінку JS імітує через міксини вручну).

6 @dataclass — цукор для "класів-даних"

Найбільш "окупний" декоратор для звичайного ООП-коду: прибирає купу одноманітного boilerplate.

без @dataclass — вручну
class Point:
    def __init__(self, x: int, y: int):
        self.x = x
        self.y = y
    def __repr__(self):
        return f"Point(x={self.x!r}, y={self.y!r})"
    def __eq__(self, other):
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)
з @dataclass — те саме, коротше
from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int
# __init__, __repr__, __eq__ згенеровані АВТОМАТИЧНО з type hints полів

@dataclass читає анотації типів класу (ті самі, що самі по собі нічого не перевіряють — туторіал 5, розділ 5) і генерує з них __init__, __repr__, __eq__. frozen=True робить екземпляри незмінними (і хешовними — туторіал 5, розділ 12); field(default_factory=list) — правильний спосіб задати mutable-значення за замовчуванням, обходячи пастку з туторіалу 5, розділ 9.

app/services/route_optimizer/service.py — реальний код з проєкту
@dataclass
class ReplanOutcome:
    """Result of `RouteOptimizerService.replan()`."""
    route: Route
    stops_before: list[RouteStop]
    stops_after: list[RouteStopRead]
    unassigned_delivery_ids: list[uuid.UUID]
Аналогія з фронтендом
@dataclass — це той функціонал, який у TypeScript дає сама компіляція interface/type: описати форму даних коротко, без ручного конструктора. Різниця в тому, що TS-типи повністю стираються в рантаймі, а @dataclass реально генерує робочі методи (__init__ тощо), які існують і виконуються під час роботи програми.

7 Передумова: функції — звичайні об'єкти

Без цього факту декоратори виглядають магією; з ним — стають очевидною технікою.

python — функції як значення
def greet(): return "hi"

greet                  # <function greet at 0x...>  -- сам об'єкт функції
other = greet           # можна присвоїти змінній, як будь-яке значення
other()                 # "hi"

def call_twice(fn):
    fn(); return fn()   # можна передати функцію АРГУМЕНТОМ в іншу функцію

def make_greeter():
    def inner(): return "hello from inside"
    return inner        # можна ПОВЕРНУТИ функцію з функції

Функція в Python — такий самий об'єкт, як число чи рядок: її можна присвоїти змінній, передати аргументом, повернути з іншої функції, зберегти в списку. Це властивість "functions as first-class citizens" — і саме вона робить декоратори можливими.

Аналогія з фронтендом
Точнісінько як у JS — функції там теж first-class citizens (звідси callback-и, .map(fn), HOC-и в React). Якщо ви колись писали функцію вищого порядку (higher-order function) у JS — ви вже інтуїтивно розумієте механізм, на якому побудовані декоратори.

8 У що насправді розгортається @decorator

Одна єдина ідея, яку варто запам'ятати назавжди — решта деталей з неї випливають.

@decorator — це просто присвоєння
@my_decorator
def say_hello():
    print("hello")

# ...буквально ідентично оцьому:

def say_hello():
    print("hello")
say_hello = my_decorator(say_hello)

@decorator над функцією означає: "визнач функцію як зазвичай, а потім одразу перезапиши цю назву результатом виклику decorator(функція)". Декоратор — це функція, що приймає функцію й повертає (зазвичай іншу) функцію.

💼
Питання-мінімум на будь-якій співбесіді з Python "Що робить @decorator?" — правильна відповідь одним реченням: "func = decorator(func), застосоване одразу після визначення функції". Якщо кандидат може написати цей рядок — решта (декоратори з аргументами, стек декораторів) стає лише деталями цієї єдиної ідеї.

9 Пишемо свій декоратор — і навіщо functools.wraps

Найпростіший робочий декоратор — логування часу виконання функції.

python
import time, functools

def timed(func):
    @functools.wraps(func)              # без цього __name__/__doc__ обгортки замінять оригінал
    def wrapper(*args, **kwargs):        # *args/**kwargs -- обгортка працює для БУДЬ-ЯКОЇ сигнатури
        start = time.perf_counter()
        result = func(*args, **kwargs)   # виклик оригінальної функції всередині
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

@timed
def slow_add(a, b):
    time.sleep(1)
    return a + b

slow_add(2, 3)   # друкує "slow_add took 1.0003s", повертає 5

Три ключові елементи: *args, **kwargs в обгортці — щоб декоратор працював із функцією будь-якої сигнатури; виклик оригінальної функції всередині обгортки (інакше декоратор просто замінює поведінку, а не доповнює); і @functools.wraps(func) — копіює __name__, __doc__ та інші метадані оригіналу на обгортку, без чого дебаг і інтроспекція (наприклад, автогенерація документації FastAPI з докстрінгів) сильно ламаються.

10 Декоратор з аргументами (фабрика декораторів)

Коли декоратору самому потрібні параметри — додається ще один рівень вкладеності функцій.

python — три рівні вкладеності
def repeat(times: int):              # рівень 1: приймає аргументи ДЕКОРАТОРА
    def decorator(func):              # рівень 2: приймає САМУ функцію
        @functools.wraps(func)
        def wrapper(*args, **kwargs): # рівень 3: приймає аргументи ВИКЛИКУ функції
            for _ in range(times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(times=3)
def say_hi(): print("hi")

# @repeat(times=3) розгортається в: say_hi = repeat(times=3)(say_hi)

Логіка та сама з розділу 8, просто @repeat(times=3) спершу викликає repeat(times=3), і лише результат цього виклику (сам decorator) застосовується до say_hi — саме тому потрібні три рівні вкладеності, а не два.

11 Стек декораторів: порядок застосування і виконання

Класична пастка на живому кодуванні — декоратори застосовуються знизу вгору, але виконуються назовні всередину.

python
@a
@b
def f(): ...
# еквівалент: f = a(b(f))  -- ЗАСТОСУВАННЯ йде знизу вгору (спершу b, потім a)

# але при ВИКЛИКУ f() порядок обертається:
# a's wrapper code (до виклику func) виконується ПЕРШИМ (він зовнішній)
# потім b's wrapper code
# потім сама f()
# потім b's wrapper code (після), потім a's wrapper code (після)
💼
Питання-пастка "У якому порядку виконаються декоратори в @a @b def f()?" — правильна відповідь показує розуміння різниці "застосування" й "виконання": обгортання відбувається знизу вгору (a(b(f))), але оскільки a стає зовнішньою функцією, її код "до виклику" запускається першим при кожному реальному виклику f() — тобто порядок виконання "до" збігається з порядком застосування (знизу вгору читання коду = зовні всередину виконання).

Частина III · Інший синтаксичний цукор

13 Comprehensions — цукор над циклами

Найчастіше вживаний "цукор" у будь-якому реальному Python-коді, включно з цим проєктом.

list comprehension — розгортання
squares = [x * x for x in range(10) if x % 2 == 0]

# буквально те саме, що:
squares = []
for x in range(10):
    if x % 2 == 0:
        squares.append(x * x)

Те саме працює для {k: v for ...} (dict comprehension) і {x for ...} (set comprehension). Круглі дужки замість квадратних — (x for x in ...) — дають generator expression: те саме, але не будує список одразу в пам'яті, а видає значення по одному, лениво (детальніше — генератори в розділі про yield, суміжна тема з асинхронністю в туторіалі 4).

app/services/route_optimizer/service.py — реальний код з проєкту
skipped_not_geocoded = [
    DeliveryRef(id=d.id, customer_name=d.customer_name, address=d.address)
    for d in deliveries
    if d not in geocoded
]
Аналогія з фронтендом
Comprehension ≈ ланцюжок .filter().map() у JS, тільки в одному виразі й без створення проміжного масиву на кожному кроці ланцюжка: deliveries.filter(d => !geocoded.includes(d)).map(d => ({id: d.id, ...})) робить те саме, що приклад вище, але Python-варіант читається "справа наліво" (спершу видно, ЩО формується, потім — звідки й за якою умовою), а не як послідовність викликів методів.

14 Розпакування: *args, **kwargs, зірочки в присвоєнні

Зірочка (*) і подвійна зірочка (**) — один символ, кілька пов'язаних значень залежно від контексту.

python
def f(*args, **kwargs):        # збирає "зайві" позиційні в tuple, іменовані — в dict
    print(args, kwargs)
f(1, 2, x=3)                    # (1, 2) {'x': 3}

numbers = [1, 2, 3]
f(*numbers)                     # розпаковує список назад в окремі аргументи -- f(1, 2, 3)

options = {"x": 3}
f(**options)                    # розпаковує dict в іменовані аргументи -- f(x=3)

first, *rest = [1, 2, 3, 4]     # first=1, rest=[2, 3, 4] -- розпакування присвоєння

merged = {**dict1, **dict2}     # об'єднання словників "розпакуванням" (PEP 448)

Той самий символ означає протилежні дії залежно від сторони: у визначенні функції *args — "збери решту позиційних аргументів у tuple"; у виклику функції *iterable — "розпакуй цей ітерований об'єкт назад в окремі аргументи".

Аналогія з фронтендом
Прямий аналог JS spread/rest-оператора (...): function f(...args) (rest) і f(...numbers) (spread), const [first, ...rest] = arr, {...obj1, ...obj2} — усе те саме, просто інший символ (... замість */**) і в Python окремий символ для словників (**), тоді як у JS spread однаковий і для масивів, і для об'єктів.

15 f-strings — найшвидший спосіб форматування

Python (f-string)
name = "Olia" f"Hello, {name}! {2 + 2} today."
JavaScript (template literal)
const name = "Olia"; `Hello, ${name}! ${2 + 2} today.`

Практично 1:1 той самий інструмент — рядок з вбудованими виразами замість конкатенації. Python f-strings додатково підтримують форматування прямо всередині дужок: f"{price:.2f}", f"{value!r}" (викликає repr() — саме так побудовано __repr__ у прикладі Money вище), і навіть відладку одним символом: f"{x=}" друкує "x=5".

16 Walrus-оператор :=

З'явився в Python 3.8 (PEP 572) — і вирішує проблему, якої в JS ніколи не існувало.

python
# без walrus — виклик двічі АБО зайва проміжна змінна поза if
data = fetch()
if data:
    process(data)

# з walrus — присвоєння прямо всередині виразу умови
if (data := fetch()):
    process(data)
🎉
Цікавий факт У JavaScript = — вже сам по собі вираз, що повертає присвоєне значення (if (data = fetch()) працює в JS без жодного спецсинтаксису — хоча лінтери зазвичай сварять за це, бо легко переплутати з ==). У Python = — це інструкція (statement), не вираз, і взагалі не може стояти всередині умови — саме тому знадобився окремий новий оператор := спеціально для цього одного випадку.

17 match/case — структурне зіставлення

З'явився в Python 3.10 (PEP 634) — набагато потужніший за звичайний switch.

python
match command:
    case {"action": "move", "x": x, "y": y}:   # розпаковує СТРУКТУРУ словника прямо в патерні
        move(x, y)
    case {"action": "stop"}:
        stop()
    case [first, *rest]:                        # розпаковує список, з rest-хвостом
        handle_list(first, rest)
    case _:
        raise ValueError("unknown command")

На відміну від JS switch (лише порівняння на рівність одного значення), match уміє розпаковувати структуру прямо в патерні — перевіряти форму словника/списку/об'єкта й одразу діставати значення з неї в одному кроці. Ближчий аналог у фронтенд-світі — деструктуризація в поєднанні з перевіркою типу/форми, яку в TS роблять вручну через звуження типів (discriminated unions + switch по полю type), тут же це вбудовано в саму мовну конструкцію.

19 Тернарний вираз — і чому порядок протилежний JS

Python
status = "ok" if response.ok else "error" # [значення] if [умова] else [значення]
JavaScript
const status = response.ok ? "ok" : "error"; // [умова] ? [значення] : [значення]

Та сама ідея, дзеркальний порядок читання: Python читається майже як звичайне речення англійською ("ok, if response is ok, else error"), C-подібні мови (і JS разом з ними) читаються "умова спершу". Жодної функціональної різниці — лише синтаксис, але легко переплутати порядок значень при швидкому перемиканні між мовами.

20 Швидка перевірка

Натисніть на питання, щоб побачити відповідь.

БазаУ що розгортається @decorator над функцією?
func = decorator(func), застосоване одразу після визначення функції — decorator приймає функцію й повертає (зазвичай іншу) функцію.
ПасткаУ якому порядку виконуються два декоратори, застосовані до однієї функції?
Застосування — знизу вгору (@a @b def f() = a(b(f))). Виконання "до"-коду при виклику — теж у тому ж напрямку читання зверху вниз, бо a стає зовнішньою обгорткою: спершу код a, потім код b, потім сама f.
БазаЧому потрібен functools.wraps у власному декораторі?
Без нього обгортка (wrapper) замінює __name__/__doc__ оригінальної функції своїми власними — ламає дебаг, інтроспекцію й автогенерацію документації (наприклад, у FastAPI). functools.wraps(func) копіює ці метадані з оригіналу на обгортку.
БазаЧим class Foo: ... насправді є "під капотом"?
Синтаксичним цукром над викликом type("Foo", (базові_класи,), {простір_імен_класу}). type — метаклас, фабрика класів за замовчуванням у Python.
ПасткаЩо згенерує @dataclass автоматично, а що — ні?
Автоматично: __init__, __repr__, __eq__ — на основі оголошених полів з type hints. НЕ генерує __hash__ за замовчуванням (клас лишається unhashable, доки не додати frozen=True або eq=False) — прямий наслідок правила "мутабельне не хешовне" з туторіалу 5.
ПасткаЧому в Python знадобився окремий walrus-оператор :=, а в JS — ні?
У JS = вже є виразом, що повертає присвоєне значення, тому if (x = f()) і без того синтаксично можливий. У Python = — інструкція (statement), яка не може стояти всередині виразу умови — тому знадобився окремий оператор := саме для цього вузького випадку.
БазаЩо таке "generator expression" і чим відрізняється від list comprehension?
(x for x in ...) замість [x for x in ...] — та сама ідея фільтрації/трансформації, але не будує весь список одразу в пам'яті: видає значення по одному, ліниво, при ітерації. Корисно для великих або нескінченних послідовностей, коли повний список не потрібен одразу.
Живе кодуванняНапишіть найпростіший декоратор, який рахує, скільки разів викликалась функція.
def count_calls(func):
    @functools.wraps(func)
    def wrapper(*a, **kw):
        wrapper.calls += 1
        return func(*a, **kw)
    wrapper.calls = 0
    return wrapper — показує розуміння, що й сама обгортка (wrapper) — звичайний об'єкт, якому можна прикріпити власний атрибут-лічильник.
