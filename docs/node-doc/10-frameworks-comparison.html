01 Карта світу: від мінімалізму до «все включено»

Фреймворк — це не про швидкість, а про те, скільки рішень він прийняв за вас. Спершу — шкала.

Усі Node-фреймворки вирішують одну задачу: перетворити (req, res) з туторіалу 9 на щось зручне — маршрути, парсинг тіла, валідацію, обробку помилок, структуру коду. Різняться вони тим, де на шкалі «свобода ↔ конвенції» вони стоять і яку абстракцію запиту беруть за основу: Node-шні req/res (Express, Fastify, Koa) чи Web-стандартні Request/Response (Hono, Elysia, Next.js Route Handlers).

💡
NestJS — це не конкурент Express/Fastify «на одному рівні», а шар над ними: Nest використовує Express (за замовчуванням) або Fastify як HTTP-адаптер. Тож порівнювати «Nest vs Fastify» за швидкістю — це порівнювати «Fastify + DI + декоратори» з «Fastify».
🧠 Запам'ятай: фреймворки відрізняються абстракцією запиту (Node req/res чи Web Request/Response) і кількістю прийнятих за вас рішень.

02 Express: лінійний ланцюжок middleware

Найпоширеніший Node-фреймворк (з 2010 року). Його модель знають усі — і майже всі колись на ній обпікалися.

Модель: масив функцій і next()

Express — це, по суті, список шарів (req, res, next), що виконуються по черзі. Кожен шар або відповідає (res.json()), або передає далі (next()), або передає помилку (next(err)) — тоді Express перестрибує всі звичайні шари до першого error middleware, якого розпізнає за чотирма аргументами (err, req, res, next) (буквально через fn.length === 4).

express-model.mjs
import express from 'express';
const app = express();

app.use(express.json({ limit: '100kb' }));          // парсер тіла → req.body
app.use((req, res, next) => {                       // мутація req — головний спосіб
  req.requestId = crypto.randomUUID();              // "передати дані далі"
  res.setHeader('x-request-id', req.requestId);
  next();
});
app.use('/admin', requireAdmin);                    // middleware на префікс

app.get('/health', (req, res) => res.json({ ok: true }));

app.use((err, req, res, next) => {                  // 4 аргументи = error handler
  res.status(err.status ?? 500).json({ error: err.message });
});

Що в цьому дизайні добре і що погано

  • Мутація req/res (req.user, req.body) — просто, але нетипізовано: у TypeScript доводиться робити declaration merging для Express.Request, і ніщо не гарантує, що middleware, який ставить req.user, справді виконався перед вашим handler-ом.
  • Порядок app.use = порядок виконання. Поставили логер після роутів — він не побачить запитів, що завершилися в роуті. Поставили error handler до роутів — він ніколи не спрацює.
  • «After»-логіки немає. next() не повертає Promise, тож «код після next()» виконується не після обробки запиту. Щоб заміряти час відповіді, Express-middleware підписуються на res.on('finish'). Порівняння з Koa — у розділі 3.
  • Екосистема — найбільша: passport, helmet, cors, multer, express-rate-limit, morgan. Більшість «connect-style» middleware працюють і в інших фреймворках через адаптери.

Express 5 вийшов у 2024 році після ~10 років розробки і з 2025 року став latest в npm. Головне:

Перевірено на express@5.2.1:

🐛
Класичний баг Express 4, через який з'явилися express-async-errors і express-async-handler: app.get('/x', async () => { throw new Error() }) — помилка не потрапляє в error middleware, клієнт чекає до таймауту, а процес отримує unhandledRejection (з Node 15 — падіння). В Express 5 це виправлено, але помилки в колбеках (наприклад, у setTimeout всередині handler-а) як і раніше ніхто не зловить.
💼
На співбесіді запитають так «Як Express відрізняє error middleware від звичайного?» — за кількістю оголошених параметрів функції (length === 4). Тому якщо ви приберете «невикористаний» next з сигнатури error handler-а (лінтер підказує!), він перестане бути error handler-ом.

03 Koa: async-цибуля і ctx

Той самий автор, що й Express (команда TJ Holowaychuk), але з виправленою моделлю: middleware — це async-функції, що обгортають одна одну.

У Koa await next() повертає Promise, що завершується, коли відпрацював увесь внутрішній стек. Тому кожен middleware має «до» і «після» — як шари цибулі. Об'єкт ctx об'єднує запит і відповідь (ctx.request, ctx.response, скорочення ctx.body, ctx.status, ctx.state для даних між шарами). Ядро Koa крихітне: немає роутера, body-parser-а, статики — це окремі пакети (@koa/router, @koa/bodyparser, koa-static).

Перевіримо обидві моделі одним скриптом (запущено, Express 5.2 і Koa 3.2):

onion.mjs
import express from 'express';
import Koa from 'koa';

const log = [];
// Express: лінійний ланцюжок; "after"-код після next() НЕ чекає на async handler
const e = express();
e.use((req, res, next) => { log.push('E1 before'); next(); log.push('E1 after next()'); });
e.use(async (req, res, next) => { log.push('E2 before'); await null; next(); });
e.get('/', async (req, res) => { await new Promise((r) => setTimeout(r, 10)); log.push('E handler'); res.send('ok'); });

// Koa: цибуля; await next() чекає весь внутрішній стек
const k = new Koa();
k.use(async (ctx, next) => { log.push('K1 before'); await next(); log.push('K1 after'); });
k.use(async (ctx, next) => { log.push('K2 before'); await next(); log.push('K2 after'); });
k.use(async (ctx) => { await new Promise((r) => setTimeout(r, 10)); log.push('K handler'); ctx.body = 'ok'; });

const s1 = e.listen(4001), s2 = k.listen(4002);
await fetch('http://localhost:4001/'); console.log('Express:', log.splice(0).join(' → '));
await fetch('http://localhost:4002/'); console.log('Koa:    ', log.splice(0).join(' → '));
s1.close(); s2.close();
terminal
Express: E1 before → E2 before → E1 after next() → E handler
Koa:     K1 before → K2 before → K handler → K2 after → K1 after

В Express «after»-рядок E1 надрукувався до handler-а: next() синхронно викликав E2, той дійшов до await і повернув керування. У Koa порядок строго вкладений — тому error handling, вимір часу, транзакції «відкрити → виконати → закомітити/відкотити» пишуться одним middleware з try/catch навколо await next().

⚠️
Пастка Koa: забути await перед next() (або return next()). Тоді шар не чекає внутрішні, помилки «вилітають» повз ваш try/catch, а Koa відправляє відповідь до того, як handler поставив ctx.body → клієнт отримує 404.

Koa сьогодні — нішевий вибір: стабільний, мінімалістичний, але екосистема і темп розвитку помітно менші, ніж у Fastify чи Hono. Його головна спадщина — onion-модель, яку взяли Hono, Elysia і (в іншій формі) інтерсептори Nest.

04 Fastify: схеми, плагіни, хуки

Фреймворк, який зробив JSON Schema центром дизайну: одна схема дає валідацію, серіалізацію, типи і документацію.

Чотири ідеї, на яких тримається Fastify

  1. JSON Schema на вході й виході. Схеми body/params/querystring/headers компілюються Ajv у JS-функції при старті (не при кожному запиті). Схема response компілюється fast-json-stringify у спеціалізований серіалізатор — він швидший за JSON.stringify, бо знає форму об'єкта, і викидає поля, яких немає в схемі (випадковий passwordHash не втече в API).
  2. Плагіни й інкапсуляція. Усе — плагін: app.register(plugin, opts) створює дочірній контекст. Декоратори, хуки й маршрути, додані всередині, не видно батькові й сусідам. Щоб плагін «поділився» (наприклад, підключенням до БД), його загортають у fastify-plugin.
  3. Хуки життєвого циклу замість універсального middleware — кожен хук має своє місце і свою семантику.
  4. Вбудовані речі: логер pino (структурований JSON, дуже дешевий), роутер find-my-way (radix tree), inject() для тестів без мережі, graceful close().

Експеримент: порядок хуків, інкапсуляція, inject()

fastify-lifecycle.mjs
import Fastify from 'fastify';
import fp from 'fastify-plugin';

const app = Fastify();
const order = [];
for (const h of ['onRequest', 'preParsing', 'preValidation', 'preHandler', 'preSerialization', 'onSend', 'onResponse']) {
  app.addHook(h, async () => { order.push(h); });
}

// Інкапсульований плагін: декоратор видно лише всередині
app.register(async function adminPlugin(instance) {
  instance.decorate('secret', 42);
  instance.get('/admin', async () => ({ hasSecret: instance.hasDecorator('secret') }));
}, { prefix: '/v1' });

// Плагін, загорнутий у fastify-plugin: "виходить" у батьківський scope
app.register(fp(async function dbPlugin(instance) {
  instance.decorate('db', { query: async () => [{ id: 1 }] });
}));

app.post('/items', {
  schema: { body: { type: 'object', required: ['name'], properties: { name: { type: 'string' } } } },
}, async function (req) {
  order.push('handler');
  return { root_hasSecret: this.hasDecorator('secret'), root_hasDb: this.hasDecorator('db'), name: req.body.name };
});

await app.ready();
let res = await app.inject({ method: 'POST', url: '/items', payload: { name: 'x' } });
console.log(res.statusCode, res.body);
console.log(order.join(' → '));
order.length = 0;
res = await app.inject({ method: 'GET', url: '/v1/admin' });
console.log(res.statusCode, res.body);
order.length = 0;
res = await app.inject({ method: 'POST', url: '/items', payload: {} });
console.log(res.statusCode, res.json().message, '| hooks:', order.join(' → '));
await app.close();
terminal (fastify 5.12)
200 {"root_hasSecret":false,"root_hasDb":true,"name":"x"}
onRequest → preParsing → preValidation → preHandler → handler → preSerialization → onSend → onResponse
200 {"hasSecret":true}
400 body must have required property 'name' | hooks: onRequest → preParsing → preValidation → onSend → onResponse
  • Інкапсуляція: secret, задекорований всередині adminPlugin, з кореня не видно (root_hasSecret: false), а db з плагіна, загорнутого в fastify-plugin, — видно.
  • Невалідне тіло не дійшло ні до preHandler, ні до handler-а: Ajv відсік запит, і одразу пішли onSend → onResponse. Ваш код ніколи не бачить «сирих» даних, що не відповідають схемі.
  • app.inject() проганяє весь життєвий цикл без відкриття порту — основа швидких інтеграційних тестів (див. туторіал 16).

TypeBox type provider: одна схема — і валідація, і типи

Проблема чистого JSON Schema в TS: схема і тип описуються двічі й розходяться. Type provider виводить тип req.params/req.body прямо зі схеми. Актуальний @fastify/type-provider-typebox (v6) працює з пакетом typebox 1.x (раніше — @sinclair/typebox) і реекспортує Type:

typebox.ts
import Fastify from 'fastify';
import { Type, type TypeBoxTypeProvider } from '@fastify/type-provider-typebox';

const app = Fastify({ logger: true }).withTypeProvider<TypeBoxTypeProvider>(); // саме в ланцюжку!

app.post('/orders', {
  schema: {
    body: Type.Object({ sku: Type.String(), qty: Type.Integer({ minimum: 1 }) }),
  },
}, async (req) => {
  req.body.qty;        // number — тип виведено зі схеми
  req.log.info({ sku: req.body.sku }, 'order');  // pino, з reqId у кожному рядку
  return { ok: true };
});

Альтернатива — fastify-type-provider-zod: схеми на Zod, які конвертуються для валідації та серіалізації. Зручніше, якщо Zod уже всюди, але ви частково втрачаєте швидкість компільованих Ajv-схем.

⚠️
Пастки Fastify: (1) withTypeProvider треба викликати в ланцюжку створення, інакше тип «губиться»; (2) у Fastify 5 повна схема обов'язкова для querystring/params/body (скорочений запис без type: 'object' прибрали); (3) якщо в схемі response немає поля — воно мовчки зникне з відповіді, і це часто сприймають як баг; (4) reply.send() + return значення в async handler-і = подвійна відповідь і попередження в лозі.

05 NestJS: архітектура поверх Express або Fastify

Коротко — тут лише місце Nest на карті. Детально DI, модулі й lifecycle — у туторіалі 11.

NestJS — opinionated-фреймворк, натхненний Angular: модулі, контролери, провайдери й DI-контейнер, усе описується декораторами і TypeScript-метаданими (reflect-metadata). HTTP-рівень делеговано адаптеру: @nestjs/platform-express (дефолт) або @nestjs/platform-fastify. Усе, що Nest додає — guards, interceptors, pipes, exception filters, — працює однаково незалежно від адаптера.

main.ts — перемикання на Fastify
import { NestFactory } from '@nestjs/core';
import { FastifyAdapter, type NestFastifyApplication } from '@nestjs/platform-fastify';
import { AppModule } from './app.module.js';

const app = await NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter());
await app.listen(3000, '0.0.0.0'); // Fastify за замовчуванням слухає лише localhost
  • Сильні сторони: однакова структура в усіх командах, DI для тестів (overrideProvider), офіційні модулі для конфігу, черг, мікросервісів, GraphQL, WebSocket, Swagger.
  • Слабкі: багато абстракцій і «магії» декораторів, повільніший холодний старт, вимога emitDecoratorMetadata (не працює з чистим type stripping Node — потрібен tsc/SWC).
  • Актуально: NestJS 12 перейшов на ESM-пакети ("type": "module") і додав вбудований StandardSchemaValidationPipe — валідація Zod/Valibot/ArkType-схемами прямо в @Param('id', { schema }).

Детально — у туторіалі 11: NestJS і архітектура Node-бекенду.

06 Hono: Web Standards і «пиши раз — запускай будь-де»

Найшвидше зростаючий фреймворк останніх років: той самий код працює на Node, Bun, Deno, Cloudflare Workers, Lambda.

Hono будується на Web-стандартних Request і Response. Застосунок — це об'єкт із методом app.fetch(request) → Response; саме такий інтерфейс очікують Cloudflare Workers, Deno.serve і Bun.serve. На Node потрібен тонкий адаптер @hono/node-server, що конвертує IncomingMessage у Request (це трохи коштує, тому на Node Hono не швидший за Fastify, хоча бенчмарки роутера в нього дуже хороші).

  • Крихітний: пресет hono/tiny — менше 14 КБ, нуль залежностей — важливо для edge, де розмір бандла впливає на холодний старт.
  • Роутери: RegExpRouter (усі маршрути компілюються в один великий regex), TrieRouter, SmartRouter обирає автоматично.
  • Middleware — onion, як у Koa: async (c, next) => { ...; await next(); ... }. Вбудовані: CORS, JWT, bearer auth, ETag, logger, secure headers, timing, compress.
  • Валідатори (@hono/zod-validator, standard-schema validator) і RPC-клієнт hc: тип маршрутів експортується з сервера, клієнт отримує автодоповнення шляхів, параметрів і типів відповіді — як tRPC, але поверх звичайного REST.
client.ts — RPC-клієнт Hono
import { hc } from 'hono/client';
import type { AppType } from './server.js';   // тільки тип — серверний код у бандл не потрапляє

const client = hc<AppType>('https://api.example.com');
const res = await client.users[':id'].$get({ param: { id: '1' } });
if (res.ok) {
  const user = await res.json();   // тип виведено з c.json(user) на сервері
}
💡
Межа Hono на Node: Node-специфічні речі (стріми fs, req.socket, деякі Express-middleware) доведеться адаптувати. Якщо проєкт живе лише на Node в контейнері й не планує edge — Fastify дасть більше готової екосистеми. Якщо є Cloudflare Workers / Vercel Edge / Bun — Hono майже поза конкуренцією. Про рантайми — у туторіалі 19.

07 AdonisJS та інші: tRPC, GraphQL-сервери, Elysia, Next.js як бекенд

Не все, що обробляє HTTP, — «фреймворк для REST». Коротка карта інших варіантів.

AdonisJS — «Laravel для Node»

Повноцінний full-stack фреймворк: власний IoC-контейнер, ORM Lucid (Active Record, міграції, сідери), валідатор VineJS, auth (сесії, токени), шаблони Edge, CLI Ace для генерації коду, тести (Japa), mailer, черги. Сучасна версія — TypeScript-first і ESM. Сильна сторона — батарейки з однією узгодженою документацією; слабка — менша спільнота, ніж у Nest, і менше людей на ринку праці з досвідом.

tRPC — типізований RPC без схеми API

Не HTTP-фреймворк, а шар процедур: ви пишете router({ getUser: publicProcedure.input(z.object(...)).query(...) }), а клієнт викликає trpc.getUser.query({ id }) з повною типізацією, бо імпортує тип роутера. Працює поверх адаптерів (standalone, Express, Fastify, Next.js, fetch). Ідеальний для монорепо «TS-фронт + TS-бек однієї команди»; поганий вибір для публічного API, мобільних клієнтів на інших мовах і там, де потрібен стабільний контракт.

GraphQL-сервери

Схему будують або SDL-first, або code-first (Pothos, TypeGraphQL, Nest GraphQL-модуль). Головні проблеми GraphQL — N+1 (DataLoader), складність запиту (depth/cost limiting) і кешування — про них у туторіалі 12 і туторіалі 14.

Elysia — Bun-first з наскрізною типізацією

Створений для Bun: TypeBox-схеми (t.Object) дають валідацію і типи, клієнт Eden — типізований виклик як у tRPC/Hono RPC. Дуже швидкий на Bun завдяки статичному аналізу handler-ів і агресивній оптимізації. Має адаптери і для інших рантаймів, але найсильніший саме на Bun. Ризик — менша зрілість і екосистема.

Next.js Route Handlers як бекенд

app/api/users/[id]/route.ts

Межі: немає довгоживучого процесу в serverless (WebSocket, фонові задачі, in-memory кеш), немає вбудованої DI/структури, складніше ділитися API з іншими клієнтами. 08 Один endpoint — п'ять фреймворків

GET /users/:id з валідацією, 404, 500 і єдиним форматом помилок. Усі п'ять версій запущені й перевірені однаковим набором запитів.

Специфікація: id — додатне ціле; невалідний → 400 { error: 'ValidationError', message }; немає користувача → 404; збій БД (імітуємо для id = 13) → 500 без витоку деталей; невідомий маршрут → 404. Спільний «репозиторій»:

users.mjs
// "репозиторій" — спільний для всіх п'яти реалізацій
const db = new Map([[1, { id: 1, name: 'Ada', email: 'ada@example.com' }]]);
export async function findUser(id) {
  if (id === 13) throw new Error('db connection lost'); // імітуємо збій БД
  return db.get(id) ?? null;
}

Express 5 + Zod

express.mjs
import express from 'express';
import { z } from 'zod';
import { findUser } from './users.mjs';

class HttpError extends Error {
  constructor(status, error, message) { super(message); this.status = status; this.error = error; }
}
const Params = z.object({ id: z.coerce.number().int().positive() });

const app = express();

// Express 5: rejected promise з async-handler-а сам іде в error middleware
app.get('/users/:id', async (req, res) => {
  const parsed = Params.safeParse(req.params);
  if (!parsed.success) {
    throw new HttpError(400, 'ValidationError', parsed.error.issues[0].message);
  }
  const user = await findUser(parsed.data.id);
  if (!user) throw new HttpError(404, 'NotFound', `User ${parsed.data.id} not found`);
  res.json(user);
});

// 404 для невідомих маршрутів — звичайний middleware в кінці ланцюжка
app.use((req, res) => res.status(404).json({ error: 'NotFound', message: 'Route not found' }));

// error middleware — розпізнається за 4 аргументами (err, req, res, next)
app.use((err, req, res, next) => {
  if (err instanceof HttpError) return res.status(err.status).json({ error: err.error, message: err.message });
  console.error(err);
  res.status(500).json({ error: 'InternalError', message: 'Internal Server Error' });
});

app.listen(Number(process.env.PORT ?? 3001));

import Fastify from 'fastify';

Koa 3 + @koa/router + Zod

koa.mjs
import Koa from 'koa';
import { Router } from '@koa/router';
import { z } from 'zod';
import { findUser } from './users.mjs';

const Params = z.object({ id: z.coerce.number().int().positive() });
const app = new Koa();
const router = new Router();

// Error handling — найзовнішній шар "цибулі": try/catch навколо await next()
app.use(async (ctx, next) => {
  try {
    await next();
    if (ctx.status === 404 && !ctx.body) ctx.throw(404, 'Route not found', { error: 'NotFound' });
  } catch (err) {
    ctx.status = err.status ?? 500;
    ctx.body = err.expose
      ? { error: err.error ?? 'HttpError', message: err.message }
      : { error: 'InternalError', message: 'Internal Server Error' };
    if (ctx.status === 500) console.error(err);
  }
});

router.get('/users/:id', async (ctx) => {
  const parsed = Params.safeParse(ctx.params);
  if (!parsed.success) ctx.throw(400, parsed.error.issues[0].message, { error: 'ValidationError' });
  const user = await findUser(parsed.data.id);
  if (!user) ctx.throw(404, `User ${parsed.data.id} not found`, { error: 'NotFound' });
  ctx.body = user;   // Koa сам серіалізує об'єкт у JSON
});

app.use(router.routes()).use(router.allowedMethods());
app.listen(Number(process.env.PORT ?? 3003));

NestJS 12 (компілюється tsc з emitDecoratorMetadata)

nest/main.mts
import 'reflect-metadata';
import {
  BadRequestException, Catch, Controller, Get, HttpException, Injectable, Module,
  NotFoundException, Param, type ArgumentsHost, type ExceptionFilter, type PipeTransform,
} from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { findUser } from './users.mjs';

@Injectable()
export class PositiveIntPipe implements PipeTransform<string, number> {
  transform(value: string): number {
    const id = Number(value);
    if (!Number.isInteger(id) || id < 1) {
      throw new BadRequestException({ error: 'ValidationError', message: 'id must be a positive integer' });
    }
    return id;
  }
}

@Injectable()
export class UsersService {
  async findOne(id: number) {
    const user = await findUser(id);
    if (!user) throw new NotFoundException({ error: 'NotFound', message: `User ${id} not found` });
    return user;
  }
}

@Controller('users')
export class UsersController {
  constructor(private readonly users: UsersService) {}      // DI: Nest бачить тип UsersService

  @Get(':id')
  findOne(@Param('id', PositiveIntPipe) id: number) {
    return this.users.findOne(id);                           // повернений об'єкт → JSON
  }
}

@Catch()   // без аргументів — ловить усе
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    if (exception instanceof HttpException) {
      const body = exception.getResponse();
      const { error, message } = typeof body === 'string'
        ? { error: exception.name, message: body }
        : (body as { error: string; message: string });
      return res.status(exception.getStatus()).json({ error, message });
    }
    console.error(exception);
    res.status(500).json({ error: 'InternalError', message: 'Internal Server Error' });
  }
}

@Module({ controllers: [UsersController], providers: [UsersService] })
export class AppModule {}

const app = await NestFactory.create(AppModule, { logger: false });
app.useGlobalFilters(new AllExceptionsFilter());
await app.listen(Number(process.env.PORT ?? 3005));

09 Чому бенчмарки фреймворків вводять в оману

«Fastify у 2 рази швидший за Express» — правда для hello world і майже неправда для вашого сервісу.

Ми самі заміряли Express 5 і Fastify 5 через autocannon (50 з'єднань, 8 с після прогріву, один процес на ноутбуці). Перший прогін — handler одразу повертає JSON. Другий — handler чекає 20 мс, імітуючи запит у БД:

bench-servers.mjs (фрагмент)
const wait = () => DELAY ? new Promise((r) => setTimeout(r, DELAY)) : null;
e.get('/u', async (req, res) => { await wait(); res.json(payload); });            // Express
f.get('/u', { schema: { response: { 200: UserSchema } } },
  async () => { await wait(); return payload; });                                  // Fastify
terminal — node bench.mjs
delay=0ms Express 5: 16239 req/s, p99 6 ms
delay=0ms Fastify 5: 25730 req/s, p99 4 ms
delay=20ms Express 5: 2310 req/s, p99 24 ms
delay=20ms Fastify 5: 2335 req/s, p99 25 ms

Без I/O Fastify дав ~1.6× більше RPS. Як тільки з'явилося 20 мс «БД», різниця зникла: обидва впираються в закон Літтла — 50 паралельних з'єднань / 0.02 с ≈ 2500 req/s максимум, незалежно від фреймворку. (Абсолютні числа залежать від машини — дивіться на співвідношення.)

Чому так відбувається

  • Hello-world міряє накладні витрати фреймворку — роутер, обгортки req/res, серіалізацію. У реальному запиті це десятки мікросекунд на тлі мілісекунд БД, мережі, валідації великого тіла, логування.
  • Різниця повертається під насиченням CPU. Якщо сервіс впирається в CPU (багато маленьких запитів, кеш у пам'яті, великі JSON-відповіді), дешевший роутер і fast-json-stringify дають реальну економію — менше інстансів. Тому «бенчмарки брешуть» не означає «швидкість не важлива»; вона важлива на вашому профілі навантаження.
  • Бенчмарк-конфіги не схожі на прод: без логера (pino vs morgan — величезна різниця), без auth, без валідації, без TLS, keep-alive вимкнено/увімкнено як зручно автору.
  • Рантайм часто важливіший за фреймворк: Hono/Elysia на Bun проти Express на Node порівнює рантайми, а не фреймворки.
  • Найдорожче — ваш код: синхронний JSON.parse 5 МБ тіла, N+1 запити, відсутність пулу з'єднань з'їдають більше, ніж будь-який фреймворк. Див. туторіал 15.
🧠 Запам'ятай: фреймворк визначає «стелю» RPS лише тоді, коли ви впираєтеся в CPU; у I/O-bound сервісі його накладні витрати тонуть у латентності БД.

11 Міграції та практичні пастки

Що ламається, коли переносите код між фреймворками або оновлюєте мажорну версію.

Express → Fastify

  • Express-middleware підключаються через @fastify/express або @fastify/middie — як міст на час міграції, не назавжди (вони виконуються в onRequest і не бачать розібраного тіла).
  • req.user = ... → fastify.decorateRequest('user', null) + присвоєння в хуку: Fastify хоче знати форму об'єкта заздалегідь (стабільні hidden classes V8).
  • Інкапсуляція дивує: хук, доданий у плагіні без fastify-plugin, не діє на маршрути сусідніх плагінів.
  • Response-схеми обрізають поля — додавайте їх поступово, перевіряючи контракт тестами.

Express 4 → 5

  • Пройдіться по всіх рядкових шляхах: *, ?, +, () у шляхах тепер помилка або інша семантика. Для механічних змін є офіційні codemod-и команди Express (пакет @expressjs/codemod), але шляхи з regex-символами все одно перевіряйте руками.
  • Приберіть express-async-errors — тепер це вбудовано, а патч може конфліктувати.
  • Код, що читав req.body без парсера і очікував {}, тепер отримає undefined.

Загальні пастки будь-якого фреймворку

  • Порядок реєстрації: CORS/helmet/body-parser/логер — до маршрутів; 404 і error handler — після.
  • Body limit — дефолти різні: express.json() 100 КБ, Fastify bodyLimit 1 МБ. Ставте явно.
  • Глобальний стан у модулі (кеш у Map на рівні файлу) не масштабується на кілька інстансів — див. туторіал 8.
  • Прив'язка бізнес-логіки до req/ctx — головна причина, чому міграція болить. Сервіси, що приймають звичайні аргументи, переносяться між фреймворками без змін.

12 Каверзні питання співбесіди

Перевіряють не знання API, а розуміння моделей і компромісів.

БазаЧим middleware-модель Express відрізняється від Koa?
Express — лінійний ланцюжок: next() повертає undefined, «after»-логіку роблять через res.on('finish'). Koa — onion: await next() чекає весь внутрішній стек, тому один middleware з try/catch довкола await next() ловить усі помилки і може заміряти час.
ПасткаМи прибрали невикористаний next з error handler-а Express — і помилки перестали оброблятися. Чому?
Express визначає error middleware за кількістю параметрів (fn.length === 4). Без next функція має 3 параметри і вважається звичайним middleware, тож помилка йде до дефолтного фінального обробника.
БазаЩо змінилося в Express 5 для async-коду?
Якщо handler/middleware повертає rejected Promise, Express 5 сам викликає next(err). В Express 4 це було unhandled rejection і «вічний» запит. Також змінився синтаксис шляхів (path-to-regexp v8: /*splat, {/:id}), req.body без парсера — undefined, req.query — getter.
ПасткаЧому Fastify швидше серіалізує JSON і який у цього побічний ефект?
Схема response компілюється fast-json-stringify у функцію, що знає порядок і типи полів, — без загального обходу об'єкта. Побічний ефект: поля, яких немає в схемі, зникають з відповіді (корисно для безпеки, дивує при розробці), а невідповідність типів може привести до приведення або помилки серіалізації.
ПасткаДекоратор, доданий у Fastify-плагіні, недоступний у сусідньому плагіні. Баг?
Ні, це інкапсуляція: register створює дочірній контекст. Щоб декоратор/хук «піднявся» до батька, плагін загортають у fastify-plugin (він ставить Symbol.for('skip-override')). Типово так роблять для спільних ресурсів (БД, конфіг), а маршрути й auth-хуки лишають інкапсульованими.
БазаЩо таке fastify.inject() і навіщо?
Емуляція HTTP-запиту (через light-my-request) без відкриття порту: проходить увесь lifecycle — хуки, валідацію, серіалізацію. Тести швидкі, паралельні, без конфліктів портів.
ПасткаЧи NestJS «повільний»?
Nest не має власного HTTP-сервера: швидкість визначає адаптер (Express або Fastify) плюс невеликі накладні витрати на guards/interceptors/pipes. На Fastify-адаптері Nest зазвичай швидший за чистий Express. Реальна ціна Nest — холодний старт (сканування модулів, рефлексія), що важливо для serverless.
БазаЧим Hono принципово відрізняється від Express?
Hono працює з Web-стандартними Request/Response і експортує app.fetch — тому той самий код запускається на Workers, Deno, Bun, Lambda і Node (через адаптер). Express прив'язаний до Node IncomingMessage/ServerResponse. Плюс onion-middleware і типізований RPC-клієнт.
ПасткаБенчмарк показує, що фреймворк X утричі швидший. Перейти?
Спершу виміряти власний сервіс: якщо латентність визначає БД/мережа, виграш буде близький до нуля (у нашому вимірі при 20 мс I/O Express і Fastify дали однакові ~2300 req/s). Перевірити, що бенчмарк з тим самим рантаймом, логуванням, валідацією, keep-alive. Перехід має сенс, якщо сервіс CPU-bound або потрібні інші фічі (схеми, edge).
БазаКоли tRPC — поганий вибір?
Публічний API, клієнти не на TypeScript (мобільні, партнери), потреба в стабільному версіонованому контракті, HTTP-кешування на CDN. tRPC прив'язує клієнта до типів сервера — ідеально в монорепо однієї команди, погано між організаціями.
ПасткаУ Koa handler поставив ctx.body, а клієнт отримав 404. Що не так?
Майже напевно в одному з middleware забули await перед next(): зовнішній шар завершився, Koa відправив відповідь до того, як внутрішній async-handler встановив ctx.body. Дефолтний статус Koa — 404.
БазаЯк зробити бізнес-логіку незалежною від фреймворку?
Тримати handler-и тонкими: розібрати вхід → викликати сервіс зі звичайними аргументами → змапити результат у відповідь. Сервіси й репозиторії не знають про req/ctx. Тоді міграція — це переписування лише транспортного шару (див. шарову архітектуру в туторіалі 11).

14 Як запам'ятати

Образи, що допомагають швидко відтворити модель кожного фреймворку.

1
Express
Лінійний ланцюжок middleware, що мутують req/res; error handler — 4 аргументи.
Асоціація: конвеєр на заводі — деталь їде в один бік, кожен робітник щось прикручує.
2
Koa onion
await next() чекає весь внутрішній стек; кожен шар має «до» і «після».
Асоціація: матрьошка — відкриваєш до найменшої, а потім закриваєш у зворотному порядку.
3
Fastify schema
Одна JSON Schema — валідація (Ajv), швидка серіалізація, типи, OpenAPI.
Асоціація: трафарет — і перевіряє форму, і малює її швидко, і зайве не пропускає.
4
Fastify encapsulation
register створює дочірній контекст; fastify-plugin «піднімає» декоратори до батька.
Асоціація: квартири в будинку — що в твоїй квартирі, сусіди не бачать; ліфт (fastify-plugin) — спільний.
5
Nest = шар над адаптером
DI, модулі й декоратори поверх Express або Fastify.
Асоціація: кузов на шасі — двигун (адаптер) можна поміняти, кузов той самий.
6
Hono
app.fetch(Request) → Response на Web Standards; запускається будь-де.
Асоціація: «炎» (hono — «полум'я» японською) — маленький вогник, що горить у будь-якій печі.
7
Express 5
Async-помилки ловляться самі; /*splat і {/:id} замість * і :id?.
Асоціація: «п'ятірка» нарешті вивчила async — через 10 років навчання.
8
Бенчмарки
Міряють накладні витрати; при I/O-bound навантаженні різниця тоне в латентності.
Асоціація: спорткар у пробці їде так само, як велосипед.
9
tRPC / Hono RPC / Eden
Клієнт імпортує тип сервера — наскрізна типізація без кодогенерації.
Асоціація: спільний словник у двох братів — розуміють одне одного, але чужим незрозуміло.
