01 Пам'ять процесу: RSS, heap, external

Перш ніж шукати витік, треба розуміти, яку саме пам'ять ви бачите на графіку — «Node їсть 2 ГБ» може взагалі не стосуватися JS-heap.

Node-процес — це не лише V8 heap. У ньому живуть: машинний код самого Node і V8, стек потоків, пул потоків libuv, нативні буфери (Buffer, ArrayBuffer), пам'ять нативних аддонів (наприклад, драйвера БД, sharp), TLS-контексти OpenSSL, і лише частина — це об'єкти JavaScript, якими керує збирач сміття. process.memoryUsage() показує п'ять чисел:

ПолеЩо цеХто керує
rssResident Set Size — скільки фізичної RAM зараз займає процес (усе разом)ОС
heapTotalСкільки пам'яті V8 зарезервував під JS-heapV8
heapUsedСкільки з цього реально зайнято живими (і ще не зібраними) об'єктамиV8 GC
externalПам'ять C++-об'єктів, прив'язаних до JS-об'єктів (включно з backing store буферів)V8 + Node
arrayBuffersПідмножина external: усі ArrayBuffer/BufferNode
mem.js — node mem.js
const fmt = (n) => (n / 1024 / 1024).toFixed(1) + ' MB';
function show(label) {
  const m = process.memoryUsage();
  console.log(label.padEnd(16),
    'rss', fmt(m.rss), '| heapUsed', fmt(m.heapUsed),
    '| external', fmt(m.external), '| arrayBuffers', fmt(m.arrayBuffers));
}
show('start');
const objs = Array.from({ length: 1e6 }, (_, i) => ({ i }));
show('1M objects');
const buf = Buffer.alloc(200 * 1024 * 1024);
show('Buffer 200MB');
buf.fill(1);
show('after fill(1)');
вивід (Node 24, macOS; числа будуть трохи іншими)
start            rss 33.5 MB | heapUsed 4.5 MB | external 1.5 MB | arrayBuffers 0.1 MB
1M objects       rss 104.9 MB | heapUsed 42.2 MB | external 1.7 MB | arrayBuffers 0.1 MB
Buffer 200MB     rss 105.1 MB | heapUsed 42.2 MB | external 201.7 MB | arrayBuffers 200.1 MB
after fill(1)    rss 305.2 MB | heapUsed 42.2 MB | external 201.7 MB | arrayBuffers 200.1 MB

Три уроки з цього виводу:

  • Буфери не в heap. 200 МБ Buffer не змінили heapUsed взагалі — вони в external/arrayBuffers. Тому --max-old-space-size не обмежує буфери, а heap snapshot покаже лише маленький JS-обгортковий об'єкт.
  • RSS — це торкнуті сторінки. Одразу після Buffer.alloc RSS майже не виріс: ОС видає нульові сторінки ліниво. Лише після fill(1) пам'ять фізично зайнята. Тому RSS «стрибає» не тоді, коли ви алокуєте, а тоді, коли пишете.
  • RSS рідко падає назад. Після GC V8 може тримати звільнені сторінки, а аллокатор (malloc) не завжди повертає пам'ять ОС. Плато RSS після піку — нормально; постійне зростання heapUsed після кожного major GC — ні.
⚠️
Діагностична розвилка. Росте heapUsed → витік JS-об'єктів, шукайте heap snapshot'ом. Росте arrayBuffers/external → тримаєте буфери (стріми без backpressure, кеш картинок). Росте лише rss, а heap і external стабільні → нативний аддон, фрагментація malloc або занадто багато потоків. На Linux з glibc іноді допомагає MALLOC_ARENA_MAX=2 або jemalloc.
🧠 Запам'ятай: RSS = heap + буфери + нативне + код; heap snapshot бачить лише JS-heap.

02 Будова V8 heap

Heap поділено на простори з різними стратегіями збирання — це пояснює, чому одні об'єкти «дешеві», а інші коштують дорогих пауз.

V8 спирається на generational hypothesis (гіпотезу поколінь): більшість об'єктів помирає молодими. Тимчасові масиви в map(), об'єкти запиту, проміжні рядки — живуть мілісекунди. Тому heap поділено на «молоде» і «старе» покоління з різними алгоритмами.

ПростірЩо тамЯк збирається
New space (young generation)Нові дрібні об'єкти. Поділений на дві semi-spaces: from-space і to-space. Розмір — одиниці-десятки МБ, налаштовується --max-semi-space-sizeScavenge (minor GC), часто й швидко
Old spaceОб'єкти, що пережили два scavenge (promotion). Основна частина heapMark-Sweep-Compact (major GC), рідше й дорожче
Large object spaceОб'єкти, більші за ліміт звичайної сторінки; кожен — у власному mmap-регіоні, ніколи не переміщуєтьсяРазом з major GC (є й young-варіант для свіжих великих об'єктів)
Code spaceСкомпільований JIT машинний кодMajor GC
Read-only / trusted / sharedНезмінні вбудовані об'єкти, службові структури V8Практично не збираються

03 Scavenge vs Mark-Sweep-Compact

Два зовсім різні алгоритми під дві різні популяції об'єктів — і саме тому алокувати тимчасові об'єкти дешево, а тримати мільйони довгоживучих — дорого.

Minor GC: Scavenge (алгоритм Чейні)

Scavenge — копіюючий збирач. Він стартує від коренів (стек, глобальні об'єкти, хендли) плюс remembered set — записаних write barrier'ом посилань «старий об'єкт → молодий». Кожен досяжний молодий об'єкт копіюється в to-space (або в old space, якщо вже переживав scavenge), на старому місці лишається forwarding-адреса. Після цього from-space повністю вважається вільним — мертві об'єкти навіть не відвідуються.

  • Вартість пропорційна кількості живих, а не мертвих об'єктів. Мільйон тимчасових об'єктів, що вже померли, — майже безкоштовні.
  • Паузи — зазвичай одиниці мілісекунд, але часті (тригер — заповнення new space, «allocation failure» у логах).
  • Алокація — це просто зсув вказівника (bump pointer), тому {} у JS дешевший за malloc.

Major GC: Mark-Sweep-Compact

  1. Mark — обхід графа від коренів, позначення всіх досяжних об'єктів (трикольорова розмітка: білий / сірий / чорний).
  2. Sweep — непозначені ділянки додаються до free-lists, куди потім алокуються нові об'єкти.
  3. Compact — для сильно фрагментованих сторінок живі об'єкти переносяться ближче один до одного, звільняючи цілі сторінки.

Вартість пропорційна розміру живого heap: 2 ГБ кешу в пам'яті означає, що кожен major GC обходить 2 ГБ об'єктів. Це головна причина, чому «тримати все в пам'яті процесу» погано масштабується — і чому великі кеші краще винести в Redis.

термінал — node --trace-gc app.js
[49082:0x7f7b0020a000]  72 ms: Scavenge 4.7 (5.7) -> 4.0 (6.7) MB, pooled: 0 MB, 1.29 / 0.00 ms  (average mu = 1.000, current mu = 1.000) allocation failure;
[49082:0x7f7b0020a000]  77 ms: Scavenge 5.0 (7.0) -> 4.5 (9.0) MB, pooled: 0 MB, 2.28 / 0.00 ms  ...
[49003:0x7fe1be10a000] 1072 ms: Mark-Compact 147.7 (212.5) -> 99.7 (228.5) MB, 111.13 / 0.00 ms  ... allocation failure; scavenge might not succeed

Читається так: тип GC, heap до → після (у дужках — зарезервовано), тривалість паузи. mu (mutator utilization) — частка часу, коли працював ваш код, а не GC. mu нижче ~0.9 на довгому відрізку — сигнал, що процес «задихається» в GC.

💼
На співбесіді запитають так «Чому scavenge швидкий, а mark-compact повільний?» — Scavenge обходить лише живі молоді об'єкти і копіює їх, мертві не чіпає взагалі; mark-compact мусить розмітити весь живий old-heap, підмести і частково ущільнити його. Тому оптимізація під GC — це «менше довгоживучих об'єктів», а не «менше алокацій взагалі».
🎉
Цікавий факт Найгірший для GC патерн — об'єкти «середнього віку»: живуть рівно стільки, щоб пережити два scavenge і потрапити в old space, а там одразу помирають. Класичний приклад — повільні запити, чий контекст тримається секундами. Вони платять і копіювання, і major GC.

04 Orinoco і stop-the-world паузи

Event loop однопотоковий, тож кожна мілісекунда паузи GC — це мілісекунда, коли сервер не відповідає нікому.

Stop-the-world — момент, коли головний потік JS зупинено і працює GC. Проєкт V8 Orinoco роками зменшував ці паузи трьома техніками:

ТехнікаІдеяДе застосовується
ParallelПауза є, але роботу GC ділять кілька helper-потоків — пауза коротшаScavenge, compaction
IncrementalВелику роботу розбито на маленькі кроки, що чергуються з JSMarking
ConcurrentGC працює у фонових потоках одночасно з JS, без паузиMarking, sweeping

Ціна concurrent-підходу — write barrier: кожен запис посилання в об'єкт трохи дорожчий, щоб фоновий маркер не пропустив щойно створене посилання. Плюс V8 використовує idle time: коли event loop простоює, частину GC-роботи можна виконати «безкоштовно».

💡
Через helper-потоки GC Node-процес використовує більше одного ядра навіть «однопотоковим» кодом. Якщо в контейнері ліміт CPU 0.5 ядра, фоновий GC конкурує з вашим JS — паузи стають довшими, ніж на ноутбуці. Ще одна причина не давати Node-контейнерам менше 1 vCPU.

Як побачити паузи у проді

  • --trace-gc — дешевий, можна тимчасово увімкнути в продакшні.
  • PerformanceObserver з entryTypes: ['gc'] — отримувати кожну GC-подію в коді й відправляти метрику (prom-client робить це за вас, див. туторіал 17).
  • Event loop delay p99 (розділ 10) — паузи GC прямо в ньому видно.

05 Ліміти heap і контейнери

Неправильний ліміт heap — найчастіша причина таємничих «OOMKilled» у Kubernetes без жодного JS-стектрейсу.

Old space має верхню межу. Коли live-heap до неї доростає, V8 спершу відчайдушно робить major GC один за одним (latency падає в прірву), а потім падає з FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory.

Дефолти

  • Дефолтний ліміт обчислюється евристично від доступної пам'яті системи, з верхньою межею близько 4 ГБ на 64-бітних системах (на машині вище — 4288 MB).
  • Новіші версії Node враховують cgroup-ліміт контейнера при обчисленні дефолту, але евристика не знає про інші процеси й про пам'ять поза heap. Покладатися на неї в проді не варто.
  • process.constrainedMemory() повертає ліміт cgroup (якщо є) — зручно для логування при старті.
термінал
# явно задати ліміт old space (у МБ)
node --max-old-space-size=512 server.js

# те саме через змінну оточення — зручно в Docker/K8s
NODE_OPTIONS="--max-old-space-size=1536" node server.js

# перевірка: heap_size_limit включає ще й young generation та службові простори
node --max-old-space-size=512 limit.js   # heap_size_limit: 704 MB
✅
Практичне правило: --max-old-space-size ≈ 70–80% від memory limit контейнера, якщо застосунок не працює з великими буферами; якщо працює (файли, зображення, стріми) — менше, 50–60%. Додайте --heapsnapshot-near-heap-limit=1, щоб при наближенні до ліміту автоматично зберегти snapshot для розслідування.
⚠️
Більший heap — не безкоштовний. Ліміт 8 ГБ і живих 6 ГБ означає major GC, що обходить 6 ГБ. Для latency-чутливих API краще кілька процесів по 1–2 ГБ (cluster/поди, див. туторіал 8), ніж один гігант.

06 Типові витоки пам'яті

У мові з GC «витік» — це не забута free(), а забуте посилання: щось досяжне з кореня тримає те, що вам уже не потрібно.

GC звільняє лише недосяжне. Тому кожен витік у Node — це ланцюжок посилань від GC root (глобальна змінна, модульна область видимості, активний таймер, живий сокет) до великого об'єкта. Шість класичних джерел:

1. Кеш без меж

lru.js — node lru.js
class LRU {
  constructor(max) { this.max = max; this.map = new Map(); }
  get(k) {
    if (!this.map.has(k)) return undefined;
    const v = this.map.get(k);
    this.map.delete(k); this.map.set(k, v);   // перенести в кінець = "нещодавно використаний"
    return v;
  }
  set(k, v) {
    this.map.delete(k);
    this.map.set(k, v);
    if (this.map.size > this.max) this.map.delete(this.map.keys().next().value); // найстаріший
  }
}
const unbounded = new Map();
const lru = new LRU(1000);
for (let i = 0; i < 100_000; i++) {
  const key = 'user:' + i;              // унікальні ключі = необмежена кардинальність
  unbounded.set(key, { payload: 'x'.repeat(100) });
  lru.set(key, { payload: 'x'.repeat(100) });
}
lru.get('user:99000');
console.log('unbounded size:', unbounded.size);
console.log('lru size:', lru.map.size, '| oldest key:', lru.map.keys().next().value);
вивід
unbounded size: 100000
lru size: 1000 | oldest key: user:99001

Map зберігає порядок вставки, тому найпростіший LRU — «видали й встав заново». У проді беріть lru-cache (ліміт за кількістю і за розміром, TTL). Особливо підступні кеші з ключем від user input: memoize(fn) по URL, мапа «userId → дані» без TTL.

2. Event listeners, які ніхто не знімає

leak.js — node --expose-gc leak.js
const { EventEmitter } = require('node:events');
const { setImmediate: tick } = require('node:timers/promises');
const bus = new EventEmitter();
const mb = () => (process.memoryUsage().arrayBuffers / 1048576).toFixed(0) + ' MB';
async function fullGC() { global.gc(); await tick(); global.gc(); await tick(); }

function handleRequest(id) {
  const big = Buffer.alloc(1024 * 1024, id);       // 1 MB "контекст запиту"
  bus.on('config-changed', () => big.length);      // listener ніколи не знімається
}

(async () => {
  for (let i = 0; i < 50; i++) handleRequest(i);
  await fullGC();
  console.log('listeners:', bus.listenerCount('config-changed'), '| arrayBuffers:', mb());
  bus.removeAllListeners('config-changed');
  await fullGC();
  console.log('after removeAllListeners:', mb());
})();
вивід
(node:48247) MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 config-changed listeners added to [EventEmitter]. MaxListeners is 10. Use emitter.setMaxListeners() to increase limit
listeners: 50 | arrayBuffers: 50 MB
after removeAllListeners: 0 MB

Навіть після примусового GC 50 МБ живі: кожен listener — замикання, що тримає свій big. MaxListenersExceededWarning — не косметика, а детектор саме цього бага. Не глушіть його через setMaxListeners(0); знімайте listener (off, once, або { signal } в events.on/addEventListener).

3. Замикання, що тримають більше, ніж здається

V8 створює один Context на функцію для всіх змінних, захоплених будь-яким вкладеним замиканням. Якщо одне внутрішнє замикання використовує hugeArray, а інше (довгоживуче, наприклад у setInterval) — лише id, обидва ділять контекст, і hugeArray живе, поки живе інтервал. Рішення — не захоплювати великі об'єкти в функціях, що створюють довгоживучі колбеки; витягувати потрібні поля в локальні змінні заздалегідь.

4. Таймери та інтервали

Активний setInterval — GC root: його колбек і все, що той захоплює, живуть вічно, поки не викличете clearInterval. Типовий баг — інтервал, створений на кожне WebSocket-з'єднання, який не очищається на close. timer.unref() лише дозволяє процесу завершитися, але не звільняє пам'ять.

5. AsyncLocalStorage, що тримає зайве

AsyncLocalStorage (див. туторіал 3) пропагує store в усі async-ресурси, створені всередині run(). Якщо покласти в store цілий req з тілом, а всередині запиту хтось створить довгоживучий ресурс — інтервал, кешований проміс, пул-з'єднання — він «захопить» store і тримає тіло запиту. Правила: класти в store мінімум (requestId, userId, logger), ніколи не використовувати enterWith() без потреби, не створювати глобальні ресурси всередині запитного контексту.

6. Проміси, які ніколи не завершуються

promises.js — node promises.js
// "Висячі" проміси: кожен тримає свій замикання-контекст, поки не завершиться
const pending = new Set();
function callUpstreamWithoutTimeout() {
  const ctx = { body: Buffer.alloc(64 * 1024) };
  const p = new Promise(() => {});              // upstream ніколи не відповідає
  pending.add(p);
  return p.then(() => ctx.body.length);
}
for (let i = 0; i < 2000; i++) callUpstreamWithoutTimeout();
console.log('pending:', pending.size, '| arrayBuffers ≈', (process.memoryUsage().arrayBuffers / 1048576).toFixed(0), 'MB');
вивід
pending: 2000 | arrayBuffers ≈ 125 MB

Сам незавершений проміс не є коренем — але якщо він досяжний (з черги, з сокета, з Set як тут), то й увесь ланцюжок .then з контекстами живий. У реальному житті це HTTP-виклик без таймауту до «завислого» сервісу. Рішення — таймаут на кожен зовнішній виклик:

timeout.js — node timeout.js
const keepAlive = setInterval(() => {}, 1000);   // імітує живий сервер
async function callUpstream(url, { signal }) {
  return fetch(url, { signal });                  // fetch поважає AbortSignal
}
callUpstream('http://10.255.255.1/', { signal: AbortSignal.timeout(300) })
  .catch((e) => console.log(e.name, '-', e.message))
  .finally(() => clearInterval(keepAlive));
вивід
TimeoutError - The operation was aborted due to timeout

Нюанс: таймер AbortSignal.timeout() — unref'нутий; без «живого» сервера (тут імітованого інтервалом) процес просто завершився б, не дочекавшись помилки.

🧠 Запам'ятай: кожен витік — це шлях від кореня: кеш без меж, listener без off, інтервал без clear, проміс без таймауту.

07 Heap snapshots: пошук витоку

Heap snapshot — фотографія всіх живих JS-об'єктів із посиланнями між ними; порівняння двох знімків — найнадійніший спосіб знайти витік.

Як отримати знімок

СпосібКоли
node --inspect server.js → chrome://inspect → вкладка Memory → «Take heap snapshot»Локально, інтерактивно. Також Allocation timeline / sampling
v8.writeHeapSnapshot()З коду, наприклад за адмін-ендпоінтом. Повертає ім'я файлу Heap.<дата>.<pid>….heapsnapshot
--heapsnapshot-signal=SIGUSR2Зняти знімок у живому процесі через kill -USR2 <pid>
--heapsnapshot-near-heap-limit=NАвтоматично, до N знімків при наближенні до ліміту — ловить OOM «на гарячому»
🛑
Знімок у проді дорогий. Він синхронно зупиняє event loop на секунди (для великих heap — десятки секунд), а процесу потрібно приблизно ще стільки ж пам'яті, скільки займає heap. Знімайте на одному поді, виведеному з балансування (readiness = false), і з запасом по memory limit — інакше сам знімок викличе OOMKill.

Метод трьох знімків

Прогріти (JIT, кеші)
→
Snapshot 1
→
N запитів підозрілого сценарію
→
Snapshot 2
→
Ще N запитів
→

У DevTools оберіть Snapshot 3, режим Comparison відносно Snapshot 1 (або «Objects allocated between 1 and 2» у Summary). Об'єкти, що з'явилися між 1 і 2 і досі живі в 3 — кандидати. DevTools перед знімком сам запускає GC, тож сміття там не буде.

Як читати

  • Shallow size — розмір самого об'єкта. Retained size — скільки звільниться, якщо його прибрати (він і все, що тримається лише через нього). Сортуйте за retained.
  • Constructor групи: (closure), (string), (array), system / Context, ваші класи. Великий приріст Context → замикання; приріст IncomingMessage/Socket → утримані запити.
  • Панель Retainers — шлях до кореня (як на діаграмі вище). Читайте знизу вгору, поки не впізнаєте свій код: listeners in EventEmitter, cache in Map…
  • Давайте класам імена (class RequestContext), а не анонімні об'єкти — у знімку їх набагато легше знайти.
💡
Якщо зростає arrayBuffers, а не heap — знімок покаже лише маленькі JS-обгортки Buffer/Uint8Array. Шукайте, хто їх тримає (retainers), а не їхній розмір: backing store у знімку майже не враховано.

08 CPU-профілювання і flame graphs

«Повільно» без профілю — це здогадка; flame graph за хвилину показує, яка саме функція з'їдає CPU.

Інструменти

термінал
# 1. Вбудований семплюючий профайлер V8 → файл .cpuprofile (відкривається в DevTools / speedscope)
node --cpu-prof --cpu-prof-dir=./prof server.js
#    ... подати навантаження, зупинити процес (Ctrl+C / SIGINT) — профіль запишеться при виході

# 2. Інтерактивно: DevTools → Performance / Profiler
node --inspect server.js

# 3. Старий формат V8 tick-профайлера (без DevTools)
node --prof server.js && node --prof-process isolate-*.log > profile.txt

# 4. 0x — одна команда, готовий інтерактивний flame graph у HTML
npx 0x -- node server.js

# 5. clinic.js — набір "лікарів"
npx clinic doctor -- node server.js      # загальний діагноз: CPU / GC / I/O / event loop
npx clinic flame -- node server.js       # flame graph (на базі 0x)
npx clinic bubbleprof -- node server.js  # візуалізація асинхронних затримок між операціями

clinic.js розвивається повільно, і частина інструментів може нестабільно працювати на найновіших версіях Node; --cpu-prof і DevTools завжди доступні як базовий варіант.

Анатомія flame graph

  • Self time vs total time. handleRequest широкий, бо він предок усього; гаряча точка — JSON.stringify, у якого над ним нічого немає.
  • (garbage collector) широкий → проблема в алокаціях/живому heap, а не в алгоритмі (див. розділи 3–5).
  • (idle)/(program) домінує, а latency висока → ви чекаєте I/O (БД, мережа), а не CPU. Flame graph тут не допоможе; потрібні трейси (туторіал 17) або bubbleprof.
  • Анонімні функції в профілі — (anonymous). Іменуйте колбеки, щоб їх розрізняти.
💼
На співбесіді запитають так «Що означає ширина прямокутника у flame graph і чи важливий порядок зліва направо?» — Ширина = скільки семплів стек містив цю функцію (пропорційно часу CPU); порядок зліва направо зазвичай алфавітний, а не часовий. Хронологію показує інший вигляд — flame chart у DevTools Performance.

09 JIT: hidden classes, inline caches, deopt

V8 швидкий тоді, коли ваш код передбачуваний: однакові форми об'єктів і стабільні типи дають машинний код майже як у C++.

Конвеєр компіляції

Parser → AST
→
Ignition (байткод-інтерпретатор, збирає type feedback)
→
Sparkplug (baseline, швидко)
→
Maglev (середній оптимізуючий)
→
TurboFan (максимальна оптимізація)

Гарячі функції піднімаються вгору по рівнях. Оптимізуючі компілятори роблять спекуляції на основі зібраного feedback («тут завжди приходить об'єкт форми X з числом у полі x») і вставляють перевірки. Якщо спекуляція порушується — deoptimization: машинний код викидається, виконання повертається в інтерпретатор, а потім, можливо, повторна оптимізація.

Hidden classes (Maps / shapes)

Кожен об'єкт має приховану «форму» (у V8 — Map): набір властивостей, їх порядок і зміщення в пам'яті. Об'єкти, створені однаково, ділять одну форму, і доступ до o.x — це просто читання за відомим зміщенням.

shapes.js — node --allow-natives-syntax shapes.js
function P(x, y) { this.x = x; this.y = y; }
const a = new P(1, 2), b = new P(3, 4);
console.log('a~b', %HaveSameMap(a, b));
const c = new P(5, 6); c.z = 7;
console.log('a~c (added z)', %HaveSameMap(a, c));
const d = { y: 1, x: 2 }, e = { x: 1, y: 2 };
console.log('{y,x}~{x,y}', %HaveSameMap(d, e));
const f = new P(1, 2); delete f.x;
console.log('a~f (delete)', %HaveSameMap(a, f), 'dictionary mode:', !%HasFastProperties(f));
вивід
a~b true
a~c (added z) false
{y,x}~{x,y} false
a~f (delete) false dictionary mode: true

%-функції — внутрішні V8-«natives», лише для експериментів (ніколи в проді). Висновки: додавання властивості після створення і інший порядок ініціалізації дають іншу форму; delete взагалі переводить об'єкт у повільний dictionary mode (хеш-таблиця замість зміщень). Замість delete obj.x у гарячому коді — obj.x = undefined або створення нового об'єкта без поля.

Inline caches: mono → poly → megamorphic

Кожне місце доступу до властивості (call site) має inline cache, що запам'ятовує бачені форми: 1 форма — monomorphic (найшвидше), 2–4 — polymorphic, більше — megamorphic (кеш здається, доступ через глобальний повільний пошук).

ic.js — for n in 1 4 16; do node ic.js $n; done
function getX(o) { return o.x; }               // одна call-site, різні shapes
function makeShapes(n) {                        // n різних "форм" з властивістю x
  return Array.from({ length: n }, (_, k) => {
    const o = {}; o['p' + k] = 0; o.x = 1; return o;
  });
}
function bench(label, shapes) {
  const objs = Array.from({ length: 1e6 }, (_, i) => shapes[i % shapes.length]);
  let s = 0;
  for (let r = 0; r < 3; r++) for (const o of objs) s += getX(o);   // прогрів
  const t = performance.now();
  for (let r = 0; r < 20; r++) for (const o of objs) s += getX(o);
  console.log(label.padEnd(20), (performance.now() - t).toFixed(0), 'ms');
}
const which = process.argv[2];
bench(which + ' shapes', makeShapes(Number(which)));
вивід на одній машині (кожен варіант — окремий процес)
1 shapes             64 ms
4 shapes             89 ms
16 shapes            301 ms
⚠️
Застереження щодо мікробенчмарків. Цифри вище — ілюстрація тенденції, а не закон. Мікробенчмарки брешуть через: (1) прогрів JIT і on-stack replacement; (2) dead-code elimination — якщо результат не використовується, TurboFan може викинути цикл (тому тут s накопичується); (3) спільний feedback — запуск кількох варіантів в одному процесі «забруднює» IC, тому кожен варіант у своєму процесі; (4) шум ОС, турбо-частоти CPU. Використовуйте tinybench/mitata, кілька прогонів і, головне, міряйте реальний ендпоінт під навантаженням — megamorphic-доступ рідко буває вузьким місцем API, що чекає на БД.

Що провокує deopt

  • Зміна форми в гарячій функції (різний порядок полів, умовне додавання полів, delete).
  • Зміна типу значення: поле було Smi (мале ціле), стало double, потім рядком; масив з чисел отримав рядок або «дірку» (arr[1000] = 1 на порожньому масиві → holey elements).
  • Читання за межами масиву, arguments у sloppy mode з переприсвоєнням параметрів, eval/with.
  • Діагностика: node --trace-opt --trace-deopt app.js | grep -i deopt — покаже функцію та причину (наприклад, «wrong map», «not a Smi»).

Колишні «правила» на кшталт «try/catch вбиває оптимізацію» з часів Crankshaft більше не актуальні для TurboFan — на співбесіді варто це зазначити.

🧠 Запам'ятай: однакові конструктори, однаковий порядок полів, стабільні типи, без delete — і JIT зробить решту.

10 Event loop delay і ELU

Головна метрика здоров'я Node-сервера — не CPU%, а наскільки затримується event loop: саме це додається до latency кожного запиту.

Дві вбудовані метрики з node:perf_hooks:

  • Event loop delay (monitorEventLoopDelay) — histogram запізнень таймера: на скільки пізніше за план спрацював колбек. Блокуючий код, довгий GC, синхронний JSON — усе видно тут. Значення в наносекундах.
  • ELU — event loop utilization (performance.eventLoopUtilization()) — частка часу, коли loop був зайнятий (не чекав у poll). 0 = простоює, 1 = насичений. Краще за CPU% для автоскейлінгу: CPU% включає GC-потоки та пул libuv.
eld.js — node eld.js
const { monitorEventLoopDelay, performance } = require('node:perf_hooks');
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
const elu1 = performance.eventLoopUtilization();

function blockFor(ms) { const end = Date.now() + ms; while (Date.now() < end) {} }
const t = setInterval(() => blockFor(80), 200);   // кожні 200 мс — 80 мс синхронної роботи

setTimeout(() => {
  clearInterval(t);
  h.disable();
  const elu = performance.eventLoopUtilization(elu1);
  const ms = (ns) => (ns / 1e6).toFixed(0) + 'ms';
  console.log('p50', ms(h.percentile(50)), '| p99', ms(h.percentile(99)), '| max', ms(h.max));
  console.log('ELU', elu.utilization.toFixed(2));
}, 2000);
вивід (два запуски; значення трохи плавають)
p50 10ms | p99 87ms | max 91ms
ELU 0.37

Як читати: p50 ≈ 10 мс — це сама роздільна здатність (resolution: 10), тобто «майже без затримки» — значення включають інтервал семплювання. p99 ≈ 87 мс відповідає 80-мс блокуванням. ELU ≈ 0.37 близько до 80/200 = 0.4: loop зайнятий ~40% часу. Для кожного запиту, що потрапив під блокування, latency виросте до +80 мс.

СимптомЙмовірна причина
Високий ELU (>0.8) і висока затримка loopCPU-bound код на головному потоці → оптимізувати / worker threads / більше інстансів
Низький ELU, але висока latency запитівЧекаєте зовнішнє I/O або вичерпаний пул (БД, libuv threadpool для fs/dns/crypto)
Періодичні піки затримкиMajor GC (дивіться --trace-gc), cron-задачі в процесі, великий JSON.parse
✅
Пакети на кшталт @fastify/under-pressure використовують саме ці метрики для load shedding: якщо event loop delay або ELU перевищує поріг, сервер віддає 503 швидко, замість того щоб приймати запити, які однаково не встигне обробити.

11 Performance APIs

Ті самі User Timing API, що в браузері, — вбудовані в Node для точних вимірів без сторонніх бібліотек.

  • performance.now() — монотонний час з високою точністю (мс із дробовою частиною) від старту процесу. На відміну від Date.now(), не стрибає при корекції системного годинника (NTP). Для наносекунд — process.hrtime.bigint().
  • performance.mark(name) / performance.measure(name, start, end) — іменовані точки й інтервали.
  • PerformanceObserver — підписка на записи: measure, mark, gc, function (через performance.timerify), http, dns, net.
  • performance.timerify(fn) — обгортка, що автоматично вимірює кожен виклик.
perf.js — node perf.js
const { performance, PerformanceObserver } = require('node:perf_hooks');
const obs = new PerformanceObserver((list) => {
  for (const e of list.getEntries())
    console.log(`${e.entryType}: ${e.name} ${e.duration.toFixed(0)}ms`);
});
obs.observe({ entryTypes: ['measure'] });

performance.mark('parse-start');
const data = JSON.parse(JSON.stringify(Array.from({ length: 3e5 }, (_, i) => ({ id: i, name: 'item' + i }))));
performance.mark('parse-end');
performance.measure('json roundtrip', 'parse-start', 'parse-end');
console.log('items:', data.length);
вивід (тривалість залежить від машини)
items: 300000
measure: json roundtrip 803ms

Зверніть увагу на порядок: колбек observer'а викликається асинхронно (записи буферизуються), тому items: друкується першим. І друге — сотні мілісекунд синхронного JSON на 300 тис. маленьких об'єктів: усі інші запити в цей час чекають.

⚠️
Записи mark/measure накопичуються в глобальному буфері. Якщо ставити унікальні марки на кожен запит і не викликати performance.clearMarks()/clearMeasures(), отримаєте ще один витік пам'яті. Для метрик продакшну краще histogram у prom-client або OpenTelemetry spans.

12 Практичні оптимізації

90% виграшу в реальних Node-сервісах — не в мікрооптимізаціях JIT, а в кількох архітектурних звичках.

1. Жодних sync API в гарячому шляху

fs.readFileSync, crypto.pbkdf2Sync, zlib.gzipSync, child_process.execSync блокують loop для всіх запитів. Sync допустимо лише при старті (читання конфігу). Знайти їх допомагає node --trace-sync-io — друкує попередження на кожен sync I/O після першого тіку.

2. Стрімінг замість буферизації

Віддавати великий файл чи CSV-експорт через pipeline(source, transform, res) (див. туторіал 6) — пам'ять O(chunk), а не O(файл), і backpressure захищає від повільних клієнтів. Те саме для читання великих результатів з БД — курсори/стріми.

3. Вартість JSON

  • JSON.parse/JSON.stringify — синхронні та O(розмір). Ліміт на розмір тіла запиту (наприклад, 1 МБ) — і захист, і перформанс.
  • fast-json-stringify компілює серіалізатор зі JSON Schema: знає поля заздалегідь, не перевіряє типи в рантаймі — зазвичай у кілька разів швидше за JSON.stringify для об'єктів відомої форми, і заодно не випускає зайві поля (захист від витоку даних). Fastify використовує його автоматично для response schema.
  • Для гігантських JSON — стрімінговий парсер (stream-json) або винос у worker.

4. Кешування — на правильному рівні

🔀 Вузол вибору: де кешувати
ВаріантПлюсиМінуси
In-process LRU (lru-cache)Наносекунди, без мережіОкремий кеш на кожен інстанс, інвалідація складна, роздуває heap і major GC
Redis ✅Спільний для всіх інстансів, TTL, переживає деплойМережевий hop (~0.2–1 мс), серіалізація, ще одна залежність

Коли що: маленький довідник, що рідко змінюється → LRU у процесі; дані користувачів і сесії → Redis; публічні GET → CDN з Cache-Control. Захищайтеся від cache stampede (одночасні промахи) через single-flight — зберігати в кеші сам проміс.

5. Повторне використання з'єднань

TCP+TLS handshake до сервісу — це кілька RTT. Вбудований fetch (undici) тримає keep-alive пул за замовчуванням; для класичного http потрібен new http.Agent({ keepAlive: true }) (у новіших версіях глобальний агент вже має keepAlive). Для БД — пул з'єднань з розумним розміром (див. туторіал 12), а не з'єднання на запит.

6. CPU-важке — в worker threads

Ресайз зображень, генерація PDF, bcrypt з високим cost, важкі обчислення маршрутів — у пул worker_threads (Piscina) або окремий сервіс/черга. Деталі — туторіал 8.

7. Інші дрібниці з великим ефектом

  • NODE_ENV=production — Express і багато бібліотек вимикають debug-режими та кешують шаблони.
  • Логер: pino замість console.log у гарячому шляху (туторіал 17).
  • Стиснення (gzip/brotli) — краще на reverse proxy/CDN, ніж у Node.
  • Паралелити незалежні await'и (Promise.all) замість послідовних — найдешевша оптимізація latency.
🧠 Запам'ятай: не блокуй loop, стрімь великі дані, кешуй у Redis, тримай з'єднання, CPU — у workers.

13 Навантажувальне тестування

Бенчмарк, проведений неправильно, гірший за відсутність бенчмарку — він дає впевненість у хибних числах.

🔀 Вузол вибору: інструмент навантаження

Коли що: швидко порівняти дві реалізації ендпоінта → autocannon; реалістичний сценарій користувача з SLO-порогами в CI → k6.

термінал — autocannon
# 100 з'єднань, 30 секунд, pipelining 1
npx autocannon -c 100 -d 30 http://localhost:3000/api/orders
# у звіті дивіться Latency p97.5/p99 і Req/Sec, а не Avg

import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',   // open model: 200 запитів/с незалежно від відповіді
      rate: 200, timeUnit: '1s', duration: '2m',
      preAllocatedVUs: 50, maxVUs: 300,
    },
  },
  thresholds: {
    http_req_duration: ['p(99)<300'],   // CI впаде, якщо p99 ≥ 300 мс
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const res = http.get('http://localhost:3000/api/orders?limit=20');
  check(res, { 'status 200': (r) => r.status === 200 });
}

Як бенчмаркати правильно

  1. Окремі машини для генератора навантаження і сервера — інакше вони конкурують за CPU, і ви міряєте autocannon.
  2. Прогрів 30–60 с: JIT, пули з'єднань, кеші. Перші секунди не враховувати.
  3. Prod-подібне оточення: NODE_ENV=production, ті самі ліміти CPU/RAM контейнера, реалістичні дані в БД (на порожній таблиці всі запити швидкі).
  4. Перцентилі, не середнє. p99 і p99.9 — те, що відчувають користувачі під навантаженням; середнє ховає хвости.
  5. Coordinated omission: у closed-model (N з'єднань) повільна відповідь затримує й наступний запит, і генератор «не помічає» черги. Open-model (constant-arrival-rate, wrk2) показує чесну latency.
  6. Знайдіть точку насичення: піднімайте rate ступенями, поки p99 не почне різко рости — це ваша реальна ємність на інстанс, від неї рахують автоскейлінг.
  7. Одна зміна за раз, кілька прогонів, порівняння з базовою лінією. Паралельно знімайте ELU, event loop delay, heap і CPU — щоб знати, що саме насичується.
💼
На співбесіді запитають так «Ендпоінт тримає 5000 RPS на ноутбуці, а в проді 800 — чому?» — Ліміт CPU в контейнері (і GC-потоки конкурують за нього), реальна мережа до БД, реальні обсяги даних, TLS, логування в проді, generator на тій самій машині при локальному тесті, середнє замість p99, відсутність прогріву.

14 Каверзні питання співбесіди

Питання, на яких відрізняють «читав статтю» від «розслідував інцидент».

БазаЩо таке generational hypothesis і як вона впливає на будову V8 heap?
Більшість об'єктів помирає молодими. Тому heap поділено на new space (дві semi-spaces, швидкий копіюючий Scavenge, вартість ∝ живим) і old space (Mark-Sweep-Compact, вартість ∝ розміру живого heap). Об'єкт, що пережив два scavenge, просувається в old space.
ПасткаВи виставили --max-old-space-size=2048 у контейнері з лімітом 2 ГБ. Що піде не так?
Heap-ліміт стосується лише old space. Young generation, буфери (external), нативна пам'ять, код і стеки — понад нього. Процес перевищить cgroup-ліміт раніше, ніж V8 дійде до свого, і ядро вб'є його OOMKilled (exit 137) без JS-стектрейсу. Ставте ~70–80% ліміту контейнера (менше, якщо багато буферів).
ПасткаRSS процесу росте, а heapUsed стабільний. Де витік?
Не в JS-об'єктах, тож heap snapshot мало допоможе. Перевірте external/arrayBuffers (утримані буфери, стріми без backpressure), нативні аддони, кількість потоків; на glibc — фрагментацію malloc (MALLOC_ARENA_MAX, jemalloc). Також RSS може просто не повертатися ОС після піку — це плато, а не витік.
БазаНазвіть 5 типових причин витоків пам'яті в Node.
Необмежені кеші/мапи з ключем від user input; event listeners без off (сигнал — MaxListenersExceededWarning); setInterval без clearInterval; замикання, що захоплюють великі об'єкти через спільний Context; проміси без таймауту до завислих сервісів; великі об'єкти в AsyncLocalStorage store; глобальні масиви «для дебагу».
БазаЯк знайти витік за допомогою heap snapshots?
Метод трьох знімків: прогрів → snapshot 1 → навантаження сценарієм → snapshot 2 → ще навантаження → snapshot 3. Comparison-режим, сортування за retained size, дивитися конструктори з постійним приростом, потім панель Retainers — шлях до GC root, поки не впізнаєте свій код. У проді — --heapsnapshot-signal або --heapsnapshot-near-heap-limit, на виведеному з балансування поді.
ПасткаЧому знімати heap snapshot у проді небезпечно?
Знімок синхронний: loop зупинений на секунди/десятки секунд — health checks падають, запити таймаутять. І він потребує додаткової пам'яті порядку розміру heap — може сам спричинити OOMKill. Тому — readiness=false, запас по пам'яті, один под.
БазаЩо таке hidden classes і inline caches?
Hidden class (Map/shape) — опис форми об'єкта: які поля, у якому порядку, за якими зміщеннями. Inline cache на кожному call site запам'ятовує бачені форми: monomorphic (1) → швидкий прямий доступ, polymorphic (2–4), megamorphic (>4) → повільний generic-пошук. Однаковий порядок ініціалізації полів і відсутність delete тримають код мономорфним.
ПасткаЧому delete obj.prop може сповільнити код, а obj.prop = undefined — ні?
delete змінює форму і часто переводить об'єкт у dictionary mode (властивості в хеш-таблиці), що ламає inline caches і може спричинити deopt гарячої функції. Присвоєння undefined зберігає форму. Але для Map-подібних даних краще одразу брати Map.
БазаЧим event loop delay відрізняється від ELU і що використовувати для алертів/автоскейлінгу?
Event loop delay — наскільки пізно спрацьовують колбеки (прямо додається до latency; ловить блокування й GC-паузи). ELU — частка часу, коли loop зайнятий (міра насичення). Для алертів — p99 event loop delay; для автоскейлінгу — ELU, бо CPU% включає GC-потоки й threadpool і погано відображає насичення головного потоку.
ПасткаFlame graph: найширший прямокутник — handleRequest. Це він повільний?
Не обов'язково — нижні прямокутники широкі, бо вони предки всього стеку (total time). Гаряча точка — широкий прямокутник з великим self time вгорі «плато». Порядок зліва направо — алфавітний, не хронологічний. Якщо домінує (garbage collector) — проблема в алокаціях, якщо (idle) — ви чекаєте I/O.
ПасткаЧому мікробенчмарк показав, що варіант A у 10 разів швидший, а в проді різниці немає?
Dead-code elimination (результат не використано — цикл викинуто), відсутність прогріву/OSR, спільний IC feedback між варіантами в одному процесі, нерепрезентативні дані (мономорфні в тесті, поліморфні в проді), і головне — ендпоінт обмежений I/O, а не цим кодом. Міряйте end-to-end під навантаженням.
БазаЩо таке coordinated omission?
Помилка closed-model генераторів: коли сервер гальмує, генератор із фіксованою кількістю з'єднань чекає відповідь і не надсилає нові запити — затримки, які відчули б реальні користувачі (що приходять незалежно), не потрапляють у статистику. Рішення — open-model (k6 constant-arrival-rate, wrk2).
ПасткаЧи звільняє timer.unref() пам'ять, яку тримає колбек інтервалу?
Ні. unref() лише каже event loop не тримати процес живим заради цього таймера. Сам таймер активний, його колбек і захоплені змінні досяжні. Звільняє тільки clearInterval/clearTimeout.

16 Як запам'ятати

Вісім образів, які тримають весь туторіал.

1
Generational hypothesis
Більшість об'єктів помирає молодими, тому молоде покоління збирають часто й дешево.
Асоціація: одноразові стаканчики в кав'ярні — їх викидають щогодини, а меблі переставляють раз на рік.
2
Scavenge
Копіює живих із from-space у to-space, мертвих не торкається; вартість ∝ живим.
Асоціація: переїзд — забираєш лише потрібні речі, а стару квартиру здаєш разом з усім мотлохом.
3
Mark-Sweep-Compact
Розмітити досяжне в old space, підмести решту, ущільнити фрагментовані сторінки.
Асоціація: генеральне прибирання складу — обійти кожну полицю, тому довго.
4
RSS ≠ heap
RSS включає буфери, нативну пам'ять і код; heap snapshot бачить лише JS-об'єкти.
Асоціація: вага валізи — це не лише одяг, а й сама валіза, взуття і пакунки збоку.
5
Retained size
Скільки пам'яті звільниться, якщо прибрати цей об'єкт разом з усім, що тримається лише через нього.
Асоціація: перерізати нитку повітряної в'язки — відлітають усі кульки, прив'язані тільки до неї.
6
Hidden class / IC
Форма об'єкта + кеш на call site; одна форма — monomorphic і швидко, багато — megamorphic і повільно.
Асоціація: касир, що бачить лише один вид купюр, рахує наосліп; мішок різних валют — перевіряє кожну.
7
Deopt
Спекуляція оптимізатора порушилась — машинний код викинуто, назад в інтерпретатор.
Асоціація: навігатор будував маршрут по автобану, а його перекрили — їдеш селами, поки не перерахує.
8
Event loop delay / ELU
Delay — наскільки запізнюються колбеки; ELU — яку частку часу loop зайнятий.
Асоціація: черга до єдиного бариста: delay — скільки чекаєш, ELU — скільки часу він не відпочиває.
9
Flame graph
Ширина — час на CPU, висота — глибина стеку; гаряче — широке плато вгорі.
Асоціація: міська панорама: дивишся не на найвищі вежі, а на найширші дахи.
10
Coordinated omission
Closed-model генератор чекає повільні відповіді й не бачить черги — latency занижено.
Асоціація: ревізор, що заходить у магазин лише коли черга порожня, і звітує «черг немає».
