01 Логування: console, pino, winston

О третій ночі під час інциденту логи — єдине, що у вас є; вони мають бути машинно-читаними, пов'язаними між собою і дешевими для процесу.

Чому не console.log

  • Неструктурований текст. console.log('user', id, 'failed') не відфільтруєш у Loki/Elasticsearch за полем userId. Потрібен JSON: одна подія — один рядок з полями level, time, msg, requestId…
  • Немає рівнів (лише log/warn/error) і немає способу вимкнути debug у проді без зміни коду.
  • Може блокувати. Залежно від ОС і того, куди веде stdout (файл, TTY, pipe), запис буває синхронним. Масивне логування великих об'єктів (console.log(req)) з util.inspect — помітна частка CPU.

02 pino на практиці: request id, redaction, pipeline

Хороший лог-рядок відповідає на «який запит, який користувач, яка версія, яка помилка» — і ніколи не містить пароля чи токена.

src/logger.js
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  base: { service: 'orders-api', version: process.env.APP_VERSION, env: process.env.APP_ENV },
  timestamp: pino.stdTimeFunctions.isoTime,
  redact: {
    paths: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.token', 'card.number'],
    censor: '[REDACTED]',
  },
  // локально — гарний вивід; у проді — чистий JSON у stdout, без transport у процесі
  transport: process.env.NODE_ENV === 'development' ? { target: 'pino-pretty' } : undefined,
});

// child logger: усі записи успадковують поля
const jobLog = logger.child({ component: 'route-optimizer' });
jobLog.info({ routeId: 42, stops: 18 }, 'optimization started');
jobLog.error({ err }, 'optimization failed');   // ключ err → серіалізатор зі stack і cause
  • Сигнатура pino — спершу об'єкт полів, потім повідомлення: log.info({ userId }, 'msg'). Навпаки (log.info('msg', { userId })) поля загубляться — типова помилка при міграції з winston.
  • Помилки логуйте під ключем err — стандартний серіалізатор додасть type, message, stack і ланцюжок cause.
  • Redaction працює за шляхами; це страховка, а не дозвіл логувати цілі об'єкти. Краще взагалі не логувати тіла запитів, а вибирати поля явно. PII (email, телефон, адреса) — теж під GDPR.
  • pino-pretty — лише локально. У проді він витрачає CPU на форматування, а збирач логів не зможе розпарсити кольоровий текст.

Request id через AsyncLocalStorage

Як функція глибоко в коді дізнається requestId, щоб додати його в лог, не прокидаючи параметр через 10 шарів? AsyncLocalStorage (див. туторіал 3) — контекст, що «йде» за асинхронним ланцюжком. Демонстрація без залежностей:

als-logger.js — node als-logger.js
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';
import { setTimeout as sleep } from 'node:timers/promises';

const als = new AsyncLocalStorage();
const REDACT = new Set(['password', 'authorization', 'token']);
const redact = (o) => Object.fromEntries(Object.entries(o).map(([k, v]) => [k, REDACT.has(k) ? '[REDACTED]' : v]));

const logger = {
  info(msg, fields = {}) {
    const ctx = als.getStore() ?? {};
    process.stdout.write(JSON.stringify({ level: 'info', msg, ...ctx, ...redact(fields) }) + '\n');
  },
};

async function chargeCard(amount) {        // глибоко в коді — про requestId не знає
  await sleep(Math.random() * 20);
  logger.info('card charged', { amount, token: 'tok_live_123' });
}

async function handleRequest(userId, incomingId) {
  const requestId = incomingId ?? randomUUID().slice(0, 8);
  return als.run({ requestId, userId }, async () => {
    logger.info('request start');
    await chargeCard(100);
    logger.info('request end');
  });
}

await Promise.all([handleRequest('u1', 'req-aaa'), handleRequest('u2', 'req-bbb')]);
вивід (порядок між двома запитами випадковий — через Math.random)
{"level":"info","msg":"request start","requestId":"req-aaa","userId":"u1"}
{"level":"info","msg":"request start","requestId":"req-bbb","userId":"u2"}
{"level":"info","msg":"card charged","requestId":"req-bbb","userId":"u2","amount":100,"token":"[REDACTED]"}
{"level":"info","msg":"request end","requestId":"req-bbb","userId":"u2"}
{"level":"info","msg":"card charged","requestId":"req-aaa","userId":"u1","amount":100,"token":"[REDACTED]"}

Записи двох паралельних запитів перемішані в часі, але кожен має свій requestId — у системі логів фільтр requestId="req-aaa" дасть повну історію одного запиту. У реальному коді: pino-http/Fastify генерують id (або беруть з заголовка x-request-id від балансувальника), а nestjs-pino чи власний middleware кладе child logger в ALS. Ще краще — використовувати trace_id з OpenTelemetry (розділ 10), тоді лог і трейс з'єднуються автоматично.

⚠️
Асинхронний запис і краш. pino за замовчуванням буферизує запис (pino.destination({ sync: false }) або transports у worker thread) — це швидко, але при різкому process.exit() останні рядки, включно з тим самим fatal-повідомленням про причину падіння, можуть не дійти. У краш-хендлері логувати fatal і викликати logger.flush() перед виходом (або мати окремий sync-логер для fatal).

Найважливіше рішення — розрізняти помилки, які треба обробити, і помилки, після яких процесу більше не можна довіряти.

Центральний error handler

src/errors.js + Express error middleware
export class AppError extends Error {
  constructor(message, { status = 500, code = 'INTERNAL', expose = false, cause } = {}) {
    super(message, { cause });              // ES2022 cause — ланцюжок причин у логах
    this.name = this.constructor.name;
    Object.assign(this, { status, code, expose });
  }
}
export class NotFoundError extends AppError {
  constructor(what) { super(`${what} not found`, { status: 404, code: 'NOT_FOUND', expose: true }); }
}

// в обробниках — лише кидаємо; Express 5 сам ловить відхилені проміси async-хендлерів
app.get('/orders/:id', async (req, res) => {
  const order = await repo.findById(req.params.id);
  if (!order) throw new NotFoundError('order');
  res.json(order);
});

// одне місце, що вирішує: статус, лог, що показати клієнту
app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  (status >= 500 ? req.log.error : req.log.warn).call(req.log, { err }, 'request failed');
  res.status(status).json({
    error: err.expose ? err.code : 'INTERNAL',
    message: err.expose ? err.message : 'Internal Server Error',   // стек і SQL ніколи не йдуть клієнту
    requestId: req.id,
  });
});

У Express 4 відхилений проміс async-хендлера не потрапляв у error middleware — потрібні були обгортки або express-async-errors. Fastify і Nest (exception filters) мають власні централізовані механізми — туторіал 10.

Починаючи з Node 15, необроблений rejection за замовчуванням (--unhandled-rejections=throw) перетворюється на uncaught exception і валить процес з кодом 1. Це правильно. Чому не можна «просто логувати і жити далі» в uncaughtException:

  • Виняток вилетів з середини якоїсь операції: транзакція не відкотилась, мьютекс/семафор не відпущено, з'єднання з пулу не повернуто, стан у пам'яті напівоновлений. Процес у невідомому стані.
  • Наступні запити до такого процесу можуть віддавати неправильні дані — це гірше, ніж падіння.
  • Тому підхід crash-only: зафіксувати (лог fatal, Sentry), спробувати швидко закрити сервер, вийти з ненульовим кодом — супервізор (Kubernetes, systemd, PM2) підніме чистий процес. Інші репліки за балансувальником тим часом обслуговують трафік.
src/crash-handlers.js
import { logger } from './logger.js';

function crash(kind) {
  return (err) => {
    logger.fatal({ err, kind }, 'process crashing');
    // спробувати м'яко закрити (shutdown з розділу 4), але з жорстким таймаутом
    shutdown('fatal').finally(() => process.exit(1));
    setTimeout(() => process.exit(1), 3000).unref();
  };
}
process.on('uncaughtException', crash('uncaughtException'));
process.on('unhandledRejection', (reason) => { throw reason; });   // уніфікувати: → uncaughtException
💼
На співбесіді запитають так «Чому б не обгорнути все в process.on('uncaughtException', log) і не падати?» — Бо після невідомого винятку інваріанти процесу порушені (транзакції, локи, пули, кеші); продовження роботи ризикує тихо псувати дані. Правильно — зафіксувати, вийти з кодом 1 і покластися на супервізор і кілька реплік. Обробляти треба operational errors у місцях їх виникнення.

04 Graceful shutdown

Кожен деплой, автоскейлінг і переїзд поду — це SIGTERM; без graceful shutdown кожен із них обриває запити користувачів.

shutdown.js — node shutdown.js (повний робочий приклад)
import http from 'node:http';
import { setTimeout as sleep } from 'node:timers/promises';

const log = (msg) => console.log(`[${(performance.now() / 1000).toFixed(2)}s] ${msg}`);
const READINESS_DRAIN_MS = Number(process.env.READINESS_DRAIN_MS ?? 200);  // у проді ~5–10 с
const SHUTDOWN_TIMEOUT_MS = 10_000;                                         // < terminationGracePeriodSeconds
const db = { async end() { await sleep(50); log('db pool closed'); } };     // імітація пулу БД

let shuttingDown = false;
function send(res, status, body) {
  if (shuttingDown) res.setHeader('connection', 'close');   // після відповіді закрити keep-alive сокет
  res.writeHead(status).end(body);
}
const server = http.createServer(async (req, res) => {
  if (req.url === '/readyz') return send(res, shuttingDown ? 503 : 200, shuttingDown ? 'draining' : 'ok');
  await sleep(300);                                          // "повільний" запит
  send(res, 200, 'done');
});

async function shutdown(signal) {
  if (shuttingDown) return;                                  // повторний сигнал ігноруємо
  shuttingDown = true;                                       // 1. readiness → 503
  log(`${signal} received, readiness=false`);
  const force = setTimeout(() => {                           // страховка: не висіти вічно
    log('shutdown timeout, force exit'); process.exit(1);
  }, SHUTDOWN_TIMEOUT_MS);
  force.unref();

  await sleep(READINESS_DRAIN_MS);                           // 2. дати балансувальнику помітити 503
  log('stop accepting new connections');
  const closed = new Promise((r) => server.close(r));        // 3. закрити listener
  server.closeIdleConnections();                             //    і простоюючі keep-alive сокети
  await closed;                                              // 4. дочекатися in-flight запитів
  log('http server closed');
  await db.end();                                            // 5. закрити пули, черги, телеметрію
  clearTimeout(force);
  log('bye');                                                // 6. loop порожній → exit code 0
}
process.once('SIGTERM', () => shutdown('SIGTERM'));
process.once('SIGINT', () => shutdown('SIGINT'));

server.listen(0, async () => {
  const base = `http://127.0.0.1:${server.address().port}`;
  const inflight = fetch(`${base}/slow`).then((r) => r.text()).then((t) => log(`in-flight finished: ${t}`));
  await sleep(50);
  process.kill(process.pid, 'SIGTERM');                      // імітуємо сигнал від Kubernetes
  await sleep(10);
  const r = await fetch(`${base}/readyz`);
  log(`readyz during drain: ${r.status}`);
  await inflight;
});
вивід ($? = 0)

Запит, що прийшов до SIGTERM, успішно завершився; проба readiness під час drain віддала 503; ресурси закрито після HTTP; код виходу 0. («http server closed» і «in-flight finished» можуть мінятися місцями: другий рядок логує клієнт після читання тіла.)

🎉
Цікавий факт Перша версія цього прикладу мала дві помилки, і обидві типові. (1) Без паузи drain server.close() одразу закривав listener, і проба readiness отримувала не 503, а ECONNREFUSED — у Kubernetes це означає, що под ще в endpoints, а з'єднання вже відхиляються. (2) Без connection: close keep-alive сокет запиту, що завершився після closeIdleConnections(), лишався відкритим, і server.close чекав ще ~3 секунди, поки клієнт сам його закриє. На проді з тисячами keep-alive клієнтів це виливається в shutdown, що впирається в SIGKILL.

Нюанси

  • Чому drain-пауза потрібна: видалення поду з endpoints і оновлення iptables/балансувальника асинхронне до SIGTERM — кілька секунд трафік ще йде. Альтернатива паузі в коді — preStop-хук зі sleep у маніфесті (у новіших версіях Kubernetes є вбудована sleep-дія без потреби в shell в образі).
  • Keep-alive: server.closeIdleConnections(), connection: close на відповідях під час shutdown, а як останній засіб по таймауту — server.closeAllConnections(). Fastify має опції forceCloseConnections і return503OnClosing; для Express є http-terminator; у Nest — app.enableShutdownHooks() і хуки onApplicationShutdown.
  • Черги і воркери: перестати брати нові задачі (worker.close() у BullMQ чекає завершення поточних), не підтверджувати незавершені — брокер віддасть їх іншому воркеру (туторіал 18).
  • WebSocket: надіслати close frame з кодом 1001 (going away), клієнт перепідключиться до іншого поду.
  • Не викликайте process.exit() одразу після close — ви обірвете асинхронний flush логів і телеметрії. Краще дати loop спорожніти (exitCode = 0) і мати таймаут-страховку.

05 Health checks: liveness, readiness, startup

Три проби відповідають на три різні питання — і їх змішування є однією з найчастіших причин каскадних аварій.

ПробаПитанняНаслідок провалуЩо перевіряти

k8s/deployment.yaml (фрагмент)
spec:
  terminationGracePeriodSeconds: 30
  containers:
    - name: api
      image: registry.example.com/orders-api:1.42.0
      ports: [{ containerPort: 3000 }]
      startupProbe:
        httpGet: { path: /livez, port: 3000 }
        periodSeconds: 2
        failureThreshold: 30          # до 60 с на старт
      livenessProbe:
        httpGet: { path: /livez, port: 3000 }
        periodSeconds: 10
        timeoutSeconds: 2
        failureThreshold: 3           # 30 с зависання → рестарт
      readinessProbe:
        httpGet: { path: /readyz, port: 3000 }
        periodSeconds: 5

        limits:   { memory: "1Gi" }           # + --max-old-space-size≈768 (див. туторіал 15)
🛑
Каскадна аварія через liveness. Якщо /livez перевіряє Postgres, то коротка недоступність БД змушує Kubernetes одночасно перезапускати всі поди. Вони стартують, разом б'ють у БД, що відновлюється, з холодними пулами — і добивають її. Liveness перевіряє лише «я сам не завис». Залежності — максимум у readiness, і то обережно: якщо БД недоступна для всіх, вивести з ротації всі поди — теж відмова; часто краще лишити ready і швидко віддавати 503 з fallback.

Event loop, заблокований на 30 секунд, не відповість на liveness — і це правильний привід для рестарту. Для readiness корисно враховувати навантаження: якщо event loop delay p99 вище порогу, тимчасово віддавати 503 (load shedding, див. туторіал 15).

07 PID 1, сигнали й npm start

Найпідступніша Docker-пастка: контейнер «ігнорує» docker stop 10 секунд і вмирає від SIGKILL, обриваючи запити.

Процес з PID 1 у Linux — особливий: ядро не застосовує до нього дефолтні обробники сигналів. Звичайний процес без обробника SIGTERM завершується; PID 1 без обробника — просто ігнорує його. Друга роль PID 1 — збирати «зомбі» (завершені дочірні процеси, чий статус ніхто не прочитав).

Як запущеноХто PID 1Що відбувається з SIGTERM
CMD node server.js (shell form)/bin/sh -cshell зазвичай не пересилає сигнал дитині → Node не дізнається → SIGKILL через grace period
CMD ["npm", "start"]npmЗайвий посередник (часто ще й з sh -c всередині); пересилання сигналів і exit code історично ненадійні; плюс зайва пам'ять
CMD ["node", "server.js"] без обробникаnodePID 1 без обробника → сигнал ігнорується
CMD ["node", "server.js"] + process.on('SIGTERM')node✅ працює; але зомбі не збираються, якщо ви спавните дочірні процеси
ENTRYPOINT ["tini","--"] + exec-form CMD, або docker run --inittini✅ tini пересилає сигнали Node і збирає зомбі; Node все одно має обробляти SIGTERM для graceful shutdown
⚠️
docker run --init і init: true у docker-compose додають tini автоматично, але в Kubernetes такого прапорця немає — init треба вбудувати в образ (як у Dockerfile вище) або розраховувати на власні обробники сигналів у Node. Перевірка: docker stop має завершити контейнер за секунди, а не рівно за 10 (дефолтний таймаут Docker).
💡
Ctrl+C у docker run -it надсилає SIGINT — обробляйте і його, як у прикладі shutdown. А SIGKILL перехопити неможливо взагалі — тому всі критичні дані мають бути в зовнішніх системах (БД, черга) до того, як відповідь пішла клієнту.

09 Три стовпи observability і метрики

Моніторинг відповідає «чи зламано?», observability — «чому?»; для цього потрібні три типи сигналів, пов'язані між собою.

Які метрики збирати

  • RED (для сервісів, що обробляють запити): Rate — запитів/с, Errors — частка 5xx, Duration — histogram latency (p50/p95/p99).
  • USE (для ресурсів): Utilization, Saturation, Errors — CPU, пам'ять, пул БД (зайняті з'єднання, черга очікування), libuv threadpool.
  • Node-специфічні: event loop lag (p99), ELU, heap used/limit, GC pause duration, active handles, кількість відкритих сокетів (туторіал 15).
  • Бізнес-метрики: створені замовлення/хв, успішні оплати — часто перші показують інцидент, якого технічні метрики не бачать.
src/metrics.js — prom-client
import client from 'prom-client';

client.collectDefaultMetrics({ labels: { service: 'orders-api' } });
// дає: process_cpu_*, process_resident_memory_bytes, nodejs_heap_size_used_bytes,
//      nodejs_eventloop_lag_p99_seconds, nodejs_gc_duration_seconds, nodejs_active_handles ...

export const httpDuration = new client.Histogram({
  name: 'http_server_request_duration_seconds',
  help: 'HTTP request latency',
  labelNames: ['method', 'route', 'status_code'],
  buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});

export function metricsMiddleware(req, res, next) {
  const end = httpDuration.startTimer({ method: req.method });
  res.on('finish', () => {
    // route — ШАБЛОН ('/orders/:id'), а не req.url ('/orders/8f3a...') — інакше вибух кардинальності
    end({ route: req.route?.path ?? 'unmatched', status_code: res.statusCode });
  });
  next();
}

// окремий порт/шлях, недоступний ззовні
app.get('/metrics', async (_req, res) => {
  res.set('content-type', client.register.contentType).send(await client.register.metrics());
});
🛑
Кардинальність. Кожна унікальна комбінація значень лейблів — окремий time series у Prometheus. Лейбли userId, orderId, сирий URL, текст помилки створюють мільйони серій: падає Prometheus і роздувається пам'ять самого процесу (prom-client тримає всі серії в heap). Лейбли — лише з малої обмеженої множини значень.

Prometheus «тягне» (pull) метрики з кожного поду. З cluster mode чи PM2 кожен воркер має свій реєстр — потрібен AggregatorRegistry; в оркестраторі з одним процесом на контейнер цієї проблеми немає.

10 Трейсинг, APM і Sentry

Розподілений трейс показує, що з 900 мс запиту 700 пішли на третій виклик до сервісу цін — без жодного рядка ручного коду.

OpenTelemetry auto-instrumentation

src/instrumentation.mjs
import { NodeSDK } from '@opentelemetry/sdk-node';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';

const sdk = new NodeSDK({
  serviceName: process.env.OTEL_SERVICE_NAME ?? 'orders-api',
  traceExporter: new OTLPTraceExporter(),   // OTEL_EXPORTER_OTLP_ENDPOINT → collector
  instrumentations: [getNodeAutoInstrumentations({
    '@opentelemetry/instrumentation-fs': { enabled: false },   // занадто шумно
  })],
});
sdk.start();
process.once('SIGTERM', () => sdk.shutdown());   // flush спанів (або в загальному shutdown)
термінал — інструментацію треба завантажити ДО коду застосунку
node --import ./src/instrumentation.mjs dist/main.js
# або без власного файлу, лише через змінні оточення:
OTEL_SERVICE_NAME=orders-api OTEL_TRACES_EXPORTER=otlp \
  node --import @opentelemetry/auto-instrumentations-node/register dist/main.js
  • Чому --import: автоінструментація патчить модулі http, pg, ioredis, express при їхньому завантаженні. Якщо застосунок імпортував pg раніше, ніж стартував SDK, — спанів БД не буде. Для ESM патчинг працює через loader hooks, які реєструє саме --import.
  • Propagation: SDK додає заголовок W3C traceparent у вихідні HTTP-запити і читає його з вхідних — так трейс «проходить» через сервіси. Контекст усередині процесу тримається на AsyncLocalStorage.
  • Логи + трейси: інструментація pino додає trace_id/span_id у кожен рядок логу — у Grafana з трейсу один клік до логів.
  • Sampling: 100% трейсів у високонавантаженому сервісі дорого. Head sampling (наприклад, 10% через OTEL_TRACES_SAMPLER=parentbased_traceidratio) або tail sampling у collector'і (зберігати всі помилки й повільні).
  • Власні спани для бізнес-операцій: tracer.startActiveSpan('optimize-route', async (span) => { ...; span.end(); }).

APM-вендори та Sentry

APM (Datadog, New Relic, Dynatrace, Elastic APM, Grafana Cloud) — готові агенти, що збирають трейси, метрики і профілі, з UI «з коробки». Більшість уже приймають OTLP, тож OpenTelemetry-інструментація дозволяє не прив'язуватися до вендора.

Sentry спеціалізується на помилках: групування однакових винятків, стек з source maps (для TS/бандлів — завантаження source maps у CI обов'язкове), breadcrumbs, релізи («помилка з'явилась у версії 1.42»), алерти на нові типи помилок. Сучасний @sentry/node побудований на OpenTelemetry і так само ініціалізується до застосунку через --import ./instrument.mjs; для Express — Sentry.setupExpressErrorHandler(app) після роутів. Детальний розбір Sentry (на прикладі Python-бекенду, концепції ті самі) — Python Doc, туторіал 26.

⚠️
Sentry/APM не замінюють crash-only: вони мають перехопити uncaughtException, відправити подію (з невеликим таймаутом Sentry.flush(2000)) — і процес усе одно має впасти. Також налаштуйте beforeSend/scrubbing, щоб токени й PII не потрапляли в сторонній сервіс.

11 Конфігурація і feature flags

Той самий образ має запускатися в dev, staging і prod — відрізняється лише оточення, а нову функціональність вмикають прапорцем, а не деплоєм.

Конфігурація за 12-factor

  • Один артефакт, різні env. Конфіг — змінні оточення (з Kubernetes ConfigMap/Secret, Vault, AWS Secrets Manager), а не config.prod.json в образі.
  • Валідація при старті. Парсити process.env через zod/envalid у типізований об'єкт і падати одразу з зрозумілим повідомленням, якщо чогось бракує — краще, ніж undefined у URL БД о 2-й ночі (туторіал 13).
  • Локально — node --env-file=.env (вбудовано в Node, без dotenv); .env у .gitignore і .dockerignore.
  • Секрети не логувати (redaction), не класти в образ, ротувати; конфіг у логах на старті — лише несекретні поля.

Feature flags

Інструменти: LaunchDarkly, Unleash, GrowthBook, Flagsmith, ConfigCat; стандарт OpenFeature дає вендор-незалежний SDK. SDK зазвичай тримають правила в пам'яті і оновлюють їх у фоні (streaming/polling), тому перевірка прапорця — локальна і швидка, без мережевого виклику на кожен запит. Головний ризик — flag debt: сотні забутих прапорців і комбінаторний вибух гілок; кожен release-прапорець має мати власника і дату видалення.

🧠 Запам'ятай: deploy ≠ release — код виїжджає вимкненим, а користувачі отримують фічу прапорцем.

12 Zero-downtime деплої та міграції

Під час будь-якого деплою деякий час одночасно працюють стара і нова версії — і код, і схема БД мають це витримувати.

🔀 Вузол вибору: стратегія деплою
СтратегіяПлюсиМінуси
Rolling ✅Дефолт у Kubernetes (maxSurge/maxUnavailable), без додаткових ресурсів, поступова заміна подівСтарі й нові версії співіснують хвилини; відкат — теж rolling
Blue/greenНове оточення поруч, перемикання трафіку миттєво, миттєвий відкатПодвійні ресурси на час деплою; БД спільна — міграції однаково мають бути сумісні
Canary1–5% трафіку на нову версію, автоматичний аналіз метрик (Argo Rollouts, Flagger), обмежений радіус ураженняПотрібні добрі метрики і інструменти; складніше налаштувати

Коли що: більшість сервісів → rolling з правильними пробами й graceful shutdown; критичні платіжні шляхи → canary з автоматичним відкатом за error rate/p99; ризиковані інфраструктурні зміни → blue/green.

→
5. Contract: видалити address (окремий реліз)
  • Міграції — окремим кроком перед rollout (Kubernetes Job, крок CI/CD, init-контейнер з блокуванням), а не в main.js кожної репліки: 10 подів, що одночасно запускають міграцію, — гонки (більшість інструментів мають advisory lock, але на нього краще не покладатися як на дизайн).
  • Небезпечні DDL у Postgres: ADD COLUMN ... DEFAULT з volatile-виразом, ALTER TYPE, створення індексу без CONCURRENTLY, NOT NULL на великій таблиці — довгі блокування. Ставте lock_timeout на міграції.
  • Відкат коду має бути можливим без відкату схеми — тому кроки expand завжди обернено сумісні.
  • Черги й події — той самий принцип: нові споживачі вміють читати старий формат повідомлень, нові поля опціональні.
💼
На співбесіді запитають так «Як перейменувати колонку без даунтайму?» — Expand/contract у кілька релізів: додати нову колонку, писати в обидві, backfill, перемкнути читання, видалити стару окремим релізом. Міграції — окремим кроком до rollout, кожен крок сумісний і з попередньою, і з наступною версією коду.

13 SLO, алерти і runbooks

Алерт має будити людину лише тоді, коли користувачі страждають і людина може щось зробити — інакше алерти почнуть ігнорувати.

ТермінЩо цеПриклад
SLIВиміряний показник якості з погляду користувачаЧастка запитів POST /orders з відповіддю не-5xx швидше за 500 мс
SLOЦільове значення SLI за період99.5% за 30 днів
Error budgetДопустима «погана» частка: 100% − SLO0.5% ≈ 3.6 год поганої роботи на місяць
SLAЮридична обіцянка клієнтам з компенсацією; завжди м'якша за SLO99% або повернення коштів

Як алертити

  • На симптоми, а не причини. «Error rate POST /orders вище SLO» — будить. «CPU 85%» — ні, це дашборд або тікет: високий CPU без впливу на користувачів не інцидент.
  • Burn rate. Алерт, коли error budget витрачається занадто швидко: наприклад, у 14 разів швидше норми і за останню годину, і за останні 5 хвилин (multi-window) — швидко ловить реальні аварії і не реагує на поодинокі сплески.
  • Node-специфічні попереджувальні сигнали (тікет/Slack, не пейджер): heap стабільно росте між major GC, event loop lag p99 > 100 мс, рестарти подів (OOMKilled, exit 137), вичерпання пулу БД.
  • Кожен алерт має runbook — посилання прямо в алерті.

Шаблон runbook «OrdersAPI high error rate»

  1. Вплив: що бачать користувачі, які ендпоінти.
  2. Дашборди: RED по маршрутах, event loop lag, heap, пул БД; посилання на трейси з помилками й Sentry issue.
  3. Чи був деплой/зміна прапорця за останню годину? → відкат (kubectl rollout undo) або вимкнення прапорця — першим кроком, розслідування потім.
  4. Залежності: статус БД, Redis, зовнішніх API; чи не спрацював circuit breaker.
  5. Пом'якшення: масштабувати репліки, увімкнути kill switch важкої функції, rate limit.
  6. Ескалація: кого кликати, якщо за 15 хвилин не зрозуміло.
  7. Після: blameless postmortem, задачі на запобігання.
🧠 Запам'ятай: алерт = симптом для користувача + burn rate + runbook; усе інше — дашборди й тікети.

14 Каверзні питання співбесіди

Питання з реальних продакшн-інцидентів.

БазаЧому pino швидший за winston і console.log?
Мінімальна робота в головному потоці: швидка серіалізація в JSON-рядок без форматування, буферизований асинхронний запис, а форматування/відправку виконують transports у worker thread або зовнішній процес (pino-pretty, агент). winston робить більше алокацій і форматування в основному потоці; console.log використовує util.inspect і може писати синхронно.
ПасткаЧому process.on('uncaughtException', (e) => logger.error(e)) без виходу — погана ідея?
Після невідомого винятку стан процесу непередбачуваний: незакриті транзакції, не відпущені локи, не повернуті з'єднання пулу, напівоновлені кеші. Процес продовжує обслуговувати запити з потенційно зіпсованим станом. Правильно — лог fatal + flush, спроба швидкого graceful shutdown з таймаутом, exit(1), рестарт супервізором.
БазаОпишіть правильну послідовність graceful shutdown.
SIGTERM → readiness=503 → пауза drain (або preStop sleep), поки балансувальник прибирає под → server.close() + closeIdleConnections() + connection: close на відповідях → дочекатися in-flight → закрити consumers черг, пули БД, Redis, flush логів/трейсів → вихід з кодом 0. Усе під власним таймаутом, коротшим за terminationGracePeriodSeconds; по таймауту — closeAllConnections() і exit(1).
ПасткаКонтейнер завжди зупиняється рівно за 10 секунд після docker stop. Чому?
SIGTERM не доходить до Node або не обробляється: shell-form CMD (PID 1 — sh, не пересилає), npm start як посередник, або Node як PID 1 без обробника SIGTERM (ядро не застосовує дефолтний обробник до PID 1). Через 10 с Docker шле SIGKILL. Рішення: exec-form CMD ["node", ...], tini/--init, обробник SIGTERM.
ПасткаЩо не так з liveness-пробою, яка перевіряє з'єднання з БД?
При збої БД усі поди одночасно провалять liveness і Kubernetes їх перезапустить — каскад: холодні старти, шторм підключень до БД, що відновлюється. Liveness перевіряє лише «процес не завис» (event loop відповідає). Залежності — максимум у readiness і обережно.
БазаЧим liveness, readiness і startup проби відрізняються за наслідками?
Liveness провалено → рестарт контейнера. Readiness провалено → под прибирають з балансування без рестарту. Startup — поки не пройде, інші проби не запускаються (захист повільних стартів від передчасного liveness-рестарту).
ПасткаЧому node:alpine може зламати застосунок, який працює на node:slim?
Alpine використовує musl замість glibc. Prebuilt бінарники нативних модулів часто зібрані під glibc — на musl вони або відсутні (потрібна компіляція з python/g++ в образі), або падають. Плюс відмінності DNS-резолвера (наприклад, обробка search-доменів), інша поведінка malloc під навантаженням. Офіційні збірки Node для musl мають статус experimental.
БазаНавіщо multi-stage build і правильний порядок COPY?
Multi-stage: у фінальний образ потрапляють лише dist і production node_modules, без компіляторів, devDependencies, вихідників і кешів — менший розмір і менше CVE. Порядок: спершу package*.json + npm ci, потім код — шар із залежностями кешується, поки не змінився lockfile, і збірка після зміни коду займає секунди.
ПасткаЧому лейбл route у метриці latency має бути шаблоном, а не req.url?
Кожне унікальне значення лейбла — новий time series. /orders/8f3a… з UUID дає мільйони серій: пам'ять процесу (prom-client тримає серії в heap) і Prometheus вибухають. Шаблон /orders/:id дає одну серію на маршрут.
ПасткаOpenTelemetry увімкнено, але спанів для Postgres немає. Чому?
SDK стартував після того, як застосунок імпортував pg — монкі-патч не встиг. Інструментацію треба завантажувати першою: node --import ./instrumentation.mjs app.js; для ESM це ще й реєструє loader hooks, без яких патчинг ESM-модулів не працює.
БазаЯк перейменувати колонку без даунтайму при rolling deploy?
Expand/contract: додати нову колонку → код пише в обидві → backfill батчами → код читає нову → окремим релізом видалити стару. Міграції — окремим кроком до rollout; кожен крок сумісний зі старою і новою версіями коду, щоб відкат коду не вимагав відкату схеми.
БазаЧим NODE_ENV відрізняється від APP_ENV і навіщо обидва?
NODE_ENV=production — сигнал бібліотекам (Express кешує шаблони й ховає стеки, npm пропускає devDependencies). Він має бути production і на staging, щоб тестувати ту саму поведінку. Розрізнення оточень (staging/prod, URL-и, прапорці) — окремою змінною APP_ENV і конфігом.
ПасткаЧи варто запускати PM2 cluster mode всередині Kubernetes-поду?
Зазвичай ні. Оркестратор уже дає рестарт і масштабування; PM2 ховає падіння воркерів від Kubernetes (под «здоровий», хоча воркери крешаться), ускладнює ліміти пам'яті (кілька heap в одному cgroup), метрики (окремий реєстр на воркер) і сигнали. Один процес на контейнер, масштабування репліками.
БазаНа що ставити пейджинговий алерт, а на що — ні?
Пейджер — на симптоми для користувачів відносно SLO: error rate і latency ключових ендпоінтів через burn rate error budget (multi-window). Не пейджер — CPU, пам'ять, окремі рестарти, ріст heap: це дашборди й тікети. Кожен алерт — з runbook і власником.

16 Як запам'ятати

Дев'ять образів продакшн-готовності.

1
Structured logging
Одна подія — один JSON-рядок з полями, які можна фільтрувати.
Асоціація: бортовий журнал літака з графами, а не щоденник з думками.
2
Request id / ALS
Контекст, що супроводжує запит крізь усі await і додається в кожен лог.
Асоціація: бирка на валізі в аеропорту — де б вона не їхала, відомо, чия вона.
3
Crash-only
Після невідомої помилки — впасти й перезапуститись, а не лагодити стан на ходу.
Асоціація: якщо в каструлю з супом впала муха — варять новий, а не виловлюють.
4
Graceful shutdown
503 → drain → close listener → in-flight → ресурси → exit, під таймаутом.
Асоціація: ресторан перед закриттям: табличка «зачинено», доїдають ті, хто сидить, потім миють кухню.
5
Liveness vs readiness
Liveness провал — рестарт; readiness провал — прибрати з балансування.
Асоціація: пульс (живий?) проти «готовий прийняти пацієнта?» у лікаря.
6
PID 1
Не отримує дефолтних обробників сигналів і має збирати зомбі — тому tini і exec-form CMD.
Асоціація: директор, якому не передають дзвінки, поки не призначить секретаря (tini).
7
Multi-stage build
Збирати в одному образі, запускати в іншому — лише артефакти.
Асоціація: меблі збирають у цеху, а в квартиру везуть готову шафу без верстатів.
8
Metrics / traces / logs
Чи зламано / де саме / що сталося — зв'язані через trace_id.
Асоціація: спідометр, GPS-трек поїздки і відеореєстратор.
9
Expand / contract
Змінювати схему кроками, кожен сумісний зі старим і новим кодом.
Асоціація: будують новий міст поруч зі старим, переводять рух, і лише потім розбирають старий.
10
Error budget
100% − SLO: скільки «поганого» можна витратити на ризик і деплої.
Асоціація: ліміт на картці — поки є залишок, можна ризикувати, вичерпав — заморожуй релізи.
