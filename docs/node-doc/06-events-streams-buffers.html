01 Як три кити пов'язані

Це не три окремі API, а одна конструкція: stream — це EventEmitter, який передає Buffer-и.

Коли ви пишете http.createServer((req, res) => ...), у вас в руках одразу всі три концепції: req — це Readable stream, який є нащадком EventEmitter (події 'data', 'end', 'error'), а шматки тіла запиту, що приходять у 'data', — це Buffer. Те саме з fs.createReadStream, net.Socket, process.stdin, zlib.createGzip(), дочірніми процесами.

02 EventEmitter: синхронний emit

Найпоширеніша хибна уява про Node: "події асинхронні". Ні — emit() викликає слухачів прямо зараз, по черзі.

EventEmitter — це просто об'єкт зі словником { ім'я_події: [слухач1, слухач2, ...] }. on() додає функцію в масив, emit() синхронно проходить масив і викликає кожну функцію в порядку реєстрації. Ніякої черги, ніякого event loop. Асинхронність з'являється лише тоді, коли хтось інший (libuv, таймер) викликає emit() пізніше.

ee-sync.js
const { EventEmitter } = require('node:events');
const bus = new EventEmitter();

bus.on('order', (id) => console.log('listener A', id));
bus.on('order', (id) => console.log('listener B', id));

console.log('before emit');
const had = bus.emit('order', 42);   // повертає true, якщо слухачі були
console.log('after emit, had listeners:', had);
console.log('emit without listeners:', bus.emit('nobody'));

// before emit
// listener A 42
// listener B 42
// after emit, had listeners: true
// emit without listeners: false

Наслідки синхронності

  • Важкий слухач блокує того, хто емітить. Якщо в обробнику 'data' ви робите 200 мс CPU-роботи — весь процес стоїть 200 мс.
  • Виняток у слухачі вилітає з emit() у код, що емітив, і наступні слухачі вже не викликаються.
  • Вкладені emit виконуються "всередині" поточного слухача — порядок як у звичайних викликах функцій.
  • Якщо треба дати шанс решті коду ініціалізуватися (наприклад, emit у конструкторі, коли підписників ще немає), класичний прийом — process.nextTick(() => this.emit('ready')). Так роблять і вбудовані модулі.
Задача 1СередньоВкладений emit
task-1.js
const { EventEmitter } = require('node:events');
const e = new EventEmitter();
e.on('tick', () => { console.log('A start'); e.emit('nested'); console.log('A end'); });
e.on('nested', () => console.log('nested handler'));
e.on('tick', () => console.log('B'));
e.emit('tick');
A start nested handler A end B

Слухач A викликає emit('nested') — це звичайний синхронний виклик, тож nested handler друкується посеред A. Лише коли A завершиться, emit('tick') перейде до B. Жодних черг — чистий стек викликів.

⚠️
Порівняйте з DOM: element.dispatchEvent() у браузері теж синхронний, а от "асинхронні" події (клік, відповідь fetch) просто ініціюються з event loop. Механіка браузерного event loop — у JS Doc, туторіал 1; тут різниця лише в тому, хто викликає emit.

03 EventEmitter: error, once, витоки

Подія 'error' — особлива і вбиває процес; а забуті слухачі — найчастіший витік пам'яті в Node.

'error' без слухача = throw

Якщо ви емітите 'error', а слухача немає — EventEmitter кидає цю помилку. На верхньому рівні це uncaughtException і падіння процесу з кодом 1. Це навмисно: помилка не повинна тихо зникнути. Тому кожен stream, сокет, клієнт БД, який ви створюєте, має отримати .on('error', ...) (або бути всередині pipeline(), який підпишеться сам).

ee-error.js
const { EventEmitter } = require('node:events');
const e = new EventEmitter();
setTimeout(() => console.log('never printed'), 100);
e.emit('error', new Error('db connection lost'));

// node:events:487
//       throw er; // Unhandled 'error' event
// Error: db connection lost
//     at Object.<anonymous> (ee-error.js:4:17) ...
// $ echo $?  → 1

Якщо емітити не Error, а рядок — отримаєте Error: Unhandled error. ('just a string'). З обробником усе спокійно: e.on('error', (err) => log(err)). Є також символ events.errorMonitor — слухач на нього отримує помилку до звичайних і не вважається обробником (для метрик/логування, процес все одно впаде, якщо справжнього обробника немає).

once, prependListener, off

ee-order.js
const e = new EventEmitter();
e.on('x', () => console.log('on'));
e.prependListener('x', () => console.log('prepend'));  // на початок масиву
e.once('x', () => console.log('once'));               // знімається перед викликом
e.emit('x'); console.log('---'); e.emit('x');
console.log('count:', e.listenerCount('x'));

const h = () => console.log('h');
e.on('y', h);
e.off('y', h);                        // = removeListener; потрібна ТА САМА функція
console.log('y emitted?', e.emit('y'));

// prepend
// on
// once
// ---
// prepend
// on
// count: 2
// y emitted? false

Пастка: e.off('y', () => ...) з новою стрілочною функцією нічого не зніме — порівняння за посиланням. Зберігайте посилання на обробник. Є ще removeAllListeners(name), але не викликайте його на чужих емітерах (сокетах, streams) — зламаєте внутрішніх слухачів Node.

Витоки слухачів і MaxListenersExceededWarning

Типовий витік: на кожен HTTP-запит ви робите db.on('reconnect', handler) на довгоживучому об'єкті й ніколи не знімаєте. Масив слухачів росте, замикання тримають req/res — пам'ять тече. Node має простий детектор: більше defaultMaxListeners (10) слухачів однієї події на одному емітері — warning.

ee-leak.js
const e = new EventEmitter();
for (let i = 0; i < 11; i++) e.on('data', () => {});
// (node:48081) MaxListenersExceededWarning: Possible EventEmitter memory leak detected.
// 11 data listeners added to [EventEmitter]. MaxListeners is 10.
// Use emitter.setMaxListeners() to increase limit
  • Це лише warning, слухачі додаються. Запустіть з --trace-warnings, щоб побачити стек, де додано 11-й.
  • e.setMaxListeners(n) — коли багато слухачів легітимно (наприклад, 50 підписників на шину). 0 = без ліміту — цим ви вимикаєте детектор, робіть свідомо.
  • Сучасний патерн прибирання — AbortSignal: e.on('x', fn, { signal }) не підтримується класичним EE, але events.on(e, 'x', { signal }), events.once(e, 'x', { signal }) і EventTarget.addEventListener('x', fn, { signal }) підтримують. Один ac.abort() знімає все.

Async-слухачі і captureRejections

EventEmitter не знає про Promise: якщо слухач — async функція і він кидає, ви отримаєте unhandled rejection (з Node 15 — падіння процесу), а не подію 'error'. Опція captureRejections: true ловить відхилені проміси слухачів і перенаправляє їх в 'error':

ee-capture.js
const e = new EventEmitter({ captureRejections: true });
e.on('job', async () => { throw new Error('async fail'); });
e.on('error', (err) => console.log('error event got:', err.message));
e.emit('job');
// error event got: async fail

Глобально: EventEmitter.captureRejections = true. Важливо: emit() все одно не чекає на проміси слухачів — emit повертається одразу.

Мости до async/await: events.once і events.on

ee-await.js
const { EventEmitter, once, on } = require('node:events');

const e = new EventEmitter();
setTimeout(() => e.emit('ready', 1, 2), 10);
const args = await once(e, 'ready');      // [1, 2]; reject, якщо раніше прийде 'error'

// async-ітератор по всіх подіях (обережно: нескінченний, поки не abort/break)
for await (const [msg] of on(socketLike, 'message', { signal })) handle(msg);

// EventTarget — веб-стандарт, вбудований у Node глобально
const et = new EventTarget();
et.addEventListener('ping', (ev) => console.log(ev.type, ev instanceof Event)); // ping true
et.dispatchEvent(new Event('ping'));

04 Buffer: байти й кодування

Рядок — це текст, Buffer — це байти. Плутанина між ними дає зламані емодзі, неправильні Content-Length і криві підписи.

JavaScript-рядок — послідовність UTF-16 code units. Але мережа, диск, криптографія працюють із байтами. Buffer — масив байтів фіксованої довжини (кожен елемент 0–255), який живе поза V8 heap. Перетворення "рядок ↔ байти" завжди йде через кодування.

buffer-encodings.js
const s = 'Привіт 👋';
console.log('length:', s.length,                 // 9  — UTF-16 code units (емодзі = 2)
            'byteLength:', Buffer.byteLength(s),   // 17 — байти в UTF-8 (кирилиця 2, емодзі 4)
            '[...s].length:', [...s].length);      // 8  — code points (символи, як бачить людина*)

console.log(Buffer.from(s));
// <Buffer d0 9f d1 80 d0 b8 d0 b2 d1 96 d1 82 20 f0 9f 91 8b>

Buffer.from('Hi!').toString('hex');        // '486921'
Buffer.from('Hi?>').toString('base64');     // 'SGk/Pg=='
Buffer.from('Hi?>').toString('base64url');  // 'SGk_Pg'   (без + / =, безпечно для URL/JWT)
Buffer.from('SGk/Pg==', 'base64').toString(); // 'Hi?>'

// різати байти посеред символу — отримаєте U+FFFD
Buffer.from(s).subarray(0, 3).toString();  // 'П�'

* Для складених емодзі (сім'я, прапори, тон шкіри) навіть code points ≠ "символ на екрані"; для цього є Intl.Segmenter з granularity: 'grapheme'.

Класичний баг: res.setHeader('Content-Length', body.length) для рядка з кирилицею. .length рахує UTF-16 одиниці, а клієнт отримає більше байтів — відповідь обріжеться або з'єднання зависне. Правильно: Buffer.byteLength(body). Друга версія того ж бага — chunk.toString() у кожному 'data': багатобайтовий символ, розрізаний між двома chunk-ами, перетвориться на �. Лікується stream.setEncoding('utf8') або StringDecoder (вони тримають "хвіст" незавершеного символу).
💡
Порівнювати секрети (HMAC-підписи, токени) треба через crypto.timingSafeEqual(bufA, bufB), а не === — інакше timing attack. Обидва аргументи мають бути Buffer однакової довжини (туторіал 14).

05 Buffer: пам'ять, pool, subarray

Buffer — це вид (view) на шматок ArrayBuffer. Звідси і швидкість, і найпідступніші баги зі спільною пам'яттю.

Buffer = Uint8Array + методи

З Node 4+ Buffer — підклас Uint8Array. Тобто кожен Buffer — це вікно (byteOffset, length) на якийсь ArrayBuffer (buf.buffer). Будь-яке API, що приймає Uint8Array (Web Crypto, fetch, TextDecoder), прийме і Buffer. Пам'ять ArrayBuffer-ів рахується як external/arrayBuffers у process.memoryUsage(), а не в heapUsed.

alloc vs allocUnsafe і pool

МетодЩо робитьКоли
Buffer.alloc(n)виділяє і заповнює нулямиза замовчуванням
Buffer.allocUnsafe(n)не обнуляє; для малих n бере шматок зі спільного poolгарячий шлях, якщо ви одразу перезапишете ВСІ байти
Buffer.allocUnsafeSlow(n)не обнуляє і не бере з poolдовгоживучий маленький буфер (щоб не тримати весь pool)
Buffer.from(...)копіює рядок/масив/ArrayBuffer (для ArrayBuffer — без копії, вид на нього)конвертація
buffer-pool.js
const small = Buffer.allocUnsafe(10);
console.log(small.buffer.byteLength, small.byteOffset); // 65536 48  ← шматок спільного pool
console.log(Buffer.alloc(10).buffer.byteLength);        // 10        ← власний ArrayBuffer
console.log(Buffer.from('abc').buffer.byteLength);      // 65536     ← from(string) теж з pool
console.log(Buffer.poolSize);                           // 65536 на Node 24 (історично було 8 KiB)

Pool існує заради швидкості: дрібні виділення не ходять у системний аллокатор щоразу. Ціна: (1) allocUnsafe може містити старі дані іншої частини програми — якщо віддати такий буфер клієнту, не перезаписавши, отримаєте витік секретів (історичний CVE-клас, через це deprecated new Buffer(n)); (2) buf.buffer — це весь pool, тож new Uint8Array(buf.buffer) без byteOffset/length побачить чужі байти.

subarray ділить пам'ять, Buffer.from — копіює

buffer-share.js
const orig = Buffer.from('hello');
const view = orig.subarray(0, 2);               // вид на ТІ САМІ байти
const copy = Buffer.from(orig.subarray(0, 2));  // справжня копія
view[0] = 0x4a;                                 // 'J'
console.log(orig.toString(), view.toString(), copy.toString());
// Jello Je he

// Увага: Buffer.prototype.slice теж НЕ копіює (і deprecated на користь subarray),
// а Uint8Array.prototype.slice — копіює. Однакова назва, різна семантика!
const u = new Uint8Array([1, 2, 3]);
u.slice(0, 2)[0] = 9; console.log(u[0]);        // 1
⚠️
Витік через subarray: ви читаєте файл на 50 MB, берете з нього 20-байтовий subarray як ключ і кладете в кеш — і тримаєте всі 50 MB, бо вид не дає звільнити батьківський ArrayBuffer. Для довгого зберігання — Buffer.from(sub) (копія).

Ціна конкатенації

Buffer має фіксовану довжину, тож "дописати" не можна — Buffer.concat щоразу виділяє новий буфер і копіює все. Конкатенація в циклі — O(n²):

buffer-concat.js
const N = 5000, chunk = Buffer.alloc(100, 1);

let acc = Buffer.alloc(0);
for (let i = 0; i < N; i++) acc = Buffer.concat([acc, chunk]); // ~683 ms на моїй машині

const parts = [];
for (let i = 0; i < N; i++) parts.push(chunk);
const once = Buffer.concat(parts);                                  // ~0.7 ms

// (при N = 20 000 перший варіант — вже ~15 секунд: квадратичне зростання)
🧠 Запам'ятай: збирайте chunk-и в масив і робіть один Buffer.concat(parts, totalLength) наприкінці — а краще взагалі не збирайте, а стрімте далі.

06 Streams: навіщо і 4 типи

Стріми роблять споживання пам'яті сталим, незалежно від розміру даних, і дають обробку "по мірі надходження".

Два способи прочитати файл на 89 MB (реальний вимір на Node 24, process.memoryUsage().arrayBuffers):

memory-compare.js
// 1) все в пам'ять
const data = fs.readFileSync('big.csv');
// readFile: arrayBuffers = 89.3 MB | file = 89.1 MB      ← росте разом із файлом

// 2) стрім chunk-ами по 64 KB
fs.createReadStream('big.csv').on('data', (c) => { bytes += c.length; /* ... */ });
// stream:   peak arrayBuffers = 28.6 MB | read = 89.1 MB  ← обмежено GC, не розміром файлу

Чесна примітка: пік у стрім-варіанті не дорівнює 64 KB, бо прочитані chunk-и звільняються збирачем сміття не миттєво. Але це значення не росте з розміром файлу: на 10 GB файлі readFile просто впаде (Buffer має ліміт ~4 GB, а рядок — ~512 MB–1 GB залежно від версії V8), а стрім пройде. Крім пам'яті, стрім дає time-to-first-byte: обробка починається з першого chunk-а, а не після завантаження всього.

07 Readable: flowing vs paused

Readable має два режими споживання; змішування стилів — джерело "втрачених" даних.

Кожен Readable стартує в стані readableFlowing === null (ніхто не споживає), і дані просто накопичуються у внутрішньому буфері до highWaterMark, після чого читання з джерела призупиняється.

  • Flowing — дані "течуть" самі через події 'data'. Вмикається: on('data'), resume(), pipe().
  • Paused — ви самі тягнете stream.read() на подію 'readable'. Вмикається: pause() або підписка на 'readable' (вона має пріоритет над 'data').
Задача 2СкладноКоли приходить 'data'?
task-2.js
const { Readable } = require('node:stream');
const r = new Readable({ read() {} });
r.push('a'); r.push('b');
console.log('readableFlowing:', r.readableFlowing);
r.on('data', (c) => console.log('data', c.toString()));
console.log('after on(data):', r.readableFlowing);
r.pause(); console.log('after pause:', r.readableFlowing);
r.push('c');
setTimeout(() => { console.log('resume'); r.resume(); r.push(null); }, 10);
r.on('end', () => console.log('end'));
readableFlowing: null after on(data): true after pause: false resume data a data b data c end

on('data') перемикає стрім у flowing, але сам потік даних стартує асинхронно (на process.nextTick). Ми встигаємо викликати pause() синхронно — тож жоден chunk не прийшов, вони лежать у буфері. Лише після resume() буфер вивантажується, а push(null) дає 'end'. Звідси правило: між on('data') і першою подією у вас є "синхронне вікно", щоб навісити решту слухачів.

Найкращий спосіб споживання — async iteration

Readable реалізує Symbol.asyncIterator. for await сам керує backpressure (бере наступний chunk, лише коли тіло циклу завершилось), прокидає помилки як винятки і знищує стрім при break/throw:

async-iter.js
const { Readable, finished } = require('node:stream');

async function* gen() { for (let i = 1; i <= 3; i++) yield `row-${i}\n`; }
for await (const chunk of Readable.from(gen())) process.stdout.write('got ' + chunk);
// got row-1  got row-2  got row-3

const r2 = Readable.from(['a', 'b', 'c']);
finished(r2, (err) => console.log('finished r2, err =', err?.code));
for await (const c of r2) { console.log('first:', c); break; }   // break → destroy()
console.log('r2.destroyed =', r2.destroyed);
// first: a
// r2.destroyed = true
// finished r2, err = ABORT_ERR    ← стрім не дочитали, finished повідомляє про це
  • Readable.from(iterable | asyncIterable) — найпростіший спосіб зробити стрім з масиву, генератора, результатів курсора БД. За замовчуванням objectMode: true; рядки не розбиваються на символи.
  • Генератор, що бере дані з повільного джерела, автоматично отримує backpressure: yield не буде викликано повторно, поки споживач не готовий.
  • Readable також має "функціональні" helpers: r.map(fn, { concurrency }), filter, take, toArray(), reduce (експериментальні в частині версій — перевіряйте документацію своєї версії перед продакшеном).
⚠️
Не змішуйте on('data'), pipe() і for await на одному стрімі — кожен з них споживає дані, і chunk-и розподіляться між ними непередбачувано. Обирайте один стиль на стрім.

08 Writable і backpressure

Backpressure — механізм, що не дає швидкому виробнику завалити пам'ять повільним споживачем. Це головне питання про streams на співбесіді.

Кожен стрім має highWaterMark — поріг (не жорсткий ліміт!) внутрішнього буфера: у байтах для звичайних стрімів (з Node 22 за замовчуванням 64 KiB, раніше було 16 KiB; у fs.createReadStream — теж 64 KiB) або в кількості об'єктів для objectMode (16).

  • writable.write(chunk) кладе chunk у буфер і повертає false, коли writableLength >= highWaterMark. Дані все одно прийняті — false означає "будь ласка, зупинись".
  • Коли буфер повністю спорожніє, Writable емітить 'drain' — сигнал продовжувати.
  • Якщо ігнорувати false і писати далі — Node не впаде і не відкине дані: буфер просто росте в RAM без межі. Це і є витік пам'яті "через стріми".
backpressure.js
const { Writable } = require('node:stream');
const slow = new Writable({
  highWaterMark: 4,                                   // 4 байти — щоб побачити ефект
  write(chunk, enc, cb) { setTimeout(cb, 10); },      // повільний споживач (диск/мережа)
});

let i = 0;
function produce() {
  while (i < 6) {
    const ok = slow.write(`c${i}`);
    console.log(`write c${i} -> ${ok}, writableLength=${slow.writableLength}`);
    i++;
    if (!ok) {                                        // буфер повний — чекаємо
      console.log('  pause, wait for drain');
      slow.once('drain', () => { console.log('  drain!'); produce(); });
      return;
    }
  }
  slow.end(() => console.log('finished'));
}
produce();

Писати цей цикл з drain руками в прикладному коді майже ніколи не потрібно — pipe(), pipeline() і for await роблять його за вас. Але треба розуміти, бо саме його ламають самописні обгортки на зразок source.on('data', c => dest.write(c)) (ігнорує false → необмежений буфер).

await-drain.mjs
import { once } from 'node:events';
// ручний запис з повагою до backpressure — компактний async-варіант
for (const row of hugeArray) {
  if (!out.write(JSON.stringify(row) + '\n')) await once(out, 'drain');
}
out.end();
💼
На співбесіді запитають так "Що станеться, якщо ігнорувати повернення write()?" — дані не втратяться і помилки не буде; вони накопичуватимуться у writableLength у пам'яті процесу, поки не скінчиться RAM (OOM). highWaterMark — поріг для сигналу, а не ліміт.

09 pipe() vs pipeline()

pipe() передає дані, але не помилки; pipeline() передає і те, й інше та прибирає за собою.

a.pipe(b) з'являвся ще в Node 0.x і робить одну річ добре — backpressure. Але:

  • помилка в a не передається в b і не закриває його — треба .on('error') на КОЖНОМУ стрімі ланцюжка;
  • при помилці стріми не знищуються → відкриті файлові дескриптори, сокети, що висять;
  • немає єдиного місця "весь ланцюжок завершився (успішно чи ні)".

stream.pipeline(...streams, callback) (і промісна версія з node:stream/promises) вирішує все це: підписується на помилки кожного стріму, при першій — викликає destroy(err) на всіх, і один раз викликає колбек (резолвить/реджектить проміс).

pipe-vs-pipeline.js
const { Readable, Transform, PassThrough, pipeline } = require('node:stream');
const make = () => ({
  src: new Readable({ read() {} }),
  bad: new Transform({ transform(c, e, cb) { cb(new Error('transform failed')); } }),
  dst: new PassThrough(),
});

{ // 1) pipe()
  const { src, bad, dst } = make();
  bad.on('error', (e) => {
    console.log('[pipe] bad error:', e.message);
    setImmediate(() => console.log('[pipe] src destroyed?', src.destroyed, '| dst destroyed?', dst.destroyed));
  });
  src.pipe(bad).pipe(dst);
  src.push('x');
}
setTimeout(() => { // 2) pipeline()
  const { src, bad, dst } = make();
  pipeline(src, bad, dst, (err) => {
    console.log('[pipeline] callback:', err && err.message);
    console.log('[pipeline] src destroyed?', src.destroyed, '| dst destroyed?', dst.destroyed);
  });
  src.push('x');
}, 50);

// [pipe] bad error: transform failed
// [pipe] src destroyed? false | dst destroyed? false      ← джерело й приймач "висять"
// [pipeline] callback: transform failed
// [pipeline] src destroyed? true | dst destroyed? true    ← прибрано все

stream/promises: сучасний стиль

pipeline-promises.mjs
import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';

const ac = new AbortController();
setTimeout(() => ac.abort(), 5_000);              // таймаут на всю операцію

await pipeline(
  createReadStream('big.csv'),
  async function* (source) {                       // генератор як Transform!
    for await (const chunk of source) yield chunk.toString().replaceAll(';', ',');
  },
  createGzip(),
  createWriteStream('big.csv.gz'),
  { signal: ac.signal },                           // abort → destroy усіх, reject AbortError
);

finished() і семантика destroy

  • stream.finished(s, cb) / finished з stream/promises — надійно дочекатися, що стрім завершився, помилився або був передчасно закритий ('end'/'finish' можуть ніколи не настати, якщо стрім знищили — тоді finished поверне помилку ERR_STREAM_PREMATURE_CLOSE чи AbortError).
  • s.destroy(err?) — негайно звільнити ресурси; буфер відкидається; далі 'error' (якщо передали err) і 'close'. Після destroy write() дає ERR_STREAM_DESTROYED.
  • s.end() — "граційно": дописати буфер, викликати _final, потім 'finish'.
  • Стріми за замовчуванням autoDestroy: true — після end/finish або помилки destroy викликається сам.

10 Власний Transform і objectMode

Найкорисніший тип для прикладного коду: парсери, конвертери, фільтри, що працюють на будь-якому обсязі.

Головна складність Transform — межі chunk-ів не збігаються з межами ваших записів. Рядок CSV легко розріжеться між двома chunk-ами по 64 KB. Тому парсер тримає "хвіст" (tail) незавершеного запису і дописує його в _flush.

csv-transform.js
const { Transform, Readable, Writable } = require('node:stream');
const { pipeline } = require('node:stream/promises');

class LineSplitter extends Transform {
  constructor() { super({ readableObjectMode: true }); this.tail = ''; } // вхід — байти, вихід — рядки
  _transform(chunk, enc, cb) {
    const lines = (this.tail + chunk.toString('utf8')).split('\n');
    this.tail = lines.pop();            // останній шматок може бути неповним
    for (const l of lines) if (l) this.push(l);
    cb();                               // готовий до наступного chunk-а
  }
  _flush(cb) { if (this.tail) this.push(this.tail); cb(); }   // кінець входу
}

const toRecord = new Transform({
  objectMode: true,
  transform(line, enc, cb) {
    const [name, qty] = line.split(',');
    cb(null, { name: name.toUpperCase(), qty: Number(qty) });  // cb(null, x) = push(x) + cb()
  },
});

const sink = new Writable({ objectMode: true, write(rec, enc, cb) { console.log(rec); cb(); } });

// chunk-и навмисно розрізають рядки посередині
const src = Readable.from(['apple,3\nban', 'ana,5\ncher', 'ry,7']);
pipeline(src, new LineSplitter(), toRecord, sink).then(() => console.log('done'));

// { name: 'APPLE', qty: 3 }
// { name: 'BANANA', qty: 5 }
// { name: 'CHERRY', qty: 7 }
// done

Для продакшену: chunk.toString() у LineSplitter теж може розрізати UTF-8 символ на межі chunk-а. Виправлення — StringDecoder з node:string_decoder у _transform (this.decoder.write(chunk)) або просто readline (s12).

Правила, які легко порушити

  • Завжди викликайте cb рівно один раз — інакше стрім зависне (не викликали) або впаде з ERR_MULTIPLE_CALLBACK.
  • Помилку передавайте через cb(err), не throw з асинхронного коду.
  • this.push() можна викликати 0..N разів на один вхідний chunk (фільтр / розгортання).
  • objectMode: true — chunk-ом може бути будь-яке JS-значення, крім null (це маркер кінця); highWaterMark рахується в штуках (16). Окремо: readableObjectMode / writableObjectMode для "байти на вхід, об'єкти на вихід".
  • Async-логіка всередині _transform (запит у БД на кожен рядок) автоматично дає backpressure: поки ви не викликали cb, наступний chunk не прийде. Але й паралелізму нуль — для нього є readable.map(fn, { concurrency: 8 }).
✅
Часто класу взагалі не треба: у pipeline() можна передати async generator function async function* (source) { for await (const c of source) yield f(c); } — це Transform без бойлерплейту, з backpressure і прокиданням помилок.

12 Практичні рецепти

Чотири задачі, які реально трапляються в бекенді, — і в кожній ключ у pipeline + backpressure.

1. Мультигігабайтний файл рядок за рядком

3 і 4. Upload прямо на диск і відповідь через Transform

http-streams.mjs
import http from 'node:http';
import { createWriteStream, createReadStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';
import { Transform } from 'node:stream';
import { createGzip } from 'node:zlib';

const server = http.createServer(async (req, res) => {
  try {
    if (req.method === 'PUT' && req.url === '/upload') {
      // req — Readable: тіло пишеться на диск chunk-ами, не накопичується в RAM
      await pipeline(req, createWriteStream('./upload.bin'));
      res.writeHead(201).end('stored\n');
    } else if (req.url === '/report') {
      const upper = new Transform({ transform(c, _e, cb) { cb(null, c.toString().toUpperCase()); } });
      res.writeHead(200, { 'content-type': 'text/plain', 'content-encoding': 'gzip' });
      // res — Writable: повільний клієнт → backpressure аж до читання файлу
      await pipeline(createReadStream('./small.txt'), upper, createGzip(), res);
    } else res.writeHead(404).end();
  } catch (err) {
    // клієнт обірвав з'єднання / диск переповнений: pipeline вже все закрив
    console.error('stream failed:', err.code ?? err.message);
    if (!res.headersSent) res.writeHead(500).end(); else res.destroy(err);
  }
});

// перевірка: fetch PUT 1 000 000 байт → "201 stored", файл 1000000 байт;
// GET /report → 200 "HELLO STREAM\nLINE TWO\n" (fetch сам розпакував gzip)
  • У реальному upload додайте ліміт розміру (Transform, що рахує байти і кидає помилку при перевищенні) і пишіть у тимчасовий файл з подальшим rename (атомарність — туторіал 7).
  • Multipart-форми парсять стрімінгово бібліотеки на кшталт busboy; S3-аплоад — @aws-sdk/lib-storage Upload, який теж приймає стрім.
  • Коли клієнт обриває з'єднання, res знищується → pipeline реджектиться з ERR_STREAM_PREMATURE_CLOSE і закриває файл — без цього в старих pipe()-реалізаціях текли дескриптори.
🎉
Цікавий факт Знамениту ідею "стрімів як Unix pipes" для Node популяризував stream-handbook Джеймса Халлідея (substack) — звідти і a.pipe(b).pipe(c), і назва through для простих transform-ів. А pipeline з'явився в ядрі лише в Node 10 — з модуля pump Матіаса Буса, який роками латав саме проблему "pipe не прокидає помилки".

13 Каверзні питання співбесіди

Питання, на яких відсіюють тих, хто знає streams лише за "fs.createReadStream().pipe(res)".

БазаEventEmitter асинхронний?
Ні. emit() синхронно викликає слухачів у порядку реєстрації й повертає true/false. Асинхронними є джерела подій (libuv, таймери). Наслідок: важкий слухач блокує того, хто емітить, і весь event loop.
ПасткаЩо буде, якщо async-слухач кине виняток?
EventEmitter не дивиться на повернений Promise → unhandled rejection (падіння процесу за замовчуванням з Node 15), а не 'error'. Рішення: captureRejections: true або try/catch у слухачі. І emit не чекає завершення async-слухачів.
БазаЧому процес падає від одного emit('error')?
Подія 'error' особлива: без жодного слухача EventEmitter робить throw. Тому кожен стрім/сокет/клієнт потребує обробника помилок або має бути частиною pipeline(). errorMonitor — для спостереження, не для обробки.
БазаЩо таке backpressure і як вона реалізована в Node?
Механізм узгодження швидкостей виробника і споживача. write() повертає false, коли внутрішній буфер досяг highWaterMark; виробник має чекати 'drain'. На Readable-стороні — якщо ніхто не читає, буфер заповнюється до HWM і _read перестає викликатися. pipe, pipeline, for await роблять це автоматично.
ПасткаhighWaterMark — це максимальний розмір буфера?
Ні, це поріг сигналу. Якщо ігнорувати false, буфер росте необмежено. Також один chunk може бути більшим за HWM — він буде прийнятий цілком.
Базаpipe() vs pipeline()?
pipe дає backpressure, але не прокидає помилки й не знищує інші стріми при помилці → витік fd/сокетів. pipeline підписується на помилки всіх, знищує всіх при першій, викликає один callback / проміс, підтримує AbortSignal і генератори як transform.
Пасткаbuf.slice() копіює дані?
Для Buffer — ні (вид на ту саму пам'ять, як subarray; slice deprecated). Для Uint8Array — так, копіює. Копія — Buffer.from(buf). Наслідок: маленький subarray великого буфера тримає весь великий буфер у пам'яті.
ПасткаЧим небезпечний Buffer.allocUnsafe?
Не обнуляє пам'ять і для малих розмірів бере шматок зі спільного pool → може містити старі дані (токени, паролі). Якщо віддати не повністю перезаписаний буфер назовні — витік. До того ж buf.buffer вказує на весь pool.
БазаЧому 'Привіт'.length ≠ Buffer.byteLength('Привіт')?
.length — UTF-16 code units (6), byteLength — байти в UTF-8 (12, кирилиця по 2). Емодзі: length 2, байтів 4. Для Content-Length потрібен саме byteLength.
ПасткаЧому chunk.toString() у кожному 'data' може ламати текст?
Межа chunk-а може пройти посеред багатобайтового UTF-8 символу → обидві половини декодуються в U+FFFD. Рішення: setEncoding('utf8'), StringDecoder, readline або накопичити байти й декодувати разом.
БазаDuplex vs Transform?
Duplex — дві незалежні сторони (сокет: що пишете — йде в мережу, що читаєте — прийшло з мережі). Transform — Duplex, де вихід обчислюється з входу (_transform), напр. gzip, шифрування, парсер.
ПасткаЩо станеться з файловим стрімом при break у for await?
Ітератор викличе destroy() — стрім закриється, fd звільниться. finished() отримає помилку передчасного закриття (на Node 24 — ABORT_ERR). Якщо треба продовжити читання пізніше — не використовуйте for await з break, або Readable.prototype.iterator({ destroyOnReturn: false }).
БазаЯк обробити 10 GB лог-файл, щоб порахувати помилки?
readline.createInterface({ input: fs.createReadStream(path), crlfDelay: Infinity }) + for await. Пам'ять стала, обробка почнеться одразу. Для CPU-важкого парсингу — розбити на діапазони байтів і обробляти у worker_threads (туторіал 8).
ПасткаWeb Streams чи Node streams у новому коді?
Всередині Node-сервісу — Node streams (швидші, вся екосистема fs/http/zlib). Web Streams — на межах з fetch і в коді, що має бути переносним між рантаймами. Міст — Readable.toWeb/fromWeb.

15 Як запам'ятати

Асоціації, які спливуть у голові на співбесіді.

1
emit()
Синхронно викликає всіх слухачів по черзі і лише потім повертається.
Асоціація: староста, що особисто обходить кожного в списку — поки не обійде всіх, далі не йде.
2
'error' без слухача
EventEmitter кидає помилку → процес падає.
Асоціація: пожежна сигналізація, не підключена до пульта, — вмикає спринклери по всій будівлі.
3
MaxListenersExceeded
Попередження про >10 слухачів однієї події — типова ознака витоку.
Асоціація: одинадцять людей у ліфті на десятьох — ліфт поїде, але дзвоник пищить не дарма.
4
Buffer
Uint8Array-вікно на ArrayBuffer поза V8 heap; байти, не текст.
Асоціація: рамка, прикладена до довгої фотоплівки: рамок багато, плівка одна.
5
subarray vs from
subarray ділить пам'ять, Buffer.from копіює.
Асоціація: посилання на Google Doc (бачиш зміни) vs завантажений PDF (знімок).
6
highWaterMark
Поріг буфера, після якого write() каже "стоп" (false).
Асоціація: позначка рівня на дамбі — вода може піднятися вище, але шлюзи вже треба закривати.
7
'drain'
Буфер Writable спорожнів — можна писати далі.
Асоціація: касир кличе "наступний!" — тоді й підходиш.
8
pipeline()
З'єднує стріми, прокидає помилку і знищує всіх при першій.
Асоціація: конвеєр з аварійною кнопкою: зупиняє всю лінію, а не одну стрічку.
9
Transform + tail
Межі chunk-ів ≠ межі записів; зберігай незавершений хвіст до наступного chunk-а.
Асоціація: читаєш книгу посторінково — речення, що перейшло на наступну сторінку, тримаєш у голові.
10
Duplex vs Transform
Duplex — дві незалежні труби; Transform — одна труба з фільтром.
Асоціація: телефон (говориш і слухаєш незалежно) vs перекладач (що чує — те й видає, перекладене).
