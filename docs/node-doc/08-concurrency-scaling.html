01 Concurrency vs parallelism

Node з коробки дає concurrency (багато задач у процесі), але не parallelism (кілька задач в один момент на різних ядрах) для вашого JS.

ConcurrencyParallelism
Визначеннябагато задач перебувають у процесі виконання, чергуючиськілька задач виконуються одночасно на різних ядрах
Аналогіяодин кухар, який поставив 10 каструль і перемикається між нимип'ять кухарів, кожен зі своєю каструлею
У Nodeevent loop + неблокуюче I/O: 10 000 відкритих з'єднань в одному потоціworker_threads, cluster/кілька процесів, libuv threadpool, нативні аддони
Допомагає дляI/O-bound: БД, HTTP-виклики, файлиCPU-bound: хешування, стиснення, парсинг, ML-інференс, рендер зображень

Ваш JavaScript у звичайному Node-процесі виконується в одному потоці — main thread з одним V8 isolate. Сам процес при цьому має ще потоки: libuv threadpool (fs, dns.lookup, crypto, zlib), потоки V8 для GC і JIT-компіляції. Тому top може показати Node на 130% CPU, а ваш код усе одно не паралельний. Як event loop чергує задачі — туторіал 2; асинхронні патерни (Promise.all — це concurrency, не parallelism!) — туторіал 3.

💼
На співбесіді запитають так "Чи робить Promise.all([hash(a), hash(b)]) обчислення паралельними?" — Якщо hash — чистий JS, ні: обидва виконаються послідовно на main thread, Promise.all лише чекає. Паралельно буде, лише якщо робота йде поза JS-потоком — в libuv (crypto.pbkdf2), у воркері або в іншому процесі/сервісі.

02 CPU-bound: демо блокування

Одна синхронна функція на 1 секунду = одна секунда, коли сервер не відповідає НІКОМУ, включно з health-check.

block.js
const http = require('node:http');
const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));

const server = http.createServer((req, res) => {
  if (req.url === '/fib') return res.end(String(fib(40)));   // ~1.2 с чистого CPU
  res.end('pong');
}).listen(0, async () => {
  const base = `http://localhost:${server.address().port}`;
  const t0 = performance.now();
  const slow = fetch(base + '/fib').then(() =>
    console.log(`/fib  done at ${Math.round(performance.now() - t0)} ms`));
  await new Promise((r) => setTimeout(r, 20));
  const t1 = performance.now();
  await fetch(base + '/ping');                                   // найлегший запит
  console.log(`/ping done at ${Math.round(performance.now() - t0)} ms (waited ${Math.round(performance.now() - t1)} ms)`);
  await slow; server.close();
});

// /fib  done at 1273 ms
// /ping done at 1274 ms (waited 1209 ms)    ← "pong" чекав, поки порахується fib

Реальні продакшен-аналоги fib(40): JSON.parse на 50 MB тілі, bcrypt/argon2 в JS-реалізації, катастрофічний backtracking у RegExp (ReDoS), sort на мільйоні елементів, генерація PDF/Excel, ресайз зображень на чистому JS, шаблонізація великої сторінки. Діагностика — event loop lag (perf_hooks.monitorEventLoopDelay), CPU-профіль (туторіал 15).

Перші ліки — без потоків

  • Зробити менше роботи: кеш, пагінація, стрімінговий парсер замість JSON.parse гіганта, правильний алгоритм.
  • Нативні/асинхронні версії: crypto.scrypt замість JS-хешування (йде в libuv threadpool), sharp (libvips у своїх потоках) замість JS-ресайзу, zlib async-API.
  • Розбити на шматки з setImmediate між ними — loop "дихає", але загальний час той самий і код складніший. Компроміс для рідкісних задач на 50–200 мс.
  • Якщо після цього CPU-робота лишається — потрібен справжній паралелізм: далі.

03 worker_threads: основи

Worker — це окремий потік ОС з власним V8 isolate, власним event loop і власною пам'яттю JS, але в тому ж процесі.

fib-worker.js
const { Worker, isMainThread, parentPort, workerData } = require('node:worker_threads');
const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));

if (!isMainThread) {
  // --- код воркера ---
  parentPort.postMessage(fib(workerData.n));
} else {
  // --- код main thread ---
  const N = 38, JOBS = 4;
  const runInWorker = (n) => new Promise((resolve, reject) => {
    const w = new Worker(__filename, { workerData: { n } });  // workerData клонується
    w.once('message', resolve);
    w.once('error', reject);                                   // виняток у воркері
  });

  let t = performance.now();
  for (let i = 0; i < JOBS; i++) fib(N);
  console.log(`main thread, ${JOBS} x fib(${N}) sequential: ${Math.round(performance.now() - t)} ms`);

  t = performance.now();
  const ticks = []; const iv = setInterval(() => ticks.push(1), 10);   // чи живий main loop?
  await Promise.all(Array.from({ length: JOBS }, () => runInWorker(N)));
  clearInterval(iv);
  console.log(`${JOBS} workers in parallel: ${Math.round(performance.now() - t)} ms (main loop ticked ${ticks.length}x meanwhile)`);

  t = performance.now();
  await runInWorker(1);
  console.log(`worker startup overhead (fib(1)): ${Math.round(performance.now() - t)} ms`);
}
output (8 фізичних ядер)
main thread, 4 x fib(38) sequential: 1816 ms
4 workers in parallel:            584 ms (main loop ticked 56x meanwhile)
worker startup overhead (fib(1)):     28 ms

(Для стислості верхньорівневий await показано в CJS-фрагменті; у реальному файлі він загорнутий в async IIFE.)

Три висновки з цифр: (1) прискорення ~3.1× на 4 воркерах — майже лінійне для чистого CPU; (2) main loop продовжував працювати (56 тіків таймера) — сервер відповідав би на запити; (3) старт воркера — десятки мілісекунд і кілька MB пам'яті (новий isolate, завантаження модулів), тому створювати воркер на кожен запит — антипатерн; потрібен пул (s7).

04 Модель пам'яті і передача даних

Воркери не діляться JS-об'єктами. Дані або копіюються, або переносяться, або живуть у явно спільному буфері.

Structured clone: що копіюється і скільки коштує

clone-cost.js
const { MessageChannel } = require('node:worker_threads');
const { port1 } = new MessageChannel();

const rows = Array.from({ length: 200_000 }, (_, i) => ({ id: i, name: 'user' + i, tags: ['a', 'b'] }));
let t = performance.now();
port1.postMessage(rows);
console.log('postMessage 200k objects:', Math.round(performance.now() - t), 'ms');  // ~115 ms БЛОКУЄ відправника

try { port1.postMessage({ fn: () => 1 }); } catch (e) { console.log(e.name, '-', e.message); }
// DataCloneError - () => 1 could not be cloned.

class User { constructor() { this.n = 1; } hi() {} }
const c = structuredClone(new User());
console.log(c, c instanceof User);       // { n: 1 } false   ← прототип і методи втрачено
  • Клонуються: примітиви, plain objects, масиви, Date, RegExp, Map, Set, BigInt, typed arrays, Error, циклічні посилання. Не клонуються: функції, класові прототипи (лишаються лише поля), DOM-подібні хендли, Symbol-ключі, геттери (обчислюються в значення).
  • Серіалізація відбувається синхронно на потоці відправника — віддати воркеру 100 MB JSON-подібних даних означає заблокувати main thread на сотні мс, тобто втратити те, заради чого воркер створювали.
  • Тому воркеру краще передавати посилання на дані (шлях до файлу, id у БД, діапазон рядків), а не самі дані.

transferList: перенос замість копії

transfer.js
const big = new ArrayBuffer(100 * 1024 * 1024);
port1.postMessage(big);                      // клон
// clone   : 133.0 ms; sender still has 104857600

const big2 = new ArrayBuffer(100 * 1024 * 1024);
port1.postMessage(big2, [big2]);             // перенос власності
// transfer: 0.0 ms; sender now has 0       ← буфер "detached" у відправника

Переносити можна ArrayBuffer, MessagePort, FileHandle, Web Streams. Пастка: Buffer-и з пулу (Buffer.from('...'), малі allocUnsafe — див. туторіал 6) ділять один ArrayBuffer — перенос "відірвав" би чужі дані, тому Node позначає pool як непереносний: postMessage(b, [b.buffer]) для Buffer.from('hello') кидає DataCloneError: Cannot transfer object of unsupported type (перевірено), а для Buffer.alloc(10) — переносить. Для переносу виділяйте Buffer.alloc / окремий ArrayBuffer.

05 SharedArrayBuffer і Atomics

Справжня спільна пам'ять між потоками — і разом з нею всі класичні проблеми: гонки, видимість, дедлоки.

SharedArrayBuffer (SAB), переданий у workerData або postMessage, не копіюється: усі потоки бачать ті самі байти. Працювати з ним можна лише через typed arrays (Int32Array, Float64Array...) — ніяких об'єктів. І тут JavaScript уперше отримує data races.

race.js
const { Worker, isMainThread, workerData } = require('node:worker_threads');
const ITER = 1_000_000, THREADS = 4;

if (!isMainThread) {
  const arr = new Int32Array(workerData.sab);
  for (let i = 0; i < ITER; i++) {
    if (workerData.atomic) Atomics.add(arr, 0, 1);   // атомарний read-modify-write
    else arr[0]++;                                   // read → +1 → write: можна перебити посередині
  }
} else {
  const run = (atomic) => new Promise((resolve) => {
    const sab = new SharedArrayBuffer(4);
    let done = 0;
    for (let t = 0; t < THREADS; t++)
      new Worker(__filename, { workerData: { sab, atomic } }).on('exit', () => {
        if (++done === THREADS) resolve(new Int32Array(sab)[0]);
      });
  });
  console.log('expected        :', ITER * THREADS);
  console.log('plain arr[0]++  :', await run(false));
  console.log('Atomics.add     :', await run(true));
}

// expected        : 4000000
// plain arr[0]++  : 1139542     ← 70% інкрементів загубилися (число різне щоразу)
// Atomics.add     : 4000000
AtomicsПризначення
load, storeчитання/запис з гарантією видимості для інших потоків
add, sub, and, or, xor, exchangeатомарні RMW-операції (лічильники, прапорці)
compareExchange(arr, i, expected, value)CAS — основа для lock-free структур і м'ютексів
wait(arr, i, value, timeout)блокуюче очікування, поки arr[i] === value; повертає 'ok' / 'not-equal' / 'timed-out'
notify(arr, i, count)розбудити N потоків, що чекають на цій комірці
waitAsyncнеблокуючий варіант, повертає проміс — придатний для main thread

Atomics.wait / notify

wait-notify.js
// worker:
const flag = new Int32Array(workerData.sab);
const r = Atomics.wait(flag, 0, 0, 5000);        // потік СПИТЬ, поки flag[0] === 0 (макс. 5 с)
parentPort.postMessage(`worker woke up: ${r}, flag=${flag[0]}`);

// main:
setTimeout(() => {
  Atomics.store(flag, 0, 1);
  console.log('main: notified', Atomics.notify(flag, 0), 'waiter(s)');
}, 300);

// main: notified 1 waiter(s)
// worker woke up: ok after ~300 ms, flag=1
🧊
Дедлоки і заморожений main thread. На відміну від браузера, Node дозволяє Atomics.wait на main thread — і це майже завжди помилка: поки main спить, event loop стоїть, жодні запити, таймери і навіть повідомлення від воркерів не обробляються. Класичний дедлок — два потоки чекають один одного: 
// worker: Atomics.wait(flags, 1, 0, 1000)   — чекає, поки main поставить flags[1]
// main:   Atomics.wait(flags, 0, 0, 1000)   — чекає, поки worker поставить flags[0]
// worker: wait -> timed-out                  ← лише таймаут розірвав цикл
// main:   wait -> ok after ~1000 ms          ← (без таймаутів — вічне зависання)
Правила: на main thread — лише Atomics.waitAsync або повідомлення; завжди таймаут; однаковий порядок захоплення "замків"; і загалом — віддавайте перевагу message passing, SAB лишайте для гарячих числових буферів (аудіо, зображення, лічильники прогресу, ring buffer-и).

06 Життєвий цикл, помилки, resourceLimits

Воркер може впасти, вийти за пам'ять або зависнути — і main thread має це пережити.

  • 'online' — почав виконувати код; 'message'; 'error' — неперехоплений виняток у воркері (воркер після цього завершується); 'exit' (code) — завжди останнє. Без слухача 'error' помилка воркера стане помилкою процесу.
  • 'messageerror' — повідомлення не вдалося десеріалізувати.
  • Зависання (нескінченний цикл) не дає ні error, ні exit — потрібен таймаут на задачу + worker.terminate(). terminate перериває навіть синхронний цикл.
limits.js
const { Worker } = require('node:worker_threads');
const w = new Worker(`const a = []; while (true) a.push(new Array(1e5).fill(1));`, {
  eval: true,
  resourceLimits: { maxOldGenerationSizeMb: 32 },   // також maxYoungGenerationSizeMb, codeRangeSizeMb, stackSizeMb
});
w.on('error', (e) => console.log('worker error:', e.code, '-', e.message));
w.on('exit', (c) => console.log('worker exit code:', c, '| main thread alive:', true));

// worker error: ERR_WORKER_OUT_OF_MEMORY - Worker terminated due to reaching memory limit: JS heap out of memory
// worker exit code: 1 | main thread alive: true

resourceLimits обмежують лише JS heap воркера — Buffer-и та нативна пам'ять у ліміт не входять. Це не ізоляція безпеки: воркер у тому ж процесі може читати файли, змінювати спільні глобальні ресурси процесу, а segfault в нативному аддоні вб'є весь процес. Для недовіреного коду — окремий процес/контейнер.

07 Пул воркерів і piscina

Створювати воркер на кожну задачу — дорого; тримайте фіксовану кількість і подавайте їм задачі з черги.

Ідея пулу: N воркерів (≈ кількість ядер мінус одне для main thread) стартують один раз, задачі стоять у черзі, вільний воркер бере наступну. Ручна реалізація — ~80 рядків (черга, мапа задача → resolve, перезапуск впалих, таймаути, abort). На практиці використовують piscina (підтримується людьми з Node core):

pool.mjs
// worker-task.mjs
export default function resize({ path, width }) {
  return heavyCpuResize(path, width);     // може бути async; повернене значення = результат задачі
}

// server.mjs
import Piscina from 'piscina';
import { availableParallelism } from 'node:os';

const pool = new Piscina({
  filename: new URL('./worker-task.mjs', import.meta.url).href,
  maxThreads: Math.max(1, availableParallelism() - 1),
  maxQueue: 1000,                          // backpressure: повна черга → помилка, а не OOM
  idleTimeout: 30_000,
});

app.post('/thumbnail', async (req, res) => {
  const ac = new AbortController();
  req.on('close', () => ac.abort());       // клієнт пішов — задача не потрібна
  const out = await pool.run({ path: req.body.path, width: 320 }, { signal: ac.signal });
  res.json(out);
});

Альтернативи: workerpool, tinypool (використовує Vitest), threads.js.

Чесний висновок з виміру: збільшення пулу прибирає "хвилі" (немає черги), але не робить CPU-роботу швидшою, якщо ядер не вистачає — у кількох прогонах UV_THREADPOOL_SIZE=8 загалом був навіть не швидшим. Задається через env до старту (UV_THREADPOOL_SIZE=16 node app.js), бо пул створюється ліниво при першому використанні.

09 cluster

Кілька Node-процесів слухають один порт: primary приймає з'єднання і роздає їх воркерам.

cluster побудований на child_process.fork (туторіал 7): primary запускає N копій того ж скрипта з IPC-каналом. Коли воркер викликає server.listen(3000), він насправді просить primary: primary тримає справжній listening-сокет і передає прийняті з'єднання воркерам через IPC (на Linux/macOS — round-robin за замовчуванням; на Windows — сокет ділиться, і розподіл робить ОС).

Спершу — child_process.fork з IPC як "воркер-процес"

До появи worker_threads (стабільні з Node 12) CPU-роботу виносили в окремі Node-процеси через fork, і цей патерн досі корисний, коли потрібна повна ізоляція: падіння нативного аддона, витік пам'яті чи process.exit() у дочірньому процесі не зачеплять батька, а пам'ять дитини ОС звільнить цілком після її завершення.

fork-pool.js
const { fork } = require('node:child_process');

const child = fork('./heavy-task.js', { serialization: 'advanced' }); // structured clone: Map, Set, BigInt, Buffer
const pending = new Map();
let seq = 0;
child.on('message', ({ id, result, error }) => {
  const p = pending.get(id); pending.delete(id);
  error ? p.reject(new Error(error)) : p.resolve(result);
});
child.on('exit', (code) => {                      // дитина впала — відхилити все, що чекало
  for (const p of pending.values()) p.reject(new Error(`child exited ${code}`));
  pending.clear();                                // ...і перезапустити (з backoff)
});
const run = (payload) => new Promise((resolve, reject) => {
  const id = ++seq; pending.set(id, { resolve, reject });
  child.send({ id, payload });
});

// heavy-task.js
process.on('message', ({ id, payload }) => {
  try { process.send({ id, result: compute(payload) }); }
  catch (e) { process.send({ id, error: e.message }); }
});

Порівняно з воркером: старт повільніший (новий процес, ~30–50 MB RSS), повідомлення йдуть через pipe з серіалізацією, немає SharedArrayBuffer і transfer. Порівняно з cluster: fork — це "виконай задачу", cluster — "обслуговуй той самий порт".

cluster.js
const cluster = require('node:cluster');
const http = require('node:http');
const PORT = 3456, WORKERS = 3;

if (cluster.isPrimary) {
  console.log(`primary ${process.pid}, schedulingPolicy RR? ${cluster.schedulingPolicy === cluster.SCHED_RR}`);
  for (let i = 0; i < WORKERS; i++) cluster.fork();
  cluster.on('exit', (worker, code) => {
    console.log(`worker ${worker.id} died (code ${code}); restarting`);
    cluster.fork();                        // у проді — з backoff, щоб не крутити crash loop
  });
  // ... після 'listening' від усіх: 9 запитів двома способами (див. вивід)
} else {
  http.createServer((req, res) => {
    if (req.url === '/crash') process.exit(1);
    res.end(String(cluster.worker.id));
  }).listen(PORT);                         // "listen" делегується primary
}
output
primary 56950, schedulingPolicy RR? true
new connection per request : { '1': 3, '2': 3, '3': 3 }   ← ідеальний round-robin
one keep-alive connection  : { '3': 9 }                   ← одне з'єднання = один воркер
worker 2 died (code 1); restarting

Другий рядок — важливий практичний нюанс: балансування відбувається на рівні з'єднань. Клієнт з keep-alive (або HTTP/2, або gRPC, або один великий upstream-проксі з пулом з'єднань) може "приклеїтися" до одного воркера. Той самий ефект — у Kubernetes Service з gRPC.

Чому cluster зараз використовують рідше

  • У контейнерах типова модель — один процес на контейнер; масштабування — кількістю pod-ів (HPA), перезапуск — оркестратором, балансування — Service/Ingress. Cluster всередині pod дублює ці функції.
  • Pod з cpu: 1 не виграє від 4 воркерів; а os.cpus() може показати ядра хоста і створити зайві процеси (туторіал 7).
  • Кожен воркер — окремий процес з власним heap: 8 воркерів × 150 MB = 1.2 GB, і 8 окремих пулів з'єднань до БД (s11).
  • Де cluster/PM2 досі доречний: VM або bare metal без оркестратора, великі інстанси, де один pod на ноду, легасі-деплої.

10 PM2

Процес-менеджер, що робить cluster, рестарти, логи і zero-downtime reload однією командою.

ecosystem.config.cjs
module.exports = {
  apps: [{
    name: 'api',
    script: './dist/server.js',
    exec_mode: 'cluster',          // використовує node:cluster всередині
    instances: 'max',              // або число; 'max' = кількість CPU

    wait_ready: true,              // чекати process.send('ready') від застосунку
    listen_timeout: 10000,
    env_production: { NODE_ENV: 'production' },
  }, {
    name: 'worker',
    script: './dist/queue-worker.js',
    exec_mode: 'fork',             // звичайний процес — для споживачів черг
    instances: 2,
  }],
};

Sticky sessions для WebSocket

WebSocket — довгоживуче з'єднання з конкретним інстансом, і воно само по собі не потребує sticky. Sticky (за cookie або IP-hash) потрібні, коли протокол робить кілька HTTP-запитів, які мають потрапити на той самий інстанс: Socket.IO long-polling fallback, handshake + upgrade. Але sticky не вирішує "повідомлення для користувача, підключеного до іншого інстансу" — для цього все одно потрібен спільний pub/sub. І sticky погіршує балансування: при масштабуванні нові інстанси довго стоять напівпорожні.

13 Каверзні питання співбесіди

Ці питання перевіряють, чи розумієте ви, де в Node насправді є паралелізм.

БазаNode однопотоковий?
Ваш JS виконується в одному потоці (на ізолят), але процес багатопотоковий: libuv threadpool (fs, dns.lookup, crypto, zlib), потоки V8 для GC/JIT, а також worker_threads, які дають кілька JS-потоків в одному процесі. Мережеве I/O йде через epoll/kqueue/IOCP без потоків.
ПасткаЧи допоможуть worker_threads прискорити запити до БД?
Ні. Очікування БД не блокує main thread — це I/O. Воркер додасть накладні витрати (clone, окремий пул з'єднань). Воркери — для CPU-bound задач.
Базаworker_threads vs child_process.fork vs cluster?
Worker — потік у тому ж процесі: дешевший старт, SharedArrayBuffer, transfer; падіння нативного коду кладе все. fork — окремий процес: повна ізоляція, лише IPC (JSON/advanced serialization), більше пам'яті. cluster — fork-и, що ділять серверний порт, для масштабування HTTP-пропускної здатності, а не для окремих CPU-задач.
ПасткаЧому postMessage великого масиву об'єктів може "заморозити" сервер?
Structured clone виконується синхронно на потоці відправника: 200k об'єктів — ~115 мс блокування в нашому вимірі. Передавайте посилання (шлях, id), переносіть ArrayBuffer через transferList або використовуйте SharedArrayBuffer.
Пасткаarr[0]++ на SharedArrayBuffer з 4 потоків — що не так?
Data race: інкремент — це read, add, write; потоки перебивають один одного. У нашому демо з 4 000 000 вийшло 1 139 542. Потрібно Atomics.add (або CAS-цикл з compareExchange).
ПасткаЧим небезпечний Atomics.wait на main thread?
Node дозволяє його (браузер — ні), але він заморожує event loop: запити, таймери і навіть повідомлення воркерів не обробляються. Легко отримати дедлок, коли main чекає на воркер, а воркер — на щось від main. Використовуйте Atomics.waitAsync або повідомлення, завжди з таймаутом.
БазаUV_THREADPOOL_SIZE і worker_threads — це одне й те саме?
Ні. Threadpool виконує C++-частини Node API (fs, dns.lookup, crypto, zlib), розмір 4 за замовчуванням, задається env до першого використання. worker_threads виконують ваш JS у окремих ізолятах. Збільшити threadpool не допоможе вашому JS-циклу.
ПасткаЧому з cluster один воркер на 100% CPU, а інші простоюють?
Cluster балансує з'єднання, а не запити. Keep-alive клієнт, HTTP/2 чи проксі з пулом кількох з'єднань "приклеюються" до одного воркера (у демо: одне keep-alive з'єднання → усі 9 запитів на воркер 3). Рішення — балансування на L7 перед інстансами, обмеження тривалості з'єднань.
БазаЧи потрібен cluster/PM2 у Kubernetes?
Зазвичай ні: один процес на контейнер, масштабування кількістю pod-ів, рестарти — kubelet, балансування — Service. Cluster у pod-і множить пам'ять і з'єднання до БД і плутає метрики. Виняток — великі pod-и з кількома ядрами, коли так дешевше.
ПасткаВи масштабували сервіс з 2 до 20 інстансів, і впала БД. Чому?
Кожен інстанс тримає свій пул: 20 × 10 = 200 з'єднань (з cluster — ще × воркери) проти max_connections 100. Ліки: PgBouncer/RDS Proxy, менші пули, обмежити max replicas, read replicas.
БазаЩо робить сервіс stateless і навіщо?
Жодного стану, потрібного для наступних запитів, у пам'яті чи на диску інстансу: сесії, кеш, rate limits, кімнати WS, файли — у Redis/БД/S3. Тоді будь-який інстанс обробляє будь-який запит, інстанси можна вбивати й додавати вільно.
ПасткаЧи потрібні sticky sessions для WebSocket?
Для самого WS-з'єднання — ні (воно і так живе на одному інстансі). Потрібні, коли протокол має кілька HTTP-запитів до upgrade (Socket.IO polling). Але для доставки повідомлень між інстансами все одно потрібен спільний pub/sub (Redis adapter).
БазаЗвіт генерується 40 секунд. Куди його подіти?
У чергу (BullMQ/SQS): HTTP повертає 202 Accepted з id задачі, окремі worker-процеси виконують, результат — у S3, клієнт дізнається через polling/SSE/webhook. Пул воркерів у HTTP-сервісі для 40 с — погано: тримає з'єднання, губиться при рестарті, конкурує з API за CPU.

Асоціація: передати ключі від машини — не копія, а машина тепер не твоя.
5
Atomics
Неподільні операції над SharedArrayBuffer — без них інкременти губляться.
Асоціація: одна дошка, четверо пишуть рахунок — без черги до крейди цифри перетираються.
6
Atomics.wait на main
Блокує event loop; ризик дедлоку.
Асоціація: диспетчер, що заснув біля телефону в очікуванні дзвінка — і не чує інших дзвінків.
7
UV_THREADPOOL_SIZE
Розмір пулу libuv для fs/dns.lookup/crypto/zlib — не для вашого JS.
Асоціація: чотири каси в банку для паперової роботи; твій власний калькулятор вони не рахують.
8
cluster
Primary роздає TCP-з'єднання N процесам round-robin.
Асоціація: хостес у ресторані садить гостей по черзі — але компанія, що сіла, лишається за тим столом весь вечір (keep-alive).
9
Stateless
Інстанс нічого не пам'ятає між запитами; стан — у Redis/БД/S3.
Асоціація: таксист: будь-яка машина довезе, бо адреса в замовленні, а не в пам'яті водія.
10
N × pool
Кожен інстанс множить з'єднання до БД.
Асоціація: кожен новий офіс компанії підключає ще 10 телефонних ліній до однієї АТС.
