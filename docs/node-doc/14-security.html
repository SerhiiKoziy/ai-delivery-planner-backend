01 Модель загроз Node API і захист у глибину

Безпека — не список бібліотек, а відповідь на питання "хто може щось нам надіслати і що станеться, якщо він збреше".

Типовий Node-бекенд приймає недовірений вхід з багатьох боків: HTTP (тіло, query, заголовки, cookies, завантажені файли), вебхуки, повідомлення з черг, відповіді сторонніх API — і сам виконує тисячі рядків чужого коду з node_modules. Дві Node-специфічні обставини роблять модель загроз особливою:

  • Один потік на всіх. Запит, що змусив процес 3 секунди рахувати regex чи парсити JSON, зупиняє всіх користувачів процесу (туторіал 2). DoS у Node часто дешевший, ніж у багатопотокових серверах.
  • Динамічна мова з мутабельними прототипами. Дані можуть змінити поведінку коду (prototype pollution), а об'єкт там, де чекали рядок, змінює семантику запиту до бази (NoSQL injection).

02 Ін'єкції: SQL, NoSQL operator injection, команди ОС

Спільний корінь усіх ін'єкцій — дані потрапили в позицію коду: у текст SQL, у структуру фільтра, у рядок shell.

SQL

Детально (з виконуваним демо на node:sqlite) — у туторіалі 12. Коротко: значення — тільки параметрами ($1, ?, tagged template), ідентифікатори (колонка сортування, назва таблиці) — тільки через allowlist, а будь-який raw/Unsafe-метод з інтерполяцією — червоний прапорець у рев'ю.

NoSQL operator injection (MongoDB)

У Mongo немає рядка запиту, який можна "зламати лапкою", — зате фільтр є об'єктом, і якщо атакувальник передасть об'єкт замість рядка, він впише туди оператор:

login.js (вразливо)
app.post('/login', async (req, res) => {
  // body: { "email": "admin@corp.com", "password": { "$ne": null } }
  const user = await users.findOne({ email: req.body.email, password: req.body.password });
  //                                  ↑ { password: { $ne: null } } — "будь-який не-null пароль"
  if (user) return res.json({ token: issueToken(user) });   // увійшли без пароля
  res.status(401).end();
});

// той самий трюк через query-рядок, якщо парсер підтримує вкладені об'єкти (qs, Express 4 "extended"):
// GET /users?email[$regex]=.*    →  req.query.email = { $regex: '.*' }
  • Головний захист — валідація типів на межі: z.object({ email: z.email(), password: z.string() }) — об'єкт замість рядка не пройде (туторіал 13).
  • Mongoose: mongoose.set('sanitizeFilter', true) загортає вкладені $-оператори з вводу в $eq; також strictQuery. Для голого драйвера — явний { email: { $eq: email } } або санітайзер, що видаляє ключі з $ і ..
  • $where і $function виконують JS на сервері бази — ніколи з вводу користувача.
  • Express 5 за замовчуванням використовує "simple" query parser (без вкладених об'єктів) — але JSON-тіло все одно може містити що завгодно.

Command injection через child_process

exec() передає рядок у /bin/sh -c, тож усі метасимволи shell (;, &&, |, $(), бектики) працюють. execFile()/spawn() без shell: true передають аргументи масивом напряму в execve — shell не бере участі:

cmd.mjs
import { exec, execFile } from 'node:child_process';
const input = 'report.pdf; echo PWNED-$(whoami)';
exec(`echo converting ${input}`, (err, out) => console.log('exec    :', out.trim()));
execFile('echo', ['converting', input], (err, out) => console.log('execFile:', out.trim()));
$ node cmd.mjs
execFile: converting report.pdf; echo PWNED-$(whoami)
exec    : converting report.pdf
PWNED-<user>

Через exec виконалась друга команда (і підстановка $(whoami)); через execFile увесь рядок лишився одним буквальним аргументом. Порядок рядків тут залежить від того, який дочірній процес завершився першим.

⚠️
execFile — не панацея. Argument injection: якщо ввід починається з -, програма сприйме його як прапорець (git з --upload-pack=..., tar --checkpoint-action=exec=...). Ставте -- перед позиційними аргументами і валідуйте формат. На Windows .bat/.cmd запускаються через cmd.exe навіть з execFile — відома категорія CVE. І найкраще — взагалі не викликати процеси, а використовувати бібліотеку (sharp замість convert).

03 Path traversal: ../ у назві файлу

Будь-який шлях, зібраний з вводу, має бути доведений як такий, що лежить усередині дозволеної директорії — після нормалізації.

path.js
const path = require('node:path');
const ROOT = path.resolve('/srv/app/uploads');

function naive(name) {
  return path.join(ROOT, name);
}
function safe(name) {
  const full = path.resolve(ROOT, name);
  if (full !== ROOT && !full.startsWith(ROOT + path.sep)) {
    throw new Error('path traversal: ' + name);
  }
  return full;
}
const inputs = ['avatar.png', '../../../etc/passwd', '/etc/passwd', 'a/../../uploads-evil/x', '..%2F..%2Fetc%2Fpasswd'];
for (const i of inputs) {
  let r;
  try { r = safe(i); } catch (e) { r = 'BLOCKED'; }
  console.log(i.padEnd(26), '| naive:', naive(i).padEnd(28), '| safe:', r);
}
console.log('bad prefix check:', '/srv/app/uploads-evil/x'.startsWith(ROOT));
console.log('decoded:', decodeURIComponent('..%2F..%2Fetc%2Fpasswd'));
$ node path.js
avatar.png                 | naive: /srv/app/uploads/avatar.png  | safe: /srv/app/uploads/avatar.png
../../../etc/passwd        | naive: /etc/passwd                  | safe: BLOCKED
/etc/passwd                | naive: /srv/app/uploads/etc/passwd  | safe: BLOCKED
a/../../uploads-evil/x     | naive: /srv/app/uploads-evil/x      | safe: BLOCKED
..%2F..%2Fetc%2Fpasswd     | naive: /srv/app/uploads/..%2F..%2Fetc%2Fpasswd | safe: /srv/app/uploads/..%2F..%2Fetc%2Fpasswd
bad prefix check: true
decoded: ../../etc/passwd

Що показало демо

  • path.join не захищає — він лише нормалізує, і ../ спокійно виходять за межі.
  • join і resolve по-різному трактують абсолютний шлях: join(ROOT, '/etc/passwd') склеює, а resolve(ROOT, '/etc/passwd') повертає /etc/passwd. Перевірка після resolve ловить обидва випадки.
  • Префікс без роздільника — баг: '/srv/app/uploads-evil'.startsWith('/srv/app/uploads') = true. Порівнюйте з ROOT + path.sep (або path.relative і перевірка, що результат не починається з .. і не абсолютний).
  • Кодування: %2F безпечний, поки його ніхто не декодує, — але фреймворк декодує req.params. Валідуйте після всіх декодувань, безпосередньо перед fs-викликом.
  • Симлінки: рядкова перевірка не бачить симлінк усередині ROOT, що веде назовні. Для високих ставок — fs.realpath і повторна перевірка; ще краще — не використовувати ім'я користувача як шлях взагалі: зберігайте файл під UUID, а оригінальну назву — в базі.
  • Також: нульовий байт (\0) Node відхиляє в fs-API помилкою, а express.static/res.sendFile з опцією root мають власний захист — використовуйте їх замість ручного createReadStream.

04 Prototype pollution

Атака, специфічна для JS: ключ __proto__ у JSON дозволяє дописати властивість у Object.prototype — і вона з'являється в кожному об'єкті процесу.

Механіка складається з трьох фактів. (1) JSON.parse створює "__proto__" як звичайну власну властивість (не змінює прототип). (2) Наївний deep merge робить target[key] для кожного ключа — а target["__proto__"] через гетер повертає Object.prototype. (3) Рекурсивний merge записує властивості туди — в спільний прототип усіх об'єктів.

proto.js
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      if (!target[key]) target[key] = {};
      merge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}
const body = JSON.parse('{"name":"x","__proto__":{"isAdmin":true}}');
console.log('own keys of body:', Object.keys(body));
merge({}, body);
const user = {};
console.log('user.isAdmin =', user.isAdmin);
console.log('({}).isAdmin =', ({}).isAdmin);
delete Object.prototype.isAdmin;

const viaLiteral = { __proto__: { isAdmin: true } };
console.log('literal own keys:', Object.keys(viaLiteral), '| ({}).isAdmin =', ({}).isAdmin);

const body2 = JSON.parse('{"constructor":{"prototype":{"polluted":"yes"}}}');
merge({}, body2);
console.log('({}).polluted =', ({}).polluted);
delete Object.prototype.polluted;

function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue;
    const v = source[key];
    if (typeof v === 'object' && v !== null) {
      if (!Object.hasOwn(target, key)) target[key] = {};
      safeMerge(target[key], v);
    } else target[key] = v;
  }
  return target;
}
safeMerge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'));
console.log('after safeMerge ({}).isAdmin =', ({}).isAdmin);
const dict = Object.create(null);
console.log('dict.toString =', dict.toString, '| "__proto__" in dict:', '__proto__' in dict);
$ node proto.js
own keys of body: [ 'name', '__proto__' ]
user.isAdmin = true
({}).isAdmin = true
literal own keys: [] | ({}).isAdmin = undefined
({}).polluted = yes
after safeMerge ({}).isAdmin = undefined
dict.toString = undefined | "__proto__" in dict: false

Зверніть увагу на різницю: JSON.parse створює __proto__ як власний ключ (небезпечно для merge), а об'єктний літерал { __proto__: x } встановлює прототип лише цього об'єкта (власних ключів 0, глобально нічого не забруднено). Шлях constructor.prototype працює без __proto__ взагалі: {}.constructor === Object, а Object.prototype — той самий спільний прототип.

На співбесіді запитають так "Як prototype pollution може дати RCE?" — забруднена властивість стає "гаджетом" у коді, що читає опції з об'єкта з дефолтами: наприклад, child_process.spawn читає options.shell або options.env, шаблонізатори читають опції компіляції; якщо в прототипі з'явилось shell або шматок шаблону — атакувальник керує виконанням. Публічні ланцюжки таких гаджетів для популярних бібліотек існують.

05 ReDoS і DoS event loop

Кілька десятків символів можуть зайняти процес на секунди — і в Node це секунди простою для всіх запитів одночасно.

Катастрофічний backtracking

Рушій регулярних виразів V8 (Irregexp) — backtracking: при невдачі він повертається і пробує інший розподіл символів між групами. Вкладений квантифікатор (a+)+ дозволяє розбити рядок з n літер a на групи 2n−1 способами — і коли в кінці стоїть !, що робить збіг неможливим, рушій перебирає всі.

redos.js
const evil = /^(a+)+$/;
for (const n of [20, 22, 24, 26, 28]) {
  const input = 'a'.repeat(n) + '!';
  const t = performance.now();
  evil.test(input);
  console.log(`n=${n}: ${(performance.now() - t).toFixed(0)} ms`);
}
const safe = /^a+$/;
const t = performance.now();
safe.test('a'.repeat(100000) + '!');
console.log(`safe /^a+$/ on 100001 chars: ${(performance.now() - t).toFixed(2)} ms`);
$ node redos.js (два запуски на одній машині)
n=20: 44 ms        |  n=20: 64 ms
n=22: 27 ms        |  n=22: 64 ms
n=24: 119 ms       |  n=24: 200 ms
n=26: 491 ms       |  n=26: 795 ms
n=28: 1922 ms      |  n=28: 2878 ms
safe /^a+$/ on 100001 chars: 0.24 ms

Абсолютні числа "шумлять" (JIT-розігрів на малих n, частота CPU), але тренд стабільний: +2 символи ≈ ×4 часу. 30 символів — це вже ~8–12 с заблокованого процесу, 40 — години. Безпечний /^a+$/ на 100 тис. символів — частки мілісекунди.

Як захищатися від ReDoS

  • Уникайте шаблонів з вкладеними квантифікаторами ((a+)+, (\w+\s?)*) і альтернаціями, що перетинаються ((a|a)*, (\d+|\d+\.)*).
  • Обмежуйте довжину входу до regex (z.string().max(254) для email) — найпростіший і найдієвіший захід.
  • Перевірка у CI: eslint-plugin-regexp, safe-regex2, recheck знаходять вразливі шаблони статично.
  • Лінійний рушій: пакет re2 (біндинг Google RE2, гарантований лінійний час, але без backreferences і lookbehind); у V8 є експериментальний non-backtracking рушій за прапорцем.
  • Залежності теж: ReDoS-CVE регулярно знаходять у парсерах (user-agent, дати, markdown, валідатори) — npm audit їх ловить.
  • Важку обробку недовіреного тексту — у worker_threads з таймаутом і worker.terminate() (туторіал 8).

Великі payload-и і JSON.parse

json-cost.mjs
const big = JSON.stringify({ items: Array.from({ length: 1_000_000 }, (_, i) => ({ id: i, name: 'item' + i })) });
console.log('payload MB:', (big.length / 1e6).toFixed(1));

const scheduled = performance.now();
setTimeout(() => console.log('timer(0) fired after ms:', Math.round(performance.now() - scheduled)), 0);

const t = performance.now();
JSON.parse(big);                       // синхронно: event loop стоїть
console.log('JSON.parse ms:', Math.round(performance.now() - t));
$ node json-cost.mjs
payload MB: 33.8
JSON.parse ms: 285
timer(0) fired after ms: 285

Таймер на 0 мс спрацював через 285 мс — увесь цей час процес не обслуговував нікого. Плюс пам'ять: 34 МБ тексту стають сотнями МБ об'єктів у купі. Тому:

  • Ліміт тіла: express.json({ limit: '100kb' }) (це й дефолт Express), Fastify bodyLimit (дефолт 1 MiB). Піднімайте лише на конкретних маршрутах, де потрібно.
  • Ліміти структури: довжина масивів і рядків у схемі; глибина вкладеності (глибокий JSON б'є по рекурсивних обробниках).
  • Завантаження файлів — стрімінгом на диск/S3 з лімітом розміру (busboy/@fastify/multipart limits), а не в пам'ять.
  • Декомпресія: gzip-тіло 1 МБ може розпакуватися в 1 ГБ (zip bomb) — ліміт застосовується до розпакованого розміру.
  • Повільні клієнти (slowloris): server.headersTimeout, server.requestTimeout, reverse proxy попереду (туторіал 9).

06 SSRF: коли ваш сервер ходить туди, куди скаже атакувальник

Будь-яка фіча "завантажити за URL", вебхук або прев'ю посилання робить ваш сервер проксі всередину вашої мережі.

Чому "заборонити 169.254.169.254 рядком" не працює

ssrf.mjs
for (const u of ['http://169.254.169.254/latest/meta-data/', 'http://2852039166/', 'http://0xA9FEA9FE/', 'http://[::ffff:169.254.169.254]/', 'http://127.1:6379/', 'http://localhost.example.com@169.254.169.254/']) {
  const p = new URL(u);

Правильний захист

  1. Allowlist доменів, якщо можливо (вебхуки лише на зареєстровані хости, аватари лише з S3-бакета).
  2. Тільки http:/https:, лише стандартні порти.
  3. Резолвити DNS самостійно і перевіряти IP (приватні, loopback, link-local, CGNAT, IPv6 ULA, IPv4-mapped — бібліотека ipaddr.js), і підключатися саме до перевіреної IP (кастомний lookup в undici Agent або готові request-filtering-agent/ssrf-req-filter) — інакше DNS rebinding.
  4. redirect: 'manual' і перевірка кожного переходу тим самим фільтром; таймаут і ліміт розміру відповіді.
  5. Мережа: egress-проксі або окрема підмережа для "fetch за URL"-воркерів; AWS IMDSv2 (потрібен PUT-токен, hop limit 1) робить метадані недосяжними для простого GET.

07 Через браузер: XSS у SSR, CSRF, CORS, security headers

Бекенд, який рендерить HTML або ставить cookies, відповідає і за те, що браузер зробить з його відповіддю.

XSS у серверному рендерингу

  • Шаблонізатори екранують за замовчуванням — але мають "сирий" вивід: EJS <%- %> (на відміну від <%= %>), Handlebars {{{ }}}, Pug !=, React dangerouslySetInnerHTML. Кожне використання — з санітайзером (DOMPurify) або не використовувати.
  • Класична SSR-пастка — стан у <script>: JSON.stringify не екранує </script>. Рядок "</script><script>alert(1)</script>" у даних закриє ваш тег. Екрануйте < як < (або serialize-javascript).
  • Контекст важливий: екранування для HTML не захищає атрибут href="javascript:..." — URL з вводу перевіряйте на схему.
  • Content-Security-Policy з nonce — другий шар: навіть пропущений інлайн-скрипт не виконається.
ssr-state.js
const safeJson = (data) => JSON.stringify(data)
  .replace(/</g, '\\u003c').replace(/\u2028/g, '\\u2028').replace(/\u2029/g, '\\u2029');

res.send(`<script nonce="${res.locals.nonce}">window.__STATE__ = ${safeJson(state)}</script>`);

CSRF з cookie-сесіями

Браузер автоматично додає cookies до запитів на ваш домен — навіть ініційованих з evil.com (форма з action="https://bank/transfer"). Захист:

  • SameSite=Lax (дефолт у сучасних браузерах для cookies без атрибута) блокує cookies на крос-сайтових POST, але пропускає top-level GET — тому GET ніколи не змінює стан. SameSite=Strict — для особливо чутливих cookies.
  • Перевірка заголовка Origin (або Sec-Fetch-Site) на змінюючих запитах.
  • CSRF-токен (synchronizer або double-submit, напр. csrf-csrf; старий csurf deprecated) — для форм і легасі-браузерів.
  • API з токеном у заголовку Authorization (не в cookie) CSRF не вразливе — браузер сам цей заголовок не додає.

CORS: найпоширеніша мисконфігурація

cors.js
// ❌ "щоб працювало": відображаємо будь-який Origin + дозволяємо cookies
app.use(cors({ origin: true, credentials: true }));
// будь-який сайт може зробити fetch('https://api.you.com/me', { credentials: 'include' })
// і ПРОЧИТАТИ відповідь з даними вашого залогіненого користувача

// ❌ regex без якорів: /example\.com/ пропускає https://example.com.evil.net і https://notexample.com

// ✅ точний allowlist
const allowed = new Set(['https://app.example.com', 'https://admin.example.com']);
app.use(cors({
  origin: (origin, cb) => cb(null, !origin || allowed.has(origin)),  // !origin — серверні клієнти, curl
  credentials: true,
}));

CORS — не захист сервера, а дозвіл браузеру читати відповідь. Запит усе одно доходить до сервера (прості запити — без preflight), тож CORS не замінює ні CSRF-захист, ні авторизацію. Origin: null (sandbox iframe, file://) не додавайте в allowlist.

08 Rate limiting і brute force

Без лімітів будь-який ендпоінт логіну — безкоштовний сервіс перевірки вкрадених паролів, а дорогий ендпоінт — кнопка DoS.

rate-limit.js
import { rateLimit } from 'express-rate-limit';
import { RedisStore } from 'rate-limit-redis';

app.set('trust proxy', 1);   // ОДИН відомий проксі попереду — інакше req.ip = IP балансувальника

const loginLimiter = rateLimit({
  windowMs: 15 * 60_000,
  limit: 10,                                     // 10 спроб за 15 хв
  keyGenerator: (req) => `${req.ip}:${String(req.body?.email).toLowerCase()}`,
  standardHeaders: 'draft-8',
  store: new RedisStore({ sendCommand: (...a) => redis.sendCommand(a) }),  // спільний для всіх інстансів
});
app.post('/auth/login', loginLimiter, loginHandler);
  • In-memory лічильник працює лише в одному процесі. При 4 інстансах ліміт фактично ×4, при рестарті скидається. Для горизонтального масштабування — Redis-store (rate-limit-redis, rate-limiter-flexible) або ліміт на рівні проксі/API gateway.
  • trust proxy: без нього всі клієнти мають IP балансувальника (один ліміт на всіх); з true за відсутності проксі — атакувальник підставляє будь-який X-Forwarded-For і обходить ліміт. Вказуйте точну кількість хопів або підмережі.
  • Brute force vs credential stuffing: ліміт по IP не зупиняє ботнет (тисячі IP по 2 спроби), ліміт по акаунту — зупиняє, але дає DoS чужого акаунта. Комбінуйте: per-IP, per-account з прогресивною затримкою, CAPTCHA після N невдач, 2FA, перевірка паролів за базою зламаних (HIBP k-anonymity).
  • Однакова відповідь і час для "немає користувача" і "невірний пароль" — щоб не дати перебирати email-и (user enumeration).
  • Ліміти потрібні не лише на логін: реєстрація, скидання пароля, відправка SMS/email (гроші!), пошук, генерація звітів, AI-виклики.

09 Паролі, JWT і сесії

Помилки тут не "трохи послаблюють" безпеку — вони дозволяють увійти будь-ким або розшифрувати всю базу паролів за вихідні.

Хешування паролів: повільно — це фіча

Навіть з накладними витратами JS-циклу одне ядро робить сотні тисяч SHA-256 на секунду; GPU — мільярди. Argon2id з параметрами OWASP (19 MiB, 2 проходи) коштує ~40 мс і 19 МБ пам'яті на кожну спробу — пам'ять і робить його дорогим на GPU.

  • Argon2id — сучасний дефолт. У свіжих Node 24.x з'явився вбудований crypto.argon2; на старших версіях — пакет argon2 (нативний, зберігає параметри й сіль у PHC-рядку $argon2id$v=19$m=19456,t=2,p=1$...).
  • bcrypt (cost 10–12) — прийнятно; пам'ятайте ліміт 72 байти пароля. scrypt — вбудований у Node давно.
  • Ніколи: MD5/SHA-*, навіть "з сіллю", навіть 1000 разів — це швидкі хеші. Ніколи — шифрування паролів (його можна розшифрувати).
  • Використовуйте асинхронні версії (argon2, scrypt з колбеком) — синхронні 40–100 мс блокують event loop, і логін стає DoS-вектором.

JWT: де ламається

jwt-none.mjs
import { createHmac, timingSafeEqual } from 'node:crypto';
const b64 = (o) => Buffer.from(JSON.stringify(o)).toString('base64url');
const SECRET = 'a-32-byte-secret-from-a-secrets-manager';

// ❌ "верифікатор", що довіряє алгоритму з заголовка токена
function naiveVerify(token) {
  const [h, p, sig] = token.split('.');
  const header = JSON.parse(Buffer.from(h, 'base64url'));
  if (header.alg === 'none') return JSON.parse(Buffer.from(p, 'base64url'));
  const expected = createHmac('sha256', SECRET).update(`${h}.${p}`).digest('base64url');
  if (sig !== expected) throw new Error('bad signature');
  return JSON.parse(Buffer.from(p, 'base64url'));
}

// ✅ алгоритм фіксує сервер, а не токен; порівняння — за сталий час; exp обов'язковий
function strictVerify(token) {
  const [h, p, sig = ''] = token.split('.');
  const header = JSON.parse(Buffer.from(h, 'base64url'));
  if (header.alg !== 'HS256') throw new Error(`alg ${header.alg} not allowed`);
  const expected = createHmac('sha256', SECRET).update(`${h}.${p}`).digest();
  const given = Buffer.from(sig, 'base64url');
  if (given.length !== expected.length || !timingSafeEqual(given, expected)) throw new Error('bad signature');
  const payload = JSON.parse(Buffer.from(p, 'base64url'));
  if (typeof payload.exp !== 'number' || payload.exp * 1000 < Date.now()) throw new Error('expired or no exp');
  return payload;
}

const forged = `${b64({ alg: 'none', typ: 'JWT' })}.${b64({ sub: '1', role: 'admin' })}.`;
console.log('naive :', naiveVerify(forged));
try { strictVerify(forged); } catch (e) { console.log('strict:', e.message); }
$ node jwt-none.mjs
naive : { sub: '1', role: 'admin' }
strict: alg none not allowed

10 Timing attacks і безпечна випадковість

Два тихі баги: порівняння секретів через === і токени з Math.random().

timingSafeEqual

a === b для рядків зупиняється на першому розбіжному символі. Час відповіді трохи більший, коли співпадає довший префікс, — і з тисячами вимірів атакувальник підбирає секрет (API-ключ, підпис вебхука) посимвольно. crypto.timingSafeEqual порівнює за час, що не залежить від вмісту:

webhook.js
import { createHmac, timingSafeEqual } from 'node:crypto';

export function verifyWebhook(rawBody, signatureHex, secret) {
  const expected = createHmac('sha256', secret).update(rawBody).digest();  // підписуємо СИРІ байти, не re-stringify
  const given = Buffer.from(signatureHex ?? '', 'hex');
  // timingSafeEqual кидає ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH на різній довжині — перевіряємо самі
  return given.length === expected.length && timingSafeEqual(given, expected);
}

Перевірено: timingSafeEqual(Buffer.from('secret-token-1'), Buffer.from('secret-token-2')) → false; буфери різної довжини → помилка ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH. Порівнювати HMAC-дайджести фіксованої довжини — найпростіший спосіб уникнути витоку довжини.

Чим permission model не є. Документація Node прямо називає її "ремнем безпеки" для довіреного коду, а не пісочницею для шкідливого: вона обмежує наслідки помилки (path traversal не прочитає /etc), але не гарантує ізоляцію від цілеспрямованого обходу. Ізоляцію дають контейнер, seccomp, окремий процес/VM. Дозвіл на мережу в різних версіях Node реалізований по-різному — перевіряйте документацію вашої версії.

Помилки і логи

errors.js
// фінальний error handler Express: деталі — в лог, клієнту — мінімум
app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  req.log.error({ err, reqId: req.id }, 'request failed');
  res.status(status).json(status < 500
    ? { error: err.expose ? err.message : 'Bad request' }
    : { error: 'Internal error', reqId: req.id });           // без stack, без SQL, без шляхів
});

// pino: маскування PII і секретів на рівні логера
const logger = pino({ redact: { paths: ['req.headers.authorization', 'req.headers.cookie', '*.password', '*.token', 'user.email'], censor: '[REDACTED]' } });
  • Дефолтний обробник Express показує stack trace, якщо NODE_ENV !== 'production' — забутий NODE_ENV у контейнері = витік шляхів, версій, SQL.
  • Повідомлення драйвера БД (duplicate key value violates unique constraint "users_email_key") розкривають схему і дозволяють user enumeration.
  • PII і токени в логах — проблема GDPR і другий шлях витоку (логи читає більше людей, ніж базу). Не логуйте тіла запитів цілком.
  • Інспектор (--inspect) ніколи не слухає 0.0.0.0 у проді — це віддалене виконання коду.

12 Каверзні питання співбесіди

Питання, де очікують не "використовуємо helmet", а механізм атаки.

БазаЧим exec небезпечніший за execFile?
exec запускає рядок через /bin/sh -c, тож ;, |, $() у вводі виконуються як команди. execFile/spawn передають аргументи масивом прямо в execve. Але лишається argument injection (ввід, що починається з -) — ставте --, валідуйте формат.
ПасткаЯк увійти в Mongo-логін без пароля, якщо там немає SQL?
Передати об'єкт замість рядка: {"password": {"$ne": null}} — фільтр стає "будь-який не-null пароль". Захист — схема з z.string(), sanitizeFilter у Mongoose, явний $eq; і, звісно, пароль порівнюють з хешем у коді, а не фільтром у базі.
ПасткаЧому path.join(ROOT, name) + startsWith(ROOT) — недостатньо?
Два баги: startsWith('/srv/uploads') пропускає /srv/uploads-evil (потрібен ROOT + path.sep), і перевірка до декодування/без resolve пропускає закодовані й абсолютні шляхи. Плюс симлінки — realpath. Найкраще — зберігати файли під згенерованими ID.
БазаПоясніть prototype pollution за 30 секунд.
JSON.parse дає власний ключ "__proto__"; наївний deep merge читає target["__proto__"] — це Object.prototype — і рекурсивно пише туди дані атакувальника. Тепер кожен об'єкт процесу "має" цю властивість: обхід перевірок (user.isAdmin), DoS, RCE через гаджети. Захист: схема, безпечний merge, Map/Object.create(null), --disable-proto, freeze.
ПасткаЧому ReDoS у Node небезпечніший, ніж у Java-сервері з пулом потоків?
У Java зависає один потік з сотень; у Node regex виконується синхронно в єдиному потоці event loop — зупиняються всі запити процесу, health-check падає, оркестратор вбиває под. Кілька запитів по 30 символів кладуть сервіс.
БазаЯк захиститися від SSRF у фічі "завантажити аватар за URL"?
Allowlist доменів, якщо можливо; інакше — лише http/https, резолв DNS і перевірка IP (private, loopback, link-local, mapped IPv6) з підключенням до перевіреної IP (проти DNS rebinding), redirect: 'manual' з повторною перевіркою, таймаут і ліміт розміру, egress-проксі, IMDSv2. Рядкова перевірка хоста не працює: http://2852039166/ — це 169.254.169.254.
ПасткаЩо не так з cors({ origin: true, credentials: true })?
Сервер відображає будь-який Origin в Access-Control-Allow-Origin і дозволяє credentials — отже будь-який сайт може зробити запит з cookies жертви і прочитати відповідь. * з credentials браузер не прийме, тому люди "лагодять" відображенням — і відкривають API всім. Потрібен точний allowlist.
БазаЧому не можна хешувати паролі SHA-256 з сіллю?
SHA-256 швидкий: сотні тисяч на ядро CPU, мільярди на GPU — вкрадена база з сіллю перебирається словником за години. Потрібна навмисно повільна і memory-hard функція: argon2id (OWASP: 19 MiB, t=2), bcrypt, scrypt. Сіль захищає лише від rainbow tables, не від перебору.
ПасткаЩо таке JWT key confusion (RS256 → HS256)?
Сервіс перевіряє RS256 публічним ключем. Якщо бібліотека бере алгоритм з заголовка токена, атакувальник ставить alg: HS256 і підписує токен HMAC-ом, використовуючи публічний ключ як секрет — верифікація "проходить". Захист: явний algorithms: ['RS256'] у verify; сучасні бібліотеки також розрізняють типи ключів.
БазаJWT у localStorage чи в HttpOnly cookie?
HttpOnly cookie: XSS не може вкрасти токен (але може діяти від імені користувача, поки сторінка відкрита); ціна — CSRF-захист (SameSite, Origin-перевірка, токен). localStorage — будь-який XSS або скомпрометований фронтенд-пакет експортує токен назовні, і той працює звідусіль до exp.
ПасткаНавіщо timingSafeEqual, якщо різниця в часі — наносекунди?
Статистика: тисячі вимірів на кожен символ усереднюють шум мережі, особливо з хоста поруч (та сама хмара). Ранній вихід === на першому розбіжному байті дає посимвольний оракул. Плюс нюанс: timingSafeEqual кидає помилку на буферах різної довжини — порівнюйте дайджести фіксованої довжини.
БазаЧим небезпечний npm install у CI і що робити?
Може оновити транзитивні залежності поза лок-файлом і запускає postinstall-скрипти сотень пакетів з доступом до секретів CI. npm ci (строго за лок-файлом), ignore-scripts з allowlist для нативних пакетів, мінімальні права токенів у CI, audit/Socket, provenance, cooldown на свіжі версії.
ПасткаRate limiter стоїть, але брутфорс логіну все одно проходить. Чому?
Варіанти: in-memory store при кількох інстансах (ліміт ×N, скидається при рестарті); trust proxy: true без проксі — атакувальник змінює X-Forwarded-For; або навпаки, без trust proxy всі мають IP балансувальника. Credential stuffing з ботнету обходить per-IP — потрібен ще per-account ліміт.
БазаЧи робить --permission безпечним запуск недовіреного коду?
Ні — це "ремінь безпеки" для власного коду: обмежує наслідки помилок (fs, child_process, workers, addons). Для недовіреного коду потрібна справжня ізоляція: окремий процес у контейнері, seccomp/gVisor, VM, isolated-vm. Модуль vm теж не є механізмом безпеки.

14 Як запам'ятати

Образи атак, які легко згадати під тиском співбесіди.

1
Ін'єкція
Дані потрапили в позицію коду: SQL-текст, структуру фільтра, рядок shell.
Асоціація: у графі "ім'я" бланка хтось дописав "...і переказати мені всі гроші" — а бланк виконали дослівно.
2
NoSQL operator injection
Об'єкт замість рядка вносить у фільтр оператор ($ne, $regex).
Асоціація: на питання "який пароль?" відповісти "будь-який, крім порожнього" — і охоронець погодився.
3
Path traversal
../ у назві файлу виводить за межі дозволеної директорії.
Асоціація: у готелі попросити "номер 305/../../сейф".
4
Prototype pollution
Запис через __proto__ у спільний Object.prototype змінює всі об'єкти процесу.
Асоціація: отруїти міський водогін, а не одну склянку — п'ють усі будинки.
5
ReDoS
Вкладені квантифікатори дають експоненційний backtracking і блокують event loop.
Асоціація: кодовий замок, де після кожної невдачі треба перепробувати всі попередні комбінації.
6
SSRF
Сервер робить запит за URL атакувальника — у внутрішню мережу й до метаданих хмари.
Асоціація: попросити секретаря з перепусткою "занести листа" в серверну.
7
CORS reflect + credentials
Віддзеркалення будь-якого Origin з cookies дозволяє будь-якому сайту читати дані користувача.
Асоціація: вишибала, який пускає кожного, хто назвав будь-яке ім'я.
8
Argon2id / bcrypt
Навмисно повільні (і memory-hard) хеші паролів — дорогі для перебору.
Асоціація: сейф з годинниковим механізмом: власнику 40 мс не шкода, зломщику мільярд спроб — вічність.
9
JWT alg: none
Алгоритм перевірки має задавати сервер, а не сам токен.
Асоціація: перепустка, на якій написано "перевіряти мене не треба".
10
timingSafeEqual
Порівняння секретів за сталий час, без раннього виходу.
Асоціація: касир, що завжди перераховує всю пачку, а не зупиняється на першій фальшивій купюрі — і по обличчю нічого не видно.
