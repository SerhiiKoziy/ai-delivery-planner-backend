01 Карта real-time підходів

"Real-time" — це не одна технологія, а спектр компромісів між простотою, затримкою і вартістю з'єднання.

HTTP створювався як модель запит → відповідь: ініціатор завжди клієнт. Real-time з'являється, коли серверу потрібно щось сказати першим: нове повідомлення в чаті, зміна статусу замовлення, прогрес довгої задачі. Історично для цього придумали п'ять підходів, і всі вони досі живі.

  • Short polling — клієнт питає "є щось нове?" кожні N секунд. Тупо, дорого, але працює всюди і переживає будь-які проксі.
  • Long polling — клієнт питає, а сервер тримає запит відкритим, доки не з'явиться подія (або timeout ~25–30 с), відповідає, і клієнт одразу шле новий запит. Так працювали ранні Facebook-чат і Comet.
  • SSE (Server-Sent Events) — один довгий HTTP-запит, у який сервер дописує події у текстовому форматі text/event-stream. Тільки сервер → клієнт, зате автоматичне перепідключення вбудоване в браузер.
  • WebSocket — HTTP-запит "апгрейдиться" до двонаправленого протоколу поверх того самого TCP-з'єднання. Повний дуплекс, мінімальні накладні витрати на повідомлення.
  • WebTransport — новіший протокол поверх HTTP/3 (QUIC): кілька незалежних потоків + ненадійні datagrams (як UDP) без head-of-line blocking. Підтримка в браузерах є, але серверна екосистема Node поки незріла — на співбесіді достатньо знати, що це і навіщо.

02 Протокол WebSocket зсередини

Знати рукостискання і формат фрейму — це те, що відрізняє "користувався Socket.IO" від "розумію, що відбувається в мережі".

HTTP Upgrade handshake

WebSocket (RFC 6455) починається як звичайний HTTP/1.1 GET. Тому він проходить через ті самі порти 80/443, балансувальники й auth-cookie. Клієнт просить змінити протокол, сервер відповідає 101 Switching Protocols, і з цього моменту по тому самому TCP-сокету йдуть уже не HTTP-повідомлення, а WebSocket-фрейми.

Sec-WebSocket-Key — це не безпека і не автентифікація. Він лише доводить, що сервер справді розуміє WebSocket (а не кешуючий проксі, що випадково віддав 101). Перевіримо формулу на прикладі з RFC:

accept.js
const { createHash } = require('node:crypto');
const GUID = '258EAFA5-E914-47DA-95CA-C5AB0DC85B11';
const key = 'dGhlIHNhbXBsZSBub25jZQ=='; // приклад із RFC 6455
const accept = createHash('sha1').update(key + GUID).digest('base64');
console.log(accept); // s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Накладні витрати — 2–14 байт на повідомлення проти сотень байт HTTP-заголовків у polling. Маскування клієнтських фреймів існує не для шифрування, а проти cache poisoning проміжних проксі: атакуючий скрипт у браузері не може сформувати байти, що виглядають як валідний HTTP-запит для "наївного" проксі.

Мінімальний WebSocket-сервер "руками" — щоб побачити байти

Ніколи не пишіть так у проді (немає фрагментації, довгих фреймів, валідації UTF-8), але цей код запущено і він показує весь механізм: 'upgrade'-подію http.Server, відповідь 101, кодування/декодування фрейму. Клієнт — вбудований глобальний WebSocket (undici), доступний за замовчуванням у Node 22+.

raw-ws.mjs
import http from 'node:http';
import { createHash } from 'node:crypto';

const GUID = '258EAFA5-E914-47DA-95CA-C5AB0DC85B11';

// Кодуємо короткий текстовий фрейм (сервер -> клієнт, без маски)
function textFrame(str) {
  const payload = Buffer.from(str);
  if (payload.length > 125) throw new Error('demo: only short frames');
  return Buffer.concat([Buffer.from([0x81, payload.length]), payload]); // FIN=1, opcode=1
}

// Декодуємо короткий фрейм клієнта (клієнт ЗАВЖДИ маскує payload)
function decodeFrame(buf) {
  const opcode = buf[0] & 0x0f;
  const masked = (buf[1] & 0x80) !== 0;
  const len = buf[1] & 0x7f;           // для демо: тільки довжини до 125
  const mask = buf.subarray(2, 6);
  const data = Buffer.from(buf.subarray(6, 6 + len));
  for (let i = 0; i < data.length; i++) data[i] ^= mask[i % 4];
  return { opcode, masked, text: data.toString() };
}

const server = http.createServer((req, res) => res.end('plain http'));

server.on('upgrade', (req, socket) => {
  console.log('server: upgrade request, version', req.headers['sec-websocket-version']);
  const accept = createHash('sha1').update(req.headers['sec-websocket-key'] + GUID).digest('base64');
  socket.write(
    'HTTP/1.1 101 Switching Protocols\r\n' +
    'Upgrade: websocket\r\nConnection: Upgrade\r\n' +
    `Sec-WebSocket-Accept: ${accept}\r\n\r\n`
  );
  socket.write(textFrame('hello from raw server'));
  socket.on('data', (buf) => {
    const f = decodeFrame(buf);
    if (f.opcode === 0x8) { socket.end(Buffer.from([0x88, 0])); return; } // close
    console.log('server got:', f.text, '| masked:', f.masked);
    socket.write(textFrame('echo: ' + f.text));
  });
});

server.listen(0, () => {
  const { port } = server.address();
  const ws = new WebSocket(`ws://localhost:${port}`); // вбудований клієнт
  ws.onopen = () => console.log('client: open');
  ws.onmessage = (e) => {
    console.log('client got:', e.data);
    if (e.data.startsWith('hello')) ws.send('ping-1');
    else { ws.close(); server.close(); }
  };
  ws.onclose = () => console.log('client: closed');
});

03 Бібліотека ws: heartbeat і backpressure

У Node немає вбудованого WebSocket-сервера — стандарт де-факто це ws, на якому стоять Socket.IO, NestJS-адаптер та інші.

Вбудований у Node WebSocket — тільки клієнт (браузерний API, реалізований в undici). Для сервера майже завжди беруть ws — мінімалістичний, швидкий, з опціональними нативними прискорювачами (bufferutil, utf-8-validate; у свіжих версіях Node їх роль частково перебрали вбудовані механізми). Альтернатива для екстремальних навантажень — uWebSockets.js (C++ ядро, власний HTTP-сервер, не сумісний із http-API).

ws-server.mjs
import http from 'node:http';
import { WebSocketServer } from 'ws';

const server = http.createServer();
// noServer: самі вирішуємо, чи приймати upgrade (auth ДО рукостискання)
const wss = new WebSocketServer({ noServer: true, maxPayload: 64 * 1024 });

server.on('upgrade', async (req, socket, head) => {
  try {
    const user = await authenticate(req);     // cookie / токен з query / subprotocol
    wss.handleUpgrade(req, socket, head, (ws) => {
      ws.user = user;
      wss.emit('connection', ws, req);
    });
  } catch {
    socket.write('HTTP/1.1 401 Unauthorized\r\n\r\n');
    socket.destroy();                          // не тримаємо сокет
  }
});

wss.on('connection', (ws) => {
  ws.isAlive = true;
  ws.on('pong', () => { ws.isAlive = true; });
  ws.on('error', (err) => log.warn({ err }, 'ws error')); // без цього — crash
  ws.on('message', (data, isBinary) => {
    const msg = JSON.parse(data.toString());   // валідуйте схемою!
    handle(ws, msg);
  });
});

// Heartbeat: знаходимо "напівмертві" з'єднання (телефон пішов у тунель)
const interval = setInterval(() => {
  for (const ws of wss.clients) {
    if (!ws.isAlive) { ws.terminate(); continue; } // не відповів на минулий ping
    ws.isAlive = false;
    ws.ping();
  }
}, 30_000);
wss.on('close', () => clearInterval(interval));

server.listen(8080);

Навіщо heartbeat, якщо є TCP?

TCP не повідомляє про розрив, якщо друга сторона просто зникла (вимкнувся Wi-Fi, NAT забув мапінг). Без трафіку сокет може вважатися "відкритим" годинами — це half-open connections, і вони їдять пам'ять та файлові дескриптори. Окремо: балансувальники і проксі (AWS ALB, nginx, Cloudflare) закривають "мовчазні" з'єднання за idle timeout (часто 60 с), тож ping кожні 20–30 с ще й тримає з'єднання живим. Браузер відповідає на ping автоматично, але з JS браузера ping надіслати не можна — тому клієнтський heartbeat роблять прикладним повідомленням {type:'ping'}.

Backpressure: bufferedAmount

ws.send() ніколи не блокує: якщо клієнт повільний (3G, завислий таб), дані накопичуються в буфері процесу. Розсилка 10 000 клієнтам великого апдейту з частотою 10 Гц — і один повільний клієнт може роздути heap на сотні мегабайт. Те саме, що backpressure у стрімах (туторіал 6), але без pipe() — керувати треба вручну:

broadcast.mjs
const HIGH_WATER = 1 * 1024 * 1024; // 1 MB у буфері — клієнт не встигає

function broadcast(wss, payload) {
  const data = JSON.stringify(payload);       // серіалізуємо ОДИН раз
  for (const ws of wss.clients) {
    if (ws.readyState !== ws.OPEN) continue;
    if (ws.bufferedAmount > HIGH_WATER) {
      // стратегії: пропустити апдейт (для "останнього стану"), агрегувати, або відключити
      metrics.slowClientDrops.inc();
      continue;
    }
    ws.send(data);
  }
}
⚠️
Пастки ws у проді: (1) без ws.on('error') помилка сокета стане uncaught exception; (2) maxPayload за замовчуванням великий (100 MiB) — зменшіть, інакше один клієнт може надіслати гігантське повідомлення; (3) permessage-deflate на сервері вимкнено за замовчуванням не просто так — zlib-контекст на кожне з'єднання з'їдає пам'ять і CPU, вмикайте свідомо; (4) перевіряйте Origin у upgrade — браузер шле cookie на WS-запити з будь-якого сайту (Cross-Site WebSocket Hijacking).

Автентифікація на connect

  • Cookie (session/JWT у httpOnly cookie) — найпростіше для браузера, але обов'язкова перевірка Origin.
  • Токен у query ?token=... — працює, але токен потрапляє в access-логи; краще короткоживучий одноразовий "ticket", отриманий звичайним HTTP-запитом.
  • Перше повідомлення {type:'auth', token} — гнучко, але сокет існує до перевірки; ставте timeout.
  • Браузерний WebSocket не дозволяє власні заголовки (на кшталт Authorization) — частий сюрприз. Хак — передати токен у Sec-WebSocket-Protocol.
  • Токен протухає, а з'єднання живе годинами — плануйте re-auth або закриття з кодом 4001.

04 Socket.IO: що це насправді

Найпопулярніша real-time бібліотека Node — і найчастіше неправильно описана на співбесідах як "обгортка над WebSocket".

Socket.IO — це власний протокол поверх транспорту Engine.IO, який використовує WebSocket або HTTP long-polling (а в новіших версіях і WebTransport). Звичайний new WebSocket('ws://...') до Socket.IO-сервера не підключиться, і навпаки — клієнт Socket.IO не говорить із "голим" ws-сервером. Пакети мають свій формат (42["chat",{"text":"hi"}] — 4 = message Engine.IO, 2 = EVENT Socket.IO).

Що ви отримуєте за цю ціну:

  • Автоматичний reconnect з exponential backoff і буферизацією emit-ів під час обриву.
  • Fallback на long-polling, якщо WebSocket ріжуть корпоративні проксі (за замовчуванням клієнт стартує з polling і апгрейдиться — тому без sticky sessions на кількох інстансах буде хаос).
  • Події з іменами замість сирих рядків, acknowledgements (callback/Promise-відповідь на emit).
  • Rooms і namespaces — групування з'єднань.
  • Адаптери (Redis, Redis Streams, Postgres, cluster) для розсилки між інстансами.
  • Connection state recovery (v4.6+) — після короткого обриву клієнт отримує пропущені події і той самий socket.id.
socketio-server.mjs
import { createServer } from 'node:http';
import { Server } from 'socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

const httpServer = createServer();
const io = new Server(httpServer, {
  cors: { origin: 'https://app.example.com', credentials: true },
  connectionStateRecovery: { maxDisconnectionDuration: 2 * 60_000 },
});

// Розсилка між інстансами через Redis pub/sub
const pub = createClient({ url: process.env.REDIS_URL });
const sub = pub.duplicate();
await Promise.all([pub.connect(), sub.connect()]);
io.adapter(createAdapter(pub, sub));

// Middleware: auth ОДИН раз на з'єднання
io.use(async (socket, next) => {
  try {
    socket.data.user = await verifyToken(socket.handshake.auth.token);
    next();
  } catch {
    next(new Error('unauthorized'));          // клієнт отримає 'connect_error'
  }
});

const orders = io.of('/orders');               // namespace = окремий "канал" з власними middleware
orders.on('connection', (socket) => {
  socket.join(`org:${socket.data.user.orgId}`); // room = довільна група сокетів

  // acknowledgement: другий аргумент — callback-відповідь
  socket.on('order:update', async (payload, ack) => {
    const order = await updateOrder(payload);
    // всім у кімнаті, крім відправника
    socket.to(`org:${order.orgId}`).emit('order:updated', order);
    ack({ ok: true, version: order.version });
  });
});

httpServer.listen(3000);
client.js
import { io } from 'socket.io-client';
const socket = io('https://api.example.com/orders', { auth: { token } });

// emit з таймаутом і Promise-ack

05 Server-Sent Events

Найнедооціненіша real-time технологія: ~30 рядків на чистому node:http, з reconnect і відновленням пропущених подій "з коробки".

Формат text/event-stream — текстові блоки, розділені порожнім рядком. Поля:

  • data: — тіло (може бути кілька рядків data: — вони склеюються через \n);
  • event: — ім'я події (у браузері es.addEventListener('order', ...), без нього — onmessage);
  • id: — ідентифікатор; браузер запам'ятовує останній і при перепідключенні шле заголовок Last-Event-ID;
  • retry: — затримка reconnect у мс;
  • рядок, що починається з : — коментар (зручно для heartbeat, щоб проксі не закрив з'єднання).
sse.mjs
import http from 'node:http';

const history = [];          // у проді — Redis Stream / БД
let nextId = 1;
const clients = new Set();

function publish(event, data) {
  const msg = { id: nextId++, event, data: JSON.stringify(data) };
  history.push(msg);
  for (const res of clients) write(res, msg);
}
function write(res, { id, event, data }) {
  res.write(`id: ${id}\nevent: ${event}\ndata: ${data}\n\n`);
}

const server = http.createServer((req, res) => {
  if (req.url !== '/events') return res.writeHead(404).end();
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
    'X-Accel-Buffering': 'no',          // вимкнути буферизацію в nginx
  });
  res.write('retry: 3000\n\n');         // через скільки мс браузер перепідключиться
  // Відновлення: браузер сам надсилає Last-Event-ID після обриву
  const lastId = Number(req.headers['last-event-id'] ?? 0);
  for (const msg of history) if (msg.id > lastId) write(res, msg);

  clients.add(res);
  const hb = setInterval(() => res.write(': ping\n\n'), 15000); // коментар-heartbeat
  req.on('close', () => { clearInterval(hb); clients.delete(res); });
});

server.listen(0, async () => {
  const url = `http://localhost:${server.address().port}/events`;
  publish('order', { id: 1, status: 'created' });
  publish('order', { id: 1, status: 'paid' });

  // Клієнт «перепідключається» після події 1 — як це зробив би EventSource
  const res = await fetch(url, { headers: { 'Last-Event-ID': '1' } });
  setTimeout(() => publish('order', { id: 1, status: 'shipped' }), 50);

  const decoder = new TextDecoderStream();
  let buf = '', got = 0;
  for await (const chunk of res.body.pipeThrough(decoder)) {
    buf += chunk;
    let i;
    while ((i = buf.indexOf('\n\n')) !== -1) {
      const block = buf.slice(0, i); buf = buf.slice(i + 2);
      if (block.startsWith('retry')) { console.log('<-', block); continue; }
      console.log('<-', block.replaceAll('\n', ' | '));
      if (++got === 2) { server.closeAllConnections(); server.close(); process.exit(0); }
    }
  }
});

<- id: 3 | event: order | data: {"id":1,"status":"shipped"}

Нюанси SSE, які питають

  • Ліміт 6 з'єднань на домен у HTTP/1.1 — кожна вкладка з EventSource з'їдає одне; 7-ма вкладка "зависне". HTTP/2 мультиплексує потоки і знімає проблему (у Node це node:http2 або проксі з HTTP/2 перед Node).
  • EventSource не вміє заголовки (немає Authorization) — або cookie, або fetch() + ручний парсинг стріму (як у демо), або бібліотеки на кшталт @microsoft/fetch-event-source.
  • Буферизація: nginx (proxy_buffering off / X-Accel-Buffering: no), compression-middleware (gzip буферизує дрібні шматки!) і деякі CDN "склеюють" події — класична причина "SSE працює локально, але не на проді".
  • Тільки текст UTF-8 — бінарне кодуйте base64 або давайте посилання.
  • Відновлення вимагає, щоб сервер мав історію за id — Redis Streams (XRANGE від last id) підходять ідеально.
  • Обов'язково req.on('close') для прибирання — інакше витік пам'яті на кожен відключений клієнт (див. туторіал 15).

06 Масштабування real-time

Stateless REST масштабується додаванням інстансів; WebSocket — ні: з'єднання "прибите" до конкретного процесу.

Проблема №1: подія виникла не там, де клієнт

Користувач A підключений до інстансу #1, B — до #3. A пише в кімнату — інстанс #1 знає тільки про свої сокети. Рішення — pub/sub fan-out: кожен інстанс підписаний на канали шини (Redis Pub/Sub, NATS, Kafka), а публікація йде в шину, а не напряму в сокети.

Проблема №2: sticky sessions

Чистому WebSocket sticky sessions потрібні лише на момент рукостискання (далі це одне TCP-з'єднання). А от Socket.IO з long-polling робить багато HTTP-запитів з одним session id — якщо вони потраплять на різні інстанси, отримаєте 400 Session ID unknown. Рішення: sticky за cookie/IP на балансувальнику, або transports: ['websocket'] на клієнті (без polling). У Node cluster — пакет @socket.io/sticky.

Проблема №3: пам'ять і ліміти з'єднань

Пам'ять на з'єднанняядро (TCP-буфери) + Node-об'єкти + ваші дані на сокеті; порядок — від кількох до десятків KB, з deflate — значно більшене тримати великі об'єкти на сокеті, вимкнути deflate, вимірювати heap на 10k з'єднань

Проблема №4: деплой і "reconnect storm"

Rolling deploy вбиває інстанс із 50 000 з'єднань — і всі 50 000 клієнтів одночасно перепідключаються, разом ідучи по auth, БД і "догнати пропущене". Захист: jitter у клієнтському backoff, graceful shutdown із поступовим закриттям (кодом 1001/1012) порціями, rate limit на connect, кеш для initial state.

💡
Pub/Sub vs Streams. Redis Pub/Sub не зберігає повідомлення: якщо інстанс перезапускався — пропустив. Для "не можна втратити" — Redis Streams (consumer groups, XREAD від id), Kafka або @socket.io/redis-streams-adapter. Для "останній стан важливіший за історію" (курсори, ціни) Pub/Sub достатньо.

07 Навіщо черги задач

Event loop не любить довгу роботу, користувач не любить чекати, а зовнішні API не люблять, коли їх викликають 1000 разів на секунду.

Job queue розв'язує одразу кілька задач:

  • Offload — HTTP-запит відповідає 202 Accepted за 20 мс, а генерація PDF / відправка email / ресайз зображення / виклик LLM відбувається у воркері. API лишається швидким і не падає разом із повільною залежністю.
  • Надійність — retries з backoff, переживає рестарт процесу (job у Redis/БД, а не в пам'яті).
  • Відкладене і періодичне виконання — "надіслати нагадування через 24 год", "щогодини синхронізувати".
  • Контроль навантаження — concurrency і rate limiting: не більше 10 запитів/с до платіжного провайдера.
  • Окреме масштабування — API і воркери деплояться і скейляться незалежно (воркерів можна скейлити за довжиною черги).
🚫
Антипатерн "fire-and-forget у процесі": sendEmail(user).catch(console.error) без await у хендлері. Працює, доки процес не перезапуститься під час відправки (деплой, OOM) — задача зникає безслідно, без retry і без сліду в логах. Для всього, що має значення, — черга.

08 BullMQ: Queue, Worker, стани

BullMQ — стандарт для черг у Node поверх Redis: TypeScript, атомарні Lua-скрипти, flows, rate limiting, job schedulers.

BullMQ — наступник Bull (Bull у режимі підтримки). Усі переходи станів робляться Lua-скриптами в Redis — тобто атомарно, без гонок між воркерами. Три основні класи: Queue (додати), Worker (обробити), QueueEvents (слухати глобальні події через Redis Streams).

queue.ts
import { Queue } from 'bullmq';
import IORedis from 'ioredis';

// BullMQ вимагає maxRetriesPerRequest: null для з'єднань воркера (блокуючі команди)
export const connection = new IORedis(process.env.REDIS_URL!, { maxRetriesPerRequest: null });

export const emailQueue = new Queue('email', {
  connection,
  defaultJobOptions: {
    attempts: 5,
    backoff: { type: 'exponential', delay: 1000 },   // 1s, 2s, 4s, 8s...
    removeOnComplete: { age: 3600, count: 1000 },     // не роздувати Redis
    removeOnFail: { age: 7 * 24 * 3600 },             // failed тримаємо тиждень для розбору
  },
});

// у HTTP-хендлері
await emailQueue.add('welcome', { userId: 42 }, {
  jobId: `welcome:42`,      // дедуплікація: job з тим самим id не додасться вдруге
  delay: 10_000,            // через 10 секунд
  priority: 1,              // 1 — найвищий; без priority job у звичайній FIFO
});
worker.ts
import { Worker, UnrecoverableError } from 'bullmq';
import { connection } from './queue';

const worker = new Worker('email', async (job) => {
  const user = await db.user.find(job.data.userId);
  if (!user) throw new UnrecoverableError('user deleted'); // без ретраїв — одразу failed
  await job.updateProgress(50);
  const { messageId } = await mailer.send(user.email, 'Welcome!');
  return { messageId };                                    // збережеться як returnvalue
}, {
  connection,
  concurrency: 20,                          // 20 job-ів паралельно в ОДНОМУ процесі (I/O-bound)
  limiter: { max: 100, duration: 1000 },    // не більше 100 job/с на всю чергу (усі воркери)
});

worker.on('completed', (job, result) => log.info({ id: job.id, result }, 'sent'));
worker.on('failed', (job, err) => log.error({ id: job?.id, attempt: job?.attemptsMade, err }, 'failed'));
worker.on('error', (err) => log.error({ err }, 'worker error')); // обов'язково

// graceful shutdown: дочекатися поточних job-ів
process.on('SIGTERM', async () => { await worker.close(); process.exit(0); });

Додаткові стани: waiting-children (батьківська job у flow чекає на дочірні — FlowProducer), paused (черга на паузі). Перевірити стан: await job.getState().

Concurrency: що реально паралельне

concurrency: 20 — це 20 async-обробників у одному event loop. Для I/O-bound (HTTP, БД, email) — чудово. Для CPU-bound (обробка зображень, PDF, crypto) — ні: обробники блокуватимуть один одного й навіть продовження lock-а (→ stalled). Варіанти: sandboxed processors (передати шлях до файлу процесора — BullMQ запустить його в окремому child process або worker thread через useWorkerThreads), або кілька процесів воркерів з concurrency: 1. Детальніше про CPU-роботу — туторіал 8.

09 BullMQ: retries, розклад, ліміти, stalled

Найбільше продакшн-інцидентів із чергами — не через "черга не працює", а через неправильно зрозумілу семантику ретраїв, lock-ів і розкладу.

Retries і backoff

  • attempts: 5 — загальна кількість спроб (не "ретраїв після першої").
  • backoff: { type: 'fixed' | 'exponential', delay }; exponential = delay * 2^(attemptsMade-1); можна додати jitter або власну стратегію через settings.backoffStrategy у Worker.
  • UnrecoverableError — помилка, яку ретраїти безглуздо (валідація, 4xx від API) — job одразу у failed.
  • Ретраї означають, що обробник виконається більше одного разу → він має бути ідемпотентним (розділ 12).

Delayed, повторювані задачі, Job Schedulers

schedulers.ts
// Одноразова відкладена
await queue.add('reminder', { orderId }, { delay: 24 * 3600_000 });

// Повторювана: Job Scheduler (новий API BullMQ v5, замінює старий repeat-опційний)
await queue.upsertJobScheduler(
  'hourly-sync',                                   // id планувальника — upsert ідемпотентний
  { pattern: '0 * * * *', tz: 'Europe/Kyiv' },     // cron, або { every: 60_000 }
  { name: 'sync', data: { source: 'crm' }, opts: { attempts: 3 } },
);
await queue.removeJobScheduler('hourly-sync');

Ключовий момент: розклад зберігається у Redis, а наступна job створюється атомарно — тому 10 інстансів воркерів не запустять одну й ту саму годинну задачу 10 разів (на відміну від node-cron, розділ 11). upsert безпечно викликати на старті кожного інстансу.

Пріоритети

priority від 1 (найвищий) до 2 097 152. Job з пріоритетом живе в окремому стані prioritized (сортований набір), що трохи дорожче за звичайну FIFO. Альтернатива пріоритетам — окремі черги ("email-transactional" і "email-marketing") з окремими воркерами: простіше пояснити і моніторити, і масова розсилка гарантовано не заблокує листи для відновлення пароля.

Rate limiter

limiter: { max, duration } у Worker діє глобально на чергу (через Redis), а не на процес. Якщо зовнішній API повернув 429 з Retry-After — викличте await worker.rateLimit(ms) і киньте Worker.RateLimitError(): job повернеться у wait без витрати спроби.

Stalled jobs — найпідступніша частина

Коли воркер бере job, він отримує lock у Redis на lockDuration (30 с за замовчуванням) і періодично його продовжує. Якщо процес упав (OOM, SIGKILL) — lock протухає, і перевірка stalled (stalledInterval) повертає job у wait. Після maxStalledCount (1 за замовчуванням) повторних "застрягань" — job у failed.

⚠️
Класичний інцидент: CPU-bound обробник (синхронний парсинг 200 MB JSON) блокує event loop на 40 с → воркер не встигає продовжити lock → job вважається stalled → інший воркер бере ту саму job → вона виконується двічі паралельно. Лікування: не блокувати event loop (sandboxed processor / worker thread), збільшити lockDuration для довгих задач, ідемпотентність.

Події та спостережуваність

events.ts
import { QueueEvents } from 'bullmq';
const events = new QueueEvents('email', { connection });   // слухає Redis Stream подій черги
events.on('failed', ({ jobId, failedReason }) => alert(jobId, failedReason));
events.on('progress', ({ jobId, data }) => sse.publish(jobId, data)); // прогрес у UI через SSE

// дочекатися результату конкретної job (обережно в HTTP-хендлерах!)
const job = await queue.add('render', { id });
const result = await job.waitUntilFinished(events, 30_000);

// метрики для алертів
const counts = await queue.getJobCounts('wait', 'active', 'delayed', 'failed');

Що моніторити: довжину wait (росте → воркерів мало), вік найстаршої job у wait (latency черги), кількість failed, частоту stalled, пам'ять Redis. UI: Bull Board або Taskforce.sh. І пам'ятайте: Redis для BullMQ має бути з maxmemory-policy noeviction — інакше Redis може тихо "видалити" ваші job-и.

Ідемпотентні job-и через jobId

Якщо jobId вже існує в черзі (у будь-якому стані, поки job не видалена), add() не створить дубль. Це захищає від подвійного кліку і повторного вебхука. Але після removeOnComplete той самий id можна додати знову — для довгострокової дедуплікації потрібна власна таблиця/ключ. Є також опція deduplication: { id, ttl } для дедуплікації в межах часового вікна.

11 Cron і дублювання між інстансами

"Ми додали node-cron, а потім масштабувались до 4 подів — і клієнти отримали 4 однакові листи".

node-cron (або croner, @nestjs/schedule) — це просто таймер усередині процесу. Він не знає про інші процеси. Запустили 4 репліки / cluster з 8 воркерами / PM2 у cluster-режимі — отримали 4 (або 8) запусків щоночі.

Коли що: у проєкті вже є черга — її scheduler; задача-"скрипт" (міграція звітів, бекап) — K8s CronJob / EventBridge; node-cron — тільки для гарантовано одного інстансу або локальних, ідемпотентних дій (почистити кеш у пам'яті цього процесу).

Lock не дає гарантії "рівно один раз": GC-пауза або мережа можуть зробити так, що lock протух, поки власник ще працює. Тому задачі з побічними ефектами все одно мають бути ідемпотентними (або використовувати fencing token).

12 Патерни надійності: idempotency, outbox, DLQ

Розподілені системи не дають "exactly once" безкоштовно — його збирають з at-least-once доставки та ідемпотентних обробників.

Гарантії доставки

ГарантіяЯк досягаєтьсяРизик
At-most-onceack до обробки (або без ack)втрата повідомлень
At-least-onceack після обробки; при збої — повторна доставкадублікати — стандарт для BullMQ, SQS, RabbitMQ
"Exactly-once"at-least-once + ідемпотентний обробник (або транзакції в межах однієї системи, як у Kafka)складність; "ефективно один раз" лише для ефектів, які ви контролюєте

Idempotency key

Обробник фіксує "я вже обробив ключ X" атомарно разом із побічним ефектом: в одній транзакції БД (UNIQUE-індекс на processed_messages.key), або передає ключ далі зовнішньому API (Stripe приймає заголовок Idempotency-Key). Демо механіки (запущено):

idempotent.mjs
// At-least-once: брокер може доставити повідомлення ще раз,
// якщо воркер упав ПІСЛЯ побічного ефекту, але ДО ack.
const processed = new Set();     // у проді: UNIQUE-індекс у БД або Redis SET NX
let charges = 0;
let crashOnce = true;

async function handle(msg) {
  if (processed.has(msg.idempotencyKey)) {
    console.log(`skip duplicate ${msg.idempotencyKey}`);
    return;
  }
  charges++;                                   // побічний ефект (списання грошей)
  processed.add(msg.idempotencyKey);
  if (crashOnce) { crashOnce = false; throw new Error('worker died before ack'); }
  console.log(`charged ${msg.idempotencyKey}`);
}

async function deliver(msg, attempt = 1) {
  try {
    await handle(msg);
    console.log(`ack after attempt ${attempt}`);
  } catch (e) {
    console.log(`attempt ${attempt} failed: ${e.message} -> redeliver`);
    await deliver(msg, attempt + 1);
  }
}

// Експоненційний backoff із «full jitter»
const backoff = (attempt, base = 1000, cap = 30000) =>
  Math.round(Math.random() * Math.min(cap, base * 2 ** (attempt - 1)));

await deliver({ idempotencyKey: 'order-42:charge' });
console.log('total charges:', charges);
console.log('max delay for attempts 1..6:',
  [1, 2, 3, 4, 5, 6].map((a) => Math.min(30000, 1000 * 2 ** (a - 1))));
console.log('jittered sample in range:', backoff(3) <= 4000);
output
attempt 1 failed: worker died before ack -> redeliver
skip duplicate order-42:charge
ack after attempt 2
total charges: 1
max delay for attempts 1..6: [ 1000, 2000, 4000, 8000, 16000, 30000 ]
jittered sample in range: true

У демо позначка і "списання" — дві окремі дії; у реальності між ними теж можна впасти. Тому або одна транзакція БД (ефект + запис ключа), або ключ іде в сам зовнішній виклик (Idempotency-Key), щоб дедуплікацію робив провайдер. Jitter потрібен, щоб тисячі клієнтів, які впали одночасно, не ретраїли синхронно ("thundering herd").

Transactional outbox

Проблема dual write: await db.insert(order); await queue.add('order.created'). Якщо процес упав між рядками — замовлення є, події немає. Якщо поміняти місцями — подія є, замовлення ні (транзакція відкотилась). Розподіленої транзакції між Postgres і Redis немає.

Dead letter queue (DLQ)

Повідомлення, яке не вдалося обробити після N спроб ("poison message"), не повинно ні вічно ретраїтись (блокуючи чергу і спалюючи гроші), ні тихо зникати. Його відкладають у DLQ для розбору людиною або автоматичного re-drive після фіксу.

  • SQS: redrive policy з maxReceiveCount → DLQ вбудовано.
  • RabbitMQ: dead-letter exchange (x-dead-letter-exchange) при nack/TTL/переповненні.
  • BullMQ: окремої DLQ немає — стан failed і є "DLQ"; часто роблять окрему чергу email-dlq у обробнику події failed, коли job.attemptsMade >= job.opts.attempts, плюс алерт і інструмент "retry all".
  • Kafka: retry-топіки з затримкою + DLT (dead letter topic).
🧠 Запам'ятай: at-least-once + idempotency key = ефективно один раз; outbox прибирає dual write; DLQ — щоб помилки не губились і не блокували чергу.

13 Каверзні питання співбесіди

Що перевіряють: розуміння протоколів, stateful-масштабування і гарантій доставки — а не знання API бібліотек.

БазаЧим WebSocket відрізняється від SSE і коли обрати SSE?
WebSocket — дуплекс, власні фрейми після HTTP Upgrade, текст і бінарні дані, reconnect вручну. SSE — один HTTP-запит, тільки сервер → клієнт, лише текст, але вбудований reconnect з Last-Event-ID, працює з HTTP/2, проксі, звичайною auth. SSE — для нотифікацій, дашбордів, стрімінгу LLM; WebSocket — коли клієнт часто шле дані (чат, ігри, колаборація).
ПасткаSocket.IO — це WebSocket?
Ні. Це власний протокол поверх Engine.IO, який може використовувати WebSocket або long-polling. Чистий WebSocket-клієнт не підключиться до Socket.IO-сервера. Через polling-fallback на кількох інстансах потрібні sticky sessions.
БазаЩо таке Sec-WebSocket-Key і чи захищає він від чогось?
Випадкове base64-значення; сервер повертає base64(sha1(key + GUID)). Це доказ, що сервер розуміє WebSocket (захист від випадкових відповідей кешуючих проксі), а не автентифікація чи шифрування. Безпека — це wss:// (TLS), перевірка Origin і ваш auth.
ПасткаНавіщо ping/pong, якщо TCP і так знає про розрив?
TCP не знає, якщо пір зник мовчки (вимкнений Wi-Fi, NAT-таймаут) — з'являються half-open з'єднання, що жеруть пам'ять і fd. Ping/pong виявляє їх (не відповів — terminate()) і заразом не дає LB/проксі закрити idle-з'єднання.
Пасткаws.send() повернувся одразу — повідомлення доставлене?
Ні, лише покладене в буфер. Для повільних клієнтів буфер росте (bufferedAmount) — це backpressure, і без контролю один повільний клієнт роздуває heap. Доставку на прикладному рівні підтверджують лише ack-повідомлення.
БазаЯк розіслати повідомлення в кімнату, якщо учасники на різних інстансах?
Pub/sub-шина: інстанс публікує в Redis Pub/Sub (NATS, Kafka), усі інстанси підписані й шлють своїм локальним сокетам. У Socket.IO — @socket.io/redis-adapter. Якщо втрата неприйнятна — Redis Streams або Kafka, бо Pub/Sub не зберігає повідомлення.
ПасткаЯк передати JWT при підключенні браузерного WebSocket?
Браузерний WebSocket не підтримує власні заголовки. Варіанти: httpOnly cookie (+ перевірка Origin проти CSWSH), короткоживучий одноразовий ticket у query, токен у Sec-WebSocket-Protocol, або перше повідомлення auth з timeout. І план на протухання токена при довгому з'єднанні.
БазаНавіщо черга, якщо можна просто не робити await?
Fire-and-forget у процесі губить задачу при рестарті/OOM, не має retry, backoff, rate limit, розкладу і видимості. Черга зберігає job поза процесом, дає ретраї та дозволяє скейлити воркери окремо від API.
ПасткаЧому BullMQ-job виконалась двічі, хоча помилок не було?
Найчастіше — stalled: event loop воркера був заблокований довше за lockDuration, lock не продовжився, job повернули в wait і її взяв інший воркер. Або ретрай після помилки, що сталась ПІСЛЯ побічного ефекту. Лікування: не блокувати loop (sandboxed processor), більший lockDuration, ідемпотентні обробники.
ПасткаУ нас 4 поди з node-cron — що може піти не так?
Задача запуститься 4 рази. Плюс вона помре разом із подом посеред виконання, без retry та історії. Рішення: scheduler черги (BullMQ upsertJobScheduler зберігає розклад у Redis і створює одну job), зовнішній планувальник або distributed lock — і в будь-якому разі ідемпотентність.
БазаЩо таке outbox pattern і яку проблему він розв'язує?
Dual write: не можна атомарно записати в БД і в брокер. Outbox: подія пишеться в таблицю outbox в тій самій транзакції, що й дані; окремий relay (polling з SKIP LOCKED або CDC) публікує її. Доставка at-least-once → консюмери ідемпотентні. pg-boss дає це "безкоштовно", бо черга живе в тій самій Postgres.
ПасткаKafka — це просто швидша черга задач?
Ні, це розподілений лог: повідомлення не видаляються після читання, кожна consumer group читає все, порядок — у межах партиції, offset рухається вперед. Per-message retry, delay і пріоритети — не вбудовані. Для фонових job-ів сервісу BullMQ/SQS простіші.
БазаЯк не "покласти" бекенд при rolling deploy WebSocket-сервера?
Graceful shutdown з поступовим закриттям з'єднань (кодом 1001/1012) порціями, клієнтський reconnect з exponential backoff + jitter, rate limit на connect, дешевий initial state (кеш), connection state recovery, щоб не перезавантажувати все.

15 Як запам'ятати

Асоціації, що чіпляються за пам'ять.

1
Long polling
Запит, який сервер тримає відкритим до появи події.
Асоціація: офіціант стоїть біля столика, доки ви не оберете страву, — і одразу приходить знову.
2
SSE
Односторонній текстовий потік подій по HTTP з авто-reconnect.
Асоціація: радіо — слухаєте, перемкнулись, а диктор каже "ви пропустили ось це" (Last-Event-ID).
3
HTTP Upgrade / 101
HTTP-запит, після якого той самий TCP говорить іншим протоколом.
Асоціація: зайшли в магазин через звичайні двері, а там — телепорт.
4
Heartbeat (ping/pong)
Періодична перевірка, що пір живий; немає pong — terminate.
Асоціація: рація: "Прийом!" — тиша — значить, зв'язку немає, кладемо трубку.
5
bufferedAmount
Скільки байт чекає на відправку повільному клієнту.
Асоціація: пошта, що накопичується під дверима того, хто поїхав у відпустку.
6
Pub/Sub fan-out
Інстанси обмінюються подіями через шину, щоб дістатись чужих сокетів.
Асоціація: гучномовець на вокзалі: кожна платформа чує оголошення, але свої пасажири — у кожної свої.
7
Stalled job
Job, чий lock протух, бо воркер помер або заблокував event loop.
Асоціація: таксист заснув з увімкненим "зайнято" — диспетчер віддає замовлення іншому, а потім приїжджають двоє.
8
Idempotency key
Ключ, за яким повторна обробка того самого повідомлення стає no-op.
Асоціація: штамп "ОПЛАЧЕНО" на рахунку — вдруге касир вже не візьме гроші.
9
Outbox
Подія пишеться в таблицю в тій самій транзакції, а публікується окремо.
Асоціація: лист кладете в поштову скриньку в офісі разом із підписанням договору — кур'єр забере потім.
10
DLQ
Окрема черга для повідомлень, що не обробились після N спроб.
Асоціація: полиця "незатребувані посилки" — не викидаємо, але й не тримаємо на конвеєрі.
