01 Еволюція: callback → Promise → async/await

Три покоління одного й того ж ідеалу: "зроби I/O, а коли буде готово — продовж". Кожне виправляло біль попереднього.

Error-first callback — конвенція, на якій виріс Node

Ранній Node (2009+) мав одне правило для всього core API: останній аргумент — callback, а перший аргумент callback — помилка (або null). Чому помилка саме першою? Щоб її неможливо було "не помітити" — вона стоїть на найвиднішому місці, і linter/рев'юер одразу бачить, якщо err ігнорується.

error-first.js
const fs = require('node:fs');

fs.readFile('config.json', 'utf8', (err, text) => {
  if (err) {
    // ENOENT, EACCES, ... — помилку ОБОВ'ЯЗКОВО обробити або передати вище
    return console.error('cannot read config:', err.code);
  }
  const cfg = JSON.parse(text);   // ⚠️ якщо JSON битий — throw тут НІХТО не зловить
  console.log(cfg.port);
});

Головні проблеми callback-стилю — не лише "піраміда":

  • Callback hell / pyramid of doom — кожен наступний крок вкладається на рівень глибше, обробка помилок дублюється на кожному рівні.
  • Inversion of control — ви віддаєте свою функцію чужому коду і довіряєте, що він викличе її рівно один раз, асинхронно, з правильними аргументами. Ніхто цього не гарантує (див. розділ 12).
  • try/catch не працює через межу асинхронності: виняток, кинутий усередині callback, вилітає вже з іншого стеку — як uncaughtException.
  • Композиція важка: "запусти 3 запити паралельно і дочекайся всіх" — це ручний лічильник.
callback-hell.js
getUser(id, (err, user) => {
  if (err) return done(err);
  getOrders(user.id, (err, orders) => {
    if (err) return done(err);
    getInvoice(orders[0].id, (err, invoice) => {
      if (err) return done(err);
      sendEmail(user.email, invoice, (err) => {
        if (err) return done(err);
        done(null, 'sent');            // 4 рівні, 4 однакові if (err)
      });
    });
  });
});

Promise → async/await

Promise (у Node стабільно з v4, ES2015) повертає контроль: функція не приймає ваш callback, а повертає об'єкт-обіцянку, на який ви підписуєтесь самі. Гарантії вбудовані в специфікацію: settle — рівно один раз, обробники — завжди асинхронно (мікрозадача), помилка тече ланцюжком до найближчого .catch. async/await (Node 7.6+/8) — синтаксичний цукор над Promise + генераторами: код виглядає синхронним, і звичайний try/catch знову працює.

same-flow-async.js
async function sendInvoice(id) {
  const user = await getUser(id);
  const orders = await getOrders(user.id);
  const invoice = await getInvoice(orders[0].id);
  await sendEmail(user.email, invoice);
  return 'sent';
}   // одна точка обробки помилок — у того, хто викликає (try/catch або .catch)
🧠 Запам'ятай: async/await — не нова модель виконання, а синтаксис над Promise; Promise — не "швидший callback", а контракт (один settle, завжди async, помилка тече ланцюжком).

02 Мости: util.promisify, callbackify і */promises API

У реальному коді все ще трапляються callback-бібліотеки — треба вміти акуратно "перекласти" їх у Promise і назад.

util.promisify і util.callbackify

promisify(fn) повертає функцію, яка додає свій callback останнім аргументом і перетворює (err, value) на reject/resolve. Працює лише для функцій, що дотримуються error-first конвенції. Якщо функція має нестандартну сигнатуру (наприклад, кілька результатів), автор може задати власну версію через символ util.promisify.custom — так зроблено для setTimeout, fs.exists, child_process.exec (повертає { stdout, stderr }).

promisify.js
const util = require('node:util');

function legacy(a, b, cb) {
  setImmediate(() => (a < 0 ? cb(new Error('neg')) : cb(null, a + b)));
}
const legacyAsync = util.promisify(legacy);
legacyAsync(1, 2).then((v) => console.log('promisified:', v));     // promisified: 3
legacyAsync(-1, 2).catch((e) => console.log('err:', e.message));    // err: neg

// у зворотний бік — коли старий API чекає callback, а у вас async-функція
const cbStyle = util.callbackify(async (x) => x * 2);
cbStyle(21, (err, v) => console.log(err, v));                       // null 42

// нюанс: reject(null) не можна передати як err=null — callbackify загортає його
const cbNull = util.callbackify(async () => { throw null; });
cbNull((err) => console.log(err.message, err.reason));
// "Promise was rejected with falsy value" null

// promisify втрачає this! Для методів — bind:
const getAsync = util.promisify(redisClient.get).bind(redisClient);

Promise-based core API — більше не треба promisify

Майже весь core Node має promise-версії. Використовуйте їх напряму — вони кращі за promisify, бо підтримують AbortSignal і правильно типізовані:

МодульЩо даєПриклад

node:stream/promisespipeline, finished — з коректним закриттям і помилкамиawait pipeline(src, gzip, dst)

core-promises.mjs
import { readFile } from 'node:fs/promises';
import { setTimeout as sleep } from 'node:timers/promises';
import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';

const cfg = JSON.parse(await readFile('config.json', 'utf8'));
await sleep(50);                                    // замість new Promise(r => setTimeout(r, 50))
await pipeline(                                     // backpressure + закриття всіх стрімів при помилці
  createReadStream('access.log'),
  createGzip(),
  createWriteStream('access.log.gz'),
);
for await (const _ of setInterval(1000)) { /* тік раз на секунду, break — і таймер зупинено */ break; }
💡
Замість stream.pipe() завжди беріть pipeline з stream/promises: .pipe() не пробрасує помилки і не закриває решту стрімів, якщо один впав, — класичне джерело file-descriptor leak. Детально — у туторіалі 6.

03 Promise: стани, ланцюжки, thenable

Більшість багів з промісами — це нерозуміння, що саме повертає .then і куди тече помилка.

Три стани і одна стрілка

  • pending → або fulfilled (зі значенням), або rejected (з причиною). Разом fulfilled і rejected називають settled. Перехід — одноразовий і незворотний.
  • "resolved" ≠ "fulfilled": проміс, resolved іншим промісом, ще може бути pending і зрештою стати rejected. Resolve = "моя доля прив'язана до X".
  • .then(onOk, onErr) завжди повертає новий проміс. Його доля визначається тим, що повернув/кинув обробник: значення → fulfilled, throw → rejected, проміс → "переходимо на нього".
  • Пропущений обробник = прозорий прохід: .then(f) без onErr пропускає rejection далі, .catch(g) пропускає значення далі.
  • .finally(fn) не бачить значення і не змінює його (якщо тільки сам не кине або не поверне rejected-проміс).
Задача 1ЛегкоКуди тече значення і помилка
task-1.js
Promise.resolve(1)
  .then((x) => x + 1)
  .then((x) => { throw new Error('boom ' + x); })
  .then((x) => console.log('skipped', x))
  .catch((e) => { console.log('caught:', e.message); return 10; })
  .finally(() => { console.log('finally'); return 999; })
  .then((x) => console.log('after:', x));
caught: boom 2 finally after: 10

1 → 2 → throw. Третій .then не має onErr, тож rejection проходить повз нього до .catch. .catch повертає 10 — ланцюжок знову fulfilled. .finally повертає 999, але це ігнорується: finally прозоро пропускає попереднє значення 10.

Thenable — "качина типізація" промісів

Специфікація Promise не перевіряє instanceof Promise: будь-який об'єкт із методом then — це thenable, і await/Promise.resolve "розгортають" його, викликаючи then(resolve, reject). Так співіснують різні реалізації (Bluebird, старі jQuery Deferred, query builder-и на кшталт Knex/Mongoose Query — у них є .then, тому await query виконує запит).

Задача 2СередньоКоли викликається then у thenable
task-2.mjs
const thenable = { then(resolve) { console.log('then called'); resolve(7); } };
console.log('await ->', await thenable);
const p = Promise.resolve(thenable);
console.log('is Promise:', p instanceof Promise, p === thenable);
console.log(await p);
then called await -> 7 is Promise: true false then called 7

Promise.resolve(thenable) повертає новий справжній Promise, а then thenable-а викликає не синхронно, а в окремій мікрозадачі (PromiseResolveThenableJob). Тому "is Promise" друкується раніше за другий "then called". Звідси й пастка: якщо випадково дати класу метод then (наприклад, у builder-і), await obj поведеться зовсім не так, як ви чекаєте.

⚠️
Promise constructor anti-pattern: загортати проміс у new Promise((res, rej) => other().then(res, rej)) — зайво й небезпечно (легко забути rej і отримати вічний pending). new Promise потрібен тільки для адаптації не-промісних API (callback, event). Винятки, кинуті синхронно в executor, перетворюються на reject — а от винятки в асинхронному callback усередині executor-а вже ні.

04 Комбінатори: all, allSettled, race, any

Чотири способи дочекатися кількох промісів — і в кожного своя семантика відмови. Найпопулярніше питання на співбесіді з async.

КомбінаторFulfilled колиRejected колиРезультатТипове застосування
Promise.allусі fulfilledперший reject (fail-fast)масив значень у порядку входуусі дані обов'язкові: user + settings + permissions
Promise.allSettledзавжди, коли всі settledніколи[{status, value | reason}]batch-операції, де часткова невдача ок: розсилка, звіт
Promise.raceперший settled — fulfilledперший settled — rejectedзначення/помилка першоготаймаут (стара школа), "хто перший відповість"
Promise.anyперший fulfilledусі rejected → AggregateErrorзначення першого успішногодзеркала/репліки: беремо найшвидшу успішну
🚫
Жоден комбінатор нічого не скасовує. Коли Promise.all відхилився через першу помилку, решта операцій продовжують виконуватись (запити летять, записи в БД пишуться). Коли race виграв таймаут — "повільний" запит теж живе далі. Справжнє скасування — тільки через AbortSignal (розділ 9).
Задача 3Середньоall падає швидко, але не зупиняє інших
task-3.js
const delay = (ms, v, fail) => new Promise((res, rej) =>
  setTimeout(() => { console.log('settled', v); fail ? rej(new Error(v)) : res(v); }, ms));

async function main() {
  try {
    await Promise.all([delay(60, 'A'), delay(10, 'B', true), delay(30, 'C')]);
  } catch (e) { console.log('all rejected with', e.message); }
  const r = await Promise.allSettled([delay(10, 'D'), delay(5, 'E', true)]);
  console.log(r.map((x) => x.status).join(','));
}
main();
settled B all rejected with B settled E settled D fulfilled,rejected settled C settled A

На 10 мс B відхиляється → all одразу rejected, ми переходимо до allSettled (стартує на ~10 мс). E (~15 мс) і D (~20 мс) settled → allSettled готовий; статуси — у порядку входу, не завершення. А C (30 мс) і A (60 мс) усе одно виконуються, коли main уже "забув" про них — їх ніхто не скасував.

Задача 4Легкоany і race
task-4.js
async function main() {
  try {
    await Promise.any([Promise.reject(new Error('a')), Promise.reject(new Error('b'))]);
  } catch (e) {
    console.log(e.constructor.name, e.errors.map((x) => x.message));
  }
  const v = await Promise.race([
    new Promise((r) => setTimeout(() => { console.log('slow finished anyway'); r('slow'); }, 20)),
    new Promise((r) => setTimeout(() => r('fast'), 5)),
  ]);
  console.log('winner:', v);
}
main();
AggregateError [ 'a', 'b' ] winner: fast slow finished anyway

any з усіма відмовами кидає AggregateError з масивом errors. race віддає перший settled, але "повільний" таймер не скасовано — і його side effect відбувається. Також пам'ятайте: Promise.race([]) назавжди pending, Promise.any([]) одразу reject, Promise.all([]) одразу [].

05 Помилки в async/await і floating promises

async/await повертає try/catch, але лише там, де ви справді чекаєте. Все, що не awaited — летить повз.

Правила async-функції

  • async function завжди повертає Promise. throw усередині = rejected promise, а не синхронний виняток.
  • try/catch ловить відмову тільки того промісу, який awaited усередині try.
  • return promise у try ≠ return await promise у try (задача 5).
  • Кидайте Error, а не рядки: тільки в Error є stack, і з ES2022 є cause: throw new Error('load user failed', { cause: err }).
Задача 5Середньоreturn vs return await у try/catch
task-5.js
async function fetchData() { throw new Error('db down'); }

async function a() {
  try { return fetchData(); }
  catch { return 'fallback-a'; }
}
async function b() {
  try { return await fetchData(); }
  catch { return 'fallback-b'; }
}
a().then(console.log, (e) => console.log('a rejected:', e.message));
b().then(console.log, (e) => console.log('b rejected:', e.message));
fallback-b a rejected: db down

У a проміс повертається з try до того, як він відхилився — catch вже не активний, і відмова "просочується" назовні. У b await чекає відмову всередині try → catch спрацьовує. Порядок рядків: a розгортає повернений проміс через додаткові мікрозадачі, тому "a rejected" приходить пізніше. Правило (і ESLint @typescript-eslint/return-await: in-try-catch): усередині try — завжди return await. Бонус: return await зберігає функцію в async stack trace.

Floating promise — тихий вбивця

Floating promise — проміс, на який ніхто не підписався: забутий await, async callback у forEach, async event handler. Наслідки: (1) помилка стає unhandled rejection → процес падає (розділ 6); (2) порядок операцій ламається — відповідь відправлено до завершення запису в БД; (3) тести "зелені", бо завершуються раніше за перевірку.

Задача 6Легкоawait у forEach
task-6.js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
async function main() {
  [3, 1, 2].forEach(async (n) => {
    await sleep(n * 10);
    console.log('item', n);
  });
  console.log('done');
}
main();
done item 1 item 2 item 3

forEach ігнорує повернене значення callback-а — три промиси "плавають". "done" друкується одразу, далі елементи в порядку таймерів, а не масиву. Виправлення: послідовно — for (const n of arr) await f(n); паралельно — await Promise.all(arr.map(f)). Те саме з .map(async) без Promise.all, .filter(async) (проміс завжди truthy!) і .reduce(async).

floating-fixes.ts
// ❌ async обробник події: відмова нікому не належить
emitter.on('order', async (o) => { await save(o); });

// ✅ ловимо всередині (або events captureRejections, див. туторіал 6)
emitter.on('order', (o) => { save(o).catch((err) => log.error({ err }, 'save failed')); });

// ✅ свідомий "fire-and-forget" — явно позначений void + catch
void audit.write(evt).catch(reportError);

// ✅ ESLint: @typescript-eslint/no-floating-promises, no-misused-promises
//    (ловить async callback там, де очікується void-функція — forEach, onClick, setInterval)
💼
На співбесіді запитають так "Чому try { promise } catch без await нічого не ловить?" — тому що try/catch синхронний: він охоплює лише виконання коду до виходу з блоку, а відмова промісу відбудеться пізніше, в мікрозадачі. await "призупиняє" функцію всередині try, і відновлення з відмовою кидає виняток у правильному місці.

06 unhandledRejection і uncaughtException

Що робить Node, коли помилка нікому не потрібна — і чому з Node 15 процес у цьому разі падає.

Поведінка за замовчуванням

  • uncaughtException — синхронний виняток, що вилетів з верхнього рівня стеку (зокрема з callback таймера чи I/O). Node друкує стек і завершує процес з кодом 1.
  • unhandledRejection — проміс відхилився, і до кінця поточного обходу мікрозадач на нього ніхто не підписався. До Node 15 був лише warning (UnhandledPromiseRejectionWarning + DeprecationWarning). З Node 15 режим за замовчуванням — throw: rejection піднімається як uncaught exception → процес падає з кодом 1.
Задача 7СередньоЧи встигне таймер?
task-7.js
process.on('exit', (c) => console.log('exit code', c));
async function job() { throw new Error('nobody awaits me'); }
job();
setTimeout(() => console.log('timer fired'), 100);
console.log('sync end');
sync end exit code 1 (+ у stderr: стек "Error: nobody awaits me")

Після синхронного коду Node обробляє мікрозадачі, бачить відхилений проміс без обробника і (режим throw) кидає його як uncaught exception. Процес падає, таймер так і не спрацьовує. З node --unhandled-rejections=warn task-7.js отримаємо warning, потім "timer fired" і "exit code 0".

Що робити в production

process-guards.js
process.on('unhandledRejection', (reason, promise) => {
  logger.fatal({ err: reason }, 'unhandledRejection');
  throw reason;                       // перетворюємо на uncaughtException — одна точка обробки
});

process.on('uncaughtException', (err, origin) => {
  logger.fatal({ err, origin }, 'uncaughtException');
  // стан процесу НЕВІДОМИЙ (недозакриті транзакції, зламані інваріанти):
  // дозаписати логи, спробувати graceful shutdown з таймаутом — і вийти
  server.close(() => process.exit(1));
  setTimeout(() => process.exit(1), 5_000).unref();
});
🚫
uncaughtException — не "try/catch для всього застосунку". Після нього процес у невизначеному стані; продовжувати обслуговувати запити — шлях до тихої корупції даних. Правильна стратегія: залогувати → graceful shutdown → exit(1), а перезапуск залишити оркестратору (systemd, PM2, Kubernetes) — див. туторіал 17.

Є ще подія rejectionHandled (обробник додали запізно) і process.on('warning'). Для "запізнілих" обробників режим throw жорсткий: обробник, доданий у setTimeout після відмови, вже не врятує процес.

07 Послідовно, паралельно, з лімітом конкурентності

Найчастіша продуктивнісна помилка в Node — випадково послідовний код. Друга за частотою — необмежено паралельний.

three-styles.js
// 1) Послідовно: час = сума. Потрібно, лише коли крок N залежить від N-1
for (const id of ids) results.push(await fetchUser(id));

// 2) Паралельно без меж: час ≈ max, але 10 000 ids = 10 000 сокетів/запитів одночасно
const results = await Promise.all(ids.map(fetchUser));

// 3) Паралельно з лімітом: час ≈ сума / N, навантаження під контролем
const limit = pLimit(8);
const results = await Promise.all(ids.map((id) => limit(() => fetchUser(id))));

// Незалежні await, записані підряд — теж прихована послідовність:
const user = await getUser(id);          // 100 ms
const feed = await getFeed(id);          // 100 ms   → 200 ms разом
// ✅
const [user2, feed2] = await Promise.all([getUser(id), getFeed(id)]);   // ~100 ms

Свій p-limit за 15 рядків

Ідея: черга функцій-фабрик (не промісів! проміс уже стартував у момент створення) + лічильник активних. Коли задача завершується (успіхом чи помилкою) — декрементуємо і беремо наступну.

p-limit.mjs
function pLimit(concurrency) {
  const queue = [];
  let active = 0;
  const next = () => {
    if (active >= concurrency || queue.length === 0) return;
    active++;
    const { fn, resolve, reject } = queue.shift();
    Promise.resolve()
      .then(fn)                       // fn() викликається тут — і синхронний throw теж стане reject
      .then(resolve, reject)
      .finally(() => { active--; next(); });
  };
  return (fn) => new Promise((resolve, reject) => {
    queue.push({ fn, resolve, reject });
    next();
  });
}

// --- перевірка ---
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const limit = pLimit(2);
let running = 0, peak = 0;
const task = (id, ms) => limit(async () => {
  running++; peak = Math.max(peak, running);
  await sleep(ms);
  running--;
  return id;
});
const t0 = Date.now();
const results = await Promise.all([task('a', 30), task('b', 10), task('c', 10), task('d', 10)]);
console.log(results, 'peak =', peak, 'took ~', Math.round((Date.now() - t0) / 10) * 10, 'ms');
// [ 'a', 'b', 'c', 'd' ] peak = 2 took ~ 30 ms

queue.shift() — O(n); для десятків тисяч задач візьміть linked-list чергу (так і робить пакет p-limit через yocto-queue).

Worker pool з промісів — для великих батчів

Альтернатива: замість черги функцій запустити N "воркерів" — async-циклів, які тягнуть наступний індекс зі спільного лічильника. Безпечно без локів, бо JS однопотоковий: між i++ і читанням немає await. Плюс — легко додати прогрес, rate-limit і зупинку по signal.

map-pool.mjs
async function mapPool(items, concurrency, worker) {
  const results = new Array(items.length);
  let i = 0;
  async function runner(wid) {
    while (i < items.length) {
      const idx = i++;              // атомарно в межах одного тіку
      results[idx] = await worker(items[idx], wid);
    }
  }
  const n = Math.min(concurrency, items.length);
  await Promise.all(Array.from({ length: n }, (_, w) => runner(w)));
  return results;
}

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
console.log(await mapPool([40, 10, 10, 10, 10], 2, async (ms, wid) => {
  await sleep(ms); return `${ms}@w${wid}`;
}));
// [ '40@w0', '10@w1', '10@w1', '10@w1', '10@w1' ]  — швидкий воркер забрав усю решту
💡
У цьому пулі перша помилка відхиляє Promise.all, але інші runner-и продовжують крутитись. Для продакшену додайте спільний AbortController: при першій помилці ac.abort(), а runner-и перевіряють signal.aborted перед наступною ітерацією. Готові рішення: p-limit, p-map (з stopOnError), p-queue (пріоритети, interval-cap для rate limit). Для CPU-задач промісний пул не допоможе — потрібні worker_threads (туторіал 8).

08 Retry з exponential backoff і jitter

Мережа ненадійна, але наївний retry перетворює короткий збій на thundering herd.

  • Що ретраїти: лише ідемпотентні операції або з idempotency key; лише тимчасові помилки — мережеві (ECONNRESET, ETIMEDOUT), 429, 502/503/504. Не ретраїти 400/401/403/404/422 — вони не "минуть".
  • Exponential backoff: пауза росте base · 2^attempt з верхньою межею (cap).
  • Jitter (випадковість) обов'язковий: без нього 1000 клієнтів, що впали одночасно, ретраять теж одночасно — синхронними хвилями. "Full jitter" (random(0, cap)) з відомої статті AWS Architecture Blog дає найменше сумарне навантаження.
  • Поважайте Retry-After у відповіді 429/503.
  • Загальний дедлайн, а не тільки кількість спроб — через спільний AbortSignal.
retry.mjs
import { setTimeout as sleep } from 'node:timers/promises';

export async function retry(fn, { retries = 5, base = 100, max = 5_000, signal } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn(attempt, signal);          // return await — щоб catch ловив
    } catch (err) {
      if (signal?.aborted || attempt >= retries || !isRetryable(err)) throw err;
      const cap = Math.min(max, base * 2 ** attempt);
      const wait = Math.random() * cap;          // full jitter: 0..cap
      await sleep(wait, undefined, { signal });  // abort перериває і очікування
    }
  }
}
const isRetryable = (e) => e.retryable !== false;   // у реальному коді: коди/статуси

// перевірка
let calls = 0;
console.log(await retry(async (n) => {
  calls++;
  if (n < 3) throw Object.assign(new Error('503'), { retryable: true });
  return 'ok after ' + n + ' retries';
}, { base: 5 }), 'calls =', calls);                // ok after 3 retries calls = 4

try { await retry(async () => { throw Object.assign(new Error('400'), { retryable: false }); }); }
catch (e) { console.log('gave up immediately:', e.message); }   // gave up immediately: 400

// використання з дедлайном на ВСЮ операцію (усі спроби разом):
await retry((n, signal) => fetch(url, { signal }), { signal: AbortSignal.timeout(10_000) });
⚠️
Retry amplification: якщо API-gateway ретраїть 3 рази, сервіс A — 3 рази, і сервіс B — 3 рази, один запит користувача може стати 27 запитами до БД саме тоді, коли вона перевантажена. Ретраї — на одному рівні (зазвичай найближчому до клієнта), плюс circuit breaker (наприклад, opossum) для швидкої відмови, коли залежність лежить.

09 Таймаути й скасування: AbortController і AbortSignal

Єдиний стандартний механізм скасування — з браузера, тепер у всьому core Node. Без нього "таймаут" лише перестає чекати.

Базова модель

  • AbortController — "пульт": має .signal і .abort(reason).
  • AbortSignal — "дріт", який ви передаєте вниз у кожну операцію: .aborted, .reason, .throwIfAborted(), подія 'abort'.
  • AbortSignal.timeout(ms) — сигнал, що спрацює сам, з reason TimeoutError. Його таймер unref-нутий — не тримає процес живим.
  • AbortSignal.any([s1, s2]) (Node 20+) — об'єднання: спрацює, коли спрацює будь-який.
  • AbortSignal.abort(reason) — вже скасований сигнал (для тестів).

Хто приймає { signal }: fetch, fs/promises (readFile, writeFile), timers/promises, events.once/on, stream.pipeline, child_process.spawn/exec, readline, http.request, net.connect, а також багато сучасних бібліотек (undici, AWS SDK v3 через abortSignal) — але не всі, перевіряйте документацію.

Задача 8СередньоЩо лежить у помилці скасування
task-8.mjs
import { setTimeout as sleep } from 'node:timers/promises';
try {
  await sleep(1000, 'value', { signal: AbortSignal.timeout(50) });
} catch (e) {
  console.log(e.name, '|', e.code, '|', e.cause?.name);
}
const ac = new AbortController();
setTimeout(() => ac.abort(new Error('user left')), 10);
try {
  await sleep(1000, null, { signal: ac.signal });
} catch (e) {
  console.log(e.name, '|', e.cause?.message);
}
AbortError | ABORT_ERR | TimeoutError AbortError | user left

Core API Node кидають AbortError (code ABORT_ERR), а справжня причина — в e.cause (signal.reason). Тому розрізняти "таймаут" і "користувач пішов" треба через cause / signal.reason. Увага: fetch поводиться інакше — він відхиляється самим reason, тобто при AbortSignal.timeout ви отримаєте DOMException з name TimeoutError, а при ac.abort() без аргументу — AbortError.

Пропагація: один сигнал на весь запит

handler-with-cancel.mjs
import http from 'node:http';

http.createServer(async (req, res) => {
  const clientGone = new AbortController();
  res.on('close', () => { if (!res.writableFinished) clientGone.abort(); });
  const signal = AbortSignal.any([clientGone.signal, AbortSignal.timeout(5_000)]);

  try {
    const r = await fetch('https://api.example.com/report', { signal });
    res.end(await r.text());
  } catch (err) {
    if (signal.reason?.name === 'TimeoutError') { res.statusCode = 504; res.end('timeout'); }
    else if (clientGone.signal.aborted) { /* відповідати нікому — просто прибираємо */ }
    else { res.statusCode = 502; res.end('upstream error'); }
  }
}).listen(3000);

// Свої async-функції теж мають приймати signal і поважати його:
async function processBatch(items, { signal } = {}) {
  for (const item of items) {
    signal?.throwIfAborted();        // кооперативне скасування між кроками
    await handle(item, { signal });
  }
}
⚠️
Скасування кооперативне. Signal не може "вбити" синхронний цикл чи CPU-обчислення — функція мусить сама перевіряти signal.aborted. І пам'ятайте про витік слухачів: якщо ви робите signal.addEventListener('abort', …) у довгоживучому сигналі для кожної операції — знімайте слухача ({ once: true } + removeEventListener) або використовуйте events.addAbortListener (повертає Disposable). Інакше — MaxListenersExceededWarning.

10 Events, async-ітератори та генератори

Pull-модель (for await) поверх push-джерел (events, streams) — природний backpressure і зрозумілий код.

events.once і events.on

events-async.mjs
import { EventEmitter, once, on } from 'node:events';
const ee = new EventEmitter();

setTimeout(() => ee.emit('ready', 42, 'x'), 5);
console.log('once ->', await once(ee, 'ready'));        // once -> [ 42, 'x' ]  (масив аргументів!)

const ac = new AbortController();
setTimeout(() => { ee.emit('tick', 1); ee.emit('tick', 2); ee.emit('tick', 3); }, 5);
try {
  for await (const [n] of on(ee, 'tick', { signal: ac.signal })) {
    console.log('tick', n);                               // tick 1, tick 2, tick 3
    if (n === 3) ac.abort();
  }
} catch (e) { console.log('loop ended:', e.name); }       // loop ended: AbortError

setTimeout(() => ee.emit('error', new Error('bad')), 5);
try { await once(ee, 'never'); }
catch (e) { console.log('once rejects on error:', e.message); }   // подія 'error' → reject
  • once повертає масив аргументів події і відхиляється на 'error' — тому await once(server, 'listening') безпечніший за ручний new Promise.
  • on буферизує події, що прийшли, поки тіло циклу зайняте (події не губляться, але буфер може рости), і ніколи не завершується сам — потрібен break, return або signal. Можна задати close-події в опціях новіших версій.

Async iteration протокол

Об'єкт async-iterable, якщо має [Symbol.asyncIterator](), що повертає ітератор з next(): Promise<{ value, done }>. for await викликає next(), чекає, обробляє — і тільки потім просить наступне. Тому це pull-модель: споживач задає темп. break/throw у циклі викликає iterator.return() — readable-стрім при цьому знищується (destroy()), ресурс закривається.

async-iter.mjs
import { createReadStream } from 'node:fs';
import { createInterface } from 'node:readline';

// 1) рядки великого файлу — без завантаження в пам'ять
const rl = createInterface({ input: createReadStream('data.txt'), crlfDelay: Infinity });
let n = 0;
for await (const line of rl) console.log(++n, line);       // 1 alpha / 2 beta / 3 gamma

// 2) будь-який Readable — async iterable з Buffer-чанками
let bytes = 0;
for await (const chunk of createReadStream('data.txt')) bytes += chunk.length;

// 3) async generator — пагінація API як "нескінченний" потік
async function* paginate(url, { signal } = {}) {
  let next = url;
  while (next) {
    const res = await fetch(next, { signal });
    const body = await res.json();
    yield* body.items;              // віддаємо елементи по одному
    next = body.nextPage;           // наступну сторінку тягнемо, лише коли споживач попросить
  }
}
for await (const item of paginate('https://api.example.com/items')) {
  if (item.id === 'stop') break;    // break → generator.return() → решта сторінок НЕ запитується
}
💡
Async-генератори можна передавати прямо в stream.pipeline як трансформацію: await pipeline(src, async function* (source) { for await (const c of source) yield c.toString().toUpperCase(); }, dst). Так пишуться ETL-скрипти без жодного класу Transform. Плюс helper-и стрімів: readable.map(fn, { concurrency }), .filter, .take (experimental у частині версій). Деталі backpressure — туторіал 6.

11 AsyncLocalStorage, async stack traces, top-level await

Як тягнути requestId крізь усі await без передачі параметром, і як читати стеки асинхронного коду.

AsyncLocalStorage — "thread-local" для async

У Java є ThreadLocal, бо один запит = один потік. У Node тисячі запитів переплітаються в одному потоці, тому глобальна змінна "поточний запит" не працює. AsyncLocalStorage (node:async_hooks, stable) прив'язує store до асинхронного контексту: усе, що запущено всередині als.run(store, fn) — проміси, таймери, I/O callback-и — бачить той самий store. Під капотом у нових версіях Node це реалізовано через V8 continuation-preserved embedder data (без накладних async_hooks), тож ціна невелика.

Задача 9СередньоЧий requestId надрукується
task-9.js
const { AsyncLocalStorage } = require('node:async_hooks');
const als = new AsyncLocalStorage();
const log = (msg) => console.log(`[${als.getStore()?.reqId ?? '-'}] ${msg}`);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
async function handler(ms) {
  log('start');
  await sleep(ms);
  log('db done');
}
als.run({ reqId: 'r1' }, () => handler(20));
als.run({ reqId: 'r2' }, () => handler(5));
log('outside');
[r1] start [r2] start [-] outside [r2] db done [r1] db done

Кожен run створює окремий контекст, який "переживає" await і таймер. Поза run store — undefined. Хоча r1 і r2 переплітаються в часі, кожен лог бачить свій reqId.

request-context.mjs
import { AsyncLocalStorage } from 'node:async_hooks';
import { randomUUID } from 'node:crypto';

export const ctx = new AsyncLocalStorage();

// middleware (Express/Fastify-подібний)
export function requestContext(req, res, next) {
  const reqId = req.headers['x-request-id'] ?? randomUUID();
  res.setHeader('x-request-id', reqId);
  ctx.run({ reqId, userId: null, start: performance.now() }, next);
}

// будь-де глибоко в коді — без прокидання параметрів
export const logger = {
  info: (msg, extra) => console.log(JSON.stringify({ msg, ...extra, reqId: ctx.getStore()?.reqId })),
};
  • Store — мутабельний об'єкт: можна дописати userId після автентифікації — побачать усі наступні кроки.
  • als.enterWith(store) — встановлює контекст до кінця поточного синхронного виконання; ризиковано, віддавайте перевагу run.
  • Контекст губиться в бібліотеках з власним пулом callback-ів (старі драйвери, кастомні черги). Фікс — AsyncResource.bind(fn) або AsyncLocalStorage.bind(fn) / AsyncLocalStorage.snapshot().
  • Саме на ALS побудовані pino-http child loggers, OpenTelemetry context у Node, nestjs-cls, request-scoped транзакції в ORM.

Async stack traces

V8 вміє показувати "логічний" стек через await (zero-cost async stack traces, рядки at async fn), але лише для ланцюжка await. Якщо проміс повертається без await або йде через .then/callback, ланка зникає.

stack.mjs
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
async function db() { await sleep(1); throw new Error('timeout'); }
async function repo() { return await db(); }
async function service() { await repo(); }
try { await service(); } catch (e) { console.log(e.stack); }
// Error: timeout
//     at db (stack.mjs:2:45)
//     at async repo (stack.mjs:3:32)
//     at async service (stack.mjs:4:28)
// Приберіть "await" у repo → рядок "at async repo" зникне зі стеку.

Ще інструменти: Error.captureStackTrace, --stack-trace-limit (за замовчуванням 10 кадрів), error.cause для ланцюжків "обгорнутих" помилок — util.inspect друкує їх разом.

Top-level await

  • Працює тільки в ESM (.mjs, "type": "module", або файл, який Node визначив як ESM за синтаксисом). У .cjs — SyntaxError. Перевірено: .js без "type" з самим лише top-level await у Node 24 запускається як ESM завдяки syntax detection.
  • TLA блокує evaluation модуля і всіх, хто його імпортує (але не сусідні гілки графа) — зручно для const db = await connect(), але повільний TLA у спільному модулі затримує старт усього застосунку.
  • Модуль із TLA не можна require() навіть у Node 22+ (ERR_REQUIRE_ASYNC_MODULE) — деталі в туторіалі 4.

12 Пастки змішування: Zalgo, подвійний callback

Класичні баги API-дизайну, через які Node-спільнота й перейшла на Promise.

"Не випускайте Zalgo"

Термін Isaac Z. Schlueter (автора npm) з есе "Designing APIs for Asynchrony": функція, яка іноді викликає callback синхронно (дані в кеші), а іноді асинхронно (пішла в мережу), — непередбачувана. Код після виклику бачить різний стан залежно від "погоди в кеші".

Задача 10СкладноZalgo в дії
task-10.js
const cache = new Map();
function getUser(id, cb) {
  if (cache.has(id)) return cb(null, cache.get(id));                          // sync!
  setTimeout(() => { cache.set(id, { id }); cb(null, cache.get(id)); }, 0);   // async
}
function run(label) {
  let ready = false;
  getUser(1, () => console.log(label, 'callback, ready =', ready));
  ready = true;
}
run('first');
setTimeout(() => run('second'), 10);
first callback, ready = true second callback, ready = false

Перший виклик — кеш порожній, callback асинхронний: ready = true встигає виконатись. Другий — кеш теплий, callback викликається синхронно, до ready = true. Один і той самий код дає різний результат. Фікс для callback-API: завжди відкладати — return process.nextTick(cb, null, cache.get(id)) (або queueMicrotask). Promise вирішує це за конструкцією: .then завжди асинхронний, навіть для Promise.resolve(cached).

Callback, викликаний двічі

Задача 11Середньоtry/catch навколо callback
task-11.js
function readConfig(cb) {
  try {
    const cfg = JSON.parse('{"port":3000}');
    cb(null, cfg);            // (1) callback кидає тут...
  } catch (err) {
    cb(err);                  // (2) ...і викликається ЩЕ РАЗ з власною помилкою
  }
}
let calls = 0;
readConfig((err, cfg) => {
  calls++;
  console.log('call', calls, err ? 'err: ' + err.message : 'cfg ok');
  if (!err) throw new Error('bug in callback');
});
call 1 cfg ok call 2 err: bug in callback

try охоплює і виклик cb — виняток з чужого callback-а ловиться і повертається туди ж. У реальному коді це "відповідь відправлено двічі" (ERR_HTTP_HEADERS_SENT), подвійний commit тощо. Правило: викликайте callback поза try, і завжди return cb(...), щоб не "провалитися" до другого виклику.

Інші пастки на межі callback ↔ promise

  • Змішаний API "повертає проміс і приймає callback" — легко обробити результат двічі або жодного разу. Обирайте одне; якщо підтримуєте обидва — callback-гілка не повинна повертати проміс, що може відхилитись без обробника.
  • Promise в EventEmitter: async-слухач, що кинув виняток, — unhandled rejection, а не 'error'-подія. Опція new EventEmitter({ captureRejections: true }) перенаправляє такі відмови в 'error'.
  • Express 4 не ловить відмови async-хендлерів (потрібен next(err) або обгортка); Express 5 і Fastify — ловлять.
  • new Promise з асинхронним throw: new Promise(() => setTimeout(() => { throw e; })) — це uncaughtException, а не reject.
  • setTimeout з async-функцією: відмова — unhandled. setInterval(async …) ще й накладає ітерації, якщо тіло довше за інтервал — використовуйте рекурсивний setTimeout або for await (const _ of setInterval(ms)) з timers/promises.
🧠 Запам'ятай: callback-контракт = "рівно один раз, завжди асинхронно, помилка першою". Promise дає це безкоштовно — тому нові API пишіть на Promise, а callback-и лише адаптуйте.

13 Каверзні питання співбесіди

Питання, на яких відрізняють "користувався async/await" від "розуміє, як це працює".

БазаЧим Promise.all відрізняється від allSettled, race і any?
all — fail-fast на першій відмові; allSettled — ніколи не відхиляється, дає статус кожного; race — перший settled (будь-який); any — перший fulfilled, а якщо всі відмовили — AggregateError. Ключове доповнення: жоден не скасовує решту операцій — для цього AbortSignal.
ПасткаЧому return promise у try не потрапляє в catch?
Бо функція виходить з try синхронно, повертаючи ще pending проміс; відмова станеться пізніше, коли try вже неактивний. return await призупиняє функцію всередині try. Тому правило: в try/catch — return await, поза ним — не обов'язково (хоча і там дає кращий async stack trace).
БазаЩо станеться з процесом при unhandled rejection у Node 20/22?
Режим за замовчуванням --unhandled-rejections=throw (з Node 15): емітиться unhandledRejection; якщо обробника немає — rejection піднімається як uncaught exception, процес завершується з кодом 1. Раніше був лише warning.
ПасткаЧи можна після uncaughtException продовжувати обслуговувати запити?
Технічно так, але не слід: стан процесу невідомий (відкриті транзакції, частково оновлені структури, зайняті локи). Правильно — залогувати, graceful shutdown з жорстким таймаутом, exit(1) і рестарт оркестратором.
БазаЯк обмежити кількість одночасних запитів до API?
Семафор/ліміт конкурентності: черга фабрик (функцій, а не промісів) + лічильник активних; при завершенні — брати наступну. Або N async-воркерів, що тягнуть індекси зі спільного лічильника. Бібліотеки — p-limit, p-map, p-queue. Важливо: передати масив промісів у ліміт уже пізно — вони стартували в момент створення.
ПасткаЧому Promise.race([fetch(url), timeout(5000)]) — поганий таймаут?
Race лише перестає чекати: запит продовжує тримати сокет, пам'ять і, можливо, змінює дані на сервері. Плюс таймер тримає event loop живим, якщо його не прибрати. Правильно: fetch(url, { signal: AbortSignal.timeout(5000) }) — справжнє скасування, unref-таймер.
БазаЩо таке jitter і навіщо він у retry?
Випадкова складова паузи між спробами. Без неї клієнти, що впали одночасно, ретраять синхронно — хвилі навантаження (thundering herd) на сервіс, що відновлюється. Full jitter: random(0, min(cap, base·2^n)). Ретраять лише ідемпотентне і тимчасове.
ПасткаЩо не так з arr.filter(async (x) => await isValid(x))?
Async-функція повертає Promise, а Promise — завжди truthy, тож filter поверне весь масив. Правильно: const flags = await Promise.all(arr.map(isValid)); arr.filter((_, i) => flags[i]).
БазаЯк прокинути requestId у логи без передачі параметром?
AsyncLocalStorage: middleware робить als.run({ reqId }, next), логер читає als.getStore(). Контекст переживає await, таймери та I/O. Губиться лише в бібліотеках з власним пулом callback-ів — лікується AsyncResource.bind.
ПасткаЩо таке Zalgo і як Promise від нього захищає?
API, що викликає callback то синхронно, то асинхронно — порядок виконання залежить від стану кешу. Promise гарантує, що обробники .then завжди виконуються асинхронно (мікрозадача), навіть для вже resolved промісу. Для callback-API — process.nextTick(cb).
ПасткаЧим відрізняється помилка скасування в fs/promises і в fetch?
Core API Node кидають AbortError (code ABORT_ERR) з причиною в err.cause. fetch (за WHATWG) відхиляється самим signal.reason: для AbortSignal.timeout — DOMException TimeoutError. Надійно — перевіряти signal.reason.
БазаЧи можна скасувати синхронний важкий цикл через AbortController?
Ні. Скасування кооперативне: signal лише виставляє прапорець і емітить подію, а подія не обробиться, поки цикл тримає потік. Для CPU-задач — розбивати роботу на шматки з await/setImmediate між ними або виносити у worker_threads і робити worker.terminate().
ПасткаЧому util.promisify(obj.method) іноді падає з "cannot read properties of undefined"?
promisify викликає функцію без контексту — this губиться. Потрібно util.promisify(obj.method).bind(obj) або util.promisify(obj.method.bind(obj)). І promisify не підходить для callback-ів з кількома результатами без util.promisify.custom.

15 Як запам'ятати

Терміни з асоціаціями — щоб на співбесіді відповідь спливала сама.

1
Error-first callback
Callback останнім аргументом, помилка — першим параметром callback-а.
Асоціація: лікар спершу повідомляє погані новини, потім хороші.
2
Floating promise
Проміс, на який ніхто не await-нув і не додав catch — його помилка нікому не належить.
Асоціація: пляшка з запискою в океані — може, хтось і прочитає.
3
all / allSettled / race / any
Fail-fast / повний звіт / перший фініш / перший успіх.
Асоціація: альпіністи в зв'язці / журі олімпіади / спринт / кастинг — беруть першого, хто пройшов.
4
Concurrency limit
Не більше N задач одночасно; нові чекають у черзі фабрик.
Асоціація: каси в супермаркеті — 4 каси, решта стоїть у черзі, а не штурмує одну.
5
Backoff + jitter
Пауза між спробами росте експоненційно і має випадкову складову.
Асоціація: після концерту люди виходять не всі в одні двері в одну секунду.
6
AbortSignal
Об'єкт-дріт, який передають у кожну операцію, щоб скасувати все одним abort().
Асоціація: рубильник у щитку — вимкнув один, згасла вся квартира.
7
AsyncLocalStorage
Store, прив'язаний до асинхронного контексту, видимий через усі await.
Асоціація: браслет у лікарні — куди б пацієнта не возили, ім'я на руці.
8
Zalgo
API, що викликає callback то синхронно, то асинхронно.
Асоціація: кур'єр, який іноді приносить піцу ще до того, як ти поклав слухавку.
9
Thenable
Будь-який об'єкт з методом then — await його "розгорне".
Асоціація: "ходить як качка, крякає як качка" — значить, проміс.
10
unhandled-rejections=throw
З Node 15 необроблена відмова валить процес з кодом 1.
Асоціація: пожежна сигналізація — раніше лише пищала, тепер вмикає спринклери.
