01 П'ять способів запустити TypeScript у Node

V8 не розуміє TypeScript — хтось мусить прибрати типи. Питання лише в тому, хто, коли і чи перевіряє він їх при цьому.

Ключова ідея, яку варто проговорити на співбесіді першою: у TypeScript-тулінгу є дві незалежні роботи. Transpile — перетворити .ts на JS, який зрозуміє рантайм (прибрати анотації, можливо переписати синтаксис). Type-check — довести, що програма коректна з погляду типів. Лише tsc робить обидві; усі швидкі інструменти (esbuild/tsx, swc, вбудований stripping у Node) роблять тільки першу, файл за файлом, не дивлячись на інші файли — тому вони в 10–100 разів швидші.

СпосібДе вживаєтьсяНюанси
tsc → distкласичний прод-білдповільно на великих проєктах; у проді немає залежності від тулінгу; source maps (--enable-source-maps)
tsxdev (tsx watch src/main.ts), скрипти, міграціїesbuild під капотом; ESM і CJS; ігнорує помилки типів; підтримує enum, decorators (але без emitDecoratorMetadata)
ts-nodeлегасі-проєкти, старі гайдиповільний з type-check; історичні болі з ESM-лоадером; розвиток сповільнився — у новому коді частіше tsx або нативний Node
swcшвидкий білд (NestJS --builder swc, Jest через @swc/jest)підтримує decorator metadata — тому популярний у Nest; конфіг .swcrc
Node type strippingскрипти, невеликі сервіси, тести, тулінглише "стираний" синтаксис; не читає tsconfig; не працює в node_modules

02 Нативний type stripping у Node: що вміє і чого ні

Node 22.18+/23.6+ запускає .ts без прапорців — але це не "Node розуміє TypeScript", а "Node вміє витерти анотації".

Під капотом Node використовує вбудовану збірку swc (пакет Amaro), яка замінює типи пробілами. Через це рядки й колонки збігаються з вихідним файлом — source maps не потрібні, stack trace вказує точно на ваш .ts. Подивимось, що реально отримує V8 (експериментальний API stripTypeScriptTypes):

try { stripTypeScriptTypes('enum E { A }'); } catch (e) { console.log(e.code); }

Erasable vs non-erasable синтаксис

"Стираний" (erasable) — синтаксис, після видалення якого лишається валідний JS з тією самою поведінкою: анотації, interface, type, as, satisfies, generics, import type, declare. "Нестираний" — той, що генерує рантайм-код:

namespace X { ... } з кодомгенерує IIFEES-модулі
constructor(private readonly db: Db)parameter property генерує this.db = dbявне поле + присвоєння

Три пастки, на які натикаються всі

Задача 1СередньоЩо впаде і з якою помилкою?
three-traps.ts
// (a)
import { greet } from './greet';             // без розширення

// (b)
import { greet, User } from './greet.ts';    // User — це interface

// (c) файл node_modules/fakepkg/index.ts
import 'fakepkg/index.ts';
(a) Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../greet' imported from ... (b) SyntaxError: The requested module './greet.ts' does not provide an export named 'User' (c) Error [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]: Stripping types is currently unsupported for files under node_modules

(a) Node застосовує звичайні правила ESM-резолюції — розширення обов'язкові, і "вгадувати" .ts він не буде. (b) після стирання interface User зникає з greet.ts, а імпорт User без type лишається звичайним рантайм-імпортом неіснуючого експорту. Лікується import { type User } і прапорцем verbatimModuleSyntax, який змушує так писати. (c) Node навмисно не стирає типи в залежностях: пакети мають публікувати JS + .d.ts.

tsconfig під нативний stripping

tsconfig.json
{
  "compilerOptions": {
    "module": "nodenext",
    "target": "es2024",
    "noEmit": true,                          // Node сам запускає .ts; tsc лише перевіряє
    "erasableSyntaxOnly": true,              // TS 5.8+: помилка на enum/namespace/parameter properties
    "verbatimModuleSyntax": true,            // змушує писати import type
    "allowImportingTsExtensions": true,      // дозволяє './greet.ts' (лише з noEmit/emitDeclarationOnly)
    "strict": true
  }
}

Якщо ж ви хочете і запускати .ts напряму в dev, і збирати dist/ через tsc, є "rewriteRelativeImportExtensions": true (TS 5.7+): у вихідному JS './greet.ts' перепишеться на './greet.js'. Працює лише для відносних шляхів — алiаси він не переписує.

⚠️
Node не читає tsconfig. Ні paths, ні target, ні jsx, ні experimentalDecorators на запуск не впливають. Тип модуля (ESM/CJS) для .ts визначається так само, як для .js: поле "type" у package.json, або явно .mts/.cts. Цікава пастка з практики: свіжий npm init -y пише "type": "commonjs" явно — і тоді import у .ts падає з "Cannot use import statement outside a module", бо явне поле вимикає автодетект синтаксису (див. туторіал 4).
💼
На співбесіді запитають так "Node тепер запускає TypeScript — tsc більше не потрібен?" — Потрібен, але для іншого: Node не перевіряє типи (програма з помилками типів запуститься), не підтримує нестираний синтаксис, не читає tsconfig. Тож tsc --noEmit лишається в CI і в редакторі, а stripping замінює лише крок транспіляції.

03 tsconfig для Node-бекенду

Половина "незрозумілих" помилок імпорту в TS-бекендах — це розбіжність між тим, як резолвить модулі tsc, і тим, як це робить Node.

tsconfig.json (білд у dist/)
{
  "compilerOptions": {
    "target": "es2023",               // Node 20+ підтримує все до ES2023 нативно — не даунлевелити
    "lib": ["es2023"],                // БЕЗ "dom": інакше fetch/window "існують" не з тих типів
    "module": "nodenext",             // моделює реальну поведінку Node (ESM + CJS за package.json)
    "moduleResolution": "nodenext",
    "outDir": "dist",
    "rootDir": "src",
    "strict": true,
    "noUncheckedIndexedAccess": true, // arr[i] має тип T | undefined
    "exactOptionalPropertyTypes": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,          // гарантує, що кожен файл можна транспілювати окремо (esbuild/swc)
    "sourceMap": true,
    "skipLibCheck": true,
    "types": ["node"]
  },
  "include": ["src"]
}

module / moduleResolution: nodenext vs bundler

🚫
Пастка paths-аліасів. "paths": { "@/*": ["src/*"] } вчить тільки tsc і IDE. tsc не переписує '@/lib/greet' у вихідному JS — і Node падає: Cannot find package '@/lib' imported from ... (перевірено нижче). Латки — tsc-alias, tsconfig-paths, бандлер. Правильне рішення для Node — subpath imports у package.json: їх розуміють і Node, і TypeScript.
package.json + alias.ts
// package.json
{
  "type": "module",
  "imports": { "#lib/*": "./src/lib/*" }
}

// alias.ts — працює нативно, без жодних плагінів
import { greet } from '#lib/greet.ts';
console.log(greet({ id: 3, name: 'Taras' }));

// alias-bad.ts — tsconfig paths, яких Node не знає
import { greet } from '@/lib/greet.ts';
$ node alias.ts; node alias-bad.ts
Hello, Taras (#3)
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@/lib' imported from .../alias-bad.ts

Для білду в dist/ використовують умовні мапінги: "#lib/*": { "development": "./src/lib/*", "default": "./dist/lib/*" }.

@types/node і "lib": ["dom"]

  • Мажорна версія @types/node = мажорна версія Node у проді. @types/node@24 на Node 20 дозволить викликати API, яких у рантаймі немає (типи "з майбутнього").
  • Без "dom" у lib глобальні fetch, Request, URL, AbortController все одно типізовані — їх надає @types/node. З "dom" з'являються window/document, і помилки "забув, що це сервер" ловляться пізно.
  • Декоратори: NestJS/TypeORM досі на experimentalDecorators + emitDecoratorMetadata (legacy). Стандартні TC39-декоратори (TS 5.0+) — інша специфікація без metadata-емісії; змішувати не можна.

Type-check у CI vs швидка транспіляція

package.json scripts
{
  "scripts": {
    "dev": "node --watch --env-file-if-exists=.env src/main.ts",
    "typecheck": "tsc --noEmit",
    "build": "tsc -p tsconfig.build.json",
    "start": "node --enable-source-maps dist/main.js",
    "test": "node --test"
  }
}

Типовий конвеєр: у dev — миттєвий запуск без перевірки (редактор показує помилки), у CI — typecheck паралельно з лінтом і тестами, і білд падає, якщо падає typecheck. На великих монорепо допомагають "incremental": true, project references (tsc -b) і нативна Go-версія компілятора TypeScript (tsgo, майбутній TS 7), яка прискорює перевірку в рази.

04 Чому типи ≠ валідація: межа довіри

Типи TypeScript існують лише під час компіляції; JSON від клієнта в рантаймі може бути чим завгодно.

JSON.parse повертає any. Коли ви пишете JSON.parse(body) as Order, ви не перевіряєте дані — ви обіцяєте компілятору, що вони правильні. Компілятор вірить, а дані — ні:

boundary.ts
interface Order { id: number; qty: number }

function total(order: Order, price: number): number {
  return order.qty * price;
}

const body = '{"id": 7, "qty": "3"}';
const order = JSON.parse(body) as Order;
console.log(total(order, 10));
console.log(order.qty + 1);
const evil = JSON.parse('{"id": 8}') as Order;
console.log(total(evil, 10));
$ node boundary.ts
30
31
NaN

Перший рядок "працює" випадково (множення приводить рядок до числа), другий тихо склеїв рядок "3" + 1 = "31", третій дав NaN, який піде в базу або в рахунок клієнту. Жодної помилки компіляції — бо типи коректні; некоректні дані.

🧠 Запам'ятай: as T на зовнішніх даних — це не перевірка, а брехня компілятору; на межі має стояти рантайм-схема, з якої виводиться тип.

Ідея "parse, don't validate": функція на межі не повертає boolean ("валідно/ні"), а повертає новий, сильніший тип (або кидає помилку). Тоді неможливо "забути перевірити" — у ядро просто не передати непарсені дані. Схемні бібліотеки роблять саме це і заодно дають тип через infer, тож немає двох джерел правди (interface і окрема валідація), які розходяться.

05 Zod: схема як джерело типу

Найпопулярніша бібліотека рантайм-валідації в TS: декларуєте схему — отримуєте і перевірку, і тип.

zod-demo.ts (zod 4)
import { z } from 'zod';

const CreateOrder = z.object({
  customerId: z.uuid(),
  qty: z.coerce.number().int().positive().max(100),
  email: z.email().transform((e) => e.toLowerCase()),
  note: z.string().max(200).optional(),
});
type CreateOrder = z.infer<typeof CreateOrder>;

const ok = CreateOrder.safeParse({
  customerId: '3f1c2b9e-8a4d-4c1e-9b2a-1d2e3f4a5b6c',
  qty: '3',
  email: 'Olena@Example.COM',
  extra: 'dropped',
});
console.log(ok.success, ok.success && ok.data);

const bad = CreateOrder.safeParse({ customerId: 'nope', qty: -1, email: 'x' });
if (!bad.success) {
  console.log(bad.error.issues.map((i) => `${i.path.join('.')}: ${i.code}`));
  console.log(z.flattenError(bad.error).fieldErrors);
}
const strict = CreateOrder.strict().safeParse({ customerId: '3f1c2b9e-8a4d-4c1e-9b2a-1d2e3f4a5b6c', qty: 1, email: 'a@b.co', role: 'admin' });
console.log('strict:', strict.success, !strict.success && strict.error.issues[0].code);

Що тут важливо

  • parse vs safeParse: перший кидає ZodError (зручно з глобальним error handler), другий повертає discriminated union { success, data | error } — без try/catch, тип звужується після if.
  • Невідомі ключі за замовчуванням вирізаються (extra зник) — це захист від mass assignment (role: 'admin' у тілі запиту не доїде до prisma.user.update({ data })). .strict() / z.strictObject() — відхиляти, .passthrough()/z.looseObject() — пропускати.
  • Коерсія z.coerce.number() — для query-рядків і form-data, де все приходить рядками. Обережно: Number('') = 0, тож пустий рядок стане нулем; для JSON-тіла коерсія зазвичай не потрібна.
  • Input ≠ output: з transform/coerce тип на вході і виході різний — z.input<typeof S> і z.output<typeof S> (z.infer = output).
  • Zod 4 переніс формати на верхній рівень (z.email(), z.uuid(), z.url(); старий z.string().email() deprecated), суттєво прискорився і має zod/mini з функціональним API для менших бандлів.
validate.middleware.ts
import type { RequestHandler } from 'express';
import { z, type ZodType } from 'zod';

export const validateBody = <T extends ZodType>(schema: T): RequestHandler => (req, res, next) => {
  const r = schema.safeParse(req.body);
  if (!r.success) return res.status(400).json({ errors: z.flattenError(r.error).fieldErrors });
  req.body = r.data;           // далі — перевірені, трансформовані дані
  next();
};

// router.post('/orders', validateBody(CreateOrder), createOrderHandler);

Standard Schema. Zod, Valibot, ArkType та інші реалізують спільний інтерфейс ~standard, тому фреймворки (tRPC, Hono, TanStack Form та ін.) можуть приймати схему будь-якої з цих бібліотек. Вибір валідатора перестав бути вибором екосистеми.

06 Valibot, TypeBox + Ajv, class-validator, Joi

Альтернативи Zod відрізняються не "силою", а моделлю: модульні функції, JSON Schema чи декоратори на класах.

Valibot: tree-shakable

API з окремих функцій, які бандлер вирізає, якщо не використовуєте: схема з кількох правил важить сотні байт. На бекенді розмір менш критичний, але це той самий код на фронтенді і в edge-функціях.

vb.ts
import * as v from 'valibot';
const Order = v.object({
  email: v.pipe(v.string(), v.email()),
  qty: v.pipe(v.number(), v.integer(), v.minValue(1)),
});
type Order = v.InferOutput<typeof Order>;
const r = v.safeParse(Order, { email: 'bad', qty: 0 });
console.log(r.success, r.issues?.map((i) => i.message));

TypeBox + Ajv: JSON Schema як стандарт

TypeBox будує звичайну JSON Schema з TS-типом поруч. Схему можна віддати Ajv (компілює її в оптимізовану JS-функцію), покласти в OpenAPI, віддати іншій мові. Це рідна модель Fastify: схема маршруту використовується і для валідації входу, і для швидкої серіалізації виходу (fast-json-stringify), див. туторіал 10.

tb.ts
import Type, { type Static } from 'typebox';   // раніше пакет звався @sinclair/typebox
import Ajv from 'ajv';
import addFormats from 'ajv-formats';

const Order = Type.Object({
  email: Type.String({ format: 'email' }),
  qty: Type.Integer({ minimum: 1 }),
}, { additionalProperties: false });
type Order = Static<typeof Order>;            // { email: string; qty: number }

console.log(JSON.stringify(Order));           // це просто JSON Schema
const ajv = addFormats(new Ajv({ allErrors: true }));
const validate = ajv.compile<Order>(Order);   // компілюється у JS-функцію один раз
console.log(validate({ email: 'a@b.co', qty: 2 }));
console.log(validate({ qty: 0, extra: 1 }), validate.errors?.map((e) => `${e.instancePath || '/'} ${e.message}`));

class-validator (NestJS) і Joi

create-order.dto.ts
import { IsEmail, IsInt, Min, Max, IsOptional, MaxLength } from 'class-validator';
import { Type } from 'class-transformer';

export class CreateOrderDto {
  @IsEmail() email!: string;
  @Type(() => Number) @IsInt() @Min(1) @Max(100) qty!: number;
  @IsOptional() @MaxLength(200) note?: string;
}

// main.ts — без whitelist зайві поля (role: 'admin') пройдуть у DTO!
app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }));

07 Конфігурація: env, .env-файли і 12-factor

Конфіг — усе, що відрізняється між середовищами; він має жити в оточенні, а не в коді, і перевірятися так само суворо, як HTTP-вхід.

12-factor коротко

  • Один артефакт (Docker-образ) для всіх середовищ; відрізняється лише оточення.
  • Конфіг — у змінних середовища (а не config/production.json з паролями в репозиторії).
  • Секрети не потрапляють ні в git, ні в образ, ні в логи.

08 Валідація env на старті: fail fast

Помилка конфігу має вбити процес за 50 мс після старту, а не через три години, коли вперше знадобиться SMTP-пароль.

src/config.ts
import { z } from 'zod';

const EnvSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.url(),
  JWT_SECRET: z.string().min(32),
  ENABLE_CACHE: z.stringbool().default(false),
});

const parsed = EnvSchema.safeParse(process.env);
if (!parsed.success) {
  console.error('Invalid environment configuration:');
  console.error(z.prettifyError(parsed.error));
  process.exit(1);
}
export const config = Object.freeze(parsed.data);
console.log(config);

Деталі, які відрізняють хороший config-модуль

  • Усі помилки разом, а не по одній: людина виправляє весь .env за раз.
  • Булеві змінні: z.coerce.boolean() — пастка (Boolean('false') === true). Використовуйте z.stringbool() (розуміє true/false/1/0/yes/no/on/off) або z.enum(['true','false']).transform(...).
  • Ніде крім config.ts не читати process.env (правило лінтера n/no-process-env) — інакше "сирі" рядки розповзаються по коду, а тести не можуть підмінити конфіг.
  • Не логувати весь конфіг — у ньому секрети. Друкуйте лише несекретні ключі або маскуйте.
  • Frozen (Object.freeze) — ніхто не мутує конфіг у рантаймі.
  • Популярні готові обгортки: envalid, @t3-oss/env-core (розділяє серверні й клієнтські змінні — важливо в Next.js).

10 Каверзні питання співбесіди

Тут перевіряють розуміння "компіляція vs рантайм", а не знання прапорців напам'ять.

БазаЧим відрізняється транспіляція від type-check, і хто що робить?
Транспіляція — перетворення TS на JS (файл за файлом, швидко): esbuild/tsx, swc, Node stripping. Type-check — аналіз усієї програми: тільки tsc (або tsgo). Тому в dev запускаємо швидким інструментом, а в CI — tsc --noEmit.
ПасткаЧому node app.ts падає на enum, хоча це валідний TypeScript?
Node робить лише type stripping — заміну типів пробілами. enum генерує рантайм-об'єкт, його не можна "стерти". Варіанти: as const-об'єкт + union-тип, --experimental-transform-types, або білд через tsc/swc. Прапорець erasableSyntaxOnly ловить це ще в редакторі.
ПасткаЧому в TS-коді з module: nodenext треба писати import './db.js', якщо файл db.ts?
tsc не переписує специфікатори імпортів: що написали, те й буде у вихідному JS, а запускатиметься db.js. Node ESM вимагає повного шляху з розширенням. Альтернатива — писати .ts з allowImportingTsExtensions (при нативному запуску) або rewriteRelativeImportExtensions (при білді).
Пасткаtsc компілює import { x } from '@/utils' без помилок, а Node падає. Чому?
paths лише вчить tsc резолвити типи; у вихідному JS лишається '@/utils', якого Node не знає (сприймає як npm-пакет @/utils). Рішення: subpath imports "imports": { "#utils/*": ... } у package.json (розуміють і Node, і TS), або бандлер/tsc-alias.
БазаНавіщо рантайм-валідація, якщо в нас strict TypeScript?
Типи стираються до запуску; JSON.parse/req.body/process.env повертають неперевірені дані. as T — лише обіцянка. На межі (HTTP, черги, env, чужі API) потрібна схема, що перетворює unknown на T — і тип виводиться з неї ж.
ПасткаЩо поверне z.coerce.boolean().parse('false')?
true — коерсія робить Boolean('false'), а непорожній рядок truthy. Для env використовуйте z.stringbool() або явний enum + transform.
БазаЯк Zod допомагає проти mass assignment?
z.object за замовчуванням вирізає невідомі ключі: { role: 'admin' } з тіла не доїде до update({ data }). .strict() — відхилити запит із зайвими полями. У NestJS аналог — ValidationPipe({ whitelist: true }); без нього class-validator пропускає зайві поля.
БазаЩо має пріоритет: змінна в оточенні чи значення з --env-file?
Оточення. --env-file не перезаписує вже встановлені змінні (перевірено: PORT=9999 node --env-file=.env дає 9999). Серед кількох --env-file пізніший перекриває попередній.
ПасткаЧому import 'dotenv/config' інколи "не працює" в ESM, хоча стоїть першим рядком?
Стоїть першим він рідко: якщо config.ts читає env на верхньому рівні, а main.ts імпортує config.ts до/паралельно з dotenv — ESM виконує залежності в порядку графа, і код читання може виконатися раніше. --env-file вирішує це повністю: env заповнений до завантаження будь-якого модуля.
БазаНавіщо isolatedModules / verbatimModuleSyntax?
Вони гарантують, що кожен файл можна коректно транспілювати окремо, без знання інших файлів: наприклад, явно відрізнити import type (стерти) від звичайного імпорту (залишити). Це вимога esbuild, swc і Node stripping.
ПасткаЧому NestJS часто не можна запустити через tsx або нативний Node без додаткових кроків?
Nest DI покладається на emitDecoratorMetadata (типи параметрів конструктора в рантаймі через reflect-metadata). esbuild/tsx не емітить ці метадані, Node stripping не підтримує legacy decorators узагалі. Тому Nest збирають tsc або swc.
БазаtRPC чи OpenAPI для спільних типів?
tRPC — коли клієнт і сервер TS в одному монорепо і API внутрішнє: нуль кодогенерації. OpenAPI — коли є сторонні клієнти, мобільні застосунки на інших мовах, потрібна документація; ціна — генерація клієнта в CI.

12 Як запам'ятати

Короткі образи для кожної ключової ідеї.

1
Type stripping
Node замінює типи пробілами і запускає решту як JS — без перевірки.
Асоціація: коректор-замазка: замазує примітки на полях, але не перевіряє, чи правильний текст.
2
Erasable syntax
Синтаксис, після видалення якого поведінка JS не змінюється.
Асоціація: риштування навколо будинку: прибрав — будинок стоїть; enum — це несуча стіна.
3
tsc --noEmit
Тільки перевірка типів, без генерації файлів — окремий крок CI.
Асоціація: техогляд авто: нічого не ремонтує, але без нього на дорогу не випустять.
4
nodenext
Резолюція модулів TS, що імітує справжній Node: розширення, exports, type.
Асоціація: тренування на тому самому стадіоні, де буде матч.
5
paths vs imports
paths знає лише tsc; #imports у package.json знають і Node, і TS.
Асоціація: прізвисько, яке знає тільки твій друг, проти адреси, яку знає пошта.
6
Межа довіри
Місце, де unknown з зовнішнього світу перетворюється схемою на перевірений тип.
Асоціація: паспортний контроль: перевіряють один раз на кордоні, а не на кожному перехресті.
