01 Шари доступу до БД: від драйвера до ORM

Перш ніж сперечатися "Prisma чи Drizzle", треба бачити, з яких шарів складається будь-який доступ до бази в Node — і на якому шарі живе кожна бібліотека.

Будь-який запит до бази з Node-процесу проходить однаковий шлях: ваш код → (ORM або query builder) → драйвер, що говорить мережевим протоколом бази (wire protocol PostgreSQL, MySQL, MongoDB OP_MSG) → TCP/TLS-з'єднання з пулу → процес бази. Усе, що вище драйвера, — лише різні способи згенерувати SQL і розпакувати результат. Тому проблеми продуктивності майже завжди лежать або у згенерованому SQL (N+1, зайві колонки, відсутні індекси), або в пулі (вичерпані з'єднання), — і майже ніколи у "швидкості ORM" як такої.

ШарЩо робитьХто відповідає за SQLТипова пастка
Драйверпротокол, параметри, парсинг типів, пулвиконкатенація рядків, витік клієнтів

🧠 Запам'ятай: ORM змінює спосіб написання запитів, але не скасовує ні пулу, ні транзакцій, ні індексів — їх розуміти треба на будь-якому шарі.

02 Драйвери і параметризовані запити

Драйвер — найнижчий шар, який ви контролюєте; правильна передача параметрів тут — головний захист від SQL-ін'єкцій.

Чому параметри, а не конкатенація

Коли ви вклеюєте вхід у рядок SQL, база отримує новий текст програми, частину якого написав атакувальник. Параметр передається окремо від тексту запиту (у PostgreSQL — повідомленням Bind розширеного протоколу), тож база вже розпарсила структуру запиту, і значення ніколи не стане кодом. Запустимо це на вбудованому node:sqlite — ефект той самий для будь-якої SQL-бази:

inject.mjs
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync(':memory:');
db.exec(`CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT, role TEXT);
         INSERT INTO users (email, role) VALUES ('olena@ex.com','admin'), ('ivan@ex.com','user');`);

const input = "nobody@ex.com' OR '1'='1";

// ❌ конкатенація: вхід стає частиною SQL-коду
const bad = db.prepare(`SELECT id, email FROM users WHERE email = '${input}'`).all();
console.log('concat  ->', bad.length, 'rows');

// ✅ параметр: вхід — лише значення, SQL-структура зафіксована
const good = db.prepare('SELECT id, email FROM users WHERE email = ?').all(input);
console.log('param   ->', good.length, 'rows');
$ node inject.mjs
concat  -> 2 rows
param   -> 0 rows
⚠️
Параметром не можна передати ідентифікатор. Назви таблиць, колонок, напрям сортування (ORDER BY ${col} ${dir}) не параметризуються — це частина структури. Для них — тільки allowlist: const col = { name: 'name', date: 'created_at' }[req.query.sort] ?? 'id'. Або спеціальні хелпери: pg-format (%I), sql(identifier) у postgres.js, sql.ref()/sql.id() у Kysely.
🚫
Пастка tagged templates. У postgres.js і в prisma.$queryRaw`...` інтерполяція безпечна тільки в тегованому шаблоні. Варто зібрати рядок заздалегідь (const q = `... ${id}`; sql.unsafe(q) або $queryRawUnsafe(q)) — і ви повернулися до конкатенації. Код-рев'ю має ловити будь-яке Unsafe/unsafe/raw( з інтерполяцією.

Що ще робить драйвер: парсинг типів

Менш очевидний аспект: pg за замовчуванням повертає bigint (int8) і numeric як рядки — бо JS number не вміщує 64-бітні цілі й десяткові без втрат. COUNT(*) у PostgreSQL має тип bigint, тож rows[0].count — це '42', а не 42. Рішення: явний каст у SQL (COUNT(*)::int), або pg.types.setTypeParser(20, BigInt), або парсити гроші як рядок у decimal-бібліотеку. Дати timestamp без зони парсяться в локальній зоні процесу — тримайте в базі timestamptz, а процес у TZ=UTC.

💼
На співбесіді запитають так "Чому COUNT(*) з pg повертає рядок?" — int8 не влазить у Number.MAX_SAFE_INTEGER (2⁵³−1) без ризику втрати точності, тож драйвер не вирішує за вас; ви або кастите, або вмикаєте BigInt-парсер.

03 Connection pooling: черга, розмір, інстанси

З'єднання з базою дороге (TCP + TLS + автентифікація + окремий процес у Postgres), тому його позичають з пулу, а не відкривають на кожен запит.

У PostgreSQL кожне з'єднання — це окремий процес-бекенд з власною пам'яттю (порядку кількох МБ і більше під навантаженням). Встановлення з'єднання з TLS коштує кілька round-trip і мілісекунди CPU. Пул тримає N "теплих" з'єднань і видає їх запитам по черзі. Якщо всі зайняті — запит чекає в черзі пулу (у Node це просто проміс, що ще не резолвнувся), а не відкриває нове з'єднання.

Ось ця механіка в 15 рядках (спрощена модель, без справжньої бази) — п'ять запитів по 100 мс на пулі з двома з'єднаннями:

pool-sim.mjs
class TinyPool {
  constructor(max) { this.max = max; this.busy = 0; this.waiting = []; }
  async connect() {
    if (this.busy < this.max) { this.busy++; return; }
    await new Promise((resolve) => this.waiting.push(resolve)); // стаємо в чергу
  }
  release() {
    const next = this.waiting.shift();
    if (next) next(); else this.busy--;          // передаємо з'єднання наступному
  }
  async query(ms) { await this.connect(); try { await new Promise((r) => setTimeout(r, ms)); } finally { this.release(); } }
}
const pool = new TinyPool(2);
const t0 = performance.now();
await Promise.all([1, 2, 3, 4, 5].map(async (id) => {
  await pool.query(100);
  console.log(`query ${id} done at ~${Math.round((performance.now() - t0) / 100) * 100} ms`);
}));

Запити 3–5 нічого не робили з базою перші 100–200 мс — вони стояли в черзі. У продакшені це виглядає як "база швидка (p50 запиту 2 мс), а ендпоінт повільний" — бо час очікування пулу не видно в логах SQL. Метрики пулу (pool.totalCount, pool.idleCount, pool.waitingCount у pg) — обов'язкові на дашборді.

Налаштування pg.Pool, які важливі

db.js
import pg from 'pg';

export const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,                        // default 10 — на ОДИН процес Node
  idleTimeoutMillis: 30_000,      // закривати простоюючі з'єднання
  connectionTimeoutMillis: 2_000, // не чекати в черзі вічно → швидка помилка 503
  statement_timeout: 5_000,       // сервер вб'є запит довший за 5 с
  application_name: 'orders-api', // видно в pg_stat_activity
});

// ОБОВ'ЯЗКОВО: idle-клієнт може отримати помилку (рестарт бази, мережа).
// Без обробника 'error' на EventEmitter — процес впаде.
pool.on('error', (err) => logger.error({ err }, 'idle pg client error'));

// graceful shutdown (див. туторіал 17)
process.on('SIGTERM', async () => { await pool.end(); process.exit(0); });

Скільки з'єднань потрібно? Інтуїція формули

Відома евристика з wiki PostgreSQL / HikariCP: connections ≈ (ядра_CPU_бази × 2) + кількість_дисків. Сенс не в точному числі, а в інтуїції: база виконує паралельно приблизно стільки запитів, скільки має ядер (плюс трохи на очікування I/O). Понад це з'єднання лише конкурують за CPU, локи й кеш — пропускна здатність падає, latency росте. Тобто менший пул часто швидший, а черга в застосунку дешевша за чергу в базі.

Друга половина інтуїції — Закон Літтла: потрібно з'єднань ≈ RPS запитів до бази × середній час запиту. 500 запитів/с × 4 мс = 2 з'єднання "в середньому зайняті"; пул 10 дає запас на піки. Якщо ж вам "потрібно" 200 з'єднань — найчастіше запити повільні або тримають з'єднання під час не-БД роботи (HTTP-виклик всередині транзакції!).

Serverless і зовнішні пулери

  • Проблема: AWS Lambda / Vercel Functions масштабуються інстансами; кожен холодний старт відкриває нове з'єднання, а "заморожені" інстанси тримають з'єднання, які ніхто не використовує. Пік трафіку = connection storm (див. туторіал 19).
  • У функції: створюйте пул поза handler (переживає warm-виклики), max: 1–2, короткий idleTimeoutMillis.
  • PgBouncer у transaction mode: серверне з'єднання видається клієнту лише на час транзакції. Ціна — не працює сесійний стан: SET без LOCAL, сесійні advisory locks, LISTEN/NOTIFY, тимчасові таблиці; іменовані prepared statements підтримуються лише новішими версіями PgBouncer з окремим налаштуванням. Prisma для цього має параметр ?pgbouncer=true.
  • RDS Proxy (AWS), Supavisor (Supabase), вбудований пулер Neon — те саме як керований сервіс. RDS Proxy "пінить" з'єднання при використанні сесійних фіч — і тоді мультиплексування зникає.
  • HTTP-драйвери (Neon serverless driver, PlanetScale/Data API-подібні): запит іде по HTTP/WebSocket — немає довгоживучого TCP взагалі; зручно для edge-рантаймів.
💼
На співбесіді запитають так "Ми збільшили pool.max з 10 до 50, а стало гірше. Чому?" — сумарна кількість з'єднань × інстанси наблизилась до max_connections; база витрачає CPU на перемикання між сотнями бекендів і конкуренцію за локи; плюс справжня причина (довгі запити або тримання з'єднання під час HTTP-викликів) нікуди не ділась.

04 Транзакції: checkout клієнта, release у finally, ізоляція

Найчастіший production-баг з pg — транзакція через pool.query або "забутий" release(), що повільно висушує пул.

Чому не можна робити BEGIN через pool.query

pool.query() щоразу бере будь-який вільний клієнт і одразу повертає його. Транзакція ж — це стан одного з'єднання. Якщо виконати pool.query('BEGIN'), а потім pool.query('UPDATE ...'), ці два виклики легко потраплять на різні з'єднання: UPDATE виконається в автокоміті, а BEGIN залишиться "висіти" на іншому клієнті, який згодом отримає чужий запит усередині відкритої транзакції. Тому транзакція = checkout конкретного клієнта.

transfer.js
export async function transfer(fromId, toId, amount) {
  const client = await pool.connect();          // checkout: клієнт тепер лише наш
  try {
    await client.query('BEGIN');
    const { rows } = await client.query(
      'SELECT balance FROM accounts WHERE id = $1 FOR UPDATE', [fromId]); // рядковий лок
    if (rows[0].balance < amount) throw new Error('insufficient funds');
    await client.query('UPDATE accounts SET balance = balance - $1 WHERE id = $2', [amount, fromId]);
    await client.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, toId]);
    await client.query('COMMIT');
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();                             // ЗАВЖДИ, навіть при помилці
  }
}

Демо: як витік клієнта вбиває сервіс

Модель тієї ж механіки: пул на 2 клієнти, функція, що кидає помилку до release():

leak.mjs
class TinyPool {
  constructor(max) { this.max = max; this.busy = 0; this.waiting = []; }
  async connect() {
    if (this.busy < this.max) { this.busy++; }
    else await new Promise((resolve) => this.waiting.push(resolve));
    return { release: () => { const n = this.waiting.shift(); if (n) n(); else this.busy--; } };
  }
}
const pool = new TinyPool(2);

async function transferBuggy(fail) {
  const client = await pool.connect();
  if (fail) throw new Error('constraint violation'); // release() ніколи не викличеться
  client.release();
}
for (let i = 1; i <= 2; i++) {
  await transferBuggy(true).catch((e) => console.log(`request ${i}: ${e.message}`));
}
console.log('busy =', pool.busy, 'of', pool.max);
console.log('request 3: waiting for a client...');
const timer = setTimeout(() => console.log('request 3: still waiting after 1s -> pool exhausted'), 1000);
await pool.connect();
clearTimeout(timer);
console.log('never printed');

Дві помилки — і сервіс мертвий, хоча база здорова. У реальному сервері процес не завершиться (є відкритий HTTP-сокет), просто всі запити до бази зависнуть до connectionTimeoutMillis (а якщо він 0, як за замовчуванням у pg, — назавжди). ✅
Захист "за конструкцією": не давайте командам писати pool.connect() вручну. Зробіть один хелпер withTransaction(fn) з try/catch/finally, або використовуйте API, де release неможливо забути: sql.begin(async (sql) => ...) у postgres.js, db.transaction(async (tx) => ...) у Drizzle/Kysely/Knex, prisma.$transaction(async (tx) => ...). У новому коді можна також використати await using з Symbol.asyncDispose, якщо ваш клієнт його підтримує.
with-transaction.js
export async function withTransaction(fn, { isolation = 'READ COMMITTED', retries = 3 } = {}) {
  for (let attempt = 1; ; attempt++) {
    const client = await pool.connect();
    try {
      await client.query(`BEGIN ISOLATION LEVEL ${isolation}`); // isolation — з allowlist, не від юзера
      const result = await fn(client);
      await client.query('COMMIT');
      return result;
    } catch (err) {
      await client.query('ROLLBACK').catch(() => {});
      // 40001 serialization_failure, 40P01 deadlock_detected — безпечно повторити ВСЮ транзакцію
      if ((err.code === '40001' || err.code === '40P01') && attempt < retries) continue;
      throw err;
    } finally {
      client.release();
    }
  }
}

Ще одна тонкість: якщо з'єднання зламалося (мережа, kill бекенду), викликайте client.release(err) — з аргументом-помилкою pg знищить клієнта замість повернення битого з'єднання в пул.

РівеньЩо гарантуєКоли брати

Детальніше про аномалії (dirty/non-repeatable/phantom read, write skew) — у Python-серії: бази даних: фундамент. Тут важливе Node-специфічне: не тримайте транзакцію відкритою через await fetch(...) до зовнішнього API — з'єднання і локи зайняті весь час відповіді стороннього сервісу.

⚠️
Паралельні запити в одній транзакції не паралельні. await Promise.all([client.query(a), client.query(b)]) на одному клієнті — запити все одно йдуть послідовно по одному з'єднанню (pg ставить їх у внутрішню чергу), а при помилці одного другий може виконатись уже в "aborted" транзакції. Пишіть послідовно.

06 Drizzle: SQL-подібний TypeScript без кодогенерації

Схема — звичайний TS-код, запити виглядають як SQL, а типи виводяться компілятором без окремого кроку generate.

src/db/schema.ts
import { pgTable, serial, text, integer, numeric, timestamp, index } from 'drizzle-orm/pg-core';
import { relations } from 'drizzle-orm';

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  email: text('email').notNull().unique(),
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
});

export const orders = pgTable('orders', {
  id: serial('id').primaryKey(),
  userId: integer('user_id').notNull().references(() => users.id),
  total: numeric('total', { precision: 12, scale: 2 }).notNull(),
}, (t) => [index('orders_user_id_idx').on(t.userId)]);

export const usersRelations = relations(users, ({ many }) => ({ orders: many(orders) }));
export const ordersRelations = relations(orders, ({ one }) => ({
  user: one(users, { fields: [orders.userId], references: [users.id] }),
}));
src/db/queries.ts
import { drizzle } from 'drizzle-orm/node-postgres';
import { eq, sql, desc } from 'drizzle-orm';
import { Pool } from 'pg';
import * as schema from './schema';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
export const db = drizzle({ client: pool, schema });

// SQL-like API — що написали, те й виконається
const rows = await db
  .select({ email: schema.users.email, spent: sql<string>`sum(${schema.orders.total})` })
  .from(schema.users)
  .leftJoin(schema.orders, eq(schema.orders.userId, schema.users.id))
  .groupBy(schema.users.email)
  .orderBy(desc(sql`2`))
  .limit(10);

// relational queries API — вкладені дані ОДНИМ SQL-запитом
const withOrders = await db.query.users.findMany({ with: { orders: true }, limit: 20 });

// транзакція: tx живе на одному checkout-клієнті, release — автоматично
await db.transaction(async (tx) => {
  await tx.update(schema.orders).set({ total: '0' }).where(eq(schema.orders.userId, 7));
  await tx.delete(schema.users).where(eq(schema.users.id, 7));
});

07 TypeORM, MikroORM, Sequelize: класичні ORM

ORM у стилі Hibernate/Doctrine: класи-сутності з декораторами, репозиторії, change tracking — потужно, але з більшою кількістю прихованої поведінки.

TypeORM

Дефолтний вибір у NestJS-туторіалах (туторіал 11). Сутності описуються класами з декораторами, метадані читаються через reflect-metadata (потрібні experimentalDecorators і emitDecoratorMetadata у tsconfig — див. туторіал 13).

  @OneToMany(() => Order, (o) => o.user) orders!: Order[];
}

const repo = dataSource.getRepository(User);

Плюсмало коду, швидкий старт (Rails, Laravel)тестованість, чистий домен, легше замінити сховище

⚠️
Відомі болі TypeORM: synchronize: true у продакшені (автоматично "підганяє" схему і може дропнути колонку з даними); save() робить SELECT перед INSERT/UPDATE і поводиться неочевидно з каскадами; типізація find-опцій і результатів слабша, ніж у Prisma/Drizzle (relations не відображаються в типі); згенеровані міграції бувають зайвими або неповними; історично повільна підтримка й накопичені issues. Для нових проєктів його обирають рідше, але в легасі NestJS-коді його багато.

MikroORM: Unit of Work та Identity Map

MikroORM — Data Mapper ORM, який чесно реалізує патерни з книги Фаулера:

  • Identity Map — в межах одного EntityManager одна сутність з одним id існує рівно одним об'єктом. Повторний findOne(User, 1) не йде в базу і повертає той самий екземпляр.
  • Unit of Work — ви просто змінюєте об'єкти; em.flush() обчислює diff (change set) і відправляє всі INSERT/UPDATE/DELETE в одній транзакції, у правильному порядку залежностей.
  • Через це EntityManager має бути per-request: em.fork() або RequestContext (під капотом — AsyncLocalStorage, див. туторіал 3). Спільний глобальний EM = identity map, що росте вічно, і "протікання" даних між запитами різних користувачів.
mikro.ts
const em = orm.em.fork();                 // окремий UoW на запит
const user = await em.findOneOrFail(User, { email });
user.name = 'Olena';                      // лише змінюємо об'єкт
em.persist(new Order(user, 100));
await em.flush();                         // UPDATE users + INSERT orders в одній транзакції

Sequelize

Найстаріший популярний Node ORM (з 2010-х), JS-first, Active Record-стиль (User.findAll({ include: Order })). Досі в тисячах легасі-проєктів, але TypeScript-підтримка прикручена збоку, нова мажорна версія роками в розробці. Для нового коду — майже ніколи; на співбесіді достатньо знати, що це і чому від нього йдуть.

Kysely

"Типобезпечний Knex": ви описуєте інтерфейс бази (руками або генеруєте з живої бази через kysely-codegen), і компілятор перевіряє назви таблиць, колонок, аліаси і тип результату — помилка в назві колонки ламає tsc, а не продакшен.

import { Kysely, PostgresDialect, sql, type Generated } from 'kysely';
import { Pool } from 'pg';

interface Database {
  users: { id: Generated<number>; email: string };
  orders: { id: Generated<number>; user_id: number; total: string };
}
const db = new Kysely<Database>({ dialect: new PostgresDialect({ pool: new Pool() }) });

const rows = await db
  .selectFrom('users as u')
  .innerJoin('orders as o', 'o.user_id', 'u.id')
  .select(['u.email', sql<string>`sum(o.total)`.as('spent')])
  .groupBy('u.email')
  .execute();
// rows: { email: string; spent: string }[]  — 'u.emial' не скомпілюється

await db.transaction().execute(async (trx) => {
  await trx.deleteFrom('orders').where('user_id', '=', 7).execute();

09 MongoDB: драйвер і Mongoose

Mongoose повертає "схему" в schemaless-базу на рівні застосунку — разом з middleware, валідацією і власними пастками продуктивності.

user.model.js
import mongoose from 'mongoose';

const userSchema = new mongoose.Schema({
  email: { type: String, required: true, unique: true, lowercase: true },
  passwordHash: { type: String, required: true, select: false },  // не повертати за замовчуванням
  team: { type: mongoose.Schema.Types.ObjectId, ref: 'Team' },
}, { timestamps: true });

// middleware (hooks): виконується перед save()
userSchema.pre('save', async function () {
  if (this.isModified('passwordHash')) { /* напр., аудит */ }
});

export const User = mongoose.model('User', userSchema);

// populate = "join" на стороні застосунку: ДОДАТКОВИЙ запит до teams з $in
const users = await User.find({ active: true }).populate('team').lean();
  • populate() — не JOIN у базі, а другий запит teams.find({ _id: { $in: [...] } }) на кожен шлях. Для списку це 2 запити, не N+1. Але populate всередині циклу, глибоко вкладені populate або findById на кожен елемент — класичний N+1. Альтернатива — $lookup в aggregation pipeline (JOIN на сервері) або денормалізація.
  • lean() — повертає прості JS-об'єкти замість Mongoose-документів (без getter-ів, virtuals, change tracking, save()). У рази менше пам'яті та CPU на великих вибірках; для read-only API — майже завжди.
  • Middleware-пастка: pre('save') НЕ спрацьовує на updateOne/findOneAndUpdate — для них окремі query middleware. Валідація на update вимкнена, поки не передати runValidators: true.
  • Безпека: фільтр з req.body напряму (User.findOne({ email: req.body.email })) дозволяє operator injection { "$ne": null } — детально в туторіалі 14; у Mongoose є опція sanitizeFilter.

10 Проблема N+1: як виглядає і як лікувати

Найдорожча помилка ORM-коду: один запит на список і ще по одному на кожен рядок — латентність множиться на N.

Демо: 51 запит проти 2

Фейкова "база" з затримкою ~5 мс на round-trip (реалістично для бази в сусідній зоні доступності):

nplus1.mjs
let queries = 0;
const users = Array.from({ length: 50 }, (_, i) => ({ id: i + 1, name: `u${i + 1}` }));
const orders = users.flatMap((u) => [{ id: u.id * 10, userId: u.id }, { id: u.id * 10 + 1, userId: u.id }]);
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
async function query(fn) { queries++; await sleep(5); return fn(); }

async function nPlusOne() {
  const list = await query(() => users);                       // 1 запит
  for (const u of list) {                                      // + N запитів
    u.orders = await query(() => orders.filter((o) => o.userId === u.id));
  }
  return list;
}

async function batched() {
  const list = await query(() => users);                       // 1 запит
  const ids = new Set(list.map((u) => u.id));
  const all = await query(() => orders.filter((o) => ids.has(o.userId))); // WHERE user_id = ANY($1)
  const byUser = Map.groupBy(all, (o) => o.userId);
  return list.map((u) => ({ ...u, orders: byUser.get(u.id) ?? [] }));
}

for (const [name, fn] of [['N+1', nPlusOne], ['batched', batched]]) {
  queries = 0;
  const t = performance.now();
  const r = await fn();
  console.log(`${name.padEnd(8)} queries=${String(queries).padStart(2)}  time≈${Math.round((performance.now() - t) / 10) * 10} ms  orders=${r.reduce((s, u) => s + u.orders.length, 0)}`);
}
$ node nplus1.mjs
N+1      queries=51  time≈290 ms  orders=100
batched  queries= 2  time≈10 ms  orders=100

Точні мілісекунди залежать від машини; важливе співвідношення — латентність N+1 росте лінійно з N, а батча — ні. Плюс N+1 тримає з'єднання з пулу в 25 разів довше.

    const { rows } = await pool.query('SELECT * FROM orders WHERE user_id = ANY($1)', [userIds]);
    const byUser = Map.groupBy(rows, (r) => r.user_id);
    return userIds.map((id) => byUser.get(id) ?? []);   // той самий порядок і довжина, що й ключі!
  }),
});

// resolver: User.orders = (user, _, ctx) => ctx.loaders.ordersByUser.load(user.id)
💼
На співбесіді запитають так "Як знайти N+1 у продакшені?" — логувати кількість SQL-запитів на HTTP-запит (через AsyncLocalStorage-лічильник або OpenTelemetry spans, туторіал 17), шукати трейси з "гребінцем" однакових коротких запитів; pg_stat_statements — запит з величезним calls і мікроскопічним mean_time; у тестах — assert на кількість запитів.

11 Міграції: expand/contract і правила безпеки

Під час rolling-деплою стара і нова версії коду працюють з ОДНІЄЮ базою одночасно — міграція мусить бути сумісною з обома.

Незламні правила

  1. Ніколи не редагуйте застосовану міграцію. Інструмент зберігає список/чексуми застосованих (_prisma_migrations, __drizzle_migrations, knex_migrations). Змінений файл або не застосується на проді (там він уже "виконаний"), або зламає перевірку чексуми — і dev/prod-схеми розійдуться. Помилка в міграції → нова міграція, що її виправляє.
  2. Міграції — у VCS і в CI, застосовуються окремим кроком деплою (migrate deploy / init-container / job), а не при старті кожного з 10 подів одночасно (гонка; якщо інакше ніяк — advisory lock).
  3. Деструктивні зміни — окремим релізом після того, як жоден код не використовує стару колонку.

Expand / contract (parallel change) на прикладі перейменування колонки

КрокМіграціяКод
1. ExpandADD COLUMN full_name TEXT NULLпише в обидві колонки, читає стару
2. BackfillUPDATE ... SET full_name = name батчами по 1–10 тис. рядків—
3. Switch(за потреби) NOT NULL через CHECK ... NOT VALID + VALIDATEчитає нову, пише в обидві
4. ContractDROP COLUMN name — окремий деплойлише нова колонка
⚠️
Операції, що лочать таблицю в PostgreSQL: CREATE INDEX без CONCURRENTLY (блокує запис); ALTER COLUMN TYPE (переписує таблицю); додавання NOT NULL чи FK без NOT VALID. Навіть "миттєвий" ALTER чекає ACCESS EXCLUSIVE-лок, і поки чекає за довгою транзакцією — блокує всі нові запити до таблиці. Ставте SET lock_timeout = '5s' у міграціях. Зверніть увагу: CREATE INDEX CONCURRENTLY не працює всередині транзакції, а багато інструментів обгортають міграцію в транзакцію — шукайте опцію її вимкнути.

Тестування: справжня база в контейнері

Моки репозиторію перевіряють, що ви викликали findMany, — але не що SQL правильний, індекс використовується, constraint спрацьовує, а міграція застосовується. Для шару доступу до даних найкраще співвідношення — інтеграційні тести з реальним Postgres через Testcontainers (потрібен Docker):

  • Ізоляція тестів: TRUNCATE між тестами, або кожен тест у транзакції з ROLLBACK в кінці (швидко, але не працює, якщо код сам комітить), або окрема база-шаблон (CREATE DATABASE ... TEMPLATE) на воркер.
  • Не підміняйте Postgres на SQLite "бо швидше" — інші типи, інший SQL, інша поведінка локів.
  • Більше про стратегії — туторіал 16.

А транзакційну логіку можна перевірити навіть без Docker на node:sqlite, коли важливий сам патерн BEGIN/COMMIT/ROLLBACK:

tx.mjs
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync(':memory:');
db.exec(`CREATE TABLE accounts (id INTEGER PRIMARY KEY, balance INTEGER CHECK (balance >= 0));
         INSERT INTO accounts VALUES (1, 100), (2, 0);`);
const move = db.prepare('UPDATE accounts SET balance = balance + ? WHERE id = ?');

function transfer(from, to, amount) {
  db.exec('BEGIN');
  try {
    move.run(amount, to);        // спершу зараховуємо
    move.run(-amount, from);     // потім списуємо — може порушити CHECK
    db.exec('COMMIT');
  } catch (e) {
    db.exec('ROLLBACK');
    console.log('rolled back:', e.message);
  }
}
transfer(1, 2, 70);
transfer(1, 2, 70);  // на рахунку 1 лишилось 30
console.log(db.prepare('SELECT id, balance FROM accounts').all().map((r) => `${r.id}:${r.balance}`).join(' '));
$ node tx.mjs
rolled back: CHECK constraint failed: balance >= 0
1:30 2:70

Другий переказ встиг зарахувати 70 на рахунок 2, але ROLLBACK скасував і це зарахування — рахунок 2 має 70, а не 140.

14 Каверзні питання співбесіди

Питання, на яких відрізняють "користувався ORM" від "розумію, що відбувається з базою".

БазаЧому не можна робити транзакцію через pool.query('BEGIN')?
Транзакція — стан одного з'єднання, а кожен pool.query може взяти інший клієнт. BEGIN потрапить на одне з'єднання, UPDATE — на інше (в автокоміті), а "висяча" транзакція захопить чужі запити. Потрібно const c = await pool.connect() і всі запити через c, з release() у finally.
ПасткаСервіс періодично "зависає" на всіх ендпоінтах з БД, база при цьому здорова. Що перевірити першим?
Витік клієнтів пулу: pool.connect() без release() у finally (або release лише в happy path). Метрика waitingCount росте, idleCount = 0. Також: транзакції, що тримають з'єднання під час HTTP-викликів, і відсутній connectionTimeoutMillis (за замовчуванням pg чекає вічно).
БазаЯк порахувати розмір пулу?
Від бази, а не від застосунку: сумарно всі процеси мають бути помітно нижче max_connections; ефективна паралельність бази ≈ ядра × 2 + диски. На процес — RPS × середній час запиту (Little's law) з запасом. Типово 5–20 на процес Node; більше пулу ≠ більше throughput.
ПасткаЧим PgBouncer у transaction mode може зламати застосунок?
Серверне з'єднання змінюється між транзакціями, тож ламається все сесійне: SET (без LOCAL), сесійні advisory locks, LISTEN/NOTIFY, temp tables, а в старих версіях — іменовані prepared statements (звідси ?pgbouncer=true у Prisma).
БазаЧи захищає ORM від SQL-ін'єкцій повністю?
Лише API, що параметризує значення. Raw-методи з рядками ($queryRawUnsafe, sql.unsafe, knex.raw(`...${x}`)), динамічні ідентифікатори (orderBy(req.query.sort) у деяких білдерах) і Mongo-фільтри з req.body залишаються дірами. Ідентифікатори — тільки allowlist.
ПасткаPrisma include — це N+1?
Ні, у класичному сенсі: один додатковий запит з IN (...) на рівень вкладеності (або JOIN з relationLoadStrategy: 'join'). N+1 — це виклик запиту в циклі. Реальна проблема include — overfetching усіх колонок і рядків зв'язку; лікується select/take. Бонус: Prisma автоматично батчить findUnique, викликані в одному тіку.
БазаActive Record vs Data Mapper?
AR: сутність сама вміє save() — просто, але домен залежить від БД. DM: сутність — чисті дані, персистентність у репозиторії/EntityManager — тестованіше, краще для складного домену. TypeORM вміє обидва, MikroORM — DM з Unit of Work, Sequelize/Mongoose — ближче до AR.
ПасткаЧому MikroORM EntityManager не можна шарити глобально?
Identity map і Unit of Work накопичують сутності: глобальний EM росте в пам'яті без меж і "протікає" стан між запитами різних користувачів (ви отримаєте застарілий кешований об'єкт замість свіжих даних). Тому em.fork() або RequestContext на кожен запит.
БазаЧому COUNT(*) з pg повертає рядок '42'?
COUNT повертає bigint (int8), який не завжди вміщається в JS number без втрати точності; pg за замовчуванням не ризикує. COUNT(*)::int, setTypeParser(20, ...) або BigInt. Те саме з numeric — для грошей правильно лишати рядком і використовувати decimal-бібліотеку.
ПасткаПомилка в уже застосованій міграції. Можна просто виправити файл?
Ні. Інструмент вважає її виконаною (за назвою/чексумою): на проді вона не перезапуститься, а на нових середовищах виконається вже інша версія — схеми розійдуться (або перевірка чексуми зламає деплой). Пишеться нова міграція-виправлення.
БазаЯк перейменувати колонку без даунтайму?
Expand/contract: додати нову колонку → код пише в обидві → backfill батчами → код читає нову → окремим релізом drop старої. Rename "в лоб" ламає стару версію коду, яка ще працює під час rolling-деплою.
ПасткаЩо не так з await Promise.all(items.map(i => tx.insert(i))) всередині транзакції?
Транзакція = одне з'єднання, тож паралелізму немає: запити серіалізуються на клієнті. Користі нуль, а при помилці одного інші продовжать відправлятися в уже aborted-транзакцію ("current transaction is aborted"), що заплутує логи. Краще один batch-INSERT з багатьма VALUES.
БазаНавіщо lean() у Mongoose?
Повертає прості об'єкти без обгорток документа (getters, virtuals, change tracking, save) — суттєво менше пам'яті та CPU на гідрацію. Для read-only відповідей API — майже завжди; не підходить, якщо потрібні virtuals/методи документа або подальший save().

16 Як запам'ятати

Асоціації, що повертають усю тему за секунду.

1
Connection pool
Фіксований набір теплих з'єднань і FIFO-черга тих, хто чекає.
Асоціація: прокат самокатів: самокатів 10, черга людей — скільки завгодно; хто не повернув самокат, той вкрав його в усіх.
2
release() у finally
Клієнт повертається в пул на будь-якому шляху виконання, включно з помилкою.
Асоціація: ключі від номера готелю здаєш на рецепції, навіть якщо виїжджаєш зі скандалом.
3
Параметризований запит
Текст SQL і значення йдуть до бази окремо; значення ніколи не стає кодом.
Асоціація: бланк з клітинками: що б ти не написав у клітинці "Ім'я", воно не змінить текст договору.
4
pool × instances
База бачить суму пулів усіх процесів, а не налаштування одного.
Асоціація: кожен із 12 гостей "взяв лише 10 тарілок" — у кухні 120 брудних тарілок.
5
N+1
Один запит на список і окремий запит на кожен елемент.
Асоціація: ходити в магазин окремо за кожним яйцем замість узяти лоток.
6
DataLoader
Збирає всі load(id) одного тіку і робить один batch-запит.
Асоціація: офіціант, який спершу обходить увесь стіл, а потім одним рейсом іде на кухню.
7
Unit of Work + Identity Map
Змінюєш об'єкти; flush() записує diff однією транзакцією; один id — один об'єкт.
Асоціація: кошик в інтернет-магазині: накидаєш і правиш, а оплачуєш один раз.
8
Expand / contract
Спершу додаємо нове поруч зі старим, потім мігруємо, і лише потім видаляємо старе.
Асоціація: новий міст будують поруч зі старим і зносять старий лише після того, як усі поїхали новим.
9
PgBouncer transaction mode
Серверне з'єднання видається лише на час транзакції — тисячі клієнтів на десятки з'єднань.
Асоціація: таксі-пул: машина твоя лише на одну поїздку, тож речі в багажнику не залишай (сесійний стан).
