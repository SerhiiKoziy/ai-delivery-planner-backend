01 Мінімальний сервер: що насправді дає node:http

Express, Fastify і Nest — це обгортки над тим самим http.Server. Хто розуміє низ, той дебажить будь-який фреймворк.

Модуль node:http — це не «фреймворк», а тонкий шар над TCP-сокетом і C-парсером HTTP (llhttp). Він дає вам рівно дві речі: розібраний запит і можливість записати відповідь. Роутинг, парсинг JSON, валідація, cookies, CORS — усе це ви (або фреймворк) робите самі.

hello.mjs
import http from 'node:http';

const server = http.createServer((req, res) => {
  // req  — http.IncomingMessage  (Readable stream + метадані)
  // res  — http.ServerResponse   (Writable stream + статус/заголовки)
  res.statusCode = 200;
  res.setHeader('content-type', 'text/plain; charset=utf-8');
  res.end(`Привіт, ${req.method} ${req.url}\n`);
});

server.listen(3000, () => console.log('http://localhost:3000'));

req — це Readable, res — це Writable

Це головна ментальна модель, яку перевіряють на співбесіді. IncomingMessage успадковує stream.Readable: заголовки вже розібрані, коли викликається ваш handler, а тіло ще ні — воно прийде потоком chunk-ів, і поки ви його не прочитаєте, воно лежить у буферах сокета (і через backpressure клієнт зупиниться). ServerResponse — stream.Writable: ви можете писати шматками (res.write()), і перший write «заморожує» статус і заголовки.

Об'єктЩо є одразуЩо треба зробити самомуТипова помилка

⚠️
req.url — це не URL, а request-target: зазвичай /users/1?x=2, без хоста. Для розбору використовують new URL(req.url, 'http://localhost') (база потрібна лише як заглушка). Не беріть базу з req.headers.host для чогось безпекового — Host контролює клієнт.

Як Node обирає framing відповіді

Якщо ви поставили content-length — Node відправить рівно стільки байтів. Якщо ні, а ви пишете через res.write() — HTTP/1.1 автоматично перейде на Transfer-Encoding: chunked. Якщо ви одразу викликали res.end(body) без write, Node сам порахує довжину. content-length у байтах, не в символах: для кирилиці 'Привіт'.length === 6, а Buffer.byteLength('Привіт') === 12.

🧠 Запам'ятай: handler викликається, коли розібрані заголовки; тіло — це ще непрочитаний стрім, і відповідальність за нього на вас.

02 Тіло запиту, ліміти й роутинг руками

Те, що express.json() робить за вас, — і чому без ліміту це DoS-вектор.

Напишімо «справжній» мінісервер без залежностей: читання JSON з лімітом, валідація content-length заздалегідь, роутинг через regex, єдиний обробник помилок. Це рівно те, що всередині роблять body-parser і роутер Express, тільки без магії.

demo-server.mjs
import http from 'node:http';

const MAX_BODY = 1024 * 1024; // 1 MB

function readJson(req, limit = MAX_BODY) {
  return new Promise((resolve, reject) => {
    let size = 0;
    const chunks = [];
    req.on('data', (chunk) => {
      size += chunk.length;
      if (size > limit) {
        req.pause();              // перестаємо читати тіло
        reject(Object.assign(new Error('Payload Too Large'), { status: 413 }));
        return;
      }
      chunks.push(chunk);
    });
    req.on('end', () => {
      try { resolve(JSON.parse(Buffer.concat(chunks).toString('utf8') || '{}')); }
      catch { reject(Object.assign(new Error('Invalid JSON'), { status: 400 })); }
    });
    req.on('error', reject);
  });
}

function send(res, status, body) {
  const json = JSON.stringify(body);
  res.writeHead(status, {
    'content-type': 'application/json; charset=utf-8',
    'content-length': Buffer.byteLength(json),
  });
  res.end(json);
}

const users = new Map([['1', { id: '1', name: 'Ada' }]]);

const server = http.createServer(async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`);
  const sock = `${req.socket.remotePort}`;
  try {
    if (req.method === 'GET' && url.pathname === '/health') {
      return send(res, 200, { ok: true, sock });
    }
    const m = url.pathname.match(/^\/users\/(\w+)$/);
    if (req.method === 'GET' && m) {
      const user = users.get(m[1]);
      return user ? send(res, 200, { ...user, sock }) : send(res, 404, { error: 'Not Found' });
    }
    if (req.method === 'POST' && url.pathname === '/users') {
      if (Number(req.headers['content-length']) > MAX_BODY) {
        res.setHeader('connection', 'close');
        return send(res, 413, { error: 'Payload Too Large' }); // навіть не читаємо
      }
      const body = await readJson(req);
      const id = String(users.size + 1);
      users.set(id, { id, name: body.name });
      return send(res, 201, { id, sock });
    }
    send(res, 404, { error: 'Not Found' });
  } catch (err) {
    if (err.status === 413) res.setHeader('connection', 'close'); // сокет не перевикористати
    send(res, err.status ?? 500, { error: err.message });
  }
});

server.keepAliveTimeout = 65_000;
server.headersTimeout = 66_000;

server.listen(3000, () => console.log('listening on :3000'));
export default server;

Клієнт (теж без залежностей — вбудований fetch), який імпортує сервер і проганяє сценарії:

Що тут видно:

  • Переюз з'єднань. Сім запитів пройшли лише через два TCP-сокети (два remote-порти): вбудований fetch тримає keep-alive pool. Детально — у розділі 4.
  • Ліміт перевіряється двічі. Спочатку дешево — за заголовком content-length (відмова без читання тіла). Потім — підрахунком байтів у стрімі, бо content-length може бути відсутній (chunked) або брехливим.
  • 413 + connection: close. Якщо ми не дочитали тіло, сокет у «брудному» стані: наступний запит на ньому почнеться посеред старого тіла. Тому такий сокет треба закрити, а не повертати у keep-alive.
🐛
Під час написання цього прикладу перша версія на переповненні робила просто req.destroy(). Результат: клієнт отримав не 413, а EPIPE/ECONNRESET — сокет знищено, поки клієнт ще писав тіло. Навіть з правильним кодом клієнт, що активно заливає великий chunked-body, може побачити reset замість 413 — це нормальна поведінка TCP, тож дешева перевірка за content-length важлива.

Чому роутинг «руками» — погана ідея у проді

  • Regex на кожен маршрут — O(n) перебір; фреймворки використовують radix tree (find-my-way у Fastify, Hono's RegExpRouter / TrieRouter).
  • Треба пам'ятати про 405 Method Not Allowed, HEAD, trailing slash, URL-decoding параметрів, OPTIONS для CORS.
  • Async-помилки: якщо забути try/catch навколо await, отримаєте unhandled rejection і запит, що висить до таймауту.
💼
На співбесіді запитають так «Що станеться, якщо в handler-і не прочитати тіло POST-запиту й одразу відповісти?» — Node спробує дочитати/відкинути залишок, щоб зберегти keep-alive, але для великого тіла простіше і безпечніше закрити з'єднання. Неспоживане тіло + backpressure = клієнт зупиняється на запису.

Що важливо з цієї картинки

  • Мережевий I/O не йде в thread pool. Сокети неблокуючі, libuv отримує сповіщення через epoll (Linux) / kqueue (macOS) / IOCP (Windows). Тому 10 000 відкритих з'єднань — це не 10 000 потоків. Деталі — у туторіалі 1 і туторіалі 2 (події сокетів обробляються у фазі poll).
  • Парсер написаний на C (llhttp, згенерований з TypeScript-опису автомата через llparse) — саме він відкидає некоректні запити ще до JS (наприклад, конфліктні Content-Length + Transfer-Encoding, захист від request smuggling) і застосовує ліміт розміру заголовків (--max-http-header-size, за замовчуванням 16 КБ → 431).
  • Ваш handler синхронний відносно event loop. Поки він рахує щось важке, жоден інший сокет не обробляється — див. туторіал 8.
  • backlog (server.listen(port, host, backlog), за замовчуванням 511) — довжина черги вже прийнятих ядром, але ще не забраних процесом з'єднань. Якщо event loop заблокований — черга росте, потім ядро починає відкидати SYN.
🎉
Цікавий факт До Node 12 використовувався http_parser — рукописний C-код, що походить від парсера nginx і який роками боялися чіпати. llhttp — переписаний з нуля автомат, згенерований з опису на TypeScript, і помітно швидший. Автор llhttp — Fedor Indutny, багаторічний контриб'ютор ядра Node (TLS, crypto).

04 Keep-alive і http.Agent: пул з'єднань

Найдешевша оптимізація латентності між сервісами — не відкривати TCP (і TLS) на кожен запит.

Новий TCP-конект коштує 1 RTT на handshake, TLS 1.3 — ще 1 RTT, плюс slow start (перші пакети йдуть повільно). Між двома сервісами в одному регіоні це «лише» мілісекунди, але при 1000 RPS і відсутності keep-alive ви створюєте 1000 сокетів на секунду, кожен потім висить у TIME_WAIT ~60 с на стороні, що закрила першою. Звідси класичне вичерпання ефемерних портів (EADDRNOTAVAIL).

Перевіряємо експериментом

Рахуємо події 'connection' на сервері для трьох конфігурацій клієнта:

agent-demo.mjs
import http from 'node:http';
import { once } from 'node:events';

let connections = 0;
const server = http.createServer((req, res) => res.end('ok'));
server.on('connection', () => connections++);
server.listen(0);
await once(server, 'listening');
const { port } = server.address();

function get(agent) {
  return new Promise((resolve, reject) => {
    http.get({ port, path: '/', agent }, (res) => {
      res.resume();               // обов'язково дочитати тіло!
      res.on('end', resolve);
    }).on('error', reject);
  });
}

async function run(label, opts) {
  connections = 0;
  let agent = new http.Agent(opts);
  for (let i = 0; i < 10; i++) await get(agent);           // послідовно
  console.log(`${label} послідовно: ${connections} TCP`);
  agent.destroy();
  connections = 0;
  agent = new http.Agent(opts);
  await Promise.all(Array.from({ length: 10 }, () => get(agent))); // паралельно
  console.log(`${label} паралельно: ${connections} TCP`);
  agent.destroy();
}

await run('keepAlive:false             ', { keepAlive: false });
await run('keepAlive:true              ', { keepAlive: true });
await run('keepAlive:true, maxSockets:2', { keepAlive: true, maxSockets: 2 });
console.log('globalAgent.keepAlive =', http.globalAgent.options.keepAlive);
server.closeAllConnections();
server.close();

keepAlive:false              паралельно: 10 TCP
keepAlive:true               послідовно: 1 TCP
keepAlive:true               паралельно: 10 TCP
keepAlive:true, maxSockets:2 послідовно: 1 TCP

  • Keep-alive не обмежує паралелізм. 10 одночасних запитів без maxSockets → 10 сокетів (за замовчуванням maxSockets: Infinity). Keep-alive лише дозволяє перевикористати сокет.
  • maxSockets — це ліміт паралельних з'єднань на origin; зайві запити стають у чергу Agent-а. Це і захист downstream-сервісу, і джерело прихованої латентності (час у черзі не видно в метриках сервера).
  • З Node 19 http.globalAgent має keepAlive: true (раніше було false, і це був класичний «чому мій сервіс робить тисячі TIME_WAIT»).
  • res.resume() обов'язковий, якщо тіло відповіді вам не потрібне: доки тіло не спожите, сокет не повернеться в пул, і з maxSockets ви отримаєте «зависання» на N+1-му запиті.
⚠️
Stale socket. Агент тримає idle-сокет, а сервер уже закрив його по своєму keepAliveTimeout. Якщо клієнт відправить запит саме в цей момент — отримає ECONNRESET / «socket hang up». Тому клієнтський idle-timeout має бути меншим, ніж серверний. Undici за замовчуванням враховує заголовок Keep-Alive: timeout=N, який Node-сервер надсилає у відповідях.

Анатомія 502

Load balancer (AWS ALB, GCP LB, nginx з keepalive в upstream) теж тримає пул з'єднань до ваших інстансів. У ALB idle timeout за замовчуванням 60 секунд. Node закриває idle-сокет через 5 секунд. Отже, LB вважає сокет живим ще 55 секунд після того, як Node його закрив. Більшість часу LB помічає FIN і не використовує сокет, але якщо запит від LB і FIN від Node «розминаються в дорозі» — LB пише в напівзакритий сокет, отримує RST і віддає клієнту 502 Bad Gateway. У логах Node — нічого, бо запит до нього так і не дійшов.

server.js — налаштування за ALB (idle 60 с)
const server = http.createServer(app);
server.keepAliveTimeout = 65_000;  // більше за idle timeout LB
server.headersTimeout = 66_000;    // історично мав бути > keepAliveTimeout
server.requestTimeout = 30_000;    // жоден легітимний API-запит не триває 5 хв
server.listen(process.env.PORT ?? 3000);
💡
Чому headersTimeout > keepAliveTimeout? У старих версіях (до Node ~18) таймер заголовків стартував у момент, коли сокет ставав idle, і при headersTimeout < keepAliveTimeout Node сам рвав «живі» keep-alive сокети. У сучасних версіях логіку переписано, але правило досі живе в усіх гайдах — дотримуватися його нічого не коштує. Те саме стосується nginx: keepalive_timeout у upstream-блоці має бути меншим за keepAliveTimeout Node.
💼
На співбесіді запитають так «У нас 0.1% 502 від ALB, у логах сервісу чисто. Що перевірите першим?» — співвідношення keep-alive таймаутів (Node vs LB), потім — чи не вбиває оркестратор поди без graceful shutdown (розділ 13), потім — чи не падає процес (OOM, unhandled rejection).

06 HTTP-клієнт: fetch, undici, таймаути

Сервіс у мікросервісній архітектурі — це передусім HTTP-клієнт. Без таймаутів один повільний downstream кладе всіх.

З Node 18 глобальний fetch — стабільний (з Node 21 без experimental-позначки) і реалізований бібліотекою undici, яка вшита в Node (у Node 24.18 — process.versions.undici === '7.28.0'). Undici — це окремий HTTP/1.1-клієнт, написаний з нуля, він не використовує http.Agent і http.request. Тому налаштування http.globalAgent на fetch не впливають.

Таймаути: AbortSignal.timeout

fetch не має опції timeout. Правильний спосіб — сигнал скасування. Реальний запуск:

timeout-demo.mjs (фрагмент) і вивід
try {
  await fetch(`${base}/slow`, { signal: AbortSignal.timeout(500) }); // сервер відповідає за 2 с
} catch (e) {
  console.log('slow:', e.name, '-', e.message);
}
// slow: TimeoutError - The operation was aborted due to timeout
  • AbortSignal.timeout(ms) кидає TimeoutError, а ручний controller.abort() — AbortError. Розрізняйте їх у метриках: це різні причини.
  • AbortSignal.any([userSignal, AbortSignal.timeout(2000)]) — скасувати, якщо клієнт пішов або минув дедлайн. Корисно прокидати req-скасування вниз: якщо користувач закрив вкладку, нема сенсу чекати downstream.
  • Таймаут має покривати і читання тіла: сигнал діє, поки ви читаєте res.body, — тому await res.json() також може кинути TimeoutError.
  • fetch не кидає на 500. Перевіряйте res.ok. І завжди споживайте або скасовуйте тіло (await res.body?.cancel()), інакше з'єднання не повернеться в пул.

07 Стрімінг відповідей

Віддати 2 ГБ CSV, не тримаючи їх у пам'яті, — і не вбити сервер, коли клієнт повільний.

Оскільки res — Writable, будь-який Readable можна «влити» в нього через pipeline, і backpressure спрацює автоматично: якщо клієнт читає повільно, буфер сокета заповнюється, res.write() повертає false, pipeline ставить джерело на паузу. Механіку backpressure розібрано в туторіалі 6.

download.mjs
import http from 'node:http';
import { createReadStream } from 'node:fs';
import { stat } from 'node:fs/promises';
import { pipeline } from 'node:stream/promises';

http.createServer(async (req, res) => {
  try {
    const { size } = await stat('./big.csv');
    res.writeHead(200, { 'content-type': 'text/csv', 'content-length': size });
    // pipeline: backpressure + знищення обох стрімів при помилці/обриві клієнта
    await pipeline(createReadStream('./big.csv'), res);
  } catch (err) {
    if (err.code === 'ERR_STREAM_PREMATURE_CLOSE') return;  // клієнт пішов — це нормально
    if (!res.headersSent) { res.statusCode = 500; res.end(); }
    else res.destroy(err);  // заголовки вже пішли — статус не змінити, рвемо з'єднання
  }
}).listen(3000);
🐛
readStream.pipe(res) замість pipeline — витік дескрипторів: якщо клієнт обірвав з'єднання, .pipe() не закриває джерело, файл лишається відкритим. Після тижня роботи — EMFILE: too many open files.

Інкрементальна відповідь і клієнт, що читає стрім

Сервер пише chunk кожні 100 мс (без content-length → chunked), клієнт читає res.body через for await. Реальний вивід:

timeout-demo.mjs
import http from 'node:http';
import { once } from 'node:events';

const server = http.createServer((req, res) => {
  if (req.url === '/slow') return setTimeout(() => res.end('finally'), 2000);
  if (req.url === '/stream') {
    res.writeHead(200, { 'content-type': 'text/plain' });
    let i = 0;
    const t = setInterval(() => {
      res.write(`chunk ${++i}\n`);
      if (i === 3) { clearInterval(t); res.end(); }
    }, 100);
    req.on('close', () => clearInterval(t)); // клієнт пішов — прибираємо таймер
    return;
  }
  res.end('ok');
});
server.listen(0);
await once(server, 'listening');
const base = `http://localhost:${server.address().port}`;

try {
  await fetch(`${base}/slow`, { signal: AbortSignal.timeout(500) });
} catch (e) {
  console.log('slow:', e.name, '-', e.message);
}

const res = await fetch(`${base}/stream`);
const t0 = Date.now();
for await (const chunk of res.body) {
  console.log(`+${Math.round((Date.now() - t0) / 100) * 100}ms`, JSON.stringify(Buffer.from(chunk).toString()));
}
server.closeAllConnections();
server.close();
terminal
slow: TimeoutError - The operation was aborted due to timeout

Зверніть увагу на req.on('close', ...): коли клієнт іде, треба зупиняти генерацію (таймери, курсори БД), інакше сервер продовжує працювати «в порожнечу». Це основа для SSE і стрімінгу відповідей LLM — див. туторіал 18.

⚠️
Проксі можуть буферизувати стрім: nginx за замовчуванням має proxy_buffering on, і клієнт отримає все одним шматком у кінці. Для SSE — заголовок X-Accel-Buffering: no або proxy_buffering off на локації. Компресія теж буферизує — див. розділ 12.

08 HTTPS і TLS: що треба знати бекендеру

Зазвичай TLS термінується на LB, але всередині кластерів (mTLS, сервіс-меш) і в клієнтах — він ваш.

https-server.mjs
import https from 'node:https';
import { readFileSync } from 'node:fs';

https.createServer({
  key: readFileSync('./certs/server.key'),
  cert: readFileSync('./certs/server.crt'),   // ланцюжок: leaf + intermediate
  minVersion: 'TLSv1.2',
  // mTLS: вимагати сертифікат клієнта, підписаний нашим CA
  ca: readFileSync('./certs/internal-ca.crt'),
  requestCert: true,
  rejectUnauthorized: true,
}, (req, res) => {
  const peer = req.socket.getPeerCertificate();
  res.end(`hello, ${peer.subject?.CN}\n`);
}).listen(8443);
  • TLS-криптографія — CPU-робота в головному потоці (OpenSSL викликається синхронно з event loop). Handshake з RSA-ключем помітно дорожчий за ECDSA. Тому TLS часто термінують на LB/ingress, а Node слухає plain HTTP у приватній мережі.
  • Keep-alive ще важливіший з TLS: без нього кожен запит платить за handshake. Сесійні тікети / resumption частково рятують.
  • NODE_TLS_REJECT_UNAUTHORIZED=0 — вимикає перевірку сертифікатів для всього процесу. Node друкує попередження. Ніколи у проді; для внутрішнього CA використовуйте NODE_EXTRA_CA_CERTS=/path/ca.pem або (у новіших версіях) --use-system-ca, щоб довіряти системному сховищу сертифікатів.
  • SNI — SNICallback дозволяє віддавати різні сертифікати для різних доменів на одному порту (мультитенантні кастомні домени).
💡
Для локальної розробки з HTTPS найпростіше — mkcert (створює локальний CA і додає його в систему). Самопідписаний сертифікат з openssl req -x509 змусить вимикати перевірку, і ця звичка потім просочується в продакшн-код.

09 HTTP/2 у Node: мультиплексування і коли воно справді потрібне

HTTP/2 вирішує head-of-line blocking на рівні HTTP, але не TCP — і для API за LB часто нічого не дає.

h2-server.mjs
import http2 from 'node:http2';
import { readFileSync } from 'node:fs';

// Браузери підтримують HTTP/2 лише поверх TLS (h2); allowHTTP1 — fallback через ALPN
const server = http2.createSecureServer({
  key: readFileSync('key.pem'), cert: readFileSync('cert.pem'), allowHTTP1: true,
});

// Core API: подія 'stream' замість 'request'
server.on('stream', (stream, headers) => {
  stream.respond({ ':status': 200, 'content-type': 'application/json' });
  stream.end(JSON.stringify({ path: headers[':path'] }));
});
server.listen(8443);
  • Є також Compatibility API (server.on('request', (req, res) => ...)) — майже як http, тому Fastify вміє http2: true. Express 4 офіційно HTTP/2 не підтримував.
  • Псевдозаголовки :method, :path, :authority, :status замість стартового рядка; заголовка Connection і Transfer-Encoding немає.
  • Server Push фактично мертвий — Chrome його вимкнув. Не будуйте на ньому архітектуру.
  • Як клієнт HTTP/2 потрібен для gRPC (@grpc/grpc-js працює поверх node:http2) і APNs. Undici теж уміє HTTP/2 (опція allowH2).
💼
На співбесіді запитають так «Чи варто вмикати HTTP/2 у Node-сервісі за ALB?» — Зазвичай ні: LB термінує HTTP/2 від браузера і ходить до таргетів по HTTP/1.1 з keep-alive-пулом. HTTP/2 до бекенду має сенс для gRPC або коли клієнт довгоживучий і робить багато паралельних запитів. Мінус — одне довге з'єднання «прилипає» до одного інстансу, балансування стає нерівномірним.

10 net і dgram: TCP і UDP без HTTP

Під кожним HTTP-сервером — net.Server. Коли пишете протокол (Redis-клієнт, власний бінарний обмін) — працюєте саме з ним.

net-demo.mjs
import net from 'node:net';
import dgram from 'node:dgram';
import { once } from 'node:events';

// TCP: потік байтів, межі повідомлень не зберігаються
const tcp = net.createServer((socket) => {
  socket.setEncoding('utf8');
  socket.on('data', (data) => socket.write(`echo:${data}`));
});
tcp.listen(0);
await once(tcp, 'listening');
const client = net.connect(tcp.address().port);
client.setEncoding('utf8');
client.write('a');
client.write('b');
client.write('c');
const [reply] = await once(client, 'data');
console.log('tcp reply:', JSON.stringify(reply));
client.end();
tcp.close();

// UDP: окремі датаграми, межі збережені, доставка не гарантована
const udp = dgram.createSocket('udp4');
udp.bind(0, '127.0.0.1');
await once(udp, 'listening');
const got = [];
udp.on('message', (msg, rinfo) => {
  got.push(msg.toString());
  if (got.length === 3) { console.log('udp got:', got); udp.close(); }
});
const sender = dgram.createSocket('udp4');
for (const m of ['a', 'b', 'c']) sender.send(m, udp.address().port, '127.0.0.1');
setTimeout(() => sender.close(), 100);
terminal (типовий вивід)
tcp reply: "echo:abc"
udp got: [ 'a', 'b', 'c' ]

Три client.write() прийшли на сервер одним 'data'-подією "abc". Це не баг — TCP це потік байтів, а не повідомлень: ядро може склеїти кілька записів (алгоритм Нейгла, буферизація) або розрізати один запис на кілька chunk-ів. На localhost найчастіше буде саме склеювання, але це не гарантовано — тому будь-який протокол поверх TCP потребує framing: роздільник (\n у RESP/SMTP), префікс довжини (Postgres wire protocol, gRPC) або фіксований розмір.

Корисні дрібниці net.Socket

  • socket.setNoDelay(true) — вимкнути Нейгла для інтерактивних протоколів (HTTP-сервер Node робить це сам за замовчуванням — опція noDelay).
  • socket.setKeepAlive(true, 30_000) — TCP keepalive (проби ядра на мертві з'єднання). Не плутати з HTTP keep-alive (перевикористання з'єднання для кількох запитів) — це зовсім різні речі з однаковою назвою.
  • allowHalfOpen — чи закривати свою сторону, коли peer надіслав FIN.
  • Unix domain sockets: server.listen('/tmp/app.sock') — швидше за TCP на тій самій машині (nginx → Node).

Кешування DNS у процесі

// undici 7: інтерсептор DNS з кешем (поважає TTL, round-robin по адресах)

// new http.Agent({ keepAlive: true, lookup: cachedLookup })
  • Порядок адрес. З Node 17 lookup повертає адреси в порядку ОС (verbatim), а не «IPv4 першим». Звідси хвиля ECONNREFUSED ::1:5432 після оновлень: localhost → ::1, а Postgres слухає лише IPv4. Лікується 127.0.0.1 замість localhost або dns.setDefaultResultOrder('ipv4first').
  • Happy Eyeballs: з Node 20 net.connect за замовчуванням має autoSelectFamily: true — пробує IPv6 і IPv4 майже паралельно, що прибрало значну частину цих проблем.
  • Кеш DNS треба поважати з TTL: при blue/green-перемиканні через DNS «вічний» кеш тримає старі IP.

12 Проксі, X-Forwarded-For, trust proxy і компресія

За LB req.socket.remoteAddress — це IP балансувальника. Справжній IP клієнта — у заголовку, якому не можна сліпо вірити.

Проксі додає заголовки: X-Forwarded-For: client, proxy1, proxy2 (кожен хоп дописує справа адресу того, хто до нього прийшов), X-Forwarded-Proto: https, X-Forwarded-Host, або стандартизований Forwarded: for=...;proto=... (RFC 7239). Клієнт може сам надіслати X-Forwarded-For: 1.2.3.4, і проксі просто допише справа. Тому ліва частина ланцюжка — під контролем атакуючого.

client-ip.mjs
// Довіряємо рівно N проксі, які ми контролюємо (наприклад, CloudFront + ALB = 2)
function clientIp(req, trustedHops = 1) {
  const xff = (req.headers['x-forwarded-for'] ?? '')
    .split(',').map((s) => s.trim()).filter(Boolean);
  const chain = [...xff, req.socket.remoteAddress]; // останній — безпосередній peer
  // Йдемо справа наліво, пропускаючи trustedHops наших проксі
  return chain[Math.max(0, chain.length - 1 - trustedHops)];
}
// XFF: "6.6.6.6, 203.0.113.7", peer = ALB (10.0.0.5), trustedHops = 1
// chain = [6.6.6.6, 203.0.113.7, 10.0.0.5] → 203.0.113.7  (6.6.6.6 — підробка клієнта)

Express робить те саме через app.set('trust proxy', 1) (кількість хопів, CIDR-и або функція) — тоді req.ip, req.protocol і req.secure беруться із заголовків. Fastify — trustProxy в опціях. Наслідки помилки: trust proxy: true («довіряти всьому») + rate limiter по req.ip = атакуючий обходить ліміт, міняючи заголовок на кожному запиті. Детальніше — у туторіалі 14.

gzip-stream.mjs
import zlib from 'node:zlib';
import { pipeline } from 'node:stream';

function sendCompressed(req, res, readable) {
  const accepts = req.headers['accept-encoding'] ?? '';
  res.setHeader('vary', 'accept-encoding');           // для CDN/кешів
  if (!/\bgzip\b/.test(accepts)) return pipeline(readable, res, () => {});
  res.setHeader('content-encoding', 'gzip');          // content-length тепер невідомий → chunked
  pipeline(readable, zlib.createGzip({ level: 6 }), res, (err) => {
    if (err) res.destroy(err);
  });
}

13 Graceful shutdown: як не втрачати запити при деплої

Кожен rolling deploy — це SIGTERM. Від того, як ви його обробите, залежить, чи бачать користувачі 502.

Kubernetes/ECS/Fly надсилають SIGTERM, чекають grace period (у k8s за замовчуванням 30 с) і потім SIGKILL. Ваше завдання за цей час: перестати приймати нові з'єднання, дочекатися in-flight запитів, закрити idle keep-alive сокети, закрити пули БД і вийти.

МетодЩо робить
server.close(cb)перестає приймати нові з'єднання; cb — коли закриються всі існуючі. З Node 19 також закриває idle-з'єднання
server.closeIdleConnections()закрити сокети, на яких зараз немає запиту (keep-alive idle)
server.closeAllConnections()жорстко закрити все, включно з активними запитами — останній крок за таймаутом

Пастка, знайдена експериментом: keep-alive сокет «переживає» close

Перша версія демо: запит /in-flight обробляється 300 мс, на 100-й мс приходить SIGTERM, ми робимо server.close() + closeIdleConnections(). Після відповіді той самий клієнт з keep-alive агентом надсилає /late. Реальний вивід:

Сервер «закритий», але прийняв і обробив новий запит — бо той прийшов по вже відкритому keep-alive сокету. closeIdleConnections() спрацював у момент, коли сокет був активний, а після відповіді сокет знову став idle і продовжив жити. Колбек close спрацював лише через 5 с на страховому таймері. У проді з LB, що тримає пул, це означає: процес може не завершитися до SIGKILL, а запити, що прийшли в останню мить, обірвуться.

Виправлення: під час shutdown додавати до кожної відповіді Connection: close — тоді Node закриє сокет одразу після відповіді, а клієнт знатиме, що його не можна перевикористати.

shutdown-fixed.mjs
import http from 'node:http';
import { once } from 'node:events';

const log = (m) => console.log(`[${String(Date.now() - t0).padStart(4)}ms] ${m}`);
const t0 = Date.now();

let shuttingDown = false;
const server = http.createServer((req, res) => {
  log(`start ${req.url}`);
  setTimeout(() => {
    if (shuttingDown) res.setHeader('connection', 'close'); // FIX
    res.end('done'); log(`finish ${req.url}`); }, 300);
});
server.listen(0);
await once(server, 'listening');
const { port } = server.address();

process.on('SIGTERM', () => {
  if (shuttingDown) return;
  shuttingDown = true;
  log('SIGTERM: stop accepting, drain in-flight');
  server.close(() => { log('all connections closed'); /* у проді тут process.exit(0) */ });
  server.closeIdleConnections();            // idle keep-alive сокети — одразу
  setTimeout(() => {                         // страховка, якщо щось зависло
    log('force close'); server.closeAllConnections();
  }, 5000).unref();
});

const agent = new http.Agent({ keepAlive: true });
const req = (path) => new Promise((resolve) => {
  http.get({ port, path, agent }, (res) => {
    let b = ''; res.on('data', (c) => (b += c)); res.on('end', () => resolve(`${res.statusCode} ${b}`));
  }).on('error', (e) => resolve(`error ${e.code}`));
});

const inflight = req('/in-flight');
setTimeout(() => process.kill(process.pid, 'SIGTERM'), 100);
log(`client got: ${await inflight}`);
await new Promise((r) => setTimeout(r, 50));
log(`new request after close: ${await req('/late')}`);

  • Затримка перед close. Видалення пода з Endpoints у k8s і SIGTERM відбуваються паралельно; LB може ще кілька секунд слати нові з'єднання. Тому спершу віддаємо 503 на readiness і чекаємо (або preStop: sleep 5).

14 Каверзні питання співбесіди

Питання, на яких видно різницю між «писав на Express» і «розумію, як працює HTTP у Node».

БазаЧому req — це стрім і що з цього випливає?
IncomingMessage — Readable: заголовки розібрані до виклику handler-а, а тіло надходить chunk-ами. Наслідки: тіло треба явно прочитати (або відкинути), обмежувати його розмір, а backpressure зупиняє клієнта, якщо ви не читаєте. Body-parser-и — це просто «прочитати стрім до кінця з лімітом і розпарсити».
ПасткаМи бачимо рідкісні 502 від ALB, у логах Node — нічого. Причина?
Найімовірніше, keepAliveTimeout Node (5 с) менший за idle timeout LB (60 с): Node закриває idle-сокет, а LB саме в цей момент шле туди запит і отримує RST. Фікс: keepAliveTimeout = 65_000, headersTimeout = 66_000. Друга причина — відсутність graceful shutdown при деплоях.
БазаЧим HTTP keep-alive відрізняється від TCP keepalive?
HTTP keep-alive — перевикористання одного з'єднання для кількох запитів (пул в Agent-і, keepAliveTimeout). TCP keepalive — проби рівня ядра для виявлення мертвого peer-а на тихому з'єднанні (socket.setKeepAlive). Назва одна, механізми різні.
ПасткаМи налаштували http.globalAgent.maxSockets = 50, а fetch все одно відкриває сотні з'єднань. Чому?
Глобальний fetch реалізований undici, який не використовує http.Agent. Налаштовувати треба undici: setGlobalDispatcher(new Agent({ connections: 50 })) або передавати dispatcher у виклик.
ПасткаЧому HTTP-клієнт «зависає» на 6-му запиті при maxSockets: 5?
Попередні відповіді не спожиті: поки тіло не прочитане (res.resume(), await res.text(), body.dump()), сокет вважається зайнятим і не повертається в пул. Шостий запит назавжди стоїть у черзі Agent-а.
ПасткаМережевий I/O в Node не використовує thread pool. Чи все одно HTTP-запит може в нього впертися?
Так — через DNS. dns.lookup (за замовчуванням у http, net, fetch) викликає блокуючий getaddrinfo у пулі з 4 потоків. Повільний DNS + багато нових з'єднань = черга в пулі, яка гальмує ще й fs, crypto, zlib. dns.resolve* працює через c-ares без пулу, але ігнорує /etc/hosts.
БазаЯк правильно зробити таймаут для fetch?
fetch(url, { signal: AbortSignal.timeout(3000) }); кидає TimeoutError. Комбінувати з іншим сигналом — AbortSignal.any([...]). Таймаут діє і на читання тіла. Додатково на рівні undici-Agent: connectTimeout, headersTimeout, bodyTimeout.
ПасткаКлієнт тричі викликав socket.write(), а сервер отримав одну подію 'data'. Баг?
Ні. TCP — потік байтів без меж повідомлень; записи можуть склеюватися або розрізатися. Будь-який протокол поверх TCP потребує framing-у (роздільник, префікс довжини). UDP межі зберігає, але не гарантує доставку.
ПасткаЩо не так з app.set('trust proxy', true) і rate limiting по IP?
true означає «довіряти будь-якому X-Forwarded-For», і req.ip стає найлівішою адресою — яку контролює клієнт. Атакуючий підставляє випадковий IP у кожен запит і обходить ліміт. Треба вказати точну кількість своїх проксі або їхні CIDR-и.
БазаЩо дає HTTP/2 і чи вирішує він head-of-line blocking?
Мультиплексування потоків в одному з'єднанні, стиснення заголовків (HPACK), двонаправлені стріми. HOL blocking прибирається на рівні HTTP, але не на рівні TCP: втрата пакета затримує всі стріми. Повністю — тільки HTTP/3 (QUIC поверх UDP).
ПасткаВикликали server.close(), а процес не завершується ще хвилину. Чому?
close() чекає закриття всіх з'єднань. Keep-alive сокети від LB або клієнтів можуть продовжувати приносити нові запити (ми бачили це в демо). Ліки: closeIdleConnections(), Connection: close у відповідях під час shutdown, страховий closeAllConnections() за таймером; також перевірити інші ref-нуті хендли (таймери, пули БД).
БазаЯк віддати великий файл і чому pipeline, а не .pipe()?
await pipeline(createReadStream(path), res) — backpressure автоматично, і при обриві клієнта або помилці обидва стріми знищуються. .pipe() не пропагує помилки й не закриває джерело, коли закрився приймач → витік файлових дескрипторів.
ПасткаПісля оновлення Node підключення до localhost:5432 почало падати з ECONNREFUSED ::1. Що сталося?
З Node 17 dns.lookup повертає адреси в порядку ОС (verbatim), і localhost резолвиться в ::1 першим, а БД слухає лише IPv4. Рішення: 127.0.0.1, dns.setDefaultResultOrder('ipv4first') або змусити сервіс слухати і IPv6. Happy Eyeballs (autoSelectFamily, дефолт з Node 20) частково це пом'якшує.

16 Як запам'ятати

Асоціації, які спливають у голові, коли на співбесіді питають про мережу в Node.

1
req / res
req — Readable з уже розібраними заголовками; res — Writable, перший write фіксує статус.
Асоціація: лист у конверті — адресу (заголовки) прочитали одразу, а сам лист (тіло) ще треба розгорнути.
2
http.Agent
Пул сокетів на host:port: sockets, freeSockets, черга requests, ліміт maxSockets.
Асоціація: стоянка таксі — машини чекають пасажирів замість того, щоб щоразу їхати з гаража.
3
502 за LB
Node закриває idle-сокет раніше, ніж LB; запит і FIN розминаються → RST → 502.
Асоціація: хто йде з вечірки першим, той має попрощатися — бекенд має «сидіти» довше за проксі.
4
fetch = undici
Вбудований fetch не використовує http.Agent; пул налаштовується через dispatcher.
Асоціація: undici — «одинадцять» італійською: HTTP/1.1, окрема команда, свої правила.
5
AbortSignal.timeout
Єдиний правильний таймаут для fetch; кидає TimeoutError і діє на читання тіла.
Асоціація: пісочний годинник на столі — коли пісок висипався, розмову обривають.
6
dns.lookup
getaddrinfo у libuv thread pool, бачить /etc/hosts; resolve — c-ares по мережі.
Асоціація: lookup питає сусіда (ОС), resolve дзвонить у довідкову (DNS-сервер).
7
TCP — потік байтів
Межі write-ів не зберігаються; протоколу потрібен framing.
Асоціація: вода в трубі — три склянки, вилиті у воронку, на виході не розрізнити.
8
HTTP/2
Багато потоків в одному TCP; немає HOL на рівні HTTP, але є на рівні TCP.
Асоціація: багатосмугова дорога в одному тунелі — аварія в тунелі зупиняє всі смуги.
9
X-Forwarded-For
Ланцюжок IP; довіряти лише правій частині, доданій вашими проксі.
Асоціація: підписи в листі-естафеті — перші можна підробити, останні ставили ваші люди.
10
Graceful shutdown
Зняти з ротації, close + Connection: close, дренаж, force за таймером.
Асоціація: кафе перед закриттям — вивіску «зачинено» повісили, але тих, хто вже їсть, не виганяють.
