01 Навіщо в Node дві модульні системи

Історична довідка, без якої незрозуміло, чому interop такий кострубатий.

У 2009 році в JavaScript не було модулів. Node взяв специфікацію CommonJS (спільнота, що намагалась стандартизувати серверний JS) і реалізував її: require() — звичайна функція, що синхронно читає файл з диска, виконує його і повертає module.exports. На сервері синхронне читання — нормально: файли локальні, а завантаження відбувається при старті.

У 2015 році ES2015 стандартизував ES Modules — import/export, розраховані і на браузер, де модулі вантажаться з мережі, тобто асинхронно. Звідси ключова відмінність дизайну: ESM — статичний (граф залежностей відомий до виконання) і асинхронний за природою; CJS — динамічний і синхронний. Node підтримує ESM стабільно з v12/v14, і з того часу екосистема живе у перехідному періоді.

02 CommonJS: module wrapper і пастка exports

Звідки в CJS-файлі беруться require, module і __dirname, якщо їх ніхто не оголошував.

Перед виконанням Node загортає код кожного CJS-файлу у функцію. Звідси п'ять "глобальних" змінних, які насправді — параметри; звідси ж і локальна область видимості файлу (ваші const не потрапляють у globalThis).

wrapper.cjs
console.log(arguments.length);                 // 5 — так, у файлі є arguments!
console.log(require('node:module').wrapper);
// [ '(function (exports, require, module, __filename, __dirname) { ', '\n});' ]
console.log(this === module.exports, exports === module.exports);   // true true
ПараметрЩо це
exportsПосилання на той самий об'єкт, що й module.exports на старті. Скорочення.
requireФункція, прив'язана до цього модуля (резолвить шляхи відносно нього). Має .resolve, .cache, .main.
moduleОб'єкт Module: exports, id, filename, loaded, children, paths.
__filenameАбсолютний шлях до файлу.
__dirnameДиректорія файлу.

Пастка: exports = …

require() повертає module.exports, а не exports. Присвоєння exports = {...} лише перенаправляє локальну змінну-параметр — зв'язок з module.exports рветься.

Задача 1ЛегкоЩо експортує модуль
lib.js
exports.a = 1;
exports = { b: 2 };          // перевизначили ЛОКАЛЬНУ змінну
module.exports.c = 3;

// main.js
console.log(require('./lib'));
{ a: 1, c: 3 }

exports.a мутує спільний об'єкт → є. exports = {b} — новий об'єкт, про який require не знає → b втрачено. module.exports.c — знову спільний об'єкт. Правило: або лише exports.x = …, або один раз module.exports = … — і не змішувати.

what-else-can-require.js
const cfg = require('./config.json');   // JSON парситься і кешується (той самий об'єкт для всіх!)
const addon = require('./build/Release/addon.node');   // нативний аддон (C++/N-API), через dlopen
const os = require('node:os');           // core module; префікс node: — явний і не підміниш через node_modules

require.main === module;                 // true, якщо файл запущено напряму (аналог if __name__ == '__main__')

03 require: кеш і singleton-и

Модуль виконується один раз — на цьому тримаються пули з'єднань, конфіги й, на жаль, частина багів у тестах.

Задача 2СередньоСкільки разів виконається модуль
cache/main.js
// counter.js:
//   console.log('counter.js evaluated');
//   let n = 0;
//   module.exports = { inc: () => ++n };

const a = require('./counter');
const b = require('./counter.js');
a.inc(); a.inc();
console.log(b.inc(), a === b);

delete require.cache[require.resolve('./counter')];
const c = require('./counter');
console.log(c.inc(), c === a);
console.log(Object.keys(require.cache).map((p) => p.split('/').pop()));
counter.js evaluated 3 true counter.js evaluated 1 false [ 'main.js', 'counter.js' ]

Ключ кешу — абсолютний резолвлений шлях, тож './counter' і './counter.js' — один запис. Модуль виконано один раз, a і b — той самий об'єкт. Після видалення з require.cache модуль виконується заново і створює новий стан — а старі посилання (a) живуть далі. Так працюють "hot reload"-хаки і так народжуються два "singleton-и" одночасно.

  • Singleton через кеш — це module.exports = new Pool(). Працює, поки шлях резолвиться в один файл. Дві копії пакета в node_modules (різні версії, симлінки в монорепо, дублікат у npm link) = два singleton-и. Класичний симптом — "instanceof повертає false" або "два екземпляри React/GraphQL".
  • Регістр важливий: на macOS (case-insensitive FS) require('./User') і require('./user') дадуть два записи в кеші одного файлу, а на Linux у CI — помилку "module not found".
  • У тестах (Jest) кожен тестовий файл має свій реєстр модулів — тому jest.resetModules(), і тому singleton-и між файлами тестів не діляться.
  • ESM теж кешує (за URL), але кеш недоступний для видалення — для перезавантаження використовують query: import(`./mod.js?v=${Date.now()}`) (з витоком пам'яті).

04 Алгоритм резолюції require

Що саме робить Node, коли бачить require('x') — і чому require.resolve корисний при дебазі.

resolve-debug.js
require.resolve('dual');                 // абсолютний шлях, БЕЗ виконання модуля
require.resolve('./config', { paths: [__dirname + '/env'] });
require.resolve.paths('lodash');
// [ '/project/src/node_modules', '/project/node_modules', '/node_modules', ... ]

// ESM-аналог (синхронний у сучасних версіях):
import.meta.resolve('dual');             // 'file:///project/node_modules/dual/dist/index.mjs'
  • Підйом по node_modules — основа hoisting-у npm і причина "phantom dependencies" (див. туторіал 5): ви можете require пакет, якого немає у вашому package.json, бо його підняв хтось інший.
  • Симлінки: за замовчуванням Node резолвить реальний шлях (realpath). Тому пакет із pnpm-store бачить свої залежності, а не ваші. Прапорець --preserve-symlinks змінює це (рідко потрібен).
  • ESM не використовує ці "розумні" здогадки для відносних шляхів: ні автододавання .js, ні index.js — тільки точний шлях (ERR_MODULE_NOT_FOUND / ERR_UNSUPPORTED_DIR_IMPORT). Bare specifiers ESM резолвить через той самий підйом по node_modules + exports.

05 ESM: статичні import/export і live bindings

Головна семантична різниця між системами — не синтаксис, а що саме ви отримуєте при імпорті.

Статичність

  • import/export — лише на верхньому рівні, специфікатор — рядковий літерал. Не можна if (x) import … — для умовного завантаження є import().
  • Import-и "піднімаються" (hoisting): усі залежності завантажуються і виконуються до першого рядка тіла модуля, незалежно від того, де в файлі написано import.
  • Завдяки статичності помилка "немає такого експорту" — це SyntaxError на етапі лінкування, ще до виконання будь-якого коду.
Задача 3ЛегкоПорядок виконання ESM
order/main.mjs
// a.mjs:  console.log('a body'); export const a = 1;
// b.mjs:  import './a.mjs'; console.log('b body');
// c.mjs:  console.log('c body'); export const c = 3;
console.log('main body (hoisting: imports run first)');
import './b.mjs';
import './a.mjs';
const lazy = await import('./c.mjs');
console.log('lazy', lazy.c);
a body b body main body (hoisting: imports run first) c body lazy 3

Обхід графа — post-order DFS: спочатку залежності b (тобто a), потім b, потім сам main. a.mjs імпортується двічі, але виконується один раз. Хоча console.log стоїть вище за import-и, він виконується після них. Динамічний import() — звичайний вираз: виконується там, де написаний, і повертає Promise простору імен.

Live bindings vs копії значень

live/main.mjs
// counter.mjs:  export let count = 0;  export function inc() { count++; }
import { count, inc } from './counter.mjs';
import * as ns from './counter.mjs';
console.log(count);            // 0
inc(); inc();
console.log(count, ns.count);  // 2 2  ← імпорт "бачить" поточне значення змінної модуля
try { count = 10; } catch (e) { console.log(e.constructor.name + ': ' + e.message); }
// TypeError: Assignment to constant variable.   ← імпорт read-only для імпортера
live/main.cjs
// counter.cjs:
//   let count = 0;
//   module.exports = { count, inc() { count++; }, get live() { return count; } };
const { count, inc } = require('./counter.cjs');
const m = require('./counter.cjs');
inc(); inc();
console.log(count, m.count, m.live);   // 0 0 2  ← count скопійовано в момент присвоєння
💼
На співбесіді запитають так "Чим import відрізняється від require, крім синтаксису?" — сильна відповідь: (1) статичний граф і лінкування до виконання → помилки імпорту на старті і tree-shaking; (2) live bindings замість копій; (3) асинхронне фазове завантаження і top-level await; (4) strict mode, this === undefined, обов'язкові розширення; (5) live bindings + TDZ змінюють поведінку циклічних залежностей.

06 ESM: фази завантаження, import.meta, import()

Чому ESM "асинхронний" навіть для локальних файлів, і що дає розділення на фази.

import.meta і заміна __dirname

paths.mjs
console.log(import.meta.url);        // 'file:///project/src/paths.mjs'
console.log(import.meta.filename);   // '/project/src/paths.mjs'   (Node 20.11+)
console.log(import.meta.dirname);    // '/project/src'
console.log(typeof __dirname);       // 'undefined' — у ESM немає wrapper-а

// для старших версій / універсальний код:
import { fileURLToPath } from 'node:url';
import path from 'node:path';
const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

// файл поруч із модулем — URL відносно import.meta.url:
const tpl = await readFile(new URL('./template.html', import.meta.url), 'utf8');

// require у ESM, коли дуже треба (наприклад, для JSON чи CJS-only API):
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const pkg = require('./package.json');

// "чи запущено напряму" (аналог require.main === module):
const isMain = import.meta.filename === process.argv[1];   // Node 24 також має import.meta.main

Динамічний import()

  • Працює і в CJS, і в ESM; повертає Promise<namespace>. Це єдиний спосіб завантажити ESM з CJS у старих Node (до require(esm)).
  • Застосування: lazy-завантаження важких модулів (зменшує cold start у serverless — туторіал 19), плагіни за шляхом з конфігу, умовні полiфіли.
  • Специфікатор — будь-який вираз, тому бандлери/статичний аналіз його не бачать повністю.
  • Default-експорт — у .default: const { default: express } = await import('express').

07 Як Node визначає тип модуля

Один і той самий .js може бути CJS чи ESM — залежно від контексту. Порядок правил.

#ПравилоРезультат
1Розширення .mjs / .cjsзавжди ESM / завжди CJS — перемагає все
2.js + найближчий package.json має "type": "module"ESM
3.js + "type": "commonjs"CJS (явно; рекомендовано вказувати)
4.js без поля typeCJS, але якщо парсинг падає через ESM-синтаксис (import/export, import.meta, top-level await) — Node перезапускає як ESM (syntax detection, без прапорця з Node 22.7 / 20.19)
5--eval, STDIN--input-type=module|commonjs
6.ts/.mts/.cts (type stripping)ті самі правила, що й для .js/.mjs/.cjs
detect.js (немає package.json з "type")
import os from 'node:os';
console.log('detected esm', typeof require);   // detected esm undefined

// $ echo 'console.log(typeof require, typeof import.meta)' | node --input-type=module
// undefined object
⚠️
Syntax detection — зручність для скриптів, не для проєктів: Node спершу пробує CJS-парсинг (зайва робота на старті), а в старих версіях друкує warning про "typeless package.json". Завжди вказуйте "type" у package.json — і для застосунку, і для бібліотеки. Поле type діє на всі .js у піддереві до наступного package.json — вкладений {"type":"commonjs"} у dist/cjs/ — стандартний трюк dual-пакетів.

08 Interop: CJS ↔ ESM, require(esm), createRequire

Хто кого може імпортувати і що при цьому губиться.

ESM імпортує CJS — завжди можна

  • Default import = весь module.exports. Працює завжди.
  • Named imports — лише ті, які Node "вгадав" статичним аналізом коду через cjs-module-lexer (без виконання!). Розпізнаються exports.x = …, module.exports.x = …, Object.defineProperty(exports, 'x', …), module.exports = { a, b: c } (лише shorthand / ідентифікатори), а також реекспорт module.exports = require('./x'). Обчислені ключі, функції-значення в літералі, циклове заповнення — не розпізнаються.
interop/main.mjs
// lib-static.cjs:   exports.add = (a, b) => a + b;  exports.name = 'static';
// lib-literal.cjs:  const mul = …; const version = 1;
//                   module.exports = { mul, version, square: (x) => x * x };
// lib-dynamic.cjs:  const api = {}; for (const k of ['sub', 'div']) api[k] = k; module.exports = api;
// lib-fn.cjs:       module.exports = function greet() {…}; module.exports.helper = () => 'help';

import def1, { add, name } from './lib-static.cjs';
import * as lit from './lib-literal.cjs';
import dyn from './lib-dynamic.cjs';
import * as dynNs from './lib-dynamic.cjs';
import greet, { helper } from './lib-fn.cjs';

console.log(add(1, 2), name, def1);   // 3 static { add: [Function (anonymous)], name: 'static' }
console.log(Object.keys(lit));        // [ 'default', 'module.exports', 'mul', 'version' ]  ← square НЕ знайдено
console.log(dyn, Object.keys(dynNs)); // { sub: 'sub', div: 'div' } [ 'default', 'module.exports' ]
console.log(greet(), helper());       // hi help

// import { sub } from './lib-dynamic.cjs'  →
// SyntaxError: Named export 'sub' not found. The requested module './lib-dynamic.cjs'
// is a CommonJS module, which may not support all module.exports as named exports.

Ключ 'module.exports' у namespace — новація свіжих версій Node: дає явний доступ до оригінального module.exports. Named-експорти CJS — це знімок на момент завершення виконання модуля, без live binding.

CJS імпортує ESM — require(esm)

Історично — заборонено (ERR_REQUIRE_ESM): require синхронний, а ESM може мати top-level await. Рішення в Node 22.12+ / 20.19+ (без прапорця): require() може синхронно завантажити ESM-граф, якщо в ньому немає top-level await.

interop/req.cjs
// esm-lib.mjs:        export default function hello() {…}; export const answer = 42;
// esm-cjsdefault.mjs: export default class Logger {}; export { Logger as 'module.exports' };
// esm-tla.mjs:        await Promise.resolve(); export const x = 1;

const ns = require('./esm-lib.mjs');
console.log(ns, ns.default(), ns.answer);
// [Module: null prototype] { __esModule: true, answer: 42, default: [Function: hello] } hello 42

console.log(require('./esm-cjsdefault.mjs').name);   // Logger  ← спец-експорт 'module.exports'

try { require('./esm-tla.mjs'); } catch (e) { console.log(e.code); }   // ERR_REQUIRE_ASYNC_MODULE
console.log(process.features.require_module);                            // true
  • require(esm) повертає namespace-об'єкт, а не default. Щоб CJS-споживач отримав саме клас/функцію, ESM-модуль може експортувати ім'я-рядок 'module.exports'.
  • __esModule: true додається для сумісності з транспільованим кодом (Babel/TS-interop).
  • Top-level await будь-де в графі → ERR_REQUIRE_ASYNC_MODULE. Тому бібліотекам: жодного TLA у публічних модулях.
  • Для старих Node: const { x } = await import('esm-only-pkg') усередині async-функції.

createRequire

Створює CJS-require, прив'язаний до довільного шляху/URL. Потрібен у ESM для: JSON без import attributes в старих версіях, require.resolve, завантаження CJS-only API з побічними ефектами, нативних .node аддонів.

09 package.json "exports" та "imports"

Публічний контракт пакета: що можна імпортувати, у якому форматі і під якими умовами.

"exports" — інкапсуляція і умовні входи

node_modules/dual/package.json
{
  "name": "dual",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs",
      "default": "./dist/index.js"
    },
    "./utils": "./dist/utils.js",
    "./features/*": "./dist/features/*.js",
    "./internal/*": null,
    "./package.json": "./package.json"
  },
  "main": "./dist/index.cjs"
}
  • Інкапсуляція: щойно є exports, будь-який шлях, не перелічений там, — ERR_PACKAGE_PATH_NOT_EXPORTED. require('dual/dist/secret.cjs') більше не працює. Додавання exports у існуючий пакет — breaking change (major).
  • Умови перевіряються по порядку, бере першу, що збіглася. Тому "types" — першим (для TypeScript), "default" — останнім.
  • Вбудовані умови Node: node, import, require, module-sync, default. Свої — через node --conditions=development (-C). Бандлери/рантайми додають browser, worker, deno, bun, react-server.
  • Subpath patterns "./features/*" і null для явного блокування піддерева.
  • "main" ігнорується сучасним Node, якщо є exports, але лишається для старих інструментів.
  • Пакет може імпортувати сам себе за власним ім'ям (self-reference), якщо має exports.

"imports" — приватні аліаси з #

package.json (застосунок)
{
  "name": "app",
  "type": "module",
  "imports": {
    "#internal/*": "./src/internal/*.js",
    "#config": { "development": "./src/config.dev.js", "default": "./src/config.prod.js" }
  }
}
pkgdemo/src/main.js
import { Money as EsmMoney, flavor } from 'dual';
import { createRequire } from 'node:module';
import { db } from '#internal/db';         // замість '../../../internal/db.js'
import config from '#config';
const require = createRequire(import.meta.url);
const { Money: CjsMoney, flavor: f2 } = require('dual');

console.log(flavor, f2, EsmMoney === CjsMoney);       // esm cjs false   ← див. розділ 10!
console.log(new EsmMoney() instanceof CjsMoney);      // false
console.log(require('dual/utils').u, db(), config);   // utils db helper prod config
try { require('dual/dist/secret.cjs'); } catch (e) { console.log(e.code); }   // ERR_PACKAGE_PATH_NOT_EXPORTED

// $ node --conditions=development src/main.js   → ... db helper dev config

#-аліаси — нативна заміна paths у tsconfig / module-alias: працюють у рантаймі без бандлера, діють лише всередині пакета, підтримують умови. TypeScript розуміє їх з moduleResolution: "nodenext"/"bundler".

10 Dual package hazard

Коли пакет публікує і ESM, і CJS версії, у процесі можуть опинитися обидві — з двома різними станами.

Подивіться на вивід вище: EsmMoney === CjsMoney → false. Застосунок імпортує dual через import, а якась його залежність — через require. Node завантажує два різні файли, два різні класи, два кеші. Наслідки:

  • instanceof ламається (помилки, класи Decimal/ObjectId, GraphQLSchema "from another realm").
  • Два singleton-и: два реєстри плагінів, два пули, конфігурація застосована до однієї копії, а використовується інша.
  • Подвоєний розмір бандла у фронтенді.
🔀 Вузол вибору: як публікувати бібліотеку
СтратегіяПлюсиМінуси
ESM-only (+ require(esm) для CJS у Node 20.19+/22.12+) ✅одна копія коду, немає hazard, простий buildстарі Node/інструменти не завантажать; жодного TLA
CJS-onlyпрацює всюди (ESM імпортує CJS)гірший tree-shaking, named exports залежать від lexer-а
CJS-ядро + тонка ESM-обгортка (export const { a, b } = cjs)стан лише в одній копії — hazard зникаєESM-споживачі все одно тягнуть CJS
Повний dual build (tsup/unbuild) з import/require"нативно" для обохhazard, якщо є стан або класи; подвійні .d.ts (.d.mts/.d.cts)

Коли що: для нових бібліотек у 2025–2026 — ESM-only або dual без внутрішнього стану. Якщо пакет має singleton-и чи класи для instanceof — ізолюйте стан у один формат (wrapper-підхід) або використовуйте умову module-sync, щоб і import, і require отримали один ESM-файл. Перевіряйте пакет інструментами publint і @arethetypeswrong/cli.

11 Циклічні залежності: CJS vs ESM

Обидві системи "дозволяють" цикли, але ламаються по-різному: CJS — тихо, ESM — голосно.

Задача 4СкладноЦикл у CommonJS
circ-cjs/a.js
console.log('a: start');
exports.fromA = 'A1';
const b = require('./b');
console.log('a: b is', b);
exports.fromA2 = 'A2';

// circ-cjs/b.js
console.log('b: start');
const a = require('./a');
console.log('b: a is', { ...a });            // partial!
console.log('b: a.fromA2 =', a.fromA2);
setImmediate(() => console.log('b later:', { ...a }));
module.exports = { fromB: 'B' };

// $ node circ-cjs/a.js
a: start b: start b: a is { fromA: 'A1' } b: a.fromA2 = undefined a: b is { fromB: 'B' } b later: { fromA: 'A1', fromA2: 'A2' } (stderr) Warning: Accessing non-existent property 'fromA2' of module exports inside circular dependency

a почав виконуватись і вже лежить у кеші з частково заповненим exports. b робить require('./a') — Node не виконує a вдруге (нескінченна рекурсія), а повертає цей недоробок. Тому fromA2 — undefined, і Node друкує спеціальний warning. Пізніше (після завершення a) той самий об'єкт уже повний — але тільки тому, що a мутував exports. Якби a зробив module.exports = {...}, b назавжди тримав би старий порожній об'єкт.

Задача 5СкладноЦикл у ESM
circ-esm/a.mjs
import { b } from './b.mjs';
console.log('a evaluated, b =', b);
export const a = 'A';
export function hello() { return 'hello from a'; }

// circ-esm/b.mjs
import { a, hello } from './a.mjs';
console.log('b evaluated; hello() =', hello());
try { console.log(a); } catch (e) { console.log(e.constructor.name + ': ' + e.message); }
export const b = 'B';

// $ node circ-esm/a.mjs
b evaluated; hello() = hello from a ReferenceError: Cannot access 'a' before initialization a evaluated, b = B

Post-order: b (залежність entry-модуля) виконується першим, хоча a ще не виконався. Але лінкування вже відбулося: імпорт a прив'язаний до слоту, який ще в TDZ → ReferenceError. Function declarations ініціалізуються на етапі instantiation, тому hello() працює. Після виконання a слот заповнюється — і live binding побачив би 'A'.

Як лікувати цикли

  • Виявляти: madge --circular src/, dpdm, ESLint import/no-cycle (повільний на великих проєктах).
  • Розривати: винести спільне в третій модуль; dependency injection замість прямого імпорту; ліниво — require/import() усередині функції, а не на верхньому рівні.
  • Barrel-файли (index.ts, що реекспортує все) — найчастіше джерело неявних циклів і повільного старту: імпорт однієї утиліти тягне весь пакет.
  • У NestJS цикли між провайдерами лікуються forwardRef() — симптом того самого (туторіал 11).
🧠 Запам'ятай: CJS у циклі віддає "недопечений" exports (тихий undefined), ESM — прив'язаний, але ще не ініціалізований слот (гучний ReferenceError у TDZ).

12 Customization hooks і JSON-імпорти

Як перехопити резолюцію і завантаження модулів — і як імпортувати не-JS файли.

Import attributes

json-import.mjs
import data from './data.json' with { type: 'json' };
console.log(data);                       // { name: 'demo', n: 1 }

try { await import('./data.json'); } catch (e) { console.log(e.code); }
// ERR_IMPORT_ATTRIBUTE_MISSING — без атрибута JSON не імпортується

const cfg = await import('./data.json', { with: { type: 'json' } });   // динамічно; дані в cfg.default

Навіщо атрибут: безпека. Без нього сервер (у браузері) міг би віддати JS замість очікуваного JSON — і той виконався б. Атрибут каже "це має бути JSON, інакше помилка". Старий синтаксис assert { type: 'json' } видалено — у Node 24 це SyntaxError: Unexpected identifier 'assert'. JSON-модуль має лише default-експорт (named — ні).

Module customization hooks

module.register() реєструє асинхронні хуки resolve і load, які виконуються в окремому потоці-завантажувачі; у новіших версіях є і синхронний in-thread варіант module.registerHooks(), що діє також на require. Так працюють TypeScript-лоадери (tsx), мок-бібліотеки, APM-інструментація (OpenTelemetry обгортає модулі при завантаженні), імпорт .yaml/.graphql.

register-hooks.mjs
// node --import ./register-hooks.mjs app.js
import { register } from 'node:module';
register('./yaml-loader.mjs', import.meta.url);

// yaml-loader.mjs
export async function resolve(specifier, context, nextResolve) {
  return nextResolve(specifier, context);          // ланцюжок: можна переписати specifier
}
export async function load(url, context, nextLoad) {
  if (url.endsWith('.yaml')) {
    const { source } = await nextLoad(url, { ...context, format: 'module' });
    const { parse } = await import('yaml');
    return {
      format: 'module',
      shortCircuit: true,
      source: `export default ${JSON.stringify(parse(String(source)))};`,
    };
  }
  return nextLoad(url, context);
}

--import (preload ESM) — сучасний аналог -r/--require для CJS; старий --loader / --experimental-loader вважається застарілим на користь register. Для TypeScript у Node 22.6+/23.6+ часто достатньо вбудованого type stripping — без лоадерів взагалі.

13 Каверзні питання співбесіди

Модулі — улюблена тема для "а що буде, якщо…".

БазаЗвідки в CJS-модулі беруться require, module, exports, __filename, __dirname?
Node загортає код файлу у функцію (function (exports, require, module, __filename, __dirname) { … }) і викликає її. Це параметри, а не глобальні змінні. Звідси ж ізоляція області видимості файлу і this === module.exports.
ПасткаЧому exports = { foo } нічого не експортує?
exports — лише локальне посилання на початковий об'єкт module.exports. Присвоєння перенаправляє локальну змінну; require повертає module.exports, який лишився старим. Треба module.exports = { foo }.
БазаЩо таке live binding?
ESM-імпорт — посилання на змінну (слот) модуля-експортера, а не копія значення. Якщо експортер змінить export let, імпортер побачить нове значення; сам імпортер змінити його не може (TypeError). У CJS деструктуризація з require копіює значення.
ПасткаЧи може require() завантажити ESM-модуль?
У Node 22.12+ / 20.19+ — так, без прапорця, якщо в графі модуля немає top-level await (інакше ERR_REQUIRE_ASYNC_MODULE). Повертається namespace-об'єкт; для "default як module.exports" ESM експортує ім'я 'module.exports'. У старших версіях — ERR_REQUIRE_ESM, вихід — await import().
ПасткаЧому import { foo } from './x.cjs' падає, хоча x.cjs експортує foo?
Named exports з CJS визначаються статично cjs-module-lexer-ом без виконання коду. Якщо foo додано динамічно (цикл, обчислений ключ, Object.assign, значення-вираз у літералі) — lexer його не бачить. Обхід: default import і деструктуризація.
БазаЯк Node вирішує, чи .js — CJS чи ESM?
.mjs/.cjs — завжди однозначно. Для .js — поле "type" найближчого package.json. Без нього — CJS з fallback на ESM, якщо знайдено ESM-синтаксис (syntax detection у Node 22.7+/20.19+). Для eval/stdin — --input-type.
БазаНавіщо поле "exports" у package.json?
(1) Інкапсуляція — неперелічені шляхи недоступні (ERR_PACKAGE_PATH_NOT_EXPORTED), можна рефакторити внутрішню структуру; (2) умовні входи — різні файли для import/require/types/browser/development; (3) subpath patterns. Додати exports у існуючий пакет — major.
ПасткаЩо таке dual package hazard?
Пакет з окремими ESM і CJS файлами може бути завантажений двічі в одному процесі (один споживач робить import, інший — require). Два кеші → два singleton-и, instanceof між копіями false. Рішення: ESM-only, CJS-ядро з ESM-обгорткою, умова module-sync, відсутність стану.
ПасткаЯк поводяться циклічні залежності в CJS і в ESM?
CJS: другий учасник циклу отримує частково заповнений exports першого — тихі undefined (Node друкує warning при доступі до неіснуючої властивості). ESM: імпорти вже прив'язані, але let/const/class ще в TDZ → ReferenceError; function declarations працюють, бо ініціалізуються при instantiation.
БазаЧим замінити __dirname в ESM?
import.meta.dirname / import.meta.filename (Node 20.11+), або path.dirname(fileURLToPath(import.meta.url)). Для файлів поруч — new URL('./file', import.meta.url), який приймають fs-функції.
ПасткаЧому в ESM import './utils' не працює, а в CJS require('./utils') — так?
ESM (за аналогією з браузером, де це URL) не вгадує розширення і не шукає index.js. Потрібно './utils.js' (навіть у TypeScript-коді з moduleResolution: nodenext пишуть .js). Бандлери дозволяють більше — звідси плутанина.
БазаЯк перевантажити модуль без рестарту процесу?
CJS: delete require.cache[require.resolve(p)] — але старі посилання і їхній стан залишаються, легко отримати два "singleton-и". ESM: кеш недоступний, лише import(p + '?v=' + Date.now()) — старі модулі ніколи не звільняються (memory leak). У продакшені — рестарт процесу; у dev — node --watch.

15 Як запам'ятати

Образи, що чіпляються до термінів.

1
Module wrapper
Функція з 5 параметрами, в яку Node загортає кожен CJS-файл.
Асоціація: конверт: усе, що в листі, — всередині; на конверті 5 полів (exports, require, module, filename, dirname).
2
exports vs module.exports
exports — ярлик на module.exports; перевизначення ярлика нічого не змінює.
Асоціація: переклеїти табличку з номером квартири — посилка все одно приїде за старою адресою.
3
require.cache
Мапа "абсолютний шлях → module"; модуль виконується один раз.
Асоціація: бібліотечний формуляр — книгу видали, вдруге не друкують.
4
Live binding
ESM-імпорт — посилання на змінну експортера, а не копія.
Асоціація: вебкамера (ESM) проти фотографії (CJS).
5
3 фази ESM
Construction → Instantiation (link) → Evaluation.
Асоціація: будівництво: завезти матеріали → прокласти проводку → увімкнути світло.
6
cjs-module-lexer
Статичний аналізатор, що вгадує named exports CJS без виконання.
Асоціація: митник, який вирішує за накладною, а не відкриваючи коробку.
7
require(esm)
Синхронне завантаження ESM з CJS у Node 22.12+, якщо немає top-level await.
Асоціація: експрес-доставка — лише для посилок, які не треба "чекати на складі" (TLA).
8
"exports"
Публічне меню пакета: що можна імпортувати і в якому форматі.
Асоціація: меню ресторану — на кухню (dist/internal) не пускають.
9
Dual package hazard
ESM- і CJS-копії одного пакета в процесі — два стани, instanceof false.
Асоціація: близнюки з однаковими іменами в одному класі — оцінки ставлять не тому.
10
Цикл: partial vs TDZ
CJS повертає недозаповнений exports; ESM кидає ReferenceError.
Асоціація: CJS — недопечений торт мовчки на столі; ESM — табличка "ще в духовці, не чіпати".
