01 Що нового порівняно з браузером

Ви вже знаєте call stack і «макро/мікрозадачі» — тепер треба дізнатися, де ця модель у Node ламається.

Базова модель — синхронний код у call stack, черга мікрозадач (проміси) з вищим пріоритетом і черга макрозадач (таймери) — розібрана в JS Doc, туторіал 1. Тут вона лишається правдивою, але в Node з'являються речі, яких у браузері немає:

Термінологія. «Event loop» у Node — це uv_run() з бібліотеки libuv (як шари Node поєднані між собою — у туторіалі 1). «Макрозадача» — неофіційне слово; у Node правильніше казати «колбек фази» (timer callback, I/O callback, immediate, close callback). «Мікрозадачі» — це черга V8 (проміси, queueMicrotask), а nextTick — окрема черга, яку веде сам Node.
🧠 Запам'ятай: у Node не одна черга макрозадач, а шість фаз по колу, і між будь-якими двома колбеками Node спершу вичерпує nextTick, потім мікрозадачі.

02 Шість фаз однієї ітерації

Карта, до якої ви повертатиметеся в кожній задачі на порядок виконання.

Кожна фаза — це черга колбеків певного типу. Входячи у фазу, цикл виконує колбеки з її черги, поки черга не спорожніє або не буде досягнуто системного ліміту, і переходить до наступної. Ваш JavaScript виконується лише в чотирьох фазах: timers, pending (рідко), poll і check, плюс close для подій закриття.

Де виконується мій колбек?

process.nextTick, .then, await, queueMicrotaskжодна — у контрольній точці μ після поточного колбеку
emitter.emit()жодна — синхронно, там, де викликано (розділ 12)
💼
На співбесіді запитають так «Назвіть фази event loop у Node.» Мінімум, який очікують: timers → pending callbacks → idle/prepare → poll → check → close callbacks, і що process.nextTick та проміси не є фазами — вони виконуються між колбеками. Хто додає «poll — єдина фаза, де цикл може блокуватися», той одразу виділяється.

03 Фаза за фазою

Що саме відбувається в кожній фазі і які підводні камені з цим пов'язані.

1. timers

Виконуються колбеки setTimeout/setInterval, чий поріг уже минув. Таймер — це не «виконати рівно через N мс», а «не раніше, ніж через N мс». Якщо поточна ітерація затрималась (довгий колбек, блокуючий poll), таймер спрацює пізніше. Деталі — у розділі 7.

2. pending callbacks

Колбеки I/O, які libuv свідомо відклав на наступну ітерацію, — наприклад, деякі помилки TCP-з'єднання (ECONNREFUSED на частині систем) або колбеки запису, що завершився миттєво. Для прикладного коду ця фаза майже непомітна; важливо лише знати, що вона існує.

3. idle, prepare

Внутрішні хуки libuv. Node використовує idle-handle хитро: коли черга setImmediate непорожня, Node «вмикає» idle-handle — і через це poll-фаза знає, що блокуватися не можна (див. наступний розділ). prepare-handles — внутрішні хуки «перед poll»; сам Node і нативні модулі використовують їх для службових задач. JS-колбеків користувача тут немає.

4. poll

Серце циклу. Дві задачі: (1) обчислити, скільки можна чекати, і заблокуватися в epoll_wait/kevent/GetQueuedCompletionStatusEx; (2) виконати колбеки всіх I/O-подій, що надійшли: дані в сокеті, нове з'єднання, завершена задача thread pool (fs, DNS, crypto). Саме тут виконується обробник вашого HTTP-запиту.

5. check

Колбеки setImmediate. Фаза йде одразу після poll — тому setImmediate, викликаний з I/O-колбека, гарантовано виконається раніше за будь-який таймер. Важливо: виконуються лише ті immediates, що були в черзі на момент входу у фазу; нові, додані під час фази, чекають наступної ітерації (тому рекурсивний setImmediate не блокує цикл — розділ 9).

6. close callbacks

Колбеки закриття handles: uv_close() завжди асинхронний, і його колбек libuv викликає саме тут. Через це, наприклад, подія 'close' сокета після socket.destroy() настає після setImmediate з того самого колбеку, але до таймерів наступної ітерації (задача 15). Не всі події з назвою close живуть тут: server.close(cb) без активних з'єднань емітить 'close' через process.nextTick.

⚠️
Фази — не пріоритети. Поширена помилка — думати, що «timers важливіші за I/O, бо йдуть першими». Порядок фаз — це лише порядок обходу кола. Таймер, що прострочився, поки виконувався I/O-колбек, чекатиме, доки цикл пройде check і close і повернеться в timers.

04 Poll: скільки чекати

Єдине місце, де Node «спить», — і правило, за яким він вирішує, наскільки довго.

Перед входом у poll libuv обчислює timeout для системного виклику очікування (функція uv_backend_timeout). Від нього залежить усе: якщо timeout = 0, poll лише «зазирає» за готовими подіями і йде далі; якщо > 0 — потік засинає в ядрі і не споживає CPU.

Звідси кілька практичних наслідків:

  • HTTP-сервер у простої не споживає CPU: timeout = −1, потік спить у ядрі, поки не прийде з'єднання.
  • Таймер на 100 мс без іншої роботи: poll засинає рівно на ~100 мс, прокидається, цикл іде check → close → timers і виконує колбек.
  • Коли poll прокинувся через I/O, він обробляє всі готові події (з внутрішнім лімітом на кількість за прохід, щоб не «зависнути» назавжди), а потім іде в check — навіть якщо таймер уже прострочився.
  • setImmediate = «не спи»: поки черга immediates непорожня, poll не блокується. Тому setImmediate — правильний інструмент «виконай якомога швидше, але після I/O».

05 process.nextTick і мікрозадачі

Дві черги з різними власниками: nextTick веде Node, проміси — V8. Їхній порядок і є головною пасткою.

Як це реалізовано

Після кожного колбеку, який C++ викликає в JS, Node запускає внутрішню функцію processTicksAndRejections. Спрощено:

lib/internal/process/task_queues.js (спрощено)
function processTicksAndRejections() {
  do {
    let tock;
    while ((tock = queue.shift()) !== null) {   // 1) УСІ nextTick
      tock.callback(...tock.args);
    }
    runMicrotasks();                             // 2) УСІ мікрозадачі V8
  } while (!queue.isEmpty() || processPromiseRejections()); // 3) повтор
}

Звідси три правила, які пояснюють 90% задач:

  1. nextTick раніше за проміси, навіть якщо проміс зарезолвили раніше (задача 2).
  2. nextTick, доданий з мікрозадачі, виконається лише після того, як спорожніє уся черга мікрозадач (задача 17).
  3. Необроблені rejections перевіряються після дренажу обох черг — тому Promise.reject() без .catch «вбиває» процес раніше за будь-який таймер (задача 22).

Node 11: мікрозадачі між окремими колбеками

До Node 11 мікрозадачі виконувались лише між фазами: два setTimeout(…, 0) підряд виконувались один за одним, а проміси з першого — вже після обох. З Node 11 поведінку вирівняли з браузером: контрольна точка — після кожного колбеку setTimeout/setInterval/setImmediate (задачі 8 і 9). Якщо у статті чи на співбесіді ви бачите «відповідь» зі старою поведінкою — це матеріал до 2018 року.

queueMicrotask

queueMicrotask(fn) кладе функцію в ту саму чергу V8, що й .then, — порядок FIFO між ними. Відмінності від Promise.resolve().then(fn): не створює проміс, а виключення з fn стає звичайним uncaughtException, а не unhandled rejection. Від nextTick — що це стандартний Web API (працює в браузері, Deno, Bun).

Пастка: ESM змінює порядок

Головний ES-модуль виконується всередині асинхронної оцінки модуля, тобто вже в контексті мікрозадач V8. Тому в .mjs проміс, створений на верхньому рівні, виконується раніше за nextTick — рівно навпаки до CJS (задача 16).

06 setImmediate vs setTimeout(fn, 0)

Найвідоміша «недетермінованість» Node — і точне пояснення, звідки вона береться.

У головному модулі порядок не гарантований. Я запустив той самий скрипт 60 разів:

main-module.js — 60 запусків поспіль
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

// $ for i in $(seq 60); do node main-module.js | tr '\n' ' '; echo; done | sort | uniq -c
//   55 immediate timeout
//    5 timeout immediate

Чому. setTimeout(fn, 0) насправді означає 1 мс. Після синхронного коду цикл першою перевіряє фазу timers. Чи минула вже 1 мс від моменту створення таймера — залежить від того, скільки зайняв bootstrap і решта стартової роботи, тобто від навантаження машини, планувальника ОС, прогрітості кешів. Минула — timeout першим; ні — таймер пропущено, цикл дійде до check і виконає immediate, а таймер спрацює на наступному колі. На швидкій машині частіше виграє immediate, на повільній CI — навпаки.

Всередині I/O-колбека порядок детермінований: колбек виконується в poll, наступна фаза — check, тож setImmediate завжди перший (60 з 60 запусків, задача 6). Те саме всередині setTimeout-колбека: з timers цикл спершу пройде check, а новий таймер чекатиме наступного кола (задача 7).

Цікавий факт Назви «переплутані»: setImmediate виконується не «негайно», а на check-фазі, тоді як process.nextTick — справді «негайно», до наступного кроку циклу. Документація Node визнає, що імена варто було б поміняти місцями, але це зламало б половину npm.

07 Таймери зсередини

Чому таймер ніколи не буває точним, як Node групує тисячі таймерів і чим відрізняється setInterval.

Мінімум 1 мс і обмеження

  • Затримка 0, від'ємна, NaN або нечислова → 1 мс.
  • Більше за 2³¹−1 мс (~24,8 доби) → теж 1 мс і попередження.
  • Тому setTimeout(a, 1) і setTimeout(b, 0) — це два таймери з однаковою тривалістю, і вони виконаються в порядку створення (задача 4).

setTimeout(() => console.log('negative delay fired'), -100);

Як Node зберігає таймери (coalescing)

Node не створює окремий libuv-таймер на кожен setTimeout. Усі JS-таймери живуть у JS-структурі: списки за тривалістю (усі таймери на 1000 мс — в одному зв'язаному списку в порядку створення) і пріоритетна черга (binary heap) цих списків за часом найближчого спрацювання. Нативно — один libuv-таймер, налаштований на найближчий термін.

  • Додавання таймера з уже наявною тривалістю — O(1): у хвіст списку (там часи спрацювання монотонно зростають).
  • Тому 10 000 таймаутів запитів «по 30 с» коштують дешево — це і є «coalescing»: таймери з однаковою тривалістю обробляються пачкою в одному проході фази timers.
  • timeout.refresh() переставляє таймер у хвіст списку без нової алокації — так реалізують idle-таймаути сокетів.

setInterval не «доганяє»

08 async/await під капотом

Скільки «тіків» мікрозадач коштує await — питання, на якому валяться навіть сильні кандидати.

Розцукрювання

async-функція — це генератор, обгорнутий у проміс. Код до першого await виконується синхронно, в момент виклику. Кожен await x приблизно перетворюється на:

desugar.js (концептуально)
async function f() {
  console.log('A');      // синхронно, у момент виклику f()
  const v = await x;
  console.log('B', v);   // мікрозадача
}

// ≈
function f() {
  return new Promise((resolve, reject) => {
    console.log('A');
    PromiseResolve(x).then((v) => {   // await = "дочекайся x як проміса"
      console.log('B', v);
      resolve(undefined);
    }, reject);
  });
}

🚫
Де starvation трапляється в реальному коді: «асинхронна» обробка великого масиву через for (const x of items) await process(x), де process насправді синхронний (повертає вже виконаний проміс) — кожен await лише стрибає по мікрозадачах і ніколи не віддає цикл I/O. 1 млн елементів = секунди «мертвого» сервера. Лікування — кожні N елементів робити await new Promise(setImmediate) (або scheduler.yield()-подібну утиліту), чи винести роботу у worker.

11 Що тримає процес живим

Node виходить не «в кінці файлу», а коли в циклі не лишилось ref-нутої роботи.

Після кожної ітерації libuv перевіряє uv_loop_alive(): чи є активні ref-нуті handles (таймер, що очікує; сервер, що слухає; відкритий сокет; дочірній процес; stdin у режимі читання) або активні requests (незавершене fs-читання, DNS-lookup, запис у сокет). Немає — цикл виходить.

Пастка «зниклого» await: await new Promise(() => {}) на верхньому рівні ESM-модуля не тримає процес — Node завершиться з кодом 13 і попередженням «unsettled top-level await». Проміс сам по собі не є handle, тримає лише I/O чи таймер, на який він чекає.

beforeExit vs exit

  • 'beforeExit' — цикл спорожнів. Обробник може запланувати нову роботу, і цикл продовжиться; потім beforeExit настане знову (задача 14). Не викликається при process.exit() і необробленій помилці.
  • 'exit' — точка неповернення: цикл більше не обертається, тож setTimeout, проміси, асинхронний запис у файл в обробнику не виконаються. Лише синхронний код (наприклад, fs.writeFileSync).
  • process.exit() обриває все, включно з незаписаним буфером stdout, якщо він — pipe. Краще виставити process.exitCode = 1 і дати циклу завершитися природно (graceful shutdown — туторіал 17).

12 EventEmitter, I/O-колбеки і close-колбеки

Три місця, де інтуїція про «асинхронність» найчастіше підводить.

emit() синхронний

emitter.emit('x') — це просто цикл, що синхронно викликає всіх слухачів по черзі, в порядку підписки, і повертає true/false. Жодної черги, жодної фази (задача 3). Наслідки:

  • Важкий слухач блокує код, що викликав emit.
  • Виключення в слухачі летить прямо з emit() у викликача.
  • Емітити подію в конструкторі марно — ніхто ще не підписався. Тому бібліотеки роблять process.nextTick(() => this.emit('error', err)).
  • Подія 'error' без слухача — виключення, що валить процес.

«Асинхронними» події стають лише тому, що сам emit викликається з I/O-колбека (наприклад, 'data' на сокеті емітиться в poll-фазі). Більше — у туторіалі 6.

I/O-колбеки і thread pool

Шлях fs.readFile: JS → задача в thread pool → потік робить блокуючі syscalls → повідомлення головному циклу через uv_async → колбек у poll-фазі. Що з цього випливає для порядку виконання:

  • Колбек fs-операції ніколи не виконається в тій самій ітерації, в якій її запустили, — щонайменше одна poll-фаза потрібна.
  • Якщо пул зайнятий, колбек чекає не на диск, а на вільний потік (туторіал 1, демо 2).
  • readFile — це кілька задач (open, fstat, read…, close), кожна з поверненням у цикл, тому між ними встигають інші колбеки.
  • Мережеві колбеки теж у poll, але без пулу: ядро повідомляє про готовність сокета.

close callbacks на практиці

close-order.js
const net = require('node:net');
const server = net.createServer((conn) => conn.end());
server.listen(0, () => {
  const socket = net.connect(server.address().port, () => {
    socket.on('close', () => {
      console.log('socket close');
      server.close();
    });
    socket.destroy();

Усередині колбека connect (poll): tick — одразу після колбеку; immediate — check; socket close — close callbacks тієї ж ітерації (destroy() викликав uv_close, і libuv поставив колбек у цю фазу); timeout — timers наступної ітерації.

13 Рівень libuv і порівняння з браузером

Реальний код uv_run і таблиця відмінностей — щоб відповідати на «чому», а не лише «що».

Одна ітерація очима libuv

deps/uv/src/unix/core.c — uv_run (скорочено, libuv 1.4x+)
int uv_run(uv_loop_t* loop, uv_run_mode mode) {
  int r = uv__loop_alive(loop);

  // Для UV_RUN_DEFAULT таймери обробляються один раз ПЕРЕД циклом —
  // для зворотної сумісності з класичним порядком фаз.
  if (mode == UV_RUN_DEFAULT && r != 0 && loop->stop_flag == 0) {
    uv__update_time(loop);
    uv__run_timers(loop);                  // 1. timers
  }

  while (r != 0 && loop->stop_flag == 0) {
    uv__run_pending(loop);                 // 2. pending callbacks
    uv__run_idle(loop);                    // 3. idle
    uv__run_prepare(loop);                 //    prepare

    int timeout = uv__backend_timeout(loop);  // скільки можна спати (розділ 4)
    uv__io_poll(loop, timeout);            // 4. poll: epoll_wait / kevent

    uv__run_check(loop);                   // 5. check  (setImmediate)
    uv__run_closing_handles(loop);         // 6. close callbacks

    uv__update_time(loop);
    uv__run_timers(loop);                  // timers наступного кола

    r = uv__loop_alive(loop);              // є ref-нуті handles/requests?
  }
  return r;
}

Зверніть увагу: у сучасному libuv таймери фізично викликаються в кінці ітерації (і один раз перед першою). Порядок по колу від цього не змінюється — це ті самі «timers → pending → idle/prepare → poll → check → close» з документації Node, просто точка «розрізу» кола інша. Колбеки nextTick і мікрозадачі в цьому коді не видно, бо їх запускає Node всередині кожного виклику JS (InternalCallbackScope → processTicksAndRejections).

15 Каверзні питання співбесіди

Питання, де відповідь «мікрозадачі раніше за макрозадачі» вже недостатня.

БазаНазвіть фази event loop у Node і що в кожній виконується.
timers (setTimeout/setInterval) → pending callbacks (відкладені системні) → idle/prepare (внутрішні) → poll (I/O-колбеки, очікування) → check (setImmediate) → close callbacks (події close). nextTick і проміси — не фази, а контрольні точки після кожного колбеку.
БазаЧим process.nextTick відрізняється від Promise.then?
Різні черги: nextTick веде Node, проміси — V8. Після кожного колбеку Node спершу вичерпує всю чергу nextTick, потім всю чергу мікрозадач, і повторює, поки обидві не порожні. У CJS nextTick виконується раніше; у головному ESM-модулі — пізніше за проміси верхнього рівня.
ПасткаЩо виконається першим: setTimeout(fn, 0) чи setImmediate(fn)?
З головного модуля — не гарантовано (залежить від того, чи минула 1 мс до першої фази timers). З I/O-колбека або з колбека таймера — завжди setImmediate, бо check іде раніше, ніж цикл повернеться в timers.
ПасткаЧи виконаються проміси між двома колбеками setTimeout, запланованими на той самий час?
Так, з Node 11: контрольна точка nextTick/мікрозадач — після кожного окремого колбеку таймера чи immediate. До Node 11 — лише після всієї фази, тому старі статті показують інший порядок.
БазаЯк poll-фаза вирішує, скільки чекати?
Timeout = 0, якщо є setImmediate у черзі, pending-колбеки, handles що закриваються або цикл зупиняється; інакше — до найближчого таймера; якщо таймерів немає, але є I/O-handles — нескінченно (−1). Тому сервер у простої споживає 0% CPU.
ПасткаРекурсивний setImmediate і рекурсивний nextTick — що з них блокує I/O?
nextTick (і рекурсивний Promise.then) — так: черги дренуються «до дна», цикл не переходить до жодної фази. setImmediate — ні: check бере лише immediates, що були на вході у фазу, нові чекають наступного кола, і між ними встигають timers і poll.
ПасткаСкільки мікрозадач «коштує» await?
await значення чи нативного проміса — 1 тік (з V8 7.2 / Node 12). Thenable — 2. return promise з async-функції — 3 тіки до зовнішнього .then, бо це резолюція промісом. Код до першого await виконується синхронно.
БазаЧи асинхронний EventEmitter.emit?
Ні, синхронний: викликає слухачів по черзі в порядку підписки й повертається. Виключення слухача летить з emit(). Асинхронність з'являється лише тому, що emit часто викликається з I/O-колбеків.
ПасткаЧому setTimeout(fn, 2 ** 31) спрацьовує одразу?
Затримка більша за 2³¹−1 мс (~24,8 доби) не вміщується в 32-бітне знакове ціле, тож Node ставить 1 мс і видає TimeoutOverflowWarning. Те саме для від'ємних затримок (TimeoutNegativeWarning). Довгі затримки — через планувальник або ланцюжок коротших таймерів.
БазаЯк виміряти, що event loop заблокований?
perf_hooks.monitorEventLoopDelay() — гістограма запізнення внутрішнього таймера (дивитися p99/max); performance.eventLoopUtilization() — частка часу без сну в poll. Знайти винуватця — --cpu-prof, clinic.js, flamegraph.
ПасткаПроцес завершився, а проміс так і не виконався. Як це можливо?
Проміс — не handle і не тримає цикл. Якщо він чекає на щось, що не створює I/O чи таймер (наприклад, resolve ніхто не викличе), цикл порожніє і процес виходить. Для top-level await у ESM Node завершується з кодом 13 і попередженням «unsettled top-level await».
ПасткаЩо можна робити в обробнику process.on('exit')?
Лише синхронний код: цикл уже не обертається, таймери, проміси й асинхронний I/O не виконаються (задача 14). Для асинхронного cleanup — beforeExit (але він не викликається при process.exit()) або обробники сигналів SIGTERM/SIGINT з graceful shutdown.
ПасткаОбробка масиву через for…of з await «асинхронна», але сервер не відповідає. Чому?
Якщо функція всередині фактично синхронна (повертає вже виконаний проміс), кожен await лише переходить до наступної мікрозадачі — цикл не доходить до poll, і I/O стоїть. Це starvation через мікрозадачі. Розбивати роботу через await new Promise(setImmediate) кожні N елементів або виносити у worker.
БазаЧим event loop Node відрізняється від браузерного?
Фіксовані фази libuv замість набору task queues; черга nextTick вища за проміси; setImmediate; немає rendering і requestAnimationFrame; poll блокується в ядрі; процес завершується, коли немає ref-нутих handles; таймери без браузерного троттлінгу і з мінімумом 1 мс.

17 Як запам'ятати

Образи для кожного правила циклу.

1
Шість фаз
timers → pending → idle/prepare → poll → check → close.
Асоціація: «Таксист Підвозить І Пасажира Чекає Close» — таксі робить коло, найдовше стоїть на стоянці poll, чекаючи пасажирів.
2
process.nextTick
Черга Node, що вичерпується після кожного колбеку раніше за проміси.
Асоціація: VIP-коридор в аеропорту — проходять перед усіма, але якщо VIP-ів нескінченно, звичайна черга не рушить ніколи.
3
Контрольна точка μ
Після кожного колбеку: усі тіки, потім усі мікрозадачі, повтор до порожніх черг.
Асоціація: після кожного клієнта касир спершу закриває всі термінові дзвінки, потім усі листи — і лише тоді кличе наступного.
4
setImmediate
Колбек check-фази — одразу після poll; з I/O-колбека завжди раніше за setTimeout(0).
Асоціація: «одразу після пошти» — щойно розібрав вхідні листи (poll), відповідаєш на них (check), а будильник (timer) задзвонить на наступному колі.
5
Poll
Єдина фаза, де цикл спить у ядрі — до I/O-події або найближчого таймера.
Асоціація: рибалка з вудкою: сидить і чекає клювання, але встає, коли дзвонить будильник; якщо в кошику вже є риба (immediate) — не сідає взагалі.
6
Таймер = «не раніше, ніж»
Мінімум 1 мс, без гарантії точності; запізнення = event loop lag.
Асоціація: «приходьте не раніше дев'ятої» — але лікар прийме, коли звільниться з попереднім пацієнтом.
7
Starvation
Нескінченні мікрозадачі не дають циклу дійти до фаз; рекурсивний setImmediate безпечний.
Асоціація: співрозмовник, що постійно каже «і ще одне…» — ви ніколи не підете на наступну зустріч.
8
await = тіки
Значення чи проміс — 1 тік, thenable — 2, return promise з async — 3.
Асоціація: пересадки в метро: пряма лінія — одна, через чужий thenable — дві, «повернути проміс» — ще одна зайва пересадка.
9
ref / unref, beforeExit / exit
Процес живе, поки є ref-нуті handles; beforeExit може оживити цикл, exit — лише sync.
Асоціація: вечірка закінчується, коли пішов останній гість (handle); «beforeExit» — останній шанс замовити ще піцу, «exit» — світло вже вимкнули.
10
emit() синхронний
Слухачі викликаються одразу, по черзі, всередині emit.
Асоціація: гучномовець в офісі: оголошення чують усі одночасно з тим, як його промовили, — ніякої поштової скриньки.
