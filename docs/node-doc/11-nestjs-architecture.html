01 Чому архітектура в Node — окрема проблема

Express дає повну свободу — і саме тому за рік типовий проєкт перетворюється на клубок handler-ів, що ходять у БД напряму.

У Django, Rails, Laravel чи Spring структура задана фреймворком: моделі тут, контролери там, сервіси ось так. Node-світ виріс на мінімалістичному Express (туторіал 10), де немає жодних конвенцій. Перший місяць це прискорює, а потім з'являється ось такий код:

routes/orders.js — типове «спагеті»
router.post('/orders/:id/cancel', async (req, res) => {
  const { rows } = await pool.query('SELECT * FROM orders WHERE id = $1', [req.params.id]);
  if (!rows[0]) return res.status(404).send('not found');
  if (rows[0].status === 'paid' && req.user.role !== 'admin') return res.status(409).send('paid');
  await pool.query('UPDATE orders SET status = $1 WHERE id = $2', ['cancelled', req.params.id]);
  await stripe.refunds.create({ payment_intent: rows[0].payment_intent });   // а якщо впаде?
  await sendEmail(req.user.email, 'Order cancelled');                       // а з крону як скасувати?
  res.json({ ok: true });
});
  • Бізнес-правило («оплачене може скасувати лише адмін») захоплене HTTP-handler-ом: його не викликати з черги, крону чи CLI без копіпасти.
  • Тестувати можна лише через HTTP + справжню БД + мок Stripe.
  • Транзакції немає: UPDATE пройшов, refund упав — дані розійшлися.
  • Зміна ORM чи фреймворку = переписати все, бо SQL і req розмазані по всіх файлах.
💼
На співбесіді запитають так «Як би ви структурували Node-бекенд на 50+ endpoint-ів?» — Очікують почути: шари (transport → application/service → domain → data access), feature-модулі замість технічних папок, напрямок залежностей до ядра, DI (ручний або контейнер), тонкі контролери. Назва фреймворку тут другорядна.

02 Шарова архітектура і напрямок залежностей

Головне правило не «скільки шарів», а «хто кого знає»: верхній шар знає про нижній, ніколи навпаки.

ШарВідповідальністьНе повинен знати про
Controller / routeрозібрати вхід (DTO), викликати сервіс, змапити результат у статус і тілоSQL, ORM, бізнес-правила
Service / use caseсценарій: перевірки, транзакція, виклики репозиторіїв і зовнішніх сервісівreq, res, статус-коди, заголовки
Domainсутності, інваріанти («оплачене не скасовується»)будь-яку інфраструктуру
Repositoryзбереження й читання агрегатів; мапінг рядків БД у доменні об'єктиHTTP, бізнес-рішення
⚠️
Не перестарайтеся. Для CRUD-сервісу на 10 таблиць повний DDD + hexagonal + CQRS — це over-engineering: ви пишете маппери між трьома однаковими типами. Розумний мінімум — тонкі контролери, сервіси без req, доступ до даних в одному місці. Порти й адаптери варто вводити там, де справді є кілька реалізацій або складна доменна логіка.

03 Feature-модулі, структура папок і hexagonal у TypeScript

Групуйте за фічею, а не за технічним типом: так зміна однієї фічі торкається однієї папки.

src/ ├── modules/ │ ├── orders/ # одна фіча = одна папка │ │ ├── orders.controller.ts # transport │ │ ├── orders.service.ts # application │ │ ├── order.entity.ts # domain │ │ ├── orders.repository.ts # data access │ │ ├── dto/create-order.dto.ts │ │ ├── orders.module.ts # публічний API модуля (exports) │ │ └── orders.service.spec.ts │ ├── users/ │ └── billing/ ├── common/ # guards, filters, interceptors, утиліти ├── config/ # схеми конфігу, registerAs ├── app.module.ts └── main.ts # composition root / bootstrap

Порівняйте з «технічною» структурою controllers/ services/ models/: там фіча orders розмазана по трьох папках, і через рік ніхто не знає, які сервіси можна чіпати. Правила для feature-модулів:

  • Модуль експортує мінімум (зазвичай лише сервіс). Інші модулі не імпортують його репозиторій чи entity напряму.
  • Залежності між модулями — ациклічні. Якщо orders і billing потребують одне одного — винесіть спільне або спілкуйтеся подіями.
  • Лінтер захищає межі: eslint-plugin-boundaries, dependency-cruiser або Nx module boundaries забороняють імпорти «вгору» й «впоперек».

Ports & adapters без фреймворку (запущено на Node 24 з type stripping)

Зверніть увагу: тут немає constructor(private x) — parameter properties не є «erasable» синтаксисом, і Node без прапорців їх не виконує (див. туторіал 13).

hexagonal.ts
// ── domain/ ── чиста бізнес-логіка, нуль імпортів з інфраструктури
export class Order {
  status: 'new' | 'paid' | 'cancelled' = 'new';
  readonly id: string;
  readonly total: number;
  constructor(id: string, total: number) { this.id = id; this.total = total; }
  cancel() {
    if (this.status === 'paid') throw new Error('Paid order cannot be cancelled');
    this.status = 'cancelled';
  }
}

// ── application/ports ── інтерфейси, які ВИЗНАЧАЄ ядро
export interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}
export interface EventPublisher { publish(name: string, payload: unknown): Promise<void> }

// ── application/ ── use case: оркестрація, без HTTP і без SQL
export class CancelOrder {
  private readonly orders: OrderRepository;
  private readonly events: EventPublisher;
  constructor(orders: OrderRepository, events: EventPublisher) { this.orders = orders; this.events = events; }
  async execute(orderId: string) {
    const order = await this.orders.findById(orderId);
    if (!order) throw new Error(`Order ${orderId} not found`);
    order.cancel();
    await this.orders.save(order);
    await this.events.publish('order.cancelled', { orderId });
    return order;
  }
}

// ── infrastructure/ ── адаптери, що РЕАЛІЗУЮТЬ порти (тут — in-memory)
class InMemoryOrders implements OrderRepository {
  private readonly rows = new Map<string, Order>();
  async findById(id: string) { return this.rows.get(id) ?? null; }
  async save(o: Order) { this.rows.set(o.id, o); }
}
class ConsolePublisher implements EventPublisher {
  async publish(name: string, payload: unknown) { console.log('event:', name, payload); }
}

// ── composition root ── єдине місце, яке знає про всі шари
const orders = new InMemoryOrders();
await orders.save(new Order('o-1', 100));
const paid = new Order('o-2', 50); paid.status = 'paid'; await orders.save(paid);

const cancelOrder = new CancelOrder(orders, new ConsolePublisher());
console.log('status:', (await cancelOrder.execute('o-1')).status);
try { await cancelOrder.execute('o-2'); } catch (e) { console.log('error:', (e as Error).message); }
terminal — node hexagonal.ts
event: order.cancelled { orderId: 'o-1' }
status: cancelled
error: Paid order cannot be cancelled

Composition root (останні рядки) — це ручний DI: одне місце створює всі об'єкти й передає залежності через конструктори. Для 10 сервісів цього достатньо. Коли їх 200, з'являються життєві цикли, конфігурація, підміни в тестах — і тут DI-контейнер (Nest, tsyringe, awilix, InversifyJS) починає окуповуватися.

04 NestJS: модулі як одиниця архітектури

Модуль у Nest — це межа видимості DI: що не експортовано, те ззовні не інжектнути.

Кожен клас з @Module() описує чотири речі:

ПолеЩо означає
providersщо цей модуль створює й тримає у своєму DI-контексті (сервіси, репозиторії, фабрики)
controllersHTTP-контролери модуля (Nest створить їх і інжектне провайдери)
importsмодулі, чиї exports стають доступними тут
exportsпідмножина providers (або реекспорт імпортованих модулів), яку бачать імпортери
users.module.ts / orders.module.ts
@Module({
  controllers: [UsersController],
  providers: [UsersService, UsersRepository],
  exports: [UsersService],               // UsersRepository лишається приватним
})
export class UsersModule {}

@Module({
  imports: [UsersModule],                // тепер OrdersService може інжектнути UsersService
  controllers: [OrdersController],
  providers: [OrdersService],
})
export class OrdersModule {}
🐛
Найчастіша помилка новачка в Nest: додати UsersService у providers ще й OrdersModule «щоб запрацювало». Помилка зникає, але тепер існують два різні екземпляри UsersService (кожен модуль створив свій), зі своїми кешами й станом. Правильно — exports в UsersModule і imports в OrdersModule.

Динамічні модулі: forRoot / forRootAsync / forFeature

Модуль, що приймає конфігурацію, повертає DynamicModule зі статичного методу. Конвенція: forRoot — один раз у корені (підключення, глобальні опції), forFeature — у feature-модулях (наприклад, TypeOrmModule.forFeature([Order]) реєструє репозиторії для конкретних сутностей), ...Async — коли опції треба отримати через DI (з ConfigService).

storage.module.ts (перевірено tsc)
import { Module, type DynamicModule, Inject, Injectable } from '@nestjs/common';

export interface StorageOptions { bucket: string; region: string }
export const STORAGE_OPTIONS = Symbol('STORAGE_OPTIONS');

@Injectable()
export class StorageService {
  constructor(@Inject(STORAGE_OPTIONS) private readonly opts: StorageOptions) {}
  url(key: string) { return `https://${this.opts.bucket}.s3.${this.opts.region}.amazonaws.com/${key}`; }
}

@Module({})
export class StorageModule {
  // forRoot — один раз у кореневому модулі, з конфігурацією
  static forRoot(opts: StorageOptions): DynamicModule {
    return {
      module: StorageModule,
      global: true,                                     // доступний усім без imports
      providers: [{ provide: STORAGE_OPTIONS, useValue: opts }, StorageService],
      exports: [StorageService],
    };
  }
  // forRootAsync — коли конфіг приходить з ConfigService
  static forRootAsync(o: { inject: any[]; useFactory: (...args: any[]) => StorageOptions }): DynamicModule {
    return {
      module: StorageModule,
      global: true,
      providers: [{ provide: STORAGE_OPTIONS, inject: o.inject, useFactory: o.useFactory }, StorageService],
      exports: [StorageService],
    };
  }
}

Для складних випадків Nest має ConfigurableModuleBuilder, який генерує forRoot/forRootAsync з підтримкою useFactory/useClass/useExisting без ручного шаблонного коду.

05 Провайдери і DI-контейнер

Nest будує граф залежностей при старті: топологічно сортує провайдери й створює кожен рівно тоді, коли готові його залежності.

Провайдер — будь-що, що контейнер вміє створити й видати за токеном. Токен — це клас, рядок або Symbol. Запис providers: [UsersService] — скорочення для { provide: UsersService, useClass: UsersService }.

РецептПрикладКоли
useClass{ provide: PaymentGateway, useClass: StripeGateway }підміна реалізації абстракції (за env, у тестах)
useValue{ provide: 'CLOCK', useValue: () => Date.now() }константи, готові об'єкти, моки
useFactory{ provide: PG_POOL, inject: [ConfigService], useFactory: (c) => new Pool(...) }створення з конфігу, async-ініціалізація (Nest дочекається Promise)
useExisting{ provide: 'Logger', useExisting: PinoLogger }аліас на вже існуючий провайдер (той самий екземпляр)
orders.service.ts
export const ORDERS_REPO = Symbol('ORDERS_REPO');      // інтерфейс у рантаймі не існує → потрібен токен

@Injectable()
export class OrdersService {
  constructor(
    @Inject(ORDERS_REPO) private readonly orders: OrdersRepository,  // інтерфейс → явний токен
    private readonly users: UsersService,                           // клас → токен = сам клас
    @Inject('CLOCK') private readonly now: () => number,
  ) {}
}

// orders.module.ts
providers: [
  OrdersService,
  { provide: ORDERS_REPO, useClass: PrismaOrdersRepo },
  { provide: 'CLOCK', useValue: () => Date.now() },
]
💡
Чому для інтерфейсу потрібен @Inject(TOKEN): TypeScript-інтерфейси стираються при компіляції. У метаданих конструктора на їхньому місці буде Object, і Nest не знатиме, що інжектити. Альтернатива — абстрактний клас як токен (abstract class OrdersRepository): він існує в рантаймі, тож @Inject не потрібен, а { provide: OrdersRepository, useClass: PrismaOrdersRepo } підміняє реалізацію.

06 Scopes: DEFAULT, REQUEST, TRANSIENT і їхня ціна

Request scope звучить зручно («свій екземпляр на запит»), але він заразний і коштує алокацій на кожному запиті.

ScopeСкільки екземплярівТипове використання
DEFAULTодин на застосунок (singleton), створюється на старті99% провайдерів: сервіси, репозиторії, клієнти
REQUESTновий на кожен вхідний запит, прибирається GC післямультитенантність «tenant з заголовка», per-request кеш DataLoader
TRANSIENTновий для кожного споживача, що його інжектитьлогер з контекстом класу-споживача, stateful helper

Експеримент: рахуємо виклики конструкторів (NestJS 12, запущено):

scopes.mts
import 'reflect-metadata';
import { Controller, Get, Inject, Injectable, Module, Scope } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';

const created: Record<string, number> = {};
const count = (name: string) => { created[name] = (created[name] ?? 0) + 1; };

@Injectable()                                   // Scope.DEFAULT — singleton
class ConfigService { constructor() { count('ConfigService (DEFAULT)'); } }

@Injectable({ scope: Scope.TRANSIENT })         // новий екземпляр для кожного споживача
class Helper { constructor() { count('Helper (TRANSIENT)'); } }

@Injectable({ scope: Scope.REQUEST })           // новий екземпляр на кожен запит
class RequestContext { constructor() { count('RequestContext (REQUEST)'); } }

@Injectable()                                   // сам DEFAULT, але залежить від REQUEST →
class UsersService {                            // теж стає request-scoped («бульбашка» вгору)
  constructor(private ctx: RequestContext, private cfg: ConfigService) { count('UsersService (DEFAULT→REQUEST)'); }
}

@Controller()
class AppController {
  constructor(private users: UsersService, private helper: Helper,
              @Inject('CLOCK') private clock: () => number) { count('AppController'); }
  @Get() hi() { return { now: typeof this.clock() }; }
}

@Module({
  controllers: [AppController],
  providers: [ConfigService, Helper, RequestContext, UsersService,
    { provide: 'CLOCK', useValue: () => Date.now() }],
})
class AppModule {}

const app = await NestFactory.create(AppModule, { logger: false });
await app.listen(3101);
console.log('після старту:', created);
for (let i = 0; i < 3; i++) await (await fetch('http://localhost:3101/')).text();
console.log('після 3 запитів:', created);
await app.close();
terminal
після старту: { 'ConfigService (DEFAULT)': 1 }
після 3 запитів: {
  'ConfigService (DEFAULT)': 1,
  'RequestContext (REQUEST)': 3,
  'Helper (TRANSIENT)': 3,
  'UsersService (DEFAULT→REQUEST)': 3,
  AppController: 3
}
  • Scope «бульбашкою» піднімається вгору. UsersService оголошений як DEFAULT, але залежить від REQUEST-провайдера — тому сам став request-scoped. І контролер теж створювався 3 рази. Один request-scoped провайдер на дні графа перетворює на request-scoped усе, що від нього залежить.
  • TRANSIENT Helper створювався заново разом із кожним новим контролером — тобто теж 3 рази.
  • Ціна: на кожен запит — створення підграфа об'єктів, резолв залежностей, більше роботи GC. На гарячих маршрутах це помітно в p99. Деякі механізми (наприклад, частина lifecycle-хуків як onModuleInit) для request-scoped провайдерів не викликаються.
✅
Краща альтернатива для per-request контексту — singleton-провайдери + AsyncLocalStorage (бібліотека nestjs-cls або власний middleware): tenant, requestId, користувач лежать у контексті async-ланцюжка, а граф об'єктів не перебудовується. Механіку ALS розібрано в туторіалі 3. Для мультитенантності Nest також має durable providers (ContextIdStrategy) — один підграф на tenant, а не на запит.

07 Декоратори і reflect-metadata: як DI «знає» типи

Магії немає: TypeScript-компілятор записує типи параметрів конструктора в метадані, а Nest їх читає.

З "experimentalDecorators": true і "emitDecoratorMetadata": true компілятор для кожного задекорованого класу генерує виклик __metadata("design:paramtypes", [...]). Ось що реально видав tsc для контролера з розділу 8 туторіалу 10:

dist/main.mjs (вихід tsc, фрагмент)
__decorate([
    Get(':id'),
    __param(0, Param('id', PositiveIntPipe)),
    __metadata("design:type", Function),
    __metadata("design:paramtypes", [Number]),
    __metadata("design:returntype", void 0)
], UsersController.prototype, "findOne", null);
UsersController = __decorate([
    Controller('users'),
    __metadata("design:paramtypes", [UsersService])
], UsersController);
  1. @Controller('users') через Reflect.defineMetadata записує шлях на клас.
  2. __metadata("design:paramtypes", [UsersService]) — посилання на сам клас UsersService, яке Nest прочитає через Reflect.getMetadata('design:paramtypes', UsersController) і використає як токен.
  3. @Param('id', PositiveIntPipe) записує, що параметр 0 треба взяти з req.params.id і прогнати через pipe.
⚠️
Наслідки для тулінгу. (1) Type stripping Node (node file.ts) і esbuild без плагінів не генерують design:paramtypes — Nest-застосунок без них не запуститься (DI бачить undefined). Потрібен tsc або SWC (nest start -b swc), Vitest — з плагіном unplugin-swc. (2) import type { UsersService } ламає DI: тип стирається, у метаданих буде Object. (3) Nest використовує legacy (experimental) декоратори, а не стандартні TC39 декоратори з TS 5.0+ — у стандартних немає параметр-декораторів і metadata у такій формі.

08 Життєвий цикл запиту в Nest

Найпопулярніше питання про Nest на співбесіді: у якому порядку виконуються middleware, guards, interceptors, pipes і filters.

Перевіримо порядок експериментом — кожен компонент пише свою позначку (NestJS 12, запущено):

lifecycle.mts
import 'reflect-metadata';
import {
  Injectable, Module, Controller, Get, Param, UseGuards, UseInterceptors, UseFilters, Catch,
  type NestMiddleware, type MiddlewareConsumer, type NestModule, type CanActivate,
  type ExecutionContext, type NestInterceptor, type CallHandler, type PipeTransform,
  type ExceptionFilter, type ArgumentsHost, BadRequestException, HttpException,
} from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { tap } from 'rxjs';

export const log: string[] = [];

@Injectable()
class LoggerMiddleware implements NestMiddleware {
  use(req: any, res: any, next: () => void) { log.push('1 middleware'); next(); }
}

@Injectable()
class AuthGuard implements CanActivate {
  canActivate(ctx: ExecutionContext) {
    log.push('2 guard');
    return ctx.switchToHttp().getRequest().headers['x-token'] === 'secret';
  }
}

@Injectable()
class TimingInterceptor implements NestInterceptor {
  intercept(ctx: ExecutionContext, next: CallHandler) {
    log.push('3 interceptor (before)');
    return next.handle().pipe(tap(() => log.push('6 interceptor (after)')));
  }
}

@Injectable()
class ParseIdPipe implements PipeTransform<string, number> {
  transform(value: string) {
    log.push('4 pipe');
    const id = Number(value);
    if (!Number.isInteger(id)) throw new BadRequestException('id must be integer');
    return id;
  }
}

@Catch(HttpException)
class HttpFilter implements ExceptionFilter {
  catch(e: HttpException, host: ArgumentsHost) {
    log.push(`7 exception filter (${e.getStatus()})`);
    host.switchToHttp().getResponse().status(e.getStatus()).json({ error: e.message });
  }
}

@Controller('items')
@UseGuards(AuthGuard)
@UseInterceptors(TimingInterceptor)
@UseFilters(HttpFilter)
class ItemsController {
  @Get(':id')
  get(@Param('id', ParseIdPipe) id: number) {
    log.push('5 handler');
    return { id };
  }
}

@Module({ controllers: [ItemsController] })
class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) { consumer.apply(LoggerMiddleware).forRoutes('*path'); }
}

const app = await NestFactory.create(AppModule, { logger: false });

  console.log('   ' + log.splice(0).join(' → '));
}

09 DTO і ValidationPipe

Валідація на межі системи: у сервіс має потрапити лише перевірений і типізований об'єкт, без зайвих полів.

import 'reflect-metadata';
import { Body, Controller, Module, Post, ValidationPipe } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { IsEmail, IsInt, IsString, Length, Min } from 'class-validator';
import { Type } from 'class-transformer';

export class CreateUserDto {
  @IsString() @Length(2, 50) name!: string;
  @IsEmail() email!: string;
  @Type(() => Number) @IsInt() @Min(18) age!: number;

@Controller('users')

    return { isDto: dto instanceof CreateUserDto, dto };

Альтернатива — схеми замість класів. 10 Config, auth-guards, interceptors, exception filters

Чотири «наскрізні» механізми, з яких складається кожен продакшн Nest-застосунок.

ConfigModule: валідований конфіг через DI

app.module.ts (перевірено tsc, @nestjs/config 12)
import { Module } from '@nestjs/common';
import { ConfigModule, ConfigService, registerAs } from '@nestjs/config';
import { StorageModule } from './dynamic.module.mjs';

export const dbConfig = registerAs('db', () => ({
  url: process.env.DATABASE_URL!,
  poolSize: Number(process.env.DB_POOL_SIZE ?? 10),

  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      load: [dbConfig],

        return env;
      },
    }),
    StorageModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (cfg: ConfigService) => ({
        bucket: cfg.getOrThrow<string>('S3_BUCKET'),
        region: cfg.get<string>('AWS_REGION', 'eu-central-1'),

    }),
  ],

  • isGlobal: true — ConfigService доступний усюди без імпорту модуля.
  • validate (або validationSchema з Joi) — застосунок падає на старті, якщо змінної немає. Найкраще місце для Zod-схеми всього env.
  • registerAs('db', ...) — namespaced-конфіг, який можна інжектнути типізовано: @Inject(dbConfig.KEY) cfg: ConfigType<typeof dbConfig>.
  • getOrThrow замість get — щоб undefined не «протікав» у рантайм.

Auth через guard: JWT + ролі + @Public()

jwt-auth.guard.ts (перевірено tsc, @nestjs/jwt 12)
import {
  CanActivate, ExecutionContext, Injectable, SetMetadata, UnauthorizedException, ForbiddenException,
} from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { JwtService } from '@nestjs/jwt';

export const IS_PUBLIC = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC, true);
export const ROLES = 'roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES, roles);

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private readonly jwt: JwtService, private readonly reflector: Reflector) {}

  async canActivate(ctx: ExecutionContext): Promise<boolean> {
    const targets = [ctx.getHandler(), ctx.getClass()];
    if (this.reflector.getAllAndOverride<boolean>(IS_PUBLIC, targets)) return true;

    const req = ctx.switchToHttp().getRequest();
    const [type, token] = (req.headers.authorization ?? '').split(' ');
    if (type !== 'Bearer' || !token) throw new UnauthorizedException();
    try {
      req.user = await this.jwt.verifyAsync(token);       // підпис + exp
    } catch {
      throw new UnauthorizedException();
    }
    const roles = this.reflector.getAllAndOverride<string[]>(ROLES, targets);
    if (roles && !roles.some((r) => req.user.roles?.includes(r))) throw new ForbiddenException();
    return true;
  }
}
// Реєстрація глобально з DI: { provide: APP_GUARD, useClass: JwtAuthGuard } у providers модуля

Патерн «глобальний guard + @Public() виняток» безпечніший за «повісити @UseGuards на кожен контролер»: новий маршрут за замовчуванням закритий. Reflector.getAllAndOverride читає метадані спершу з методу, потім з класу. Альтернатива — @nestjs/passport зі стратегіями (passport-jwt, OAuth, local): більше церемоній, але готові стратегії для десятків провайдерів. Безпека токенів — у туторіалі 14.

Interceptors: логування і таймаут

interceptors.ts (перевірено tsc)
import {
  CallHandler, ExecutionContext, Injectable, Logger, NestInterceptor, RequestTimeoutException,
} from '@nestjs/common';
import { Observable, TimeoutError, catchError, tap, throwError, timeout } from 'rxjs';

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  private readonly logger = new Logger('HTTP');
  intercept(ctx: ExecutionContext, next: CallHandler): Observable<unknown> {
    const req = ctx.switchToHttp().getRequest();
    const started = performance.now();
    return next.handle().pipe(
      tap(() => this.logger.log(`${req.method} ${req.url} ${Math.round(performance.now() - started)}ms`)),
    );
  }
}

@Injectable()
export class TimeoutInterceptor implements NestInterceptor {
  intercept(ctx: ExecutionContext, next: CallHandler): Observable<unknown> {
    return next.handle().pipe(
      timeout(5_000),
      catchError((err) => throwError(() => (err instanceof TimeoutError ? new RequestTimeoutException() : err))),
    );
  }
}

Interceptor працює з Observable відповіді, тому може змінити результат (map), обробити помилку (catchError), обмежити час (timeout) або взагалі не викликати handler (кеш: повернути of(cached)). Вбудований CacheInterceptor з @nestjs/cache-manager кешує GET-відповіді. Увага: timeout скасовує очікування, але не сам запит у БД — для справжнього скасування потрібен AbortSignal.

Exception filters: доменні помилки → HTTP

domain-exception.filter.ts
export class DomainError extends Error {}
export class OrderNotFound extends DomainError {}
export class OrderAlreadyPaid extends DomainError {}

@Catch(DomainError)                               // сервіси кидають доменні помилки, не HttpException
export class DomainExceptionFilter implements ExceptionFilter {
  private static readonly map = new Map<Function, number>([
    [OrderNotFound, 404],
    [OrderAlreadyPaid, 409],
  ]);
  catch(err: DomainError, host: ArgumentsHost) {
    const status = DomainExceptionFilter.map.get(err.constructor) ?? 422;
    host.switchToHttp().getResponse().status(status).json({ error: err.constructor.name, message: err.message });
  }
}

Так сервіси лишаються незалежними від HTTP (їх можна викликати з черги чи CLI), а мапінг у статус-коди живе в транспортному шарі — рівно як вимагає шарова архітектура з розділу 2.

12 Мікросервіси, CQRS і циклічні залежності

Три теми, які часто згадують разом із Nest: дві корисні можливості і одна пастка, що в ESM стала гострішою.

Microservices: ті самі контролери, інший транспорт

billing.microservice.ts (перевірено tsc)
import { Controller } from '@nestjs/common';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './config.mjs';
import { EventPattern, MessagePattern, Payload, Transport, type MicroserviceOptions } from '@nestjs/microservices';

@Controller()
export class BillingController {
  @MessagePattern('invoice.get')            // request-response
  getInvoice(@Payload() data: { id: string }) { return { id: data.id, total: 100 }; }

  @EventPattern('order.created')            // fire-and-forget подія
  onOrderCreated(@Payload() data: { orderId: string }) { /* ... */ }
}

async function bootstrap() {
  const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.NATS,
    options: { servers: ['nats://nats:4222'] },
  });
  await app.listen();
}

@nestjs/microservices абстрагує транспорт: TCP, Redis, NATS, MQTT, RabbitMQ, Kafka, gRPC. @MessagePattern — request/response, @EventPattern — події без відповіді. Guards, pipes, interceptors і filters працюють і тут. Застосунок може бути гібридним (app.connectMicroservice()): HTTP + споживач черги в одному процесі. Чесно: абстракція «один API для всіх брокерів» приховує суттєві відмінності (гарантії доставки Kafka vs NATS, ack-и RabbitMQ), тож для серйозних черг часто беруть нативні клієнти або BullMQ — див. туторіал 18.

CQRS-модуль

orders.cqrs.ts (перевірено tsc, @nestjs/cqrs 12)
import { Controller, Module, Param, Post } from '@nestjs/common';

CommandBus/QueryBus/EventBus розділяють запис і читання, а sagas (RxJS-потоки подій) оркеструють реакції на події. Корисно в складному домені з event sourcing чи окремими read-моделями; для CRUD — зайвий рівень непрямості, де «перейти до визначення» більше не працює.

Циклічні залежності і forwardRef — і чому в ESM цього недостатньо

Класична порада: якщо AService ↔ BService залежать одне від одного, обгорнути обидва в @Inject(forwardRef(() => BService)). Ми перевірили це на NestJS 12, який тепер поставляється як ESM, з файлами a.service.mts ↔ b.service.mts, що імпортують одне одного:

terminal — з forwardRef, ESM
file:///.../dist/circ2/b.service.mjs:25
    __metadata("design:paramtypes", [AService])
                                     ^

ReferenceError: Cannot access 'AService' before initialization

Застосунок падає ще до того, як Nest щось побачив: forwardRef відкладає лише резолв токена, а emitDecoratorMetadata генерує жадібне посилання [AService] на рівні модуля. У CommonJS тут тихо був би undefined і зрозуміла помилка Nest про невирішену залежність (з підказкою про forwardRef); в ESM це TDZ ReferenceError через циклічний імпорт. Робочий обхід — тип-обгортка, щоб у метаданих був Object:

circ2/a.service.mts — запускається: "A sees B"
import { Inject, Injectable, forwardRef } from '@nestjs/common';
import type { Ref } from './ref.mjs';          // export type Ref<T> = T;
import { BService } from './b.service.mjs';

@Injectable()
export class AService {
  constructor(@Inject(forwardRef(() => BService)) private b: Ref<BService>) {}
  ping() { return 'A sees ' + this.b.name(); }
}
// tsc тепер видає: __metadata("design:paramtypes", [Object])
🧠 Запам'ятай: forwardRef — це пластир, а не рішення. Цикл між сервісами майже завжди означає, що спільну логіку треба винести в третій сервіс або замінити прямий виклик подією.

13 Чесно: Nest чи «голий» Fastify/Express

Nest — не «правильний вибір за замовчуванням», а компроміс, що окуповується з розміром команди і кодової бази.

14 Каверзні питання співбесіди

Питання про Nest і архітектуру, на яких «знаю декоратори» відрізняється від «розумію, як це працює».

БазаНазвіть порядок виконання компонентів у Nest.
Middleware → Guards → Interceptors (before) → Pipes → Handler → Interceptors (after) → відповідь; при винятку — Exception filters. У межах етапу: global → controller → route (filters — від найближчого). Ми перевірили це логами в розділі 8.
ПасткаЧим guard відрізняється від middleware, якщо обидва можуть перевірити токен?
Middleware не знає, який handler буде викликано. Guard отримує ExecutionContext (клас + метод) і через Reflector читає метадані (@Roles, @Public) — тому авторизація з урахуванням маршруту належить guards. Також guards працюють у WebSocket- і microservice-контекстах.
ПасткаЯк Nest дізнається, що в конструктор треба передати UsersService?
З emitDecoratorMetadata TypeScript генерує __metadata("design:paramtypes", [UsersService]) для задекорованого класу; Nest читає це через reflect-metadata і використовує клас як токен. Тому інтерфейси потребують @Inject(TOKEN) (у метаданих буде Object), а import type або type stripping ламають DI.
ПасткаВи зробили один провайдер Scope.REQUEST. Що станеться з рештою графа?
Усі, хто від нього залежить (транзитивно, аж до контролерів), теж стають request-scoped і створюються на кожен запит. У нашому експерименті DEFAULT-сервіс і контролер створилися по 3 рази на 3 запити. Ціна — алокації й латентність. Альтернатива — AsyncLocalStorage (nestjs-cls) або durable providers.
БазаЩо роблять whitelist, forbidNonWhitelisted і transform у ValidationPipe?
whitelist — видаляє поля без декораторів; forbidNonWhitelisted — повертає 400 замість видалення; transform — створює екземпляр DTO і застосовує перетворення типів ("36" → 36 з @Type). Перші два — захист від mass assignment.
Пасткаapp.useGlobalGuards(new AuthGuard()) — і guard не може отримати JwtService. Чому?
Екземпляр створений вручну поза DI-контейнером — залежності ніхто не інжектить. Реєструйте як провайдер: { provide: APP_GUARD, useClass: AuthGuard } у модулі; тоді Nest створить його через DI.
ПасткаПомилка зникла після того, як UsersService додали у providers двох модулів. Що не так?
Тепер існує два екземпляри сервісу з окремим станом. Правильно: оголосити в UsersModule, додати в exports, а в інших модулях — imports: [UsersModule].
БазаЩо таке dynamic module і навіщо forRoot/forFeature?
Модуль, конфігурований під час імпорту: статичний метод повертає DynamicModule з провайдерами, що залежать від опцій. forRoot — один раз у корені (підключення), forFeature — у feature-модулях (репозиторії для конкретних сутностей), forRootAsync — опції з DI (useFactory + inject: [ConfigService]).
ПасткаДодали forwardRef з обох боків циклу, а застосунок падає з Cannot access 'AService' before initialization. Чому?
В ESM (а NestJS 12 — ESM) циклічний імпорт + emitDecoratorMetadata дає жадібне посилання на клас у design:paramtypes на етапі завантаження модуля — TDZ. forwardRef тут не допомагає. Обхід — тип-обгортка (Ref<T>), щоб у метаданих був Object; рішення — розірвати цикл (третій сервіс або події).
БазаЯк протестувати сервіс, не піднімаючи БД?
Test.createTestingModule({ imports: [UsersModule] }).overrideProvider(USERS_REPO).useValue(fake).compile(), потім moduleRef.get(UsersService). Граф справжній, підмінена одна вершина. Для e2e — createNestApplication() + supertest або Fastify inject.
ПасткаЧому не можна запустити Nest-застосунок через node --experimental-strip-types / просто node main.ts?
Type stripping лише стирає типи і не підтримує не-erasable синтаксис: legacy-декоратори, parameter properties (constructor(private x)) і, головне, не генерує design:paramtypes. Потрібен tsc або SWC.
БазаДе в шаровій архітектурі має жити мапінг «замовлення вже оплачене» → HTTP 409?
У транспортному шарі (exception filter чи контролер). Сервіс кидає доменну помилку (OrderAlreadyPaid) і не знає про HTTP — тоді той самий сервіс можна викликати з черги, крону чи CLI.
ПасткаЧи варто брати Nest для serverless-функцій?
Зазвичай ні: холодний старт включає сканування модулів, рефлексію та інстанціювання всього графа. Можна пом'якшити (lazy-loading модулів через LazyModuleLoader, кешування app між викликами, SWC-бандл), але Hono/Fastify стартують помітно швидше. Див. туторіал 19.

16 Як запам'ятати

Образи для швидкого відтворення архітектури й механізмів Nest.

1
Шари
Контролер розбирає HTTP, сервіс виконує сценарій, домен тримає правила, репозиторій — дані.
Асоціація: ресторан — офіціант (контролер), кухар (сервіс), рецепт (домен), комора (репозиторій). Офіціант не готує.
2
Ports & adapters
Ядро оголошує інтерфейси, інфраструктура їх реалізує й залежить від ядра.
Асоціація: розетка (порт) і вилки різних приладів (адаптери) — стіна не знає, що в неї вставлять.
3
@Module exports
Провайдер видно лише в модулі-власнику і в тих, хто імпортує модуль, що його експортує.
Асоціація: вітрина магазину — склад (providers) бачать лише працівники, покупці — тільки вітрину (exports).
4
DI-контейнер
Будує граф з метаданих конструкторів і створює об'єкти знизу вгору.
Асоціація: збирання LEGO за інструкцією — спершу дрібні деталі, потім блоки, потім модель.
5
Scope.REQUEST
Новий екземпляр на запит; заражає всіх залежних аж до контролера.
Асоціація: одноразовий посуд — зручно, але вся кухня перемикається на одноразове, і сміття багато.
6
design:paramtypes
Метадані з типами параметрів конструктора, які генерує tsc і читає Nest.
Асоціація: бирка на валізі — без неї (type stripping) багаж не доїде до власника.
7
Lifecycle
Middleware → Guards → Interceptors → Pipes → Handler → Interceptors → (Filters).
Асоціація: «Мій Гість Іде По Хол Ідучи (Фільтр)» — двері, охорона, рецепція, металошукач, зала, рецепція, лікарня при пригодах.
8
ValidationPipe whitelist
Видаляє або забороняє поля без декораторів — захист від mass assignment.
Асоціація: фейсконтроль за списком — кого нема в списку (isAdmin), того не пускають.
9
overrideProvider
Підміна однієї вершини справжнього графа в тесті.
Асоціація: дублер у кіно — сцена та сама, лише небезпечний трюк виконує інша людина.
10
forwardRef в ESM
Не рятує від TDZ у метаданих; потрібна тип-обгортка або розрив циклу.
Асоціація: двоє тримають двері одне для одного — ніхто не проходить; хтось має відійти.
