01 fs: три API

Одна й та сама операція є в трьох варіантах; вибір між ними — це вибір "блокувати event loop чи ні".

three-apis.mjs
import fs from 'node:fs';
import { readFile } from 'node:fs/promises';

// 1) Sync — блокує весь потік, поки ОС не віддасть дані; помилка = throw
const a = fs.readFileSync('config.json', 'utf8');

// 2) Callback — error-first, виконується в threadpool libuv
fs.readFile('config.json', 'utf8', (err, b) => { if (err) return handle(err); /* ... */ });

// 3) Promises — те саме, що callback, але з await; рекомендований стиль
const c = await readFile('config.json', 'utf8');
APIБлокує event loop?Де виконуєтьсяКоли доречний
fs.*Syncтакголовний потікстарт застосунку, CLI-скрипти, build-тули, require-час
fs.*(cb)ніlibuv threadpool (4 потоки за замовчуванням)легасі-код, максимальна швидкодія в гарячих шляхах
fs/promisesнітой самий threadpoolза замовчуванням у новому коді

Коли sync — це нормально

  • На старті: прочитати конфіг, TLS-сертифікат, SQL-міграцію до server.listen(). Запитів ще немає — блокувати нікого. Код простіший, помилка одразу валить старт (що й треба).
  • CLI-утиліти та скрипти, які роблять одну справу послідовно: паралельно обслуговувати нікого.
  • Ніколи — в обробнику HTTP-запиту, у колбеку черги, у будь-якому коді, що виконується "на кожен запит". Один readFileSync на 50 MB файлі — і всі паралельні запити чекають.
💡
Файлові операції в libuv — це не справжнє асинхронне I/O ОС (як epoll для сокетів), а блокуючі виклики в пулі потоків. Тому 4 повільні операції з диском (або 4 crypto.pbkdf2, або dns.lookup) можуть зайняти весь пул, і п'ята readFile чекатиме. Детально — туторіал 2 та UV_THREADPOOL_SIZE у туторіалі 8.
💼
На співбесіді запитають так "Чи завжди readFileSync — погано?" — Ні: на старті й у CLI він доречний і навіть кращий (простіше, помилка рано). Погано — в коді, що виконується конкурентно з обробкою запитів.

02 readFile vs streams, fd і FileHandle

readFile тримає весь файл у пам'яті; file descriptor — це лічильний ресурс ОС, і він закінчується.

readFile виділяє Buffer розміром із файл (максимум — близько 2–4 GB, і ще менше, якщо просите рядок). Для файлів, розмір яких ви не контролюєте (аплоади, логи, експорти), використовуйте стріми — вимір пам'яті й рецепти є в туторіалі 6. Правило: конфіги й маленькі JSON — readFile; все, що надходить від користувачів або росте з часом, — stream.

File descriptors

Кожен відкритий файл, сокет, pipe — це файловий дескриптор (ціле число в таблиці процесу). 0, 1, 2 — stdin, stdout, stderr. Ліміт на процес (ulimit -n) часто 1024 або 10 240 → якщо відкривати і не закривати — отримаєте EMFILE: too many open files.

filehandle.mjs
import { open } from 'node:fs/promises';

const fh = await open('out/config.json', 'r');     // FileHandle — обгортка над fd
try {
  console.log('fd:', fh.fd);                          // число, > 2
  const { bytesRead, buffer } = await fh.read(Buffer.alloc(4), 0, 4, 1); // 4 байти з позиції 1
  console.log(bytesRead, buffer.toString());          // 4 '"v":'
  for await (const line of fh.readLines()) { /* ... */ }
} finally {
  await fh.close();                                   // ЗАВЖДИ закривати
}

// Node 24+ / TS 5.2+: explicit resource management
// await using fh = await open('file.txt');           // close() викличеться сам при виході з блоку
  • Прапори open: 'r', 'w' (створити/обрізати), 'a' (дописати), 'wx' (створити, помилка якщо існує — простий lock-файл), 'r+'.
  • FileHandle, який зібрав GC незакритим, Node закриє сам і видасть warning — але покладатися на це не можна.
  • Масовий Promise.all(files.map(readFile)) на 50 000 файлів = EMFILE. Обмежуйте конкурентність (p-limit або пачками).
🐛
TOCTOU: if (fs.existsSync(p)) fs.readFileSync(p) — між перевіркою і дією файл можуть видалити. Правильно: просто робити операцію й обробляти err.code === 'ENOENT'. Помилки fs мають code (ENOENT, EACCES, EEXIST, EISDIR, EMFILE), syscall і path.

03 Атомарні записи і робота з деревами

writeFile не атомарний: падіння посеред запису лишить напівфайл. Класичне рішення — temp + rename.

writeFile('config.json', data) спочатку обрізає файл до 0, потім пише. Якщо процес вбили (OOM, деплой, SIGKILL) між цими кроками — на диску порожній або обрізаний JSON, і наступний старт падає на парсингу. Рішення: записати в тимчасовий файл у тій самій директорії і зробити rename — на POSIX файлових системах це атомарна заміна: читач бачить або старий файл, або новий, ніколи — половину.

atomic-write.mjs
import { open, rename } from 'node:fs/promises';
import { randomUUID } from 'node:crypto';
import path from 'node:path';

async function writeFileAtomic(file, data) {
  // та сама директорія = та сама ФС; rename між ФС не атомарний (EXDEV)
  const tmp = path.join(path.dirname(file), `.${path.basename(file)}.${randomUUID()}.tmp`);
  const fh = await open(tmp, 'w');
  try {
    await fh.writeFile(data);
    await fh.sync();            // fsync: дані на диску, а не лише в page cache
  } finally {
    await fh.close();
  }
  await rename(tmp, file);      // атомарна заміна
}

await writeFileAtomic('out/config.json', JSON.stringify({ v: 1 }));

Для абсолютної надійності після rename ще роблять fsync директорії; на практиці цим займається бібліотека write-file-atomic (її використовує npm). Windows: rename поверх відкритого іншим процесом файлу може дати EPERM — бібліотеки роблять retry.

Дерева: mkdir, cp, rm, readdir

trees.mjs
import { mkdir, cp, rm, readdir } from 'node:fs/promises';

await mkdir('out/a/b/c', { recursive: true });       // як mkdir -p; повторно — без EEXIST
await cp('out', 'out-copy', { recursive: true });     // як cp -r (стабільний з Node 22)
console.log((await readdir('out-copy', { recursive: true })).sort());
// [ 'a', 'a/b', 'a/b/c', 'config.json' ]

await rm('out-copy', { recursive: true, force: true }); // як rm -rf
await rm('does-not-exist', { recursive: true, force: true }); // force: без ENOENT
try { await rm('out/a'); } catch (e) { console.log(e.code); }  // ERR_FS_EISDIR

// glob вбудований у свіжих версіях: for await (const f of glob('src/**/*.ts')) ...
⚠️
rm(path, { recursive: true, force: true }) зі шляхом, зібраним з користувацьких даних або змінних середовища — це той самий rm -rf $DIR/ з порожньою змінною. Перевіряйте, що шлях лежить усередині очікуваної директорії (див. path traversal у s5).

04 fs.watch: чому це важко

Стеження за файлами виглядає як один виклик, але поводиться по-різному на кожній ОС.

fs.watchfs.watchFile
Механізмнативні події ОС: inotify (Linux), FSEvents/kqueue (macOS), ReadDirectoryChangesW (Windows)polling: stat() кожні N мс
Швидкодіямиттєво, дешевоCPU і затримка до інтервалу
Надійністьзалежить від ОС і ФСпрацює скрізь, навіть у мережевих ФС

Відомі пастки fs.watch

  • Дублікати подій: одне збереження в редакторі дає 2–4 події ('rename' + кілька 'change'), бо редактори пишуть у temp-файл і роблять rename (той самий атомарний патерн з s3!). Потрібен debounce.
  • filename у колбеку може бути null на деяких платформах.
  • Якщо файл замінили через rename, watcher на старому inode може "осліпнути" — дивіться за директорією, не за файлом.
  • recursive: true історично працював лише на macOS/Windows; на Linux з'явився в новіших версіях, але на великих деревах впирається в ліміт inotify watchers (fs.inotify.max_user_watches).
  • Docker-volume з хоста macOS/Windows, NFS, SMB — події часто не доходять узагалі; доводиться вмикати polling.
watch.mjs
import { watch } from 'node:fs/promises';

const ac = new AbortController();
let timer;
for await (const { eventType, filename } of watch('./config', { signal: ac.signal })) {
  clearTimeout(timer);
  timer = setTimeout(() => reload(filename), 100);   // debounce дублікатів
}

Тому інструменти розробки (Vite, webpack, nodemon) використовують chokidar або власні шари з нормалізацією, а вбудований node --watch (s13) достатній для перезапуску сервера. У продакшені для "hot reload конфігу" надійніше сигнал (SIGHUP) або періодичне перечитування, ніж watcher.

05 path: join vs resolve

join склеює сегменти, resolve будує абсолютний шлях "як cd справа наліво". Плутанина між ними — джерело багів і вразливостей.

path.js
const path = require('node:path');

path.join('/app', 'src', '../config', 'db.json');     // '/app/config/db.json'
path.resolve('/app', 'src', '../config', 'db.json');  // '/app/config/db.json'  (те саме — бо почали з абсолютного)

path.join('a', '/b', 'c');      // 'a/b/c'   ← '/b' просто ще один сегмент
path.resolve('a', '/b', 'c');   // '/b/c'    ← абсолютний сегмент "скидає" все зліва

path.join('uploads', 'img.png');      // 'uploads/img.png'  — відносний, як був
path.resolve('uploads', 'img.png');   // process.cwd() + '/uploads/img.png'  — завжди абсолютний

path.normalize('/a//b/../c/./d');                       // '/a/c/d'
path.relative('/app/src/routes', '/app/config/db.json'); // '../../config/db.json'
path.parse('/home/u/report.tar.gz');
// { root: '/', dir: '/home/u', base: 'report.tar.gz', ext: '.gz', name: 'report.tar' }
path.extname('archive.tar.gz');               // '.gz'  (лише останнє розширення)
path.basename('/x/y/file.txt', '.txt');       // 'file'

cwd ≠ директорія скрипта

path.resolve('data.json') і fs.readFile('data.json') рахуються від process.cwd() — директорії, з якої запустили процес, а не від файлу з кодом. cd / && node /app/server.js — і відносні шляхи зламалися. Шляхи до своїх ресурсів будуйте від __dirname (CJS) або import.meta.dirname (ESM, s6).

posix vs win32

path за замовчуванням працює за правилами поточної ОС. Явно: path.posix.join (для URL, S3-ключів, zip-архівів — завжди /), path.win32.join('C:\\app', 'src') → C:\app\src. path.sep — / чи \; path.delimiter — роздільник у PATH (: чи ;). Не будуйте шляхи конкатенацією рядків з '/', якщо код має працювати на Windows.

🔓
Path traversal: path.join('/srv/files', req.query.name) з name = '../../etc/passwd' дає '/etc/passwd'. join нормалізує .., а не захищає від них. Правильна перевірка: 
const root = path.resolve('/srv/files');
const target = path.resolve(root, userInput);
if (!target.startsWith(root + path.sep)) throw new Error('forbidden');

06 URL і file:// шляхи

У ESM модулі ідентифікуються URL-ами, тому конвертація URL ↔ шлях — щоденна операція.

urls.mjs
import { fileURLToPath, pathToFileURL } from 'node:url';

import.meta.url;                       // 'file:///app/src/index.js'
import.meta.dirname;                   // '/app/src'      (Node 20.11+ / 21.2+)
import.meta.filename;                  // '/app/src/index.js'

// старий спосіб (і для старіших Node):
const __dirname = path.dirname(fileURLToPath(import.meta.url));

fileURLToPath('file:///tmp/my%20dir/a.txt');     // '/tmp/my dir/a.txt'  — декодує %20
pathToFileURL('/tmp/my dir/#a.txt').href;        // 'file:///tmp/my%20dir/%23a.txt' — екранує # і пробіл
new URL('./data.json', import.meta.url);         // ресурс поруч із модулем (fs приймає URL напряму)

const u = new URL('https://api.example.com:8080/v1/orders?status=new&page=2#top');
u.hostname; u.port; u.pathname;                  // 'api.example.com' '8080' '/v1/orders'
u.searchParams.get('page');                      // '2'
u.searchParams.append('q', 'кава & чай');
u.search; // '?status=new&page=2&q=%D0%BA%D0%B0%D0%B2%D0%B0+%26+%D1%87%D0%B0%D0%B9'
⚠️
Не робіть new URL(import.meta.url).pathname як шлях: він лишить %20 замість пробілів і дасть /C:/... на Windows. Тільки fileURLToPath. І не використовуйте застарілий url.parse() — він нестрогий і мав проблеми безпеки; WHATWG URL — стандарт.

08 Життєвий цикл і коди виходу

Node-процес завершується сам, коли event loop порожній. process.exit() обриває це на півслові — і може загубити дані.

beforeExit vs exit

Задача 1СередньоСкільки разів beforeExit?
task-1.js
process.on('beforeExit', (code) => {
  console.log('beforeExit', code);
  if (!globalThis.done) {
    globalThis.done = true;
    setTimeout(() => console.log('extra work scheduled in beforeExit'), 10);
  }
});
process.on('exit', (code) => {
  console.log('exit', code);
  setTimeout(() => console.log('never'), 0);
});
console.log('main done');
process.exitCode = 3;
main done beforeExit 3 extra work scheduled in beforeExit beforeExit 3 exit 3

beforeExit емітиться щоразу, коли loop спорожнів. Перший раз ми запланували таймер — loop ожив, виконав його і знову спорожнів → другий beforeExit. Тепер нічого не заплановано → exit з кодом з process.exitCode (3, echo $? теж покаже 3). Таймер у exit ніколи не спрацює: після цієї події loop вже не крутиться.

Якщо замість цього викликати process.exit(0) одразу після setTimeout — побачите лише exit 0: ні таймера, ні beforeExit (перевірено).

Чому exitCode, а не exit()

exit-truncation.sh
$ node -e "process.stdout.write('x'.repeat(5e6)); process.exit(0)" | wc -c
  131072          # ← загубили 4.87 MB виводу!
$ node -e "process.stdout.write('x'.repeat(5e6)); process.exitCode = 0" | wc -c
 5000000

Коли stdout — pipe (а в Docker/Kubernetes логи йдуть саме в pipe), запис у нього асинхронний. process.exit() завершує процес, не дочекавшись, поки буфер зіллється, — і хвіст логів, включно з повідомленням про помилку, зникає. process.exitCode = n лише встановлює код, а процес завершиться природно, коли все дописано і всі ресурси закриті. Правило: exit() — лише як аварійний "force exit" за таймаутом (див. graceful shutdown у s9).

uncaughtException і unhandledRejection

uncaught.js
process.on('uncaughtException', (err, origin) => {
  console.log('caught:', err.message, '| origin:', origin);
  process.exitCode = 1;
});
process.on('exit', (c) => console.log('exit', c));
setTimeout(() => { throw new Error('boom in timer'); }, 0);
Promise.reject(new Error('rejected promise'));

// caught: rejected promise | origin: unhandledRejection   ← з Node 15 rejection → exception
// caught: boom in timer | origin: uncaughtException
// exit 1
  • З Node 15 --unhandled-rejections=throw за замовчуванням: неперехоплений rejection стає uncaughtException і без обробника валить процес з кодом 1. Якщо є слухач 'unhandledRejection' — процес не падає (перевірено: "still alive").
  • uncaughtException — не спосіб "продовжити роботу". Після невідомого винятку стан процесу невизначений (недозакриті транзакції, зламані інваріанти). Правильно: залогувати, віддати метрику, почати graceful shutdown і дати оркестратору (k8s, PM2) підняти новий процес.
  • Для спостереження без зміни поведінки є 'uncaughtExceptionMonitor'.

На співбесіді запитають так "Pod у Kubernetes рестартиться з exit code 137 — що це?" — 128 + 9 = SIGKILL. Найчастіше OOMKilled (перевищено memory limit; підтвердити в kubectl describe pod) або процес не завершився за terminationGracePeriodSeconds після SIGTERM.

09 Сигнали, stdio і graceful shutdown

Деплой без втрати запитів = правильна реакція на SIGTERM. Це питання, яке перевіряє реальний продакшен-досвід.

СигналХто надсилаєМожна перехопити?Поведінка Node за замовчуванням

Спроба process.on('SIGKILL', ...) кидає EINVAL (перевірено) — ядро не дає процесу шансу. Тому все важливе має бути зроблено до SIGKILL: у вікні між SIGTERM і закінченням grace period.

graceful.js
const http = require('node:http');
const server = http.createServer((req, res) => res.end('ok')).listen(3000);

let shuttingDown = false;
function shutdown(signal) {
  if (shuttingDown) return;                 // другий Ctrl+C ігноруємо (або робимо force)
  shuttingDown = true;
  console.log(`got ${signal}, closing server...`);
  server.close(async () => {                // 1. перестати приймати, дочекатись in-flight запитів
    await db.end();                         // 2. закрити пули, черги, flush телеметрії
    console.log('server closed, cleanup done');
    process.exitCode = 0;                   // 3. процес вийде сам, коли loop спорожніє
  });
  server.closeIdleConnections();            // keep-alive сокети без запитів — закрити одразу
  setTimeout(() => { console.log('force exit'); process.exit(1); }, 10_000).unref(); // страховка
}
process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
output (батько шле SIGTERM, потім іншому дочірньому — SIGKILL)
[child] SIGKILL listener: EINVAL
[child] got SIGTERM, closing server...
[child] server closed, cleanup done
[parent] stubborn child code = null signal = SIGKILL     ← ігнорував SIGTERM, вбили -9
[parent] child exit code = 0 signal = null               ← завершився сам, код 0
  • .unref() на таймері-страховці: він не тримає процес живим, якщо все закрилося раніше.
  • У Kubernetes між SIGTERM і видаленням pod з endpoints є гонка: деякий час трафік ще може приходити. Тому часто перші кілька секунд після SIGTERM readiness-probe повертає 503, а сервер ще приймає запити (туторіал 17).
  • PID 1 у Docker: якщо запустити CMD npm start, сигнал отримає npm, який історично не завжди прокидав його дитині. Використовуйте CMD ["node", "server.js"] (exec-форма) і --init/tini, щоб хтось збирав зомбі-процеси. Shell-форма CMD node server.js ставить PID 1 = sh.
  • На Windows сигналів у POSIX-сенсі немає: Node емулює SIGINT (Ctrl+C) і SIGBREAK; kill('SIGTERM') просто вбиває.

stdin, stdout, stderr — це стріми

  • process.stdout/stderr — Writable, process.stdin — Readable. Отже, process.stdin.pipe(transform).pipe(process.stdout) — валідна Unix-утиліта.
  • Синхронність запису залежить від типу: файли — синхронно; TTY — синхронно на Linux/macOS; pipes і сокети — асинхронно на Linux (звідси і обрізаний вивід у s8).
  • console.log → stdout, console.error → stderr. Дані — у stdout, діагностика — у stderr: тоді mytool | jq працює, а помилки видно в терміналі.
  • process.stdout.isTTY — true, якщо вивід у термінал (тоді доречні кольори й прогрес-бари); у pipe/файл — undefined.
  • EPIPE: mytool | head -1 — head закрився, наступний write падає. CLI мають це тихо ігнорувати.

10 Модуль os

Інформація про машину: скільки ядер, пам'яті, де temp-директорія, які мережеві інтерфейси.

os.js
const os = require('node:os');

os.cpus().length;            // 16 — логічні ядра хоста (з моделлю й часами кожного)
os.availableParallelism();   // 16 — рекомендована кількість паралельних задач (Node 18.14+)
os.totalmem(); os.freemem(); // байти
os.EOL;                      // '\n' (POSIX) або '\r\n' (Windows)
os.tmpdir();                 // '/var/folders/.../T' на macOS, '/tmp' на Linux
os.platform(); os.arch(); os.type(); os.release();
os.networkInterfaces();      // { lo0: [...], en0: [{ address, family, internal, mac }] }
os.loadavg();                // [1, 5, 15]-хвилинне навантаження (на Windows — нулі)
os.homedir(); os.hostname(); os.userInfo();
os.constants.signals.SIGTERM; // 15
⚠️
Контейнери: os.cpus().length і os.totalmem() історично показують ресурси хоста, а не ліміти cgroup. Pod з cpu: 2 на 64-ядерній ноді отримає 64 — і запустить 64 cluster-воркери, які задушать один одного. availableParallelism() краще (враховує CPU affinity), а для пам'яті — process.constrainedMemory() (cgroup-ліміт). Надійніше — явно задати кількість воркерів через env.

Для тимчасових файлів — fs.mkdtemp(path.join(os.tmpdir(), 'myapp-')) (унікальна директорія, без колізій між процесами) і прибирання в finally.

11 child_process

Чотири функції для запуску процесів відрізняються трьома речами: чи є shell, чи буферизується вивід, чи є IPC-канал.

ФункціяShell?ВивідIPCДля чого
spawn(cmd, args)ні (опц. shell: true)стріми stdout/stderrопційнодовгі процеси, великий вивід (ffmpeg, git clone)
execFile(file, args, cb)нібуфер у пам'ять (maxBuffer 1 MB)нікоротка команда з невеликим виводом, безпечні аргументи
exec(command, cb)так (/bin/sh -c)буфер у пам'ятьніshell-фічі: pipes, glob, && — з ДОВІРЕНИМ рядком
fork(modulePath)ніуспадкований stdioтак, завждиінший Node-скрипт з send()/'message'

Кожна має sync-версію (spawnSync, execSync, execFileSync) — блокують event loop, доречні в скриптах і на старті. Промісні версії: util.promisify(execFile) → { stdout, stderr }.

Shell injection

injection.js
const { exec, execFile } = require('node:child_process');
const userInput = 'report.txt; echo HACKED';     // уявіть: rm -rf / або curl evil.sh | sh

exec(`echo processing ${userInput}`, (err, stdout) => console.log('[exec]    ', JSON.stringify(stdout)));
execFile('echo', ['processing', userInput], (err, stdout) => console.log('[execFile]', JSON.stringify(stdout)));

// [exec]     "processing report.txt\nHACKED\n"          ← shell виконав ДРУГУ команду
// [execFile] "processing report.txt; echo HACKED\n"    ← один аргумент, буквально
🔓
Правило: ніколи не підставляйте зовнішні дані в рядок для exec/execSync або spawn(..., { shell: true }). Використовуйте execFile/spawn з масивом аргументів — тоді ;, |, $(), бектики не мають спецзначення. Але й тут лишається argument injection: userInput = '--upload-pack=evil' для git. Ставте '--' перед позиційними аргументами і валідуйте за allowlist. На Windows .bat/.cmd завжди запускаються через cmd.exe — окремий клас вразливостей (саме тому Node у 2024 заборонив їх спавн без shell: true).

spawn: стріми й stdio

spawn.js
const { spawn } = require('node:child_process');
const p = spawn('node', ['-e', 'for (let i=0;i<3;i++) console.log("line", i); console.error("warn!"); process.exit(2)']);
p.stdout.on('data', (d) => process.stdout.write('[spawn stdout] ' + d));
p.stderr.on('data', (d) => process.stdout.write('[spawn stderr] ' + d));
p.on('close', (code) => console.log('[spawn] exit code', code));

// [spawn stdout] line 0
// [spawn stdout] line 1
// line 2                    ← "line 1\nline 2\n" прийшли ОДНИМ chunk-ом: chunk ≠ рядок!
// [spawn stderr] warn!
// [spawn] exit code 2
  • stdio: 'pipe' (default) — батько отримує стріми; 'inherit' — дитина пише прямо в термінал батька (для npm install з прогрес-баром); 'ignore' — у /dev/null. Можна масивом: ['ignore', 'pipe', 'inherit', 'ipc'].
  • Пастка: з 'pipe' ви мусите читати stdout/stderr. Якщо дитина пише багато, а ви не читаєте, — pipe-буфер ОС (~64 KB) заповниться, дитина заблокується на write і "зависне" назавжди.
  • 'exit' vs 'close': exit — процес завершився, close — і всі його stdio-стріми закриті (вивід дочитано). Для обробки виводу чекайте 'close'.
  • 'error' — процес не вдалося запустити (ENOENT — немає такої програми). Без слухача — падіння (s3 туторіалу 6).
  • execFile-сімейство має timeout, maxBuffer (перевищення → ERR_CHILD_PROCESS_STDIO_MAXBUFFER, перевірено), signal (AbortController), cwd, env.

fork + IPC

fork-parent.js / fork-child.js
// parent
const child = fork('./fork-child.js');
child.on('message', (m) => { console.log('[parent] got', m); child.disconnect(); });
child.send({ cmd: 'sum', nums: [1, 2, 3, 4] });
child.on('exit', (c) => console.log('[parent] child exited', c));

// child
process.on('message', (m) => {
  if (m.cmd === 'sum') process.send({ result: m.nums.reduce((a, b) => a + b, 0) });
});
process.on('disconnect', () => console.log('[child] IPC closed, exiting'));

// [parent] got { result: 10 }
// [child] IPC closed, exiting       ← відкритий IPC-канал тримає дитину живою; disconnect() відпускає
// [parent] child exited 0

Повідомлення серіалізуються в JSON (або serialization: 'advanced' — structured clone з Map, Set, BigInt, Buffer). Кожна дитина — окремий V8 і ~30–50 MB RSS. Для CPU-паралелізму всередині одного сервісу сучасніший вибір — worker_threads (туторіал 8).

Вбити дерево процесів і detached

kill-tree.js
// shell запускає дві "онуки"; kill() вбиває лише shell
const a = spawn('sh', ['-c', 'sleep 77 & sleep 77 & wait']);
a.kill('SIGTERM');
// after child.kill(): 2 sleep processes still alive     ← сироти, переїхали до init

// detached: true → дитина стає лідером НОВОЇ групи процесів (POSIX setsid)
const b = spawn('sh', ['-c', 'sleep 77 & sleep 77 & wait'], { detached: true, stdio: 'ignore' });
process.kill(-b.pid, 'SIGTERM');                          // мінус = вся група
// after process.kill(-pid): 0 sleep processes alive
  • detached: true + child.unref() + stdio: 'ignore' — запустити фоновий процес, який переживе батька (демон). Без unref батько чекатиме на дитину.
  • На Windows групи процесів працюють інакше; там використовують taskkill /pid N /T /F (пакет tree-kill).
  • Коли падає батько, діти не вмирають автоматично (на Linux). Тому в тест-раннерах і dev-серверах "висять" процеси — потрібне явне прибирання на 'exit'/SIGTERM.

cli.mjs
#!/usr/bin/env node
import { parseArgs, styleText } from 'node:util';
import { createInterface } from 'node:readline/promises';
import { stdin, stdout, stderr } from 'node:process';

const { values, positionals } = parseArgs({
  allowPositionals: true,
  options: {
    env:    { type: 'string', short: 'e', default: 'dev' },
    dryRun: { type: 'boolean', default: false },
    tag:    { type: 'string', multiple: true },
    help:   { type: 'boolean', short: 'h' },
  },
});   // strict за замовчуванням: невідомий прапор → TypeError ERR_PARSE_ARGS_UNKNOWN_OPTION

if (values.help) { console.log('usage: deploy [--env prod] [--dryRun] <service>'); process.exit(0); }
const [service] = positionals;
if (!service) {
  stderr.write(styleText('red', 'error: service is required\n'));
  process.exitCode = 2;                       // 2 = помилка використання
} else {
  console.log(values, positionals);
  const rl = createInterface({ input: stdin, output: stdout });
  const answer = await rl.question(`Deploy ${styleText(['bold', 'yellow'], service)} to ${values.env}? (y/N) `);
  rl.close();
  if (answer.trim().toLowerCase() !== 'y') { console.log(styleText('gray', 'aborted')); process.exitCode = 1; }
  else console.log(styleText('green', '✔ deployed'));
}

14 Каверзні питання співбесіди

Тут відрізняються ті, хто деплоїв Node у продакшен, від тих, хто лише писав роути.

БазаКоли fs.readFileSync — це нормально?
На старті (до listen) і в CLI/скриптах: блокувати нікого, код простіший, помилка рано. Ніколи — в коді, що виконується на кожен запит: блокує весь event loop.
Пасткаpath.join('a', '/b') vs path.resolve('a', '/b')?
join → 'a/b' (просто сегменти). resolve → '/b': іде справа наліво до першого абсолютного сегмента; без абсолютного — додає process.cwd(). Жоден з них не захищає від ../ у користувацькому вводі — потрібна перевірка префікса після resolve.
ПасткаЧому process.exitCode краще за process.exit()?
exit() завершує негайно: асинхронні записи в stdout-pipe, незакриті з'єднання, проміси — відкидаються. Ми бачили: з 5 MB виводу в pipe дійшло 131 072 байти. exitCode лише задає код — процес вийде сам, коли loop спорожніє. exit() — тільки як force-exit за таймаутом.
БазаЯк реалізувати graceful shutdown?
На SIGTERM/SIGINT: перестати приймати (server.close(), readiness → 503), дочекатися in-flight запитів, закрити idle keep-alive, закрити пули БД/черги, flush логів і метрик, встановити exitCode. Страховка — setTimeout(() => process.exit(1), N).unref() менше за grace period оркестратора.
ПасткаЧи можна перехопити SIGKILL?
Ні. process.on('SIGKILL') кидає EINVAL; ядро вбиває процес без попередження. Те ж з SIGSTOP. Тому cleanup має завершитися в вікні після SIGTERM. Exit code у оболонці — 137.
Базаspawn vs exec vs execFile vs fork?
exec — через shell, вивід у буфер; execFile — без shell, буфер; spawn — без shell, стріми (великий/довгий вивід); fork — Node-скрипт з IPC (send/'message'). Лише exec (і shell: true) інтерпретує рядок shell-ом.
ПасткаЧим небезпечний exec(`convert ${file}`)?
Shell injection: file = 'a.png; rm -rf ~' виконає другу команду. Лікування — execFile('convert', [file]), '--' перед позиційними аргументами, allowlist значень. Масив аргументів знімає shell-метасимволи, але не argument injection.
ПасткаЧому дочірній процес "завис" без жодної помилки?
Найчастіше: stdio: 'pipe', а батько не читає stdout/stderr. Pipe-буфер ОС (~64 KB) заповнився, дитина заблокувалась на write. Або відкритий IPC-канал fork тримає її живою — потрібен disconnect().
БазаЯк убити процес разом з його нащадками?
child.kill() вбиває лише прямого нащадка — онуки стають сиротами. На POSIX: spawn(..., { detached: true }) (нова група процесів) і process.kill(-child.pid, 'SIGTERM'). На Windows — taskkill /T /F.
ПасткаExit code 137 / 143 / 130?
128 + номер сигналу: 137 = SIGKILL (часто OOMKilled або не вклались у grace period), 143 = SIGTERM (вас зупинили і ви не перехопили сигнал), 130 = SIGINT (Ctrl+C).
ПасткаЧому в Docker Node не реагує на docker stop?
Процес — PID 1, а для PID 1 ядро не застосовує дії за замовчуванням для сигналів — без явного обробника SIGTERM нічого не станеться, і через 10 с прийде SIGKILL. Або сигнал отримує sh/npm і не прокидає. Рішення: exec-форма CMD ["node", "server.js"], явний обробник SIGTERM, --init/tini.
БазаЯк атомарно перезаписати файл?
Записати в temp-файл у тій самій директорії (та сама ФС), fsync, закрити, rename поверх цільового. Читачі бачать або старий, або новий вміст. rename між різними ФС дає EXDEV.
Пасткаos.cpus().length у контейнері з лімітом 2 CPU?
Може повернути кількість ядер хоста (64), бо cgroup quota не змінює видимих CPU. Краще os.availableParallelism() і явна конфігурація кількості воркерів; пам'ять — process.constrainedMemory().
БазаЧи є --permission повноцінною пісочницею?
Ні — це запобіжник проти випадкового/компрометованого доступу (fs, child_process, workers, addons). Не захищає від зловмисного коду з повним виконанням. Ізоляція — контейнери, окремий користувач ОС, seccomp.

16 Як запам'ятати

Короткі образи для кожної ключової ідеї.

1
*Sync API
Блокує event loop; ок на старті й у CLI.
Асоціація: прибирати ресторан до відкриття — нормально; посеред обіду, коли зал повний, — ні.
2
temp + rename
Атомарний запис: читач бачить або старе, або нове.
Асоціація: готуєш нову вітрину за ширмою і знімаєш ширму одним рухом.
3
path.resolve
Справа наліво до першого абсолютного, інакше від cwd.
Асоціація: серія команд cd — cd /b посередині перекреслює все, що було до нього.
4
exitCode vs exit()
exitCode — вийти, коли все дописано; exit() — обірвати зараз.
Асоціація: сказати "останнє замовлення" в барі vs вимкнути світло, поки люди ще п'ють.
5
SIGTERM vs SIGKILL
SIGTERM — прохання (можна прибрати за собою), SIGKILL — неперехоплюване вбивство.
Асоціація: "готель закривається за 30 секунд, збирайте речі" vs охоронець виносить вас разом з ліжком.
6
128 + N
Код виходу процесу, вбитого сигналом N: 137 = KILL, 143 = TERM.
Асоціація: "137 — вбили сім раз" (…7), "143 — попросили по-доброму".
7
exec
Єдиний варіант через shell — і єдиний з shell injection за замовчуванням.
Асоціація: передати записку через перекладача-імпровізатора: він може "додати від себе".
8
spawn
Без shell, вивід стрімами — для довгих процесів і великого виводу.
Асоціація: водопровід (тече постійно) vs відро (exec — набрали і принесли все разом).
9
fork
Новий Node-процес з IPC-каналом send/'message'.
Асоціація: найняти помічника в інший офіс і дати йому рацію.
10
--permission
Запобіжник прав на fs/процеси/воркери, не пісочниця.
Асоціація: ремінь безпеки: рятує в типовій аварії, але не робить з машини танк.
