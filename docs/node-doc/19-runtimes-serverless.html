01 Чому з'явились альтернативи

Node вирішив задачу "JS на сервері" у 2009-му; за 15 років накопичились рішення, які автор сам назвав помилками, — і нові вимоги, яких тоді не було.

У 2018 році Ryan Dahl, автор Node, виступив з доповіддю "10 Things I Regret About Node.js" і того ж вечора показав прототип Deno. Серед "жалів": відмова від Promise у ранніх API (звідси callback-епоха), відсутність моделі безпеки (будь-який npm-пакет може читати ~/.ssh і ходити в мережу), node_modules з його алгоритмом резолву, package.json як централізований реєстр модулів, index.js-магія, GYP для нативних аддонів.

Паралельно змінився світ:

  • TypeScript став мейнстрімом — а в Node він вимагав ланцюжка tsc/ts-node/babel/esbuild і конфігів.
  • Браузерні стандарти дозріли: fetch, Request/Response, Web Streams, URL, crypto.subtle, ES-модулі. Node мав власні аналоги (http, stream, CJS) — код не переносився між браузером і сервером.
  • Інструментальна втома: окремо npm/yarn/pnpm, jest/vitest, webpack/esbuild, prettier/eslint, nodemon, dotenv.
  • Edge і serverless: оплата за мілісекунди і запуск у сотнях точок світу вимагають старту за мілісекунди, а не секунди.
  • Supply-chain атаки на npm (event-stream, ua-parser-js, шкідливі postinstall) зробили безпеку за замовчуванням реальною вимогою.
🧠 Запам'ятай: Deno відповідав на "безпеку і стандарти", Bun — на "швидкість і all-in-one", edge — на "мілісекундний старт"; Node відповів, забравши найкраще собі.

02 Архітектура трьох рантаймів

Усі три — "JS-рушій + асинхронний I/O + системні API", але кожен шар зроблено з різних матеріалів.

Наслідки для практики:

  • JavaScriptCore vs V8: JSC має чотири рівні виконання (LLInt → Baseline → DFG → FTL) і зазвичай швидше стартує, V8 (Ignition → Sparkplug → Maglev → TurboFan) — більш "прогріваний" на довгих навантаженнях. На мікробенчмарках старту Bun часто виграє; на довгоживучому сервері з реальною БД різниця зазвичай малопомітна.
  • Deno і Node на V8 → однакова поведінка мови, однаковий формат heap-snapshot, схожі прапорці --v8-options.
  • Нативні аддони: Node-API (N-API) — це C ABI, тому його можна реалізувати в іншому рантаймі; Bun і Deno це роблять. А от аддони, що лізуть у V8 API напряму (старий NAN-стиль), у Bun працювати не можуть принципово — там немає V8.

Детально про V8 і libuv у Node — туторіал 1.

03 Deno

"Node, зроблений заново з урахуванням помилок": безпека за замовчуванням, TypeScript без налаштувань, веб-стандарти як основний API.

Secure by default: дозволи

Скрипт у Deno за замовчуванням не може читати файли, ходити в мережу, читати env чи запускати процеси. Кожен доступ — явний прапорець, причому з гранулярністю до хоста чи шляху:

terminal
deno run main.ts                                   # доступ до мережі -> інтерактивний запит / помилка
deno run --allow-net=api.stripe.com:443 --allow-env=STRIPE_KEY --allow-read=./data main.ts
deno run -A main.ts                                # allow all (так роблять усі на практиці... і даремно)
deno run --allow-net --deny-net=169.254.169.254 main.ts   # deny-* має пріоритет (блок metadata-сервісу хмари)

Чому це важливо: залежність, що раптом почала відправляти process.env на чужий сервер, у Deno впаде з помилкою дозволу. Обмеження: дозволи — на весь процес, а не на окремий пакет; якщо застосунку потрібна мережа, вона є і в усіх його залежностей.

TypeScript, Web API, std

  • TS/JSX/TSX запускаються напряму (транспіляція на Rust через swc); deno check — перевірка типів.
  • API — веб-стандарти: fetch, Request/Response, Web Streams, WebSocket, crypto.subtle, localStorage, BroadcastChannel. Сервер — Deno.serve((req) => new Response('hi')).
  • Стандартна бібліотека @std/* (path, fs, http, assert, csv, testing...) — аудитовані модулі, що публікуються в JSR (новий реєстр від команди Deno: публікація TS без збірки, працює і для Node/Bun).
  • Вбудований тулінг: deno fmt, deno lint, deno test, deno bench, deno doc, deno compile (один виконуваний файл), deno task, deno jupyter.

Deno 2: розворот до сумісності

Deno 1.x вимагав імпортів за URL і погано дружив з npm — і це гальмувало adoption. Deno 2 (жовтень 2024) зробив прагматичний поворот: специфікатори npm: і node:, підтримка package.json і node_modules, запуск багатьох Node-фреймворків (Express, Next.js, Astro), робота з приватними npm-реєстрами, LTS-гілка.

main.ts
import express from 'npm:express@4';          // npm-пакет без npm install
import { readFile } from 'node:fs/promises';    // Node built-in через сумісний шар
import { join } from 'jsr:@std/path';           // JSR

const app = express();
app.get('/', async (_req, res) => res.send(await readFile(join('.', 'hello.txt'), 'utf8')));
app.listen(3000);
deno.json
{
  "tasks": { "dev": "deno run --watch --allow-net --allow-read main.ts" },
  "imports": {
    "@std/path": "jsr:@std/path@^1",
    "express": "npm:express@^4"
  },
  "compilerOptions": { "strict": true },
  "fmt": { "lineWidth": 100 },
  "lint": { "rules": { "exclude": ["no-explicit-any"] } }
}

deno.json — один файл замість package.json + tsconfig.json + .prettierrc + .eslintrc, а imports — це стандартна import map.

Deno Deploy та екосистема

Deno Deploy — хостинг від авторів Deno, що запускає код на V8-ізолятах по всьому світу (див. розділ 7), з вбудованими сервісами на кшталт Deno KV (key-value сховище з транзакціями). Це аналог Cloudflare Workers, але з Deno API.

💡
Чесна оцінка. Технічно Deno дуже якісний, але більшість продакшн-бекендів лишаються на Node: екосистема, найм, APM-агенти, хмарні рантайми та "ніхто не звільнений за вибір Node". Deno найчастіше беруть для скриптів/CLI (дозволи + один файл), edge-функцій (Supabase Edge Functions працюють на Deno) і нових сервісів, де команда готова.

04 Bun

Ставка на швидкість і "один бінарник замість десяти інструментів" — і на сумісність з Node як drop-in заміна.

Що всередині

Bun написаний на Zig (мова системного рівня з ручним керуванням пам'яттю, без прихованих алокацій) і використовує JavaScriptCore — рушій Safari — замість V8. HTTP-сервер побудований на uWebSockets, багато "гарячих" шляхів (читання файлів, парсинг, серіалізація) реалізовані нативно.

Швидкість: заяви vs реальність

  • Реально швидше: bun install (глобальний кеш, hardlinks/clonefile, паралельність — часто в рази швидше за npm), старт процесу, запуск TS без компіляції, bun test на великих наборах.
  • "Hello world" бенчмарки HTTP показують великі цифри, але реальний сервіс упирається в БД, мережу, JSON, бізнес-логіку. Коли ендпоінт чекає Postgres 20 мс, різниця рантаймів у 50 мкс на запит не видна.
  • Довгоживучі CPU-навантаження: V8 TurboFan і JSC FTL — обидва топові оптимізуючі компілятори; переможець залежить від коду. Міряйте свій навантажувальний профіль (див. туторіал 15).

Прогалини сумісності

Bun позиціонується як drop-in заміна Node і проходить значну частину тестів Node, але "майже" — ключове слово:

  • Аддони, що використовують V8 API напряму (не Node-API), — не працюють принципово.
  • Частина node:* модулів реалізована неповністю або з відмінностями в краях (історично — vm, inspector, worker_threads, http2, тонкощі child_process і стрімів). Список змінюється з кожним релізом — перевіряйте сторінку сумісності.
  • APM/профайлери, що спираються на V8 inspector і async_hooks, можуть не працювати або давати неповні дані.
  • Інша семантика деяких дрібниць (порядок мікрозадач у краях, точність таймерів, поведінка GC) — тести, що спираються на них, падають.

Коли що: почніть з bun install/bun test у dev-циклі; прод-рантайм — тільки для нового сервісу з вимірюваним виграшем і без критичних нативних залежностей.

Конкуренція зробила Node кращим: за кілька релізів він вбудував більшість фіч, заради яких люди дивились на Deno і Bun.

$ node enum.ts          # enum Status { Active, Blocked }

$ node --experimental-transform-types enum.ts
0

Type stripping буквально замінює анотації типів пробілами (номери рядків і колонок у stack trace не зсуваються, source maps не потрібні). Тому синтаксис, що генерує код — enum, namespace з кодом, parameter properties у конструкторі — не підтримується без --experimental-transform-types. Типи не перевіряються: tsc --noEmit лишається в CI. У tsconfig варто ввімкнути erasableSyntaxOnly і verbatimModuleSyntax, а імпорти писати з розширенням .ts. Також type stripping не працює для файлів у node_modules.

perm.mjs
import { readFileSync } from 'node:fs';
console.log('read allowed?', process.permission.has('fs.read', '/etc/hosts'));
try {
  readFileSync('/etc/hosts', 'utf8');
} catch (e) {
  console.log(e.code, e.permission, e.resource);
}
terminal
$ node --permission --allow-fs-read="$PWD/*" perm.mjs
read allowed? false
ERR_ACCESS_DENIED FileSystemRead /etc/hosts

$ node --env-file=.env env.mjs        # .env: PORT=3000, DB_URL=postgres://localhost/app
3000 postgres://localhost/app

$ node main.cjs                       # const lib = require('./lib.mjs')  (ESM-файл!)
5 default-export [ '__esModule', 'default', 'sum' ]

Permission model у Node — це "ремінь безпеки" від випадкових помилок і вразливостей застосунку, а не sandbox проти шкідливого коду: документація прямо каже, що він не захищає від коду, який свідомо намагається обійти обмеження (наприклад, через нативні аддони). require(esm) працює лише для ESM-графа без top-level await (інакше ERR_REQUIRE_ASYNC_MODULE) — деталі в туторіалі 4.

⚠️
Дрібна пастка node:test: node --test t/ (каталог як аргумент) у Node 24 сприймається як шлях до файлу і падає; передавайте glob: node --test 't/**/*.test.mjs' або просто node --test — тоді рантайм сам знайде файли за стандартними патернами (*.test.*, test/ тощо). Перевірено на Node 24.

06 WinterTC: спільний знаменник

Щоб бібліотека працювала в Node, Deno, Bun, Workers і браузері, потрібна домовленість, які API "точно є" скрізь.

WinterCG (Web-interoperable Runtimes Community Group, 2022) — спільнота Cloudflare, Deno, Vercel, Shopify, Node та інших, яка визначала, яку частину веб-платформи мають підтримувати серверні рантайми. Наприкінці 2024 року робота переїхала в Ecma як технічний комітет TC55 — WinterTC, щоб публікувати формальні стандарти.

Головний документ — Minimum Common Web Platform API: список глобалів, які має кожен сумісний рантайм:

КатегоріяAPI
Мережаfetch, Request, Response, Headers, FormData, AbortController/AbortSignal
URL і кодуванняURL, URLSearchParams, TextEncoder/TextDecoder, atob/btoa
ПотокиReadableStream, WritableStream, TransformStream, CompressionStream
Криптографіяcrypto.getRandomValues, crypto.randomUUID, crypto.subtle
Події й таймериEventTarget, Event, setTimeout, queueMicrotask, structuredClone
ІншеBlob, File, performance.now, console, navigator.userAgent, WebAssembly

Чого там немає: файлової системи, процесів, TCP-сокетів, process, Buffer, require. Тобто бібліотека, яка хоче працювати всюди, будується на fetch + Web Streams + Web Crypto, а не на http + stream + crypto з Node. Приклади таких бібліотек: Hono, jose (JWT), Drizzle з HTTP-драйверами, офіційні SDK багатьох API.

🎉
Цікавий факт navigator.userAgent у Node 21+ повертає "Node.js/24" (на Node 24) — саме заради WinterCG-сумісного способу визначити рантайм без process.versions.

07 Edge-рантайми та ізоляти

Edge — це не "Node ближче до користувача", а принципово інша модель виконання з жорсткими обмеженнями.

Cloudflare Workers, Vercel Edge Runtime, Deno Deploy, Fastly Compute (на Wasm), Netlify Edge Functions (на Deno) запускають ваш код у сотнях дата-центрів. Щоб це було економічно, кожен запит не може мати свій контейнер — замість цього використовуються V8 isolates: окремі "всесвіти" JS (власний heap, глобали, GC) усередині одного процесу рантайму.

Обмеження edge-рантаймів (на прикладі Cloudflare Workers)

  • Немає справжньої файлової системи і процесів: ні child_process, ні запису на диск. Статичні дані — через бандл, KV, R2.
  • Ліміт CPU-часу на запит (не wall-clock!): очікування fetch не рахується, а цикл по мільйону елементів — так. На безкоштовному плані — мілісекунди, на платних — секунди-хвилини (конфігурується).
  • Пам'ять ~128 MB на ізолят, ліміт розміру бандла (одиниці–десяток MB після стиснення).
  • Node API — частково: з прапорцем nodejs_compat доступні Buffer, node:crypto, node:stream, AsyncLocalStorage та багато іншого, але не все. Пакети з нативними аддонами не працюють узагалі.
  • Немає TCP-драйверів "як у Node" історично — для БД використовують HTTP/WebSocket-драйвери або сокети через connect() API Cloudflare і Hyperdrive (пул з'єднань до Postgres з боку платформи).
  • Глобальний стан ненадійний: змінна в module scope живе, доки живе ізолят, але запити одного користувача можуть потрапити в різні ізоляти й різні дата-центри. Кеш у пам'яті — лише як оптимізація.
  • Безпека між тенантами: деякі API свідомо "загрублені" (наприклад, Date.now() не рухається під час синхронного виконання) — захист від timing side-channel атак на зразок Spectre.

08 Serverless: життєвий цикл Lambda

Більшість проблем Node у Lambda зникає, коли розумієш одне: між викликами процес не вмирає, а заморожується.

AWS Lambda запускає функцію в execution environment — Firecracker microVM з вашим кодом і рантаймом Node. Одне середовище обробляє один запит одночасно (паралельні запити → нові середовища). Середовище переживає багато викликів поспіль і проходить три фази.

handler.mjs
import { DynamoDBClient } from '@aws-sdk/client-dynamodb';   // AWS SDK v3, модульні клієнти
import { DynamoDBDocumentClient, GetCommand } from '@aws-sdk/lib-dynamodb';

// INIT-фаза: один раз на execution environment, перевикористовується теплими викликами
const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const config = await loadConfig();          // top-level await в ESM — теж у INIT

export const handler = async (event, context) => {
  // INVOKE-фаза: тільки робота запиту
  const id = event.pathParameters?.id;
  const { Item } = await ddb.send(new GetCommand({ TableName: config.table, Key: { id } }));
  if (!Item) return { statusCode: 404, body: 'not found' };
  return { statusCode: 200, headers: { 'content-type': 'application/json' }, body: JSON.stringify(Item) };
};

Різниця видна в цифрах (симуляція, запущено)

Модуль завантажується раз, handler викликається тричі в тому самому процесі — як три виклики в одному теплому середовищі:

lambda-sim.mjs
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
let connects = 0;

async function connectDb() { connects++; await sleep(150); return { query: async () => 'row' }; }

// ПОГАНО: підключення всередині handler -> платимо на КОЖЕН виклик
async function badHandler() {
  const db = await connectDb();
  return db.query();
}

// ДОБРЕ: lazy-singleton у module scope -> платимо раз на execution environment
let dbPromise;
async function goodHandler() {
  dbPromise ??= connectDb();          // зберігаємо Promise, а не результат: без гонки
  const db = await dbPromise;
  return db.query();
}

async function invoke(name, handler) {
  const t = performance.now();
  await handler();
  return `${name}: ${Math.round(performance.now() - t)}ms`;
}

for (const [name, h] of [['bad', badHandler], ['good', goodHandler]]) {
  connects = 0;
  const runs = [];
  for (let i = 0; i < 3; i++) runs.push(await invoke(`${name}#${i + 1}`, h));
  console.log(runs.join(' | '), `| connects=${connects}`);
}
output (мілісекунди можуть відрізнятися на ±1–2)
bad#1: 151ms | bad#2: 150ms | bad#3: 151ms | connects=3
good#1: 150ms | good#2: 0ms | good#3: 0ms | connects=1

Що ламається через freeze

  • "Fire-and-forget" після відповіді: sendAnalytics() без await — Promise заморозиться і, можливо, доїде при наступному виклику (або ніколи). Завжди await до return, або Lambda extension, або черга.
  • Буферизовані логери/метрики (батчинг кожні 5 с) — flush до завершення handler.
  • Протухлі з'єднання: TCP-з'єднання з БД, заморожене на 10 хвилин, сервер міг закрити — перший запит після паузи отримає ECONNRESET. Потрібні retry і перевірка з'єднання.
  • Для callback-стилю історично існував context.callbackWaitsForEmptyEventLoop = false — щоб не чекати відкриті сокети пулу; в async-handler відповідь повертається, щойно Promise резолвиться.
  • Стан у module scope — кеш, а не сховище: середовищ може бути 300, і кожне має свою копію.

09 Cold start: анатомія і ліки

Cold start — це не одна цифра, а сума кроків, і більшість із них під вашим контролем.

Що збільшує cold start у Node

  • Розмір і кількість модулів: Node парсить і компілює кожен файл; тисячі файлів з node_modules — тисячі звернень до ФС у resolve. Бандл (esbuild/rollup) з tree-shaking і мініфікацією — одна з найефективніших оптимізацій.
  • Важкі залежності на старті: монолітний AWS SDK v2 замість модульних клієнтів v3, ORM з великим рушієм, "importиш усе — використовуєш 5%".
  • Мережа в init: завантаження секретів, підключення до БД, прогрів кешів.
  • Пам'ять функції: CPU в Lambda виділяється пропорційно до memory — 128 MB = частка ядра; 1024+ MB часто дають і швидший init, і нижчу ціну за рахунок коротшого виконання.
  • VPC історично додавала секунди (створення ENI); зараз це суттєво оптимізовано, але мережеві налаштування все ще впливають.

І чесно: якщо трафік постійний, можливо, контейнер дешевший і передбачуваніший.

10 Бази даних і з'єднання в serverless

Пул з'єднань у Node — це оптимізація для одного довгоживучого процесу; serverless перетворює її на атаку на власну БД.

Звичайний Node-сервер: 4 процеси × пул 10 = 40 з'єднань до Postgres. Lambda: сплеск трафіку → 500 паралельних середовищ × пул 10 = 5 000 з'єднань. Postgres кожне з'єднання обслуговує окремим процесом (кілька MB пам'яті), max_connections зазвичай сотні — БД відмовляє з too many connections, і падає вже все, включно з "нормальними" сервісами. Плюс заморожені середовища тримають з'єднання відкритими, нічого не роблячи.

Таймаути — ланцюжок, що має зменшуватись

  • Lambda: максимум 15 хвилин виконання.
  • API Gateway перед Lambda: ~29–30 секунд за замовчуванням — функція з таймаутом 60 с за API Gateway все одно "відповість" клієнту 504 через 30 с, продовжуючи працювати (і витрачати гроші).
  • Правило: timeout клієнта БД < timeout функції < timeout шлюзу, і використовуйте context.getRemainingTimeInMillis(), щоб завершитись коректно.
  • Ретраї асинхронних викликів (SQS, EventBridge): Lambda повторить подію — обробник має бути ідемпотентним (див. туторіал 18).

13 Портабельний код: Request/Response і Hono

Найкращий захист від vendor lock-in — писати бізнес-логіку проти Web-стандартів, а рантайм-специфіку тримати в тонкому адаптері.

Ключова ідея: handler = функція (Request) => Promise<Response>. Workers, Deno, Bun, Vercel, Netlify приймають саме таку функцію. Node http історично використовує (req, res) з власними класами, тож для нього потрібен адаптер. Ось він — і він запущений на Node 24:

portable.mjs
import http from 'node:http';
import { Readable } from 'node:stream';

// 1) Портабельний хендлер: тільки Web-стандарти (Request -> Response)
const app = {
  async fetch(request) {
    const url = new URL(request.url);
    if (url.pathname === '/hello') {
      return Response.json({ hello: url.searchParams.get('name') ?? 'world' });
    }
    if (request.method === 'POST' && url.pathname === '/echo') {
      const body = await request.json();
      return new Response(JSON.stringify({ got: body }), {
        status: 201, headers: { 'content-type': 'application/json' },
      });
    }
    return new Response('not found', { status: 404 });
  },
};

// 2) Тонкий адаптер під node:http (Workers/Deno/Bun викликають app.fetch напряму)
function toNodeHandler(app) {
  return async (req, res) => {
    const url = `http://${req.headers.host}${req.url}`;
    const hasBody = req.method !== 'GET' && req.method !== 'HEAD';
    const request = new Request(url, {
      method: req.method,
      headers: req.headers,
      body: hasBody ? Readable.toWeb(req) : undefined,
      duplex: 'half',                    // обов'язково для стрімінгового body в Node
    });
    const response = await app.fetch(request);
    res.writeHead(response.status, Object.fromEntries(response.headers));
    if (response.body) Readable.fromWeb(response.body).pipe(res);
    else res.end();
  };
}

const server = http.createServer(toNodeHandler(app)).listen(0, async () => {
  const base = `http://localhost:${server.address().port}`;
  const a = await fetch(`${base}/hello?name=Node`);
  console.log(a.status, await a.json());
  const b = await fetch(`${base}/echo`, { method: 'POST', body: JSON.stringify({ x: 1 }) });
  console.log(b.status, await b.text());
  const c = await fetch(`${base}/nope`);
  console.log(c.status, await c.text());
  server.close();
});
output
200 { hello: 'Node' }
201 {"got":{"x":1}}
404 not found

Той самий app без змін: у Deno — Deno.serve(app.fetch); у Bun — Bun.serve({ fetch: app.fetch }) або export default app; у Workers — export default app.

Hono — це саме цей підхід, але з роутером і middleware

app.ts
import { Hono } from 'hono';
import { logger } from 'hono/logger';
import { jwt } from 'hono/jwt';

export const app = new Hono();
app.use('*', logger());
app.use('/api/*', jwt({ secret: process.env.JWT_SECRET!, alg: 'HS256' })); // на Workers — з c.env
app.get('/api/orders/:id', async (c) => {
  const order = await repo.find(c.req.param('id'));   // repo — інжектований, без прив'язки до рантайму
  return order ? c.json(order) : c.notFound();
});
entrypoints
// node.ts — Node
import { serve } from '@hono/node-server';
import { app } from './app';
serve({ fetch: app.fetch, port: 3000 });

// lambda.ts — AWS Lambda
import { handle } from 'hono/aws-lambda';
import { app } from './app';
export const handler = handle(app);

// worker.ts — Cloudflare Workers / Bun / Deno
import { app } from './app';
export default app;

Правила портабельного коду

  • Бізнес-логіка не імпортує node:*, Deno.*, Bun.* — тільки Web API і чисті функції.
  • Конфіг і секрети передаються параметром (у Workers env приходить в аргументі fetch(req, env), а не через process.env).
  • Uint8Array замість Buffer, crypto.subtle замість node:crypto, Web Streams замість Node streams.
  • Доступ до БД — через інтерфейс репозиторію з окремими реалізаціями (TCP-драйвер для Node, HTTP-драйвер для edge).
  • У package.json — умовні exports ("workerd", "deno", "bun", "node"), якщо бібліотеці потрібна рантайм-специфіка.

14 Каверзні питання співбесіди

Перевіряють, чи розумієте ви моделі виконання, а не чи читали маркетингові бенчмарки.

БазаЧим Deno принципово відрізняється від Node?
Deny-by-default дозволи (--allow-net, --allow-read...), TS із коробки, Web API як основний інтерфейс, вбудований тулінг (fmt/lint/test/compile), ядро на Rust + Tokio замість C++ + libuv. Рушій той самий — V8. З Deno 2 — сумісність з npm і node: модулями, тому "не можна використовувати npm" вже неправда.
ПасткаBun швидший за Node — переводимо прод?
Залежить від того, що саме повільне. Bun суттєво швидший у install, старті й тестах; на I/O-bound сервісі, що чекає БД, приріст часто непомітний. Ризики: прогалини в node:*, V8-специфічні аддони не працюють, APM/профайлинг. Правильний шлях — виміряти свій сервіс під навантаженням, почати з Bun як інструменту в dev/CI.
БазаЩо таке V8 isolate і чому edge-функції стартують за мілісекунди?
Isolate — окремий екземпляр JS-середовища (свій heap, глобали, GC) в одному процесі рантайму. Не треба створювати VM чи контейнер і запускати Node — лише новий контекст у вже теплому процесі. Ціна: немає ФС і процесів, ліміти CPU-часу та пам'яті, частковий Node API.
ПасткаЧому setInterval, який шле метрики кожні 10 с, "губить" дані в Lambda?
Між викликами середовище заморожене: таймери не тікають, фонові Promise не виконуються. Дані відправляться при наступному виклику або зникнуть із shutdown. Flush до завершення handler, Lambda extensions або EMF-метрики через логи.
БазаДе ініціалізувати клієнт БД у Lambda і чому?
У module scope (або lazy singleton, що кешує Promise) — виконується в INIT один раз на execution environment і перевикористовується теплими викликами. Усередині handler — новий connect на кожен запит. Плюс обробка протухлих з'єднань після freeze.
ПасткаТрафік виріс, і Postgres упав з "too many connections", хоча код не мінявся. Що сталося?
Lambda масштабується горизонтально: кожне паралельне середовище має свій пул. 500 середовищ × пул 10 = 5000 з'єднань. Рішення: RDS Proxy/PgBouncer, max: 1 у функції, reserved concurrency як запобіжник, HTTP-драйвери, або DynamoDB.
Пасткаnode app.ts працює — значить, Node перевіряє типи?
Ні. Type stripping лише стирає анотації (заміна пробілами), без перевірки. Синтаксис, що генерує код (enum, namespace, parameter properties), падає з ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX без --experimental-transform-types. tsc --noEmit лишається в CI.
БазаЩо таке WinterTC/WinterCG і навіщо воно бекенд-розробнику?
Група (тепер Ecma TC55), що стандартизує Minimum Common Web Platform API для серверних рантаймів: fetch, Request/Response, Web Streams, Web Crypto, URL, TextEncoder тощо. Код, що спирається тільки на нього, працює в Node, Deno, Bun, Workers без змін.
ПасткаЧи робить --permission у Node безпечним запуск недовіреного коду?
Ні. Це механізм обмеження для довіреного коду (захист від помилок і частини вразливостей), а не sandbox: документація не гарантує захист від свідомих обхідних шляхів (нативні аддони тощо). Для недовіреного коду — окремі процеси/контейнери/VM, ізоляти з жорсткою ізоляцією.
БазаКоли ви НЕ оберете serverless?
WebSocket і довгі з'єднання, задачі довші за ліміт (15 хв у Lambda), стабільно високе навантаження (дорожче за контейнери), жорсткі p99 без бюджету на provisioned concurrency, потреба в локальному стані/кеші, GPU або важкі нативні залежності.
ПасткаПеренесли API на edge — і він став повільнішим. Як так?
Функція стала ближче до користувача, але далі від БД: кожен із 5 запитів до Postgres у us-east тепер іде через океан. Edge виграє для локальної роботи (auth, редіректи, кеш, персоналізація), а data-heavy логіку краще тримати поруч із даними — або реплікувати дані на edge.
БазаЯк зробити код переносимим між Node, Lambda і Workers?
Писати handler як (Request) => Response на Web API (Hono, власний тонкий адаптер), тримати рантайм-специфіку в entrypoint-файлах, передавати env/залежності параметрами, абстрагувати доступ до БД, уникати Buffer/node:* у доменному коді.

16 Як запам'ятати

Асоціації для кожного ключового поняття.

1
Deno permissions
Процес не має доступу до мережі, ФС, env без явного прапорця.
Асоціація: готель, де картка відкриває лише ваш номер, а не всі двері поверху (Node).
2
Bun
Рантайм на JSC і Zig, що об'єднує runtime, пакетний менеджер, тести й бандлер.
Асоціація: швейцарський ніж — швидко і все в одному, але кожне лезо трохи коротше за спеціалізований інструмент.
3
Type stripping
Node стирає анотації TS пробілами й виконує JS, не перевіряючи типів.
Асоціація: коректор "замазує" нотатки на полях — текст той самий, ніхто його не перевіряв.
4
WinterTC
Стандарт мінімального спільного набору Web API для серверних рантаймів.
Асоціація: євророзетка — один штекер підходить у всіх країнах.
5
V8 isolate
Ізольований JS-світ (heap, глобали) всередині спільного процесу рантайму.
Асоціація: кабінки в коворкінгу: окремий стіл за секунду, а не окремий офіс (контейнер) чи будинок (VM).
6
Cold start
Перший виклик у новому середовищі: створення, старт рантайму, module init.
Асоціація: машина взимку — спочатку прогріти двигун, потім їхати; теплу заводиш і одразу їдеш.
7
Freeze між викликами
Після відповіді процес Lambda зупинено — таймери й фонові задачі стоять.
Асоціація: гра на паузі: персонажі завмерли посеред кроку і продовжать, тільки коли натиснете "грати".
8
RDS Proxy
Мультиплексор, що зводить тисячі з'єднань функцій до десятків з'єднань з БД.
Асоціація: диспетчер таксі: сотні дзвінків — кілька водіїв.
9
Durable Object
Однопотоковий об'єкт з унікальним id і власним сховищем на edge.
Асоціація: одна дошка в переговорці: всі пишуть на ній, тож немає копій, що розходяться.
10
Hono / Request→Response
Фреймворк на Web-стандартах, що запускається в будь-якому рантаймі через адаптер.
Асоціація: USB-C: один кабель, а в коробці — перехідники під кожну розетку.
