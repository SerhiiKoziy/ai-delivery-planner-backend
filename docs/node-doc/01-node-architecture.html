01 Що таке Node.js насправді

Перше питання співбесіди звучить просто, але неточна відповідь одразу видає людину, яка не заглядала під капот.

Node.js — це середовище виконання (runtime) для JavaScript поза браузером. Не мова (мова — це JavaScript / ECMAScript), не фреймворк (фреймворки — Express, Fastify, NestJS будуються поверх Node), і не «сервер» (HTTP-сервер — лише один із модулів, які Node надає). Якщо спростити до формули:

Node.js = V8 (виконує JavaScript) + libuv (event loop, асинхронний I/O, thread pool) + C++ bindings (місток між JS і системою) + стандартна бібліотека на JS (fs, http, stream, crypto...) + набір C/C++-залежностей (OpenSSL, zlib, llhttp, c-ares, ICU...).

Сам по собі JavaScript (як мова) не вміє читати файли, відкривати сокети чи запускати процеси — у специфікації ECMAScript немає ні слова про I/O. Усе це дає хост-середовище. У браузері хост — це Chrome/Firefox з їхніми Web API (DOM, fetch, setTimeout). У Node хост — це сам Node зі своїми API. Тому setTimeout у браузері й у Node — це дві різні реалізації з однаковим іменем (і, як побачимо, навіть різним типом значення, що повертається).

На співбесіді запитають так «Що таке Node.js?» Сильна відповідь за 20 секунд: «Runtime для JavaScript на базі V8 і libuv. V8 виконує JS, libuv дає event loop і неблокуючий I/O — мережа через механізми ОС (epoll/kqueue/IOCP), а файли, DNS-lookup і важкий crypto — через пул потоків. Модель — один потік для JS + event-driven I/O, тому Node чудовий для I/O-bound задач і поганий для CPU-bound без worker threads.» Кожне слово тут — гачок для наступних питань, до яких ви будете готові після цього туторіалу.

02 Коротка історія: від C10k до OpenJS Foundation

Історія пояснює архітектуру: Node створювали саме як відповідь на проблему «багато з'єднань — мало потоків».

Проблема C10k

Наприкінці 1990-х Ден Кегел сформулював C10k problem: як одному серверу обслуговувати 10 000 одночасних клієнтів? Класичний підхід «один потік (або процес) на з'єднання», як у Apache з prefork/worker MPM, на цьому ламається: кожен потік — це мегабайти стеку і робота планувальника ОС, а більшість часу ці потоки просто чекають на мережу чи диск. Відповіддю стали event-driven сервери (nginx, 2004): один потік + неблокуючі сокети + системний виклик на кшталт epoll, який каже «ось ці 37 сокетів готові до читання».

2009: Ryan Dahl і Node.js

Ryan Dahl представив Node.js на JSConf EU у листопаді 2009. Ідея: взяти модель nginx (event loop + неблокуючий I/O) і зробити її єдиною моделлю програмування, причому мовою, де немає легасі синхронного I/O. JavaScript підійшов ідеально: у браузері програмісти вже звикли до колбеків і подій, а в мові не було жодної «блокуючої» стандартної бібліотеки, яку довелося б обходити. Рушій V8 (Chrome, 2008) якраз зробив JS достатньо швидким.

Перші версії працювали на libev + libeio; для підтримки Windows (де замість readiness-моделі epoll є completion-модель IOCP) команда написала власну абстракцію — libuv. Сьогодні libuv — окремий проєкт, яким користуються й інші середовища (наприклад, Julia, pyuv, uvloop для Python).

03 Шари архітектури

Коли ви пишете fs.readFile, виклик проходить крізь п'ять шарів — знати їх означає розуміти, де шукати проблему.

Що лежить на кожному шарі

ШарДе в репозиторії nodejs/nodeПриклад
Node API на JSlib/ (lib/fs.js, lib/internal/...)Валідація аргументів, обгортки в проміси, streams, EventEmitter
C++ bindingssrc/ (node_file.cc, tcp_wrap.cc)Перетворення JS-значень у C-структури, виклик uv_fs_open
V8deps/v8Компілює й виконує ваш JS і JS самого Node
libuvdeps/uvEvent loop, неблокуючі сокети, пул потоків для fs
Інші depsdeps/openssl, deps/llhttp, deps/undici...TLS, парсинг HTTP, вбудований fetch (undici — це JS)

Простежимо один виклик fs.readFile('a.txt', cb):

  1. lib/fs.js валідує аргументи, створює об'єкт-запит (FSReqCallback) і викликає binding.
  2. C++ binding (node_file.cc) перетворює рядок шляху в C-рядок і викликає uv_fs_open(loop, req, path, ..., callback).
  3. libuv кладе задачу в чергу thread pool; вільний потік пулу робить блокуючий open(), потім fstat, read, close (readFile — це кілька таких кроків).
  4. Після завершення потік пулу сигналізує головному циклу (через uv_async), і на наступній ітерації в poll-фазі libuv викликає C++-колбек.
  5. C++ «входить» у V8 (MakeCallback) і викликає ваш JS cb(err, data); після колбеку Node проганяє чергу process.nextTick і мікрозадачі.
🧠 Запам'ятай: V8 вміє лише виконувати JS; усе, що «торкається світу» (файли, мережа, таймери), робить libuv через ОС, а C++ bindings склеюють ці два світи.

04 V8: від тексту до машинного коду

Достатньо розуміти конвеєр компіляції і що таке деоптимізація — глибоке тюнінгування в туторіалі 15.

V8 — рушій JavaScript і WebAssembly від Google, написаний на C++. Той самий, що в Chrome. Node вбудовує його як бібліотеку: створює Isolate (ізольований екземпляр рушія зі своєю купою і GC) і Context (набір глобальних об'єктів). Кожен worker thread у Node — це окремий Isolate, тому workers не ділять звичайні JS-об'єкти (лише SharedArrayBuffer).

Hidden classes (shapes/maps) та inline caches — ключ до швидкості: об'єкти з однаковим набором властивостей, доданих в однаковому порядку, мають одну «форму», і доступ до obj.x компілюється в зчитування за фіксованим зміщенням. Якщо в одне місце коду приходять об'єкти багатьох форм (megamorphic), оптимізація пропадає.

Що варто знати на рівні senior, а що — ні. Достатньо: «V8 — багаторівневий JIT з інтерпретатором Ignition і оптимізуючими компіляторами; він спекулює на типах і деоптимізується, якщо спекуляція хибна; тому мономорфний код зі стабільними формами об'єктів швидший». Назви рівнів і те, що Maglev — відносно нова проміжна ланка, — приємний бонус. Купа, GC (Scavenger / Mark-Compact), --max-old-space-size і профілювання — у туторіалі 15.
🎉
Цікавий факт Node стартує за десятки мілісекунд, хоча при запуску виконує чималий шматок власного JS (bootstrap, CJS/ESM-завантажувачі). Секрет — V8 startup snapshot: стан купи після bootstrap серіалізується під час збирання Node і просто десеріалізується при старті. Той самий механізм доступний і вам (--build-snapshot), а також використовується для Single Executable Applications (node:sea).

05 libuv: event loop і thread pool

Найважливіше знання про Node: які операції не займають жодного потоку, а які стоять у черзі до пулу з 4 потоків.

libuv — кросплатформна C-бібліотека асинхронного I/O. Вона дає Node:

  • event loop — цикл із 6 фаз, який чекає на події ОС і викликає колбеки (детально — туторіал 2);
  • handles — довгоживучі об'єкти: TCP/UDP-сокети, таймери, pipes, TTY, сигнали, дочірні процеси;
  • requests — короткі операції: запис у сокет, операція з файлом, DNS-lookup;
  • thread pool — пул робочих потоків для того, що ОС не вміє робити асинхронно.

Два принципово різні шляхи асинхронності

Ключова ідея: «асинхронна операція» у Node може бути реалізована двома способами.

Хто куди йде

UV_THREADPOOL_SIZE

  • Розмір за замовчуванням — 4; можна збільшити змінною середовища UV_THREADPOOL_SIZE (максимум — 1024 у сучасних libuv).
  • Пул створюється ліниво — при першій задачі — і далі розмір не змінюється. Тому задавайте змінну до старту процесу: UV_THREADPOOL_SIZE=16 node app.js. Присвоєння process.env.UV_THREADPOOL_SIZE у першому рядку коду інколи спрацьовує, але це крихко (і на Windows не працює) — не покладайтеся.
  • Пул один на процес і спільний для всіх: ваші fs, bcrypt-addon, dns.lookup з HTTP-клієнта. Повільний NFS-диск або 4 одночасні хешування паролів можуть «заморозити» вихідні HTTP-запити, яким потрібен DNS-lookup.
  • Більше потоків ≠ завжди швидше: для CPU-задач немає сенсу ставити більше, ніж ядер; для повільних fs-операцій (мережеві диски) — має.
⚠️
Класичний продакшн-інцидент. Сервіс логіну хешує паролі через bcrypt (native addon, використовує thread pool). Під навантаженням усі 4 потоки зайняті хешуванням → dns.lookup для вихідних запитів до БД/API стоїть у черзі → таймаути «звідусіль», хоча CPU не на 100% і event loop не заблокований. Лікування: більший UV_THREADPOOL_SIZE, кешування DNS або IP, винесення хешування у worker threads / окремий сервіс.
🎉
Цікавий факт На Linux libuv експериментував з io_uring — інтерфейсом ядра, який дає справді асинхронні файлові операції без пулу потоків. Через проблеми з безпекою і сумісністю його використання за замовчуванням згодом обмежили, тож на практиці вважайте: fs у Node = thread pool.
🧠 Запам'ятай: мережа — без потоків (ядро ОС), а fs, dns.lookup, crypto.pbkdf2/scrypt/randomBytes і zlib — у спільний пул з 4 потоків.

06 Демо: насичуємо thread pool

Три маленькі скрипти, які за хвилину переконують сильніше за будь-яку діаграму.

Демо 1: хеші йдуть «пачками по 4»

pool.js
const crypto = require('node:crypto');
const start = Date.now();

for (let i = 1; i <= 8; i++) {
  crypto.pbkdf2('secret', 'salt', 200_000, 64, 'sha512', () => {
    console.log(`hash ${i}: ${Date.now() - start} ms`);
  });
}

hash 3: 212 ms

Що видно: (1) рівно чотири хеші завершуються разом, наступні чотири — через ще один «квант» часу; (2) порядок завершення всередині пачки випадковий — потоки працюють паралельно; (3) з 8 потоками всі вісім закінчуються однією хвилею. Кожен окремий хеш при 8 потоках трохи повільніший (~200 мс замість ~145) — ядра ділять кеш, частоту і пропускну здатність пам'яті.

07 C++ bindings, N-API і вбудовані модулі

Звідки береться require('fs'), як працюють native-пакети на кшталт bcrypt і sharp, і навіщо префікс node:.

Internal bindings

JS-модулі в lib/ отримують доступ до C++ через internalBinding('fs'), internalBinding('tcp_wrap') тощо. Це внутрішній, нестабільний API — з коду користувача він недоступний (колись існував process.binding(), нині застарілий). Тобто публічний контракт Node — це саме JS-модулі, а C++ — деталь реалізації.

Native addons: від NAN до N-API

Деякі пакети містять C/C++/Rust-код, скомпільований у .node-файл (динамічна бібліотека, яку require завантажує через dlopen): bcrypt, sharp, better-sqlite3, canvas, драйвери на кшталт @node-rs/*.

// require('node:test') → працює
  • Префікс захищає від typosquatting/підміни: пакет з назвою events у node_modules не перекриє вбудований node:events.
  • Модулі, додані останніми роками (node:test, node:sqlite, node:sea), доступні тільки з префіксом — щоб не ламати існуючі npm-пакети з такими іменами.
  • Вбудовані модулі завантажуються зі snapshot / вбудованого коду, а не з диска — тому вони швидкі й не потребують node_modules.

08 Що відбувається, коли ви пишете node app.js

Життєвий цикл процесу: від bootstrap до моменту, коли Node вирішує, що роботи більше немає.

1. Bootstrap

C++-функція node::Start парсить аргументи CLI та NODE_OPTIONS, ініціалізує OpenSSL, V8-платформу (у неї свої фонові потоки), створює Isolate і Context (зі snapshot), налаштовує process, globalThis, таймери, обробники сигналів, запускає internal JS-bootstrap і створює libuv-loop.

2. Module wrapper

CommonJS-файл не виконується «як є» — Node загортає його у функцію. Саме тому require, module, __dirname «глобальні», хоча насправді це параметри функції:

wrapper.js
console.log(typeof require, typeof module, typeof exports, typeof __filename);
console.log(arguments.length);              // у файлі верхнього рівня є arguments!
console.log(require('node:module').wrapper);
console.log(this === module.exports);

// Реальний вивід (Node 24):
// function object object string
// 5
// [ '(function (exports, require, module, __filename, __dirname) { ', '\n});' ]
// true

ES-модулі (.mjs або "type": "module") так не загортаються: там немає require/__dirname (замість них — import.meta.url, import.meta.dirname, import.meta.filename), this на верхньому рівні — undefined, а top-level await дозволений. Деталі — у туторіалі 4.

3. Синхронний код і вхід у цикл

Увесь код верхнього рівня виконується синхронно від першого до останнього рядка: він лише реєструє роботу (server.listen, setTimeout, fs.readFile). Потім Node проганяє process.nextTick і мікрозадачі, і викликає uv_run() — event loop.

4. Коли процес завершується: ref і unref

Цикл крутиться, поки є хоч один активний ref-нутий handle (сервер слухає порт, таймер очікує, сокет відкритий, stdin читається) або незавершений request (файл читається). Будь-який handle можна «відв'язати»: unref() означає «не тримай процес заради мене».

unref.js
const t = setInterval(() => console.log('tick'), 100);
t.unref();                         // інтервал не тримає процес живим
setTimeout(() => console.log('done'), 250);
process.on('beforeExit', () => console.log('beforeExit'));
process.on('exit', (code) => console.log('exit', code));

// Реальний вивід:
// tick
// tick
// done
// beforeExit
// exit 0

Без unref() процес жив би вічно. Типові застосування: фоновий heartbeat чи періодичний flush метрик, які не повинні заважати graceful exit; server.unref() у тестах. 'beforeExit' не викликається при process.exit() і при необробленому виключенні; в обробнику 'exit' можна робити лише синхронні речі — цикл уже не працює. Ще більше прикладів (включно з «зацикленим» beforeExit) — у туторіалі 2.

💼
На співбесіді запитають так «Чому мій скрипт міграції не завершується після останнього рядка?» — майже завжди відкритий handle: пул з'єднань до БД (pg.Pool, Prisma, Redis-клієнт) тримає сокети. Правильно — викликати pool.end() / prisma.$disconnect(), а не process.exit(). Діагностика: process.getActiveResourcesInfo() або пакет why-is-node-running.

09 Міф про «однопотоковість»

«Node однопотоковий» — правильно про ваш JS-код і неправильно про процес.

Точне формулювання: JavaScript-код у Node виконується в одному потоці (на один Isolate), тому немає data races між вашими колбеками і не потрібні mutex-и для звичайних змінних. Але процес Node має багато потоків:

  • головний потік — V8 + event loop + усі ваші колбеки;
  • libuv thread pool — 4 потоки (створюються при першій задачі);
  • V8 platform worker threads — фонова компіляція (Maglev/TurboFan компілюють не в головному потоці), конкурентне маркування і sweeping для GC;
  • службові потоки: inspector, обробка сигналів тощо;
  • worker_threads, якщо ви їх створили — кожен зі своїм Isolate і своїм event loop.
threads.js (macOS; на Linux — ls /proc/$PID/task | wc -l)
const { execSync } = require('node:child_process');
const count = () => execSync(`ps -M -p ${process.pid} | tail -n +2 | wc -l`).toString().trim();

console.log('idle process threads:', count());
require('node:crypto').pbkdf2('a', 'b', 1, 8, 'sha1', () => {
  console.log('after first thread-pool task:', count());
});

// Реальний вивід:
// idle process threads: 7
// after first thread-pool task: 11     ← +4 потоки libuv-пулу, створені ліниво
✅
Як сказати правильно: «Node використовує один потік для виконання JavaScript і event loop, а паралелізм I/O забезпечують ядро ОС і пул потоків libuv. Для паралельних обчислень на JS є worker_threads, для використання всіх ядер під HTTP — cluster або кілька процесів за балансувальником» (див. туторіал 8).

Порівняння з Python: у CPython теж «один потік виконує байткод одночасно» — через GIL (див. Python, туторіал 6). Різниця в тому, що Python дає вам потоки, які конкурують за GIL, а Node взагалі не дає потоків для звичайного JS — лише ізольовані workers з передачею повідомлень.

11 Для чого Node добрий, а для чого ні

Інтуїція «на рівні чисел»: скільки запитів витягне один процес і що його вбиває.

I/O-bound: сильна сторона

Типовий бекенд-запит: розпарсити JSON (0.1 мс CPU), сходити в БД (20 мс очікування), ще в Redis (1 мс), відповісти. CPU зайнятий частки мілісекунди, решту часу запит просто «висить» у event loop, не займаючи потоку. Один процес може тримати десятки тисяч одночасних з'єднань — кожне коштує кілька кілобайт пам'яті на об'єкти сокета, а не мегабайти стеку окремого потоку.

io-concurrency.js
const http = require('node:http');

// Сервер «повільно» відповідає: 200 мс очікування (імітація БД/API)
const server = http.createServer((req, res) => {
  setTimeout(() => res.end('ok'), 200);
});

server.listen(0, async () => {
  const { port } = server.address();
  const start = Date.now();
  // 300 одночасних запитів — клієнт і сервер в ОДНОМУ процесі, без жодного worker
  await Promise.all(
    Array.from({ length: 300 }, () => fetch(`http://127.0.0.1:${port}/`).then((r) => r.text()))
  );
  console.log(`300 запитів по 200 мс: ${Date.now() - start} ms`);
  server.close();
});

// Реальний вивід (3 запуски): 419 ms, 420 ms, 418 ms
// Послідовно це було б 300 × 200 = 60 000 ms

CPU-bound: слабка сторона

Проста арифметика: якщо обробка одного запиту займає X мс чистого CPU, один процес Node обробить не більше 1000 / X запитів на секунду — незалежно від того, скільки запитів чекають. Гірше: поки йде обчислення, усі інші запити стоять, тож p99 latency росте для всіх.

12 Релізний цикл і керування версіями

Яку версію ставити в прод, що таке LTS і чому непарні версії — не для продакшну.

Як влаштований графік

  • Нова мажорна версія виходить двічі на рік: у квітні та жовтні.
  • Кожна нова мажорна версія спершу має статус Current (~6 місяців): нові фічі, можливі breaking changes у мінорних релізах екосистеми — для тестування.
  • Парні версії (18, 20, 22, 24...) у жовтні стають Active LTS (Long-Term Support) — ~12 місяців активної підтримки з бекпортом фіч і фіксів.
  • Далі — Maintenance LTS: лише критичні баги і безпека. Загальний строк життя парної версії — близько 30 місяців, після чого — EOL (End-of-Life).
  • Непарні версії (21, 23, 25...) ніколи не стають LTS і живуть ~8 місяців.

Станом на осінь 2026: Node 24 — Active LTS, Node 22 — Maintenance LTS, Node 20 вже досяг EOL, а свіжа парна версія проходить шлях Current → LTS. Перевіряйте актуальну таблицю на nodejs.org/en/about/previous-releases — проєкт також обговорював зміну графіку релізів, тож деталі можуть змінитися.

✅
Правило для продакшну: лише Active або Maintenance LTS; оновлюватися на нову LTS протягом її першого року (а не в останній місяць перед EOL); закріплювати версію в .nvmrc / .node-version, полі engines у package.json і в базовому Docker-образі (node:24-slim, а не node:latest).

13 Каверзні питання співбесіди

Питання, на яких перевіряють, чи розумієте ви механіку, а не лише API.

БазаЩо таке Node.js і з чого він складається?
Runtime для JS поза браузером: V8 (виконує JS), libuv (event loop, async I/O, thread pool), C++ bindings, стандартна бібліотека на JS (lib/) і C-залежності (OpenSSL, zlib, llhttp, c-ares, ICU). Не мова і не фреймворк.
ПасткаNode.js однопотоковий?
JS-код виконується в одному потоці (на Isolate), але процес має щонайменше головний потік, 4 потоки libuv-пулу, фонові потоки V8 (компіляція, GC) і службові потоки. Мережевий I/O взагалі не займає потоків — його веде ядро ОС через epoll/kqueue/IOCP.
БазаЯкі операції йдуть у libuv thread pool?
Async fs.* (крім fs.watch), dns.lookup (а отже й підключення за hostname), crypto.pbkdf2/scrypt/randomBytes/randomFill/generateKeyPair з колбеком, async zlib, а також native addons, які самі ставлять задачі (bcrypt). Мережа, таймери, процеси, dns.resolve* — не в пулі.
ПасткаЧому HTTP-запити до зовнішнього API раптом почали «висіти», коли ми додали хешування паролів?
Обидві речі ділять один thread pool: bcrypt/pbkdf2 займають усі 4 потоки, а dns.lookup для вихідних з'єднань стоїть у черзі за ними. Event loop при цьому не заблокований. Рішення: UV_THREADPOOL_SIZE, keep-alive агенти (менше нових lookup-ів), кеш DNS, винесення хешування у workers.
БазаЩо таке UV_THREADPOOL_SIZE і як його правильно задати?
Розмір пулу libuv (за замовчуванням 4, максимум 1024). Пул створюється ліниво при першій задачі й більше не змінюється, тому задають змінною середовища до старту процесу: UV_THREADPOOL_SIZE=16 node app.js (або в Dockerfile ENV).
ПасткаЧому файлові операції йдуть через пул, а не через epoll, як сокети?
epoll/kqueue — це readiness-модель: «скажи, коли дескриптор готовий». Звичайний файл на POSIX завжди вважається «готовим», а читання з диска все одно блокує потік. Тому libuv робить блокуючий read() у потоці пулу. (На Windows є completion-модель IOCP, на Linux — io_uring, але переносимий шлях libuv — пул.)
БазаЩо відбувається при node app.js?
Bootstrap (V8, isolate зі snapshot, process, libuv loop) → завантаження модуля (CJS обгортається у function (exports, require, module, __filename, __dirname)) → синхронний top-level код → дренаж nextTick і мікрозадач → event loop, поки є ref-нуті handles/requests → beforeExit → exit.
ПасткаЗвідки береться require, якщо це не глобальна змінна?
З module wrapper: CJS-модуль загортається у функцію з 5 параметрами (exports, require, module, __filename, __dirname). Тому в CJS-файлі навіть працює arguments.length === 5, а this === module.exports. У ESM обгортки немає.
БазаЩо таке Node-API (N-API) і навіщо він?
Стабільний C ABI для native addons, незалежний від внутрішнього API V8. Addon, зібраний під певну версію Node-API, завантажується в новіших версіях Node без перекомпіляції. C++-обгортка — node-addon-api, для Rust — napi-rs.
ПасткаНавіщо префікс node:, якщо require('fs') і так працює?
Однозначність і безпека: імпорт гарантовано береться з вбудованих модулів, а не з node_modules; читач коду одразу бачить, що це built-in. Плюс нові модулі (node:test, node:sqlite, node:sea) доступні лише з префіксом.
ПасткаСкрипт закінчився, але процес не виходить. Чому і як знайти причину?
Є ref-нутий handle: відкритий сокет (пул БД, Redis), інтервал, сервер, stdin. Діагностика — process.getActiveResourcesInfo(), why-is-node-running. Лікування — закрити ресурс (pool.end()) або unref() для фонових таймерів, а не process.exit(), який обриває незаписані логи і незавершені запити.
БазаЧим Node-середовище відрізняється від браузера?
Немає DOM; є process, Buffer, доступ до ФС і мережі; CJS + ESM; setTimeout повертає об'єкт Timeout; є setImmediate і process.nextTick; event loop — фази libuv замість HTML-моделі з rendering. Спільне: globalThis і дедалі більше Web API (fetch, URL, Web Streams, WebSocket).
ПасткаЩо таке деоптимізація у V8 і чому вона важлива для бекенду?
Оптимізуючі компілятори (Maglev, TurboFan) генерують код під припущення з type feedback (наприклад, «тут завжди числа», «об'єкт має таку форму»). Якщо припущення порушене — V8 викидає оптимізований код і повертається в інтерпретатор. Гарячий шлях з поліморфними об'єктами (різні набори полів, delete obj.x) може постійно деоптимізуватися. Діагностика — --trace-deopt, профайлер (туторіал 15).
БазаЯку версію Node брати в продакшн?
Парну у статусі Active LTS (або Maintenance, якщо міграція ще триває). Непарні версії ніколи не стають LTS. Закріплювати версію в .nvmrc, engines і Docker-тезі.

15 Як запам'ятати

Асоціації, які спливуть у голові на співбесіді.

1
Node.js
Runtime, що поєднує V8 (виконання JS) і libuv (I/O) через C++ bindings.
Асоціація: автомобіль — V8 це двигун, libuv — коробка передач і колеса, а Node — уся машина з кермом (API).
2
libuv thread pool
4 спільні потоки для fs, dns.lookup, важкого crypto і zlib.
Асоціація: 4 каси в супермаркеті: восьмий покупець з повним возиком (pbkdf2) чекає, поки звільниться каса, навіть якщо в нього лише хліб (readFile).
3
epoll / kqueue / IOCP
Механізми ОС, що повідомляють про готовність тисяч сокетів без окремих потоків.
Асоціація: пейджер у ресторані — не стоїш біля кухні, а чекаєш, поки завібрує саме твій.
4
C10k
Проблема обслуговування 10 000 одночасних клієнтів, через яку з'явилися event-driven сервери і Node.
Асоціація: один офіціант на весь зал замість офіціанта біля кожного столика.
5
JIT-рівні V8
Ignition → Sparkplug → Maglev → TurboFan: що гарячіший код, то сильніша оптимізація.
Асоціація: «ІСМТ» — Іди, Спринтуй, Мчи, Турбо; а deopt — штраф і назад на старт.
6
Module wrapper
CJS-файл загортається у функцію з exports, require, module, __filename, __dirname.
Асоціація: лист у конверті — require і __dirname надруковані на конверті, а не в самому листі.
7
ref / unref
Ref-нутий handle тримає процес живим; unref() каже «не чекай на мене».
Асоціація: останній, хто виходить з офісу, вимикає світло — але фонове радіо (unref) не рахується як «людина в офісі».
8
Node-API
Стабільний ABI для native addons, що не ламається при оновленні V8.
Асоціація: стандартна розетка — техніку не перепаюєш при кожній заміні електростанції.
9
LTS
Парні версії стають LTS у жовтні й живуть ~30 місяців; непарні — ніколи.
Асоціація: «парне — надійне»: як парна кількість коліс у машині, а непарне — одноколісний велосипед для експериментів.
