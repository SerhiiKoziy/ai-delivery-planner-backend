01 Анатомія package.json

Маніфест пакета — водночас опис для реєстру, конфіг для Node і контракт для споживачів.

package.json
{
  "name": "@acme/route-planner",
  "version": "2.4.1",
  "description": "Route optimization SDK",
  "license": "MIT",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
    "./package.json": "./package.json"
  },
  "bin": { "route-planner": "./dist/cli.js" },
  "files": ["dist", "README.md"],
  "sideEffects": false,
  "engines": { "node": ">=20.19" },
  "packageManager": "pnpm@10.18.0",
  "scripts": {
    "build": "tsc -p tsconfig.build.json",
    "test": "node --test",
    "prepublishOnly": "pnpm build && pnpm test"
  },
  "dependencies": { "zod": "^4.1.0" },
  "devDependencies": { "typescript": "~5.9.2" },
  "peerDependencies": { "pino": ">=9" },
  "peerDependenciesMeta": { "pino": { "optional": true } },
  "optionalDependencies": { "fsevents": "^2.3.3" },
  "publishConfig": { "access": "public", "provenance": true }
}
ПолеДля когоЩо варто знати
nameреєстр, require≤ 214 символів, lowercase; scope @org/ дає namespace і захист від typosquatting у вашому імені.
versionреєстрsemver; опубліковану версію неможливо перезаписати (навіть після unpublish).
typeNodemodule/commonjs для .js (туторіал 4). Вказуйте завжди.
main / exportsNode, бандлериexports перекриває main і інкапсулює пакет.
binnpmПри встановленні створюється симлінк у node_modules/.bin (або глобально в PATH). Файлу потрібен shebang #!/usr/bin/env node.
filesnpm publishAllowlist того, що потрапить у tarball. Безпечніше за .npmignore (denylist). package.json, README, LICENSE включаються завжди.
enginesnpm/pnpm/yarnnpm лише попереджає (якщо не engine-strict=true), yarn classic і pnpm з engineStrict — падають.

private: truenpmЗабороняє випадковий npm publish. Обов'язково для застосунків і кореня монорепо.
💡
Не редагуйте package.json руками в CI-скриптах — є npm pkg get version, npm pkg set scripts.lint="eslint .", npm pkg delete scripts.prepare. Корисно в Dockerfile, щоб, наприклад, прибрати prepare-хук перед production-інсталяцією.

02 Види залежностей

П'ять секцій — п'ять різних контрактів про те, хто, коли і в якій версії встановлює пакет.

СекціяВстановлюється у споживача?Коли використовувати
dependenciesтак, транзитивнопотрібне в рантаймі: express, zod, pg
devDependenciesні (лише у вашому проєкті)збірка, тести, лінтери, типи @types/*. npm ci --omit=dev їх пропускає
peerDependenciesочікується, що хост уже маєплагіни: eslint-plugin-x → eslint; react-dom → react; @nestjs/typeorm → @nestjs/core. Гарантує одну копію хоста
peerDependenciesMeta.optionalpeer, але необов'язковийінтеграції: "якщо є pino — підключимось", без warning-у при відсутності
optionalDependenciesтак, але помилка встановлення не фатальнаплатформо-специфічні бінарники (fsevents лише на macOS; esbuild/swc/sharp публікують @scope/linux-x64 тощо з полями os/cpu)
bundleDependenciesвкладаються в tarballрідко: офлайн-дистрибуція, патчені форки. Не дедуплікуються

Peer dependencies: історія болю

  • npm 3–6: peer-и не встановлювались автоматично — лише warning.
  • npm 7+: peer-и встановлюються автоматично, а конфлікт версій — помилка ERESOLVE. Звідси масове --legacy-peer-deps (повернути стару поведінку) і --force. Обидва — милиці: краще виправити версії або додати overrides.
  • pnpm за замовчуванням теж встановлює peer-и (auto-install-peers=true з v8) і суворіше повідомляє про конфлікти.
⚠️
Класична помилка автора бібліотеки: покласти react чи @nestjs/core у dependencies плагіна. Результат — дві копії фреймворка у споживача, "Invalid hook call", instanceof між DI-контейнерами false. Хост-фреймворк — завжди peerDependencies (+ та сама версія в devDependencies для локальних тестів).

03 Semver і діапазони версій

MAJOR.MINOR.PATCH — обіцянка, а не гарантія. Діапазони визначають, наскільки ви довіряєте цій обіцянці.

  • MAJOR — ламає API; MINOR — нова функціональність, сумісна назад; PATCH — виправлення.
  • Pre-release: 2.0.0-beta.3 — нижчий за 2.0.0. Build metadata: 1.0.0+sha.abc — ігнорується при порівнянні.
  • 0.x — "усе може змінитися": за специфікацією semver, до 1.0.0 публічний API нестабільний, і npm трактує minor як major.

Таблиця нижче отримана з бібліотеки semver, яку використовує сам npm (new Range(r).range і maxSatisfying для набору версій 0.0.3…2.0.0):

ДіапазонРозгортається вНайвища підходяща з наборуСенс
^1.2.3>=1.2.3 <2.0.0-01.9.9caret: все до наступного major (default npm i)
~1.2.3>=1.2.3 <1.3.0-01.2.9tilde: лише патчі
1.2.31.2.31.2.3exact pin (npm i -E, save-exact=true)
^0.2.3>=0.2.3 <0.3.0-00.2.9для 0.x caret = tilde!
^0.0.3>=0.0.3 <0.0.4-00.0.3для 0.0.x caret = exact
1.x / ^1>=1.0.0 <2.0.0-01.9.9X-range
~1.2>=1.2.0 <1.3.0-01.2.9tilde без патча
* / ""будь-яка2.0.0ніколи так не робіть
^1.2.3-beta.1>=1.2.3-beta.1 <2.0.0-01.9.9pre-release лише для 1.2.3-*
💼
На співбесіді запитають так "Чому ^0.4.1 не оновиться до 0.5.0?" — бо для major 0 npm вважає minor ламаючим: caret фіксує найлівішу ненульову цифру. І друге: "навіщо діапазони, якщо є lockfile?" — діапазон потрібен бібліотекам (щоб споживач міг дедуплікувати одну версію на кілька пакетів), а відтворюваність застосунку дає lockfile, не pin.

package.json каже "що підходить", lockfile — "що саме було встановлено, до байта".

npm error npm-shrinkwrap.json with lockfileVersion >= 1. ...

# аналоги "frozen" режиму в інших менеджерах:

yarn install --immutable           # Yarn Berry
bun install --frozen-lockfile

Що лежить у lockfile

  • package-lock.json (lockfileVersion 3 у npm 9+): плоска мапа "node_modules/a/node_modules/b" → version, resolved URL, integrity (SRI-хеш sha512), прапорці dev/optional/peer. Фактично — знімок дерева.
  • pnpm-lock.yaml: граф пакетів name@version(peer-контекст) і snapshots — layout вираховується з графа.
  • yarn.lock: у classic — власний формат; у Berry — YAML з checksum і resolution.
  • bun.lock: текстовий JSONC (раніше — бінарний bun.lockb).
  • npm-shrinkwrap.json — lockfile, що публікується разом з пакетом (лише для CLI-застосунків, не для бібліотек).
✅
Правила: lockfile комітити завжди (і для застосунків, і для бібліотек — для відтворюваного CI); один менеджер — один lockfile (два різні lock-и в репо = різні дерева у різних розробників); merge-конфлікт у lockfile не правити руками — взяти одну сторону і перезапустити install. Lockfile бібліотеки не впливає на її споживачів — у них свій.

05 node_modules: hoisting і phantom dependencies

Чому require('debug') працює, хоча в package.json його немає — і чому одного дня перестане.

npm v1–2 будував вкладене дерево: кожен пакет мав свій node_modules. Результат — шляхи довші за ліміт Windows (260 символів) і десятки копій одного пакета. npm 3 (2015) перейшов на hoisting: усе, що можна, піднімається в корінь node_modules, вкладені копії лишаються лише при конфлікті версій. Резолюція require (підйом по node_modules вгору — туторіал 4) знаходить підняті пакети.

  • Phantom dependency — ваш код імпортує пакет, якого немає у вашому package.json, але він "випадково" піднятий як залежність залежності. Працює, поки хтось не оновить ту залежність, і вона перестане тягнути цей пакет (або потягне іншу major-версію).
  • Doppelgangers — одна версія пакета встановлена кілька разів у різних вкладених місцях, бо в корені вже лежить інша версія. Дублікати = кілька singleton-ів.
  • Недетермінованість layout-у: яка версія опиниться в корені, залежить від порядку обходу — тому layout фіксує саме lockfile.
terminal
npm ls debug              # хто тягне debug і які версії
npm explain debug         # чому пакет встановлено (ланцюжок залежностей)
npm dedupe                # спробувати звести дублікати до однієї версії
npm query ":root > .dev"  # CSS-подібні запити по дереву
pnpm why debug            # аналог у pnpm

06 pnpm і Yarn Plug'n'Play

Два радикальні способи прибрати phantom deps і дублювання на диску.

pnpm: content-addressable store + симлінки

  • Усі файли всіх версій пакетів лежать один раз у глобальному store (pnpm store path), адресовані хешем вмісту. Дві версії lodash, що відрізняються одним файлом, ділять решту файлів.
  • У проєкті файли hard-link-уються зі store у node_modules/.pnpm/<name>@<version>/node_modules/<name> — копіювання немає, встановлення миттєве при теплому store.
  • У корені node_modules — лише симлінки на ваші прямі залежності. Транзитивні залежності не видно → phantom import падає одразу.
  • Кожен пакет у .pnpm бачить свої залежності через сусідні симлінки в тому ж node_modules — стандартний алгоритм резолюції Node працює без патчів (бо Node резолвить realpath).
⚠️
Деякі старі інструменти (React Native, деякі плагіни Webpack/ESLint, Serverless-пакувальники) очікують плаский node_modules. Для них у pnpm є node-linker=hoisted (повністю npm-подібний layout) або точкові public-hoist-pattern. Якщо пакет сам має phantom dependency — packageExtensions дописує йому відсутню залежність, не форкаючи.

Yarn Berry (v2+): Plug'n'Play і zero-installs

  • PnP взагалі не створює node_modules. Yarn генерує .pnp.cjs — таблицю "пакет → де лежить його zip у кеші і що йому дозволено імпортувати", і патчить резолюцію Node через --require .pnp.cjs.
  • Плюси: найшвидший старт, сувора перевірка залежностей (phantom import — помилка з поясненням), один zip на пакет.
  • Zero-installs: .yarn/cache (zip-и) комітиться в git → git clone і можна запускати без yarn install; CI без мережі. Ціна — великий репозиторій і бінарні diff-и.
  • Мінуси: IDE і інструменти потребують SDK (yarn dlx @yarnpkg/sdks vscode), нативні модулі й інструменти, що читають файли з node_modules напряму, ламаються. Тому багато команд на Berry вмикають nodeLinker: node-modules — і отримують "звичайний" yarn.
  • Yarn classic (1.x) — у режимі підтримки, нових фіч немає.

08 Workspaces і монорепо

Кілька пакетів в одному репозиторії: спільний lockfile, локальні лінки, оркестрація задач.

pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

catalog:                      # одна версія залежності на весь монорепо
  zod: ^4.1.0
  typescript: ~5.9.2

onlyBuiltDependencies:        # pnpm 10: кому дозволено postinstall
  - esbuild
  - "@prisma/engines"
apps/api/package.json
{
  "name": "@acme/api",
  "private": true,
  "dependencies": {
    "@acme/domain": "workspace:*",
    "zod": "catalog:"
  }
}
  • Workspaces є в усіх менеджерах: npm ("workspaces": ["packages/*"] у package.json, команди -w <name> / --workspaces), yarn (те саме поле, yarn workspace x add), pnpm (pnpm-workspace.yaml, pnpm --filter).
  • Пакети монорепо лінкуються симлінками — зміни в packages/domain одразу видно в apps/api.
  • workspace:* (pnpm, yarn) — "завжди локальна версія"; при publish автоматично замінюється на реальну версію. npm використовує звичайний діапазон, що збігається з локальною версією.
  • Catalogs (pnpm) — централізовані версії залежностей, щоб не мати трьох різних typescript у різних пакетах.

Turborepo ✅простий turbo.json, локальний + remote cache, паралельний граф задач, мінімум концепційлише оркестрація задач — без генераторів і правил меж модулів

Lerna (зараз під Nx)історично — версіонування і публікаціядля нових проєктів беруть changesets + turbo/nx
Changesetsверсіонування і CHANGELOG для багатьох пакетів, PR-флоуне оркеструє збірку — доповнює turbo/nx

Коли що: 2–5 пакетів — pnpm workspaces; від десятка пакетів і тривалого CI — Turborepo (простота) або Nx (якщо потрібні генератори й enforced-межі); публікуєте пакети — додайте changesets (changeset add → changeset version → changeset publish).

09 Scripts, lifecycle-хуки, npx і overrides

npm scripts — маленький task runner з неочевидними хуками, один з яких запускає чужий код на вашій машині.

  • npm run x додає node_modules/.bin у PATH — тому в скриптах пишуть tsc, а не ./node_modules/.bin/tsc.
  • pre/post-хуки: npm run build виконує prebuild → build → postbuild. Yarn Berry не запускає довільні pre/post-хуки (лише lifecycle), а в pnpm це залежить від версії і налаштування enable-pre-post-scripts — не покладайтесь на них у кросменеджерному коді.
  • Аргументи: npm run test -- --watch (усе після -- передається скрипту).
  • Змінні: npm виставляє npm_package_version, npm_lifecycle_event, npm_config_*.
terminal (npm 11)
$ npm pkg set scripts.prebuild="echo pre" scripts.build="echo build" scripts.postbuild="echo post"
$ npm run build --silent
pre
build
post
$ npm run build --silent --ignore-scripts
build                      # pre/post пропущені, сам скрипт — ні

Захист — шарами

  • Lockfile + npm ci: нова шкідлива версія не потрапить у збірку, доки ви явно не оновите lock. Integrity-хеш захищає від підміни tarball-а.
  • Затримка на свіжі версії: більшість шкідливих версій виявляють і видаляють за години-дні. pnpm має minimumReleaseAge, Renovate — minimumReleaseAge/"stabilityDays": не брати версію, молодшу за N днів.
  • Вимкнені install-скрипти (див. вище) — закривають найпоширеніший вектор виконання.
  • npm audit — звіряє дерево з GitHub Advisory Database. Корисно, але шумно (багато "high" в devDependencies, недосяжних у рантаймі). npm audit --omit=dev, npm audit fix (без --force, який робить major-апгрейди).
  • Поведінковий аналіз: сервіси типу Socket, Snyk, Aikido, GitHub Dependabot malware alerts дивляться не на CVE, а на поведінку нової версії: з'явився install-скрипт, мережа, eval, обфускація, доступ до env.
  • Provenance і підписи: npm publish --provenance з GitHub Actions/GitLab CI (OIDC + Sigstore) — публічно засвідчує, з якого репо і коміту зібрано пакет; trusted publishing дозволяє публікувати з CI взагалі без довгоживучого токена. Перевірка: npm audit signatures.
  • Мінімізуйте дерево: кожна залежність — ризик; is-odd-рівень пакетів замінюйте рядком коду, дивіться на кількість транзитивних залежностей і maintainer-ів перед додаванням.
  • Секрети в CI: install-крок — без production-секретів; токени npm — granular, з коротким терміном, read-only там, де не потрібна публікація.
  • Scope для внутрішніх пакетів (@acme/*) прив'язаний до приватного реєстру в .npmrc — закриває dependency confusion.

11 Публікація пакета

Що треба зробити, щоб пакет коректно працював у споживачів і не "протік" зайвим.

terminal
npm pack --dry-run                 # подивитись, що потрапить у tarball (files!)
npx publint                        # перевірка exports/main/types
npx @arethetypeswrong/cli --pack   # чи резолвляться типи для ESM/CJS/bundler

npm version minor                  # 2.4.1 → 2.5.0, коміт + git tag v2.5.0
npm publish --provenance --access public
npm version prerelease --preid beta    # 2.5.1-beta.0
npm publish --tag next                 # НЕ стане latest

npm dist-tag ls @acme/route-planner
npm dist-tag add @acme/route-planner@2.5.1 latest
npm deprecate @acme/route-planner@"< 2" "Upgrade to v2"
  • files або .npmignore — інакше в пакет потрапляють тести, .env, вихідники. Класичний інцидент — опублікований .env з ключами чи source maps з усім вихідним кодом.
  • exports + types: умова "types" першою; для dual-пакетів — окремі .d.mts/.d.cts.
  • dist-tags: npm i pkg бере тег latest. Пре-релізи публікуйте з --tag next/beta, інакше всі отримають бету.
  • unpublish вільно дозволено протягом 72 годин після публікації; пізніше — лише якщо немає залежних пакетів, мало завантажень і один власник. Ім'я+версію не можна перевикористати ніколи. Після leftpad-інциденту (2016), коли видалення 11-рядкового пакета зламало збірки півінтернету, правила стали суворими. Зазвичай правильно — deprecate.
  • 2FA на акаунті і для публікації (npm profile enable-2fa auth-and-writes), або trusted publishing з CI без токенів.
  • Автоматизація: changesets або semantic-release (версія з conventional commits).

13 Каверзні питання співбесіди

Від "яка різниця між ^ і ~" до "як ви захищаєте CI від шкідливого postinstall".

БазаЯка різниця між ^1.2.3 і ~1.2.3?
Caret ^1.2.3 = >=1.2.3 <2.0.0 (minor і patch), tilde ~1.2.3 = >=1.2.3 <1.3.0 (лише patch). Для 0.x caret фіксує першу ненульову цифру: ^0.2.3 = <0.3.0, ^0.0.3 = рівно 0.0.3.
Базаnpm install vs npm ci?
ci вимагає lockfile, ставить рівно те, що в ньому, падає при розсинхроні з package.json, видаляє node_modules перед встановленням. install може оновити lockfile. У CI і Docker — завжди ci (або frozen-lockfile аналоги).
ПасткаЧи треба комітити lockfile бібліотеки, якщо він не потрапляє до споживачів?
Так. Він не впливає на споживачів (у них свій), але робить CI і локальну розробку бібліотеки відтворюваними. А щоб ловити поломки від нових версій залежностей — окремий CI-джоб без lockfile або регулярні оновлення ботом.
ПасткаЩо таке phantom dependency і як від неї захиститись?
Імпорт пакета, якого немає у вашому package.json, але він доступний через hoisting транзитивних залежностей. Ламається при оновленні чужої залежності. Захист: pnpm (strict layout), Yarn PnP, ESLint import/no-extraneous-dependencies, інструменти на кшталт knip/depcheck.
БазаКоли пакет має бути в peerDependencies?
Коли ваш пакет — плагін/розширення хоста, і в процесі має бути одна копія хоста (react, eslint, @nestjs/core, typeorm). У dependencies це дасть дублікат і зламані singleton-и/instanceof. З npm 7+ peer-и ставляться автоматично, конфлікт — ERESOLVE.
ПасткаЧому pnpm економить диск, якщо в кожному проєкті є node_modules?
Файли в node_modules — hard links на файли глобального content-addressable store: на диску вони існують один раз на машину. Нова версія пакета додає в store лише змінені файли. Застосунку видно лише прямі залежності (симлінки), решта — в node_modules/.pnpm.
ПасткаЯк захистити CI від шкідливого postinstall у транзитивній залежності?
npm ci --ignore-scripts + точковий npm rebuild для пакетів, яким потрібна компіляція (або pnpm 10 з allowlist onlyBuiltDependencies); install-крок без секретів; lockfile + затримка на свіжі версії; поведінкові сканери (Socket тощо); перевірка provenance.
БазаЩо таке dependency confusion?
Атакувальник публікує у публічний реєстр пакет з ім'ям вашого внутрішнього і вищою версією — менеджер, налаштований на обидва реєстри, бере публічний. Захист: scope (@acme/*) прив'язаний до приватного реєстру в .npmrc, резервування імен, проксі-реєстр з правилами.
БазаЩо дає npm provenance?
Підписане (Sigstore) засвідчення, що конкретна версія пакета зібрана в конкретному CI-workflow з конкретного репозиторію і коміту. Дозволяє виявити версію, опубліковану вручну з вкраденим токеном. Перевірка — npm audit signatures; на npmjs.com — бейдж provenance.
ПасткаВи опублікували 2.0.0-beta.1 без --tag. Що станеться?
Вона отримає тег latest, і npm i pkg у всіх нових користувачів поставить бету. Виправлення: npm dist-tag add pkg@1.9.0 latest і npm dist-tag add pkg@2.0.0-beta.1 next. Надалі — npm publish --tag next для пре-релізів.
БазаНавіщо workspace:* і catalogs у pnpm?
workspace:* гарантує лінк на локальний пакет (не з реєстру) і при публікації замінюється на реальну версію. catalog: — одна версія зовнішньої залежності на весь монорепо, оновлюється в одному місці (pnpm-workspace.yaml).
ПасткаЧим небезпечний npx з неправильним ім'ям?
Якщо бінарника немає локально, npx завантажить і виконає пакет з реєстру з цим ім'ям — ідеальна мішень для typosquatting. Завжди перевіряйте ім'я, вказуйте версію і не використовуйте --yes у скриптах з динамічними іменами.

15 Як запам'ятати

Асоціації для ключових понять екосистеми.

1
Caret ^ vs tilde ~
^ дозволяє minor+patch, ~ лише patch.
Асоціація: ^ — дах будинку (усе під дахом до наступного major-поверху); ~ — хвиля, маленькі коливання.
2
Lockfile
Точний знімок дерева залежностей з хешами integrity.
Асоціація: package.json — рецепт "борошно будь-якого виробника", lockfile — чек з магазину з артикулами.
3
npm ci
Чисте встановлення рівно з lockfile, падає при розсинхроні.
Асоціація: збирати IKEA строго за інструкцією, а не "на око".
4
Phantom dependency
Імпорт пакета, якого немає у вашому package.json, — працює завдяки hoisting.
Асоціація: користуватися Wi-Fi сусіда — поки він не змінив пароль.
5
