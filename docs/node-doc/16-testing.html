01 Піраміда, трофей і що тестувати

Форма тестового набору визначає, чи ловить він реальні баги — і чи не стане він гальмом для кожного рефакторингу.

Класична піраміда (Mike Cohn): багато швидких юніт-тестів, менше інтеграційних, мало e2e. Testing trophy (Kent C. Dodds) зміщує вагу до інтеграційних: «чим більше тест схожий на те, як систему використовують, тим більше впевненості він дає». Для бекенду це особливо доречно: більшість багів живе на стиках — SQL, серіалізація, валідація, middleware, — а не в чистих функціях.

Що тестувати на кожному рівні

РівеньПриклад у Node-бекендіЗалежності
UnitРозрахунок ціни, валідатор, мапер DTO, алгоритм ретраївУсе зовнішнє — fake/stub, без I/O
IntegrationPOST /orders → валідація → сервіс → Postgres → відповідьСправжня БД (testcontainers), зовнішні HTTP — моки
ContractВідповідь нашого API відповідає очікуванням фронтенду/іншого сервісуPact broker або OpenAPI-схема
E2EЛогін → створити маршрут → побачити його в UIРозгорнута система
💡
Тестуйте поведінку, а не реалізацію. Тест, що перевіряє «сервіс викликав repo.save рівно з такими аргументами», ламається при кожному рефакторингу. Тест «після POST /orders запит GET /orders/:id повертає замовлення» переживе заміну ORM. Моки взаємодій — для справжніх побічних ефектів на межі системи (відправка email, оплата), а не для кожного внутрішнього виклику.

02 node:test + node:assert

З Node 20 у вас є повноцінний test runner без жодної залежності: describe/it, хуки, моки, fake timers, snapshot'и, coverage, watch.

Модуль, який тестуємо, отримує залежності параметрами — це робить його тестованим без магії:

price.js
// price.js — модуль із залежностями, переданими через параметри (DI)
export function createPriceService({ rates, clock = () => new Date() }) {
  return {
    async quote(amountUsd, currency) {
      if (amountUsd < 0) throw new RangeError('amount must be >= 0');
      const rate = await rates.get(currency);
      if (!rate) throw new Error(`unknown currency ${currency}`);
      const isNight = clock().getUTCHours() < 6;
      const total = amountUsd * rate * (isNight ? 1.2 : 1);
      return { currency, total: Math.round(total * 100) / 100 };
    },
  };
}
price.test.js
import { describe, it, mock, beforeEach } from 'node:test';
import assert from 'node:assert/strict';
import { createPriceService } from './price.js';

describe('PriceService.quote', () => {
  let rates;
  beforeEach(() => {
    rates = { get: mock.fn(async (c) => ({ EUR: 0.9, UAH: 41 })[c]) };   // stub + spy
  });

  it('конвертує за курсом удень', async () => {
    const svc = createPriceService({ rates, clock: () => new Date('2026-01-01T12:00:00Z') });
    assert.deepEqual(await svc.quote(10, 'EUR'), { currency: 'EUR', total: 9 });
    assert.equal(rates.get.mock.callCount(), 1);
    assert.deepEqual(rates.get.mock.calls[0].arguments, ['EUR']);
  });

  it('нічна надбавка 20%', async () => {
    const svc = createPriceService({ rates, clock: () => new Date('2026-01-01T03:00:00Z') });
    assert.equal((await svc.quote(10, 'UAH')).total, 492);
  });

  it('відхиляє невідому валюту', async () => {
    const svc = createPriceService({ rates });
    await assert.rejects(svc.quote(1, 'XXX'), { message: /unknown currency XXX/ });
  });

  it('відхиляє відʼємну суму типом помилки', async () => {
    const svc = createPriceService({ rates });
    await assert.rejects(() => svc.quote(-1, 'EUR'), RangeError);
    assert.equal(rates.get.mock.callCount(), 0);   // до залежності навіть не дійшло
  });
});

Що варто знати про runner

  • Пошук файлів. node --test без аргументів шукає *.test.js, *-test.js, *_test.js, test-*.js, файли в директоріях test/ (і варіанти .mjs/.cjs, а з type stripping — і .ts). Можна передати glob: node --test "src/**/*.test.js".
  • Ізоляція. Кожен файл за замовчуванням запускається в окремому підпроцесі, файли — паралельно (--test-concurrency). Тести всередині файлу — послідовно, якщо не вказати { concurrency: true }.
  • Фільтри: --test-name-pattern="нічна", --test-skip-pattern, it.only + --test-only, it.skip, it.todo.
  • Watch: node --test --watch перезапускає тести, що залежать від змінених файлів.
  • Репортери: spec (дефолт у терміналі), tap, dot, junit, lcov; кілька одночасно: --test-reporter=spec --test-reporter=junit --test-reporter-destination=stdout --test-reporter-destination=junit.xml.
  • Strict assert. Імпортуйте node:assert/strict: equal там — це ===, deepEqual — строгий (з урахуванням типів і прототипів). Нестрогий assert.equal('1', 1) проходить — типова пастка.

Падіння показує зрозумілий diff:

Snapshot-тести

snapshot.test.js
test('snapshot відповіді API', (t) => {
  const body = { id: 1, status: 'planned', stops: [{ seq: 1, addr: 'Kyiv' }] };
  t.assert.snapshot(body);
});
// перший запуск / оновлення:  node --test --test-update-snapshots
// створює поруч файл async.test.js.snapshot з exports[`snapshot відповіді API 1`] = `{ ... }`

Snapshot'и зручні для великих стабільних структур (згенерований SQL, OpenAPI-документ, повідомлення помилок), але небезпечні як «замінник думання»: якщо команда звикла запускати --test-update-snapshots не дивлячись на diff, тест нічого не перевіряє. Динамічні поля (дати, uuid) нормалізуйте перед snapshot'ом.

🧠 Запам'ятай: node --test + node:assert/strict — нуль залежностей, файли паралельно в підпроцесах.

03 Моки в node:test

Вбудований mock покриває 90% потреб: шпигунські функції, підміну методів, фейковий час і (експериментально) підміну модулів.

APIЩо робить
mock.fn(impl?)Функція-шпигун: записує calls (arguments, result, error, this), callCount(); mockImplementation, mockImplementationOnce
mock.method(obj, 'name', impl?)Підміняє метод об'єкта (або getter/setter), зберігає оригінал; .mock.restore()
mock.timers.enable({ apis, now })Фейкові setTimeout/setInterval/setImmediate/Date; tick(ms), runAll()
mock.module(specifier, opts)Підміна імпортованого модуля (ESM і CJS); потребує --experimental-test-module-mocks
t.mock vs mockt.mock.* автоматично відновлюється після тесту; глобальний mock — вручну через mock.restoreAll()/mock.reset()
retry.js
// retry з експоненційною затримкою — класичний "залежний від часу" код
const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

export async function retry(fn, { attempts = 3, baseMs = 100 } = {}) {
  for (let i = 0; ; i++) {
    try { return await fn(); }
    catch (err) {
      if (i + 1 >= attempts) throw err;
      await sleep(baseMs * 2 ** i);          // 100, 200, 400...
    }
  }
}

export function debounce(fn, ms) {
  let t;
  return (...args) => { clearTimeout(t); t = setTimeout(() => fn(...args), ms); };
}
time.test.js — node --test time.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { debounce, retry } from './retry.js';

test('debounce викликає fn один раз після тиші', (t) => {
  t.mock.timers.enable({ apis: ['setTimeout'] });
  const fn = t.mock.fn();
  const d = debounce(fn, 300);
  d('a'); t.mock.timers.tick(200);
  d('b'); t.mock.timers.tick(299);
  assert.equal(fn.mock.callCount(), 0);
  t.mock.timers.tick(1);
  assert.equal(fn.mock.callCount(), 1);
  assert.deepEqual(fn.mock.calls[0].arguments, ['b']);
});

test('Date теж можна заморозити', (t) => {
  t.mock.timers.enable({ apis: ['Date'], now: new Date('2026-03-01T00:00:00Z') });
  assert.equal(new Date().toISOString(), '2026-03-01T00:00:00.000Z');
  t.mock.timers.tick(60_000);
  assert.equal(new Date().toISOString(), '2026-03-01T00:01:00.000Z');
});

test('mock.method підміняє метод обʼєкта і відновлюється', (t) => {
  const mailer = { send: (to) => `real send to ${to}` };
  t.mock.method(mailer, 'send', () => 'fake');
  assert.equal(mailer.send('a@b.c'), 'fake');
  assert.equal(mailer.send.mock.calls.length, 1);
  mailer.send.mock.restore();                 // або автоматично після тесту (t.mock)
  assert.equal(mailer.send('a@b.c'), 'real send to a@b.c');
});

test('retry: 3 спроби з backoff 100 → 200 мс без реального очікування', async (t) => {
  t.mock.timers.enable({ apis: ['setTimeout'] });
  let n = 0;
  const fn = t.mock.fn(async () => { if (++n < 3) throw new Error('boom'); return 'ok'; });
  const flush = () => new Promise(setImmediate);   // дати промісам дійти до setTimeout

  const p = retry(fn, { attempts: 3, baseMs: 100 });
  await flush(); assert.equal(fn.mock.callCount(), 1);
  t.mock.timers.tick(99);  await flush(); assert.equal(fn.mock.callCount(), 1);
  t.mock.timers.tick(1);   await flush(); assert.equal(fn.mock.callCount(), 2);
  t.mock.timers.tick(200); await flush();
  assert.equal(await p, 'ok');
  assert.equal(fn.mock.callCount(), 3);
});

✔ debounce викликає fn один раз після тиші (2.495964ms)
✔ Date теж можна заморозити (1.472447ms)
✔ mock.method підміняє метод обʼєкта і відновлюється (0.458891ms)

Тест ретраїв зайняв 6 мс замість 300. Головна тонкість — фейкові таймери + проміси: tick() синхронно запускає колбеки таймерів, але await після них виконується в мікрозадачах. Тому між тіками потрібно «промити» чергу (flush через справжній setImmediate — ми його не мокали). Якщо замокати всі API, flush доведеться робити інакше — це найчастіша причина «тест з fake timers висить».

04 Jest vs Vitest vs Mocha

Вибір раннера — це насамперед вибір того, як він дружить з ESM і TypeScript вашого проєкту.

Jest

Довго був стандартом: «батарейки» (assert'и expect, моки, snapshot'и, coverage, паралельні воркери, watch). Модульні моки jest.mock('./x') автоматично піднімаються (hoisting) над імпортами через babel-трансформацію. Біль — ESM: нативний ESM вимагає NODE_OPTIONS=--experimental-vm-modules, а jest.mock там не працює — потрібен jest.unstable_mockModule + динамічний await import() після нього. TypeScript — через ts-jest (з type-check, повільніше) або babel-jest/@swc/jest (лише видаляє типи, швидко). Кожен тестовий файл живе в окремому vm-контексті: ізоляція добра, але instanceof між контекстами іноді дивує, а холодний старт повільний.

Vitest

Побудований на Vite/esbuild: ESM і TypeScript «з коробки», API майже повністю Jest-сумісний (describe/it/expect, vi.fn, vi.mock з hoisting, vi.useFakeTimers), швидкий watch з розумінням графа залежностей, coverage через V8 або istanbul. Для нових TS/ESM-проєктів — дефолтний вибір; міграція з Jest часто зводиться до заміни jest. на vi..

Mocha + Chai + Sinon

Legacy-стек: Mocha — лише runner, Chai — assertions (expect(x).to.equal), Sinon — spies/stubs/fake timers, nyc/c8 — coverage. Гнучко, але все збираєте самі. Зустрічається в старих кодових базах; нові проєкти рідко його обирають.

Коли що: бібліотека або невеликий сервіс без бандлера → node:test; TS/ESM-застосунок, команда звикла до Jest API → Vitest; існуючий Nest-проєкт на Jest, що працює, → не мігрувати заради моди; legacy на Mocha → лишити, нові тести можна писати в тому ж стилі.

price.vitest.test.ts — той самий тест на Vitest
import { describe, it, expect, vi } from 'vitest';
import { createPriceService } from './price';

describe('PriceService.quote', () => {
  it('нічна надбавка 20%', async () => {
    const rates = { get: vi.fn().mockResolvedValue(41) };
    const svc = createPriceService({ rates, clock: () => new Date('2026-01-01T03:00:00Z') });
    await expect(svc.quote(10, 'UAH')).resolves.toEqual({ currency: 'UAH', total: 492 });
    expect(rates.get).toHaveBeenCalledWith('UAH');
  });
});
⚠️
Пастка з expect(...).rejects. Без await (або return) асинхронна перевірка не чекається, тест проходить «зеленим» навіть коли проміс не відхилено. У node:test те саме з assert.rejects — завжди await assert.rejects(...).

05 Таксономія test doubles

«Мок» у розмовній мові означає що завгодно; на співбесіді очікують, що ви розрізняєте п'ять видів дублерів за Мезаросом/Фаулером.

  • Spy vs mock. У Jest/Vitest/node:test fn() — технічно spy (перевірка після: toHaveBeenCalledWith). Класичний mock (Sinon mock().expects(...)) програмується наперед і падає сам. У розмові обидва звуть «моками» — на співбесіді покажіть, що розумієте різницю.
  • Fake найкращий для репозиторіїв. InMemoryOrderRepo з Map дозволяє тестувати сервіс через стан («після create є findById»), а не через виклики. Але fake може розійтися з реальною БД (унікальні індекси, транзакції) — тому інтеграційні тести зі справжньою БД все одно потрібні.
  • Не мокайте те, чим не володієте (don't mock what you don't own): замість мока SDK Stripe напишіть свій тонкий адаптер PaymentsGateway, мокайте його в юніт-тестах, а сам адаптер перевірте інтеграційно (з HTTP-моком або sandbox).

06 Шви: DI vs module mocking, HTTP-моки

«Шов» (seam) — місце, де тест може підмінити поведінку без зміни коду; від вибору шва залежить, наскільки тести крихкі.

🔀 Вузол вибору: як підміняти залежність
ВаріантПлюсиМінуси

Мережевий шов: три інструменти

undici MockAgent — для вбудованого fetch
import { MockAgent, setGlobalDispatcher, getGlobalDispatcher } from 'undici';

const original = getGlobalDispatcher();
const agent = new MockAgent();
agent.disableNetConnect();                     // будь-який незамоканий запит — помилка
setGlobalDispatcher(agent);

agent.get('https://api.rates.example')
  .intercept({ path: '/v1/EUR', method: 'GET' })
  .reply(200, { rate: 0.9 }, { headers: { 'content-type': 'application/json' } });

// ... викликати код, що робить fetch('https://api.rates.example/v1/EUR')

agent.assertNoPendingInterceptors();           // усі очікувані запити справді відбулися
setGlobalDispatcher(original);

Глобальний fetch використовує вбудовану копію undici; npm-пакет undici ставить dispatcher через спільний глобальний символ, тож працює з ним — але тримайте мажорну версію пакета сумісною з версією Node.

msw — однакові хендлери для браузера і Node

});

nock — класика для http/https-модулів (axios, got); новіші мажорні версії перехоплюють і fetch. Для швидкого юніт-тесту часто вистачає й простого t.mock.method(globalThis, 'fetch', async () => Response.json({ rate: 0.9 })) — перевірено на Node 24, працює.

💼
На співбесіді запитають так «Як протестувати код, що ходить у зовнішній API?» — Розділити: бізнес-логіка отримує адаптер через DI (тест зі stub); сам адаптер тестується з мережевим моком (MockAgent/msw/nock) зі disableNetConnect/onUnhandledRequest: 'error', включно з таймаутами, 5xx, некоректним JSON; відповідність реальному API — контрактним тестом або періодичним smoke-тестом проти sandbox.

07 Час, async, події, стріми, помилки

Найпідступніші тести — асинхронні: вони можуть «пройти», нічого не перевіривши, або висіти до таймауту.

async.test.js — node --test async.test.js
import { test } from 'node:test';
import assert from 'node:assert/strict';
import { EventEmitter, once } from 'node:events';
import { Readable, Transform } from 'node:stream';
import { pipeline } from 'node:stream/promises';

test('подія: чекаємо через events.once з таймаутом', async () => {
  const job = new EventEmitter();
  setImmediate(() => job.emit('done', { id: 42 }));
  const [payload] = await once(job, 'done', { signal: AbortSignal.timeout(1000) });
  assert.deepEqual(payload, { id: 42 });
});

test('подія error відхиляє once', async () => {
  const job = new EventEmitter();
  setImmediate(() => job.emit('error', new Error('disk full')));
  await assert.rejects(once(job, 'done'), /disk full/);
});

test('стрім: Transform у верхній регістр', async () => {
  const upper = new Transform({
    transform(chunk, _enc, cb) { cb(null, chunk.toString().toUpperCase()); },
  });
  const chunks = [];
  await pipeline(Readable.from(['a', 'b', 'c']), upper, async function (source) {
    for await (const c of source) chunks.push(c.toString());
  });
  assert.equal(chunks.join(''), 'ABC');   // межі чанків не гарантовані — порівнюємо склеєне
});

test('синхронний throw: assert.throws', () => {
  assert.throws(() => JSON.parse('{bad'), SyntaxError);
});
вивід
✔ подія: чекаємо через events.once з таймаутом (5.361267ms)
✔ подія error відхиляє once (1.424762ms)
✔ стрім: Transform у верхній регістр (5.634608ms)
✔ синхронний throw: assert.throws (0.389743ms)
🎉
Цікавий факт Перша версія тесту стрімів порівнювала масив ['A','B','C'] і впала: не-objectMode Transform склеює рядки з Readable.from у буфер, і чанки прийшли інакше. Мораль — у тестах стрімів перевіряйте зміст, а не межі чанків, якщо межі не є частиною контракту.

Правила асинхронних тестів

  • Завжди await або return проміс у тесті. Тест, що не дочекався, «зелений» назавжди, а помилка вилетить як unhandled rejection в іншому тесті.
  • Події чекайте через events.once з AbortSignal.timeout — інакше тест, у якому подія не настала, висить до глобального таймауту.
  • Помилки — assert.rejects/assert.throws з перевіркою типу або повідомлення, а не порожній try/catch (який пройде, якщо помилки не було взагалі).
  • Час — інжектити clock (як createPriceService) або mock.timers. Ніколи await sleep(1000) «щоб встигло» — це і повільно, і flaky.
  • Таймаут на тест: it('...', { timeout: 2000 }, fn) або --test-timeout.
  • Ресурси: закривати сервери, пули, таймери в after/afterEach. Відкритий handle тримає процес тесту живим — runner «висить» після останнього тесту (Jest пише «did not exit one second after the test run»).

08 HTTP-тести: supertest, inject, Nest

Інтеграційний тест через HTTP перевіряє маршрутизацію, валідацію, серіалізацію, коди статусів і middleware — усе, що юніт-тести пропускають.

Без бібліотек: справжній сервер на порту 0

app.js
import http from 'node:http';
export function createApp({ repo }) {
  return http.createServer(async (req, res) => {
    const m = req.url.match(/^\/orders\/(\d+)$/);
    const order = m && await repo.findById(Number(m[1]));
    res.writeHead(order ? 200 : 404, { 'content-type': 'application/json' });
    res.end(JSON.stringify(order ?? { error: 'not found' }));
  });
}
app.test.js — node --test app.test.js
import { describe, it, before, after } from 'node:test';
import assert from 'node:assert/strict';
import { once } from 'node:events';
import { createApp } from './app.js';

describe('GET /orders/:id', () => {
  let server, base;
  before(async () => {
    const repo = { findById: async (id) => (id === 1 ? { id: 1, status: 'new' } : null) }; // fake
    server = createApp({ repo }).listen(0);          // порт 0 = ОС видасть вільний
    await once(server, 'listening');
    base = `http://127.0.0.1:${server.address().port}`;
  });
  after(() => server.close());

  it('200 для існуючого', async () => {
    const res = await fetch(`${base}/orders/1`);
    assert.equal(res.status, 200);
    assert.deepEqual(await res.json(), { id: 1, status: 'new' });
  });

  it('404 для відсутнього', async () => {
    const res = await fetch(`${base}/orders/999`);
    assert.equal(res.status, 404);
  });
});

NestJS: Test.createTestingModule

orders.e2e-spec.ts
import { Test } from '@nestjs/testing';
import { INestApplication, ValidationPipe } from '@nestjs/common';
import request from 'supertest';
import { AppModule } from '../src/app.module';
import { PaymentsGateway } from '../src/payments/payments.gateway';

describe('Orders (e2e)', () => {
  let app: INestApplication;
  const payments = { charge: jest.fn().mockResolvedValue({ id: 'ch_1' }) };

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
      .overrideProvider(PaymentsGateway).useValue(payments)   // DI-шов Nest
      .compile();
    app = moduleRef.createNestApplication();
    app.useGlobalPipes(new ValidationPipe({ whitelist: true })); // ті самі пайпи, що в main.ts!
    await app.init();
  });
  afterAll(() => app.close());

  it('POST /orders → 201', () =>
    request(app.getHttpServer()).post('/orders').send({ stops: [{ addr: 'Kyiv' }] }).expect(201));
});
⚠️
Класична Nest-пастка: глобальні пайпи, фільтри та інтерсептори, налаштовані в main.ts, не застосовуються в createNestApplication() тесту. Винесіть конфігурацію в спільну функцію configureApp(app) і викликайте її і в main.ts, і в тесті — або реєструйте їх через провайдери APP_PIPE/APP_FILTER у модулі. 09 Тести з базою даних

Мок репозиторію не знайде помилку в SQL, міграції чи унікальному індексі — для цього потрібна справжня БД того ж типу і версії, що в проді.

Testcontainers: справжній Postgres на тест-ран

test/global-setup.js
import { PostgreSqlContainer } from '@testcontainers/postgresql';
import { execSync } from 'node:child_process';

let container;
export async function globalSetup() {
  container = await new PostgreSqlContainer('postgres:16-alpine').start();   // та сама major-версія, що в проді

  execSync('npx prisma migrate deploy', { stdio: 'inherit' });              // або knex/typeorm migrations

export async function globalTeardown() {
  await container?.stop();
}

Testcontainers запускає Docker-контейнер з випадковим портом і чекає готовності. Один контейнер на весь прогін (global setup — --test-global-setup у node:test, globalSetup у Vitest/Jest), а не на кожен тест — інакше прогін триватиме хвилини. SQLite в пам'яті замість Postgres — економія, що бреше: інші типи, інші блокування, немає jsonb, ON CONFLICT поводиться інакше.

10 Контрактні та e2e-тести

Коли сервісів кілька, найдорожчі баги — розбіжність очікувань між ними; контрактні тести ловлять її без розгортання всього світу.

Consumer-driven contracts (Pact)

Consumer-тест (фронт / сервіс A) описує очікувані запити й відповіді
→
Pact-файл (JSON-контракт)
→
Pact Broker
→
Provider verification: справжній API сервісу B проганяє контракт
→
can-i-deploy перед релізом
  • Consumer-тест працює проти mock-сервера Pact і водночас записує контракт. Провайдер у своєму CI відтворює кожну взаємодію проти себе (з provider states — «замовлення 42 існує» — які налаштовують дані).
  • Перевіряється лише те, що consumer реально використовує: провайдер може додавати поля, не ламаючи нікого, але видалити поле, яке хтось читає, — CI не дасть.
  • Альтернатива для одного API з багатьма клієнтами — schema-first: OpenAPI як контракт, валідація відповідей у тестах (наприклад, через згенеровані zod/ajv-схеми) і diff схеми на breaking changes у CI.

E2E

Наскрізні тести (Playwright для UI+API, або чисто API-сценарії на k6/Postman/власних скриптах проти preview-оточення) — найповільніші й найкрихкіші. Тримайте їх мало: 5–20 критичних шляхів (логін, оплата, створення головної сутності), запускайте на preview-оточенні перед merge або після deploy як smoke. Кожна перевірка, яку можна опустити на інтеграційний рівень, має туди переїхати.

💼
На співбесіді запитають так «Чим контрактний тест відрізняється від інтеграційного?» — Інтеграційний перевіряє, що наш сервіс працює зі своїми залежностями (БД). Контрактний перевіряє, що два незалежно розгорнуті сервіси однаково розуміють спільний інтерфейс, при цьому кожна сторона тестується окремо у своєму CI.

11 Coverage і його межі

Coverage показує, який код не виконувався тестами; він нічого не каже про те, чи перевіряли ви результат.

Сучасний спосіб — V8 coverage: рушій сам рахує виконані блоки, без інструментування коду (на відміну від istanbul/nyc, що переписує код лічильниками). Варіанти: node --test --experimental-test-coverage, c8 node --test (обгортка над V8 coverage з istanbul-звітами html/lcov), vitest --coverage з провайдером v8.

термінал — node --test --experimental-test-coverage (на прикладах цього туторіалу)
ℹ start of coverage report
ℹ ----------------------------------------------------------
ℹ file      | line % | branch % | funcs % | uncovered lines
ℹ ----------------------------------------------------------
ℹ price.js  | 100.00 |   100.00 |   66.67 |
ℹ retry.js  | 100.00 |    81.82 |  100.00 |
ℹ ----------------------------------------------------------
ℹ all files | 100.00 |    90.00 |   88.89 |
ℹ ----------------------------------------------------------
ℹ end of coverage report

Цей звіт — готовий урок. 100% рядків у price.js, але функцій 66.67%: дефолтний clock = () => new Date() не викликався жодного разу — усі тести передавали свій годинник або падали раніше. У retry.js 100% рядків, але гілки 81.82%: серед непокритих — саме сценарій, коли спроби вичерпано і помилка має прокинутись нагору (if (i + 1 >= attempts) throw err — рядок виконувався, але гілка «true» — ні). Додавши один тест на вичерпання спроб, ми підняли branches до 90% (решта — невикористані дефолтні параметри). Тобто баг у найважливішому сценарії ретраїв пройшов би непоміченим при «100% line coverage».

Чого coverage не каже

  • Наявність асертів. Тест без жодного assert дає таке саме покриття, як і хороший.
  • Комбінації. Кожна гілка окремо покрита ≠ покриті всі комбінації гілок (path coverage).
  • Відсутній код. Забута перевірка прав доступу не може бути «непокритою» — її просто немає.
  • Інтеграцію. 100% юніт-покриття з моками не доводить, що SQL правильний.

Корисні практики: поріг як «не падати нижче» (--test-coverage-lines=80 --test-coverage-branches=70 у node:test, thresholds у Vitest), дивитися coverage diff у PR (нові рядки без тестів), а для оцінки якості асертів — mutation testing (Stryker): він змінює код (< на <=, видаляє виклики) і перевіряє, чи впаде хоч один тест.

🧠 Запам'ятай: coverage — це карта неперевіреного, а не сертифікат якості; дивіться на branches, а не лише на lines.

12 Flaky-тести

Тест, що іноді падає без змін у коді, гірший за відсутній: команда вчиться ігнорувати червоний CI.

13 Тести в CI

Швидкий фідбек у PR — це паралелізм, кешування та правильний порядок кроків: дешеві й найчастіше падаючі перевірки — першими.

.github/workflows/test.yml (фрагмент)
jobs:
  unit:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: true
      matrix:
        shard: [1, 2, 3]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }          # кеш ~/.npm за package-lock.json
      - run: npm ci
      - run: >
          node --test --test-shard=${{ matrix.shard }}/3
          --experimental-test-coverage
          --test-reporter=spec --test-reporter-destination=stdout
          --test-reporter=junit --test-reporter-destination=junit-${{ matrix.shard }}.xml
        env: { TZ: UTC, NODE_ENV: test }
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: junit-${{ matrix.shard }}, path: junit-*.xml }
  • Паралелізм на двох рівнях: всередині машини (воркери раннера — node:test запускає файли паралельно) і між машинами (шарди: --test-shard, vitest --shard=1/3, jest --shard=1/3). Шарди ділять файли, тож один гігантський тестовий файл не розпаралелиться.
  • Кешування: ~/.npm за хешем lockfile (не node_modules — npm ci однаково його видаляє), Docker-образи для testcontainers, кеш трансформацій Vitest/Jest. Turborepo/Nx у монорепо запускають лише тести змінених пакетів.
  • Оточення: TZ=UTC, фіксована локаль, та сама major-версія Node, що в проді (matrix по 2 версіях для бібліотек).
  • Звіти: JUnit XML — щоб CI показував, який тест упав, без читання логів; lcov з усіх шардів зливається для coverage-коментаря в PR.
  • Порядок: lint і typecheck за секунди відсікають більшість помилок; інтеграційні й e2e — після них. Детальніше про пайплайни деплою — туторіал 17.

14 Каверзні питання співбесіди

Питання, що відрізняють «пишу тести, бо треба» від «проєктую тестову стратегію».

БазаПіраміда чи трофей — що обрати для REST-бекенду?
Для бекенду, де більшість логіки — оркестрація БД і зовнішніх сервісів, — ближче до трофея: основа статичний аналіз (TS, ESLint), багато інтеграційних тестів через HTTP зі справжньою БД, юніт-тести для чистої складної логіки (ціни, алгоритми), мінімум e2e. Піраміда доречна, коли домен багатий на чисту логіку.
БазаЧим stub відрізняється від mock і spy?
Stub повертає заготовлені відповіді (state verification). Spy — stub, що ще й записує виклики, перевірка після дії. Mock заздалегідь знає очікувані виклики і сам їх верифікує (behavior verification). Fake — робоча спрощена реалізація (in-memory repo). Dummy — заглушка параметра.
ПасткаТест з expect(promise).rejects.toThrow() проходить, хоча функція не кидає. Чому?
Немає await/return — тест завершився синхронно до перевірки, а відхилення (або його відсутність) нікого не цікавить. Те саме з assert.rejects без await. Лікується await і правилом ESLint @typescript-eslint/no-floating-promises / jest/valid-expect.
ПасткаЧому jest.mock('./db') не працює в нативному ESM-проєкті?
ESM-імпорти статичні й зв'язуються до виконання коду, тому трюк з hoisting jest.mock над require не спрацьовує. Потрібно jest.unstable_mockModule('./db', factory) і потім await import('./service.js') — динамічний імпорт після реєстрації мока (і --experimental-vm-modules). Vitest вирішує це своїм трансформером, node:test — mock.module + динамічний import.
БазаЯк протестувати код із setTimeout/Date.now() без очікування?
Інжектити годинник (clock параметром) або fake timers: t.mock.timers.enable({ apis: ['setTimeout', 'Date'] }) + tick(ms) у node:test, vi.useFakeTimers() + vi.advanceTimersByTimeAsync у Vitest. Пастка: між тіками треба «промивати» мікрозадачі, інакше код після await не дійде до наступного таймера.
Пастка100% line coverage — чи достатньо?
Ні. Coverage не перевіряє наявність асертів, комбінації гілок і відсутній код. Рядок if (i + 1 >= attempts) throw err може бути «покритим», хоча гілка з throw не виконувалась жодного разу (branch coverage < 100%). Для якості асертів — mutation testing (Stryker).
БазаЯк ізолювати тести, що працюють зі спільною БД?
Testcontainers (одна БД на прогін) + одна зі стратегій: транзакція на тест з rollback (швидко, але не для коду з власними транзакціями), TRUNCATE в beforeEach, окрема схема/БД на паралельного воркера, або унікальні дані (свій tenant на тест). Плюс фабрики замість спільного seed.
ПасткаTransaction-per-test rollback — у чому підступ?
Код під тестом має використовувати те саме з'єднання, де відкрито транзакцію. Якщо сервіс бере інший клієнт з пулу — він не бачить незакомічених даних тесту. Код, що сам робить BEGIN/COMMIT, конфліктує (потрібні savepoints). І не тестуються ефекти commit: тригери deferred constraints, LISTEN/NOTIFY, видимість для інших з'єднань.
БазаНавіщо відокремлювати buildApp() від listen()?
Щоб тест створював застосунок з тестовими залежностями і сам вирішував, як його запускати: supertest(app), fastify.inject() без мережі або listen(0) на випадковому порту. Інакше імпорт модуля застосунку піднімає сервер на фіксованому порту — EADDRINUSE при паралельних тестах.
ПасткаТестовий процес не завершується після проходження всіх тестів. Причини?
Відкриті handles: незакритий HTTP-сервер, пул БД (pool.end()), Redis-клієнт, setInterval, keep-alive сокети. Лікувати закриттям в after, а не --test-force-exit/--forceExit — ті ховають витоки ресурсів, які в проді заважатимуть graceful shutdown.
БазаЩо таке контрактний тест і коли він кращий за e2e?
Consumer записує очікувані взаємодії (Pact), provider у своєму CI перевіряє їх проти реального коду. Кожна сторона тестується окремо, без розгортання обох — швидше й стабільніше за e2e, і точно показує, яка зміна ламає якого споживача (can-i-deploy).
ПасткаЧому вмикати автоматичні ретраї flaky-тестів у CI — погана довгострокова стратегія?
Ретраї ховають симптом. Частина «flaky» тестів ловить справжні гонки в продакшн-коді (порядок промісів, відсутність ORDER BY, спільний стан). Краще: карантин з тікетом і власником, --test-randomize для виявлення залежності від порядку, fake timers замість sleep.
БазаЧим шардинг відрізняється від паралельних воркерів?
Воркери паралелять файли всередині однієї машини (обмежені її ядрами й спільними ресурсами). Шардинг (--test-shard=2/3) ділить набір файлів між кількома CI-машинами. Обидва працюють на рівні файлів — великий файл не розіб'ється, тому тести краще тримати в багатьох помірних файлах.

16 Як запам'ятати

Вісім образів для швидкого пригадування.

1
Testing trophy
Основа — статичний аналіз, центр ваги — інтеграційні тести, мало e2e.
Асоціація: кубок — найширша частина посередині, а не внизу.
2
Stub
Дублер, що повертає заготовлені відповіді.
Асоціація: автовідповідач: «залиште повідомлення» — завжди однаково.
3
Spy
Записує, як його викликали, щоб перевірити після дії.
Асоціація: відеореєстратор — нічого не вирішує, але все записує.
4
Fake
Робоча спрощена реалізація, напр. in-memory репозиторій.
Асоціація: тренажер-симулятор польоту — літає по-справжньому, але без неба.
5
Seam (шов)
Місце, де тест підміняє поведінку: DI, завантажувач модулів, мережа.
Асоціація: розетка — прилад можна замінити, не розбираючи стіну.
6
Fake timers + flush
tick() запускає таймери, але await після них чекає мікрозадач — промивайте чергу.
Асоціація: перемотати годинник уперед не означає, що кур'єр уже доніс посилку до дверей.
7
Branch coverage
Чи виконувалась кожна гілка умови; суворіше за line coverage.
Асоціація: проїхати перехрестя ≠ проїхати кожен поворот з нього.
8
Contract test
Consumer записує очікування, provider перевіряє їх у своєму CI.
Асоціація: договір оренди — кожна сторона перевіряє свої зобов'язання окремо, без спільного переїзду.
9
Flaky test
Падає без змін у коді: спільний стан, час, порядок, порти, мережа.
Асоціація: пожежна сигналізація, що спрацьовує від тостера — скоро її перестануть чути.
10
Port 0
listen(0) — ОС видає вільний порт, паралельні тести не конфліктують.
Асоціація: «посадіть мене куди завгодно» в ресторані — ніколи не чекаєш на конкретний столик.
