01 Ментальна модель: що відбувається, коли запит потрапляє в систему

🎯
На співбесіді: на high-level схемі достатньо «Client → LB/API Gateway → Services». Розгортайте мережевий шар у deep dive лише тоді, коли він важливий для задачі: глобальна латентність (CDN, GeoDNS), real-time (WebSocket-шар), відео (CDN), публічний API (rate limiting, versioning).
DNS → CDN → LB → gateway → сервіс → дані. Кожен шар має чітку відповідальність; додавайте шар на схему лише з причиною.

02 DNS: записи, TTL, GeoDNS, anycast

DNS — це розподілена, ієрархічна, агресивно кешована база даних «ім'я → адреса». Для System Design він важливий як перший інструмент маршрутизації трафіку: між регіонами, при failover і для міграцій.

TTL: компроміс між гнучкістю і навантаженням

Короткий TTL (30–60 с)

  • Швидкий failover і перемикання регіонів
  • Більше запитів до авторитетних серверів, трохи більша латентність при промахах
  • Частину клієнтів все одно не прискорить: деякі резолвери/рантайми ігнорують TTL

Довгий TTL (година–доба)

  • Майже все обслуговується з кешів, стабільно
  • Помилкова зміна або міграція «застрягає» на години
  • Прийом: знизити TTL заздалегідь (за TTL до міграції), переключити, потім підняти

GeoDNS і anycast: як привести користувача в найближчу точку

  • GeoDNS / latency-based routing (наприклад, Route 53 latency/geolocation routing): авторитетний сервер дивиться на IP резолвера (або на EDNS Client Subnet, якщо резолвер його передає) і повертає адресу найближчого регіону. Плюс — точний контроль; мінус — користувач з публічним резолвером в іншій країні може отримати «не той» регіон, а перемикання впирається в TTL.
  • Anycast: один IP-префікс анонсують з багатьох точок присутності (PoP). Так працюють кореневі DNS-сервери (13 «імен» root-серверів, але сотні фізичних інстансів), публічні резолвери 1.1.1.1 і 8.8.8.8, мережа Cloudflare. Плюси: failover без очікування TTL (PoP перестає анонсувати маршрут — трафік іде в інший), природне «розмазування» DDoS-атак. Мінус: маршрут може змінитися посеред TCP-з'єднання, тому anycast особливо природний для UDP (DNS) і короткоживучих з'єднань, а для довгих потрібні додаткові інженерні рішення.

Як це роблять у реальних системах

Cloudflare за публічними матеріалами використовує anycast для всієї своєї мережі: кожен сервер у кожному PoP може обслуговувати будь-який сервіс, тож атака розподіляється по всій мережі. AWS Route 53 пропонує weighted, latency-based, geolocation і failover routing policies — класичний інструмент для active-passive multi-region: health check первинного регіону падає → DNS віддає адресу резервного.

🚩
Пастки: (1) «DNS round robin замість load balancer» — DNS не знає про стан серверів, кешується, а клієнти часто беруть перший запис; (2) розраховувати на миттєвий failover через DNS при TTL у годину; (3) забути про негативне кешування — відповідь «такого імені немає» (NXDOMAIN) теж кешується.
Аналогія для фронтендера
DNS-кешування з TTL — це Cache-Control: max-age для адрес. Коли ви змінили DNS, а «у колеги досі стара версія», — це та сама історія, що й зі старим index.html у кеші браузера. <link rel="dns-prefetch"> і preconnect у вашому HTML існують саме тому, що DNS + TCP + TLS — це сотні мілісекунд на холодному з'єднанні. Де ламається: HTTP-кеш ви можете скинути versioned URL, а DNS-кеш на мільйонах резолверів не скине ніхто — тільки чекати TTL.
🎯
На співбесіді: DNS згадуйте в контексті multi-region («GeoDNS / latency-based routing направляє користувача в найближчий регіон; при відмові регіону health check перемикає DNS, але з урахуванням TTL це хвилини, тому для швидшого failover — anycast або глобальний LB»). Для одного регіону DNS просто «є», на ньому не зупиняйтесь.
DNS — кешована ієрархія; TTL = компроміс швидкості змін і навантаження. GeoDNS вирішує в DNS-відповіді, anycast — у маршрутизації. DNS round robin ≠ load balancer.

03 CDN: pull vs push, cache keys, інвалідація, Netflix Open Connect

CDN (Content Delivery Network) — мережа кешуючих серверів (edge, PoP) по всьому світу. Вона зменшує латентність (фізично ближче), знімає навантаження з origin і поглинає піки й атаки. На співбесіді CDN — стандартна відповідь на «багато статичного контенту, глобальні користувачі».

Pull vs push

Pull (origin pull)

  • CDN завантажує об'єкт з origin при першому запиті, далі — з кешу до TTL
  • Нічого не треба завантажувати заздалегідь, просто підключити домен
  • Перший користувач у кожному PoP отримує «холодний» промах
  • Стандарт для вебсайтів, зображень, API-відповідей

Push (pre-positioning)

  • Ви самі заливаєте контент на CDN/edge до того, як його попросять
  • Передбачувано: немає холодних промахів, origin не бачить сплесків
  • Треба керувати місцем і розкладкою: що, куди, коли видаляти
  • Великі файли, відомі заздалегідь: відео, ігрові оновлення, релізи

Cache key: що робить два запити «однаковими»

  • За замовчуванням ключ — це URL (host + path + query). Нормалізуйте query: ?utm_source=… і порядок параметрів не повинні створювати окремі копії — інакше hit ratio падає.
  • Vary: Accept-Encoding — окремі копії для gzip/brotli; Vary: Cookie або Authorization фактично вимикають спільне кешування — персоналізовані відповіді CDN зазвичай не кешує (або кешує з Cache-Control: private лише браузер).
  • Не кешуйте помилки надовго і не кешуйте відповіді з Set-Cookie — класичні причини інцидентів, коли користувачі бачили чужі дані.

Як це роблять у реальних системах: Netflix Open Connect

За публічними матеріалами Netflix, Open Connect — власна CDN компанії: Open Connect Appliances (OCA) безкоштовно ставляться у мережі провайдерів і на точках обміну трафіком (IXP). Усе, що не є передачею відео (каталог, рекомендації, авторизація, вибір OCA), працює в AWS. Контент на OCA заливається проактивно — у «вікна наповнення» поза піком, на основі прогнозу того, що дивитимуться. Для провайдера це вигідно: відео не йде через дорогі зовнішні канали. Детально про відео-конвеєр — у туторіалі 11.

Аналогія для фронтендера
Ви щодня користуєтесь CDN для статичних асетів: Vite/webpack генерує index-3f9a2c.js з хешем у назві — це і є versioned URL, який робить інвалідацію непотрібною, а index.html віддається з коротким TTL або no-cache. Push-модель схожа на precache у service worker (Workbox): ви заздалегідь кладете файли в кеш, не чекаючи запиту. Де ламається: service worker кешує для одного користувача; CDN — для всіх, тому помилка в cache key (наприклад, кешування відповіді з персональними даними) покаже чужі дані тисячам людей.
🎯
На співбесіді: кажіть не просто «додамо CDN», а «медіа — в object storage як origin, перед ним pull CDN; URL містять версію/хеш вмісту, тому TTL рік і інвалідація не потрібна; при видаленні контенту — purge за URL і перевірка прав на origin через підписані URL з коротким терміном дії». Для приватного контенту — signed URLs / signed cookies.
🚩
Типові помилки: кешувати на CDN персоналізовані відповіді; не нормалізувати query (hit ratio 20% замість 95%); покладатися на purge як на основний механізм оновлення; забути, що CDN не допоможе з «довгим хвостом» рідко запитуваного контенту — для нього hit ratio низький, і origin має витримувати ці промахи.
Pull — за замовчуванням, push — для великого передбачуваного контенту. Versioned URL кращий за purge. Shield захищає origin. Netflix: control plane в AWS, байти — з OCA всередині ISP.

04 Load balancer: L4 vs L7

Load balancer (LB) розподіляє трафік між кількома однаковими інстансами і прибирає з ротації хворі. Головне питання — на якому рівні він працює: бачить лише TCP/UDP-з'єднання (L4) чи розуміє HTTP-запити (L7).

L4 LBL7 LB
БачитьIP, порт, протокол (TCP/UDP)HTTP: метод, шлях, заголовки, cookie, тіло
Одиниця балансуванняЗ'єднанняЗапит (в т. ч. запити всередині одного HTTP/2-з'єднання)
МожливостіДуже висока продуктивність, будь-які протоколи (БД, MQTT, ігри по UDP)Маршрутизація за шляхом/хостом, canary за заголовком, ретраї, rewrite, auth, кешування, compression

ПрикладиAWS NLB, Linux IPVS, Google MaglevNginx, HAProxy (L7-режим), Envoy, AWS ALB, GCP HTTP(S) LB
⚠️
Трікі з gRPC і HTTP/2. gRPC тримає одне довге HTTP/2-з'єднання, по якому мультиплексує тисячі запитів. L4 LB балансує з'єднання — тож усі запити клієнта прилипнуть до одного бекенду, а нові інстанси після autoscaling не отримають трафіку. Рішення: L7 LB, що розуміє HTTP/2 (Envoy, Linkerd, ALB з gRPC), або client-side балансування (клієнт знає список бекендів і сам розподіляє запити).

Як це роблять у реальних системах

Типова багатошарова схема у великих компаніях: anycast або DNS → шар L4 (наприклад, Google Maglev — програмний L4 LB на звичайних серверах, описаний у статті NSDI 2016; Facebook Katran на XDP/eBPF) → шар L7 проксі (Envoy, власні рішення на кшталт Facebook Proxygen) → сервіси. L4 дешево «розмазує» пакети по флоту L7-проксі, а L7 робить розумну маршрутизацію. Масштабувати один L7 LB вертикально не потрібно — їх багато за L4.

🎯
На співбесіді: «LB теж може бути SPOF?» — так, тому LB розгортають парами/флотами: active-passive з віртуальною IP (VRRP/keepalived) або керований хмарний LB, який вже розподілений по AZ. Достатньо однієї фрази: «використаємо керований L7 LB, він multi-AZ».
L4 = з'єднання, швидко, будь-який протокол. L7 = HTTP-запити, розумна маршрутизація, TLS, дорожче. gRPC/HTTP2 → потрібен L7 або client-side балансування.

05 Алгоритми балансування

Як LB обирає, куди відправити наступний запит. Алгоритм суттєвий, коли запити різні за вартістю або коли потрібна «прив'язка» ключа до сервера (кеші, stateful-сервіси).

Power of two choices: майже ідеально без глобального стану

Проблема least connections у великому масштабі: у вас десятки LB-інстансів, кожен бачить лише свої з'єднання, а якщо всі вони одночасно оберуть «найменш завантажений» сервер, то разом його перевантажать (herd behavior). P2C (робота Mitzenmacher про «power of two choices») бере два випадкові сервери і відправляє на менш завантажений з них. Математично максимальне навантаження при цьому різко падає порівняно з чисто випадковим вибором. P2C використовується, наприклад, у Envoy (алгоритм least request за замовчуванням порівнює двох випадкових кандидатів) і в Nginx (random two least_conn).

p2c.py
import random

def simulate(strategy, servers=1000, requests=10_000, seed=42):
    rng = random.Random(seed)
    load = [0] * servers
    for _ in range(requests):
        if strategy == "random":
            i = rng.randrange(servers)
        elif strategy == "p2c":                      # power of two choices
            a, b = rng.randrange(servers), rng.randrange(servers)
            i = a if load[a] <= load[b] else b
        load[i] += 1
    avg = requests / servers
    return max(load), max(load) / avg

for s in ["random", "p2c"]:
    mx, ratio = simulate(s)
    print(f"{s:6}: max={mx}  max/avg={ratio:.2f}")

# random: max=21  max/avg=2.10
# p2c   : max=12  max/avg=1.20

При середньому навантаженні 10 запитів на сервер найбільш завантажений сервер при випадковому виборі має 21 (удвічі більше за середнє), а з P2C — 12. Одне додаткове порівняння — і хвіст майже зник.

Consistent hashing: коли важливо, ЯКИЙ сервер

Аналогія для фронтендера
Round robin — як розкидати задачі по Web Workers по черзі, не дивлячись, чи зайнятий worker. Least connections — як черга з пулом воркерів, яка дає задачу вільному. P2C — як вибір каси в супермаркеті: ви не обходите всі 20 кас, а дивитесь на дві найближчі й стаєте в коротшу — і майже завжди виходить добре. Де ламається: у браузері ви бачите стан усіх воркерів; LB у розподіленій системі бачить лише свою частину картини, тому «ідеальний» алгоритм неможливий.
🎯
На співбесіді: для stateless API назвіть «least request / P2C» і поясніть, чому не просто round robin (різна вартість запитів). Для кеш-кластера чи чату з прив'язкою користувача до сервера — consistent hashing. Для WebSocket — least connections (довгі з'єднання, RR дасть перекіс після рестартів).
RR — для однакових дешевих запитів; least-conn — для різних; P2C — майже як least-conn без глобального стану; consistent hashing — коли ключ має жити на тому самому сервері.

06 Health checks, sticky sessions і stateless-сервіси

LB корисний лише тоді, коли знає, які бекенди живі, і коли будь-який бекенд може обслужити будь-який запит. Друге — це і є «stateless», головна властивість, що робить горизонтальне масштабування тривіальним.

Sticky sessions vs stateless

Sticky sessions (session affinity)

  • LB прив'язує клієнта до сервера (cookie від LB або hash IP)
  • Можна тримати сесію в пам'яті — просто
  • Падіння сервера = втрата сесій
  • Нерівномірне навантаження («важкий» клієнт прилип)
  • Деплої й autoscaling складніші: треба «зливати» з'єднання

Stateless + зовнішній стан

  • Сесія в Redis/БД або підписаний токен (JWT)
  • Будь-який інстанс, будь-який запит; легко масштабувати
  • Ціна: мережевий виклик до сховища сесій (або неможливість миттєво відкликати JWT — потрібні короткий TTL + refresh token або denylist)
  • Стандарт за замовчуванням для API

Sticky лишається виправданим там, де стан справді локальний і дорогий для перенесення: WebSocket-з'єднання (вони «прилипли» фізично), локальні кеші з великим «прогрівом», ігрові сервери з кімнатами. Але навіть тоді сервер має пережити втрату стану (клієнт перепідключиться і відновить контекст).

Аналогія для фронтендера
Stateless-сервер — як чистий React-компонент: результат залежить лише від props (запит + токен) і зовнішнього store (Redis), а не від прихованого локального стану. Тому його можна «перемонтувати» (перезапустити, замінити) без наслідків. Sticky session — як стан у useState конкретного екземпляра: unmount — і стан зник. Health check — як ErrorBoundary з fallback: несправну частину вимикають, щоб не впала вся сторінка.
🎯
На співбесіді: одне речення на high-level: «API-сервіси stateless, сесії/токени — JWT або Redis, тому масштабуємося горизонтально за LB з health checks і autoscaling». Якщо задача про WebSocket/чат — окремо поясніть, де живе стан з'єднання (§9).
Stateless — за замовчуванням. Health checks: active + passive, обережно з deep checks (fail-open). Sticky — лише коли стан справді локальний, і з планом на його втрату.

TLS termination: де розшифровувати

Нюанси, які можуть спитати: TLS 1.3 скорочує handshake до 1 RTT (у TLS 1.2 — 2 RTT), а 0-RTT resumption дозволяє надіслати дані одразу, але такі дані можна «переграти» (replay) — тому 0-RTT допустимий лише для ідемпотентних запитів. Термінування TLS на CDN-edge поряд з користувачем економить кілька RTT на далеких з'єднаннях — ще одна причина, чому CDN прискорює і динамічний контент.

🎯
На співбесіді: «Зовнішній трафік: CDN/edge → API gateway (TLS termination, JWT-валідація, rate limiting за user_id) → сервіси. Внутрішній трафік — mTLS через service mesh, якщо сервісів багато; інакше — мережева ізоляція в VPC». Не малюйте service mesh для системи з трьох сервісів без причини — це over-engineering.
🚩
Пастки: бізнес-логіка в API gateway (він стає розподіленим монолітом, який усі бояться змінювати); gateway як SPOF без резервування; авторизація «тільки на gateway» без перевірок у сервісах (будь-який внутрішній зловмисник або SSRF обходить її).
Reverse proxy — пул однакових бекендів. Gateway — вхід north-south з auth/rate limit. Mesh — east-west з mTLS і ретраями. TLS термінуємо на краю; re-encrypt/mTLS — коли цього вимагає безпека.

Як це роблять у реальних системах

GraphQL створили у Facebook (внутрішньо приблизно з 2012 року для мобільного News Feed, відкрито у 2015-му) саме для проблеми «мобільний екран потребує даних з багатьох ресурсів, а мережа повільна». gRPC Google відкрив у 2015-му як публічного наступника свого внутрішнього RPC-фреймворку Stubby. Публічні API платіжних і SaaS-компаній (Stripe, GitHub REST, Twilio) — переважно REST, бо його розуміють усі і він дружній до кешів і інструментів; GitHub паралельно пропонує GraphQL API. Типовий гібрид: REST або GraphQL на краю (часто через BFF), gRPC всередині.

Аналогія для фронтендера
Ви знаєте біль REST з фронтенду: три useQuery поспіль, водоспад запитів і половина полів не потрібна. GraphQL з Apollo/Relay — це коли компонент сам декларує свої дані (fragments), а клієнт збирає один запит. gRPC — як суворо типізований tRPC/OpenAPI-клієнт, згенерований зі схеми, але з бінарним форматом. Де ламається: на фронтенді GraphQL «безкоштовно» вирішує водоспад; на бекенді він переносить складність на сервер — резолвери легко генерують N+1 запитів до БД (рішення — DataLoader/batching), і будь-який клієнт може надіслати дуже дорогий запит.
🎯
На співбесіді: не витрачайте час на суперечку про стилі. Скажіть: «Публічний API — REST: просто, кешується на CDN. Між сервісами — gRPC для ефективності і контрактів. Якщо б у нас було багато різних клієнтів з різними екранами — розглянув би GraphQL/BFF». Якщо інтерв'юер наполягає на GraphQL — обов'язково згадайте N+1 і обмеження складності запитів.
REST — назовні і для кешованого. gRPC — всередині, швидко, зі стрімінгом, але потребує L7 LB. GraphQL — для багатьох клієнтів, ціною N+1 і складного кешування.

Масштабування WebSocket-серверів

  1. З'єднання — це стан. Сервер з 500K відкритих сокетів не можна просто вбити при деплої: треба graceful drain (перестати приймати нові, попросити клієнтів перепідключитися, поступово закрити старі).
  2. Reconnect storm. Якщо впав сервер з сотнями тисяч з'єднань, усі клієнти перепідключаються одночасно. Клієнт має робити exponential backoff з jitter, сервери — мати запас і rate limit на handshake.
  3. Балансування. LB має підтримувати Upgrade (L7) або працювати на L4; алгоритм — least connections; idle timeout LB має бути більшим за інтервал heartbeat (ping/pong), інакше LB тихо рве «мовчазні» з'єднання.
  4. Розділення відповідальності. WS-шар — «тупий» gateway з'єднань (автентифікація, доставка); бізнес-логіка і збереження — у звичайних stateless сервісах. Тоді WS-сервери масштабуються за кількістю з'єднань, а сервіси — за QPS.
  5. Доставка ≠ збереження. Повідомлення спершу зберігається (БД/лог), потім доставляється. Клієнт, що перепідключився, догружає пропущене за курсором («дай все після message_id X»).

WhatsApp, побудований на Erlang/FreeBSD, у своєму блозі 2012 року писав про понад 2 мільйони одночасних TCP-з'єднань на одному сервері — приклад того, що стан з'єднання дешевий, якщо платформа під це заточена. Slack і Discord (за їхніми інженерними блогами) мають окремий gateway-шар для WebSocket-з'єднань, відокремлений від сервісів, що обробляють повідомлення. Детальний дизайн чату — у туторіалі 10; брокери для pub/sub — у туторіалі 7.

Де ламається: у браузері одна вкладка — одне з'єднання; на сервері — мільйон, і кожен деплой, кожен рестарт сервера — це «мільйон reconnect» одночасно.

На співбесіді: не обирайте WebSocket за замовчуванням. «Нотифікації в один бік — SSE: простіше, звичайний HTTP, автоматичне перепідключення. Чат з двостороннім обміном і індикаторами набору — WebSocket. Статус довгої задачі раз на 10 с — polling». Потім обов'язково поясніть, як повідомлення потрапляє на потрібний WS-сервер (реєстр + pub/sub).
Polling — просто і stateless; SSE — push в один бік по HTTP; WebSocket — дуплекс, але stateful. Масштабування WS = реєстр з'єднань + pub/sub між серверами + graceful drain + reconnect з jitter.

Пагінація: offset vs cursor

Offset (?page=3&limit=20)

  • Просто; можна стрибнути на сторінку 37
  • OFFSET 100000 — БД все одно читає і відкидає 100K рядків: глибокі сторінки повільні
  • Дублі/пропуски при змінах даних
  • Підходить: адмінки, невеликі статичні списки, пошук з номерами сторінок

Cursor / keyset (?cursor=…&limit=20)

  • WHERE (created_at, id) < (…) ORDER BY … LIMIT 20 — працює по індексу, однаково швидко на будь-якій глибині
  • Стабільно при вставках; ідеально для нескінченних стрічок
  • Не можна стрибнути на довільну сторінку; сортування має бути за унікальним ключем (додавайте id як tie-breaker)
  • Курсор — непрозорий рядок (base64), щоб клієнти не залежали від його формату

Idempotency keys: як не списати гроші двічі

idempotency.py
import hashlib, json, threading

class IdempotencyStore:
    """Спрощено: у проді це Redis/таблиця БД з TTL ~24 год."""
    def __init__(self):
        self._data = {}
        self._lock = threading.Lock()

    def begin(self, key, fingerprint):
        with self._lock:
            rec = self._data.get(key)
            if rec is None:
                self._data[key] = {"state": "in_progress", "fp": fingerprint}
                return "new", None
            if rec["fp"] != fingerprint:
                return "mismatch", None          # той самий ключ, інше тіло -> 422
            if rec["state"] == "in_progress":
                return "conflict", None          # паралельний дубль -> 409
            return "replay", rec["response"]     # повертаємо збережену відповідь

    def finish(self, key, response):
        with self._lock:
            self._data[key].update(state="done", response=response)

store = IdempotencyStore()
charges = []

def create_charge(idem_key, body):
    fp = hashlib.sha256(json.dumps(body, sort_keys=True).encode()).hexdigest()
    status, saved = store.begin(idem_key, fp)
    if status == "replay":
        return saved
    if status == "conflict":
        return {"status": 409, "error": "request_in_progress"}
    if status == "mismatch":
        return {"status": 422, "error": "idempotency_key_reused"}
    charges.append(body)                         # побічний ефект рівно один раз
    resp = {"status": 201, "charge_id": f"ch_{len(charges)}"}
    store.finish(idem_key, resp)
    return resp

print(create_charge("k-1", {"amount": 500}))
print(create_charge("k-1", {"amount": 500}))   # retry після таймауту
print(create_charge("k-1", {"amount": 900}))
print("charges:", len(charges))

# {'status': 201, 'charge_id': 'ch_1'}
# {'status': 201, 'charge_id': 'ch_1'}
# {'status': 422, 'error': 'idempotency_key_reused'}
# charges: 1

Трікі місця: (1) що, якщо процес упав між кроками 2 і 4 — ключ «завис» у in_progress? Потрібен таймаут блокування і безпечний повтор (а побічний ефект — сам ідемпотентний або в одній транзакції із записом ключа, якщо сховище спільне); (2) відбиток тіла (fingerprint) захищає від помилкового повторного використання ключа з іншими параметрами; (3) ключі живуть обмежений час — Stripe у документації вказує, що ключі можуть бути видалені через 24 години. Глибше — у туторіалі 12 (платежі) і туторіалі 7 (idempotent consumers).

Аналогія для фронтендера
Idempotency key — це те, що ви інтуїтивно робите проти подвійного кліку на «Оплатити»: блокуєте кнопку. Але блокування кнопки не рятує від ретраю мережевого шару (fetch з автоповтором, мобільна мережа, що «з'їла» відповідь). Ключ, згенерований один раз при відкритті форми (crypto.randomUUID()) і надісланий у кожній спробі, рятує на рівні сервера. Курсорна пагінація — те, що ви використовуєте в useInfiniteQuery з getNextPageParam: (last) => last.nextCursor. Де ламається: на фронтенді дубль — це неприємність; у платежах — гроші і юридичні наслідки.

Це 30 секунд, які відрізняють senior-відповідь.

Іменники + HTTP-методи; userId з токена; cursor для стрічок; Idempotency-Key для POST з ефектами; версія в шляху; Problem Details; 429 + Retry-After.

11 Трікі питання

Питання, на яких «пливуть» навіть досвідчені кандидати, бо відповідь неочевидна або суперечить інтуїції.

TRICKYЧому б не обійтися DNS round robin замість load balancer?

DNS не знає про стан серверів: якщо сервер упав, його IP ще TTL (а часто довше) роздається клієнтам. Відповіді кешуються резолверами, тому розподіл нерівномірний: великий корпоративний резолвер «посадить» тисячі користувачів на один IP. Клієнти часто беруть перший запис зі списку. Немає L7-функцій, health checks, drain при деплоях. DNS-балансування використовують між регіонами/точками входу (GeoDNS, кілька IP флоту LB), а всередині — справжній LB.

TRICKY«Сервер не може тримати більше 65 535 з'єднань, бо портів стільки» — правда?

Ні. TCP-з'єднання ідентифікується четвіркою (src IP, src port, dst IP, dst port). На сервері всі з'єднання приходять на один порт 443, а відрізняються IP і портом клієнта. Обмеження 64K стосується вихідних з'єднань з одного IP до однієї адреси:порту (ефемерні порти) — це реальна проблема для проксі й LB, що відкривають багато з'єднань до одного бекенда (лікується кількома IP, пулами з'єднань, keep-alive). Реальні межі сервера — пам'ять на з'єднання, файлові дескриптори (ulimit), CPU на TLS і heartbeat.

COREЧим L7 load balancer відрізняється від API gateway, якщо обидва маршрутизують за шляхом?

Технічно — нічим принциповим, часто це той самий Envoy. Різниця у відповідальності: L7 LB розподіляє навантаження і маршрутизує; gateway додає політики API як продукту: автентифікація, API-ключі й плани, rate limiting за клієнтом, трансформації, агрегація, документація, аналітика використання. На співбесіді нормально малювати один блок «LB / API gateway» і назвати, які функції він виконує.

ADVЩо дає HTTP/3 (QUIC) порівняно з HTTP/2?

HTTP/2 мультиплексує потоки в одному TCP-з'єднанні, але втрата одного TCP-пакета зупиняє всі потоки, доки його не перешлють (head-of-line blocking на рівні TCP). QUIC працює поверх UDP, має незалежні потоки, вбудований TLS 1.3 (менше RTT на встановлення) і connection migration — з'єднання переживає зміну IP (Wi-Fi → LTE) завдяки connection ID. Виграш найбільший на мобільних мережах з втратами. Для внутрішнього трафіку в ДЦ різниця зазвичай невелика.

TRICKYЧи можна кешувати GraphQL або POST-запити на CDN?

POST за HTTP-семантикою не кешується CDN за замовчуванням. Для GraphQL використовують persisted queries: клієнт надсилає не текст запиту, а його хеш через GET (/graphql?id=abc123&variables=…) — тоді URL стабільний і CDN може кешувати публічні відповіді. Альтернатива — кешування на рівні резолверів/об'єктів (нормалізований кеш на клієнті, як в Apollo, і кеш даних на сервері). Персоналізовані відповіді все одно не кешуються спільно.

COREJWT чи сесії в Redis? Як відкликати JWT?

JWT перевіряється локально (підпис) — без мережевого виклику, ідеально для stateless сервісів і gateway. Ціна — неможливо миттєво відкликати: токен валідний до exp. Практика: короткоживучий access token (5–15 хв) + refresh token, що зберігається на сервері і може бути відкликаний; для критичних випадків — denylist за jti у Redis (але це знову мережевий виклик). Сесії в Redis — простий миттєвий logout, ціною виклику на кожен запит. Часто поєднують: JWT між сервісами, серверна сесія на краю.

TRICKYGET має бути ідемпотентним. А лічильник переглядів, який інкрементується на GET?

Ідемпотентність у HTTP — про намір клієнта і стан ресурсу, а не про відсутність логів чи метрик. Лічильник переглядів — побічний ефект «аналітики», і повторний GET його збільшить, що допустимо, якщо ви свідомо приймаєте неточність. Але тоді: (1) CDN-кешовані GET не дійдуть до сервера — лічильник рахуватиме лише промахи; (2) prefetch браузера і краулери накрутять лічильник. Тому перегляди зазвичай рахують окремою подією (beacon/POST в аналітику) і агрегують асинхронно, з дедуплікацією.

ADVAnycast і TCP: що станеться, якщо маршрут зміниться посеред з'єднання?

Пакети підуть в інший PoP, де немає стану цього TCP-з'єднання, — з'єднання обірветься (RST). На практиці BGP-маршрути змінюються нечасто, тому для коротких HTTP-запитів це рідкість, і великі CDN давно працюють по TCP через anycast. Для довгих з'єднань (стрімінг, WebSocket) застосовують додаткові механізми: деякі CDN передають пакети між серверами, щоб доставити їх тому, хто тримає з'єднання, або використовують anycast лише для першого кроку, а далі направляють клієнта на unicast-адресу конкретного вузла. QUIC з connection ID теж спрощує цю проблему.

12 Задачі

Оцінки, вибір протоколів і налагодження зламаних схем мережевого шару.

Задача 1ЛегкоМіграція з довгим TTL

A-запис api.example.com має TTL 86 400 с. Через тиждень ви переносите API на новий LB з новою IP. Як мінімізувати час, коли частина клієнтів ходить на стару адресу?

  1. Щонайменше за добу (старий TTL) до міграції знизити TTL до 60 с — щоб усі кеші встигли отримати запис із коротким TTL.
  2. У день міграції — змінити A-запис; більшість клієнтів перейде за ~хвилину.
  3. Старий LB тримати живим і проксувати на новий ще кілька днів: частина резолверів і клієнтів ігнорує TTL.
  4. Після стабілізації повернути TTL на годину і більше.
Задача 2ЛегкоОберіть real-time техніку

Що б ви обрали для: (a) рахунку футбольного матчу на сайті, (b) чату підтримки з індикатором «друкує…», (c) статусу експорту звіту, що триває 2–5 хв, (d) спільного редагування документа?

  • (a) SSE: потік в один бік, мільйони глядачів, звичайний HTTP; навіть short polling раз на 10–15 с з CDN-кешем — гідний варіант для величезної аудиторії.
  • (b) WebSocket: двосторонній обмін, часті дрібні події.
  • (c) Polling раз на 5–10 с (або один email/push після завершення) — подій мало, тримати з'єднання немає сенсу.
  • (d) WebSocket + алгоритм злиття (OT/CRDT) — дуплекс, низька латентність.
Задача 3СередньоЧому CDN не кешує?

Після запуску маркетингової кампанії hit ratio CDN для картинок товарів упав з 95% до 40%, origin перевантажений. Відповіді origin містять Cache-Control: public, max-age=86400 і Vary: Accept-Encoding, Cookie. Посилання в розсилці мають вигляд /img/42.jpg?utm_source=mail&utm_campaign=…&uid=…. Що не так?

  1. Query в ключі кешу: кожен uid і комбінація UTM-міток — окремий ключ, тобто фактично кожен користувач отримує промах. Рішення: на CDN ігнорувати/відрізати маркетингові параметри з cache key (або whitelisting дозволених параметрів).
  2. Vary: Cookie для картинок: у кожного користувача свої cookie → окрема копія. Картинкам не потрібні cookie: прибрати Vary: Cookie (і, бажано, віддавати статику з окремого cookieless-домену).
  3. Додатково: origin shield, щоб промахи з сотень PoP зводилися до одного запиту на origin.
Задача 4СередньоТрафік CDN і origin

10M користувачів на добу, кожен завантажує ~2 MB статики. Hit ratio CDN — 95%. Оцініть середній трафік з edge і з origin. Що зміниться при hit ratio 80%?

Усього: 10⁷ × 2×10⁶ B = 2×10¹³ B = 20 TB/добу → 20×10¹² × 8 / 86 400 ≈ 1.85 Гбіт/с з edge у середньому (пік ×2–3).

Origin при 95%: 5% = 1 TB/добу ≈ ~93 Мбіт/с. При 80%: 20% = 4 TB/добу ≈ ~370 Мбіт/с — учетверо більше. Мораль: зниження hit ratio на 15 п.п. множить навантаження на origin у рази; hit ratio — ключова метрика CDN (і причина використовувати versioned URL з довгим TTL).

Задача 5СередньоНові поди не отримують трафіку

Сервіс A викликає сервіс B по gRPC через Kubernetes Service (L4, kube-proxy). Під навантаженням B відмасштабувався з 3 до 10 подів, але CPU у 3 старих подах на 95%, а нові простоюють. Чому і як виправити?

gRPC тримає довгоживучі HTTP/2-з'єднання; L4-балансування розподіляє з'єднання, а не запити. Клієнти A відкрили з'єднання до 3 старих подів і мультиплексують у них усі запити; нові поди ніхто не «бачить».

Рішення: (1) L7-балансування запитів — service mesh (Envoy/Linkerd sidecar) або L7-проксі; (2) client-side LB у gRPC (headless Service + DNS-резолвер з round_robin, періодичне оновлення списку); (3) як милиця — обмежити час життя з'єднання (MaxConnectionAge на сервері), щоб клієнти періодично перепідключались.

Задача 6СередньоФлот WebSocket-серверів

Месенджер має 10M одночасних з'єднань у піку. Припустимо, один сервер комфортно тримає 100K з'єднань (~20 KB пам'яті на кожне), heartbeat раз на 30 с. Скільки серверів, скільки пам'яті під з'єднання на сервер і скільки heartbeat-повідомлень на секунду сумарно?

  1. Сервери: 10⁷ / 10⁵ = 100; із запасом на відмову зони і reconnect storm (+30–50%) → ~130–150.
  2. Пам'ять: 10⁵ × 20 KB = 2 GB на сервер лише під стан з'єднань — небагато; обмеженням швидше стане CPU (TLS, heartbeat) і мережа.
  3. Heartbeat: 10⁷ / 30 ≈ 333K повідомлень/с сумарно (~3.3K на сервер) — помітна, але прийнятна фонова робота.
  4. Висновок про reconnect storm: падіння одного сервера = 100K клієнтів перепідключаються. Без jitter це сплеск 100K TLS-handshake за секунду на решту флоту.
Задача 7СередньоHealth check поклав усе

Health check сервісу перевіряє «процес живий + SELECT 1 у БД + ping Redis». Під час короткої деградації Redis (латентність 3 с) увесь флот зник з LB, і сервіс повністю впав, хоча 80% ендпоінтів Redis не використовують. Що змінити?

  • Розділити liveness (лише процес) і readiness; readiness не повинна залежати від некритичних залежностей.
  • Деградація залежності — це не «нездоровий інстанс»: усі інстанси однаково страждають, виключати їх безглуздо. Краще graceful degradation в коді (таймаут + fallback для ендпоінтів з Redis, circuit breaker).
  • Налаштувати fail-open на LB: якщо нездорові майже всі цілі, слати трафік на всіх (так роблять, наприклад, AWS ALB/Route 53 і Envoy panic threshold).
Задача 8СкладноПагінація ранжованої стрічки

Стрічка сортується не за часом, а за score, який перераховується щохвилини. Користувач гортає 5 сторінок за кілька хвилин. Чому cursor (score, id) тут не працює і що запропонувати?

Keyset-курсор вимагає стабільного порядку. Якщо score змінюється, пост може «перестрибнути» вище курсора (користувач його не побачить) або нижче (побачить двічі).

Рішення — snapshot: при першому запиті сформувати ранжований список id (наприклад, 500 штук) і зберегти в кеші з TTL ~30 хв під feed_session_id; курсор = (session_id, позиція). Сторінки читаються зі знімка — стабільно і швидко; дані постів (лайки, текст) гідратуються свіжими. Коли знімок вичерпано або протух — новий знімок з дедуплікацією вже показаного. Так влаштовано багато ранжованих стрічок.

Задача 9СкладноІдемпотентність на двох сховищах

Сервіс переказів зберігає ключі ідемпотентності в Redis, а записи ledger — у PostgreSQL. Послідовність: SETNX key → INSERT ledger → SET key = response. Знайдіть сценарії, коли гарантія порушується, і запропонуйте надійний дизайн.

  1. Процес упав після INSERT, але до SET response: ключ «завис» у in_progress. Коли блокування протухне, ретрай виконає INSERT вдруге → подвійний переказ.
  2. Redis втратив ключ (failover з асинхронною реплікацією, eviction) — ретрай знову виконає переказ.

Надійно: тримати ключ ідемпотентності в тій самій транзакції, що й ефект: таблиця idempotency_keys(key PRIMARY KEY, request_hash, response, created_at) у PostgreSQL; в одній транзакції INSERT key + INSERT ledger + збереження відповіді. Дубль упирається в унікальний індекс. Redis можна лишити як швидкий кеш перед цим, але не як джерело правди. Цей підхід («atomic phases») детально описав Brandur Leach (тоді інженер Stripe) у статті «Implementing Stripe-like Idempotency Keys in Postgres».

Задача 10СкладноКористувачі в Австралії

API розгорнуто лише в us-east; RTT із Сіднея ≈ 200 мс. Нове з'єднання: TCP handshake + TLS 1.3 + сам запит. Оцініть час до першого байта на холодному з'єднанні і запропонуйте, як скоротити його без перенесення БД.

Холодне з'єднання: TCP (1 RTT) + TLS 1.3 (1 RTT) + запит/відповідь (1 RTT) ≈ 3 × 200 = ~600 мс плюс обробка. На TLS 1.2 — ще +1 RTT.

  1. TLS termination на edge (CDN/глобальний LB з PoP у Сіднеї) + пул постійних з'єднань edge → origin: ~2 × 10 + 200 ≈ ~220 мс.
  2. Кешування на edge публічних GET (каталоги, конфіги) — ~10–20 мс.
  3. Read-only регіональний шар: read replica + stateless API в ap-southeast для читань (eventual consistency), записи — в us-east.
  4. Клієнт: keep-alive/HTTP/2 (одне з'єднання на сесію), TLS session resumption, preconnect.
