01 Чотири задачі «доставки» і що в них спільного

Стрічка, чат, сповіщення й автодоповнення — найчастіші «продуктові» задачі на співбесіді. Усі вони про одне: як доставити правильні дані правильній людині вчасно — і де робити дорогу роботу: при записі чи при читанні.

У туторіалі 9 ми будували «інфраструктурні» блоки: генератор ID, KV-сховище, rate limiter. Тут ці блоки складаються в продукти, якими ви користуєтеся щодня. Хороша новина: у всіх чотирьох задачах повторюються одні й ті самі ідеї, тож вивчивши одну глибоко, ви на третину готові до інших.

Правило «write-time vs read-time». Якщо читань значно більше, ніж записів, і читання мусить бути швидким — переносьте роботу на запис (передобчислення, денормалізація, кеш). Якщо запис може породити величезну роботу (пост зірки → 100 млн стрічок) — переносьте цю частину на читання. Це і є вся теорія fan-out.
Аналогія для фронтендера
Це той самий вибір, що між SSG і SSR. SSG (static site generation) — передобчислюємо сторінки при деплої (fan-out on write): читання миттєве, але перебудова 1 млн сторінок через одну зміну — болісна. SSR — рендеримо на кожен запит (fan-out on read): завжди свіже, але дорожче на читанні. ISR у Next.js — гібрид: популярне передобчислене, рідкісне — на льоту. Де ламається: сторінка SSG однакова для всіх, а стрічка персональна для кожного користувача — «сторінок» стільки ж, скільки користувачів.
🎯
На співбесіді: у продуктових задачах вимоги — половина успіху. Стрічка «хронологічна чи ранжована?», чат «1:1 чи групи до 100 000?», «потрібна історія на всіх пристроях?», «E2E шифрування?». Кожна відповідь міняє архітектуру. Інтерв'юер часто навмисно не каже — чекає, що спитаєте ви.
Стрічка = fan-out; чат = stateful з'єднання + порядок; сповіщення = черги + ретраї + налаштування; typeahead = передобчислений top-K + кеш на всіх рівнях.

02 News feed: вимоги, оцінки, API, дані, high-level

«Спроєктуйте домашню стрічку Twitter/Instagram/Facebook»: користувач бачить пости тих, на кого підписаний, нові — зверху.

Крок 1. Вимоги

Функціональні

  • Опублікувати пост (текст + медіа).
  • Підписатися / відписатися (граф підписок, односпрямований).
  • Отримати домашню стрічку: пости фоловінгів, від нових до старих, з пагінацією.
  • Уточнити: хронологічна чи ранжована? (почнемо з хронологічної, ранжування — deep dive).
  • Поза скоупом: коментарі, лайки (лише як лічильники), пошук, реклама.

Нефункціональні

  • Відкриття стрічки — p99 < ~200–500 мс (p99 — «99-й перцентиль»: 99% запитів не повільніші за це).
  • Пост з'являється у фоловерів протягом секунд (eventual consistency OK).
  • Читань стрічки значно більше, ніж постів (read-heavy).
  • Висока доступність: краще показати трохи застарілу стрічку, ніж помилку.
  • Розподіл фоловерів дуже нерівномірний: від 0 до 100+ млн (зірки).

Крок 5. High-level схема

Зверніть увагу на два принципи: (1) стрічка зберігає лише ID, не копії постів — інакше редагування чи видалення поста довелося б розсилати в мільйони стрічок, а пам'ять зросла б у сотні разів; (2) медіа ніколи не йде через наші сервіси: клієнт вантажить напряму в S3 за presigned URL, а читає з CDN (детально — туторіал 11).

Стрічка = кеш списків ID + гідрація. Запис поста — синхронно в БД, розсилка — асинхронно через чергу. Медіа — S3 + CDN, повз наші сервіси.

03 Deep dive: fan-out on write vs fan-out on read vs hybrid

Центральне питання задачі. Хто платить за зірку з 100 млн фоловерів — автор при публікації чи кожен читач при відкритті стрічки?

Гібрид: push для звичайних, pull для зірок

fanout.py
from collections import defaultdict, deque

CELEB_THRESHOLD = 10_000      # вище цього — не робимо fan-out on write
FEED_LEN = 800                # скільки ID тримаємо в кеші стрічки

followers = defaultdict(set)  # author -> {follower}
following = defaultdict(set)  # user -> {author}
posts = defaultdict(list)     # author -> [(ts, post_id)]
feed_cache = defaultdict(lambda: deque(maxlen=FEED_LEN))  # user -> [(ts, post_id)]

def follow(u, a):
    followers[a].add(u); following[u].add(a)

def is_celeb(a):
    return len(followers[a]) >= CELEB_THRESHOLD

def publish(author, ts, post_id):
    posts[author].append((ts, post_id))
    if not is_celeb(author):              # push: пишемо в стрічки фоловерів
        for f in followers[author]:
            feed_cache[f].appendleft((ts, post_id))

def read_feed(user, limit=5):
    pushed = list(feed_cache[user])
    pulled = [p for a in following[user] if is_celeb(a)   # pull: зірок мерджимо при читанні
                for p in posts[a][-limit:]]
    return [pid for _, pid in sorted(pushed + pulled, reverse=True)[:limit]]

for i in range(CELEB_THRESHOLD):
    follow(f"fan{i}", "star")
follow("alice", "bob"); follow("alice", "star")
publish("bob", 1, "bob-1"); publish("star", 2, "star-1"); publish("bob", 3, "bob-2")
print(read_feed("alice"))
print(len(feed_cache["fan0"]))        # зірка нічого не розсилала

Виведе ['bob-2', 'star-1', 'bob-1'] — пости Bob прийшли push-ом, пост зірки підмішано pull-ом, усе відсортовано за часом — і 0: зірка не записала нічого в стрічки 10 000 фоловерів.

Деталі, які люблять питати

  • Fan-out асинхронний і батчевий: воркер бере пачку фоловерів (наприклад, 1 000 за раз з графу) і робить pipelined LPUSH + LTRIM у Redis. Для автора з 50 тис. фоловерів це десятки батчів — секунди.
  • Видалення поста: не обов'язково «вичищати» ID з мільйонів стрічок — при гідрації видалені/приховані пости просто відфільтровуються (lazy delete). Те саме для блокувань і відписок.
  • Відписка/підписка: при новій підписці можна «доналити» останні пости автора в стрічку (backfill), при відписці — фільтрувати при читанні.
  • Порядок: Snowflake ID постів сортуються за часом, тому злиття push і pull — простий merge за ID.
  • Hot path для зірки: її пости читають мільйони — тож timeline зірки і самі пости мусять бути в кеші з реплікацією (hot key, туторіал 3).
🏭
Як це роблять у реальних системах. За доповіддю Raffi Krikorian «Timelines at Scale» (QCon, 2012) Twitter робив fan-out on write у Redis-кластер: домашня стрічка — список з ~800 ID, з реплікацією; навантаження — порядку 300 тис. читань стрічки/с проти кількох тисяч твітів/с; fan-out твіту акаунта з десятками мільйонів фоловерів міг тривати хвилини, тому для таких акаунтів твіти підмішувалися при читанні. Facebook історично будував стрічку ближче до pull-моделі (Multifeed: агрегатори опитують leaf-сервери з останніми діями друзів і ранжують на льоту) — бо стрічка ранжована, а не хронологічна. Instagram публічно описував перехід від хронологічної до ранжованої стрічки (2016).
🎯
На співбесіді: не кажіть одразу «гібрид». Покажіть хід думки: «Push дає дешеве читання, але ламається на зірках; pull — навпаки. Оскільки стрічку читають частіше, базово push. Для акаунтів понад поріг фоловерів — pull при читанні. Для неактивних — не робимо fan-out взагалі». Потім назвіть ціну гібриду: дві логіки, складніший read path, «стик» пагінації при мерджі.
🚩
Red flags: fan-out синхронно в запиті публікації (користувач чекає, поки пост розійдеться по 50 тис. стрічок); копіювати повний текст поста в кожну стрічку; не помітити проблему зірок; забути про неактивних користувачів (більшість fan-out-записів ідуть у стрічки, які ніхто не відкриє).
Push для більшості, pull для зірок, нічого для неактивних. Стрічка — це ID, видалення — фільтром при гідрації.

04 Deep dive: кеш стрічки, ранжування, пагінація курсорами, медіа

Як влаштований кеш стрічки в Redis, що змінює ранжування, чому offset-пагінація ламає нескінченну стрічку і як доставляти фото й відео.

Кеш стрічки в Redis

redis-feed.txt
# fan-out worker, для кожного фоловера (у pipeline):
LPUSH feed:{alice} 1789234567890123456       # ID поста зверху
LTRIM feed:{alice} 0 799                     # тримаємо лише 800 останніх
# читання першої сторінки:
LRANGE feed:{alice} 0 19
# варіант для ранжованої стрічки / пагінації за ID:
ZADD  feed:{alice} 1789234567890123456 1789234567890123456   # score = id (або score ранжування)
ZREVRANGEBYSCORE feed:{alice} (1789000000000000000 -inf LIMIT 0 20   # «старші за курсор»
  • List vs Sorted Set: list — дешевший і простий для хронології; sorted set — дозволяє «вставити в середину» (пізня доставка, ранжування) і пагінацію за score.
  • Лише активні користувачі: TTL на ключ стрічки (наприклад, 30 днів без відкриття — ключ зникає). При поверненні — перебудова pull-ом (cache miss → «rebuild»).
  • Реплікація: стрічку можна відновити з постів і графу — тому це кеш, а не джерело правди. Втрата Redis-шарду = повільні стрічки на хвилини, а не втрата даних.

Ранжування (коротко)

Ранжована стрічка змінює архітектуру: замість «останні N» маємо candidate generation → ranking → filtering. Кандидати — ті самі push/pull-джерела (кілька сотень–тисяч постів), далі ML-модель рахує score (ймовірність взаємодії: лайк, коментар, перегляд), застосовуються правила різноманітності (не 5 постів поспіль від одного автора) і фільтри (заблоковані, вже бачені). Ранжування зазвичай робиться при читанні (свіжі сигнали), тому стрічку часто кешують коротко (хвилини) як вже відранжований список для поточної сесії. На співбесіді достатньо цього рівня й фрази «ML-ранжування — окрема задача; я залишу точку розширення».

Пагінація курсорами

Курсор віддають клієнту непрозорим (base64 від JSON {"id": …, "score": …}, бажано з підписом): клієнт не повинен його парсити, а сервер може змінити формат. Для ранжованої стрічки курсор — це «ID сесії ранжування + позиція», бо score змінюються з часом. Детально про пагінацію в API — туторіал 2.

Медіа через CDN

  1. Клієнт просить presigned URL → вантажить файл напряму в S3 (наші сервери не проганяють гігабайти).
  2. Подія «завантажено» → асинхронна обробка: ресайз зображень у кілька розмірів, транскодування відео, видалення EXIF, перевірка на заборонений контент.
  3. Пост посилається на media_id; клієнт отримує URL CDN з потрібним розміром (/m/91…/w_640.webp) і вантажить звідти.
  4. CDN кешує «гарячі» медіа на edge; для приватних — підписані URL з коротким TTL.
Аналогія для фронтендера
Нескінченна стрічка з курсором — це useInfiniteQuery у React Query: getNextPageParam: (last) => last.next_cursor. Ви ніколи не передаєте «номер сторінки», бо між прокрутками дані зверху змінилися. А «є 5 нових постів» над стрічкою — це окремий запит since_id, а не перезавантаження списку (щоб користувач не втратив позицію скролу). Медіа — як <img srcset> з різними розмірами з CDN. Де ламається: на фронтенді список зберігається в пам'яті однієї вкладки, а серверний курсор мусить працювати між пристроями й після рестартів сервісів.
🎯
Що кажуть сильні кандидати: «Стрічка — Redis list/zset з ID, обрізаний до ~800, лише для активних; гідрація з кешу постів батчем (MGET). Пагінація — курсором за Snowflake ID, нові пости — через since_id. Гібридний fan-out з порогом для зірок. Медіа — presigned upload у S3 і CDN. Кеш стрічки відновлюваний з джерел правди — тож його втрата це деградація латентності, а не даних».

Follow-up питання

  • Як показати «нові пости» в реальному часі? (long polling / SSE для лічильника «є N нових», не пуш самих постів)
  • Користувач підписався на 5 000 акаунтів, з них 300 зірок — pull стає дорогим. Що робити? (кешувати «зіркові» timelines, обмежити кількість, частково push для «найближчих» зірок)
  • Як рахувати лайки під вірусним постом? (шардовані лічильники / агрегація в стрімі — задача 10 з туторіалу 9)
  • Як зробити стрічку в кількох регіонах? (кеш стрічок регіональний, пости реплікуються асинхронно, fan-out у регіоні читача)
Курсор, а не offset. Стрічка в Redis — відновлюваний кеш ID. Ранжування — candidate generation → ranking → filtering при читанні. Медіа — S3 + CDN напряму з клієнта.
Частина II · Чат (WhatsApp, Slack, Discord)

05 Чат: вимоги, оцінки, API, high-level

«Спроєктуйте WhatsApp / Messenger / Slack». Головна відмінність від решти задач: stateful довгоживучі з'єднання з мільйонами клієнтів і доставка в реальному часі.

Вимоги

Функціональні

  • 1:1 повідомлення і групи (уточнити розмір: WhatsApp — до сотень/тисяч учасників, Slack/Discord-канали — до сотень тисяч).
  • Історія повідомлень, синхронізація між пристроями.
  • Статуси: надіслано / доставлено / прочитано.
  • Онлайн-статус (presence), «друкує…».
  • Офлайн-доставка: push-сповіщення, отримання пропущеного при підключенні.
  • Медіа — через object storage (як у стрічці), E2E — уточнити.

Нефункціональні

  • Низька латентність доставки: ~100–500 мс між континентами.
  • Жодне повідомлення не губиться (durability) і не дублюється на екрані.
  • Порядок у межах чату — однаковий для всіх учасників.
  • Сотні мільйонів одночасних з'єднань.
  • Висока доступність; при відмові gateway клієнти перепідключаються без втрат.

Для відправлення й отримання — WebSocket (двонаправлений, один TCP на клієнта); REST — для історії, створення груп, завантаження медіа. Порівняння WebSocket / SSE / long polling — туторіал 2 і JS: дані в реальному часі.

High-level схема

Gateway і connection registry

  • L4-балансування на gateway (WebSocket — довгоживуче TCP-з'єднання; L7 теж можливо, але гейтвей сам термінує TLS). Нове з'єднання → будь-який gateway з вільною ємністю.
  • При підключенні gateway пише в registry: conn:{user_id}:{device_id} → gateway_id з TTL, що продовжується heartbeat-ами. Так chat service знає, куди слати.
  • Альтернатива реєстру — pub/sub: кожен gateway підписаний на канали своїх користувачів (Redis Pub/Sub, NATS), chat service публікує в user:{id}. Простіше, але гірше масштабується на мільйони каналів.
  • Рестарт/деплой gateway розриває сотні тисяч з'єднань → «thundering herd» реконектів. Ліки: поступовий drain (сервер просить клієнтів перепідключитися порціями), клієнтський backoff з jitter.
🏭
Як це роблять у реальних системах. WhatsApp (Erlang/FreeBSD) у 2012 писав у блозі про понад 2 млн одночасних TCP-з'єднань на одному сервері — завдяки легким процесам Erlang. Slack описував (блог «Real-time Messaging», 2023) розділення на gateway-сервери (WebSocket), channel-сервери (stateful, консистентне хешування каналів) та інші сервіси; повідомлення доставляється по світу за ~500 мс (за їхніми даними — перевірте першоджерело). Discord тримає з'єднання на Elixir/Erlang-сервісах (BEAM), а для гарячих шляхів частину переписував на Rust.
Чат = stateful gateway (з'єднання) + stateless логіка + registry «хто де підключений» + durable сховище + push для офлайн.

06 Deep dive: шлях повідомлення, порядок, receipts, офлайн-доставка

Що відбувається між натисканням «надіслати» і двома галочками, як не загубити й не продублювати повідомлення і чому «порядок» — найтонше місце задачі.

Шлях повідомлення 1:1

Ідемпотентність і дедуплікація

Мобільна мережа ненадійна: клієнт надіслав, з'єднання впало, ack не прийшов — клієнт повторює. Без захисту отримувач побачить повідомлення двічі. Рішення: клієнт генерує client_msg_id (UUID) до першої спроби; сервер зберігає відповідність (sender, client_msg_id) → msg_id (з TTL, наприклад, доба) і при повторі повертає існуючий msg_id, не створюючи нового. На стороні отримувача — дедуп за msg_id (доставка at-least-once + дедуп на клієнті = «рівно один раз на екрані»).

Порядок повідомлень і ID

  • Час клієнта не підходить: годинники телефонів брешуть, а користувач може змінити час вручну.
  • Snowflake ID від сервера (Discord так і робить): k-sorted, відображає порядок прийому сервером. Два повідомлення, що надійшли на різні сервери з різницею в мілісекунди, можуть бути «переставлені» — для чату людей зазвичай прийнятно.
  • Послідовний номер у межах чату (chat_seq): строгий порядок, однаковий для всіх учасників, легко знайти «дірки» при синхронізації («в мене 1…57, на сервері 60 — дозавантаж 58–60»). Ціна — серіалізація записів у межах чату (один «власник» чату: шард/актор/партиція Kafka за chat_id). Для 1:1 і невеликих груп — чудовий варіант.
  • Порядок на рівні UI: клієнт сортує за серверним ID/seq, а своє ще не підтверджене повідомлення показує внизу (optimistic UI) і переставляє, коли прийде msg_id.

Delivery receipts

Офлайн-доставка і синхронізація

  1. Registry каже: у B немає активних з'єднань → повідомлення вже лежить у сховищі (воно durable до доставки), Chat service публікує подію для push-сервісу.
  2. Push через APNs (iOS) / FCM (Android) — «розбудити» застосунок і показати сповіщення. Push — підказка, не канал доставки: він може загубитися, згорнутися, прийти із запізненням.
  3. Коли B підключається — надсилає sync з курсорами «останнє, що я маю, у кожному чаті» (або один глобальний курсор «inbox»). Сервер віддає все новіше пачками.
  4. Для багатьох чатів ефективно тримати per-user inbox: таблиця «user → (chat_id, last_msg_id, unread_count)», щоб одним запитом знати, які чати змінилися, а не опитувати тисячі чатів.
Аналогія для фронтендера
Optimistic UI у useMutation з onMutate: показуємо повідомлення зі статусом «відправляється» і тимчасовим ID, а в onSuccess замінюємо на серверний msg_id. client_msg_id — це ваш ключ ідемпотентності для повтору мутації. А синхронізація після реконекту — як refetch після window.onfocus у React Query, тільки інкрементальна: «дай усе після курсора». Де ламається: React Query може просто перезапитати весь список, а чат з історією в мільйони повідомлень — ні; тому курсори і дельти.
🎯
На співбесіді: проговоріть гарантії явно: «Доставка at-least-once з дедуплікацією за client_msg_id і msg_id; відправник бачить ✓ лише після durable-запису; порядок — серверний (Snowflake або seq у межах чату); офлайн — повідомлення в сховищі + push як підказка + sync за курсором при підключенні».
Ack після запису. client_msg_id — для ідемпотентності. Порядок — від сервера, не від годинника телефону. Push — підказка, sync за курсором — гарантія.

07 Deep dive: зберігання (історія Discord), presence, групи, multi-device, E2E

Найкращий публічний кейс для цієї задачі — як Discord пройшов шлях MongoDB → Cassandra → ScyllaDB. Плюс presence, групи, кілька пристроїв і що змінює наскрізне шифрування.

Модель даних повідомлень

Патерн доступу: «останні N повідомлень чату», «повідомлення до курсора», запис — append. Ідеально лягає на wide-column сховище: partition key = чат (усе повідомлення чату поруч), clustering key = msg_id DESC (відсортовано, нові першими). Проблема: популярний канал за роки накопичує мільйони повідомлень → одна гігантська партиція. Тому до ключа партиції додають часовий bucket.

messages.cql
CREATE TABLE messages (
  channel_id  bigint,
  bucket      int,          -- номер 10-денного вікна від епохи (як у Discord, 2017)
  message_id  bigint,       -- Snowflake: час у старших бітах
  author_id   bigint,
  content     text,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

-- «останні 50 у каналі»: читаємо поточний bucket, якщо мало — попередній
SELECT * FROM messages WHERE channel_id = ? AND bucket = ? LIMIT 50;
bucket.py
DISCORD_EPOCH = 1420070400000            # 2015-01-01 UTC, мс
BUCKET_MS = 1000 * 60 * 60 * 24 * 10     # 10 днів

def bucket_of(snowflake_id: int) -> int:
    ts_ms = (snowflake_id >> 22) + DISCORD_EPOCH
    return (ts_ms - DISCORD_EPOCH) // BUCKET_MS

def make_id(ts_ms: int) -> int:
    return (ts_ms - DISCORD_EPOCH) << 22

import datetime as dt
t = int(dt.datetime(2026, 10, 19, tzinfo=dt.timezone.utc).timestamp() * 1000)
print(bucket_of(make_id(t)))
print(bucket_of(make_id(t)) - bucket_of(make_id(t - 25 * 24 * 3600 * 1000)))

Виведе 430 (номер 10-денного bucket-а на 19.10.2026) і 2 — повідомлення 25-денної давнини лежить на 2 bucket-и раніше. Bucket обчислюється з самого ID, тож окреме поле часу для маршрутизації не потрібне.

Головна інженерна думка з історії Discord, яку варто переказати на співбесіді: гарячі партиції (величезний сервер, де тисячі людей одночасно відкривають той самий канал) створюють навантаження на одні й ті самі репліки. Discord додав проміжний шар data services на Rust, що маршрутизує запити за channel_id (consistent hashing) і об'єднує однакові конкурентні запити (request coalescing): якщо 1 000 клієнтів одночасно просять ті самі повідомлення, у БД іде один запит. Це той самий прийом, що «single-flight» проти cache stampede (туторіал 3).

Presence: хто онлайн

  • Heartbeat через уже відкритий WebSocket (дешево); presence-сервіс тримає presence:{user} з TTL у Redis.
  • Fan-out presence — дорогий: зміна статусу людини з 500 контактами = 500 повідомлень; 100 млн онлайн-змін на годину перетворюються на мільярди подій. Тому: розсилати лише тим, хто зараз дивиться на цього користувача (підписка при відкритті чату/списку), батчити, згладжувати мерехтіння (offline лише після N секунд без з'єднання).
  • Великі групи: presence для 100 000 учасників не розсилають взагалі — список учасників завантажується ліниво (Discord робив lazy loading списку учасників для великих серверів).
  • «Друкує…» — ефемерна подія без збереження, з throttle на клієнті (не частіше раз на 2–3 с) і автоматичним зникненням.

Групи і канали

  • Малі групи (до сотень): fan-out on write — chat service знаходить gateway кожного онлайн-учасника й доставляє; офлайн-учасникам — push.
  • Великі канали (Slack/Discord, тисячі–сотні тисяч): повідомлення зберігається один раз у партиції каналу; онлайн-клієнти, що «дивляться» канал, отримують його через підписку (gateway підписаний на канал), решта — бачать лише бейдж «непрочитане» і дозавантажують при відкритті. Це pull-модель, як у стрічці для зірок.
  • Членство — окрема таблиця (channel_members), кешована; права перевіряються на запис і на читання.

Multi-device sync

У користувача телефон, ноутбук і веб. Кожен пристрій — окреме з'єднання в registry (user → [device1@gw3, device2@gw7]), повідомлення доставляються на всі. Синхронізація історії — за курсором на пристрій; власні повідомлення, надіслані з іншого пристрою, теж приходять як події. «Прочитано» на одному пристрої → подія для інших (зняти бейджі). Для E2E-месенджерів це складніше: кожен пристрій має власні ключі, і відправник шифрує повідомлення окремо для кожного пристрою кожного учасника (WhatsApp описував такий підхід при запуску multi-device у 2021).

End-to-end encryption: що змінюється в дизайні

  • Сервер бачить лише метадані (хто, кому, коли, розмір) і зашифрований blob — серверний пошук, модерація контенту й ML по тексту неможливі.
  • Протокол Signal (Double Ratchet + X3DH) — у Signal і WhatsApp (WhatsApp завершив розгортання E2E у 2016). Для груп — «sender keys»: кожен учасник шифрує один раз своїм груповим ключем, а розсилка ключа — попарно.
  • Потрібен сервіс розподілу публічних ключів (prekeys), а історія на новому пристрої — лише через перенесення зі старого або зашифрований бекап.
  • Slack і Discord (текстові канали) E2E не мають — бо їм потрібні пошук, інтеграції, модерація. Це продуктовий trade-off, а не технічна неможливість.
🎯
Що кажуть сильні кандидати: «Повідомлення — у wide-column з ключем (chat_id, bucket) і Snowflake ID як clustering key DESC, як у Discord; bucket обмежує розмір партиції. Перед БД — шар з request coalescing проти гарячих каналів. Presence — heartbeat + TTL у Redis, розсилка лише зацікавленим, у великих групах — без presence. Малі групи — fan-out on write, великі канали — збереження раз і доставка підписаним. Multi-device — registry на рівні пристрою і курсори на пристрій. E2E обмежує серверні можливості — уточнюю, чи це вимога».
🚩
Red flags: «зберігаємо повідомлення в MySQL з індексом за часом» без розмови про обсяг (сотні ТБ на рік); партиція = весь канал назавжди; розсилати presence всім контактам; доставка лише через push без синхронізації; порядок за часом клієнта; HTTP-polling кожну секунду на 150 млн клієнтів.

Follow-up питання

  • Як шукати по історії повідомлень? (асинхронна індексація з Kafka в Elasticsearch/OpenSearch, шардинг індексу за workspace/guild — і це неможливо з E2E)
  • Як редагувати/видаляти повідомлення? (нова версія з тим самим msg_id + подія «edited/deleted» усім онлайн; tombstone у сховищі)
  • Як обробити регіони? (gateway у кожному регіоні, «домашній регіон» чату для порядку; міжрегіональна доставка через бекбон)
  • Як не втратити повідомлення при падінні gateway? (ack лише після durable-запису; клієнт перепідключається і робить sync за курсором)
Сховище: (chat, bucket) + Snowflake DESC. Гарячі канали — coalescing. Presence — heartbeat + TTL, розсилка лише зацікавленим. E2E = сервер сліпий до вмісту.
Частина III · Notification system

08 Система сповіщень: push, SMS, email

«Спроєктуйте сервіс, через який усі команди компанії надсилають push, SMS та email». Задача про черги, ненадійних зовнішніх провайдерів, налаштування користувача і те, як не надіслати один і той самий OTP тричі.

Вимоги

Функціональні

  • Канали: mobile push (iOS/Android), SMS, email, (in-app).
  • Тригери: події сервісів (новий коментар, замовлення відправлено), заплановані (нагадування), масові (маркетинг).
  • Шаблони з локалізацією і персоналізацією.
  • Налаштування користувача: opt-out за типом і каналом, тихі години, часовий пояс.
  • Трекінг: надіслано / доставлено / відкрито / клікнуто.

Нефункціональні

  • Масштаб (приклад з Alex Xu): ~10 млн push, ~1 млн SMS, ~5 млн email на день — плюс піки маркетингових розсилок.
  • Не губити важливі сповіщення (at-least-once), але й не дублювати (дубль OTP чи «замовлення оплачено» — погано).
  • Пріоритети: OTP за секунди навіть під час маркетингової розсилки на 50 млн.
  • Захист користувача: частотні ліміти, щоб не заспамити.
  • Відмова одного провайдера не зупиняє канал.

High-level схема

Надійність: ідемпотентність, ретраї, DLQ

  • Dedup: ключ ідемпотентності (від джерела: event_id чи order-81723-shipped) → SET key NX EX 86400 у Redis або унікальний індекс у БД. Повтор події з Kafka чи ретрай клієнта не дає другого сповіщення.
  • Ретраї: експоненційний backoff з jitter (туторіал 8), обмежена кількість спроб, для OTP — короткий дедлайн (код, що прийшов через 10 хвилин, марний: краще надіслати в інший канал).
  • Провайдери: для SMS — 2+ провайдери з автоматичним failover і маршрутизацією за країною/вартістю; для push — APNs (HTTP/2, токен-автентифікація) і FCM (HTTP v1 API). APNs повертає статус «Unregistered» (HTTP 410) для неактивного токена, FCM — помилку UNREGISTERED: такі токени треба видаляти.
  • Частотні ліміти на користувача (frequency capping): наприклад, не більше 3 маркетингових push на день; групування («5 нових коментарів» замість п'яти push-ів) — digest.
  • Тихі години й часові пояси: маркетинговий лист о 3-й ночі за місцевим часом відкладається (scheduler з чергою за send_at); транзакційні (OTP, безпека) — ігнорують тихі години.
  • Трекінг: delivery receipts від провайдерів (webhooks), відкриття email — піксель, кліки — redirect-посилання (привіт, URL shortener з туторіалу 9!).

Як це роблять у реальних системах. Великі компанії мають внутрішні notification-платформи (Uber, LinkedIn, Airbnb, Slack публікували статті про свої — з акцентом на ранжування і частотні ліміти: LinkedIn, наприклад, писав про оптимізацію обсягу сповіщень, щоб не «вигоряли» користувачі). Готові сервіси: AWS SNS/Pinpoint, Firebase Cloud Messaging, OneSignal, Braze. На співбесіді варто згадати «build vs buy»: для більшості компаній провайдери закривають доставку, а власна платформа потрібна для налаштувань, пріоритетів і дедуплікації між командами.
Аналогія для фронтендера
Web Push у браузері — та сама модель: ваш сервер не шле сповіщення в браузер напряму, а через push-сервіс браузера (FCM для Chrome, Mozilla autopush для Firefox, Apple — для Safari) за PushSubscription.endpoint; service worker «прокидається» в push-події. Коли користувач відкликав дозвіл — сервіс відповідає 404/410, і підписку треба видалити: рівно як із недійсними токенами APNs. Toast-черга в UI з дедуплікацією за ключем (одне повідомлення «немає мережі» замість десяти) — це той самий dedup. Де ламається: у браузері черга живе в одній вкладці, а тут — розподілена і має пережити падіння воркерів.
🎯
Що кажуть сильні кандидати: «API приймає запит асинхронно (202) з ключем ідемпотентності. Перед відправленням — prefs, тихі години, частотні ліміти. Черги за каналом (bulkhead) з пріоритетними підчергами — OTP ніколи не чекає маркетингу. Воркери розрізняють тимчасові й постійні помилки; backoff + jitter, DLQ. Для SMS — кілька провайдерів з failover. Трекінг доставки через webhooks. Масові розсилки — окремий throttled-потік, щоб не зробити DDoS власному бекенду кліками».
🚩
Red flags: синхронний виклик APNs/Twilio з бізнес-сервісу; одна черга для всього (маркетинг блокує OTP); ретраї без ідемпотентності (користувач отримує 5 однакових SMS — і ви платите за кожну); ігнорування opt-out (юридичні ризики: GDPR, CAN-SPAM, TCPA); не видаляти недійсні токени.

Follow-up питання

  • Як надіслати 50 млн маркетингових push за годину, не поклавши бекенд кліками? (throttling розсилки, рознесення за часом, прогрів кешу цільових сторінок)
  • Як гарантувати, що OTP прийде, якщо SMS-провайдер лежить? (failover на іншого провайдера, альтернативний канал — push/email/голосовий дзвінок)
  • Як агрегувати «Вас лайкнули 37 людей»? (буфер подій на користувача з вікном, digest)
  • Як дати командам self-service без хаосу? (реєстр типів сповіщень з категорією, пріоритетом, лімітами; рев'ю нових типів)
Сповіщення: 202 + idempotency key → prefs/ліміти → черга на канал з пріоритетами → воркер → провайдер; тимчасові помилки — retry, постійні — чистка; DLQ і трекінг.

09 Автодоповнення: trie з top-K, пайплайн, шардинг, кеш і фронтенд

«Спроєктуйте підказки в пошуковому рядку Google/Amazon/Twitter». Найбільш «фронтендерська» задача з усіх: половина латентності і навантаження вирішується в браузері.

Вимоги

Функціональні

  • За префіксом повернути топ-5…10 найпопулярніших запитів.
  • Популярність — за частотою в історії пошуку (з часовим затуханням).
  • Уточнити: персоналізація? trending у реальному часі? кілька мов? виправлення опечаток (fuzzy)?
  • Фільтрація: образливе, небезпечне, персональні дані.

Нефункціональні

  • Дуже низька латентність: підказка має з'явитися до наступного натискання — серверна частина ~десятки мс, повна — бажано < 100–150 мс.
  • Великий QPS: запит на (майже) кожну літеру.
  • Свіжість — години/дні для базових підказок, хвилини — для trending (якщо потрібно).
  • Доступність важливіша за узгодженість: застарілі підказки — не проблема.

Структура даних: trie з top-K у вузлах

trie.py
import heapq

K = 3

class Node:
    __slots__ = ("children", "top")
    def __init__(self):
        self.children = {}
        self.top = []            # готовий top-K: [(count, query)], відсортований

def build(freq: dict[str, int]) -> Node:
    """Офлайн-збірка: на кожному вузлі зберігаємо top-K запитів з цим префіксом."""
    root = Node()
    for q, c in freq.items():
        node = root
        for ch in q:
            node = node.children.setdefault(ch, Node())
            node.top.append((c, q))
    stack = [root]
    while stack:                 # обрізаємо до K найпопулярніших
        n = stack.pop()
        n.top = heapq.nlargest(K, n.top)
        stack.extend(n.children.values())
    return root

def suggest(root: Node, prefix: str) -> list[str]:
    node = root
    for ch in prefix:            # O(len(prefix)) — і все, без обходу піддерева
        node = node.children.get(ch)
        if node is None:
            return []
    return [q for _, q in node.top]

freq = {"twitter": 35, "twitch": 29, "twilight": 12, "tree": 10,
        "try": 8, "true": 22, "trump": 30, "twin peaks": 5}
root = build(freq)
print(suggest(root, "tw"))
print(suggest(root, "tr"))
print(suggest(root, "x"))

Виведе ['twitter', 'twitch', 'twilight'], ['trump', 'true', 'tree'] і []. Будуємо дерево офлайн, а онлайн-шлях — лише спуск за літерами й повернення готового списку.

Альтернативи, які варто назвати: (1) KV-таблиця «префікс → top-K» (Redis/DynamoDB): та сама ідея без дерева — для кожного префікса до довжини ~20 зберігаємо готовий список; простіше шардувати і реплікувати, більше пам'яті; (2) Elasticsearch/OpenSearch completion suggester — FST (FST — finite state transducer, стиснутий автомат для префіксів) у пам'яті з вагами; добре, коли вже є пошуковий кластер; (3) Redis sorted set на префікс з ZINCRBY — для простих trending-підказок.

Пайплайн даних і сервінг

Шардинг trie

  • За першими літерами (a–c, d–f…) — просто, але нерівномірно: на «s» і «c» запитів значно більше, ніж на «x». Рішення — межі шардів за історичним розподілом (shard map: «s» окремо, «sa–sm» і «sn–sz» окремо…), як range-шардинг у туторіалі 5.
  • Короткі префікси («a», «s») — найгарячіші і їхні відповіді однакові для всіх: вони майже повністю обслуговуються з кешу (CDN/браузер).
  • Реплікація кожного шарду ×N для читань; snapshot однаковий на всіх репліках, тож узгодженість не проблема.
  • Якщо весь trie влазить у RAM одного сервера — шардинг не потрібен, лише реплікація. Скажіть це вголос: це показує, що ви рахуєте, а не ускладнюєте.

Кешування на всіх рівнях і фронтенд

  1. Браузер: debounce 100–300 мс (або throttle для «живого» відчуття), мінімальна довжина префікса (1–2 символи), кеш відповідей у пам'яті (Map<prefix, suggestions>) — Backspace повертає миттєво; HTTP-кеш через Cache-Control.
  2. Race conditions: AbortController скасовує попередній fetch; додатково перевіряємо, що відповідь відповідає поточному значенню input (сервер повертає q у відповіді).
  3. Prefetch: деякі системи одразу після фокусу на полі вантажать підказки для порожнього/частого префікса або top-K для наступних літер.
  4. CDN: неперсоналізовані відповіді за ?q=tw&lang=uk кешуються на edge з max-age у хвилини–години — короткі префікси майже не доходять до бекенду.
  5. Персоналізація (історія користувача) — окремий маленький запит/шар, який мерджиться з глобальними підказками; він private і не кешується на CDN.
  6. Доступність: патерн WAI-ARIA combobox (role="combobox", aria-activedescendant, керування стрілками), підсвічування збігу.

Частина V · Практика

10 Трікі питання

Питання, які інтерв'юери ставлять після «канонічної» відповіді, щоб перевірити глибину. Спершу відповідайте вголос.

TRICKYЧому в кеші стрічки зберігаються ID постів, а не самі пости?

(1) Пам'ять: 8 байт проти ~1 КБ — різниця у ~100 разів, помножена на сотні мільйонів стрічок по 800 елементів. (2) Оновлення: редагування, видалення, зміна аватара автора, лічильники лайків — усе це довелося б розсилати в мільйони копій. З ID пост живе в одному місці (кеш постів), стрічка лише посилається. (3) Модерація: заблокований пост зникає з усіх стрічок миттєво — фільтром при гідрації. Ціна — додатковий батчевий MGET при читанні, але кеш постів має дуже високий hit ratio (свіжі пости гарячі).

TRICKYКористувач фоловить 2 000 акаунтів, з них 400 — «зірки». Гібридний fan-out не ламається?

Ламається: pull-частина стає 400 запитами на кожне відкриття стрічки. Варіанти: (1) кешувати «зіркові» timelines агресивно — їх читають мільйони, тож вони й так гарячі; запит — це MGET до кешу, а не до БД; (2) обмежити pull до N найактивніших/найближчих зірок і робити для решти «відкладений» push (fan-out з низьким пріоритетом лише активним фоловерам); (3) ліміт на кількість підписок (Twitter історично мав ліміт на кількість фоловінгів). Головне — показати, що ви бачите: «зірковість» — це властивість пари (автор, читач), а не лише автора.

COREЧому для чату WebSocket, а не SSE чи long polling?

Чат — двонаправлений і з високою частотою дрібних повідомлень в обидва боки (send, ack, receipts, typing). WebSocket дає одне довгоживуче з'єднання з мінімальним оверхедом на кадр. SSE — лише сервер → клієнт (відправлення довелося б робити окремими HTTP POST, що теж нормально для «рідко пишемо, часто читаємо», наприклад, стрічка «нові пости» чи нотифікації). Long polling — fallback для мереж, де WebSocket ріжеться проксі: більше латентності й HTTP-оверхеду. Мобільні клієнти, крім того, тримають з'єднання лише у foreground — у фоні доставку забирає push (APNs/FCM). Детально — JS: дані в реальному часі і Node: realtime і черги.

TRICKYЧи можна гарантувати exactly-once доставку повідомлення в чаті?

По мережі — ні: якщо ack загубився, відправник не може відрізнити «не дійшло» від «дійшло, але відповідь загубилась» (Two Generals problem). Реальна гарантія — at-least-once доставка + ідемпотентна обробка: сервер дедуплікує за client_msg_id, клієнт отримувача — за msg_id. Для користувача це виглядає як «рівно один раз», але технічно повідомлення може пройти мережею двічі. Детально — туторіал 7.

TRICKYPresence на Redis keyspace notifications («ключ сплив → offline») — у чому підступ?

(1) Подія expired генерується, коли Redis фактично видаляє ключ — при зверненні до нього або фоновим циклом, який перевіряє випадкову вибірку ключів; на великому датасеті подія може запізнюватися. (2) Keyspace notifications — це Pub/Sub, fire-and-forget: якщо підписник перепідключався — подію втрачено назавжди. (3) У Redis Cluster сповіщення локальні для кожного вузла — треба підписуватися на всі. Надійніше: sorted set last_seen (score = timestamp) + періодичний «прибиральник», що вибирає ZRANGEBYSCORE … -inf now-60 і публікує offline-події в durable-чергу; а онлайн-статус при читанні обчислювати як now - last_seen < 60 с.

ADVУчасники групи пишуть одночасно з різних континентів. Як отримати однаковий порядок для всіх?

Потрібен один «власник» порядку на чат: усі повідомлення чату проходять через одну партицію/актора/шард (вибір за hash(chat_id)), який присвоює послідовний seq. Усі клієнти сортують за seq — порядок однаковий. Ціна: повідомлення з Австралії в чат, «домашній» регіон якого — EU, йде через EU (+сотні мс). Альтернатива — Snowflake ID з різних регіонів (порядок «майже» за часом, але двоє можуть побачити різний порядок до синхронізації, якщо сортують за часом прийому). Для чату людей зазвичай прийнятне друге; для «журналу подій» — лише перше.

TRICKYDedup сповіщень: SET NX до відправлення чи після?

Обидва варіанти мають дірку. До: воркер поставив ключ і впав до відправлення → при ретраї бачимо «вже є» і пропускаємо → сповіщення втрачено. Після: воркер відправив і впав до запису ключа → ретрай відправить вдруге. Рішення — стан-машина зі статусом і lease: pending → sending(lease до T) → sent; ретрай бере запис, лише якщо lease протермінований, і для критичних каналів передає провайдеру власний ідемпотентний ключ, якщо API провайдера його підтримує. І свідомо обираєте, що гірше для типу: для OTP краще дубль, ніж втрата; для «з вас списано 1000 грн» — теж дубль; для маркетингу — краще втрата.

COREЧому не робити typeahead запитом LIKE 'tw%' до БД?

B-tree індекс підтримує префіксний LIKE, але потім треба відсортувати всі збіги за популярністю: для префікса «t» це мільйони рядків на кожне натискання при десятках тисяч QPS. Top-K, передобчислений для кожного префікса, перетворює запит на O(довжина префікса) + читання готового списку. Плюс БД — диск і транзакції, а тут потрібна RAM-структура, яку можна перебудовувати офлайн і реплікувати без координації.

ADVЯк робити пагінацію курсором у ранжованій стрічці, де score змінюються щохвилини?

Курсор «score < X» не працює: пост із наступної сторінки може «підскочити» вгору й зникнути, або з'явитися двічі. Рішення: при першому запиті відранжувати сесію (наприклад, 500 кандидатів), зберегти список ID у кеші з TTL (хвилини) під session_id, а курсор = (session_id, offset) по цьому замороженому списку. Коли сесія закінчилась — нове ранжування, з фільтром «вже показані». Instagram/TikTok-подібні стрічки працюють за схожим принципом (знімок кандидатів на сесію).

ADVДеплой WebSocket-gateway розриває 500 тис. з'єднань. Що станеться і як цього уникнути?

Усі 500 тис. клієнтів одночасно перепідключаються → сплеск TLS-handshake-ів (CPU), запитів до registry, sync-запитів історії → каскадне перевантаження (thundering herd). Захист: (1) graceful drain — сервер перестає приймати нові з'єднання і просить існуючих клієнтів перепідключитися порціями протягом хвилин; (2) клієнтський reconnect з exponential backoff і jitter; (3) інкрементальний sync (курсор), а не «завантажити все»; (4) rate limit на sync і пріоритет «доставка нових» над «історією»; (5) відокремлений від логіки gateway, щоб деплоїти його рідко.

Задача 1ЛегкоСкільки коштує fan-out

50 млн DAU, 10 млн постів на день, середня кількість фоловерів — 300. Скільки записів у кеш стрічок на секунду дає чистий fan-out on write? Що зміниться, якщо пропускати користувачів, неактивних понад 30 днів (припустимо, це 60% фоловерів)?

10⁷ × 300 / 86 400 ≈ 34 700 записів/с у середньому, пік ×2–3 ≈ 70–100 тис./с. Без неактивних — 40% від цього: ≈ 14 000/с. Плюс економія пам'яті: стрічки неактивних користувачів не зберігаються взагалі. Висновок: «пропуск неактивних» — найдешевша оптимізація fan-out, часто ефективніша за складні схеми.

Задача 2ЛегкоСкільки gateway-серверів

Пік — 80 млн одночасних WebSocket-з'єднань. Один gateway стабільно тримає 400 тис. з'єднань. Потрібен запас 50% на сплески/реконекти і витримування падіння цілої зони доступності з трьох. Скільки серверів?

Базово: 8 × 10⁷ / 4 × 10⁵ = 200. Запас 50% → 300. Щоб пережити втрату 1 з 3 AZ, решта двох мають тримати все: 300 × 3/2 = 450 серверів (по 150 на зону). Додатково варто згадати, що на практиці ліміт з'єднань упирається не лише в пам'ять, а й у CPU на TLS і heartbeat-и — 400 тис. треба перевірити навантажувальним тестом.

Задача 3СередньоDebug: дублікати повідомлень у метро

Користувачі скаржаться: у метро їхні повідомлення іноді з'являються в отримувача двічі або тричі. Сервер логує кілька send з однаковим текстом з інтервалом 5–10 с. Клієнт при таймауті ack повторює відправлення. Що не так і як виправити?

Ack загубився (з'єднання впало після запису на сервері, але до доставки ack), клієнт повторив — сервер сприйняв повтор як нове повідомлення і присвоїв новий msg_id. Виправлення: (1) клієнт генерує client_msg_id один раз при створенні повідомлення і використовує його в усіх повторах; (2) сервер тримає (sender_id, client_msg_id) → msg_id (унікальний індекс або Redis з TTL) і при повторі повертає існуючий msg_id без нового запису й доставки; (3) клієнт отримувача дедуплікує за msg_id на випадок повторної доставки. Це ідемпотентність як у Stripe Idempotency-Key, тільки в WebSocket-протоколі.

Задача 4СередньоРозмір bucket-а для каналу

Повідомлення — у Cassandra з ключем (channel_id, bucket). Найактивніший канал — 1 млн повідомлень на добу по ~200 Б. Ви хочете тримати партиції до ~100 МБ. Яким має бути bucket? Що буде з тихими каналами, якщо зробити bucket однаковим для всіх?

Активний канал: 10⁶ × 200 Б = 200 МБ/добу → для ≤ 100 МБ потрібен bucket ≤ 12 годин. Якщо зробити 12 годин для всіх, тихий канал (кілька повідомлень на тиждень) змусить запит «останні 50» перебрати десятки порожніх bucket-ів — багато дрібних запитів. Варіанти: (1) розмір bucket-а — властивість каналу (зберігається в метаданих, змінюється при рості — як «перешардинг» для гарячих каналів); (2) таблиця-індекс «channel → список непорожніх bucket-ів», щоб пропускати порожні; (3) компроміс на глобальному розмірі (Discord обрав 10 днів, орієнтуючись на типовий розмір партиції). На співбесіді цінується саме розуміння обох крайнощів.

Задача 5СередньоDebug: OTP приходить через 20 хвилин

Під час маркетингової розсилки на 30 млн користувачів SMS із кодами входу приходять із затримкою 15–20 хвилин, і люди не можуть залогінитися. Усі SMS ідуть через одну чергу і один пул воркерів. Що змінити?

  1. Розділити транзакційні (OTP, безпека, платежі) і маркетингові потоки: окремі черги й окремі пули воркерів (bulkhead) — маркетинг фізично не може зайняти воркери OTP.
  2. Пріоритетні підчерги в межах каналу: воркер спершу вибирає high.
  3. Окремі квоти в провайдера (rate limit провайдера часто спільний на акаунт!) — окремий sender/акаунт для транзакційних, або резерв пропускної здатності.
  4. Маркетинг — throttled-розсилка (наприклад, N тис./хв), розтягнута в часі.
  5. Дедлайн для OTP: якщо не відправлено за 60 с — альтернативний канал/провайдер, бо пізній код марний.
Задача 6СередньоПам'ять для typeahead

50 млн унікальних запитів, середня довжина 20 символів. Ви обираєте KV-варіант «префікс → top-5». Оцініть кількість ключів і пам'ять, якщо top-5 зберігає 4-байтні ID запитів, а оверхед на ключ (сам рядок префікса + структура) ~50 Б.

Верхня межа унікальних префіксів — 50 млн × 20 = 10⁹, але префікси спільні (особливо короткі), і довгі префікси майже унікальні для одного запиту. Розумне спрощення: зберігати префікси лише до довжини ~15 і реалістично отримати порядку 2–5 × 10⁸ ключів. Пам'ять на ключ: 50 Б + 5 × 4 Б = 70 Б → 14–35 ГБ плюс таблиця самих рядків запитів (50 млн × ~30 Б ≈ 1,5 ГБ). Висновок: влазить у RAM кількох серверів; можна реплікувати повністю, а шардувати — лише якщо потрібна менша пам'ять на інстанс.

Задача 7ЛегкоФронтенд: застарілі підказки

У полі пошуку підказки іноді «стрибають» на старі: користувач набрав «react», а бачить підказки для «re». Код: onChange = (q) => fetch('/suggest?q=' + q).then(r => r.json()).then(setSuggestions). Виправте.

Race condition: відповідь на «re» прийшла пізніше за «react» і перезаписала стан. Виправлення: debounce (~150–250 мс), AbortController — скасовувати попередній запит при новому введенні, і перевірка актуальності: застосовувати відповідь лише якщо response.q === currentInput. Плюс кеш Map<prefix, suggestions> і мінімальна довжина префікса. У React — useEffect з cleanup, що викликає controller.abort(), або React Query з queryKey: ['suggest', debouncedQ], який сам ігнорує застарілі відповіді.

Задача 8СкладноЛічильники непрочитаного для каналів на 100 тис. учасників

Slack-подібний продукт: у користувача 300 каналів, деякі канали мають 100 тис. учасників і 50 повідомлень/хв. Потрібно показувати бейдж «є непрочитане» на кожному каналі та точний лічильник згадок (@mentions). Наївний підхід «інкрементувати unread_count кожному учаснику на кожне повідомлення» дає 100 тис. × 50 = 5 млн записів/хв на один канал. Спроєктуйте краще.

  1. Бейдж — обчислюваний: порівнюємо latest_msg_id каналу з last_read_msg_id користувача. Snowflake ID дозволяє порівнювати без лічильників. Для 300 каналів — два батчеві запити.
  2. Точний unread_count для великого каналу показувати не обов'язково (у великих каналах продукти часто показують просто жирну назву без числа) — це продуктове рішення, яке знімає технічну проблему.
  3. Згадки — справжній fan-out on write, але лише на згаданих користувачів (одиниці); @channel/@here — обмежувати правами й частотою.
  4. Онлайн-клієнти отримують події каналу і підтримують лічильники локально; при реконекті — перерахунок з сервера.
Задача 9СкладноDebug: стрічки «гальмують», коли постить знаменитість

Щоразу, коли акаунт із 8 млн фоловерів публікує пост, p99 відкриття стрічки для всіх користувачів зростає з 150 мс до 2 с на 10–15 хвилин. Поріг «зірки» — 10 млн фоловерів. Fan-out workers і Feed service використовують один Redis-кластер. Знайдіть причини і запропонуйте виправлення.

  1. Причина 1: 8 млн < порогу → робимо push: 8 млн LPUSH+LTRIM за хвилини забивають Redis, і читання стрічок усіх користувачів чекають у тих самих шардах (noisy neighbor). Знизити поріг (наприклад, 100 тис.–1 млн) або зробити його динамічним.
  2. Причина 2: fan-out не має throttling-у — воркери пишуть на максимальній швидкості. Обмежити швидкість fan-out (rate limit на воркери), пріоритезувати читання.
  3. Причина 3: один кластер для запису fan-out і читання. Розділити (або хоча б виділити ресурси), реплікувати шарди для читань.
  4. Причина 4: після поста 8 млн людей отримують push-сповіщення і відкривають стрічку + сам пост — hot key на пості й timeline автора. Local cache у Feed service для гарячих постів, request coalescing.
  5. Метрика для алерту: лаг fan-out (час від публікації до появи у стрічці) і p99 читання стрічки окремо для «звичайних» і «зіркових» подій.
Задача 10СкладноTrending у підказках за 5 хвилин

Базовий trie перебудовується щодня. Продукт хоче, щоб запит, який «вибухнув» через новину, з'являвся в підказках за 5 хвилин. Як змінити дизайн, не перебудовуючи весь trie кожні 5 хвилин?

  1. Стрім-контур: пошукові запити з Kafka → Flink рахує частоти в ковзному вікні (5–15 хв) і порівнює з базовою частотою (сплеск = відношення поточної до звичайної).
  2. Топ «вибухових» запитів (сотні–тисячі) — у невеликій структурі «префікс → trending top-K» (Redis/в пам'яті), що оновлюється щохвилини. Count-Min Sketch для оцінки частот з обмеженою пам'яттю (туторіал 12).
  3. Suggest-сервер мерджить базовий top-K з trending top-K з бустом і затуханням.
  4. Модерація: trending — найризикованіші підказки (дезінформація, образи) → суворіший фільтр і denylist з миттєвим застосуванням.
  5. Кеш CDN для коротких префіксів — короткий max-age (хвилина), інакше trending не буде видно.
