01 Ментальна модель: надійність — це шари захисту

На співбесіді надійність перевіряють двома способами: окремою задачею («спроектуйте rate limiter») і follow-up питаннями до будь-якого дизайну («а що, якщо БД почне відповідати за 5 секунд?»). В обох випадках потрібно бачити систему як шари, кожен з яких зупиняє свою частину проблем.

Чому системи падають «каскадом»

Типовий сценарій: БД сповільнилась з 5 до 500 мс → потоки сервісу чекають довше → пул потоків вичерпано → сервіс перестає відповідати навіть на запити, яким БД не потрібна → клієнти ретраять → навантаження зростає ще більше → БД остаточно лягає. Жоден компонент не «зламався», але система мертва. Усі механізми цього туторіалу розривають цю петлю в різних місцях:

МеханізмЩо розриває

Таймаути й дедлайниНе дають потокам вічно чекати
Backoff + jitter + retry budgetНе дають ретраям помножити навантаження
Circuit breakerПерестає бити хвору залежність, дає їй відновитися
BulkheadПовільна залежність з'їдає лише свій пул ресурсів
Load sheddingСервіс відкидає надлишок, щоб обслужити решту якісно
Graceful degradationВіддає «гірший, але робочий» результат замість помилки
Аналогія для фронтендера

Ви вже користуєтесь більшістю цих ідей у браузері: debounce на пошуку — це rate limiting клієнта; AbortController з таймаутом — дедлайн; React Query з retry: 3 і retryDelay — експоненційний backoff; Error Boundary — bulkhead (падіння віджета не валить сторінку); skeleton/заглушка замість рекомендацій — graceful degradation. Де ламається: у браузері збій зачіпає одного користувача, а на сервері — мільйони одночасно, і їхні ретраї синхронізуються в «шторм».

🎤
На співбесіді: після high-level дизайну сам скажіть: «Тепер про відмови: на gateway — rate limiting за API key; між сервісами — таймаути з дедлайном, ретраї лише для ідемпотентних операцій з backoff і jitter, circuit breaker на зовнішній платіжний API; SLO — 99.9% успішних запитів з p99 < 300 мс». Це переводить вас з рівня middle на senior.
Надійність = шари, кожен з яких зупиняє розповзання збою. Найнебезпечніше — не відмова, а повільність і ретраї.

02 Алгоритми rate limiting

П'ять класичних алгоритмів. Треба вміти пояснити кожен, намалювати, назвати плюси/мінуси і написати token bucket за 5 хвилин.

Token bucket і leaky bucket

Fixed window, sliding window log, sliding window counter

limiters.py — усі п'ять алгоритмів, перевірено python3
from collections import deque

class TokenBucket:
    """capacity - максимальний burst; rate - токенів за секунду."""
    def __init__(self, capacity: float, rate: float, now: float = 0.0):
        self.capacity, self.rate = capacity, rate
        self.tokens, self.last = capacity, now

    def allow(self, now: float, cost: float = 1.0) -> bool:
        # ліниве поповнення: рахуємо, скільки "накрапало" з минулого виклику
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

class LeakyBucket:
    """Як лічильник (meter): відро витікає зі швидкістю rate; переповнення = reject."""
    def __init__(self, capacity: float, rate: float, now: float = 0.0):
        self.capacity, self.rate = capacity, rate
        self.level, self.last = 0.0, now

    def allow(self, now: float) -> bool:
        self.level = max(0.0, self.level - (now - self.last) * self.rate)
        self.last = now
        if self.level + 1 <= self.capacity:
            self.level += 1
            return True
        return False

class FixedWindow:
    def __init__(self, limit: int, window: float):
        self.limit, self.window = limit, window
        self.cur_window, self.count = None, 0

    def allow(self, now: float) -> bool:
        w = int(now // self.window)
        if w != self.cur_window:
            self.cur_window, self.count = w, 0
        if self.count < self.limit:
            self.count += 1
            return True
        return False

class SlidingWindowLog:
    def __init__(self, limit: int, window: float):
        self.limit, self.window = limit, window
        self.log = deque()                       # таймстемпи прийнятих запитів

    def allow(self, now: float) -> bool:
        while self.log and self.log[0] <= now - self.window:
            self.log.popleft()
        if len(self.log) < self.limit:
            self.log.append(now)
            return True
        return False

class SlidingWindowCounter:
    """Зважує лічильник попереднього вікна часткою перекриття."""
    def __init__(self, limit: int, window: float):
        self.limit, self.window = limit, window
        self.cur_start, self.cur, self.prev = 0.0, 0, 0

    def allow(self, now: float) -> bool:
        start = (now // self.window) * self.window
        if start != self.cur_start:
            # якщо пропустили більше одного вікна - попереднє порожнє
            self.prev = self.cur if start - self.cur_start == self.window else 0
            self.cur_start, self.cur = start, 0
        overlap = 1 - (now - start) / self.window   # частка попереднього вікна
        estimated = self.prev * overlap + self.cur
        if estimated + 1 <= self.limit:
            self.cur += 1
            return True
        return False

if __name__ == "__main__":

    print("t=0.5 allow?", tb.allow(0.5), "| t=0.6 allow?", tb.allow(0.6))

    b = sum(fw.allow(1.01) for _ in range(5))
    print("fixed window: accepted", a + b, "requests within 20 ms (limit 5/s)")

Розбір виводу: token bucket віддав 5 токенів сплеском, за 0.5 с накрапав 1 токен (2/с × 0.5) — один запит пройшов, наступний через 0.1 с — ні (лише 0.2 токена). Fixed window пропустив 10 запитів за 20 мс. Sliding counter на t=1.3 оцінює 5 × 0.7 = 3.5 → пропускає ще один (4.5 ≤ 5), а наступний уже ні (5.5 > 5).

Аналогія для фронтендера

throttle(fn, 1000) — це майже leaky bucket з ємністю 1: виклики рівномірно, не частіше разу на секунду. debounce — інша ідея (чекати тиші), у rate limiting її аналога немає. Де ламається: throttle у браузері стоїть у одному процесі з одним годинником; серверний ліміт мусить бути спільним для сотень інстансів (розділ 3).

🎤
На співбесіді: дефолтний вибір — token bucket: O(1) пам'яті, дозволяє природні сплески, два параметри зрозумілі продукту (rate і burst). Якщо потрібна строгість без сплесків — sliding window counter. Назвіть проблему межі у fixed window — це класичне питання «а що не так з простим лічильником?».
Token bucket = rate + burst. Leaky bucket = рівний вихід. Fixed window = 2× на межі. Sliding log = точно, але дорого. Sliding counter = майже точно і дешево.

03 Розподілений rate limiter: Redis + Lua, де ставити, які заголовки

Ліміт «100 запитів/хв на користувача» має працювати, коли запити користувача розкидані балансувальником по 50 інстансах. Значить, стан лічильника — спільний, а оновлення — атомарне.

Token bucket у Redis одним Lua-скриптом

token_bucket.lua
-- KEYS[1] = ключ бакета, напр. "rl:{user:42}"
-- ARGV: capacity, rate (токенів/с), now_ms, cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local cost     = tonumber(ARGV[4])

local b      = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity        -- новий ключ = повний бакет
local ts     = tonumber(b[2]) or now

tokens = math.min(capacity, tokens + math.max(0, now - ts) / 1000 * rate)
local allowed = 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
-- ключ сам зникне, коли бакет точно повний (економія пам'яті)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 1000)
return {allowed, tostring(tokens)}   -- tostring: Redis обрізає дробові числа Lua до цілих
rate_limit.py — виклик з Python (redis-py)
import time, redis

r = redis.Redis()
bucket = r.register_script(open("token_bucket.lua").read())   # EVALSHA під капотом

def allow(user_id: str, capacity=20, rate=5.0, cost=1) -> tuple[bool, float]:
    allowed, tokens = bucket(keys=["rl:{user:" + user_id + "}"],
                             args=[capacity, rate, int(time.time() * 1000), cost])
    return bool(allowed), float(tokens)

Логіка скрипта дослівно повторює перевірений вище TokenBucket.allow; сам Lua-скрипт у цьому середовищі не запускався (немає Redis) — перевірте в себе на redis-server. Нюанси: час передається з клієнта — розбіжність годинників gateway-інстансів дає невелику похибку (альтернатива — redis.call('TIME') всередині скрипта); фігурні дужки в ключі — hash tag для Redis Cluster, щоб усі ключі одного користувача були в одному слоті; sliding log робиться так само через sorted set: ZREMRANGEBYSCORE старих → ZCARD → ZADD.

  • 429 — «ти перевищив свій ліміт»; 503 — «сервер перевантажений загалом» (load shedding). Клієнт поводиться з ними однаково: backoff і повтор після Retry-After.
  • X-RateLimit-* — де-факто стандарт (GitHub, Twitter/X); є IETF-драфт стандартних заголовків RateLimit/RateLimit-Policy (перевірте актуальний статус).
  • Що робити з відхиленим: відкинути (API), поставити в чергу (вебхуки, email), деградувати (віддати кеш).

Тонкі питання дизайну

  • Redis недоступний: fail open чи fail closed? Зазвичай fail open (пропускати) з локальним запасним лімітом у пам'яті кожного інстансу — краще тимчасово неточний ліміт, ніж повна відмова API через лімітер. Для захисту від зловживань (логін, SMS) — fail closed.
  • Латентність: +1 мережевий виклик (~0.5–1 мс в одному AZ) на кожен запит. Оптимізація: локальний бакет із «позиченими» в Redis партіями токенів (напр., по 10) — менше викликів, трохи менша точність.
  • Мульти-регіон: глобальний лічильник через океан — +100 мс. Зазвичай ліміт ділять між регіонами або синхронізують асинхронно, приймаючи похибку.
  • Ключ: user id / API key / IP / (user, endpoint) / tenant. За IP — обережно з NAT (тисячі користувачів офісу за однією адресою) і IPv6 (атакувальник має мільйони адрес — лімітують за /64).
  • Вартість запиту: не всі запити рівні. GitHub GraphQL рахує «очки» за складністю запиту; у token bucket це параметр cost.

На співбесіді (детальна задача — у туторіалі 9): «Token bucket у Redis через Lua для атомарності; ключ — API key з hash tag; ліміти в конфігу, що кешується локально; при недоступності Redis — fail open з локальним лімітом; відповідь 429 з Retry-After і X-RateLimit-заголовками; метрики відхилених запитів за ключами».
🚩
Red flags: GET + SET з коду без атомарності; лічильник у пам'яті кожного інстансу (ліміт множиться на кількість інстансів і змінюється при автоскейлінгу); блокувальні розподілені локи на кожен запит; ліміт лише на фронтенді.
Спільний стан + атомарність (INCR / Lua). Кілька рівнів: edge за IP, gateway за ключем, сервіс за бізнес-ресурсом. 429 + Retry-After.

04 Таймаути, дедлайни, ретраї, backoff і jitter

Найпростіші механізми, які найчастіше роблять неправильно. Ретраї без меж — головна причина того, що маленький збій перетворюється на повну відмову.

Таймаути: завжди і з розумом

  • Кожен мережевий виклик має таймаут. Багато бібліотек за замовчуванням чекають вічно — наприклад, Python requests без параметра timeout. Один «завислий» виклик тримає потік/з'єднання, сотня таких — і пул вичерпано.
  • Окремо connect timeout і read/request timeout. Connect — короткий (сотні мс; якщо хост не відповідає на TCP SYN, далі чекати марно), request — за латентністю залежності.
  • Як обрати значення: AWS Builders' Library радить відштовхуватись від перцентиля латентності залежності, з яким ви згодні мати хибні таймаути (наприклад, p99.9): таймаут нижче → забагато хибних відмов, вище → потоки довго «висять».

Дедлайни та їх поширення

Ретраї: коли можна

  1. Лише ідемпотентні операції (GET, PUT, DELETE) або неідемпотентні з idempotency key (POST з ключем, як у Stripe). Повтор POST без ключа = подвійне списання.
  2. Лише тимчасові помилки: таймаут, 503, 429 (з урахуванням Retry-After), connection reset. Не ретраїти 400/401/403/404/422.
  3. Обмежена кількість (2–3 спроби) і в межах дедлайну.
  4. Ретраїти на одному рівні стеку, а не на кожному (див. нижче — множення).
  5. Exponential backoff + jitter, щоб клієнти не синхронізувались.

Чому jitter обов'язковий

backoff.py — формули з AWS Architecture Blog «Exponential Backoff And Jitter», перевірено python3
import random

def full_jitter(attempt: int, base=0.1, cap=10.0) -> float:
    """AWS 'Full Jitter': sleep = random(0, min(cap, base * 2**attempt))."""
    return random.uniform(0, min(cap, base * 2 ** attempt))

def decorrelated_jitter(prev: float, base=0.1, cap=10.0) -> float:
    """AWS 'Decorrelated Jitter': sleep = min(cap, random(base, prev * 3))."""
    return min(cap, random.uniform(base, prev * 3))

def retry(fn, max_attempts=4, retryable=(TimeoutError, ConnectionError), sleep=None):
    import time
    sleep = sleep or time.sleep
    for attempt in range(max_attempts):
        try:
            return fn()
        except retryable:
            if attempt == max_attempts - 1:
                raise                     # бюджет спроб вичерпано
            sleep(full_jitter(attempt))

if __name__ == "__main__":
    random.seed(7)
    print("caps:", [min(10.0, 0.1 * 2 ** a) for a in range(8)])
    print("full jitter:", [round(full_jitter(a), 3) for a in range(8)])
    calls = {"n": 0}
    def flaky():
        calls["n"] += 1
        if calls["n"] < 3:
            raise ConnectionError("reset")
        return "200 OK"
    slept = []
    print(retry(flaky, sleep=slept.append), "after", calls["n"], "calls; slept",
          [round(s, 3) for s in slept])

# caps: [0.1, 0.2, 0.4, 0.8, 1.6, 3.2, 6.4, 10.0]
# full jitter: [0.032, 0.03, 0.26, 0.058, 0.857, 1.17, 0.371, 5.074]
# 200 OK after 3 calls; slept [0.004, 0.087]

У статті AWS порівнюються «No jitter», «Full Jitter», «Equal Jitter» і «Decorrelated Jitter»: варіанти з jitter роблять помітно менше сумарних викликів і завершують роботу швидше, а Full Jitter — простий і хороший дефолт. У продакшені також: поважати Retry-After, не перевищувати дедлайн, логувати номер спроби.

Retry storm: множення ретраїв по рівнях

(3³ — «три в кубі» = 3 × 3 × 3 = 27.)

Retry budget

Замість (або на додачу до) «максимум N спроб на запит» — бюджет на рівні клієнта: ретраї не можуть перевищувати, наприклад, 10% від успішних запитів за останню хвилину. Google SRE Book (розділ «Handling Overload») описує саме таку комбінацію: ліміт спроб на запит (3) і співвідношення ретраїв до запитів на клієнта (10%). Envoy має retry budgets як налаштування. AWS SDK у «standard» режимі ретраїв використовує token bucket для ретраїв: коли помилок багато, токени закінчуються і ретраї припиняються. Ефект: при короткому збої ретраї допомагають, при масовому — автоматично вимикаються і не добивають систему.

Hedged requests — ретраї навпаки

Для зменшення хвостової латентності (а не для помилок): якщо відповідь не прийшла за час p95, надіслати дублюючий запит іншій репліці і взяти першу відповідь. Описано в «The Tail at Scale» (Dean, Barroso, 2013). Працює лише для ідемпотентних читань і коштує кількох відсотків додаткового навантаження.

Аналогія для фронтендера

React Query за замовчуванням ретраїть невдалий запит 3 рази з експоненційною затримкою (retryDelay), а AbortSignal.timeout(ms) — це дедлайн. Тепер уявіть, що бекенд упав на 10 секунд, а відкрито 2 млн вкладок: якщо всі ретраять із тим самим кроком, бекенд після підйому отримує ідеально синхронізований удар — thundering herd. Тому jitter. Де ламається: у браузері ретраїть лише один рівень; у мікросервісах ретраї множаться по глибині стеку.

🎤
На співбесіді: «Кожен виклик з таймаутом, дедлайн поширюється в контексті. Ретраї — лише для ідемпотентних операцій або з idempotency key, на одному рівні, максимум 3, exponential backoff із full jitter, плюс retry budget ~10%, щоб при масовому збої ретраї не множили навантаження».
Таймаут на кожен виклик; дедлайн — наскрізь; ретраї — ідемпотентно, на одному рівні, з jitter і бюджетом.

05 Circuit breaker і bulkhead

Таймаут обмежує один виклик. Circuit breaker обмежує серію викликів до хворої залежності. Bulkhead обмежує, скільки ресурсів може з'їсти одна залежність.

Circuit breaker: машина станів

circuit_breaker.py — перевірено python3 (фейковий годинник)
import time

class CircuitOpenError(Exception):
    pass

class CircuitBreaker:
    """CLOSED -> (N помилок поспіль) -> OPEN -> (cooldown) -> HALF_OPEN -> пробний запит."""
    def __init__(self, failure_threshold=3, reset_timeout=5.0, clock=time.monotonic):
        self.failure_threshold = failure_threshold
        self.reset_timeout = reset_timeout
        self.clock = clock
        self.state = "CLOSED"
        self.failures = 0
        self.opened_at = 0.0

    def call(self, fn, *args, **kwargs):
        if self.state == "OPEN":
            if self.clock() - self.opened_at >= self.reset_timeout:
                self.state = "HALF_OPEN"          # пускаємо один пробний запит
            else:
                raise CircuitOpenError("fail fast")  # навіть не ходимо в мережу
        try:
            result = fn(*args, **kwargs)
        except Exception:
            self._on_failure()
            raise
        self._on_success()
        return result

    def _on_success(self):
        self.failures = 0
        self.state = "CLOSED"

    def _on_failure(self):
        self.failures += 1
        if self.state == "HALF_OPEN" or self.failures >= self.failure_threshold:
            self.state = "OPEN"
            self.opened_at = self.clock()

if __name__ == "__main__":
    now = [0.0]
    cb = CircuitBreaker(failure_threshold=3, reset_timeout=5.0, clock=lambda: now[0])
    healthy = [False]
    def remote():
        if not healthy[0]:
            raise TimeoutError("upstream timeout")
        return "ok"

    log = []
    for t in [0, 1, 2, 3, 4, 8.5, 9, 15, 16]:
        now[0] = t
        if t == 15:
            healthy[0] = True
        try:
            r = cb.call(remote)
        except CircuitOpenError:
            r = "rejected"
        except TimeoutError:
            r = "error"
        log.append(f"t={t}: {r:<8} -> {cb.state}")
    print("\n".join(log))

# t=0: error    -> CLOSED
# t=1: error    -> CLOSED
# t=2: error    -> OPEN
# t=3: rejected -> OPEN
# t=4: rejected -> OPEN
# t=8.5: error    -> OPEN      <- HALF_OPEN, пробний впав, новий cooldown
# t=9: rejected -> OPEN
# t=15: ok       -> CLOSED    <- пробний успішний
# t=16: ok       -> CLOSED

Спрощення навчальної версії: вона не потокобезпечна і в HALF_OPEN пропускає всі конкурентні запити, а не один. Продакшн-бібліотеки (resilience4j для JVM, Polly для .NET, pybreaker, Envoy outlier detection) рахують частку помилок у ковзному вікні з мінімальною кількістю запитів, окремо враховують «повільні» виклики і обмежують кількість пробних запитів.

Що повертати, коли breaker відкритий

  • Fallback: кеш (stale-but-ok), дефолтне значення, спрощена відповідь (неперсоналізовані рекомендації).
  • Швидка помилка з чітким кодом (503) — краще, ніж 30-секундний таймаут.
  • Відкласти: покласти в чергу і виконати пізніше (email, вебхуки).

Bulkhead: перегородки між відсіками

Варіанти bulkhead: окремі пули потоків/з'єднань на залежність; семафори (ліміт конкурентних викликів); окремі інстанси/кластери для різних класів клієнтів (наприклад, окремий пул серверів для внутрішніх batch-задач, щоб вони не заважали користувачам); cell-based architecture — розбиття всієї системи на незалежні «клітини» з підмножиною клієнтів (AWS описує цей підхід для обмеження blast radius).

🏭
Як це роблять у реальних системах. Netflix популяризував обидва патерни бібліотекою Hystrix (з 2018 — у режимі підтримки; спільнота перейшла на resilience4j і на рівень service mesh). Сьогодні circuit breaking і outlier detection часто живуть в Envoy/Istio: sidecar викидає з балансування інстанс, що повертає 5xx, без змін у коді.
Аналогія для фронтендера

Error Boundary — це bulkhead: помилка у віджеті рекомендацій не валить усю сторінку. А circuit breaker — як логіка «якщо API чату тричі поспіль не відповів, перестати опитувати його на 30 с і показати банер "чат тимчасово недоступний"», замість того щоб кожні 2 с бомбити мертвий бекенд. Де ламається: Error Boundary ізолює помилки рендеру, а не ресурси; bulkhead на сервері ізолює саме ресурси (потоки, з'єднання, пам'ять).

🎤
На співбесіді: на зовнішні та некритичні залежності — circuit breaker із fallback (кеш/дефолт); окремі пули з'єднань (bulkhead) для критичних і некритичних шляхів. Скажіть, що breaker рахує частку помилок і повільних викликів у вікні, а HALF-OPEN пропускає обмежену кількість пробних запитів.
Breaker — перестати бити хворого (CLOSED → OPEN → HALF-OPEN). Bulkhead — одна повільна залежність не з'їдає всі ресурси.

06 Load shedding, admission control, graceful degradation, health checks

Що робить сам сервіс, коли запитів більше, ніж він здатен обробити: відмовляє частині, щоб якісно обслужити решту, і чесно повідомляє балансувальнику про свій стан.

(ρ — «ро», утилізація: частка часу, коли сервер зайнятий; ∝ — «пропорційно». Формула ρ/(1−ρ) — середня кількість «часів обслуговування», які запит чекає в черзі, для найпростішої моделі черги M/M/1.)

Load shedding: як відмовляти правильно

  1. Відмовляти рано і дешево: перевірка на вході (кількість in-flight запитів, довжина черги, CPU) → одразу 503/429, не витрачаючи ресурсів на парсинг і БД.
  2. Пріоритети: критичний трафік (оплата, логін) обслуговується, «sheddable» (аналітика, префетч, batch) відкидається першим. Google SRE Book описує критичність запитів, що поширюється по ланцюжку викликів.
  3. Не обробляти протухле: якщо запит пролежав у черзі довше за дедлайн клієнта — викинути без обробки. AWS Builders' Library («Using load shedding to avoid overload») наголошує саме на цьому.
  4. LIFO під перевантаженням: свіжі запити ще мають шанс бути корисними, старі — вже ні (клієнт пішов).
  5. Admission control / adaptive concurrency: ліміт одночасних запитів не задається вручну, а підлаштовується за латентністю (ідея як у TCP congestion control). Приклад — бібліотека Netflix concurrency-limits. За законом Літтла: concurrency = throughput × latency.

Graceful degradation

Idempotency — щоб ретраї були безпечними

Клієнт генерує Idempotency-Key (UUID) на одну бізнес-операцію і надсилає його з кожним повтором. Сервер: (1) атомарно резервує ключ (INSERT … ON CONFLICT DO NOTHING); (2) якщо ключ уже завершено — повертає збережену відповідь; (3) якщо ключ «в процесі» (паралельний повтор) — 409 Conflict; (4) зберігає відповідь разом із результатом операції в одній транзакції. Stripe описує це в статті «Designing robust and predictable APIs with idempotency» і зберігає ключі щонайменше 24 години. Детальніше про ідемпотентних консьюмерів — у туторіалі 7.

Аналогія для фронтендера

Load shedding — як requestIdleCallback: неважливу роботу (аналітика, префетч) робимо лише тоді, коли головний потік вільний. Де ламається: на фронті «відкинута» робота стосується одного користувача; на сервері ви свідомо відмовляєте реальним людям, тому потрібні пріоритети і метрики відкинутого.

🎤
На співбесіді: «Сервіс захищає себе сам: ліміт конкурентних запитів, швидкий 503 при перевантаженні, пріоритет платежів над аналітикою, відкидання запитів з простроченим дедлайном. Для некритичних блоків — деградація до кешу або дефолту через kill switch. Liveness — поверхнева, readiness не залежить від спільних залежностей».
Краще швидко відмовити 20%, ніж повільно провалити 100%. Fallback має бути протестований. Liveness ≠ readiness.
Частина III · Вимірювання і виживання

07 SLI, SLO, SLA і error budget — надійність у числах

«Система має бути надійною» — не вимога. «99.9% запитів до checkout успішні і швидші за 300 мс протягом 30 днів» — вимога. На співбесіді в non-functional requirements варто називати саме такі числа.

SLI — індикатор

Що вимірюємо: частка «хороших» подій серед усіх. SLI = good / valid. Наприклад, частка запитів зі статусом не 5xx і латентністю < 300 мс.

SLO — ціль

Внутрішня ціль для SLI за вікно: «99.9% за 30 днів». Обирається за потребами користувачів, а не «скільки зможемо».

SLA — контракт

Зовнішнє зобов'язання з фінансовими наслідками (кредити клієнтам). Завжди м'якше за SLO, щоб мати запас: SLO 99.95% → SLA 99.9%.

Error budget

1 − SLO: скільки «поганого» дозволено. При 99.9% — 0.1% запитів або ~43 хв на 30 днів. Бюджет витрачається на релізи, експерименти, інциденти.

Композиція доступності

Error budget і burn rate

Burn rate — у скільки разів швидше за рівномірне ми витрачаємо бюджет. Burn rate 1 вичерпає бюджет рівно за вікно (30 днів). SRE Workbook (розділ «Alerting on SLOs») рекомендує multi-window алерти: пейдж, якщо за 1 год згоріло 2% місячного бюджету (burn rate = 0.02 × 720 год = 14.4) або за 6 год — 5% (burn rate 6); тікет — за повільнішого горіння. Інцидент на графіку: 40% за 2 год = 0.4 × 720 / 2 = 144.

(720 — кількість годин у 30-денному вікні: 30 × 24.)

Як обрати SLI

  • Availability: частка успішних запитів (не 5xx), виміряна якомога ближче до користувача (на LB або клієнтськими метриками, а не «процес живий»).
  • Latency: частка запитів, швидших за поріг (p99 < 300 мс трансформується в «99% запитів < 300 мс»).
  • Freshness / correctness для пайплайнів: частка даних, оновлених за останні N хвилин.
  • Не більше 3–5 SLO на сервіс, і лише ті, що відображають біль користувача.
Аналогія для фронтендера

Core Web Vitals — це SLO фронтенду: LCP ≤ 2.5 с для 75-го перцентиля відвідувань — це SLI («частка відвідувань з хорошим LCP») і ціль. Performance budget у Lighthouse CI («бандл ≤ 200 KB») — аналог error budget: перевищили — мердж блокується, поки не оптимізуєте. Де ламається: Web Vitals рахуються за p75, а бекенд SLO зазвичай на p99/p99.9, бо один запит сторінки тягне десятки бекенд-викликів.

🎤
На співбесіді в non-functional requirements: «Доступність 99.9% для читання стрічки і 99.99% для платежів; p99 латентності читання < 200 мс. 99.99% — це ~4.3 хв на місяць, тому потрібні multi-AZ, автоматичний failover і канарковий деплой, без ручних кроків у відновленні». Пов'язування числа з архітектурними наслідками — те, що відрізняє сильну відповідь.
🚩
Red flags: «нам потрібно 100%» (нескінченно дорого і неможливо — навіть мережа клієнта дає менше); SLO, вищий за SLO залежностей, без резервування; SLI «CPU < 80%» (це не біль користувача).
SLO = ціль, error budget = 1 − SLO, burn rate = швидкість витрачання. 99.9% ≈ 43 хв/міс, 99.99% ≈ 4.3 хв/міс.

Перцентилі й хвостова латентність

(p50 — медіана: половина запитів швидша; p99 — «99-й перцентиль»: 99% запитів швидші за це значення, 1% — повільніші. 0.99¹⁰⁰ — «нуль дев'яносто дев'ять у сотому степені» ≈ 0.366.)

  • Не усереднюйте перцентилі між інстансами чи хвилинами: «середнє p99 за годину» математично безглузде. Агрегуйте гістограми (Prometheus histogram buckets, HDR Histogram), а з них рахуйте перцентиль.
  • Чому важливий p99: найповільніші запити часто належать найцінніших користувачам (найбільші кошики, найбільше даних), і один користувач за сесію робить сотні запитів — хтось обов'язково потрапить у хвіст.
  • Як скорочувати хвіст: hedged requests, менший fan-out, часткові результати по дедлайну («показати 95 зі 100 шардів»), прибрати GC-паузи і шумних сусідів, прогрів кешів.

Capacity planning: як рахувати

  1. Пікове навантаження: середній QPS × пік-фактор (добовий пік зазвичай 2–3× від середнього; події — Black Friday, фінал чемпіонату — 10× і більше).
  2. Ємність інстансу — з навантажувального тесту при цільовій латентності (не «скільки витримає до падіння»).
  3. Цільова утилізація 50–70% (див. криву черги вище), а не 90%.
  4. Резерв на відмову: з 3 AZ при втраті однієї решта дві мусять тримати 100% → кожна AZ розрахована на 50% піку → разом 150% (N+1 по зонах). Плюс запас на деплой (rolling забирає частину інстансів).
  5. Час реакції автоскейлінгу: нові інстанси стартують хвилини — на різкий пік потрібен pre-warming або запас.
🧮
Приклад. Середнє 20 000 QPS, пік-фактор 3 → 60 000 QPS. Тест: інстанс тримає 1 000 QPS при p99 < 200 мс. Цільова утилізація 60% → 600 QPS на інстанс → 100 інстансів. Переживаємо втрату 1 з 3 AZ: 100 / 2 × 3 = 150 інстансів (по 50 у кожній AZ). Детальніше про такі оцінки — у туторіалі 1.
Аналогія для фронтендера

Метрики — це RUM-дашборд Web Vitals, логи — Sentry breadcrumbs, трейси — вкладка Performance у DevTools (waterfall спанів одного запиту). Fan-out у хвості — як сторінка, що чекає на 30 паралельних fetch перед першим рендером: достатньо одного повільного, щоб LCP став поганим. Звідси Suspense і стрімінг часткового результату. Де ламається: у браузері waterfall видно одразу; у бекенді трейс треба явно прокинути через усі сервіси (traceparent) і семплювати.

🎤
На співбесіді: «Метрики RED на кожен сервіс, USE на БД і черги; алерти на SLO burn rate; OpenTelemetry-трейси з tail sampling (зберігаємо всі помилкові й повільні). Говорю про p99, а не середнє, і пам'ятаю про хвіст при fan-out — тому таймаути з частковими результатами». Для capacity — рахуйте вголос із запасом на AZ.
RED для сервісів, USE для ресурсів. p99, а не середнє; гістограми, а не середні перцентилі. Fan-out = хвіст стає нормою. Утилізація 50–70% + запас на втрату AZ.

09 High availability і disaster recovery

HA — пережити відмову компонента без помітного простою (інстанс, диск, AZ). DR — відновитися після катастрофи (регіон, видалені дані, ransomware, помилковий скрипт). Різні цілі, різні механізми.

Резервування і рівні ізоляції

  • Прибрати single points of failure: щонайменше 2 інстанси кожного компонента, БД з репліками і автоматичним failover, LB у кількох AZ.
  • Multi-AZ (зони в одному регіоні — окремі датацентри з окремим живленням, на відстані, що дає мілісекунди затримки): можна реплікувати синхронно. Дефолт для будь-якого продакшену.
  • Multi-region: десятки–сотні мс між регіонами → реплікація зазвичай асинхронна → при failover можлива втрата останніх записів (RPO > 0). Потрібно для 99.99%+ або вимог DR/регуляторів.
  • Static stability (термін AWS): система продовжує працювати при відмові AZ без дій control plane — ємність уже розгорнута заздалегідь, а не «автоскейлер підніме».

Як уникнути конфліктів в active-active

  • Home region: кожен користувач/тенант «живе» в одному регіоні, його записи йдуть туди; інший регіон читає репліку. Конфліктів немає, failover — переназначення home region.
  • Last-write-wins за таймстемпом — так працюють DynamoDB global tables; просто, але можливі тихі втрати конкурентних записів.
  • CRDT або комутативні операції (лічильники, множини) — злиття без конфліктів.
  • Глобально узгоджена БД (Spanner, CockroachDB) — консенсус через регіони, платимо латентністю запису (див. туторіал 6).

Бекапи — те, що ламається тихо

  • Реплікація ≠ бекап. DELETE FROM users або шифрувальник реплікуються на всі репліки за мілісекунди. Потрібні знімки в часі.
  • PITR (point-in-time recovery): базовий бекап + архів WAL → відновлення на будь-яку секунду (Postgres, RDS).
  • Правило 3-2-1: 3 копії, 2 різні носії, 1 поза основним сайтом; плюс immutable/air-gapped копія проти ransomware і скомпрометованих облікових записів.
  • Тестуйте відновлення. Інцидент GitLab (січень 2017): після випадкового видалення даних з'ясувалося, що кілька механізмів бекапу не працювали; втратили кілька годин даних. Бекап, з якого не відновлювались, — не бекап.
🏭
Як це роблять у реальних системах. Netflix працює active-active у кількох регіонах AWS і регулярно тренує «евакуацію» регіону (Chaos Kong) — переводить увесь трафік з одного регіону в інші. AWS для власних сервісів описує cell-based architecture і static stability як основні прийоми обмеження зони ураження.
Аналогія для фронтендера

Multi-CDN з fallback-доменом для статики — це active-active: якщо один CDN лежить, браузер вантажить із другого. Service worker з offline-кешем — DR для UI: RPO = вік кешу (скільки свіжих даних втратимо), RTO ≈ 0 (сторінка відкривається одразу). Де ламається: статика read-only — конфліктів записів немає; у БД active-active головна складність саме в одночасних записах.

🎤
На співбесіді уточніть: «Які RPO/RTO для бізнесу?» Типова відповідь: «Multi-AZ із синхронною реплікою — RPO ≈ 0 при втраті AZ, автоматичний failover за ~хвилину. Для регіону — warm standby з асинхронною реплікацією, RPO — секунди, RTO — хвилини; щоквартальні DR-навчання. Бекапи з PITR, окремий акаунт, регулярне тестове відновлення».
HA — переживаємо відмову компонента/AZ; DR — катастрофу. RPO — скільки даних, RTO — скільки часу. Реплікація ≠ бекап; невідтестований бекап ≠ бекап.

10 Деплої, feature flags, chaos engineering і реальні інциденти

За даними багатьох постмортемів, значна частина інцидентів починається зі зміни: деплой коду, конфігу, правила, міграції. Тому надійність — це ще й те, як ви випускаєте зміни.

Що ще потрібно для безпечних змін

  • Feature flags: розділяють deploy (код на серверах) і release (фіча ввімкнена для користувачів). Поступове ввімкнення (1% → 100%), таргетинг (лише співробітники), kill switch. Пастка — «флаговий борг»: старі флаги треба прибирати.
  • Dark launch: нова система отримує реальний трафік (дзеркалений або з прихованого UI), але користувач не бачить результату. Facebook у 2008 році описували запуск чату саме так: клієнти навантажували новий бекенд задовго до появи UI. Варіант — shadow traffic: копія запитів іде на нову версію, відповіді порівнюються.
  • Міграції БД expand/contract: (1) додати нову колонку, (2) писати в обидві, (3) backfill, (4) читати з нової, (5) прибрати стару. Кожен крок сумісний і з попередньою, і з наступною версією коду — тоді rolling і відкат безпечні.
  • Автоматичний canary-аналіз: статистичне порівняння метрик canary з baseline (наприклад, Kayenta від Netflix і Google).
  • Конфіг — це теж деплой: зміни конфігурації і правил мають проходити той самий поетапний rollout.

Chaos engineering

Netflix створив Chaos Monkey (приблизно 2011 рік, під час переїзду в AWS): у робочий час він випадково вимикає продакшн-інстанси, змушуючи команди будувати сервіси, що це переживають. Далі з'явились Simian Army, Chaos Kong (евакуація регіону) і платформи для контрольованих експериментів. Принципи (principlesofchaos.org):

  1. Визначте steady state через бізнес-метрику (наприклад, кількість стартів відтворення за секунду).
  2. Сформулюйте гіпотезу: «steady state не зміниться, якщо впаде одна AZ».
  3. Вносьте реальні збої: падіння інстансу, затримки мережі, недоступність залежності, переповнений диск.
  4. Експериментуйте в продакшені, але мінімізуйте зону ураження (малий відсоток трафіку, кнопка «стоп»).
  5. Автоматизуйте і повторюйте регулярно. Ручний варіант — GameDay.

Метастабільна відмова — як нескінченний цикл ре-рендерів: useEffect змінює стан, що знову запускає ефект, і система не повертається в норму сама, навіть якщо початкова зміна була одноразовою. На співбесіді: «Деплой — canary з автоматичним відкатом за SLO-метриками; міграції — expand/contract; ризиковані фічі — за feature flag з kill switch; конфіги проходять той самий rollout. Регулярні GameDay й chaos-експерименти, щоб перевірити failover і fallback». І назвіть метастабільні відмови, якщо питають, «чому система не відновилась сама».
Більшість аварій — від змін. Обмежуйте зону ураження: canary, feature flags, expand/contract, staged rollout конфігів. Тренуйте відмови до того, як вони стануться.

11 Трікі питання

Відповідайте вголос, потім відкривайте.

TRICKYЧому ретраї можуть зробити систему менш надійною?

Ретраї множать навантаження саме тоді, коли система перевантажена: 3 рівні × 3 спроби = 27× на нижній рівень; синхронні ретраї без jitter створюють піки; ретраї неідемпотентних операцій дають дублі; ретраї довші за дедлайн клієнта — марна робота. Плюс вони можуть утримувати систему в метастабільному стані. Ретраї корисні лише при рідкісних випадкових збоях — тому їх обмежують бюджетом (≈10%), роблять на одному рівні і з jitter.

TRICKYТаймаут клієнта 2 с, gateway — 5 с, сервісу — 10 с. Що не так?

Таймаути «перевернуті»: клієнт здається через 2 с і, можливо, ретраїть, а gateway і сервіс ще 3–8 с виконують уже непотрібну роботу; ретрай клієнта додає другу копію. Таймаути мають зменшуватись углиб стеку, а краще — поширювати дедлайн: кожен рівень отримує «скільки лишилось» мінус свій запас.

COREToken bucket vs leaky bucket — у чому реальна різниця?

Обидва обмежують середню швидкість r. Token bucket дозволяє сплеск до b одразу (накопичені токени), тобто вихід нерівномірний — зручно для API, де клієнт робить кілька запитів підряд. Leaky bucket (як черга) віддає назовні рівно r/с, згладжуючи сплески ціною затримки або відкидання — зручно для захисту бекенду, що не витримує піків. У варіанті «leaky bucket as a meter» (як у коді вище) він математично еквівалентний token bucket і відрізняється лише інтерпретацією.

TRICKYRedis із лічильниками rate limiter упав. Що робить API?

Свідомий вибір: fail open (пропускати) з локальним in-memory лімітом на інстанс (грубий ліміт = глобальний / кількість інстансів) — API продовжує працювати, ліміт тимчасово неточний. Fail closed (відмовляти) — лише для операцій, де зловживання дорожче за простій: логін, відправка SMS, платіжні спроби. Обов'язково circuit breaker на виклик Redis, щоб не чекати таймаут на кожен запит.

ADVЧи можна мати SLO 99.99%, якщо БД має SLA 99.95%?

Ні, якщо кожен запит синхронно залежить від цієї БД: доступність ланцюжка ≤ доступності найслабшої ланки. Варіанти: резервування (дві незалежні БД/регіони — з урахуванням кореляції відмов), кеш і деградація (читання з кешу при недоступності БД), асинхронність (записи в чергу і підтвердження пізніше), або чесно знизити SLO для операцій, що вимагають БД. Також SLA провайдера — це про компенсацію, а не гарантія; реальна доступність часто вища, але закладатися на це не можна.

TRICKYЧому середня латентність 50 мс — погана метрика?

Середнє ховає хвіст: 98% запитів по 20 мс і 2% по 1.5 с дають середнє ≈ 50 мс, а кожен 50-й користувач чекає півтори секунди. При fan-out на 100 бекендів хвіст стає нормою. Дивіться на p50/p99/p99.9, будуйте їх з гістограм, і ніколи не усереднюйте перцентилі між хостами.

ADVLiveness probe перевіряє з'єднання з БД. Що може статися?

БД блимнула на 20 с → liveness провалюється на всіх подах → Kubernetes перезапускає всі поди одночасно → холодний старт, порожні кеші, шторм нових з'єднань до БД, яка щойно піднялась → вона знову лягає. Ми перетворили 20-секундний збій на годинний. Liveness має перевіряти лише сам процес; залежності — через readiness (обережно) і circuit breaker.

TRICKYМи робимо blue-green. Як відкотитись, якщо нова версія вже змінила схему БД?

Ніяк швидко — тому так і не роблять. Схема має бути сумісна з обома версіями (expand/contract): спершу «expand»-міграція, сумісна зі старим кодом; потім перемикання; «contract» (видалення старих колонок) — лише коли відкат на стару версію більше не потрібен. Те саме для формату подій у черзі і кешу: нова версія має вміти читати старий формат і навпаки.

COREActive-active у двох регіонах дає 2× ємності?

Ні. Щоб пережити відмову регіону, кожен регіон мусить витримати 100% трафіку, тож при нормальній роботі кожен завантажений ≤ 50%. Active-active дає швидкий failover і близькість до користувачів, а не «подвійну потужність». Те саме з AZ: при 3 зонах — кожна на 50% піку.

Обчислення, вибір механізмів, дебаг. Спершу самі.

Задача 1ЛегкоДев'ятки в хвилинах

SLO 99.95% за 30 днів. Скільки хвилин простою дозволено? А якщо SLO рахується за запитами і сервіс отримує 50 млн запитів на місяць?

(1 − 0.9995) × 30 × 24 × 60 = 0.0005 × 43 200 = 21.6 хв. За запитами: 0.0005 × 50 000 000 = 25 000 невдалих запитів на місяць.

Задача 2ЛегкоЯкий алгоритм?

(a) Публічний API: 100 запитів/хв, клієнти часто роблять 10–20 запитів підряд; (b) логін: не більше 5 спроб за 15 хв на акаунт, строго; (c) безкоштовний тариф: 10 000 запитів на календарну добу; (d) черга відправки в повільний SMS-шлюз, що витримує 50 повідомлень/с.

(a) Token bucket (rate 100/хв, burst ~20). (b) Sliding window log (малий ліміт, потрібна точність; sorted set у Redis). (c) Fixed window (INCR з ключем на дату, EXPIRE) — межа вікна тут і є бізнес-правилом. (d) Leaky bucket / черга з постійною швидкістю виходу 50/с.

Задача 3СередньоЛанцюжок залежностей

Checkout синхронно викликає 5 сервісів, кожен з доступністю 99.95%. Продукт хоче 99.9% для checkout. Чи реально? Що змінити?

  1. 0.9995⁵ ≈ 0.9975 → 99.75% — нижче цілі навіть без власних збоїв checkout.
  2. Прибрати залежності з критичного шляху: рекомендації, аналітику, лояльність — асинхронно або з fallback (відсутність бонусів не має блокувати оплату).
  3. Для обов'язкових залежностей — підвищити їхні SLO (multi-AZ) або резервувати (кеш цін і каталогу).
  4. Якщо лишилось 2 жорсткі залежності по 99.95%: 0.9995² ≈ 0.999 — на межі; потрібен запас для самого checkout → ціль досяжна лише з деградацією.
Задача 4СередньоСкільки інстансів?

Пік — 30 000 QPS. Навантажувальний тест: інстанс тримає 500 QPS при p99 < 150 мс. Цільова утилізація 60%. Сервіс у 3 AZ і має пережити втрату однієї. Скільки інстансів?

Робоча ємність інстансу: 500 × 0.6 = 300 QPS. На пік: 30 000 / 300 = 100 інстансів. Після втрати 1 з 3 AZ мають лишитися 100 → по 50 у кожній з 2 зон → у 3 зонах 150 інстансів (по 50). Додайте запас на rolling deploy (наприклад, maxSurge) і на зростання.

Задача 5СередньоМноження ретраїв

4 рівні (mobile → BFF → service → DB client), кожен робить до 3 спроб. БД почала таймаутити. У скільки разів зросте навантаження на БД? Як виправити, не вимикаючи ретраї повністю?

До 3⁴ = 81× на один запит користувача. Виправлення: ретраї лише на одному рівні (наприклад, у service, найближчому до БД) — інші рівні не ретраять або ретраять лише помилки з'єднання до відправки запиту; retry budget 10% на клієнт; дедлайн, що поширюється (немає сенсу ретраїти після його спливу); circuit breaker на БД-клієнті; сигнал «overloaded — не ретраїти» у відповіді.

Задача 6СередньоBurn rate

SLO 99.9% за 30 днів, 10 млн запитів на добу рівномірно. Інцидент: 3 години з 2% помилок. Яку частку бюджету спалено? Який burn rate? Чи мав спрацювати пейдж за правилом «2% бюджету за годину»?

  1. Бюджет: 0.001 × 300 млн = 300 000 невдалих запитів.
  2. Інцидент: 10 млн / 24 ≈ 417 000 запитів/год × 3 год × 0.02 ≈ 25 000 помилок ≈ 8.3% бюджету.
  3. Burn rate = частка помилок / (1 − SLO) = 0.02 / 0.001 = 20.
  4. Поріг пейджа за 1 год — burn rate 14.4; 20 > 14.4 → пейдж мав спрацювати приблизно в першу годину (за годину згоряє 20/720 ≈ 2.8% бюджету).
Задача 7СкладноRate limiter для 10 млн користувачів

API з 10 млн активних користувачів, пік 1 млн QPS через 200 gateway-інстансів. Ліміт: 100 запитів/хв на користувача + 10 000/хв на тенант. Спроектуйте: алгоритм, сховище, оцінка пам'яті й навантаження, поведінка при відмовах.

  1. Алгоритм: token bucket (capacity 100, rate 100/60 токена/с) для користувача і окремий для тенанта; обидва в одному Lua-скрипті, якщо ключі в одному слоті, або дві перевірки (спершу дешевша/строгіша).
  2. Пам'ять: ключ-хеш із двома полями — порядку 100–200 байт з накладними витратами Redis → 10 млн × ~150 B ≈ 1.5 GB (+ тенанти — дрібниця). TTL прибирає неактивних.
  3. Навантаження: 1 млн EVALSHA/с (×2, якщо дві перевірки). Один Redis-шард обробляє порядку 100 тис. простих операцій/с (залежить від заліза й скрипта — міряти) → ~10–20 шардів з репліками.
  4. Оптимізація: «позичати» токени партіями в локальний бакет gateway для гарячих клієнтів; для тенант-ліміту — локальні лічильники з синхронізацією раз на секунду (наближено).
  5. Відмови: circuit breaker на Redis, fail open з локальним лімітом (1 млн / 200 → грубий ліміт на інстанс); для логіну/SMS — fail closed. Відповідь 429 + Retry-After; метрики відхилень за тенантами.
Задача 8СкладноДебаг: 30 секунд збою → 2 години простою

Primary БД перезапустився за 30 с. Після цього API лежав 2 години, хоча БД була здорова. Відомо: клієнти ретраять кожну секунду без jitter до 10 разів; кеш Redis має TTL 5 хв і при промаху йде в БД; liveness-проба перевіряє БД; автоскейлер додає інстанси при CPU > 70%. Поясніть і виправте.

  1. Liveness → БД: усі поди перезапустились одночасно → холодні процеси, шторм нових з'єднань до БД.
  2. Ретраї без jitter: синхронні хвилі, ×10 навантаження, без бюджету.
  3. Кеш: за 30 с значення не протухли масово, але рестарт подів скинув локальні кеші, і за кілька хвилин після відновлення синхронно спливли TTL → stampede на БД.
  4. Автоскейлер: більше інстансів → більше з'єднань і ретраїв до вже перевантаженої БД (позитивний зворотний зв'язок).
  5. Разом — метастабільний стан: навантаження з ретраїв і промахів кешу тримає БД перевантаженою без початкової причини.
  6. Виправлення: liveness без залежностей; backoff + jitter + retry budget; request coalescing / stale-while-revalidate для кешу і jitter у TTL; пул з'єднань з лімітом; load shedding у API (швидкий 503); автоскейлінг з урахуванням ємності БД; runbook «скинути навантаження» (тимчасово відкидати частину трафіку, щоб вийти з метастабільного стану).
Задача 9СередньоБезпечний POST /payments

Мобільний клієнт відправляє платіж, отримує таймаут через 10 с і ретраїть. Іноді гроші списуються двічі. Спроектуйте виправлення на клієнті і сервері.

  1. Клієнт генерує Idempotency-Key (UUID) при натисканні «Оплатити» і відправляє з усіма повторами (backoff + jitter, ≤ 3 спроби).
  2. Сервер: INSERT INTO idempotency_keys(key, user_id, request_hash, status='in_progress') з унікальним ключем; конфлікт + статус «done» → повернути збережену відповідь; «in_progress» → 409, клієнт спробує пізніше; інший request_hash з тим самим ключем → 422.
  3. Виклик платіжного провайдера — з тим самим ключем (провайдери на кшталт Stripe приймають idempotency key).
  4. Збереження відповіді й зміна статусу — в одній транзакції з записом платежу. TTL ключів ≥ 24 год.
  5. Таймаут клієнта ≥ серверний дедлайн + запас, щоб не ретраїти запити, які ще виконуються.
Задача 10СкладноDR-план для сервісу платежів

Бізнес: «втрата підтверджених платежів неприпустима; простій до 15 хв при втраті регіону прийнятний; при втраті AZ — до 1 хв». Запропонуйте архітектуру даних і процеси.

  1. AZ: БД з синхронною реплікою в іншій AZ (RPO = 0) і автоматичним failover (~30–60 с); застосунок у 3 AZ зі static stability (ємність на втрату однієї зони).
  2. Регіон, RPO = 0: асинхронна реплікація дає RPO > 0, тому або синхронний коміт у другий регіон (кворум через регіони: +латентність на кожен запис, Spanner/CockroachDB-стиль), або підтверджувати платіж користувачу лише після реплікації журналу в другий регіон.
  3. RTO 15 хв: warm standby у другому регіоні (зменшена працююча копія + автоскейлінг), автоматизований runbook перемикання DNS/трафіку; DNS TTL короткий.
  4. Бекапи: PITR, копії в окремому акаунті/регіоні, immutable; щомісячне тестове відновлення.
  5. Процеси: DR-навчання щокварталу (переключення регіону в робочий час), звірка (reconciliation) з платіжним провайдером після failover — він є другим джерелом правди про платежі.
