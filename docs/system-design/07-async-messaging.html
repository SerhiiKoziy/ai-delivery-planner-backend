Частина I · Навіщо і які бувають брокери

01 Навіщо асинхронність і що питають на співбесіді

Майже кожна задача рівня middle+/senior (стрічка, чат, оплата, відео, нотифікації) у якийсь момент вимагає сказати «тут я ставлю чергу». Інтерв'юер одразу перевірить: яку саме, з якими гарантіями, що буде з дублями й порядком, як не втратити подію.

Три причини поставити брокер між сервісами

1. Розчеплення (decoupling)

Продюсер не знає, хто і скільки споживачів читає подію. Додати новий сервіс (аналітика, антифрод) = підписатися на топік, без зміни коду продюсера. Падіння споживача не валить продюсера.

2. Буферизація піків

Черга — це амортизатор: на Black Friday приходить 10× трафіку, воркери обробляють із постійною швидкістю, хвіст «розсмоктується» за хвилини. Без черги піки б'ють напряму в БД.

3. Латентність для користувача

Все, що не потрібно для відповіді (email, ресайз картинки, перерахунок рекомендацій), виноситься з критичного шляху. API відповідає 202 Accepted за десятки мілісекунд.

4. Надійність і повтори

Брокер зберігає повідомлення, поки споживач не підтвердить обробку. Тимчасова помилка → повтор пізніше, а не 500 користувачу.

(0.999⁴ ≈ 0.996 — «нуль кома дев'ять дев'ять дев'ять у четвертому степені приблизно дорівнює…»: якщо кожен із 4 послідовних сервісів доступний 99.9% часу, весь ланцюжок — лише ≈ 99.6%.)

Ціна асинхронності (назвіть її самі — це сигнал сеньйорності)

  • Eventual consistency: користувач створив замовлення, а в «Мої замовлення» (інший сервіс) його ще нема. Треба UX (оптимістичний UI) або read-your-writes.
  • Дублікати і зміна порядку — нормальний стан, а не баг брокера.
  • Складніше дебажити: немає одного стек-трейсу; потрібні correlation id, distributed tracing, моніторинг lag.
  • Новий компонент зі своєю експлуатацією (Kafka-кластер, моніторинг, апгрейди, квоти).
  • Неможливо повернути результат у тій самій відповіді — потрібні polling, WebSocket/SSE або webhook.
Аналогія для фронтендера

Синхронний ланцюжок — це await a(); await b(); await c(); у обробнику кліку: UI «висить», поки не виконаються всі. Асинхронна черга — як postMessage у Web Worker або navigator.sendBeacon для аналітики: ви «кинули» повідомлення і одразу повернули керування користувачу. Де аналогія ламається: браузерні черги живуть у пам'яті однієї вкладки й зникають при закритті; брокер — окремий довговічний сервіс із реплікацією, і повідомлення переживає рестарт будь-кого.

🎤
На співбесіді: не кажіть просто «додам Kafka». Скажіть: «Запис замовлення синхронний і транзакційний; побічні ефекти (email, аналітика, склад) — асинхронно через лог подій з ключем order_id. Доставка at-least-once, тому споживачі ідемпотентні; подію публікую через transactional outbox, щоб не було dual write». Одне речення — і ви закрили п'ять follow-up питань.
🚩
Red flags: черга «бо так модно» там, де потрібна синхронна відповідь (перевірка балансу перед оплатою); «Kafka гарантує exactly-once, тому дублів не буде»; «спочатку пишу в БД, потім у Kafka» без згадки про збій між ними.
Брокер = розчеплення + буфер + довговічність. Платимо eventual consistency, дублями та складнішою експлуатацією.

Ключові відмінності, які варто проговорити

Queue (smart broker, dumb consumer)

  • Брокер сам відстежує стан кожного повідомлення (in-flight, acked, redelivered).
  • Можна ack/nack поштучно, пріоритети, delay, per-message TTL.
  • Ідеально для задач («зроби ресайз фото»): неважливо, хто виконає, важливо — один раз і з ретраями.
  • Нема replay: прочитали — забули. Новий споживач не побачить історії.

Log (dumb broker, smart consumer)

  • Брокер лише дописує в кінець і віддає діапазони; стан читання — один offset на партицію для групи.
  • Послідовний I/O диска + zero-copy → дуже висока пропускна здатність.
  • Ідеально для фактів/подій («замовлення створено»), які потрібні багатьом і, можливо, повторно.
  • Нема поштучного ack: одне «отруйне» повідомлення блокує партицію (head-of-line blocking).

RabbitMQ за 1 хвилину

Продюсер шле в exchange, а не в чергу. Exchange за типом і routing key розкладає копії по чергах: direct (точний ключ), topic (шаблони order.*.eu), fanout (усім), headers. Споживач бере з черги з prefetch (скільки unacked повідомлень може тримати — це і є backpressure). Для надійності — quorum queues (реплікація на Raft) замість класичних mirrored queues. Для лог-подібних сценаріїв з'явились RabbitMQ Streams.

SNS + SQS fan-out — класичний AWS-патерн

Один SNS-топік «OrderCreated» → кілька SQS-черг (email, склад, аналітика), у кожної — свої воркери, свій DLQ, свій темп. Це «pub/sub з буферами» — функціонально схоже на Kafka з кількома consumer groups, але без replay і без довгого зберігання.

Аналогія для фронтендера

Queue — як черга задач event loop: кожен колбек виконується рівно один раз, і після виконання його вже немає. Pub/Sub — як window.dispatchEvent(new CustomEvent('cart:updated')): всі поточні слухачі отримують подію, а компонент, який змонтувався пізніше, її не побачить. Log — як журнал дій Redux DevTools: кожна дія записана з номером, і будь-хто може «перемотати» й відтворити стан із нуля. Де ламається: Redux-лог необмежений і в пам'яті; Kafka-лог обмежений retention і розкладений по партиціях без глобального порядку.

🎤
На співбесіді: обирайте за питанням «це задача чи факт?». Задача (згенерувати PDF, надіслати email) → черга (SQS/RabbitMQ). Факт, який цікавий багатьом і може знадобитись повторно (OrderCreated, location update, клік) → лог (Kafka/Kinesis). Потрібно миттєво сповістити всі інстанси й не страшно втратити → Redis Pub/Sub.
⚠️
Типова помилка: використовувати Redis Pub/Sub як надійну чергу. Якщо підписник перепідключається, все надіслане в цей момент — втрачено. Для надійності — Redis Streams (consumer groups, XACK, pending entries list) або справжній брокер.
Queue — «зроби один раз». Log — «ось що сталося, читайте скільки завгодно». Pub/Sub — «гей, усі, хто зараз слухає».

03 Kafka зсередини: мінімум, який треба знати на співбесіді

Topic, partition, offset, consumer group, rebalancing, retention, replication/ISR, acks. Цих восьми слів достатньо, щоб відповісти на 90% питань про Kafka — якщо ви розумієте, як вони пов'язані.

Topic → partitions → offsets

Topic — логічна назва потоку («orders»). Фізично він розрізаний на partitions — кожна партиція є окремим append-only логом на диску одного брокера (лідера) з копіями на інших. Кожне повідомлення в партиції має offset — монотонно зростаючий номер. Порядок існує лише всередині партиції.

Consumer groups і паралелізм

  • У межах групи кожна партиція призначена рівно одному консьюмеру. Один консьюмер може мати кілька партицій.
  • Максимальний паралелізм групи = кількість партицій. 12 партицій і 20 консьюмерів → 8 консьюмерів простоюють. Це найчастіше трікі-питання.
  • Щоб «додати читача» (новий сервіс) — нова група, а не новий консьюмер в існуючій групі.
  • Консьюмер періодично комітить offset — «я обробив усе до N». Після рестарту читання продовжується з закоміченого offset. Що саме і коли комітити — визначає семантику доставки (розділ 5).

Rebalancing — болюча частина

Коли консьюмер приєднується, падає або не надсилає heartbeat / не викликає poll() довше за max.poll.interval.ms, координатор групи перерозподіляє партиції.

Класичний інцидент: обробка одного батчу триває довше за max.poll.interval.ms (наприклад, повільний HTTP-виклик) → консьюмера викидають із групи → ребаланс → партицію отримує інший консьюмер і обробляє той самий батч заново → він теж не встигає → «rebalance storm» і нескінченні дублі. Лікування: менший max.poll.records, таймаути на зовнішні виклики, винесення важкої роботи в окремий пул із паузою партиції (pause()/resume()).

Retention і compaction

  • Time/size retention (retention.ms, за замовчуванням 7 днів): старі сегменти видаляються цілими файлами, незалежно від того, чи хтось їх прочитав. Kafka не «видаляє після читання».
  • Log compaction (cleanup.policy=compact): для кожного ключа лишається щонайменше останнє значення. Повідомлення з value=null — tombstone (видалення ключа). Так Kafka стає «таблицею змін»: можна відновити повний поточний стан, прочитавши компактований топік з початку (KTable у Kafka Streams, __consumer_offsets, CDC-топіки).
  • Tiered storage (KIP-405): старі сегменти вивантажуються в об'єктне сховище (S3), локально лишається «гарячий» хвіст. Робить довгий retention дешевим.

Реплікація, ISR і acks

(LEO — log end offset, «наступний offset, який буде записано»; HW — high watermark, «поріг закоміченості»; |ISR| — «кількість реплік в ISR».)

  • ISR (in-sync replicas) — репліки, що встигають за лідером (не відстають довше за replica.lag.time.max.ms). Новим лідером може стати лише репліка з ISR (якщо unclean.leader.election.enable=false — дефолт; інакше можлива втрата даних заради доступності — живий приклад CAP-вибору).
  • Надійний профіль: replication.factor=3, min.insync.replicas=2, acks=all. Витримує втрату одного брокера без втрати записів і без зупинки запису. Втрата двох → запис зупиняється (обираємо consistency), читання ще працює.
  • Метадані кластера: раніше ZooKeeper, тепер KRaft (вбудований Raft-кворум контролерів); у Kafka 4.0 ZooKeeper прибрали повністю.

Чому Kafka така швидка (часте питання)

  1. Послідовний append на диск замість випадкового I/O; читання теж послідовне.
  2. Page cache ОС замість власного кешу в JVM-хіпі: свіжі дані читаються з пам'яті.
  3. Zero-copy (sendfile): байти йдуть з page cache в сокет без копіювання в user space (не працює з TLS, бо треба шифрувати).
  4. Батчинг і стиснення на продюсері; брокер зберігає батч як є.
  5. Партиціонування: горизонтальне масштабування запису й читання по брокерах.
📏
Скільки партицій? Груба формула: partitions ≥ max(T / p, T / c), де T — цільова пропускна, p — пропускна на партицію з боку продюсера, c — з боку одного консьюмера. Наприклад, 100 MB/s при ~10 MB/s на консьюмер → щонайменше 10, беруть із запасом (12–24). Кількість партицій можна збільшити, але не зменшити, а збільшення змінює мапінг key → partition (порядок для ключа ламається на перехідний період). Тому закладають запас одразу. Занадто багато партицій — більше файлів, довші вибори лідерів, більше пам'яті на клієнтах.
Аналогія для фронтендера

Партиції — як кілька паралельних Web Workers, між якими ви «шардуєте» задачі за userId % N: усі задачі одного користувача потрапляють в один воркер і виконуються по черзі, а різні користувачі — паралельно. Consumer group — пул воркерів одного «застосунку»; друга група — інша вкладка, яка отримує ті самі повідомлення через BroadcastChannel, але читає у своєму темпі. Де ламається: воркери не зберігають «offset» і не переживають перезавантаження сторінки.

🎤
На співбесіді: коли малюєте Kafka, підпишіть ключ партиціонування, приблизну кількість партицій і хто є consumer group. Назвіть «RF=3, min.insync=2, acks=all, idempotent producer» як надійний дефолт. Скажіть, що паралелізм обмежений числом партицій, і що rebalancing — джерело дублів, тому обробка ідемпотентна.
Порядок — у партиції; паралелізм — ≤ партицій; надійність — RF=3 + min.insync=2 + acks=all; Kafka нічого не видаляє після читання.

04 Порядок повідомлень і вибір ключа

«Глобальний порядок» у розподіленому брокері коштує всього паралелізму. Тому питання не «чи є порядок», а «порядок чого саме нам потрібен».

Пастки

  • Hot key / hot partition. Ключ tenant_id, і один клієнт — 40% трафіку → одна партиція перевантажена, решта простоюють. Рішення: дрібніший ключ (tenant_id:order_id), якщо порядок потрібен лише в межах замовлення; «солення» ключа для read-only агрегацій (з подальшим злиттям).
  • Ключ null → sticky/round-robin розподіл: максимум рівномірності, нуль гарантій порядку.
  • Збільшення кількості партицій змінює hash % N → нові події ключа йдуть в іншу партицію, поки старі ще в черзі старої. Рішення: закладати запас партицій, або «drain then switch» (спочатку дочитати), або новий топік із міграцією.
  • Ретраї ламають порядок, якщо продюсер не ідемпотентний і кілька запитів in-flight: батч 1 впав, батч 2 записався, ретрай батчу 1 — після 2. Idempotent producer це виправляє.
  • Retry topic ламає порядок у консьюмері: повідомлення A2 пішло в retry-топік, а A3 обробилось одразу. Якщо порядок критичний — блокуємо ключ (або всю партицію) до успіху A2, або зберігаємо «паркінг» для ключа.
  • Паралельна обробка всередині консьюмера (thread pool на батч) втрачає порядок, якщо не групувати за ключем: «per-key executor».
🧭
Коли порядок не потрібен зовсім: якщо події несуть повний стан + версію ({"order_id":7,"status":"PAID","version":5}), споживач просто ігнорує подію з version ≤ current. Порядок доставки стає неважливим — це найбільш стійкий дизайн. Так само роблять з таймстемпами «last-write-wins», але пам'ятайте про розбіжність годинників (див. туторіал 6).
Аналогія для фронтендера

Race condition у пошуку з автодоповненням: запит «re» відповів пізніше за «react», і список показує результати для «re». Класичне рішення — ігнорувати відповіді зі старим requestId (як AbortController або порівняння лічильника в React Query). Це той самий «version check» замість гарантії порядку доставки. Де ламається: у браузері є один «консьюмер» і локальний лічильник; у розподіленій системі версію має видавати власник даних (БД/агрегат), а не годинник клієнта.

🎤
На співбесіді: на питання «а як гарантувати порядок?» відповідайте трьома реченнями: (1) глобальний порядок не потрібен і вбив би масштаб; (2) порядок потрібен у межах сутності → ключ = id сутності, одна партиція, один консьюмер; (3) для стійкості — версії в подіях, щоб консьюмер міг відкинути застарілі.
Ключ = одиниця порядку. Багато рівномірних ключів = масштаб. Версія в події = незалежність від порядку.

05 Семантика доставки: at-most-once, at-least-once, exactly-once

Найпопулярніше трікі-питання з цієї теми. Відповідь сеньйора: «exactly-once доставка через мережу неможлива; досяжний exactly-once ефект — at-least-once плюс ідемпотентність або атомарний коміт результату разом з offset».

Що насправді означає «exactly-once» у Kafka

  1. Idempotent producer (enable.idempotence=true, дефолт у сучасних клієнтах): кожен продюсер має producer id, кожен батч — sequence number на партицію; брокер відкидає повтор того самого батчу. Прибирає дублі від ретраїв продюсера в одну партицію.
  2. Транзакції (transactional.id): продюсер атомарно пише в кілька партицій і комітить offsets вхідного топіку (sendOffsetsToTransaction). Або все стає видимим, або нічого.
  3. Консьюмери з isolation.level=read_committed не бачать повідомлень з незавершених/скасованих транзакцій.
  4. Разом це дає exactly-once для ланцюжка Kafka → обробка → Kafka (Kafka Streams: processing.guarantee=exactly_once_v2).
🚩
Чого Kafka EOS НЕ дає: якщо обробник надсилає email, викликає Stripe або пише в Postgres — ці побічні ефекти поза транзакцією Kafka. Падіння після email, але до коміту → email піде ще раз. Тут знову потрібна ідемпотентність на стороні ефекту (idempotency key у Stripe, дедуп-таблиця в Postgres) або збереження offset у тій же БД-транзакції, що й результат (тоді при старті консьюмер робить seek() до offset з БД).
📨
А в черг? SQS Standard — at-least-once (зрідка дублі навіть без збоїв). SQS FIFO має дедуплікацію за MessageDeduplicationId у 5-хвилинному вікні — це дедуп на вході в чергу, але обробник, що впав після ефекту, все одно отримає повідомлення вдруге після visibility timeout. RabbitMQ: ack після обробки = at-least-once; повторна доставка позначається redelivered=true.
Аналогія для фронтендера

Користувач натиснув «Оплатити», мережа «підвисла», fetch впав по таймауту. Платіж пройшов чи ні? Ви не знаєте — це і є неможливість exactly-once доставки (проблема двох генералів). Правильний фронтенд генерує Idempotency-Key при відкритті форми і повторює запит з тим самим ключем — бекенд поверне той самий результат. Exactly-once ефект через at-least-once + ключ. Де ламається: у браузері ретраїть одна вкладка; у брокері ретраять інфраструктура, ребаланс, рестарти — дублі приходять звідусіль.

🎤
На співбесіді: «Я проектую на at-least-once, бо це дефолт і найпростіша надійна модель. Ефект робимо exactly-once через ідемпотентність: event_id + дедуп у тій же транзакції. Kafka transactions використаю лише для Kafka-to-Kafka пайплайнів (агрегації в Kafka Streams), і чесно скажу, що на зовнішні сайд-ефекти вони не поширюються».
Exactly-once delivery — міф; exactly-once effect — інженерія: at-least-once + ідемпотентність.

06 Ідемпотентні споживачі

Ідемпотентна операція — така, що повторне виконання з тим самим входом не змінює результат: f(f(x)) = f(x). Це головний інструмент, що робить at-least-once безпечним.

П'ять технік (від найпростішої)

  1. Природна ідемпотентність. SET status='SHIPPED' замість «перемкнути статус»; balance = 150 замість balance += 50; DELETE WHERE id=…. Абсолютні значення замість дельт.
  2. Upsert з ключем події. INSERT … ON CONFLICT (event_id) DO NOTHING — для «записати факт» (лайк, платіж, рядок у ledger).
  3. Умовний апдейт (state machine guard). UPDATE orders SET status='PAID' WHERE id=? AND status='PENDING' — повтор не знайде рядок у потрібному стані.
  4. Перевірка версії. UPDATE … SET …, version=? WHERE id=? AND version < ? — застарілі/повторні події ігноруються; заодно лікує зміну порядку.
  5. Дедуп-таблиця (inbox). processed_events(event_id PK) вставляється в тій самій транзакції, що й бізнес-ефект. Дубль → порушення PK → вся транзакція відкочується.
idempotent_consumer.py — перевірено з python3 (sqlite3 у пам'яті)
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE processed_events (event_id TEXT PRIMARY KEY, processed_at TEXT);
CREATE TABLE balances (user_id TEXT PRIMARY KEY, amount INTEGER NOT NULL);
INSERT INTO balances VALUES ('alice', 0);
""")

def handle(event: dict) -> str:
    """Ідемпотентний обробник: дедуп + ефект в ОДНІЙ транзакції."""
    try:
        with db:
            db.execute("INSERT INTO processed_events VALUES (?, datetime('now'))",
                       (event["event_id"],))          # PK не дасть вставити двічі
            db.execute("UPDATE balances SET amount = amount + ? WHERE user_id = ?",
                       (event["amount"], event["user_id"]))
        return "applied"
    except sqlite3.IntegrityError:
        return "duplicate-skipped"                     # транзакцію відкочено цілком

events = [
    {"event_id": "e1", "user_id": "alice", "amount": 100},
    {"event_id": "e2", "user_id": "alice", "amount": 50},
    {"event_id": "e1", "user_id": "alice", "amount": 100},  # redelivery!
    {"event_id": "e2", "user_id": "alice", "amount": 50},   # redelivery!
]
for e in events:
    print(e["event_id"], handle(e))
print("balance:", db.execute("SELECT amount FROM balances WHERE user_id='alice'").fetchone()[0])

# e1 applied
# e2 applied
# e1 duplicate-skipped
# e2 duplicate-skipped
# balance: 150

Зверніть увагу: amount = amount + ? сам по собі не ідемпотентний (дельта), але дедуп-таблиця в тій самій транзакції робить ідемпотентним весь обробник.

Практичні деталі, про які питають

  • Звідки event_id? Генерує продюсер (UUID/ULID) у момент створення факту і зберігає разом із подією (outbox). Не генеруйте його в релеї чи консьюмері — тоді у дубля буде інший id. Для Kafka можна використовувати (topic, partition, offset), але це ламається, якщо продюсер сам задублював запис.
  • Скільки зберігати дедуп-записи? Довше, ніж максимальне вікно можливого дубля (retention топіку + час можливого replay). Stripe, за їхньою документацією, зберігає idempotency keys щонайменше 24 години. Старі записи чистять TTL/партиціями за датою.
  • Ефект у зовнішній системі (email-провайдер, платіжний шлюз) — передайте event_id як idempotency key далі вниз. Якщо зовнішня система ключів не підтримує — запишіть «намір» у свою БД зі статусом і робіть звірку (reconciliation).
  • Дедуп у Redis (SET key NX EX 86400) — дешево й швидко, але не атомарно з ефектом у БД. Годиться як оптимізація («відсікти 99% дублів»), а не як гарантія.
  • Дедуп ≠ впорядкування. Дедуп-таблиця не врятує від «Shipped» раніше за «Paid» — для цього версії/state machine guard.
Аналогія для фронтендера

React 18 StrictMode у dev-режимі навмисно викликає ефекти двічі (mount → unmount → mount), щоб ви писали їх ідемпотентно: підписка з відпискою в cleanup, fetch з ігноруванням застарілої відповіді. Брокер повідомлень — це «StrictMode на продакшені», який дублює не навмисно, а через збої. Де ламається: React дублює передбачувано й одразу; брокер — через хвилини чи години (replay), тому дедуп-пам'ять мусить жити довго й бути персистентною.

🎤
На співбесіді: щойно ви сказали «черга», додайте: «консьюмер ідемпотентний: кожна подія має event_id від продюсера; дедуп-таблиця пишеться в тій самій транзакції, що й ефект; для зовнішніх викликів передаю idempotency key». Це закриває питання про дублі від ребалансу, ретраїв, visibility timeout і replay одним махом.
Дублі прийдуть обов'язково. Ідемпотентність = event_id від продюсера + дедуп/умова в тій же транзакції, що й ефект.

07 Dual write, transactional outbox і CDC

Найважливіший патерн цього туторіалу. Його згадують у кожному сильному інтерв'ю: «як ви гарантуєте, що подія буде опублікована, якщо транзакція закомітилась — і не буде, якщо ні?»

Проблема: запис у дві системи без спільної транзакції

Варіанти «розподілена транзакція (2PC/XA) між БД і брокером» на практиці відпадають: Kafka не є XA-ресурсом, а 2PC блокує ресурси і залежить від координатора (див. туторіал 6).

Рішення: transactional outbox

Подія записується в ту саму БД і в ту саму локальну транзакцію, що й бізнес-дані, — у таблицю outbox. Окремий процес (relay) читає outbox і публікує в брокер. Атомарність дає БД; доставку «рано чи пізно» дає релей з ретраями.

Як виглядає по кроках (і де можуть бути дублі)

outbox_relay.py — скетч, перевірено з python3 (sqlite3 + фейковий брокер)
import sqlite3, json, uuid

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE orders (id TEXT PRIMARY KEY, user_id TEXT, total INTEGER, status TEXT);
CREATE TABLE outbox (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    event_id    TEXT UNIQUE,
    aggregate   TEXT,
    key         TEXT,
    type        TEXT,
    payload     TEXT,
    published   INTEGER DEFAULT 0
);
""")

def create_order(user_id: str, total: int) -> str:
    order_id = str(uuid.uuid4())
    with db:  # ОДНА локальна транзакція: і бізнес-дані, і подія
        db.execute("INSERT INTO orders VALUES (?, ?, ?, 'CREATED')",
                   (order_id, user_id, total))
        db.execute(
            "INSERT INTO outbox (event_id, aggregate, key, type, payload) "
            "VALUES (?, 'order', ?, 'OrderCreated', ?)",
            (str(uuid.uuid4()), order_id,
             json.dumps({"order_id": order_id, "total": total})))
    return order_id

class FakeBroker:
    def __init__(self, fail_every=0):
        self.log, self.calls, self.fail_every = [], 0, fail_every
    def send(self, topic, key, value, headers):
        self.calls += 1
        if self.fail_every and self.calls % self.fail_every == 0:
            raise ConnectionError("broker timeout")
        self.log.append((topic, key, headers["event_id"]))

def relay_once(broker, batch=100):
    """Polling publisher: читає неопубліковані рядки по порядку id."""
    rows = db.execute("SELECT id, event_id, key, type, payload FROM outbox "
                      "WHERE published = 0 ORDER BY id LIMIT ?", (batch,)).fetchall()
    sent = 0
    for row_id, event_id, key, typ, payload in rows:
        try:
            broker.send("orders", key, payload, {"event_id": event_id, "type": typ})
        except ConnectionError:
            break                     # зупиняємось, щоб не зламати порядок
        # якщо впадемо ТУТ (після send, до UPDATE) - подію відправлять ще раз:
        # це at-least-once, тому споживач має бути ідемпотентним
        with db:
            db.execute("UPDATE outbox SET published = 1 WHERE id = ?", (row_id,))
        sent += 1
    return sent

for i in range(5):
    create_order(f"u{i}", 100 * (i + 1))

broker = FakeBroker(fail_every=3)
print("pass 1 sent:", relay_once(broker))
print("pass 2 sent:", relay_once(broker))
print("pass 3 sent:", relay_once(broker))
print("in broker:", len(broker.log),
      "| pending:", db.execute("SELECT COUNT(*) FROM outbox WHERE published=0").fetchone()[0])

# pass 1 sent: 2
# pass 2 sent: 2
# pass 3 sent: 1
# in broker: 5 | pending: 0

Polling relay vs CDC (Debezium)

Polling relay

  • Простий: SQL-запит у циклі, жодної нової інфраструктури.
  • Навантажує БД запитами; латентність = інтервал опитування (100 мс – 1 с).
  • Кілька інстансів релея → або один активний (leader election / advisory lock), або FOR UPDATE SKIP LOCKED з розбиттям за ключем, інакше ламається порядок.
  • Пастка: ORDER BY id з автоінкрементом — транзакція з меншим id може закомітитись пізніше, і релей її «перестрибне», якщо відстежує «останній id». Безпечніше — прапорець published, як у коді вище.

CDC (Change Data Capture)

  • Читає журнал транзакцій (Postgres logical decoding / replication slot, MySQL binlog): лише закомічені зміни, в порядку коміту.
  • Майже нульове навантаження запитами, латентність — десятки мс.
  • Debezium має «Outbox Event Router» SMT: бере рядок outbox і публікує в топік за полем aggregate з ключем aggregate_id.
  • Пастка: якщо Debezium лежить, replication slot утримує WAL → диск Postgres може заповнитись. Потрібен моніторинг лагу слота.

Чому outbox, а не CDC прямо з бізнес-таблиць?

CDC з таблиці orders працює, але публікує внутрішню схему як публічний контракт: перейменували колонку → зламали всіх споживачів. Outbox — це явний, версіонований контракт подій («OrderCreated v2»), незалежний від структури таблиць. CDC з бізнес-таблиць добрий для внутрішніх задач: реплікація в пошук/сховище даних, інвалідація кешу.

Альтернативи

  • Listen to yourself: сервіс пише лише в Kafka, а власну БД оновлює, споживаючи свою ж подію. Атомарність є (один запис), але сервіс не може синхронно перевірити інваріанти (унікальність email) — read-your-writes ламається.
  • Event sourcing: подія і є записом стану (розділ 10) — dual write зникає за побудовою.
  • Inbox pattern (дзеркальний до outbox): консьюмер спочатку записує вхідне повідомлення в таблицю inbox (з дедупом), а обробляє вже з неї — зручно, коли обробка довга.
🏭
Як це роблять у реальних системах. Shopify описували в інженерному блозі побудову CDC-платформи на Debezium + Kafka Connect для свого шардованого MySQL-моноліту («Capturing Every Change From Shopify's Sharded Monolith»). Debezium (Red Hat) став де-факто стандартом CDC для Postgres/MySQL/MongoDB. Патерн outbox описаний у microservices.io (Chris Richardson) і в документації Debezium. У AWS аналог — DynamoDB Streams: зміни таблиці як потік подій.
Аналогія для фронтендера

Offline-first застосунок (PWA): користувач редагує нотатку без мережі. Ви в одній транзакції IndexedDB оновлюєте нотатку і додаєте запис у store pendingSync. Service worker через Background Sync пізніше відправляє pending-записи на сервер і видаляє їх після 200 OK. Якщо вкладку закрили між 200 OK і видаленням — запит піде вдруге, тому сервер має приймати idempotency key. Це один в один transactional outbox + relay + ідемпотентний консьюмер. Де ламається: у браузері «брокер» — це HTTP до вашого ж бекенду; у бекенді релей і консьюмери — окремі процеси з власними збоями.

🎤
На співбесіді: якщо в дизайні є «записати в БД і повідомити інших» — сам проговоріть dual write і outbox, не чекаючи питання. Формула: «бізнес-рядок і рядок outbox в одній транзакції; Debezium читає WAL і публікує в Kafka з ключем aggregate_id; at-least-once, консьюмери дедуплікують за event_id; моніторю лаг replication slot».
🚩
Red flags: «пишу в БД, а потім у Kafka в try/catch з ретраєм» (процес може померти); «використаю 2PC між Postgres і Kafka»; «подію публікую в after_commit хуці ORM» (той самий dual write, просто красивіше).
Дані й подія — в одній локальній транзакції (outbox). Доставка в брокер — окремим процесом (CDC/polling), at-least-once.

08 Коли щось іде не так: ретраї, DLQ, poison messages, backpressure, lag, visibility timeout

Happy path малює кожен. Сеньйора відрізняє відповідь на «а що, якщо обробка падає?» і «а що, якщо консьюмери не встигають?».

Класифікуйте помилки

Transient (варто ретраїти)

  • Таймаут, 503, connection reset, deadlock, throttling 429.
  • Ретрай з exponential backoff + jitter (детально — туторіал 8).
  • Обмежена кількість спроб, потім — DLQ.

Permanent (ретрай не допоможе)

  • Невалідний JSON, порушення схеми, «замовлення не існує», 400/422.
  • Одразу в DLQ (або «parking lot») з причиною.
  • Ретраї тут — це poison message, що вічно крутиться і блокує решту.

Retry topics + DLQ (патерн Uber)

Стратегія ретраюПлюсиМінуси
In-place (спати і повторювати в тому ж консьюмері)Простота, порядок збереженоБлокує всю партицію (head-of-line); довгі паузи → max.poll.interval.ms → ребаланс
Retry topics з затримкамиОсновний потік не стоїтьПорядок втрачено; більше топіків і консьюмерів

DLQ — не «сміттєвий кошик»

  • Зберігайте оригінальний payload + метадані: вихідний топік/партиція/offset, кількість спроб, клас помилки, стек, час. Інакше розбирати нічого.
  • Алерт на ненульовий DLQ (або на швидкість зростання). DLQ, на яку ніхто не дивиться, = тиха втрата даних.
  • Redrive: інструмент, що повертає повідомлення в основний потік після фіксу бага. Обробник має бути ідемпотентним — частина вже могла бути оброблена.
  • Не плутайте з parking lot — довгостроковим сховищем для ручної обробки бізнес-кейсів.

Visibility timeout (SQS) — звідки беруться дублі в чергах

SQS: visibility timeout за замовчуванням 30 с (максимум 12 год), повідомлення зберігаються від 1 хв до 14 днів (дефолт 4 дні). Після maxReceiveCount отримань redrive policy переносить повідомлення в DLQ.

Backpressure і consumer lag

Consumer lag = log end offset − committed offset (по кожній партиції). Це головна метрика здоров'я асинхронної системи — разом із «віком найстарішого повідомлення» (ApproximateAgeOfOldestMessage у SQS).

Що робити, коли консьюмери не встигають

  1. Порахувати. Закон Літтла: потрібна паралельність ≈ швидкість надходження × час обробки. 2 000 msg/s × 50 мс = 100 одночасних обробок. (закон Літтла: L = λ·W — «середня кількість у системі дорівнює швидкості надходження, помноженій на середній час перебування».)
  2. Масштабувати консьюмерів — autoscaling за lag (наприклад, KEDA у Kubernetes). Для Kafka — стеля = кількість партицій; для SQS стелі практично немає.
  3. Прискорити обробку: батчі в БД (bulk insert), менше синхронних викликів, кеш довідників, асинхронний I/O всередині консьюмера (з per-key порядком).
  4. Backpressure до продюсера: обмежені буфери; продюсер блокується/отримує помилку, коли брокер або черга переповнені; API відповідає 429/503 замість того, щоб накопичувати нескінченну чергу.
  5. Load shedding / пріоритизація: окремі топіки для критичних і «best effort» подій; при перевантаженні відкидати або семплювати аналітику, а не платежі.
⚠️
Pull vs push. Kafka-консьюмер сам тягне дані (pull) — він природно не візьме більше, ніж може обробити: backpressure «безкоштовний». Push-системи (RabbitMQ, SNS → HTTP, WebSocket) мусять мати механізм кредитів: prefetch у RabbitMQ, ліміт конкурентності Lambda, інакше повільний споживач захлинеться. Небезпечний антипатерн — необмежена in-memory черга в консьюмері: lag «ховається» в пам'яті, а при OOM усе втрачається.
Аналогія для фронтендера

Streams API у браузері: ReadableStream з highWaterMark і desiredSize — це pull-модель з backpressure: джерело не «пхає» дані, поки читач не готовий. А throttle для scroll-обробника — це load shedding: зайві події просто відкидаються. Де ламається: у браузері відкинута подія scroll нічого не коштує; у бекенді відкинута подія може бути платежем, тому шедити можна лише свідомо обрані класи трафіку.

🎤
На співбесіді: назвіть метрики: consumer lag (за партиціями), вік найстарішого повідомлення, розмір DLQ, rate помилок обробки. Скажіть, що на lag стоїть алерт і autoscaling, що retention топіку з запасом більший за найдовший можливий простій консьюмера, і що poison messages після N спроб ідуть у DLQ з алертом.
Transient → backoff-ретраї; permanent → одразу DLQ. Lag — головна метрика; retention має пережити найдовший інцидент.
Частина III · Event-driven архітектура

09 Події, хореографія vs оркестрація, саги

Як побудувати бізнес-процес, що проходить через кілька сервісів (замовлення → оплата → склад → доставка), без розподіленої транзакції.

Команда vs подія

Команда (command)

  • Наказовий спосіб: ChargePayment, ReserveStock.
  • Має одного адресата, який може відмовити.
  • Відправник чекає результату (відповідь/подію-результат).

Подія (event)

  • Минулий час: OrderCreated, PaymentFailed.
  • Факт, що вже стався; його не можна «відхилити».
  • Відправник не знає, хто слухає.

Два стилі подій (Martin Fowler, «What do you mean by Event-Driven?»)

Saga: розподілена «транзакція» з компенсаціями

Saga (Garcia-Molina & Salem, 1987) — послідовність локальних транзакцій T1…Tn у різних сервісах. Якщо Tk падає, виконуються компенсуючі транзакції Ck-1…C1 у зворотному порядку. Компенсація — це семантичне скасування (refund, release), а не rollback: стан між кроками вже був видимий іншим.

saga_orchestrator.py — мінімальний оркестратор (перевірено python3 ≥ 3.10)
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class Step:
    name: str
    action: Callable[[dict], None]
    compensate: Callable[[dict], None] | None = None   # None = не треба/неможливо

@dataclass
class SagaOrchestrator:
    steps: list[Step]
    log: list[str] = field(default_factory=list)       # у проді: персистентний стан саги

    def run(self, ctx: dict) -> str:
        done: list[Step] = []
        for step in self.steps:
            try:
                step.action(ctx)
                done.append(step)
                self.log.append(f"ok   {step.name}")
            except Exception as e:
                self.log.append(f"FAIL {step.name}: {e}")
                for prev in reversed(done):               # компенсуємо у зворотному порядку
                    if prev.compensate:
                        prev.compensate(ctx)               # має бути ідемпотентною + ретраї
                        self.log.append(f"comp {prev.name}")
                return "COMPENSATED"
        return "COMPLETED"

stock = {"sku-1": 1}
def create_order(c):   c["status"] = "PENDING"
def cancel_order(c):   c["status"] = "CANCELLED"
def reserve(c):
    if stock[c["sku"]] < 1: raise RuntimeError("out of stock")
    stock[c["sku"]] -= 1
def release(c):        stock[c["sku"]] += 1
def charge(c):
    if c["card"] == "declined": raise RuntimeError("card declined")
def ship(c):           c["status"] = "SHIPPED"

def saga():
    return SagaOrchestrator([
        Step("create_order", create_order, cancel_order),
        Step("reserve_stock", reserve, release),
        Step("charge_payment", charge, None),   # pivot: після нього лише вперед
        Step("ship", ship, None),               # retriable: ретраїмо до успіху
    ])

s1 = saga(); print(s1.run({"sku": "sku-1", "card": "declined"}), s1.log, "stock:", stock)
s2 = saga(); ctx = {"sku": "sku-1", "card": "ok"}
print(s2.run(ctx), ctx["status"], "stock:", stock)

# COMPENSATED ['ok   create_order', 'ok   reserve_stock', 'FAIL charge_payment: card declined',
#              'comp reserve_stock', 'comp create_order'] stock: {'sku-1': 1}
# COMPLETED SHIPPED stock: {'sku-1': 0}

У продакшені стан саги персистується (таблиця saga_instances або workflow-рушій на кшталт Temporal), кожен крок викликається через чергу/RPC з idempotency key, а оркестратор після рестарту продовжує з останнього збереженого кроку.

Найтонше місце саг: відсутність ізоляції

Saga — це ACD без I: проміжні стани видимі. Покупець бачить «замовлення створено», а через секунду воно скасоване; інша сага читає резерв, якого скоро не буде. Контрзаходи (за Chris Richardson, «Microservices Patterns»):

  • Semantic lock: статус PENDING/*_PENDING — інші операції знають, що запис «у процесі» і чекають/відмовляють.
  • Commutative updates: операції, порядок яких неважливий (інкременти/декременти балансу).
  • Reread value / version: перед оновленням перевірити, що дані не змінились (optimistic locking).
  • Порядок кроків: compensatable → pivot (точка неповернення) → retriable.

Аналогія для фронтендера

Optimistic UI з відкатом: ви одразу показуєте лайк (T1), шлете запит; сервер відповів помилкою — ви «компенсуєте»: прибираєте лайк і показуєте тост. Ви не можете «відкотити» те, що користувач уже побачив, — лише семантично скасувати. Саме так у сазі. Де ламається: у UI компенсація миттєва і локальна; у сазі вона сама може впасти (refund-сервіс недоступний), тому її ретраять до успіху і вона мусить бути ідемпотентною.

🎤
На співбесіді: «Між сервісами Order, Inventory і Payment — сага. Оркестрація через Temporal/Step Functions, бо кроків багато і є таймаути. Кожен крок — локальна транзакція з outbox; компенсації ідемпотентні. Порядок: резерв → оплата (pivot) → доставка. Ізоляцію замінюю semantic lock-статусами PENDING». І обов'язково: «2PC не беру, бо Kafka і платіжний провайдер не підтримують XA, і 2PC блокує при падінні координатора».
🚩
Типові помилки: компенсація, що може «не вдатись назавжди» (без ретраїв і алертів); компенсація, яка не ідемпотентна (refund двічі); відсутність таймауту на кроці («чекаємо відповідь від Payment вічно»); хореографія з 8 кроків, яку ніхто не може намалювати.
Saga = локальні транзакції + ідемпотентні компенсації у зворотному порядку. Немає ізоляції → semantic locks і правильний порядок кроків.

10 CQRS і event sourcing

Два патерни, які часто згадують разом, але вони незалежні: CQRS можна без event sourcing, а event sourcing майже завжди тягне за собою CQRS.

CQRS (Command Query Responsibility Segregation)

  • Окремі моделі (часто — окремі сховища) для запису і для читання. Запис нормалізований і транзакційний; читання — денормалізовані «вітрини» під конкретні екрани.
  • Синхронізація — через події/CDC, тобто eventual consistency: після команди read-модель оновиться через мілісекунди–секунди.
  • Коли варто: навантаження читання ≫ запису і запити різнорідні (пошук, агрегати, стрічки). Приклад з життя — будь-яка стрічка: пишемо пост в одну таблицю, читаємо з попередньо зібраного timeline у Redis (див. туторіал 10).
  • Коли ні: простий CRUD. CQRS подвоює кількість рухомих частин.

(≫ — «набагато більше»: наприклад, 100 читань на 1 запис.)

Event sourcing

Джерело правди — не поточний стан, а незмінний журнал подій. Поточний стан = fold(apply, events, initial). Баланс рахунку — не колонка balance, а сума всіх Deposited/Withdrawn.

Плюси

  • Повний аудит «хто, що, коли» — безкоштовно (фінанси, медицина, юридичні домени).
  • Темпоральні запити: «який був стан на 1 березня?»
  • Нові read-моделі будуються replay історії — навіть для подій, що сталися до появи моделі.
  • Немає dual write: запис події і є публікацією.
  • Дебаг: відтворити баг, програвши ті самі події.

Мінуси

  • Еволюція схем подій назавжди: старі події ніколи не зникають → upcasting, версіонування.
  • Запити «знайди всі замовлення > 100$» неможливі без проекцій → обов'язковий CQRS.
  • Eventual consistency проекцій, складність replay (години на мільярдах подій).
  • GDPR «право на забуття» в незмінному журналі → crypto-shredding (шифрувати PII ключем користувача і видаляти ключ).
  • Крива навчання для команди; легко зробити «CRUD-події» (OrderUpdated з усім станом) без жодної користі.

Снапшоти

Агрегат з 1 млн подій завантажувати з нуля довго. Періодично (кожні N подій) зберігають snapshot стану з версією; завантаження = останній снапшот + події після нього. Снапшот — лише оптимізація (кеш), його можна перебудувати з подій.

Конкурентність у event store

Два запити одночасно змінюють один агрегат: обидва прочитали версію 41 і хочуть дописати подію 42. Event store робить optimistic concurrency: append(stream, events, expectedVersion=41) — другий отримає конфлікт і повторить команду на свіжому стані. Це аналог UNIQUE(stream_id, version) у звичайній SQL-таблиці подій.

Аналогія для фронтендера

Redux — це event sourcing у браузері: actions — незмінні події в минулому часі (todoAdded), reducer — apply, store — поточний стан як fold над діями, Redux DevTools — time travel і replay. Селектори з reselect — це read-моделі (проекції), оптимізовані під конкретний компонент, — CQRS у мініатюрі. Де ламається: Redux-лог живе в пам'яті і зникає при перезавантаженні; event store — довговічний, з версіями, конкурентними записами і роками історії, де схема подій мусить еволюціонувати сумісно.

🎤
На співбесіді: event sourcing пропонуйте лише там, де аудит/історія — вимога (ledger, платежі, бронювання), і одразу називайте ціну: еволюція схем, проекції, GDPR. Для решти — звичайна БД + outbox. CQRS доречно згадати, коли читання й запис мають різні форми (пошук, стрічки, дашборди).
🚩
Red flag: «Зробимо event sourcing для всього, щоб було масштабованіше». ES не про масштаб; він про аудит і моделювання домену, а масштаб читання дає CQRS-проекція, яку можна мати й без ES.
CQRS — розділити моделі читання й запису. Event sourcing — журнал подій як джерело правди. Снапшоти — кеш для швидкого завантаження.

11 Stream processing і як це роблять великі

Коли подій мільйони на секунду, їх обробляють не «по одній у воркері», а потоково: агрегації у вікнах часу, join потоків, стан у вбудованих сховищах. На співбесіді це з'являється в задачах «Top-K», «real-time аналітика кліків», «surge pricing», «fraud detection».

Event time vs processing time

Event time — коли подія сталася (таймстемп на пристрої). Processing time — коли її обробили. Мобільний клієнт у метро шле клік через 10 хвилин — для аналітики він має потрапити у «свою» хвилину, а не в поточну. Звідси вікна за event time і watermarks.

Ключові поняття

  • Watermark — монотонна мітка «event time, до якого ми вважаємо дані повними». Вікно закривається і видає результат, коли watermark переходить його кінець. Компроміс: агресивний watermark → менша затримка, більше запізнілих подій; консервативний → точніше, але повільніше.
  • Late data: відкинути, оновити результат (allowed lateness — вікно ще якийсь час приймає виправлення), або відправити в side output для пакетного дорахунку.
  • State: агрегати вікон і таблиці для join живуть у локальному сховищі (RocksDB) з бекапом — changelog-топік у Kafka Streams, чекпойнти в S3 у Flink.
  • Exactly-once у стрімінгу: Flink робить розподілені снапшоти (checkpoints, алгоритм у дусі Chandy–Lamport) стану й offset-ів; з транзакційним sink отримуємо end-to-end exactly-once. Kafka Streams — через транзакції Kafka.
  • Stream–table join: потік кліків збагачують таблицею профілів (компактований топік → KTable): класичне ECST.

Як це роблять у реальних системах

LinkedIn — батьківщина Kafka

Kafka створена в LinkedIn (Jay Kreps, Neha Narkhede, Jun Rao; paper «Kafka: a Distributed Messaging System for Log Processing», NetDB 2011) для збору activity-подій і логів у реальному часі. За публічними доповідями LinkedIn, обсяг сягав трильйонів повідомлень на день (порядку 7 трлн/добу в 2019).

Uber — Kafka як хребет

Uber публічно описував одну з найбільших інсталяцій Kafka: події поїздок, локації водіїв, логи, вхід для real-time аналітики та ціноутворення. Відомі артефакти: uReplicator (міжкластерна реплікація), патерн retry-топіків + DLQ (блог 2018), «Consumer Proxy» — push-проксі перед Kafka для сервісів на багатьох мовах.

Shopify розповідали, як знімають кожну зміну з шардованого MySQL-моноліту через Debezium + Kafka Connect, щоб інші системи (пошук, аналітика) отримували потік змін без dual write з коду Rails.

Netflix — Keystone

Netflix описували Keystone — пайплайн обробки подій на Kafka + Flink: роутинг подій у сховища і real-time обробка (за публічними доповідями — трильйони подій на день). Гарний приклад «платформи стрімінгу» як внутрішнього продукту.

Аналогія для фронтендера

Tumbling window — це throttle, що раз на N мс видає агрегат (наприклад, кількість scroll-подій), session window — debounce: «сесія» закінчується після паузи. RxJS має прямі аналоги: bufferTime (tumbling), windowTime(size, hop) (hopping). Де ламається: у браузері немає запізнілих подій — час події ≈ час обробки; у стрімінгу події приходять із затримкою і не по порядку, тому потрібні watermarks.

🎤
На співбесіді (наприклад, «топ-10 відео за останню годину»): «Kafka з кліками → Flink з hopping window 1 год / крок 1 хв за event time, watermark із затримкою ~30 с, late data в side output; локальний стан у RocksDB з чекпойнтами; результат у Redis sorted set для API». Детально — у туторіалі 12.
Вікна за event time + watermark = коректна агрегація потоку з запізнілими подіями. Kafka Streams — бібліотека, Flink — кластер.

12 Трікі питання

Питання, на яких «плавають» навіть досвідчені розробники. Спершу відповідайте вголос самі, потім відкривайте.

TRICKY«У Kafka є exactly-once. Звідки тоді дублі в нашій БД?»

Kafka EOS (idempotent producer + транзакції + read_committed) покриває лише ланцюжок Kafka → обробка → Kafka, де вихідні записи й коміт offset-ів ідуть в одній транзакції Kafka. Запис у Postgres — зовнішній сайд-ефект: консьюмер записав рядок, впав до коміту offset → після ребалансу інший консьюмер прочитає те саме повідомлення і запише ще раз. Рішення: ідемпотентний запис (upsert за event_id / дедуп-таблиця в тій самій транзакції) або зберігати offset у тій же БД-транзакції, що й результат, і при старті робити seek().

TRICKYУ групі 20 консьюмерів, у топіку 12 партицій. Додамо ще 10 консьюмерів — пришвидшиться?

Ні. Партиція в межах групи читається одним консьюмером, тож активних буде максимум 12, решта 18 простоюють (корисні лише як «гарячий резерв» на випадок падіння). Варіанти: збільшити кількість партицій (з урахуванням зміни мапінгу ключів), або паралелізувати обробку всередині консьюмера з per-key порядком (так роблять бібліотеки на кшталт Confluent Parallel Consumer), або прискорити саму обробку (батчі).

COREЯк гарантувати глобальний порядок усіх подій?

Технічно — одна партиція (і один консьюмер), тобто стеля пропускної здатності одного брокера/процесу. Тому правильна відповідь — уточнити вимогу: майже завжди потрібен порядок у межах сутності (замовлення, рахунку, чату) → ключ = id сутності. Якщо справді потрібен глобальний порядок (наприклад, ledger), — один «sequencer», що видає монотонні номери, або БД з серіалізованими транзакціями, і свідомо прийнята стеля масштабу.

TRICKYБатч з 10 повідомлень: 5-те впало, 6–10 оброблено. Який offset комітити?

В Kafka offset — це «все до N оброблено», поштучного ack немає. Закомітити 11 = втратити 5-те. Закомітити 5 = після рестарту повторно обробити 6–10 (тому вони мусять бути ідемпотентні). Практичні варіанти: (1) 5-те — в retry-топік/DLQ і коміт 11; (2) комітити лише «суцільний» префікс оброблених (як роблять паралельні консьюмери, що тримають «дірки» в метаданих коміту). Відповідь, яку чекають: «комічу найбільший безперервно оброблений offset + 1, решта — ідемпотентні повтори; невдале — у retry/DLQ».

ADVЧому б не використати таблицю в Postgres як чергу?

Цілком нормальне рішення для помірних навантажень (сотні–тисячі задач/с): SELECT … FOR UPDATE SKIP LOCKED LIMIT 10 дає конкурентних воркерів без блокувань один одного, а задача ставиться в тій самій транзакції, що й бізнес-дані — dual write зникає. Так працюють, наприклад, Que, GoodJob, River, Oban (в екосистемі Elixir). Мінуси: bloat і VACUUM від постійних UPDATE/DELETE, навантаження на основну БД, немає fan-out і replay. Коли трафік росте або потрібні багато споживачів — переходять на брокер (часто через outbox із тієї ж таблиці).

TRICKYPolling relay запам'ятовує «останній опублікований id». Чому він може пропустити подію?

Автоінкремент видається на початку транзакції, а видимим рядок стає після коміту. Транзакція A отримала id=100, транзакція B — id=101; B закомітилась раніше. Релей бачить 101, публікує, запам'ятовує «101». Потім комітиться A з id=100 — релей її ніколи не візьме (він шукає id > 101). Рішення: прапорець published замість курсора; або CDC (журнал транзакцій упорядкований за порядком коміту, а не за id); або курсор із «вікном безпеки» (перечитувати останні N секунд) + дедуп.

ADVLeader партиції помер. Чи можуть зникнути вже «підтверджені» записи?

Залежить від acks. При acks=1 лідер підтверджує після запису в свій лог; якщо він помер до реплікації — новий лідер з ISR цих записів не має, вони втрачені, хоча продюсер отримав «успіх». При acks=all + min.insync.replicas=2 запис підтверджується, лише коли він є в усіх ISR (щонайменше 2), а новий лідер обирається з ISR — підтверджене не втрачається, поки живий хоча б один ISR-член. Якщо ввімкнено unclean.leader.election, лідером може стати відстала репліка → втрата даних заради доступності.

TRICKYМи розсилаємо тонкі події «UserUpdated{id}». Після масової міграції 2 млн користувачів впав user-service. Чому?

Event notification: кожен з N споживачів на кожну подію робить callback GET /users/{id}. 2 млн подій × 5 споживачів = 10 млн запитів за хвилини — ви влаштували собі DDoS. Рішення: event-carried state transfer (подія містить потрібні поля), або споживачі батчують і кешують, або rate limit на споживачах; для масових міграцій — окремий bulk-канал і throttling продюсера.

TRICKYДедуп через Redis: SETNX event_id перед обробкою. Що не так?

Ключ ставиться до ефекту. Якщо обробник впав після SETNX, але до запису в БД, — повторна доставка побачить ключ і пропустить подію: втрата. Якщо ставити ключ після ефекту — падіння між ефектом і SETNX дає дубль. Redis і БД не мають спільної транзакції. Надійно: дедуп у тій же БД і транзакції, що й ефект; Redis — лише як швидкий передфільтр, або SETNX зі статусом «in-progress» + TTL + перевірка в БД.

COREKafka чи RabbitMQ/SQS — як вибрати за 30 секунд?
  • Потрібен replay, кілька незалежних споживачів, великий throughput, CDC, стрімінг → Kafka (або Kinesis/Pulsar/Redpanda).
  • Задачі для воркерів, поштучний ack, затримані повідомлення, пріоритети, складна маршрутизація → RabbitMQ.
  • AWS, мінімум операційної роботи, job queue → SQS (+ SNS для fan-out).
  • Не забудьте операційну сторону: Kafka — найдорожча в експлуатації (керовані варіанти: MSK, Confluent Cloud).

Задача 1ЛегкоЧерга, лог чи pub/sub?

Оберіть інструмент для кожного випадку: (a) генерація PDF-рахунків; (b) clickstream 200k подій/с для аналітики й рекомендацій; (c) інвалідація локального in-memory кешу на 50 інстансах API; (d) подія «OrderCreated», яку слухають 5 сервісів, а через місяць додадуть шостий, якому потрібна історія.

Задача 2ЛегкоСемантика доставки

Яку семантику оберете і чому: (a) метрики CPU кожні 10 с; (b) списання коштів; (c) індикатор «друкує…» в чаті; (d) email «ваше замовлення відправлено».

(a) at-most-once — наступна точка через 10 с перекриє втрату. (b) at-least-once + ідемпотентність (idempotency key) = exactly-once ефект. (c) at-most-once, ефемерно, без зберігання. (d) at-least-once + дедуп за (order_id, "shipped_email"): дубль листа неприємний, втрата — гірша.

Задача 3СередньоОцінка Kafka-кластера

50 000 подій/с, середній розмір 1 KB, retention 7 днів, replication factor 3. Один консьюмер обробляє ~5 000 подій/с. Скільки дискового простору і скільки партицій?

  1. Потік: 50 000 × 1 KB = 50 MB/с.
  2. За добу: 50 MB × 86 400 с ≈ 4.32 TB. За 7 днів ≈ 30.2 TB.
  3. З RF=3: ≈ 90.7 TB «сирих». Стиснення (lz4/zstd) для JSON часто дає 2–5× → реально ~20–45 TB. Плюс запас 30–50% на піки і перебалансування.
  4. Партиції: 50 000 / 5 000 = 10 консьюмерів мінімум → ≥ 10 партицій; беремо з запасом на зростання і піки 24–32 (партиції не можна зменшити, а збільшення ламає мапінг ключів).
  5. Мережа: запис 50 MB/с × 3 (реплікація) + читання кожною групою по 50 MB/с — рахуйте вихідний трафік брокерів, він часто вузьке місце.
Задача 4СередньоЗакон Літтла для консьюмерів

3 000 повідомлень/с, обробка кожного — 200 мс (виклик зовнішнього API). Скільки потрібно паралельності? Що зміниться, якщо обробка в Kafka-консьюмері строго послідовна в межах партиції?

L = λ × W = 3 000 × 0.2 = 600 одночасних обробок. З SQS: 30 інстансів × 20 потоків — і готово. З Kafka при послідовній обробці партиції одна партиція дає 1 / 0.2 = 5 msg/с → потрібно ≥ 600 партицій, що недоцільно. Тому: (1) per-key паралелізм усередині консьюмера (наприклад, 50 партицій × 12 «слотів» з ключовим порядком); (2) батчити виклики API; (3) якщо порядок не потрібен — подумати, чи це не задача для черги, а не для логу.

Задача 5Середньо«Shipped» раніше за «Paid»

Сервіс статусів замовлень споживає події OrderPaid і OrderShipped (ключ — order_id). Після впровадження retry-топіків користувачі зрідка бачать статус «PAID» після «SHIPPED». Чому і як виправити?

OrderPaid впав з тимчасовою помилкою і пішов у retry-топік (затримка 1 хв), а OrderShipped того ж ключа обробився одразу; через хвилину ретрай OrderPaid перезаписав статус назад. Порядок у партиції гарантований, але retry-топік його порушує. Виправлення: (1) події несуть version/sequence від агрегату, апдейт WHERE version < :v; (2) state machine guard: дозволені лише переходи вперед (PAID → SHIPPED, але не навпаки); (3) якщо потрібна строга послідовність — блокувати ключ, поки його повідомлення в ретраї («parking» за ключем).

Задача 6СкладноДебаг: листи губляться і дублюються

Payment Service після успішної оплати робить db.commit(), а потім kafka.send("payments", event) з 3 ретраями. Notification Service читає топік з enable.auto.commit=true і шле email. Скарги: ~0.1% клієнтів не отримують лист, деякі отримують два. Знайдіть усі причини і запропонуйте дизайн.

Причини втрат: (1) dual write — процес упав/задеплоївся між commit і send, або 3 ретраї не вистачило; (2) auto-commit комітить offset за таймером незалежно від того, чи email відправлено — падіння після авто-коміту, але до відправки = втрата.

Причини дублів: (1) продюсер без idempotence ретраїть після таймауту, хоча перший запис дійшов; (2) падіння консьюмера після відправки email, але до (авто)коміту → повторна обробка після ребалансу.

Залишковий ризик: email-провайдер прийняв лист, а відповідь не дійшла. Якщо провайдер підтримує idempotency key — дубля не буде; якщо ні — приймаємо рідкісний дубль (краще, ніж втрата) і пишемо статус «sending/sent» у дедуп-таблицю.

Задача 7СередньоSQS і дублі відео-транскодингу

Воркери беруть із SQS задачі транскодингу відео. Visibility timeout — 30 с, медіанний час обробки — 40 с, p99 — 4 хв. Кожне відео транскодується 2–8 разів. Що робити?

  1. Причина: повідомлення стає видимим через 30 с, поки перший воркер ще працює → інші воркери беруть його ж.
  2. Heartbeat: воркер кожні ~20 с викликає ChangeMessageVisibility (продовжує на, скажімо, 60 с), поки працює. Якщо воркер помер — heartbeat припиняється, і задача повертається в чергу швидко.
  3. Або великий таймаут (наприклад, 15 хв ≈ кілька p99), але тоді після падіння воркера задача чекає 15 хв.
  4. Ідемпотентність: результат пишеться в детермінований ключ S3 (videos/{id}/{rendition}.mp4), статус задачі — умовним апдейтом; повторний запуск бачить «DONE» і виходить.
  5. Велике відео — розбити на чанки (кожен — окрема коротка задача), як роблять у пайплайнах відео (див. туторіал 11).
Задача 8СкладноСага бронювання подорожі

Користувач бронює рейс + готель + авто. У кожного — зовнішній партнерський API. Авіабілет після оплати неповоротний (refund — лише частковий), готель скасовується безкоштовно до 24 год, авто — безкоштовно завжди. Спроектуйте сагу: порядок кроків, компенсації, таймаути.

  1. Оркестрація (Temporal/Step Functions): кроків багато, є таймаути й людські рішення.
  2. Порядок за вартістю компенсації: спершу hold/резерви без оплати (авто → готель → рейс-hold, якщо API дозволяє), потім pivot — викуп авіаквитка (найдорожче скасувати), потім підтвердження готелю й авто (retriable — ретраїмо до успіху).
  3. Компенсації: release авто, cancel готелю; після pivot — тільки вперед, проблеми вирішуються ретраями й підтримкою.
  4. Таймаути: кожен крок має дедлайн; партнер «мовчить» → запит статусу (чи пройшла бронь?) перед компенсацією, бо таймаут ≠ відмова.
  5. Ідемпотентність: idempotency key на кожен виклик партнера (trip_id:step), стан саги персистований; UI показує «бронювання в процесі» (semantic lock).
Задача 9СкладноКоли почнемо втрачати дані?

Продюсер пише 10 000 msg/с, консьюмер-група встигає лише 9 000 msg/с. Поточний lag — 50 млн повідомлень. Retention топіку — 3 дні. Через скільки часу непрочитані повідомлення почнуть видалятися?

  1. Втрата настає, коли вік найстарішого непрочитаного повідомлення перевищить retention, а не коли lag «досягне числа».
  2. Поточне відставання в часі: 50 млн / 10 000 msg/с = 5 000 с (≈ 1.4 год): консьюмер читає повідомлення, записані ~1.4 год тому.
  3. За кожну секунду консьюмер просувається на 9 000 повідомлень = 0.9 с «часу продюсера», тобто відставання в часі росте на 0.1 с щосекунди.
  4. Запас: 3 дні = 259 200 с; (259 200 − 5 000) / 0.1 ≈ 2 542 000 с ≈ 29.4 доби.
  5. Висновок: не паніка, але lag росте лінійно — масштабувати консьюмерів (≥ 12% потужності) і поставити алерт на вік найстарішого повідомлення, а не лише на кількість.
Задача 10СкладноEvent sourcing для рахунку

Рахунок зберігається як потік подій Deposited/Withdrawn. Два запити на зняття по 80 при балансі 100 приходять одночасно на різні інстанси. Як не допустити мінуса? Як швидко завантажувати рахунок із 2 млн подій?

  1. Обидва інстанси завантажують агрегат (версія 41, баланс 100), перевіряють інваріант «баланс ≥ 80» — обидва ок.
  2. Append з expectedVersion=41: перший записує подію 42, другий отримує WrongExpectedVersion (у SQL — порушення UNIQUE(stream_id, version)).
  3. Другий перезавантажує агрегат (версія 42, баланс 20) і повторює команду → відмова «недостатньо коштів». Інваріант збережено без блокувань.
  4. Завантаження: снапшот кожні ~1 000 подій → читаємо снапшот + ≤ 1 000 подій. Плюс read-модель «balance» для API, оновлювана проектором.
  5. Ключ партиції для подій рахунку в Kafka — account_id, щоб проекції бачили їх по порядку.

Consumer group
Набір консьюмерів, що ділять партиції топіка; кожна партиція — одному члену групи.

Offset
Порядковий номер повідомлення в партиції; committed offset — «звідки продовжити».
Закладка в книзі.

ISR
In-sync replicas — репліки, що встигають за лідером; лише з них обирається новий лідер.
«Хто в строю».
04
High watermark
Останній offset, що є в усіх ISR; консьюмери бачать лише записи до HW.
Ватерлінія закоміченого.

Rebalance
Перерозподіл партицій у групі при вході/виході консьюмера; джерело пауз і дублів.
Пересадка за столом.

f(f(x)) = f(x).

Подія пишеться в таблицю outbox у тій же транзакції, що й дані; релей публікує її пізніше.
Лист у поштову скриньку в тому ж будинку.

Dead-letter queue: місце для повідомлень, які не вдалося обробити після N спроб.

Час, на який SQS ховає отримане повідомлення; без видалення воно повернеться.

Механізм, яким повільний споживач стримує швидкого продюсера (pull, кредити, обмежені буфери).

Послідовність локальних транзакцій із компенсаціями у зворотному порядку.
Не rollback, а «вибачте, повертаємо гроші».

Крок саги, після якого лише вперед; до нього все компенсовне.
Точка неповернення.

Event-carried state transfer: подія несе дані, споживачі тримають локальну копію.
Товста подія — нуль callback-ів.
