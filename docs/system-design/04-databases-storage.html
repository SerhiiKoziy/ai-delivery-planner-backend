01 Навіщо це на співбесіді: ментальна модель

Інтерв'юера цікавить не назва БД, а ланцюжок міркувань: від запитів до схеми, від схеми до движка.

На співбесіді є дві типові помилки. Перша — «візьмемо MongoDB, бо вона масштабується» (назва замість аргументу). Друга — годину обговорювати схему, не сказавши, які запити вона має обслуговувати. Сильна відповідь іде в одному напрямку: access patterns → модель даних → тип БД → індекси та движок → транзакції й ізоляція → масштабування. Кожен крок обґрунтовується попереднім.

Для кожного сховища тримайте в голові чотири осі: модель даних (таблиці, документи, ключі, граф), запити (за ключем, діапазон, JOIN, повний текст, агрегати), гарантії (транзакції, ізоляція, durability) і масштабування (вертикальне, read-репліки, шардинг). Більшість «холіварів» SQL vs NoSQL зникає, коли ви явно проговорюєте ці осі.

Аналогія для фронтендера

Це як вибір state-менеджменту: спершу ви з'ясовуєте, як компоненти читають і змінюють стан (access patterns), потім форму стану (нормалізований store у Redux Toolkit createEntityAdapter чи вкладене дерево), і лише потім — бібліотеку. «Візьмемо Redux, бо всі беруть» — той самий червоний прапорець, що «візьмемо MongoDB».

🎯
На співбесіді: перед вибором БД вголос перелічіть 2–4 головні запити з частотами: «читання стрічки — 50k rps, за user_id, сортування за часом; запис поста — 500 rps; пошук по тексту — рідко». Потім: «Під ці запити підходить …, бо …». Якщо немає явних причин інакше — реляційна БД (Postgres) за замовчуванням, це нормальна й поважна відповідь.
Access patterns → модель → тип БД → індекси → ізоляція → масштаб. Назва БД без аргументу — red flag.

Як це роблять у реальних системах: Discord

У статті «How Discord Stores Trillions of Messages» вони наводять скорочення кластера приблизно зі 177 вузлів Cassandra до 72 ScyllaDB і падіння p99-латентності читання з десятків–сотні мс до ~15 мс. Важлива деталь: перед БД вони поставили власні data services на Rust з request coalescing — та сама ідея single-flight з туторіалу 3, щоб гарячий канал не перевантажував один розділ.

🎯
На співбесіді: називайте тип + конкретну БД + причину + ціну. «Повідомлення чату: wide-column (Cassandra/ScyllaDB), бо потрібен високий write throughput і всі читання — "останні N повідомлень каналу" (ключ розділу + сортування). 03 Моделювання під access patterns, нормалізація vs денормалізація

Реляційна модель оптимізує запис і гнучкість запитів; NoSQL-моделювання — конкретні читання.

Нормалізація vs денормалізація

Нормалізація (3NF) — кожен факт зберігається в одному місці; зв'язки — через зовнішні ключі; читання збирає дані JOIN-ами. Денормалізація — свідоме дублювання даних, щоб читання було одним зверненням без JOIN.

Моделювання «від запитів» (query-first)

У Cassandra/DynamoDB схема проектується від запитів: одна таблиця на запит (або single-table design у DynamoDB), ключ розділу = те, за чим фільтрують, ключ сортування = те, за чим сортують і роблять діапазони. Алгоритм:

  1. Випишіть усі запити: «останні 50 повідомлень каналу», «повідомлення користувача за місяць», «непрочитані для user».
  2. Для кожного: що в WHERE на рівність → partition key; що в ORDER BY / діапазоні → clustering/sort key.
  3. Перевірте розмір розділу: він не має рости необмежено (Discord додав bucket — часове вікно — саме тому, що розділ «канал за весь час» ріс би нескінченно). Орієнтир для Cassandra — розділи до сотень МБ, краще десятки.
  4. Перевірте рівномірність: популярний канал = гарячий розділ (туторіал 5).
  5. Запити, які не вкладаються в модель, — окреме сховище (пошук → ES) або окрема денормалізована таблиця, яку оновлюємо на запис.

Типові прийоми денормалізації в SQL

  • Лічильники: posts.comment_count замість COUNT(*) на кожен показ (оновлюється в тій самій транзакції або асинхронно).
  • Materialized views: попередньо обчислений результат важкого запиту, оновлюється періодично (REFRESH MATERIALIZED VIEW CONCURRENTLY у Postgres).
  • JSONB-колонка для рідко запитуваних атрибутів зі змінною структурою (атрибути товару різних категорій).
  • Read-моделі (CQRS): окрема таблиця/сховище, оптимізоване під читання, оновлюється подіями — туторіал 7.
Аналогія для фронтендера

Нормалізований Redux-store (entities.users[id], entities.posts[id] з authorId) vs вкладена відповідь API, яку ви кладете «як є». Нормалізований store легко оновлювати (ім'я в одному місці), але для рендеру потрібні селектори-«JOIN-и». Вкладений — рендериться одразу, але при зміні імені треба оновити його в кожному пості. Це той самий trade-off, тільки в БД ціна помножена на мільйони рядків і паралельні записи.

🎯
На співбесіді: «Починаю з нормалізованої схеми; денормалізую цілеспрямовано там, де гарячий запит інакше потребує дорогого JOIN/агрегату, — і кажу, як підтримую копії в актуальному стані (та сама транзакція, тригер, CDC/події) і яка допустима розбіжність». Покажіть схему таблиць з ключами та індексами — інтерв'юери це люблять.
Нормалізація — дешевий запис і гнучкі запити; денормалізація — дешеве читання й дорогий запис. NoSQL-моделювання — від запитів: partition key = WHERE, sort key = ORDER BY.

04 Індекси: B-tree, hash, composite, covering, secondary

Індекс — це додаткова відсортована структура, яка прискорює читання і сповільнює кожен запис.

B-tree (точніше, B+tree)

Майже всі індекси в реляційних БД — B+tree: дерево сторінок фіксованого розміру (8 КБ у Postgres, 16 КБ в InnoDB). Внутрішні сторінки містять ключі-розділювачі й посилання на дочірні сторінки, листки — ключі та посилання на рядки (або самі рядки), і листки зв'язані між собою для діапазонних сканів. Через великий fanout (fanout — «коефіцієнт розгалуження»: скільки дочірніх сторінок має одна сторінка, зазвичай сотні) дерево неглибоке: при fanout 500 три рівні адресують 500³ ≈ 1.25·10⁸ ключів, чотири — ≈ 6·10¹⁰ (10⁸ — «десять у восьмому», сто мільйонів). Тобто пошук за ключем — 3–4 читання сторінок, і верхні рівні майже завжди в buffer pool.

Composite-індекс і правило leftmost prefix

Composite-індекс (user_id, status, created_at) — це записи, відсортовані спершу за user_id, у межах нього за status, у межах — за created_at. Як телефонний довідник «прізвище, ім'я»: знайти всіх Коваленків легко, всіх Олен — тільки перебором.

db.execute("CREATE INDEX idx_user_status_created ON orders (user_id, status, created_at)")

               [(i % 1000, "paid" if i % 3 else "new", f"2026-01-{i % 28 + 1:02d}", i) for i in range(20_000)])
db.execute("ANALYZE")

Зверніть увагу на останній рядок: запит читає лише колонки, що є в індексі, тож таблицю не відкривають зовсім — covering index. У Postgres план покаже Index Only Scan (якщо visibility map свіжа після VACUUM).

Clustered vs secondary: InnoDB проти Postgres

InnoDB (MySQL)

  • Таблиця і є B+tree за primary key (clustered index): рядки лежать у листках, відсортовані за PK.
  • Secondary index зберігає значення PK → пошук = прохід secondary + прохід clustered («подвійний lookup»).
  • Випадковий PK (UUIDv4) → вставки в довільні сторінки, page splits, фрагментація. Краще монотонний (auto-increment, UUIDv7, Snowflake).

Postgres

  • Таблиця — heap (рядки без порядку); усі індекси, включно з PK, — окремі й вказують на фізичне розташування (ctid).
  • Нова версія рядка (MVCC) отримує нове розташування → оновлювати треба всі індекси, якщо не спрацював HOT update (змінені колонки не в індексах і є місце на сторінці).
  • Саме write amplification індексів була однією з причин, які Uber навів у статті 2016 «Why Uber Engineering Switched from Postgres to MySQL».

Ціна індексів

  • Кожен INSERT/UPDATE/DELETE оновлює кожен індекс таблиці: 8 індексів = ~9 записів у B-tree на одну вставку рядка.
  • Індекси займають пам'ять і витісняють з buffer pool корисні сторінки.
  • Низька селективність (індекс по is_deleted, де 99% false) — оптимізатор все одно обере seq scan. Тут допомагає partial index.
  • Створення індексу на великій таблиці блокує записи — у Postgres CREATE INDEX CONCURRENTLY.
Аналогія для фронтендера

Індекс — це Map, який ви будуєте поверх масиву, щоб не робити array.find() на кожен рендер: const byId = new Map(users.map(u => [u.id, u])). Пошук швидкий, але при кожній зміні масиву Map треба оновити — і якщо у вас п'ять таких Map-ів за різними полями, кожен push стає вп'ятеро дорожчим. Composite index — це Map з ключем `${userId}:${status}`: шукати лише за status через нього не вийде.

🎯
На співбесіді: на кожен гарячий запит у схемі назвіть індекс: «для "замовлення користувача за датою" — (user_id, created_at DESC); пагінація курсором по ньому». На питання «чому б не проіндексувати все?» — відповідь про write amplification, пам'ять і селективність. Знання leftmost prefix і covering index — обов'язковий мінімум middle+.
B+tree: 3–4 рівні на мільярди рядків. Composite — leftmost prefix, спершу «=», потім діапазон. Кожен індекс — податок на запис.

05 Движки: B-tree vs LSM-tree, ампліфікації, Bloom filters

Дві великі родини storage engines: оновлення на місці (B-tree) і лише дописування з подальшим злиттям (LSM).

B-tree-движки (InnoDB, Postgres heap + B-tree, SQL Server, Oracle) змінюють сторінки «на місці»: знайшли сторінку, змінили, колись записали на диск. LSM-движки (Log-Structured Merge-tree: RocksDB, LevelDB, Cassandra, ScyllaDB, HBase, Bigtable, а також MyRocks, CockroachDB через Pebble) ніколи не змінюють записане: усе дописується, а старе прибирається фоновим злиттям.

lsm.py
import bisect


class TinyLSM:
    """Іграшковий LSM-tree: memtable → незмінні відсортовані SSTables → compaction."""

    def __init__(self, memtable_limit=3):
        self.memtable = {}
        self.sstables = []                       # новіші — в кінці списку
        self.limit = memtable_limit

    def put(self, key, value):                   # value=None — tombstone (видалення)
        self.memtable[key] = value               # (у справжній БД спершу запис у WAL)
        if len(self.memtable) >= self.limit:
            self.flush()

    def flush(self):
        table = sorted(self.memtable.items())    # SSTable = Sorted String Table
        self.sstables.append(table)
        self.memtable = {}

    def get(self, key):
        if key in self.memtable:
            return self.memtable[key]
        for table in reversed(self.sstables):    # від найновішої до найстарішої
            keys = [k for k, _ in table]
            i = bisect.bisect_left(keys, key)    # бінарний пошук у відсортованій таблиці
            if i < len(keys) and keys[i] == key:
                return table[i][1]
        return None

    def compact(self):
        merged = {}
        for table in self.sstables:              # старі → нові: новіше перезаписує
            merged.update(table)
        self.sstables = [sorted((k, v) for k, v in merged.items() if v is not None)]


db = TinyLSM()
for k, v in [("b", 1), ("a", 1), ("c", 1), ("a", 2), ("d", 1), ("b", None)]:
    db.put(k, v)
print("SSTables:", db.sstables)
print("get a =", db.get("a"), "| get b =", db.get("b"))
db.compact()
print("after compaction:", db.sstables)

# SSTables: [[('a', 1), ('b', 1), ('c', 1)], [('a', 2), ('b', None), ('d', 1)]]
# get a = 2 | get b = None
# after compaction: [[('a', 2), ('c', 1), ('d', 1)]]

Видалення в LSM — це запис tombstone (надгробка), а не стирання: старе значення b=1 фізично лежить у першому SSTable, поки compaction не зіллє файли. Звідси відома проблема Cassandra: багато видалень → багато tombstones → повільні читання, поки не мине gc_grace_seconds і compaction їх не прибере.

Три ампліфікації

Будь-який движок балансує три величини (RUM-conjecture: Read, Update, Memory — оптимізувати можна дві з трьох):

  • Write amplification — скільки байтів реально пишеться на диск на 1 байт даних користувача. B-tree: переписується ціла сторінка 8–16 КБ заради рядка в 100 байт (+ WAL + full-page writes). LSM: кожен байт переписується при compaction на кожному рівні (leveled — порядку 10+ разів).
  • Read amplification — скільки сторінок/файлів читається на один запит. B-tree: висота дерева (3–4). LSM: memtable + кілька SSTables (зменшується Bloom filters).
  • Space amplification — скільки місця займає на диску відносно «живих» даних. B-tree: напівпорожні сторінки після splits, bloat у Postgres. LSM: старі версії й tombstones до compaction (size-tiered може тимчасово потребувати ×2 місця).

Compaction-стратегії

Size-tiered (STCS)

  • Зливає кілька SSTables схожого розміру в один більший.
  • Менше write amplification → добре для write-heavy.
  • Більше read і space amplification (ключ може бути в багатьох файлах; тимчасово ×2 місця).
  • Історично дефолт у Cassandra (у новіших версіях з'явилась Unified Compaction Strategy).

Leveled (LCS)

  • Рівні L1, L2, … кожен ~10× більший; у межах рівня SSTables не перетинаються за ключами.
  • Ключ — максимум в одному файлі на рівень → краще читання й місце.
  • Більше write amplification (постійне переписування між рівнями).
  • Дефолт у LevelDB/RocksDB; для read-heavy.

Як це роблять у реальних системах

  • Facebook MyRocks: MySQL з RocksDB замість InnoDB; за їхніми публікаціями — помітна економія місця (порядку половини) і менший знос SSD для UDB (соцграф).
  • Cassandra/ScyllaDB у Discord: write-heavy потік повідомлень ідеально лягає на LSM; проблеми, які вони описують, — саме хвости латентності при compaction і GC-паузи JVM.
  • CockroachDB використовує Pebble (LSM, натхненний RocksDB) під SQL-шаром — LSM не означає «без SQL».
🎯
На співбесіді: «Write-heavy, append-only дані з точковими читаннями за ключем — LSM (Cassandra/ScyllaDB/RocksDB): послідовні записи, гарне стиснення, Bloom filters для читань. Read-heavy з діапазонами й транзакціями — B-tree (Postgres/MySQL)». Термін «write amplification» і розуміння, що видалення в LSM — це tombstone, — гарні сигнали.
B-tree: оновлення на місці, стабільні читання. LSM: WAL + memtable → SSTables → compaction, дешевий запис, Bloom для читань, tombstones для видалень.

WAL — Write-Ahead Log

Головне правило: спершу запиши в журнал, що збираєшся змінити, потім змінюй сторінки. Журнал — послідовний append-only файл, і дописати в нього кілька сотень байт + fsync значно дешевше, ніж записати всі змінені 8-КБ сторінки по випадкових місцях диска. Сторінки в buffer pool залишаються «брудними» й скидаються на диск пізніше, на checkpoint.

WAL має й інші життя: Postgres реплікує фізичний WAL на standby, logical decoding з WAL живить CDC; MySQL реплікує через binlog (окремий від InnoDB redo log журнал). Ідея «журнал — джерело правди, таблиці — кеш журналу» — фундамент Kafka і event sourcing (туторіал 7).

⚠️
Durability — це спектр. fsync на локальний диск захищає від падіння процесу і ОС, але не від смерті диска чи інстансу. Для «не втратити підтверджений запис» потрібна синхронна реплікація хоча б на одну репліку (Postgres synchronous_commit = on + synchronous_standby_names, Aurora — запис кворумом 4 з 6 копій у 3 AZ). Асинхронна реплікація + failover = можлива втрата останніх транзакцій (RPO > 0). Детально — туторіал 5 і туторіал 8.
Аналогія для фронтендера

Атомарність — як setState з одним об'єктом проти кількох послідовних: або весь новий стан, або старий, без «напівоновленого» UI. WAL — як офлайн-черга мутацій у PWA, яку ви спершу пишете в IndexedDB, а потім застосовуєте: якщо вкладку закрили, при наступному відкритті черга «відтворюється» (replay).

🎯
На співбесіді: якщо питають «що таке ACID?» — поясніть кожну літеру одним реченням і обов'язково розведіть «C в ACID» і «C в CAP». Бонус: «durability на одному вузлі — це WAL + fsync, а в розподіленій системі — синхронна реплікація/кворум».
A = все або нічого (WAL/undo). C = інваріанти (переважно застосунок). I = як послідовно (рівні!). D = WAL + fsync + реплікація.

08 MVCC, песимістичне й оптимістичне блокування

Як БД дозволяє читачам не блокувати письменників — і як застосунку захиститись від конфліктних записів.

MVCC — Multi-Version Concurrency Control

Замість того, щоб блокувати рядок на час читання, БД зберігає кілька версій рядка. Кожна транзакція бачить знімок (snapshot): версії, закомічені до її початку (або до початку оператора — у Read Committed). Читачі не блокують письменників, письменники не блокують читачів. Два письменники одного рядка все ще конфліктують — другий чекає на лок рядка.

Postgres

  • Старі версії лежать у самій таблиці (heap); UPDATE = INSERT нової версії + позначка xmax на старій.
  • Прибирання — VACUUM (autovacuum). Довга відкрита транзакція (навіть «idle in transaction») блокує прибирання → bloat, деградація.
  • Ризик transaction ID wraparound на дуже навантажених базах без вчасного VACUUM.

MySQL InnoDB, Oracle

  • У таблиці лише остання версія; старі відновлюються з undo log.
  • Прибирання — purge-потік; довгі транзакції роздувають undo (history list length).
  • UPDATE на місці → secondary-індекси оновлюються лише для змінених колонок.

Песимістичне блокування — SELECT … FOR UPDATE

«Конфлікт ймовірний — заблокую заздалегідь». Рядок блокується до кінця транзакції; інші FOR UPDATE/UPDATE на нього чекають.

pessimistic.sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- інші чекають тут
-- перевірка в застосунку: balance >= 30
UPDATE accounts SET balance = balance - 30 WHERE id = 1;
COMMIT;                                                  -- лок знято

-- Черга задач без конкуренції воркерів:
SELECT id FROM jobs WHERE status = 'pending'
ORDER BY id LIMIT 10
FOR UPDATE SKIP LOCKED;                                  -- взяти незаблоковані

Ризики: deadlock (T1 лочить A потім B, T2 — B потім A; БД виявить і відкотить одну — лочте в сталому порядку), довгі локи під час зовнішніх викликів (ніколи не викликайте платіжний API, тримаючи FOR UPDATE), черги очікування на гарячому рядку.

Оптимістичне блокування — version column

«Конфлікт рідкісний — перевірю при записі». Читаємо рядок з version, пишемо з умовою WHERE version = :seen. 0 змінених рядків → хтось встиг раніше → перечитати й повторити (або показати користувачу конфлікт).

optimistic.py
import sqlite3

db = sqlite3.connect(":memory:", isolation_level=None)
db.execute("CREATE TABLE accounts (id INT PRIMARY KEY, balance INT, version INT)")
db.execute("INSERT INTO accounts VALUES (1, 100, 1)")


def withdraw(amount, seen_balance, seen_version):
    """Оптимістичне блокування: UPDATE спрацює, лише якщо version не змінилась."""
    cur = db.execute(
        "UPDATE accounts SET balance = ?, version = version + 1 "
        "WHERE id = 1 AND version = ?",
        (seen_balance - amount, seen_version),
    )
    return cur.rowcount == 1          # 0 рядків → хтось встиг раніше

bal, ver = db.execute("SELECT balance, version FROM accounts WHERE id = 1").fetchone()
print("A:", withdraw(30, bal, ver))   # True  — перший виграв
print("B:", withdraw(50, bal, ver))   # False — конфлікт, треба перечитати й повторити
print(db.execute("SELECT balance, version FROM accounts").fetchone())

Частина IV · Аналітика, файли, вибір

09 OLTP vs OLAP, колонкове й об'єктне сховище

Транзакції користувачів і аналітика мають протилежні патерни доступу — і різні сховища. Файли — третій світ.

OLTP (online transaction processing)

  • Багато дрібних запитів: прочитати/змінити кілька рядків за ключем.
  • Латентність — мілісекунди; тисячі–десятки тисяч TPS.
  • Рядкове зберігання (row store), B-tree індекси, транзакції.
  • Postgres, MySQL, DynamoDB, Cassandra.

OLAP (online analytical processing)

  • Мало важких запитів: агрегати по мільйонах–мільярдах рядків, кілька колонок.
  • Латентність — секунди; пропускна здатність сканування — ГБ/с.
  • Колонкове зберігання, стиснення, векторизоване виконання.
  • ClickHouse, BigQuery, Snowflake, Redshift, Druid, DuckDB; формати Parquet/ORC.

Як це роблять у реальних системах: OLTP-база → CDC/ETL → сховище даних (data warehouse) або озеро (S3 + Parquet + Iceberg/Delta) → BI. Cloudflare за їхнім блогом використовує ClickHouse для аналітики HTTP-трафіку з мільйонами подій на секунду; BigQuery спирається на ідеї Dremel (Google, 2010). Звичайний «перший крок» для стартапу — read-replica Postgres для звітів, потім колонкове сховище.

Object / blob storage (S3)

Файли (фото, відео, PDF, бекапи, логи) зберігаються в object storage: S3, Google Cloud Storage, Azure Blob, Cloudflare R2, MinIO. Плоский простір «bucket + key → байти + метадані», HTTP API, практично необмежений об'єм. S3 заявляє проектну довговічність 99.999999999% («11 дев'яток»), а з грудня 2020 дає строгу read-after-write консистентність. Об'єкт до 5 ТБ; великі файли — multipart upload (частини паралельно, retry окремої частини).

Чому не зберігати blobs у БД

  • Buffer pool заповнюється мегабайтами картинок і витісняє гарячі індекси та рядки.
  • Бекапи, реплікація, WAL роздуваються: кожне завантаження фото = мегабайти в WAL, що їдуть на кожну репліку.
  • Ціна: блочне сховище під БД (SSD з IOPS) у рази дорожче за object storage за ГБ; S3 має дешевші класи (Infrequent Access, Glacier) і lifecycle-правила.
  • Роздача: S3 + CDN дають HTTP range requests, кешування на edge, presigned URLs — БД нічого з цього не вміє, і кожен байт пройшов би через ваш API.
  • Виняток: дрібні бінарні дані (аватар-іконка на кілька КБ, підпис) — можна в bytea; Postgres сам винесе великі значення в TOAST.
Аналогія для фронтендера

Ви ж не кладете картинки в Redux-store як base64 — store тримає URL, а байти браузер тягне з CDN паралельно й кешує окремо. Presigned URL — як завантаження файлу з <input type="file"> прямо в S3 через fetch(url, {method: 'PUT', body: file}): ваш бекенд лише видав «квиток», а гігабайтне відео пішло повз нього.

🎯
На співбесіді: у будь-якій задачі з медіа (Instagram, Dropbox, YouTube) скажіть: «файли — в S3, метадані — в БД, завантаження через presigned URL/multipart напряму в S3, обробка асинхронно за подією, роздача — через CDN». Для аналітики: «не на primary; CDC → колонкове сховище (ClickHouse/BigQuery)».
OLTP — рядки, ключі, мс; OLAP — колонки, скани, секунди. Байти — в S3, метадані — в БД, роздача — CDN.

10 Як обрати БД на співбесіді

Почніть з Postgres і чесно спитайте: чого саме він не витягне?

Чек-лист обґрунтування

  1. Форма даних і зв'язки: багато зв'язків і інваріантів між сутностями → relational.
  2. Запити: лише за ключем? діапазони? повний текст? агрегати? обходи графа?
  3. Обсяг і швидкість: записів/с, читань/с, ГБ/ТБ/ПБ, ріст на рік (з оцінок туторіалу 1).
  4. Гарантії: потрібні транзакції між кількома об'єктами? яка ізоляція? яка допустима застарілість?
  5. Масштабування: чи вистачить вертикального + read-реплік? Якщо ні — чи вміє БД шардитись (вбудовано, як Cassandra/DynamoDB/Spanner, чи вручну)?
  6. Операційне: керований сервіс, команда, що це вміє, вартість.
🎯
На співбесіді: «polyglot persistence» — нормально, але кожне додаткове сховище — це синхронізація (CDC/outbox), операційна вартість і нові режими відмов. Хороший тон — мінімізувати: «Postgres для замовлень і користувачів, S3 для фото, Elasticsearch для пошуку через CDC — і все». Для класичних задач див. туторіал 9–12.
Default — Postgres. Кожне нове сховище — тільки під конкретний access pattern, з планом синхронізації.
Частина V · Практика

11 Трікі питання

Що інтерв'юери питають, щоб відрізнити «читав статтю» від «розумію, як працює».

TRICKYЧому б не ввімкнути Serializable всюди й забути про аномалії?

Можна, і для деяких систем це правильний дефолт (CockroachDB, Spanner так і роблять). Ціна: (1) транзакції почнуть відкочуватись з serialization failure — застосунок зобов'язаний мати retry всієї транзакції, а не одного запиту; (2) пропускна здатність падає при високому контеншні (SSI відкочує «підозрілі» транзакції, 2PL — тримає локи довше); (3) зовнішні побічні ефекти всередині транзакції (відправка email) при retry повторяться. На практиці часто комбінують: Read Committed за замовчуванням + точкові захисти (атомарні UPDATE, FOR UPDATE, constraints) або Serializable для кількох критичних транзакцій.

TRICKYUUID чи auto-increment для первинного ключа?

Auto-increment: компактний (8 байт), монотонний (вставки в кінець B-tree — локальність, мало page splits), але розкриває кількість записів і не генерується без БД (складно при шардингу). UUIDv4: генерується будь-де, не вгадується, але 16 байт і випадковий — вставки розкидані по всьому індексу, page splits, гірший кеш (в InnoDB, де таблиця — це clustered index, особливо болісно). Компроміс: UUIDv7 (RFC 9562, 2024) або Snowflake-ID — унікальні без координації й упорядковані за часом. Детально про генерацію ID — туторіал 9.

TRICKYЧому SELECT COUNT(*) по великій таблиці в Postgres повільний, навіть з індексом?

Через MVCC: різні транзакції бачать різну кількість рядків, тож «загальної кількості» просто немає — треба перевірити видимість кожної версії. Index-only scan допомагає, лише якщо visibility map свіжа. Рішення: приблизна оцінка (reltuples з pg_class, EXPLAIN), лічильник у окремій таблиці (оновлюється тригером/подіями; гарячий рядок → шардований лічильник), або «10 000+» в UI замість точного числа. MySQL InnoDB має ту саму проблему з тієї ж причини.

COREЧому пагінація через OFFSET повільна на далеких сторінках?

OFFSET 1000000 LIMIT 20 змушує БД прочитати й викинути мільйон рядків — індекс не вміє «стрибнути» на N-ту позицію. Плюс нестабільність: нові рядки зсувають сторінки (дублікати/пропуски). Рішення — keyset (cursor) pagination: WHERE (created_at, id) < (:last_created, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20 з індексом (created_at, id). Сталий час на будь-якій глибині. Ціна — немає «перейти на сторінку 537». Про API-рівень — туторіал 2.

TRICKY«Перевірити, що username вільний, потім вставити» — в одній транзакції. Це безпечно?

Ні, на Read Committed і навіть на snapshot isolation. Дві транзакції одночасно бачать «немає такого username» і обидві вставляють — це write skew через фантом (перевіряли відсутність рядка, а лочити нічого). Правильно — перенести інваріант у БД: UNIQUE (lower(username)) і обробити помилку унікальності. Загальне правило: інваріанти «не більше одного», «не перетинаються» — через constraints (UNIQUE, EXCLUDE у Postgres для інтервалів), а не через перевірку в коді.

COREКоли NoSQL — поганий вибір, навіть якщо «потрібен масштаб»?

Коли (1) access patterns невідомі або часто змінюються (аналітика продукту, адмінки) — у Cassandra кожен новий запит = нова таблиця й міграція даних; (2) потрібні транзакції між сутностями (гроші, інвентар) — їх доведеться «будувати» сагами й ідемпотентністю; (3) дані реляційні за природою (many-to-many) — JOIN-и переїдуть у застосунок. І (4) «масштаб» часто переоцінений: один інстанс Postgres на сучасному залізі тримає терабайти й десятки тисяч TPS; Instagram, Notion, Figma публічно розповідали про масштабування саме Postgres (шардинг на рівні застосунку).

ADVЯк додати індекс або колонку в таблицю на мільярд рядків без даунтайму?

Індекс: Postgres CREATE INDEX CONCURRENTLY (довше, не блокує записи; при падінні лишає INVALID-індекс — перевірити й перестворити); MySQL 8 — online DDL (ALGORITHM=INPLACE, LOCK=NONE). Колонка: у Postgres 11+ ADD COLUMN … DEFAULT const — миттєво (метадані), а от зміна типу переписує таблицю. Для складних змін — патерн expand → migrate → contract: додати нову колонку, писати в обидві, backfill батчами з паузами (щоб не вбити реплікаційний лаг), перемкнути читання, прибрати стару. Інструменти для MySQL: gh-ost (GitHub), pt-online-schema-change. Детально — туторіал 13.

TRICKYЧим небезпечний soft delete (deleted_at)?

(1) UNIQUE(email) ламається: видалений користувач блокує повторну реєстрацію → потрібен partial unique index WHERE deleted_at IS NULL. (2) Кожен запит мусить пам'ятати фільтр — один забутий WHERE = «воскреслі» дані (часто через view або ORM-scope). (3) Таблиця й індекси ростуть видаленими рядками → partial indexes, архівація. (4) GDPR «право на забуття» вимагає справжнього видалення персональних даних. Альтернатива — переносити видалене в архівну таблицю.

ADVЧому Elasticsearch не можна робити основним сховищем?

Near-real-time: документ стає видимим для пошуку після refresh (за замовчуванням ~1 с); немає багатодокументних транзакцій; історично були сценарії втрати даних при split brain (до переробки кластерної координації в 7.x); зміна mapping поля часто вимагає reindex; оновлення документа = видалення + нова версія в новому сегменті (сегменти Lucene незмінні й зливаються — та сама ідея, що LSM). Тому джерело правди — OLTP-БД, а ES — похідний індекс, який можна перебудувати з нуля через CDC/reindex.

COREЧитання з репліки повернуло старі дані одразу після запису. Це баг БД?

Ні, це replication lag асинхронної реплікації: репліка застосовує WAL/binlog із затримкою (мс — секунди, під навантаженням — хвилини). Користувач зберіг профіль, оновив сторінку — читання пішло на репліку — «зміни зникли». Рішення: read-your-writes (читати з primary N секунд після запису цього користувача або чекати, поки репліка дожене LSN/GTID запису), sticky-сесії на primary для автора. Повний розбір — туторіал 5.

12 Задачі

Оцінки, вибір індексів і БД, баги конкурентності. Спершу розв'яжіть самі.

Задача 1ЛегкоВисота B-tree на 2 млрд рядків

Secondary-індекс по BIGINT у таблиці з 2 млрд рядків, сторінка 16 КБ. Припустіть ~600 записів у листку і fanout ~800 у внутрішніх сторінках. Скільки рівнів у дереві, скільки займають листки і скільки читань з диска потрібно на пошук, якщо внутрішні рівні в RAM?

  1. Листків: 2·10⁹ / 600 ≈ 3.3 млн сторінок × 16 КБ ≈ 51 ГБ.
  2. Рівень вище: 3.3 млн / 800 ≈ 4 200 сторінок (~65 МБ). Ще вище: 4 200 / 800 ≈ 5–6 сторінок. Потім корінь. Разом 4 рівні.
  3. Усі внутрішні рівні (~65 МБ) легко живуть у buffer pool → пошук = ~1 читання з диска (листок), якщо і він не в кеші. Плюс, для InnoDB, ще один прохід по clustered index за PK, щоб дістати рядок (якщо індекс не covering).

Висновок: «індекс на мільярд рядків» — це не страшно для пошуку; страшно — його розмір у RAM і вартість підтримки на записах.

Задача 2ЛегкоЯкий індекс?

Гарячий запит: SELECT id, total FROM orders WHERE user_id = ? AND status = 'paid' ORDER BY created_at DESC LIMIT 20. Запропонуйте індекс і поясніть порядок колонок.

CREATE INDEX ON orders (user_id, status, created_at DESC) INCLUDE (total);

  • Спершу колонки з рівністю (user_id, status) — вони звужують діапазон до суцільного шматка індексу.
  • Потім created_at DESC — у межах цього шматка записи вже відсортовані, тож ORDER BY … LIMIT 20 = прочитати перші 20 записів, без сортування.
  • INCLUDE (total) (Postgres 11+) робить індекс covering — index-only scan без звернення до таблиці (id у Postgres треба теж включити; в InnoDB PK і так є в кожному secondary-індексі).
  • Якщо 95% запитів саме з status='paid' — розгляньте partial index (user_id, created_at DESC) WHERE status = 'paid': менший і швидший.
Задача 3ЛегкоПідберіть сховище

Для кожного випадку назвіть тип сховища і причину: (a) баланси гаманців; (b) телеметрія 50 000 датчиків щосекунди; (c) пошук товарів «червоні кросівки 42» з фільтрами; (d) відеофайли курсів; (e) сесії користувачів з TTL; (f) «люди, яких ви можете знати» до 3 хопів; (g) дашборд продажів за роки по регіонах.

  1. Relational (Postgres) — ACID, constraints, ledger-модель.
  2. Time-series (TimescaleDB/InfluxDB) або LSM wide-column — 50k точок/с, retention, downsampling.
  3. Search (Elasticsearch/OpenSearch) через CDC з каталогу в Postgres — інвертований індекс, фасети, релевантність.
  4. Object storage (S3) + CDN; метадані в Postgres.
  5. Key-value (Redis) — TTL з коробки, мс-латентність.
  6. Graph DB (Neo4j) — або, частіше на практиці, офлайн-обчислення рекомендацій у batch-пайплайні з кешем результату.
  7. Колонкове сховище (ClickHouse/BigQuery/Snowflake), наповнене через CDC/ETL.
Задача 4СередньоІнвентар іде в мінус

Код резервування: qty = SELECT qty FROM stock WHERE sku = ?; if qty >= n: UPDATE stock SET qty = :qty_minus_n WHERE sku = ?. Postgres, Read Committed. Під час розпродажу залишок іноді від'ємний або «продано більше, ніж було». Поясніть і дайте три способи виправити.

Lost update: дві транзакції читають qty = 5, обидві проходять перевірку, обидві пишуть «обчислене в застосунку» значення. Read Committed цього не забороняє.

  1. Атомарний умовний UPDATE (найкраще): UPDATE stock SET qty = qty - :n WHERE sku = :sku AND qty >= :n; перевірити, що змінено 1 рядок. Плюс CHECK (qty >= 0) як остання лінія захисту.
  2. Песимістично: SELECT … FOR UPDATE, потім перевірка й UPDATE. Працює, але гарячий SKU стає чергою на лок.
  3. Оптимістично: колонка version і WHERE version = :seen + retry. На гарячому SKU під час розпродажу — багато повторів, тож тут гірше за варіант 1.

Для екстремального контеншну (flash sale) — розщеплення залишку на бакети в Redis і резервації з TTL (див. задачу 8 у туторіалі 3).

Задача 5СередньоПодвійне бронювання переговорки

Бронювання: SELECT count(*) FROM bookings WHERE room = ? AND tstzrange(start, end) && :range; якщо 0 — INSERT. Інколи з'являються дві броні на один час. Чому FOR UPDATE тут не допоможе і як виправити?

Це write skew через фантом: обидві транзакції перевіряють відсутність рядків і вставляють нові. FOR UPDATE лочить існуючі рядки, а конфліктних рядків ще немає — лочити нічого.

  1. Constraint у БД (найкраще для Postgres): ALTER TABLE bookings ADD EXCLUDE USING gist (room WITH =, tstzrange(start_at, end_at) WITH &&) (потрібне розширення btree_gist). Друга вставка впаде з помилкою — обробляємо як «зайнято».
  2. Матеріалізувати конфлікт: таблиця слотів (room, slot_15min) з PK; бронювання = вставка всіх слотів; дублікат PK = конфлікт. Або SELECT … FOR UPDATE на рядок кімнати (rooms) як м'ютекс перед перевіркою.
  3. Serializable з retry: SSI виявить небезпечну залежність і відкотить одну транзакцію.
Задача 6СередньоРозмір розділу для повідомлень

Чат у Cassandra з ключем ((channel_id, bucket), message_id). Середнє повідомлення з метаданими — 1 КБ. Типовий канал — 2 000 повідомлень/день, найбільший — 1 млн/день. Ціль — розділи до ~100 МБ. Яким має бути bucket?

  • Типовий канал: 2 000 × 1 КБ = 2 МБ/день → bucket у 30–50 днів дає 60–100 МБ.
  • Найбільший: 1 млн × 1 КБ = 1 ГБ/день → навіть добовий bucket у 10 разів більший за ціль; потрібні ~2.4-годинні бакети.
  • Одного фіксованого розміру не вистачає: або фіксований малий bucket (наприклад, 1 день) і «порожні» читання для тихих каналів (запит «останні 50» мусить пройти кілька порожніх бакетів назад), або розмір бакета залежно від активності каналу (зберігається в метаданих каналу).
  • Discord за їхнім описом використовував фіксовані часові бакети (порядку 10 днів) — і окремо боровся з гарячими розділами великих серверів через request coalescing.
Задача 7СередньоФото в БД чи в S3?

Соцмережа: 10 млн нових фото на день, ~2 МБ кожне (з усіма розмірами). Тімлід пропонує bytea в Postgres, «бо простіше бекапити». Порахуйте і аргументуйте.

  1. Об'єм: 10 млн × 2 МБ = 20 ТБ/день, ~7.3 ПБ/рік. Жоден інстанс Postgres цього не тримає; шардинг заради байтів — абсурд.
  2. WAL і реплікація: кожне фото проходить через WAL і пересилається на кожну репліку — десятки ТБ мережевого трафіку на день лише на реплікацію.
  3. Бекапи стають складнішими, а не простішими: PITR-бекап на петабайти — години/дні відновлення.
  4. Ціна: SSD-диски для БД у рази дорожчі за S3 Standard, а старі фото можна перевести в Infrequent Access/Glacier lifecycle-правилом.
  5. Рішення: S3 (presigned/multipart upload) + CDN; у Postgres — метадані (~1 КБ на фото → 10 ГБ/день, нормально). Довговічність S3 вища, ніж у самописної схеми бекапів, а версіонування бакета захищає від випадкового видалення.
Задача 8СкладноДашборди вбивають продакшн

Аналітики запускають важкі звіти (GROUP BY за роки) прямо на primary Postgres. У ці моменти API-латентність зростає вдесятеро. Запропонуйте поетапне рішення від «за день» до «за квартал».

  1. За день: окрема read-replica для аналітиків (окремий користувач БД з statement_timeout). Увага: довгі запити на репліці конфліктують із застосуванням WAL (hot_standby_feedback → bloat на primary або скасування запитів) — налаштувати свідомо.
  2. За тиждень: матеріалізовані денні агрегати (daily_sales), що оновлюються інкрементально; дашборди читають їх, а не сирі таблиці.
  3. За квартал: CDC (Debezium → Kafka) у ClickHouse/BigQuery/Snowflake; колонкове зберігання дає секундні агрегати по мільярдах рядків, а OLTP повністю ізольований. Альтернатива для меншого масштабу — нічний ETL у Parquet на S3 + DuckDB/Athena.
Задача 9СкладноТелеметрія 1 млн точок/с

IoT-платформа: 1 млн точок на секунду (timestamp + device_id + float), зберігати 1 рік сирих даних і 5 років агрегатів. Запити: графік пристрою за період, агрегати по групах пристроїв. Оцініть об'єм і оберіть сховище/движок.

  1. Точок на добу: 10⁶ × 86 400 ≈ 8.6·10¹⁰. Сиро по ~16 байт → ~1.4 ТБ/день, ~500 ТБ/рік.
  2. Зі стисненням у стилі Gorilla (delta-of-delta для часу, XOR для float) — у статті Facebook наводять в середньому ~1.37 байта на точку → ~120 ГБ/день, ~43 ТБ/рік. Колонкове/TSDB-стиснення — ключовий аргумент.
  3. Запис 1 млн/с — для B-tree з випадковими вставками важко; LSM-движки та TSDB (послідовні дописування блоками за часом) — природний вибір.
  4. Модель: розділ = (device_id, день), сортування за часом → «графік пристрою» = послідовне читання. Агрегати по групах — у колонковому сховищі або continuous aggregates (TimescaleDB), rollups 1 хв/1 год для 5-річного зберігання.
  5. Варіанти: TimescaleDB (якщо команда знає Postgres, з компресією й continuous aggregates), InfluxDB/VictoriaMetrics, або Kafka → ClickHouse для аналітики + S3/Parquet для холодних даних. Retention: сирі — 1 рік (TTL/drop partitions), агрегати — 5 років.
Задача 10СкладноДебаг: Postgres повільнішає щотижня

Таблиця jobs (черга задач, ~5 млн вставок і оновлень статусу на день) з часом розростається до сотень ГБ, хоча «живих» рядків ~100 тис. Запити WHERE status='pending' стають дедалі повільнішими. Після рестарту воркерів ненадовго краще. Що відбувається?

  1. MVCC-bloat: кожен UPDATE статусу створює нову версію рядка, старі мають прибиратися VACUUM. Якщо щось тримає старий snapshot — довга транзакція (воркер, що відкрив транзакцію й «завис» у idle in transaction, або довгий звіт на репліці з hot_standby_feedback), VACUUM не може прибрати мертві версії. «Рестарт воркерів допомагає» — сильна підказка: рестарт закриває завислу транзакцію.
  2. Діагностика: pg_stat_activity (найстаріший xact_start, стан idle in transaction), pg_stat_user_tables.n_dead_tup, час останнього autovacuum.
  3. Виправлення: idle_in_transaction_session_timeout, короткі транзакції у воркерах (не тримати транзакцію під час виконання задачі), агресивніші налаштування autovacuum для цієї таблиці, partial index WHERE status = 'pending', FOR UPDATE SKIP LOCKED для вибору задач, партиціонування за часом з DROP PARTITION для завершених задач. Для дуже великих черг — розглянути спеціалізовану чергу (туторіал 7).
