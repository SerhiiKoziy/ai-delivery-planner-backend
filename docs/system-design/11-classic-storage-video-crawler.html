Частина I · Вступ

01 Три задачі, одна ментальна модель

Чому інтерв'юери так люблять саме ці задачі і що в них спільного.

Попередні класичні задачі (URL shortener, KV store, стрічка й чат) були про маленькі записи й багато запитів. Ці три — про великі байти: гігабайтні файли, години відео, мільярди HTML-сторінок. Тут ламаються «наївні» рішення на кшталт «прийняти файл у наш API-сервер і покласти в базу». Інтерв'юер перевіряє, чи ви розумієте:

  • що метадані (хто, що, яка версія, які права) і самі байти живуть у різних сховищах з різними властивостями;
  • що важку роботу (транскодування, обхід вебу) треба робити асинхронно — через черги, воркери й ідемпотентні кроки;
  • що читання великих об'єктів має йти з краю мережі (CDN), а не з вашого дата-центру;
  • що мережа ненадійна: завантаження обривається, клієнти офлайн, сайти повільні або ворожі.

Як іде відповідь на класичну задачу

  1. Функціональні вимоги — 3–5 пунктів, домовитися, що поза скоупом.
  2. Нефункціональні — масштаб, латентність, доступність vs узгодженість, durability.
  3. Оцінки — QPS, обсяг даних, пропускна здатність (детально — у туторіалі 1).
  4. API — 3–6 ендпоінтів.
  5. Модель даних — таблиці/колекції та де вони живуть.
  6. High-level схема — малюєте за 5–7 хвилин.
  7. Deep dives — 2–4 найцікавіші місця (часто інтерв'юер сам обирає).
  8. Bottlenecks і trade-offs — що зламається першим і що ви свідомо віддали.
🎯
На співбесіді: у «байтових» задачах перше речення після вимог — «я розділю шлях метаданих і шлях даних». Це одразу показує сеньйорне мислення: API-сервери не ганяють гігабайти через себе, а лише видають дозволи (presigned URL) і зберігають факти про файли.
Великі байти — в object storage і CDN; маленькі факти про них — у базі; важка обробка — у черзі.
Частина II · Google Drive / Dropbox

02 Drive / Dropbox: вимоги, оцінки, API, дані, схема

Перші 10–15 хвилин інтерв'ю: домовляємося про скоуп і малюємо каркас.

Функціональні вимоги

  • Завантажити (upload) і скачати (download) файл будь-якого розміру — до, скажімо, 50 ГБ.
  • Синхронізація між пристроями: змінив на ноутбуці — з'явилося на телефоні.
  • Історія версій (відновити файл як він був тиждень тому).
  • Шеринг: дати доступ на читання/редагування користувачу або за посиланням.
  • Поза скоупом (проговоріть!): спільне редагування документа в реальному часі (це Google Docs з OT/CRDT — окрема задача), повнотекстовий пошук по вмісту, антивірус.

Нефункціональні вимоги

  • Durability — не втрачати файли ніколи. Це важливіше за доступність: краще «сервіс недоступний 5 хвилин», ніж «ваш диплом зник». Object storage типу S3 проєктується на 11 дев'яток durability (99.999999999% — «одинадцять дев'яток»: імовірність втратити конкретний об'єкт за рік — порядку 10⁻¹¹).
  • Узгодженість метаданих — сильна в межах одного простору (namespace) користувача: дві версії одного файлу не мають «перемогти» мовчки.
  • Ефективність трафіку — змінили 1 МБ у 2-гігабайтному файлі → передати ≈ 1 МБ, а не 2 ГБ.
  • Офлайн-робота і відновлення після обриву.

Модель даних

metadata.sql
-- шардуємо за namespace_id (простір користувача або спільна папка)
CREATE TABLE files (
  file_id      BIGINT PRIMARY KEY,
  namespace_id BIGINT NOT NULL,
  path         TEXT NOT NULL,
  head_version INT NOT NULL,
  is_deleted   BOOLEAN NOT NULL DEFAULT false,
  UNIQUE (namespace_id, path)
);
CREATE TABLE file_versions (
  file_id    BIGINT, version INT, size_bytes BIGINT,
  chunk_list BIGINT[],          -- або окрема таблиця (file_id, version, idx, chunk_hash)
  created_by BIGINT, created_at TIMESTAMPTZ,
  PRIMARY KEY (file_id, version)
);
CREATE TABLE chunks (           -- content-addressed: ключ = хеш вмісту
  chunk_hash BYTEA PRIMARY KEY, -- SHA-256
  size_bytes INT, storage_key TEXT, ref_count BIGINT
);
CREATE TABLE journal (          -- лог змін простору: основа sync-курсорів
  namespace_id BIGINT, seq BIGINT, file_id BIGINT, version INT, op TEXT,
  PRIMARY KEY (namespace_id, seq)
);

Ключова ідея — journal (лог змін на namespace з монотонним seq). Курсор синхронізації — це просто «останній seq, який бачив пристрій». Dropbox публічно описував схожу модель: журнал на namespace і курсори, які клієнт передає серверу.

🏗️
Як це роблять у реальних системах. Dropbox спершу зберігав блоки в Amazon S3, а метадані — у MySQL; приблизно у 2015–2016 роках компанія публічно розповіла про перенесення більшості даних у власне сховище Magic Pocket. Desktop-клієнт за публічними доповідями ріже файли на блоки до 4 МБ і адресує їх SHA-256-хешем. У 2020 році Dropbox описував переписаний на Rust sync engine (Nucleus). Google Drive тримає метадані у внутрішніх розподілених базах (деталі публічно описані мало) — тому на співбесіді говоріть про принципи, а не «як у Google».
🎯
На співбесіді: назвіть явно, чому метадані в SQL: потрібні транзакції (commit версії + інкремент ref_count + запис у journal атомарно), унікальність шляху в папці, запити «покажи вміст папки». А байти — в object storage, бо він дешевий, нескінченно масштабується і дає durability «з коробки». Шардування метаданих — за namespace_id, щоб усі операції однієї папки були в одному шарді.
🚩
Red flags: «зберігаю файли в BLOB-колонці Postgres»; «файл проходить через наш API-сервер у S3» (ви платите за трафік двічі і тримаєте потоки на гігабайти); «синхронізація — клієнт кожні 5 секунд питає список усіх файлів» (O(N) на кожен poll).
Drive = SQL для фактів (файли, версії, чанки, журнал) + object storage для байтів + журнал змін як джерело синхронізації.

03 Deep dive: завантаження, чанки, дедуплікація

Presigned URL, resumable upload, fixed-size vs content-defined chunking, dedup за хешем.

Presigned URL і завантаження напряму в S3

Presigned URL — це звичайний URL до об'єкта в S3 з підписом у query-параметрах (ключ доступу, термін дії, підпис HMAC). Наш сервер підписує його своїм секретом, клієнт виконує один PUT — і S3 сам перевіряє, що підпис валідний і не протух. Так ми віддаємо клієнту дозвіл на одну дію з одним ключем на 15 хвилин, не віддаючи облікових даних.

Що відбувається з чанками, які завантажили, але не закомітили (клієнт помер)? Вони мають ref_count = 0 або взагалі не записані в chunks. Їх прибирає garbage collector — фонова задача, що видаляє об'єкти без посилань, старші за N годин. Для S3 multipart upload є lifecycle-правило «AbortIncompleteMultipartUpload» — інакше незавершені частини тихо накопичуються і коштують грошей.

Resumable uploads

Є два стандартні способи не починати 5-гігабайтний upload з нуля після обриву Wi-Fi:

S3 multipart upload

  • CreateMultipartUpload → upload_id.
  • Кожна частина — окремий UploadPart (presigned URL на частину); частини від 5 МіБ (крім останньої), до 10 000 частин.
  • CompleteMultipartUpload зі списком ETag-ів — S3 склеює об'єкт.
  • Після обриву: ListParts → довантажити відсутні.

Протокол поверх HTTP (tus, Google resumable)

  • POST створює сесію, повертає URL сесії.
  • PATCH/PUT з Content-Range або Upload-Offset.
  • Після обриву: HEAD → «скільки байтів уже є?» → продовжити з офсету.
  • Відкритий протокол tus.io; Google Cloud Storage і YouTube Data API мають власний «resumable upload».

У Drive-дизайні з чанками resumable виходить «безкоштовно»: кожен чанк — окремий ідемпотентний PUT за хешем. Обірвалося — upload-init знову повертає список відсутніх чанків, і клієнт довантажує тільки їх.

Fixed-size vs content-defined chunking (CDC)

Чому взагалі ріжемо файл на частини? (1) паралельне завантаження, (2) докачка, (3) дельта-синхронізація — передаємо лише змінені частини, (4) дедуплікація — однакові частини зберігаються один раз.

Fixed-size: межі кожні 4 МБ. Просто, але є відома проблема: вставили 1 байт на початку файлу — усі межі зсунулися, і всі хеші змінилися. Content-defined chunking: межу ставимо там, де rolling hash останніх ~32–64 байтів має певну властивість (наприклад, молодші 13 біт = 0 → середній чанк ≈ 8 КБ). Межі «прив'язані» до вмісту, тож після вставки вони зміщуються разом із даними.

Перевіримо це кодом. Нижче — мінімальний CDC на «gear hash» (так працює алгоритм FastCDC, лише без його оптимізацій) проти fixed-size на 4 КБ випадкових даних, у які вставили 5 байтів на початок:

cdc.py
import hashlib, random

def fixed_chunks(data: bytes, size: int = 64):
    return [data[i:i + size] for i in range(0, len(data), size)]

def cdc_chunks(data: bytes, mask: int = 0x3F, min_size: int = 16, max_size: int = 256):
    """Content-defined chunking: межа там, де rolling hash & mask == 0."""
    chunks, start, h = [], 0, 0
    for i, b in enumerate(data):
        h = ((h << 1) + GEAR[b]) & 0xFFFFFFFF          # gear hash: «забуває» старі байти
        size = i - start + 1
        if (size >= min_size and (h & mask) == 0) or size >= max_size:
            chunks.append(data[start:i + 1]); start, h = i + 1, 0
    if start < len(data):
        chunks.append(data[start:])
    return chunks

rnd = random.Random(42)
GEAR = [rnd.getrandbits(32) for _ in range(256)]

def ids(chunks):
    return {hashlib.sha256(c).hexdigest()[:8] for c in chunks}

original = bytes(rnd.getrandbits(8) for _ in range(4096))
edited = b"HELLO" + original          # вставили 5 байтів на початок

for name, fn in [("fixed", fixed_chunks), ("cdc", cdc_chunks)]:
    a, b = ids(fn(original)), ids(fn(edited))
    print(f"{name:5}: chunks={len(b):3}  reused={len(a & b):3}  new_to_upload={len(b - a)}")

# fixed: chunks= 65  reused=  0  new_to_upload=65
# cdc  : chunks= 56  reused= 55  new_to_upload=1

Чому працює: h << 1 у 32-бітному регістрі означає, що байт, який увійшов 32 кроки тому, повністю «виштовхнутий» — хеш залежить лише від останніх 32 байтів. Тому після вставки, щойно ми пройшли 32 байти за нею, хеш синхронізується з оригіналом і межі збігаються. min_size/max_size обмежують розкид розмірів (інакше бувають чанки по 3 байти або по 50 МБ).

Дедуплікація за хешем

  • Content addressing: ключ чанка = SHA-256 від вмісту. Однаковий вміст → однаковий ключ → зберігаємо раз. Колізія SHA-256 на практиці неймовірна (2²⁵⁶ значень).
  • Скоуп дедупу: у межах одного користувача — безпечно. Між користувачами — економія більша (популярні інсталятори, фільми), але це side channel: якщо upload «миттєвий», атакувальник дізнається, що такий файл у когось уже є («confirmation of a file» attack). Dropbox у 2011 році мав історію з утилітою Dropship, яка дозволяла «отримати» чужий файл, знаючи лише хеші — після цього дедуп між акаунтами обмежили. Компроміс: глобальний дедуп на сервері, але клієнт все одно вантажить байти (економимо диск, не трафік), або перевіряємо «proof of ownership».
  • Видалення: не можна видалити чанк, на який посилається хоч одна версія. Звідси ref_count (або mark-and-sweep GC). Інкремент/декремент — у тій самій транзакції, що й версія.
  • Шифрування: якщо шифруємо кожен файл унікальним ключем, однакові байти стають різними — дедуп між користувачами зникає. Це свідомий trade-off (так роблять E2E-сховища).
Аналогія для фронтендера
Content addressing — це рівно те, що робить ваш бандлер: main.3f9a1c.js, vendor.88e2b0.js. Хеш у назві файлу залежить від вмісту, тож після деплою браузер перекачує лише змінені чанки, а vendor бере з кешу. Fixed-size vs CDC — як «різати бандл кожні 100 КБ» проти «різати по модулях»: друге стабільніше до змін. Де аналогія ламається: бандлер ріже за семантикою (межі модулів), а CDC — за статистикою байтів, нічого не знаючи про структуру файлу.
🎯
На співбесіді: сильна відповідь звучить так: «Клієнт ріже файл на чанки (fixed 4 МБ — просто, як у Dropbox; CDC — якщо очікуємо вставки в середину), рахує SHA-256 кожного, питає сервер, яких хешів немає, і вантажить тільки їх напряму в S3 за presigned URL. Commit створює версію як список хешів. Це дає паралелізм, докачку, дельту і дедуп одним механізмом». І одразу назвіть ризик дедупу між акаунтами.
🚩
Типові помилки: зберігати чанки під ключем {user}/{file}/{index} (дедуп неможливий); видаляти чанк при видаленні файлу без перевірки посилань; не мати GC для «сиріт» після обірваних upload-ів; присилати presigned URL з терміном дії «тиждень».
Чанк = одиниця передачі, докачки, дедупу й версіонування. Ключ чанка = хеш вмісту.

04 Deep dive: синхронізація, конфлікти, версії, шеринг

Як пристрій дізнається про зміни, що робити з одночасними правками і як працюють права доступу.

Протокол синхронізації

Кожен пристрій тримає курсор — позицію в журналі змін свого namespace. Синхронізація — це два незалежні потоки:

  • Upload (локальна зміна → сервер): file watcher (inotify / FSEvents / ReadDirectoryChangesW) помічає зміну → debounce → чанкінг → upload-init → PUT відсутніх → commit з base_version.
  • Download (сервер → локально): «чи є щось нове після мого курсору?» → отримати дельту → докачати відсутні чанки → атомарно замінити файл на диску (записати в тимчасовий, потім rename).

Як дізнатися «чи є нове»? Варіанти з туторіалу 2: short polling (дорого), long polling, WebSocket/SSE. Dropbox історично використовував саме long polling для desktop-клієнта (публічний API має ендпоінт /files/list_folder/longpoll, який «висить» до появи змін або тайм-ауту і повертає лише changes: true/false). Чому long poll, а не WebSocket? Простий HTTP, проходить через корпоративні проксі, сервер нотифікацій stateless щодо даних — відповідає лише «є/нема», а самі зміни клієнт бере звичайним запитом.

Правило: нотифікація — це підказка («подивись»), а не носій даних. Джерело правди — журнал і курсор. Тоді втрачене push-повідомлення, перезапуск сервера нотифікацій чи пристрій, який був офлайн тиждень, обробляються однаково: «дай дельту від мого курсору».

Конфлікти

Два пристрої змінили один файл офлайн, обидва на основі версії 7. Commit використовує optimistic concurrency: UPDATE files SET head_version = 8 WHERE file_id = ? AND head_version = 7. Перший виграє, другий отримує 409 Conflict. Що далі?

Стратегії для «файлів» (Dropbox, Drive)

  • Conflicted copy — обидві версії зберігаються, друга під іншою назвою. Нуль втрат, але людина розбирається руками.
  • Last-writer-wins — простіше, але мовчки губить дані. Для файлового сховища — red flag.
  • Версії рятують і тут: навіть LWW-перезапис видно в історії.

Стратегії для «документів» (Google Docs, Figma, Notion)

  • OT (operational transformation) — Google Docs: сервер упорядковує й трансформує операції.
  • CRDT — структури, що мерджаться без координатора (Yjs, Automerge); Figma описувала власний підхід, натхненний CRDT, з центральним сервером.
  • Це вже інша задача («collaborative editor») — назвіть, але не заглиблюйтесь без запиту.

Версіонування

  • Версія = незмінний список хешів чанків. Нова версія 2-ГБ файлу, де змінився 1 чанк, коштує 1 чанк + рядок метаданих.
  • Політика зберігання: «усі версії за 30/180 днів» (так рекламують Dropbox-плани), далі GC декрементує ref_count.
  • Старі й рідко читані чанки — у холодніший клас сховища (S3 Infrequent Access / Glacier). Lifecycle-правила це автоматизують.
  • Видалення = «tombstone» у журналі (is_deleted) + кошик; фізичне видалення — пізніше.

Шеринг і права

  • ACL на папку/файл: таблиця shares(resource_id, principal, role); права успадковуються вниз по дереву. Перевірка «чи можна» — на кожен запит метаданих і перед видачею presigned URL.
  • Спільна папка = окремий namespace, який «змонтований» у namespace кількох користувачів. Тоді журнал змін спільної папки один, а курсори в кожного свої. (Dropbox описував саме модель namespaces.)
  • Посилання: share_links(token, resource_id, role, expires_at, password_hash). Токен — випадковий, ≥128 біт, не ID.
  • Для великих організацій — модель на кшталт Google Zanzibar (папір 2019): універсальне сховище відношень «користувач — роль — об'єкт» з перевіркою успадкування. Відкриті аналоги: SpiceDB, OpenFGA.
  • Presigned GET URL видаємо лише після перевірки прав і з коротким TTL — URL сам по собі є «ключем».
Аналогія для фронтендера
Курсор синхронізації — як cursor у GraphQL-пагінації або since_id у старому Twitter API: ви не питаєте «дай усе», ви питаєте «дай усе після X». Long poll — це fetch, який сервер навмисно не завершує, доки не з'являться дані (як await на промісі, що резолвиться подією). Conflicted copy — як merge conflict у git, тільки без маркерів <<<<<<<: обидві версії лежать поруч. Де аналогія ламається: курсор у GraphQL зазвичай про сортування видачі, а тут — про позицію в журналі змін, який мусить бути строго впорядкований у межах namespace.

Bottlenecks і trade-offs

  • Гарячий namespace (спільна папка компанії на 50 тис. людей): журнал одного namespace — послідовний, commit-и серіалізуються. Рішення: розбити на під-namespace-и, батчити commit-и, кешувати дельти.
  • Мільйони long-poll з'єднань: сервер нотифікацій на async-I/O (epoll), кожне з'єднання — кілька КБ пам'яті; шардування за namespace_id, pub/sub між вузлами.
  • Desktop-клієнт — частина системи: баги в ньому = масові повторні upload-и. Тому — rate limiting на сервері, backoff на клієнті, поступовий rollout версій клієнта.
  • Узгодженість метаданих vs дані в S3: коміт посилається на чанк, якого ще немає (S3 PUT не завершився)? Commit перевіряє наявність усіх чанків (HEAD або запис у таблиці chunks по event-у від S3).
🎯
Що кажуть сильні кандидати: «Нотифікація — лише підказка, джерело правди — журнал і курсор»; «commit з base_version = optimistic concurrency, конфлікт → conflicted copy, бо для файлів нема семантичного мерджу»; «дедуп між акаунтами — side channel, обмежу його»; «GC сиріт і ref_count — у тій самій транзакції, що й версія».
Follow-ups, до яких готуйтеся: як працює перейменування великої папки (це операція над метаданими, байти не рухаються); як синхронізувати 1 млн файлів при першому вході (snapshot + курсор, пагінація); як підтримати «selective sync»; як зробити E2E-шифрування і що воно ламає (дедуп, превʼю, пошук).
Sync = курсор у журналі + нотифікація-підказка + дельта за курсором. Конфлікт = optimistic concurrency + conflicted copy.
Частина III · YouTube / Netflix

05 YouTube / Netflix: вимоги, оцінки, API, дані, схема

Два різні продукти з однаковим ядром: «завантажили один раз — дивляться мільйони разів з краю мережі».

Спершу уточніть, який продукт: YouTube — user-generated content, мільйони завантажень на день, довгий хвіст переглядів. Netflix — невеликий каталог (десятки тисяч тайтлів), завантажує сама компанія, зате величезний і передбачуваний трафік переглядів у прайм-тайм. Ядро однакове, а акценти — різні.

Функціональні вимоги

  • Креатор завантажує відео (до кількох ГБ, може бути годинне 4K).
  • Глядач дивиться відео на будь-якому пристрої й мережі, без зависань, з автоматичним вибором якості.
  • Метадані: назва, опис, превʼю (thumbnail), лічильник переглядів, пошук.
  • Поза скоупом (проговорити): рекомендації, коментарі, лайв-стрімінг, монетизація, Content ID.

Нефункціональні вимоги

  • Перегляд: низький час старту (time-to-first-frame ≲ 1–2 с), мінімум rebuffering, висока доступність. Читань на порядки більше, ніж записів.
  • Завантаження: надійне (resumable), але обробка може йти хвилини — eventual «відео з'явиться за кілька хвилин» прийнятно.
  • Вартість: зберігання (багато версій кожного відео) і особливо egress-трафік — головні статті витрат.

06 Deep dive: upload-конвеєр і транскодування

Чому одне відео перетворюється на сотні файлів і як паралелізувати годинну роботу до хвилин.

Що таке транскодування і навіщо

Креатор завантажує файл у будь-якому форматі (MOV з iPhone у HEVC, MKV, 4K 60fps з ProRes…). Глядачам потрібні: (1) кілька роздільностей і бітрейтів — «драбина» (bitrate ladder) від ~240p до 4K; (2) кілька кодеків — H.264/AVC (грає скрізь), VP9 і AV1 (на 30–50% економніші, але дорожчі в кодуванні й не на всіх пристроях), HEVC для частини Apple-пристроїв; (3) нарізка на сегменти по кілька секунд для HLS/DASH; (4) аудіодоріжки (AAC/Opus), субтитри, превʼю.

DAG обробки

Кодувати годинне відео одним процесом — це години. Тому відео ріжуть на шматки по межах GOP (GOP, «group of pictures» — послідовність кадрів, що починається з ключового I-кадру; з I-кадру можна декодувати без попередніх) і кодують шматки паралельно на сотнях воркерів, а потім склеюють. Уся обробка — це орієнтований ациклічний граф (DAG) задач:

Як зробити конвеєр надійним

  • Кожна задача — ідемпотентна: вхід → вихід за детермінованим ключем (encoded/{video}/{rendition}/part_17). Повтор просто перезаписує той самий об'єкт.
  • Оркестратор DAG (стан у БД: які вузли готові) + черга задач. Воркер бере задачу, робить heartbeat; помер — задачу отримає інший після visibility timeout (як у SQS, див. туторіал 7).
  • Retries з лімітом і DLQ: «битий» файл не повинен нескінченно крутитися.
  • Пріоритети: спочатку швидко робимо 360p/720p H.264 → відео доступне за хвилини; 4K і AV1 доганяють пізніше (і AV1 — часто лише для популярних відео, бо кодування дороге, а економія трафіку окупається лише на великій кількості переглядів).
  • Компʼют: spot/preemptible-інстанси (задачі короткі й ідемпотентні — переривання не страшні), GPU або спеціалізовані чипи. Google публічно розповідав про власні чипи для кодування відео в YouTube (Argos VCU, 2021).
🏗️
Як це роблять у реальних системах. Netflix у 2015 році описав per-title encoding: драбина бітрейтів підбирається під кожен тайтл (мультфільм із пласкими кольорами стискається краще за бойовик зі зйомкою з рук), пізніше — кодування на рівні окремих сцен (shot-based / dynamic optimizer) і метрику якості VMAF. Медіа-конвеєр Netflix описано в блозі як платформу Cosmos (мікросервіси + workflow + serverless-функції). YouTube кодує в H.264, VP9 і AV1 залежно від популярності й пристрою.

Thumbnails (превʼю)

  • Генеруються в DAG: кандидати — кадри з різних точок (часто з фільтром «не розмитий, не чорний, є обличчя»); креатор може завантажити свій.
  • Зберігаються як звичайні зображення в object storage, роздаються через image-CDN із ресайзом під пристрій (srcset, WebP/AVIF).
  • Netflix публічно описував персоналізацію артворку: різним людям показують різні обкладинки одного тайтлу, вибір — бандит-алгоритми й A/B-тести.
  • «Sprite sheet» — один великий JPEG із сіткою мініатюр для прев'ю при наведенні на таймлайн плеєра (плюс WebVTT із координатами).
Аналогія для фронтендера
Транскодування — це «білд» для відео. Як ваш CI з одного src/ робить modern.js (ES2022) і legacy.js (з поліфілами), так конвеєр з одного оригіналу робить AV1 для сучасних пристроїв і H.264 для старих телевізорів. Thumbnails — як генерація srcset у next/image. Де аналогія ламається: білд фронтенду — секунди-хвилини на одній машині; кодування відео — CPU-години на кожне відео, тому розпаралелювання по GOP-шматках обов'язкове.
🚩
Red flags: «транскодую синхронно в запиті upload-у»; «один воркер кодує весь фільм»; немає стану DAG — після падіння починаємо все спочатку; кодуємо всі відео в усі кодеки одразу (дорого для довгого хвоста, який ніхто не дивиться).
Транскодування = DAG ідемпотентних задач на шматках по GOP; спершу швидкі якості, дорогі кодеки — для популярного.

07 Deep dive: HLS/DASH і adaptive bitrate у плеєрі

Найбільш «фронтендова» частина задачі: відео — це плейлист маленьких файлів, а плеєр сам вирішує, яку якість качати.

Як влаштовані HLS і DASH

HLS (HTTP Live Streaming, Apple) і MPEG-DASH (стандарт ISO) працюють однаково: відео в кожній якості нарізане на сегменти по 2–6 секунд, а маніфест (текстовий .m3u8 для HLS або XML .mpd для DASH) перелічує якості та сегменти. Усе — звичайні HTTP GET статичних файлів, тому їх ідеально кешує будь-який CDN. Формат CMAF (fragmented MP4) дозволяє мати одні й ті самі сегменти і для HLS, і для DASH — менше копій у сховищі.

Adaptive bitrate (ABR): логіка плеєра

Вибір якості робить клієнт, а не сервер. Плеєр після кожного сегмента знає: скільки байтів і за скільки часу скачав (оцінка пропускної здатності) і скільки секунд відео в буфері. Два класичні сімейства алгоритмів:

  • Throughput-based: беремо найвищий варіант, чий BANDWIDTH ≤ 0.8 × оцінки швидкості (оцінка — EWMA (EWMA — «експоненційно зважене ковзне середнє»: нові виміри важать більше, старі поступово «забуваються») за останні сегменти).
  • Buffer-based (BBA): що повніший буфер, то вищу якість можна дозволити; буфер порожніє — вниз. Netflix і Стенфорд опублікували цей підхід (SIGCOMM 2014, «A Buffer-Based Approach to Rate Adaptation»). Сучасні плеєри комбінують обидва (dash.js має гібрид, т. зв. DYNAMIC; Shaka, hls.js — свої евристики).

Фронтенд-реальність

  • Safari (macOS/iOS) грає HLS нативно в <video src="…m3u8">. В інших браузерах — JS-плеєр (hls.js, dash.js, Shaka Player), який сам качає сегменти через fetch і підкладає їх у <video> через Media Source Extensions (MSE): sourceBuffer.appendBuffer(bytes).
  • DRM: Encrypted Media Extensions (EME) + Widevine (Chrome, Android), FairPlay (Apple), PlayReady (Microsoft). Ліцензію видає наш license server після перевірки прав.
  • Метрики QoE з клієнта: time-to-first-frame, rebuffering ratio, середній бітрейт, кількість перемикань. Їх шлють beacon-ами — і це ті самі події, з яких рахують перегляди.
  • Live: та сама модель, але плейлист постійно оновлюється; Low-Latency HLS (часткові сегменти) знижує затримку з ~20–30 с до кількох секунд.
Аналогія для фронтендера
ABR — це <img srcset> на стероїдах. srcset дає браузеру список варіантів картинки, і він сам обирає за DPR і шириною в'юпорту. Master-плейлист — такий самий список, але вибір робиться знову після кожних 4 секунд з урахуванням реальної швидкості мережі і стану буфера. Де аналогія ламається: картинка вибирається один раз, а відео — постійно; і в плеєрі є стан (буфер), якого в img немає — саме буфер робить алгоритм цікавим.
🎯
На співбесіді: скажіть три речі: (1) «сегменти по 2–6 с, вирівняні по ключових кадрах, маніфест перелічує якості»; (2) «ABR — логіка клієнта: throughput + буфер, старт з низької якості для швидкого first frame»; (3) «оскільки сегменти — статичні immutable файли з унікальними URL, CDN кешує їх з довгим TTL; короткий TTL — лише для live-плейлистів». Trade-off довжини сегмента: короткі — швидший старт і перемикання, але більше запитів і гірше стиснення; довгі — навпаки.
HLS/DASH = маніфест + дрібні статичні сегменти; ABR вирішує клієнт після кожного сегмента, дивлячись на швидкість і буфер.

08 Deep dive: CDN, Open Connect, перегляди, пошук

Як роздати сотні терабіт за секунду, порахувати мільярди переглядів і знайти відео.

CDN для відео

Відеотрафік має сильний степеневий розподіл: невелика частка тайтлів дає більшість переглядів. Тому кеш на краю мережі має дуже високий hit ratio для «голови» і майже марний для «хвоста». Стратегії:

  • Pull CDN (Cloudflare, Akamai, CloudFront): edge бере сегмент з origin при першому промаху. Підходить для UGC (YouTube-подібне), де не знаєш наперед, що вистрілить.
  • Push / proactive fill: заливаємо популярне наперед. Підходить, коли каталог відомий (Netflix).
  • Ієрархія кешів: edge → regional (mid-tier) → origin shield → origin. Промах на edge не йде одразу в S3.
  • Сегменти immutable: URL містить версію/хеш, Cache-Control: max-age=31536000, immutable. Інвалідація не потрібна.
🏗️
Як це роблять у реальних системах. Netflix Open Connect — власний CDN: Netflix безкоштовно ставить свої кеш-сервери (Open Connect Appliances, OCA) у дата-центри провайдерів та точки обміну трафіком. Контент заливається в OCA проактивно в години низького навантаження на основі прогнозу популярності, а сервіс у AWS під час натискання «play» обирає, з яких OCA клієнту качати (steering), враховуючи здоров'я серверів і мережеву близькість. За публічними даними Netflix, практично весь відеотрафік іде через Open Connect, а AWS обслуговує все інше (логін, каталог, рекомендації). YouTube використовує власну мережу Google з кешами у провайдерів (Google Global Cache).

Лічильник переглядів у масштабі

Наївно: UPDATE videos SET views = views + 1 на кожен перегляд. При десятках тисяч переглядів на секунду для вірусного відео — це гарячий рядок, блокування і мертва база. До того ж «перегляд» треба валідувати (боти, накрутки, повтори).

  • Агрегація в пам'яті: stream job рахує video_id → +k за хвилину і робить один INCRBY замість тисячі.
  • Шардування гарячого лічильника: views:{id}:{0..15}, читання = сума шардів.
  • Дедуп: ключ (user/device, video, вікно часу); для унікальних глядачів — HyperLogLog (≈ 12 КБ на лічильник у Redis з похибкою ~0.81%).
  • Історичний курйоз: YouTube роками «заморожував» лічильник біля 301 перегляду, поки перевіряв, що перегляди справжні, — гарний приклад, що продукт свідомо обирав eventual consistency.

Метадані й пошук

  • Метадані (назва, опис, теги, канал) — в OLTP-базі; через CDC/outbox летять у пошуковий індекс (Elasticsearch/OpenSearch): інвертований індекс + ранжування за релевантністю, свіжістю, переглядами.
  • Субтитри та ASR-транскрипти теж індексуються — пошук по тому, що говорять у відео.
  • Typeahead — окрема задача (trie / префіксний індекс, див. туторіал 10).
  • Кеш сторінки відео: метадані популярних відео — у Redis/CDN з коротким TTL; лічильник — окремим запитом, щоб не інвалідувати весь кеш через кожен перегляд.

09 Web crawler: вимоги, оцінки, схема

Пошуковий краулер — це нескінченний цикл «взяти URL → скачати → розпарсити → додати нові URL». Уся складність — у масштабі та ворожому середовищі.

Вимоги

  • Мета (уточніть!): індекс для пошуку, архів (як Internet Archive / Common Crawl), моніторинг цін, навчальні дані для LLM. Від мети залежать пріоритети й свіжість.
  • Функціонально: стартові URL (seeds) → обійти веб, зберегти HTML, витягнути посилання, періодично оновлювати.
  • Не функціонально:
    • Ввічливість (politeness) — не покласти чужий сайт: ≤ 1 одночасне з'єднання на хост і пауза між запитами; поважати robots.txt.
    • Масштабованість — мільярди сторінок; горизонтально додаємо вузли.
    • Robustness — биті HTML, нескінченні редіректи, повільні сервери, пастки.
    • Extensibility — нові типи контенту (PDF, зображення) без переписування.

10 Deep dive: URL frontier, ввічливість, robots.txt, DNS

Mercator-дизайн frontier, правила robots.txt і чому DNS стає вузьким місцем.

Frontier за Mercator: front queues і back queues

Класичний дизайн з краулера Mercator (Heydon, Najork, 1999), який повторює і Alex Xu. Frontier розділений на дві частини:

  • Front queues — відповідають на питання «що важливіше». Prioritizer кладе URL у чергу F1…Fn за пріоритетом (PageRank, частота змін, тип сайту). Селектор частіше бере з високопріоритетних черг.
  • Back queues — відповідають на питання «коли можна». Кожна back-черга містить URL лише одного хоста. Heap тримає «час, коли хост знову можна чіпати». Fetcher бере хост з найменшим часом, качає один URL, кладе хост назад з часом now + delay.

Мінімальна робоча модель back-частини — словник «хост → FIFO» плюс heap за часом наступного дозволеного запиту:

frontier.py
import heapq
from collections import deque
from urllib.parse import urlsplit

class PoliteFrontier:
    """Mercator-style: одна FIFO-черга на хост + heap «коли хост знову можна чіпати»."""
    def __init__(self, delay: float = 1.0):
        self.delay = delay
        self.queues: dict[str, deque] = {}
        self.ready: list[tuple[float, str]] = []   # (next_allowed_time, host)

    def add(self, url: str, now: float = 0.0):
        host = urlsplit(url).hostname
        if host not in self.queues:
            self.queues[host] = deque()
            heapq.heappush(self.ready, (now, host))
        self.queues[host].append(url)

    def next_url(self, now: float):
        if not self.ready or self.ready[0][0] > now:
            return None                              # усі хости «відпочивають»
        _, host = heapq.heappop(self.ready)
        url = self.queues[host].popleft()
        if self.queues[host]:
            heapq.heappush(self.ready, (now + self.delay, host))
        else:
            del self.queues[host]
        return url

f = PoliteFrontier(delay=1.0)
for u in ["https://a.com/1", "https://a.com/2", "https://a.com/3",
          "https://b.org/x", "https://c.net/y"]:
    f.add(u)

t = 0.0
while f.queues:
    url = f.next_url(t)
    print(f"t={t:.1f}s -> {url}")
    t += 0.5

# t=0.0s -> https://a.com/1
# t=0.5s -> https://b.org/x
# t=1.0s -> https://c.net/y
# t=1.5s -> https://a.com/2
# t=2.0s -> None
# t=2.5s -> https://a.com/3

Зверніть увагу: три URL з a.com додані першими, але між ними фетчер встигає сходити на b.org і c.net, а на t=2.0 чесно чекає — a.com ще «відпочиває». У продакшені затримка адаптивна: якщо сервер відповідає за 2 с, наступний запит — через ~10× час відповіді (ідея з Mercator), а на 429/503 — backoff.

robots.txt

  • Стандартизований як RFC 9309 (Robots Exclusion Protocol, 2022) — після майже 30 років де-факто існування.
  • Групи правил за User-agent, директиви Allow/Disallow; при конфлікті перемагає найдовше (найконкретніше) правило; підтримуються * і $.
  • Crawl-delay — не входить у RFC; частина краулерів (Bing, Yandex) його поважає, Google — ігнорує. Sitemap: — підказка, де шукати URL.
  • Кешуємо robots.txt на хост (RFC рекомендує не довше 24 год). Якщо robots.txt повертає 5xx — вважаємо, що краулити не можна (повна заборона); 4xx — що можна все.
  • robots.txt — це домовленість, а не захист: справжній захист — авторизація. Але на співбесіді «поважаємо robots.txt» — обов'язково.

DNS — неочевидне вузьке місце

Кожен новий хост — DNS-запит, а системний резолвер (getaddrinfo) у багатьох середовищах блокуючий і серіалізований. Автори Mercator писали, що DNS спершу «з'їдав» значну частку часу потоків, і вони зробили власний асинхронний резолвер з кешем. Рішення:

  • Локальний кеш (host → IP) з повагою до TTL, але з нижньою межею (кешувати хоча б хвилини).
  • Асинхронний резолвер / локальний рекурсивний DNS-сервер (unbound) поруч із fetcher-ами.
  • Prefetch: резолвити хост, щойно URL потрапив у back-чергу, а не в момент fetch.
  • Ввічливість за IP, а не лише за hostname: тисячі піддоменів на shared-хостингу можуть бути одним сервером.
Аналогія для фронтендера
Back-черги — це те, що браузер робить сам: у HTTP/1.1 Chrome тримає максимум 6 з'єднань на хост, а решта запитів до цього хоста чекають у черзі, тоді як запити до інших доменів ідуть паралельно (звідси колишній трюк «domain sharding» з static1., static2.). Пауза між запитами — як throttle на обробнику скролу: «не частіше разу на N мс». DNS-кеш — як <link rel="dns-prefetch">. Де аналогія ламається: браузер обмежує себе заради власної продуктивності, а краулер — заради чужого сервера; і хостів у краулера мільйони, тож «6 з'єднань» на кожен — це DDoS.
🚩
Red flags: одна глобальна FIFO-черга (перша ж сторінка з 1000 посилань на свій сайт перетворить краулер на DDoS цього сайту); ігнорування robots.txt; синхронний DNS у кожному потоці; ввічливість лише за hostname.
Front queues — пріоритет, back queues — ввічливість (1 хост = 1 черга + heap за часом). robots.txt кешуємо, DNS кешуємо й резолвимо асинхронно.

11 Deep dive: дедуплікація, пастки, свіжість, масштаб

Dedup URL: нормалізація + «бачили?»

Спершу нормалізація, інакше HTTP://Example.com:80/a/../b?utm_source=x#top і http://example.com/b — «різні». Правила: нижній регістр схеми й хоста, прибрати порт за замовчуванням, розвʼязати ./.., прибрати #fragment, відсортувати параметри, видалити трекінгові (utm_*, fbclid), врахувати <link rel="canonical">.

Далі — «чи бачили ми цей URL?» на ~10 млрд елементів:

Bloom filter

  • m біт, k хеш-функцій. «Ні» — точно ні; «так» — можливо (false positive).
  • Розмір: m = −n·ln p / (ln 2)² (n — кількість елементів, p — бажана частка хибних «так»). Для n = 10¹⁰, p = 1% → ≈ 9.6 біт на URL → ≈ 12 ГБ, k ≈ 7.
  • Ціна FP: 1% нових URL ми помилково вважаємо баченими і ніколи не скачаємо. Для пошуку — прийнятно; для архіву — ні.
  • Не підтримує видалення (є counting Bloom / cuckoo filter).

Точний набір fingerprint-ів

  • Зберігаємо 8-байтовий хеш URL у шардованому KV (RocksDB, Cassandra) — 10¹⁰ × 8 Б ≈ 80 ГБ + індекси.
  • Колізії 64-бітного хешу на 10¹⁰ елементів — уже реальні (парадокс днів народження), але рідкісні; можна 128 біт.
  • Часто комбінують: Bloom у пам'яті як швидкий фільтр «точно новий», а на «можливо бачили» — точна перевірка в KV.

Dedup контенту: точні й майже-дублікати

Значна частка вебу — дублікати: дзеркала, версії для друку, сторінки, що відрізняються лише датою чи банером. Точні дублікати ловить хеш вмісту (MD5/SHA). Для майже-дублікатів потрібен хеш, у якого схожі документи дають схожі відбитки: SimHash (Charikar, 2002). Google описав його застосування в краулері в статті «Detecting Near-Duplicates for Web Crawling» (Manku, Jain, Das Sarma, WWW 2007): 64-бітні відбитки, документи вважаються майже-дублікатами, якщо відбитки відрізняються не більш ніж у ~3 бітах (на корпусі порядку 8 млрд сторінок).

simhash.py
import hashlib

def simhash(text: str, bits: int = 64) -> int:
    v = [0] * bits
    words = text.lower().split()
    for sh in words:                      # фічі = слова (у проді: шинґли + ваги)
        h = int.from_bytes(hashlib.md5(sh.encode()).digest()[:8], "big")
        for i in range(bits):
            v[i] += 1 if (h >> i) & 1 else -1
    return sum(1 << i for i in range(bits) if v[i] > 0)

def hamming(a: int, b: int) -> int:
    return bin(a ^ b).count("1")

base = 3 * ("system design interview web crawler must respect robots txt keep a polite "
        "rate per host deduplicate urls with a bloom filter and detect near duplicate "
        "pages with simhash fingerprints stored in a big table ")
near = base.replace("big table", "large table", 1) + "updated 2026"
other = "how to bake sourdough bread at home with a cast iron pot and a lot of patience"

a, b, c = simhash(base), simhash(near), simhash(other)
print("base vs near :", hamming(a, b))
print("base vs other:", hamming(a, c))

# base vs near : 2
# base vs other: 27

Ідея: кожна фіча «голосує» за кожен біт (+1 якщо біт хешу фічі = 1, −1 інакше), фінальний біт = знак суми. Невелика зміна тексту змінює кілька голосів — і перевертає лише ті біти, де голосування було майже нічиєю. Для випадкових документів відстань Геммінга ≈ 32 з 64 (тут 27). Як шукати «всі відбитки на відстані ≤ 3» серед мільярдів? Трюк зі статті: розбити 64 біти на блоки і тримати кілька відсортованих таблиць з перестановками блоків — якщо відстань ≤ 3, хоча б один блок збігається точно, і пошук стає точним пошуком префікса.

Crawler traps і ворожий веб

  • Нескінченні простори URL: календар з «наступний місяць» до 3000 року, фільтри магазину з усіма комбінаціями параметрів, session ID в URL, симлінк-петлі /a/b/a/b/a/b/….
  • Захист: ліміт глибини й довжини URL; ліміт сторінок на хост (бюджет); детектор повторюваних сегментів шляху; ігнорування відомих параметрів сесій; пріоритет хоста знижується, якщо він генерує багато «нових» сторінок з однаковим SimHash.
  • Spider traps навмисні і spam-ферми — ранжування та бюджет на домен, а не на URL.
  • Soft 404 — «сторінку не знайдено» зі статусом 200: ловиться через SimHash (усі однакові) або евристики.
  • Технічна гігієна: тайм-аути на з'єднання й читання, ліміт розміру відповіді, ліміт редіректів (≤ 5), перевірка Content-Type.

Свіжість (recrawl)

  • Сторінки змінюються з різною частотою: головна новинного сайту — щохвилини, стаття 2015 року — ніколи. Оцінюємо частоту змін для кожного URL (скільки разів з останніх N візитів вміст змінився) і плануємо наступний візит відповідно.
  • Conditional GET: If-Modified-Since / If-None-Match (ETag) → 304 Not Modified без тіла — дешевий recrawl.
  • Sitemaps з <lastmod>, RSS, push-протоколи (IndexNow, підтримують Bing і Yandex) — сайт сам каже, що змінилося.
  • Пріоритет recrawl = важливість × імовірність зміни. Окремий «швидкий» краулер для новин.

JavaScript-сторінки

Single-page застосунки без SSR повертають порожній <div id="root">. Рендеринг у headless Chrome коштує на порядок-два більше CPU, ніж парсинг HTML. Google описує свій процес як «crawl → render (у черзі, пізніше) → index». Висновок для фронтендера: SSR/SSG — досі найнадійніший шлях до індексації.

Розподіл по вузлах і сховище

  • Partition by host (а не за URL): інакше два вузли одночасно б'ють той самий сайт і потрібна розподілена координація. Consistent hashing — щоб додавання вузла переносило лише частку хостів (туторіал 5).
  • Гарячі хости (wikipedia.org, великі платформи) з дозволеною високою швидкістю — окремі «великі» back-черги або кілька вузлів з домовленою квотою.
  • Frontier на диску: мільярди URL не влазять у RAM — черги як файли/лог (Kafka-топік на вузол, RocksDB), у пам'яті лише голови черг.
  • Сховище сторінок: формат WARC (так зберігають Internet Archive і Common Crawl — великі стиснені файли з записами «запит + відповідь»), у S3. Для індексації — Bigtable-подібна таблиця. Хрестоматійний приклад з паперу Bigtable — «webtable» з ключем рядка у вигляді перевернутого URL (com.cnn.www), щоб сторінки одного домену лежали поруч.
  • Географія: fetcher-и ближче до сайтів (кілька регіонів) — менша латентність і правильні геоверсії сторінок.

Що кажуть сильні кандидати: «дві різні дедуплікації: URL — до скачування (Bloom, FP прийнятні для пошуку), контент — після (SimHash для майже-дублікатів)»; «партиціюю за хостом — ввічливість стає локальною»; «бюджет на хост захищає від пасток краще, ніж будь-які регулярки»; «recrawl планую за оцінкою частоти змін і використовую conditional GET».

12 Трікі питання

Питання, на яких «сиплються» навіть досвідчені кандидати. Спершу відповідайте самі, потім розгортайте.

TRICKYЧому б не зберігати файли просто в BLOB-колонці Postgres? Транзакції ж!

Для маленьких об'єктів (аватарка 20 КБ у невеликому застосунку) — можна. Для файлового сховища — ні:

  • База стає гігантською: бекапи, реплікація, VACUUM і відновлення займають дні; репліки копіюють ті самі гігабайти.
  • Байти йдуть через пул з'єднань БД і API-сервери — дорогий ресурс витрачається на тупе перекладання байтів.
  • Немає presigned URL, CDN, класів сховища (холодне/гаряче), multipart.
  • Ціна за ГБ у SSD-базі на порядок вища, ніж в object storage.

Транзакційність досягається інакше: байти спершу лягають в S3 під незмінним ключем (хеш), а транзакція в БД лише «публікує» версію, що на них посилається. Невдалий commit залишає сиріт, яких прибирає GC — це безпечно.

TRICKYДедуплікація між користувачами економить ПБ. Чому її обмежують?

Бо вона створює side channel: якщо завантаження файлу «миттєве» (сервер відповів «такий хеш уже є»), атакувальник дізнається, що хтось уже має цей файл. Це дозволяє перевіряти гіпотези («чи є в когось документ з моєю зарплатою і ПІБ колеги?» — перебором варіантів). Друга атака — «отримати файл за хешем»: якщо сервер віддає чанк кожному, хто знає його хеш, хеш стає паролем. Захист: дедуп лише в межах акаунта; або глобальний дедуп тільки на рівні зберігання (клієнт усе одно вантажить байти, сервер сам їх порівнює); або proof-of-ownership (сервер питає випадкові байти з файлу). Плюс шифрування на клієнті з унікальними ключами взагалі вимикає крос-дедуп.

COREЧому Dropbox використовував long polling, а не WebSocket?

Long poll дає майже ту саму латентність для сценарію «рідкісні події», але: (1) це звичайний HTTP-запит — проходить корпоративні проксі й фаєрволи, які колись ламали WebSocket; (2) сервер нотифікацій не тримає складного стану — лише «підписка на namespace»; (3) відповідь — лише «є зміни», тому втрата відповіді нічого не ламає. Мінус — накладні витрати на повторне встановлення запиту і заголовки. Сьогодні WebSocket/SSE — теж нормальний вибір; головне — нотифікація як підказка + дельта за курсором. Порівняння транспортів — у туторіалі 2.

TRICKYЧому вибір якості відео робить клієнт, а не сервер, який «бачить» мережу?

Бо сервер — це CDN-edge, який віддає статичні файли і нічого не знає про стан буфера плеєра, розмір екрана, енергозбереження, чи вкладка у фоні. Клієнт бачить усе це і реальну швидкість завантаження кожного сегмента. До того ж, коли логіка на клієнті, CDN лишається тупим кешем статики — це і є масштабованість. Сервер може підказувати: обмежувати драбину в маніфесті (наприклад, без 4K для мобільного тарифу) або steering на інший CDN, але рішення «яку якість наступним сегментом» — за плеєром.

ADVЧому межі сегментів мають збігатися в усіх якостях і що станеться, якщо ні?

Кожен сегмент має починатися з ключового кадру (IDR), щоб декодер міг стартувати з нього без попередніх кадрів. Якщо в 1080p сегмент 7 починається на 28.0 с, а в 360p — на 27.6 с, то при перемиканні після сегмента 6 плеєр або отримає «дірку»/дубль у часі, або муситиме декодувати з неключового кадру — артефакти, зависання. Тому енкодер налаштовують з фіксованим інтервалом ключових кадрів (наприклад, кожні 2 с) і «закритим» GOP (closed GOP — кадри групи не посилаються на кадри попередньої групи), однаково для всіх якостей. Це також вимога для паралельного кодування шматками.

TRICKYМи додали підписаний токен у URL сегментів — і hit ratio CDN упав майже до нуля. Чому?

Бо CDN за замовчуванням використовує повний URL з query-рядком як ключ кешу. У кожного користувача свій токен → кожен сегмент для кожного глядача — унікальний ключ → кожен запит — промах і похід в origin. Рішення: (1) виключити токен з cache key і перевіряти його на edge (CloudFront signed URLs/cookies, Akamai token auth, Cloudflare Workers роблять саме це); (2) підписувати не кожен сегмент, а шлях-префікс (signed cookie на /video/123/*); (3) для DRM-контенту сегменти взагалі можна не захищати токеном — вони зашифровані, а захищається видача ліцензії. Гарний приклад «невидимої» зміни, що ламає продуктивність.

COREBloom filter у краулері помиляється. Яка саме помилка можлива і чим вона загрожує?

Bloom filter дає лише false positives: «так, бачили» для URL, якого ми не бачили. False negatives неможливі — якщо елемент додано, всі його k біт виставлені. Для краулера це означає: частка нових URL (≈ p) буде пропущена назавжди. Для пошукової системи 1% пропущених сторінок зазвичай прийнятно: важливі сторінки ми все одно отримуємо через seeds і sitemaps, а повторне посилання на той самий URL не допоможе — той самий URL завжди дає ту саму помилку фільтра. Для архіву, де пропуск недопустимий, — точний набір у KV або Bloom лише як префільтр «точно новий». Ще один нюанс: Bloom не можна «почистити» від старих URL — для recrawl потрібна окрема структура з часом останнього візиту.

TRICKYЧому краулер партиціюють за хостом, а не за хешем URL — це ж рівномірніше?

Хеш URL справді рівномірніший, але тоді сторінки одного сайту розкидані по всіх вузлах, і ввічливість («1 запит на хост за раз, пауза 1 с») вимагає глобальної координації: розподілений лок або rate limiter на кожен хост — мільйони ключів і мережевий запит перед кожним fetch. Партиціювання за хостом робить це локальною структурою (heap у пам'яті вузла), а заодно DNS-кеш і кеш robots.txt теж стають локальними і мають високий hit ratio. Ціна — нерівномірність (гігантські хости); її лікують бюджетами на хост і окремою обробкою «великих» хостів.

ADVЯк завантажити файл 50 ГБ з браузера, щоб вкладка не впала і upload пережив перезапуск?
  • Не читати файл у пам'ять: File — це посилання на диск; file.slice(start, end) дає Blob шматка без копіювання всього файлу.
  • Хешування у Web Worker (SubtleCrypto не вміє стрімінгового SHA-256, тому — WASM-бібліотека або хеш кожного чанка окремо), щоб не блокувати UI.
  • Паралельні PUT по 3–6 чанків на presigned URL-и, ретраї з backoff, прогрес через XMLHttpRequest.upload.onprogress (у fetch прогресу upload досі немає стабільно).
  • Resume: upload_id і список завершених частин зберегти в IndexedDB; після перезапуску користувач заново обирає файл (доступу до диска без жесту немає), ми звіряємо розмір і lastModified і продовжуємо.
TRICKYЧи можна порахувати перегляди «exactly once»?

Наскрізного exactly-once через мережу з клієнтом не існує: beacon може загубитися (недорахуємо) або прийти двічі після ретраю (перерахуємо). Що реально: (1) ідемпотентність подій — кожен beacon має event_id, stream job дедуплікує у вікні; (2) exactly-once обробка всередині конвеєра (Kafka transactions + Flink checkpoints) — лише для шляху «Kafka → лічильник»; (3) визначення «перегляду» — бізнес-правило (≥ 30 с, не бот), а отже число завжди оцінка. Тому для продукту: приблизне швидке число + точний batch-перерахунок пізніше. Детальніше — туторіал 7.

Задача 1ЛегкоСкільки коштує зберігання Drive

100 млн користувачів, у середньому 5 ГБ даних. Історія версій додає 20%, дедуплікація зменшує на 30%. Скільки сховища потрібно і порядок місячної вартості в публічному object storage, якщо гарячий клас — порядку $0.02 за ГБ на місяць?

  1. Логічно: 100 млн × 5 ГБ = 500 ПБ.
  2. З версіями: 500 × 1.2 = 600 ПБ.
  3. Після дедупу: 600 × 0.7 = 420 ПБ = 420 млн ГБ.
  4. Вартість: 420 млн × $0.02 ≈ $8.4 млн на місяць (≈ $100 млн на рік), без трафіку й запитів.

Висновок для співбесіди: на такому масштабі власне сховище (як Magic Pocket у Dropbox) і агресивний tiering (холодні версії в архівний клас) — бізнес-рішення, а не інженерна забаганка. Реплікацію/erasure coding object storage вже враховано в ціні. Ціни в хмарі змінюються — перевіряйте актуальні.

Задача 2ЛегкоPresigned URL: що підписати і на скільки

Колега пропонує видавати клієнту presigned PUT URL на весь bucket з терміном дії 7 днів, «щоб не перевидавати». Що не так і як правильно?

  • URL на bucket = будь-хто, хто його перехопив (логи проксі, історія браузера, Sentry), може писати що завгодно куди завгодно тиждень.
  • Правильно: URL на конкретний ключ (chunks/{sha256}) і конкретний метод, TTL 5–15 хв; за можливості — обмеження Content-Length / Content-MD5 (для POST-policy — content-length-range).
  • Ключ визначає сервер, не клієнт: інакше клієнт перезапише чужий об'єкт.
  • Після upload сервер перевіряє хеш (або S3 checksum) перед commit — клієнту не довіряємо.
  • Протух URL посеред великого upload-у — клієнт просить новий для решти частин; це дешево.
Задача 3СередньоДельта для 2-гігабайтного файлу

Файл 2 ГіБ, чанки фіксовані 4 МіБ. Скільки чанків? Скільки даних передасть клієнт, якщо (а) перезаписати 10 КБ посередині без зміни довжини; (б) вставити 10 КБ посередині? А з CDC із середнім чанком 4 МіБ?

  1. Чанків: 2048 / 4 = 512.
  2. (а) Перезапис на місці не зсуває межі: змінюється 1 чанк (або 2, якщо 10 КБ потрапили на межу) → 4–8 МіБ. Тут fixed-size працює чудово — підступ у тому, що багато кандидатів одразу кажуть «fixed погано».
  3. (б) Вставка зсуває всі межі після точки вставки → змінюються ≈ 256 чанків → ≈ 1 ГіБ.
  4. CDC: і в (а), і в (б) змінюються 1–2 чанки → ≈ 4–8 МіБ.

Висновок: CDC важливий для файлів, у які вставляють (тексти, деякі формати архівів), і майже не потрібен для файлів, які переписують на місці (образи дисків, БД-файли) або дописують у кінець (логи). Додатковий нюанс: багато форматів (DOCX, стиснені архіви) після будь-якої правки перепаковуються цілком — тоді не допоможе жоден чанкінг.

Задача 4СередньоДебаг: видалені файли «воскресають»

Користувачі скаржаться: видаляють файл на ноутбуці, а за кілька годин він з'являється знову. Видалення реалізовано як DELETE FROM files WHERE id = ?. Що відбувається і як виправити?

  • Причина: інший пристрій (телефон) був офлайн і має файл локально. Коли він виходить онлайн, бачить «у мене є файл, на сервері немає» — і трактує це як новий локальний файл → upload. Сервер не має жодного сліду, що файл видаляли.
  • Виправлення: видалення — це tombstone: is_deleted = true, нова версія і запис у журнал. Пристрій, що повертається, отримує дельту «файл X видалено у версії 9» і видаляє локально.
  • Якщо пристрій офлайн змінював файл, а на сервері його видалили — це конфлікт «edit vs delete»: зберігаємо змінену версію (краще воскресити, ніж втратити правки) і показуємо користувачу.
  • Tombstones прибираємо GC не раніше, ніж через період, довший за максимальний офлайн пристрою (або змушуємо давно офлайн пристрій зробити повний resync).

Це та сама проблема, що й у leaderless-БД (Dynamo/Cassandra): без tombstones видалення «воскресають» через репліку, яка пропустила delete (туторіал 5).

Задача 5СередньоСховище й трафік одного відео

10-хвилинне відео, драбина H.264: 240p 0.4, 360p 0.8, 480p 1.4, 720p 2.8, 1080p 5 Мбіт/с; плюс те саме у VP9. Скільки займає? Скільки трафіку дасть 1 млн переглядів, якщо в середньому дивляться половину при 2.8 Мбіт/с?

  1. Сума бітрейтів: 0.4 + 0.8 + 1.4 + 2.8 + 5 = 10.4 Мбіт/с.
  2. За 600 с: 10.4 × 600 = 6240 Мбіт = 780 МБ на кодек.
  3. Два кодеки (VP9 трохи менший, але для оцінки — так само): ≈ 1.5 ГБ на відео + оригінал.
  4. Перегляд: 2.8 Мбіт/с × 300 с = 840 Мбіт = 105 МБ. 1 млн переглядів → ≈ 105 ТБ трафіку.

Порівняння: трафік від 1 млн переглядів у ~70 разів більший за все сховище цього відео. Тому для популярних відео окупається дорожче кодування (AV1, per-title), яке зменшить ці 105 ТБ на десятки відсотків, а для відео з 10 переглядами — ні.

Задача 6ЛегкоДовжина сегмента: VOD vs live

Для VOD-сервісу і для live-трансляції футболу виберіть довжину сегмента (2 с, 6 с, 10 с) і поясніть.

  • VOD: ~4–6 с (Apple рекомендує цільову тривалість 6 с). Менше запитів і накладних витрат, краще стиснення (довший GOP), а час старту рятує те, що перший сегмент беремо в низькій якості.
  • Live: затримка ≈ кілька сегментів (плеєр тримає 2–3 сегменти в буфері). Сегменти по 6 с → 20–30 с відставання — сусід закричить «гол» раніше. Тому 2 с або Low-Latency HLS / CMAF chunks (часткові сегменти по сотні мс) → затримка кількох секунд.
  • Ціна коротких сегментів: більше запитів до CDN і маніфестів, гірше стиснення, частіші оновлення плейлиста.
Задача 7СкладноОркестрація транскодування без повторів

Поточний дизайн: один воркер бере «відео» з черги і робить усе (split, encode, package). Якщо воркер падає на 90%, відео обробляється з нуля; деякі відео «застрягають» назавжди. Перепроєктуйте.

  1. Гранулярність: задача = (відео, rendition, шматок GOP). Годинне відео → сотні задач по 10–30 с роботи. Падіння втрачає одну дрібну задачу.
  2. Стан у БД: таблиця tasks(video, task_key, state, lease_until, attempts). Оркестратор (або workflow-рушій типу Temporal/Step Functions) запускає задачі, чиї залежності DONE.
  3. Lease + heartbeat: воркер бере задачу на 60 с і продовжує lease кожні 10 с. Помер — lease протух → задача знову PENDING.
  4. Ідемпотентний вихід: результат пишеться за детермінованим ключем; повтор перезаписує той самий об'єкт.
  5. Ліміт спроб + DLQ: після 3 невдач — FAILED, алерт; відео отримує статус FAILED, а не «застрягає».
  6. Watchdog: періодично шукати відео в PROCESSING довше за SLA.
Задача 8СередньоВірусне відео поклало origin

Нове відео популярного блогера: за 2 хвилини 5 млн глядачів. CDN має 300 edge-локацій, але origin (S3 + наш proxy) отримує шквал запитів і віддає 503. Чому, і що змінити?

Причина: кожна з 300 локацій (а в кожній — десятки серверів з власним кешем) має холодний кеш. Перші запити на кожен сегмент у кожному сервері — промахи, і всі одночасно йдуть в origin: thundering herd (туторіал 3). Тисячі серверів × сотні сегментів × кілька якостей.

  • Origin shield (CloudFront Origin Shield, Fastly shielding, Akamai tiered distribution) — усі edge ходять в 1–2 регіональні вузли.
  • Request coalescing / collapsed forwarding на кожному рівні: перший промах іде вгору, решта чекає його відповіді.
  • Prewarm: для очікуваних прем'єр — заздалегідь «прогріти» перші сегменти популярних якостей у CDN (Netflix-підхід з proactive fill).
  • Origin — це S3 без нашого proxy (або proxy з автомасштабуванням і load shedding, туторіал 8).
Задача 9ЛегкоРозмір Bloom filter

Скільки пам'яті потрібно Bloom filter-у на 1 млрд URL з часткою хибних «так» 1%? А 0.1%?

  1. Біт на елемент: −ln p / (ln 2)². Для p = 0.01: 4.605 / 0.4805 ≈ 9.6 біт.
  2. 10⁹ × 9.6 біт ≈ 9.6·10⁹ біт ≈ 1.2 ГБ. Хеш-функцій k = (m/n)·ln 2 ≈ 7.
  3. Для p = 0.001: 6.908 / 0.4805 ≈ 14.4 біт → ≈ 1.8 ГБ, k ≈ 10.

Правило для запам'ятовування: кожні ~4.8 біт на елемент зменшують FP у 10 разів. Порівняйте з точним набором 8-байтових хешів: 8 ГБ.

Задача 10СкладноДебаг: краулер DDoS-ить сайт

Власник сайту скаржиться: з ваших IP приходить 40 запитів/с, хоча ввічливість налаштована «1 запит/с на хост». Краулер — 40 вузлів, URL розподіляються між вузлами за hash(url) mod 40, кожен вузол має локальний heap ввічливості. Знайдіть усі причини й виправте.

  1. Головна: партиціювання за URL. Сторінки сайту розкидані на всі 40 вузлів, у кожного своя «1/с» → 40/с. Виправлення: hash(host) (а ще краще — за зареєстрованим доменом eTLD+1 або IP), consistent hashing.
  2. Піддомени: shop.site.com, img.site.com, api.site.com — різні хости, один сервер. Ввічливість за eTLD+1 / IP.
  3. Ретраї: на 503 fetcher одразу повторює — множник навантаження. Потрібен exponential backoff з jitter і зниження rate хоста на 429/503 (адаптивна ввічливість).
  4. Рендеринг JS: headless-браузер підтягує ще 50 ресурсів зі сторінки — їх теж треба рахувати в бюджеті хоста (або кешувати ресурси).
  5. Ребалансування: при додаванні вузла хост «переїжджає», а старий вузол ще дочищає чергу → короткочасно два вузли. Передача володіння з паузою/лізом.

Додатково: опублікувати User-Agent з контактом і сторінкою «як нас обмежити», поважати Crawl-delay, якщо вирішили його підтримувати.

Задача 11СередньоБюджет recrawl

Краулер має пропускну здатність 400 сторінок/с. В індексі 1 млрд сторінок. Як часто можна оновлювати кожну, і як розподілити бюджет розумніше, ніж рівномірно?

  1. 400 × 86 400 = 34.56 млн сторінок/добу → повний обхід ≈ 29 днів.
  2. Рівномірно — погано: новинна головна застаріє, а архівна стаття перевірятиметься марно.
  3. Розбийте на класи: «гарячі» 1% (10 млн, новини, головні сторінки) — щогодини: 10 млн × 24 = 240 млн/добу — це більше, ніж увесь бюджет! Отже, щогодини можна лише ~1 млн сторінок (24 млн/добу), решта ~10 млн/добу — на теплі й холодні.
  4. Пріоритет = важливість × P(змінилася з останнього візиту); P оцінюємо з історії змін (пуассонівська модель).
  5. Здешевити візит: conditional GET → 304 (без тіла), sitemaps з lastmod, IndexNow-пінги.

Головний висновок: бюджет — жорсткий ліміт, свіжість — задача оптимізації, а не «просто частіше».

Задача 12СкладноГаряча спільна папка на 50 тис. людей

Компанія тримає всю документацію в одній спільній папці; 50 тис. співробітників, сотні змін за хвилину. Сервер нотифікацій і шард метаданих цього namespace перевантажені. Що відбувається і що робити?

  • Fan-out нотифікацій: кожна зміна → 50 тис. long-poll відповідей → 50 тис. запитів дельти одночасно на один шард. Сотні змін за хвилину = мільйони запитів за хвилину на один namespace.
  • Коалесування: нотифікація каже лише «є зміни» — сервер може відповідати не частіше, ніж раз на N секунд на клієнта (debounce), об'єднуючи сотні змін в одну дельту.
  • Кеш дельт: дельта «від c41 до c42» однакова для всіх — кешувати її (Redis/CDN) за ключем (ns, from, to), а не будувати 50 тис. разів.
  • Read-репліки шарду для дельт; запис (commit) — на лідері.
  • Розбиття namespace на під-namespace-и (по підпапках), щоб журнал і курсори були меншими; клієнт підписується лише на ті, що синхронізує (selective sync).
  • Jitter на клієнтах: після «є зміни» чекати випадкові 0–5 с перед запитом дельти, щоб не було thundering herd.

Це та сама проблема «знаменитості» з туторіалу 10 (fan-out для акаунта з мільйонами підписників) — і ті самі ліки: коалесування, кеш, pull замість push для гарячих випадків.
