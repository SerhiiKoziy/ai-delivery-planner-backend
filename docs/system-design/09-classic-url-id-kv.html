01 Шаблон класичної задачі і ментальна модель

Чому саме ці чотири задачі, за яким сценарієм їх розв'язувати за 45 хвилин і що в кожній є «головним трюком».

URL shortener, генератор ID, key-value store і rate limiter — це «азбука» system design. Інтерв'юери люблять їх з простої причини: функціональних вимог мало (2–3 ендпоїнти), тож уся розмова йде про нефункціональні речі — масштаб, латентність, доступність, узгодженість. Тут не сховаєшся за складною бізнес-логікою: або ти розумієш, як генерувати унікальні ключі без єдиної точки відмови, або ні.

Крім того, ці задачі — будівельні блоки для більших. Чат потребує генератора ID (туторіал 10), будь-яка публічна API — rate limiter, а Cassandra чи DynamoDB, які ви «просто беретe» в інших задачах, — це і є Dynamo-style KV store з частини III. Коли на співбесіді про стрічку новин ви кажете «тут Cassandra», сильний інтерв'юер може спитати «а як вона влаштована всередині?» — і відповідь буде в цьому туторіалі.

Як читати цей туторіал

Кожна задача розібрана так, як її варто проговорювати вголос: спочатку уточнюємо вимоги (і явно кажемо, що не робимо), потім оцінки на серветці (back-of-the-envelope — «на звороті конверта»: грубі оцінки порядку величини, а не точні розрахунки), API, модель даних, high-level схема, а потім 2–4 deep dives — місця, де ховається вся складність. Наприкінці кожної задачі — блок «що кажуть сильні кандидати» і типові follow-up питання.

🎯
На співбесіді: у класичних задачах інтерв'юер майже завжди знає «канонічну» відповідь (Alex Xu, Hello Interview). Тому оцінюють не те, чи ви її знаєте, а як ви приймаєте рішення: чи називаєте альтернативи, чи пояснюєте, чому обрали одну, і чи бачите, де вона зламається. Фраза «є три варіанти, я беру другий, бо в нас читань у 100 разів більше, ніж записів, — і ось де він болить» коштує більше за ідеальну схему без пояснень.
🚩
Red flags у класичних задачах: одразу малювати коробки без вимог; казати «візьмемо MongoDB/Cassandra» без аргументу; один інстанс генератора ID чи один Redis без розмови про відмову; ігнорувати співвідношення читань і записів; не помічати, що ID можна перебрати (enumeration) чи що rate limiter сам стає single point of failure.
Класична задача = мало функціональних вимог + багато нефункціональних. Виграє той, хто чесно називає trade-offs.
Частина I · URL shortener (bit.ly, TinyURL)

02 URL shortener: вимоги, оцінки, API, дані, high-level

Найпопулярніша «перша» задача. Виглядає тривіально — таблиця «код → URL», — але відкриває розмову про генерацію ID, кешування, редиректи й зловживання.

Крок 1. Вимоги

Функціональні (FR)

  • За довгим URL створити короткий: https://sho.rt/hBxM5A4.
  • Перехід за коротким URL → редирект на оригінал.
  • Опційно: власний alias (sho.rt/my-sale), термін дії (expiration).
  • Опційно: аналітика кліків (кількість, країна, referrer).
  • Поза скоупом (кажемо явно): акаунти й UI, редагування цільового URL, QR-коди.

Нефункціональні (NFR)

  • Низька латентність редиректу — ціль p99 < ~50–100 мс (p99 — «99-й перцентиль»: 99% запитів швидші за це значення).
  • Висока доступність читань: биті короткі посилання в розісланих email — це втрачені гроші клієнта.
  • Коди унікальні і, бажано, не вгадувані послідовно.
  • Читань значно більше, ніж записів: типове припущення 10:1 … 100:1.
  • Масштаб: сотні мільйонів нових URL на день (уточнюємо!).

Крок 2. Оцінки

Припустимо (і проговорюємо це вголос): 100 млн нових URL на день, читань у 10 разів більше, зберігаємо 10 років, запис ≈ 500 байт (довгий URL, код, метадані).

Висновки з оцінок, які треба сказати вголос: (1) записів небагато — один кластер БД їх витримає, а от читання треба кешувати; (2) 180 ТБ — це вже не один Postgres-сервер, потрібен шардинг або KV/wide-column сховище; (3) 7 символів base62 вистачає із запасом у ~10 разів.

Крок 4. Модель даних

Доступ майже завжди за точним ключем (code → long_url), без join-ів і діапазонних запитів. Це ідеальний профіль для key-value / wide-column сховища (DynamoDB, Cassandra) або для шардованого за code реляційного кластера.

Крок 5. High-level схема

  1. Створення. Write API перевіряє URL (схема http/https, довжина, чорні списки доменів), бере наступний ID з локально закешованого діапазону, кодує його в base62 і робить INSERT. Для custom alias — INSERT … IF NOT EXISTS (умовний запис), щоб два користувачі не забрали той самий alias.
  2. Редирект. Redirect API шукає code у Redis; при промаху — у БД, кладе в кеш (cache-aside). Перевіряє expires_at і is_blocked, віддає 301/302, публікує подію кліку в Kafka (fire-and-forget з локальним буфером).
  3. Аналітика. Консюмери агрегують кліки (за хвилину/годину, країна, referrer) у колонкове сховище — ClickHouse, Druid, BigQuery.
Аналогія для фронтендера
Короткий код — як хеш у імені бандла main.3f9a1c.js: короткий ідентифікатор, за яким CDN віддає «справжній» вміст. А розділення читання й запису — як у React Query: мутація (useMutation) іде рідко й «важко», а запити (useQuery) — часто й мають обслуговуватися з кешу. Де ламається: хеш бандла детермінований від вмісту, а код шортенера зазвичай не залежить від URL (той самий URL від двох користувачів може мати два коди).
URL shortener = read-heavy KV: code → long_url. Розділяйте write path і read path, кешуйте читання, аналітику — асинхронно.

03 Deep dive: base62 і генерація коротких кодів

Головне питання задачі: звідки брати унікальний короткий код, коли пишуть десятки серверів одночасно. Чотири підходи, їхня математика і де кожен ламається.

Математика base62

Алфавіт base62 — це 0-9, a-z, A-Z: 10 + 26 + 26 = 62 символи, усі безпечні для URL (без +, /, =, як у base64). Код довжини k дає 62k варіантів:

62⁶ = 56 800 235 584 ≈ 5,7 × 10¹⁰   |   62⁷ = 3 521 614 606 208 ≈ 3,5 × 10¹²   |   62⁸ ≈ 2,2 × 10¹⁴

Тобто 7 символів — це ~3,5 трильйона кодів: для 365 млрд URL (наша оцінка на 10 років) заповнення ≈ 10%. Довжину коду обирають з умови 62k ≫ N (≫ — «значно більше»: з запасом на порядок), особливо якщо коди генеруються випадково: тоді ймовірність колізії росте разом із заповненням простору.

Кодування — звичайне переведення числа в систему числення з основою 62 (як у двійкову, лише цифр 62):

base62.py
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
BASE = len(ALPHABET)  # 62
INDEX = {ch: i for i, ch in enumerate(ALPHABET)}

def encode(n: int) -> str:
    if n == 0:
        return ALPHABET[0]
    out = []
    while n > 0:
        n, r = divmod(n, BASE)
        out.append(ALPHABET[r])
    return "".join(reversed(out))

def decode(s: str) -> int:
    n = 0
    for ch in s:
        n = n * BASE + INDEX[ch]
    return n

print(62 ** 6, 62 ** 7)            # ємність 6 і 7 символів
print(encode(125), decode("21"))   # 125 = 2*62 + 1
print(encode(10**12), decode(encode(10**12)))

Виведе 56800235584 3521614606208, 21 125 і hBxM5A4 1000000000000: трильйонний ID — це рівно 7 символів. Зверніть увагу: ID близько трильйона «займають» 7 символів, а перші мільйони — лише 4. Якщо потрібна фіксована довжина — доповнюють нулями зліва або починають лічильник з 62⁶.

Чотири способи отримати унікальний код

A. Хеш + обробка колізій — деталі

Беремо MD5/SHA-256 від long_url (або від long_url + user_id, якщо різні користувачі мають отримувати різні коди), кодуємо в base62, обрізаємо до 7 символів. Обрізання ламає унікальність: різні URL можуть дати однакові 7 символів. Тому:

  1. Пробуємо INSERT … IF NOT EXISTS (умовний запис; у SQL — INSERT … ON CONFLICT DO NOTHING). Саме умовний запис, а не «SELECT, потім INSERT», — інакше два паралельні запити пройдуть перевірку одночасно (класична race condition «check-then-act»).
  2. Якщо зайнято іншим URL — додаємо сіль (лічильник спроб) і повторюємо.
  3. Щоб не ходити в БД за кожною перевіркою, перед нею ставлять Bloom filter (Bloom filter — імовірнісна структура: «точно ні» або «можливо так») усіх зайнятих кодів: «точно вільний» — пишемо одразу.

За «парадоксом днів народження» перша колізія при випадкових 7-символьних кодах очікується вже після ~√(62⁷) ≈ 1,9 млн кодів (√ — «квадратний корінь»). Тобто колізії — не теоретична екзотика, а щоденна реальність, і код повинен їх обробляти.

C. Виділення діапазонів — деталі

Координатор (etcd, ZooKeeper або просто рядок у Postgres з UPDATE … SET next = next + 1000000 RETURNING) зберігає «наступний вільний ID». Кожен інстанс Write API при старті і при вичерпанні діапазону атомарно забирає блок, наприклад мільйон ID, і далі видає їх з пам'яті. При 3 000 записів/с на весь кластер координатор отримує запит раз на ~5 хвилин. Якщо інстанс упав — його недовикористаний діапазон просто втрачено; при 3,5 трлн можливих кодів це не проблема.

Проблема передбачуваності і як її прибрати

Послідовні ID дають послідовні коди: hBxM5A4, hBxM5A5, … Зловмисник може перебрати сусідні коди і знайти чужі приватні посилання (документи, інвойси, «секретні» Google Docs). Рішення — пропустити ID через біекцію (біекція — взаємно однозначне відображення: різні входи → різні виходи, можна обернути) на просторі [0, 62⁷): унікальність зберігається, а сусідні ID дають зовсім різні коди.

shuffle.py
from math import gcd
from base62 import encode   # з попереднього прикладу

SPACE = 62 ** 7                 # 3 521 614 606 208 можливих кодів
P = 2_176_477_521_739         # ≈ 0.618 · 62^7, непарне, не ділиться на 31
P_INV = pow(P, -1, SPACE)       # обернений елемент (Python 3.8+)
assert gcd(P, SPACE) == 1

def obfuscate(seq_id: int) -> str:
    """Біекція [0, 62^7) -> [0, 62^7): сусідні ID дають «несхожі» коди."""
    return encode(seq_id * P % SPACE).rjust(7, "0")

def restore(n: int) -> int:
    return n * P_INV % SPACE

for i in (1000, 1001, 1002):
    print(i, obfuscate(i))
print(restore(1001 * P % SPACE))

Виведе 1000 26Ess0E, 1001 EqngklJ, 1002 gK64cGO і відновлений 1001. Множення на число, взаємно просте з 62⁷, — найпростіша біекція; це обфускація, а не криптографія: знаючи кілька пар, множник можна вирахувати. Для сильнішого захисту використовують Feistel-шифр на потрібній кількості біт або бібліотеки на кшталт Sqids (колишні Hashids), а приватні посилання доповнюють довшим випадковим токеном.

🏭
Як це роблять у реальних системах. Публічних деталей внутрішньої генерації кодів у Bitly небагато, тому на співбесіді краще не вигадувати «як у Bitly». Відомий публічний приклад розподіленої генерації ID — Flickr ticket servers і Twitter Snowflake (розділ 5). YouTube-ідентифікатори відео (11 символів base64-подібного алфавіту ≈ 64 біти) — гарний приклад «короткий непослідовний ID поверх 64-бітного числа».
🎯
На співбесіді: «Мені потрібно ~365 млрд кодів, тому 7 символів base62. Варіанти: хеш з обробкою колізій, глобальний лічильник, діапазони, Snowflake. Беру діапазони з etcd: немає колізій, координатор не на гарячому шляху. Мінус — послідовні коди, тож пропускаю ID через біекцію. Якщо вимога "той самий URL — той самий код" — додаю індекс hash(long_url) → code».
🚩
Типові помилки: «беремо перші 7 символів MD5 — і все» (без обробки колізій); «SELECT, щоб перевірити, потім INSERT» (race condition); один Redis з INCR без відповіді на питання «а якщо він упав і втратив останні значення?» (після рестарту без AOF лічильник може повернутися назад і видати вже використані ID!); UUID у URL («короткий» код з 36 символів).
7 символів base62 ≈ 3,5 трлн кодів. Канон: діапазони ID з координатора + біекція проти перебору. Колізії хешів обробляються умовним записом, а не «перевір і встав».

04 Deep dive: 301 чи 302, аналітика, кеш, custom aliases, expiration, abuse

Друга половина задачі — шлях читання. Тут інтерв'юер перевіряє, чи ви розумієте HTTP-кешування, як масштабувати 30 000+ читань/с і як не стати хостингом для фішингу.

301 Moved Permanently vs 302 Found

301 Moved Permanently

  • Браузер може кешувати редирект без обмеження в часі, якщо немає Cache-Control.
  • Менше трафіку на сервіс, швидше для користувача.
  • SEO: «вага» посилання передається цільовій сторінці.
  • Неможливо надійно «перенаправити» посилання на іншу ціль чи заблокувати — у браузерах лишився старий редирект.

302 Found / 307 Temporary Redirect

  • Кожен клік проходить через сервіс → повна аналітика.
  • Можна змінити ціль, заблокувати фішинг, закінчити термін дії.
  • Більше навантаження (але ми все одно кешуємо на сервері).
  • 307 зберігає метод запиту (POST лишається POST); для GET-кліків різниці немає.

Тонкість, що вирізняє сильних кандидатів: вибір не бінарний. Можна віддавати 301 з коротким Cache-Control: private, max-age=90 — браузер кешує лише на 90 секунд (захист від подвійних кліків), CDN-и не кешують (private), а аналітика втрачає лише повтори протягом цього вікна. Великі шортенери, за їхніми ж довідковими статтями, віддають саме 301 (через SEO), але з контрольованим кешуванням — перевіряйте актуальну поведінку curl -I.

Аналітика кліків без шкоди для латентності

Подія кліку (code, ts, ip → country, user_agent, referrer) пишеться асинхронно: Redirect API кладе її в локальний буфер і пачками відправляє в Kafka; редирект віддається, не чекаючи підтвердження. Далі stream-обробка (Flink/Kafka Streams) або батчі агрегують кліки у ClickHouse/Druid. Якщо Kafka тимчасово недоступна — втрачаємо частину аналітики, але не редиректи: це правильний пріоритет. Точні лічильники «унікальних відвідувачів» дорогі — для них беруть HyperLogLog (HyperLogLog — імовірнісна структура для оцінки кількості унікальних елементів з похибкою ~1% у кількох КБ пам'яті).

Кешування гарячих посилань

Політика — cache-aside з TTL, бо code → long_url майже незмінне (детально про патерни — туторіал 3). Інвалідація потрібна лише при блокуванні посилання чи зміні цілі: видаляємо ключ з Redis і публікуємо подію «invalidate» для локальних LRU (або тримаємо їм короткий TTL ~30–60 с). Негативне кешування: «такого коду немає» теж кешуємо на коротко, інакше бот, що перебирає коди, пробиває кеш і б'є в БД (cache penetration).

Custom aliases

  • Alias живе в тому самому просторі ключів, що й згенеровані коди. Щоб вони не конфліктували, або забороняють aliases рівно з 7 символів base62, або резервують окремий префікс/довжину.
  • Резервування — тільки умовним записом (IF NOT EXISTS), без «перевір і встав».
  • Валідація: дозволені символи, довжина, чорний список (admin, login, api, образливі слова, назви брендів — тайпсквотинг).

Expiration

  • Лінива перевірка при читанні: expires_at < now() → 404/410 Gone. Дешево і завжди коректно.
  • Фонове прибирання: батч-джоб або нативний TTL сховища (DynamoDB TTL, Cassandra USING TTL, Redis EXPIRE) — звільняє місце. Нативний TTL видаляє не миттєво (DynamoDB — протягом днів, за документацією), тому лінива перевірка все одно потрібна.
  • Повторне використання прострочених кодів — зазвичай погана ідея: старе посилання в чиємусь PDF раптом поведе на чужий сайт. Простір 62⁷ достатньо великий, щоб не перевикористовувати.

Abuse: фішинг, спам, перебір

  • Rate limit на створення (per API key / IP) — частина IV туторіалу.
  • Перевірка цільових URL через репутаційні сервіси (наприклад, Google Safe Browsing API) синхронно при створенні та асинхронно повторно; прапорець is_blocked + інвалідація кешу.
  • Проміжна сторінка-попередження для підозрілих посилань; заборона редиректу на інші шортенери (ланцюжки ховають ціль).
  • Захист від перебору: непослідовні коди, rate limit на 404, негативне кешування.
Аналогія для фронтендера
301 vs 302 — це як Cache-Control: immutable на хешованому бандлі проти no-cache на index.html. Хешований бандл кешують «назавжди», бо він ніколи не змінюється, а index.html перевіряють щоразу, бо він може вказувати на нову версію. Короткий редирект теж: якщо ціль може змінитися або нам потрібна кожна взаємодія — не дозволяйте кешувати надовго. Де ламається: бандл ви можете «інвалідувати» новим іменем файлу, а закешований у чужому браузері 301 ви вже не відкличете.

Follow-up питання, до яких варто бути готовим

  • Як зробити, щоб той самий long_url від того самого користувача повертав той самий код? (індекс hash(user_id, long_url) → code, idempotency key)
  • Як порахувати топ-100 посилань за останню годину? (туторіал 12, Top-K)
  • Як мігрувати з 6 на 7 символів? (просто подовжити: старі коди лишаються валідними, бо простори не перетинаються, якщо нові ≥ 62⁶)
  • Як працювати в multi-region active-active? (діапазони ID для кожного регіону окремо — колізій не буде)
  • Що робити, якщо Redis упав? (local LRU + БД витримують деградований режим; rate limit на промахи; прогрів кешу)
Read path: CDN → local LRU → Redis → БД, негативне кешування, 302 або 301 з коротким max-age. Аналітика — асинхронно. Коди не перевикористовуємо, фішинг блокуємо прапорцем + інвалідацією.
Частина II · Генератор унікальних ID

05 Генератор ID: вимоги і варіанти — UUID, ticket servers, Snowflake

«Спроєктуйте сервіс, що видає унікальні ID для твітів/повідомлень/замовлень у розподіленій системі». Задача про те, як отримати унікальність і порядок без єдиного лічильника.

Вимоги

Функціональні

  • Кожен виклик повертає унікальний ID (ніколи не повторюється, навіть після рестартів).
  • ID — числові, 64 біти (влазять у BIGINT, швидкі індекси).
  • ID приблизно впорядковані за часом (k-sorted): новіші → більші. Потрібно для пагінації «нові спочатку» і кластеризації в БД.

Нефункціональні

  • Масштаб: десятки–сотні тисяч ID/с на весь кластер.
  • Латентність генерації — мікросекунди; бажано без мережевого виклику.
  • Висока доступність: немає SPOF (single point of failure — єдина точка відмови).
  • Строгий глобальний порядок не потрібен (уточнюємо! якщо потрібен — це зовсім інша задача).

Ticket servers (Flickr, 2010) і виділення діапазонів

Flickr описав у блозі «Ticket Servers: Distributed Unique Primary Keys on the Cheap» дуже прагматичне рішення: окремий MySQL-сервер з однією таблицею, де REPLACE INTO Tickets64 (stub) VALUES ('a'); SELECT LAST_INSERT_ID(); повертає наступне число. Щоб не було SPOF — два сервери: один з auto_increment_increment=2, offset=1 (непарні), інший з offset=2 (парні), клієнти ходять по черзі. Мінуси: мережевий виклик на кожен ID і відсутність глобального порядку між серверами (один може «втекти» вперед).

UUID: v4 vs v7

UUIDv4 — 122 випадкові біти: генерується будь-де без координації, ймовірність колізії мізерна. Але як первинний ключ у B-tree він поганий: кожна вставка потрапляє у випадкову сторінку індексу → page splits, погана локальність кешу, роздуття індексу. UUIDv7 (стандартизований у RFC 9562, 2024) виправляє це: 48 старших біт — Unix-час у мілісекундах, тож вставки йдуть «у кінець» індексу. Ціна — 128 біт замість 64 (більші індекси й foreign keys) і витік часу створення з ID (іноді це проблема приватності).

Instagram: ID, що знає свій шард

Instagram у 2012 описав («Sharding & IDs at Instagram») генерацію ID прямо в Postgres: PL/pgSQL-функція збирає 41 біт часу, 13 біт логічного шарду (тисячі логічних шардів на меншій кількості фізичних серверів) і 10 біт послідовності (nextval() % 1024). Бонус: з ID одразу видно, у якому шарді лежить запис — не потрібен окремий lookup. Той самий трюк використовують, коли ID поста містить шард автора.

🏭
Як це роблять у реальних системах. Twitter Snowflake (2010, відкритий код, згодом архівований) — сервіс на Thrift, що видає 64-бітні ID; власна епоха 1288834974657 мс (листопад 2010). Discord використовує Snowflake-формат з епохою 2015-01-01 — тому з ID повідомлення в Discord можна дістати час його створення. Sonyflake (Sony) змінює баланс: 39 біт часу в одиницях по 10 мс (~174 роки), 8 біт лічильника, 16 біт машини. MongoDB ObjectId (12 байт) теж починається з timestamp у секундах.
🎯
На співбесіді: спочатку уточніть, чи потрібен строгий глобальний порядок. Майже завжди відповідь «ні, достатньо приблизного» — і тоді Snowflake. Якщо «так» — це вже консенсус/єдиний секвенсор (повільно, дорого) або TrueTime (Spanner) — згадайте й переходьте далі. Назвіть, що UUIDv4 як PK шкодить B-tree, а UUIDv7 — компроміс без координації.
Час у старших бітах = сортування за часом + дружба з B-tree. Snowflake: 41 час + 10 машина + 12 лічильник. UUIDv7 — те саме без координації, але 128 біт.

06 Deep dive: Snowflake — годинник, worker_id і порядок

Snowflake здається тривіальним: зсуви бітів. Уся складність — у годиннику, що може піти назад, і в гарантії, що два процеси не отримають однаковий worker_id.

Реалізація

snowflake.py
import threading, time

EPOCH_MS = 1288834974657          # епоха Twitter (4 листопада 2010)
WORKER_BITS, SEQ_BITS = 10, 12
MAX_SEQ = (1 << SEQ_BITS) - 1     # 4095

class Snowflake:
    def __init__(self, worker_id: int):
        assert 0 <= worker_id < (1 << WORKER_BITS)
        self.worker_id = worker_id
        self.last_ms = -1
        self.seq = 0
        self.lock = threading.Lock()

    def next_id(self) -> int:
        with self.lock:
            now = int(time.time() * 1000)
            if now < self.last_ms:                 # годинник пішов назад
                raise RuntimeError(f"clock moved back {self.last_ms - now} ms")
            if now == self.last_ms:
                self.seq = (self.seq + 1) & MAX_SEQ
                if self.seq == 0:                  # 4096 ID за мс вичерпано
                    while now <= self.last_ms:     # чекаємо наступну мс
                        now = int(time.time() * 1000)
            else:
                self.seq = 0
            self.last_ms = now
            return ((now - EPOCH_MS) << (WORKER_BITS + SEQ_BITS)) \
                   | (self.worker_id << SEQ_BITS) | self.seq

def parse(id_: int):
    seq = id_ & MAX_SEQ
    worker = (id_ >> SEQ_BITS) & ((1 << WORKER_BITS) - 1)
    ms = (id_ >> (WORKER_BITS + SEQ_BITS)) + EPOCH_MS
    return ms, worker, seq

gen = Snowflake(worker_id=7)
ids = [gen.next_id() for _ in range(5)]
print(ids == sorted(ids), len(set(ids)))
print(parse(ids[0])[1:])                         # (worker, seq)
years = (1 << 41) / 1000 / 3600 / 24 / 365.25
print(f"41 біт мілісекунд ≈ {years:.1f} років")

Виведе True 5 (ID зростають і унікальні), (7, 0) (worker 7, перший у своїй мілісекунді) і 41 біт мілісекунд ≈ 69.7 років. Пропускна здатність одного воркера — 4 096 ID за мілісекунду ≈ 4 млн/с, на 1 024 воркерах — ~4 млрд/с теоретично. Вузьке місце ніколи не тут.

Ємність бітів — що варто вміти порахувати

  • 41 біт мс: 2⁴¹ мс ≈ 69,7 року від власної епохи. Саме тому епоху ставлять на дату запуску, а не на 1970 рік — інакше «з'їли» б 40+ років.
  • 10 біт машини = 1 024 воркери (Twitter ділив на 5 біт датацентру + 5 біт воркера).
  • 12 біт лічильника = 4 096 ID/мс на воркер. Вичерпали — чекаємо наступну мілісекунду (busy-wait у коді).
  • Старший знаковий біт = 0, щоб ID був додатним у мовах зі знаковим int64 (Java long).

Годинник іде назад

Чому годинник іде назад: NTP-корекція кроком (step) замість плавного slew, ручна зміна часу, міграція VM, leap second. Стратегії:

  1. Відмовити (як оригінальний Snowflake): кидати помилку, поки now < last_ms. Клієнт ретраїть на іншому воркері.
  2. Почекати, якщо відставання мале (кілька мс), — busy-wait до last_ms.
  3. Логічний годинник: продовжувати від last_ms, ніби час не йшов назад (позичати час «з майбутнього»), — так роблять гібридні логічні годинники (HLC), див. туторіал 6.
  4. Профілактика: налаштувати NTP/chrony на slew-режим (плавне підстроювання), leap smearing (Google і AWS «розмазують» високосну секунду на години).

Ще тонший випадок — рестарт процесу: last_ms у пам'яті втрачено. Якщо після рестарту годинник раптом відстає — дублікати. Захист: при старті почекати кілька секунд або персистити «high watermark» часу.

Як роздати worker_id

  • Статична конфігурація — просто, але помилка оператора = два процеси з однаковим ID = дублікати. Найнебезпечніший варіант.
  • ZooKeeper/etcd: при старті воркер створює ephemeral-вузол / lease з номером; номер звільняється, коли сесія вмирає. Так робив оригінальний Snowflake (ZooKeeper).
  • Kubernetes StatefulSet: ordinal поду (idgen-7) → worker_id 7. Просто, але треба гарантувати, що два поди з тим самим ordinal не живуть одночасно (StatefulSet цього намагається не допускати).
  • Вбудувати генератор у кожен сервіс (бібліотека, а не окремий сервіс): тоді worker_id = ідентифікатор інстансу. Немає мережевого виклику — найпоширеніший варіант сьогодні.

Порядок: що гарантує, а що ні

Snowflake ID — k-sorted: усередині одного воркера строго зростають, між воркерами — впорядковані з точністю до розбіжності годинників (зазвичай мілісекунди, з NTP — до десятків мс). Тобто ID повідомлення з сервера A може бути меншим за ID повідомлення, яке реально створили на сервері B на 2 мс раніше. Для стрічки чи чату це нормально (туторіал 10), для фінансового журналу — ні: там потрібен строгий порядок у межах рахунку (секвенсор на партицію).

Аналогія для фронтендера
Тимчасовий ID для optimistic UI — crypto.randomUUID() чи Date.now() + Math.random() на клієнті — та сама задача: унікальність без сервера. Snowflake — це «Date.now() + номер вкладки + лічильник у межах мілісекунди». І так само, як Date.now() у браузері може стрибнути назад, коли користувач змінив системний час (тому для вимірювань беруть монотонний performance.now()), Snowflake мусить захищатися від немонотонного годинника. Де ламається: performance.now() монотонний лише в межах сторінки, а ID мусять бути унікальними між рестартами й машинами.
🎯
Що кажуть сильні кандидати: «Генератор — бібліотека в кожному сервісі, не окремий мережевий сервіс. worker_id — з lease в etcd, щоб два процеси ніколи не мали однаковий. Годинник — chrony у slew-режимі, а в коді — перевірка now < last_ms з очікуванням або відмовою. Порядок — k-sorted; якщо бізнесу потрібен строгий порядок у межах сутності, роблю секвенсор на партицію».
🚩
Red flags: «беремо timestamp у мілісекундах як ID» (дві події в одну мс на різних серверах = колізія); «UUIDv4 як PK у MySQL — нормально на мільярдах рядків» (fragmentation); не згадати годинник; worker_id з конфігу без захисту від дублювання.

Follow-up питання

  • Як зробити ID коротшим для URL? (base62 від 64-біт → до 11 символів; або менше біт часу і більша одиниця — як Sonyflake)
  • Що буде через 69 років? (змінити епоху/розкладку — нові ID лишаються унікальними, якщо старші біти відрізняються; або перейти на 128 біт)
  • Як перевірити, що немає дублікатів у продакшені? (унікальний індекс у БД як остання лінія оборони + метрика конфліктів)
  • Чи можна з ID дізнатися щось приватне? (час створення, кількість воркерів, приблизну швидкість створення — так, Snowflake/UUIDv7 «протікають»)
Snowflake ламається лише двома способами: годинник пішов назад або два воркери з однаковим worker_id. Захист: last_ms + wait/refuse, lease в etcd/ZooKeeper.
Частина III · Розподілене key-value сховище (Dynamo-style)

07 KV store: вимоги, API, partitioning і реплікація

«Спроєктуйте розподілене key-value сховище» — задача-«матрьошка»: у ній уся теорія туторіалів 4–6. Канонічна відповідь — Amazon Dynamo (2007) і його нащадки Cassandra, Riak, ScyllaDB.

Вимоги

Функціональні

  • put(key, value), get(key), delete(key).
  • Ключі й значення — невеликі (значення до ~1 МБ, типово < 10 КБ).
  • Немає транзакцій між ключами, немає запитів за діапазоном (уточнюємо!).

Нефункціональні

  • Always writable: запис має проходити навіть при падінні вузлів і мережевих розділеннях (AP за CAP).
  • Горизонтальне масштабування: додаємо вузли — росте ємність і пропускна здатність.
  • Низька латентність на p99.9, бо одна сторінка робить десятки запитів до сховища.
  • Налаштовувана узгодженість (tunable consistency): клієнт обирає між швидкістю і свіжістю.
  • Немає «головного» вузла: всі вузли рівноправні (симетрія, децентралізація).

Контекст із Dynamo paper: Amazon хотів, щоб кошик покупок можна було оновити завжди — відмова в записі = втрачений продаж. Тому дизайн свідомо жертвує узгодженістю заради доступності запису, а конфлікти розв'язує при читанні.

API

kv_api.txt
get(key) -> [(value, context), ...]      # може повернути КІЛЬКА версій-конфліктів
put(key, value, context)                 # context = vector clock прочитаної версії
delete(key, context)                     # насправді пише tombstone
# Налаштування на рівні запиту/таблиці: N (реплік), R, W (кворуми)

Важлива деталь, про яку часто забувають: get повертає не одне значення, а список, якщо є конкурентні версії, а put приймає context — «я оновлюю ось цю версію». Без цього неможливо коректно мерджити конфлікти.

Partitioning: consistent hashing з віртуальними вузлами

ring.py
import bisect, hashlib
from collections import Counter

def h(key: str) -> int:
    return int.from_bytes(hashlib.md5(key.encode()).digest()[:8], "big")

class Ring:
    def __init__(self, nodes, vnodes=100):
        self.points = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))
        self.hashes = [p for p, _ in self.points]

    def preference_list(self, key: str, n: int = 3):
        """Перші n РІЗНИХ фізичних вузлів за годинниковою стрілкою від h(key)."""
        i = bisect.bisect(self.hashes, h(key))
        out = []
        while len(out) < n:
            node = self.points[i % len(self.points)][1]
            if node not in out:
                out.append(node)
            i += 1
        return out

ring = Ring(["A", "B", "C", "D", "E"])
print(ring.preference_list("user:42"))
load = Counter(ring.preference_list(f"k{i}", 1)[0] for i in range(100_000))
print(sorted(load.items()))

Виведе ['B', 'E', 'A'] — preference list для ключа (конкретні вузли залежать від хешу) — і розподіл 100 000 ключів між 5 вузлами: від ~17,6 до ~22,6 тисяч. Без vnodes (1 точка на вузол) розкид був би в рази. Детально про consistent hashing — туторіал 5.

Реплікація

Кожен ключ зберігається на N вузлах (типово N = 3), бажано в різних зонах доступності. Реплікація leaderless: будь-який вузол з preference list може прийняти запис. Клієнт або звертається до вузла-координатора (через partition-aware драйвер, який знає кільце), або до будь-якого вузла, який перешле запит координатору.

🏭
Як це роблять у реальних системах. Dynamo (внутрішній сервіс Amazon, paper 2007) — саме такий дизайн. Cassandra взяла з Dynamo кільце, кворуми, hinted handoff, gossip, а модель даних і LSM-сховище — з Google Bigtable. Важливо: Amazon DynamoDB — це інший сервіс з тим самим іменем. За paper'ом DynamoDB (USENIX ATC 2022) він використовує лідера на кожну партицію з Multi-Paxos, а не leaderless-кворуми з vector clocks. Сплутати Dynamo і DynamoDB на співбесіді — класична помилка.
🎯
На співбесіді: одразу задайте каркас: «Партиціювання — consistent hashing з vnodes; реплікація — N=3 на наступні різні вузли в різних AZ; узгодженість — кворуми R/W; конфлікти — vector clocks або LWW; відновлення — hinted handoff (тимчасові збої) і Merkle trees (постійні розбіжності); членство — gossip; сховище вузла — LSM». Це 7 «цеглинок» — дальше кожну можна розкрити.
Dynamo-style KV = consistent hashing + N реплік без лідера + кворуми + розв'язання конфліктів + anti-entropy + gossip + LSM на кожному вузлі.

08 Кворуми, конфлікти, sloppy quorum і hinted handoff

Як leaderless-сховище дає «налаштовувану» узгодженість, що відбувається, коли два клієнти пишуть одночасно, і як писати, коли репліка лежить.

Кворуми: R + W > N

Запис вважається успішним, коли його підтвердили W реплік з N; читання опитує R реплік і бере найновішу версію. Якщо R + W > N, множини реплік читання й запису гарантовано перетинаються хоча б в одній репліці — і читання побачить останній підтверджений запис (за ідеальних умов).

Конфігурація (N=3)ВластивістьКоли
W=1, R=1Найшвидше, найдоступніше, можливі застарілі читанняКеш, метрики, сесії
W=2, R=2Баланс: кворум, витримує падіння 1 вузлаТиповий дефолт (Dynamo paper: (3,2,2))

⚠️
Трікі: навіть строгий кворум R + W > N не дає лінеаризованості. Приклади: (1) конкурентні записи з LWW губляться; (2) запис пройшов на 1 репліку з 3 і «впав» — не відкочується, частина читань його бачить, частина — ні; (3) sloppy quorum ламає перетин. Для лінеаризованості потрібні read repair синхронно перед поверненням + додаткові механізми, або консенсус (Raft/Paxos). Детально — туторіал 6 і DDIA, розділ про leaderless replication.

Конфлікти: vector clocks vs LWW

Без лідера два клієнти можуть одночасно записати той самий ключ через різні вузли. Хтось має вирішити, яка версія «правильна» — або визнати, що обидві.

vclock.py
def compare(a: dict, b: dict) -> str:
    keys = a.keys() | b.keys()
    a_le_b = all(a.get(k, 0) <= b.get(k, 0) for k in keys)
    b_le_a = all(b.get(k, 0) <= a.get(k, 0) for k in keys)
    if a_le_b and b_le_a: return "equal"
    if a_le_b: return "a → b (b новіша, a можна викинути)"
    if b_le_a: return "b → a (a новіша)"
    return "concurrent (конфлікт: повернути обидві версії)"

v1 = {"Sx": 1}                    # запис через вузол Sx
v2 = {"Sx": 2}                    # ще один запис через Sx
v3 = {"Sx": 2, "Sy": 1}           # клієнт 1 пише через Sy
v4 = {"Sx": 2, "Sz": 1}           # клієнт 2 паралельно пише через Sz
print(compare(v1, v2))
print(compare(v3, v4))
merged = {k: max(v3.get(k, 0), v4.get(k, 0)) for k in v3.keys() | v4.keys()}
merged["Sx"] += 1                 # reconcile записується через Sx
print(dict(sorted(merged.items())))

Виведе a → b (b новіша, a можна викинути), concurrent (конфлікт: повернути обидві версії) і злиту версію {'Sx': 3, 'Sy': 1, 'Sz': 1} — рівно D5 з діаграми.

Vector clocks (Dynamo, Riak)

  • Точно розрізняють «новіша» і «конкурентна» — нічого не губиться без відома.
  • Merge — на клієнті, за бізнес-правилом (кошик: об'єднання множин товарів).
  • Відомий побічний ефект із paper: видалений з кошика товар може «воскреснути» після merge об'єднанням.
  • Годинники ростуть з кількістю вузлів-записувачів — Dynamo обрізав найстаріші записи (truncation).
  • Сучасніше: dotted version vectors, CRDT (CRDT — conflict-free replicated data types: структури, що мерджаться автоматично).

Last-Write-Wins (Cassandra)

  • Кожен запис має timestamp; перемагає більший.
  • Дуже просто, API без «списку версій».
  • Мовчки губить конкурентні записи.
  • Залежить від годинників: вузол із годинником, що поспішає, «перемагає» навіть старішими даними.
  • Ідеально для незмінних даних (insert-only, ключ = UUID) — там конфліктів не буває.

Sloppy quorum і hinted handoff — деталі

Строгий кворум рахує лише вузли з preference list. Якщо 2 з 3 лежать — запис з W=2 неможливий. Sloppy quorum дозволяє зарахувати «перших N здорових вузлів» з кільця: запис ляже на запасний вузол D з метаданими-підказкою (hint) «це для C». D тримає такі записи в окремому локальному сховищі і періодично перевіряє, чи ожив C; коли так — передає дані (hinted handoff) і видаляє свою копію. Cassandra має hinted handoff, але не рахує hints у кворум для consistency level (окрім рівня ANY) — ще одна відмінність від оригінального Dynamo.

Аналогія для фронтендера
Hinted handoff — як офлайн-черга мутацій у PWA: користувач без мережі натискає «зберегти», service worker кладе запит у IndexedDB з поміткою «відправити на сервер», а коли мережа повертається (Background Sync) — доставляє. Конфлікти vector clocks — як конфлікт при одночасному редагуванні одного документа у двох вкладках: або «остання вкладка перемагає» (LWW, втрата даних), або показуємо обидві версії й просимо змерджити. Де ламається: у браузера одна черга й один сервер, а в Dynamo «посилкою» тимчасово володіє чужий вузол, і поки він не віддав дані, читання з кворуму можуть їх не бачити.
🎯
На співбесіді: назвіть усі три рівні відновлення: read repair (при читанні помітили застарілу репліку — дописали), hinted handoff (тимчасова відмова вузла, хвилини–години), anti-entropy з Merkle trees (довгі відмови, втрачені hints, нова репліка). Кожен закриває свою «дірку».
R + W > N дає перетин, але не лінеаризованість. Vector clocks виявляють конфлікти, LWW — мовчки губить. Sloppy quorum + hinted handoff = завжди можна писати.

09 Anti-entropy (Merkle trees), gossip, write path і read path

Як репліки знаходять розбіжності, не порівнюючи терабайти; як вузли дізнаються, хто живий, без центрального реєстру; і що відбувається всередині одного вузла при записі й читанні.

Merkle trees: знайти розбіжність за O(log n)

Дві репліки зберігають той самий діапазон ключів. Як знайти, які саме ключі відрізняються, не пересилаючи все? Будуємо дерево хешів: листки — хеші діапазонів ключів, кожен внутрішній вузол — хеш дітей. Порівнюємо корені: однакові — репліки ідентичні (один обмін хешем!). Різні — спускаємось лише в ті гілки, де хеші відрізняються (O(log n) — «о від логарифма n»: кількість кроків росте як логарифм кількості діапазонів).

У Cassandra це nodetool repair: вузли будують Merkle trees («validation compaction») і стрімлять відмінні діапазони. Ремонт треба запускати регулярно — частіше, ніж gc_grace_seconds (за замовчуванням 10 днів), інакше видалені дані «воскресають»: tombstone прибрали compaction-ом на одних репліках, а на репліці, що «проспала» видалення, старе значення лишилося — і repair розповсюдить його назад.

Gossip: хто живий

Немає центрального «реєстру вузлів» (він був би SPOF). Замість цього кожну секунду кожен вузол обирає 1–3 випадкових сусідів і обмінюється з ними своєю таблицею членства: «вузол → (generation, heartbeat counter, статус)». Інформація поширюється як епідемія: за O(log N) раундів її знає весь кластер. Якщо heartbeat вузла довго не росте — його позначають підозрілим. Cassandra використовує phi accrual failure detector: замість бінарного «живий/мертвий» за таймаутом рахує рівень підозри φ (φ — «фі») з урахуванням історичних інтервалів між heartbeat-ами.

Важливо: gossip каже лише «я не бачу вузол», а не «вузол назавжди видалено». Постійне видалення/додавання вузла (зміна кільця) — явна адміністративна операція, бо інакше короткий мережевий збій спричинив би масове переміщення даних.

Write path і read path на одному вузлі (LSM)

  1. Запис на рівні кластера: клієнт → координатор → паралельно N реплікам → чекаємо W підтверджень → відповідь. Решта реплік дописують асинхронно (або отримають hint).
  2. Запис на вузлі: commit log (для відновлення після краху) + memtable. Коли memtable заповнилась — flush у новий SSTable; старі SSTable-и ніколи не змінюються.
  3. Видалення — запис спеціального маркера tombstone: фізично дані зникнуть лише при compaction, і не раніше gc_grace_seconds, щоб видалення встигло дійти до всіх реплік.
  4. Читання на рівні кластера: координатор шле запит R реплікам (часто: повні дані від найближчої, лише digest-хеш від інших), порівнює; якщо розбіжність — бере новішу версію і робить read repair застарілих реплік.
🏭
Як це роблять у реальних системах. Cassandra/ScyllaDB — рівно цей write/read path. RocksDB (LSM-бібліотека від Facebook) — сховище під капотом багатьох систем (CockroachDB використовувала її до власного Pebble, TiKV, Kafka Streams state stores). Dynamo в paper використовував підключувані движки — Berkeley DB та MySQL залежно від розміру об'єктів.
🎯
Що кажуть сильні кандидати: «Це AP-система: запис приймається завжди (sloppy quorum + hinted handoff), узгодженість — eventual з налаштовуваним R/W. Конфлікти: для незмінних або «останній вигравав» даних — LWW, для кошика/лічильників — vector clocks або CRDT. Розбіжності закриваються трьома механізмами: read repair, hinted handoff, Merkle-tree repair. Кожен вузол — LSM, бо ми оптимізуємо запис. Ризики: tombstones і воскресіння даних, гарячі партиції, довгий repair, LWW і clock skew».

Follow-up питання

  • Як додати вузол без простою? (vnodes нового вузла забирають частини діапазонів у кількох сусідів; стрімінг даних; кільце оновлюється, поки старі вузли ще обслуговують)
  • Що робити з гарячим ключем? (кеш перед сховищем, розбиття ключа на key#0..key#9 з агрегацією при читанні)
  • Як підтримати range-запити? (order-preserving партиціювання — ризик гарячих діапазонів; або partition key + clustering key, як у Cassandra)
  • Чи можна отримати strong consistency? (W=N/R=1 не рятує при відмовах; потрібен консенсус на партицію — як DynamoDB, Spanner, CockroachDB)
Merkle tree = знайти розбіжність, обмінюючись хешами. Gossip = членство без центру. LSM = швидкий запис; tombstones + gc_grace — головна пастка.
Частина IV · Rate limiter як задача на дизайн

10 Rate limiter як задача на дизайн

Алгоритми (token bucket, sliding window…) детально — у туторіалі 8. Тут — rate limiter як окрема співбесіда: де його ставити, як зберігати стан для тисяч серверів, що робити при відмові Redis і як жити в кількох регіонах.

Вимоги

Функціональні

  • Обмежувати запити за ключем: user_id, API key, IP, (ключ, endpoint).
  • Гнучкі правила: «100 запитів/хв на /search для free-плану, 1 000 для pro».
  • Відповідати 429 Too Many Requests з Retry-After і заголовками залишку.

Нефункціональні

  • Додаткова латентність — до ~1–2 мс (rate limiter стоїть на кожному запиті).
  • Точність «приблизно»: перебір на кілька % допустимий (уточнюємо).
  • Відмова limiter-а не повинна покласти весь API.
  • Масштаб: сотні тисяч–мільйони запитів/с, мільйони ключів.

sliding.py
import time

class SlidingWindowCounter:
    """Наближене ковзне вікно: 2 лічильники на ключ замість лога всіх запитів."""
    def __init__(self, limit: int, window_s: int):
        self.limit, self.window = limit, window_s
        self.counts = {}                       # (key, window_index) -> count

    def allow(self, key: str, now: float | None = None) -> bool:
        now = time.time() if now is None else now
        idx = int(now // self.window)
        elapsed = (now % self.window) / self.window      # частка поточного вікна
        prev = self.counts.get((key, idx - 1), 0)
        cur = self.counts.get((key, idx), 0)
        estimated = prev * (1 - elapsed) + cur
        if estimated >= self.limit:
            return False
        self.counts[(key, idx)] = cur + 1
        return True

rl = SlidingWindowCounter(limit=100, window_s=60)
for _ in range(80):
    rl.allow("u1", now=59.0)                   # 80 запитів наприкінці хвилини 0
ok = sum(rl.allow("u1", now=75.0) for _ in range(100))   # 25% у хвилину 1
print(ok)   # 80*0.75 = 60 «з минулого» -> пропустить ще 40

Виведе 40: на 15-й секунді нової хвилини 75% попереднього вікна ще «рахуються» (80 × 0,75 = 60), тож лишається 40 запитів до ліміту 100. Cloudflare у блозі про свій rate limiting описував саме таку апроксимацію і повідомляв про дуже малу частку помилкових рішень на реальному трафіку (за їхніми даними — соті частки відсотка).

Розподілений стан: Redis і атомарність

Сотні інстансів gateway мусять бачити спільний лічильник. Стандарт — Redis Cluster, ключ шардується за rl:{user_id}. Наївне «GET → перевірити → SET» дає race condition: два інстанси прочитали 99, обидва пропустили. Рішення:

  • Fixed window: INCR + EXPIRE (атомарний інкремент; перевіряємо повернуте значення).
  • Token bucket / sliding window: Lua-скрипт (EVAL/EVALSHA) — Redis виконує його атомарно, жодна інша команда не вклинюється.
token_bucket.lua
-- KEYS[1] = rl:{user42}; ARGV: capacity, refill_per_sec, now_ms
local cap, rate, now = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local s = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(s[1]) or cap
local ts = tonumber(s[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)   -- поповнення
local allowed = 0
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000) * 2)
return { allowed, math.floor(tokens) }

Тонкість: now передає клієнт, а годинники gateway-інстансів розходяться. Варіант — брати час самого Redis (redis.call('TIME'); у Redis 5+ скрипти реплікуються як ефекти, тож це дозволено).

Продуктивність і відмовостійкість

  • Латентність: один RTT до Redis (~0,3–1 мс в межах AZ). Батчинг/пайплайнінг; локальний «попередній фільтр» — якщо ключ явно в межах ліміту, перевіряти Redis не на кожен запит.
  • Гарячий ключ: один величезний клієнт — один шард Redis. Рішення: локальні токени, які інстанс «позичає» пачками з глобального bucket (як діапазони ID!).
  • Redis недоступний: fail-open (пропускати — для більшості API краще, ніж покласти весь сервіс) або fail-closed (блокувати — для логіну, OTP, платежів, де ліміт — захист безпеки). Плюс локальний in-memory ліміт як деградований режим.
  • Правила: зберігаються в конфігу/БД, кешуються в пам'яті gateway, оновлюються підпискою або періодично — не читати правила з БД на кожен запит.
  • Відповідь: 429, Retry-After, X-RateLimit-Limit / Remaining / Reset (або стандартизовані IETF-заголовки RateLimit-* — документ у стадії draft, перевірте актуальний статус).

Multi-region

🏭
Як це роблять у реальних системах. Stripe у статті «Scaling your API with rate limiters» (2017) описав чотири типи: request rate limiter (token bucket у Redis), concurrent requests limiter, fleet usage load shedder (резерв ємності для критичних запитів) і worker utilization load shedder. Envoy/Lyft мають відкритий глобальний rate limit service на Redis (gRPC, правила в YAML). Cloudflare рахує ліміти на edge в кожному дата-центрі, без глобальної синхронізації на кожен запит. GitHub API віддає X-RateLimit-* заголовки — зручний приклад для розмови.
Аналогія для фронтендера
Клієнтський debounce на полі пошуку — rate limiter на вашому боці: ви відправляєте не більше одного запиту за 300 мс. Token bucket — це throttle з дозволеним «запасом»: можна різко відправити 10 подій, а далі — не частіше за задану швидкість. А Retry-After — сигнал для вашого fetch-обгортки з exponential backoff. Де ламається: клієнтський ліміт — ввічливість, а не захист: зловмисник просто не виконує ваш JS, тому серверний ліміт обов'язковий.
🎯
Що кажуть сильні кандидати: «Багатошаровий захист: per-IP на edge, per-key token bucket на gateway з Redis + Lua, concurrency limiter у сервісах. Redis-ключ шардую за користувачем; при відмові Redis — fail-open з локальним fallback-лімітом, але fail-closed для логіну й OTP. Правила кешуються в gateway. Multi-region — локальні бюджети з асинхронною синхронізацією: перебір на кілька відсотків прийнятний, а +100 мс на кожен запит — ні. Повертаю 429 з Retry-After, щоб клієнти не робили retry storm».
🚩
Red flags: лічильник у пам'яті кожного інстансу без розмови про те, що ліміт множиться на кількість інстансів; GET-check-SET без атомарності; rate limiter, відмова якого кладе весь API; ліміт лише за IP (NAT, мобільні оператори — тисячі користувачів за одним IP); забути про Retry-After і retry storm.

Follow-up питання

  • Як дати pro-клієнтам сплески, а free — ні? (різні capacity/rate у token bucket за планом)
  • Як лімітувати за вартістю, а не кількістю (GraphQL: дорогі запити)? (bucket у «одиницях вартості», як cost-based ліміти GitHub GraphQL API)
  • Як тестувати limiter? (shadow mode: рахувати і логувати, але не блокувати; потім вмикати)
  • Як лімітувати вихідні запити до стороннього API з квотою? (leaky bucket/черга перед клієнтом, спільна квота в Redis)
Rate limiter: шари (edge → gateway → сервіс), token bucket/sliding window counter, Redis + Lua для атомарності, fail-open/closed — свідомо, multi-region — локальні бюджети.
Частина V · Практика

11 Трікі питання

Питання, на яких «посипаються» навіть ті, хто знає канонічні відповіді. Спробуйте відповісти вголос, перш ніж відкривати.

TRICKYЧому б не використати хеш від long URL як код — тоді й дедуплікація безкоштовна?

Бо (1) обрізаний до 7 символів хеш має колізії — за парадоксом днів народження вони почнуться вже після ~1,9 млн кодів, тож потрібна обробка; (2) детермінований код означає, що будь-хто може обчислити код для відомого URL і перевірити, чи його хтось скоротив (витік інформації); (3) різні користувачі з тим самим URL отримують той самий код — і спільну аналітику, і неможливість для одного з них змінити ціль чи задати TTL. Якщо дедуплікація потрібна, її роблять окремим індексом hash(user_id, long_url) → code, а сам код генерують незалежно.

TRICKY301 чи 302 — що «правильно» для шортенера?

Немає одного правильного. 301 — менше навантаження і SEO-«вага» переходить цілі, але браузери кешують його (без явного Cache-Control — потенційно назавжди), тож губимо повторні кліки і не можемо надійно змінити/заблокувати ціль. 302/307 — кожен клік через нас. Сильна відповідь: «302, бо аналітика й модерація — частина продукту; або 301 з Cache-Control: private, max-age=… на хвилини — компроміс». Додатково: private не дає CDN-ам і проксі кешувати відповідь спільно для всіх.

TRICKYRedis INCR як генератор ID — що може піти не так?

Redis за замовчуванням асинхронно персистить (RDB-снапшоти, AOF з fsync everysec) і асинхронно реплікує. Після краху або failover на репліку лічильник може повернутися назад на кілька тисяч значень — і видати вже використані ID. Отже, або AOF з appendfsync always (повільно), або при старті/failover «перестрибувати» вперед із запасом (наприклад, +1 млн), або брати не по одному ID, а діапазонами з персистентного координатора. Плюс INCR — мережевий виклик на кожен ID і SPOF без кластера.

CORESnowflake ID «відсортовані за часом». Чи можна на них покладатися для порядку подій?

Лише приблизно. Усередині одного воркера — так, строго. Між воркерами — з точністю до розбіжності годинників (NTP: одиниці–десятки мс). Подія B, створена на 2 мс пізніше за A на іншому сервері, може отримати менший ID. Для UI-стрічок це неважливо; для «хто перший купив останній квиток» чи журналу транзакцій рахунку — потрібен єдиний порядок у межах сутності: секвенсор на партицію (Kafka offset у партиції, auto-increment у шарді, Raft-лог).

TRICKYR + W > N — значить, у нас strong consistency?

Ні. Кворуми дають перетин множин, але: (1) sloppy quorum рахує «чужі» вузли — перетину немає; (2) запис, що впав після W' < W підтверджень, не відкочується — читання то бачать його, то ні (не лінеаризовано); (3) конкурентні записи з LWW губляться; (4) годинники при LWW можуть «перемогти» новіший запис старішим. Лінеаризованість потребує консенсусу (Raft/Paxos) або обережного протоколу з синхронним read repair. Це улюблене питання після «назвіть формулу кворуму».

ADVDynamo і DynamoDB — це одне й те саме?

Ні. Dynamo (2007) — внутрішнє leaderless-сховище Amazon з vector clocks і sloppy quorum. DynamoDB (2012) — керований сервіс AWS, який запозичив ідеї (партиціювання, реплікація в 3 AZ), але за paper'ом 2022 року використовує лідера на партицію з Multi-Paxos, пише в журнал, підтримує strongly consistent reads (з лідера) і транзакції. Vector clocks клієнтам він не повертає. На співбесіді коректно сказати: «Dynamo-style, як Cassandra», а не «як DynamoDB».

TRICKYМи видалили ключ у Cassandra, а через два тижні він повернувся. Як?

«Воскресіння» (zombie data). Видалення = tombstone. Одна репліка була недоступна під час видалення і не отримала tombstone (hint протермінувався). Через gc_grace_seconds (10 днів за замовчуванням) compaction на здорових репліках фізично прибрав і дані, і tombstone. Потім repair/read repair побачив на «відсталій» репліці старе значення без жодного tombstone поруч — і вважав його актуальним, розповсюдивши назад. Ліки: запускати повний repair частіше за gc_grace_seconds; не повертати в кластер вузол, що був офлайн довше; для черг-подібних патернів (багато видалень) — інша модель даних.

CORERate limiter на Redis — single point of failure. Як бути?

(1) Redis Cluster з репліками й автоматичним failover — при failover можна втратити кілька лічильників, це прийнятно; (2) короткі таймаути (кілька мс) на виклик limiter-а; (3) стратегія при недоступності: fail-open для звичайних API з локальним in-memory лімітом як «запобіжником», fail-closed для чутливих ендпоїнтів (логін, OTP, створення платежу); (4) circuit breaker навколо Redis, щоб не накопичувати таймаути. Ключова думка: limiter — захисний механізм, його відмова не повинна бути страшнішою за те, від чого він захищає.

ADVЧому fixed window допускає 2× ліміту і чим це небезпечно?

Ліміт 100/хв: 100 запитів о 00:59 і ще 100 о 01:00 — обидва вікна «чесні», а за 2 секунди пройшло 200. Для захисту крихкого бекенду це саме той сплеск, від якого ми ховалися. Sliding window counter зважує попереднє вікно (у прикладі вище на 01:15 «з минулого» рахується 75% попереднього вікна) і прибирає ефект межі майже без додаткової пам'яті; token bucket обмежує сплеск явно розміром bucket.

ADVЯк KV store з consistent hashing переживає додавання вузла під навантаженням?

Новий вузол отримує свої vnodes — кожен «відрізає» шматок діапазону в якогось існуючого вузла. Без vnodes увесь потік даних ішов би з одного сусіда (він перевантажується); з vnodes — потроху з багатьох. Процес: новий вузол оголошує себе через gossip у стані «joining», старі власники стрімлять йому дані, записи в цей час ідуть і старому, і новому власнику (щоб не загубити), і лише після завершення стрімінгу вузол стає «normal» і починає обслуговувати читання. Стрімінг троттлять, щоб не вбити латентність продакшен-трафіку.

Задача 1ЛегкоСкільки символів потрібно?

Сервіс очікує 5 млрд коротких посилань за весь час життя. Коди генеруються з глобального лічильника через base62. Яка мінімальна довжина коду? А якщо коди генеруються випадково?

Лічильник: потрібно 62k ≥ 5 × 10⁹. 62⁵ ≈ 9,2 × 10⁸ — мало; 62⁶ ≈ 5,68 × 10¹⁰ — вистачає з запасом ~11×. Відповідь: 6 символів.

Випадкові коди: при заповненні 5 × 10⁹ / 5,68 × 10¹⁰ ≈ 9% кожна нова генерація з імовірністю ~9% влучає в зайнятий код — ретраї стають помітними. Краще 7 символів (заповнення ~0,14%), щоб колізії були рідкісними, хоча обробка колізій потрібна все одно.

Задача 2ЛегкоМежі Snowflake

Скільки ID на секунду може видати один Snowflake-воркер (12 біт лічильника)? Скільки воркерів підтримує розкладка? Що станеться, якщо одному воркеру прийде 6 млн запитів за секунду?

2¹² = 4 096 ID на мілісекунду → 4 096 000 ID/с на воркер. 10 біт машини → 1 024 воркери. При 6 млн/с воркер вичерпуватиме лічильник у кожній мілісекунді й чекатиме наступну — латентність зросте, пропускна здатність упреться в ~4,1 млн/с. Рішення: більше воркерів (горизонтально), а не більше біт лічильника.

Задача 3СередньоОцінки для шортенера

500 млн нових URL на місяць, співвідношення читань до записів 100:1, зберігання 5 років, запис ≈ 500 Б. Порахуйте QPS записів і читань, обсяг сховища і розмір кешу (20% денних читань).

  1. Записи: 5 × 10⁸ / (30 × 86 400) ≈ 193/с.
  2. Читання: ×100 ≈ 19 300/с, пік ×2–3 ≈ 40–60 тис./с.
  3. URL за 5 років: 5 × 10⁸ × 12 × 5 = 3 × 10¹⁰ → вистачає 62⁶ ≈ 5,7 × 10¹⁰, але з невеликим запасом; беремо 7 символів.
  4. Сховище: 3 × 10¹⁰ × 500 Б = 15 ТБ (×3 з реплікацією = 45 ТБ).
  5. Кеш: читань на день ≈ 1,67 × 10⁹; 20% × 500 Б ≈ 167 ГБ (насправді менше: багато читань — ті самі гарячі ключі).

Висновок вголос: «Записи — дрібниця, читання — головне; 15 ТБ — шардинг або KV-сховище; кеш — кілька Redis-нод».

Задача 4СередньоDebug: дублікати коротких кодів

Після масштабування Write API з 4 до 8 подів у логах з'явилися помилки «duplicate key» при вставці коротких кодів, а деякі користувачі скаржаться, що їхнє посилання веде на чужий сайт. Генерація — Snowflake-бібліотека, worker_id береться з env-змінної в Helm chart. Що сталося і як виправити?

Причина: нові поди отримали той самий worker_id (наприклад, однакове значення в шаблоні Deployment), тож два поди в ту саму мілісекунду видають ідентичні ID. «Duplicate key» — це коли спрацював унікальний індекс; «чужий сайт» — коли вставка була upsert-ом без перевірки і перезаписала чужий рядок.

Виправлення: (1) негайно: INSERT IF NOT EXISTS замість upsert, щоб ніколи не перезаписувати; (2) worker_id — з lease в etcd/ZooKeeper (ephemeral node) або ordinal StatefulSet, з перевіркою унікальності при старті; (3) відновити перезаписані записи з бекапу/CDC-логу; (4) алерт на кількість конфліктів унікального індексу. Мораль: унікальний індекс — остання лінія оборони, а «upsert за замовчуванням» перетворив гучну помилку на тиху корупцію даних.

Задача 5СередньоГонка за custom alias

Два користувачі одночасно намагаються зареєструвати alias black-friday. Поточний код: if not db.exists(alias): db.insert(alias, url). Що піде не так у Cassandra і в Postgres, і як виправити?

Check-then-act: обидва запити бачать «не існує», обидва вставляють. У Postgres з PRIMARY KEY друга вставка впаде (це добре — обробляємо помилку як «зайнято»), але якщо унікального обмеження немає — два рядки. У Cassandra INSERT — це upsert: другий запис мовчки перезапише перший (LWW), і перший користувач втратить alias, не знаючи про це.

Виправлення: Postgres — INSERT … ON CONFLICT DO NOTHING RETURNING code (немає рядка у відповіді → зайнято). Cassandra — lightweight transaction INSERT … IF NOT EXISTS (Paxos під капотом, повільніше, але для рідкісних custom aliases прийнятно). DynamoDB — PutItem з ConditionExpression attribute_not_exists(code).

Задача 6СередньоПідібрати N, R, W

Кластер з N = 5 репліками на ключ. Потрібно: (а) і записи, і читання переживають відмову будь-яких 2 реплік, і читання бачать останній підтверджений запис (за відсутності sloppy quorum); (б) система read-heavy, записи можуть бути трохи менш доступними. Які R і W?

(а) Умови: R + W > 5, W ≤ 3 (щоб 2 відмови не блокували запис), R ≤ 3. Єдиний варіант: W = 3, R = 3.

(б) Хочемо менше R: W = 4, R = 2 (4 + 2 = 6 > 5). Читання переживають відмову 3 реплік і опитують лише 2 вузли (швидше); записи переживають лише 1 відмову. Крайній варіант W = 5, R = 1 — найшвидші читання, але будь-яка відмова блокує запис — зазвичай неприйнятно.

Задача 7СередньоПорівняти vector clocks

Є три версії ключа: V1 = {A:2, B:1}, V2 = {A:2, B:2, C:1}, V3 = {A:3, B:1}. Які пари впорядковані, а які конкурентні? Що поверне get?

  • V1 vs V2: 2≤2, 1≤2, 0≤1 → V1 → V2 (V1 — предок).
  • V1 vs V3: 2≤3, 1≤1 → V1 → V3.
  • V2 vs V3: B: 2 > 1, але A: 2 < 3 → конкурентні.

get поверне [V2, V3] (V1 відкидається як застаріла). Клієнт зливає їх, і новий запис через вузол, скажімо, A матиме годинник {A:4, B:2, C:1}.

Задача 8СкладноШортенер у трьох регіонах active-active

Бізнес хоче, щоб створення і редирект працювали з низькою латентністю в US, EU і APAC, і щоб падіння цілого регіону не ламало ні створення, ні редиректи. Спроєктуйте генерацію ID, реплікацію і шлях читання. Що станеться, якщо користувач створив посилання в EU і за 100 мс його відкрили в US?

  1. ID: кожен регіон має власний координатор діапазонів, а простори не перетинаються (2 старші біти = регіон, або діапазони заздалегідь розділені). Створення ніколи не потребує міжрегіональної координації.
  2. Дані: multi-region KV з асинхронною реплікацією (Cassandra multi-DC з LOCAL_QUORUM, DynamoDB Global Tables). Конфліктів практично немає: ключі унікальні за регіоном, записи — insert-only.
  3. Читання: локальний кеш → локальна репліка. Промах для коду, створеного < ~1 с тому в іншому регіоні: декодуємо регіон з ID і робимо fallback-запит туди (одноразово +100–200 мс) — замість 404.
  4. Падіння регіону: GeoDNS/Anycast переводить трафік; редиректи працюють з реплік (крім посилань, створених в останні секунди перед падінням — їх втрачено або вони затримаються, RPO ≈ лаг реплікації). Створення в уцілілих регіонах триває у своїх просторах ID.
Задача 9СкладноГарячий клієнт у rate limiter

Великий клієнт має ліміт 50 000 запитів/с і шле трафік через 200 інстансів gateway. Його ключ у Redis отримує 50 000+ Lua-викликів/с, шард Redis з цим ключем завантажений на 100% CPU, і латентність усіх клієнтів на цьому шарді росте. Що робити?

Ідея — «позичати» токени пачками (як діапазони ID). Кожен gateway-інстанс тримає локальний bucket і бере з глобального Redis-бакета не 1 токен, а пачку (наприклад, 1% ліміту = 500 токенів) одним викликом. При 200 інстансах навантаження на Redis падає в сотні разів.

  • Ціна: точність. Інстанс може «тримати» невикористані токени, а інші — отримати відмову; на межі секунди можливий перебір на розмір пачки × кількість інстансів. Пачку роблять адаптивною (менша, коли глобальний бакет майже порожній).
  • Альтернатива: розшардувати ключ на rl:{client}:0..15, кожен з лімітом 1/16, інстанс обирає підключ за своїм ID — навантаження розходиться по шардах, точність трохи падає.
  • Для дуже великих клієнтів — ліміт пропорційно на інстанс (50 000 / 200 = 250/с локально) без Redis взагалі, якщо балансувальник розподіляє рівномірно.
Задача 10СкладноDebug: «лайки» губляться в Cassandra

Лічильник лайків поста зберігається як likes int у рядку поста. Сервіс робить «прочитати → +1 → записати». Під час вірусного поста лайків у БД значно менше, ніж подій «лайк» у Kafka. Пояснити й перепроєктувати.

Причина: read-modify-write без атомарності + LWW. Два сервери прочитали 100, обидва записали 101 — один інкремент втрачено. Під навантаженням таких гонок тисячі. Clock skew між серверами погіршує: «новіший» запис з годинником, що відстає, програє.

Варіанти: (1) таблиця likes(post_id, user_id) — один рядок на лайк (idempotent, без конфліктів, бо ключі різні; ще й не дає лайкнути двічі), лічильник — агрегат; (2) Cassandra counter-колонки (атомарний інкремент, але не ідемпотентні при ретраях); (3) агрегувати в стрімі (Kafka → Flink: вікно 1 с, сумуємо й пишемо дельту одним записом) — значно менше записів у гарячий ключ; (4) CRDT G-Counter (кожна репліка рахує своє, значення = сума). На практиці часто (1) як джерело правди + (3) для відображуваного лічильника.

Задача 11ЛегкоМаркетингова кампанія

Маркетинг розсилає 20 млн email із коротким посиланням і хоче бачити кожен клік, а також мати можливість перенаправити посилання на іншу сторінку, якщо акція закінчиться раніше. Який статус редиректу і заголовки?

302 (або 307) з Cache-Control: no-store чи private, max-age=0: кожен клік проходить через сервіс, ціль можна змінити будь-якої миті (з інвалідацією серверного кешу). 301 тут шкідливий: браузери, що вже кешували редирект, продовжать вести на стару сторінку. Додатково — готовність до сплеску: 20 млн листів відкривають у перші години → прогріти кеш цим кодом заздалегідь.
