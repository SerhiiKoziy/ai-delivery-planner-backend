Частина I · Ментальна модель

01 QPU як віддалений співпроцесор

Найважливіша ідея всього туторіалу: квантовий комп'ютер не замінює ваш бекенд, а стає ще однією зовнішньою залежністю.

Коли кажуть "бекенд на квантовому комп'ютері", уявляють сервер, де FastAPI крутиться на кубітах. Так не буває і найближчими роками не буде. Реальна картина нудніша: ваш звичайний Python-сервіс на звичайному CPU будує квантову схему (опис програми з гейтів), відправляє її через HTTPS у хмару IBM, де вона стає в чергу до конкретного процесора, виконується тисячі разів (shots) і повертає статистику результатів вимірювань. Усе інше — валідація, БД, бізнес-логіка, постобробка — класичне.

Найближчі аналогії з того, що ви вже знаєте:

Схоже наЧим схожеЧим відрізняється
Зовнішній API (OpenAI, Google Maps)HTTP-клієнт, токен, ліміти, гроші за використання, мережеві збоїВідповідь не за секунди, а за хвилини–години через чергу
GPU для MLСпеціалізований прискорювач для вузького класу задач; CPU готує даніQPU не можна "мати локально", а результат ймовірнісний і шумний
Пакетна обробка (Spark job, AWS Batch)Відправив задачу → отримав ID → чекаєш статус → забираєш результатРозмір "даних" на вході крихітний (схема на кілька КБ), обмеження — кількість кубітів і глибина
💡
Правило для архітектури: будь-який виклик QPU — це довга фонова задача. Ніколи не тримайте HTTP-запит відкритим, поки job стоїть у черзі. Шаблон той самий, що й для оптимізації маршрутів у цьому репо (optimize_routes_task в app/workers/tasks.py): API повертає 202 з ID, Celery-воркер робить важку роботу, клієнт питає статус.

03 Режими виконання: job, batch, session

Як ваша задача потрапляє на процесор — і чому це впливає на архітектуру.

QPU — спільний ресурс для тисяч користувачів, тому між вашим run() і реальним виконанням стоїть планувальник. Qiskit Runtime дає три execution modes:

РежимЯк працюєКоли брати
JobОдин запит примітиву = одна задача в черзіНезалежні одноразові обчислення: QRNG, демо, один експеримент
BatchКілька незалежних задач відправляються разом; планувальник може виконувати їх паралельно і щільнішеБагато незалежних схем (перебір параметрів, багато спостережуваних)
SessionЕксклюзивне "вікно" на процесорі: наступні задачі не стоять у загальній черзіІтеративні гібридні алгоритми (VQE/QAOA), де кожен крок залежить від попереднього. Не на Open plan
modes.py
from qiskit_ibm_runtime import Batch, Session, SamplerV2 as Sampler

# Job mode: mode = сам backend
sampler = Sampler(mode=backend)
job = sampler.run([isa_circuit])

# Batch mode: незалежні схеми однією "пачкою"
with Batch(backend=backend) as batch:
    sampler = Sampler(mode=batch)
    jobs = [sampler.run([c]) for c in isa_circuits]
    results = [j.result() for j in jobs]

# Session mode: ітеративний цикл без повторного стояння в черзі (платні плани)
with Session(backend=backend) as session:
    sampler = Sampler(mode=session)
    ...
Аналогія з бекенду
Job — окремий HTTP-запит. Batch — bulk-endpoint. Session — утримане з'єднання з транзакцією: дешевше для серії кроків, але ви платите за час, поки "тримаєте" ресурс, навіть якщо ваш класичний оптимізатор думає.

05 Bell-стан на локальному симуляторі

"Hello world" квантового програмування: два заплутані кубіти, які завжди вимірюються однаково.

Схема: Hadamard на кубіті 0 створює суперпозицію, CNOT заплутує кубіт 1 з кубітом 0. В ідеалі отримуємо лише 00 і 11, кожен приблизно у 50% вимірювань, і ніколи 01 чи 10. Детально фізика — в туторіалі 1.

bell_local.py
from qiskit import QuantumCircuit
from qiskit_aer import AerSimulator
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime import SamplerV2 as Sampler


def bell() -> QuantumCircuit:
    qc = QuantumCircuit(2)
    qc.h(0)
    qc.cx(0, 1)
    qc.measure_all()  # класичний регістр отримає ім'я "meas"
    return qc


backend = AerSimulator()
pm = generate_preset_pass_manager(backend=backend, optimization_level=1)
isa = pm.run(bell())

# "local testing mode": той самий SamplerV2 з runtime, але mode = локальний симулятор
sampler = Sampler(mode=backend)
job = sampler.run([isa], shots=2000)
result = job.result()

counts = result[0].data.meas.get_counts()
print(counts)  # приблизно {'00': 1003, '11': 997}
💡
Чому однаковий код для симулятора і заліза — це добре. Той самий SamplerV2 приймає і AerSimulator, і fake backend, і справжній QPU. Для бекенду це означає, що провайдер можна підмінити конфігом, а не переписуванням логіки (див. розділ 12).

06 Транспіляція та ISA-схеми

Чому схему, яку ви написали, процесор виконати не може — і що з цим робить транспайлер.

Ви пишете логічну схему: будь-які гейти, будь-які пари кубітів. Справжній процесор має обмеження:

  • Basis gates. Апаратно підтримується невеликий набір гейтів (на сучасних IBM — щось на кшталт rz, sx, x і двокубітний cz або ecr). Решту треба розкласти.
  • Топологія (coupling map). Двокубітний гейт можна застосувати лише до фізично з'єднаних кубітів (heavy-hex у Eagle/Heron, квадратна решітка в новіших процесорах). Якщо треба з'єднати далекі кубіти — вставляються SWAP-и.
  • Якість кубітів різна. Варто обрати фізичні кубіти з найменшими помилками й найдовшим часом когерентності.

Результат транспіляції — ISA-схема (Instruction Set Architecture): лише нативні гейти, лише дозволені пари. З 2024 року примітиви IBM приймають тільки ISA-схеми — транспіляцію робите ви на клієнті, явно.

transpile_inspect.py
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime.fake_provider import FakeSherbrooke

backend = FakeSherbrooke()  # 127-кубітний "знімок" реального процесора з моделлю шуму
logical = bell()

for level in (0, 1, 2, 3):
    pm = generate_preset_pass_manager(backend=backend, optimization_level=level, seed_transpiler=42)
    isa = pm.run(logical)
    ops = isa.count_ops()
    print(level, "depth:", isa.depth(), "2q gates:", ops.get("ecr", 0) + ops.get("cz", 0), dict(ops))

# які фізичні кубіти отримала схема
print(isa.layout.final_index_layout())
🧩
Метрика, яку варто логувати: кількість двокубітних гейтів і глибина ISA-схеми. Це головний предиктор якості результату. Якщо після транспіляції схема для вашої задачі має тисячі двокубітних гейтів на десятках кубітів — на сучасному залізі ви отримаєте майже шум, і бекенд має про це знати до витрачання QPU-секунд.

07 Примітиви V2: Sampler і Estimator

Два "ендпоінти" квантового комп'ютера: дай розподіл бітрядків або дай середнє значення спостережуваної.

Замість низькорівневого "запусти схему" Qiskit Runtime дає два примітиви. На вхід обидва приймають список PUB-ів (Primitive Unified Bloc) — кортежів, що описують одне обчислення.

⚠️
API рухається: у qiskit-ibm-runtime 0.50 класи EstimatorV2 / SamplerV2 вже позначені як deprecated на користь qiskit_ibm_runtime.executor_estimator.Estimator / executor_sampler.Sampler (перевірено прогоном у туторіалі 4). Концепції PUB, shots, observables лишаються тими самими. У продакшн-коді тримайте імпорт примітивів в одному адаптері (див. розділ 12), щоб міграція торкалась одного файлу.
estimator_demo.py
from qiskit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime import EstimatorV2 as Estimator
from qiskit_ibm_runtime.fake_provider import FakeSherbrooke

qc = QuantumCircuit(2)
qc.h(0)
qc.cx(0, 1)            # без measure: Estimator вимірює сам у потрібних базисах

observables = [SparsePauliOp("ZZ"), SparsePauliOp("XX"), SparsePauliOp("ZI")]

backend = FakeSherbrooke()
pm = generate_preset_pass_manager(backend=backend, optimization_level=1)
isa = pm.run(qc)
# спостережувані треба "перенести" на фізичні кубіти, які обрав транспайлер
isa_obs = [o.apply_layout(isa.layout) for o in observables]

estimator = Estimator(mode=backend)
job = estimator.run([(isa, isa_obs)])
pub = job.result()[0]
print(pub.data.evs)   # ідеально [1, 1, 0]; на шумному fake — щось на кшталт [0.93, 0.92, 0.01]
print(pub.data.stds)
⚠️
Типова помилка: забути apply_layout. Спостережувана описана на 2 логічних кубітах, а ISA-схема вже живе на 127 фізичних — примітив поверне помилку про невідповідність кількості кубітів. Друга помилка — measure_all() у схемі для Estimator.

09 Шум: suppression і mitigation

Чому 01 і 10 з'явилися в результаті Bell і що з цим можна зробити програмно.

Сучасні QPU — це епоха NISQ / pre-fault-tolerant: кубіти втрачають когерентність, гейти мають помилки ~0.1–1% для двокубітних, вимірювання помиляються. Повноцінної корекції помилок ще немає (див. туторіал 2), тому використовують програмні техніки двох типів:

11 Життєвий цикл квантової задачі в бекенді

Від HTTP-запиту до відповіді — хто що робить і де зберігається стан.

Покроково, з відповідальністю кожного шару:

  1. Валідація (API). Pydantic-схема: тип задачі, розмір (кількість вершин графа, кубітів), shots, рівень mitigation. Відхиляємо все, що не влізе в QPU або бюджет.
  2. Ідемпотентність (API). Idempotency-Key або хеш вхідних даних → якщо така задача вже є, повертаємо її, а не відправляємо нову.
  3. Побудова схеми (worker). Доменні дані → гамільтоніан / схема. Чиста функція, покрита тестами.
  4. Транспіляція (worker). Під конкретний backend. Тут же — перевірка "чи має сенс": глибина, кількість двокубітних гейтів.
  5. Submit (worker). sampler.run(...) → job_id → одразу в БД.
  6. Очікування (worker). Не блокуючий job.result(), а повторна Celery-задача з countdown.
  7. Постобробка (worker). Бітрядки → доменна відповідь (розріз графа, маршрут, випадкове число), оцінка якості, порівняння з класичною базою.
  8. Видача (API). GET зі статусом; опційно веб-хук/WebSocket-сповіщення клієнту.

from enum import StrEnum
from typing import Protocol

from qiskit import QuantumCircuit


class JobState(StrEnum):
    QUEUED = "QUEUED"
    RUNNING = "RUNNING"
    DONE = "DONE"
    ERROR = "ERROR"
    CANCELLED = "CANCELLED"

    @property
    def is_final(self) -> bool:
        return self in (JobState.DONE, JobState.ERROR, JobState.CANCELLED)


@dataclass(frozen=True)
class ProviderJobRef:
    provider: str          # "aer" | "ibm" | "classical"
    external_id: str       # ibm job id або локальний uuid
    backend_name: str


@dataclass(frozen=True)
class SamplingResult:
    counts: list[dict[str, int]]     # по одному словнику на кожну схему
    qpu_seconds: float | None = None


class QuantumProvider(Protocol):
    name: str

    def submit(self, circuits: list[QuantumCircuit], shots: int) -> ProviderJobRef: ...
    def status(self, ref: ProviderJobRef) -> JobState: ...
    def result(self, ref: ProviderJobRef) -> SamplingResult: ...
    def cancel(self, ref: ProviderJobRef) -> None: ...

from qiskit import QuantumCircuit
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime import QiskitRuntimeService, SamplerV2 as Sampler

from app.quantum.providers.base import JobState, ProviderJobRef, SamplingResult

_STATE_MAP = {
    "INITIALIZING": JobState.QUEUED,
    "QUEUED": JobState.QUEUED,
    "VALIDATING": JobState.QUEUED,
    "RUNNING": JobState.RUNNING,
    "DONE": JobState.DONE,
    "ERROR": JobState.ERROR,
    "CANCELLED": JobState.CANCELLED,
}


class IbmRuntimeProvider:
    name = "ibm"

    def __init__(self, token: str, instance: str, backend_name: str | None = None,
                 min_qubits: int = 2, optimization_level: int = 1):
        self._service = QiskitRuntimeService(
            channel="ibm_quantum_platform", token=token, instance=instance
        )
        self._backend_name = backend_name
        self._min_qubits = min_qubits
        self._opt_level = optimization_level

    def _backend(self):
        if self._backend_name:
            return self._service.backend(self._backend_name)
        return self._service.least_busy(
            operational=True, simulator=False, min_num_qubits=self._min_qubits
        )

    def submit(self, circuits: list[QuantumCircuit], shots: int) -> ProviderJobRef:
        backend = self._backend()
        pm = generate_preset_pass_manager(backend=backend, optimization_level=self._opt_level)
        isa = [pm.run(c) for c in circuits]
        sampler = Sampler(mode=backend)
        sampler.options.dynamical_decoupling.enable = True
        job = sampler.run(isa, shots=shots)
        return ProviderJobRef(provider=self.name, external_id=job.job_id(), backend_name=backend.name)

    def status(self, ref: ProviderJobRef) -> JobState:
        raw = self._service.job(ref.external_id).status()
        return _STATE_MAP.get(str(raw).upper(), JobState.QUEUED)

    def result(self, ref: ProviderJobRef) -> SamplingResult:
        job = self._service.job(ref.external_id)
        res = job.result()
        # ім'я регістру = "meas" для measure_all(); для довільних регістрів беремо перше поле
        counts = [next(iter(pub.data.values())).get_counts() for pub in res]
        return SamplingResult(counts=counts, qpu_seconds=_quantum_seconds(job))

    def cancel(self, ref: ProviderJobRef) -> None:
        self._service.job(ref.external_id).cancel()


def _quantum_seconds(job) -> float | None:
    # структура metrics() відрізняється між версіями клієнта — читаємо обережно
    try:
        return float(job.metrics()["usage"]["quantum_seconds"])
    except Exception:  # noqa: BLE001 — метрика допоміжна, не валимо задачу
        return None

import uuid

from qiskit import QuantumCircuit
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_aer import AerSimulator
from qiskit_ibm_runtime import SamplerV2 as Sampler

from app.quantum.providers.base import JobState, ProviderJobRef, SamplingResult


class AerProvider:
    """Синхронний локальний провайдер: submit одразу рахує результат і тримає його в пам'яті.
    Підходить для dev/CI і для одного процесу-воркера. Для кількох воркерів кладіть результат у Redis."""

    name = "aer"

    def __init__(self, backend=None):
        self._backend = backend or AerSimulator()
        self._results: dict[str, SamplingResult] = {}

    def submit(self, circuits: list[QuantumCircuit], shots: int) -> ProviderJobRef:
        pm = generate_preset_pass_manager(backend=self._backend, optimization_level=1)
        res = Sampler(mode=self._backend).run([pm.run(c) for c in circuits], shots=shots).result()
        counts = [next(iter(pub.data.values())).get_counts() for pub in res]
        ref = ProviderJobRef(provider=self.name, external_id=str(uuid.uuid4()),
                             backend_name=self._backend.name)
        self._results[ref.external_id] = SamplingResult(counts=counts)
        return ref

    def status(self, ref: ProviderJobRef) -> JobState:
        return JobState.DONE if ref.external_id in self._results else JobState.ERROR

    def result(self, ref: ProviderJobRef) -> SamplingResult:
        return self._results.pop(ref.external_id)

    def cancel(self, ref: ProviderJobRef) -> None:
        self._results.pop(ref.external_id, None)

import hashlib
import json
from uuid import UUID

from fastapi import APIRouter, Depends, Header, HTTPException, status

from app.core.dependencies import get_current_user, get_quantum_job_repo
from app.schemas.quantum import MaxCutRequest, QuantumJobOut
from app.workers.quantum_tasks import submit_quantum_job

router = APIRouter(prefix="/quantum/jobs", tags=["quantum"])


@router.post("", response_model=QuantumJobOut, status_code=status.HTTP_202_ACCEPTED)
async def create_job(
    body: MaxCutRequest,
    idempotency_key: str | None = Header(default=None, alias="Idempotency-Key"),
    user=Depends(get_current_user),
    repo=Depends(get_quantum_job_repo),
):
    # ключ ідемпотентності: явний заголовок або хеш нормалізованого запиту
    key = idempotency_key or hashlib.sha256(
        json.dumps(body.model_dump(), sort_keys=True).encode()
    ).hexdigest()

    if existing := await repo.get_by_key(user.id, key):
        return existing

    await repo.check_budget(user.id, estimated_shots=body.shots)   # 402/429, якщо ліміт вичерпано
    job = await repo.create(user_id=user.id, idempotency_key=key, payload=body.model_dump())
    submit_quantum_job.delay(str(job.id))
    return job


@router.get("/{job_id}", response_model=QuantumJobOut)
async def get_job(job_id: UUID, user=Depends(get_current_user), repo=Depends(get_quantum_job_repo)):
    job = await repo.get(job_id, user_id=user.id)
    if job is None:
        raise HTTPException(status_code=404, detail="job not found")
    return job
app/workers/quantum_tasks.py
import logging
from datetime import UTC, datetime, timedelta

import sentry_sdk

from app.quantum.maxcut import build_maxcut_circuit, decode_best_cut
from app.quantum.providers.base import JobState, ProviderJobRef
from app.quantum.providers.factory import get_quantum_provider
from app.quantum.repo_sync import QuantumJobRepoSync   # синхронний репозиторій для воркера
from app.workers.celery_app import celery_app

log = logging.getLogger(__name__)
POLL_SCHEDULE = [10, 20, 30, 60]          # секунди: швидко на старті, потім рідше
MAX_WAIT = timedelta(hours=6)             # після цього — cancel і FAILED


@celery_app.task(
    name="submit_quantum_job",
    bind=True,
    autoretry_for=(ConnectionError, TimeoutError),
    retry_backoff=True,
    max_retries=5,
    acks_late=True,
)
def submit_quantum_job(self, job_id: str) -> None:
    repo = QuantumJobRepoSync()
    job = repo.get(job_id)
    if job.external_job_id:               # ідемпотентність: вже відправлено — тільки поллимо
        poll_quantum_job.apply_async(args=[job_id], countdown=POLL_SCHEDULE[0])
        return

    req = job.payload
    circuit = build_maxcut_circuit(req["num_nodes"], req["edges"], reps=req["reps"])
    provider = get_quantum_provider()
    ref = provider.submit([circuit], shots=req["shots"])

    # КРИТИЧНО: зберегти зовнішній id ДО того, як щось ще може впасти
    repo.mark_submitted(job_id, provider=ref.provider, backend_name=ref.backend_name,
                        external_job_id=ref.external_id)
    sentry_sdk.set_tag("quantum.job_id", ref.external_id)
    log.info("quantum job submitted", extra={"job_id": job_id, "ibm_job_id": ref.external_id,
                                             "backend": ref.backend_name})
    poll_quantum_job.apply_async(args=[job_id], countdown=POLL_SCHEDULE[0])


@celery_app.task(name="poll_quantum_job", bind=True, max_retries=None, acks_late=True)
def poll_quantum_job(self, job_id: str, attempt: int = 0) -> None:
    repo = QuantumJobRepoSync()
    job = repo.get(job_id)
    if job.status in ("SUCCEEDED", "FAILED", "CANCELLED"):
        return

    provider = get_quantum_provider()
    ref = ProviderJobRef(job.provider, job.external_job_id, job.backend_name)
    state = provider.status(ref)

    if state is JobState.DONE:
        res = provider.result(ref)
        best = decode_best_cut(res.counts[0], job.payload["edges"])
        repo.mark_succeeded(job_id, result=best, qpu_seconds=res.qpu_seconds)
        return
    if state in (JobState.ERROR, JobState.CANCELLED):
        repo.mark_failed(job_id, error=f"provider state {state}")
        return

    if datetime.now(UTC) - job.submitted_at > MAX_WAIT:
        provider.cancel(ref)
        repo.mark_failed(job_id, error="timeout waiting for QPU")
        return

    repo.mark_status(job_id, "RUNNING" if state is JobState.RUNNING else "SUBMITTED")
    delay = POLL_SCHEDULE[min(attempt, len(POLL_SCHEDULE) - 1)]
    poll_quantum_job.apply_async(args=[job_id], kwargs={"attempt": attempt + 1}, countdown=delay)
💡
Чому не job.result() у воркері. Він блокує процес воркера на години черги — один такий job займе слот Celery повністю. Ланцюжок коротких задач poll → apply_async(countdown) тримає воркер вільним і переживає рестарти. Альтернатива для великих обсягів — окремий "reconciler": періодична задача (Celery beat), яка раз на хвилину перевіряє всі незавершені job-и пачкою.

from dataclasses import dataclass


@dataclass(frozen=True)
class CostEstimate:
    est_qpu_seconds: float
    two_qubit_gates: int
    depth: int


def estimate(isa_circuit, shots: int, per_shot_us: float = 250.0, overhead_s: float = 2.0) -> CostEstimate:
    """Груба оцінка: накладні + shots × тривалість одного прогону. Калібруйте коефіцієнти
    за фактичними metrics() ваших job-ів — реальна формула білінгу IBM інша й змінюється."""
    ops = isa_circuit.count_ops()
    two_q = sum(n for g, n in ops.items() if g in {"cz", "ecr", "cx"})
    return CostEstimate(
        est_qpu_seconds=overhead_s + shots * per_shot_us / 1e6,
        two_qubit_gates=two_q,
        depth=isa_circuit.depth(),
    )


def guard(cost: CostEstimate, remaining_seconds: float, max_two_qubit_gates: int = 2000) -> None:
    if cost.two_qubit_gates > max_two_qubit_gates:
        raise ValueError("circuit too deep for current hardware — result would be mostly noise")
    if cost.est_qpu_seconds > remaining_seconds:
        raise PermissionError("QPU budget exceeded")

18 Варіаційний цикл: QAOA для MaxCut

Найтиповіша "гібридна" програма: класичний оптимізатор керує параметрами квантової схеми.

MaxCut: розбити вершини графа на дві групи так, щоб якомога більше ребер з'єднували різні групи. Задача NP-складна і природно записується як гамільтоніан H = Σ(i,j)∈E ZiZj: кожна вершина — кубіт, Z = ±1 — номер групи. Мінімум енергії H = максимальний розріз. QAOA будує параметризовану схему з параметрами (γ, β), Estimator міряє ⟨H⟩, класичний оптимізатор (COBYLA) підкручує параметри.

app/quantum/maxcut.py
import numpy as np
from qiskit import QuantumCircuit
from qiskit.circuit.library import QAOAAnsatz
from qiskit.primitives import StatevectorEstimator
from qiskit.quantum_info import SparsePauliOp
from scipy.optimize import minimize


def maxcut_hamiltonian(n: int, edges: list[tuple[int, int]]) -> SparsePauliOp:
    # мінімізуємо Σ Z_i Z_j: ребро "розрізане", коли Z_i Z_j = -1
    return SparsePauliOp.from_sparse_list([("ZZ", [i, j], 1.0) for i, j in edges], num_qubits=n)


def build_maxcut_circuit(n: int, edges: list[tuple[int, int]], reps: int = 1, seed: int = 7) -> QuantumCircuit:
    """Стратегія для Open plan: параметри оптимізуємо на точному симуляторі (n <= ~20),
    а на QPU відправляємо лише фінальну схему для вибірки."""
    hamiltonian = maxcut_hamiltonian(n, edges)
    ansatz = QAOAAnsatz(cost_operator=hamiltonian, reps=reps)
    estimator = StatevectorEstimator()

    def cost(theta: np.ndarray) -> float:
        return float(estimator.run([(ansatz, hamiltonian, theta)]).result()[0].data.evs)

    x0 = np.random.default_rng(seed).uniform(0, np.pi, ansatz.num_parameters)
    opt = minimize(cost, x0, method="COBYLA", options={"maxiter": 300})

    qc = ansatz.assign_parameters(opt.x)
    qc.measure_all()
    return qc


def cut_value(bitstring: str, edges: list[tuple[int, int]]) -> int:
    bits = bitstring[::-1]            # Qiskit little-endian: qubit 0 — крайній правий символ
    return sum(1 for i, j in edges if bits[i] != bits[j])


def decode_best_cut(counts: dict[str, int], edges: list[tuple[int, int]]) -> dict:
    shots = sum(counts.values())
    scored = sorted(((cut_value(b, edges), c, b) for b, c in counts.items()), reverse=True)
    best_val, _, best_bits = scored[0]
    expected = sum(cut_value(b, edges) * c for b, c in counts.items()) / shots
    return {
        "partition": [int(x) for x in best_bits[::-1]],  # partition[i] = група вершини i
        "cut_value": best_val,
        "expected_cut": round(expected, 3),               # середня якість — чесніша метрика за "best"
        "distinct_samples": len(counts),
    }

from scipy.optimize import minimize
from qiskit.circuit.library import QAOAAnsatz
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime import EstimatorV2 as Estimator, QiskitRuntimeService, Session

from app.quantum.maxcut import maxcut_hamiltonian

edges = [(0, 1), (1, 2), (2, 3), (3, 0), (0, 2)]
H = maxcut_hamiltonian(4, edges)
ansatz = QAOAAnsatz(cost_operator=H, reps=2)

service = QiskitRuntimeService()
backend = service.least_busy(operational=True, simulator=False, min_num_qubits=4)
pm = generate_preset_pass_manager(backend=backend, optimization_level=3)
isa_ansatz = pm.run(ansatz)                     # транспілюємо ОДИН раз — параметри лишаються символьними
isa_H = H.apply_layout(isa_ansatz.layout)

history: list[float] = []
with Session(backend=backend) as session:
    estimator = Estimator(mode=session)
    estimator.options.default_shots = 2000
    estimator.options.dynamical_decoupling.enable = True

    def cost(theta):
        ev = estimator.run([(isa_ansatz, isa_H, theta)]).result()[0].data.evs
        history.append(float(ev))
        return float(ev)

    opt = minimize(cost, np.full(ansatz.num_parameters, 0.5), method="COBYLA", options={"maxiter": 60})

print("best energy:", opt.fun, "iterations:", len(history))

Частина V · Перевір себе

QA Питання й відповіді

Перевірка розуміння і типові питання на співбесіді на позицію, де бекенд працює з QPU.

01БазаЧому виклик QPU в бекенді завжди асинхронний?

QPU — спільний ресурс із чергою: між run() і виконанням можуть минути хвилини або години. Тримати HTTP-з'єднання стільки не можна, тому шаблон — 202 з ID, фонова задача (Celery), зберігання job_id у БД, polling або сповіщення.

02БазаЩо таке ISA-схема і чому примітиви не приймають звичайну?

ISA-схема містить лише нативні гейти процесора і двокубітні операції тільки між фізично з'єднаними кубітами. Транспіляцію винесли на клієнт, щоб розробник бачив і контролював результат (глибину, layout), а сервіс не робив неочевидних перетворень.

Що перевіряють: розуміння basis gates, coupling map, SWAP-оверхеду і впливу глибини на шум.
03БазаКоли Sampler, а коли Estimator?

Sampler — коли потрібен розподіл бітрядків (рішення оптимізаційної задачі, QRNG, пошук). Estimator — коли потрібне середнє значення спостережуваної (енергія, функція вартості у VQE/QAOA); він також вміє вбудовану mitigation (TREX, ZNE).

04ПасткаНавіщо apply_layout для спостережуваної?

Після транспіляції логічні кубіти 0 і 1 можуть опинитися на фізичних 37 і 38 процесора на 127 кубітів. Спостережувана має бути описана в тих самих фізичних індексах і на тій самій кількості кубітів, що й ISA-схема, інакше Estimator поверне помилку або, гірше, порахує не те.

05ПасткаВоркер упав після sampler.run(), але до запису в БД. Що відбулося і як цього уникнути?

Job виконається і буде оплачений, але ваша система про нього не знає; ретрай задачі відправить дублікат. Мінімізуємо вікно: запис job_id — перша дія після submit; задачі з acks_late; для повного захисту — теги job-а (job_tags в опціях runtime) з вашим внутрішнім ID і reconciler, який знаходить "сирітські" job-и через service.jobs(...).

Що перевіряють: мислення про розподілені збої і "at-least-once" доставку при зовнішніх платних викликах.
06БазаЧим відрізняються job, batch і session?

Job — одна задача в загальній черзі. Batch — набір незалежних задач, які планувальник виконує щільніше. Session — ексклюзивне вікно для ітеративних алгоритмів, коли наступний крок залежить від попереднього (VQE/QAOA); на безкоштовному плані недоступна.

07ГлибшеЧим suppression відрізняється від mitigation і як це впливає на вартість?

Suppression (dynamical decoupling, twirling) зменшує помилки під час виконання і майже нічого не коштує. Mitigation (TREX, ZNE, PEC) виправляє оцінку постфактум ціною додаткових запусків: ZNE — у кілька разів більше QPU-часу, PEC — експоненційно. Тому рівень mitigation — це параметр тарифу і бюджету, а не "завжди максимум".

08БазаЯк тестувати квантовий бекенд у CI?

Чисті функції побудови схем і декодування — через Statevector з точними ймовірностями. Інтеграцію з примітивами — через AerSimulator з фіксованим seed. Сумісність з реальним залізом — через fake backends (реальна топологія, basis gates, модель шуму). Справжній QPU — лише ручний smoke-тест.

09ПасткаЗамовник хоче "квантову оптимізацію маршрутів, бо це швидше". Що відповісте?

Що на сьогоднішньому залізі квантова оптимізація для реальних розмірів не швидша і не якісніша за OR-Tools чи комерційні солвери; вона корисна як дослідження і як підготовка до майбутнього. Запропоную гібрид: класичний солвер у продакшні, квантовий шлях — експериментальний провайдер за feature flag із порівнянням якості. Цифри — з baseline, а не з маркетингу.

10ГлибшеЧому результат QAOA варто оцінювати за "expected cut", а не лише за найкращим бітрядком?

З тисяч shots на шумному залізі випадково трапиться і хороший бітрядок — навіть рівномірний шум для малого графа знайде оптимум. Найкращий бітрядок показує, що його можна знайти перебором вибірки, а середня якість розподілу показує, чи схема справді зміщує ймовірність до хороших рішень. Порівнюйте обидві метрики з випадковою вибіркою і класичним baseline.
