01 Що ви вмітимете після цього туторіалу

Один конкретний навик, доведений до рівня «роблю сам, без підглядання»: запустити схему на справжньому квантовому процесорі і правильно прочитати, що повернулось.

У туторіалі 3 ми дивились на QPU очима архітектора бекенду: адаптер провайдера, Celery-воркер, ретраї, бюджет. У туторіалі 11 — збирали схеми й ганяли їх на Aer. Цей туторіал — «перший виїзд на реальну дорогу»: що саме треба натиснути в кабінеті IBM, які рядки Python виконати, як не спалити безкоштовні хвилини на помилці транспіляції і як інтерпретувати шумний результат.

Перший запуск на QPU — як перший прогін застосунку на справжньому дешевому Android-телефоні після роботи в DevTools із device emulation. Код той самий, але з'являються реальні затримки, шум і "погода" конкретного пристрою. Fake-бекенд — це профіль троттлінгу CPU/мережі, знятий з реального девайса на конкретну дату (як снапшот BrowserStack); реальний QPU — той самий телефон сьогодні, з іншим зарядом батареї й фоновими процесами. А Open Plan з його хвилинами — це ліміт хвилин GitHub Actions: спершу все ганяєте локально, на "залізо" — лише фінальний прогін.
Де аналогія ламається: калібрування QPU змінюються щодня, і на ваш job чекає черга інших користувачів — результат не можна "перезапустити в один клік" миттєво.
💡
Чесно про перевірку: у мене немає IBM-токена, тож на реальному залізі код не запускався. Усе, що працює офлайн (fake-бекенди, local testing mode, Estimator, ручні TREX/ZNE) — реально виконано, і виходи на сторінці справжні. Гістограми «з реального QPU» — ілюстративні, побудовані на типових для Heron-процесорів рівнях помилок, і підписані як такі. API-сигнатури перевірено інтроспекцією встановленого qiskit-ibm-runtime 0.50.0.

05 Огляд бекендів і калібрувань

Перед відправкою подивіться, на якому чипі рахуєте і які в нього помилки.

scripts/list_backends.py
from qiskit_ibm_runtime import QiskitRuntimeService

service = QiskitRuntimeService(name="open-learning")

for b in service.backends(simulator=False, operational=True):
    st = b.status()
    print(f"{b.name:14} qubits={b.num_qubits:4} pending_jobs={st.pending_jobs}")

backend = service.least_busy(operational=True, simulator=False, min_num_qubits=2)
print("chosen:", backend.name)

least_busy у 0.50 має сигнатуру least_busy(min_num_qubits=None, instance=None, filters=None, use_fractional_gates=False, **kwargs); operational і simulator ідуть через **kwargs як фільтри до backends(). «Найменш завантажений» = найменше pending_jobs, а не «найкращий за якістю».

Калібрування: Target

Усе, що транспілятору треба знати про чип, лежить у backend.target: нативні гейти, пари кубітів, на яких є двокубітний гейт, і помилка кожної операції. Однаковий API у реального бекенду і fake-бекенду — тому можна вчитися офлайн.

work/pick_pair.py — реально запущено на FakeFez
from qiskit_ibm_runtime.fake_provider import FakeFez

be = FakeFez()            # знімок калібрування Heron r2 156 кубітів; для реального: service.backend("ibm_fez")
t = be.target
ro = {q: t["measure"][(q,)].error for q in range(be.num_qubits)}

best = []
for (a, b), props in t["cz"].items():
    if props is None or props.error is None:
        continue
    best.append((props.error + ro[a] + ro[b], a, b, props.error, ro[a], ro[b]))
best.sort()
for s, a, b, cz, ra, rb in best[:3]:
    print(f"({a},{b}) cz={cz:.4f} ro=({ra:.4f},{rb:.4f}) score={s:.4f}")
print("worst:", best[-1][1:3], f"score={best[-1][0]:.4f}")
print("native ops:", list(t.operation_names))

Що тут видно:

  • Нативний набір Heron — cz, rz, sx, x + вимірювання. h і cx там немає: їх розкладе транспілятор.
  • Помилка зчитування (measure) ~0.2–1.5 % — того ж порядку, що й помилка двокубітного гейта. Для короткої схеми Bell саме readout часто домінує.
  • Пара (68,69) має помилку 1.0 — це «мертвий» каплер у знімку калібрування. Транспілятор з optimization_level≥1 зазвичай обходить такі пари, але якщо ви жорстко задасте initial_layout=[68, 69], отримаєте шум замість Bell (див. розділ 9).
  • Також є be.properties() (старіший API): readout_error(q), t1(q), t2(q). На FakeFez для кубіта 0: readout 0.0115, T1 ≈ (≈ — «приблизно дорівнює») 48.8 мкс, T2 ≈ 42.4 мкс.
⚠️
Fake ≠ сьогоднішній реальний чип. FakeFez — знімок калібрування на дату релізу пакета (тут backend_version 1.2.8). Реальний ibm_fez перекалібровується щодня; «найкраща пара» сьогодні може бути іншою. Для реального запуску рахуйте score з service.backend("ibm_fez").target безпосередньо перед відправкою.

06 Dry-run на fake-бекенді: безкоштовна репетиція

Правило: жодна схема не йде на QPU, поки не пройшла той самий код на fake-бекенді.

Fake-бекенд (qiskit_ibm_runtime.fake_provider) має ту саму target (гейти, топологію, помилки), що й реальний чип на дату знімка. Коли ви передаєте його в примітив як mode=, runtime вмикає local testing mode: схема симулюється локально через Aer з шумовою моделлю цього чипа. Код при цьому ідентичний до реального запуску — відрізняється одна функція get_backend().

bell_lab.py — один скрипт для fake і real
"""Bell-стан: dry-run на fake-бекенді або запуск на реальному QPU.

python bell_lab.py --mode fake      # безкоштовно, офлайн
python bell_lab.py --mode real      # витрачає QPU-секунди Open Plan
"""
import argparse, json, time, warnings
from pathlib import Path

from qiskit import QuantumCircuit
from qiskit.transpiler import generate_preset_pass_manager

warnings.filterwarnings("ignore", category=DeprecationWarning)
SHOTS = 4000


def get_backend(mode: str):
    if mode == "fake":
        from qiskit_ibm_runtime.fake_provider import FakeFez
        return FakeFez()
    from qiskit_ibm_runtime import QiskitRuntimeService
    service = QiskitRuntimeService(name="open-learning")
    return service.least_busy(operational=True, simulator=False, min_num_qubits=2)


def bell() -> QuantumCircuit:
    qc = QuantumCircuit(2, name="bell")
    qc.h(0)
    qc.cx(0, 1)
    qc.measure_all()
    return qc


def main(mode: str) -> None:
    backend = get_backend(mode)
    pm = generate_preset_pass_manager(backend=backend, optimization_level=1)
    isa = pm.run(bell())
    print("backend:", backend.name)
    print("ISA ops:", dict(isa.count_ops()), "depth:", isa.depth())
    print("physical qubits:", isa.layout.final_index_layout())

    from qiskit_ibm_runtime import SamplerV2 as Sampler   # див. розділ 15 про executor_sampler
    sampler = Sampler(mode=backend)
    sampler.options.environment.job_tags = ["bell-lab"]
    job = sampler.run([isa], shots=SHOTS)
    print("job_id:", job.job_id())
    Path("last.job.json").write_text(json.dumps(
        {"job_id": job.job_id(), "backend": backend.name, "ts": time.time()}))

    result = job.result()                 # блокує до DONE/ERROR/CANCELLED
    counts = result[0].data.meas.get_counts()
    good = (counts.get("00", 0) + counts.get("11", 0)) / SHOTS
    print("counts:", dict(sorted(counts.items())))
    print(f"P(00)+P(11) = {good:.4f}")


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--mode", choices=["fake", "real"], default="fake")
    main(ap.parse_args().mode)

import time

FINAL = {"DONE", "ERROR", "CANCELLED"}

def wait(job, every_s: float = 30, timeout_s: float = 6 * 3600):
    started = time.monotonic()
    while True:
        status = str(job.status()).split(".")[-1].upper()   # str у cloud, enum у local mode
        print(time.strftime("%H:%M:%S"), status)
        if status in FINAL:
            return status
        if time.monotonic() - started > timeout_s:
            raise TimeoutError(f"job {job.job_id()} still {status}")
        time.sleep(every_s)

11 Estimator: ⟨ZZ⟩, ⟨XX⟩, ⟨ZI⟩ на залізі

Sampler дає бітрядки; Estimator одразу дає середнє значення спостережуваної з похибкою — і вміє вбудовану mitigation.

Для стану Белла |Φ⁺⟩ = (|00⟩+|11⟩)/√2 (Φ — «фі велика») ідеальні значення: ⟨ZZ⟩ = 1, ⟨XX⟩ = 1, ⟨ZI⟩ = 0. Перші два разом — «свідок» заплутаності: класична суміш 00/11 дала б ⟨ZZ⟩ = 1, але ⟨XX⟩ = 0. Тобто Estimator бачить те, чого не бачить гістограма в Z-базисі — фазову когерентність.

Readout mitigation через матрицю плутанини

Ідея (сучасний TREX робить це хитріше, через twirling, але суть та сама): готуємо кожен базисний стан, міряємо, будуємо матрицю M[i, j] = P(виміряли i | приготували j). Тоді виміряний розподіл p̃ = M·p (p̃ — «p з хвилькою»), і справжній p ≈ M⁻¹·p̃. Для фронтендера: це як корекція аналітики на відомий bias вимірювання. Якщо з A/B-тестів ви знаєте, що adblock "з'їдає" 20 % подій кнопки A і 5 % кнопки B, ви спершу міряєте цю матрицю втрат на контрольних подіях, а потім "розвертаєте" сирі лічильники, щоб отримати справжні частки. Матриця плутанини — та сама відома "матриця втрат" для бітів 0/1.

readout_mitigation.py — реально запущено, 20 000 shots
import numpy as np
from qiskit import QuantumCircuit
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime import SamplerV2 as Sampler
from qiskit_ibm_runtime.fake_provider import FakeFez

be = FakeFez()
pm = generate_preset_pass_manager(backend=be, optimization_level=1, initial_layout=[0, 1])
keys = ["00", "01", "10", "11"]

def prep(bits: str) -> QuantumCircuit:      # bits у порядку Qiskit: "q1q0"
    qc = QuantumCircuit(2)
    if bits[1] == "1": qc.x(0)
    if bits[0] == "1": qc.x(1)
    qc.measure_all()
    return pm.run(qc)

bell = QuantumCircuit(2); bell.h(0); bell.cx(0, 1); bell.measure_all()
res = Sampler(mode=be, options={"default_shots": 20000}).run(
    [prep(k) for k in keys] + [pm.run(bell)]).result()    # 5 схем — ОДНА задача

def probs(pub):
    c = pub.data.meas.get_counts(); n = sum(c.values())
    return np.array([c.get(k, 0) / n for k in keys])

M = np.column_stack([probs(p) for p in res[:4]])   # стовпець j — приготували keys[j]
raw = probs(res[4])
mit = np.linalg.solve(M, raw)
zz = lambda p: p[0] - p[1] - p[2] + p[3]
print(np.round(M, 4)); print("raw", raw.round(4), "ZZ", round(zz(raw), 4))
print("mit", mit.round(4), "ZZ", round(zz(mit), 4))

ZNE: екстраполяція до нульового шуму

Шум підсилюють «згортанням» (folding): кожен CX замінюють на CX·CX·CX — логічно те саме (бо CX² = I), а помилок утричі більше. Міряють ⟨O⟩(λ) для кількох λ і екстраполюють до λ = 0. Для перевірки візьмемо глибшу схему: Bell + 4 «порожні» пари CX·CX, ідеальне ⟨ZZ⟩ = 1.

zne_manual.py — реально запущено, 40 000 shots на точку
import numpy as np
from qiskit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime import EstimatorV2 as Estimator
from qiskit_ibm_runtime.fake_provider import FakeFez

be = FakeFez()
pm = generate_preset_pass_manager(backend=be, optimization_level=1, initial_layout=[0, 1])

def circ(fold: int, layers: int = 4) -> QuantumCircuit:
    qc = QuantumCircuit(2); qc.h(0)
    for _ in range(layers):
        for _ in range(2 * fold):
            qc.cx(0, 1); qc.barrier()   # barrier не дає транспілятору скоротити CX·CX = I
    qc.cx(0, 1)
    return qc

pubs = []
for f in (1, 3, 5):
    isa = pm.run(circ(f))
    pubs.append((isa, SparsePauliOp("ZZ").apply_layout(isa.layout)))
    print("fold", f, "CZ =", isa.count_ops()["cz"])

Виміряно E(λ=1) = 0.84, E(λ=3) = 0.62, кожне зі стандартною похибкою σ. (а) Лінійна екстраполяція до λ=0. (б) Яка похибка екстрапольованого значення?

(а) Пряма через дві точки: E(0) = E(1) − (E(3) − E(1))/2 = (3·E(1) − E(3))/2 = (2.52 − 0.62)/2 = 0.95.

(б) Var[E(0)] = (9σ² + σ²)/4 = 2.5σ² ⇒ σ₀ = √2.5·σ ≈ 1.58σ. Щоб повернути початкову точність, потрібно в 2.5 рази більше shots на кожну точку — плюс сама схема з λ=3 утричі глибша. Ось чому ZNE «дорогий» і чому екстраполяція з 3 точок і нелінійною моделлю (як у resilience_level=2) ще дорожча за дисперсією.

Задача 17СкладноОбрати режим і mitigation

Для кожного сценарію на Open Plan оберіть режим виконання і resilience_level: (а) Bell-тест навику; (б) 30 незалежних схем для бенчмарку readout на різних парах; (в) VQE з 50 ітераціями оптимізатора; (г) схема з 60 CZ, вимірюється одна спостережувана.

(а) job; Sampler без mitigation (вам і треба побачити сирий шум) або Estimator level 1 для порівняння.

(б) один job з 30 PUB-ами або batch; resilience_level=0 — ви саме вимірюєте помилки, mitigation їх сховає.

(в) Ідеально — session, але на Open Plan він недоступний. Варіанти: job на кожну ітерацію (50 черг — може тривати добу), або зменшити кількість ітерацій (оптимізатор з малою кількістю викликів, теплий старт із симулятора) і/або оцінювати кілька наборів параметрів в одному job. Level 1.

(г) Глибока схема — помилки гейтів домінують: level 2 (ZNE) або level 1 + DD + twirling, якщо бюджет не дозволяє ZNE; збільшити shots з урахуванням росту дисперсії (задача 16).

Задача 18СкладноТестувати mitigation у CI

Ви пишете сервіс, що вмикає resilience_level=2. У CI немає токена. Як протестувати, що mitigation-конвеєр працює, якщо local mode його ігнорує?

Розділіть відповідальності: (1) контракт — юніт-тест, що в примітив передаються правильні опції (мок примітиву, перевірка options.resilience_level == 2, noise_factors); (2) математика — власні функції екстраполяції й інверсії readout тестуються на синтетичних даних з відомою відповіддю (наприклад, E(λ) = 0.97·e^{−0.12λ} → має повернути 0.97); (3) інтеграція офлайн — ручні TREX/ZNE з розділу 13 на FakeFez як регресійний тест («mitigated ближче до 1, ніж raw»); (4) смоук на залізі — рідкісний ручний або нічний job з малим бюджетом і тегом ci-smoke. Не перевіряйте точні числа з шумних прогонів — тільки нерівності з запасом у кілька σ.

Задача 19Складно«Захищений» скрипт першого запуску

Додайте до bell_lab.py запобіжники: не відправляти, якщо схема не ISA; shots ≤ 10 000; обов'язковий тег; підтвердження в консолі для режиму real; запис job_id до очікування.

MAX_SHOTS = 10_000 def assert_isa(circuit, backend): t = backend.target for inst in circuit.data: name = inst.operation.name if name in ("barrier",): continue qargs = tuple(circuit.find_bit(q).index for q in inst.qubits) if not t.instruction_supported(name, qargs): raise ValueError(f"not ISA: {name} on {qargs}") def submit(sampler, isa, backend, shots, mode): assert shots <= MAX_SHOTS, "shots cap" assert_isa(isa, backend) if mode == "real" and input(f"Send to {backend.name}? Target.instruction_supported(name, qargs) перевірено на FakeFez: ('h',(0,)) → False, ('cz',(0,1)) → True, ('cz',(0,5)) → False (немає з'єднання). Підтвердження в консолі — дешевий захист від «запустив real замість fake».

Задача 20СкладноReal гірший за fake на тій самій парі

На FakeFez пара [96, 103] дала P = 0.989, а на реальному ibm_fez сьогодні — 0.962 (ілюстративно), 8000 shots. Це значуще? Які причини і як перевірити?

Похибки: σ_fake = √(0.989·0.011/8000) ≈ 0.0012, σ_real = √(0.962·0.038/8000) ≈ 0.0021, σ різниці ≈ 0.0024. Різниця 0.027 ≈ 11σ — точно не статистика.

Причини: (1) знімок калібрування FakeFez старий — сьогодні ця пара може бути гіршою (калібровки змінюються щодня, деякі каплери тимчасово деградують); (2) fake-модель неповна: немає crosstalk, leakage, TLS-дефектів, немарківського шуму; (3) інший фізичний layout, якщо транспілятор переставив кубіти.

Перевірка: подивитися backend.target реального бекенду на момент запуску (помилки CZ і readout цієї пари), переконатися через isa.layout.final_index_layout(), що пара та сама; запустити readout-калібрування (розділ 13) у тому ж job; порівняти з іншою парою з хорошим сьогоднішнім score.
