Next.js — практичне використання

Практичні навички роботи з Next.js — маршрутизація, data fetching, базова структура проєкту — вже оцінені на реальних технічних співбесідах на високому рівні. Це не та тема, де варто витрачати основний час підготовки: додаткове читання документації API навряд чи підвищить враження, яке вже склалось.

"Поглиблення" тут означає не більше API-поверхні фреймворка, а саме архітектурне мислення навколо нього — те, які рішення про рендеринг і структуру застосунку приймаються на рівні продукту, а не окремого компонента. Це предмет наступних двох тем.

🟡

Стратегії рендерингу й оптимізації Next.js глибше

Next.js пропонує кілька принципово різних стратегій отримання даних для сторінки, і кожна — свідомий компроміс між свіжістю даних, швидкістю віддачі й навантаженням на сервер. Розуміти лише "як зробити" запит у компоненті недостатньо — важливо вміти пояснити, чому для конкретної сторінки обрано саме цю стратегію.

СтратегіяКоли отримуються даніНайкраще дляКомпроміс
SSR (Server-Side Rendering) На кожен запит, на сервері Персоналізований або часто змінний контент (дашборд, авторизований профіль) Найповільніший TTFB — сервер щоразу виконує повний рендер
SSG (Static Site Generation) Один раз, під час білду Контент, що майже не змінюється (лендінг, документація, блог-пост) Дані можуть застаріти до наступного білду й деплою
ISR (Incremental Static Regeneration) Під час білду, потім періодично перегенеровується у фоні Контент, що змінюється нечасто, але має "самооновлюватись" без повного редеплою (каталог товарів) Проміжна свіжість — читач може на короткий час побачити застарілу версію, поки йде фонова регенерація
App Router / Server Components На сервері, компонент за компонентом, з дрібнішою гранулярністю кешування Змішані сторінки, де частина дерева статична, а частина — динамічна, без падіння всієї сторінки до найповільнішої стратегії Складніша ментальна модель: потрібно свідомо розділяти server- і client-компоненти ("use client")

Ключова відмінність App Router — не просто "нова файлова структура", а можливість змішувати ці стратегії всередині однієї сторінки: частина дерева компонентів рендериться на сервері й кешується статично, а інтерактивна частина (наприклад, кошик покупок) залишається клієнтським компонентом. Це усуває стару дилему "вся сторінка або SSR, або вся SSG".

Оптимізація на рівні фреймворка йде далі за ручний React.lazy:

  • Оптимізація зображень — компонент next/image автоматично віддає зображення в сучасних форматах (WebP/AVIF), генерує потрібні розміри під viewport і лениво завантажує позаекранні зображення без ручної настройки.
  • Оптимізація шрифтів — вбудований механізм самостійно хостить шрифти Google Fonts разом зі статикою застосунку, усуваючи окремий мережевий запит до стороннього хосту й пов'язаний з ним "стрибок" тексту при завантаженні.
  • Розбиття коду на рівні фреймворка — кожен маршрут (route) автоматично стає окремим JS-чанком: користувач довантажує код лише тієї сторінки, яку відвідує, без ручного розставляння React.lazy на кожен великий компонент.
🎯
Що перевіряють: чи можете ви для конкретної сторінки реального продукту (наприклад, сторінка товару в інтернет-магазині) аргументовано обрати між SSG, ISR і SSR — а не просто перелічити визначення трьох абревіатур.
🔴

SSR під капотом

Таблиця вище показує наслідки кожної стратегії — але на співбесіді сеньйорського рівня частіше просять пояснити механізм: що конкретно відбувається між моментом, коли браузер надсилає запит, і моментом, коли користувач бачить готову сторінку.

Запит до сервера
→
Сервер виконує React-дерево
→
HTML згенеровано
→
HTML + дані надіслано
→
Браузер малює HTML (ще не інтерактивний)
→
JS-бандл завантажується
→
Гідратація
→
Інтерактивно

Крок за кроком: (1) сервер зіставляє URL із маршрутом; (2) виконує дерево React-компонентів просто в Node.js і викликає серверний рендер-API React — історично renderToString, у сучасних застосунках частіше стрімінгові renderToPipeableStream / renderToReadableStream — щоб отримати HTML-рядок або потік; (3) сервер вставляє цей HTML у повний документ разом із <script>-тегами клієнтського бандла й серіалізованими початковими даними, які знадобляться клієнту; (4) відповідь (можливо, частинами, якщо застосовано стрімінг) іде до браузера, який малює її одразу — саме тому SSR дає швидкий First Contentful Paint і повний контент "з коробки" для пошукових роботів.

⚠️
Критичний нюанс: намальований HTML на цьому кроці — ще не інтерактивний. Жоден обробник подій ще не прикріплений: клік по кнопці поки що нічого не робить. Прикріплення обробників — це вже робота гідратації (наступна тема).

Тепер точно, на рівні механізму, а не лише результату: CSR — браузер завантажує майже порожню HTML-оболонку і JS-бандл, і весь DOM будується з нуля вже в браузері, без жодного серверного кроку рендерингу. SSG — той самий крок рендерингу, що й у SSR, просто виконується один раз, під час білду, на білд-машині, і видає статичні HTML-файли, які CDN віддає як є, без виконання серверного коду на кожен запит. SSR — цей самий крок рендерингу виконується на живому сервері окремо для кожного вхідного запиту.

приклад: стрімінговий серверний рендер (спрощено)
import { renderToPipeableStream } from 'react-dom/server';

function handleRequest(req, res) {
  const { pipe } = renderToPipeableStream(<App />, {
    onShellReady() {
      res.setHeader('Content-Type', 'text/html');
      pipe(res); // перший, швидкий шматок HTML іде одразу
    },
    onError(err) {
      console.error(err);
    },
  });
}
🎯
Стрімінговий SSR (renderToPipeableStream разом із межами <Suspense>) дозволяє повільним частинам дерева "дострімитись" пізнішими шматками HTML замість того, щоб уся відповідь чекала на найповільніший запит даних. Саме на цьому механізмі побудований стрімінг App Router у Next.js — докладніше про Suspense-межі й UX-ефект — у супутньому Q&A-туторіалі.

Гідратація та регідратація

Гідратація — клієнтський процес, коли React "приєднується" до вже готового DOM, який згенерував сервер, замість того щоб викинути цей HTML і побудувати все заново. React проходить наявне дерево DOM і віртуальне дерево, яке видали б ті самі компонент-функції, і зіставляє їх один з одним, прикріплюючи обробники подій та внутрішній стан без повторного створення вузлів, що вже збігаються. Якби клієнт наївно рендерив усе з нуля поверх серверного HTML, це означало б повне перебудування дерева, видимий "блимок" інтерфейсу і втрату всієї користі від швидкого SSR-малювання.

Помилки неузгодженості гідратації (hydration mismatch) — найчастіший реальний баг цього механізму: якщо компонент під час рендеру звертається до чогось, що відрізняється між сервером і клієнтом (наприклад, new Date().toLocaleString() чи Math.random() прямо в тілі рендеру), клієнтський прогін тієї самої функції видає інше значення, ніж те, що реально прийшло в HTML із сервера. React виявляє розбіжність DOM, логує попередження про гідратацію і в багатьох випадках відкидає невідповідний піддерево, перерендерюючи його вже суто на клієнті — тобто саме в цьому місці частина користі SSR втрачається.

до: значення різне на сервері й клієнті
function LastUpdated() {
  // сервер видасть один рядок часу, клієнт при гідратації — інший
  return <span>Оновлено: {new Date().toLocaleString()}</span>;
}
після: значення однакове під час самої гідратації
function LastUpdated() {
  const [text, setText] = useState('');

  useEffect(() => {
    // виконується лише після монтування на клієнті —
    // сервер і початковий клієнтський рендер збігаються (порожній рядок)
    setText(new Date().toLocaleString());
  }, []);

  return <span>Оновлено: {text}</span>;
}

Інші типові причини неузгодженості: звернення під час рендеру до браузерних API (window, localStorage), яких просто не існує під час серверного виконання; розбіжність часового поясу чи локалі між сервером і клієнтом при форматуванні дат; розширення браузера, що встигає вставити власну розмітку в DOM ще до того, як відбудеться гідратація.

Регідратація — окреме поняття від першої, "стартової" гідратації сторінки: повторне приєднання React до нового серверно згенерованого фрагмента після, наприклад, клієнтської навігації. У App Router навігація може підвантажити свіжий вивід Server Components і влити його в уже змонтоване клієнтське дерево — це саме регідратація нового шматка, а не гідратація сторінки "з нуля".

Продуктивність: розрив між "HTML намальовано" (швидко, завдяки SSR) і "сторінка справді інтерактивна" (потрібно довантажити, розпарсити й виконати весь JS-бандл, а тоді завершити гідратацію) — реальна, іменована UX-проблема: користувач бачить кнопку, що виглядає клікабельною, ще до того, як вона реально під'єднана. Саме тому Time To Interactive (TTI) відстежують окремо від First Contentful Paint (FCP) — це різні моменти в часі.

Сучасні пом'якшення: стрімінговий SSR разом із вибірковою/поступовою гідратацією в React 18 — високопріоритетні інтерактивні частини (наприклад, поле пошуку) гідруються першими, а менш критичні (футер) — пізніше або лише за фактичної взаємодії користувача з ними. Більш радикальна альтернатива, яку використовують фреймворки на кшталт Astro, — islands architecture: лише окремі "острівці" інтерактивності на здебільшого статичній сторінці взагалі отримують JS і проходять гідратацію, решта сторінки лишається чистим HTML без жодного клієнтського JS.

⚠️
Найчастіший реальний баг: hydration mismatch через недетерміновані значення (час, випадкові числа, звернення до window) прямо в тілі рендеру. Правило: усе, що відрізняється між сервером і клієнтом, обчислюйте в useEffect після монтування, а не під час самого рендеру.

Типи архітектури вебзастосунків і масштабування

Коли один Next.js/React-застосунок і одна команда переростають у кілька команд з різними циклами релізів, постає питання архітектури на рівень вище окремого фреймворка. Тут важливо не "знати всі підходи", а розуміти реальний компроміс кожного — і головне, коли складність виправдана, а коли це передчасна інженерія.

Моноліт vs мікрофронтенди (module federation). Моноліт — один білд, один деплой, спільні залежності й версії React/бібліотек за замовчуванням узгоджені. Мікрофронтенди (наприклад, через Webpack Module Federation) дозволяють кільком командам деплоїти свої частини UI незалежно одна від одної — ціна цього: кожна частина може тягнути власну копію важких залежностей (або потрібна ретельна координація спільних версій), а налагодження проблем, що перетинають межі частин, стає складнішим. Головний тригер для переходу — організаційний (кілька автономних команд, що заважають одна одній у спільному репозиторії/білді), а не суто технічний масштаб трафіку.

Мікросервіси через iframe. Історично найпростіший спосіб ізолювати команди — кожна частина продукту живе у власному застосунку, вбудованому через <iframe>. Це дає повну ізоляцію стилів і рантайму "безкоштовно", але ціна — погана інтеграція в UX (складно зробити спільний скрол, модалки поверх межі iframe, узгоджену навігацію) і незручна комунікація між частинами (лише через postMessage, без прямого доступу до DOM чи стану одна одної). Це радше обмежений, часто застарілий підхід, ніж цільова архітектура для нового проєкту.

Web Components. Фреймворк-агностичні кастомні елементи (customElements.define) дозволяють ізолювати частину UI (включно зі стилями через Shadow DOM) так, щоб її можна було вставити в застосунок на будь-якому фреймворку — корисно, коли частину продукту потрібно "продавати" як вбудовуваний віджет для чужих сайтів, а не лише всередині власного застосунку на React.

✅
Головне правило вибору: кожен із цих підходів вирішує проблему організаційного масштабу (незалежні команди, незалежний деплой, чужі середовища вбудовування), а не проблему продуктивності чи трафіку. Додавати мікрофронтенди чи iframe-ізоляцію в застосунок з однією командою — це купувати складність координації версій і збірки без відповідної проблеми, яку вона мала б вирішувати.
