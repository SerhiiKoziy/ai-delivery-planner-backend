this і виклик функції

Головне правило, яке варто промовляти вголос, поки воно не стане автоматичним: this визначається способом виклику, а не місцем оголошення функції (крім стрілочних функцій — про них наприкінці розділу). Одна й та сама функція foo нижче поверне п'ять різних значень this залежно від того, як саме її викликати.

1. Звичайний виклик функції

приклад
function foo() {
  console.log(this);
}

foo();

У non-strict mode — this дорівнює глобальному об'єкту (window у браузері, globalThis узагалі). У strict mode ("use strict", або автоматично всередині ES-модулів і класів) — this дорівнює undefined. Причина: при звичайному виклику немає жодного об'єкта "зліва від крапки", тому рушій підставляє дефолтне значення — глобальний об'єкт історично (ще до strict mode), або свідомо undefined у strict mode, щоб випадковий запис на кшталт this.x = 1 усередині функції не тихо створював глобальну змінну.

🎯
Питання, яке ставлять одразу після: "як змінити this вручну?" — відповідь у розділі "Явне зв'язування" нижче (call/apply/bind).

2. Порожні фігурні дужки — не об'єкт

приклад
{}
// нічого не відбувається — і жодного стосунку до this

{} як окремий рядок коду (у позиції інструкції, а не виразу) — це порожній блок коду, а не об'єктний літерал. JS вирішує, як трактувати { на початку рядка, за контекстом синтаксичного аналізу: на початку інструкції — це блок; у позиції виразу (const obj = {}, чи в дужках ({})) — це об'єкт. Це той самий клас неоднозначності, через який стрілочна функція, що повертає об'єктний літерал одним рядком, вимагає дужок: () => ({ a: 1 }), інакше { a: 1 } прочитається як блок з міткою a і виразом 1.

3. Виклик через об'єкт — implicit binding

приклад
const x = { bar: foo };
x.bar();
// this === x

Коли функція викликається як метод — об'єкт.метод() — this стає саме тим об'єктом, через який стався виклик. Але це зв'язування прив'язане до синтаксису виклику, а не до функції самої по собі — щойно та сама функція від'єднується від об'єкта, зв'язок губиться:

класична пастка: "відірваний" метод
const f = x.bar;
f();
// this знову global (non-strict) / undefined (strict) —
// f викликана як звичайна функція, x тут узагалі не бере участі
⚠️
Це не рідкісний штучний приклад — це реальний щоденний баг: передача методу об'єкта як колбек (setTimeout(obj.method, 100), element.addEventListener('click', obj.method), деструктуризація методу з об'єкта) щоразу губить прив'язку так само, як const f = x.bar вище. Три стандартні виправлення: обгорнути у стрілочну функцію (() => obj.method()), заздалегідь прив'язати через bind (obj.method.bind(obj)), або оголосити метод як стрілочну властивість класу (method = () => {...}) — тоді this захоплюється лексично один раз при створенні екземпляра і більше ніколи не губиться.

4. Виклик через new — new binding

приклад
const y = new foo();
// this усередині foo — щойно створений порожній об'єкт y

new робить чотири речі одночасно: створює новий порожній об'єкт; прив'язує його прототип до foo.prototype; викликає foo з this, встановленим на цей новий об'єкт; і повертає цей об'єкт як результат виразу new foo() — якщо тільки сама функція явно не поверне інший об'єкт.

що якщо конструктор явно щось повертає
function FooObj() {
  this.a = 1;
  return { b: 2 };   // об'єкт — ПЕРЕМАГАЄ щойно створений this
}
new FooObj(); // { b: 2 }, властивість a втрачена

function FooPrim() {
  this.a = 1;
  return 42;         // примітив — ІГНОРУЄТЬСЯ повністю
}
new FooPrim(); // FooPrim { a: 1 }, значення 42 відкинуто

Правило запам'ятовується просто: new поверне явно повернутий об'єкт, якщо він об'єкт (включно з масивом чи функцією) — і завжди поверне щойно створений this, якщо явне повернене значення примітивне (число, рядок, булеве, undefined).

5. Явне зв'язування — call, apply, bind

приклад
const z = { a: 1 };
foo.apply(z);
// this === z
МетодВикликає функцію одразу?Як передає аргументи
call(thisArg, a, b, c)ТакПерелічені окремо, через кому
apply(thisArg, [a, b, c])ТакМасивом
bind(thisArg, a, b)Ні — повертає нову функціюЧастково застосовані (як у частковому застосуванні функцій), можна довизначити при реальному виклику
⚠️
Якщо z у прикладі вище взагалі не оголошено (не const z = {...}, а просто відсутня змінна) — це не "this буде undefined", а ReferenceError: z is not defined ще до виклику apply узагалі, бо z — некоректний вираз-аргумент сам по собі.

Порядок пріоритету й стрілочні функції

Коли кілька правил ніби застосовні одночасно, пріоритет такий (від найвищого): new binding → явне зв'язування (call/apply/bind) → implicit binding (виклик через об'єкт) → default binding (звичайний виклик). Стрілочні функції стоять окремо від усієї цієї ієрархії: вони не мають власного this узагалі й завжди беруть його лексично — з того оточення, де стрілочну функцію було оголошено, і жодне з правил вище (навіть new чи bind) не може це змінити. Детальніше про механіку лексичного this у стрілочних функціях — у туторіалі 1, тема 4.

Promise chaining: тонкощі

Друга тема, на якій "простий" ланцюжок .then() раптово перестає бути простим — те, що саме повертається з колбека .then, вирішує все.

Повернене значення автоматично загортається

приклад — перевірено запуском
Promise.resolve()
  .then(() => 5)
  .then(arg => console.log(arg)); // 5

Якщо колбек .then повертає звичайне значення — цей результат автоматично загортається у вже виконаний (resolved) проміс, і наступний .then отримує розгорнуте значення напряму.

Повернений проміс автоматично розпаковується

приклад — перевірено запуском
Promise.resolve()
  .then(() => Promise.resolve(5))
  .then(arg => console.log(arg)); // 5, а НЕ Promise{5}

Якщо колбек повертає вже готовий проміс — ланцюжок сам "розгортає" (flatten) його: чекає на завершення внутрішнього проміса і передає далі саме його розв'язане значення, а не вкладений Promise<Promise<5>>. Саме ця механіка робить .then()-ланцюжки плоскими, а не вкладеними, навіть коли всередині повертаються нові проміси.

Забутий resolve — вічно pending

приклад — перевірено запуском: наступний .then НІКОЛИ не виконається
Promise.resolve()
  .then(() => new Promise(() => {
    // executor отримує (resolve, reject), але жоден з них
    // тут не викликається — проміс лишається pending НАЗАВЖДИ
  }))
  .then(arg => console.log('це ніколи не надрукується'));
⚠️
Практичний наслідок: це не просто навчальний приклад — це реальна причина, чому await на такому промісі "зависає" назавжди без будь-якої помилки, а UI застрягає на індикаторі завантаження навічно. Виконавча функція (executor) конструктора Promise отримує resolve/reject як аргументи саме для того, щоб їх викликали — забутий виклик і є цілим багом.

Executor виконується синхронно й негайно

приклад
new Promise(() => {
  while (true) {}
});
// UI зависає / event loop блокується НАЗАВЖДИ

Функція-виконавець (executor), що передається в new Promise(executor), викликається синхронно й негайно — у момент виклику new Promise(...), а не колись пізніше в мікрозадачі. Синхронний нескінченний цикл усередині неї блокує основний потік точно так само, як блокував би поза будь-яким промісом — бо JS однопотоковий (детальніше про модель конкурентності — туторіал 1, тема 10), і жоден проміс сам по собі не дає "паралельності", яка врятувала б від синхронного блокування.

17 питань для співбесіди

Від визначень до трюкових кейсів, які реально ламають досвідчених кандидатів наживо.

База Пастка Просунуте Системний дизайн
01БазаЩо таке implicit, explicit, new і default binding — і який у них пріоритет?

Default — звичайний виклик, this = глобальний об'єкт/undefined. Implicit — виклик через об'єкт (obj.method()), this = цей об'єкт. Explicit — call/apply/bind, this задається вручну. New — виклик через new, this = щойно створений об'єкт. Пріоритет від найвищого: new → explicit → implicit → default. Стрілочні функції стоять поза цією системою — вони завжди беруть this лексично, і жодне з чотирьох правил на них не діє.

02ПасткаЩо виведе цей код?
питання
const obj = {
  foo: function() { return this; }
};
const bar = obj.foo;
bar();

bar() — звичайний виклик, не obj.bar(). Функція від'єдналась від obj у момент присвоєння const bar = obj.foo — саме посилання на функцію скопіювалось, а не зв'язок з об'єктом. Тому this усередині — глобальний об'єкт (non-strict) або undefined (strict), а не obj.

03ПросунутеТри способи не втратити this, передаючи метод як колбек

1. Стрілочна обгортка в місці виклику: setTimeout(() => obj.method(), 100) — стрілочна функція лексично захоплює зовнішній this, а виклик obj.method() усередині неї — це implicit binding, який і потрібен. 2. bind: setTimeout(obj.method.bind(obj), 100) — створює нову функцію з назавжди зафіксованим this. 3. Стрілочне поле класу: method = () => {...} замість звичайного методу — кожен екземпляр отримує власну функцію-властивість із this, захопленим один раз при створенні, тож її можна передавати як колбек без обгортки й без bind.

04ПасткаКласична пастка: вкладена звичайна функція всередині методу
питання
const obj = {
  name: 'obj',
  foo() {
    function inner() {
      console.log(this); // ?
    }
    inner();
  }
};
obj.foo();

inner() викликається як звичайна функція (немає obj зліва від крапки в цьому конкретному виклику) — тому this усередині inner це глобальний об'єкт/undefined, а не obj, попри те що inner оголошена всередині методу obj. Це одна з причин, чому до появи стрілочних функцій типовим обхідним шляхом було const self = this; перед вкладеною функцією, щоб зберегти доступ до зовнішнього this через звичайне замикання по змінній, а не через сам this.

05БазаЩо поверне конструктор, якщо явно повернути об'єкт? А примітив?

Явно повернений об'єкт перемагає щойно створений this — саме він і стає результатом new. Явно повернений примітив (число, рядок, булеве, undefined) повністю ігнорується — new усе одно поверне щойно створений об'єкт this з усіма властивостями, які встигли на нього записатись усередині конструктора.

06БазаУ чому різниця між call, apply і bind?

call(thisArg, arg1, arg2, ...) і apply(thisArg, [arg1, arg2]) обидва викликають функцію негайно із заданим this — різниця лише у формі передачі аргументів (перелік проти масиву; apply зручний, коли аргументи вже зібрані в масив). bind(thisArg, ...) нічого не викликає — повертає нову функцію із назавжди "приклеєним" this, яку можна викликати пізніше скільки завгодно разів.

07ПросунутеЧи можна перебити this у функції, створеній через bind — навіть викликавши її з new?

Ні, для звичайного повторного bind/call/apply — прив'язаний this незмінний. Але є один особливий виняток: якщо саму bound-функцію викликати через new, спрацьовує new binding замість зафіксованого this — специфікація явно дозволяє new "перебити" bind саме для цього випадку (хоча прив'язані заздалегідь аргументи як і раніше застосовуються). Це рідкісний нюанс, який вартий згадки саме на рівні senior, а не типова щоденна практика.

08БазаЧому стрілочні функції "ігнорують" усі правила this?

Стрілочні функції не мають власного зв'язування this узагалі — вони не створюють нового контексту виконання для нього. Замість цього this усередині стрілочної функції — це просто те саме значення this, яке було доступне в лексичному оточенні на момент оголошення функції (звичайний пошук по ланцюжку області видимості, як зі звичайною змінною) — тому ані call, ані apply, ані навіть виклик через об'єкт не можуть це змінити.

09БазаЧим різняться return value, return Promise.resolve(value) і return new Promise(...) усередині .then?

return value — звичайне значення автоматично загортається у виконаний проміс, наступний .then отримує його напряму. return Promise.resolve(value) — по суті те саме з погляду наступного .then (той самий фінальний ефект), лише написано явно. return new Promise((resolve, reject) => {...}) — ланцюжок буде чекати, поки хтось явно викличе resolve/reject усередині цього нового проміса; якщо жоден з них ніколи не викликається — ланцюжок зависає на цьому кроці назавжди (розділ 2 вище).

10ПасткаЩо виведе цей ланцюжок?
питання
Promise.resolve(1)
  .then(x => x + 1)
  .then(x => Promise.resolve(x + 1))
  .then(console.log);

Відповідь — 3. Крок за кроком: 1 → x + 1 = 2 (звичайне значення, автозагортання) → Promise.resolve(x + 1) = Promise.resolve(3) (автоматично розпаковується до 3) → console.log(3). Форма повернення (голе значення чи проміс) не впливає на фінальний результат — обидві автоматично зводяться до плоского ланцюжка розв'язаних значень.

11ПасткаТрюкове питання: що виведе цей ланцюжок з throw і catch усередині?
питання
Promise.resolve(1)
  .then(() => { throw new Error('err'); })
  .then(() => 2)
  .catch(() => 3)
  .then(console.log);

Відповідь — 3. throw усередині .then() перетворює результуючий проміс на відхилений (rejected) — виконання одразу перескакує через усі проміжні .then()-и (другий .then(() => 2) повністю пропускається) до найближчого обробника відхилення, тобто .catch(). .catch(() => 3) сам повертає звичайне значення 3 — це знову перетворює ланцюжок на розв'язаний (resolved), тож наступний .then(console.log) виконується як звичайно й отримує 3.

12ПросунутеТой самий трюк — але у формі async/await. Що зміниться?
еквівалент попереднього питання через async/await
async function run() {
  let x;
  try {
    x = await Promise.resolve(1).then(() => { throw new Error('err'); });
    x = 2; // ніколи не виконається — throw вище вже кинув
  } catch {
    x = 3;
  }
  console.log(x); // 3
}
run();

Логіка ідентична, лише синтаксис інший: throw усередині ланцюжка, на який очікує await, перетворюється на звичайний JS-виняток у точці await — тому його ловить найближчий оточуючий try/catch, повністю аналогічно до того, як .catch() ловить відхилений проміс. Це та сама механіка, просто інший синтаксичний фасад над нею.

13ПросунутеЧим відрізняються Promise.all, allSettled, race і any на змішаному наборі проміс?

Promise.all відхиляється одразу, щойно відхилився перший проміс — результати інших (навіть успішних) втрачаються. Promise.allSettled ніколи не відхиляється сам, повертає масив статусів кожного проміса окремо (fulfilled/rejected). Promise.race вирішується (успішно чи з відхиленням) станом того проміса, який завершився першим — байдуже, успіхом чи помилкою. Promise.any вирішується першим успішним результатом і ігнорує відхилення, поки не відхиляться геть усі проміси одразу. Детальніше з кодом — у туторіалі 1, тема 2.

14Системний дизайнЩо відбувається з необробленим (unhandled) відхиленням проміса в кінці ланцюжка без catch?

Середовище виконання (браузер чи Node) генерує подію "unhandled rejection" (window.onunhandledrejection у браузері) — користувач нічого явно не побачить у UI, якщо це не оброблено окремо, але сама помилка не зникає безслідно: саме на цій події базуються інструменти моніторингу (Sentry й подібні), автоматично відловлюючи такі відхилення без потреби вручну логувати кожне — детальніше в туторіалі 9, тема 3.

15ПасткаПастка this усередині .then(), коли колбек — метод класу
типовий реальний баг у класах з асинхронними методами
class Loader {
  data = null;
  load() {
    fetch('/api/data')
      .then(function(response) {
        this.data = response; // BUG: this тут НЕ екземпляр Loader
      });
  }
}

Звичайна (не стрілочна) функція, передана в .then(), викликається внутрішнім кодом Promise як звичайний виклик — implicit binding через обʼєкт.метод() тут не відбувається, тому this усередині — знову глобальний об'єкт/undefined, а не екземпляр Loader. Виправлення точно те саме, що й у розділі 3 вище: стрілочна функція замість звичайної (.then(response => { this.data = response; })) — вона захопить this самого методу load лексично.

16Базаthis у звичайному методі класу проти стрілочного поля класу

Звичайний метод класу (method() {...}) визначається на prototype і підпорядковується звичайним правилам виклику — якщо його від'єднати від екземпляра, this губиться так само, як у розділі 3. Стрілочне поле класу (method = () => {...}) створює окрему функцію для кожного екземпляра вже в конструкторі, з this, захопленим лексично (тобто рівним екземпляру) один раз і назавжди — ціна цього підходу: трохи більше пам'яті (окрема функція на кожен екземпляр замість однієї спільної на прототипі) заради гарантії, що прив'язку неможливо випадково втратити.

17ПросунутеЧи змінює strict mode те, як executor конструктора Promise виконується?

Ні — синхронність і негайність виконання executor-функції в new Promise(executor) не залежить від strict/non-strict mode взагалі; це властивість самого механізму Promise, а не правил визначення this. Strict mode впливає лише на те, яким буде this при звичайному виклику функції (розділ 1) — це дві незалежні одна від одної теми, які легко сплутати саме тому, що обидві часто обговорюються поряд у контексті "особливостей виконання функцій у JS".
