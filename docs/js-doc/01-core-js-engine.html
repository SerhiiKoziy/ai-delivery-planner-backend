Event loop, call stack, мікро/макротаск черги

Живий код на "що виведеться в консоль і в якому порядку" — типове завдання, де плавають навіть на середньому й вищому рівні, бо порядок виконання в JS не завжди інтуїтивний. JS однопотоковий: є один call stack, який виконує синхронний код зверху вниз. Коли зустрічається асинхронна операція (setTimeout, проміс, мережевий запит), вона не блокує стек, а реєструється деінде, і стек продовжує виконувати наступний синхронний рядок.

Коли асинхронна операція готова, її колбек не виконується одразу — він потрапляє в одну з двох черг. Мікрозадачі (обробники .then/.catch промісів, код після await, queueMicrotask) мають вищий пріоритет. Макрозадачі (setTimeout, setInterval, події UI) чекають своєї черги. Ключове правило event loop: після кожної завершеної синхронної ділянки коду рушій спершу повністю спорожняє чергу мікрозадач — і лише потім бере одну задачу з черги макрозадач.

приклад
console.log('1: sync');

setTimeout(() => console.log('2: macrotask (setTimeout)'), 0);

Promise.resolve().then(() => console.log('3: microtask (then)'));

(async () => {
  console.log('4: sync (у тілі async до await)');
  await null;
  console.log('5: microtask (після await)');
})();

console.log('6: sync');

// Порядок виводу: 1, 4, 6, 3, 5, 2
// — увесь синхронний код спершу (1, 4, 6),
// потім ВСІ мікрозадачі по черзі (3, 5),
// і лише тоді одна макрозадача (2), навіть з таймаутом 0.
🎯
Що перевіряють: чи розумієте ви, що setTimeout(fn, 0) не означає "виконати негайно" — це означає "виконати найшвидше, коли дійде черга, але точно після всіх поточних мікрозадач". Це і є найчастіша пастка в такому коді.

Async/await та обробка помилок у асинхронному коді

Що таке Promise насправді: об'єкт-обіцянка результату, який завжди перебуває в одному з трьох станів — pending (очікування, початковий стан), fulfilled (успішно виконано, є значення) або rejected (відхилено, є причина відмови). Перехід можливий лише один раз і лише в одному напрямку: із pending у fulfilled або в rejected — уже завершений проміс ніколи не змінить стан повторно, скільки б разів на нього не підписувались через .then().

async/await — це синтаксичний цукор над промісами: він не змінює модель виконання (описану вище), лише робить асинхронний код читабельним як синхронний. Але обробка помилок під ним має власні нюанси. try/catch навколо await ловить і синхронні помилки, і відхилення проміса — це найпростіший і найнадійніший спосіб. Окремий виклик .catch() на промісі теж працює, але легко забути його на одному з кількох незалежних await у функції, і тоді необроблене відхилення "тихо" піде вгору по ланцюжку викликів.

Другий нюанс — стек-трейс. Якщо помилку перекидають (re-throw) уручну без збереження оригінальної, або якщо асинхронна помилка ловиться в дуже загальному обробнику вищого рівня, легко втратити інформацію про те, де саме в ланцюжку промісів усе почалось. Практичне правило: не "проковтувати" помилку мовчки і не створювати нову помилку без причини (cause) — сучасний Error підтримує new Error('...', { cause: err }) саме для збереження оригінального контексту.

Третій нюанс — вибір правильного комбінатора промісів, коли їх декілька:

поведінка при одному відхиленні
const ok  = Promise.resolve(1);
const bad = Promise.reject(new Error('fail'));

await Promise.all([ok, bad]);
// -> кидає одразу, щойно ПЕРШИЙ проміс відхилився;
//    результат другого (успішного) проміса втрачається

await Promise.allSettled([ok, bad]);
// -> ніколи не кидає; повертає масив
//    [{status:'fulfilled', value:1}, {status:'rejected', reason:Error}]

await Promise.race([ok, bad]);
// -> повертає результат ТОГО, хто завершився першим (fulfilled чи rejected)

await Promise.any([ok, bad]);
// -> повертає перший УСПІШНИЙ результат;
//    кине лише якщо ВСІ проміси відхилились
⚠️
Типова пастка: Promise.all для незалежних запитів, один з яких може легітимно "не знайти дані" — тоді весь набір валиться через один неважливий провал. У такому випадку майже завжди правильніший вибір — Promise.allSettled.

for await...of — окрема конструкція для проходу по асинхронному ітерованому об'єкту (наприклад, асинхронному генератору чи потоку сторінок з API): кожна ітерація дочікується власного проміса, перш ніж перейти до наступної. Це принципова відмінність від Promise.all, який запускає всі проміси одночасно — for await обробляє їх послідовно, один за одним, що потрібно саме тоді, коли наступний крок логічно залежить від результату попереднього (наприклад, підвантаження наступної сторінки пагінованого списку).

послідовний обхід асинхронного генератора
async function* fetchPages() {
  yield await Promise.resolve('сторінка 1');
  yield await Promise.resolve('сторінка 2');
  yield await Promise.resolve('сторінка 3');
}

for await (const page of fetchPages()) {
  console.log(page); // 'сторінка 1', потім 'сторінка 2', потім 'сторінка 3' — по черзі
}

Лексична область видимості vs область виконання, hoisting, TDZ

Лексична (статична) область видимості визначається місцем, де змінна оголошена в тексті коду, і не залежить від того, звідки функцію викликали. Це відрізняється від "області виконання" (динамічного контексту виклику) — саме тому замикання (closures) працюють передбачувано: функція "пам'ятає" змінні свого оточення на момент оголошення, а не на момент виклику.

Hoisting — оголошення var і функцій піднімаються у вершину своєї області видимості ще до виконання коду (сама змінна, а не її значення). let і const теж "підняті" технічно, але потрапляють у Temporal Dead Zone (TDZ) — звернення до них до рядка оголошення кидає ReferenceError, замість мовчазного undefined, як було б із var.

класична пастка var + setTimeout у циклі
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// Виведе: 3, 3, 3
// var — одна спільна змінна на весь цикл; до моменту виконання
// колбеків цикл уже завершився, і i дорівнює 3.

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// Виведе: 0, 1, 2
// let створює НОВУ прив'язку змінної на кожну ітерацію циклу —
// кожен колбек замикається на своє власне i.
🎯
Що перевіряють: чи можете ви пояснити чому, а не лише "запам'ятати", що let виправляє цей приклад — саме через нову прив'язку змінної на ітерацію, а не через якусь магію блочної області видимості загалом.

this і контекст виклику

Значення this у звичайній функції визначається способом виклику, а не місцем оголошення: obj.method() — this дорівнює obj; проста виклик функції fn() — this дорівнює undefined у строгому режимі; fn.call(ctx)/fn.apply(ctx) — явно задає this; fn.bind(ctx) — повертає нову функцію з назавжди прив'язаним this.

Стрілочні функції — виняток: вони не мають власного this узагалі, а беруть його лексично, з місця, де стрілочна функція була оголошена в коді. Це зручно всередині колбеків, але стає багом, якщо стрілочну функцію використали там, де очікувалась динамічна прив'язка — наприклад, як метод об'єкта.

стрілочна функція як метод — типовий баг
const counter = {
  value: 0,
  // Стрілочна функція бере this з зовнішньої (модульної) області
  // видимості на момент оголошення, а не з counter — тут об'єкта
  // counter ще не існує в цьому лексичному контексті.
  incrementBad: () => {
    this.value++; // this !== counter
  },
  // Звичайна функція отримує this з місця виклику (counter.incrementGood())
  incrementGood() {
    this.value++; // this === counter
  },
};

Клонування об'єктів: неглибоке vs глибоке

Spread-оператор ({...obj}) і Object.assign({}, obj) копіюють лише перший рівень об'єкта: якщо всередині є вкладений об'єкт чи масив, копіюється посилання на нього, а не сам вміст — зміна вкладеного поля в копії вплине й на оригінал. Це називається неглибоким (shallow) клонуванням.

Для глибокого клонування сучасний і правильний вибір — вбудована функція structuredClone(obj), доступна в усіх сучасних браузерах і Node.js. Старий "хак" JSON.parse(JSON.stringify(obj)) теж клонує глибоко, але з важливими втратами: він мовчки псує чи губить Date (перетворює на рядок), поля зі значенням undefined, функції та не вміє циклічні посилання (кидає помилку).

пастка JSON.parse(JSON.stringify())
const original = { createdAt: new Date(), note: undefined };

const viaJson = JSON.parse(JSON.stringify(original));
console.log(viaJson.createdAt instanceof Date); // false — це вже рядок ISO
console.log('note' in viaJson);                 // false — поле зникло

const viaStructuredClone = structuredClone(original);
console.log(viaStructuredClone.createdAt instanceof Date); // true

Масивні методи "з нуля", не лише "яка сигнатура"

Типове завдання на живий код, де саме тут найлегше "поплисти" під тиском — не тому, що методи складні, а тому, що під стресом легко переплутати, який метод мутує оригінальний масив, а який повертає новий.

МетодПовертаєМутує оригінал?
forEachundefined (лише побічний ефект)Ні
mapновий масив тієї ж довжиниНі
filterновий масив (можливо коротший)Ні
slice(start, end)новий масив-зрізНі
splice(start, count, ...items)масив ВИДАЛЕНИХ елементівТак
⚠️
Мнемоніка, яка реально рятує на живому кодингу: slice — "тихий" і безпечний (не чіпає оригінал), splice — "хірургічний" і руйнівний (вирізає прямо з оригінального масиву). Схожі назви, протилежна поведінка — саме тому їх плутають найчастіше.

Генератори та ітератори

Функція-генератор (function*) при виклику не виконується одразу, а повертає об'єкт-ітератор. Кожен виклик .next() просуває виконання до наступного yield і призупиняє його там, повертаючи значення. Це рідше практикується в щоденній роботі, ніж масиви чи проміси, тому й забувається першим.

Під капотом генератори реалізують протокол ітератора: об'єкт вважається ітерованим, якщо в нього є метод [Symbol.iterator], що повертає об'єкт із методом .next(). Саме завдяки цьому протоколу такий об'єкт можна використовувати в for...of чи з оператором розкриття (spread).

власний ітерований об'єкт через генератор
function range(start, end) {
  return {
    [Symbol.iterator]: function* () {
      for (let i = start; i < end; i++) yield i;
    },
  };
}

console.log([...range(1, 4)]); // [1, 2, 3]
for (const n of range(1, 4)) console.log(n); // 1, 2, 3

Прототипи й класи як синтаксичний цукор над ними

У JS немає "класів" у класичному сенсі (як у Java/C#) — успадкування будується через ланцюжок прототипів: кожен об'єкт має внутрішнє посилання на інший об'єкт ([[Prototype]]), і якщо властивість не знайдена на самому об'єкті, пошук продовжується вгору цим ланцюжком. Object.create(proto) — найпряміший спосіб створити об'єкт із заданим прототипом уручну, без синтаксису класів узагалі, а Object.getPrototypeOf(obj) — зворотна операція: повертає сам об'єкт-прототип, на який посилається obj, незалежно від того, створений він через Object.create, звичайний конструктор функції чи class.

Ключовий момент для співбесіди: ключове слово class, додане в ES2015, — це синтаксичний цукор над тим самим прототипним механізмом, а не окрема модель ООП. class Dog extends Animal під капотом усе одно будує ланцюжок прототипів — тобто для екземпляра d = new Dog() виконується Object.getPrototypeOf(d) === Dog.prototype, а сам Object.getPrototypeOf(Dog.prototype) === Animal.prototype — той самий ланцюжок, що й для функцій-конструкторів, просто із зручнішим, знайомим за іншими мовами синтаксисом.

Як влаштований сам JS-рушій

Питання на цю тему перевіряють саме "що відбувається під капотом", а не "як користуватись мовою". Спрощений конвеєр виконання коду в рушії на кшталт V8 (Chrome, Node.js): вихідний текст спершу перетворюється на AST (абстрактне синтаксичне дерево), з якого швидкий "холодний" інтерпретатор (у V8 він називається Ignition) одразу генерує байткод і починає виконання. Ділянки коду, які виконуються багато разів ("гарячі" функції), рушій помічає й компілює в дуже швидкий машинний код через оптимізувальний JIT-компілятор (у V8 — TurboFan).

Пам'ять під час виконання поділена на стек викликів (call stack) — фіксованого розміру, зберігає локальні примітиви й адреси повернення для кожного виклику функції — і купу (heap) — велику неструктуровану область, де живуть об'єкти, масиви, замикання. Коли об'єкт у купі більше не досяжний із жодної активної змінної, збирач сміття (garbage collector) рано чи пізно звільняє цю пам'ять — типова базова стратегія: позначити всі досяжні від "коренів" (глобальні змінні, стек) об'єкти, а решту прибрати (mark-and-sweep).

Модель конкурентності: один потік, Web Workers

Модель виконання JS у браузері — один потік на подію: код виконується один шматок за раз без переривань посеред виконання, що усуває цілий клас проблем із гонками даних (race conditions) над спільною пам'яттю, типових для багатопотокових мов. Ціна цього — будь-яка важка синхронна операція (важкі обчислення, парсинг великого JSON, складна обробка зображення) блокує весь UI-потік: сторінка "замерзає", доки обчислення не завершиться.

Web Worker — спосіб винести саме таку важку, суто обчислювальну роботу в окремий потік ОС, який виконується паралельно й не має прямого доступу до DOM; спілкування з головним потоком іде через повідомлення (postMessage). Реальний привід застосувати воркер — коли обчислення дійсно триває довше за один кадр рендерингу (~16 мс) і немає способу розбити його на дрібніші шматки в основному потоці.

мінімальний приклад запуску воркера
// main.js
const worker = new Worker('heavy-calc.js');
worker.postMessage({ n: 45 });
worker.onmessage = (e) => console.log('Результат:', e.data);

// heavy-calc.js
self.onmessage = (e) => {
  const result = fib(e.data.n); // важке обчислення, не блокує UI-потік
  self.postMessage(result);
};

Set, Map, WeakMap, WeakSet

Чотири вбудовані колекції, кожна — під конкретний патерн доступу до даних, а не просто "альтернатива масиву/об'єкту".

Set — унікальні значення
const ids = new Set([1, 2, 2, 3]);
console.log([...ids]);      // [1, 2, 3] — дублікати відкинуто автоматично
console.log(ids.has(2));    // true — перевірка належності швидша й читабельніша за indexOf

Set зберігає лише унікальні значення (порядок вставки — той самий, що порядок ітерації), а .has() — природний, ідіоматичний спосіб перевірити належність замість array.includes().

Map — ключі БУДЬ-ЯКОГО типу, не лише рядки
const cache = new Map();
const requestObj = { id: 42 };

cache.set(requestObj, 'кешований результат');   // ключ — сам об'єкт, не його рядкове представлення
console.log(cache.size);                        // 1 — на відміну від об'єкта, у Map є .size
console.log(cache.get(requestObj));             // 'кешований результат'

Ключ у звичайному об'єкті завжди приводиться до рядка (obj[someObject] насправді стає obj["[object Object]"]) — у Map ключем може бути будь-яке значення, включно з об'єктами, функціями чи іншими Map/Set, без цього приведення. Плюс вбудований .size і гарантований порядок ітерації за вставкою.

WeakMap / WeakSet — метадані без витоку пам'яті
const metadata = new WeakMap();

function attachMeta(domNode, info) {
  metadata.set(domNode, info);   // прив'язали дані до вузла, не змінюючи сам вузол
}
// якщо domNode пізніше видалять з DOM і на нього більше немає посилань —
// збирач сміття звільнить і сам вузол, і цей запис у WeakMap автоматично

WeakMap/WeakSet тримають ключі (або значення в WeakSet) лише "слабко" — це не заважає збирачу сміття звільнити пам'ять, якщо на об'єкт-ключ більше ніде немає посилань. Саме тому в них немає .size, .keys() чи можливості ітерації — вміст може зникнути в будь-який момент під час роботи GC, тож операція "показати всі записи" структурно неможлива й не пропонується взагалі.

Сучасні оператори JS

Компактний синтаксис, який варто впізнавати миттєво — кожен вирішує конкретну, часто повторювану незручність.

?. — optional chaining
const city = user?.address?.city;
// якщо user або user.address — null/undefined, весь вираз одразу дає undefined,
// замість того щоб кинути TypeError на спробі прочитати .city з undefined
?? — nullish coalescing (НЕ те саме, що ||)
console.log(0 ?? 'значення за замовчуванням');   // 0 — 0 не null і не undefined
console.log(0 || 'значення за замовчуванням');   // 'значення за замовчуванням' — 0 це falsy

?? підставляє запасне значення лише коли ліва частина — null або undefined. || підставляє його при будь-якому falsy-значенні (0, '', false) — класична пастка, коли легітимний 0 чи порожній рядок несподівано замінюються значенням за замовчуванням.

||=, &&=, ??= — логічне присвоєння
function connect(options = {}) {
  options.timeout ??= 5000;   // виставити дефолт, лише якщо timeout ще не задано
  // options.timeout ??= 5000  еквівалентно:
  // options.timeout = options.timeout ?? 5000;
  return options;
}
console.log(connect({ timeout: 0 }));   // { timeout: 0 } — легітимний 0 НЕ перезаписано

Саме тут ??= критично відрізняється від ||=: якби виставляли дефолт через options.timeout ||= 5000, легітимний виклик з timeout: 0 ("не чекати взагалі") був би помилково замінений на 5000.

?: — тернарний оператор
const label = count > 0 ? `${count} нових` : 'немає нових';

Компактний вираз-версія if/else — використовується там, де потрібне саме значення, а не блок інструкцій.

Array.prototype.at() — індекс з кінця
const arr = [10, 20, 30];
console.log(arr.at(-1));           // 30 — останній елемент
console.log(arr[arr.length - 1]);  // те саме, але довше й легше помилитись в індексі

structuredClone(obj) для глибокого клонування вже розібраний детально в розділі 5 цього туторіалу — тут лише нагадування, що це теж частина сучасного "стандартного" інструментарію поруч із цими операторами.

for...in vs for...of

for...in проходить по ключах (enumerable-властивостях) об'єкта — працює на звичайних об'єктах, але на масиві віддає індекси як рядки, і додатково включає успадковані enumerable-властивості з ланцюжка прототипів, якщо такі є. for...of проходить по значеннях будь-чого, що реалізує протокол ітератора (масиви, рядки, Map, Set, NodeList) — але НЕ звичайні об'єкти, які за замовчуванням не ітеровані.

той самий масив, різний результат
const colors = ['red', 'green', 'blue'];

for (const key in colors) console.log(key);     // '0', '1', '2' — індекси-рядки
for (const value of colors) console.log(value); // 'red', 'green', 'blue' — самі значення
⚠️
Якщо потрібні саме елементи масиву — майже завжди правильний вибір for...of. for...in на масиві — типова помилка новачка: технічно працює, але віддає індекси-рядки, а не значення, і теоретично може підхопити зайві успадковані властивості.
🟣

Symbol для унікальних і "прихованих" ключів об'єкта

Symbol() створює гарантовано унікальне значення — навіть два виклики з однаковим описом ніколи не рівні одне одному. Використання символу як ключа властивості об'єкта означає, що цей ключ ніколи не зіткнеться з жодним рядковим ключем — навіть тим, що якийсь інший код додасть пізніше.

символ як "прихований" ключ
const HIDDEN = Symbol('внутрішні метадані');

const record = {
  visible: 'звичайне поле',
  [HIDDEN]: 'не для зовнішнього коду',
};

console.log(Object.keys(record));        // ['visible'] — символьний ключ не потрапляє сюди
console.log(JSON.stringify(record));     // {"visible":"звичайне поле"} — теж пропущено
console.log(record[HIDDEN]);             // 'не для зовнішнього коду' — доступно, якщо маєш сам символ

Символьні ключі не з'являються в Object.keys(), for...in чи JSON.stringify() — це і робить їх зручними для "прихованих" внутрішніх позначок на об'єкті. Той самий механізм лежить в основі "відомих символів" (well-known symbols) на кшталт Symbol.iterator (розділ 7 цього туторіалу) — вони дозволяють об'єкту "підписатись" на вбудований протокол мови (наприклад, стати ітерованим), не ризикуючи випадково зіткнутися з реальною властивістю, що випадково називається iterator.
