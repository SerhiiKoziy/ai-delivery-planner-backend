Рівень 1 · Базові патерни мови

Module — інкапсуляція

Проблема: усе, що лежить у глобальній області, може змінити будь-який код, і незрозуміло, хто саме це зробив. Рішення: приховати стан усередині модуля й віддати назовні лише функції, через які з ним можна працювати.

У сучасному JS кожен ES-модуль уже є «Module-патерном»: усе, що не export, недоступне ззовні. Раніше те саме робили через IIFE і замикання, а в класах для цього є приватні поля #field.

cart.js
// items не експортується → ніхто ззовні не може його зіпсувати
const items = new Map();

export function add(id, qty = 1) {
  items.set(id, (items.get(id) ?? 0) + qty);
}

export function total(prices) {
  let sum = 0;
  for (const [id, qty] of items) sum += prices[id] * qty;
  return sum;
}

Коли: завжди, це базова одиниця організації коду. Пастка: стан на рівні модуля живе, поки живе застосунок. Про наслідки цього — у темі 3 (Singleton).

🟡

Factory — функція, що створює об'єкти

Проблема: код, який створює об'єкт, не повинен знати всіх деталей його побудови і того, яку саме реалізацію обрати. Рішення: звичайна функція, яка приймає налаштування й повертає готовий об'єкт.

logger.js — factory function
export function createLogger({ level = 'info', prefix = '' } = {}) {
  const order = ['debug', 'info', 'warn', 'error'];
  const enabled = l => order.indexOf(l) >= order.indexOf(level);
  const make = l => (...args) => enabled(l) && console[l](prefix, ...args);

  return { debug: make('debug'), info: make('info'), warn: make('warn'), error: make('error') };
}

const log = createLogger({ level: 'warn', prefix: '[api]' });
log.info('не виведеться');   // нижче за поріг warn
log.error('виведеться');

Factory vs class: фабрика не потребує new, не має проблем із втраченим this (див. туторіал 2), а приватність дає замикання. Ціна — кожен екземпляр отримує власні копії функцій, а не спільні з прототипу. Для тисяч об'єктів клас економніший, для сервісів і конфігурованих утиліт зручніша фабрика. Коротші приклади Factory, Builder і Prototype є в туторіалі 4.

🔴

Singleton — один екземпляр на весь застосунок

Проблема: деякі речі мають існувати в одному екземплярі: API-клієнт, WebSocket-з'єднання, конфіг. Рішення в JS: окремий клас із getInstance() зазвичай не потрібен. ES-модуль виконується один раз і кешується, тому експортований об'єкт уже є singleton.

api-client.js
class ApiClient {
  constructor(baseUrl) { this.baseUrl = baseUrl; }
  get(path) { return fetch(this.baseUrl + path).then(r => r.json()); }
}

// усі import { api } отримують той самий об'єкт
export const api = new ApiClient(import.meta.env.VITE_API_URL);
⚠️
Дві реальні пастки. (1) Тести: стан singleton переходить між тестами, і вони починають залежати від порядку запуску. (2) SSR (Next.js): на сервері модуль один на всі запити всіх користувачів. Якщо покласти в модульну змінну «поточного користувача», один клієнт побачить дані іншого. На сервері стан на запит створюють для кожного запиту окремо, а не в модулі.

Decorator — додати поведінку, не змінюючи функцію

Проблема: повтор запиту, кешування, логування потрібні багатьом функціям, і копіювати цю логіку в кожну погано. Рішення: функція вищого порядку, яка приймає функцію й повертає нову з тим самим інтерфейсом, але з додатковою поведінкою.

decorators.js
export function withRetry(fn, { retries = 3, delay = 300 } = {}) {
  return async function (...args) {
    for (let attempt = 0; ; attempt++) {
      try {
        return await fn.apply(this, args);
      } catch (err) {
        if (attempt >= retries) throw err;
        await new Promise(r => setTimeout(r, delay * 2 ** attempt)); // 300, 600, 1200 мс
      }
    }
  };
}

export function memoize(fn) {
  const cache = new Map();
  return arg => {
    if (!cache.has(arg)) cache.set(arg, fn(arg));
    return cache.get(arg);
  };
}

const fetchUser = id => fetch(`/api/users/${id}`).then(r => r.json());
// порядок має значення: кешуємо вже «надійну» версію
export const getUser = memoize(withRetry(fetchUser));

Порядок обгорток важливий. Якщо зробити навпаки, withRetry(memoize(fetchUser)), memoize закешує перший відхилений Promise, і всі повторні спроби отримають ту саму помилку з кешу. Це гарне уточнювальне питання на співбесіді.

Той самий патерн зустрічається під іншими назвами: HOC у React (withAuth(Component)), синтаксис @decorator у TypeScript/NestJS/Angular (TC39 decorators), interceptors в axios.

🟡

Adapter і Facade — підлаштувати й спростити

Adapter перетворює чужий інтерфейс на той, якого очікує ваш код. Найчастіший приклад на фронтенді — DTO з бекенду: snake_case, дати рядками, вкладені поля. Адаптер робить це перетворення один раз на межі, і компоненти ніколи не бачать сирого формату API.

route.adapter.js
export function toRoute(dto) {
  return {
    id: dto.route_id,
    stops: dto.stops.map(s => ({ lat: s.latitude, lng: s.longitude })),
    createdAt: new Date(dto.created_at),
  };
}

Facade ховає складну підсистему за простим входом. Замість того щоб у кожному компоненті писати fetch + токен + JSON + обробку помилок, є один об'єкт http:

http.js — facade над fetch
export const http = {
  async request(path, { method = 'GET', body } = {}) {
    const res = await fetch(BASE_URL + path, {
      method,
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${getToken()}` },
      body: body && JSON.stringify(body),
    });
    if (!res.ok) throw new HttpError(res.status, await res.text());
    return res.status === 204 ? null : res.json();
  },
  get: path => http.request(path),
  post: (path, body) => http.request(path, { method: 'POST', body }),
};

Чотири «обгорткові» патерни легко сплутати. Різниця — у тому, що відбувається з інтерфейсом:

ПатернІнтерфейсНавіщо
AdapterЗмінює на інший, очікуванийСумісність: чужий формат → свій
FacadeНовий, простіший, над кількома частинамиСховати складність підсистеми
DecoratorТой самийДодати поведінку (retry, кеш, лог)
ProxyТой самийКонтролювати доступ (валідація, lazy, реактивність)

Proxy — перехопити доступ до об'єкта

Проблема: потрібно реагувати на кожне читання чи запис властивості: валідувати, логувати, відстежувати зміни. Рішення: вбудований Proxy ставить «пастки» (get, set, has, deleteProperty…) перед справжнім об'єктом.

validated.js
function validated(target, rules) {
  return new Proxy(target, {
    set(obj, key, value) {
      if (key in rules && !rules[key](value)) {
        throw new TypeError(`Invalid ${String(key)}: ${value}`);
      }
      obj[key] = value;
      return true; // false у strict mode кине TypeError
    },
  });
}

const settings = validated({}, { volume: v => v >= 0 && v <= 100 });
settings.volume = 50;  // ok
settings.volume = 150; // TypeError: Invalid volume: 150

Де працює під капотом: реактивність Vue 3 і MobX (перехоплюють get, щоб знати, хто що читає, і set, щоб перерендерити), Immer (пише «мутації» в чернетку й будує з них новий імутабельний об'єкт). Ціна: кожен доступ проходить через пастку, тож це повільніше, а proxy !== target, що ламає порівняння за посиланням.

Observer і Pub/Sub — підписка на події

Проблема: коли щось змінилось, про це мають дізнатися кілька інших частин, а джерело не повинно знати їх поіменно. Рішення: підписники реєструються, джерело сповіщає всіх зареєстрованих.

emitter.js
export class Emitter {
  #handlers = new Map();

  on(event, fn) {
    if (!this.#handlers.has(event)) this.#handlers.set(event, new Set());
    this.#handlers.get(event).add(fn);
    return () => this.#handlers.get(event).delete(fn); // функція відписки
  }

  emit(event, payload) {
    this.#handlers.get(event)?.forEach(fn => fn(payload));
  }
}

// у React: відписка обов'язково в cleanup, інакше витік пам'яті
useEffect(() => bus.on('order:paid', refresh), []);

Strategy — замінити switch набором взаємозамінних функцій

Проблема: великий if/else чи switch, до якого з кожною новою вимогою дописують ще одну гілку. Рішення: кожен варіант поведінки — окрема функція з однаковим інтерфейсом, а вибір — за ключем.

pricing.js
const shipping = {
  standard: order => 0,
  express:  order => 15,
  free:     order => (order.subtotal >= 100 ? 0 : 7),
};

export function total(order) {
  const strategy = shipping[order.shipping];
  if (!strategy) throw new Error(`Unknown shipping: ${order.shipping}`);
  return order.subtotal + strategy(order);
}

// новий спосіб доставки = новий рядок у об'єкті, total() не змінюється
shipping.pickup = () => 0;

Це і є принцип Open/Closed на практиці: код відкритий для розширення й закритий для змін. Strategy ви вже використовуєте щодня: компаратор у arr.sort((a, b) => …), стратегії Passport.js, резолвери валідації у формах, різні алгоритми оптимізації маршруту за одним інтерфейсом.

Command — дія як об'єкт (undo/redo)

Проблема: дію потрібно не лише виконати, а й скасувати, повторити, поставити в чергу чи залогувати. Рішення: кожна дія — об'єкт із методами do і undo, а історія зберігає ці об'єкти у двох стеках.

history.js
export function createHistory() {
  const undoStack = [];
  const redoStack = [];
  return {
    run(cmd)  { cmd.do(); undoStack.push(cmd); redoStack.length = 0; }, // нова дія стирає redo
    undo()    { const c = undoStack.pop(); if (c) { c.undo(); redoStack.push(c); } },
    redo()    { const c = redoStack.pop(); if (c) { c.do();   undoStack.push(c); } },
  };
}

const moveStop = (route, from, to) => ({
  do:   () => route.move(from, to),
  undo: () => route.move(to, from),
});

history.run(moveStop(route, 2, 5));
🟣

Iterator — однаковий обхід будь-якого джерела

Проблема: споживачу даних байдуже, звідки вони: масив, дерево чи API з пагінацією. Він хоче просто for…of. Рішення: протокол ітератора, а найзручніше — генератор. Async-генератор ховає пагінацію повністю:

paginate.js
async function* paginate(url) {
  while (url) {
    const page = await fetch(url).then(r => r.json());
    yield* page.items;
    url = page.next; // null на останній сторінці → цикл завершиться
  }
}

for await (const order of paginate('/api/orders?page=1')) {
  if (order.total > 1000) { console.log(order.id); break; } // break → решту сторінок не вантажимо
}

Ключова властивість — лінивість: наступну сторінку завантажено лише тоді, коли споживач до неї дійшов. Як генератори працюють усередині, розібрано в туторіалі 1.

Middleware / Chain of Responsibility — конвеєр обробників

Проблема: кожен запит має пройти логування, автентифікацію, парсинг, обробку помилок, і ці кроки треба комбінувати й переставляти. Рішення: ланцюжок функцій (ctx, next): кожна робить свою частину й викликає next(), щоб передати керування далі.

compose.js — те, що всередині Koa / Redux middleware
function compose(middlewares) {
  return ctx => {
    const dispatch = i => {
      const fn = middlewares[i];
      return fn ? Promise.resolve(fn(ctx, () => dispatch(i + 1))) : Promise.resolve();
    };
    return dispatch(0);
  };
}

const logger = async (ctx, next) => {
  const start = Date.now();
  await next();                                  // усе нижче виконається на «зворотному шляху»
  console.log(ctx.url, ctx.status, Date.now() - start, 'ms');
};
const auth = async (ctx, next) => {
  if (!ctx.user) { ctx.status = 401; return; }   // не викликаємо next → ланцюг зупинено
  await next();
};
const handler = async ctx => { ctx.status = 200; ctx.body = 'ok'; };

compose([logger, auth, handler])({ url: '/me', user: null }); // лог: /me 401 0 ms

State Machine — лише дозволені стани й переходи

Проблема: «суп із булевих прапорців»: isLoading, isError, isSuccess. Чотири прапорці дають 16 комбінацій, а осмислених із них лише кілька. Звідси баги на кшталт одночасних спінера й повідомлення про помилку. Рішення: один рядок-стан і таблиця дозволених переходів.

fetch-machine.js
const machine = {
  idle:    { FETCH: 'loading' },
  loading: { RESOLVE: 'success', REJECT: 'error' },
  success: { FETCH: 'loading' },
  error:   { RETRY: 'loading' },
};

export const transition = (state, event) => machine[state][event] ?? state; // невідомий перехід ігнорується

// у React це звичайний useReducer
const [status, send] = useReducer(transition, 'idle');
send('FETCH');

Патерни компонентів: hooks, compound, render props, HOC

Усі вони відповідають на одне питання: як перевикористати логіку чи структуру між компонентами. Історично їх змінювали один за одним, і сьогодні більшість задач закривають кастомні хуки.

ПатернЩо перевикористовуєКоли сьогодні

Compound componentsСтруктуру з неявним спільним станом (Tabs, Select, Accordion)Гнучкі UI-кіти: Radix, Headless UI, shadcn

HOC withX(Comp)Обгортку навколо компонента (Decorator із теми 4)Легасі та крос-різальні речі (withAuth); створює «пекло обгорток»

Compound components — найчастіше питання з цієї групи. Батько тримає стан у контексті, а дочірні частини читають його самі, тож користувач компонента складає їх як HTML-теги:

Tabs.jsx
const TabsCtx = createContext(null);

export function Tabs({ defaultValue, children }) {
  const [value, setValue] = useState(defaultValue);
  return <TabsCtx value={{ value, setValue }}>{children}</TabsCtx>; // React 19: контекст як провайдер
}

Tabs.Tab = function Tab({ id, children }) {
  const { value, setValue } = useContext(TabsCtx);
  return <button role="tab" aria-selected={value === id} onClick={() => setValue(id)}>{children}</button>;
};

Tabs.Panel = function Panel({ id, children }) {
  const { value } = useContext(TabsCtx);
  return value === id ? <div role="tabpanel">{children}</div> : null;
};

// використання — жодних пропсів activeTab/onChange між частинами
<Tabs defaultValue="map">
  <Tabs.Tab id="map">Карта</Tabs.Tab>
  <Tabs.Tab id="list">Список</Tabs.Tab>
  <Tabs.Panel id="map"><RouteMap /></Tabs.Panel>
  <Tabs.Panel id="list"><StopList /></Tabs.Panel>
</Tabs>

Dependency Injection — залежності передаються ззовні

Проблема: сервіс сам робить import { http } і Date.now(), тому його неможливо протестувати без моків модулів і неможливо підмінити реалізацію. Рішення: сервіс отримує залежності параметрами. Хто їх створює, вирішує «збирач» на верхньому рівні (composition root).

route-service.js
export function createRouteService({ http, cache, clock = Date }) {
  return {
    async list() {
      const hit = cache.get('routes');
      if (hit && clock.now() - hit.at < 60_000) return hit.data;
      const data = await http.get('/routes');
      cache.set('routes', { data, at: clock.now() });
      return data;
    },
  };
}

// прод: збираємо один раз
export const routeService = createRouteService({ http, cache: new Map() });

// тест: жодного jest.mock — просто передаємо фейки
const svc = createRouteService({
  http: { get: async () => [{ id: 1 }] },
  cache: new Map(),
  clock: { now: () => 0 },
});

У React роль DI-контейнера часто грає Context: провайдер на верхньому рівні вирішує, яку реалізацію (справжню чи фейкову для Storybook і тестів) отримають компоненти. Angular і NestJS мають повноцінні DI-контейнери з декораторами. Базовий приклад DI також є в туторіалі 4.

API-шар: Repository + Service замість fetch у компонентах

Проблема: URL-и, формат бекенду й обробка помилок розкидані по десятках компонентів, і зміна одного поля в API тягне правки по всьому проєкту. Рішення: шари, кожен з однією відповідальністю:

ШарВідповідальністьПриклад
КомпонентЛише показати дані й зібрати дії користувача<RouteList />
Хук / queryКеш, стан завантаження, інвалідаціяuseRoutes() на TanStack Query
RepositoryЄдине місце, що знає URL-и й формат DTOrouteRepo.list()
AdapterDTO → доменний об'єкт і назадtoRoute(dto)
HTTP facadeТокен, заголовки, помилки, retryhttp.get()
entities/route/api.js
export const routeRepo = {
  list:   ()    => http.get('/routes').then(list => list.map(toRoute)),
  byId:   id    => http.get(`/routes/${id}`).then(toRoute),
  create: draft => http.post('/routes', toRouteDto(draft)).then(toRoute),
};

export const useRoutes = () => useQuery({ queryKey: ['routes'], queryFn: routeRepo.list });

Бонус: коли бекенд перейменує route_id, правка буде в одному адаптері. Коли потрібні моки для Storybook, підміняється один репозиторій (або весь API через MSW).

Flux / односпрямований потік даних, MVC і MVVM

Проблема: у двосторонньому зв'язуванні будь-яка частина може змінити будь-яку іншу, і в великому застосунку неможливо відповісти на питання «чому змінився цей стан?». Рішення Flux: дані течуть лише в один бік, а змінити стан можна тільки через дію (action).

ПатернЯк тече потікДе зустрічається

MVVMViewModel із двостороннім зв'язуванням: View ⇄ ViewModelAngular ([(ngModel)]), Vue (v-model), Knockout
Flux / ReduxОдноспрямовано: View → Action → Reducer → Store → ViewReact + Redux, Zustand, useReducer

Шарова архітектура фронтенду і Feature-Sliced Design

Проблема: структура «за типом файлу» (components/, hooks/, utils/) на 50+ фічах перетворюється на смітник, де все імпортує все. Рішення: організувати код за бізнес-сутностями й фічами, з одним жорстким правилом: шар може імпортувати лише шари, нижчі за нього.

  entities/       route/  vehicle/  depot/
  shared/         api/http.js  ui/Button.jsx  lib/format.js

Micro-frontends — застосунок із незалежних частин

Проблема: над одним фронтендом працюють кілька команд, і вони блокують одна одну спільним релізом, спільною версією React і довгим CI. Рішення: розрізати застосунок на частини, які окремо збираються й деплояться, а зводить їх разом shell (host).

СпосібЯкКомпроміс
Module FederationHost під час роботи завантажує remoteEntry.js іншої збіркиСпільні залежності, але потрібна узгодженість версій
Multi-zones (Next.js)Різні застосунки на різних шляхах одного доменуПросто, але перехід між зонами — повне перезавантаження
iframeПовна ізоляціяНайгірший UX, складна комунікація
⚠️
Це організаційний патерн, а не технічний. Він вирішує проблему «багато команд на одному коді» ціною складності: кілька версій бібліотек, узгоджений UI-кіт, важчий дебаг. Для однієї команди майже завжди краще добре структурований моноліт (тема 17). Детальніше — у туторіалі 10.

Що перевіряють насправді: не вміння назвати патерн, а вміння почати з проблеми. Сильна відповідь звучить так: «у нас був switch на 12 гілок для розрахунку доставки, кожна нова вимога ламала старі — ми винесли гілки в Strategy, і новий тип доставки став одним рядком». Друга часта перевірка — чи знаєте ви ціну: Singleton ускладнює тести й небезпечний в SSR, Pub/Sub ускладнює трасування, micro-frontends — це складність заради незалежності команд. Типові питання: Decorator vs Proxy vs Adapter; Observer vs Pub/Sub; навіщо DI, якщо є jest.mock; як уникнути неможливих станів.
