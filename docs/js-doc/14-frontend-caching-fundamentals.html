Основи кешування

Кеш — це проміжне сховище результату дорогої операції (мережевого запиту, важкого обчислення), яке дозволяє наступного разу віддати вже готову відповідь замість того, щоб повторювати цю операцію. Ціна — застаріння: кешоване значення рано чи пізно розходиться з реальним джерелом правди. Уся складність теми кешування — це, по суті, керування цим компромісом.

ТермінЩо означає
Cache hitПотрібні дані знайдені в кеші — операція взагалі не виконувалась повторно
Cache missДаних у кеші немає — доводиться виконати реальну операцію (запит/обчислення) і, як правило, покласти результат у кеш на майбутнє
Cache invalidationВидалення або позначення застарілим кеш-запису, коли джерело даних змінилось — одна з двох "по-справжньому важких" задач у computer science, за відомим жартом
TTL (time-to-live)Час, після якого запис автоматично вважається застарілим, без потреби в явній інвалідації
Stale dataДані, які прострочені або відомо застарілі, але свідомо все одно віддаються (наприклад, поки йде фонове оновлення) — стан, відмінний від "видалено з кешу"
Cache evictionПримусове видалення записів для звільнення місця, коли кеш переповнений — наприклад, LRU (Least Recently Used): першим видаляється запис, до якого найдовше не зверталися

Три стратегії кешування

СтратегіяЯк працюєКоли доречна
Cache-firstЗавжди спершу дивимось у кеш; мережа — лише при промахуДані, що рідко змінюються (статичні ассети, конфігурація)
Network-firstЗавжди спершу йдемо в мережу; кеш — резерв на випадок відмови мережіДані, що мають бути максимально свіжими, але потрібен offline-фолбек
Stale-while-revalidateОдразу віддаємо застарілу кешовану відповідь (швидко!), а паралельно у фоні запускаємо реальний запит, щоб оновити кеш на наступний разНайпоширеніший компроміс — саме на цьому принципі побудовані TanStack Query й SWR "з коробки" (детальніше — частина 2)

І два останні розрізнення, які варто тримати окремо один від одного: клієнтський кеш vs серверний кеш — кеш живе на пристрої одного користувача (браузер) проти кешу, який живе на сервері/CDN і обслуговує одразу багатьох користувачів; і memory cache vs persistent cache — живе лише поки живий процес/вкладка (зникає з перезавантаженням сторінки) проти того, що переживає перезавантаження й навіть перезапуск браузера (localStorage, IndexedDB, дисковий кеш браузера).

Browser HTTP Cache

Механіка Cache-Control, різниця no-cache/no-store і весь цикл умовних запитів (ETag/If-None-Match, Last-Modified/If-Modified-Since, 304 Not Modified) уже детально розібрані в туторіалі 11 — тут не повторюємо той матеріал, а закриваємо те, чого там немає.

ДирективаЩо саме означає
max-age=NСкільки секунд браузер (приватний кеш) може використовувати відповідь без звернення до сервера
s-maxage=NТе саме, але для спільних кешів (CDN, проксі) — і ігнорується звичайним браузерним кешем. Якщо задані обидва, браузер підкоряється max-age, а CDN — s-maxage. Це дозволяє, наприклад, тримати щось у CDN довше, ніж у кеші окремого користувача
publicВідповідь можна кешувати будь-де, включно зі спільними/проміжними кешами — навіть якщо запит ішов із Authorization-заголовком (без цього прапорця спільні кеші за замовчуванням обережні з авторизованими відповідями)
privateКешувати можна лише в кеші конкретного браузера користувача — жодні спільні/проміжні кеші (CDN, корпоративний проксі) не мають права зберігати цю відповідь. Обов'язково для будь-чого персоналізованого
must-revalidateЩойно запис став застарілим (minus max-age вийшов) — кеш зобов'язаний перевірити свіжість на сервері перед використанням, навіть якщо клієнт у принципі був би готовий стерпіти трохи застарілі дані при збої мережі

Стан кешованого запису в будь-який момент — або fresh (свіжий: у межах max-age, можна віддавати без запиту взагалі), або stale (застарілий: термін вийшов, потрібна ревалідація — або, якщо ревалідація неможлива/не потрібна за поточними директивами, повне повторне завантаження).

Fetch API: керування кешем із коду

Опція cache в fetch() дає явний контроль над тим, як саме запит взаємодіє з браузерним HTTP-кешем, незалежно від заголовків відповіді сервера:

РежимПоведінка
defaultЗвичайна поведінка браузера: свіжий кеш — використати без запиту; застарілий — ревалідувати; відсутній — запит із нуля
no-storeПовністю ігнорувати кеш в обидва боки: не читати з нього і не писати в нього відповідь
reloadЗавжди йти в мережу, ігноруючи наявний кеш при читанні — але записати свіжу відповідь у кеш після отримання
no-cacheЗавжди ревалідувати з сервером (умовний запит), навіть якщо локальна копія формально ще fresh за max-age
force-cacheВикористати кешовану копію, навіть якщо вона вже застаріла (stale) — піти в мережу лише якщо в кеші взагалі нічого немає
only-if-cachedВзяти лише з кешу, ніколи не звертатись до мережі — якщо в кеші нічого немає, запит одразу провалюється з помилкою (працює тільки для same-origin запитів)
приклад: примусово брати з кешу, навіть застаріле
const response = await fetch('/api/static-config', {
  cache: 'force-cache',
});

CDN caching

Браузерний кеш обслуговує одного користувача на одному пристрої. CDN (Content Delivery Network) — це мережа проміжних серверів, географічно розташованих ближче до користувачів, кожен вузол якої кешує відповідь один раз і віддає її одразу багатьом користувачам поруч — і саме тому директива s-maxage з попереднього розділу існує окремо від max-age: вона керує саме цим спільним, багатокористувацьким шаром кешу.

ПоняттяЩо означає
Cache keyТе, за чим CDN вирішує, чи два запити "однакові" для цілей кешування — типово URL плюс якась підмножина заголовків/query-параметрів. Неправильно підібраний cache key — класичне джерело багів: наприклад, якщо персоналізована відповідь кешується лише за URL без урахування заголовка авторизації, різні користувачі можуть отримати чужий кеш
Purge / інвалідаціяЯвна команда CDN "видали цей запис негайно", не чекаючи природного закінчення TTL — типово викликається після деплою нового контенту
Cache bustingСвідома зміна URL ресурсу (app.js?v=123 або, надійніше, ім'я файлу з хешем вмісту — app.a1b2c3.js), щоб застаріла кешована копія фізично ніколи не могла бути повернена під новим запитом — стандартна техніка для інвалідації статичних ассетів при білді

Реальні приклади такого шару в індустрії — Vercel Edge Network, Cloudflare, AWS CloudFront: досить розуміти їхню роль (спільний, географічно розподілений кеш перед оригінальним сервером), не заглиблюючись у налаштування конкретного постачальника.

Сховища браузера як простір для кешу

Компроміси безпеки localStorage/sessionStorage/cookies вже розібрані в туторіалі 2 — тут дивимось саме на придатність кожного сховища для кешування, включно з двома, яких там немає.

СховищеТипове застосування як кешПерсистентністьРозмір (орієнтовно)API
Пам'ять (змінна/Map)Тимчасовий кеш на час життя вкладки/процесуЗникає при перезавантаженніОбмежено лише RAMСинхронний
sessionStorageДані рівня однієї вкладки/сесіїДо закриття вкладки~5-10 МБСинхронний
localStorageНевеликі персистентні дані (налаштування, токени — з застереженнями з туторіалу 2)Переживає перезапуск браузера~5-10 МБСинхронний
IndexedDBВеликі структуровані/бінарні дані — база даних просто в браузері, часто основа offline-first застосунківПереживає перезапуск браузераСотні МБ і більше (залежить від квоти диска)Асинхронний
Cache Storage APIКешування реальних пар HTTP-запит/відповідь — саме те, чим оперує Service Worker (розділ 6)Переживає перезапуск браузераЗалежить від квоти дискаАсинхронний

Синхронний API localStorage/sessionStorage — сам по собі причина не тримати там багато даних: кожне звернення блокує основний потік, на відміну від асинхронних IndexedDB і Cache Storage.

In-memory кешування: патерни

Механіка Map/WeakMap/Set/WeakSet як структур даних уже пояснена в туторіалі 1 — тут дивимось саме на них як на будівельний матеріал для кеш-патернів.

кеш рівня модуля
const cache = new Map();

async function getOrFetch(key, fetcher) {
  if (cache.has(key)) return cache.get(key);
  const value = await fetcher();
  cache.set(key, value);
  return value;
}

Найпростіший робочий кеш — жодної бібліотеки не потрібно. Але без ліміту розміру чи TTL такий Map буде рости необмежено, поки живий модуль, — практичний ризик витоку пам'яті для будь-яких ключів із необмеженою кардинальністю (наприклад, ID користувача чи пошуковий запит).

мінімальний LRU-кеш на Map
class LRUCache {
  #cache = new Map();
  #capacity;

  constructor(capacity) {
    this.#capacity = capacity;
  }

  get(key) {
    if (!this.#cache.has(key)) return undefined;
    const value = this.#cache.get(key);
    this.#cache.delete(key);
    this.#cache.set(key, value); // перевставити — позначити "нещодавно використаний"
    return value;
  }

  set(key, value) {
    if (this.#cache.has(key)) this.#cache.delete(key);
    else if (this.#cache.size >= this.#capacity) {
      const oldestKey = this.#cache.keys().next().value; // Map зберігає порядок вставки
      this.#cache.delete(oldestKey); // витісняємо найдавніше використаний запис
    }
    this.#cache.set(key, value);
  }
}

Хитрість тут — саме в тому, що Map зберігає порядок вставки: щоб позначити ключ "нещодавно використаним", досить видалити й одразу вставити його знову — він автоматично переміститься в кінець ітераційного порядку, а найдавніший запис завжди опиниться першим у .keys().

WeakMap — кеш, що сам себе прибирає
const computedCache = new WeakMap();

function getExpensiveResult(objectKey) {
  if (computedCache.has(objectKey)) return computedCache.get(objectKey);
  const result = doExpensiveComputation(objectKey);
  computedCache.set(objectKey, result);
  return result;
}
// щойно objectKey більше ніде не використовується — збирач сміття звільнить
// і сам об'єкт, і цей запис у WeakMap, без жодного ручного видалення
🎯
Коли цей кеш потрібно очищати? Залежно від патерну: за TTL (час вийшов — незалежно від того, звертались до запису чи ні), за LRU-витісненням (розмір перевищив ліміт — прибираємо найдавніше використане), за явною подією інвалідації (дані, від яких залежить кеш, змінились — детальніше в частині 3), або — саме для WeakMap — ніколи вручну, за задумом: очищення відбувається автоматично через збирач сміття, тому WeakMap навмисно не має .size чи способу перелічити всі записи (інакше довелось би тримати живими об'єкти, які мали б уже зникнути).

Service Worker / PWA caching

Service Worker — це скрипт, який виконується окремо від сторінки, діючи як програмований мережевий проксі між сторінкою та мережею: він може перехопити кожен запит, вирішити, звідки віддати відповідь, і продовжує існувати навіть після закриття вкладки. Саме на ньому будується offline-first поведінка PWA.

Cache Storage API — сховище, яким оперує Service Worker: caches.open(name) (відкрити/створити іменований кеш), cache.match(request) (знайти збережену відповідь на запит), cache.put(request, response) (зберегти пару запит/відповідь), cache.delete(request) (видалити запис).

service-worker.js — cache-first для статичних ассетів
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.open('static-v2').then(async (cache) => {
      const cached = await cache.match(event.request);
      if (cached) return cached; // cache-first: є в кеші — віддаємо одразу

      const response = await fetch(event.request);
      cache.put(event.request, response.clone()); // клон — тіло можна прочитати лише раз
      return response;
    })
  );
});

Ті самі три стратегії з розділу 1 застосовуються тут буквально: cache-first для статичних ассетів (JS/CSS/шрифти — рідко змінюються, максимальна швидкість); network-first для API-даних, що часто змінюються (з кешем як offline-фолбеком); stale-while-revalidate як типовий середній варіант.

Коротко варто знати ще два терміни: background sync (відкласти дію — наприклад, відправку форми — до відновлення з'єднання, а не просто провалити її офлайн) і версіонування кешу (називати кеш-сховища з версією, наприклад static-v2, і видаляти кеші зі старими іменами на подію activate — стандартний спосіб безпечно розкотити зміну структури кешу, не змішавши старі й нові ассети).
