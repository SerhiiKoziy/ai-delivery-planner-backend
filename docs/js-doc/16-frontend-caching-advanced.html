Cache invalidation

Є стара програмістська приказка: у computer science є лише дві по-справжньому важкі речі — інвалідація кешу та називання змінних (ну і помилки на одиницю). Це не жарт заради жарту: кеш і джерело правди (сервер, база даних) можуть змінюватись незалежно одне від одного, і не існує єдиного універсально правильного способу дізнатись, що саме зараз кеш уже бреше. Кожна стратегія нижче — це різний компроміс між простотою, точністю й вартістю зайвих запитів.

СтратегіяМеханізмКомпроміс
TTL (time-to-live) Запис у кеші автоматично "протухає" через N секунд/хвилин, незалежно від того, чи дані реально змінились Найпростіше в реалізації; або віддаєте застарілі дані впродовж вікна TTL, або перезапитуєте частіше, ніж треба, якщо TTL занизити "про всяк випадок"
Ручна (явна) інвалідація Код явно каже "цей запис більше не валідний" одразу після дії, що могла його змінити — напр. invalidateQueries(...) одразу після успішної мутації Точна й миттєва, але вимагає, щоб розробник згадав кожне місце, де ці дані могли застаріти — легко забути одне
Тег-базована інвалідація Кожен запис при записі позначається семантичним тегом (напр. Product:123), а інвалідація йде по тегу, а не по точному ключу — один запис може одразу зробити невалідними багато пов'язаних читань Не потребує хардкодити кожен query key вручну; ціна — ще одна абстракція (теги), яку треба консистентно розставляти
Версіонування Замість "протухання" старого запису — нова адреса/ідентичність для нових даних (напр. app.js?v=123 чи хеш вмісту у назві файлу) Ідеально для незмінних (immutable) статичних ресурсів — старий кеш просто ніколи не запитується повторно, бо URL уже інший; не підходить для даних, що змінюються "на місці"
Подієва інвалідація Сервер сам активно повідомляє клієнта, що дані змінились (WebSocket, push), замість того щоб клієнт чекав TTL чи опитував (polling) Найсвіжіші дані з мінімальною затримкою, але вимагає постійного з'єднання й інфраструктури для доставки подій

Optimistic Updates

Ідея проста: не чекати підтвердження сервера, щоб оновити UI. Замість "запит → чекаємо → оновлюємо екран" — "оновлюємо екран одразу → надсилаємо запит у фоні → якщо щось пішло не так, відкочуємо назад". Користувачу це відчувається як миттєва реакція інтерфейсу, а не затримка мережевого round-trip.

Дія користувача
→
Оновити UI одразу
→
Запит до сервера
→
✅ Успіх → лишити
Дія користувача
→
Оновити UI одразу
→
Запит до сервера
→
❌ Провал → rollback

Механізм відкату (rollback) на практиці завжди зводиться до одного й того самого: зробити знімок (snapshot) попереднього значення ще ДО того, як застосувати оптимістичну зміну — і якщо мутація провалилась, просто повернути кеш до цього знімка. Це працює однаково, чи ви вручну керуєте станом, чи використовуєте хуки на кшталт React Query onMutate/onError (детальніше в туторіалі 15).

snapshot → optimistic apply → rollback
async function toggleTodoOptimistic(cache, id) {
  const key = 'todo:' + id;
  const previous = cache.get(key);              // 1. знімок ДО зміни
  cache.set(key, { ...previous, done: !previous.done }); // 2. миттєва зміна UI

  try {
    await api.updateTodo(id, { done: !previous.done }); // 3. запит у фоні
    // сервер підтвердив — залишаємо оптимістичний стан як є
  } catch (err) {
    cache.set(key, previous);                    // 4. rollback до знімка
    throw err;
  }
}
⚠️
Дві реальні пастки: по-перше, race condition — що, якщо користувач встигає натиснути дію вдруге ще до того, як прийшла відповідь на першу (детально — розділ 5 нижче). По-друге, синхронізація — відповідь сервера не завжди точно збігається з тим, що ви оптимістично вгадали (напр. сервер міг застосувати додаткову бізнес-логіку) — тоді потрібно звірити й, за потреби, тихо скоригувати UI під реальну відповідь, а не сліпо довіряти вже застосованому здогаду.

Prefetching

Ідея: почати завантажувати дані чи код до того, як вони реально знадобляться — щоб у момент, коли користувач їх таки запросить, відповідь уже лежала готова в кеші, а не йшла в мережу з нуля.

ФормаЯк працює
Route prefetchingNext.js <Link> автоматично підвантажує код і дані сторінки, щойно посилання потрапляє у viewport (або на hover, залежно від версії/налаштувань)
Data prefetchingЯвний виклик на кшталт queryClient.prefetchQuery(...) — прогріти кеш бібліотеки даними, які ви впевнені знадобляться найближчим часом
Hover prefetchЗапустити запит саме в момент, коли курсор заходить на посилання/кнопку — між "навів" і "клікнув" природно є ~100-300 мс, яких часто достатньо, щоб випередити мережу
GraphQL prefetchТа сама ідея для GraphQL-клієнта — напр. client.query(...) в Apollo заздалегідь, щоб прогріти InMemoryCache ще до навігації

Cache consistency

Центральне запитання цього розділу: що станеться, якщо кеш містить застарілі дані? Відповідь залежить від того, яку модель узгодженості ви (свідомо чи ні) обрали.

МодельГарантія
Сильна узгодженість (strong consistency)Кожне читання одразу відображає найсвіжіший запис, всюди й миттєво — дорого й складно забезпечити в розподіленій системі клієнт+сервер+CDN
Кінцева узгодженість (eventual consistency)Читання МОЖУТЬ якийсь час повертати застарілі дані після запису, але система гарантує, що вони врешті-решт зійдуться до правильного значення, якщо нових записів більше не буде

Практично весь фронтенд-кешинг — це кінцева узгодженість за визначенням: будь-який кеш на основі TTL чи stale-while-revalidate не гарантує миттєвої свіжості, лише конвергенцію з часом. Реальне мистецтво — усвідомлено обирати, де сильна узгодженість дійсно критична (баланс банківського рахунку одразу після переказу), а де кінцева цілком прийнятна (лічильник лайків, що оновиться за секунду).

Той самий компроміс — центральна тема CAP-теореми в контексті розподілених баз даних (Python Doc, туторіал 17) — тут та сама логіка застосована до фронтенд-кешу, а не до бази даних.

Прийнявши кінцеву узгодженість як реальність, постає наступне питання: конкурентні запити й синхронізація сервер→клієнт стають чимось, що треба явно продумувати — саме це й розбирає наступний розділ.

Race conditions у кешуванні

Класичний сценарій, який ламає наївний кеш:

  1. Користувач вводить "cat" → летить Запит A (пошук за "cat").
  2. Користувач одразу змінює запит на "dog" → летить Запит B.
  3. Відповідь B (свіжа, "dog") повертається раніше, ніж відповідь A — наприклад, серверний запит для A виявився повільнішим.
  4. Якщо наївно застосовувати "хто відповів останнім — той і правий": застаріла відповідь A перезаписує свіжу відповідь B, і користувач бачить результати пошуку "cat" замість щойно введеного "dog".
❌
Проблема не в тому, який запит стартував раніше — а в тому, який відповів раніше. Порядок відповідей мережі не гарантує порядок запитів.

Реальні рішення, кожне зі своїм механізмом:

AbortController — скасування попереднього запиту
let currentController = null;

async function search(query) {
  if (currentController) currentController.abort(); // скасувати попередній
  currentController = new AbortController();

  const response = await fetch(`/api/search?q=${query}`, {
    signal: currentController.signal,
  });
  return response.json();
}
ПідхідМеханізм
AbortControllerЯвно скасовує попередній запит у момент старту нового — навіть якщо стара відповідь усе ж прийде, вона вже позначена як aborted і ігнорується
ID запитівКожному запиту присвоюється зростаючий ідентифікатор; застосовується лише відповідь, чий ID досі збігається з останнім запущеним запитом — інші тихо ігноруються, навіть без явного скасування
Часові міткиТа сама ідея: порівнюється момент старту запиту, а не момент приходу відповіді — застосовується відповідь найновішого запиту, а не та, що прийшла останньою
Query-бібліотеки роблять це саміReact Query, SWR та Apollo внутрішньо відстежують, чи відповідь досі належить активному query key/змінним, і мовчки відкидають "застарілі" відповіді (детальніше — туторіал 15) — одна з непомітних, але реальних причин обирати зрілу бібліотеку замість fetch + useState вручну
Версіонування кешуКожному запису присвоюється покоління (generation), що зростає з кожним новим запитом; запис зі старішим поколінням, ніж уже в кеші, просто відкидається при спробі запису

Безпека й кешування

Кеш за визначенням віддає ту саму відповідь кільком запитувачам — і саме тому приватні/персоналізовані дані в спільному кеші (CDN, спільний проксі) без додаткової обережності — це майже завжди помилка: наступний користувач цілком реально може отримати дані попереднього.

🎯
Cache poisoning: атакуючий маніпулює запитом так, що шкідлива або неправильна відповідь потрапляє в кеш і віддається іншим, легітимним користувачам — класичний вектор: сервер варіює відповідь за заголовком, якого CDN не враховує в ключі кешування, тож підроблене значення цього заголовка від атакуючого закешовується й повторюється всім наступним відвідувачам.

Навіть без спільного кешу лишається ризик чутливих даних у кеші самого браузера — на спільному/публічному комп'ютері, через розширення браузера чи інший скрипт на сторінці, що потенційно може прочитати закешовані відповіді чи сховище.

ДирективаЩо означає
privateСпільні кеші (CDN тощо) не мають права зберігати цю відповідь — лише браузер самого користувача
no-storeНе кешувати ніде взагалі — навіть у браузері; найсуворіша директива, доречна для дійсно чутливих відповідей (дані рахунку, платіжна інформація)
⚠️
JWT + кешування: відповідь, що залежить від заголовка Authorization, за визначенням персоналізована під конкретного користувача — ніколи не дозволяйте CDN кешувати таку відповідь, якщо тільки цей заголовок явно не включений у ключ кешування (типова конфігурація CDN за замовчуванням цього не робить) — класична й небезпечна помилка конфігурації.

CDN + персоналізований контент — не суперечність, якщо розділити відповідальність: кешувати на edge лише ту частину сторінки, що однакова для всіх (базовий HTML, статичний контент) з довгим TTL, а персоналізовані фрагменти — або довантажувати окремим клієнтським запитом, позначеним private/no-store, або взагалі не кешувати на CDN, довіряючи це виключно браузеру користувача.

Q&A: найпопулярніші питання про кешування для React-розробників

Ці 22 питання зібрані з тем, позначених 🔥 у всіх трьох частинах серії — саме ті, що найчастіше звучать на реальних співбесідах React/Next.js-розробників.

База Пастка Просунуте Системний дизайн
01ПасткаstaleTime vs gcTime у React Query — у чому різниця?

staleTime — як довго дані вважаються "свіжими" й НЕ тригерять автоматичний рефетч (напр. при новому монтуванні компонента чи фокусі вікна). gcTime (раніше cacheTime) — як довго дані взагалі залишаються в пам'яті кешу після того, як жоден компонент на них більше не підписаний, перш ніж їх остаточно приберуть. Дані можуть бути одночасно "несвіжими" (по staleTime) але все ще присутніми в кеші (по gcTime) — саме тому старий екран часто миттєво показує попередні дані, а тоді тихо оновлюється у фоні.

02БазаЧому useMemo — це не кеш даних?

useMemo — це мемоізація результату обчислення всередині одного компонента, прив'язана до масиву залежностей і до життєвого циклу цього конкретного компонента: розмонтували компонент — значення зникло, і воно ніколи не ходить у мережу. Кеш даних (React Query, SWR, Apollo) — це сховище, незалежне від конкретного компонента, з власним TTL/інвалідацією, здатне ділитись однією й тією самою відповіддю сервера між багатьма непов'язаними компонентами й пережити розмонтування будь-якого з них.

03ПросунутеНазвіть чотири рівні кешу Next.js по порядку — що інвалідує кожен?

Request Memoization (живе рівно один рендер сервера, дедуплікує однакові fetch-виклики в межах одного запиту — інвалідується завершенням запиту) → Data Cache (переживає окремі запити й навіть деплої, керується опціями fetch — revalidate/revalidateTag/revalidatePath) → Full Route Cache (кешує згенерований HTML+RSC payload статичних маршрутів на білді — інвалідується новим білдом або ревалідацією Data Cache, від якої він залежить) → Router Cache (клієнтський, у пам'яті браузера, кешує вже відвіданий RSC payload для миттєвої навігації назад — інвалідується оновленням сторінки чи закінченням TTL сесії). Детальний розбір усіх чотирьох — туторіал 15.

04ПасткаApollo: cache-first vs cache-and-network — коли який?

cache-first — якщо в кеші вже є відповідь на цей запит, віддати її й не ходити в мережу взагалі (навіть у фоні). cache-and-network — одразу віддати те, що є в кеші (для миттєвого UI), АЛЕ паралельно все одно піти в мережу за свіжими даними й оновити UI, коли вони прийдуть. Перше економить мережу ціною можливої застарілості; друге завжди свіже, ціною зайвого мережевого запиту навіть коли кеш і так був актуальний.

05ПросунутеЩо реально дає нормалізований кеш порівняно з наївним кешем відповідей?

Наївний кеш зберігає ЦІЛУ відповідь запиту як один непрозорий блоб під ключем цього запиту — та сама сутність (напр. користувач User:1), що прийшла в складі двох різних запитів, зберігається в кеші двічі, незалежно одна від одної. Оновіть її в одному місці — друга копія лишається застарілою. Нормалізований кеш зберігає кожну сутність рівно один раз за її ідентичністю (__typename + id в Apollo), а запити просто тримають посилання на ці сутності — оновлення однієї сутності одразу відображається скрізь, де на неї є посилання, без ручної синхронізації копій.

06БазаКоли ставити Cache-Control: private, no-store?

Для будь-якої відповіді, що містить персоналізовані або чутливі дані конкретного автентифікованого користувача (баланс рахунку, платіжні дані, приватний профіль). private забороняє спільним кешам (CDN, проксі) зберігати відповідь — лише браузер користувача може; no-store йде ще суворіше й забороняє зберігання взагалі будь-де, навіть у браузері. Разом вони — правильний дефолт для всього, що не повинно пережити закриття вкладки чи потрапити до іншого користувача через спільний кеш.

07Системний дизайнОпишіть повний flow optimistic update із відкатом.

1) Користувач ініціює дію. 2) Перед відправкою запиту — зробити знімок поточного стану кешу. 3) Одразу застосувати очікувану зміну до UI/кешу, не чекаючи сервера. 4) Надіслати реальний запит у фоні. 5а) Якщо сервер підтвердив успіх — лишити оптимістичний стан (за потреби звірити з реальною відповіддю сервера й скоригувати розбіжності). 5б) Якщо запит провалився — відновити кеш точно до знімка з кроку 2, показавши користувачу, що дія не вдалась.

08ПросунутеКласичний сценарій "стара відповідь перезаписує нову" — як його уникнути?

Запит A (повільний) стартує першим, запит B (швидкий, з новішими параметрами) стартує другим — але відповідь B приходить раніше відповіді A. Наївне застосування "останньої отриманої відповіді" дає застарілий результат A поверх свіжого B. Рішення: скасовувати попередній запит через AbortController при старті нового, або перевіряти, що відповідь відповідає саме останньому запущеному запиту (за ID чи часовою міткою старту, не приходу) перед тим, як її застосувати. React Query/SWR/Apollo роблять це автоматично внутрішньо.

09БазаprovidesTags vs invalidatesTags у RTK Query?

providesTags оголошується на запиті (query) — які теги описують дані, які він повернув (напр. { type: 'Product', id: 123 }). invalidatesTags оголошується на мутації — які теги вона робить невалідними після успіху. RTK Query автоматично рефетчить будь-який активний запит, чиї теги збіглись із тегами, які щойно інвалідувала мутація — типова реалізація тег-базованої інвалідації з розділу 1.

10ПасткаSWR mutate vs React Query invalidateQueries + setQueryData?

SWR об'єднує обидва сценарії в одну функцію mutate: викликана без аргументів — просто тригерить ревалідацію (аналог invalidateQueries); викликана зі значенням — одразу підміняє кеш цим значенням, опційно без ревалідації (аналог setQueryData). React Query розділяє це на дві явно різні функції: invalidateQueries (позначити застарілим і рефетчити) та setQueryData (напряму записати значення в кеш, часто саме для optimistic-апдейтів, без походу в мережу).

11Системний дизайнКоли cache-first стратегія Service Worker — неправильний вибір?

Для даних, що змінюються часто (напр. відповіді API з живими цінами чи статусами) — cache-first означає, що користувач може довго бачити застарілі дані, доки кеш нарешті не оновиться. Для такого API доречніший network-first (спробувати мережу, відкотитись на кеш лише при відмові мережі) або stale-while-revalidate (віддати кеш миттєво, але одразу оновити його у фоні для наступного разу). Cache-first залишається правильним вибором саме для статичних, рідко змінюваних ресурсів (іконки, шрифти, версійовані бандли).

12Базаmax-age vs s-maxage?

max-age застосовується до будь-якого кешу — і браузера, і спільних (CDN, проксі). s-maxage ("shared max-age") застосовується лише до спільних кешів і, коли присутній, перевизначає для них max-age — дозволяючи, наприклад, тримати відповідь довше на CDN, ніж у браузері конкретного користувача (чи навпаки).

13ПросунутеЧому WeakMap іноді правильніша структура для кешу, ніж Map?

Якщо ключами кешу є самі об'єкти (напр. кешування результату обчислення "для цього конкретного DOM-вузла" чи "для цього конкретного React-компонента"), Map тримає сильне посилання на ключ — об'єкт-ключ ніколи не збереться сміттязбирачем, доки живий сам Map, навіть якщо ніде в застосунку більше немає інших посилань на цей об'єкт — витік пам'яті. WeakMap тримає ключ слабко: щойно зникає остання "звичайна" посилання на об'єкт-ключ, запис автоматично прибирається збирачем сміття разом з ним — ідеально для кешу метаданих "прив'язаних" до об'єкта, що не повинен продовжувати жити лише через те, що є в кеші.

14ПасткаStale-while-revalidate — це один патерн чи три різні речі?

Насправді той самий концепт на трьох різних рівнях, і плутанина виникає саме тому, що назва однакова: (1) як загальна ідея кешування — віддати застарілу копію миттєво, оновити у фоні для наступного разу; (2) як конкретна HTTP-директива Cache-Control: stale-while-revalidate=N — браузер сам реалізує саме цю поведінку на рівні мережевого кешу протягом N секунд після закінчення max-age; (3) як дефолтна поведінка бібліотек React Query/SWR — вони роблять концептуально те саме на рівні кешу даних застосунку, незалежно від того, чи сервер взагалі надсилає HTTP-директиву SWR. Це одна ідея, реалізована на трьох різних шарах стека одночасно.

15БазаЧим browser cache відрізняється від CDN cache?

Browser cache — приватний кеш одного користувача, живе локально в його браузері. CDN cache — спільний кеш на серверах, географічно розподілених ближче до користувачів, що обслуговує багатьох різних користувачів однією закешованою копією. Саме тому персоналізовані дані безпечно кешувати в browser cache ( private), але небезпечно — на CDN без явного розмежування, хто саме отримає закешовану відповідь.

16ПросунутеЩо таке cache busting і навіщо версіонувати статичні файли?

Статичним бандлам зазвичай ставлять дуже довгий max-age (роки) для максимальної швидкості повторних візитів — але тоді оновлення коду ніколи не дійде до користувача, поки старий файл не "протухне" сам. Cache busting вирішує це не протуханням, а зміною ідентичності: ім'я файлу включає хеш вмісту чи номер версії (app.a3f9c1.js) — новий білд отримує нову назву файлу, тож старий закешований файл просто ніколи більше не запитується, а новий запитується як цілком новий ресурс, якого ще немає в кеші.

17Системний дизайнСпроєктуйте кешування сторінки товару: частина контенту спільна, частина — персоналізована.

Розділити відповідальність за шарами: базовий HTML (назва, опис, ціна, фото) — однаковий для всіх, кешується на CDN з довгим s-maxage і тег-базованою інвалідацією при зміні товару. Персоналізовані фрагменти (рекомендації "для вас", статус у кошику, персональна знижка) — або взагалі виключені із закешованого HTML і довантажені окремим клієнтським запитом, позначеним Cache-Control: private, no-store, або вся сторінка позначена private й кешується лише в браузері конкретного користувача, жертвуючи швидкістю CDN заради простоти. Вибір між цими двома підходами — компроміс складності реалізації проти швидкості першого відображення.

18БазаЩо таке cache hit і cache miss?

Cache hit — запитані дані знайдено в кеші, мережевий похід не потрібен. Cache miss — даних у кеші немає (або вони інвалідовані), доводиться йти в мережу/до джерела правди й, зазвичай, покласти результат у кеш для наступного разу. Відсоток hit vs miss (hit rate) — основна метрика, якою оцінюють, наскільки взагалі ефективний конкретний шар кешування.

19ПросунутеЧому Zustand — не заміна React Query/SWR, навіть якщо технічно можна зберігати серверні дані в ньому?

Zustand — інструмент керування клієнтським станом: він не знає нічого про мережу, не має вбудованого поняття "застарілості" даних, не дедуплікує паралельні запити за тим самим ключем, не інвалідує сам себе за тегами чи TTL. Усе це довелось би реалізовувати вручну поверх нього. React Query/SWR спроєктовані спеціально під "server state" — дані, власником яких є сервер, а клієнт лише тримає тимчасову, потенційно застарілу копію — з усією потрібною для цього інфраструктурою з коробки. Технічно можливо — не означає доречно.

20ПасткаЩо станеться з незавершеним запитом при синхронному тяжкому обчисленні в Service Worker?

Service Worker виконується в окремому потоці від основного UI-потоку сторінки — важке синхронне обчислення всередині нього не заморожує сам інтерфейс сторінки напряму. Але воно все одно затримує обробку самого fetch-івенту в Service Worker, а отже й відповідь на перехоплений запит — з погляду сторінки це виглядає як довга мережева затримка, а не як "зависання UI". Це важлива відмінність від тяжкого обчислення прямо в головному потоці, яке дійсно заморожує рендер.

21БазаЧим IndexedDB відрізняється від localStorage для кешування?

localStorage — синхронне (блокує головний потік при читанні/записі), зберігає лише рядки, дуже обмежений об'єм (~5-10 МБ), простий ключ-значення API. IndexedDB — асинхронне, зберігає структуровані об'єкти (не лише рядки), набагато більший ліміт об'єму, підтримує індекси й транзакційні запити. Для серйозного офлайн-кешу структурованих даних (список товарів, повідомлення) — IndexedDB; для дрібних прапорців/налаштувань — localStorage цілком достатньо.

22Системний дизайнЯк забезpечити, щоб dependent (залежні) запити не показали проміжний неконсистентний стан?

Якщо запит B залежить від результату запиту A (напр. спершу отримати userId, потім за ним — профіль користувача), і B тимчасово рендериться зі старим/порожнім значенням, поки A ще не завершився — типове рішення: явно тримати B у стані enabled: false (React Query) чи еквіваленті, доки A не має валідного результату, замість того щоб дозволяти B стартувати з завідомо неповними даними й потім "мерехтіти" при отриманні реального значення від A.
