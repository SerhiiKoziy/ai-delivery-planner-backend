Структура HTTP-запиту

Кожен HTTP-запит складається з трьох частин: рядка запиту (request line) — метод, шлях і версія протоколу; заголовків — метадані запиту у форматі "ключ: значення"; і опційного тіла — фактичні дані, які надсилаються разом із запитом.

структура запиту
POST /api/v1/routes/optimize HTTP/1.1      ← метод + шлях + версія протоколу
Host: example.com                          ← заголовки (метадані запиту)
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{"delivery_ids": [...], "vehicle_ids": [...]}   ← тіло (не обов'язкове для GET)

Дані потрапляють у запит трьома різними шляхами, і те, який шлях обрати — не випадковість, а конвенція:

СпосібПрикладКоли ідіоматично
Query-параметри/search?q=react&page=2Фільтрація, пагінація, сортування на GET — те, що логічно "не обов'язкове" й людині зручно бачити прямо в URL
Path-параметри/users/42/ordersІдентифікація конкретного ресурсу — 42 тут не фільтр, а сама адреса ресурсу
Тіло запиту{"email": "...", "name": "..."}Корисне навантаження POST/PUT/PATCH — структуровані дані, які не мають природного місця в URL (і не повинні там опинятись — URL логуються, кешуються, зберігаються в історії браузера)
🟡

Структура HTTP-відповіді

Відповідь дзеркальна за формою: рядок статусу (версія протоколу + код + текстова фраза), заголовки відповіді, і опційне тіло.

структура відповіді
HTTP/1.1 200 OK                            ← версія протоколу + статус-код + фраза
Content-Type: application/json             ← заголовки відповіді
Cache-Control: no-store

{"routes": [...], "unassigned_deliveries": []}  ← тіло відповіді

Статус-коди групуються в п'ять класів за першою цифрою — і в кожному класі є кілька кодів, які варто знати саме за номером, а не лише за класом:

КодКласЩо саме відрізняє
200 OK2xx — успіхСтандартний успіх із тілом відповіді
201 Created2xx — успіхУспішний POST, що створив новий ресурс — часто разом із заголовком Location на цей ресурс
204 No Content2xx — успіхУспіх без тіла відповіді — типово для DELETE
301 Moved Permanently3xx — редиректПостійний редирект — браузери й пошукові боти кешують його надовго, наступного разу підуть напряму за новою адресою
302 Found3xx — редиректТимчасовий редирект — не кешується так само агресивно, наступний запит знову піде на стару адресу
304 Not Modified3xx — редиректРесурс не змінився з часу останнього запиту — тіла немає, клієнт використовує кешовану копію (розділ 6)
400 Bad Request4xx — помилка клієнтаЗапит структурно некоректний (не парситься, не той формат)
401 Unauthorized4xx — помилка клієнтаКлієнт не автентифікований — сервер не знає, хто ви (незважаючи на назву, це саме про автентифікацію)
403 Forbidden4xx — помилка клієнтаКлієнт автентифікований, але не авторизований — сервер знає, хто ви, і саме тому відмовляє
404 Not Found4xx — помилка клієнтаРесурсу за цією адресою не існує
409 Conflict4xx — помилка клієнтаЗапит конфліктує з поточним станом ресурсу (наприклад, версія застаріла)
422 Unprocessable Entity4xx — помилка клієнтаЗапит структурно коректний (валідний JSON), але семантично невалідний (не пройшла бізнес-валідація полів)
429 Too Many Requests4xx — помилка клієнтаСпрацював rate limiting — забагато запитів за проміжок часу
500 Internal Server Error5xx — помилка сервераНевідома/необроблена помилка на сервері
502 Bad Gateway5xx — помилка сервераПроміжний сервер (проксі/балансувальник) отримав невалідну відповідь від бекенда
503 Service Unavailable5xx — помилка сервераСервер тимчасово не може обробити запит (перевантаження, обслуговування)

Методи: властивості safe і idempotent

Це дві різні властивості, які часто плутають між собою. Safe (безпечний) — метод не змінює стан сервера, лише читає дані. Idempotent (ідемпотентний) — повторний виклик із тими самими параметрами дає той самий кінцевий стан сервера, що й один виклик (сам результат виклику може відрізнятись, але стан — ні).

МетодSafe?Idempotent?Має тіло?
GETТакТакНі
HEADТакТакНі
OPTIONSТакТакНі
PUTНіТакТак
DELETEНіТакЗазвичай ні
POSTНіНіТак
PATCHНіЗазвичай ніТак
⚠️
Найчастіше плутають саме PATCH: формально специфікація не гарантує його ідемпотентність, і на практиці це залежить від семантики конкретного запиту. PATCH {"status": "paid"} — ідемпотентний (повторний виклик дає той самий кінцевий стан). Але PATCH {"$inc": {"balance": 100}} ("додати 100 до балансу") — ні: кожен повторний виклик змінює стан по-новому. PUT, навпаки, ідемпотентний за визначенням, бо він завжди замінює весь ресурс цілком тим самим значенням, а не застосовує дельту.

Саме тому мережеві тайм-аути з автоматичним повтором (retry) найнебезпечніші для не-ідемпотентних запитів без окремого захисту: якщо POST /payments "завис", а клієнт автоматично повторив запит, є ризик списати гроші двічі. Захист — ключ ідемпотентності (Idempotency-Key): клієнт генерує унікальний ключ на одну логічну операцію, сервер запам'ятовує результат для цього ключа й при повторному запиті з тим самим ключем повертає той самий збережений результат, не виконуючи операцію вдруге.

Заголовки: як з ними реально взаємодіяти в коді

Знати, що заголовки існують — недостатньо; варто впевнено читати й писати їх у коді обома основними API браузера.

Fetch API — об'єкт Headers
const headers = new Headers();
headers.set('Content-Type', 'application/json');
headers.append('X-Request-Id', 'abc-123');

const response = await fetch('/api/users', { headers });

// читання заголовків відповіді — назви регістронезалежні
console.log(response.headers.get('content-type')); // те саме, що 'Content-Type'
console.log(response.headers.has('Content-Type'));

for (const [key, value] of response.headers.entries()) {
  console.log(key, value);
}

Headers сам нормалізує регістр назв — get('content-type') і get('Content-Type') завжди повертають те саме значення, бо специфікація HTTP явно визначає назви заголовків як регістронезалежні.

XMLHttpRequest — старіший API, усе ще трапляється в легасі-коді
const xhr = new XMLHttpRequest();
xhr.open('POST', '/api/users');
xhr.setRequestHeader('Content-Type', 'application/json'); // ДО .send()
xhr.onload = () => {
  console.log(xhr.getResponseHeader('Content-Type'));
  console.log(xhr.getAllResponseHeaders()); // весь список одним рядком
};
xhr.send(JSON.stringify({ name: 'Ada' }));
⚠️
"Заборонені" заголовки (forbidden header names): код на JS не може вручну виставити деякі заголовки через fetch/XMLHttpRequest — наприклад, Host, Content-Length, Origin, Cookie, Connection. Ними керує сам браузер — і не з примхи: якщо би JS міг підмінити Origin, це повністю знецінило б увесь механізм CORS (розділ 5), бо сервер вирішує, довіряти запиту чи ні, саме на основі цього заголовка. Типовий симптом цієї пастки — код, що намагається виставити такий заголовок вручну, і браузер його просто мовчки ігнорує (без помилки), що спантеличує ще більше.

CORS: що це і як насправді працює

Відправна точка — same-origin policy: браузер за замовчуванням забороняє JS-коду на одній сторінці читати відповіді з запитів на інший origin. Origin — це комбінація трьох речей одночасно: схема + хост + порт. Якщо хоч одне з трьох відрізняється — це вже інший origin, навіть якщо решта виглядає ідентично.

URL AURL BТой самий origin?
https://app.example.comhttp://app.example.comНі — інша схема
https://app.example.comhttps://app.example.com:8443Ні — інший порт
https://app.example.comhttps://api.example.comНі — інший хост (субдомен важить)

CORS (Cross-Origin Resource Sharing) — це механізм, яким сервер явно дозволяє виняток із цієї заборони для конкретних інших origin-ів, через заголовки відповіді: Access-Control-Allow-Origin, Access-Control-Allow-Methods, Access-Control-Allow-Headers, Access-Control-Allow-Credentials.

🎯
Найважливіший і найчастіше незрозумілий факт: CORS перевіряє й застосовує браузер, а не сервер. Запит найчастіше реально доходить до сервера й обробляється — сервер навіть може повернути валідну відповідь. Просто браузер відмовляється віддати цю відповідь коду, що її запросив, якщо заголовки не дозволяють саме цей origin. Тому у вкладці Network в DevTools цілком реально побачити успішну відповідь (200, з тілом) — а в консолі водночас червону помилку CORS у JS.

Із цього прямо випливає: CORS неможливо "полагодити" з клієнтського коду — це заголовок відповіді, який має надіслати сервер. Немає жодного налаштування fetch, яке змусить чужий сервер повернути потрібний Access-Control-Allow-Origin.

Simple requests vs preflight

Не кожен cross-origin запит трактується однаково. "Простий" (simple) запит — GET/HEAD/POST із вузьким дозволеним набором заголовків і типів вмісту (application/x-www-form-urlencoded, multipart/form-data, text/plain) — браузер надсилає одразу, без додаткових перевірок. Усе інше (кастомні заголовки на кшталт Authorization, методи PUT/DELETE/PATCH, Content-Type: application/json) вимагає preflight: браузер САМ автоматично шле попередній запит методом OPTIONS, питаючи дозволу — і лише якщо відповідь на нього дозволяє, надсилає справжній запит.

preflight — OPTIONS-запит і відповідь
// Браузер автоматично шле ПЕРЕД реальним PUT-запитом:
OPTIONS /api/users/42 HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, authorization

// Якщо сервер дозволяє — відповідає:
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization

// І лише ТЕПЕР браузер надсилає справжній PUT-запит

Заголовки Access-Control-Request-Method і Access-Control-Request-Headers у preflight-запиті — це браузер повідомляє серверу, який метод і які заголовки хоче використати справжній запит, ще ДО того, як його надіслати.

Credentials (cookies) і CORS

Щоб cross-origin запит міг нести cookie, потрібні узгоджені дії з обох боків: клієнт мусить явно попросити про це — fetch(url, { credentials: 'include' }) — а сервер мусить відповісти Access-Control-Allow-Credentials: true. Критичне обмеження: коли задіяні credentials, Access-Control-Allow-Origin не може бути wildcard (*) — сервер зобов'язаний повернути конкретний, явний origin.

⚠️
Найпоширеніша реальна помилка: побачивши CORS-помилку, поставити Access-Control-Allow-Origin: * всюди "щоб просто запрацювало" — не усвідомлюючи, що це одразу ламає будь-які запити з credentials: 'include' (браузер сам відхилить відповідь із wildcard-origin, якщо запит був credentialed). Друга поширена помилка — намагатись "виправити CORS" на стороні клієнта: це неможливо в принципі, бо це заголовок відповіді сервера, який лише читає й застосовує браузер.

Кешування: заголовки й умовні запити

Cache-Control керує тим, чи й як довго можна використовувати кешовану копію відповіді. Дві директиви системно плутають:

ДирективаЩо означає
no-storeНе кешувати взагалі ніколи — ані в браузері, ані в проміжних кешах
no-cacheКешувати можна, але перед кожним використанням кешованої копії треба заново звернутись до сервера й перевірити, чи вона ще актуальна (revalidate)
max-age=NВикористовувати кешовану копію без звернення до сервера протягом N секунд
private / publicЧи можуть проміжні спільні кеші (CDN, проксі) кешувати відповідь, чи лише кеш конкретного браузера користувача

Умовні запити — спосіб перевірити свіжість кешу дешево, без повторного завантаження всього тіла: сервер віддає ETag (відбиток версії ресурсу) або Last-Modified разом із першою відповіддю; наступного разу клієнт надсилає цей самий відбиток назад у заголовку If-None-Match (або If-Modified-Since). Якщо ресурс не змінився — сервер відповідає 304 Not Modified із порожнім тілом, економлячи трафік, але мережевий запит усе одно відбувається (на відміну від max-age, де запиту взагалі не буде).

Content negotiation: Accept-заголовки

Accept повідомляє серверу, які формати відповіді клієнт готовий прийняти (наприклад, application/json проти text/html); Accept-Language — якою мовою; Accept-Encoding — яке стиснення (gzip, br) клієнт уміє розпаковувати. Сервер обирає підходящий варіант відповіді на основі цих заголовків — це і є content negotiation.

Якщо сервер не може задовольнити Accept (наприклад, клієнт просить лише application/xml, а сервер уміє тільки JSON), коректна відповідь — 406 Not Acceptable.

Заголовок Vary у відповіді каже проміжним кешам, які саме заголовки запиту вплинули на обраний варіант відповіді (наприклад, Vary: Accept-Language) — без цього кеш міг би помилково віддати англійську версію сторінки користувачу, що просив французьку, бо для кешу URL виглядав однаковим.

Cookies і атрибути Set-Cookie

Сервер встановлює cookie через заголовок відповіді Set-Cookie. На співбесіді очікують впізнати кожен атрибут за назвою й пояснити його одним реченням — ось повний практичний набір:

АтрибутЩо визначає
DomainЯким (під)доменам браузер надсилатиме cookie назад; якщо не вказано — лише той самий хост, що встановив cookie (без піддоменів)
PathЗвужує cookie до конкретного шляху на сайті (наприклад, лише /admin) — рідко використовується суворо, але варто знати, що це не про безпеку, а про область видимості
ExpiresАбсолютна дата, коли cookie перестає існувати; без неї (і без Max-Age) — це session cookie, що зникає із закриттям браузера
Max-AgeТе саме, що Expires, але як відносний інтервал у секундах від моменту встановлення — сучасніший і надійніший спосіб (не залежить від розсинхронізації годинників клієнта й сервера)
HttpOnlyJS не має доступу до значення — document.cookie його не покаже; ключовий захист авторизаційних токенів від крадіжки через XSS
SecureCookie передається лише по HTTPS — ніколи по звичайному HTTP, навіть на той самий домен
SameSite=Strict/Lax/NoneЧи надсилається cookie разом із cross-site запитами — існує саме як механізм пом'якшення CSRF-атак (детальніше в наступному пункті)
PartitionedНовіший атрибут (CHIPS): прив'язує сторонню (third-party) cookie окремо до кожного top-level сайту, що її вбудовує — той самий cross-site скрипт на різних сайтах більше не ділиться однією й тією самою cookie між ними, що закриває механізм крос-сайтового трекінгу, який SameSite сам по собі не закривав

Повний розбір моделі атак і чому саме комбінація HttpOnly + Secure + SameSite вважається безпечною для авторизаційних токенів — у туторіалі 3.

Коротко: HTTP/1.1 vs HTTP/2 vs HTTP/3

Досить знати, що вони існують, і одну ключову різницю кожного — не протокольні деталі:

ВерсіяКлючова відмінність
HTTP/1.1Одне з'єднання обробляє по одному запиту за раз — тому браузери відкривають кілька паралельних TCP-з'єднань на один origin, щоб завантажувати ресурси одночасно
HTTP/2Мультиплексування — багато запитів одночасно через одне з'єднання, плюс стиснення заголовків (HPACK). Прибрало потребу в старих трюках на кшталт спрайтів/конкатенації файлів "щоб зменшити кількість запитів"
HTTP/3Працює поверх QUIC (на UDP, а не TCP) — головна мета: прибрати head-of-line blocking на рівні самого TCP, який усе ще залишався проблемою навіть у HTTP/2 (загублений один TCP-пакет блокує весь мультиплексований потік)

20 найчастіших і найважчих питань про HTTP

Від базових визначень до питань, на яких плаваю навіть досвідчені кандидати — саме тому, що тема здається "занадто простою, щоб готуватись".

База Пастка Просунуте Системний дизайн
01ПасткаЧим "safe" відрізняється від "idempotent"?

Це дві незалежні властивості, які легко переплутати. Safe — метод не змінює стан сервера взагалі (лише GET/HEAD/OPTIONS). Idempotent — повторний виклик із тими самими параметрами залишає сервер у тому самому кінцевому стані, що й один виклик, навіть якщо сам метод змінює дані (PUT, DELETE). Кожен safe-метод автоматично ідемпотентний, але не навпаки — PUT ідемпотентний, хоч і не safe.

02ПасткаЧому PATCH не гарантовано ідемпотентний?

Бо PATCH описує часткову зміну, а не заміну всього ресурсу — і форма цієї зміни вирішує все. PATCH {"status": "paid"} ідемпотентний (той самий кінцевий стан при повторі). PATCH {"$inc": {"views": 1}} — ні, кожен повтор додає ще одиницю. На відміну від PUT, який ідемпотентний за визначенням протоколу, ідемпотентність PATCH — питання конкретної семантики API, а не гарантія специфікації.

03БазаЧим відрізняються 401 і 403?

401 Unauthorized — сервер не знає, хто ви (немає валідних credentials узагалі, або вони прострочені/невалідні). 403 Forbidden — сервер точно знає, хто ви, і саме тому відмовляє: у вас недостатньо прав на цю дію. Практичне правило: 401 виправляється логіном, 403 — ні (потрібні інші права).

04БазаЧим відрізняються 301 і 302 — і чому це важливо для кешування?

301 Moved Permanently сигналізує, що стара адреса більше ніколи не буде дійсною — браузери й пошукові боти кешують це агресивно й довго, наступного разу підуть напряму на нову адресу (і SEO-вага "переносить" на нову адресу). 302 Found — тимчасовий редирект, кешується не так довго/агресивно, наступний запит цілком може знову піти на стару адресу. Використання 301 замість 302 (чи навпаки) для тимчасового обслуговування — реальна помилка, яка "прилипає" в кешах браузерів і CDN надовго.

05ПасткаЧому CORS-помилка все одно показує відповідь у вкладці Network?

Бо CORS — це обмеження на рівні браузера, застосоване вже після того, як мережевий запит реально відбувся і сервер відповів. Сервер найчастіше не в курсі жодного "CORS-порушення" — він обробив запит і повернув відповідь як завжди. Браузер просто відмовляється передати цю вже отриману відповідь коду, що її ініціював, якщо заголовки відповіді не дозволяють викликаючий origin. Тому в Network — повна відповідь з тілом і статусом 200, а в консолі JS — помилка "blocked by CORS policy".

06ПасткаЧи можна "виправити" CORS з клієнтського коду?

Ні, у принципі. Access-Control-Allow-Origin та інші CORS-заголовки — це заголовки відповіді сервера, які лише зчитує й застосовує браузер. Жодна опція fetch, жоден заголовок запиту з боку клієнта не змусить чужий сервер повернути потрібний дозвіл. Єдиний реальний спосіб "обійти" CORS з клієнта — проксіювати запит через свій власний сервер (той-таки origin для браузера), який уже сам звертається до чужого API без обмежень CORS (вони застосовуються лише в браузерах, не в серверному коді).

07ПросунутеЩо саме перетворює звичайний запит на "preflighted"?

Запит виходить за межі "simple request", якщо: метод не входить у GET/HEAD/POST; або є заголовок поза вузьким дозволеним списком (наприклад, Authorization, будь-який кастомний X-*); або Content-Type не входить у application/x-www-form-urlencoded/multipart/form-data/text/plain (зокрема, application/json завжди викликає preflight). У будь-якому з цих випадків браузер автоматично вставляє попередній OPTIONS-запит.

08ПросунутеЩо конкретно міститься в preflight-запиті?

Метод OPTIONS плюс два спеціальні заголовки, якими браузер заздалегідь повідомляє, що саме планує зробити справжній запит: Access-Control-Request-Method (який метод буде використано) і Access-Control-Request-Headers (які нестандартні заголовки будуть надіслані). Сервер відповідає списком дозволеного у відповідних Access-Control-Allow-* заголовках — і лише якщо реальний метод/заголовки входять у цей дозволений список, браузер надсилає справжній запит.

09ПасткаЧому Access-Control-Allow-Origin: * і credentials несумісні?

Це свідоме обмеження безпеки специфікації: якщо сервер міг би відповідати wildcard-origin і водночас дозволяти credentials (cookies), будь-який сайт у світі міг би зробити credentialed-запит від імені залогіненого користувача й отримати відповідь — практично CSRF, узаконений самим CORS. Тому браузер відхиляє відповідь, якщо запит був credentials: 'include', а Access-Control-Allow-Origin дорівнює * — сервер зобов'язаний повернути конкретний, явний origin.

10БазаЧим no-cache відрізняється від no-store?

Назви оманливо схожі, а поведінка різна. no-store — не кешувати взагалі, кожен запит іде на сервер по повну відповідь. no-cache — кешувати можна, але кешовану копію не можна використати без попереднього звернення до сервера для перевірки актуальності (revalidate) — фактично завжди мережевий запит, але потенційно з порожньою 304-відповіддю замість повного тіла.

11ПросунутеЯк саме ETag економить трафік, якщо запит усе одно йде на сервер?

Економія не в кількості запитів, а в розмірі відповіді. Клієнт надсилає збережений ETag назад у заголовку If-None-Match. Сервер порівнює його з поточним відбитком ресурсу: якщо збігається — повертає 304 Not Modified з порожнім тілом (лише заголовки), а не заново все тіло відповіді. Для великих відповідей (списки, зображення) це суттєва економія трафіку, навіть попри те, що мережевий раунд-тріп усе одно відбувається.

12ПасткаЧому JS-код не може вручну виставити заголовок Origin у fetch-запиті?

Тому що Origin — один із "заборонених" (forbidden) заголовків, якими керує сам браузер, а не код застосунку. Якщо би це можна було підмінити з JS, увесь механізм CORS втратив би сенс — будь-який сайт міг би прикинутись іншим origin і отримати дозвіл, на який не мав права. Спроба виставити такий заголовок вручну звичайно просто мовчки ігнорується браузером, без явної помилки.

13БазаЧому назви HTTP-заголовків регістронезалежні — і що це означає для коду?

Так визначено самою специфікацією HTTP — Content-Type і content-type це той самий заголовок. Практичний наслідок для коду: Headers.get()/.set()/.has() самі нормалізують регістр, тому шукати заголовок точним порівнянням рядків (if (key === 'Content-Type') по сирому об'єкту, а не через Headers) — крихкий код, який зламається, щойно сервер (чи проксі на шляху) віддасть той самий заголовок в іншому регістрі.

14ПасткаЧи будуть https://shop.example.com і https://shop.example.com:8443 одним origin?

Ні. Origin — це строго схема + хост + порт одночасно; порт входить у порівняння так само, як схема й хост. Навіть коли схема і хост візуально ідентичні, різний порт (у прикладі — явний 8443 проти імпліцитного 443 для HTTPS) робить це двома різними origin-ами з погляду same-origin policy й CORS. Так само різними origin є різні субдомени (app.example.com проти api.example.com) — попри спільний батьківський домен.

15ПросунутеУ чому різниця між "будь-який заголовок працює" і Access-Control-Allow-Headers?

Access-Control-Allow-Headers у відповіді на preflight — це явний білий список нестандартних заголовків, які сервер дозволяє клієнту надсилати в справжньому cross-origin запиті. Якщо клієнт спробує надіслати заголовок, якого немає в цьому списку, браузер заблокує сам запит ще до відправки (preflight не пройде) — сервер навіть не побачить цей запит. Це протилежність до "будь-який заголовок автоматично працює" — навпаки, усе поза вузьким simple-списком за замовчуванням заборонено, поки явно не дозволено.

16БазаНаведіть конкретний приклад, чому POST не ідемпотентний, а PUT — так

POST /orders {"item": "book"}, викликаний двічі, зазвичай створює два окремі замовлення — кожен виклик додає новий ресурс. PUT /orders/42 {"item": "book"}, викликаний двічі, обидва рази встановлює замовлення 42 в один і той самий стан — другий виклик нічого додатково не змінює. Різниця в самій семантиці методів: POST означає "створи щось нове", PUT — "нехай ресурс за цією адресою буде саме таким".

17БазаЩо відбувається, якщо сервер не може задовольнити заголовок Accept клієнта?

Коректна відповідь у такому разі — 406 Not Acceptable: сервер явно повідомляє, що жоден із запитаних клієнтом форматів відповіді він видати не може. На практиці багато API спрощують це й просто завжди повертають один формат (зазвичай JSON) незалежно від Accept, ігноруючи повноцінне узгодження змісту — але знати про існування 406 і сам механізм негоціації вартий уваги.

18ПросунутеНавіщо потрібен заголовок Vary?

Vary каже проміжним і браузерним кешам, які саме заголовки запиту вплинули на те, яку саме версію відповіді сервер обрав і повернув — наприклад, Vary: Accept-Language. Без цього кеш бачить лише URL і може помилково віддати збережену раніше англійську версію користувачу, чий запит просив французьку — бо для кешу, який не знає про Vary, URL виглядає однаковим незалежно від мовних заголовків запиту.

19Системний дизайнЯк спроєктувати ключ ідемпотентності для платіжного API?

Клієнт генерує унікальний ідентифікатор (наприклад, UUID) один раз на одну логічну спробу оплати і надсилає його в заголовку на кшталт Idempotency-Key. Сервер, отримавши запит із цим ключем уперше, виконує операцію і зберігає пару "ключ → результат". Якщо той самий ключ прийде повторно (мережевий тайм-аут і клієнтський retry) — сервер не виконує оплату вдруге, а просто повертає раніше збережений результат. Критично: ключ генерується на стороні клієнта й лишається незмінним для всіх спроб retry однієї й тієї ж користувацької дії, інакше весь захист втрачає сенс.

20ПросунутеЯк HTTP/2 і HTTP/3 по-різному вирішують head-of-line blocking?

HTTP/1.1 мав head-of-line blocking на рівні застосунку: одне з'єднання обробляло запити по черзі. HTTP/2 вирішив це мультиплексуванням — багато запитів одночасно в одному TCP-з'єднанні. Але лишилась проблема на рівень нижче: TCP сам гарантує порядок доставки байтів, тож один загублений TCP-пакет блокує всі мультиплексовані потоки в цьому з'єднанні, поки він не буде повторно доставлений — це head-of-line blocking на рівні транспорту. HTTP/3 усуває це, перейшовши на QUIC (поверх UDP), де кожен потік обробляє втрату пакетів незалежно від інших, не блокуючи все з'єднання цілком.
