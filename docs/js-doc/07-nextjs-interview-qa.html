A

Рендеринг у Next.js: основи

Абревіатури, які зобов'язаний знати кожен — але справжня перевірка в тому, чи можете ви пояснити механізм за кожною з них, а не просто розшифрувати скорочення.

01БазаЯкі основні способи рендерингу є в Next.js?

Чотири принципово різні стратегії: SSR (Server-Side Rendering) — HTML генерується на сервері під кожен запит; SSG (Static Site Generation) — сторінка генерується один раз під час білду; ISR (Incremental Static Regeneration) — статична сторінка, яка вміє оновлюватись у фоні без повного redeploy; CSR (Client-Side Rendering) — сторінка рендериться в браузері з мінімальним HTML із сервера. Детальне порівняння "коли яку обирати" з таблицею компромісів — у туторіалі 6, тема 2, а що відбувається технічно всередині самого SSR — у темі 3.

02БазаЩо таке SSR?

Server-Side Rendering — HTML генерується на сервері при кожному вхідному запиті, а не заздалегідь. Головні плюси: краще SEO (пошуковий бот одразу отримує повний HTML, а не порожній <div id="root">) і швидший first paint (браузер може почати малювати сторінку одразу після отримання HTML, не чекаючи завантаження й виконання всього JS-бандла). Ціна — найповільніший TTFB серед усіх стратегій, бо сервер виконує повний рендер під кожен запит окремо.

03БазаЩо таке SSG?

Static Site Generation — сторінки генеруються один раз, під час білду, і віддаються як готові статичні файли. Плюси: дуже швидка віддача (немає рендеру під запит узагалі) і природне CDN-кешування — статичний файл однаковий для всіх користувачів, тож CDN може роздавати його з edge-локацій по всьому світу без жодної додаткової логіки.

04БазаЩо таке ISR?

Incremental Static Regeneration дозволяє оновлювати вже задеплоєні статичні сторінки без повного rebuild усього застосунку. Сторінка позначається періодом "протухання" — наприклад, revalidate: 60 означає, що не частіше ніж раз на 60 секунд Next.js у фоні перегенерує сторінку, а поки нова версія не готова, користувачі продовжують отримувати стару (stale-while-revalidate). Це компроміс між швидкістю SSG і свіжістю SSR, без потреби деплоїти застосунок заново під кожну зміну даних.

05БазаЩо таке App Router?

Нова, файлово-орієнтована система маршрутизації Next.js (на заміну старому Pages Router). Ключові особливості: нативна підтримка React Server Components, вкладені layouts (спільний UI, що не перемонтовується між переходами всередині одного сегмента маршруту), nested routing (маршрут будується композицією вкладених папок/сегментів, кожна зі своїм layout.tsx/page.tsx) і вбудований streaming — можливість віддавати частини HTML раніше, ніж увесь рендер завершиться (детально — категорія E, питання про Streaming).

06БазаЩо таке Server Components?

Компоненти, які виконуються й рендеряться виключно на сервері — їхній JavaScript-код узагалі не потрапляє в браузерний бандл. Плюси: менший розмір бандла (усе, що не потребує інтерактивності на клієнті, просто не відправляється користувачу) і краща продуктивність першого завантаження. У App Router це дефолтний тип компонента — компонент стає клієнтським лише тоді, коли ви явно позначите його директивою "use client" (наступне питання).

07БазаЩо таке "use client"?

Директива, що позначає файл (і все, що з нього імпортується вниз по дереву) як клієнтський компонент — тобто такий, що виконується в браузері й може використовувати хуки стану (useState, useEffect), обробники подій, браузерні API. Без цієї директиви компонент за замовчуванням є server component.

app/components/Counter.tsx
"use client";

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
08БазаЩо таке API Routes?

Next.js дозволяє створювати повноцінні backend-ендпоінти прямо всередині проєкту, без окремого бекенд-сервісу — файл route.ts у папці маршруту стає HTTP-хендлером.

app/api/users/route.ts
export async function GET() {
  const users = await db.users.findMany();
  return Response.json(users);
}
B

Routing, Layouts, Data Fetching, Next.js vs React

Базовий шар App Router, який тримає на собі все інше з категорій C і D нижче.

09БазаЯк працює routing в App Router?

Next.js використовує file-based routing: структура папок і файлів усередині app/ напряму визначає структуру URL. Файл app/blog/page.tsx автоматично стає доступним за шляхом /blog — без окремого файлу конфігурації маршрутів, як у класичних SPA-роутерах.

10БазаЩо таке Layout?

layout.tsx дозволяє зберігати спільний UI (навігацію, сайдбар, футер) між переходами сторінок усередині одного сегмента маршруту — при навігації між вкладеними сторінками layout не перемонтовується заново, перерендериться лише вміст конкретної page.tsx. Це і зберігає стан (наприклад, скрол сайдбару), і економить роботу рендеру.

11БазаЯк працює data fetching у App Router?

Server Component може напряму викликати await fetch(url) усередині свого тіла — без окремого хука чи бібліотеки завантаження даних, бо код і так виконується на сервері під час рендеру. Історично (до Next.js 15) такий fetch кешувався автоматично за замовчуванням; як саме ця поведінка кешування змінилась — дивіться категорію E, це одне з найчастіших питань про свіжі версії.

12БазаЧим Next.js відрізняється від React?

React — бібліотека для побудови UI-компонентів, сама по собі не має думки про маршрутизацію, рендеринг на сервері чи завантаження даних. Next.js — фреймворк поверх React, який додає готові рішення для цих задач "з коробки": файлову маршрутизацію, кілька стратегій рендерингу (SSR/SSG/ISR), вбудований data fetching, оптимізацію зображень/шрифтів і продакшн-збірку. Коротко: React відповідає на "як намалювати UI", Next.js — на "як побудувати застосунок навколо цього UI".

C

Middleware

Код, що виконується перед обробкою запиту до сторінки чи API — і одна з найбагатших на трюкові питання тем на Next.js-співбесідах.

13БазаЩо таке Middleware в Next.js?

Middleware — код, який виконується перед тим, як запит дістанеться сторінки чи API-роуту. Він дозволяє: перехопити request, змінити response, зробити redirect чи rewrite, перевірити авторизацію, виконати довільну логіку до рендеру. Класичний Middleware працює на Edge Runtime (детальний розбір обмежень Edge — категорія D).

14БазаДе знаходиться файл middleware?

У корені проєкту (або в src/, якщо проєкт використовує цю структуру): /middleware.ts або /src/middleware.ts. Рівно один файл на застосунок — уся логіка перехоплення запитів збирається в ньому, з розгалуженням через перевірку request.nextUrl.pathname чи config.matcher (питання 20 нижче).

15БазаЯк виглядає найпростіший приклад Middleware?
middleware.ts
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  console.log("Request:", request.nextUrl.pathname);

  return NextResponse.next();
}

NextResponse.next() — пропускає запит далі, без жодного втручання; це те, що middleware має повернути за замовчуванням для всіх маршрутів, які не потребують спеціальної обробки.

16БазаЯк реалізувати Auth Guard через Middleware?
middleware.ts — перевірка токена
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const token = request.cookies.get("token");

  if (!token) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  return NextResponse.next();
}

Типове застосування — захищені маршрути: protected routes, dashboard, admin pages. Middleware тут відіграє роль першого, дешевого бар'єру ще до того, як запит взагалі дістанеться логіки сторінки.

17БазаЯк зробити redirect у Middleware?
middleware.ts — redirect
export function middleware(request: NextRequest) {
  if (request.nextUrl.pathname === "/old-page") {
    return NextResponse.redirect(new URL("/new-page", request.url));
  }

  return NextResponse.next();
}

NextResponse.redirect(...) дає браузеру справжню HTTP-переадресацію — URL у адресному рядку змінюється на новий.

18ПасткаЩо таке Rewrite — і чим він принципово відрізняється від redirect?
middleware.ts — rewrite
export function middleware(request: NextRequest) {
  if (request.nextUrl.pathname === "/dashboard") {
    return NextResponse.rewrite(new URL("/dashboard/user", request.url));
  }

  return NextResponse.next();
}

Rewrite змінює маршрут, який фактично обробляє запит, без зміни URL у браузері — користувач і далі бачить /dashboard в адресному рядку, хоча контент насправді прийшов з /dashboard/user. Redirect, навпаки, завжди міняє видиму адресу. Це одна з найчастіших плутанин на співбесіді — якщо запитують "чим rewrite відрізняється від redirect", ключове слово у відповіді саме "видима адреса в браузері".

19БазаЩо таке matcher і навіщо він потрібен?

Middleware за замовчуванням запускається на кожен запит до застосунку — matcher дозволяє обмежити його роботу лише певними маршрутами.

middleware.ts — обмеження маршрутів
export const config = {
  matcher: ["/dashboard/:path*"],
};
20ПасткаЧому middleware не підходить для складної auth-логіки?

Причина — обмеження Edge Runtime (детально в категорії D): немає повного Node API, немає прямого стабільного доступу до бази даних. Правильна стратегія — розділити відповідальність: middleware робить дешеву, швидку перевірку (чи є взагалі cookie/token), а API route (або server component) на повному Node-рантаймі виконує повну валідацію — перевірку підпису токена, звернення до БД за роллю користувача тощо.

21Системний дизайнMiddleware vs Server Components — де що краще перевіряти?

Це питання явно перевіряє розуміння межі відповідальності. Middleware найкраще підходить для рішень, які потрібно прийняти до рендеру й які є "блокуючими" за своєю природою: redirect неавторизованого користувача, blocking-перевірка перед тим, як взагалі почати генерувати сторінку. Server Component краще підходить для власне data fetching і дрібнішого access control (наприклад, показати різний вміст усередині вже дозволеної сторінки залежно від ролі) — там, де потрібен доступ до повного Node-рантайму й бази даних.

22ПасткаКласична помилка: infinite redirect loop у middleware — де вона ховається?

Якщо middleware застосовується до усіх маршрутів (немає звуженого matcher) і редиректить на /login кожного разу, коли немає токена — він спрацює і для самого запиту до /login, знову не знайде токена й знову редиректить на /login. Браузер отримує нескінченний ланцюжок редиректів.

❌ баг — нескінченний redirect
if (!token) {
  return NextResponse.redirect("/login");
}
✅ виправлено — виняток для самої сторінки логіну
if (!token && request.nextUrl.pathname !== "/login") {
  return NextResponse.redirect("/login");
}
23ПасткаMiddleware performance trap — у чому небезпека запуску на всіх маршрутах?

Якщо middleware не обмежений matcher, він виконується для кожного запиту застосунку — включно з внутрішніми службовими маршрутами (/_next), статичними зображеннями (/images) і статикою (/static). Це додає непотрібну затримку до речей, які middleware ніколи не мав контролювати, і помітно погіршує продуктивність усього застосунку.

middleware.ts — правильне звуження
export const config = {
  matcher: ["/dashboard/:path*"],
};
24ПросунутеCookies vs Authorization header — звідки middleware зазвичай бере токен?

У прикладах вище токен читається як request.cookies.get("token") — типовий підхід для браузерних сесій. Але деякі клієнти (мобільні застосунки, серверні інтеграції, SPA без cookie-based сесій) передають авторизацію через заголовок Authorization: Bearer <token> замість cookie. Middleware, розрахований лише на cookie, просто не побачить такого токена — реальна auth-логіка часто мусить перевіряти обидва джерела.

25БазаЯк коротко відповісти про Middleware на співбесіді?
✅
Middleware у Next.js дозволяє перехоплювати запити перед рендером сторінки. Воно використовується для auth guards, redirects, rewrites і logging. Middleware працює на Edge Runtime і має обмеження, тому складну логіку краще виконувати на сервері або в API routes.
D

Edge Runtime

Середовище виконання, у якому працює Middleware — і окрема, часто плутана з ним тема сама по собі.

26БазаЩо таке Edge Runtime?

Середовище виконання, де код запускається на edge-серверах CDN — фізично ближче до користувача, ніж центральний сервер застосунку. Це дозволяє зменшити latency, швидше обробляти requests і виконувати routing/auth-логіку ближче до клієнта, ще до того, як запит взагалі дістанеться основного сервера.

27БазаДе в Next.js використовується Edge Runtime?

Три основні місця: Middleware (за замовчуванням), Edge API Routes (окремі API-роути, явно позначені для виконання на edge) і Edge Functions (загальний термін для будь-якого коду, що виконується в цьому середовищі).

28БазаЯк увімкнути Edge Runtime для API route?
app/api/hello/route.ts
export const runtime = "edge";

export async function GET() {
  return new Response("Hello from Edge");
}
29БазаЧим шлях запиту в Edge відрізняється від звичайного SSR?

Звичайний SSR: Client → Server → Response — запит завжди йде до центрального сервера застосунку. Edge Runtime: Client → CDN Edge → Response — запит обробляється на найближчому географічно edge-сервері, яких зазвичай багато й розташовані вони в різних регіонах світу, тож фізична відстань до користувача коротша.

30ПросунутеПриклад geo-based routing на Edge
middleware.ts — маршрутизація за країною
export function middleware(request: NextRequest) {
  const country = request.geo?.country;

  if (country === "DE") {
    return NextResponse.redirect("/de");
  }

  return NextResponse.next();
}

Оскільки код виконується на edge-сервері, географічно найближчому до користувача, інформація про країну доступна одразу, без додаткового мережевого запиту до геолокаційного сервісу.

31БазаПриклад auth-перевірки на Edge
middleware.ts — auth на edge
export function middleware(request: NextRequest) {
  const token = request.cookies.get("token");

  if (!token) {
    return NextResponse.redirect("/login");
  }

  return NextResponse.next();
}
32БазаЯкі обмеження має Edge Runtime?

Edge Runtime не підтримує Node.js API — недоступні fs (файлова система), net, child_process, Node-версія crypto. Замість них Edge пропонує стандартні Web API: Fetch API, Web Crypto API, Streams — той самий набір примітивів, що доступний у браузері, а не повноцінне Node.js-середовище.

33Системний дизайнЧому Edge Runtime не підходить для запитів до бази даних?

Edge-функції короткоживучі за задумом (виконуються й завершуються швидко), тому не мають стабільного connection pool до бази даних — кожен виклик потенційно відкриває нове з'єднання, що дорого й повільно. Крім того, latency від конкретного edge-сервера до вашої бази даних (яка фізично живе в одному регіоні) може виявитись більшою, ніж якби запит одразу пішов із центрального сервера в тому самому дата-центрі, що й база. Правильний розподіл: Edge — auth/routing-рішення, Server (звичайний Node-рантайм) — запити до БД.

34БазаEdge Runtime vs Node Runtime — коротке порівняння

35ПасткаЧому Edge інколи виявляється повільнішим, а не швидшим?

Парадоксальна, але реальна ситуація: якщо логіці на edge усе одно потрібні дані з центрального сервера чи бази даних, ланцюжок стає User → Edge → Server → DB — тобто Edge не замінює похід до сервера, а додає зайвий проміжний хоп перед ним. Edge дає виграш лише тоді, коли рішення справді ухвалюється повністю на самому edge-сервері, без походу далі.

36ПросунутеЩо таке Edge cold start?

Edge-функції, як і будь-які serverless-функції, можуть мати cold start — затримку на перший виклик після періоду бездіяльності, поки середовище виконання ініціалізується. Ключова відмінність — цей cold start у edge-середовищі зазвичай суттєво менший, ніж у традиційних serverless-функціях (легше рантайм-середовище, менше залежностей для ініціалізації).

37ПросунутеЧому деякі npm-бібліотеки просто не працюють на Edge?

Бо вони напряму залежать від Node.js-специфічних глобальних об'єктів і модулів, яких у Edge Runtime немає: fs (робота з файлами), process (детальна інформація про Node-процес), Buffer (Node-специфічний тип бінарних даних), Node-версія crypto. Бібліотека, написана з розрахунком на повне Node-середовище, просто впаде на edge — потрібен або edge-сумісний аналог, або виконання цієї частини логіки на звичайному сервері.

38БазаЯк коротко відповісти про Edge Runtime на співбесіді?
✅
Edge Runtime дозволяє запускати код ближче до користувача на CDN edge-серверах. Це зменшує latency для таких задач як auth, redirects або routing. Але Edge має обмеження, оскільки не підтримує Node.js API, тому складну бізнес-логіку або DB-запити краще виконувати на сервері.
🚀
Senior insight: Edge Runtime — це шар мережевої оптимізації (network optimization layer), а не повноцінний backend runtime. Він ідеально підходить для auth gating, A/B testing, geo routing, caching logic — і свідомо не претендує замінити сервер там, де потрібна повна бізнес-логіка чи доступ до БД.
E

Next.js 15: що нового (Senior-рівень)

Ключові зміни релізу, який на момент написання цього довідника вже став "минулою" версією — але його breaking changes досі найчастіше запитують, бо саме на них ламається код при міграції.

39ПасткаAsync Request APIs — у чому суть цієї breaking change?

headers(), cookies() і params стали асинхронними — тепер їх обов'язково потрібно await-ити.

до і після
const headersList = await headers();

Причина зміни — підготовка архітектури до глибшого streaming і edge-виконання: коли рендер сторінки може бути частково відкладений (Suspense-межі, часткова пререндеризація), доступ до request-специфічних даних синхронно перестає бути гарантовано коректним — асинхронний API дає фреймворку гнучкіший контроль над тим, коли саме ці дані реально готові.

40ПасткаЯк змінилась поведінка кешування fetch?

Дуже часте питання на співбесіді саме через те, що це тихий, легко пропущений breaking change. Раніше (до Next.js 15): fetch у Server Component кешувався за замовчуванням — розробник міг про це навіть не здогадуватись. Тепер: кешування стало explicit — щоб зберегти стару поведінку, потрібно явно попросити про це.

явне кешування
fetch(url, { cache: 'force-cache' })

Практичний наслідок для міграції зі старіших версій: код, який мовчки покладався на автоматичне кешування, після оновлення почне робити мережевий запит щоразу — без явної помилки, лише зміна поведінки й продуктивності.

41БазаServer Actions — що змінилось у їхньому статусі?

Server Actions більше не є experimental-фічею — вони стабільні й готові для продакшн-використання. Застосовуються для форм (forms), мутацій даних (mutations) і будь-якої backend-логіки, яку зручно викликати прямо з клієнтського коду без ручного створення окремого API route.

позначення server action
'use server'
42ПросунутеЩо таке Streaming у Next.js — і як він насправді працює?

Streaming — механізм, що дозволяє віддавати HTML сторінки частинами (chunk-ами), не чекаючи, поки завершиться рендер усієї сторінки. Простими словами: замість того щоб чекати на всі дані і лише потім показати готову сторінку, Next.js показує частину UI одразу, а решту довантажує пізніше, коли вона стане готовою.

Як це працює покроково: сервер починає рендер сторінки; швидкі частини UI (ті, що не залежать від повільних даних) відправляються клієнту одразу; повільні частини огортаються в межу <Suspense>; коли повільні дані нарешті готові, відповідний HTML "дострімується" й вставляється в потрібне місце на сторінці, яка вже відображається користувачу.

межа Suspense
<Suspense fallback={<Loading />}>
  <SlowComponent />
</Suspense>

Loading приходить до користувача одразу; SlowComponent довантажується пізніше, коли його дані готові — користувач весь цей час бачить активну, небло­ковану сторінку, а не порожній екран.

SSR (старий, без streaming)Streaming
ОчікуванняЧекає весь HTML цілкомВіддає частинами
UXПовільніший UXШвидший UX
РендерBlockingNon-blocking

Що це дає: швидший First Contentful Paint, кращий загальний UX, менше blocking-рендерингу. Ключовий момент, який часто вислизає: streaming працює саме через Suspense-межі React — без жодного Suspense у дереві компонентів streaming практично не відбувається, сторінка й далі поводиться як класичний блокуючий SSR. Використовується найчастіше в App Router, у Server Components, для повільних зовнішніх API та дашбордів/UI з великою кількістю даних.

✅
Коротка відповідь (20 сек): Streaming у Next.js — це спосіб віддавати HTML частинами, щоб користувач бачив контент швидше. Він працює разом із Suspense, який визначає, які частини UI можна відкласти.
🧠
Senior-інсайт: Streaming змінює SSR з blocking-моделі (все або нічого) на progressive rendering (показуй готове, довантажуй решту) — це не окрема фіча поверх SSR, а фундаментальна зміна самої моделі рендерингу.
43ПросунутеЩо таке Partial Prerendering (PPR)?

Комбінація SSG + SSR + Streaming в межах однієї сторінки: статична частина сторінки (наприклад, шаблон/оболонка) віддається миттєво, як готовий SSG-артефакт, а динамічна частина довантажується через streaming поверх цієї статичної основи. Це дозволяє мати швидкість статики й свіжість динамічних даних одночасно, без вибору "вся сторінка статична АБО вся динамічна" — питання важливе саме для продуктивності реальних продуктових сторінок зі змішаним вмістом.

44БазаЩо покращилось у Middleware/Edge у Next.js 15?

Загальні покращення стабільності, швидшого виконання й кращого DX (developer experience) навколо Middleware й Edge Runtime — без концептуальних змін самої моделі. Глибокий розбір того, як усе це працює й де межі — категорії C і D вище.

45БазаЩо таке Turbopack (у контексті Next.js 15)?

Значно швидший dev-сервер порівняно з класичним Webpack-конфігом, із кращим Hot Module Replacement (HMR) — зміни в коді підхоплюються швидше під час розробки. У Next.js 15 Turbopack ще позиціювався як (майже готова) альтернатива Webpack для розробки; наскільки він стабілізувався далі — дивіться категорію F.

46БазаЩо покращилось у Metadata API?

Краща інтеграція з SEO (більш повний і гнучкий контроль над тегами <head>) та підтримка асинхронної генерації метаданих — функції на кшталт generateMetadata можуть самі звертатись за даними (наприклад, назвою товару з бази даних), перш ніж сформувати фінальні <title>/<meta>-теги сторінки.

✅
Коротка відповідь (20-30 сек): У Next.js 15 ключові зміни — це асинхронні request API, нова модель кешування fetch, стабілізація Server Actions, Partial Prerendering та покращений streaming. Основний фокус — performance, контроль кешу та server-first підхід.
F

Найновіша версія: Next.js 16

На момент підготовки цього довідника найновішим стабільним релізом є Next.js 16 — ці питання перевіряють, чи ваші знання не застрягли на версії 15. Факти нижче звірені з офіційним анонсом релізу на nextjs.org/blog.

47ПросунутеЩо змінилось у статусі Turbopack у Next.js 16?

Turbopack досяг повної стабільності — і для розробки, і для продакшн-збірок — і став дефолтним бандлером для всіх нових проєктів Next.js 16 (у 15-й версії він був лише швидкою альтернативою для dev-режиму). Заявлені показники: у 2-5 разів швидші продакшн-білди й до 10 разів швидший Fast Refresh під час розробки. Для проєктів із кастомним Webpack-налаштуванням лишили шлях відступу: next dev --webpack і next build --webpack.

48ПросунутеЩо таке Cache Components — і як вони завершують історію PPR?

Нова модель кешування, побудована на директиві "use cache", яка дозволяє явно позначати для кешування сторінки, компоненти чи окремі функції — компілятор сам генерує ключ кешу там, де директива застосована. Головна філософська зміна порівняно з попередніми версіями App Router: кешування стає повністю опційним (opt-in) — увесь динамічний код за замовчуванням виконується під кожен запит наживо, а не кешується неявно "за домовленістю фреймворка". Це саме та модель, яка завершує історію Partial Prerendering (представленої ще 2023-го): PPR більше не окремий experimental-прапорець, а вбудована частина цієї єдиної моделі кешування, яку вмикають через cacheComponents: true у next.config.ts.

49Пасткаproxy.ts замінив middleware.ts — що саме змінилось?

Дуже вірогідне питання саме для перевірки актуальності знань: у Next.js 16 middleware.ts перейменований на proxy.ts (з відповідним перейменуванням експортованої функції на proxy), щоб явніше показати, що цей файл — мережева межа (network boundary) застосунку. Ключова технічна відмінність, яку легко пропустити: proxy.ts за замовчуванням виконується на Node.js runtime, а не на Edge Runtime, як було з класичним middleware — це прямо суперечить старому припущенню "middleware = завжди Edge" із категорій C/D і саме тому варто перевіряти, чи співрозмовник знає про цю зміну, а не повторює застарілу модель. Файл middleware.ts усе ще працює (позначений deprecated) для випадків, де потрібен саме Edge Runtime.

50ПросунутеЯкі нові API кешування з'явились у Next.js 16?

Три різні інструменти для трьох різних сценаріїв: revalidateTag(tag, profile) тепер вимагає другим аргументом профіль cacheLife (наприклад, 'max', 'hours') і дає stale-while-revalidate поведінку — підходить для контенту, що толерує невелику затримку в оновленні. Новий updateTag(tag) — лише для Server Actions, дає семантику "read-your-writes": миттєво читає свіжі дані одразу в тому самому запиті, де відбулась зміна (ідеально для форм, де користувач має одразу побачити результат своєї дії). Новий refresh() — теж лише для Server Actions, оновлює некешовані дані, не чіпаючи кеш узагалі (наприклад, лічильник сповіщень в шапці сайту, який і так не кешувався).

51БазаЩо таке стабільна підтримка React Compiler у Next.js 16?

Вбудована, тепер уже стабільна (не experimental) інтеграція з React Compiler — інструментом, що автоматично мемоізує компоненти під час білду, зменшуючи зайві ре-рендери без ручного розставляння useMemo/useCallback/ React.memo по всьому коду. Вмикається явно (reactCompiler: true в конфігу) і поки не увімкнений за замовчуванням — команда Next.js ще збирає дані про вплив на час білду в різних типах застосунків.

52БазаЩо таке Next.js DevTools MCP?

Нова інтеграція протоколу MCP (Model Context Protocol) — того самого, що розібраний у туторіалі 10, тема 3. Вона дає AI-агентам (наприклад, помічнику всередині IDE) прямий контекстний доступ до внутрішньої логіки застосунку під час дебагу: розуміння маршрутизації/кешування/рендерингу конкретного проєкту, об'єднані логи браузера й сервера в одному місці, автоматичний доступ до детальних стек-трейсів помилок без ручного копіювання, і контекстне розуміння, яка сторінка зараз активна. Практичний наслідок — AI-асистент може діагностувати помилку чи пояснити поведінку рендерингу конкретно цього застосунку, а не лише загальної документації Next.js.
