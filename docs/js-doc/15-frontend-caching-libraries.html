React caching

Перше, з чого варто почати: React сам по собі має лише один справжній механізм кешування — і це не useMemo.

React.memo, useMemo та useCallback уже детально розібрані в туторіалі 5 — тут лише ключовий висновок, який варто вміти сформулювати одним реченням на співбесіді:

⚠️
useMemo — це не кеш даних, а мемоізація результату обчислення. Значення живе рівно стільки, скільки живе конкретний екземпляр компонента — розмонтували компонент, значення зникло без сліду. Жодного поняття "застарілості", жодного request-дедуплікування, жодного спільного доступу з іншого компонента. Це принципово інша річ, ніж бібліотеки кешування даних (TanStack Query, SWR, Apollo) нижче на цій сторінці — ті кешують дані ЗА МЕЖАМИ життєвого циклу одного компонента, іноді роками (доки явно не інвалідовані), і діляться цим кешем між будь-якою кількістю компонентів, які попросять ті самі дані.

React.cache() (з пакета react, не плутати з useMemo) — механізм для дедуплікації/мемоізації викликів функцій (найчастіше функцій завантаження даних) у межах одного серверного рендер-проходу. Активно використовується React Server Components: якщо кілька різних компонентів у дереві незалежно один від одного викликають ту саму обгорнуту в cache() функцію з тими самими аргументами під час рендеру одного запиту — реально виконається лише один виклик, решта отримають те саме мемоізоване значення. Життєвий цикл — рівно один рендер-прохід сервера, не довше (це і є "Request Memoization", перший із чотирьох шарів кешу Next.js — розділ 2 нижче).

React.cache() — дедуплікація в межах одного рендеру
import { cache } from 'react';

const getUser = cache(async (id) => {
  console.log('реальний запит до БД для', id); // виконається лише один раз на id
  return db.user.findUnique({ where: { id } });
});

// Компонент A і компонент B обидва викликають getUser(42)
// під час рендеру ОДНІЄЇ сторінки — реальний запит піде лише один раз.

use() — хук, що вміє читати проміс або контекст прямо під час рендеру. Стосовно кешування це працює так: якщо кілька компонентів отримують ПОСИЛАННЯ на той самий проміс (наприклад, створений одним fetch вище по дереву й переданий як пропс), use() дозволяє кожному з них "дочекатись" саме цього спільного проміса (інтегруючись із Suspense для показу лоадера, поки він не резолвиться) — замість того, щоб кожен компонент незалежно запускав свій власний запит. Це не сам механізм кешу, а спосіб кількох компонентам безпечно поділити один уже наявний результат, включно з тим, що прийшов із кешованого джерела.

🎯
Коли мемоізація допомагає, а коли шкодить: допомагає, коли обчислення справді дороге (сортування/фільтрація великого масиву, важка похідна структура) або коли потрібна стабільність посилання, щоб не зламати React.memo дочірнього компонента (детальніше — туторіал 5). Шкодить, коли обчислення дешеве: сама мемоізація (порівняння залежностей, зберігання кешованого значення в пам'яті) коштує реальних CPU-циклів і пам'яті — для тривіального обчислення (наприклад, a + b) накладні витрати на сам useMemo можуть перевищити вартість просто порахувати це заново на кожен рендер.

Next.js caching: чотири шари

Стратегії рендерингу (SSR/SSG/ISR) і зміна поведінки fetch-кешування в Next.js 15 уже розібрані в туторіалі 6 та туторіалі 7. Тут — те, чого там ще немає: як саме кеш Next.js влаштований зсередини, чотирма окремими шарами, кожен зі своїм місцем життя й способом інвалідації.

ШарДе живеЩо інвалідує
Request MemoizationПам'ять сервера, один рендер-прохідАвтоматично — закінчується разом із запитом
Data CacheСервер, персистентно (між запитами й деплоями)revalidatePath, revalidateTag, час (revalidate: N)
Full Route CacheСервер, персистентно (з білду або ISR)Новий білд, on-demand ISR-регенерація, ті самі revalidate*
Router CacheКлієнт, пам'ять браузера, одна сесіяХардовий рефреш, явний router.refresh(), спливання таймера

fetch у Server Component напряму керує шаром 2 (Data Cache) через свої опції: { cache: 'force-cache' } — кешувати безстроково, поки не інвалідовано вручну; { cache: 'no-store' } — ніколи не кешувати, завжди свіжий запит; { next: { revalidate: 60 } } — ISR-подібна поведінка за часом, ідентична за духом до вже розібраного в тексті "протухання" в туторіалі 7.

теґований fetch + точкова інвалідація
// у Server Component
const res = await fetch('https://api.example.com/products', {
  next: { tags: ['products'] },
});

// пізніше — у Server Action чи Route Handler, після зміни товару
import { revalidateTag } from 'next/cache';

export async function updateProduct(data) {
  await db.product.update(data);
  revalidateTag('products'); // бʼє саме Data Cache + Full Route Cache для цього тега
}

revalidatePath('/products') робить те саме, але за URL-шляхом, а не за довільним тегом — зручно, коли простіше сказати "оновити ось цю сторінку", ніж заздалегідь продумувати систему тегів. Статичний рендеринг маршруту залучає всі чотири шари; повністю динамічний маршрут (наприклад, той, що читає cookies() чи інші per-request джерела) пропускає шар 3 (Full Route Cache) — його HTML у принципі не можна закешувати наперед, бо він унікальний для кожного запиту. Найновіша модель кешування поверх цього ж фундаменту ("use cache", Cache Components) розібрана в туторіалі 7, категорія F.

TanStack Query (React Query)

Одна з найважливіших тем цього списку. Ментальна модель: TanStack Query — не заміна Redux/Zustand, а спеціалізований кеш саме для server state (даних, якими володіє сервер і які можуть застаріти) — на відміну від client state (даних, якими повністю володієте ви самі), для якого потрібен зовсім інший інструментарій.

queryKey — масив, що унікально ідентифікує запит у кеші, наприклад ['todo', todoId]. Включення змінної в ключ — це і є механізм "залежних" записів кешу на параметр: різні todoId означають різні, незалежні одна від одної записи кешу.

🎯
staleTime vs gcTime — ключове питання цієї теми. staleTime — як довго дані вважаються свіжими після отримання: поки цей час не сплив, повторний рендер/монтування компонента отримує дані з кешу МИТТЄВО, без жодного фонового рефетчу. gcTime (раніше cacheTime) — як довго невикористаний запис кешу (жоден активний компонент його не запитує) лишається в пам'яті, перш ніж його остаточно приберуть. Приклад: staleTime: 0, gcTime: 5 * 60_000 означає — дані рефетчаться при кожному новому монтуванні (бо вважаються застарілими одразу), але сам об'єкт даних переживе 5 хвилин без жодного активного спостерігача, перш ніж його видалять з пам'яті повністю.
базовий useQuery з обома опціями
const { data } = useQuery({
  queryKey: ['todo', todoId],
  queryFn: () => fetchTodo(todoId),
  staleTime: 60_000,      // свіже 1 хвилину — без фонового рефетчу
  gcTime: 5 * 60_000,     // а якщо ніхто не питає — видалити з пам'яті через 5 хв
});

invalidateQueries(['todos']) — позначає збіжні за ключем запити застарілими й одразу тригерить рефетч, якщо на них зараз хтось активно підписаний. refetch() — імперативний ручний рефетч без очікування на природне протухання. refetchOnWindowFocus (рефетч, коли користувач повертається на вкладку — типово для даних, що часто змінюються ззовні), refetchOnMount (чи рефетчити при новому монтуванні компонента, навіть якщо дані технічно ще "свіжі"), refetchInterval (поллінг за таймером — для живих дашбордів без WebSocket).

initialData vs placeholderData — часто плутана пара. initialData трактується як РЕАЛЬНІ отримані дані: одразу потрапляє в кеш і підпорядковується звичайному staleTime. placeholderData — явно тимчасові дані лише для UI, поки триває справжній запит: НІКОЛИ не записуються в кеш і зникають, щойно приходить справжня відповідь.

оптимістичне оновлення з відкатом
const mutation = useMutation({
  mutationFn: updateTodo,
  onMutate: async (newTodo) => {
    await queryClient.cancelQueries({ queryKey: ['todo', newTodo.id] });
    const previous = queryClient.getQueryData(['todo', newTodo.id]);
    queryClient.setQueryData(['todo', newTodo.id], newTodo); // оновили одразу
    return { previous }; // контекст для відкату
  },
  onError: (err, newTodo, context) => {
    queryClient.setQueryData(['todo', newTodo.id], context.previous); // відкат
  },
  onSettled: (newTodo) => {
    queryClient.invalidateQueries({ queryKey: ['todo', newTodo.id] }); // звірка з сервером
  },
});

Інші важливі можливості: prefetching (queryClient.prefetchQuery(...) — наповнити кеш ще ДО монтування компонента, наприклад по ховеру над посиланням); dependent queries (enabled: !!userId — запит запускається лише коли попередня умова виконана); infinite queries (useInfiniteQuery із getNextPageParam — курсорна пагінація/безкінечний скрол); SSR/гідратація (dehydrate серіалізує наповнений на сервері кеш у початковий HTML-payload, клієнтський QueryClient потім hydrate-иться цими даними й НЕ робить зайвий рефетч того, що вже отримав); persisted query cache — збереження кешу в localStorage/IndexedDB через persister-плагін, щоб кеш пережив повне перезавантаження сторінки.

SWR

Назва — це і є концепція: stale-while-revalidate — віддати закешовані дані миттєво, паралельно перевалідувати їх у фоні, оновити UI, коли прийде свіжа відповідь.

useSWR базовий приклад
const { data, error, isLoading, mutate } = useSWR('/api/user', fetcher);

SWR тримає один глобальний кеш (по суті — спільна мапа, ключована першим аргументом useSWR): кілька компонентів, що викликають useSWR з ОДНАКОВИМ ключем, автоматично діляться й дедуплікують запит, без жодного зусилля з вашого боку — приємний контраст до ручного підняття fetch-стану нагору по дереву.

mutate — один універсальний інструмент SWR одразу для ручного оновлення кешу, перевалідації й оптимістичних апдейтів (де в TanStack Query за це відповідають три різні речі — setQueryData/invalidateQueries/callbacks мутації, тут — одна функція з різними аргументами). dedupingInterval — запити з тим самим ключем у межах цього вікна злипаються в один. refreshInterval — поллінг. revalidateOnFocus/revalidateOnReconnect — той самий принцип, що й refetchOnWindowFocus у TanStack Query, лише інша назва.

оптимістичне оновлення через mutate
mutate('/api/user', { ...user, name: newName }, {
  optimisticData: { ...user, name: newName },
  rollbackOnError: true,
});

SSR-підтримка — концептуально просто: сервер передає fallbackData, яке useSWR показує одразу, поки (за потреби) не довалідує дані на клієнті.

GraphQL caching: Apollo Client

Найчастіше питане GraphQL-питання взагалі. InMemoryCache — не просто "кеш відповідей", а нормалізований кеш (повний розбір нормалізації — розділ 10 нижче): замість зберігати цілі відповіді запитів як непрозорі блоби, Apollo розкладає кожен об'єкт із ID в один плаский довідник, ключований Cache ID — зазвичай __typename + id (наприклад, User:1). Тому той самий об'єкт, отриманий двома зовсім різними запитами, оновлюється в ОДНОМУ місці — і обидва запити одразу бачать зміну.

__typename — Apollo додає це поле в кожен запит автоматично, щоб мати з чого рахувати Cache ID. keyFields (в typePolicies) — перевизначає, які поля формують ID сутності, для типів без звичайного id. typePolicies — загальна конфігурація кешу per-тип, включно з кастомними read/merge для окремого поля (наприклад, власна логіка об'єднання сторінок пагінації замість дефолтної заміни).

Ручне керування кешем: writeQuery/readQuery й writeFragment/readFragment — записати/прочитати дані за формою GraphQL-документа, коли Apollo сам не може вивести оновлення після мутації; cache.modify — точково змінити конкретні поля вже закешованої сутності без повного документа; cache.evict + cache.gc() — видалити сутність, потім прибрати сміттям усе, що було досяжне лише через неї; refetchQueries — "груба сила, зате надійно": попросити мутацію перезапитати конкретні запити після себе; update — callback у мутації з повним контролем над записом у кеш одразу після відповіді сервера; optimisticResponse — той самий принцип оптимістичного оновлення, що й у TanStack Query/SWR, у форматі Apollo.

🎯
cache-first vs cache-and-network — друга ключова пара цієї теми. cache-first (дефолт): якщо в кеші взагалі є дані — використати їх, мережевий запит лише при справжньому промаху ("миттєво, але потенційно застаріло"). cache-and-network: показати кешовані дані одразу І одночасно завжди відправити мережевий запит, щоб оновити їх ("миттєво І врешті свіжо").
Fetch PolicyПоведінка
cache-firstКеш, якщо є хоч щось; мережа лише при промаху
cache-and-networkКеш одразу + завжди мережевий запит паралельно
network-onlyЗавжди мережа, але результат все одно пишеться в кеш
no-cacheЗавжди мережа, і НЕ пишеться в кеш узагалі
cache-onlyНіколи мережа — помилка, якщо ще не закешовано
standbyЯк cache-first, але не тригерить мережевий запит при монтуванні
🟣

Relay

Концептуальний рівень: теж нормалізований GraphQL-кеш (Relay Store), але побудований довкола двох ідей, яких немає в Apollo в такому вигляді.

Fragments — кожен компонент декларує рівно ті поля, які йому потрібні, через власний GraphQL-фрагмент; Relay-компілятор статично об'єднує всі фрагменти дерева в один запит на етапі білду. Data masking — компонент фізично не має доступу до жодних полів, окрім задекларованих у ЙОГО ВЛАСНОМУ фрагменті, навіть якщо батьківський запит отримав більше — це унеможливлює випадкову залежність від даних, які "просто випадково" завантажив хтось інший.

Connections — стандартизована Relay-специфікація курсорної пагінації (edges/node/pageInfo). Garbage collection непотрібних записів стору й оптимістичні оновлення — концептуально ті самі ідеї, що й в Apollo.

ApolloRelayTanStack Query

Лише для GraphQLТакТакНі (будь-який fetcher)

Головний компроміс саме тут: нормалізація дає безкоштовну узгодженість між запитами ціною складнішої ментальної моделі; простіший per-key кеш TanStack Query легший для розуміння, але не оновлює одну сутність автоматично всюди, де вона згадується в різних запитах.

Інші GraphQL-клієнти

Достатньо на рівні концепцій: urql і graphql-request — легші альтернативи Apollo/Relay.

Ключова вісь розуміння: нормалізований кеш (Apollo/Relay — узгодженість на рівні сутності між усіма запитами) проти document cache (дефолтний режим urql — кешує цілі результати запиту, ключовані запитом+змінними; простіше й дешевше, але оновлення однієї сутності НЕ поширюється автоматично на всі запити, що випадково теж її містять).

🟣

Redux caching / RTK Query

Сам стор Redux — уже форма клієнтського кешу для будь-яких даних, які ви вирішили в ньому тримати. RTK Query — це вже спеціалізоване рішення Redux Toolkit саме для server-state кешування, пряма паралель до TanStack Query, але інтегроване в Redux store/DevTools.

→

providesTags/invalidatesTags — тег-орієнтована система інвалідації RTK Query: запит декларує, які теги "надає" його результат, мутація декларує, які теги вона "інвалідує" — RTK Query автоматично рефетчить будь-який активний запит, чиї теги збіглися.

providesTags / invalidatesTags
const api = createApi({
  endpoints: (builder) => ({
    getTodos: builder.query({
      query: () => '/todos',
      providesTags: ['Todo'],
    }),
    addTodo: builder.mutation({
      query: (body) => ({ url: '/todos', method: 'POST', body }),
      invalidatesTags: ['Todo'], // автоматично рефетчить getTodos
    }),
  }),
});

Кеш ділиться автоматично між усіма компонентами, що використовують той самий query-хук (той самий принцип, що й у TanStack Query/SWR). Далі — поллінг, prefetching, оптимістичні оновлення (той самий підхід, що й вище) та персистентність кешу через redux-persist, концептуально ідентична persisted query cache TanStack Query.

🟣

Zustand caching

Middleware persist автоматично серіалізує стор у localStorage/sessionStorage і регідратує його при завантаженні. У SSR-контекстах є реальна пастка з таймінгом: персистований клієнтський стан фізично недоступний під час серверного рендеру (сервер не бачить localStorage користувача), тому перший клієнтський рендер до завершення регідратації може на мить відрізнятись від серверного HTML.

⚠️
Ключове розмежування: Zustand — це загальний state management, а НЕ спеціалізований server-state кеш на кшталт TanStack Query/SWR/Apollo. У нього немає вбудованого поняття "ці дані можуть застаріти", немає дедуплікування запитів, немає автоматичної фонової перевалідації. Якщо тримати серверні дані в Zustand — усе це доведеться будувати вручну самому, що й пояснює, чому спеціалізовані бібліотеки кешування даних узагалі існують як окрема категорія.
🟣

Нормалізація даних

Особливо релевантно для GraphQL — це те, на чому побудований InMemoryCache Apollo (розділ 5) і Relay Store (розділ 6).

Замість того, щоб дублювати дані автора всередині кожного поста, що на нього посилається, нормалізований кеш зберігає кожну сутність один раз у плаский довідник, а пости тримають лише ПОСИЛАННЯ на автора:

денормалізовано (наївно) → нормалізовано (кеш)
// Денормалізовано — автор продубльований у кожному пості
{
  posts: [
    { id: 10, title: 'A', author: { id: 1, name: 'Ольга' } },
    { id: 11, title: 'B', author: { id: 1, name: 'Ольга' } }, // той самий автор, копія
  ],
}

// Нормалізовано — так це реально лежить у InMemoryCache
{
  'User:1':  { id: 1, name: 'Ольга' },
  'Post:10': { id: 10, title: 'A', author: { __ref: 'User:1' } },
  'Post:11': { id: 11, title: 'B', author: { __ref: 'User:1' } },
}

Ідентичність сутності — те, що робить два об'єкти "тим самим" записом у кеші (найчастіше __typename + id). Головний виграш: онови User:1 один раз — і обидва пости (Post:10, Post:11), що на нього посилаються, автоматично побачать зміну, без жодного явного рефетчу кожного з них. Денормалізація — зворотна операція, яку кеш робить прозоро для вас при читанні: відновлює вкладену форму, яку насправді запитав компонент, збираючи її на льоту з плаского сховища за посиланнями.
