Контроль ре-рендерів на практиці

React.memo порівнює нові пропси зі старими по посиланню (для об'єктів і функцій) і пропускає ре-рендер, якщо всі пропси рівні. Проблема в тому, що в JavaScript функція, оголошена всередині компонента, отримує нове посилання на кожен рендер — тож навіть обгорнутий у memo дочірній компонент все одно перерендериться, якщо йому передають такий callback.

до — callback ламає memo
function Parent() {
  const [count, setCount] = useState(0);

  // нова функція на КОЖЕН рендер Parent — навіть якщо логіка та сама
  const handleClick = () => console.log('click');

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      {/* перерендериться щоразу, попри React.memo */}
      <ExpensiveChild onClick={handleClick} />
    </div>
  );
}

const ExpensiveChild = React.memo(function ExpensiveChild({ onClick }) {
  console.log('render ExpensiveChild');
  return <button onClick={onClick}>Дія</button>;
});
після — useCallback фіксує посилання
function Parent() {
  const [count, setCount] = useState(0);

  // те саме посилання між рендерами, доки залежності не зміняться
  const handleClick = useCallback(() => console.log('click'), []);

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      {/* тепер НЕ перерендериться при зміні count */}
      <ExpensiveChild onClick={handleClick} />
    </div>
  );
}

useMemo працює за тим самим принципом, але для обчисленого значення, а не функції: кешує результат обчислення між рендерами, доки залежності не зміняться, замість того щоб рахувати наново щоразу.

⚠️
Типова помилка: обгортати в useMemo/useCallback буквально все "про всяк випадок". Сама мемоізація має вартість (порівняння залежностей на кожен рендер) — виправдана вона там, де дочірній компонент дійсно важкий або де без неї реально виникає видимий зайвий ре-рендер, а не за замовчуванням скрізь.

Правила хуків і кастомні хуки

React асоціює стан кожного виклику useState/useEffect з конкретним компонентом не за іменем, а за порядком виклику під час рендеру — це внутрішня структура даних, схожа на пронумерований список. Якщо хук викликати умовно (всередині if) або в циклі, порядок викликів може змінитись між рендерами — і React переплутає, якому саме шматку стану відповідає який виклик. Тому правило "хуки лише на верхньому рівні компонента, завжди в однаковому порядку" — не стилістична умовність, а прямий наслідок того, як усередині влаштований механізм.

кастомний хук usePrevious
function usePrevious(value) {
  const ref = useRef();

  useEffect(() => {
    // записуємо значення ПІСЛЯ рендеру —
    // тому під час поточного рендеру ref.current ще містить попереднє
    ref.current = value;
  }, [value]);

  return ref.current;
}

function Counter() {
  const [count, setCount] = useState(0);
  const prevCount = usePrevious(count);

  return (
    <div>
      <p>Зараз: {count}, було: {prevCount ?? '—'}</p>
      <button onClick={() => setCount(c => c + 1)}>+1</button>
    </div>
  );
}

Redux vs Flux, коли Redux виправданий

Flux — це загальний архітектурний патерн Facebook (2014): односпрямований потік даних (action → dispatcher → store → view), без конкретної реалізації "з коробки" і з можливістю кількох сторів. Redux — це одна конкретна, дуже опінійована реалізація ідеї Flux: рівно один store на застосунок, оновлення стану лише через чисті редʼюсери (без побічних ефектів, новий стан замість мутації), і сувора незмінність (immutability) даних.

Головне практичне питання не "Redux чи Flux" (Redux вже виграв цю дискусію років тому), а чи потрібен Redux взагалі. Для застосунків, де більшість стану — це дані з сервера (списки, деталі сутностей), інструмент на кшталt React Query вже вирішує кешування, інвалідацію й синхронізацію без жодного глобального стору. Redux виправданий там, де є справді складний клієнтський стан, не похідний напряму від сервера: багатокрокові форми, стан складного редактора, взаємодія багатьох непов'язаних компонентів з одними й тими самими даними.

Чи можна працювати з Redux на сервері? Так, і це реальне питання на співбесіді: типовий патерн — створити й наповнити екземпляр store саме під час серверного завантаження даних (наприклад, усередині getServerSideProps, або в App Router — в еквівалентній серверній точці завантаження даних), серіалізувати його стан у початковий HTML-payload, який іде клієнту, а тоді на клієнті створити новий екземпляр store і ініціалізувати (гідратувати) його саме цим серіалізованим станом. Критично: ніколи не ділити один мутабельний екземпляр store між різними запитами на сервері — інакше стан одного користувача просочиться в запит іншого, класична й серйозна помилка. Загальний механізм гідратації (чому взагалі потрібне це "перестворення" стану на клієнті, а не пряме використання серверного) детально розібраний у туторіалі 10, тема 4.

Готові рішення для великих таблиць/гридів "з коробки"

Найконкретніший виявлений розрив у цій категорії: досвід із власноруч побудованою віртуалізацією (наприклад, поверх react-window) є, але легко недооцінити, скільки готового вже дають спеціалізовані grid-бібліотеки на кшталт AG Grid чи TanStack Table одразу "з коробки" — і скільки додаткової роботи означає доробляти те саме вручну поверх голої віртуалізації списку.

Доступність (a11y) у виробничій якості компонентів

Базова обізнаність про доступність зазвичай уже є — прогалина не в знанні, а в послідовному застосуванні в реальній верстці, особливо в інтерактивних елементах на кшталт модалок і сайдбарів.

до — модалка без a11y
function Modal({ onClose, children }) {
  return (
    <div className="modal-overlay">
      <div className="modal">
        <button className="close-icon" onClick={onClose}>
          <XIcon />
        </button>
        {children}
      </div>
    </div>
  );
}
після — role, aria, Esc, focus trap
function Modal({ onClose, children }) {
  const ref = useRef(null);

  useEffect(() => {
    const onKeyDown = (e) => { if (e.key === 'Escape') onClose(); };
    document.addEventListener('keydown', onKeyDown);
    ref.current?.focus(); // фокус усередину модалки при відкритті
    return () => document.removeEventListener('keydown', onKeyDown);
  }, [onClose]);

  return (
    <div className="modal-overlay">
      <div
        className="modal"
        role="dialog"
        aria-modal="true"
        aria-label="Деталі доставки"
        ref={ref}
        tabIndex={-1}
      >
        <button className="close-icon" onClick={onClose} aria-label="Закрити">
          <XIcon />
        </button>
        {children}
      </div>
    </div>
  );
}

Повноцінний focus trap (фокус не повинен виходити за межі модалки по Tab) вручну писати не обов'язково — саме тут стає в пригоді тема 7: headless-бібліотеки на кшталт Radix уже реалізують focus trap, керування фокусом і всю ARIA-семантику всередині своїх примітивів (Dialog, Popover тощо), якщо ними користуватись повністю, а не лише їхньою стилізованою обгорткою.

Компонування замість монолітних компонентів

Типовий шлях, яким компонент стає монолітним: спершу маленька фіча, потім до неї додають ще один стан, ще один умовний рендер, ще один обробник — і за кілька ітерацій один файл відповідає за всю логіку сторінки одразу, замість того щоб бути composition кількох дрібних частин.

до — один компонент робить усе
function DeliveryPanel({ delivery }) {
  const [isEditing, setIsEditing] = useState(false);
  const [isGenerating, setIsGenerating] = useState(false);
  // ... ще 6 useState і 200 рядків JSX з умовами всередині одного return
}
після — композиція дрібних частин
function DeliveryPanel({ delivery }) {
  return (
    <Card>
      <DeliveryHeader delivery={delivery} />
      <DeliveryStatusBadge status={delivery.status} />
      {delivery.status === 'generating'
        ? <GeneratingOverlay />
        : <DeliveryStopsList stops={delivery.stops} />}
    </Card>
  );
}

Друга частина цієї теми — повноцінне використання вже підключених headless-бібліотек (Radix, а поверх них — shadcn). Типова половинчаста практика: взяти стилізовану обгортку shadcn заради готового вигляду, але не використовувати сам примітив Radix під нею для складної взаємодії (наприклад, зібрати власний сайдбар на голих div-ах поруч із уже підключеним Dialog з Radix) — і тоді втрачається саме те, заради чого ці бібліотеки взагалі підключали: керування фокусом, ARIA-семантика, клавіатурна навігація "з коробки" з теми 6.

Pixel-perfect і продакшн-рівень UI-деталей

Це найчастіше повторюваний конкретний коментар взагалі в основі цього довідника — і оцінюється він як окрема вісь, незалежна від функціональної правильності коду. Код може бути архітектурно чистим, типізованим, добре структурованим — і водночас отримати зауваження щодо UI, якщо інтерфейс не доведений до кінця у видимих дрібницях.

🎯
Чому це окрема вісь: функціональна правильність відповідає на питання "чи працює це", а pixel-perfect — на питання "чи відчувається це як завершений продукт". Для ролей, де очікується довести UI до продакшн-ідеалу з першої ітерації (а не "зробимо, потім поправимо"), другий критерій оцінюється так само суворо, як перший.

Практичний чекліст, який варто прогнати перед тим, як вважати компонент готовим:

  • Курсор: cursor:pointer є на всьому клікабельному — і немає на тому, що лише виглядає клікабельним (картка з фоном-заливкою, за якою насправді нічого не відбувається).
  • Стани фокуса (:focus-visible) видимі й не зняті випадковим outline:none без заміни.
  • Hover-переходи плавні (transition), а не миттєва зміна кольору.
  • Порожній стан, стан завантаження й стан помилки продумані так само, як "щасливий шлях" — а не залишені як типовий рендер порожнього списку.

Клас vs функціональний vs pure-компонент, нові версії React

Класовий компонент та еквівалентний функціональний із хуками поводяться однаково зовні, але механізм усередині різний: клас зберігає стан у екземплярі (this.state) і використовує lifecycle-методи, функціональний — у внутрішньому "слоті", прив'язаному до порядку виклику хуків (звідси й правило хуків із теми 3). PureComponent / React.memo додають до цього поверхневе (shallow) порівняння пропсів, щоб пропускати непотрібні ре-рендери.

Останні мажорні версії React (конкурентний рендеринг, автоматичний батчинг оновлень стану поза обробниками подій, нові хуки на кшталт useTransition/useDeferredValue) змінюють деякі базові припущення — варто перевірити, що ваша ментальна модель не застигла на рівні React 16-17, особливо щодо того, коли саме й скільки разів React ре-рендерить компонент у відповідь на кілька оновлень стану підряд.

🟣

ref і forwardRef

ref — це "аварійний вихід" із декларативної моделі React: спосіб імперативно дістатись реального DOM-вузла чи екземпляра компонента в обхід звичайного потоку "пропси → рендер". Типові законні застосування: програмно поставити фокус на інпут, виміряти реальний розмір/позицію елемента, підключити стороннню бібліотеку, якій потрібен саме реальний DOM-вузол (наприклад, карта чи графік). Для функціональних компонентів ref-об'єкт створюється хуком useRef і не викликає ре-рендер при зміні свого .current — на відміну від useState.

Важливий нюанс, який часто плутають: ref — це не звичайний проп. React обробляє його спеціально й не передає в об'єкт props компонента разом з рештою пропсів — тому якщо просто написати function Input(props) без forwardRef і очікувати props.ref усередині — там нічого не буде. forwardRef — явний механізм, який "підписує" компонент на отримання рефа від батька і дозволяє передати (forward) його далі — на внутрішній DOM-вузол чи ще глибше.

forwardRef — прокидання рефа на внутрішній input
const Input = React.forwardRef(function Input(props, ref) {
  return <input ref={ref} className="styled-input" {...props} />;
});

function Form() {
  const inputRef = useRef(null);

  const focusInput = () => inputRef.current?.focus();

  return (
    <>
      <Input ref={inputRef} placeholder="Ім'я" />
      <button onClick={focusInput}>Фокус на поле</button>
    </>
  );
}

Без forwardRef рядок <Input ref={inputRef} /> просто мовчки не спрацював би для функціонального компонента — inputRef.current лишився б null.

Virtual DOM — навіщо його взагалі придумали

Пряма робота з реальним DOM порівняно дорога: кожна мутація може викликати перерахунок layout і перемальовування (туторіал 5, тема "Reflow vs repaint"). Virtual DOM — легке представлення бажаного вигляду інтерфейсу як звичайних JS-об'єктів у пам'яті, яке React може дешево створити заново на кожен рендер і звірити (diff) з попередньою версією, а тоді застосувати до реального DOM лише мінімальний набір змін, які дійсно потрібні (процес називається reconciliation).

Тобто ідея не в тому, що Virtual DOM сам по собі "швидший за DOM" (порівняння двох дерев об'єктів — теж робота, не безкоштовна) — а в тому, що він дозволяє писати код декларативно ("ось як має виглядати UI зараз"), водночас гарантуючи, що дорога частина (реальні мутації DOM) виконується пакетно й мінімально, а не наївно при кожній окремій зміні стану.

🔴🟣

React Fiber і synthetic events

Fiber — внутрішній рушій узгодження (reconciliation), на якому React працює з React 16. Він представляє дерево компонентів не як просте рекурсивне дерево викликів, а як зв'язану структуру "fiber"-вузлів, що дозволяє React виконувати рендер інкрементально й перервно: поставити рендер на паузу, продовжити пізніше або взагалі скасувати його, щоб терміново обробити щось важливіше (наприклад, ввід користувача). Це низькорівневий фундамент, на якому побудовані конкурентний рендеринг і Suspense — на співбесіді достатньо рівня "знаю, що це і навіщо", а не повна внутрішня механіка Fiber.

Synthetic events. React обгортає нативні DOM-події у власний SyntheticEvent, нормалізований між браузерами — той самий код обробника поводиться однаково, навіть якщо нативні API браузерів трохи різняться. Технічно React підключає один слухач на корінь дерева (event delegation) замість окремого реального слухача на кожен елемент, і сам диспетчеризує синтетичні події до ваших обробників звідти — це і оптимізація продуктивності (менше реальних listener-ів), і причина, чому в старіших версіях React синтетичні події перевикористовувались (pooling) — об'єкт події "спорожнявся" одразу після обробника (тому event.persist() існував як обхідний шлях); це історична деталь, а не те, на чому варто зациклюватись при підготовці.

🟣

key у списках

key — це те, за чим алгоритм узгодження зіставляє елементи списку між рендерами: чи це той самий елемент (просто переміщений/оновлений), чи справді новий/ видалений. Без стабільного key — а особливо якщо як key використати індекс масиву у списку, що може змінювати порядок чи фільтруватись — React може неправильно зіставити стан між елементами списку або виконати зайву роботу з DOM.

⚠️
Класична помилка index-as-key: список текстових полів для введення, кожне зі своїм локальним станом. Якщо видалити елемент з середини списку, а key — це індекс, усі елементи ПІСЛЯ видаленого зсуваються на позицію вище — і React, бачачи "той самий" key на новій позиції, зіставляє його зі старим DOM-вузлом і залишає там уведений текст. Результат: зникає вміст не того поля, яке видалили, а сусіднього — класична помилка, яку важко одразу пов'язати з причиною. Правильний key — стабільний ідентифікатор самих даних (наприклад, id запису), не його позиція в масиві.
🟣

useEffect vs useLayoutEffect

Обидва запускають побічний ефект після рендеру, різниця — у моменті відносно малювання екрана браузером. useEffect виконується асинхронно, вже після того, як браузер намалював оновлений екран — не блокує візуальне оновлення. useLayoutEffect виконується синхронно, одразу після мутацій DOM, але до того, як браузер намалює кадр — тобто може заблокувати малювання, якщо робить важку роботу.

Коли реально потрібен саме useLayoutEffect: якщо потрібно прочитати властивість layout (виміряний розмір/позицію елемента) і одразу синхронно внести зміну в DOM на основі цього виміру — до того, як користувач встигне побачити візуальний "стрибок" проміжного неправильного стану (класичний приклад — позиціювання тултипа за результатами вимірювання власного розміру). У решті випадків — useEffect за замовчуванням; useLayoutEffect — точковий інструмент саме для цього одного сценарію, а не "швидший" аналог useEffect.

Шпаргалка: усі хуки React 19.2

Повний список вбудованих хуків актуальної версії (React 19.2), згрупований за призначенням. Позначка 19 / 19.2 — у якій версії хук з'явився. Усі, крім use, підкоряються правилам хуків: лише на верхньому рівні компонента чи кастомного хука, без умов і циклів.

ХукДля чогоОсобливість / пастка
Стан
useState
Локальний стан компонентаОновлення асинхронне й батчиться. Якщо новий стан залежить від попереднього, передавайте функцію: setN(n => n + 1). Порівняння через Object.is, тому мутований об'єкт ре-рендер не викличе

Кейс: Лічильник кошика, відкрита/закрита модалка, значення поля вводу: будь-яке значення, зміна якого має оновити UI.

Cart.jsx
function Cart() {
  const [count, setCount] = useState(0);
  // лінива ініціалізація: функція виконається лише на першому рендері
  const [filter, setFilter] = useState(() => localStorage.getItem('filter') ?? 'all');
  const [items, setItems] = useState([]);

  // +1: обидва виклики бачать той самий count
  const wrong = () => { setCount(count + 1); setCount(count + 1); };
  // +2: кожен виклик отримує свіжий c
  const right = () => { setCount(c => c + 1); setCount(c => c + 1); };

  // новий масив; prev.push(item) ре-рендер НЕ викличе
  const addItem = item => setItems(prev => [...prev, item]);
}

Пастки: одразу після setCount змінна count ще стара, бо нове значення з'явиться лише в наступному рендері. useState(expensive()) викликає expensive на кожному рендері, а useState(() => expensive()) лише один раз.

useReducer
Складний стан із багатьма переходами: dispatch(action) → reducer(state, action)Логіка оновлень винесена в чисту функцію, яку легко тестувати. dispatch стабільний між рендерами, тож його можна спокійно передавати вниз

Кейс: Стан із кількома пов'язаними полями й чіткими діями: кошик, багатокрокова форма, редактор маршруту. Також коли наступний стан залежить від попереднього складним чином.

cartReducer.jsx
function reducer(state, action) {
  switch (action.type) {
    case 'added':   return { ...state, items: [...state.items, action.item] };
    case 'removed': return { ...state, items: state.items.filter(i => i.id !== action.id) };
    case 'cleared': return { ...state, items: [] };
    default: throw new Error(`Unknown action: ${action.type}`);
  }
}

function Cart() {
  const [state, dispatch] = useReducer(reducer, { items: [] });
  return (
    <button onClick={() => dispatch({ type: 'cleared' })}>
      Очистити ({state.items.length})
    </button>
  );
}

Reducer — чиста функція, тож його тестують без React: expect(reducer(s, {type:'cleared'}).items).toEqual([]). dispatch стабільний, тому його можна передавати в memo-дітей і не додавати в deps.

Контекст
useContext
Прочитати значення найближчого <Context>-провайдера без прокидання пропсівБудь-яка зміна value ре-рендерить усіх споживачів, і memo цього не зупиняє. Мемоїзуйте value або діліть контекст на кілька дрібніших

Кейс: Дані, потрібні багатьом компонентам на різній глибині: тема, поточний користувач, локаль, feature flags.

ThemeContext.jsx
const ThemeContext = createContext(null);

function App() {
  const [theme, setTheme] = useState('dark');
  // без useMemo новий об'єкт на кожен рендер App → ре-рендер УСІХ споживачів
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeContext value={value}><Toolbar /></ThemeContext>; // React 19: без .Provider
}

function ThemeButton() {
  const { theme, setTheme } = useContext(ThemeContext);
  return <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>{theme}</button>;
}

Контекст — це механізм доставки, а не state manager. Для часто змінних даних (позиція курсора, введений текст) краще Zustand/Redux із селекторами, бо контекст не вміє оновлювати лише тих, кому потрібна конкретна частина значення.

Refs
useRef
Мутабельна «коробка» { current }: DOM-вузол, id таймера, попереднє значенняЗміна .current не викликає ре-рендер. Не читайте й не пишіть ref під час рендеру, лише в ефектах і обробниках

Кейс: Доступ до DOM (фокус, скрол, вимір), зберігання id таймера, WebSocket чи попереднього значення, тобто всього, що має пережити рендер, але не повинно його викликати.

SearchBox.jsx
function SearchBox({ onSearch }) {
  const inputRef = useRef(null);
  const timerRef = useRef(null);

  const onChange = e => {
    clearTimeout(timerRef.current);                              // debounce без жодного ре-рендеру
    timerRef.current = setTimeout(() => onSearch(e.target.value), 300);
  };

  return (
    <>
      <input ref={inputRef} onChange={onChange} />
      <button onClick={() => inputRef.current.focus()}>Фокус</button>
    </>
  );
}

React 19: ref-callback може повертати функцію очищення: ref={node => { observer.observe(node); return () => observer.unobserve(node); }}.

useImperativeHandle
Обмежити, що батьківський компонент бачить через ref: { focus, reset } замість усього DOM-вузлаУ React 19 ref — звичайний проп, тож forwardRef більше не потрібен. Це аварійний вихід; зазвичай краще керувати через пропси

Кейс: Компонент бібліотеки (плеєр, модалка, поле з маскою) має дати батькові кілька методів (play(), open(), focus()), але не весь DOM-вузол.

VideoPlayer.jsx
// React 19: ref приходить звичайним пропом, forwardRef не потрібен
function VideoPlayer({ src, ref }) {
  const videoRef = useRef(null);

  useImperativeHandle(ref, () => ({
    play:  () => videoRef.current.play(),
    pause: () => videoRef.current.pause(),
  }), []);

  return <video ref={videoRef} src={src} />;
}

function Lesson() {
  const player = useRef(null);
  return (
    <>
      <VideoPlayer ref={player} src="/intro.mp4" />
      <button onClick={() => player.current.play()}>▶</button> {/* батько бачить лише play/pause */}
    </>
  );
}

Якщо те саме можна виразити пропсом (isPlaying, isOpen), краще пропс: декларативний стан легше тестувати й синхронізувати.

Ефекти
useEffect
Синхронізація із зовнішнім світом: підписки, запити, таймериЗапускається після малювання кадру. Функція очищення викликається перед наступним запуском і при unmount. У StrictMode в dev ефект навмисно запускається двічі

Кейс: Синхронізація із системою поза React: WebSocket, підписка на подію, сторонній віджет (карта, графік), document.title.

RouteTracker.jsx
function RouteTracker({ routeId }) {
  const [position, setPosition] = useState(null);

  useEffect(() => {
    const ws = new WebSocket(`wss://api.example/routes/${routeId}`);
    ws.onmessage = e => setPosition(JSON.parse(e.data));
    return () => ws.close();   // cleanup: перед наступним запуском і при unmount
  }, [routeId]);               // перепідписка лише коли змінився routeId

  return <Map position={position} />;
}

Коли ефект НЕ потрібен: для похідних даних (порахуйте під час рендеру), для реакції на клік (робіть в обробнику), для завантаження даних (TanStack Query / Server Components). Подвійний запуск у StrictMode перевіряє, що cleanup справді все прибирає.

useLayoutEffect
Виміряти DOM і змінити його до того, як користувач побачить кадрСинхронний і блокує малювання (див. тему 14). На сервері не виконується

Кейс: Спливаюча підказка чи дропдаун, який має виміряти себе й стати в правильну позицію до того, як користувач побачить кадр.

Tooltip.jsx
function Tooltip({ targetRect, children }) {
  const ref = useRef(null);
  const [top, setTop] = useState(0);

  useLayoutEffect(() => {
    const { height } = ref.current.getBoundingClientRect(); // вимір DOM
    setTop(targetRect.top - height - 8);                    // синхронно, до малювання кадру
  }, [targetRect]);

  return <div ref={ref} style={{ position: 'fixed', top }}>{children}</div>;
}

Зі звичайним useEffect користувач на мить побачив би підказку в позиції top: 0, а потім стрибок. Усе, що виконується в useLayoutEffect, блокує малювання, тому робота там має бути мінімальною.

useInsertionEffect
Вставити <style> до того, як спрацюють layout-ефектиЛише для авторів CSS-in-JS бібліотек. Ні стану, ні refs усередині

Кейс: Лише всередині CSS-in-JS бібліотек (styled-components, Emotion), щоб динамічні <style> потрапили в DOM раніше, ніж layout-ефекти почнуть вимірювати елементи.

useCss.js — код бібліотеки
function useCss(rule) {
  useInsertionEffect(() => {
    const style = document.createElement('style');
    style.textContent = rule;
    document.head.appendChild(style); // стилі вже є, коли спрацює будь-який useLayoutEffect
    return () => style.remove();
  }, [rule]);
}

У прикладному коді цей хук вам майже напевно не знадобиться. На співбесіді достатньо знати порядок: insertion → layout → (малювання) → effect.

useEffectEvent 19.2
Функція для ефекту, яка завжди бачить свіжі пропси/стан, але не є залежністю ефектуПрибирає класичну дилему «додати в deps і отримати зайвий перезапуск або не додати й отримати застарілі дані». Викликати лише всередині ефектів, не передавати іншим компонентам

Кейс: Ефект має реагувати на одні значення (roomId), але лише читати свіжі інші (theme, вміст кошика), не перезапускаючись через них. Типові випадки: аналітика, нотифікації, колбеки з пропсів усередині підписок.

ChatRoom.jsx — React 19.2
import { useEffect, useEffectEvent } from 'react';

function ChatRoom({ roomId, theme }) {
  // завжди бачить найсвіжіший theme, але НЕ є реактивною залежністю
  const onConnected = useEffectEvent(() => {
    showNotification('Підключено!', theme);
  });

  useEffect(() => {
    const conn = createConnection(roomId);
    conn.on('connected', () => onConnected());
    conn.connect();
    return () => conn.disconnect();
  }, [roomId]); // theme тут немає: перемикання теми НЕ перепідключає чат
}
Page.jsx — аналітика
function Page({ url, cartCount }) {
  const onVisit = useEffectEvent(visitedUrl => logVisit(visitedUrl, cartCount));

  useEffect(() => {
    // лог при зміні url; зміна cartCount лог НЕ викликає,
    // але в лог потрапить її актуальне значення
    onVisit(url);
  }, [url]);
}

Раніше vs тепер: до 19.2 було два погані варіанти. Можна було додати theme у deps і отримати перепідключення при кожній зміні теми, або вимкнути лінтер і отримати застарілий theme (stale closure). Ще був костиль із useRef + ref.current = theme. Обмеження: викликати лише з ефектів, не під час рендеру й не передавати в інші компоненти. eslint-plugin-react-hooks знає, що такі функції не є залежностями.

Продуктивність
useMemo
Закешувати результат дорогого обчислення між рендерамиЦе оптимізація, не гарантія: React може скинути кеш. З React Compiler здебільшого не потрібен, бо компілятор мемоїзує сам

Кейс: Дороге обчислення (фільтрація й сортування тисяч рядків, побудова графа), або об'єкт чи масив, який іде в deps іншого хука чи в memo-дитину.

RouteTable.jsx
function RouteTable({ stops, query }) {
  // перераховується лише коли змінились stops або query, а не на кожен ре-рендер
  const visible = useMemo(
    () => stops
      .filter(s => s.name.toLowerCase().includes(query.toLowerCase()))
      .sort((a, b) => a.eta - b.eta),
    [stops, query],
  );
  return <Table rows={visible} />;
}

Спершу виміряйте (React Profiler, console.time): мемоїзація дешевих обчислень лише додає шум. З React Compiler ручні useMemo/useCallback здебільшого не потрібні, бо компілятор розставляє їх сам.

useCallback
Стабільне посилання на функцію, коли вона йде в memo-дитину чи в depsТе саме, що useMemo(() => fn, deps). Без memo на дитині сенсу немає

Кейс: Функція передається в memo-компонент або використовується як залежність іншого хука (useEffect, кастомного хука).

StopList.jsx
const StopRow = memo(function StopRow({ stop, onRemove }) {
  return <li>{stop.name} <button onClick={() => onRemove(stop.id)}>×</button></li>;
});

function StopList({ stops, setStops }) {
  // без useCallback — нова функція на кожен рендер → memo(StopRow) нічого не дає
  const handleRemove = useCallback(id => {
    setStops(prev => prev.filter(s => s.id !== id));
  }, [setStops]);

  return <ul>{stops.map(s => <StopRow key={s.id} stop={s} onRemove={handleRemove} />)}</ul>;
}

useCallback без memo на дитині — марна робота. Функціональне оновлення (prev => …) дозволяє не додавати stops у deps, і функція лишається стабільною.

useTransition
Позначити оновлення як нетермінове: startTransition(() => …) + прапорець isPendingІнтерфейс лишається чуйним, а важкий рендер можна перервати. У 19 startTransition приймає async-функцію (Actions)

Кейс: Перемикання важких вкладок чи фільтрів, де UI не повинен «замерзати», а також async-збереження з індикатором (React 19 Actions).

RouteTabs.jsx — нетермінове оновлення
function RouteTabs() {
  const [tab, setTab] = useState('map');
  const [isPending, startTransition] = useTransition();

  // важкий рендер нової вкладки можна перервати, кнопки лишаються чуйними
  const select = next => startTransition(() => setTab(next));

  return (
    <>
      <TabButtons onSelect={select} dimmed={isPending} />
      {tab === 'map' ? <HeavyMap /> : <StopsTable />}
    </>
  );
}
SaveButton.jsx — React 19: async Action
function SaveButton({ route }) {
  const [error, setError] = useState(null);
  const [isPending, startTransition] = useTransition();

  const save = () => startTransition(async () => {
    const err = await saveRoute(route);             // isPending = true до кінця запиту
    startTransition(() => setError(err ?? null));   // setState після await — знову обгорнути
  });

  return (
    <>
      <button onClick={save} disabled={isPending}>{isPending ? 'Зберігаю…' : 'Зберегти'}</button>
      {error && <p role="alert">{error}</p>}
    </>
  );
}

Transition не робить код швидшим, лише дозволяє React перервати й відкласти рендер. Контрольоване поле вводу в transition не загортають: текст має оновлюватися одразу.

useDeferredValue
«Відстаюча» копія значення: поле вводу оновлюється одразу, важкий список — трохи пізнішеКоли немає доступу до місця, де викликається setState. Другий аргумент (з 19) — початкове значення для першого рендеру

Кейс: Пошук із миттєвим полем вводу й важким списком результатів, коли ви не контролюєте місце виклику setState (значення прийшло пропсом).

StopSearch.jsx
function StopSearch({ stops }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);   // «відстає» від query під час набору
  const isStale = query !== deferredQuery;

  return (
    <>
      {/* поле оновлюється одразу */}
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <div style={{ opacity: isStale ? 0.5 : 1 }}>
        {/* список ре-рендериться з низьким пріоритетом */}
        <SlowList stops={stops} query={deferredQuery} />
      </div>
    </>
  );
}

// ОБОВ'ЯЗКОВО memo: інакше SlowList ре-рендериться разом з батьком на кожну літеру
const SlowList = memo(function SlowList({ stops, query }) { /* важкий рендер */ });

На відміну від debounce, тут немає фіксованої затримки: на швидкому пристрої список оновиться майже одразу, на повільному пізніше, а незавершений рендер буде перервано новим вводом.

Форми та Actions (React 19)
useActionState 19
Стан, що оновлюється результатом action: [state, formAction, isPending]Передаєте formAction у <form action>, і pending та помилки обробляються без ручних useState. Працює із Server Actions

Кейс: Форма зі збереженням на сервер, де потрібні результат (помилка валідації чи успіх) і стан очікування. Працює як із клієнтськими функціями, так і з Server Actions.

DepotForm.jsx — React 19
import { useActionState } from 'react';

// action отримує ПОПЕРЕДНІЙ стан і FormData, повертає новий стан
async function createDepot(prevState, formData) {
  const name = formData.get('name');
  if (!name) return { error: "Назва обов'язкова", name };

  const res = await fetch('/api/depots', { method: 'POST', body: formData });
  if (!res.ok) return { error: 'Не вдалося зберегти', name };
  return { error: null, name: '' };
}

function DepotForm() {
  const [state, formAction, isPending] = useActionState(createDepot, { error: null, name: '' });

  return (
    <form action={formAction}>
      <input name="name" defaultValue={state.name} />
      <button disabled={isPending}>{isPending ? 'Зберігаю…' : 'Створити'}</button>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}

Раніше vs тепер: раніше це були три useState (дані, помилка, loading) + onSubmit з e.preventDefault() + try/finally. Тепер стан очікування, послідовність відправок і результат бере на себе React. Після успішного action React 19 сам скидає неконтрольовані поля форми. З Server Action ('use server') форма працює навіть до завантаження JS (progressive enhancement).

useOptimistic 19
Показати результат одразу, поки запит ще йде (лайк, нове повідомлення)Оптимістичне значення живе лише під час transition/action і саме відкочується до реального стану після завершення чи помилки

Кейс: Лайки, додавання повідомлення в чат, перемикачі, перетягування елементів, тобто дії, які майже завжди вдаються, тож чекати відповіді сервера — зайва затримка для користувача.

LikeButton.jsx — React 19
import { useOptimistic, startTransition } from 'react';

function LikeButton({ liked, onToggle }) {
  const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);

  const toggle = () => startTransition(async () => {
    setOptimisticLiked(!optimisticLiked);  // UI змінюється миттєво
    await onToggle(!optimisticLiked);      // запит; батько оновить liked
  });  // після завершення показується справжній liked, а при помилці — автоматичний відкат

  return <button onClick={toggle}>{optimisticLiked ? '♥' : '♡'}</button>;
}
Messages.jsx — з функцією оновлення
function Messages({ messages, sendMessage }) {
  const [optimistic, addOptimistic] = useOptimistic(
    messages,
    (current, text) => [...current, { id: crypto.randomUUID(), text, sending: true }],
  );

  async function action(formData) {       // form action уже є transition
    const text = formData.get('text');
    addOptimistic(text);
    await sendMessage(text);
  }

  return (
    <>
      {optimistic.map(m => <p key={m.id} style={{ opacity: m.sending ? 0.5 : 1 }}>{m.text}</p>)}
      <form action={action}><input name="text" /></form>
    </>
  );
}

Раніше vs тепер: раніше доводилось вручну зберігати попередній стан, міняти його й відкочувати в catch. Тепер оптимістичне значення «живе» лише поки триває transition, а потім React сам повертає справжнє з пропсів. Викликати сеттер можна лише всередині transition чи action, інакше React видасть попередження.

useFormStatus 19
Дізнатися pending/data батьківської форми з дочірнього компонента (кнопки Submit)Імпортується з react-dom. Бачить лише <form>, що рендериться вище в дереві, а не форму в тому самому компоненті

Кейс: Перевикористовувана кнопка Submit у дизайн-системі, яка сама знає, що форма відправляється, без прокидання isPending через пропси.

SubmitButton.jsx — React 19
import { useFormStatus } from 'react-dom';

function SubmitButton({ children }) {
  const { pending, data } = useFormStatus();   // статус найближчої БАТЬКІВСЬКОЇ <form>
  return (
    <button type="submit" disabled={pending}>
      {pending ? `Надсилаю ${data?.get('name') ?? ''}…` : children}
    </button>
  );
}

function VehicleForm() {
  return (
    <form action={createVehicle}>
      <input name="name" />
      <SubmitButton>Додати авто</SubmitButton>   {/* всередині form — працює */}
    </form>
  );
}

Типова помилка: викликати useFormStatus() у тому самому компоненті, що рендерить <form>. Він завжди поверне pending: false, бо бачить лише форму вище себе в дереві. Також повертає method і action.

Інше
use 19
Прочитати Promise (з Suspense) або контекстЄдиний, який можна викликати в умовах і циклах. Promise не можна створювати під час рендеру: його має передати батько, Server Component чи кеш, інакше вийде нескінченний цикл

Кейс: Читання даних, які батько чи Server Component почав вантажити заздалегідь (streaming у Next.js), а також умовне читання контексту.

RoutePage.jsx — React 19
import { use, Suspense } from 'react';

// Server Component (або батько) СТВОРЮЄ Promise і передає вниз, не чекаючи на нього
export default function RoutePage({ id }) {
  const routePromise = fetchRoute(id);
  return (
    <Suspense fallback={<Spinner />}>
      <RouteDetails routePromise={routePromise} />
    </Suspense>
  );
}

function RouteDetails({ routePromise }) {
  const route = use(routePromise);   // поки Promise pending — показується fallback
  return <h1>{route.name}</h1>;
}

// контекст можна читати після раннього return — useContext так не можна
function Hint({ show }) {
  if (!show) return null;
  const theme = use(ThemeContext);
  return <p className={theme}>Підказка</p>;
}

Головна пастка: не створюйте Promise у тому ж клієнтському компоненті, що викликає use. Кожен рендер створить новий Promise, і вийде нескінченний цикл suspend. Promise має прийти ззовні (пропс, Server Component, кеш бібліотеки). Відхилений Promise потрапляє в найближчий Error Boundary. У try/catch хук use загортати не можна.

useId
Унікальний стабільний id для htmlFor/aria-*Однаковий на сервері й клієнті, тому немає помилок гідратації. Не для key у списках

Кейс: Зв'язати <label> з <input> і aria-describedby у перевикористовуваному компоненті, який може бути на сторінці кілька разів, зокрема з SSR.

Field.jsx
function Field({ label, hint }) {
  const id = useId();   // унікальний і однаковий на сервері та клієнті
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} aria-describedby={`${id}-hint`} />
      <p id={`${id}-hint`}>{hint}</p>
    </>
  );
}

Math.random() чи лічильник модуля дали б різні id на сервері й клієнті, а отже помилку гідратації. Для key у списках useId не підходить: ключ має походити з даних.

useSyncExternalStore
Безпечна підписка на зовнішній стор (Redux, Zustand, matchMedia, navigator.onLine)Захищає від «tearing», коли частини UI показують різні версії стану під час конкурентного рендеру. getSnapshot має повертати те саме посилання, якщо дані не змінились

Кейс: Підписка на джерело даних поза React: браузерні API (navigator.onLine, matchMedia, localStorage з інших вкладок) або власний стор. Саме на ньому побудовані Redux і Zustand.

useOnlineStatus.js
// subscribe поза компонентом → стабільне посилання, без перепідписки на кожен рендер
function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

export function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,
    () => navigator.onLine,  // getSnapshot — на клієнті
    () => true,              // getServerSnapshot — для SSR
  );
}

function SyncBadge() {
  const online = useOnlineStatus();
  return <span>{online ? '🟢 Онлайн' : '🔴 Офлайн — зміни в черзі'}</span>;
}

getSnapshot має повертати те саме значення, якщо дані не змінились. () => ({ ...store }) щоразу створює новий об'єкт, і це призведе до нескінченного ре-рендеру. Навіщо не просто useEffect + useState: під час конкурентного рендеру стор може змінитися посередині, і різні компоненти покажуть різні версії даних (tearing).

useDebugValue
Підпис кастомного хука в React DevToolsЛише для DevTools, у продакшені ні на що не впливає

Кейс: Бібліотечні кастомні хуки, де в DevTools корисно одразу бачити їхній поточний стан.

useOnlineStatus.js
function useOnlineStatus() {
  const online = useSyncExternalStore(subscribe, () => navigator.onLine);
  useDebugValue(online ? 'Online' : 'Offline');   // DevTools: OnlineStatus: "Online"
  return online;
}

// дорого форматувати? другий аргумент — функція, викликається лише коли DevTools відкриті
useDebugValue(date, d => d.toISOString());

У звичайних компонентах і дрібних хуках це зайве.
