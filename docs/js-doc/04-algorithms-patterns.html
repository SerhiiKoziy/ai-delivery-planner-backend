Живе розв'язання алгоритмічних задач під час екрана

Це найконкретніший сигнал із реального фідбеку: труднощі виникали саме в процесі кодингу під спостереженням, навіть у людей з роками практичного досвіду. Причина рідко в тому, що людина "не знає алгоритмів" у принципі — щоденна робота з фреймворками рідко вимагає писати цикли з нуля, обходити масив вручну чи тримати в голові два вказівники одночасно. Ці навички атрофуються без регулярної практики, а на співбесіді додається ще й тиск часу, спостереження та вербалізації думок уголос — усе одразу, чого немає в щоденній роботі.

Другий фактор — сама форма задачі. У реальній роботі ви рідко розв'язуєте задачу "з чистого аркуша" без документації, автодоповнення й можливості погуглити сигнатуру методу. На інтерв'ю це середовище зникає, і виявляється, що саме навичка працювати без цих милиць — окрема навичка, яку варто тренувати окремо, а не сподіватись, що вона сама собою випливе з досвіду.

Практична порада не в тому, щоб "порішати більше задач", а в тому, щоб тренувати саме умови співбесіди: розв'язувати із таймером, без підказок редактора, проговорюючи підхід уголос ще до того, як почали писати код, і свідомо стартувати з "тупого", але робочого рішення (brute force), а вже потім оптимізувати — а не намагатись одразу вигадати ідеальний алгоритм і застрягати.

приклад: two pointers
// Задача: чи є в відсортованому масиві дві пари, що в сумі дають target?
function hasPairWithSum(sortedArr, target) {
  let left = 0;
  let right = sortedArr.length - 1;

  while (left < right) {
    const sum = sortedArr[left] + sortedArr[right];
    if (sum === target) return true;
    if (sum < target) left++;   // сума замала — рухаємо лівий вказівник праворуч
    else right--;               // сума завелика — рухаємо правий вказівник ліворуч
  }
  return false;
}
🎯
Чому цей приклад типовий: two pointers на відсортованому масиві — O(n) замість наївних O(n²) вкладених циклів. Уміння одразу впізнати "тут підійде два вказівники" замість перебору всіх пар — саме та навичка розпізнавання патернів, яку тренує регулярна практика.

Складність алгоритмів: Big O

Найпоширеніший теоретичний пробіл — думати лише про час виконання, забуваючи про пам'ять.

Складність алгоритму насправді вимірюють двома окремими вимірами: Time Complexity (TC) — як зростає кількість операцій зі зростанням розміру вхідних даних n, і Space Complexity (SC) — як зростає обсяг додаткової пам'яті, яку алгоритм використовує понад самі вхідні дані. Дуже часто на співбесіді людина впевнено називає TC і зовсім забуває, що в того самого алгоритму може бути зовсім інша SC — нижче побачимо конкретний приклад, де вони навіть відрізняються за порядком величини.

O(1) — константна

Кількість операцій не залежить від розміру вхідних даних узагалі:

O(1)
function firstElement(arr) {
  return arr[0]; // одна операція незалежно від довжини arr
}

O(n) — лінійна

Один прохід по всіх елементах — кількість операцій росте прямо пропорційно розміру входу:

O(n)
function printAll(arr) {
  for (let i = 0; i < arr.length; i++) {
    console.log(arr[i]);
  }
}

O(log n) — логарифмічна

Найлегше запам'ятати через аналогію з тортом: якщо торт довжиною 16 см розрізати навпіл, потім кожну половину знову навпіл — за 4 розрізи (k = 4) дійдемо до шматочків довжиною 1 см, бо 16 = 2⁴, тобто log₂16 = 4. Кожен крок алгоритму відкидає половину залишку роботи — так само працює бінарний пошук (розділ 6 нижче) і висота збалансованого дерева (розділ 3):

O(log n) — скільки разів можна поділити навпіл
function halvingSteps(n) {
  let steps = 0;
  while (n > 1) {
    n = Math.floor(n / 2); // щоразу відкидаємо половину залишку
    steps++;
  }
  return steps; // приблизно log2(n)
}

O(n²) — квадратична

Вкладені цикли по тому самому входу — типова "наївна" перша версія рішення:

O(n²)
function hasDuplicate(arr) {
  for (let i = 0; i < arr.length; i++) {
    for (let j = i + 1; j < arr.length; j++) {
      if (arr[i] === arr[j]) return true;
    }
  }
  return false;
}

O(n log n) — лінійно-логарифмічна

Класичний приклад — сортування злиттям (повна реалізація — у розділі 5 нижче): масив рекурсивно ділиться навпіл (log n рівнів вкладеності), а на кожному рівні всі елементи проходять через об'єднання (O(n) роботи на рівень) — разом O(n log n).

O(n log n) — форма рекурсії сортування злиттям
function mergeSort(arr) {
  if (arr.length <= 1) return arr;
  const mid = Math.floor(arr.length / 2);
  const left = mergeSort(arr.slice(0, mid));
  const right = mergeSort(arr.slice(mid));
  return merge(left, right); // O(n) на кожному рівні злиття, log n рівнів → O(n log n)
}
⚠️
Ось де TC і SC розходяться: сортування злиттям має TC O(n log n), але SC — O(n), бо на кожному рівні рекурсії створюються нові допоміжні масиви (slice, результат merge) — на відміну від, наприклад, сортування бульбашкою, яке повільніше за TC (O(n²)), зате сортує "на місці" з SC O(1). Один із двох вимірів ніколи не варто оцінювати "за замовчуванням" через інший.

O(2ⁿ) — експоненційна

Наївна рекурсивна послідовність Фібоначчі без запам'ятовування — кожен виклик розгалужується ще на два виклики, і дерево викликів росте експоненційно (детальніше — розділ 4 нижче):

O(2ⁿ)
function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2); // кожен виклик породжує ще два
}

O(n!) — факторіальна

Найгірший поширений рівень — генерація всіх перестановок множини з n елементів:

O(n!)
function permutations(arr) {
  if (arr.length <= 1) return [arr];
  const result = [];
  for (let i = 0; i < arr.length; i++) {
    const rest = [...arr.slice(0, i), ...arr.slice(i + 1)];
    for (const perm of permutations(rest)) {
      result.push([arr[i], ...perm]);
    }
  }
  return result; // n! перестановок для n елементів
}

Базові структури даних

Не йдеться про вміння реалізувати кожну структуру з нуля щодня — йдеться про рівень "розумію, коли яка структура доречна і чому", щоб швидко вибрати правильний інструмент замість того, щоб робити все через масив і лінійний пошук.

На практиці найчастіша "прихована" структура даних у JS — саме об'єкт/Map як хеш-мапа: величезна частка задач на кшталт "знайти дублікати" чи "порахувати частоту елементів" розв'язується за O(n) саме заміною лінійного пошуку в масиві на один прохід з хеш-мапою.

Масив і зв'язний список

Масив зберігається в послідовних комірках пам'яті — саме тому доступ за індексом arr[i] коштує O(1): рушій просто обчислює адресу комірки. Зв'язний список, навпаки, складається з вузлів, розкиданих у пам'яті довільно, кожен з яких зберігає посилання на наступний — щоб дістатись до i-го елемента, доведеться пройти всі попередні (O(n)), зате вставка нового вузла, коли посилання на місце вставки вже є в руках, коштує O(1) — не потрібно зсувати весь масив праворуч, як довелось би для масиву.

мінімальний зв'язний список
function createNode(value, next = null) {
  return { value, next };
}

class LinkedList {
  constructor() {
    this.head = null;
  }
  insertAtHead(value) {
    this.head = createNode(value, this.head); // O(1) — просто перепідключаємо посилання
  }
}

Стек і черга

В JS обидві найпростіше реалізувати через звичайний масив: стек (LIFO) — це push/pop з одного кінця; черга (FIFO) — це push з одного кінця й shift з іншого.

⚠️
Нюанс, який видає рівень: Array.prototype.shift() у JS — це O(n), а не O(1), бо рушій змушений перенумерувати індекси всіх елементів, що лишились. Для навчальних прикладів (як BFS нижче) це прийнятно, але у справді продуктивному коді з великою чергою для O(1)-видалення з початку варто використовувати іншу структуру (наприклад, чергу на основі зв'язного списку або двох стеків).

Дерево та бінарне дерево пошуку (BST)

У бінарному дереві пошуку для кожного вузла всі значення в лівому піддереві менші за нього, а в правому — більші. Це дає пошук/вставку за O(log n) — якщо дерево збалансоване. Класична пастка: якщо вставляти вже відсортовані дані одне за одним у звичайний BST без балансування, дерево вироджується у зв'язний список — і всі операції зісковзують до O(n). Саме тому в продуктивному коді використовують самобалансувальні дерева (AVL, red-black), а не наївний BST.

BST: вставка й обхід in-order
function insertBST(node, value) {
  if (node === null) return { value, left: null, right: null };
  if (value < node.value) node.left = insertBST(node.left, value);
  else node.right = insertBST(node.right, value);
  return node;
}

function inOrder(node, out = []) {
  if (node === null) return out;
  inOrder(node.left, out);
  out.push(node.value);           // ліве піддерево → сам вузол → праве піддерево
  inOrder(node.right, out);
  return out;                     // дає відсортований порядок для BST
}

Хеш-таблиця зсередини

Під капотом хеш-функція перетворює ключ на індекс "відра" (bucket) у внутрішньому масиві. Колізія — коли два різні ключі хешуються в те саме відро — розв'язується одним із двох способів: ланцюжки (separate chaining) — кожне відро тримає невеликий список усіх записів, що в нього потрапили, і при колізії новий запис просто додається в цей список; відкрита адресація (open addressing) — при колізії алгоритм шукає наступне вільне відро за визначеним правилом (наприклад, наступне по порядку) і кладе запис туди. В обох випадках багато колізій псують заявлений O(1) — деталі дивіться в питанні про це в розділі 9.

Граф і обхід (BFS/DFS)

Граф найчастіше представляють списком суміжності — для кожної вершини зберігають масив сусідів. "Напишіть BFS/DFS з нуля" — один із найпоширеніших запитів на живому кодингу:

граф як список суміжності + BFS і DFS
const graph = new Map([
  ['A', ['B', 'C']],
  ['B', ['D']],
  ['C', ['D']],
  ['D', []],
]);

function bfs(start) {
  const visited = new Set([start]);
  const queue = [start];
  const order = [];
  while (queue.length) {
    const node = queue.shift();       // черга — обходимо "вшир", рівень за рівнем
    order.push(node);
    for (const neighbor of graph.get(node)) {
      if (!visited.has(neighbor)) {
        visited.add(neighbor);
        queue.push(neighbor);
      }
    }
  }
  return order;
}

function dfs(start, visited = new Set(), order = []) {
  visited.add(start);
  order.push(start);
  for (const neighbor of graph.get(start)) {
    if (!visited.has(neighbor)) dfs(neighbor, visited, order); // рекурсія — обходимо "вглиб"
  }
  return order;
}
🎯
Коли який обхід: BFS гарантує найкоротший шлях у зваженому однаково (unweighted) графі, бо обходить рівень за рівнем — тому пошук найкоротшого шляху майже завжди BFS, а не DFS. DFS природніше лягає на задачі "перебрати всі можливі шляхи/варіанти" (backtracking) чи виявити цикли й топологічне сортування.

Рекурсія на практиці

Будь-яка рекурсивна функція складається з двох частин: базового випадку (умова, коли рекурсія зупиняється й повертає значення напряму, без подальших викликів) і рекурсивного випадку (виклик тієї самої функції з "меншим" підзавданням, що наближає нас до базового випадку). Забутий або неправильно сформульований базовий випадок — найчастіша причина нескінченної рекурсії й переповнення стека.

Наївний рекурсивний Фібоначчі з розділу 2 — хрестоматійний приклад того, як відсутність запам'ятовування вже обчисленого перетворює задачу на експоненційну: fib(5) обчислює fib(3) двічі, fib(2) — тричі, і так далі. Рішення — мемоізація: кешувати результат кожного унікального виклику, щоб порахувати його рівно один раз.

Фібоначчі з мемоізацією: O(2ⁿ) → O(n)
function fibMemo(n, cache = new Map()) {
  if (n <= 1) return n;
  if (cache.has(n)) return cache.get(n);       // уже рахували — беремо готове
  const result = fibMemo(n - 1, cache) + fibMemo(n - 2, cache);
  cache.set(n, result);                        // запам'ятовуємо перед поверненням
  return result;
}

Це і є найпростіший приклад динамічного програмування у форматі "згори вниз" (memoization) — той самий результат можна порахувати й "знизу вгору" (tabulation), заповнюючи масив результатів ітеративно від базового випадку; різниця між цими двома стилями — типове питання на співбесіді (розділ 10).

⚠️
JS-специфічна пастка: на відміну від деяких мов, рушії JavaScript (V8 у Chrome/Node включно) не гарантують оптимізацію хвостових викликів (tail call optimization) — навіть якщо технічно специфікація ES2015 її дозволяє. Це означає, що глибока рекурсія в JS реально ризикує впертись у справжній RangeError: Maximum call stack size exceeded, і "переписати рекурсію в цикл" — це не стилістична забаганка, а іноді єдиний коректний production-варіант, навіть якщо рекурсивна версія виглядає чистіше. На співбесіді варто прямо показувати, що ви це розумієте.

Сортування: що варто знати

Не варто тримати в голові реалізацію десятка алгоритмів сортування — практичний мінімум для співбесіди вужчий: розуміти, у якому "тарифному класі складності" лежить кожен поширений алгоритм, уміти чисто реалізувати рівно один із них, і знати, коли в реальному коді взагалі не варто писати сортування самостійно.

АлгоритмСередній випадокНайгірший випадокПам'ять
Бульбашкове / сортування вставками / виборомO(n²)O(n²)O(1) — на місці
Сортування злиттям (merge sort)O(n log n)O(n log n)O(n) — допоміжні масиви
Швидке сортування (quicksort)O(n log n)O(n²)O(log n) — стек рекурсії

"Наївний" рівень (бульбашкове, вставками, вибором) рідко просять написати повністю — але варто впевнено пояснити, чому кожне з них O(n²): усі вони, у тій чи іншій формі, порівнюють кожен елемент з кожним іншим через вкладені цикли.

Сортування злиттям — найкращий вибір для повної реалізації на співбесіді, бо воно напряму ілюструє межу TC/SC, яку ми обговорили в розділі 2:

повна реалізація merge sort
function mergeSort(arr) {
  if (arr.length <= 1) return arr;
  const mid = Math.floor(arr.length / 2);
  const left = mergeSort(arr.slice(0, mid));
  const right = mergeSort(arr.slice(mid));
  return merge(left, right);
}

function merge(left, right) {
  const result = [];
  let i = 0, j = 0;
  while (i < left.length && j < right.length) {
    if (left[i] <= right[j]) result.push(left[i++]);
    else result.push(right[j++]);
  }
  // долити залишок того масиву, який ще не вичерпався
  return [...result, ...left.slice(i), ...right.slice(j)];
}

Швидке сортування (quicksort) у середньому також O(n log n), і на місці (менше пам'яті, ніж merge sort), але з важливим нюансом: якщо наївно завжди обирати опорний елемент (pivot) як перший або останній елемент, на вже відсортованому вхідному масиві алгоритм деградує до O(n²) — кожен розподіл ділить масив на "порожню" і "усе інше" частини замість приблизно навпіл. Практичне рішення — обирати pivot випадково або як медіану з трьох кандидатів, що робить деградацію статистично малоймовірною.

✅
Практична порада на щодень: у реальному production-коді майже завжди достатньо вбудованого Array.prototype.sort(). Його точна реалізація не фіксована специфікацією (у V8 це гібрид, близький до Timsort/сортування злиттям для великих масивів і сортування вставками для малих), але з ES2019 специфікація гарантує, що воно стабільне (елементи з однаковим ключем сортування зберігають відносний порядок). Уміння розпізнати, коли варто написати власне сортування (нетипова логіка порівняння, навчальний контекст, конкретна вимога до пам'яті), а коли просто викликати .sort() і не переізобретати колесо — саме та ознака, яку шукають у senior-кандидата більше, ніж вміння продекламувати псевдокод quicksort напам'ять.
🟡

Пошук: бінарний пошук

Класичний O(log n) пошук у відсортованому масиві: на кожному кроці порівнюємо середній елемент діапазону з ціллю і відкидаємо ту половину діапазону, де цілі точно немає — та сама ідея "ділення навпіл", що й у розділі 2.

бінарний пошук — ітеративна версія
function binarySearch(sortedArr, target) {
  let low = 0;
  let high = sortedArr.length - 1;

  while (low <= high) {
    const mid = Math.floor((low + high) / 2);
    if (sortedArr[mid] === target) return mid;
    if (sortedArr[mid] < target) low = mid + 1;   // ціль правіше — відкидаємо ліву половину
    else high = mid - 1;                          // ціль лівіше — відкидаємо праву половину
  }
  return -1; // не знайдено
}

Навмисно ітеративна, а не рекурсивна версія — жодного ризику переповнення стека (розділ 4) і на практиці саме такий варіант очікують у більшості команд.

⚠️
Головна умова, яку часто забувають вголос згадати: бінарний пошук працює лише на відсортованих даних — на невідсортованому масиві весь алгоритм неспроможний. Класичне ускладнення, яке інтерв'юер запитує одразу після базової версії: "а як знайти перше (або останнє) входження, якщо значення в масиві дублюється?" — відповідь: замість негайного return mid при збігу, запам'ятати позицію і продовжити звужувати пошук у потрібний бік (ліворуч для першого входження, праворуч для останнього), поки діапазон не вичерпається.

Патерни для живого кодингу: two pointers, sliding window, monotonic stack, backtracking

Це не окремі алгоритми, а іменовані патерни — і саме вміння одразу впізнати назву патерна за формою задачі (а не винаходити підхід з нуля щоразу) відрізняє впевнене живе розв'язання від тривалого перебору варіантів під тиском часу.

Two pointers

Two pointers на відсортованому масиві вже з'являвся в розділі 1 (перевірка пари із заданою сумою). Той самий прийом узагальнюється: два вказівники сходяться з протилежних кінців масиву, і на кожному кроці порівняння суми з ціллю однозначно каже, який вказівник рухати — замість O(n²) перебору всіх пар маємо O(n) за один прохід.

two-sum на відсортованому масиві
function twoSumSorted(sortedArr, target) {
  let left = 0;
  let right = sortedArr.length - 1;
  while (left < right) {
    const sum = sortedArr[left] + sortedArr[right];
    if (sum === target) return [left, right];
    if (sum < target) left++;
    else right--;
  }
  return null;
}

Природне розширення — 3Sum (знайти трійку з нульовою сумою): зафіксувати один елемент у зовнішньому циклі й запустити той самий two-pointer пошук по решті масиву для двох інших — O(n²) замість наївного O(n³) перебору всіх трійок.

Sliding window

Коли задача про "суму/кількість елементів у безперервному фрагменті масиву", наївний підхід — для кожного початку фрагмента заново рахувати суму, O(n·k). Sliding window уникає цього: вікно фіксованого розміру зсувається на одну позицію за раз, додаючи новий елемент праворуч і віднімаючи той, що випав зліва — сума перераховується за O(1) на крок замість перерахунку всього вікна.

максимальна сума вікна фіксованого розміру k
function maxSumSubarray(arr, k) {
  let windowSum = 0;
  for (let i = 0; i < k; i++) windowSum += arr[i];

  let maxSum = windowSum;
  for (let i = k; i < arr.length; i++) {
    windowSum += arr[i] - arr[i - k]; // +новий елемент, -той, що випав з вікна
    maxSum = Math.max(maxSum, windowSum);
  }
  return maxSum;
}

Наступний рівень — вікно змінного розміру (наприклад, "найменший фрагмент із сумою не менше target"): вікно розширюється вправо, поки умова не виконається, а тоді стискається зліва, поки умова тримається — той самий дух "не перераховувати з нуля", але межі вікна рухаються незалежно одна від одної, а не синхронно.

Monotonic stack

Класична задача "для кожного елемента масиву знайти найближчий справа більший за нього" наївно розв'язується за O(n²) (для кожного елемента — окремий прохід праворуч). Прийом monotonic stack зводить це до одного проходу: у стеку тримаємо індекси елементів, для яких відповідь ще не знайдена, і щойно зустрічаємо елемент, більший за той, що на верхівці стека — це і є відповідь для нього, тож знімаємо його зі стека.

next greater element — O(n) замість O(n²)
function nextGreaterElement(arr) {
  const result = new Array(arr.length).fill(-1);
  const stack = []; // індекси елементів, чия відповідь ще невідома

  for (let i = 0; i < arr.length; i++) {
    while (stack.length && arr[stack[stack.length - 1]] < arr[i]) {
      const idx = stack.pop();
      result[idx] = arr[i]; // arr[i] — перший більший елемент справа для arr[idx]
    }
    stack.push(i);
  }
  return result;
}
🎯
Чому це "пастка": рішення O(n) тут неочевидне з першого погляду — здається нелогічним, що один прохід взагалі може дати відповідь для кожного елемента. Саме тому це популярна задача для перевірки: чи бачили ви цей патерн раніше, а не чи вмієте писати цикли.

Backtracking

Основна ідея, без якої не обійтись у задачах на кшталт перестановок, N-ферзів чи судоку: спробувати варіант → рекурсивно піти далі → якщо це нікуди не веде, відкотити вибір і спробувати наступний. Кожен рівень рекурсії — це один "вибір", а відкат (backtrack) — це просто повернення з рекурсивного виклику й видалення щойно зробленого вибору перед тим, як спробувати інший.

перестановки масиву — класичний backtracking
function permute(arr) {
  const result = [];

  function backtrack(path, remaining) {
    if (remaining.length === 0) {
      result.push(path);
      return;
    }
    for (let i = 0; i < remaining.length; i++) {
      const next = [...remaining.slice(0, i), ...remaining.slice(i + 1)];
      backtrack([...path, remaining[i]], next); // спробувати
      // "відкат" тут неявний: remaining[i] просто не потрапляє в наступну ітерацію циклу
    }
  }

  backtrack([], arr);
  return result;
}

На співбесіді зазвичай достатньо впізнати назву патерна й пояснити ідею "спробувати — рекурсія — відкат" на прикладі (перестановки або N-ферзі) — рідко очікують повну оптимізовану реалізацію судоку-солвера з нуля за 20 хвилин.

🔴

Дизайн-принципи в щоденній роботі, а не в теорії

Формулювання принципів SOLID/KISS/DRY назубок — недостатньо. У реальному фідбеку питання звучало саме як "де і чому ви це застосували", і саме тут очікується конкретний приклад коду з рефакторингом, а не визначення з підручника.

Single Responsibility — до/після
// До: один клас робить валідацію, форматування і мережевий запит одночасно
class UserForm {
  submit(data) {
    if (!data.email.includes('@')) throw new Error('bad email');
    const payload = { ...data, email: data.email.trim().toLowerCase() };
    return fetch('/api/users', { method: 'POST', body: JSON.stringify(payload) });
  }
}

// Після: кожна відповідальність — окрема функція/клас, легко тестувати ізольовано
function validateEmail(email) {
  if (!email.includes('@')) throw new Error('bad email');
}
function normalizeUser(data) {
  return { ...data, email: data.email.trim().toLowerCase() };
}
class UserApi {
  submit(payload) {
    return fetch('/api/users', { method: 'POST', body: JSON.stringify(payload) });
  }
}

Open/Closed на практиці найчастіше проявляється як заміна довгого if/else чи switch по типу на мапу обробників — новий тип додається новим записом у мапі, без правки існуючого коду:

Open/Closed — мапа обробників замість switch
// До: щоб додати новий тип сповіщення, треба міняти саму функцію
function renderNotification(type, data) {
  if (type === 'email') return renderEmail(data);
  if (type === 'sms') return renderSms(data);
  // ще один if для кожного нового типу...
}

// Після: додавання нового типу не чіпає існуючий код
const renderers = {
  email: renderEmail,
  sms: renderSms,
};
function renderNotification(type, data) {
  return renderers[type](data);
}

DRY — не "жодного повторення коду будь-якою ціною", а усунення дублювання саме знання: якщо та сама бізнес-правило (наприклад, формула розрахунку знижки) продубльоване в трьох місцях, зміна правила вимагає пам'ятати про всі три — і рано чи пізно одне забудуть оновити.

🎯
Що перевіряють: здатність розпізнати ці ситуації у власному реальному коді й розповісти конкретний кейс — а не переказати визначення абревіатури SOLID.
🟡

Патерни проєктування у JS/фронтенді + Dependency Injection

Чотири патерни, які найчастіше зустрічаються у фронтенд-коді, кожен коротким ідіоматичним прикладом:

Module — інкапсуляція через closure/ES-модуль
// Приватний стан, доступний лише через експортований інтерфейс
let counter = 0;
export function increment() { return ++counter; }
export function getCount() { return counter; }
Singleton — один спільний екземпляр
let instance = null;
class ApiClient {
  static getInstance() {
    if (!instance) instance = new ApiClient();
    return instance;
  }
}
Observer — підписка на події
class EventBus {
  #listeners = new Map();
  on(event, cb) {
    if (!this.#listeners.has(event)) this.#listeners.set(event, []);
    this.#listeners.get(event).push(cb);
  }
  emit(event, payload) {
    (this.#listeners.get(event) || []).forEach(cb => cb(payload));
  }
}
Factory — створення об'єктів без прив'язки до конкретного класу
function createShape(type) {
  if (type === 'circle') return { area: r => Math.PI * r * r };
  if (type === 'square') return { area: s => s * s };
  throw new Error(`Unknown shape: ${type}`);
}

Dependency Injection — принцип, за яким об'єкт отримує свої залежності ззовні (як параметр конструктора чи функції), а не створює їх сам усередині. Це ключове для тестованості: замінити реальну залежність на тестовий мок можна без зміни коду самого класу, лише передавши інший об'єкт при створенні. У великих TS-застосунках цю відповідальність часто бере на себе DI-контейнер — бібліотека, що сама розв'язує ланцюжок залежностей за метаданими (декораторами), а не вручну через кожен конструктор. inversify.js — типовий приклад такого контейнера для JS/TS, вартий принаймні поверхового знайомства навіть без досвіду використання в проді.

Найчастіші питання про алгоритми на співбесіді

Ці 12 питань покривають переважну більшість того, що реально запитують на живому кодингу — від класики із зв'язними списками до практичних компромісів між алгоритмами.

База Пастка Просунуте Системний дизайн
01БазаРозверніть однозв'язний список

Класична ітеративна "танцювальна" схема з трьома вказівниками: prev, curr, next. На кожному кроці зберігаємо посилання на наступний вузол перед тим, як перезаписати curr.next — інакше втратимо решту списку.

reverseList
function reverseList(head) {
  let prev = null;
  let curr = head;
  while (curr !== null) {
    const next = curr.next;   // запам'ятати "далі" ДО перезапису
    curr.next = prev;
    prev = curr;
    curr = next;
  }
  return prev; // нова голова списку
}
02ПросунутеЯк визначити, чи є в зв'язному списку цикл?

Алгоритм Флойда ("черепаха і заєць"): два вказівники рухаються по списку з різною швидкістю — slow на один крок, fast на два. Якщо в списку є цикл, вони рано чи пізно зустрінуться в одній і тій самій точці всередині циклу; якщо циклу немає, fast дійде до null першим. Ключова перевага перед альтернативою (класти відвідані вузли в Set) — O(1) додаткової пам'яті замість O(n).

hasCycle — Floyd's cycle detection
function hasCycle(head) {
  let slow = head;
  let fast = head;
  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) return true; // зустрілись — цикл є
  }
  return false;
}
03БазаЗнайдіть середину зв'язного списку за один прохід

Той самий трюк повільного/швидкого вказівника з попереднього питання, тільки без перевірки на зустріч: коли fast доходить до кінця, slow опиняється рівно посередині — за один прохід, замість того щоб спершу порахувати довжину, а потім пройти список удруге.

findMiddle
function findMiddle(head) {
  let slow = head;
  let fast = head;
  while (fast !== null && fast.next !== null) {
    slow = slow.next;
    fast = fast.next.next;
  }
  return slow; // середина (або друга з двох середніх при парній довжині)
}
04БазаПеревірте, чи правильно розставлені дужки в рядку

Класична ілюстрація того, навіщо взагалі потрібен стек: кожна відкривна дужка кладеться на стек, кожна закривна має "закрити" останню відкриту того самого типу — тобто верхівку стека. Якщо в кінці стек не порожній або в якийсь момент типи не збіглись — рядок невалідний.

isValid — валідні дужки через стек
function isValid(s) {
  const stack = [];
  const pairs = { ')': '(', ']': '[', '}': '{' };
  for (const ch of s) {
    if (ch === '(' || ch === '[' || ch === '{') {
      stack.push(ch);
    } else if (stack.pop() !== pairs[ch]) {
      return false; // закривна дужка не збіглась з верхівкою стека
    }
  }
  return stack.length === 0; // усі відкриті дужки мають бути закриті
}
05ПасткаTwo Sum — чому наївне рішення O(n²), і як звести до O(n)?

Наївний підхід перебирає всі пари чисел вкладеними циклами — O(n²). Ключове спостереження: для кожного числа nums[i] потрібне саме число target - nums[i] — і якщо зберігати вже переглянуті числа в хеш-мапі "значення → індекс", перевірка "чи бачили ми вже потрібне доповнення" коштує O(1), а весь алгоритм — O(n) за один прохід.

twoSum — O(n) через хеш-мапу
function twoSum(nums, target) {
  const seen = new Map(); // значення → індекс
  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];
    if (seen.has(complement)) return [seen.get(complement), i];
    seen.set(nums[i], i);
  }
  return null;
}
🎯 Що перевіряють: чи назвете ви обидва варіанти й свідомо поясните компроміс — O(n²) без додаткової пам'яті проти O(n) ціною O(n) пам'яті на хеш-мапу — а не одразу вискочите з "оптимальним" рішенням, не показавши, що розумієте, від чого саме воно рятує.
06БазаBFS чи DFS — як обрати?

BFS обходить граф "рівень за рівнем" через чергу — і саме тому гарантовано знаходить найкоротший шлях у графі з однаковою вагою ребер: перший момент, коли ви дійшли до цільової вершини, і є найкоротшим шляхом. DFS занурюється "вглиб" одним маршрутом через рекурсію чи явний стек — природний вибір для задач "перебрати всі можливі варіанти" (backtracking), виявлення циклів чи топологічного сортування, де важливо дослідити повний маршрут, а не найкоротшу відстань.

07БазаСкладність основних структур даних — швидкий чек-лист

Масив: O(1) доступ за індексом, O(n) пошук за значенням. Зв'язний список: O(n) доступ/пошук, O(1) вставка/видалення за наявним посиланням на вузол. Стек/черга: O(1) на всі основні операції (окрім Array.shift() у JS — див. розділ 3 вище). Хеш-мапа: O(1) у середньому на пошук/вставку, O(n) у найгіршому разі (питання 9 нижче). Збалансоване дерево: O(log n) на пошук/вставку; незбалансоване в найгіршому разі — O(n).

08ПросунутеQuicksort проти merge sort — коли який обирати?

Merge sort гарантує O(n log n) завжди, незалежно від вхідних даних, ціною O(n) додаткової пам'яті й того, що це не сортування "на місці" (in-place). Quicksort у середньому теж O(n log n) і сортує на місці (O(log n) пам'яті на стек рекурсії), але має гірший найгірший випадок O(n²) на невдало підібраному pivot (розділ 5) і, на відміну від merge sort, зазвичай нестабільний (не гарантує збереження порядку рівних елементів). Вибір: потрібна гарантія найгіршого випадку чи стабільність — merge sort; критична економія пам'яті на великих масивах і прийнятний ризик рідкісного найгіршого випадку — quicksort.

09ПасткаЧому пошук у хеш-мапі, "O(1) за визначенням", інколи насправді O(n)?

Заявлений O(1) — це середній випадок за умови рівномірного розподілу ключів по "відрах" (buckets). Якщо хеш-функція погана або (в гіршому теоретичному випадку, навмисно) багато різних ключів хешуються в те саме відро, для стратегії з ланцюжками (розділ 3) пошук у переповненому відрі вироджується в лінійний перебір списку — O(n) у найгіршому випадку. Це не теоретична дрібниця: саме тому в деяких мовах хеш-мапи додають захист від навмисних "hash flooding" атак на бекенді, що приймає ключі від користувача.

10ПасткаЧому глибока рекурсія в JS може впасти навіть на "правильному" алгоритмі?

Як уже згадано в розділі 4: рушії JavaScript не гарантують оптимізацію хвостових викликів, тож кожен рекурсивний виклик додає новий кадр на стек викликів. На достатньо великому вході (наприклад, рекурсивний обхід зв'язного списку з мільйоном вузлів) це реально впирається в RangeError: Maximum call stack size exceeded — незалежно від того, наскільки коректна логіка. Правильна відповідь у такому випадку — переписати рекурсію в цикл або використати явний стек (масив) замість стека викликів мови.

11Системний дизайнМемоізація проти табуляції — у чому різниця?

Обидві — форми динамічного програмування, що уникають повторного розрахунку тих самих підзадач, але з протилежним напрямком: мемоізація ("згори вниз") — це звичайна рекурсія плюс кеш, яка рахує підзадачі лише тоді, коли вони реально знадобились (як fibMemo у розділі 4); табуляція ("знизу вгору") — ітеративне заповнення масиву результатів від базового випадку до потрібного значення, без рекурсії взагалі, а отже без ризику переповнення стека з попереднього питання. Табуляція зазвичай трохи ефективніша за пам'яттю й повністю уникає ризику стека, зате мемоізація часто читається природніше, бо напряму повторює структуру задачі.

12Системний дизайн"Climbing stairs" — канонічна найпростіша DP-задача. Як її розв'язати?

Умова: скількома способами можна піднятись на n сходинок, якщо дозволено робити крок на 1 або на 2 сходинки за раз. Ключове спостереження — кількість способів дійти до сходинки n дорівнює сумі способів дійти до n-1 (а потім зробити крок на 1) і до n-2 (а потім крок на 2) — тобто це буквально послідовність Фібоначчі в новому вбранні. Це і є суть DP-мислення: розпізнати, що задача зводиться до комбінації менших підзадач того самого типу, а не вигадувати рішення з нуля щоразу.
