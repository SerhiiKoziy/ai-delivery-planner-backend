Utility types

Усі приклади нижче трансформують один і той самий тип, щоб було видно саме різницю між утилітами, а не форму даних:

базовий тип для всіх прикладів
interface User {
  id: string;
  name: string;
  email: string;
  age: number;
}

Pick<T, K> і Omit<T, K>

Pick будує новий тип лише з переліченого набору властивостей T. Omit — дзеркальна протилежність: усі властивості T, крім перелічених. Обирайте Pick, коли простіше перелічити "що лишити" (коротка публічна форма з великого типу); Omit — коли простіше перелічити "що прибрати" (наприклад, повний тип мінус поле, яке генерується сервером).

Pick vs Omit
type UserPreview = Pick;
// { id: string; name: string }

type UserWithoutId = Omit;
// { name: string; email: string; age: number }

Partial<T> і Required<T>

Partial робить кожну властивість необов'язковою — класичне застосування: функція оновлення, що приймає лише ті поля, які реально змінюються, а не весь об'єкт цілком. Required — протилежність: робить обов'язковою навіть ту властивість, що в оригінальному типі була позначена як опційна (?).

Partial у функції оновлення
function updateUser(id: string, patch: Partial) {
  // patch може містити будь-яку підмножину полів User,
  // включно з порожнім об'єктом {}
}

updateUser('1', { name: 'Нове імʼя' }); // ок, інші поля не потрібні

Readonly<T>

Робить кожну властивість тільки для читання — повторне присвоєння викликає помилку компіляції. Важливий нюанс, який часто забувають: Readonly — поверхневий (shallow). Якщо всередині T є вкладений об'єкт, сам вкладений об'єкт лишається повністю мутабельним — Readonly захищає лише властивості верхнього рівня.

Readonly — поверхневий, не глибокий
interface Profile { user: User; }
const p: Readonly = { user: { id: '1', name: 'A', email: 'a@a.com', age: 20 } };

p.user = { ...p.user }; // ПОМИЛКА компіляції — user readonly
p.user.name = 'B';      // ✅ компілюється без помилок — вкладений User не readonly

Record<K, V>

Будує тип об'єкта, де всі ключі мають тип K, а всі значення — тип V. Найкорисніше або для простого словника (Record<string, number>), або коли набір ключів — фіксована унія рядкових літералів, і компілятор може перевірити, що жоден ключ не забуто:

Record із фіксованим набором ключів
type Role = 'admin' | 'user' | 'guest';

const roleLabels: Record = {
  admin: 'Адміністратор',
  user: 'Користувач',
  guest: 'Гість',
  // забутий ключ тут дав би помилку компіляції ще ДО рантайму
};

ReturnType<T>

Витягує тип значення, яке повертає функція, — замість того щоб описувати цей тип окремо і вручну синхронізувати обидва місця щоразу, коли функція змінюється. Особливо корисно, коли сама функція — єдине джерело правди про форму даних (наприклад, фабрика чи парсер), а тип результату описувати окремо було б дублюванням знання.

ReturnType замість ручного дублювання типу
function createUser(name: string) {
  return { id: crypto.randomUUID(), name, createdAt: new Date() };
}

type CreatedUser = ReturnType;
// { id: string; name: string; createdAt: Date } — виведено автоматично,
// зміна createUser() автоматично оновить і цей тип

Exclude<T, U> і Extract<T, U>

Обидві працюють над union-типами. Exclude прибирає з T усі члени, що присвоювані до U. Extract — дзеркальна протилежність: залишає лише ті члени T, що присвоювані до U.

Exclude vs Extract на одній унії — симетрія видна одразу
type Status = 'idle' | 'loading' | 'success' | 'error';

type NotIdle = Exclude;
// 'loading' | 'success' | 'error'

type Finished = Extract;
// 'success' | 'error'

any vs unknown

any вимикає перевірку типів повністю — можна викликати будь-який метод, звернутись до будь-якої властивості, присвоїти будь-де, і компілятор мовчить у всіх випадках. По суті це спосіб сказати компілятору: "довірся мені, більше не перевіряй". unknown — типобезпечний аналог: теж може містити будь-яке значення, але компілятор забороняє будь-яку дію над ним, доки значення не буде звужене (через type guard, typeof, instanceof чи явне приведення типу).

те саме дозволено з any, заборонено з unknown
function handleAny(data: any) {
  console.log(data.toUpperCase()); // компілюється — і впаде в рантаймі, якщо data не рядок
}

function handleUnknown(data: unknown) {
  console.log(data.toUpperCase()); // ПОМИЛКА компіляції: 'data' is of type 'unknown'

  if (typeof data === 'string') {
    console.log(data.toUpperCase()); // ✅ ок — тип звужено до string усередині if
  }
}

Практичне правило: використовуйте unknown для дійсно невідомих зовнішніх даних (розпарсена відповідь API, значення, спіймане в catch) — компілятор сам не дасть забути перевірку форми даних перед використанням. any лишайте як свідомий крайній засіб, а не зручність за замовчуванням — кожен any у коді є "дірою" в системі типів, яку компілятор більше не перевіряє.

⚠️
Найчастіша помилка новачків: ловити помилку як catch (e: any) "щоб компілятор не заважав" — правильніше catch (e: unknown) і звузити тип (e instanceof Error) перед зверненням до e.message, бо в JS/TS можна кинути буквально будь-яке значення, не обов'язково Error.

Type Guards

Type guard — це перевірка в рантаймі, яку компілятор TypeScript розпізнає як сигнал звузити тип значення в коді, що йде після неї.

typeof — для примітивів

typeof guard
function double(value: number | string) {
  if (typeof value === 'number') {
    return value * 2; // тут value звужено до number
  }
  return value + value; // тут — до string
}

instanceof — для екземплярів класів

instanceof guard
class ApiError extends Error {}

function handle(err: unknown) {
  if (err instanceof ApiError) {
    // тут err звужено до ApiError — доступні його специфічні поля/методи
  }
}

Оператор in — розрізнення членів унії за наявністю поля

in guard
type Circle = { kind: 'circle'; radius: number };
type Square = { kind: 'square'; side: number };

function area(shape: Circle | Square) {
  if ('radius' in shape) {
    return Math.PI * shape.radius ** 2; // звужено до Circle
  }
  return shape.side ** 2; // звужено до Square
}

Власний type guard через предикат is

Функція, що просто повертає boolean, для компілятора — звичайний булевий результат, який не звужує тип виклику навіть якщо логіка всередині фактично перевіряє форму значення. Синтаксис x is User у сигнатурі повернення — саме те, що каже компілятору довіряти цій функції як справжньому звужувачу типу.

власний type guard з предикатом is
function isUser(x: unknown): x is User {
  return (
    typeof x === 'object' && x !== null &&
    'id' in x && 'email' in x
  );
}

function greet(x: unknown) {
  if (isUser(x)) {
    console.log(`Привіт, ${x.name}`); // x звужено до User саме завдяки "x is User"
  }
}
🎯
Що перевіряють: чи розумієте ви, що звичайна функція, яка повертає boolean (без предиката is), НЕ звузить тип у виклику — компілятор бачить лише boolean і не "заглядає" всередину логіки функції.

enum vs const enum

Звичайний enum компілюється у справжній JS-об'єкт у рантаймі — з прямим і зворотним мапінгом ключ↔значення для числових enum. Це реальний артефакт: додатковий згенерований код, додаткова вага бандла, і щось, що бандлер справді має обробити. const enum натомість повністю стирається на етапі компіляції — кожне використання інлайниться прямо як літеральне значення, без жодного рантайм-об'єкта і без жодного впливу на розмір бандла.

той самий enum — дві компіляції
enum Direction {
  Up,
  Down,
}
// компілюється приблизно в:
// var Direction; (function (Direction) {
//   Direction[Direction["Up"] = 0] = "Up";
//   Direction[Direction["Down"] = 1] = "Down";
// })(Direction || (Direction = {}));

const enum ConstDirection {
  Up,
  Down,
}
const d = ConstDirection.Up;
// компілюється в: const d = 0; — жодного обʼєкта ConstDirection у рантаймі взагалі немає
⚠️
Практичне застереження: const enum вимагає повної інформації про типи на етапі збірки — у пайплайнах, де файли транспілюються ізольовано одне від одного без повного type-checking прохід (наприклад, лише через Babel без TypeScript-компілятора), const enum може не працювати коректно. Саме тому частина команд свідомо уникає enum узагалі — і замість цього використовує просту унію рядкових літералів: type Direction = 'up' | 'down' | 'left' | 'right', яка теж не має рантайм-вартості (union-тип існує лише на етапі компіляції), але без жодних обмежень пайплайна.

Питання для співбесіди

Практичні запитання на матеріал вище — від базових визначень до нюансів, які плутають навіть досвідчених кандидатів.

База Пастка Просунуте Системний дизайн
01БазаУ чому різниця між Pick і Omit?

Pick<T, K> залишає лише перелічені властивості K з T. Omit<T, K> — навпаки, залишає все, крім перелічених. Обирайте залежно від того, що коротше перелічити: список "що лишити" чи список "що прибрати".

02ПасткаЧому Readonly<T> іноді "не захищає" дані так, як очікувалось?

Бо Readonly — поверхневий (shallow): він захищає лише властивості верхнього рівня самого T. Якщо всередині є вкладений обʼєкт, цей вкладений обʼєкт лишається повністю мутабельним — присвоєння нового значення властивості верхнього рівня заборонене, а мутація вкладеного обʼєкта "в обхід" — ні.

03БазаНавіщо ReturnType<T>, якщо можна просто написати тип результату вручну?

Щоб уникнути дублювання знання: якщо функція — єдине джерело правди про форму результату, ручний тип поруч із нею рано чи пізно розійдеться з реальністю, щойно функцію зміняли, а тип забули оновити. ReturnType<typeof fn> завжди автоматично синхронний із реальним типом, який функція справді повертає.

04Системний дизайнНавіщо взагалі потрібен unknown, якщо any вже дозволяє робити що завгодно?

any дає свободу ціною повного вимкнення перевірки типів — компілятор довіряє коду сліпо. unknown дає ту саму гнучкість "може містити будь-що", але змушує явно довести (через звуження типу), що саме там міститься, перш ніж щось робити з значенням. Це різниця між "вимкнути захист" і "захист, який просто вимагає спочатку перевірити" — для зовнішніх/ненадійних даних друге майже завжди правильніший дефолт.

05ПасткаЧому функція, що повертає boolean, не звужує тип так, як isUser(x): x is User?

Компілятор бачить лише оголошений тип повернення функції. Якщо це просто boolean — компілятор знає тільки "функція повернула true чи false", і не має підстав пов'язати цей факт зі звуженням типу аргументу, навіть якщо логіка всередині фактично перевіряє форму значення. Синтаксис-предикат x is User — це явна декларація для компілятора: "якщо ця функція повернула true, вважай x типу User далі по коду".

06БазаЧим typeof-guard відрізняється від instanceof-guard?

typeof перевіряє примітивні типи рантайму ("string", "number", "boolean", "object", "undefined" тощо) і працює для примітивів та функцій. instanceof перевіряє, чи є значення екземпляром конкретного класу (через ланцюжок прototype) — доречний для розрізнення класів, зокрема кастомних підкласів Error.

07ПросунутеЩо насправді генерує звичайний числовий enum у скомпільованому JS — і чому це має значення?

Звичайний числовий enum генерує обʼєкт із двостороннім мапінгом: і Direction.Up === 0, і Direction[0] === "Up" одночасно працюють. Це означає реальний рантайм-обʼєкт у бандлі — на відміну від const enum, який повністю зникає, залишаючи лише інлайнені літерали в місцях використання.

08ПросунутеЧому деякі команди уникають const enum і навіть enum узагалі?

const enum вимагає, щоб компілятор мав повну інформацію про типи під час компіляції кожного файлу — у пайплайнах, де файли транспілюються ізольовано без повного проходу тайпчекера (типово при транспіляції лише через Babel без TypeScript-компілятора в цьому кроці), це може працювати некоректно або взагалі заборонятись інструментом. Практична альтернатива без цих обмежень і без рантайм-вартості — проста унія рядкових літералів (type Direction = 'up' | 'down'), яка теж повністю стирається на етапі компіляції, але не покладається на спеціальну підтримку const enum конкретним інструментом збірки.
