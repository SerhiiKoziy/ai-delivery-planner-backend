Юніт-тестування (Jest/RTL), лінтери, CI/CD пайплайни

Цей блок уже підтверджений як сильна сторона в реальних технічних інтерв'ю: досвід написання юніт-тестів через Jest і React Testing Library, налаштування лінтерів та інших інструментів якості коду, робота з CI/CD-пайплайнами — усе це не потребує додаткового форсування підготовки саме на рівні "чи вмію я це робити".

Наступний рівень запиту на співбесідах — не "чи писали ви тести", а чи можете ви впевнено розповісти про побудову CI-пайплайна з нуля: не лише роботу у вже готовому пайплайні, а усвідомлення послідовності стадій і того, навіщо кожна з них існує саме в цьому порядку — лінт і тайпчек мають провалитись раніше й дешевше, ніж збірка; збірка — раніше й дешевше, ніж деплой.

приклад: типові стадії CI-пайплайна
stages:
  - lint        # ESLint/Prettier — найшвидша й найдешевша перевірка, провалюємось тут першими
  - typecheck   # tsc --noEmit — ловить помилки типів ще до запуску будь-якого коду
  - test        # unit-тести (Jest) — швидкі, ізольовані, без реальної мережі/БД
  - build       # production-збірка (напр. next build / vite build)
  - deploy      # публікація build-артефактів на CDN (напр. S3 + CloudFront, Vercel, Netlify)
💡
Чому саме такий порядок: кожна наступна стадія дорожча за часом і ресурсами за попередню — немає сенсу чекати на повну збірку (хвилини), щоб дізнатись про забуту крапку з комою, яку лінтер знайшов би за секунди. Провал "дешево і рано" — принцип, а не формальність.

E2E-тестування глибше

На відміну від юніт-рівня, досвід з end-to-end тестуванням виявився обмеженішим — а це саме той рівень тестів, що перевіряє реальний користувацький сценарій через увесь стек: UI, роутинг, мережеві запити, разом узяті, а не одну ізольовану функцію чи компонент.

Практично варто розібрати один інструмент — Cypress або Playwright — на рівні структури тесту: arrange (підготувати стан, відкрити сторінку), act (виконати дії користувача — клік, ввід тексту), assert (перевірити результат у вже відрендереному DOM реального застосунку, що працює в реальному чи headless-браузері).

приклад: структура E2E-тесту (Playwright-подібний синтаксис)
test('користувач бачить створену доставку у списку', async ({ page }) => {
  // arrange
  await page.goto('/deliveries')

  // act
  await page.getByRole('button', { name: 'Додати доставку' }).click()
  await page.getByLabel('Адреса').fill('вул. Хрещатик, 1')
  await page.getByRole('button', { name: 'Зберегти' }).click()

  // assert
  await expect(page.getByText('вул. Хрещатик, 1')).toBeVisible()
})

Ключова практична проблема E2E-тестів — мережеві залежності й нестабільність (flaky tests). Якщо тест б'є в реальний бекенд, він стає повільним і залежним від чужого стану (даних у тестовій БД, доступності стороннього сервісу); тому мережеві запити зазвичай мокають на рівні браузера (перехоплення запитів), лишаючи реальним лише сам фронтенд. Нестабільність найчастіше походить від тестів, що покладаються на фіксовані затримки (sleep/setTimeout) замість очікування конкретної умови — сучасні інструменти (Cypress, Playwright) вирішують це вбудованим auto-waiting: асершн сам повторює спробу, поки елемент не з'явиться або не мине таймаут, замість одноразової перевірки одразу після фіксованої паузи.

Моніторинг і трекінг помилок у продакшені

Конкретного досвіду з інструментами на кшталт Sentry чи Datadog не було зафіксовано — хоча базовий принцип роботи таких систем варто розуміти навіть без глибокого практичного досвіду, бо питання про них дедалі частіше зустрічається саме як "а як ви дізнаєтесь про помилку користувача, якого ви фізично не бачите".

Механізм у Sentry (і подібних інструментів) простий і важливий: вони підписуються на глобальні браузерні обробники — window.onerror для необроблених синхронних помилок і window.onunhandledrejection для промісів, які впали, але їхній .catch() ніхто не написав. Це означає, що помилка потрапляє в моніторинг автоматично, навіть якщо розробник явно її ніде не залогував.

приклад: чому необроблений reject не завжди "тихий"
fetchUserProfile().then(profile => render(profile))
// якщо fetchUserProfile() впаде, а .catch() не додано —
// це "unhandled promise rejection": користувач нічого не побачить,
// але window.onunhandledrejection його зловить і надішле в Sentry
⚠️
Source maps — не опційна деталь. Мінімізований продакшн-код (одна літера замість імені змінної, стиснуті рядки) робить сирий стек-трейс майже нечитабельним. Source map — файл-відповідність між мінімізованим кодом і оригінальним — дозволяє моніторингу показати справжні імена файлів, функцій і номери рядків з вихідного коду, замість a.js:1:48213.

Це напряму пов'язано з темою async-помилок із категорії Core JS (1): помилка, тихо загублена всередині ланцюжка промісів без явного .catch() чи try/catch навколо await, не дійде ані до користувача, ані до моніторингу як щось зрозуміле — вона повинна бути явно "піднята на поверхню", а не просто статись.

Базові хмарні сервіси (AWS)

Прямого практичного досвіду з конкретними сервісами AWS не зафіксовано — і мета тут не "вивчити AWS", а мати достатню широту знань, щоб впевнено підтримати розмову про типову інфраструктуру хостингу фронтенд-застосунку, коли про неї запитають.

СервісРоль у типовому фронтенд-стеку
S3Об'єктне сховище — тримає статичні білд-артефакти (HTML/JS/CSS/зображення) як звичайні файли.
CloudFrontCDN перед S3 — кешує ці файли ближче до користувача географічно, зменшуючи латентність завантаження.
Lambda@EdgeКод, що виконується на самих edge-вузлах CloudFront під час запиту — типово для редіректів, підміни заголовків, A/B-логіки ще до того, як запит дійде до основного застосунку.
🎯
Мета цієї теми — не глибока експертиза з AWS, а достатня обізнаність, щоб впевнено підтримати розмову про типову архітектуру хостингу: "статичні файли в S3, роздача через CloudFront, точкова логіка на edge через Lambda@Edge" — цього рівня деталізації зазвичай достатньо.
